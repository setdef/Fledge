# ADR 026: Ruby's Own Answers Hold Inside an App

## Status
Accepted (requested). Agents wrote this ADR and may change it (AGENTS.md, Questions). It applies the maintainer's decisions 9, 10, and 23 in `doc/contributors/decisions.md`: an app's code stays as it was without Fledge, its globals are what a Ruby developer expects, and it needs no branch per operating system. It amends ADR 003, section 5, and lifts the limit ADR 005 and ADR 020 record for a Ruby an app starts under a C locale.

## Date
2026-11-03

## Context

A Ruby developer knows where things are by asking Ruby: `$0` and `__FILE__` for the running script, `__dir__` for its folder, `RbConfig.ruby` for the interpreter, `Gem.dir` for the gems. A program that restarts itself does it with those answers, as Puma's hot restart does (`exec Gem.ruby, $0, ...`; `lib/puma/launcher.rb`, lines 296 to 320 and 404 to 412, at Puma 8.0.2):

```ruby
exec RbConfig.ruby, $0, *ARGV
```

Fledge's answers to these questions should be Ruby's own and true, so that no app needs a constant of Fledge's, an environment variable, or a branch for a built app. The `experiment/path-probe` branch built three probes with Fledge 0.2.1 and its released runtimes (a lone `main.rb`, the same with a Gemfile, and a windowed app), ran each where it was built and on a fresh runner of every desktop platform, and had each restart itself twice, three ways: with `exec RbConfig.ruby, $0`, by running its own launcher again, and with `RbConfig.ruby` after clearing every Ruby variable (CI run 41747218312, every job green, its artifacts the report). It ran each in a clean environment, in a person's (`LANG`, `RUBYOPT=-W0`, `RUBYLIB`, `GEM_HOME`), in Delivery's hostile one, and in a C locale, from a folder named `My Apps/Ünïcödé 日本`. Every answer Ruby gave before a restart was true. A restart through `RbConfig.ruby` broke five ways:

1. **The person's Ruby settings reach the restarted app.** `RbConfig.ruby` is the runtime's `bin/ruby`, Ruby's own `main.c` (ADR 003, section 2), which hides nothing from Ruby's boot. The launcher put the person's `RUBYOPT`, `RUBYLIB`, `GEM_HOME`, and `BUNDLER_SETUP` back before the app ran (ADR 003, section 3), so the restart booted with them: a `RUBYLIB` file shadowed the runtime's `json`, a hostile `BUNDLER_SETUP` raised a `LoadError`, on every platform.
2. **The restart reads the app's folder as US-ASCII.** The launcher turns a bare C locale into a UTF-8 one in its own process only (`fledge_coerce_locale`, `runtime/launcher/locale.c`, called from `unix.c`'s `main`). `bin/ruby` calls `setlocale(LC_CTYPE, "")`, as `main.c` does, so in a C locale `$0`, `__FILE__`, and `__dir__` came back US-ASCII with invalid bytes, and for an app with a Gemfile, Bundler's vendored Thor raised "invalid multibyte character" as it loaded, on macOS and glibc Linux.
3. **In a macOS `.app`, `$0` and `__dir__` name different folders.** The launcher is `Contents/MacOS/NAME`, beside links to `../Resources/app` and the rest (`Fledge::MacBundle`, `LINKED`). It ran `ROOT/app/ENTRY` through the link, so `$0` and `__FILE__` named `Contents/MacOS/app/main.rb`, while `__dir__` (which Ruby resolves), `RbConfig::CONFIG["prefix"]`, and `RbConfig.ruby` named `Contents/Resources`. `File.dirname(__FILE__) == __dir__` was false.
4. **On macOS the restarted app loses its bundle.** `bin/ruby` lives in `Contents/Resources/bin`, so after `exec` the process's executable is no longer the bundle's, and `NSBundle.mainBundle` no longer reads the app's `Info.plist`: no identifier, no name in the Dock.
5. **On Windows the restart is a new console process.** `RbConfig.ruby` is RubyInstaller's console `ruby.exe` (ADR 001, section 8), and Ruby's `exec` on Windows starts the program and waits for it (`process.c`, line 1660, calls `rb_w32_uaspawn` with `P_OVERLAY`, and `win32/win32.c`'s `child_result`, lines 1175 to 1190, waits for the child and exits with its status, at Ruby 4.0.9), so a windowed app restarting through it got a console window and lost the AppUserModelID its launcher set.

Running the launcher again had none of these problems on any platform: it hid the person's settings, chose a UTF-8 locale, set up Bundler, and kept the PID and the bundle on macOS and Linux. But an app has no Ruby answer that names its launcher.

## Decision

### 1. bin/ruby chooses its locale as the launcher does

`runtime/launcher/ruby_main.c` calls `fledge_coerce_locale` where Ruby's `main.c` calls `setlocale(LC_CTYPE, "")` (`main.c`, lines 52 to 63 at Ruby 4.0.9), and the runtime links `locale.c` into `bin/ruby` beside it. The function does what `main.c` does and then, as Python does for its own interpreter (PEP 538, "Coercing the legacy C locale to a UTF-8 based locale"), replaces a bare C or POSIX locale with the first UTF-8 locale the system has; a locale the person chose stays theirs. Every Ruby in a runtime now starts in the same locale the launcher gives the app: a restart, a child Ruby (`system(RbConfig.ruby, ...)`), and a gem's executable, whose wrapper in `bin/` runs `bin/ruby`.

A C locale is coerced only when it comes from `LANG` or from no variable at all. An explicit `LC_ALL` or `LC_CTYPE`, `C` included, is left as `ruby` leaves it, so `Encoding.default_external` is then what `ruby` gives. PEP 538 never coerces when `LC_ALL` is set (CPython v3.13.0, `Python/pylifecycle.c`, lines 189 to 194 and 293 to 294) and documents `LC_ALL=C` as the way to keep the C locale. It does coerce an explicit `LC_CTYPE=C`; Fledge does not, because `LC_CTYPE` is the one category Ruby's encoding comes from, and a person who sets it has said which character set they want (AGENTS.md, Design precedence 2 over 4). Until 2026-11-04 the launcher coerced both: ruby/spec's `Encoding.locale_charmap when setting LC_ALL=C` failed in a built app on macOS and glibc Linux (branch `experiment/ruby-spec`, run 41776558621).

PEP 538 also exports `LC_CTYPE`, so that every child process, Python or not, inherits the coerced locale. Fledge does not: the app's `ENV` must be what `ruby main.rb` gives it (ADR 003, section 3; decision 9), and a variable the launcher added would be a difference the parity check fails on. Coercing in each Ruby gives every Ruby the app starts the same locale without it; a program that is not Ruby sees the person's locale, as it would under `ruby main.rb`.

The limit ADR 005 and ADR 020 recorded goes with it: under a C locale, in a folder whose name is not ASCII, a child Ruby in the app's bundle now sets the bundle up. `examples/real_gems` no longer gives its gem's executable `LC_ALL`, and `test/built_app_test.rb` runs the Bundler app's child Rubies with no locale at all.

`ruby_main.c` stays under Ruby's license, since it is Ruby's `main.c` with Fledge's calls in it; `locale.c` is Fledge's own (AGPL-3.0-or-later and commercially licensable), as it is in the launcher, and so is the code section 3 adds, so `bin/ruby` now carries Fledge's code, which decision 8 permits. `runtime/licenses.yml` says so: Fledge's component is compiled into `bin/ruby`, and the license audit finds it there by a string of `relaunch.c`'s.

### 2. In a macOS .app, the app runs from the folder it is really in

The launcher names the app folder by its real path, `realpath(ROOT/app)`, and runs `ENTRY` there, and sets up Bundler with the Gemfile and `.bundle/config` there (`find_app_folder`, `runtime/launcher/unix.c`). In a `.app` that is `Contents/Resources/app`, where Ruby's prefix already is: `$0`, `__FILE__`, `$PROGRAM_NAME`, `__dir__`, `RbConfig::CONFIG["prefix"]`, `RbConfig.ruby`, and `BUNDLE_GEMFILE` all name `Contents/Resources`, and `File.dirname(__FILE__) == __dir__`, as under `ruby`. Ruby resolves links in the main script's real path, from which `__dir__` comes (`ruby.c`, lines 2674 to 2685, at Ruby 4.0.9), and keeps the path it was given for `$0` and `__FILE__`, so the launcher gives it the resolved one. Everywhere else the launcher's folder is already a real path (`fledge_executable_path` resolves it) and `app` a real folder, so nothing changes there, and the parity check, which runs a console app, sees no new difference.

Considered: resolving the whole entry path, which would also resolve a link inside the project, such as `bin/tool` pointing at `../exe/tool`, and make `$0` the link's target where `ruby bin/tool` keeps `bin/tool`; and moving the app out of `Contents/Resources` into `Contents/MacOS`, where Apple's tools expect only code (`Fledge::MacBundle`).

### 3. On macOS and Linux, bin/ruby hands the app's own program back to its launcher

When `bin/ruby`'s first argument is the program a launcher of this app runs, `bin/ruby` runs that launcher in its own place, with `execv`, and the arguments that followed the program (`fledge_relaunch`, `runtime/launcher/relaunch.c`, which `ruby_main.c` calls before anything else). So `exec RbConfig.ruby, $0, *ARGV` runs the launcher again in the same process: it hides the person's Ruby settings from Ruby's boot, chooses the locale, has Bundler set up the app's gems, and puts the settings back, exactly as the first time (ADR 003, section 3; ADR 005). `execv` keeps the PID, and on macOS the launcher is the bundle's own program, so `NSBundle.mainBundle` reads the app's `Info.plist` again. The same holds for `system(RbConfig.ruby, $0, ...)` and `spawn`, which start the app again as a child.

The detection is the smallest one that cannot mistake another script for the app's program:

1. `argv[1]` is not an option (it does not begin with `-`) and names a regular file.
2. `bin/ruby` finds its own real path (`fledge_executable_path`, the launcher's `darwin.c` or `linux.c`), and the runtime is the folder above its `bin`. That folder's `fledge.cfg` is read with the launcher's own reader (`config.c`).
3. The launchers are the regular, executable files (not links) in the runtime's folder, or in a `.app` in `Contents/MacOS`, whose `fledge.cfg` must be the same file as the runtime's (it is a link to it; `Fledge::MacBundle`). For each, `fledge_parse_config` reads its section, by its file name, of an app of several programs (ADR 024), or the whole file for an app of one.
4. The entry that section names, under the runtime's `app/`, is the same file as `argv[1]`, by device and inode, so a relative path, a link, or the path through `Contents/MacOS/app` all match.

What it cannot cover, and so leaves to plain Ruby, as Ruby's own `main.c` would run it:

- **An option before the program**, as in `exec RbConfig.ruby, "--yjit", $0` or `ruby -W0 main.rb`. Ruby's options can take arguments (`-I DIR`, `-r LIB`, `-C DIR`), so finding the script behind them means parsing Ruby's command line as `ruby.c` does; the launcher already fixes the options its app starts with (ADR 003, section 1), and would have to merge them. A program that restarts with options of its own enables them in Ruby instead (`RubyVM::YJIT.enable`, `$VERBOSE`), or clears the person's settings itself. A gem's executable runs `bin/ruby -x`, so it is always plain Ruby, as under `ruby`.
- **Any other script**, such as a helper the app starts with `system(RbConfig.ruby, "worker.rb")`. It runs with the person's Ruby settings, which `ruby worker.rb` on that computer would use too (ADR 003, Consequences), and in an app with a Gemfile in Bundler's environment, as under `bundle exec`.
- **An app of one program with more than one executable file beside its launcher.** `fledge build` puts none there, so the first is the launcher.
- **A runtime whose `fledge.cfg` is missing or unreadable**, or a launcher renamed by hand in an app of several programs, which has no section of its own (ADR 024): `bin/ruby` stays Ruby, as the launcher would refuse to start.

When the launcher is found but `execv` fails, `bin/ruby` says so and exits 70 (EX_SOFTWARE), as the launcher does for a damaged app, rather than run the app as plain Ruby with the person's settings.

Design precedence 2 exists so that Fledge never surprises an app developer with how Ruby, its globals, its built-ins, and its standard library behave, compared with not using Fledge (decisions, 2026-11-02). A developer who writes `exec RbConfig.ruby, $0, *ARGV` expects the app to start again as it started. Before this change it started as plain Ruby, without the setup the first start had, and it failed when the person's settings clashed with the runtime's: that was the surprise. The restart now behaves as the first start does, so the developer meets the same behavior twice. The one deviation it carries, hiding the person's `RUBYOPT`, `RUBYLIB`, and `GEM_HOME` from the app's boot, is the deviation the first start already makes under Design precedence 1 and `Parity::JUSTIFIED` records (ADR 003, section 3), so a restart adds no new surprise. The parity check does not see it, because the probe's child Rubies run `-e` code, which stays plain Ruby.

Considered and rejected:

- **A constant or an environment variable naming the launcher**, such as `FLEDGE_LAUNCHER`. The app would need Fledge-specific code to restart, and an `ENV` that differs from `ruby main.rb`'s (decisions 9, 10).
- **`bin/ruby` doing the launcher's work itself**, scrubbing and setting up Bundler when it runs the entry. On macOS the process would still be `Contents/Resources/bin/ruby`, outside the bundle's program, so `NSBundle.mainBundle` would stay lost; and the launcher's work would live in two programs.
- **Making `RbConfig.ruby` name the launcher.** `RbConfig.ruby` must run any script and accept Ruby's options (`system(RbConfig.ruby, "-e", ...)`, which the parity check and RubyGems' own tools do), and the launcher runs only the app.
- **A shell script in `bin/ruby`.** It would cost a process and a shell for every Ruby the app starts, and could not keep the PID through its own `exec` any better than C does.

### 4. On Windows, an app restarts by running its launcher

A Windows runtime keeps RubyInstaller's `ruby.exe` and `rubyw.exe` (ADR 001, section 8), so `RbConfig.ruby` stays RubyInstaller's console `ruby.exe`, and Fledge does not build a `ruby.exe` of its own: RubyInstaller's tree stays whole, as its DLLs and manifests need. Windows has no `exec` that keeps the process: Ruby's `exec` there starts the program and waits for it (section "Context", item 5), so a restart is a new process however it is made. The one that matches the first start is the launcher itself, `NAME.exe`, which a Windows program finds as any Windows program finds its own file, with `GetModuleFileNameW(NULL, ...)` (through Fiddle, as `examples/windowed_app` already calls Windows); the probe did, and in run 41747218312 its restarts that way passed in every environment, the hostile one included, and a windowed probe kept running without a console. Restarting through `RbConfig.ruby` on Windows still boots with the person's Ruby settings, and in a windowed app with a console. This is a limit, written in the help header and the README, not a choice an app has to make on macOS and Linux.

### 5. No constant, no variable

Fledge adds nothing an app reads to find itself. `$0`, `__FILE__`, `__dir__`, `RbConfig.ruby`, `RbConfig::CONFIG["prefix"]`, `Gem.dir`, and `Gem.path` are true inside a built app on every platform, as the probe and the parity check show, and on macOS and Linux `RbConfig.ruby` with `$0` restarts the app as it first started.

## Consequences

- `exec RbConfig.ruby, $0, *ARGV`, `system(RbConfig.ruby, $0, ...)`, and `Gem.ruby` in their place start the app as it first started, on macOS and Linux. `test/built_app_test.rb` restarts the parity probe as a lone script, as a gem-shaped program, and as a macOS `.app`, in a clean, a person's, and a hostile environment, and the probe compares what it sees before and after: the PID, the program the process runs, the main bundle, `$0`, `__FILE__`, `__dir__`, the encodings, `RbConfig.ruby`, `Gem.path`, the loaded gems, `Bundler.original_env`, and `ENV`. Delivery (`.github/scripts/deliver.sh`) runs the same restarts on fresh macOS and Linux runners and in the Debian and Alpine containers, which a trial of this change passed on `experiment/true-paths` (run 41758130321).
- `bin/ruby` reads `fledge.cfg` and the folder beside it when its first argument is a file, before Ruby starts: a few system calls for every Ruby the app starts with a script.
- `bin/ruby` behaves as the launcher does in a C locale, so `Encoding.default_external` is UTF-8 in every Ruby of a runtime that a desktop or `env -i` starts. A person who runs `bin/ruby` by hand with no locale, or with `LANG=C`, gets UTF-8 too, where `ruby` would give US-ASCII. This is a difference from `ruby`, and `Parity::JUSTIFIED` lists it: the parity check runs the probe a second time with no locale variable at all, where the encodings `Encoding.default_external`, `Encoding.find("locale")`, and `Encoding.find("filesystem")` may differ and nothing else may, and twice more under `LC_ALL=C` and `LC_CTYPE=C`, where nothing may.
