> Findings of 2026-11-13 on whether the C locale coercion of ADR 041 can be closed at its source. Requested: written by an agent and not reviewed line by line. ADRs cite these findings by this file.

# The C locale: where stock Ruby fails, and what would close the difference

ADR 041 turns a bare C locale into a UTF-8 one in every Ruby of a runtime. The maintainer accepted it "for now" (decisions, 2026-11-03), then set a bar for every difference (decisions, 2026-11-12): accept it only when it is inherent to where the app ships or a platform truly forbids what Ruby does; "Every difference, every lack of parity, is a knife in Fledge's back." These findings measure what stock Ruby does without the coercion, ask whether the failures could be fixed where they start, and ask whether a desktop really starts an app with no locale. Every page and file below was read on 2026-11-13.

## Verdict

Stock Ruby 4.1.0-preview1 boots in a C locale under a folder named outside ASCII. It does not fail building its load path, as ADR 041 says. What fails is Bundler, three ways, and then the app's own code: in a C locale Ruby gives one folder's path three encodings (BINARY in `$LOAD_PATH`, US-ASCII with invalid bytes in `__dir__`, `$0`, and some of `$LOADED_FEATURES`, and UTF-8 in the rest), and Ruby code that compares or matches them raises.

Each failure could be fixed where it starts, in Ruby and in Bundler. But a Ruby fixed that way still gives the app US-ASCII, and `__dir__ =~ /x/` still raises "invalid byte sequence in US-ASCII", as it does under `env -i ruby main.rb` today. So fixing the failures at their source closes Fledge's own failures, not the difference a person would meet: the app's code and its gems would fail for the person, as stock Ruby does in the same place.

Only one change makes stock `ruby main.rb` give UTF-8 in a C locale: Ruby itself treating the C locale as UTF-8, as CPython has since 3.7 (PEP 540). Ruby did the same for Windows in 3.0 (Feature #16604). Until Ruby does it for the C locale, the difference is inherent to where the app ships: macOS gives a double-clicked app no locale at all, and so do phones.

## 1. Where stock Ruby fails

### How it was measured

Linux, through `machines`: jdx/ruby's Ruby 4.1.0-preview1 for x86_64-linux, which mise installs from `mise.toml`, configured `--enable-load-relative` as rv-ruby's builds are, with RubyGems 4.1.0.beta2 and Bundler 4.0.20 (`require "bundler"`) and 4.1.0.beta2 (`bin/bundle`). Ubuntu 24.04, glibc 2.39, whose `locale -a` lists `C`, `C.utf8`, and `POSIX`. Runs 20261113-151943-9af080 (pc-wsl) and 20261113-152431-9c3b0e (laptop). The probe made a folder `My Apps/Ünïcödé 日本`, put an app in `app/` (a `main.rb`, a `lib/helper.rb` it loads with `require_relative`, and a Gemfile locking `rake` and `paint` 2.3.0 into `vendor/bundle`), copied the whole Ruby into `ruby/` beside it, as a runtime sits inside an app, and ran each case with `env -i PATH=... HOME=...` and again with `LANG=C.UTF-8` added.

On macOS 27.2.1 the C locale's character set is `US-ASCII` (`unset LANG LC_ALL LC_CTYPE; ruby -e 'p Encoding.locale_charmap'` prints `"US-ASCII"`, and `default_external` and `filesystem` are US-ASCII), so Ruby takes the same paths there; this was not run on macOS, but ADR 026's probe (CI run 41747218312) saw Thor's failure on macOS and glibc Linux.

### What happened

With `LANG=C.UTF-8`, every case below passed, but one (`bundle exec ruby`, below).

| Case | No locale |
|---|---|
| Ruby at an ASCII prefix, app in the non-ASCII folder: `ruby main.rb` | Runs. `Encoding.default_external`, `find("locale")`, `find("filesystem")` are US-ASCII. `__dir__` is US-ASCII with invalid bytes; `__dir__ =~ /app/` and `__dir__.split("/")` raise `ArgumentError: invalid byte sequence in US-ASCII`. |
| Same, with the Gemfile: `ruby -rbundler/setup main.rb`, `bundle exec ruby main.rb` | Runs, as above. |
| Ruby inside the non-ASCII folder (Fledge's case): `ruby -e 'require "json"'`, `ruby main.rb`, `rake` | Runs. `$LOAD_PATH` is all BINARY; `__dir__` as above. |
| Ruby inside it: `require "bundler/setup"` | `Encoding::CompatibilityError: incompatible character encodings: US-ASCII and BINARY (ASCII-8BIT)`, in `Bundler::SharedHelpers#clean_load_path`. |
| Ruby inside it: `ruby -rbundler/setup main.rb` | `ArgumentError: invalid multibyte character`, in Bundler's vendored Thor, `thor/command.rb`, line 3, as `Bundler.ui` loads it. |
| Ruby inside it: `bundle -v`, `bundle install --local`, `bundle exec rake` | `Encoding::CompatibilityError: incompatible character encodings: UTF-8 and US-ASCII` in `Bundler::FriendlyErrors.serialized_exception_for`, raised while reporting another error, which it hides. |
| Ruby inside it: `gem list` | Prints `Error loading RubyGems plugin ".../site_ruby/rubygems_plugin.rb": incompatible character encodings: UTF-8 and BINARY (ASCII-8BIT)`, then lists. |

So stock Ruby's own boot survives. Every failure comes when Ruby code puts two path strings together.

### Why: one folder, three encodings

`main.c` (lines 51 to 63) calls `setlocale(LC_CTYPE, "")`. In a C locale `nl_langinfo(CODESET)` is `ANSI_X3.4-1968` on glibc and `US-ASCII` on macOS (`localeinit.c`, lines 56 and 57), so the locale encoding is US-ASCII, and the filesystem encoding follows `default_external` on every Unix (`localeinit.c`, lines 117 to 140, the last `#else`). Ruby then tags the paths it makes in three ways:

- **`$LOAD_PATH`: BINARY.** `ruby_init_loadpath` (`ruby.c`, lines 670 to 767) builds the paths from `dladdr` before encodings exist, as plain strings. After `Init_enc`, `process_options` re-tags each in the locale encoding (`ruby.c`, lines 2546 to 2573) through `copy_str` (lines 2051 to 2059), which keeps a path whose bytes are not valid in that encoding as it was: BINARY. `File.realpath` of one is BINARY too.
- **Features loaded before encodings existed, `__dir__`, `$0`: US-ASCII with invalid bytes.** The same function re-tags the features loaded during boot (`enc/encdb.so`, `enc/trans/transdb.so`) with `copy_str(path, lenc, true)` (`ruby.c`, lines 2574 to 2589). With `intern` true, `copy_str` skips the validity check it makes for the load path. `rb_progname` and the script name get the locale encoding unchecked (`ruby.c`, lines 2510, 2511, and 2538). A file found through `require_relative`, or through `require` with a US-ASCII or BINARY name, is tagged with the filesystem encoding unchecked (`file.c`, `copy_path_class`, lines 7996 to 8006, from `rb_find_file`, lines 8134 to 8159; `load.c`, lines 1214 and 1242).
- **Features required by a UTF-8 name: UTF-8.** `copy_path_class` keeps the encoding of the name passed to `require`, and a literal in a Ruby file is UTF-8, so `require "rbconfig"` records `.../rbconfig.rb` as valid UTF-8.

Ruby already has the rule that would keep these together: `rb_external_str_new_with_enc` returns BINARY for a US-ASCII string with bytes outside ASCII (`string.c`, lines 1395 to 1398). The three places above do not use it.

### Where Bundler and Thor trip on it

- **`Bundler::SharedHelpers#clean_load_path`** (`bundler/shared_helpers.rb`, lines 385 to 394, at Bundler 4.0.20, and unchanged at ruby/rubygems master, `lib/bundler/shared_helpers.rb`, lines 386 to 394): `$LOADED_FEATURES.any? {|lf| lf.start_with?(resolved_path) }`. `lf` is one of the boot features (US-ASCII, invalid) and `resolved_path` comes from a BINARY load path. Two strings with bytes outside ASCII in two encodings raise.
- **Thor's `Command::FILE_REGEXP`** (`bundler/vendor/thor/lib/thor/command.rb`, line 3, and Thor's own `lib/thor/command.rb` at rails/thor main): `/^#{Regexp.escape(File.dirname(__FILE__))}/`. `__FILE__` came through `require_relative`, so it is US-ASCII with invalid bytes, and a Regexp cannot be built from it.
- **`Bundler::FriendlyErrors.serialized_exception_for`** (`bundler/friendly_errors.rb`, lines 95 to 99): joins a backtrace whose lines mix UTF-8 and US-ASCII paths, so the report of the real error raises in its turn.

A fourth Bundler failure is not the locale's: `bundle exec ruby main.rb` fails under `LANG=C.UTF-8` too, in `Bundler::CLI::Exec#ruby_shebang?` (`bundler/cli/exec.rb`, line 125: a BINARY `first_line` against UTF-8 shebangs), whenever the `ruby` it finds lies in a folder named outside ASCII. Fledge's launcher sets up Bundler itself (`runtime/launcher/bundler.c`) and does not reach it.

## 2. Could they be fixed at the source?

Yes, each of them, in Ruby or in Bundler, and none needs a Bundler setting: no setting changes these code paths.

**In Ruby.** Tag a path that is not valid in the filesystem encoding as BINARY everywhere, as `rb_external_str_new_with_enc` already does and as the load path already is: in the boot features' re-tagging (`ruby.c`, lines 2574 to 2589, the validity check that `copy_str` makes when `intern` is false), in `copy_path_class` (`file.c`, lines 7996 to 8006), in `load.c`'s `rb_filesystem_str_new_cstr` calls, and for `rb_progname`, the script name, and so `__FILE__` and `__dir__`. Fledge carries edits to Ruby already, so the runtime could carry this. The probe imitated only the first part (re-tagging the boot features BINARY before Bundler loaded): Bundler then raised "UTF-8 and BINARY" at the same line, because the UTF-8 features remain. The whole of it is several functions in three files, and it would make the runtime's paths BINARY where stock Ruby's are US-ASCII or UTF-8: itself a difference from `ruby main.rb`, until upstream takes it.

**Is it a bug upstream would take?** Arguably yes: the same folder in three encodings is an inconsistency, not a policy. Ruby took a close relative, Bug #18191 ("All loaded feature filenames should be in the file system encoding", fixed by nobu in 60d0421c, 2021-10-01), whose fix is the re-tagging at `ruby.c`, lines 2574 to 2589, that skips the check. Bug #22194 (open, 2026-07-13) reports `File.realpath` and `File.realdirpath` disagreeing on the encoding of a path incompatible with the filesystem's. Bug #1614 (2009) and Bug #9737 (2014) fixed boot failures under a non-ASCII prefix. No report on bugs.ruby-lang.org covers this case: searches of issue subjects for "locale", "US-ASCII", "default_external", "C.UTF-8", "LOADED_FEATURES", "filesystem encoding", and "non-ASCII path" found none. Against it: Ruby's maintainers have treated a missing locale as the system's business (Bug #18495, closed by its reporter: "it's up to the system to properly define locales").

**In Bundler.** Three small changes: compare bytes in `clean_load_path` (`lf.b.start_with?(resolved_path.b)`); build Thor's `FILE_REGEXP` from a string that cannot be invalid; and join the backtrace in `FriendlyErrors` without mixing encodings. The probe proved the first: with `clean_load_path` comparing bytes, `require "bundler/setup"` set up the bundle in a C locale under `My Apps/Ünïcödé 日本`. RubyGems' maintainers take this kind of fix: ruby/rubygems#9968 ("Read sources as binary when checking for require_relative of extensions", merged 2026-10-26) fixed `gem build` "whenever the locale is unset or ASCII", and #8196 (merged 2024-11-04) fixed "incompatible encodings" with a UTF-8 install folder. Thor's fix belongs in rails/thor, which Bundler vendors.

**Filing upstream needs an account** on bugs.ruby-lang.org or GitHub. Agents open none (AGENTS.md, Questions), so filing is the maintainer's, or needs his word to use an existing one.

## 3. What the app would then see

Something else, not nothing. With every failure above fixed, a Ruby in a C locale boots and Bundler sets the app up, and the app sees what `env -i ruby main.rb` gives today:

- `Encoding.default_external`, `Encoding.find("locale")`, and `Encoding.find("filesystem")` are US-ASCII, and `Encoding.locale_charmap` is `"ANSI_X3.4-1968"` on glibc or `"US-ASCII"` on macOS.
- `__dir__`, and `$0` and `__FILE__` when the path is absolute, are US-ASCII with invalid bytes. `__dir__ =~ /app/` and `__dir__.split("/")` raise "invalid byte sequence in US-ASCII" (measured above), and `File.join(__dir__, "café")` raises "incompatible character encodings: US-ASCII and UTF-8" (the desktop parity audit, J26 to J28).
- Text the app reads with `File.read` is US-ASCII, and its `Dir.home` too when the home folder's name is outside ASCII.

That is parity with `env -i ruby main.rb`. It is not what the developer saw: the developer ran `ruby main.rb` in a terminal, which gives a UTF-8 locale. And the person who double-clicks the app meets an error that names a Ruby encoding, from the app's code or any gem that matches a path, the moment their folder's name is outside ASCII (Design precedence 1).

A third way, `-E UTF-8` in place of the coercion, changes too little. Measured under no locale: `default_external` and `filesystem` become UTF-8, `find("locale")` stays US-ASCII, the boot features stay US-ASCII with invalid bytes, and `require "bundler/setup"` fails at `clean_load_path` as before. It would also be a difference from `ruby`, as the coercion is.

## 4. Is a launch with no locale inherent?

**macOS: yes.** launchd, which starts every app LaunchServices opens, sets no `LANG`: `launchctl getenv LANG` prints nothing on this Mac (macOS 27.2.1), and the environment of a process Docker.app started holds `PATH`, `HOME`, `TMPDIR`, `__CFBundleIdentifier`, and the like, and no `LANG` or `LC_*` (`ps -E`). A terminal sets them for its own shells: Terminal's "Set locale environment variables on startup", a profile setting (Terminal User Guide, "Change Profiles Advanced settings in Terminal on Mac", https://support.apple.com/guide/terminal/change-profiles-advanced-settings-trmladvn/mac). So the same `main.rb` is UTF-8 where the developer runs it and US-ASCII where the person double-clicks it.

**Linux: not always.** systemd reads `/etc/locale.conf` at boot, and "the locale settings configured in /etc/locale.conf are system-wide and are inherited by every service or user" (locale.conf(5), systemd 262, https://www.freedesktop.org/software/systemd/man/latest/locale.conf.html). The service manager propagates `$LANG`, "set in locale.conf(5) or on the kernel command line" (systemd.exec(5), "Environment Variables Set or Propagated by the Service Manager"); a user service inherits the user manager's environment, which receives "additional imported variables when the user starts a graphical session" (systemd.exec(5), "Environment Variables in Spawned Processes"). So on a desktop whose distribution set a locale, an app a `.desktop` entry starts, or a user service, has `LANG`. It has none under `env -i`, in a container or minimal image with no locale configured (PEP 538, "Motivation", gives Fedora and Debian base images as examples), and over SSH, which may forward a locale the server lacks (PEP 538). Fledge's Delivery check runs `env -i` on purpose.

**Windows: not a question.** Ruby's `default_external` is UTF-8 there whatever the code page (Feature #16604, Ruby 3.0), and its filesystem encoding is UTF-8 (`localeinit.c`, line 126), so a C locale never reaches Ruby's paths. Fledge does not coerce there (ADR 041; `launcher.md`, "The locale").

**Phones: yes.** iOS and Android start apps with no locale variable; on Android `setlocale(LC_CTYPE, "")` gives "C" whatever the environment (PEP 538, "Changes to locale settings on Android"). PEP 538 has CPython call `setlocale(LC_CTYPE, "C.UTF-8")` on Android for that reason, and PEP 540's UTF-8 Mode turns on in the POSIX locale on every platform.

**Prior art.** CPython coerces the C locale (PEP 538, Python 3.7), and also turns on UTF-8 Mode in the POSIX locale (PEP 540, Python 3.7: "This mode is off by default, but is automatically activated when using the 'POSIX' locale"), without changing the environment. PEP 686 (Final, Python 3.15) makes UTF-8 Mode the default everywhere. Ruby's own move on Windows (Feature #16604) cited the same reasoning: "UTF-8 as the default external encoding is the expected encoding for most of the people on Windows, now".

## Options

| Option | Cost | Difference it closes |
|---|---|---|
| A. Keep ADR 041 | None. | None. The three encodings stay UTF-8 where `env -i ruby` gives US-ASCII. |
| B. Fix at the source in the runtime, drop the coercion | Edits to `ruby.c`, `file.c`, and `load.c`, and to Bundler, Thor, and RubyGems' plugin loading, carried on every Ruby and Bundler update; the BINARY tagging is itself a difference until upstream takes it. | The encodings match `env -i ruby`. But the app's code and gems fail for a person whose folder name is outside ASCII, as stock Ruby does: a precedence 1 harm in place of a precedence 2 difference. |
| C. Fix upstream, keep the coercion until it ships | A Ruby bug report with the three-encodings reproduction above, and PRs to ruby/rubygems (`clean_load_path`, `FriendlyErrors`) and rails/thor (`FILE_REGEXP`). Needs the maintainer's account. A Ruby fix ships with the next Ruby that takes it. | None by itself: when it ships, B costs Fledge no patches, but B's harm to the app remains. |
| D. Propose UTF-8 in the C locale to Ruby, as PEP 540 and Feature #16604 did | A Feature request and its discussion; the outcome is uncertain (Bug #18495). Needs the maintainer's account. A new default ships no sooner than the Ruby after 4.1. | All of it, if Ruby takes it: stock `ruby main.rb` would give UTF-8 too, and the coercion would match Ruby, or could go. |
| E. `-E UTF-8` in place of the coercion | A launcher change. | None: still a difference, and Bundler still fails (measured). |

## Recommendation

Keep ADR 041 (A), and give it the reason the 2026-11-12 bar asks for: the difference is inherent to where the app ships. macOS and phones give a double-clicked app no locale, and fixing Ruby and Bundler at their source would still leave the app's own code failing there, where the developer's terminal never did. Closing a difference that way trades a documented encoding for a person who meets Ruby.

Then do C and D together, which the maintainer has to file or authorize: report the three encodings to Ruby with this reproduction, send the Bundler and Thor fixes, and propose that Ruby treat the C locale as UTF-8, citing PEP 540, PEP 686, and Feature #16604. D is the only path that makes the difference disappear rather than move. If Ruby takes it, the coercion becomes Ruby's own behavior, and the reversal in ADR 041 runs.
