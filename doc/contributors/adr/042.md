# ADR 042: Ship libxcrypt and GNU MP as Shared Libraries a Person Can Replace

## Context and Problem Statement

Two libraries under the LGPL come with the Rubies Fledge takes (ADR 035). On glibc Linux, libruby calls libxcrypt (LGPL-2.1-or-later) for `String#crypt`, and rv-ruby links it statically into its own `bin/ruby`. On Windows, RubyInstaller's Ruby DLL imports GNU MP (LGPL-3.0-or-later OR GPL-2.0-or-later) for big-integer arithmetic, as `libgmp-10.dll`.

The maintainer's rule is that a developer owes nothing beyond notices for what Fledge ships (`decisions.md`, 2026-10-26, decisions 8 and 24). Asked about these two, he wrote: "Remember that LGPL and GPL/AGPL's main differentiator is dynamic linking. Relevant here or not?", then "Source offer for... the app? Or the LGPL'ed library? Former won't be liked, latter is fine and normal.", and "As long as we're clear about that to app devs, that's great." (2026-10-26, later). Shipped as separate shared libraries a person can replace, the LGPL asks for a notice, the library's source, the means to replace it, and app terms that permit reverse engineering to debug such a replacement (LGPL-2.1, section 6; LGPL-3.0, section 4). It never asks for the app's source. Should runtimes keep these libraries, and how?

## Decision Drivers

- No LGPL code linked into the launcher or any program whose source Fledge does not publish (AGENTS.md, Licensing).
- No app's source or object files ever asked of a developer.
- `String#crypt` and `Integer` arithmetic behave as under `ruby` on the same system (ADR 039).
- Fledge maintains no fork of a Ruby distribution.

## Considered Options

1. **Keep both as shared libraries a person can replace:** Linux runtimes build libxcrypt from rv-ruby's pinned release as `lib/libcrypt.so.2`, which the launcher and `bin/ruby` load through their RPATH; Windows runtimes ship RubyInstaller's `libgmp-10.dll` unchanged. Fledge publishes each one's exact source.
2. **musl's crypt in place of libxcrypt.**
3. **A Windows Ruby built without GNU MP.**
4. **libxcrypt linked statically, as rv-ruby's own `bin/ruby` links it.**

## Decision Outcome

Chosen: option 1, because the others each break a driver. musl's crypt silently computes a wrong (DES) hash for yescrypt, the default password hash of current Debian, Ubuntu, and Fedora, so `String#crypt` would differ from `ruby`'s. A Windows Ruby without GNU MP means forking RubyInstaller's packaging onto MSYS2's rolling toolchain, a fork to maintain. Static linking puts LGPL code inside a program an app's developer ships as their own, which the maintainer's replies and AGENTS.md rule out.

Neither library is linked into any other file. musl Linux runtimes ship no libxcrypt at all, since musl's own C library carries `crypt(3)` there (ADR 017), and the phones ship neither.

Confidence: high. CI proves on every push that whoever receives an app can replace each library and the app loads and behaves as the replacement does.

### Consequences

- Good, because an app stays the developer's own, under any terms, with only notices and the libraries' sources to pass on, which every app carries (ADR 043).
- Good, because `String#crypt` knows yescrypt on glibc Linux, as `ruby` does there.
- Bad, because a Linux app needs `lib/libcrypt.so.2` beside it and a Windows app GMP's DLL, and a developer whose own policy forbids LGPL-3.0 has GMP to raise.
- Bad, because Fledge builds libxcrypt itself in each Linux runtime build, and must follow rv-ruby's release of it; and the Windows runtime's GMP must stay byte for byte the build whose source Fledge publishes, which the audit checks by SHA-256.
- Bad, because the developer's terms must permit reverse engineering for debugging a replacement, which `doc/licensing.md` tells them.

### Confirmation

- The license audit fails when libxcrypt's or GNU MP's code, by byte signatures, is in any file but that library's own shared library (`static-copyleft`), and when GMP's DLL's SHA-256 moves.
- CI's "Replace libcrypt" jobs swap in a libxcrypt rebuilt from the source the app carries, and musl's crypt, and check the app behaves as each does.
- CI's "Replace GMP" jobs swap in another GNU MP, cross-built with the pinned llvm-mingw, and check `Integer::GMP_VERSION` changes while a large product does not.
- CI's Windows "Runtime" jobs check that MSYS2's binary package holds RubyInstaller's DLL byte for byte, which makes MSYS2's source package its exact source.
