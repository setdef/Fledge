# ADR 002: `fledge` and an app's launcher follow GNU's and sysexits' conventions

## Context and Problem Statement

Two programs talk to people. A developer runs `fledge`; anyone runs the launcher inside a built app. Each prints help or errors, and exits with a status that scripts read. How should each spell its options, word its messages, and choose its exit statuses?

The maintainer asked that agents follow the standards rather than ask him (`decisions.md`, 2026-10-26, decision 4: "What is the GNU standard? What is the Unix standard? What would Windows users expect?"; decision 16: "Why is this something I should decide? Isn't this something where there's prior art or an industry standard we can/should follow?"). The agents proposed the conventions below, and he answered "Ok." (2026-10-26, later, reply 4).

## Decision Drivers

- A script can tell "you called me wrong" from "I tried and it failed", and both from the app's own failure.
- Developers keep the habits they bring: Ruby's `-v`, GNU's `--help`, Windows' `-?`.
- A person who runs an app never asked for Ruby, so a launcher's message names the app (AGENTS.md, Design precedence 1).
- An app's own exit status reaches its caller unchanged, as under `ruby main.rb`.

## Considered Options

1. GNU's conventions with Ruby's and Windows' short options, exit status 2 for a usage error; a launcher that names the app and exits with sysexits' statuses.
2. The first draft's own invention: `fledge -V`, help on standard error with status 1 for a bare `fledge`, status 1 for every mistake, and 70 for every launcher failure.
3. Exit status 1 for a usage error, as most coreutils and BSD `usage()` functions do.
4. sysexits' `EX_USAGE` (64) for a usage error.

## Decision Outcome

Chosen: option 1, because it is what the standards and the tools scripts test most already do, and the maintainer accepted it.

- `fledge` prints help and the version to standard output and exits 0, with `-h`, `-?`, `--help`, `-v`, and `--version`. A usage error prints the message and the short usage to standard error and exits 2. A build that fails prints `fledge build: ...` and exits 1.
- A launcher that cannot start its app prints `NAME: what went wrong`, as Ruby prints `ruby: ...`, and exits 66 (`EX_NOINPUT`) when the program or its `fledge.cfg` is missing, 72 (`EX_OSFILE`) on Linux when a library the app's gems load from the distribution is not on the computer (ADR 030), and 70 (`EX_SOFTWARE`) for anything else. Once the app runs, its status is the app's own.

`exe/fledge`'s help header lists the options and statuses. `doc/contributors/design/launcher.md`, "Messages and exit statuses", lists every launcher message and status, and `doc/contributors/design/public-interface.md` which statuses 1.x keeps.

Confidence: high. Each convention is a published standard or a habit of widely used tools, and tests pin every status.

### Consequences

- Good, because a script tells a call it got wrong (2) from a build that failed (1), and a broken app (66, 70, 72) from the app's own failure.
- Good, because the launcher's messages name the app, never Ruby.
- Bad, because the help header's SYNOPSIS is load-bearing: every usage error prints it. The CLI and the header change together.
- Bad, because an app that exits 66, 70, or 72 for reasons of its own looks, by status alone, like a broken app; only the message tells them apart.
- Neutral: a tool that expects sysexits' `EX_USAGE` from every program gets 2 from `fledge`.

### Confirmation

- `test/cli_test.rb` runs `Fledge::CLI` through `StringIO` streams, and pins the help, the SYNOPSIS as usage, and statuses 0, 1, and 2; `test/integration/exe_test.rb` runs `exe/fledge` as a subprocess.
- `test/integration/built_app_test.rb` checks 66 for a missing program and `fledge.cfg`, 70 when `bin/ruby` cannot start the launcher, and 72 for a missing system library.
- Delivery checks 66 and the message on every desktop platform (`.github/scripts/deliver.sh`, `deliver.ps1`); `deliver.sh` checks 70 for an app unpacked into a folder named `bin`; and 72 is checked in `.github/scripts/deliver-system-library.sh`.

## Pros and Cons of the Options

### The first draft's own conventions

- Bad, because `-V` means nothing to `ruby`, `gem`, or `bundle`, which spell the version `-v`, as the maintainer's Lota and Rooibos do.
- Bad, because one status for every mistake hides a usage error among real failures.

### Exit 1 for a usage error

- Good, because most coreutils and BSD `usage()` functions do it.
- Bad, because the habit is older than the distinction, and 1 then means two things.

### `EX_USAGE` (64)

- Neutral, because sysexits defines it; bad, because command-line tools rarely use it, and scripts expect 2 from the tools below.

## More Information

- GNU Coding Standards, section 4.8 ("Standards for Command Line Interfaces"), 4.8.1 (`--version`) and 4.8.2 (`--help`): both print to standard output and exit successfully. GNU's usage error is `ls: unrecognized option '--bogus'`, then `Try 'ls --help' for more information.`; BSD tools print a one-line `usage:` synopsis. Fledge prints both.
- Status 2 for a usage error: `grep`, `diff`, and `cmp`, whose statuses POSIX specifies; GNU `ls` (coreutils' `ls.c` passes `LS_FAILURE`, 2, to `usage`); `bash`'s builtins.
- Windows: `dotnet -?`, `winget -?`, and `cmd`'s `/?`.
- sysexits(3), from FreeBSD, shipped by macOS and glibc: `EX_NOINPUT` (66), "An input file (not a system file) did not exist or was not readable"; `EX_SOFTWARE` (70), "An internal software error has been detected"; `EX_OSFILE` (72), "Some system file ... does not exist, cannot be opened, or has some sort of error." A launcher cannot reuse Ruby's own statuses, because the app's failures already exit with whatever the app chooses.
- `Fledge::UsageError` carries a usage error out of a command to `Fledge::CLI`, which owns the usage text. `runtime/launcher/launcher.h` defines the launcher's statuses once for every platform.
