# ADR 082: On Android, the runtime carries a ruby program the installer extracts with the app's native libraries

## Context and Problem Statement

A Ruby program that runs Ruby again asks Ruby where it is: `system(RbConfig.ruby, "script.rb")`, `IO.popen([Gem.ruby, "-e", code])`, `exec RbConfig.ruby, $0, *ARGV`. On a desktop `RbConfig.ruby` names the runtime's `bin/ruby`, Ruby's `main.c` built against the launcher's libruby, with the launcher's locale and relaunch (ADR 026, ADR 085, ADR 041). On a phone, Ruby is a library inside the app (ADR 079): the runtime had no program, `RbConfig.ruby` named `ROOT/bin/ruby`, where none was, and starting it failed with `ENOENT`. So an app that starts Ruby failed on a phone, and ruby/spec on phones skipped about 300 examples that check a feature by running a child Ruby through MSpec's `ruby_exe` (`tasks/ruby_spec/phone_config.rb`).

An app's code should run as under `ruby main.rb` (AGENTS.md, Design precedence 2). iOS lets no app run a program. Android does, but not any file: "Untrusted apps that target Android 10 cannot invoke `execve()` directly on files within the app's home directory", and "Apps should load only the binary code that's embedded within an app's APK file" (developer.android.com, Android 10 behavior changes, "Removed execute permission for app home directory", read 2026-11-12). The files an app may run are those its package installer extracts from the APK into the app's native library folder, `ApplicationInfo.nativeLibraryDir`, whose name changes with each install. The installer extracts the APK's `lib/ABI/` entries named `lib*.so`, and only when the app's native libraries are packed compressed: with `android:extractNativeLibs="false"`, which the Android Gradle plugin writes when `packaging.jniLibs.useLegacyPackaging` is false, as Fledge's template set it, "your native libraries are stored uncompressed in the APK" and load from it (developer.android.com, `<application>`, `android:extractNativeLibs`, read 2026-11-12).

Where can an Android app's runtime keep a Ruby program the app may run?

## Decision Drivers

- An app's code runs as under `ruby main.rb` (decisions 9, 10, and 20): `RbConfig.ruby` and `Gem.ruby` name a Ruby that runs, and `RbConfig` itself stays what stock Ruby's is.
- A Ruby the app starts is what a desktop's `bin/ruby` is: plain Ruby with the locale the launcher would choose, and the app's own program run as the app first ran (ADR 026, ADR 041).
- Android's rules: only extracted native libraries run, Google Play takes only apps that target a recent API (API 36 for the template), and 16 KB pages (`doc/contributors/design/phone-projects.md`, "The Android App Bundle check").
- No second copy of Ruby in the app: `libfledgeruby.so` is most of an Android app's size.
- iOS cannot have one, and must not pay for Android's.

## Considered Options

1. In each ABI's folder of the AAR, named `libfledgerubyexe.so`, so that the app's package carries it as a native library, with the template packing native libraries compressed (`useLegacyPackaging = true`), so that the installer extracts it.
2. In the app's files, unpacked from the asset as `ROOT/bin/ruby`.
3. In the app's files, with the template targeting API 28, as Termux does.
4. In the app's files, run through the system's linker, `/system/bin/linker64 ROOT/bin/ruby`.
5. No program: start a child Ruby in a process of Android's own, a `Service` with `android:process`, as an app embedding Python with Chaquopy or Buildozer does.

## Decision Outcome

Chosen: option 1, because it is the one place Android lets an app run a file of its own, for the API levels Google Play takes. How `RbConfig.ruby` names it is ADR 083's; how it is built and linked is in `doc/contributors/design/phone-runtimes.md`, "The ruby program on Android".

The AAR carries the program in each ABI's folder, `jni/ABI/`, as `libfledgerubyexe.so` beside `libfledgeruby.so`. The template packs the app's native libraries compressed, so that the installer extracts both into `nativeLibraryDir`. That costs every Android app installed space, those that never start Ruby too, which is the trade decision 20 makes: "Tiny filesize is not a priority; "my ruby code just works" _is_ a (high) priority." A developer whose code never starts Ruby takes the space back by setting `useLegacyPackaging = false`, as `doc/phones.md` says, and loses `RbConfig.ruby`.

When the native libraries are not extracted, `libfledgeruby.so` loads from inside the APK (`base.apk!/lib/ABI/`), there is no program to link, and `fledge_ruby_link_program` removes any old link: `RbConfig.ruby` names nothing. A developer who sets `useLegacyPackaging = false` gets that, and smaller installs; the template's comment says so.

iOS has none of this: its runtime builds no program, and `apple.c`'s `fledge_ruby_link_program` does nothing. ruby/spec's `ruby_exe` skips on iOS alone.

Option 2 is what Android 10 forbids. Option 3 is what Termux did to keep running its packages from its files (termux/termux-app issue 1072, "No more exec from data folder on targetAPI >= Android Q"), and Google Play takes no new app or update that targets API 28. Option 4 maps the program's code from the app's files with execute permission, which the same rule forbids, and is a path only API 29 and later have. Option 5 is no program: `RbConfig.ruby` would still name nothing, and an app would need Android-only code to start Ruby, which decision 23 hoped to spare developers; Python on Android made that choice: "There is no `python3` executable, Python's `sys.executable` is empty. To run a Python script in a new process, we use an Android Service" (Android-for-Python's users' guide to Buildozer, `README.md`, read 2026-11-12), and PEP 738 loads `libpython3.x.so` into the app's process, so that "A python3.x executable will not be officially supported on this platform", since "apps may only run executables in certain locations, none of which are writable at runtime. Long-running subprocesses are officially discouraged" (PEP 738, "App lifecycle"). Fledge's precedence is Ruby's behavior first (AGENTS.md, Design precedence 2), and Android does let an app run what it extracts, so Fledge ships the program Python chose not to.

Confidence: high. CI's Android emulators, API 36 with 4 KB and 16 KB pages, run the parity probe's child Ruby and ruby/spec's `ruby_exe` examples, and a OnePlus Nord, arm64-v8a with API 34, ran a child Ruby through `system` and `IO.popen` from an app with no unjustified parity difference.

### Consequences

- Good, because `RbConfig.ruby`, `Gem.ruby`, `system`, `spawn`, backquotes, and `IO.popen` start Ruby on Android as on a desktop, with the app's gems through Bundler's `RUBYOPT`, and the parity probe's child Ruby reports what a desktop's does.
- Good, because ruby/spec's examples that run a child Ruby through `ruby_exe` run on Android and are compared with stock Ruby.
- Good, because the program costs a few kilobytes per ABI.
- Bad, because the app's native libraries are compressed in the APK and extracted on install, so the app takes more space installed: the extracted libraries beside the APK's compressed ones. Android's page-size guide warns that such an app "takes up more space when installed" and "might more frequently fail to install" for it (developer.android.com, "Support 16 KB page sizes", read 2026-11-12). The download is smaller, since the libraries are compressed. A developer who does not start Ruby may set `useLegacyPackaging = false` and lose the program.
- Bad, because the program is a native library by name only: a tool that lists an app's libraries lists it, and `System.loadLibrary("fledgerubyexe")` would fail.
- Bad, because a child Ruby is a process of its own: it has no Java virtual machine, so nothing in it can call Android's Java APIs, and Android may stop it with the app.
- Bad, because `exec RbConfig.ruby, $0` replaces the app's own process, which Android then no longer runs as the app; on a phone an app restarts its Ruby with `system` or `spawn`.
- Good, because ruby/spec's files that start processes, `command_line`, `Process.spawn`'s, `Kernel#system`'s, `Process.wait`'s, and `Process.kill`'s among them, run on Android and are compared with stock Ruby; iOS alone leaves them out, since it lets no app start a process.

### Confirmation

- `test/integration/mobile_ruby_program_test.rb` compiles `fledge_ruby_main` with this computer's Ruby and runs it: `-e` and another script as plain Ruby with `RUBYOPT`, and the app's program, by its path, a relative path, and a link, as the host runs it; an option before the program, or no `fledge.cfg`, leaves it plain.
- The runtime build fails unless the program needs only Android's libraries and `libfledgeruby.so`, has the run path `$ORIGIN`, and aligns every LOAD segment to 16 KB (`RuntimeBuilder::Android#program`), and the license audit accounts for it in the AAR.
- The mobile parity check runs the probe on Android emulators, where `RbConfig.ruby is a program` and `RbConfig.ruby runs` match `ruby main.rb`, and the child's `ENV` is the app's (`Parity::MOBILE_JUSTIFIED`); the bundle check fails a bundle whose native libraries are stored (`MobileParity::Android.packed_wrongly`, `UNCOMPRESSED_NATIVE_LIBRARIES`).
- ruby/spec on Android emulators runs `ruby_exe`'s examples (`tasks/ruby_spec/phone_config.rb`).
