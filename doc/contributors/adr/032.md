# ADR 032: An App Built From an App Already Built, and the Files an App Opens

## Status
Accepted (requested), and built. Agents wrote this ADR and may change it until 1.0 (AGENTS.md, Questions); from 1.0, ADR 029, section 2, freezes what it builds. It designs Plan 003's story "Build from a built app, and the files an app opens". `fledge build --from` (section 2) is built, for the computer's own platform only, as section 8 records; `file_associations` (section 3) and `build_tools` (section 4) are built, as each section's end records. First released in `v0.6.0`. What is not built is future work, and each place that says so is marked: a copy-only `--from` for another system's APP (section 6), a single Windows file (section 7), and the proofs the Consequences list as not made. It serves the maintainer's entry on drag-to-fuse, the last of `doc/contributors/decisions.md`: a command line is a barrier for the newcomers a framework built on Fledge is for, and a framework's way to make an app by dropping a folder on another app is in scope. The maintainer's correction of the same day governs its shape: Fledge depends on no framework and knows none of their concepts (the Dependency Rule of Robert C. Martin's *Clean Architecture*: the inner, stable policy names nothing of the outer layers that plug into it). So this ADR gives frameworks general primitives, and each framework builds its own drop-to-make-an-app on them. Section 6 meets the maintainer's decision of 2026-10-28 that Fledge does not build one platform's app on another, as his answer of 2026-11-04 to question D lets it (decisions, 2026-11-04: a step that only copies and needs no cross-compiling is allowed when it adds little code and room for bugs). The evidence is `doc/contributors/research/2026-11-05-drag-to-fuse.md` (the research, which also maps one framework's needs onto these primitives as an example consumer) and run 41978615197 on `experiment/drag-to-fuse` (the spike).

## Date
2026-11-05

## Context

`fledge build` needs Ruby 4.0, Bundler, the network for the lockfile's gems, and a compiler for a gem with no build for the platform (ADR 005, 006, 019). A person with none of these cannot make an app, even when every gem their program needs is already compiled inside an app Fledge built.

Prior art makes a new app from one already built, without building anything:

- **LÖVE** ships its executable; a game made with it becomes an app when the game is appended to a copy of that executable, or copied into a renamed copy of its `.app` (research, section 1).
- **Electron**: an app is a prebuilt Electron with the developer's code in `resources/app` or `app.asar`, and electron-builder's `--prepackaged DIR` packages an app already laid out.
- **Python's embeddable distribution** and Briefcase's app templates: a finished interpreter tree into which a project is copied.

Prior art lets an app say which files it opens, and the system hands them to it: Tauri's `bundle > fileAssociations` and electron-builder's `fileAssociations` (`ext`, `name`, `role`, `mimeType`, and on macOS content types), written as `CFBundleDocumentTypes` on macOS, registry entries on Windows, and `MimeType` in a Linux desktop entry. A file or folder dropped on a Windows program arrives in its arguments (Microsoft's `uap5:ExecutionAlias` reference); on macOS it arrives as an Apple event, and Finder offers the drop only to an app whose document types cover it (research, section 3).

Fledge's constraints, from accepted ADRs: Ruby's prefix comes from the file that holds libruby (ADR 001); the launcher reads `fledge.cfg` and `app/` beside itself (ADR 005); `fledge.cfg` is Fledge's alone (ADR 029, section 3); each platform's app is built on that platform with its own tools (ADR 010); an app's code runs as under `ruby main.rb` (Design precedence 2).

## Decision

### 1. Four designs, weighed

**(A) A self-extracting single file**: a small program with the app zipped on its end unpacks it once into a per-user cache keyed by the payload's hash and starts it there, as warp-packer does; PyInstaller's `--onefile` and electron-builder's `portable` unpack on every launch (research, section 2). Its costs: the first launch waits (the spike unpacked 2,906 files, 50.8 MB, from an exe of 19.5 MB in 1.13 s with Windows' own `tar.exe` on a CI runner); a second copy per version that nothing removes; antivirus heuristics ("an indefinite cycle", PyInstaller); a signature that must be made after the payload is appended; on macOS a pattern PyInstaller deprecates because "a .app bundle can not be a single file"; `__dir__` and `RbConfig.ruby` naming the cache rather than the place the person put the file (Design precedence 2); and a second process between the person and the app. ADR 001, section 1, turned this down. It stays possible later as an opt-in Windows output; the spike showed Windows' `tar.exe -xf` reads a zip appended to an exe with `copy /b`, so it would need no zip code (section 7).

**(B) Running from an archive never unpacked.** Ruby cannot `require` from a zip, load a library from one, or keep its prefix in one; that is the virtual file system ADR 001 rejected and Tebako v2 builds over libc with an interposition shim. A framework may read its own data files from an archive through its own API; that is the framework's. Not taken.

**(C) A new app built from an app already built.** An app Fledge built holds the runtime and the compiled gems. A new project that needs no other gems becomes an app by copying that app, replacing its project with the new one, and writing the new identity with the system's own tools. Nothing is downloaded, resolved, or compiled. The spike did this inside a built app, with only Ruby's standard library and the system's tools, on fresh macOS and Windows runners with no Ruby reachable, in 1.4 to 2.3 s; the result ran and passed `codesign --verify --deep --strict` (research, section 7). **Taken**, as section 2.

**(D) Receiving what is dropped.** Taken as section 3: the app declares the files and folders it opens, and the system delivers them by its own means.

### 2. `fledge build --from APP`

`fledge build --from APP [OPTIONS] [PATH]` builds the project at PATH as `fledge build` does, but takes the runtime and the gems from APP, an app's folder (`NAME-PLATFORM/`, or on macOS its `.app`) that Fledge built, instead of downloading the runtime and installing the lockfile's gems. electron-builder's `--prepackaged` is the nearest prior art; `--from` reads as Docker's `COPY --from` does, "take it from that already-built thing". It:

1. Refuses, with status 2, an APP Fledge did not build, built by another Fledge release (its `fledge.cfg` is that release's), or built for another platform than the computer's (section 6, which says why the first version refuses it).
2. Refuses, with status 1, a PATH whose project has a `Gemfile`, `gems.rb`, or gemspec of its own ("--from builds no gems: build this project with fledge build"). The new app runs with APP's `Gemfile` and `Gemfile.lock`, which `--from` copies into the new project, refusing a PATH that holds files by those names. Bundler sets up APP's gems for the new program as it did for APP's (ADR 005, section 5).
3. Reads `fledge.yml` and finds the program as `fledge build` does (ADR 005, section 1). The program, `name`, `identifier`, `version`, `icon`, `publisher`, `copyright`, `kind`, `installers`, and `file_associations` are the new project's; nothing of APP's identity carries over, and APP's `file_associations` are dropped. `programs`, `linux`, `ios`, and `android` are refused with `--from`: they change the runtime or the gems.
4. Copies APP to `DIR/NAME-PLATFORM/`, replaces its project folder (`app/`) with PATH's project and APP's Gemfile and lockfile, writes `fledge.cfg`, removes `build_tools` (section 4), and writes the identity as `fledge build` does: `Info.plist`, the icon, and `codesign` (ad hoc, or `--sign`, ADR 016) on macOS; rcedit on Windows; the desktop entry and icons on Linux. On Windows, rcedit comes from APP's build tools when it has them, else from the runtime Fledge would use when the computer has it (its cache or `FLEDGE_RUNTIME_DIR`; section 8 says why the first version downloads nothing).
5. Archives, makes the installers asked for, and prints each path on standard output, with `fledge build`'s names and exit statuses (ADR 029, section 2).

`--from` takes a folder only; unpacking a zip a person dropped is the caller's, since Linux has no zip reader every computer has (research, section 5).

### 3. `file_associations` in `fledge.yml`

A windowed app lists the files and folders it opens, in Tauri's and electron-builder's terms:

```yaml
file_associations:
  - name: Project folder
    role: viewer           # viewer (default) or editor
    folders: true          # opens folders
  - name: Project archive
    extensions: [zip]
    mime_types: [application/zip]
```

- **macOS:** `CFBundleDocumentTypes` in `Info.plist`: `CFBundleTypeName`, `CFBundleTypeRole`, `LSItemContentTypes` (`public.folder` for `folders`, the system's uniform type for each extension, or `content_types` given outright), and `LSHandlerRank` `Alternate`, so the app is offered but never made the default without the person's choice. A drop on its icon in Finder or the Dock, and `open -a`, deliver an Apple event: AppKit's `application(_:open:)`. Fledge's launcher runs no event loop, so the app receives it through its GUI library's (SDL3's `SDL_EVENT_DROP_FILE`, for one); an app with none does not see it, and the spike's `ARGV` was empty. Fledge does not turn the event into arguments: `ruby main.rb` gets none either (Design precedence 2).
- **Windows:** a file or folder dropped on the program arrives in `ARGV`, with nothing declared. The setup program registers the extensions under `HKCU\Software\Classes` with an `Open with` entry, as electron-builder's NSIS installer registers its `fileAssociations`; a portable folder registers nothing.
- **Linux:** `MimeType=` in the desktop entry (`inode/directory` for `folders`), and `Exec=... %F`, so a file manager passes the paths as arguments.

Plan 003's "The installers developers expect" deferred file associations until a developer or a wrapper asked; a framework has.

**What was built** (`Fledge::Config::FileAssociation`; agents' decisions, from the prior art read at its source):

- **The keys.** An entry has `name` (needed), `role` (`viewer`, the default, or `editor`), and `extensions` (without the dot, one part: Windows associates only an extension's last part), `mime_types`, and `content_types`, or `folders: true`, which an entry for files may not also say: macOS reads `LSItemContentTypes` in place of extensions, so one entry for both would lose the files there. An entry that names nothing to open is refused, and so is the key in a console app's `fledge.yml`, as `installers` is, since only a windowed app has a bundle, a desktop entry, or a setup program to declare them in. With `programs`, the windowed program declares them.
- **macOS.** "The system's uniform type for each extension", which the first draft above wrote, needs a tool that maps an extension to a type, and none in `/usr/bin` does without a file of that type. So an extension goes in as `CFBundleTypeExtensions` and a MIME type as `CFBundleTypeMIMETypes`, as electron-builder writes them (`packages/app-builder-lib/src/electron/mac/electronMac.ts`, lines 160 to 189, at c63f98a), and Launch Services matches a file to them through the dynamic type it gives the extension; `content_types` and `public.folder` go in `LSItemContentTypes`. The role is `CFBundleTypeRole`'s `Viewer` or `Editor`, and the rank is always `Alternate`, where electron-builder and Tauri default to `Default` (Tauri's `HandlerRank`, `crates/tauri-utils/src/config.rs`, lines 1150 to 1165, at 2e23492).
- **Windows.** Tauri's and electron-builder's installers set the extension's default to the app (Tauri's `FileAssociation.nsh`, `APP_ASSOCIATE`, lines 68 to 80, at 2e23492; electron-builder's, lines 66 and 67, at c63f98a), which a person never asked for. Fledge's setup program writes what electron-builder writes beside the default, and not the default: a ProgID, `IDENTIFIER.N` for the Nth entry, with the entry's name, the program's icon, and `shell\open\command` = `"PROGRAM" "%1"`, listed as a value of each extension's `OpenWithProgids` (written with NSIS's `WriteRegNone`, as electron-builder writes it), which puts the app in Explorer's "Open with" and leaves the default alone; and for folders, a verb on every folder, `Directory\shell\IDENTIFIER`, "Open with NAME", with the same command. Then `SHChangeNotify(SHCNE_ASSOCCHANGED)`, as both installers call it. The uninstaller deletes the ProgIDs, their `OpenWithProgids` values, each extension's key when nothing else is in it, and the verb. A ProgID longer than the 39 characters Microsoft's ProgID guidance gives, from an identifier longer than 36, is written all the same; no test covers what Explorer makes of one.
- **Linux.** A desktop entry knows files only by MIME type, so `extensions` alone does nothing there; `MimeType=` lists `mime_types`, and `inode/directory` for folders, as electron-builder's `LinuxTargetHelper.ts` (lines 342 to 357, at c63f98a) lists its own, and `Exec` ends in `%F` when it lists any. Fledge writes no shared-mime-info package to define a new type, which electron-builder does for a `.deb` and an AppImage could not install.

**Proved** by Delivery's scripts on `experiment/file-associations` (macOS and Linux in run 42102622918, Windows x64 and ARM64 in run 42121489631) on `examples/windowed_app`, which opens folders and its own reports (`.hellowindow`, `application/x-hellowindow`): on macOS, `plutil` reads the document types back, and Launch Services, once `lsregister -f` registers the bundle, offers the app for a folder and for a report (`NSWorkspace.URLsForApplicationsToOpenURL`, through `osascript`), which is the list Finder's "Open With" shows (Launch Services leaves out an app in a temporary folder such as mktemp's, so Delivery registers a copy in the home folder); and on the maintainer's Mac (macOS 27), in the hidden test session, `open -a "Hello Window.app" FOLDER` and `open -a "Hello Window.app" FILE.hellowindow`, which hand a document to an app as a drop on its icon does, started the app with no arguments (its report: `"arguments":0`), as section 3 says; on Windows, after a silent install, the registry holds the ProgID, the `OpenWithProgids` value with no default set, and the folders' verb, `AssocQueryString` gives each one's command, `ShellExecuteEx`, called from a single-threaded apartment as the shell's folder handlers need, opens a report through the ProgID and a folder through the `Directory` class's verb, in a folder named `Ein Ordner ü`, and the app gets each path in `ARGV`, as it does when started with the folder as a drop starts it, and the uninstaller leaves none of it; on Linux, `desktop-file-validate` accepts the entry in the folder and in the `.deb`, x86_64 and aarch64, and after `apt install` the `mimeinfo.cache` that `update-desktop-database` writes names the app for `application/x-hellowindow`. Not proved: a drop on the app's icon in Finder or the Dock, which needs a person or an event a GUI library receives; a file manager's double-click on Linux.

### 4. `build_tools` in `fledge.yml`

An app that runs `fledge build --from` itself, on a computer with no Ruby, needs Fledge and the tools Fledge runs that the system lacks. `build_tools: true` (default false) puts the runtime's tools in the app: on Windows rcedit, and NSIS's compiler, which the license audit already accounts for (ADR 004, ADR 010); macOS has `plutil`, `codesign`, `ditto`, and `hdiutil` in `/usr/bin`, and Windows has `tar.exe`. Fledge itself is a gem the app's Gemfile ships, outside the `development` and `test` groups, and the app runs it as a command: the `fledge` executable RubyGems writes into `Gem.bindir` (ADR 020, section 6), a Ruby of its own in the app's bundle. Because the app's Fledge built the app, the two always agree on `fledge.cfg`. A key of its own, not implied by `--from`, because an app may be built from by a developer's own Fledge with no tools inside it.

**What was built** (`Fledge::Assembly::BuildTools`; agents' decisions):

- **What the app carries**, in a folder `tools` beside its runtime (the name the runtime gives the same files), is exactly what `--from` takes from a runtime at hand: on Windows the runtime's `launcher.exe` and `launcherw.exe` and its tools folder, rcedit and NSIS, but `llvm-readobj.exe`, which reads the DLLs compiled gems import, and `--from` compiles none; on Linux the tools folder, AppImage's runtime; on macOS nothing, since the app's program is the runtime's launcher and `/usr/bin` has the rest. A program named `tools` is refused, as one named `app` is.
- **When.** The tools go in after the app's code is signed and before it is archived, so `--sign` signs none of them: a launcher signed by the developer and changed by rcedit in a later `--from` would carry a broken signature, where an unsigned one carries none. They are copied as the runtime holds them, so the installers a build writes hold them too.
- **Where `--from` looks.** `Fledge::BuiltApp` takes the launchers and tools from APP's `tools` before it asks for a runtime at hand (`Runtimes#at_hand`), and fails on Windows only when neither has them, naming both. APP's `tools` never passes to the new app: the new app carries its own only when its own `fledge.yml` sets `build_tools`, copied from where `--from` found them.
- **What it cannot carry.** An AppImage needs squashfs-tools' `mksquashfs`, which is GPL-2.0, and AGENTS.md's licensing rule keeps GPL code out of a runtime and so out of what `build_tools` copies from one; a `.deb` needs `dpkg-deb`, which every Debian and Ubuntu has. A framework whose users lack squashfs-tools asks for no AppImage, or says to install it. Considered: a static `mksquashfs` built and published with its source, which the GPL allows but the rule does not, and which would make Fledge maintain a build of a GPL tool.
- **Licenses.** Every tool carried is in the runtime's license audit already (ADR 004, ADR 010): rcedit (MIT), NSIS (zlib, bzip2's, and CPL-1.0, whose source every Windows app holds in `notices/sources/nsis/`), and AppImage's runtime (MIT, with libfuse's LGPL source in every Linux app's `notices/sources/`), so each app's `notices/` covers them, and `runtime/licenses.yml` says they ship in the app when `build_tools` is set. The two launchers are Fledge's own code, AGPL-3.0-or-later (MIT since 2026-11-07, decisions, 2026-11-07), as the app's program is.
- **What it costs**, measured on the experiment's builder app (Fledge as a gem, no other gems): on Windows 5.5 MB unpacked (4,966 KB of tools: rcedit 1.3 MB, NSIS, and two launchers of 28 KB) and 1.5 MB in the `.zip` (x64: 25.4 MB against 23.9 MB; ARM64: 24.9 MB against 23.4 MB); on Linux 0.9 MB unpacked and 0.5 MB in the `.tar.gz` (AppImage's runtime; x86_64 27.9 MB against 27.4 MB, musl alike); on macOS nothing.

**Proved** on `experiment/file-associations` (`.github/file_associations/`), on the runtimes of trunk's run 42089720531: a console builder app with `build_tools: true` and this Fledge as an ordinary gem, unpacked on a fresh runner in `Mein Ort/Prüfung 日本`, with no Ruby on `PATH`, no Fledge runtime anywhere (no `FLEDGE_RUNTIME_DIR`, an empty cache), and `RUBYOPT=-rbogus`, `RUBYLIB`, `GEM_HOME`, and `GEM_PATH` set, ran its own `fledge build --from` on a windowed game with `file_associations` and the installers `dmg`, `nsis`, `appimage`, and `deb`. Run 42102622918: on Windows x64 and ARM64 it wrote the `.zip` and the setup program with the builder's launchers, rcedit, and NSIS in 27 and 35 s, the game's program carried the game's version information, ran with a path, and ran again after a silent install from its setup program, which had registered the game's folder verb; on glibc Linux, x86_64 and aarch64, it wrote the archive, the AppImage, which ran extracted, and the `.deb`, in about 20 s, with `mksquashfs` and `dpkg-deb` the system's; on musl Linux, in Alpine with only `squashfs-tools` added, the archive and the AppImage, in about 7 s; and the game's folder held no `tools`. On macOS, where the builder carries no tools folder, it wrote the bundle, sealed so that `codesign --verify --deep --strict` accepts it, with `public.folder` among its document types, and the disk image, in 63 s, most of it `hdiutil`. Every job of that run passed but Windows' Delivery of `examples/windowed_app`, which hung opening a folder through the shell from PowerShell's thread; section 3's proof of it is run 42121489631, which calls the shell from a single-threaded apartment of its own and names the `Directory` class that holds the verb. Run 42128094310, on trunk 82f60e8 with the app metadata stories, passed all 21 jobs again with both features in one app: `examples/windowed_app` with its description, homepage, license, changelog, and build number beside its file associations, and a game built `--from` with the same keys, whose desktop entry carried `Comment=`, `Exec=Spiel %F`, and `MimeType=`, whose `.deb` its homepage, description, copyright, and changelog, whose Windows program its description as `Comments` and whose setup program its `URLInfoAbout` and `OpenWithProgids`, and whose `Info.plist` its build number `2.3.417` and its document types; trunk's icon-size check passed on that example.

### 5. What a framework provides, and what Fledge provides

**Fledge provides**, and a framework may rely on, as ADR 019 and ADR 029 define reliance: `fledge build --from APP`, its refusals, statuses, and output; `file_associations` and what each system makes of it; `build_tools`; that an app built `--from` keeps APP's runtime, gems, `Gemfile.lock`, and `notices/` (`NOTICES.txt`, `sbom.spdx.json`, `sources/`) unchanged, and holds the new project as plain files, so `__dir__`, `__FILE__`, `require_relative`, and backtraces name real files.

**A framework provides:** the app it publishes for people to build from, built with `fledge build` in its own CI with its gems, Fledge in its Gemfile, `build_tools`, and `file_associations`; receiving a drop (its GUI library's events) and the screen that asks for one; turning what was dropped into a project, which may mean unpacking a zip, reading its own configuration files, writing `fledge.yml` with a name and a unique identifier, and writing the program that starts the dropped content; running `fledge build --from` and saying where the output went; and everything its programs do at run time, such as where they save. The research note maps one framework's needs onto this as an example.

### 6. `--from` builds for its own platform, and another system's APP is future work

**Built.** `--from` refuses an APP built for another system than the computer's, with status 2 and a message that names both (`Fledge::BuiltApp#check`: "--from APP is an app for PLATFORM, and this computer builds for PLATFORM. Build from an app for this computer."). The decision of 2026-10-28 that each system's app is built on that system holds for everything `--from` does today, because most of what it does runs a system's own tool: `codesign` and `plutil` on macOS, rcedit and NSIS on Windows, and the installers' `hdiutil`, `makensis`, `mksquashfs`, and `dpkg-deb`.

**Not built.** The maintainer's answer to question D (decisions, 2026-11-04) lets `--from` take another system's APP, because it compiles nothing, when it adds little code and no cross-compiling. The copy-only form would put the project in place of `app/`, rename the program, rewrite `fledge.cfg`, and archive the result with the computer's own tar, and do what needs a system's own tool only on that system. It would say on standard error which steps it left undone, so a developer does not ship a Windows program that still shows APP's icon, or a macOS app whose seal is broken (a downloaded copy is refused as damaged; TN2206, TN3126). No new code would write a format or run a foreign tool: the steps that remain are the ones `fledge build` already skips for a console app, and the message is one line. Whether a framework offers this to its users is the framework's to decide. It waits for a developer or a framework to ask; the refusal stays until then, and lifting it is compatible (ADR 029, section 4: turning a refusal into an acceptance).

### 7. Reserved, and what waits

ADR 029, section 5, held `--from`, `file_associations`, and `build_tools`; the two keys are built and frozen in its section 2. A single Windows file that runs without unpacking by hand (A) waits for a developer to ask, and then a spike measures Defender's and SmartScreen's verdicts on a downloaded copy, a cold first launch, and a signature made after the payload.

### 8. What the first version builds

`fledge build --from APP [OPTIONS] [PATH]` is built as section 2 says, for the computer's own platform (`lib/fledge/built_app.rb`, `Fledge::BuiltApp`; `Fledge::Assembly` takes it in place of a runtime archive). These are its details, decided by agents:

- **How `fledge.cfg` tells the release and the platform.** The first line `fledge build` writes, a comment the launcher skips, reads `# Written by fledge build VERSION for PLATFORM: ...` (`Assembly#launch_config`). A key would be the cleaner record, as `pyvenv.cfg` has `version = ...` (PEP 405), but the launcher refuses a key it does not know (`runtime/launcher/config.c`), so a key needs a launcher of the same release, and nothing the launcher reads changes. A phone project's `fledge.cfg` keeps the plain first line: no app is built from it. An APP whose first line names no release was built before this one, and is refused as another release's.
- **Where APP is.** `--from` takes the folder `fledge build` wrote or, on macOS, the `.app` in it. The program's name comes from `fledge.cfg`'s sections, or for one program from the bundle's name or the folder's `NAME-PLATFORM`, which ADR 029, section 2, freezes.
- **What stays of APP's project.** Bundler needs more than the Gemfile and lockfile to set up APP's gems: its `.bundle/config` (frozen, the groups left out), `vendor/cache`, where Bundler finds a path gem from outside the project (ADR 020), and each folder inside the project that the lockfile's `PATH` sections name, read with `Bundler::LockfileParser`. These stay, and a PATH that holds a file at one of those paths is refused (status 1), as one holding a Gemfile is. An APP whose lockfile takes a gem from the project's own folder (`gemspec`, or `path: "."`) is refused: its project is the gem, and replacing it would take the gem away.
- **What goes of APP.** Its `fledge.cfg`, its programs, on macOS its bundle's `Info.plist`, program, seal, and `NAME.icns` (only `Contents/Resources` is copied), and on Linux each `IDENTIFIER.desktop` and `share/icons/hicolor/*/apps/IDENTIFIER.png`, with the folders they leave empty. The runtime, the gems, and `notices/` are copied unchanged; `fledge.cfg`'s `system_libraries` (ADR 030) stays, since the gems that load them do.
- **The program.** On macOS and Linux the program is a copy of APP's, which is the runtime's launcher renamed; on macOS it is signed again ad hoc first (`codesign --force --sign -`), so that a console app made from a bundle carries no seal naming APP's identifier. On Windows APP's program holds APP's icon, company, and copyright in its resources, which rcedit can replace but not remove, and its subsystem is APP's kind; so a Windows build takes `launcher.exe` or `launcherw.exe`, rcedit, and NSIS from Fledge's runtime for the platform when the computer has it (`Runtimes#at_hand`: `FLEDGE_RUNTIME_DIR`, or the cache when it matches its pin), unpacking only those, and otherwise fails, naming where to put it. On every platform a runtime at hand also supplies the tools folder, which a Linux AppImage needs. Nothing is downloaded: the first draft of section 2 said "or a download", and it was left out, because a computer that can download a runtime can run `fledge build` itself, and the person `--from` is for may have no network.
- **Refusals.** Status 2 (`Fledge::UsageError`): `--from` without APP, with a phone, an APP that is not a folder, has no `fledge.cfg` or no program, was built by another release, or is for another platform. Status 1: a PATH with a Gemfile, `gems.rb`, or gemspec ("--from builds no gems: build this project with fledge build"); a `fledge.yml` with `programs`, `linux`, `ios`, or `android`; a PATH holding a file APP's Bundler needs; APP's project as its own gem; on Windows, no runtime at hand.

**Proved inside a built app.** Run 42059830583 on `experiment/build-from` (`.github/build_from/`), every job green on all seven desktop platforms: a console app whose Gemfile holds this Fledge as an ordinary gem (packed with `gem build`, unpacked beside it, `path: "../fledge"`, so in the app's `vendor/cache`), built with `fledge build`, was unpacked on a fresh runner that never ran `fledge build`, in `Mein Ort/Prüfung 日本`, with no Ruby on `PATH` (only `tar` and `gzip`, and `codesign` on macOS; on Windows `System32`) and `RUBYOPT=-rbogus`, `RUBYLIB`, `GEM_HOME`, and `GEM_PATH` set. Its program ran the `fledge` that RubyGems wrote into `Gem.bindir` (`bin/fledge`, `ruby/bin/fledge.bat` on Windows) with `build --from` on its own folder and a project beside it, in 2.3 to 4.9 s on macOS and Linux and 8.6 and 16.7 s on Windows, and the app it wrote ran from its unpacked archive, reading its asset through `__dir__`, with the game's name in its Windows version information. On Windows the first attempt, with no runtime at hand, failed with status 1 naming where to put one; the second had `FLEDGE_RUNTIME_DIR`. Two things the proof met:

- **Fixed, Fledge's.** Windows' `tar.exe` reads its arguments in the ANSI code page, so it could not change into a folder named outside ASCII, and its error, in the console's code page, raised an encoding error in `Fledge::Command`. Fledge now runs tar in the folder that holds what it packs, and on Windows unpacks and reads an archive through standard input (`Fledge::Archive`), and quotes a tool's output with what is not UTF-8 replaced. A Windows app whose own name is outside the ANSI code page is still named to tar as an argument when packed; no test covers it.
- **The framework's, not Fledge's.** The person's `RUBYOPT` and `RUBYLIB` reach a child Ruby as under `bundle exec`, which records them in `BUNDLER_ORIG_RUBYOPT` (Parity; ADR 020, section 6), so a `RUBYOPT=-rbogus` stops `fledge` run as a child with a `LoadError`, as it would stop it under `bundle exec`. The proof's program runs `fledge` with `RUBYOPT=-rbundler/setup` and no `RUBYLIB`, the app's own Bundler setup without the person's additions; a framework does the same, or runs `Fledge::CLI` in its own process.

The first version had neither `build_tools` nor `file_associations`, so an app that ran `fledge build --from` from inside itself on Windows, or for an AppImage on Linux, needed the runtime archive beside it. Both are built now, as sections 3 and 4 record.

## Consequences

- A person with nothing installed but a framework's app can make an app of their own, on that platform, from a project that needs no gems beyond the ones that app ships, and gets what `fledge build` would have built.
- Fledge gains an option and two keys to freeze (ADR 029, section 2). The job the Delivery stage still lacks on `trunk`: build an app with `build_tools`, run `fledge build --from` inside it on a fresh runner with no Ruby, and deliver the result on another. The runs of sections 4 and 8 did the first two steps on the `experiment/build-from` and `experiment/file-associations` branches, whose scripts are not in `trunk`'s CI; no recorded run delivers the result on a second runner. `test/build_from_test.rb` and `test/built_app_test.rb` hold the command's behavior and refusals on every push, and `trunk`'s Delivery scripts read back the file associations of `examples/windowed_app`.
- Every app built `--from` is as large as APP (63 MB in the spike on macOS), and carries Fledge's own Ruby code as a gem, under the same terms as its launcher (AGENTS.md, Licensing).
- An unsigned downloaded APP meets Gatekeeper's and SmartScreen's warnings before anyone builds from it; signing waits on Plan 003's "Notarization and real trust chains". What `--from` writes on the person's computer carries no quarantine (the spike's `xattr` was empty); a copy others download does.
- Not proven: a drop on the app's icon in Finder or the Dock, and a GUI library's drop event in a Fledge app (Launch Services' offer and `open -a` are proved, section 3); a file manager's double-click on Linux; a downloaded result under Gatekeeper and SmartScreen; an AppImage built `--from` on a computer without squashfs-tools, which fails naming it.
