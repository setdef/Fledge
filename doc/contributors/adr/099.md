# ADR 099: On a phone, Ruby is a shared library Fledge builds from source, with each of its extensions a file

## Context and Problem Statement

Phones are in scope: iOS, iPadOS, and Android, aimed at 1.0 unless they prove incredibly burdensome (`decisions.md`, 2026-10-27).

A phone runs no program of Fledge's own. An iOS app is one signed binary in a bundle, which may load code only from frameworks the bundle carries, never a loose library. An Android app is an APK whose native code Java loads, and whose assets are not files. So a phone's runtime cannot be a launcher with a relocatable Ruby beside it, as a desktop's is (ADR 001). Ruby has to be a library, linked into an app that Xcode or Gradle builds. No one publishes a prebuilt CRuby for either system. Where does the phone's Ruby come from, and what shape does it take?

The shape matters to the app. With Ruby's own extensions linked into the library, `$LOADED_FEATURES` records them under bare names and `archdir` holds no extension, where `ruby main.rb` records files under `archdir`. Android loads any library its installer extracted. iOS loads code only from frameworks, but a framework may hold one extension.

## Decision Drivers

- The app's Ruby code runs as under `ruby main.rb`: the whole standard library, every default and bundled gem (decisions 9, 10, and 20).
- "Code is a liability" (`decisions.md`, 2026-10-28): use maintained tools, and write only what none does.
- Each target is built on its own system, with that system's tools (`decisions.md`, 2026-10-28).
- Every input is pinned by version and SHA-256 (`doc/contributors/design/architecture.md`, "What the design answers to").
- The runtime carries no copyleft obligation beyond notices (decision 8).

## Considered Options

1. Build CRuby from its release tarball with Ruby's own `configure` and `make`, cross-compiled with Xcode's or the NDK's compilers, after xord/cruby's iOS recipe and Termux's Android one, and pack it as an XCFramework and an AAR: on both phones a shared library, with each of Ruby's extensions a file at the path Ruby gives it, which on iOS is a framework of its own.
2. The same build, with Ruby a static library on iOS and its extensions linked in, as Fledge's iOS runtime was until 2026-11-22.
3. Use xord/cruby's Rakefile itself (the build behind RubySketch, on the App Store).
4. Use Termux's Ruby packages (`termux-packages/packages/ruby/build.sh`).
5. Port CPython's `Apple/` and `Android/` build scripts to Ruby.

## Decision Outcome

Chosen: option 1, because it alone gives a standard Ruby that Fledge pins, with nothing it does not need, and leaves no difference from `ruby main.rb` in how Ruby's own extensions load. xord/cruby's Rakefile builds an older Ruby and folds every bundled gem into the standard library, so the gems stop being gems. Termux's packages build for Termux's own prefix, with its `libandroid-support`. CPython's scripts build Python, and porting them would be more code of Fledge's than following Ruby's own build. What is Fledge's own is the order of the maintained tools' commands, a few scripted edits to Ruby's source, and the embedding API.

Ruby's own build makes every extension, the encodings and bundled gems' among them, as a file, because the second rule of `doc/contributors/design/architecture.md`, "What the design answers to", allows no difference that can be closed. On Android the files travel as the app's gems' extensions do (`doc/contributors/design/phone-runtimes.md`, "Ruby's extensions on Android"). On iOS Ruby is `FledgeRuby.framework` and each extension is a framework of its own, which the app's bundle carries and Ruby loads from the path it expects (`doc/contributors/design/phone-runtimes.md`, "Ruby's extensions on iOS"). Option 2 lost because it left `$LOADED_FEATURES` and `archdir` different from `ruby main.rb` on iOS, a defect `doc/phones.md` had to tell developers about.

One difference remains on iOS: an extension of a gem the app itself brings is still linked into the app's executable, so `$LOADED_FEATURES` records its feature under a bare name. `doc/phones.md` says so.

Confidence: high that it works in the iOS Simulator and on Android emulators. With Xcode 27.2, on an iPhone and an iPad in the Simulator, every parity app and the iOS integration tests pass, and ruby/spec shows no unjustified difference; every example archives unsigned for devices and passes Fledge's checks of an archive's structure. Android's shared library passed the same checks on an x86-64 emulator. Unproven: a real iPhone or iPad with a framework for each extension (the device runs on record predate it), App Store Connect's acceptance of an app with 99 frameworks, and how long such an app takes to start on a device. No recorded comparison says a framework for each extension is better than another way of closing the difference; it is the way iOS allows.

### Consequences

- Good, because the runtime is Ruby's own build, with every default and bundled gem a gem, so the parity check finds only the differences a phone forces.
- Good, because on both phones Ruby's own extensions load from files under `archdir`, as under `ruby main.rb`.
- Good, because each input, from Ruby's tarball to the NDK and Gradle, is pinned in `runtime/sources.yml`.
- Good, because the iOS runtime builds on a Mac with Xcode, and the Android runtime on Linux or a Mac with Google's NDK, each with its own tools.
- Bad, because a cross build needs work Ruby's build does not do, which each new Ruby means checking again: scripted edits to its source, and a builtin binary written by a miniruby for the build machine (`doc/contributors/design/phone-runtimes.md`).
- Bad, because an iOS app carries a framework for Ruby and one for each extension, and costs more to build: the hello example holds 99 frameworks and is 65.8 MB unsigned where it was 59.0 MB, and `fledge build ios` takes 88 seconds where it took 13, most of it one `xcodebuild -create-xcframework` for each extension.
- Bad, because every extension must export its `Init_` function for Ruby to find it by name, so the iOS runtime's extensions are built without hidden visibility, and the runtime build refuses an extension that does not export it.
- Bad, because OpenSSL's symbols are global in Android's `openssl.so`, so an app that links this runtime and another OpenSSL may see them clash; it is untried. On iOS OpenSSL is in the `openssl` extension's framework, and a clash there is untried too.
- Bad, because every Android app's host `build.gradle` must set `useLegacyPackaging = true`, so that the installer extracts the extension files, and `fledge build android` refuses one that does not.
- Bad, because the Android arm64-v8a library runs on no CI runner, only on a real phone (`doc/contributors/design/public-interface.md`, "Phones").
- Bad, because CI builds both runtimes on every push, which costs macOS and Linux runner minutes.
- Neutral: App Store and Play review need the developer accounts, which are paid for (`decisions.md`, 2026-11-04). `doc/contributors/account-tests.md` lists those tests. No app with this many frameworks has been through App Review.

### Confirmation

CI's `runtime-mobile` jobs build both runtimes from `runtime/sources.yml` and run the license audit on them; the iOS build refuses an extension that does not export its `Init_` function. The `mobile-apps-ios` and `mobile-apps-android` jobs build apps on them and run each in the Simulator and on emulators with 4 KB and 16 KB pages (`tasks/mobile_parity.rb`), and the mobile parity check compares the probe with `ruby main.rb`. `test/mobile_runtime_test.rb` checks the runtimes' targets, pins, and configuration, `test/ruby_source_test.rb` the edits to Ruby's source, and `test/integration/mobile_default_gems_test.rb` the default gems of built ones: an Android runtime's in the `mobile-apps-android` jobs, and an iOS runtime's in the `mobile-tests-ios` job, which runs the iOS integration tests and fails one that would skip for want of a runtime or a tool (`FLEDGE_REQUIRE_IOS`).

## Pros and Cons of the Options

### A static Ruby on iOS, with its extensions linked in

- Good, because an app carries no framework of Ruby's, builds faster, and is smaller.
- Bad, because `$LOADED_FEATURES` records Ruby's extensions under bare names and `archdir` holds none, so an app's code that reads either sees what `ruby main.rb` does not.
