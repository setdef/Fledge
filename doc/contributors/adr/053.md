# ADR 053: A Release Publishes the Runtimes Its Commit's CI Built and Tested, and Does Not Test Them Again

## Context and Problem Statement

A release is two commits and a tag (ADR 014). The release commit's CI run on `trunk` builds every runtime and delivers each on a fresh runner. The pin commit changes only `lib/fledge/SHA256SUMS`, which no runtime contains and no job but the gate reads. The tag goes on the pin commit, and `release.yml` publishes.

Every file the tag names was already tested by those two pushes. A run of all of CI on the tag would test the same files a third time, throw its runtimes away, and draw every flaky download again. So would a full run on the pin commit, which builds and delivers its parent's files byte for byte. Each run is about 30 minutes, and flakes in jobs that publish nothing have kept a release from going out.

What must a release prove before it publishes, and which CI runs prove it?

## Decision Drivers

- Every file of a tagged commit is tested by a run that passed on every job, on `trunk`, before the tag exists.
- The runtimes published are the bytes the pins were written from (ADR 014).
- A flake in a job that builds nothing a release publishes should not stop a release.
- `release.yml` and `rake runtime:pin` must agree on which run they take.

## Considered Options

1. Look the push's runs up: the pin commit runs a short CI (the gate, and a check of its pins against its parent's runtimes), and `release.yml` requires the pin commit's run and its parent's to have passed.
2. Run all of CI again on the tag before publishing.
3. Run all of CI on the pin commit, as on any commit.
4. Skip the pin commit's run with `on.push.paths`.

## Decision Outcome

Chosen: option 1, because it keeps the guarantee of the drivers and drops only the repeats. `release.yml` asks GitHub's REST API for the tagged commit's run of `ci.yml` on a push to `trunk`, and for its parent's newest run in which every job passed, through `tasks/ci_runs.rb`, which `rake runtime:pin` uses too. The pin commit's run may count skipped jobs; its parent's may skip none. A run whose failed jobs were run again counts once they pass. `doc/contributors/design/releases.md` gives the details.

Option 4 was rejected because it skips the whole workflow and leaves the pin commit no run to look up.

Confidence: high. Every release since has gone through this path, and a tag that fails a check fails before anything is published.

### Consequences

- Good, because a release no longer runs CI for a third time, and a flake in an unrelated job between the push and the tag cannot stop it.
- Good, because the pin check CI runs and the check before publishing are one script, `.github/scripts/check-pins.sh`.
- Bad, because a change in the world between the push and the tag, such as a gem server or a mirror going down, goes unseen until `installed.yml`, which installs Fledge from the tag on every platform and delivers the examples with the published runtimes.
- Bad, because the pin check is a step of the `Changes` job, which runs on every commit, rather than a job of its own. A job of its own would be skipped on every other commit, and the release commit's run may skip none. The rule is less obvious to a reader of `ci.yml`.
- Neutral, because the runtimes still come from the release commit's run, whose artifacts GitHub keeps 14 days, so both commits come within that window.

### Confirmation

`.github/scripts/pins-only.sh` tells a pin commit apart: one parent, and `lib/fledge/SHA256SUMS` its only change. `test/integration/release_checks_test.rb` runs it and `.github/scripts/check-pins.sh` in real git repositories against assets pinned by `RuntimePins`, one of them with a pin written from other bytes, and holds `ci.yml` to skipping jobs on a pin commit and only there. `test/ci_runs_test.rb` drives `tasks/ci_runs.rb` against a loopback server that answers as GitHub's API does. A dry run of `release.yml` (`workflow_dispatch` without `publish`) runs every check against the last tag and publishes nothing.
