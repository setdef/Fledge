# ADR 028: Versions, Rubies, and Releases

## Status
Accepted (requested). Agents wrote this ADR and may change it (AGENTS.md, Questions), as long as it stays true to the maintainer's words it applies, all in `decisions.md`: of 2026-11-03, that from 1.0.0 a human releases Fledge on RubyGems.org; that a minor release may add Rubies and change only a default's patch, that Ruby does not follow SemVer, and that dropping a Ruby or an operating system version takes a major; and that Fledge reuses RatatuiRuby's and Rooibos's version and git tooling, which works differently before 1.0.0 and after it. The first draft, of 2026-11-03, had a default Ruby that switched once a year; section 3 replaces it, and section 5 drops its exception for a floor a platform's owner forces.

## Date
2026-11-03, rewritten 2026-11-04.

## Context

1.0 tells developers the CLI, `fledge.yml`, and what a built app contains will not change without a major version (ADR 029). After 1.0 a developer installs Fledge from RubyGems.org and writes a constraint such as `~> 1.2` in a Gemfile, so the version number is something Bundler reads on every update.

Four ways to time major versions were weighed in conversation:

1. A major on a schedule, like Ember's, sweeping every deprecation and default switch into it.
2. No majors for as long as possible, with breaking changes behind opt-in flags.
3. A major as a marketing event.
4. A major whenever a breaking change is ready, with the number a non-event.

Facts that decided between them:

- A built app is a frozen artifact. A Fledge version affects only the next build, and most breaks then fail loudly.
- Fledge embeds Ruby, OpenSSL, and libyaml. A developer who stays on an old Fledge ships apps with an old runtime, and the stores raise their requirements about once a year.
- Compatibility flags cost more than a line of code. Each one adds a key to `Fledge::Config`, the schema, the help, the docs, and a test matrix across nine targets.
- A small team cannot patch many old lines. A rule that follows live Rubies bounds the lines by the number of Rubies in use, not by how many majors Fledge has shipped.

The maintainer's words of 2026-11-03 set the rest. Ruby does not follow SemVer: 4.1 is expected to break what ran on 4.0, so an app must never move to a new Ruby minor without its developer choosing it. A minor release of Fledge may make more Rubies available and may change only the patch of a default, unless Fledge has no default at all and the developer names the version, which the maintainer called "maybe better?" and left to the agents. Dropping a Ruby, or an operating system version (macOS 26 against macOS 27, not a patch), takes a major.

## Decision

### 1. Semantic versioning, with a major whenever a break is ready

A breaking change is a change to what ADR 029, section 2, freezes. A major ships whenever a breaking change is ready. The number is a label, and no one holds a change back to shape it.

### 2. Deprecation before removal

A removal or a changed default is announced by a build-time message and a CHANGELOG entry in at least one earlier minor release. No compatibility flags are added for breaking changes: the notice warns, and the major switches.

### 3. No default Ruby: an app gets the Ruby that runs `fledge build`

Fledge has no default Ruby. An app's Ruby is the Ruby its developer runs `fledge build` with: the build uses the runtime of that Ruby's major and minor version, such as 4.0, at the patch level that Fledge release ships, and fails, naming both versions, when the release has no runtime for that minor (`Fledge::CLI::Build`, `same_ruby`). A `ruby` line in the Gemfile must still accept the runtime's Ruby, as `Fledge::Bundle` already checks.

This is how the prior art closest to Fledge works. Briefcase says that on macOS, Windows, and Linux AppImage "the version of Python used to run Briefcase will be the version of Python used by the bundled app" (Briefcase, "Native System Packages", stable docs, fetched 2026-11-04), with a support package per Python minor. PyInstaller builds with the interpreter that runs it, and its usage guide recommends a virtual environment for each Python you build for (pyinstaller.org, "Using PyInstaller", fetched 2026-11-04). python-build-standalone publishes a build of each Python version and has no default; the tool that picks one decides.

The other designs weighed:

- **Require a `ruby` line in the Gemfile**, as Heroku recommends. Heroku has to ask: no Ruby runs the app before Heroku builds it, so without the Gemfile's `ruby` line, or Gemfile.lock's `RUBY VERSION`, Heroku uses a default that "isn't sticky" and changes under the app (Heroku Dev Center, "Ruby Support", fetched 2026-11-04). Fledge always runs inside a Ruby, the developer's. Requiring the line would make the README's greeter, a lone `main.rb` with no Gemfile, write a Gemfile only to say what the Ruby running it already says.
- **Read `.ruby-version` in Fledge.** mise, asdf (as `.tool-versions`), rbenv, chruby, rv, and `ruby/setup-ruby` already read it to choose the Ruby that runs Fledge, and Bundler 4.0.20 reads it for `ruby file: ".ruby-version"` (`lib/bundler/ruby_dsl.rb`, `normalize_ruby_file`). A second reader in Fledge would only repeat what those tools already did.
- **A `ruby` key in `fledge.yml`, written by a generator such as `fledge init`.** The maintainer suggested that a generated file could carry the version and change in a minor release, since an upgrade does not regenerate it. That is a new command, a new key in `Fledge::Config` and the schema, and a second statement of the app's Ruby that can disagree with the Ruby the developer runs and tests on. A `fledge.yml` that said 4.0 on a computer running 4.1 would ship code tested on 4.1 to a 4.0 runtime, the surprise Design precedence 2 forbids, unless Fledge also checked the running Ruby, which is this section's design with a file and a command added. The greeter's first run would also gain a step, `fledge init` or an error before the first build.

Each of the three adds a file or a command to say what the running Ruby already says. None makes the Ruby more certain, and each can disagree with the Ruby the developer's tests ran on. The running Ruby is the one source of truth, and the developer already names it the way Ruby developers do, with a version manager and usually `.ruby-version`. The README tells developers to keep a `.ruby-version` so that every computer that builds their app builds it with the same Ruby, and that `ruby file: ".ruby-version"` makes Bundler hold every computer to it as well. No project writes anything new, and the greeter builds as before.

The selection names a minor series, not an exact patch. A runtime carries one patch of its minor, the newest the release was built with, and Fledge moves it (section 4). Selecting an exact patch would freeze it: each Fledge release would have to keep every older patch's runtime, or refuse a developer one patch behind. A developer who wants an exact patch says so with `ruby "4.0.9"` in the Gemfile, and Bundler and Fledge then refuse every other.

What this costs. An app's Ruby follows the computer that builds it, so a laptop on 4.1 and a CI runner on 4.0 build different apps. `.ruby-version`, with `ruby file:` in the Gemfile, is the remedy, and the README gives it. A developer who moves to a new Ruby before Fledge has its runtime gets an error until a Fledge release adds one. And `fledge build` now reads the runtime's `rbconfig.rb` for an app with no Gemfile too, which takes one more pass over the runtime archive.

The maintainer's rule that generated files may change in a minor release applies to no file Fledge writes today, since this design adds no generator.

### 4. What a minor release may do with Rubies

- **Add a Ruby.** A minor release may add a runtime for a new Ruby minor, under the reserved names of ADR 029, section 5. A developer gets it by running that Ruby. A new Ruby minor is expected to break code that ran on the previous one, since Ruby does not follow SemVer, so no Fledge release ever moves an app to it: only its developer does.
- **Move a patch.** A minor or patch release may move each runtime to a newer patch of its Ruby minor, such as 4.0.9 to 4.0.10, with a CHANGELOG entry. Ruby's patch releases fix bugs and security problems.
- **Drop a Ruby.** Dropping the runtime of a Ruby minor is a major.

### 5. The platform floors

Dropping an operating system version is a major, always: the version that tells macOS 26 from macOS 27, not a patch within one. A floor is raised in a major and in nothing else. The first draft let a minor release raise a floor when Apple, Google, or Microsoft forced it; that exception is gone. If a store's rule makes Fledge drop a version, Fledge ships a major for it.

The floors by operating system version are macOS 14 on Apple silicon, Windows 10 on x64 and Windows 11 on ARM64, iOS 15, and Android 8.0 (API 26).

Linux has no single operating system version: Fledge's Linux floors are the C library's. `x86_64-linux` and `aarch64-linux` need glibc 2.39 (ADR 001, section 3), and the musl targets need musl 1.2, the series PEP 656's `musllinux_1_2` tag names and `Fledge::Platform#libraries` follows (ADR 017). The Python packaging standards name a Linux platform the same way: PEP 600's `manylinux_2_39` and PEP 656's `musllinux_1_2` tags carry the C library's major and minor version. Raising either drops whole distribution releases at once: glibc 2.40 would drop Ubuntu 24.04 and Debian 13. Each is therefore treated as an operating system version: raising glibc 2.39 or musl 1.2 is a major, and so is dropping a Linux distribution's release that meets them. A patch within a C library version is not a floor.

The same rule holds where `fledge build` runs: a release that stops building on an operating system version the last release built on is a major.

A store's yearly rule that drops no version is not a floor. Google Play's target API level and the Xcode version Apple requires for App Store uploads live in the phone templates, which ADR 029, section 3, leaves free to change in any release, with a CHANGELOG entry. Android's minimum (`minSdk`) and iOS's deployment target are floors.

### 6. Support follows live Rubies

For each Ruby minor that is not end-of-life, the last Fledge minor line to support it gets security fixes for the embedded runtime, and platform-deadline fixes where feasible, until that Ruby is end-of-life. The last minor before a Ruby is dropped says so at build time and in its CHANGELOG, and names itself the long-term line for that Ruby, with the date. That line's release branch, such as `release/1.7` (section 7), is the branch its fixes go to; it needs no branch of another name. A line that is the last for no live Ruby gets nothing. A new feature never goes to an old line.

### 7. How Fledge releases, before 1.0 and after

**Before 1.0, today.** Every commit, and every release, is on `trunk`. A release is two commits and a tag (ADR 014): the release commit, which moves `Fledge::VERSION` and the CHANGELOG, and the pin commit, which changes only `lib/fledge/SHA256SUMS` to the runtimes that commit's CI built, and which carries the tag `vX.Y.Z`. `.github/workflows/release.yml` publishes the GitHub Release with the runtimes when the tag is pushed, and `installed.yml` installs Fledge from the tag and delivers hello. Agents push `trunk`, tag, and create the Release (decision 6), and never publish to RubyGems.org. There are no release branches: before 1.0 there is no older series to patch. RatatuiRuby's tooling releases a prerelease the same way, on trunk with no branch (`ratatui_ruby-devtools` at `1a31a719`, `lib/ratatui_ruby/devtools/tasks/bump/unbranched_release.rb`).

**From 1.0.** Fledge follows RatatuiRuby's model (`~/Developer/ratatui_ruby/doc/contributors/releasing.md` at `10dd1800`), which Rooibos uses through `ratatui_ruby-devtools` (Rooibos's `Rakefile` at `54a73ebb`, `RatatuiRuby::Devtools.install!`):

- **Trunk-based development.** Every change lands on `trunk` first.
- **A release branch for each minor.** `rake bump:minor` or `rake bump:major` cuts `release/X.Y` from `trunk` and releases `X.Y.0` from it (RatatuiRuby's `tasks/bump/release_from_trunk.rb`); devtools' `BumpWorkflow.to` (`lib/ratatui_ruby/devtools/tasks/bump/bump_workflow.rb`, lines 19 to 33) picks the workflow by the version, so a prerelease stays unbranched and a `.0` opens a series.
- **Backports by cherry-pick.** A fix lands on `trunk`, then goes to each release branch that needs it with `git cherry-pick -x`, which records the commit it came from. `rake bump:patch` releases it from the branch (`tasks/bump/patch_release.rb`). This is how section 6's long-term lines get their fixes.
- **SemVer tags.** Every release has a tag, `vX.Y.Z`, or `v1.0.0-beta.1` for a prerelease, not the `v1.0.0.pre.beta.1` RubyGems would write: the release task replaces Bundler's normalized tag with the SemVer one (RatatuiRuby's `tasks/release.rake`; devtools' `lib/ratatui_ruby/devtools/tasks/release_tasks.rb`).
- **`stable`.** A branch that points at the newest stable release, moved by the release task, and the repository's default branch.
- **The CHANGELOG.** Each release branch keeps its own; when a final release ships, its section is consolidated on the branch and copied to `trunk`.

Three things differ from RatatuiRuby. First, a human publishes. `rake release` runs Bundler's release task, which pushes the gem to RubyGems.org, so the maintainer runs it (decisions, 2026-11-02, later, and 2026-11-03). Agents prepare the release: the bump, the branch, the backports, the CHANGELOG, and green CI. The tag and the move of `stable`, which `rake release` makes, come with the human's run, and so does the force-push that moves `stable`, which AGENTS.md otherwise forbids agents. Second, Fledge does not yet have the tooling: `ratatui_ruby-devtools` is being extracted by RatatuiRuby's agents, and once that is done its parts outside the RatatuiRuby ecosystem are to be extracted again for Fledge, Lota, and the rest; nothing is ported or copied before then, and Fledge's agents do that second extraction only when the maintainer explicitly instructs it (decisions, 2026-11-07). Third, Fledge is one gem that is pure Ruby, and its runtimes are not in it. A runtime is Fledge's own build (a launcher and a `bin/ruby` with Fledge's code in them, pruned, audited, with notices and the LGPL sources beside it), which CI makes once for each target and which `fledge build` downloads and checks against the pins the gem carries (ADR 014). RatatuiRuby's platform gems carry compiled code its own Ruby loads; a runtime is files Fledge copies into an app, so there is no payload to build per platform inside the gem. A gem on RubyGems.org is one more way to find a release. The tag and the GitHub Release stay, because they hold the runtimes and the LGPL sources that each app's notices name (ADR 004, section 5). Where else the runtimes can be had, so that a change in a host's terms costs a URL and not a rewrite, is Plan 003's story "Fledge on RubyGems.org, and runtimes that do not depend on one host".

The schema of `fledge.yml` names its release's tag (ADR 023, section 3). This model keeps a tag on every release, so that address exists for every release from 1.0 too.

## Consequences

- No project names its Ruby anywhere new. The greeter, a lone `main.rb`, builds as before, and an app's Ruby is the one its developer tested it on, at Fledge's patch.
- Fledge never moves an app to a new Ruby minor, in any release. A new Ruby reaches apps as fast as developers adopt it, with no default to switch and no yearly major for it.
- A Fledge release that carries two Ruby minors builds twice the runtimes in every CI run and every release, and the reserved asset names of ADR 029, section 5, come into use. Until then, each release carries one.
- At any time the patched lines number about one per live Ruby minor, so three or four, however high the Fledge number climbs.
- A developer who wants the Ruby of an older line moves to that line's last release. If several majors lie between, the deprecation notices and per-major migration notes carry the cost.
- A platform-deadline fix may need newer toolchains and rebuilt runtimes on an old line. The promise there is best effort, and the CHANGELOG says when a fix cannot be made.
- A store that forces a floor up forces a major. That can mean a major in a year with no other break, and the number is a label (section 1).
- Plan 003's stories "Fledge on RubyGems.org, and runtimes that do not depend on one host" and "1.0" wait for the extracted tooling: `rake bump:*`, `rake release`'s tag handling, and `release:update_stable` (decisions, 2026-11-07).

## Not decided

- The minimum time between a deprecation and its removal, beyond one minor release.
- Whether `fledge build` should warn when a newer patch of its embedded Ruby exists. Bundler already reports newer gems, so only the embedded runtime and platform deadlines would be new; there is no evidence yet that developers need it.
- Which patch of musl 1.2 the musl runtimes need. They are built and delivered on Alpine 3.24's musl (ADR 017), and no older one has been tried; the README names no musl version until one has.
- The exact end-of-life dates, which come from ruby-lang.org's maintenance page when a line becomes a long-term line.
