# ADR 048: Take Each System's Icon Files From the Developer

## Context and Problem Statement

Each system wants an app's icon in its own format: macOS an `.icns`, Windows a multi-size `.ico`, and Linux desktops PNGs of several sizes in an icon theme. Fledge read one PNG of 1024 pixels and wrote every size and format itself: a PNG decoder for every color type and interlacing, an area-averaging resampler, and `.icns`, `.ico`, and PNG writers, about 600 lines.

The maintainer's words of 2026-10-28 (`decisions.md`): "Code is a liability and we should _not_ have 4k+ lines of things we could use existing tools for." Decision 18 makes the icon the developer's to control. Where should an app's icon files come from?

## Decision Drivers

- No image codec of Fledge's own (AGENTS.md, How to work).
- No tool a developer may lack, of different versions on different computers.
- Each system's icon looks as its developer made it, at every size.
- Prior art: Briefcase's `icon` is a path without an extension, to which it adds each platform's; Tauri's bundler takes the files its `bundle.icon` lists, which a separate `tauri icon` command generates.

## Considered Options

1. Each system's own icon files, made by the developer and named by one path without an extension, as Briefcase names them.
2. ImageMagick, which writes every format with `-define icon:auto-resize`.
3. libvips.
4. chunky_png (MIT), a pure-Ruby PNG codec.
5. icoutils' `icotool`.
6. macOS's own `sips` and `iconutil`.
7. Fledge's own PNG codec, resampler, and icon writers.

## Decision Outcome

Chosen: option 1, because it is less code than any of the others and is what Briefcase and Tauri's bundler ask. ImageMagick is a large program a developer may not have, of different major versions on different Linux distributions, so a pin would be a wish. libvips writes no `.ico`. chunky_png's bilinear resampling blurs an icon shrunk from 1024 to 16 pixels unless Fledge resamples in steps itself, and it writes neither `.icns` nor `.ico`. `icotool` runs only on Linux and makes only `.ico`. `sips` and `iconutil` make `.icns` and leave Windows and Linux with nothing. Fledge's own code is what the maintainer's words remove.

`icon: icons/app` in `fledge.yml` names `icons/app.icns` for macOS, `icons/app.ico` for Windows, and `icons/app-16.png` to `icons/app-512.png` for Linux, Briefcase's six sizes. A missing file fails that platform's build, saying what it needs and how to make it. A Linux build ships each size there is, names the rest on standard error, and needs at least one, since the Icon Theme Specification requires no set of sizes and scales the nearest size a theme has. Fledge reads none of these formats and checks no sizes.

Confidence: high. Delivery reads each system's icon back with that system's tools.

### Consequences

- Good, because about 600 lines of codec and resampler are gone, and each icon is exactly what its developer drew at each size.
- Bad, because a developer makes three kinds of file, where one PNG was enough; `iconutil -c icns` on any Mac makes the `.icns` from an `.iconset`.
- Bad, because Fledge cannot tell a developer that an `.ico` lacks a size Windows shows; a missing size shows scaled.
- Neutral, because the same key names a phone's icons too (`doc/contributors/design/phones.md`).

### Confirmation

`test/desktop_entry_test.rb`, `test/app_image_test.rb`, `test/deb_test.rb`, and `test/config_test.rb` hold the file names, the Linux sizes, and the refusal of an `icon` with an extension. `.github/scripts/check-icon-sizes.sh` builds `examples/windowed_app` with three of the six Linux sizes and checks the warning, the icons in its `.deb` and AppImage, and the failure with none. Delivery checks that Windows extracts the program's icon and that a bundle names its `.icns`.
