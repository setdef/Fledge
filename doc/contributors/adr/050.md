# ADR 050: Sign a Mac App With the Hardened Runtime and Briefcase's Two Entitlements

## Context and Problem Statement

Apple notarizes only code signed with a Developer ID, a secure timestamp, and the hardened runtime ("Resolving common notarization issues"). The hardened runtime forbids, unless an entitlement grants it, memory that is writable and then executable, and loading a library signed by another team. Ruby needs both at times. YJIT, which an app may enable as Rails does (ADR 003), reserves its code region with `mmap(PROT_NONE, MAP_PRIVATE | MAP_ANONYMOUS)` and makes it executable with `mprotect(PROT_READ | PROT_EXEC)`, with no `MAP_JIT` (`jit.c`, `rb_jit_reserve_addr_space` and `rb_jit_mark_executable`, at Ruby 4.1.0-preview1). And a gem may load a library from outside the app, through FFI or as a plug-in.

Apple's entitlements: `com.apple.security.cs.allow-unsigned-executable-memory` "indicates whether the app may create writable and executable memory without using the MAP_JIT flag"; `com.apple.security.cs.allow-jit` covers memory made with `MAP_JIT`; `com.apple.security.cs.disable-library-validation` lets a process load a library its team did not sign. Which should `--sign` (ADR 016) sign a Mac app's code with?

## Decision Drivers

- Notarization needs the hardened runtime.
- An app that enables YJIT, or a gem that loads an outside library, keeps working once signed.
- The fewest exceptions that keep Ruby working, from what Apple documents, not what a self-signed run happens to tolerate.
- Any Mac, with no certificate, proves the same signing a Developer ID gets.

## Considered Options

1. The hardened runtime with Briefcase's two entitlements, `allow-unsigned-executable-memory` and `disable-library-validation`, on every Mach-O file, for every identity, the ad hoc one (`--sign -`) included.
2. `allow-jit`, as Tebako's signing specification gives YJIT "for MAP_JIT on arm64".
3. The hardened runtime with no entitlement.
4. The ad hoc identity signed without the hardened runtime, as Briefcase signs it.

## Decision Outcome

Chosen: option 1, because `allow-unsigned-executable-memory` is the entitlement Apple names for memory made without `MAP_JIT`, as YJIT makes it, and `disable-library-validation` is what lets Ruby load a library its app did not sign. Option 2 grants the wrong one: Ruby's source does not use `MAP_JIT`, so `allow-jit` covers none of YJIT's memory. Option 3 passed in CI, where YJIT wrote code under a self-signed identity's hardened runtime with no entitlement; but Apple documents the entitlement for this memory, Briefcase notarizes apps that carry it, and dropping it could break an app that enables YJIT under a Developer ID. Option 4 would leave the ad hoc run proving less than a Developer ID gets.

The entitlements are `lib/fledge/templates/macos/entitlements.plist`. A bundle Fledge signs without `--sign` keeps a plain ad hoc signature, with no hardened runtime, which Apple Silicon needs to run it at all (`doc/contributors/design/desktop-apps.md`).

Confidence: medium. Apple's documents settle which entitlement applies, but not whether the kernel treats a Developer ID's hardened runtime more strictly than a self-signed one's. Only the maintainer's Developer ID run answers that.

### Consequences

- Good, because a signed app runs YJIT and loads outside libraries under the hardened runtime, as notarization requires.
- Good, because `--sign -` on any Mac proves the same signing as a Developer ID, with no certificate.
- Bad, because both entitlements loosen the hardened runtime for every app, whether or not it enables YJIT or loads an outside library.
- Bad, because an app that needs other entitlements (the camera, the microphone) has no way to add them yet.
- Neutral, because if a Developer ID run shows YJIT writing code without the entitlement, a later change may drop it; `examples/windowed_app`'s report says whether YJIT wrote code.

### Confirmation

`test/mac_signing_test.rb` holds the options and the entitlements file. `.github/scripts/deliver-signed.sh` checks, on a fresh Mac runner, the hardened runtime and a timestamp on every Mach-O file, the entitlements, and YJIT writing code in the signed app. The Developer ID question is the optional step of `doc/contributors/signing-test.md`, which signs the app again without entitlements and runs its YJIT check (`doc/contributors/account-tests.md`).

## More Information

- Apple's "Hardened Runtime" page says the exceptions are entitlements of the executable, which its libraries inherit. "Resolving common notarization issues" names a missing hardened runtime and `get-task-allow`, not a runtime exception, among what fails.
- Briefcase grants the same two entitlements to every macOS app (`src/briefcase/platforms/macOS/__init__.py`, lines 463 to 467, beeware/briefcase at 0bdaaf5).
- The order of signing and the options codesign gets: `doc/contributors/design/signing.md`, "Signing on macOS".
