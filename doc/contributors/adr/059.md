# ADR 059: A phone app's standard streams reach the system log line by line

## Context and Problem Statement

iOS and Android discard what an app writes to standard output and standard error. On a phone the system log (os_log, logcat) is the only place an app's output can go, and a developer reads it to watch the app run, as one watches a terminal under `ruby main.rb`.

Two things decide whether that works. Where the output is taken: Ruby's `$stdout`, or the process's descriptors 1 and 2, which a C extension and Ruby's own warnings write to as well. And when it arrives: Ruby writes through to a terminal, but buffers standard output when it is a pipe, until the buffer fills or the program ends (`io.c`, `io_binwrite_requires_flush_write`, lines 1941 to 1954 at Ruby 4.1.0-preview1). A game a framework ran in the iPad Simulator logged nothing until it ended, until the game set `$stdout.sync = true` itself. How do a phone app's streams reach the log, and when?

## Decision Drivers

- Everything the app prints reaches the log, its C extensions' output and Ruby's warnings included.
- A line reaches the log when it is printed, as it reaches a terminal (precedence 2: no surprise against `ruby main.rb`).
- `$stdout.tty?` stays false: a phone has no terminal, and a library that colors terminal output must not send escape codes into the log.
- Prior art: Briefcase's iOS host unbuffers Python's streams, "We want output to appears in the log immediately" (`config.buffered_stdio = 0`); CPython's iOS and Android streams are line-buffered and never claim to be a terminal; Chaquopy's Android stream flushes at each newline.

## Considered Options

1. The embedding API forwards descriptors 1 and 2, each the write end of a pipe a thread reads line by line into the log; it sets `$stdout.sync = true` whenever descriptor 1 is not a terminal; and on Apple's systems it leaves the streams alone when `OS_ACTIVITY_DT_MODE` is set.
2. Replace only the language's stream objects with ones that call the log, as CPython's iOS support replaces `sys.stdout` and `sys.stderr`.
3. Make descriptor 1 a pseudo-terminal, which Ruby writes through to.
4. Set `FMODE_TTY` on `$stdout` without a terminal.
5. Leave `$stdout.sync` to each developer.

## Decision Outcome

Chosen: option 1, because forwarding the descriptors catches what C extensions and Ruby itself write, which option 2 misses. Sync mode is what a developer would write, through Ruby's own method, and costs one write call per `puts`, as a terminal does. A pseudo-terminal would turn `$stdout.tty?` true, so libraries would color their output and `IO#winsize` would answer for a window that does not exist, and whether iOS's sandbox lets an app open one is unknown. Ruby's header forbids setting `FMODE_TTY` ("You cannot change this", `include/ruby/io.h`, lines 188 to 192), through a field it deprecates. Leaving it to each developer is what surprised the framework's.

Forwarding the descriptors made a loop that option 2 never meets. `OS_ACTIVITY_DT_MODE` makes the unified log copy each entry to standard error for a developer tool that reads the app's streams. Under it, the forwarding thread read the log's copy back from its own pipe and logged it again, nested in the next copy, until the pipe filled and Ruby's `puts` blocked. So on Apple's systems `fledge_ruby_forward_output` does nothing when the variable is present, whatever its value: the tool that asked for the copy reads the streams itself. Android's logcat copies nothing, so it always forwards.

Confidence: high. CI and the experiments showed a line printed before a sleep reaching the log during it, on iPhone and iPad Simulators and on Android emulators, and each app's line printed once under `OS_ACTIVITY_DT_MODE`.

### Consequences

- Good, because a developer watches the app's lines in Console, `log stream`, or `adb logcat` as they are printed.
- Good, because the forwarding's lines reach the log away from Xcode as from it, and a developer tool that sets the variable shows each line once, from the app's streams.
- Neutral: how `$stdout` writes through, with `$stdout.sync` false as under `ruby main.rb`, is ADR 076's.
- Bad, because the rule rests on `OS_ACTIVITY_DT_MODE`, which Apple calls "an implementation detail" (Quinn, Apple DTS, developer.apple.com/forums/thread/705868). If Apple changes it, the check changes with it.
- Bad, because a log entry holds less than a long line, so such a line goes as several entries in a row.

### Confirmation

`test/integration/mobile_output_test.rb` runs `output.c` and `apple.c` with the real `os_log` on a Mac, with and without the variable, and runs `fledge_ruby.c` linked with the test Ruby to check that a line printed before a sleep reaches the log during it. The mobile parity check compares `$stdout.sync` on both phones (ADR 076).
