# Plan 001: Ship an App That Does Nothing

## Status

Done (requested). All three operating systems deliver: macOS (`arm64-darwin`), Linux (`x86_64-linux`, `aarch64-linux`), and Windows (`x64-mingw-ucrt`) are built end to end, with pinned sources, launchers, runtimes in CI, `fledge build` from one Linux runner, Delivery on fresh runners, the parity check (ADR 003), and the license audit (ADR 004). The first pre-release, [`v0.0.1.pre.1`](https://github.com/setdef/Fledge/releases/tag/v0.0.1.pre.1), shipped the skeleton through its real pipeline on 2026-10-27: `release.yml` published the four runtimes with their SBOMs, NOTICES, LGPL sources, and `SHA256SUMS`, and `installed.yml` installed Fledge from the tag with Bundler on a fresh runner of each platform, built hello with runtimes downloaded from the release, and delivered it, as was also done by hand on an Apple Silicon Mac. Agents wrote this plan and may change it (decision 15 in `doc/contributors/decisions.md`).

ADR 001 decides what Fledge is: a launcher that embeds CRuby, prebuilt runtimes per platform from pinned Ruby builds, and `fledge build` copying an app into them. This plan decides the order of the work.

The first slice is a walking skeleton: the thinnest path through every layer, from a folder with a `main.rb` to an archive someone with no Ruby downloads, unpacks, and runs, shipped through the same pipeline every later change will use. It does nothing a person would want. Shipping nothing first forces every decision that is cheap now and expensive later (where Ruby comes from, how the launcher finds it, what a runtime holds, how CI proves an app runs where no Ruby is) while the stakes are lowest. Every later story adds one capability to a pipeline that already delivers.

## The app: hello

`examples/hello/main.rb` prints one line and exits with status 0:

```
Hello from Ruby 4.0.9 on PLATFORM
```

`PLATFORM` is `RUBY_PLATFORM`, as the runtime reports it: `arm64-darwin23` (rv-ruby builds for macOS 14, Darwin 23), `x86_64-linux`, `aarch64-linux`, or `x64-mingw-ucrt`. The plan first said the target's RubyGems name, but Ruby has no value that is exactly that on macOS: `RUBY_PLATFORM` and `Gem::Platform.local` both carry the Darwin version rv-ruby was built for. `RUBY_PLATFORM` is Ruby's own name for where it runs, which the Windows spike printed too, so hello prints it. Given a number, hello exits with it (`hello 3` exits 3), so Delivery can check that an app's exit status reaches whoever ran it. Before it prints, the app requires `json` and round-trips a value through `JSON.generate` and `JSON.parse`, because `json` is a C extension in Ruby's standard library: if extensions load from the runtime, this proves it, and if they don't, the app fails with a nonzero status instead of printing.

## Spikes: answer the risky questions with throwaway code

Each spike is a small experiment that answers one question, then gets thrown away. The answer goes in this plan.

1. **Does a Unix launcher run an app on rv-ruby, from anywhere it is unpacked?** Done. Answer: yes, on `arm64-darwin`, `x86_64-linux`, and `aarch64-linux`. With libruby linked statically, the launcher *is* the Ruby interpreter, and rv-ruby's `--enable-load-relative` makes Ruby derive its prefix from the launcher's own folder, so the layout is `NAME`, `lib/ruby/4.0.0`, `lib/ruby/gems/4.0.0`, `libexec/cert.pem`, and `app/` side by side, with no `-I` for the standard library and no path baked in. The folder may not be named `bin` or `lib`, where Ruby would take its parent as the prefix. On macOS the link needs `-Wl,-force_load` of libruby; on Linux, `-rdynamic`, `--whole-archive`, and `-static-libgcc`. On Linux, Ruby recognizes the program that holds libruby by comparing pointers with the original `argv[0]`, so the launcher passes that pointer on. A bare C locale (`env -i`, apps started by a desktop) breaks a non-ASCII install path, so the launcher coerces it to UTF-8, as Python's PEP 538 does. Scrubbing `RUBY*`, `GEM_*`, `GEMRC`, `BUNDLE_*`, and `BUNDLER_*` (rubygems.rb requires `$BUNDLER_SETUP`) and keeping RubyGems out of `~/.gem` made output byte-identical in clean and hostile environments. rv-ruby's Linux builds need glibc 2.39 or newer, a floor the maintainer accepted (decision 7); its musl builds cannot be used (Plan 002, "musl Linux"). Built-app sizes at the time: a macOS app folder was 28 MB (8.6 MB archived) and a Linux one 31 MB on x86_64 and 34 MB on aarch64 (10 MB archived), without bundled gems, which runtimes now ship (ADR 003).
2. **Does a Windows launcher run an app on RubyInstaller's Ruby?** Done. Answer: yes, on `x64-mingw-ucrt`, with RubyInstaller 4.0.9-1 (its `.7z`, SHA-256 `1dc07159…f47b4`, signature verified against RubyInstaller's package signing key). The layout is `NAME.exe` at the top, `app\`, and RubyInstaller's tree in `ruby\` with its shape unchanged, because Ruby derives its prefix from its DLL's path and the DLL's own dependencies load through manifests that name their folders. The launcher cannot import the DLL, since Windows never searches a subfolder for an executable's imports (an import-linked launcher at the top fails with `0xC0000135`), so it loads `ruby\bin\x64-ucrt-ruby400.dll` by absolute path with `LoadLibraryExW` and looks up `ruby_sysinit`, `ruby_init_stack`, `ruby_init`, `ruby_options`, and `ruby_run_node`; it retries with a `\\?\` path past `MAX_PATH`, where `LoadLibraryExW` otherwise fails with error 206. It uses `wmain` and `-municode`, as `ruby.exe` does, though `ruby_sysinit` rebuilds a UTF-8 argv from `GetCommandLineW` either way, and embeds a `longPathAware` manifest, without which RubyGems fails at long paths; the manifest is a resource, so a renamed copy keeps it. It must be built for UCRT, RubyInstaller's C runtime, so that `_wputenv_s` and `SetEnvironmentVariableW` clear the copies of the environment Ruby reads before and after it initializes. RubyInstaller's `rubygems/defaults/operating_system.rb` let a json 99 in `Gem.user_dir` crash the app even with `GEM_HOME` and `GEM_PATH` scrubbed, and hunts for MSYS2; Fledge's own file replaces it, and OpenSSL still loads, through manifests alone. It cross-compiles: llvm-mingw's UCRT toolchain on Linux builds a launcher that passes the same Delivery, from Ruby's headers alone (Ubuntu's own mingw-w64 targets msvcrt and cannot be used). A runtime is 28 MB in about 1,030 files, and `hello-x64-mingw-ucrt.zip` 10 MB. Exit statuses reach the caller (`exit 3` exits 3, an uncaught exception 1), and a launcher failure exits 70. A GUI-subsystem build (`-DFLEDGE_WINDOWED`, `-mwindows`) runs too, but PowerShell's `&` neither waits for it nor captures its output, so Delivery runs programs through .NET's `Process`.

## The walking skeleton, layer by layer

- **Pinned Ruby sources.** Done. `runtime/sources.yml` records, per target, the URL and SHA-256 of rv-ruby `20261023`'s build, or for `x64-mingw-ucrt` RubyInstaller 4.0.9-1's with its signature and signing key, and of libxcrypt 4.5.2's source and llvm-mingw `20261020` for each computer that builds the Windows runtime; `rake runtime` downloads them into `tmp/downloads/` through `Fledge::Download`, which fails on a mismatch and keeps nothing, and checks RubyInstaller's signature with `gpgv` on every build.
- **The C launcher.** Done, in `runtime/launcher/`: `unix.c` holds what macOS and Linux share and starts Ruby as Ruby's own `main.c` does; `darwin.c` and `linux.c` each find the executable (`_NSGetExecutablePath`, `/proc/self/exe`); `windows.c` is the Windows launcher (spike 2's answer, made production code), with `windows.rc` embedding `windows.manifest`; `scrub.c` holds the rule all of them share. It scrubs every variable starting `RUBY`, `GEM_`, `GEMRC`, `BUNDLE_`, or `BUNDLER_`, and RubyInstaller's `RI_FORCE_PATH_FOR_DLL`, before Ruby starts (on Windows in any case, from both copies of the environment), coerces a C locale to UTF-8, and runs `main.rb` with `--disable=rubyopt` on the main thread, as `ruby main.rb` would (it first passed `--yjit` and `-I ROOT/app`, which ADR 003 removed), putting the person's Ruby environment back once Ruby has booted. Its exit status is the app's, or 66 or 70 from sysexits when it cannot start the app (ADR 002). Each runtime also carries `rubygems/defaults/operating_system.rb`, which keeps RubyGems to the runtime's own gems instead of putting `Gem.user_dir` first, as the Windows spike does too; a fake json gem in `~/.gem` or `~/.local/share/gem` no longer loads. It builds with `-Wall -Wextra -Werror -Wpedantic` and more, under the compiler's static analyzer (`clang --analyze` on macOS and for Windows, `gcc -fanalyzer` on Linux) in `rake runtime`, and clang-format checks it in the gate. The Windows build also compiles the windowed launcher, which no runtime ships yet, and checks both programs' PE subsystems and that they import only Windows' kernel and UCRT (and USER32, windowed).
- **A runtime per target, built in CI.** Done. `rake runtime` (`tasks/runtime_builder.rb`, one recipe per OS) builds the launcher and Ruby's own `bin/ruby`, copies rv-ruby's standard library, default gems, and bundled gems beside them, strips debug information and stale RUNPATHs, and archives the result as `tmp/runtime/fledge-runtime-VERSION-PLATFORM.tar.gz`, with the license notices in `notices/` (Ruby, the Rust standard library in YJIT, OpenSSL, libyaml, the CA bundle, and on Linux zlib and libxcrypt, plus the launcher's own AGPL). On Linux, libxcrypt is a shared library in the runtime's `lib/`, not linked into the launcher (Plan 002, "Copyleft-free runtimes"). The Windows recipe cross-compiles the launcher with llvm-mingw and puts RubyInstaller's tree beside it in `ruby\`, pruned of what no running code reads (ADR 003), with Fledge's RubyGems defaults in place of RubyInstaller's and the notices of RubyInstaller, OpenSSL 3.6.5, libyaml, zlib, GMP, the MinGW-w64 runtime and winpthreads, and the CA bundle. CI's runtime jobs run it on `macos-15`, `ubuntu-24.04`, and `ubuntu-24.04-arm`, and the Windows one on `ubuntu-24.04`; runtimes are CI artifacts until a tag publishes them.
- **`fledge build`.** Done. It takes each `--target`'s runtime from `FLEDGE_RUNTIME_DIR`, the cache, or this version's GitHub Release (checked against its `SHA256SUMS`; ADR 001, section 2), streams it and the app into `dist/hello-PLATFORM/` and `dist/hello-PLATFORM.tar.gz` at once with the launcher renamed to `hello`, so the archive keeps executable bits and symlinks even when built on a disk that has none. For Windows it writes `dist/hello-x64-mingw-ucrt.zip` with `hello.exe`, through `Fledge::Zip`, since Ruby's standard library has no zip writer. One computer builds every target.
- **Delivery.** Done, in `.github/scripts/deliver.sh` (POSIX sh, no Ruby). On fresh `macos-15`, `ubuntu-24.04`, and `ubuntu-24.04-arm` runners, and in `debian:trixie-slim` containers with no Ruby installed at all, it unpacks the archive the build job made under a path with spaces and non-ASCII characters, runs the app with an empty `PATH` (checked to hold no `ruby`) and asserts stdout is exactly the hello line, stderr is empty, and the status is 0: in a clean environment, with a json 99 gem in `~/.gem` and in `~/.local/share/gem`, in a hostile environment (`RUBYLIB`, `RUBYOPT`, `GEM_HOME`, `GEM_PATH`, `BUNDLE_GEMFILE`, `BUNDLER_SETUP`, `RUBYGEMS_GEMDEPS`, and a bogus `libcrypt.so.2` on `LD_LIBRARY_PATH`), through a symlink found on `PATH`, and with `hello 3`, which must exit 3. It also checks that libcrypt loads from the runtime on Linux, and that the macOS launcher links only libraries macOS ships. On a fresh `windows-latest` runner, `.github/scripts/deliver.ps1` unpacks `hello-x64-mingw-ucrt.zip` with Expand-Archive under `D:\Fledge test\héllo wörld\`, keeps only Windows' own folders on `PATH` (checked with `where ruby`, `where gcc`, and `Get-Command ruby`, since the runner has Rubies and MSYS2), and runs `hello.exe` from `C:\Windows` in a clean environment, with a json 99 gem in `%USERPROFILE%\.local\share\gem` and `%USERPROFILE%\.gem`, in a hostile environment (`RUBYLIB`, `RUBYOPT`, `GEM_*`, `GEMRC`, a lowercase `bundle_gemfile`, `BUNDLER_SETUP`, `RUBY_DLL_PATH`, `RI_FORCE_PATH_FOR_DLL`), with DLLs that are not DLLs planted on `PATH` and in the current folder, as a renamed copy `héllo wörld.exe`, and with `hello 3`, asserting the same exact stdout, empty stderr, and status, and that running wrote nothing into the app's folder. `test/built_app_test.rb` runs the same build-and-run in each platform's test job, Windows included.
- **Release.** Done. `.github/workflows/release.yml` runs on a `v*` tag, calls CI, and only after every job passes, Delivery included, checks the tag against `Fledge::VERSION` and the assets against `RuntimeBuilder.release_assets`, and creates the GitHub Release (a prerelease for a version with "pre" in it) with each runtime, its SBOM and NOTICES, the LGPL source bundles, and a `SHA256SUMS`; then `.github/workflows/installed.yml` installs Fledge from the tag on each platform and delivers hello with the published runtimes. Never RubyGems.org (ADR 001, section 7). Before 1.0, agents may tag and release (decision 6); `v0.0.1.pre.1` was the first.
- **The gates.** The gem's gate exists from the first commit: tests, RuboCop, RubyCritic, RDoc coverage, REUSE, actionlint and shellcheck (now over `.github/scripts` too), Steep with no `untyped`, signature parity, and the package check. The launcher's C gates are compiler warnings as errors and the compiler's static analyzer in `rake runtime`, and clang-format (pinned in `mise.toml`) in the gate.

**Done when:** on every push, Delivery passes on all three operating systems (it does since Windows joined): `examples/hello`, built by `fledge build`, unpacked on a fresh runner with no Ruby, prints `Hello from Ruby 4.0.9 on PLATFORM` and exits 0 on `arm64-darwin`, `x86_64-linux`, and `x64-mingw-ucrt`; and every gate passes with zero errors and zero warnings.

## Out of scope for the skeleton

- macOS `.app` bundles, and the windowed kind on every OS.
- Code signing and notarization.
- Vendoring an app's gems (a Gemfile), and gems with native extensions.
- A `fledge doctor` command that explains why an app won't build.
- Framework wrappers (Lota, Tokra, Rooibos) calling Fledge.
- More targets (`x86_64-darwin`, musl Linux, Windows on ARM). `aarch64-linux` joined the skeleton, since rv-ruby builds it and GitHub has arm64 Linux runners; musl and Windows on ARM are Plan 002 stories.
- Building Ruby ourselves; that is ADR 001's fallback if a source fails.
