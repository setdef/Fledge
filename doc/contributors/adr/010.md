# ADR 010: Each Platform's App, Built on That Platform with Its Own Tools

## Status
Accepted (requested). Agents wrote this ADR and may change it (AGENTS.md, Questions). It applies the maintainer's words of 2026-10-28 in `doc/contributors/decisions.md` ("Code is a liability and we should _not_ have 4k+ lines of things we could use existing tools for." and "We already have to have target-environment-platform machines to compile on, right? If so, what value does cross-platform non-compilation building add?"), which accepted the orchestrator's recommendation to build each target on its own operating system with that system's maintained tools. It supersedes ADR 001, section 2's promise that any computer builds every platform, and the parts of ADR 006, ADR 008, and ADR 009 that kept it.

## Date
2026-10-28

## Context

Through 0.0.1.pre.7, `fledge build -t PLATFORM` built any platform's app on any computer. A Mac built the Windows program and its installer, and a Linux runner built every platform's app in CI. That promise (ADR 001, section 2) was never the maintainer's; agents made it, and kept it by writing in Ruby what each platform's own tools do, because those tools run only on their own platform.

The promise bought little. A gem with an extension to compile already had to be built on its own platform (ADR 006), so a project with one needed a computer of each platform anyway. A developer needs each platform to test the app on, and to sign it with Apple's or Microsoft's credentials when they have them (decision 17). And the prior art builds each platform on itself:

- **Tauri's bundler** builds for the computer it runs on: `.app` and `.dmg` on macOS with `hdiutil` (`crates/tauri-bundler/src/bundle/macos/dmg/mod.rs`), `.msi` on Windows only, and AppImages on Linux with linuxdeploy and appimagetool (`crates/tauri-bundler/src/bundle/linux/appimage/linuxdeploy.rs`); its `--target` chooses a Rust target triple for the compiler, not another operating system's package.
- **Briefcase** builds an app only on the platform it is for: each platform declares the hosts it builds on, and a Windows app's says "Windows applications can only be built on Windows." (`src/briefcase/platforms/windows/__init__.py`, `supported_host_os` and `supported_host_os_reason`, lines 81 and 82, on its main branch), which its commands raise as `UnsupportedHostError`.
- **Electron's tooling** signs and makes disk images with Apple's tools on a Mac, and edits a Windows program's resources with rcedit, which calls Windows' own `UpdateResource`.

## Decision

### 1. `fledge build` builds for the computer it runs on

`fledge build` builds the app for the platform it runs on, `Platform.local`, and nothing else. Its `-t` and `--target` are gone: given either, it says so and exits 2, as any usage error does, naming what to do instead (build each platform's app on that platform), since a script written for 0.0.1.pre.7 would otherwise read only "unrecognized option". A computer Fledge has no runtime for (Intel macOS, musl Linux, 32-bit Windows) cannot build, and the error lists the platforms that can.

So a gem with an extension to compile is always compiled, for the platform it is for, and the error that named a gem as needing another computer is gone with the case it described.

Fledge's own CI builds each platform's apps on a runner of that platform (`ci.yml`, Build), the job that built every platform's on one Linux runner is gone, and Delivery runs each on a fresh runner of its own platform, as before. The runtimes still build as is simplest: the Windows runtime's launcher is still compiled on Linux by the pinned llvm-mingw, which is a compiler, not a format Fledge wrote.

### 2. Archives: the computer's own tar

A runtime arrives as a `.tar.gz` and a built app leaves as one, or as a `.zip` on Windows. Every computer that builds apps has a tar that reads and writes these and keeps executable bits and symbolic links: GNU tar on Linux, bsdtar (libarchive) on macOS, and on Windows 10 and 11 the bsdtar Windows ships as `C:\Windows\System32\tar.exe`, which writes ZIP too (`--format zip`). So `Fledge::Archive` runs that tar, and Fledge's own tar reader and writer and ZIP writer (`Fledge::TarGz`, `Fledge::Zip`, about 480 lines) are gone. It names `System32\tar.exe` itself on Windows, since Git's GNU tar, often first on a developer's `PATH`, writes no ZIP and reads `C:` as a host name; on macOS it sets `COPYFILE_DISABLE`, so bsdtar adds no AppleDouble files. The runtime builder, the source bundles, and the licensing page's audit pack and unpack with it too.

Considered: rubyzip (BSD-2-Clause) and minitar (Ruby's license or BSD-2-Clause), which would make Fledge depend on gems it has done without, for what every host's tar already does; RubyGems' own `Gem::Package::TarWriter`, which refuses a path longer than ustar's 256 bytes, which a gem's files can exceed; and PowerShell's `Compress-Archive`, which a Ruby program would start for every archive and which has written backslashes into ZIP paths in Windows PowerShell 5.1.

Because each build runs on its own platform, the app's folder is written to disk first and archived from there: the runtime is unpacked, moved into the folder (or a bundle's `Contents/Resources`), the app and its gems copied in, and the launcher placed last; the archive and each installer are made from that folder by the platform's tools. Fledge no longer streams entries into an archive, a disk image, and a file system at once. Reproducible archives (every entry dated `SOURCE_DATE_EPOCH`), which Fledge's own writer gave runtime archives, are not kept: GNU tar and bsdtar spell it differently, and nothing reads the dates.

### 3. macOS: plutil, codesign, and hdiutil

A Mac has the tools Apple makes bundles and disk images with, from Xcode's command line tools (`xcode-select --install`), which compiling a gem already needed:

- `Info.plist` is the keys Tauri's bundler writes (ADR 008, section 2), written as JSON and converted by `plutil -convert xml1`; `Fledge::Plist` is gone.
- The bundle is signed ad hoc by `codesign --force --sign - --identifier IDENTIFIER NAME.app`, which seals `Info.plist` and every resource and signs the launcher for them, and `codesign --verify --strict --deep` accepts it, in its folder, in its archive, and in its disk image. `Fledge::AdHocSignature` and `Fledge::CodeResources`, which wrote a SuperBlob, a CodeDirectory, and the seal as codesign writes them (about 450 lines), are gone.
- The disk image is made as Tauri's create-dmg makes one: the bundle, copied with `ditto` (which keeps its signature, links, and modes), beside a link named `Applications` to `/Applications`, in a folder `hdiutil create -volname NAME -srcfolder FOLDER -fs HFS+ -format UDZO` makes a read-only, zlib-compressed image of. `Fledge::HfsPlus` and `Fledge::Udif` (about 600 lines) are gone, and the volume is Mac OS Extended, as create-dmg's are, rather than the case-sensitive HFSX Fledge wrote, so an app that opens its own files by a name of another case runs from the image as it does once dragged out. On macOS 26 and newer, `hdiutil create` prints that `diskutil image create` replaces it; macOS 14 and 15, which Fledge's runners and its oldest supported Macs run, have only `hdiutil`, so Fledge runs it and takes its output only when it fails.

## Consequences

- A developer builds the macOS app on a Mac, the Windows app on Windows, and the Linux apps on Linux, on their own computers or on CI runners of each; one computer no longer builds every platform.
- Scripts that pass `-t` or `--target` fail, saying why.
