# Desktop Runtimes

This document says what a desktop runtime holds and how `rake runtime` (`tasks/runtime_builder.rb`) builds one: the layout on each platform, where each input comes from and how it is pinned, what is kept and what is pruned, Fledge's RubyGems defaults, the `tools/` folder, what compiling a gem takes from a runtime, the platform names, and the release assets. ADR 093 decides that Fledge's CI prebuilds the runtimes; "Where each platform's Ruby comes from" says where their Ruby comes from. The license audit every runtime passes is `doc/contributors/design/license-audit.md`; the phones' runtimes are `doc/contributors/design/phone-runtimes.md`. For app developers, `doc/runtimes.md` says which runtime an app gets.

## What a runtime is

A runtime is a folder: Fledge's launcher at its top, a relocatable CRuby beside it in Ruby's own layout, the tools `fledge build` runs, and `notices/`. `fledge build` unpacks it, copies the app in, and archives the result. Nothing in a runtime records where it was built: on macOS and Linux, Ruby is configured `--enable-load-relative` and finds its library from the program that holds libruby; on Windows, Ruby finds its prefix from its DLL's own path.

Every runtime is a `.tar.gz` with one top folder, named as the asset is without its extension (`tasks/release_archive.rb`), on Windows too: only Fledge reads it.

The build runs in this order (`RuntimeBuilder#call`):

1. the platform's recipe builds the folder (`tasks/runtime_builder/`);
2. `RuntimeBuilder::RubyDescription.write` copies the description of the folder's Ruby into `RUBY_DESCRIPTION` ("The Ruby's description");
3. `LicenseAudit::SourceBundle#copy_into` writes `notices/sources/`;
4. `RuntimeBuilder#license` audits the folder and writes `notices/NOTICES.txt` and `notices/sbom.spdx.json`, or raises and archives nothing;
5. the folder is archived, and the SBOM, NOTICES, and source bundle are written beside it.

A recipe builds only on the computers it names (`Recipe#hosts`): each Unix runtime on its own platform, since its launcher links that platform's libruby; the Windows runtimes on any computer llvm-mingw is pinned for.

## Layout on macOS and Linux

| Path | What it is |
|---|---|
| `launcher` | Fledge's launcher, `runtime/launcher/unix.c` and the rest, linked with the static libruby. `fledge build` renames it for the app. |
| `bin/ruby` | Ruby's own `main.c` (`runtime/launcher/ruby_main.c`), linked with the same libruby and the same link line, so `RbConfig.ruby` and `Gem.ruby` run. Given the app's own program, it hands it back to the app's launcher (`doc/contributors/design/launcher.md`, "bin/ruby and restarts"). |
| `bin/*` | The default and bundled gems' executables, as the pinned Ruby installs them. |
| `include/ruby-X.Y.0/` | Ruby's C headers, which `require "mkmf"` reads at run time ("What a runtime keeps"). |
| `lib/libruby*-static.a` | Ruby's static library, stripped of its debug information, which `mkmf` links the test program of every `have_func`, `have_library`, and `try_link` against ("What a runtime keeps"). |
| `lib/ruby/` | The standard library, `gems/X.Y.0` with every default and bundled gem, `site_ruby`, and `vendor_ruby`, as Ruby lays them out. |
| `lib/libcrypt.so.2` | libxcrypt, glibc Linux only ("libxcrypt on glibc Linux"). |
| `libexec/cert.pem` | Mozilla's CA bundle. On macOS and musl Linux, Ruby's `openssl.rb` points OpenSSL at it unless `SSL_CERT_FILE` names others; on glibc Linux, only on a computer with no CA certificates of its own ("Certificates"). |
| `tools/appimage-runtime` | Linux only, glibc and musl ("The tools folder"). |
| `RUBY_DESCRIPTION` | The description Ruby compiled into `bin/ruby`, which `fledge build` reads and no app holds ("The Ruby's description"). |
| `notices/` | `NOTICES.txt`, `sbom.spdx.json`, and, on Linux, `sources/`. |

`X.Y.0` is the pinned Ruby's ABI folder.

How each program is linked (`tasks/runtime_builder/darwin.rb`, `linux.rb`, `musl.rb`):

- **macOS:** libruby linked whole with `-force_load`, `-mmacosx-version-min` set to the macOS floor, stripped with `strip -x`, and signed ad hoc, since Apple Silicon runs only signed code. The build fails if the program links anything outside `/usr/lib` and `/System/Library`.
- **glibc Linux:** libruby linked whole and its symbols exported (`-rdynamic`), so extensions find them; libgcc's unwinder taken statically (`-static-libgcc`); libxcrypt linked dynamically. Each program has an RPATH, never a RUNPATH, which `LD_LIBRARY_PATH` would override: `$ORIGIN/lib` for the launcher, `$ORIGIN/../lib` for `bin/ruby`. The build fails if a program needs a library beyond glibc's and libcrypt, and if any ELF file in the runtime, its own programs and libxcrypt as much as the Ruby's extensions, references a `GLIBC_` symbol version newer than the platform's floor (`Fledge::Platform::GLIBC_MINIMUM`), as `fledge build` holds a compiled gem to it (`RuntimeBuilder::Linux.above_glibc_floor`), so a build machine's newer glibc cannot raise the floor unseen. Extensions are stripped of debug sections, and `patchelf` removes the RUNPATHs rv-ruby's build machine left in some (`zlib.so` names a Linuxbrew folder).
- **musl Linux:** as glibc Linux, but with no libxcrypt and no RPATH; the programs may need only musl's C library.

Each program builds with warnings as errors (`RuntimeBuilder::WARNINGS`) and under a static analyzer: clang's on macOS and Windows, gcc's `-fanalyzer` on Linux.

## Layout on Windows

| Path | What it is |
|---|---|
| `launcher.exe` | The console launcher (`runtime/launcher/windows.c`), which loads Ruby's DLL when it runs. |
| `launcherw.exe` | The same launcher built as a GUI program, for windowed apps (`doc/contributors/design/desktop-apps.md`, "Windows"). |
| `ruby\` | RubyInstaller's tree, its shape unchanged: `bin\` with Ruby's DLL (`x64-ucrt-ruby410.dll` or `aarch64-ucrt-ruby410.dll` for Ruby 4.1), `ruby.exe`, `rubyw.exe`, the gems' wrappers, and `ruby_builtin_dlls\`; `include\`; `lib\ruby\`. `ruby.exe` and `rubyw.exe` are Fledge's, Ruby's `main.c` built against that DLL in their place (`RuntimeBuilder::Windows#compile_ruby`; `launcher.md`, "bin/ruby and restarts"). Fledge adds two DLLs RubyInstaller leaves out (`windows-dlls` in `runtime/sources.yml`, `RuntimeBuilder::Windows#add_missing_dlls`): `libz-1.dll` in Ruby's architecture folder under `lib\ruby\`, named in `zlib.so`'s assembly manifest, and, on x64, `libgcc_s_seh-1.dll` in `ruby_builtin_dlls\`. It also copies the `libffi-8.dll` RubyInstaller keeps beside the fiddle gem's extension into `ruby_builtin_dlls\` (`RuntimeBuilder::Windows.reach_gem_dlls`; "The DLLs a compiled gem finds on Windows"). |
| `tools\nsis\`, `tools\rcedit.exe`, `tools\llvm-readobj.exe` | What `fledge build` runs ("The tools folder"). |
| `RUBY_DESCRIPTION` | The description Ruby compiled into its DLL, which `fledge build` reads and no app holds ("The Ruby's description"). |
| `notices\` | `NOTICES.txt`, `sbom.spdx.json`, and `sources\`. |

The launchers may import only `KERNEL32.dll` and the universal C runtime's `api-ms-win-crt-*.dll`, and the windowed one `USER32.dll` for its message box. The build reads each one's PE Subsystem and imports with llvm-mingw's `llvm-readobj` and fails otherwise.

RubyInstaller's tree stays whole because Ruby and its DLLs depend on its shape. Ruby takes its prefix from its DLL's own path: a DLL in `PREFIX\bin` makes `PREFIX` the prefix (`ruby.c`, `runtime_libruby_path` and `ruby_init_loadpath`, at Ruby 4.1.0-preview1). The DLL's own dependencies load through the private assembly its embedded manifest names (`ruby_builtin_dlls`), and each extension's through its `*.so-assembly.manifest`, so a DLL moved out of the tree breaks what loads it. Kept whole, the tree works as RubyInstaller ships it, and a new Ruby pin unpacks into the same place. The app's program stays at the top of its folder and reaches the tree by loading Ruby's DLL when it runs (`doc/contributors/design/launcher.md`, "Windows").

Two other layouts worked when tried, and were worse for the person who opens the folder: the launcher inside `ruby\bin`, beside the DLL, and a side-by-side manifest that reshapes the tree (`doc/contributors/research/2026-11-10-findings-from-the-adrs.md`, "The Windows launcher spike: importing Ruby's DLL, and the layouts tried"). One layout on every system, a Ruby built statically for Windows or the Unix runtimes moved into `ruby/` with a shared libruby, would be a large change for nothing an app can observe: Ruby and RubyGems answer every question about the layout (`RbConfig::CONFIG["prefix"]`, `RbConfig.ruby`, `Gem.dir`, and `__dir__`), so app code needs no branch for it, which is what decision 23 asks of a layout that differs (`decisions.md`, 2026-10-26). The cost is that the assembly, the license audit, and signing each know two layouts.

How the launcher loads Ruby's DLL, its manifest, and the variables it hides are `doc/contributors/design/launcher.md`.

## The DLLs a compiled gem finds on Windows

A gem compiled from source on Windows links against MSYS2's libraries, which RubyInstaller's devkit provides, and its extension imports their DLLs by name: ffi 1.17.4's `ffi_c.so` imports `libffi-8.dll` when its `extconf.rb` finds a libffi on the system, and rugged 1.9.6's `rugged.so` imports `libz-1.dll`. Windows looks for such a DLL among the modules already loaded, then in the folders the process's DLL search names ("Dynamic-link library search order"), and never beside the extension that imports it. RubyInstaller's start-up names them in `RubyInstaller::Runtime.enable_dll_search_paths`: it calls `SetDefaultDllDirectories(LOAD_LIBRARY_SEARCH_DEFAULT_DIRS)` and `AddDllDirectory` for each folder of `RUBY_DLL_PATH`, for Ruby's architecture folder ("for libcrypto.dll loading zlib.dll and legacy.dll loading libcrypto.dll"), and for MSYS2's `bin` folder ("for user-installed gems") when it finds an MSYS2 (`runtime/singleton.rb` line 24 and `runtime/msys2_installation.rb` lines 134 to 145, in `site_ruby` of RubyInstaller's head build of 2026-11-10, which the runtime ships). Under `bundle exec` on a developer's computer, then, those two DLLs come from MSYS2's `bin`, and a gem may also find anything in Ruby's architecture folder (`libssl-3-x64.dll`, `libcrypto-3-x64.dll`, `libyaml-0-2.dll`, `zlib1.dll`, `libwinpthread-1.dll`, and the `libz-1.dll` the runtime adds).

An app has no MSYS2, and a person's own MSYS2 or `RUBY_DLL_PATH` must not reach it (`architecture.md`, "What the design answers to"; the launcher hides `RUBY_DLL_PATH`). The app's Ruby searches `ruby\bin\ruby_builtin_dlls`, which the launcher and the runtime's `ruby.exe` add (`launcher.md`, "Windows"), and Ruby's architecture folder, which Fledge's `operating_system.rb` adds with RubyInstaller's own `DllDirectory.new`, as RubyInstaller's start-up does ("Fledge's RubyGems defaults"). The one DLL of Ruby's own extensions outside both is `libffi-8.dll`, which RubyInstaller keeps beside `fiddle.so` in the fiddle gem's extensions folder, named in `fiddle.so-assembly.manifest`, where nothing else reaches it, and which the app does not hold at all when the bundle leaves fiddle out. So the runtime builder copies every DLL in a bundled gem's extension folder into `ruby_builtin_dlls` (`RuntimeBuilder::Windows.reach_gem_dlls`), leaving the original for its manifest; a process that loads both gets one, since Windows takes a module already loaded under the same name. The copy is the libffi RubyInstaller built fiddle with, whose soname, `libffi-8`, is the one MSYS2's libffi has: libffi changes that number when it breaks its ABI.

Before this, the app's Ruby searched neither place, and an app over any gem that goes through ffi, compiled from source, as a gem with an extension is for Windows' head build of Ruby, for which no gem ships a precompiled build, stopped at `require "ffi"` with "126: The specified module could not be found", where `bundle exec` ran (raylib-bindings, gosu, onnxruntime); rugged did the same for `libz-1.dll`. `test/fixtures/msys2_linked`, a gem whose two extensions link MSYS2's zlib and libffi, is built and run by `test/integration/built_app_test.rb` on each Windows runtime.

Two other answers were weighed. Copying, at `fledge build`, each DLL a compiled gem imports from the developer's MSYS2 into the app, as delvewheel repairs a wheel, would ship what the developer's `bundle exec` loaded, but it would put libraries into apps whose licenses no audit has read, from one computer's MSYS2, which is the repair `doc/contributors/design/gems.md`, "The linkage check", declines. Adding the fiddle gem's extension folder to the DLL search would reach the DLL without a copy, but that folder's name carries fiddle's version, and an app whose bundle leaves fiddle out does not have it. What the copy costs: about 40 KB more in every Windows app, and a second path for `libffi-8.dll` in `runtime/licenses.yml`.

## The Windows launcher, cross-compiled with llvm-mingw

The Windows launcher needs only Ruby's headers to build, never a library to link, since it loads Ruby's DLL at run time. So it cross-compiles with llvm-mingw's UCRT toolchain, pinned by version and SHA-256 in `runtime/sources.yml` for each computer that may build a Windows runtime (x86_64 and aarch64 Linux, Apple Silicon macOS). CI builds both Windows runtimes on Linux.

- **UCRT, not msvcrt.** The launcher must share RubyInstaller's C runtime, so that removing a variable from its environment removes it from the one Ruby reads. Ubuntu's own mingw-w64 targets the older msvcrt.
- **Pinned, not MSYS2's.** MSYS2's gcc on a Windows runner rolls and cannot be pinned.
- **One toolchain, two targets.** The triple is `x86_64-w64-mingw32` for `x64-mingw-ucrt` and `aarch64-w64-mingw32` for `aarch64-mingw-ucrt` (`RuntimeBuilder::Windows::TARGETS`).
- **Resources.** llvm-mingw's `windres` compiles `runtime/launcher/windows.rc`, which embeds the manifest (`windows.manifest`), into each launcher.
- **The audit's readers.** The Windows recipe's license audit reads the runtime with the same llvm-mingw's `llvm-objdump` and `llvm-readobj` (`doc/contributors/design/license-audit.md`, "Which tools read compiled files").

## Where each platform's Ruby comes from

Each desktop runtime copies a relocatable CRuby built for its platform, pinned in `runtime/sources.yml`. On macOS and glibc Linux it is jdx/ruby's (github.com/jdx/ruby), with the macOS floor at 26. On Windows it is RubyInstaller's (oneclick/rubyinstaller2), x64 and ARM64. For musl Linux Fledge builds Ruby itself ("musl Linux's Ruby, built in Alpine"), and for the phones too (`doc/contributors/design/phone-runtimes.md`). Building Ruby for macOS and glibc Linux as well waits until jdx/ruby stops publishing, publishes a build that fails Delivery, or cannot be relied on.

**What the Ruby has to be.**

- An app runs on the Linux people run: the distributions their vendors still support.
- A gem that compiles on the developer's computer under `bundle exec` compiles into the app the same way, with no setting (`doc/contributors/design/architecture.md`, "What the design answers to").
- Fledge maintains as little as it can (`decisions.md`, 2026-10-28: code is a liability), and takes a maintained project's portable Ruby before it builds one (`decisions.md`, 2026-11-22).
- The Ruby is relocatable: on macOS and Linux a static libruby the launcher can link (ADR 001), with its extensions as files; on Windows, Ruby's DLL in RubyInstaller's tree.
- Every download is pinned by version and SHA-256, and RubyInstaller's by its signature too ("The RubyInstaller signing key").
- The app's Ruby behaves as the same Ruby does under `ruby main.rb` (`doc/contributors/design/architecture.md`, "What the design answers to").

**Why jdx/ruby, and not rv-ruby.** rv-ruby (spinel-coop/rv-ruby) was the first source of the macOS and glibc Linux Ruby, and RubyInstaller of Windows's. Two things rv-ruby's builds could not give moved Fledge off it, one platform at a time.

On glibc Linux, rv-ruby builds on Ubuntu 24.04, so an app needed glibc 2.39 or newer, and did not run on Ubuntu 22.04, Debian 12, RHEL 8 or 9 and their clones, or Amazon Linux 2023. That floor was accepted (`decisions.md`, 2026-10-26, decision 7). On 2026-11-22, with the systems it leaves out in view, a change of the Linux Ruby's source was allowed, and switching away from rv-ruby entirely was left to the agents' judgment (`decisions.md`, 2026-11-22).

On macOS, rv-ruby's tree keeps no OpenSSL for gems to compile against. A gem that links OpenSSL, as Puma's does, linked Homebrew's library on a developer's Mac that had one, and `fledge build` refused the app; on a Mac without one it built with no TLS, where the developer's `bundle exec` had it.

jdx/ruby, a fork of rv-ruby that publishes the precompiled Rubies mise downloads, builds the same shape of tree. Its Linux builds are made in manylinux2014 containers and fail if a file needs more than glibc 2.17. Its trees keep the headers, static libraries, and pkg-config files of the OpenSSL and libyaml its Ruby is built with. Its macOS files declare macOS 26.0 as their minimum, where Fledge's floor was 15.

**The options weighed.** Five were weighed, and the first is taken:

1. jdx/ruby on macOS and glibc Linux, RubyInstaller on Windows, each pinned in `runtime/sources.yml`, with the macOS floor raised to 26. It lowers the Linux floor and gives gems the runtime's own OpenSSL on both platforms, with a maintained Ruby that Fledge does not build, and leaves one upstream for macOS and glibc Linux.
2. jdx/ruby on glibc Linux, rv-ruby on macOS, with an OpenSSL for gems that Fledge builds for the Mac, keeping the macOS floor at 15. It keeps the floor, but Fledge would build, audit, and keep current an OpenSSL of its own on macOS runners, and a Mac app would then hold two OpenSSL versions in one process, Ruby's and the gems'.
3. jdx/ruby on glibc Linux, rv-ruby on macOS as it stood, with gems that link OpenSSL left to a `fledge.yml` setting. A gem that builds under `bundle exec` would still be refused or lose TLS.
4. rv-ruby on macOS and glibc Linux, as before either move. Its tree carries notices and an SBOM, and one project serves both platforms; but its Linux builds need glibc 2.38 on x86-64 by measurement, and 2.39 by the runner they are built on, and its trees keep no OpenSSL for gems.
5. Building CRuby in Fledge's CI for these platforms, in an old-glibc container and on a Mac, as python-build-standalone builds CPython and as Fledge already builds Ruby for musl Linux. Fledge would choose the floors and the libraries, and its pin watch could move them; but Fledge would maintain a build of Ruby on its most used platforms. "Why Fledge builds no Ruby for macOS and glibc Linux" says what was examined and what it would cost.

No recorded comparison says jdx/ruby's builds are better kept than rv-ruby's. What was measured is the glibc each needs, the macOS each declares, and what each tree holds for gems.

**The floors that follow.** On glibc Linux, jdx/ruby's builds measured at most GLIBC_2.17 in every file, on x86-64 and ARM64. Fledge's own compiled parts (the launcher, `bin/ruby`, libxcrypt) set the floor above that: they are built in the manylinux_2_28 image, pinned by digest, because the compiler of manylinux2014 reports a double free in the launcher that is not there under the analyzer gate, and the gate is not weakened. So the floor is glibc 2.28, which every distribution named above has ("The glibc floor").

On macOS, every file of jdx/ruby's build declares macOS 26.0. The floor may rise to 15, and to 26 if keeping 15 becomes costly, and the weighing between that floor and a Fledge-built OpenSSL is the agents' (`decisions.md`, 2026-11-22). macOS 26 runs on every Apple silicon Mac ("The Mac's Ruby is jdx/ruby's"). The platform floors are in `doc/contributors/design/releases.md`, "Platform floors".

Windows stays on RubyInstaller, its x64 and its ARM64 builds ("Windows on ARM64").

**What it gives.**

- An app runs on Ubuntu 22.04, Debian 12, RHEL 8 and 9, and Amazon Linux 2023.
- A gem that links OpenSSL or libyaml compiles against the runtime's own, on macOS and Linux, with no `fledge.yml` setting, and the app holds one version of each.
- Fledge's Rubies are ones other projects build and test, and a new Ruby is a pin to move.
- An app trusts the computer's own certificate store first, as jdx/ruby's Ruby does and as a native program does, and the bundled file only where the computer has none ("Certificates").

**What it costs.**

- A Mac app needs macOS 26 or newer, and no maintained project publishes a portable Ruby for Intel Macs that Fledge now takes, so Fledge builds no Intel Mac apps.
- The macOS minimum is the default of the runner jdx/ruby builds on, not a setting of its recipe. A later build may declare a newer macOS; the license audit then refuses the runtime, and the pin cannot move until the floor does.
- The libraries inside jdx/ruby's builds are as current as its recipe, which a person there edits: on 2026-11-22 it compiled in OpenSSL 3.5.5, where OpenSSL's newest 3.5 release was 3.5.9. Fledge's pin watch moves the libraries of the runtimes Fledge builds itself, and cannot move these.
- Fledge depends on two projects' release schedules for its desktop Rubies, and jdx/ruby is one maintainer's.
- The Linux runtime is built in a container, which needs three Perl packages the image lacks, each pinned by SHA-256, and those are not watched for newer builds.
- jdx/ruby's tree carries no notices or SBOM, so `runtime/licenses.yml` lists what it compiles in (OpenSSL, zlib, libffi, libyaml, libxcrypt, Rust's standard library) from its recipes, and whoever moves the pin checks them again.
- jdx/ruby's `rbconfig.rb` puts its own folder first in `PKG_CONFIG_PATH` each time Ruby starts, so the app's value differs from `bundle exec`'s, which starts Ruby twice; `Parity::JUSTIFIED` says so.
- A gem compiled on the developer's computer still needs that computer's glibc, so an app with such a gem has the higher floor of the two.
- The Mac's Ruby has YJIT and not ZJIT, which rv-ruby's build had.
- Each upstream tree carries what a developer's Ruby needs, which the runtime builder prunes and replaces, and RubyInstaller's signing key expires on a known date, which whoever moves the pin must follow.

**What is shown, and what is not.** The runtimes built from jdx/ruby pass the license audit, the parity check, and Delivery on a computer of each platform, and a gem that links OpenSSL compiles against the runtime's and runs with the same version Ruby's own `openssl` reports, on glibc Linux, on musl Linux, and on a Mac that has Homebrew's OpenSSL installed. No file in the glibc runtime needs more than GLIBC_2.25, and every file in the Mac runtime declares macOS 26.0. The ARM64 Linux runtime, Delivery on the oldest distributions the floor admits, and the Mac's CI jobs on macOS 26 runners are CI's to show.

**What checks it.** Every runtime build (`rake runtime`) checks each download against its pin, and RubyInstaller's archive with `gpgv` against the pinned key, by fingerprint. A glibc runtime build fails if any file it stages needs a newer glibc than the platform's floor, and the license audit refuses a macOS runtime with a file whose minimum macOS is above the floor (`doc/contributors/design/license-audit.md`, the `macos-floor` rule). `test/integration/openssl_gem_test.rb` compiles a gem against the runtime's OpenSSL and compares its version with Ruby's. CI's "Licenses of the whole upstream tree" jobs audit each source's whole tree, and CI builds, tests, and delivers every runtime on a runner of its platform.

**What reopens it.** jdx/ruby stops publishing, publishes a build that fails Delivery, or cannot be relied on; its macOS builds declare a newer macOS than Fledge's floor; or another maintained project publishes a portable Ruby with a lower floor. That its libraries lag their upstreams is a known cost, above, and a stated dependency (`decisions.md`, 2026-11-22), not a reason to reopen it.

## Sources and pins

Every input that comes from outside the repository is in `runtime/sources.yml`, pinned by version and SHA-256, and `DownloadCache#fetch` (`tasks/download_cache.rb`) refuses a download whose SHA-256 differs. The file's comments say what each pin is and why; its top-level keys group the pins by what they feed: each platform's Ruby (`ruby`, `musl-ruby`, `mobile`), the Windows launcher's compiler (`llvm-mingw`), the libraries a runtime adds (`libxcrypt`, `gmp`, `windows-dlls`), the tools of a runtime's `tools/` folder (`rcedit`, `llvm-readobj`, `nsis`, `appimage-runtime`, `libfuse`), and what only CI's replaceability jobs read (`replaceability`). The phones' pins are described in `doc/contributors/design/phone-runtimes.md`.

`test/runtime_builder_test.rb` checks the pins' shape. CI's tools that build runtimes are pinned beside them: the manylinux_2_28 image for glibc Linux and the Perl packages its build adds, in `runtime/sources.yml` itself (`manylinux` and `almalinux-perl`, "The glibc floor"), as is every container image CI runs in (`images`, "Container images"); the Xcode version in `ci.yml`'s Runtime job, and the Alpine packages for musl ("musl Linux's Ruby, built in Alpine"), are pinned where they are installed.

The Ruby versions pinned today: on macOS and Linux, `ruby`, `mobile.ruby`, and `musl-ruby.ruby` name the same release, 4.1.0-preview1, and the musl build runs in the Alpine Ruby image of that version. On Windows, `ruby` names RubyInstaller's head build of Ruby's main branch instead ("Windows' Ruby until Ruby 4.1.0", below). A move to a new Ruby moves all of them together.

jdx/ruby, whose Rubies the macOS and glibc Linux runtimes take, publishes two releases for each build of a Ruby, and the pins name the one that keeps its files. Its `.github/workflows/release.yml` (jdx/ruby at 09c4b6b, lines 65 to 83 and 153 to 179) gives each build a release of its own, `VERSION-N`, with N one more than the last build of that Ruby, and deletes the release `VERSION`, and its tag, and publishes it again with the new build's files. jdx/ruby builds its Rubies again about monthly, so a pin of `VERSION`'s files would fail its SHA-256 at the next build, and every runtime build with it, until a person moved the pin. No workflow there deletes a `VERSION-N`: on 2026-11-22 it had 327 releases and as many tags, 253 of them `VERSION-N` with no number missing, and 4.1.0-preview1 had one build, whose three files Fledge pins had the very SHA-256 of `VERSION`'s, downloaded and hashed. GitHub does not mark these releases immutable (`immutable` is false), so it is jdx/ruby's practice, not GitHub, that keeps them. The asset names carry the Ruby's version and not N, as `4.0.10-1/ruby-4.0.10.macos.tar.gz`, and both releases of a preview are marked as prereleases.

`runtime/upstreams.yml` says where each pin is released, so that a newer release upstream is found without anyone looking ("Keeping the pins current", below).

## Keeping the pins current

A pin holds a runtime to one release of each input. When OpenSSL, zlib, or Ruby itself fixes a security hole, no app built with Fledge gets the fix until the pin moves and Fledge releases, and nothing in a pin says upstream has moved. So the candidate for 1.0.0 has automation that moves the pins itself: when an input has a newer release, Fledge moves the pin, proves the new runtimes in CI, and releases, and nobody is told unless that path fails (decisions.md, 2026-11-22; `releases.md`, "Versions"). It is built in four steps:

1. **The watch**, `tasks/pin_watch.rb`, finds what is newer, and `.github/workflows/pin-watch.yml` runs it every day. Built.
2. **The move**, `tasks/pin_move.rb`, rewrites the pin and everything that names its version. Built.
3. **The proof**, `.github/scripts/pin-prove.sh`: the same workflow puts the move on a branch of its own, has CI run on it, and puts it on trunk when CI passes. Built.
4. **The release**, `.github/workflows/cut.yml`: the release commit, the pin commit, the tag, and `release.yml`, made off trunk, and then recorded on trunk (`releases.md`, "How a release is made"). Built, and `pin-watch.yml`'s Release job starts it once a move is green on trunk, for now without `publish` ("The proof", below).

`.github/workflows/pin-watch.yml` runs the watch at 06:37 UTC each day, and by hand (`gh workflow run pin-watch.yml`), with `contents: read` and the run's own token, which only lifts GitHub's limit on reading public releases. It prints what it found in the run's summary and keeps the JSON as the run's `pin-watch` artifact for 30 days: `gh run download RUN -n pin-watch` fetches it. A pin with a newer release starts the move, its proof, and the release ("The proof", below), and leaves the run green when they pass, since nobody is to be notified on the happy path (decisions.md, 2026-11-22). The run fails when an upstream could not be read or listed nothing its pattern takes, because then a release could pass unseen, and when a pin behind could not be moved or failed its proof, or has been held for a person for longer than 30 days ("Held pins", below), or when a pin's line has ended ("A line that has ended", below), because then a fix waits on a person: those failures are the ones a person has to hear of. Every other pin behind still moves in that run. GitHub sends the notice of a scheduled run to the account that created the workflow, or to whoever changed its `cron` line since, as that account's notification settings ask ("Notifications for workflow runs", docs.github.com/en/actions/concepts/workflows-and-actions/notifications-for-workflow-runs): the account that pushes this repository's commits. That is how keep-rubyinstaller-head.yml's failures reach anyone too.

"In a public repository, scheduled workflows are automatically disabled when no repository activity has occurred in 60 days" ("Events that trigger workflows", `schedule`, docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows); the page does not say what counts as activity, or whether anyone is warned first. Trunk takes commits every day today, and once steps 2 to 4 exist, every pin the workflow moves is a commit too, and the inputs it watches release every few weeks: the CA certificates, llvm-mingw, and rv-ruby each released in November 2026. A repository whose upstreams are all quiet for 60 days, and where nobody pushes, could still lose the schedule, and a disabled workflow cannot enable itself; `keep-schedules.yml` enables it again each day ("A quiet repository", below), and `gh workflow enable pin-watch.yml` is the remedy by hand.

### The watch

`runtime/upstreams.yml` names, for each watched input, the components of `runtime/sources.yml` it is the upstream of, the key that holds the version, and where its releases are listed: a GitHub repository, with a pattern for its tags, or a page with a pattern for the versions on it. Components that are not watched are listed there with the reason, such as GMP and the two DLLs Windows adds, which move with RubyInstaller's build and not on their own, and libfuse, which moves with AppImage's runtime. `test/pin_watch_test.rb` fails when a component of `runtime/sources.yml` is in neither list, so a new pin is watched or says why not.

`ruby tasks/pin_watch.rb REPORT` asks each upstream once, compares its newest release with the pin, prints one line for each, writes them to REPORT as JSON, and exits 0 when no pin is behind but those held in time, 3 when a pin nobody holds has a newer release, and 1 when an upstream could not be read or listed nothing its pattern takes, a held pin is overdue ("Held pins", below), or a pin's line has ended ("A line that has ended", below). It reads public listings and needs no token, though GitHub gives an anonymous caller 60 requests an hour and the workflow passes its own. Releases GitHub marks as drafts or prereleases are left out, and so is any version with a letter in it, as `4.1.0-preview2` or `9.6.0-alpha05`, unless the pin is a prerelease too: while Ruby's pin is 4.1.0-preview1, preview2 is its next version. An upstream that publishes each build of a release under a version of its own, as jdx/ruby published `4.0.10-1` and would publish `4.0.10-2` if it built that Ruby again, has `rebuild` in `runtime/upstreams.yml`, a pattern that takes the release out of a version. A later build of the pin's own release is then its next version even when the upstream is held, since a hold is for a new release ("Held pins"), and a prerelease mark does not leave it out, since such an upstream marks every build of a preview as it marked the pin's. For such an upstream the watch reads every page of GitHub's list of its releases, not the first hundred: GitHub lists them newest first, and when jdx/ruby builds all of its 55 or so Rubies again at once, as it can, the two releases each build publishes come to more than a page, and the pin's could fall below the first. jdx/ruby listed 327 releases on 2026-11-22, four pages.

An input with `line` stays in a line: OpenSSL in 3.6, the line RubyInstaller's Ruby links, and Ruby in 4.1. A newer release in the line is the pin's next version, and one beyond it is reported as `beyond` and not taken, since a new line of OpenSSL or a new Ruby minor is planned work (`releases.md`, "Ruby minors and runtimes"), which arrives on purpose (`architecture.md`, "What the design answers to"). A line does not last for ever, and when it ends no newer release appears in it to say so, so the watch also tells when it has ended ("A line that has ended", below). Every other input takes its newest release, and CI is what proves it fits. zlib and libxcrypt have a line of one number, their major: zlib's `deflateInit_` and `inflateInit_` refuse a caller built against another first character of the version (`deflate.c`, `my_version[0]`, at zlib v1.4) and its soname is `libz.so.1`, and libxcrypt's 4.x installs `libcrypt.so.1` and keeps its symbols, with `libcrypt.so.2` the name its configure script gives a build without the obsolete interfaces, so a new major of either is a new interface and is reported, not taken. libffi takes any release: its libtool version went from 10:0:2 at v3.5.2 to 13:1:5 at v3.8.1, so its soname number (current minus age) stayed 8 and each release since added interfaces only (`FFI_TYPE_VECTOR` and its kin, `ffi_call_plan_*`); a gem compiled against its newer header sees constants and functions it did not have. libyaml's 0.2.6 sets its libtool age to 1 beside current 2, which gives a soname of `libyaml-0.so.1` where the release before it had `.so.2`: that is libyaml's own, and Fledge links libyaml into psych (or builds it static), so no app meets it. The Mozilla CA certificates are dated files and have no line.

Run by hand on 2026-11-22 against the real upstreams, it found ten pins behind: rv-ruby, llvm-mingw, llvm-readobj, libyaml, libffi, zlib, the CA certificates, Gradle, the Android Gradle plugin, and XcodeGen; OpenSSL was the newest of its line, with 4.1.0 beyond it. The tests read what each upstream answered that day, cut down to the lines that name a version, in `test/fixtures/pin_watch/`; no test reaches an upstream.

### The move

`ruby tasks/pin_move.rb REPORT` reads the watch's report and moves each pin it found behind: `runtime/sources.yml`'s version, each URL that names the version, and the SHA-256 beside each such URL. It rewrites them as text, as `tasks/ruby_snapshot.rb` moves the Ruby snapshot's pin, so every comment stays; the version only on the pin's own line, so another component that happens to hold the same version is left; and then reads the file back as YAML and fails unless each pin holds the new version. `--only NAME` moves one, and `--into DIR` writes the files it changed into DIR in place of the checkout, so that a run against the real upstreams changes nothing and can be compared. It exits 1 when a pin behind could not be moved, after writing every move that could.

Each SHA-256 comes from the upstream's record of it, as `runtime/upstreams.yml`'s `checksum` says: for a GitHub release, the `digest` GitHub's API lists beside each asset, which is the SHA-256 of the bytes GitHub serves (on 2026-11-22, mise's download of the newest XcodeGen's `xcodegen.zip` hashed to the very digest GitHub lists for it); for Gradle and the CA certificates, the `.sha256` file each publishes beside the download. NSIS's SourceForge folder, and a GitHub asset uploaded before GitHub recorded digests, record none, so the move downloads the file once, hashes it as it arrives, and keeps nothing. A container image is pinned as `REPOSITORY:TAG@sha256:DIGEST`, and its digest is the SHA-256 of a manifest only the registry serves, so the move gives each such pin its tag, with the version moved where the tag names it, and the digest the registry's own record gives that tag now: the `manifest_digest` quay.io's API lists (`?specificTag=TAG`), or the `digest` Docker Hub's API gives; it stops at an image on any other registry ("Container images", below). None of these records is signed, and a record served from the host that serves the file proves no more than TLS to that host does; what it buys is not downloading a file only to hash it. The pin's SHA-256 then holds every later build to those bytes, as every pin always has. No moved pin carries a signature today: OpenSSL signs its releases, and its pins have never checked one; the RubyInstaller pins, which do, are held.

The version is named in a few more places, which `runtime/upstreams.yml` lists for each upstream, and the move rewrites them in the same pass: `licenses`, the entries of `runtime/licenses.yml` built from the pin, whose version, download, and evidence name it (the license audit reads the evidence in each runtime, so an entry left behind fails the build); `also`, a file a tool reads, with a pattern for where it names the version, as `mise.toml`'s XcodeGen, the Gradle wrapper's properties, and `Fledge::MobileProject::Android::AGP`, in which each replaced URL and SHA-256 is replaced too; and `CHANGELOG.md`, where a pin that ships gets one line under `[Unreleased]`, `### Changed`, as "`libffi NEW, from OLD.`", and a second move before the next release rewrites that line and keeps the version the release's readers had. An entry of `runtime/licenses.yml` that records another build's copy of the same library, as rv-ruby's libyaml, keeps its own version: so the musl runtimes' libyaml, zlib, and libffi have entries of their own (`libyaml-musl`, `zlib-musl`, `libffi-musl`), apart from rv-ruby's, and every entry has an id no other entry has, which the license audit enforces (`doc/contributors/design/license-audit.md`, "When a pin moves"). When a step fails (no asset of that name in the release, a pattern that no longer finds the version, a licenses entry that no longer names it), that pin's move is undone and the others stand.

A line elsewhere that names a pinned version as the pin goes false when the move moves it. So `test/pin_move_test.rb` fails when a line names a movable pin's current version beside the input's name (`names` in `runtime/upstreams.yml`) anywhere but in the files the move rewrites, the records of what changed (`CHANGELOG.md`, `decisions.md`, and the research, plans, and drafts kept as they were on their day), and the files an upstream lists as `named`: those that name a release for itself, as a fact about it ("libxcrypt 4.5.2 assigns `strchr`'s result to a `char *`"), a source cited at it, or a test's own data. Prose about the pin names no version ("the Android Gradle plugin `runtime/sources.yml` pins"). The test reads today's versions, so a file that comes to name a pin's new version by chance after a move, as `mise.toml` names the version of MSYS2's zlib for Windows, fails the move's proof until a person lists it; a move of every movable pin to a made-up newer release, with the unit tests run after it, found that one, and listed it before the first real move. The first moves of llvm-readobj and of zlib found two more, `mise.rust.toml`'s LLVM for bindgen's libclang, which had reached the version llvm-readobj moved to, and this document's table of zlib's newest release, and a person listed them too: a move can still meet such a file when its new version is one the checkout already names for another purpose, which `test_a_pin_may_move_to_a_version_the_checkout_names_for_itself` pins down for those two, and a person lists the next. After a move, `bundle exec rake licensing` regenerates `doc/licensing.md`, which names each component's version, as it does after any change to `runtime/licenses.yml`. A second test checks that every `licenses` entry and every `also` pattern names the version each movable pin holds today, so a change that would break a move fails before a push, not on the day upstream releases.

Android's NDK has two names for one release: the revision the listing orders its packages by, three numbers, which `sdkmanager` installs and `Fledge::MobileExtensions::NDK::RECOMMENDED` names, and the release name, as `r29b`, which its archives and so its URLs carry. The watch compares revisions, and leaves out a package whose revision has a `preview`, since Google lists the NDK's betas in the stable channel too; the move then takes the new release name from the name of that package's Linux archive in the same listing (`release` in `runtime/upstreams.yml`) and rewrites it as it rewrites a version. The listing gives each archive's SHA-1 and no SHA-256, so the move downloads each archive once to hash it.

llvm-readobj is one file of LLVM's Windows release, about a gigabyte compressed, and it links the zlib and Zstandard that LLVM's own `llvm/utils/release/build_llvm_release.bat` downloads and names (`set zlib_version=`, `set zstd_version=`). Its pin holds the archive's SHA-256, which GitHub records, the file's path in the archive, and the file's own SHA-256, which nobody records. So the move rewrites the version in the path (`member` in `runtime/upstreams.yml`), downloads the new archive into a folder of its own, unpacks the one file through `zstd -dc --long=31` and `tar` (7-Zip's `7zz`, which `mise.toml` pins, where a computer has no zstd), hashes it, and deletes the folder; the same SHA-256 moves in `runtime/licenses.yml`, which checks the file in every Windows runtime. Then it reads the script at the new tag from `raw.githubusercontent.com` (`linked`), which is not GitHub's API and spends none of its allowance, and moves each library's entry in `runtime/licenses.yml` whose version the script no longer names: its version, download, and evidence (zlib's `deflate` and its version). The license audit of the Windows runtimes in the proof's full run then checks that the file holds what the entries say. The cost is a gigabyte downloaded in the run that moves it, a few times a year, and a script whose shape may change: a pattern that no longer matches stops that pin's move and fails the run, as any failed move does ("The proof").

A move that would need a person's reading is not made: an upstream with `hold` is the watch's to report and a person's to move ("Held pins", below). A mapping whose URL moves and that holds any key but its URL, its SHA-256, its version, and those its upstream lists in `keep` (Gradle's `wrapper_sha256`, the wrapper jar's, which the move does not change) stops the move, since the move cannot know what that key should become.

An input that compiles in other libraries carries their versions in its own files, not in its release's name. rv-ruby, the Mac's Ruby until 2026-11-22, compiled OpenSSL and libyaml into the macOS Ruby's `openssl.bundle` and `psych.bundle`, so a new rv-ruby release could carry another OpenSSL, which the license audit would then find unlisted, failing the build. So an upstream's `compiled` in `runtime/upstreams.yml` names, for each such library, its entry in `runtime/licenses.yml`, the file in the archive that holds it, and a pattern for its version in that file's bytes, which is the string the audit's evidence names: OpenSSL's version text (`OpenSSL X.Y.Z `) in `openssl.bundle`, and libyaml's version between NULs in `psych.bundle`. The move reads those files out of each platform's new archive, in the same download that names its platform (below), rewrites each entry whose version they no longer hold, and adds a `CHANGELOG.md` line for it ("OpenSSL in the macOS Ruby"), since a security fix in OpenSSL is what an app developer would look for. A file that names no version, or two, stops the move rather than being guessed at. An entry may describe several platforms when the upstream builds them all from one list of libraries, as jdx/ruby builds every target from its `recipes/dependencies.yml`; `compiled` then names it under each of them, the move reads it from each platform's archive, and moves it only when they all name one version, since one entry cannot say two. `test/pin_move_test.rb` fails when an entry describes a platform the move does not read it from, or one it does not describe, or another build of Ruby than the one the move reads it from (`ruby_build`), or when its pattern does not read its version out of its own evidence. jdx/ruby's names OpenSSL in `openssl`, libyaml in `psych`, zlib in `zlib`, and libffi in `fiddle`, on macOS and on both glibc Linuxes, each an entry of its own build (`openssl-jdx`, `libyaml-jdx`, `zlib-jdx`, `libffi-jdx`); `test/pin_move_test.rb` proves the step on an upstream shaped as rv-ruby's was, and on one shaped as jdx/ruby's. On 2026-11-22 the move ran on jdx/ruby's real archives of the pinned build, served from disk as a made-up later build, and read each of the four on all three platforms; with the copy's `openssl-jdx` set one version back, it moved that entry to 3.5.5 and added its line to `CHANGELOG.md`. Its Linux archives are written by GNU tar, which stores a path longer than a header's hundred bytes, as `fiddle.so`'s, in an entry of its own before the one it names; RubyGems' reader yields the two apart, so the listing takes the first's bytes as the second's path.

A Ruby names its platform for the system it was built on, and that name is not in its release's name. rv-ruby's release of 2026-10-23 was built on macOS 14 and called its platform `arm64-darwin23`; its release of 2026-11-19, in an asset of the same name, was built on macOS 15 and called it `arm64-darwin24`. jdx/ruby's, built on macOS 26, calls it `arm64-darwin25`. The name is RbConfig's `arch`, so it is `RUBY_PLATFORM` and the RubyGems platform an app's Bundler runs as, and `Gem::Platform#===` compares a darwin platform's version exactly (`rubygems/platform.rb` at RubyGems 4.1.0.beta2): a lockfile that locks only `arm64-darwin-23` fits the Ruby of one release and not that of the next. `fledge build` takes such a lockfile as `bundle exec` on that Ruby does, and ships it with the Ruby's platform added (`gems.md`, "A Mac locked under another Darwin version"), so a new name refuses only a gem the lockfile locks for the old Darwin version alone, which `bundle exec` on the new Ruby could not load either. `runtime/licenses.yml`'s platforms hold the name, as `arch` and as RubyGems' `gem_arch` (`arm64-darwin-25`), and the license audit looks for each compiled file under it; the first real proof of a move of rv-ruby, on 2026-11-22, failed because nothing moved it, and every compiled file of the macOS runtime was "unlisted". So `platform` in `runtime/upstreams.yml`, which `jdx-ruby` has for the Mac, gives a pattern for the Ruby's own folder in the archive. The move downloads the new macOS archive once, lists it with RubyGems' tar reader, and, when the name differs, moves the platform's `arch` and `gem_arch` in `runtime/licenses.yml` to it, with a line in `CHANGELOG.md`, since `RUBY_PLATFORM` is what an app's code sees. Nothing else has to move with it: the line Delivery expects an app to print reads the name from `runtime/licenses.yml` (`.github/scripts/ruby-platform.sh`), since the token that pushes a move cannot change a workflow; mobile parity's justifications take a desktop Mac's platform with any Darwin number; and the tests that name `arm64-darwin23` name a fake runtime's.

What was weighed. Generating every line that names a version from `runtime/sources.yml` would take a template for each document and each tool's file, more code than the lines it rewrites. Forbidding any version number outside `runtime/sources.yml` would forbid the facts that are about one release, which a design must be able to state. Listing the few places and checking the rest with a test keeps the move to text substitution and the rule to one test.

### Container images

CI runs in images from two registries: PyPA's manylinux_2_28 on quay.io, which builds the glibc Linux runtimes, and, from Docker Hub, the Alpine with Ruby that builds the musl runtimes and an Alpine developer's apps, the bare Alpine their Delivery runs on, the AlmaLinux, Amazon Linux, Debian, and Ubuntu that the glibc Linux apps and `.deb` packages are delivered on, and the Arch Linux that builds the AUR recipe. Every one is pinned in `runtime/sources.yml` by tag and by digest, and no workflow names one: a workflow reads `images` with `.github/scripts/pinned-images.sh`, into its environment for a step that runs `docker run "$ALPINE_RUBY"`, or, in `ci.yml`'s Changes job, into an output from which a later job names its container by key (`fromJSON(needs.changes.outputs.images)['debian-trixie-slim']`), since a job's container is chosen before any of its steps runs. They live there rather than in the workflows because the move pushes with the workflow's own token, and that token cannot push a commit that changes a file under `.github/workflows` (GitHub grants a `workflows` permission to apps and personal tokens, and none to `GITHUB_TOKEN`), so a pin in a workflow could only be moved by a person. `test/workflow_images_test.rb` fails when a workflow holds an image digest, when a container names a key `images` lacks (an empty container, which GitHub would take as none and run the job on the runner itself), and when a step runs an image's variable before the step that reads it.

What newest means depends on the tag. A tag that names a release, as `alpine:X.Y.Z`, names that release, and its move is to the next release in its line (`line` in `runtime/upstreams.yml`), from Docker Hub's list of the repository's tags; Alpine's next branch, 3.25, is reported, not taken, since every package pinned by version changes with it ("Alpine's packages", below). A tag that names no release, as `debian:trixie-slim`, `ubuntu:24.04`, or `ruby:4.1.0-preview1-alpine3.24`, is one the image's maintainers push again under the same name whenever its packages are rebuilt, so the tag stays and the move is the digest changing under it: the pin's version is the day Docker Hub's record of the tag says it was last pushed (`tag_last_pushed`), the watch finds that record dated later, and the move takes the `digest` the same record gives. A pin's day may be earlier than its image's, as the first pins of 2026-11-22 are, which costs one move that finds the digest it already has, or a new one. Two pushes on one day are seen as one, and the second is taken on the next push or not at all, which leaves the first image, still pinned and still whole.

The digest pinned is the one of the tag's multi-platform index, so one pin serves the x86_64 and ARM64 runners alike. Docker Hub's API answers without an account for a public image, and its `digest` is the registry's own: on 2026-11-22, for each of the four tags `ci.yml` named, it equalled the `Docker-Content-Digest` that `registry-1.docker.io` returned, with an anonymous token from `auth.docker.io`, for the tag's index, and so it did the same day for `almalinux:8`, `amazonlinux:2023`, `ubuntu:22.04`, and `debian:bookworm-slim`, pinned for the Delivery on the oldest glibc ("The glibc floor"). The API was chosen over the registry's own protocol because one plain request gives both the day and the digest, as quay.io's API does, where the registry needs a token first and dates nothing. None of these images ships in a runtime or an app (`ships: false`): what a musl runtime is compiled with is pinned by package, not by image, so a move adds no line to `CHANGELOG.md`.

Ruby's Alpine image names Ruby's version in its tag, and so does the page `runtime/upstreams.yml` reads it from; the move of Ruby is held ("Held pins", below), and the person who takes Ruby to its next version moves that tag and that page with it.

### Alpine's packages

The musl jobs install their tools from Alpine 3.24 by upstream version (`apk add NAME~UPSTREAM`, as in `NAME~1.2.3`), as the Ubuntu jobs pin theirs, so that what builds a musl runtime changes its upstream versions only on purpose. An Alpine branch keeps only each package's newest build, and Alpine rebuilds a package without a new upstream version: it rebuilt GLib on 2026-11-22, and zstd twice in the days after a new release of it. A pin of the exact build (`NAME=1.2.3-r0`) is gone from the branch at the rebuild, `apk` refuses it (`breaks: world[NAME=1.2.3-r0]`), and every job that installs it is red until a person moves the pin. A rebuild changes no upstream version, and the upstream version is what the license audit reads of a musl runtime: the evidence in `runtime/licenses.yml` records GCC's version (`GCC: (Alpine 15.2.0) 15.2.0`) and Rust's (`/rustc/HASH/`), and never Alpine's build number. So each job installs the pin's upstream version, its version with the `-rN` build number taken off, and `apk` takes `~` as a prefix match (`apk-world(5)`: `busybox~1.6` matches 1.6, 1.6.0, and 1.6.5, and `src/version.c` of apk-tools 3.0.9 ends a fuzzy comparison as equal when the constraint's tokens end first): `NAME~1.2.3` installs `1.2.3-r0` and `1.2.3-r1`, and stops with `breaks:` against a branch that serves `1.2.4-r0`. So the versions live in `runtime/sources.yml`, under `alpine-packages`, each in full (`1.2.3-r0`) as the record of the build last proven, and `.github/scripts/alpine-packages.sh` keeps only which job takes which package, reading the versions with `awk`, since Delivery's bare Alpine has no Ruby, and taking the build number off with the shell's own `${version%-r[0-9]*}`. In a workflow they could not move: the move pushes with the workflow's own token, which cannot push a change to `.github/workflows` ("Container images", above), and the script is outside that folder.

`runtime/upstreams.yml`'s `alpine-packages` is one upstream for each package of that mapping, read from the index of each repository (main and community) for each architecture (x86_64 and aarch64): four files of half a megabyte to two and a half, each two gzip members, the first holding the signature's tar entry with no end of archive and the second the index, so the watch reads them as one stream (`Zlib::GzipReader.zcat`), as `tar` does. apk's versions (`2.88.4-r0`, a release and a build number) are not RubyGems versions, and they need no order here: the branch keeps one build, so the pin is behind exactly when its indexes serve no build of the pin's upstream version, older or newer, since only a build of the pinned upstream version installs. When every architecture serves some build of the pinned upstream version (`1.2.3-r0` pinned, `1.2.3-r1` served, or `-r0` on one architecture and `-r1` on the other), the pin is current: the watch reports it as `current`, with no newer version, and the move has nothing to do, so `runtime/sources.yml` keeps the build last proven until a new upstream version moves it. When they all serve one build of another upstream version, that build is its next version, and the move writes its full version; when they serve different builds of it, or none, the watch fails, since then no pin installs on both and a person has to look. On 2026-11-22 every one of the 20 packages was in exactly one repository, once, and the same on both architectures. The move then rewrites the one line of `runtime/sources.yml` and nothing else. None of these packages ships, so a move adds no line to `CHANGELOG.md`; what a musl runtime compiles in from them, GCC's runtime and Rust's standard library, is recorded in `runtime/licenses.yml` by GCC's and Rust's own version, which a rebuild does not change and a new version does. A new GCC or Rust in the branch is moved like any new upstream version, and the license audit of the musl runtimes in the proof's full run then fails on the version its entry names, which calls a person, who moves the entry and adds the line to `CHANGELOG.md`.

A pin whose upstream version the branch has left does not ship something old: it stops the build, on purpose, until the pin moves, since a new upstream version is the change the proof judges. So a move that fails, or a proof that is red, means trunk's musl jobs stay red until a person moves the pin, and the run that failed says which package and why. What the rule costs is a rebuild's changes: a rebuild of the pinned upstream version installs with no commit, so a tool's bytes, or the GCC runtime and the Rust standard library a musl runtime compiles in, may change while their versions stay what the license audit reads. The proof's full run is what judges the new build: it builds both musl runtimes with it, runs parity and Delivery on Alpine, and audits the runtimes' licenses, as for any move.

A new Alpine branch is not a rebuilt package. Alpine 3.25 brings new versions of every package and a new image (`alpine:3.25.0`, and Ruby's image for that Alpine), and the image's watch reports it as beyond its line and does not take it ("Container images", above). The person who moves the branch moves the images, the branch in the index URL of `runtime/upstreams.yml`, the comment of the script, and every package pin together, and proves them in one run.

The three AlmaLinux 8 Perl packages that libxcrypt's build needs in the manylinux image (`almalinux-perl`) are not watched this way. Their index, the AppStream repository's `repodata/primary.xml.gz` (4.3 MB), is as readable, but AlmaLinux keeps every build it has published: on 2026-11-22 it listed perl-open 1.11-422.el8.0.1, 1.11-423.el8_10, and the pinned 1.11-423.el8_10.1, and builds of module streams for other Perls. So their pin keeps resolving, a newer build there is a choice of which stream fits the image's Perl, and the rule "the index serves something else" would be false for them.

### The proof

When the watch finds a pin behind, `pin-watch.yml`'s Move job runs `.github/scripts/pin-prove.sh` on trunk as it stands. It moves every pin behind at once with `tasks/pin_move.rb`, with the run's token as `GITHUB_TOKEN`, as the watch has it. An anonymous caller gets 60 requests an hour, and the moves of libyaml, libffi, and zlib alone in the first real run were refused that way, each with a 403. A refusal for a spent rate limit says so, and when the limit resets. Then the script regenerates `doc/licensing.md` with `bundle exec rake licensing`, and commits the move as `github-actions[bot]`, with a message `PinMove#message` writes. It pushes that commit to the branch `pin-move`, starts a full run of `ci.yml` there (`gh workflow run ci.yml --ref pin-move`), waits for it in the job, and deletes the branch. Green, it pushes the commit to trunk: as proven when trunk has not moved since, which is a fast-forward; and otherwise rebased onto trunk, when it rebases cleanly, with `doc/licensing.md` regenerated on the result and a run of `ci.yml` started on trunk, which judges the move and what landed meanwhile together, as every push's run judges a batch ("Runs, batches, and the release commit" in `releases.md`), and which the script waits for. A push another push beat is tried again, three times.

Once a move is on trunk and its run there is green (the proof's own run when it landed as proven, the run on trunk when it was rebased), the Pick job takes the newest move the run landed, and the Release job runs `cut.yml` on it, which releases it off trunk and records the release on trunk (`releases.md`, "How a release is made"). Until `cut.yml` has run on GitHub as far as the tag once and passed, the job runs it without `publish`, so it makes and proves both commits on `release-next` and stops before the tag; that run is what proves dispatching CI and `installed.yml` on the branch, `rake runtime:pin` on a dispatched run, and the pin commit's short CI found by its dispatched parent, and the job then takes `publish`. The first release it publishes is then the proof of the rest: the tag pushed with the App's token, `release.yml` started by that push and finding both runs, the published release's `installed.yml`, and the record on trunk. A move of only pins marked `ships: false` adds no `CHANGELOG.md` line, so the Pick job asks `tasks/release_commit.rb pending` of the CHANGELOG at the newest move, and when it has nothing under `[Unreleased]` it picks nothing and starts no release: the move is on trunk, and the next move or change that a person can observe makes the release. A release takes everything trunk held when the move began, not the move alone, as any release from trunk does. A move that landed and whose run on trunk was red with what landed meanwhile is not released, and its job is green all the same: the move passed its own proof and is on trunk, so the job warns, and its summary says that it landed, is not released, and names trunk's red run. What failed on trunk is the failure of `ci.yml`'s run there, which calls a person as any red trunk does, and a second failed job for the same red run would say a pin failed when none did (pin-watch run 45114311202: "Prove alpine-ruby alone" ended red with its move on trunk, because Lent and iOS jobs it does not touch were red). A red proof stays the job's failure, since then nothing landed.

A move that changes what a runtime holds, as a new Ruby's gems would, leaves `runtime/audited.yml` and `doc/licensing.md` behind the runtimes CI built, which only CI's "Licensing page is current" job can see (`license-audit.md`, "The licensing page"). When that job is the only one that failed, the script takes the two files the job uploaded, as a person would, adds them to the move's commit, and proves it once more.

Red, with more than one pin moved, the Alone job moves and proves each pin by itself, one after another (`max-parallel: 1`), each on trunk as it stands when its turn comes, and lands each that passes; the one that fails is the job named for it ("Prove libffi alone"), red. A single pin's red proof fails the Move job itself. Either way trunk is never given a move that did not pass.

A person is called by the failed run, and by nothing else. GitHub notifies the account that owns a scheduled workflow (the one that created it, or last changed its `cron`) when a run fails, by the notification settings that account already has ("Notifications for workflow runs", docs.github.com/en/actions/concepts/workflows-and-actions/notifications-for-workflow-runs), and the job's name and its summary say which pin, why, and which run of CI. An issue opened with the workflow's token was weighed: it would say the same at more length, but it needs `issues: write`, code to find and close its own issues, and someone watching the repository, and a scheduled run's failure already reaches that account with no setup. The `ci.yml` runs the workflow starts notify nobody: their actor is `github-actions[bot]`. That is why the job waits for them rather than handing on.

Why it is built so:

- **The workflow's own token, and a dispatch.** A push made with `GITHUB_TOKEN` starts no workflow run, but `workflow_dispatch` is the exception GitHub names ("When GITHUB_TOKEN triggers workflow runs", docs.github.com/en/actions/concepts/security/github_token), so `ci.yml` takes `workflow_dispatch`, and the jobs that need it have `contents: write` and `actions: write`. No account, app, or stored token is added. A dispatched run chooses its jobs from the commit, as a push's does, so a move, which changes more than the pins, gets the full CI; and it is that commit's run as a push's would be, which the pins and `release.yml` take (`releases.md`, "Which runs are a commit's").
- **`workflow_dispatch`, not `workflow_call`.** Called as a reusable workflow, `ci.yml` would run as part of the pin watch's run, with the caller's commit as `github.sha`, so every checkout in it would need the branch passed in, and its runs would not be `ci.yml`'s runs that the pins and `release.yml` look up.
- **Waiting in the job.** A job may run six hours, and a full run takes one to three. A `workflow_run` workflow started by the CI run's end would hold no runner, but GitHub does not say whether the end of a run its token started starts one (`releases.md`, "A job no runner took", has the same doubt), so the proof could stop silently.
- **A branch, and its rules.** `pin-move` is written only by this workflow, with `git push --force`, since a run cancelled midway may leave it behind, and it is deleted after each proof. The trunk-based rules against pushing branches and force-pushing (decisions, 2026-11-12) bind agents and people; this workflow is the exception, because a move with nobody in the loop has no one to run a fast check before its push, so the full run comes first, as a commit queue's robot proves a change before it reaches trunk. Renovate's `automergeType: "branch"` is the same shape ("Tools considered", below).
- **All together, then one at a time.** One proof covers every pin behind on most days; when it is red, the pins that pass still land the same day, and the failure is narrowed to one pin by name, at the cost of one full run of CI per pin moved.
- **Rebase on a busy trunk.** Agents push to trunk every few minutes, so a proof of an hour almost never finds trunk where it left it. Proving again after each rebase would never land. The move's files are its own (`runtime/sources.yml`, `runtime/licenses.yml`, `CHANGELOG.md`, the files `also` names, and `doc/licensing.md`, regenerated), so a clean rebase changes what the move meets, not the move, and the run started on trunk then judges the combination, as it judges every agent's commit.

`gh workflow run pin-watch.yml -f land=false` runs the watch, the move, and the proof, and leaves trunk alone. `PIN_PROVE_DRY_RUN=true .github/scripts/pin-prove.sh REPORT` makes the move's commit in the checkout and stops, pushing and starting nothing; with a name after REPORT, it moves that pin alone.

The verdict is the conclusion of the run of `ci.yml`, which the script reads once the run is completed. When `gh run watch` ends early, the script watches again. In the first real run, the proof of llvm-mingw alone was called red 2.5 minutes into a run in which no job had failed. Its branch was then deleted, and the next pin's dispatch cancelled that run as the newer request for the branch's concurrency group, so llvm-mingw was never judged. A red run's summary lists each job that failed and the step in it, or says that the run was cancelled. That list is what a person reads first when the run calls them.

What it does not do. A runner that never comes for a macOS job turns the proof red, as it turns any run red, and `runnerless.yml`, which heals only trunk's runs, does not run it again; the Alone job then proves each pin, and a second such loss calls a person.

### Held pins

A pin whose move needs a person's reading or choice has `hold` in `runtime/upstreams.yml`, with the reason. Holding a pin on purpose is not a failure, so a held pin behind does not fail the run: the watch reports it as `held`, with the reason and the day the oldest release newer than the pin came out (`since`), in the run's summary and its JSON, and the move leaves it. It is a failure when nobody has moved it for longer than `PinWatch::HELD_DAYS`, 30 days after that day: the watch reports it as `overdue` and fails, and fails every day after until a person moves it, since a fix upstream then waits on that person. Thirty days is ten times the three days Ruby 4.0.0 took to reach RubyInstaller, the longest planned move a hold waits for, and short enough that a fix does not wait a season unseen. The other pins behind still move in that run. The cost is that a security fix in a held input can wait 30 days before anyone hears of it. A hold covers a new release only where the upstream has `rebuild` ("The watch"): a later build of the pinned release is reported as `newer` and moved as any pin is, and the move refuses only a new release. On a day both are newer, the watch reports the build, and the held release is reported from the next run, with the day it came out, so its 30 days are counted from that day as before.

The day comes from GitHub, which dates every release (`published_at`), and for Ruby from its tarball. Ruby's index dates nothing, so for each release newer than the pin in the pin's line the watch sends one HEAD request to the tarball's URL the index gives, on `cache.ruby-lang.org`, and takes the day of its `Last-Modified` header (`modified` in `runtime/upstreams.yml`). That is the day the release's tarball appeared, the day `releases.md`, "The day Ruby 4.1.0 appears", times the other projects' builds from. A held Ruby, a preview among them, is overdue 30 days after that day as every hold is, whether or not RubyInstaller builds it. jdx/ruby marks its previews as prereleases, and they count while the pin is a preview, so its next Ruby is dated by GitHub as well. A tarball that sends no `Last-Modified`, or that the request cannot get, fails the watch, as an upstream it could not read does. So `test/pin_watch_test.rb` fails when a held upstream has none of three ways to be dated: it is on GitHub, it is dated by its tarball, or it shares a pin with a held upstream that is dated one of those ways.

What is held, and why:

- **Ruby and RubyInstaller.** The step from Ruby 4.1's preview to 4.1.0 is a person's to take (`releases.md`, "The day Ruby 4.1.0 appears"), and RubyInstaller's numbered release comes with it. After it, a patch release of Ruby 4.1, and RubyInstaller's build of it, is to move with no person, which needs code the move does not have yet ("Ruby's patches, with no person", below). jdx/ruby's next Ruby is held with them, as a move of Ruby; its later builds of the Ruby already pinned are not (`rebuild`, "The watch"), and move as any pin does.
- **AppImage's runtime.** Its pin holds the release's two programs, which GitHub's digests cover, and three things no release lists: the commit the tag names, the SHA-256 of GitHub's archive of that commit (the source each Linux release publishes for LGPL-2.1, section 6(a)), and, in `runtime/licenses.yml`, the versions of what the programs link statically: libfuse, squashfuse, zstd, zlib, musl, mimalloc, and GCC's runtime. The first two are mechanical (one request to GitHub's API for the tag's commit, and one small download). The versions are not: its `scripts/common/install-dependencies.sh` names only libfuse's and squashfuse's, and the rest are whatever Alpine's packages were in its build image that day, which no file records. A move would have to read them out of the new programs' own bytes, the evidence strings the license audit checks, which for zstd and mimalloc are messages with no version in them; and a new libfuse moves libfuse's own source pin, the LGPL source every Linux runtime publishes. Until that reading exists, the move cannot say the new entries are true, so the pin is held; AppImage releases a few times a year, and the hold goes overdue 30 days after one.

### A line that has ended

A pin with `line` takes only releases in its line ("The watch", above). When the line stops getting releases, nothing the watch sees changes: no newer release appears in it, the pin stays `beyond`, and the runtime keeps a library that no longer gets fixes, with nobody told (issue 23). The watch cannot read when an upstream ends a line. OpenSSL, Ruby, and Alpine each state their support in prose of their own, and the decision is for automation that takes care of every update, not for a reading of each policy (decisions.md, 2026-11-22). What the watch has is the day GitHub dates each release (`published_at`).

So `PinWatch::Quiet` calls a pin's line ended when both of these hold:

- Newer lines have released on at least three days (`ENDED_RELEASES`) since the line's newest release. The upstream is releasing, and leaving this line out.
- The line's newest release is older than 180 days (`ENDED_DAYS`), or than 1.5 times (`ENDED_GAPS`) the longest the upstream's listing ever went between two releases, whichever is longer. The line is quieter than the upstream has ever been.

A line the listing holds no release of last released before the oldest release it lists. An upstream that dates nothing never ends a line. The finding carries the day the line last released (`last`) whenever the upstream dates it, so the summary says how quiet a line is before it ends.

**The evidence.** On 2026-11-22 each rule below was replayed against the release history of every upstream with a line, as if the watch had run each day with each line pinned: OpenSSL's releases on GitHub (2023 to 2026), RubyInstaller's (2019 to 2026), jdx/ruby's (from April 2026), Ruby's own list (`_data/releases.yml` in ruby/www.ruby-lang.org, 2002 to 2026), and Alpine's (`alpinelinux.org/releases.json`, 2011 to 2026). zlib and libxcrypt have one line each, so nothing is beyond them. A false alarm is a day a rule called a line ended that released again later; the delay is the days from a line's last release to the rule's call.

| Rule | OpenSSL (9 lines) | RubyInstaller (10 lines of Ruby) | Alpine (32 branches) |
|---|---|---|---|
| The oldest release beyond the line is older than 365 days (reverted in 78dd2330) | false on 3.0 to 3.4, up to 894 days each, and calls 3.5 ended today, eight weeks after its last release | false on every line, 90 to 481 days each | false on 14 branches |
| The line's newest release is older than 180 days, and a newer line released since | none; 181 days | false on 7 lines, up to 236 days (3.1) | false on 9 branches |
| The same, older than 365 days | none; 366 days | false on 2.5, 2.6, 3.0, and 3.1, 15 to 24 days each | false on 3.5 and 3.6 |
| Older than 3 times the line's median gap | false on 3.0, 77 days | false on 2.6, 3.1, and 3.2 | false on 14 branches |
| Older than 1.5 times the longest gap in any line | false on 3.0, 77 days | false on 2.4, 2.5, and 2.6 | false on 3 branches |
| Newer lines released on 3 days since, at any age | none; 140 to 189 days | false on 3.1 to 3.4, up to 242 days | false on 12 branches |
| **Chosen** | **none; 181 to 189 days** | **none; 280 to 404 days** | false on 3.5 and 3.8 |

The chosen rule called no line ended that released again in OpenSSL's, RubyInstaller's, jdx/ruby's, or Ruby's history; Ruby's own list, whose sparse early years hold a gap of 565 days, would call its lines ended 848 days on, and jdx/ruby's 3.2 181 days on. Alpine's false alarms come from 3.5 and 3.8 releasing again after 558 and 323 days of silence between 2017 and 2020; the watch reads Alpine from Docker Hub, which it does not date, so the rule never runs on it. Ruby's lines are where a short rule goes wrong: a line in security maintenance can go 390 days between releases, as 3.0 and 3.1 did, so any limit shorter than that calls them ended while they live. The longest-gap term is what keeps them quiet: RubyInstaller went 269 days without a release in 2023, which puts its limit at 404 days, while OpenSSL's longest gap on its page, 118 days, leaves the floor of 180 in force. The requirement of three newer days keeps a line from ending while the whole upstream is quiet.

**What firing does.** The watch reports the pin as `ended` and fails, as it does for an overdue hold, and fails every day until a person moves the pin to a newer line. Nobody is called on the happy path, and a line's end is off it: a new line is planned work the move does not take, so fixes stop reaching the runtime until a person moves the pin. That is a failure a person has to hear of, and a scheduled run's failure is how one hears ("The proof", above). Reporting it only in the summary was weighed: no one reads a green run's summary, so it would be the silence issue 23 is about. The cost is a red run each day for a line that is in fact alive but quieter than any history above shows; a release in the line ends it at once, since the pin is then `newer` and moves.

**What it cannot know.**

- **When the line ended.** It hears of an end after the line has gone quiet, not when the upstream stopped it: about six months after the last release for OpenSSL, and nine to thirteen for Ruby's lines through RubyInstaller. Until then a runtime can carry a library that no longer gets fixes. The line of OpenSSL the musl and phone runtimes pin last released on 2026-09-29; if that was its last release, the watch calls it ended from 2027-03-29, once newer lines have released on three days since.
- **An upstream that dates nothing.** Ruby's index and Docker Hub's list of Alpine's tags date no release, and Ruby's tarballs are dated only for the releases newer than the pin in its line ("Held pins"), which is too few to tell a line's end from. Ruby's line is dated through RubyInstaller and jdx/ruby, which watch the same pin with the same line; Alpine's images ship in nothing (`ships: false`), so their branch's end is reported as `beyond` and no more. `test/pin_watch_test.rb` fails when a line that ships has no upstream on GitHub to date it.
- **A rebuild.** jdx/ruby publishes each build as a release of its own, so a rebuild of a Ruby whose line has ended dates that line anew and puts off the call.
- **A release published again.** GitHub dates a release by when it was published there: OpenSSL published 3.0.2 to 3.0.5 again on 2024-09-21. Such a day can make a line look alive, or shorten the longest gap.
- **A page of a hundred.** The watch reads one page of an upstream's releases unless it has `rebuild`, so the longest gap is the longest on that page: nearly four years of OpenSSL's, seven and a half of RubyInstaller's.

### Ruby's patches, with no person

Once Ruby 4.1.0 is pinned, a patch of 4.1 should move as libffi does. What the move would need, and why none of it is built yet:

- **jdx/ruby's assets.** The macOS and glibc Linux Rubies are jdx/ruby's, named `ruby-VERSION.PLATFORM.tar.gz` in the release of one build, `VERSION-N`, so a move of Ruby moves both the version and `jdx_release`, with GitHub's digest of each asset. For whichever rows take jdx/ruby's builds then, the same rule holds with their own asset names.
- **RubyInstaller's release**, `RubyInstaller-VERSION-1`, whose `.7z` for each Windows platform and its `.asc` signature replace the head build kept on Fledge's own release, each with GitHub's digest, with the signing key and its fingerprint unchanged; the runtime build already checks the signature against that key ("The RubyInstaller signing key", below).
- **Ruby's own tarball**, for the phone, musl, and Fledge-built Rubies, with the SHA-256 Ruby's index gives.

Each is a few lines of the move, but each depends on the shape the step to 4.1.0 leaves the pins in: whether Windows then runs RubyInstaller's release or that day's head build, and which Linux rows take rv-ruby's builds, jdx/ruby's, or Fledge's own. Code written now would be written against the shape of a preview, so it waits for that step, and the hold's reason says so until then.

### A quiet repository

GitHub disables a public repository's scheduled workflows when nothing has happened in the repository for 60 days (docs.github.com/en/actions/learn-github-actions/usage-limits-billing-and-administration#disabling-and-enabling-workflows, the page liskin/gh-workflow-keepalive cites), and a disabled schedule fails no run, so nobody would hear of it. A repository where nobody pushes is the pin watch's happy path, and a quiet stretch with no upstream release is exactly when it would stop. So `keep-schedules.yml` runs each day, and `tasks/keep_schedules.rb` asks GitHub's API the state of every workflow whose triggers name a schedule, itself among them, and enables each again (`PUT /repos/OWNER/REPO/actions/workflows/FILE/enable`), with the workflow's own token and `actions: write`, the one right that endpoint needs, beside `contents: read` for the checkout. One GitHub disabled for inactivity is enabled and named in a warning on the run; one a person disabled is left as it is. Its run fails, and so calls a person, only when the API refuses. Run by hand, it reads the states and enables none unless its `dry-run` input is false. `test/keep_schedules_test.rb` serves GitHub's own answer for a workflow, with each state the API gives, from a loopback server.

This is the step liskin/gh-workflow-keepalive takes (its `action.yml` is that one request, for the workflow that runs it), and what it was weighed against. An empty commit every few weeks, the older keepalive actions' way, is activity by GitHub's definition, but it puts commits nobody needs on trunk and needs `contents: write`. Failing a run when the last commit is near 60 days old would call a person on the happy path, which the decision of 2026-11-22 rules out. A job inside `pin-watch.yml` would serve as well, but a workflow of its own can be run by hand to read the states without starting a move. What is not proven: GitHub does not document that enabling an enabled workflow restarts the 60 days, and it cannot be seen before a stretch of 60 quiet days. If it does not, the cost is the one this guards against, a schedule that stops unseen, and since every scheduled workflow stops at once, nothing scheduled could report it. Every push, every pin move that lands, and every release is activity too, so the stretch needs both no upstream release of any pin and nobody pushing for 60 days.

### Tools considered

The watch is about 150 lines because no maintained tool fits the shape of `runtime/sources.yml`. Dependabot updates the manifests of package managers, GitHub Actions' `uses:`, and Docker images; it has no notion of a URL and SHA-256 pinned in a YAML file. Renovate does, with its regex managers and its `github-releases` and custom datasources, and its `automergeType: "branch"` is the shape step 3 takes ("automergeType", docs.renovatebot.com/configuration-options/). But it runs as a Node application with a write token, its branches pushed with the workflow's token start no CI, exactly as this workflow's would not, and the rest of a move (the SHA-256 from GitHub's digest, `runtime/licenses.yml`'s versions and evidence, the release) would still be Fledge's code, behind a configuration as long as `runtime/upstreams.yml`. nvchecker, the version checker Arch Linux's packagers use, finds versions from GitHub and from pages much as the watch does, but brings a Python tool to pin, gives a version without an asset or its SHA-256, and leaves the comparison with the pins to Fledge. Homebrew's livecheck has the same strategies (GitHub's latest release, a page and a pattern) and its autobump opens a pull request every three hours for formulae on its list (docs.brew.sh/Autobump), but it runs only inside Homebrew. So the watch takes their way of finding a version, a listing and a pattern, and keeps the pins' own shape.

### What the watch cannot know

It knows releases, not fixes. A fix backported without a new version, as a distribution's patched package, is invisible to it; MSYS2's package release numbers (`1.4-2`) would show one, but those inputs move with RubyInstaller. An advisory for a version that has no fixed release yet leaves nothing to move to. jdx/ruby compiles its own OpenSSL into the macOS and glibc Linux Rubies, so OpenSSL's fixes reach those runtimes only through a later build of jdx/ruby's that carries them, which the watch sees and the move takes, reading the OpenSSL it carries ("The move"), and jdx/ruby builds again with a newer OpenSSL only when a person there moves its recipe ("Why Fledge builds no Ruby for macOS and glibc Linux"). An advisory feed would be a second source: OSV and GitHub's advisory database index package managers' packages, not C libraries' release tarballs, and would need a mapping from each pin to the identifier each database uses; ruby-advisory-db covers Ruby itself and is cheap to read. Neither is wired in: what Fledge can act on is a release, and the watch sees every one.

The pins outside `runtime/sources.yml` are not watched: the Ubuntu packages and Xcode of CI's runtime jobs, the tools `mise.toml` pins, and the actions every workflow pins.

### Known limits

Each of these is a case in which the automation stops short, with what it costs and who hears of it. Those stated where their part is specified are gathered here too, so that this list is the whole of what is known.

- **A build that compiles in other library versions** than the move reads: a new GCC or Rust in Alpine's branch ("Alpine's packages"), or a build of jdx/ruby's with another Rust, whose `rustc` path the audit's evidence names, fails the license audit in the proof's run, which calls a person to move the entries of `runtime/licenses.yml`. Cost: one person's reading per such release; nothing ships until then.
- **What a build of jdx/ruby's carries that nothing reads.** Its CA bundle, `libexec/cert.pem`, which an app reads only on a computer with no certificates of its own, dates itself by a sentence ("as of: Tue Jul 15 03:12:01 2025 GMT") and not in the form of the entry's version (`cacert-2025-07-15`), so its entry, like each CA bundle's, pins the file's SHA-256 (`sha256` in `runtime/licenses.yml`, the same as for GNU MP's DLL), and a build with another bundle fails the audit as `stale` until a person moves the entry; and its `libcrypt.a`, which no runtime keeps, is not read either (`libxcrypt-static-jdx`). A date line was weighed and not taken: the extract Fledge pins for the phones and musl Linux says "last updated on: Wed Feb 11 18:26:30 2026 GMT", so no line says the entry's version, and a SHA-256 is the one form that works for all three. Cost: a move of a pin that carries a bundle must move the SHA-256 in the entry too, which `PinMove` does for curl's extract, and which a person does for jdx/ruby's and RubyInstaller's when their pins move.
- **Held pins** (Ruby, RubyInstaller, jdx/ruby's next Ruby, AppImage's runtime) wait for a person, and fail the run only after 30 days ("Held pins"). Cost: a security fix in one of them can wait 30 days before anyone hears of it.
- **A line that has ended** is heard of only once it has been quiet for 180 days, or 1.5 times its upstream's longest silence, while newer lines released on three days, and only where GitHub dates the releases; Alpine's branches are reported as `beyond` and no more ("A line that has ended"). Cost: a runtime can carry a library that gets no fixes for six months (OpenSSL) to thirteen (Ruby) before the run fails and calls a person.
- **Ruby's Alpine image** names Ruby's version in its tag, and so does the page the watch reads it from; both move by hand with Ruby ("Container images").
- **Docker Hub dates a tag by the day.** Two pushes of one tag on one day are seen as one, and the second is taken on the next push or not at all ("Container images"). Cost: CI may run on an image a day older than the newest; the pinned one is still whole.
- **A rebuild of an Alpine package** installs with no commit, since each musl job installs `NAME~UPSTREAM` ("Alpine's packages"). Cost: a tool's bytes, or GCC's runtime and Rust's standard library compiled into a musl runtime, may change without a commit while their upstream versions, which the license audit reads, stay the same.
- **A new Alpine branch** is reported and not taken; a person moves the images and every package pin together ("Alpine's packages"). Cost: Alpine's next branch reaches the musl runtimes only when a person moves it, as Ruby's next minor does.
- **The pins outside `runtime/sources.yml`**, the Ubuntu packages and Xcode of CI's runtime jobs, the tools `mise.toml` pins, and the actions every workflow pins, are not watched ("What the watch cannot know"). Cost: they move when a person moves them, and an Ubuntu package pin the archive drops turns a job red, as Alpine's did before they were watched.
- **A runner that never comes** for a job of the proof's run, or of the release's runs on `release-next`, turns that run red: `runnerless.yml` runs again only `trunk`'s own runs (`releases.md`, "A job no runner took"). For a move, the Alone job proves each pin again, and a second loss calls a person ("The proof"); for a release, the cut fails and calls a person, who runs `cut.yml` again on the same commit. Cost: a person, on a day GitHub's macOS runners run short.
- **The cut's time limit.** `cut.yml`'s Cut job waits in one job for the release commit's full run, `installed.yml`, the pin commit's short run, and `release.yml` with its own `installed.yml`, and GitHub stops it at 350 minutes, under the six hours a job may take. A full run takes one to three hours; on a day macOS runners are slow, the sum can pass 350 minutes, and the cut fails, which calls a person. Nothing is half published by it: the tag is pushed only after both commits' runs passed, and a release whose `release.yml` was cut short is finished by running `release.yml` on its tag by hand (`releases.md`, "release.yml").
- **A commit made before `cut.yml` existed** cannot be cut by it, since the cut uses the picked commit's own `tasks/release_commit.rb` (`releases.md`, "How a release is made"). Cost: none from now on; every later commit has it.
- **Whether enabling an enabled workflow restarts GitHub's 60 days** is not documented, and cannot be seen before 60 quiet days ("A quiet repository"). If it does not, every scheduled workflow stops at once and nothing scheduled can report it; any push, landed move, or release restarts the count, so the stretch needs no upstream release of any pin and nobody pushing for 60 days.
- **A release of a commit whose workflow files `trunk` no longer has** was refused at its first push until 2026-11-23: the cut pushed with the run's own token, which never holds the `workflows` permission, and GitHub then takes a workflow file only when "the same file (with both the same path and contents) exists on another branch in the same repository" (GitHub's [scopes for OAuth apps](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps), `workflow`). The first cut, of c5227c2a, was refused so, after three commits to the workflows had landed above it, while the pin watch's push of `pin-move` on `trunk`'s tip went through in the same minute (issue 25). The cut now pushes `release-next` and the tag with a token of the project's GitHub App, which holds that permission (`releases.md`, "How a release is made", "The push token"; issues 74 and 82). That a job of the pin watch's schedule can read the environment `release`, limited to `trunk`, that holds the App's secrets, and that a pick whose workflow files differ from `trunk`'s is accepted, are proved by the first cuts that run (issue 82). Cost: the App's private key is a secret of the repository, which a person must keep and may replace; a cut fails, calling a person, when the App is uninstalled or its key is revoked.
- **The first published release** is the proof of what `cut.yml` has not yet done on GitHub: the tag pushed with the App's token, `release.yml` started by that push and found by the cut, and the record on trunk ("The proof"). Until it has run once with `publish`, `pin-watch.yml` runs the cut without it, which stops before the tag, so a person turns `publish` on.

## A runtime left in tmp/runtime

`rake runtime` and `rake "runtime[PLATFORM]"`, desktop, Windows, iOS, and Android alike (they are one `RuntimeBuilder#call`), reuse the runtime that an earlier build left in `tmp/runtime` when it is the one this build would make, and build it again when it is not, saying which and why: `x86_64-linux: reusing tmp/runtime/…, built from the inputs it would be built from now`, or `x86_64-linux: building, because its pins changed since it was built`. Before this, every call removed the platform's build folder and built from nothing (only the downloads in the cache were kept), and a developer or a proof that wanted to avoid a stale runtime had to start from an empty `tmp/`. Nothing needs clearing now.

The runtime's key (`RuntimeBuilder::Key`, `tasks/runtime_builder/key.rb`) is a SHA-256 for each of what it is built from: the pins (`runtime/sources.yml`), the rest of `runtime/` but `audited.yml` (the launcher's C, the notices, the license records, the mobile projects' files), the build tasks (`tasks/runtime_builder*`, the license audit, the archive and download code), the parts of `lib/fledge/` those use, the platform with the computer that builds and Fledge's version, and the first line of each toolchain command's version output (the C compiler and `rustc`; `xcodebuild` and Xcode's `clang` for iOS; none for Windows, whose toolchain and Android's NDK are pins). The key is written to `NAME.key.json` beside the archive once the runtime is complete, and removed when a build starts, so an interrupted build leaves no key and is built again. A runtime is reused when every file of it is there (the archive, SBOM, NOTICES, and any source bundle) and every part of its key matches; otherwise the line names the parts that changed. `audited.yml` is left out because CI's runs write it and no build reads it. A pin for another platform in `sources.yml` also changes the key, which costs a rebuild that was not needed and never reuses a runtime that was; the other choice, reading only the pins a platform's recipe fetches, would put a second list of them in the key to keep true. An input read from outside the checkout that no pin names, such as a system library a Linux build links, is not in the key; the toolchain's version is the stand-in for those.

## Proving a runtime change before its push

`bin/check` is the fast check before every push: lint and the unit tests, in about half a minute (CONTRIBUTING.md, "Before a push"). It builds no runtime, and so it cannot see what a runtime change breaks. On 2026-11-22 a change of the glibc Linux runtime's Ruby, and two follow-ups, passed it and one parity run, and broke five of CI's jobs that nothing before the push had run: Delivery's restart check, Delivery of `build --from`, the licensing page's integration test, Android's parity check against the new reference Ruby, and ruby/spec on Android. `trunk` stayed red for hours.

`mise x -- ruby bin/check --runtime[=PLATFORM]` closes that hole for the commits that open it. It is the fast check, then `rake runtime:prove` (`tasks/runtime_proof.rb`): the runtime of this computer's platform, or Android's, built as CI's Runtime job builds it, and then the checks of CI's that run an app built from it, each by the script or task CI runs, in CI's order (CONTRIBUTING.md, "Before the push of a runtime change", lists them). It reuses those scripts rather than copying them, so the proof and CI cannot drift apart: `test/runtime_proof_test.rb` fails when the proof runs a script under `.github/scripts/` that `ci.yml` does not. The checks it runs are those that reach an app built from the runtime on its own platform, which today's red needed and the fast check cannot give: the parity check, Delivery, Delivery of `build --from`, and, for Android, mobile parity and ruby/spec in an emulator. The licensing page's integration test joins them because it reads `runtime/licenses.yml`, which a runtime change edits, and needs only LLVM's readers; with `FLEDGE_REQUIRE_READERS` it fails rather than skips without them, as in CI's gate, which sets the same variable.

The proof is a switch of the fast check's own command, not a second workflow, because a check that reaches farther belongs in the build script a developer already runs before a push, as Duvall, Matyas, and Glover's private build runs the integration build's steps on the developer's own computer before the commit. It is one run, on one platform, of the checks the change needs; it is not CI's full run made private. Every other platform, Delivery in other systems' images, the signed and windowed apps, iOS, and the integration tests that need a runtime stay in CI's full run, after the push, which proves each batch of commits on every platform, as Humble and Farley's deployment pipeline proves each commit stage's output in the stages after it.

A runtime built elsewhere comes in by `FLEDGE_RUNTIME_DIR`: Windows runtimes, which are built on Linux or macOS; musl ones, built in CI's Alpine image; and a glibc Linux runtime on a computer with neither docker nor user namespaces ("The glibc floor"). With a runtime CI built or a release published, the proof shows a change to Fledge's own code against that runtime, not a change to the runtime itself.

## Windows' Ruby until Ruby 4.1.0

The Ruby versions pinned today are not one release everywhere. While that release is a preview, which RubyInstaller does not build, the Windows pins name RubyInstaller's head build of Ruby's main branch taken on the day the release appeared, or the nearest day with one: today the build of 2026-11-10, ruby 4.1.0dev at 0e25874222, beside 4.1.0-preview1 at 2d08b5f42f everywhere else, since no head build exists from preview1's day. Its library folders may carry another ABI version (`4.1.0+6` beside the preview's `4.1.0+5`); nothing in Fledge keeps that name, which `RuntimeBuilder.ruby_abi` and `LicenseAudit#abi` read from each tree. RubyGems and Bundler call it Ruby 4.1.0.dev, where the others are 4.1.0.preview1 (`Gem.ruby_version`), so a Gemfile that asks for `ruby "4.1.0-preview1"` builds and starts everywhere but Windows, under `bundle exec` as in an app (`doc/contributors/design/gems.md`, "The runtime's Ruby version"). Each move to a later preview, a release candidate, or 4.1.0 moves every platform in one Fledge release, takes that day's head build, and says in `runtime/sources.yml` and the CHANGELOG which revision Windows runs against the release's own; at 4.1.0, RubyInstaller's numbered build replaces head.

Building every platform from one commit of Ruby's main branch would have Fledge build Ruby for macOS and glibc Linux too, two more builds to keep, which "Where each platform's Ruby comes from" defers until a maintained build fails. A Fledge release on every night's head build would turn trunk red whenever Ruby's main branch broke, and move every app's Ruby each day. So until 4.1.0 Windows runs another revision than the other platforms, with other default and bundled gem versions, another ABI version in its folders, and C API changes the preview lacks, and code that runs on one may not run on the other. The parity check compares each Windows app with the very head build its runtime came from, so that gap is not a parity difference.

## Rolling upstream inputs

Some inputs are published at a URL that serves a new file every day, as RubyInstaller's `rubyinstaller-head` release does. A pin of such a URL would stop resolving the next day, and with it every build, parity check, and audit that fetches it. Fledge keeps the exact files it pins, unchanged, as assets of a pre-release of its own repository, named `inputs-<source>-<date>` for where they came from and the day they were taken, such as `inputs-rubyinstaller-head-20261110`, or `inputs-rubyinstaller-head-<date>-for-<version>` when it is taken for a Ruby release, and the pins name that copy. Fledge's own Ruby builds are kept the same way, as `inputs-fledge-ruby-<version>-<date>-<commit>` ("Fledge's own Ruby builds"). The tag does not start with `v`, so `release.yml` does not run, and the pre-release is never the latest release. The pin keeps its SHA-256, and its signature and key where it has them, so the copy is held to the same bytes and the same signer as the original; `runtime/sources.yml` names the original URL in a comment, for provenance. Whoever publishes the pre-release checks each file's SHA-256 and signature again before publishing it; such a pre-release is never deleted, since every commit that pins it builds from it. A head build must be taken on its day: RubyInstaller's CI keeps each successful build as an artifact for about 90 days, but the `.asc` the build checks exists only on the release asset, which the next day's build replaces; `.github/workflows/keep-rubyinstaller-head.yml` takes it on each Ruby 4.1 release's day.

A copy that a release published beside its runtimes would not exist until that release's pin commit passed CI, which needs the input first. The Actions cache holds only on the branch that filled it, and for at most seven days unused, and committing the files would put tens of megabytes of binaries in every clone. The cost is that the files must be taken on the day upstream serves them, and that the releases list holds pre-releases that are not versions of Fledge.

## The glibc floor

A glibc Linux runtime needs no newer glibc than the newest `GLIBC_` symbol version any of its ELF files asks for, and `RuntimeBuilder::Linux#finish` fails the build of a runtime that has one above `Fledge::Platform::GLIBC_MINIMUM`, naming each file. Two things decide that version: whose Ruby the runtime copies, and where the builder compiles the launcher, `bin/ruby`, and libxcrypt.

**The Ruby is jdx/ruby's.** jdx/ruby (github.com/jdx/ruby) is a fork of rv-ruby, whose builds mise installs as its precompiled Rubies, and it builds each Ruby in a manylinux2014 container, against glibc 2.17. Measured on 2026-11-22, every one of the 101 ELF files of its 4.1.0-preview1 archive asks for `GLIBC_2.17` at most, on x86_64 and on arm64. rv-ruby's builds are made on Ubuntu 24.04: the x86_64 archive of its Ruby 4.1.0-preview1, measured the same day, asks for `GLIBC_2.38` (`__isoc23_strtoul` among others), and the runtimes Fledge built from it through v0.17.0 needed 2.38 in their launcher, `bin/ruby`, and `lib/libcrypt.so.2`, which the builder compiled on Ubuntu 24.04 with its GCC 13. Both projects lay out the same prefix (`bin/`, `include/`, `lib/` with a static libruby, `libexec/cert.pem`) from the same recipe, so the Unix recipe copies from either alike; jdx/ruby's archive holds it in `ruby-VERSION/` where rv-ruby's holds `rv-ruby@VERSION/VERSION/` (`Unix.prefix`). Its tree carries more beside it: static archives of OpenSSL, libyaml, zlib, and libxcrypt in `lib/`, with their headers and pkg-config files, of which the runtime keeps OpenSSL's and libyaml's for `fledge build` to compile gems against and leaves out the rest ("What a runtime keeps for compiling gems"). It also differs where a running program can see it, in two places. Its `openssl.rb` trusts the computer's CA certificates ("Certificates on glibc Linux", below). Its `rbconfig.rb`, when loaded, which RubyGems does as Ruby boots, prepends the prefix's `include/` and `lib/` to RbConfig's `CPPFLAGS`, `LDFLAGS`, and `DLDFLAGS`, and its `lib/pkgconfig` to `ENV["PKG_CONFIG_PATH"]`, so that a gem compiled against it finds the libraries it ships. A built app runs the same `rbconfig.rb`, as `ruby main.rb` on that Ruby does, so its `ENV` gains the same variable, naming the runtime's own `lib/pkgconfig`, which the app does not hold ("What a runtime keeps for compiling gems"), and each Ruby the app starts through `bin/ruby`, a restart included, puts the folder before it once more, as each Ruby a program on jdx/ruby starts does.

**macOS takes jdx/ruby's too** ("The Mac's Ruby is jdx/ruby's", below).

**Fledge's own programs are compiled in manylinux_2_28.** `.github/scripts/glibc-runtime.sh` runs the builder in PyPA's manylinux_2_28 image, AlmaLinux 8 with glibc 2.28 and a newer GCC from its gcc-toolset, pinned by digest for each architecture, as the musl runtimes are built in a pinned Alpine image ("musl Linux's Ruby, built in Alpine"). The digests are `runtime/sources.yml`'s `manylinux`, by the image's weekly release, which the pin watch finds newer ones of in quay.io's listing of the x86_64 image's tags, newest first; the move takes each architecture's digest of the new tag from the same API ("The move"), and the full run of CI that proves every move builds both runtimes in the new image, whose GCC may be newer. The image's Perl lacks its `open` module, which AlmaLinux ships apart as `perl-open` and libxcrypt's `configure` loads, so the script installs AlmaLinux 8.10's own package of it, with the two packages it requires that the image lacks, `perl-encoding` and `perl-Filter` (dnf's resolution of the install in the image, on 2026-11-22), all three together and none without its dependencies, each pinned by its SHA-256 in `runtime/sources.yml`'s `almalinux-perl`, the two that hold compiled code once for each processor. The pin watch leaves the three out: an RPM's version and release (`1.11-423.el8_10.1`) are no version Ruby's `Gem::Version`, by which the watch orders releases, can parse, so a person moves them when a new image's Perl needs it, and the full run of CI that proves a move of the image shows when it does. They are pinned at `repo.almalinux.org/almalinux/8.10/`, whose tree keeps every build of 8.10's packages (its listing held `perl-open` 1.10-404 to 1.12-475 on 2026-11-22), not at `almalinux/8/`, which follows the newest release; a retired release's tree is kept at `vault.almalinux.org/` under the same path, as `vault.almalinux.org/8.9/` still held `perl-open` 1.11-422.el8.0.1 on 2026-11-22, so the pins move there when 8.10 is retired. The image has no Ruby, so the script runs the builder on the platform's own Ruby pin, which it downloads on the host and checks by its SHA-256, and which the image's glibc can run. manylinux2014, glibc 2.17, would have let the floor fall to jdx/ruby's: its GCC 10.2.1, run with `-fanalyzer` as the launcher is always compiled, reports a double free in `forget_set_aside` (`runtime/launcher/unix.c`) that is not there, since each element of the array it frees is a separate `strdup`, and GCC 10's analyzer does not tell an array's elements apart. The analyzer stays a gate, with no exception for one compiler, so the image is the next one up. Every distribution release a person is likely to run still ships glibc 2.28 or newer: Debian 10, Ubuntu 20.04, RHEL 8 and its clones, Amazon Linux 2023.

**The image runs with docker, or with no root at all.** CI's runners have docker, and the script runs the image with `docker run`. A contributor's Linux computer, or a build machine, may have no docker, and no root to install it or rootless podman's helpers (`newuidmap`, the `/etc/subuid` ranges) with. There the script does what `docker run` does with two maintained tools that need no root: crane, go-containerregistry's, pinned in `mise.toml` by the SHA-256 its release's `checksums.txt` lists, writes the image's filesystem, named by the digest `runtime/sources.yml` pins, as one tar with its layers applied (`crane export`) and reads its environment from its config (`crane config`); bubblewrap, the distribution's `bwrap`, enters it as root of a user namespace of its own, with the checkout and the download cache bound where `docker run` binds them. In that namespace the build installs the Perl packages with `rpm` and writes the runtime as it does under docker, and every file it writes is the caller's already. GNU tar unpacks the image with `--delay-directory-restore`, since AlmaLinux keeps folders such as `/root` and `/usr/lib64` read-only, which an unprivileged tar cannot write into once it has given them their modes. On 2026-11-22 the script built the x86_64-linux runtime this way, on an x86_64 Linux computer with bubblewrap and neither docker nor podman, in under three minutes: GCC 14.2.1 and glibc 2.28 as in CI, the floor check and the license audit passed. Tools considered: rootless podman, which runs the same image with the same options, needs those helpers set up by root, and is not installed where docker is not; skopeo with umoci, which pull and unpack an image as crane does, in two tools rather than one, where skopeo publishes no build of its own to pin; and a registry client of Fledge's own, the few dozen lines of Ruby an earlier proof used, which "code is a liability" (decisions, 2026-10-28) rules out while crane does the same.

`Fledge::Platform::GLIBC_MINIMUM` names 2.28, the image's glibc, and every file of the runtime keeps to it: measured on 2026-11-22, the x86_64 runtime's newest `GLIBC_` version is 2.25, in `lib/libcrypt.so.2`, and its launcher and `bin/ruby` ask for 2.18. A gem compiled on the developer's own computer can raise an app's floor above it, which `fledge build` says (`doc/contributors/design/gems.md`, "The toolchain and the oldest systems"); the floors and when they may move are `doc/contributors/design/releases.md`, "Platform floors".

CI's Delivery runs apps where the floor says they run, on each processor: in AlmaLinux 8 (glibc 2.28), Amazon Linux 2023 (2.34), Ubuntu 22.04 (2.35), and Debian 12 (2.36), the oldest releases the floor admits of the systems a person is likely to run, each image pinned by digest in `runtime/sources.yml`'s `images` ("Container images") and none with Ruby installed (`ci.yml`, "Delivery on the oldest glibc"). hello comes from the Build job, built on Ubuntu 24.04 from the runtime. `test/fixtures/my_cool_app`, whose sqlite3 compiles from source for Ruby 4.1, is built in the job itself in manylinux_2_28 by `.github/scripts/glibc-app.sh`, which runs `fledge build` there on the platform's Ruby pin, as the runtime's build does, and so its compiled file needs no newer glibc than the image's; built on Ubuntu 24.04 instead, the same app gets `fledge build`'s warning and stops on the older systems with the dynamic loader's `GLIBC_2.38' not found`. Each image runs from a step with `docker run` (`.github/scripts/deliver-glibc-floor.sh`) rather than as the job's container, since GitHub's actions run inside a job's container with tools of the image's own, which a minimal image need not have.

On 2026-11-22 these scripts ran on an x86_64 Linux computer, with a runtime built there, as the job runs them. The my_cool_app built in manylinux_2_28 had a `sqlite3_native.so` whose newest `GLIBC_` version was 2.28, and hello and it ran in all four images and in Debian 13 and Ubuntu 24.04, the images the other Delivery jobs use; in each of those but Amazon Linux 2023, which has no `tar` for it, every check of `.github/scripts/deliver.sh` passed for both apps. The same app built on the computer itself, whose glibc is newer, got the warning for sqlite3's glibc 2.38 and stopped in AlmaLinux 8 for `GLIBC_2.33` and in Ubuntu 22.04 and Debian 12 for `GLIBC_2.38`, and ran in Debian 13 and Ubuntu 24.04. The same job delivers the HTTPS probe in each image ("Certificates", "The HTTPS check"). Amazon Linux 2023's image has no `tar`, so its step installs `tar` and `gzip` with `dnf` before it unpacks the apps. The ARM64 job's images and runs are CI's to show.

## The Mac's Ruby is jdx/ruby's

The macOS runtime takes jdx/ruby's Ruby, as glibc Linux does, from the same release, `ruby-4.1.0-preview1.macos.tar.gz`. It took rv-ruby's until 2026-11-22. Its reason to move is what a gem finds to compile against ("What a runtime keeps for compiling gems"): jdx/ruby's macOS tree holds OpenSSL's and libyaml's headers, static libraries, and pkg-config files for compiling gems, as its Linux trees do, and rv-ruby's holds none, so on a Mac a gem that links OpenSSL linked Homebrew's and was refused, or found none and built without TLS. The rule of 2026-11-22 is to look for a maintained project's build before building one, and none fits on the Mac but jdx/ruby's: rv-ruby publishes only Rubies (its release `20261119` holds 307 `ruby-*` archives and a `SHA256SUMS`); Homebrew's `openssl@3` keg has static libraries, but its OpenSSL's configuration and module folders are Homebrew's prefix, and its bottles are built for recent macOS versions only; python-build-standalone's archives keep no OpenSSL headers. Building OpenSSL in Fledge for the Mac was the alternative, at a few minutes of macOS CI for each build that moves its pin and a second OpenSSL version in each app's process beside rv-ruby's.

What jdx/ruby's archive is, measured on 2026-11-22 (SHA-256 `57fbc4a9`..., the one `runtime/sources.yml` pins):

- **Its macOS.** Every one of its 201 Mach-O files declares `minos` 26.0 (`vtool -show-build`), and so does every object in its six static libraries, the static libruby, `libssl.a`, `libcrypto.a`, `libyaml.a`, `libffi.a`, and `libz.a` (`otool -l`). So the floor is macOS 26 (`doc/contributors/design/releases.md`, "Platform floors"), the second floor the decision allows (decisions.md, 2026-11-22). macOS Tahoe 26 runs on every Mac with Apple silicon, from the M1 models of 2020 on (Apple's "macOS Tahoe 26 is compatible with these computers", support.apple.com, article 122867, published 2026-09-14), so no Mac that ran an arm64-darwin app before is left out but those that stayed on macOS 15.
- **Its processor.** arm64 only (`lipo -archs`), in every file, in 4.1.0-preview1's archive and in 4.0.10's, its newest release: jdx/ruby builds no Intel Mac Ruby, in one macOS job on an Apple silicon runner (`.github/workflows/build.yml`, `build-macos`). rv-ruby publishes Intel builds (`ventura`), so leaving rv-ruby leaves Fledge with no maintained project that publishes an Intel Mac Ruby beside the Apple silicon one it takes. Building apps for Intel Macs was an open question until then, whose default was no; with no Ruby to take for it, it is no longer one.
- **Its shape.** The static libruby the launcher links (`lib/libruby.4.1-static.a`), every extension a `.bundle` file, `--enable-load-relative`, and `bin/ruby` linking only CoreFoundation, libSystem, and libobjc: the same shape as rv-ruby's, so `RuntimeBuilder::Darwin` copies from it as before. YJIT is built in and ZJIT is not, as on glibc Linux, with Rust 1.58.1's standard library. It names its platform `arm64-darwin25`, for the Darwin it was built on.
- **What it carries.** No SBOM and no notices, as on Linux: `runtime/licenses.yml` names what it compiles in from jdx/ruby's recipes, the entries glibc Linux has (`openssl-jdx`, `libyaml-jdx`, `zlib-jdx`, `libffi-jdx`, `rust-std-jdx`, `ca-certificates-jdx`, `jdx-ruby`), with OpenSSL 3.5.5 in `openssl.bundle`, zlib 1.3.1 in `zlib.bundle`, and libffi 3.5.1 in `fiddle.bundle` linked statically, where rv-ruby's took zlib and libffi from macOS. CI's audit of the whole upstream tree finds what `.github/license-expectations/arm64-darwin.yml` lists, which a runtime prunes.

**A known risk: its floor is nobody's choice.** jdx/ruby sets no deployment target: neither its recipe (`libexec/package.rb`) nor `recipes/targets.yml`, which gives Linux `max_glibc: "2.17"` and macOS nothing, nor its workflows name one (jdx/ruby at 09c4b6b). 26.0 is the default of the SDK on the runner it builds on, `runs-on: macos-26` in `.github/workflows/build.yml`. When that label moves to macOS 27, its next build declares 27.0 with no notice. Fledge would not ship it: the license audit refuses a Mach-O file in a macOS runtime that needs a newer macOS than `Fledge::Platform::MACOS_MINIMUM` (`macos-floor`, `doc/contributors/design/license-audit.md`), so the move of that pin fails its proof. But then the pin cannot move without the floor moving, a major, and until one of them does, the Mac's OpenSSL takes no update. The cure is upstream's: jdx/ruby setting `MACOSX_DEPLOYMENT_TARGET` for its macOS build, as rv-ruby's formulae do (`Abstract/rv-portable-formula.rb`, line 52, at spinel-coop/rv-ruby 7f7993f). Whether to ask is the maintainer's.

What changed for a Mac app with the move, besides the floor: `RUBY_PLATFORM` is `arm64-darwin25` where it was `arm64-darwin23`; ZJIT is gone; a gem that links OpenSSL or libyaml links the runtime's ("What a runtime keeps for compiling gems"); the app trusts macOS's own `/etc/ssl/cert.pem` ("Certificates on macOS"); and jdx/ruby's `rbconfig.rb` puts the runtime's `lib/pkgconfig` first in `PKG_CONFIG_PATH`, as on glibc Linux (`Parity::JUSTIFIED`).

## Why Fledge builds no Ruby for macOS and glibc Linux

The Ruby of the macOS and glibc Linux runtimes is jdx/ruby's ("Where each platform's Ruby comes from", above). Fledge builds Ruby itself for musl Linux and the phones, and takes RubyInstaller's for Windows; for macOS and glibc Linux it builds Ruby only for testing against Ruby's master ("Fledge's own Ruby builds"), and no runtime ships it. The decision on it, 2026-11-22 (`decisions.md`): Fledge takes these Rubies from jdx/ruby because depending on a project that many people already use is preferred to depending on Fledge's own build automation, and the cost, that jdx/ruby's libraries lag, is a stated dependency, the same every mise user has.

**What lags.** jdx/ruby compiles into its Ruby the libraries its `recipes/dependencies.yml` names, and a person edits that file: on 2026-11-22 it had one commit, the one that created it on 2026-06-25, and its Ruby had been rebuilt about monthly since with the same libraries. Fledge's pin watch cannot move them: it takes what jdx/ruby releases, and a fix reaches Fledge's runtimes when jdx/ruby builds its Ruby again with it ("What is Fledge's own", below). On 2026-11-22, with the newest release of each library the same day:

| Library | In jdx/ruby's Ruby | Newest release |
|---|---|---|
| OpenSSL | 3.5.5 | 3.5.9 (of the 3.5 line, which jdx/ruby takes; Fledge's musl runtimes carry a newer line) |
| libyaml | 0.2.5 | 0.2.6 |
| libffi | 3.5.1 | 3.8.1 |
| zlib | 1.3.1 | 1.4 |

OpenSSL 3.5.6 to 3.5.9 fixed 45 vulnerabilities, 2 High, 8 Moderate, and 35 Low by OpenSSL's own ratings (`CHANGES.md` of OpenSSL 3.5.9). Most are in code Ruby's `openssl` extension (gem 4.0.2, read in Ruby's master of 2026-11-10) does not call: CMS, CMP, QUIC, and DTLS, where the second High is, a read past a buffer in DTLS retransmission. Ruby code reaches others, among them:

- CVE-2026-45447, High, fixed in 3.5.7: a use-after-free in `PKCS7_verify()` that OpenSSL says may result in "potentially, remote code execution". `OpenSSL::PKCS7#verify` calls it.
- CVE-2026-35189, Low, fixed in 3.5.9: a crafted peer certificate with many relative CRL distribution points makes OpenSSL use disproportionate memory, in clients and in servers that ask for client certificates. Any HTTPS client, `net/http` included, meets it.
- CVE-2026-72897, Low, fixed in 3.5.9: a TLS server that switches context during a handshake with `SSL_set_SSL_CTX()` may read and write out of bounds. Ruby's `servername_cb` does.

libyaml 0.2.6 fixes CVE-2026-44842 with a limit on nesting depth, libffi 3.8.1 is "a bug-fix and security release", and zlib 1.4 fixes overflows and bad writes in several functions. A gem that links OpenSSL or libyaml against the runtime (`doc/gems.md`) holds the same versions. An app developer who needs a newer OpenSSL has no setting for it: `fledge.yml` has no key for the runtime's libraries, and a fix reaches an app when a Fledge release carries a runtime whose Ruby has it, and the app is built again.

**What was examined instead, and why none was taken.**

- *Another project's Ruby.* rv-ruby's newest OpenSSL was 3.6.2 on 2026-11-22, no automated bump of it had landed in its newest 100 pull requests, its Linux builds need glibc 2.38 or newer, its macOS tree has no OpenSSL files for gems, and its releases are moving off GitHub. Traveling Ruby's OpenSSL, 3.5.9, was current, but its builds remove the static libruby the launcher links, are not relocatable by `--enable-load-relative`, and stop at Ruby 4.0.9. ruby/ruby-builder's and conda-forge's builds link a shared libruby and a shared OpenSSL under a fixed prefix. Homebrew's portable-ruby is archived, and python-build-standalone publishes no Ruby.
- *Asking jdx/ruby to bump its libraries by automation.* It is not enough alone: a pull request and a rebuild would each wait on a person there, and the Mac's floor would still be the runner's default.
- *Pinning jdx/ruby's numbered rebuilds.* Fledge does, and moves to each later one with no person ("What is Fledge's own", below), but a rebuild brings only the libraries jdx/ruby's recipe names, so alone it fixes nothing that recipe lags in.
- *Keeping jdx/ruby's Ruby and rebuilding the extensions that link these libraries* (`openssl`, `psych`, `zlib`, `fiddle`) and the headers gems compile against: about 100 to 150 lines (estimated), a hybrid no other project builds or tests, and it leaves the floor and the pin's address as they are.
- *A fork of jdx/ruby under setdef:* a repository to stand up and about 1,000 lines of jdx/ruby's `libexec/package.rb` to keep, against the 133 lines of `RuntimeBuilder::RubyBuild`.
- *Fledge builds Ruby for these platforms in the Runtime job, as for musl.* The pins the watch already moves would serve it. The cost, as the study measured and estimated it: 4 to 5 minutes more in each glibc Runtime job (estimated from the musl jobs' 5 to 6 minutes against the glibc jobs' under 1), 575 seconds of wall time for the Mac's Ruby on a 10-core M1 Max (measured) and 8 to 12 minutes on GitHub's `macos-26` runner (estimated), and about 150 to 250 lines changed (estimated), most of them `runtime/licenses.yml`, tests, and documents. It would give a fix in about a day with nobody acting, and it would make Fledge's own automation the thing every desktop developer relies on.

**What reopens it.** What "Where each platform's Ruby comes from" says: building Ruby for macOS and glibc Linux waits until jdx/ruby stops publishing, publishes a build that fails Delivery, or cannot be relied on.

**What is Fledge's own, whatever the Ruby's source.** Fledge carries what jdx/ruby releases to a Fledge release, with no person on the happy path; it does not make jdx/ruby's libraries current. The pin names the release of one build, which a later build does not change ("Sources and pins"). The watch sees a later build of the pinned Ruby as the pin's next version though the upstream is held (`rebuild`, "The watch"), and a new Ruby stays held ("Held pins"). The move takes the build: the three URLs and GitHub's digest of each file, `jdx_release`, the `jdx-ruby` entry, which names the build and its tag, the Mac's platform name, and the versions of OpenSSL, libyaml, zlib, and libffi, which it reads out of each platform's archive, with a line in `CHANGELOG.md` for the build and for each library that moved ("The move"). Then the proof ("The proof") runs a full CI on the move's own branch and lands it only if every job is green, and the Release job cuts a release of it, for now stopping before the tag until `cut.yml` has gone that far once ("The proof").

What in that full run refuses a bad build, by what it would get wrong:

- *A tree of another shape* (another top folder, a missing static libruby, an extension moved): the Runtime job of that platform fails to build the runtime, and parity and Delivery have nothing to run.
- *A file that needs a newer glibc than 2.28*: `RuntimeBuilder::Linux#finish` fails the build, naming each file ("The glibc floor"); jdx/ruby's own build refuses one above 2.17 before it publishes.
- *A newer macOS minimum*: the license audit's `macos-floor` rule refuses the runtime (`license-audit.md`); the pin then cannot move until the floor does, and the run calls a person ("What reopens it", above).
- *A library compiled in under another version*: the move reads OpenSSL's, libyaml's, zlib's, and libffi's, and stops when the platforms' archives disagree; a version it does not read, as Rust's, fails the audit's evidence, which calls a person ("Known limits").
- *A component added* (a new static library or a library's files under new names): CI's "Licenses of the whole upstream tree" jobs audit jdx/ruby's whole tree against `.github/license-expectations/`, and a file no entry owns fails them, as an unlisted file in the runtime fails its build.
- *Ruby that behaves otherwise*: parity compares an app built from the new runtime with `ruby main.rb` on the same archive, and Delivery runs built apps on macOS 26, on the oldest glibc systems the floor admits, and on Debian and Ubuntu; `test/integration/openssl_gem_test.rb` compiles a gem against the runtime's OpenSSL.

What gets past all of them: a library whose license changes while its files keep their names (the move rewrites a version, and nothing reads a license); the CA bundle and `libcrypt.a`, which nothing reads ("Known limits"); a build whose bytes are not what jdx/ruby's workflow built but behave as it would in every check, since the SHA-256 comes from GitHub's record on the same host and Fledge checks neither the SLSA provenance nor the GitHub attestation jdx/ruby publishes for each build; and any fault no test reaches. The watch reads the newest build in each run; a build that jdx/ruby publishes and then replaces with a higher N before the watch runs is skipped, which costs nothing, since the later one is what jdx/ruby would have mise users take.

## Certificates

An app that makes an HTTPS request with Ruby's own `net/http` and `openssl` verifies the server's certificate against what the runtime's Ruby trusts, on each platform, as the same program does under `ruby main.rb` on the Ruby the runtime came from. Fledge changes none of it: the rule is that Ruby's, and the parity check holds the app to it. The rules differ by platform, because the Rubies do.

### Certificates on macOS

A macOS app trusts what jdx/ruby's Ruby trusts, by the same `openssl.rb` as on glibc Linux ("Certificates on glibc Linux", below): the first of the computer's own bundle files it finds, which on a Mac is `/etc/ssl/cert.pem`, the list of certificate authorities macOS itself keeps there, then the runtime's `libexec/cert.pem` only where none is found; `SSL_CERT_FILE` and `SSL_CERT_DIR` win over both. The Keychain is not read: OpenSSL does not read it, and jdx/ruby adds nothing that does, so a certificate authority a company installs in the Keychain is trusted by Safari and not by the app, as it is not by `ruby main.rb` on that Ruby. That is a difference from a native Mac program, kept because it is the Ruby's: an app that needs such an authority sets `SSL_CERT_FILE`, or its code gives `net/http` a `ca_file`, as under `ruby`. Until 2026-11-22 the Mac's Ruby was rv-ruby's, which renamed OpenSSL's `SSL_CERT_FILE` to `PORTABLE_RUBY_SSL_CERT_FILE` and read the runtime's bundle first.

### Certificates on glibc Linux

A glibc Linux app trusts what jdx/ruby's Ruby trusts. Its `openssl.rb` and its OpenSSL's default certificate paths look first at the computer's own CA certificates, the first of `/etc/ssl/certs/ca-certificates.crt` (Debian, Ubuntu, Alpine), `/etc/pki/tls/certs/ca-bundle.crt` (RHEL, Fedora, Amazon Linux), `/etc/ssl/ca-bundle.pem` (openSUSE), and `/etc/ssl/cert.pem`, and the folders `/etc/ssl/certs` and `/etc/pki/tls/certs`. Only on a computer with none of those files does it set `SSL_CERT_FILE` to the runtime's `libexec/cert.pem`. `SSL_CERT_FILE` and `SSL_CERT_DIR` in the environment win over both, and so do `JDX_RUBY_SSL_CERT_FILE` and `JDX_RUBY_SSL_CERT_DIR`, which `openssl.rb` copies into them.

That is right for three reasons. It is what the same program does under `ruby main.rb` on that Ruby, which the parity check holds the app to. It is what a native Linux program does, so a company's own certificate authority, installed in the computer's store, and the distribution's updates to the store reach the app. And a bundled file ages with the app: a certificate authority distrusted after the app was built stays trusted by a file nobody updates. The bundled file remains for a computer with no store, such as a slim container.

The launcher hides from Ruby's boot the variables that would let a person's own Ruby reach the app (`doc/contributors/design/launcher.md`, "Hiding and restoring the person's Ruby settings"). The four certificate variables are not among them: Ruby's boot does not read them, `openssl.rb` reads them when the app requires `openssl`, as it reads them under `ruby main.rb`, and naming certificates is a choice the person who runs a program makes for every program they run. So they are the app's environment like any other variable, on every platform.

### Certificates on musl Linux

A musl Linux app trusts what the runtime's own Ruby trusts, which Fledge builds with rv-ruby's rule ("musl Linux's Ruby, built in Alpine"): its `openssl.rb` sets `PORTABLE_RUBY_SSL_CERT_FILE` to `SSL_CERT_FILE` or to `libexec/cert.pem`, so the app reads the runtime's bundle as a macOS app does. Its OpenSSL is configured with OpenSSL's default folder, `/etc/ssl`, so its default directory is `/etc/ssl/certs`, which OpenSSL searches by hashed names (`HASH.0`), and `SSL_CERT_DIR` names another. So the computer's store counts by half. Alpine's `ca-certificates` package's `update-ca-certificates` writes a hashed name for each authority beside its bundle file, and an authority a person adds that way is trusted: on 2026-11-22, in the pinned Alpine image with that package added, a test authority put in `/usr/local/share/ca-certificates` and `update-ca-certificates` run was trusted by the app and by the runtime's `bin/ruby` under `ruby main.rb`. An authority only appended to `/etc/ssl/certs/ca-certificates.crt`, the one file the bare image's `ca-certificates-bundle` installs, is not, by either. That is the reference Ruby's rule, so the app keeps it.

### Certificates on Windows

A Windows app trusts what RubyInstaller's Ruby trusts, and Fledge's Windows builder changes nothing of it. RubyInstaller's OpenSSL is MSYS2's, built with the folder `/ucrt64/etc/ssl` and relocated at run time to the folder beside its DLLs, so its default file is the runtime's `ruby\lib\ruby\4.1.0+6\etc\ssl\cert.pem`, with the hashed folder `certs` beside it, as RubyInstaller's own `README-SSL.md` there says, and `SSL_CERT_FILE` names another file in its place. On 2026-11-22 the runtime's `ruby.exe`, run on Windows 11 from an app unpacked in a temporary folder, reported that folder's `etc\ssl\cert.pem` as `OpenSSL::X509::DEFAULT_CERT_FILE`, refused a server whose authority was nowhere, and trusted it from `SSL_CERT_FILE` and from the bundle. Windows' own store is not read, by OpenSSL or by RubyInstaller, so an authority a company installs there is trusted by Edge and not by the app, as it is not by `ruby.exe`; as on macOS, that is the Ruby's difference from a native program, and the app keeps it.

### Where each bundle comes from

Each runtime's bundle is Mozilla's list of certificate authorities, and each is pinned by the SHA-256 of what it comes in. The macOS and glibc Linux runtimes copy jdx/ruby's `libexec/cert.pem` from the pinned archive (`runtime/sources.yml`, `ruby.platforms`), which they read only on a computer with no bundle of its own; the musl Linux runtimes and the phones' copy curl's extract from its own pin (`musl-ruby.ca-certificates` and `mobile.ca-certificates`); the Windows runtimes keep RubyInstaller's, in its signed and pinned archive. `runtime/licenses.yml` names each extract (`ca-certificates`, `ca-certificates-jdx`, `ca-certificates-msys2`) and pins its SHA-256, which the license audit checks against the file in the runtime, so the version in the notices, the SBOM, and `doc/licensing.md` is the version of the bytes the app carries (checked 2026-11-22: jdx/ruby's three archives hold one `cert.pem`, curl's extract of 2025-07-15 byte for byte, and RubyInstaller's two hold one, "as of: 2026-10-21 11:14:25 UTC"). jdx/ruby's file is curl's extract of 2025-07-15, older than the musl pin's, which is one reason it is read last. Since the file is fixed by those pins, the HTTPS check below needs no public server to show which file an app reads: it puts a certificate of its own in that file.

### The HTTPS check

Delivery asks every desktop app that makes an HTTPS request to verify a server, with no network beyond the computer and no server anyone else runs. `.github/scripts/https-server.sh` makes a certificate authority for the run alone and a certificate it signs for `127.0.0.1`, and serves it with `openssl s_server`, on the runner, from the `openssl` command the runner has, OpenSSL's or the LibreSSL of macOS. It serves a file that gives its length (`-HTTP`) rather than `-www`'s page, which has none: LibreSSL's `s_server` ends that page's connection with no TLS `close_notify`, and Ruby's OpenSSL 3, reading a body to the connection's end, reports `SSL_read: unexpected eof while reading` after the certificate has verified. The probe, `test/fixtures/https`, asks the URL it is given and prints the status, or that the certificate did not verify, with each variable that names a certificate file. The script's `prepare` makes the authority and the certificate without serving them, for the mobile check, which puts the authority in the phone apps' certificates before it builds them (`parity.md`, "The mobile parity").

`.github/scripts/deliver-https.sh` runs it, and `deliver-https.ps1` on Windows, which starts the same server through Git's `bash`, with an empty `PATH`, or only Windows' own folders on it, and no Ruby, once for each place the authority's certificate can be, and checks that the app trusts the server or refuses it as the platform's Ruby does:

| The authority is | macOS | glibc Linux | musl Linux | Windows |
| --- | --- | --- | --- | --- |
| nowhere | refused | refused | refused | refused |
| in the file `SSL_CERT_FILE` names | trusted | trusted | trusted | trusted |
| added to the runtime's bundle | trusted | trusted only with no store; refused where the store is read in its place | trusted | trusted |
| in the computer's store | refused (the Keychain) | trusted | refused in its bundle file; trusted by its hashed name | refused (Windows' store) |

The first case shows that the check fails when certificates do not work, and the third that the bundle is, or is not, the file read. The fourth changes what the computer trusts, so it runs only on GitHub's runners, where `GITHUB_ACTIONS` is `true` (`CI` is set on other computers too), with `sudo security add-trusted-cert` into the System keychain on macOS, `update-ca-certificates` on Ubuntu, and `Import-Certificate` into the local machine's root authorities on Windows, each undone after but macOS's: there `security remove-trusted-cert` waited, unanswered, until the job's time ran out, and each of GitHub's runners is a new machine thrown away after its job, so the authority stays, and the case runs on macOS only there; and in a container made for the check, which `--store-may-change` names, where the authority is added to the image's own bundle file, and on musl Linux then under its hashed name in `/etc/ssl/certs`, as `update-ca-certificates` would name it (the server writes the name, from `openssl x509 -hash`, since the bare Alpine image has no `openssl` command). Elsewhere it says it was not tried. The Delivery jobs of macOS and glibc Linux run it on their runner; the jobs on the oldest glibc, in each image, and musl Linux's, in the bare Alpine image, run it there, the image on the runner's network (`.github/scripts/deliver-glibc-floor.sh`, and the musl job's own step); and the Windows jobs, x64 and ARM64, on their runner.

## libxcrypt on glibc Linux

rv-ruby and jdx/ruby link libxcrypt, which is LGPL-2.1-or-later, statically into their own `bin/ruby`. A glibc Linux runtime never ships that `bin/ruby`. It builds the same libxcrypt release from its pin with rv-ruby's configure options, shared instead of static, and with libxcrypt's own `--disable-werror` (`RuntimeBuilder::Linux::LIBXCRYPT_CONFIGURE`). That option drops only the `-Werror` libxcrypt's configure adds, and keeps every warning it enables: libxcrypt 4.5.2 assigns `strchr`'s result to a `char *` in `crypt-sm3-yescrypt.c` and `crypt-gost-yescrypt.c`, which GCC 15, compiling C23 by default against glibc 2.43's `strchr` that keeps its argument's `const`, reports as a discarded qualifier, so with `-Werror` the release does not build on a current distribution. libxcrypt fixed those lines after 4.5.2 (commit 174c24d6e8), and the option costs a release with the fix nothing. The runtime installs `libcrypt.so.2` into the runtime's `lib/`, stripped, and links the launcher and its own `bin/ruby` against it. The source bundle's `BUILD.txt` prints those options as the way the runtime's copy was built.

libxcrypt ships as a shared library a person can replace, as the license policy asks of an LGPL library (`doc/contributors/design/license-audit.md`, "LGPL linked into a component that is not Fledge's"). Linked statically, as rv-ruby links it, its code would sit inside a program an app's developer ships as their own. musl's crypt in its place would keep `String#crypt` from behaving as under `ruby`: it silently computes a DES hash for yescrypt, the default password hash of current Debian, Ubuntu, and Fedora (`doc/contributors/research/2026-11-10-findings-from-the-adrs.md`, "The permissive spike: what the first license audit found"). The cost is a library Fledge builds in each glibc Linux runtime build, following rv-ruby's release of it.

musl Linux ships no libxcrypt: musl's own `crypt(3)` serves `String#crypt`. It does not know every hash current glibc systems use, so an app that checks such hashes on Alpine meets what `ruby` does there.

## The RubyInstaller signing key

Every Windows runtime build checks RubyInstaller's archive against its detached PGP signature (`RuntimeBuilder::Windows#verify`):

1. the signature and the key are downloaded and checked against their SHA-256s;
2. the key's ASCII armor is decoded (`RuntimeBuilder::Armor`, with its CRC-24 checked), since `gpgv` reads only a binary keyring;
3. `gpgv` checks the signature against a keyring of that one key;
4. the signature must be that key's, by the fingerprint the pin names (`VALIDSIG`).

The key is RubyInstaller's package signing key as `oneclick/rubyinstaller2` records it, `recipes/unpack/appveyor-repo-key.asc`, at a pinned commit. Both Windows archives are signed with it.

The pin records the key's expiry. `gpgv` does not judge a key's expiry, so an archive already pinned keeps verifying after that date. When the Ruby pin moves to a RubyInstaller release signed by a renewed or a new key, whoever moves it pins that key the same way: its URL in `oneclick/rubyinstaller2` at a commit, its SHA-256, its fingerprint, and its expiry. `test/runtime_builder_test.rb` checks that every Windows pin has all four.

## Windows on ARM64

`aarch64-mingw-ucrt` is built as `x64-mingw-ucrt` is, from RubyInstaller's ARM64 archive of the same release, with llvm-mingw for `aarch64-w64-mingw32` ("Where each platform's Ruby comes from"). It is a native runtime, not the x64 runtime under Windows' emulation, since a native program runs at full speed and Windows on ARM is to be supported (`decisions.md`, 2026-10-26, decision 22); the x64 runtime under emulation was the other option, and no recorded reason preferred it. It costs little: RubyInstaller's ARM64 archive comes from the same release, signed with the same key, and the pinned llvm-mingw already targets `aarch64-w64-mingw32`, so the recipe is the x64 one with another archive and triple. What differs:

- **GNU MP.** The audit pins the ARM64 `libgmp-10.dll` by its own SHA-256. It is byte for byte the DLL of MSYS2's CLANGARM64 package of the same source package as x64's, which CI's Runtime job checks, and the source bundle's `BUILD.txt` says how to build a replacement for `aarch64-w64-mingw32`.
- **No GCC runtime.** LLVM built RubyInstaller's ARM64 tree, so `runtime/licenses.yml` lists no libgcc for it. The MinGW-w64 runtime and winpthreads are as on x64.
- **The tools are x64 and x86 programs** (rcedit, NSIS, `llvm-readobj`), which Windows 11 on ARM64 runs under its own emulation. None ships in an app.
- **Temporary copies of the tools.** The emulator's cache service, XtaCache, holds an emulated program's file open for a while after it exits, so a folder that held the program cannot be deleted at once. So `Fledge::Nsis` runs makensis, `Fledge::WindowsResources` runs rcedit, and `Fledge::AppGems` runs `llvm-readobj` from a copy in the system's temporary folder (`Dir.mktmpdir`), which each removes as far as Windows lets it and leaves the rest to the temporary folder. They do so on every Windows computer, so the code has one path.

## musl Linux's Ruby, built in Alpine

`RuntimeBuilder::Musl` (`tasks/runtime_builder/musl.rb`) builds Ruby from source on a computer of each architecture, in Alpine. CI runs it in the Alpine Ruby image `runtime/sources.yml` pins by digest (`images.alpine-ruby`, which a workflow reads as `ALPINE_RUBY`), whose Ruby is the build's `--with-baseruby`, with the packages `.github/scripts/alpine-packages.sh build` pins by version: a C toolchain, Rust for YJIT, Perl for OpenSSL's build, and binutils, whose objdump the license audit reads with. Before it configures Ruby, it makes one edit to Ruby's source, `thread_c` (`RuntimeBuilder::Musl::EDITS`; `doc/contributors/design/phone-runtimes.md`, "Scripted edits to Ruby's source"): `Thread#name=` on a thread that has ended passed its freed `pthread_t` to musl's `pthread_setname_np`, which crashed stock Ruby and the app alike in ruby/spec's `core/thread/to_s_spec.rb` (run 43354884978), until Ruby 4.1.0 brings ruby/ruby 6fdd452087.

1. **Libraries.** zlib, libyaml, and libffi are built from their `musl-ruby` pins, static and position-independent (`-fPIC`), and OpenSSL `no-shared` the same way, so each links into the one extension that uses it, as rv-ruby's glibc builds link them.
2. **Certificates.** As rv-ruby does (`Formula/rv-portable-openssl.rb`, line 77; `Abstract/rv-ruby.rb`, lines 203 to 208, at 7a0e584), OpenSSL's `SSL_CERT_FILE` is renamed `PORTABLE_RUBY_SSL_CERT_FILE` in its source, so no other program's OpenSSL reads it, and the installed `openssl.rb` sets it to `SSL_CERT_FILE`, or else to `libexec/cert.pem` beside the Ruby, before it loads `openssl.so`. Each edit fails the build when the line it replaces is gone.
3. **Ruby.** From its release tarball, configured and built in its source folder, as rv-ruby builds it (`Abstract/rv-ruby.rb`, lines 157 to 174, at f57186e), `--enable-load-relative --disable-shared --enable-yjit --without-gmp`, every extension a shared object, `win32` and `win32ole` left out, linked `-static-libgcc`, and installed with `make install-nodoc`. Built beside its source, Ruby's install wrote default gems' specifications unlike a desktop's, and RubyGems did not activate io-nonblock for `require "io/nonblock"` (`doc/contributors/design/phone-runtimes.md`, "Building Ruby for a phone").
4. **The CA bundle** from its pin, as `libexec/cert.pem`.
5. **The rest is the Unix recipe:** the launcher and `bin/ruby` linked against that `libruby-static.a`, the standard library, pruning, Fledge's RubyGems defaults, AppImage's runtime in `tools/`, and the audit.

Fledge builds this Ruby because no prebuilt one fits, the fallback "Where each platform's Ruby comes from" names, as python-build-standalone builds CPython. rv-ruby publishes musl builds, and they are the wrong shape for a launcher: they are configured `--with-static-linked-ext` (`alpine/4.sh`, line 11, spinel-coop/rv-ruby at 7f7993f), so every extension of the standard library is linked into their own `bin/ruby`, and their `libruby-static.a` ships without them, so a launcher linked against it has no `json`, `openssl`, or `psych` (first found on 2026-11-10, `doc/contributors/research/2026-11-10-findings-from-the-adrs.md`, "musl Linux: the Alpine build spike"). Measured again on 2026-11-22, in both archives of Ruby 4.1.0-preview1 in rv-ruby's release `20261119`, `ruby-4.1.0-preview1.x86_64_linux_musl.tar.gz` and `ruby-4.1.0-preview1.arm64_linux_musl.tar.gz`: `rbconfig.rb`'s `configure_args` hold `--with-static-linked-ext` and its `EXTSTATIC` is `static`; the only shared objects are eight bundled gems' (bigdecimal, debug, fiddle, nkf, prism, racc, rbs, syslog); `libruby-static.a` defines no `Init_openssl`, `Init_json`, `Init_psych`, or `Init_socket`, only the empty `Init_ext` of Ruby's `dmyext.c`, and no archive of an extension ships beside it. The archives carry no SBOM and no notices for the OpenSSL, libyaml, libffi, and zlib their `bin/ruby` links, which the license audit would need, and their `bin/ruby` keeps the build's `/tmp/static-deps/lib` in its `RUNPATH`. The two other projects that publish prebuilt Rubies do not fit either: jdx/ruby's release `4.1.0-preview1` has no musl archive, and Traveling Ruby's newest Ruby is 4.0.9, with no 4.1 or preview. Taking rv-ruby's `bin/ruby` in place of a launcher would undo how a Fledge app starts Ruby (ADR 001; `doc/contributors/design/launcher.md`, "The program runs as ruby runs it"), and compiling only the extensions against rv-ruby's headers would keep Ruby's source, OpenSSL's, and the Alpine toolchain all the same, with a second Ruby's layout to match. Alpine's own `ruby` package is built for `/usr` and links Alpine's shared OpenSSL and libyaml, which an app's computer may lack. Built this way, a musl runtime is the pinned Ruby every other runtime is, and runs on any musl Linux, not only the Alpine it was built in. musl is supported because many CI platforms run only on musl Linux (`decisions.md`, 2026-10-26, decision 12). The cost is a Ruby build Fledge keeps, with its pins moved on purpose and the certificate edits rechecked at each Ruby release; CI runs it with `docker run` on a runner of each architecture, since GitHub's JavaScript actions cannot run inside an Alpine container on ARM. If rv-ruby's musl builds kept their extensions as shared objects, they would serve, and this build could go.

The parity check's reference on musl is this build's own `bin/ruby` with Fledge's RubyGems defaults taken out (`doc/contributors/design/parity.md`).

## Fledge's own Ruby builds

Apps and frameworks are to be tested on Rubies much newer than the last numbered one, on every platform, and Fledge is to help Lota and Tokra test with its releases and ship sample apps on recent Rubies (decisions.md, 2026-11-21). jdx/ruby, whose builds the macOS and glibc Linux runtimes take ("Where each platform's Ruby comes from"; "The glibc floor"), and rv-ruby, whose builds they took until 2026-11-22, publish numbered versions and previews only, and no other project publishes a relocatable build of Ruby's master with a static libruby ("Where a recent Ruby comes from", below). So Fledge builds one for those platforms itself: `tasks/ruby_archive.rb` (`RubyArchive`, run as `ruby tasks/ruby_archive.rb PLATFORM`) writes `tmp/ruby-archive/ruby-VERSION-PLATFORM.tar.gz`.

One archive serves a runtime and a developer:

- **rv-ruby's shape.** The archive holds `ruby/VERSION/`, a prefix in Ruby's own layout (`bin/`, `include/`, `lib/` with the static libruby and `lib/ruby`, `libexec/cert.pem`), as rv-ruby's archives hold theirs, so a runtime's `ruby.platforms` pin can name either by URL and SHA-256 and the Unix recipe copies a runtime from either alike (`Unix#unpack_ruby` finds `*/VERSION`). Moving the build to another home later changes a URL.
- **The musl runtimes' Ruby.** `RuntimeBuilder::RubyBuild` builds it, the steps the musl recipe takes ("musl Linux's Ruby, built in Alpine"): a static libruby configured `--enable-load-relative`, every extension a shared object, and OpenSSL, libyaml, libffi, and zlib from `musl-ruby`'s pins, linked statically into the extensions that use them. The source is `runtime/sources.yml`'s `ruby-build.ruby`, a release-shaped tarball, and takes no scripted edit.
- **YJIT and ZJIT.** Both are configured in (`--enable-yjit --enable-zjit`), so a Ruby without either fails to configure rather than build without it, and the build fails unless `ruby --yjit` and `ruby --zjit` each report their JIT enabled. Lota runs both. The Rust compiler and standard library are `ruby-build.rust`'s pins, the release `mise.toml`'s Rust names, installed into the build folder by their own installers.
- **libxcrypt on glibc Linux,** built from its pin as a glibc runtime builds it ("libxcrypt on glibc Linux"), shared: `lib/libcrypt.so.2`, with `lib/libcrypt.so` for a gem's `-lcrypt`, and `bin/ruby` finds it through the RPATH `$ORIGIN/../lib`. rv-ruby links it statically into its `bin/ruby` instead. The build fails if `bin/ruby` needs any other library than glibc's and that one.
- **Headers and RbConfig that move.** `include/` and the static libruby are what `mkmf` compiles and links a gem against, as in a runtime ("What a runtime keeps"), and with `--enable-load-relative` RbConfig's prefix, library, and header folders follow the folder the archive is unpacked in. Lota's C++ extension, whose CMake reads Ruby's paths, and Tokra's rb-sys read more than those: the flags and the configure arguments in `rbconfig.rb`, and Ruby's pkg-config file, which record every folder of the build. So `RubyArchive#relocate` rewrites them once Ruby is installed. libxcrypt's library folder becomes `$(libdir)`, where its library now is, and its headers' folder goes, since no installed header includes `crypt.h`; the `--with-*-dir` arguments that named the folder of the statically linked libraries go, since nothing outside the build has it and `mkmf`'s `dir_config` would read them; the prefix, left in `configure_args` and in the fallback for an `rbconfig.rb` loaded from somewhere else, becomes `/ruby/VERSION`, the folder's name in the archive; and the pkg-config file's `prefix` becomes `${pcfiledir}/../..`, the folder pkg-config found the file in. python-build-standalone leaves such paths in its builds (`/build` and `/install` on Linux) for its installer, uv, to fix up where it unpacks one (`docs/quirks.rst`, "References to Build-Time Paths", lines 148 to 192, in astral-sh/python-build-standalone's main branch on 2026-11-21); Fledge's archive has no installer of its own, since mise's http backend only unpacks it, so the archive carries the fix itself. The build fails if `rbconfig.rb`, a pkg-config file, or a header still names the build folder.
- **An embedder finds Ruby from where it sits.** A program that links the static libruby and starts Ruby as Ruby's `main.c` does (`ruby_sysinit`, `RUBY_INIT_STACK`, `ruby_init`, then `ruby_run_node(ruby_options(...))`, as Fledge's launcher does) gets its prefix from its own path, since with `--enable-load-relative` Ruby finds its load path from the file that holds its code, which `dladdr` names (`ruby.c`, from line 592, `dladdr` at line 645, at 4.1.0-preview1), and with a static libruby that file is the program. Built with the archive's pkg-config flags and `RbConfig`'s `LIBRUBYARG_STATIC`, such a program ran from the prefix's `bin/` with its load path inside the archive, and from any other folder stopped with `cannot load such file -- rbconfig`, exactly as one built against rv-ruby's archive did. So an embedder sits in the prefix's `bin/`, as Fledge's launcher sits where the runtime's Ruby expects it, or sets the load path itself. One that evaluates code after `ruby_init` alone, unprotected, turns that LoadError into a crash.
- **What differs from rv-ruby's archive.** Of rv-ruby's 3,188 files and this archive's 3,036, 2,968 are in both. rv-ruby's alone holds its own bookkeeping (`INSTALL_RECEIPT.json`, `.brew/`, an SBOM, Ruby's README, NEWS, and COPYING files), `lib/libcrypt.a` and `portable_ruby_gems.rb`, the bootsnap and msgpack gems it adds, which no standard Ruby installs, and more of Prism's files; this one alone holds `lib/libcrypt.so` and `.so.2`, and win32-registry's specification, which `make install` writes on every system.

The floors are two, and differ on purpose. An app's floor on glibc Linux is the one `Fledge::Platform::GLIBC_MINIMUM` names ("The glibc floor"), which the runtime's own programs, compiled in manylinux_2_28, keep to. The archive's floor is glibc 2.35 (`RubyArchive::GLIBC_FLOOR`), Ubuntu 22.04's, because Lota's CI installs its development Ruby there, so the archive is built in Ubuntu 22.04 and the build fails if `bin/ruby` or any extension needs a newer `GLIBC_` symbol version. A runtime built from it is held to the runtime's floor, for its own programs. python-build-standalone builds against an old glibc for the same reason, so that one build installs on as many systems as can run it. On macOS the archive's floor is the apps' floor, `Fledge::Platform::MACOS_MINIMUM`, set as `MACOSX_DEPLOYMENT_TARGET`, and it is linked with no LDFLAGS of Fledge's: Apple's clang refuses `-static-libgcc` ("unsupported option"), which Linux's builds pass, so with it Ruby's `configure` found no working compiler. A Mac has no libgcc to take statically. That stopped the first build of the Mac archive, on 2026-11-23, which then built on an Apple silicon Mac in about ten minutes, with every file within the floor and both JITs enabled. Building in Ubuntu 22.04 needs a Ruby 4.1 to run Fledge's tasks there, which rv-ruby's builds cannot be, since they need glibc 2.38; the build runs on ruby/setup-ruby's own build of the same Ruby for Ubuntu 22.04, from ruby/ruby-builder, checked by its SHA-256. jdx/ruby's, which need glibc 2.17, would serve as well, as they serve the glibc runtimes' build in manylinux_2_28.

`.github/scripts/ruby-archive.sh PLATFORM` builds the archive in Ubuntu 22.04 with every input pinned, on a computer with Docker of that platform's architecture, and refuses one of the other architecture rather than emulate it. It runs `ubuntu:22.04` by the digest of its index of images for every architecture, installs with apt each package the build needs at the version it pins, downloads the driver Ruby, ruby-builder's `ruby-4.1.0-preview1-ubuntu-22.04-x64.tar.gz` or `-arm64.tar.gz`, and checks it by the SHA-256 it pins for that architecture, unpacks it at the folder it was built for (`/opt/hostedtoolcache/Ruby/4.1.0-preview1`), and runs `ruby tasks/ruby_archive.rb PLATFORM`, whose downloads go to the computer's own download cache, each checked by its SHA-256. A contributor runs the same command. The package pins are top-level packages, as `.github/scripts/alpine-packages.sh` pins musl's: a compiler's own parts depend on its exact version, so `gcc-11` and `binutils` hold theirs, and other dependencies come at whatever version apt then picks. Ubuntu's `-updates` and `-security` pockets keep only each package's newest build, so a pin stops resolving when Ubuntu publishes a newer one, and the build fails with apt's `Version '...' was not found`. Move it on purpose, as an Alpine pin is moved; the script's header says how. Ubuntu's snapshot service, `snapshot.ubuntu.com`, would pin every package, dependencies too, to one moment, and no pin would rot. It was weighed and set aside. On 2026-11-21 it served amd64's archive over HTTPS only, and its `ubuntu-ports` path, where arm64's packages are, answered 401. An image with no CA certificates cannot reach it before apt has installed them from the live archive. Each pin resolved on both architectures on that day, in jammy's own indexes.

`.github/workflows/ruby-builds.yml` runs the script on a runner of each architecture, `ubuntu-24.04` and `ubuntu-24.04-arm`, with `docker run` as the musl runtimes are built. It keeps each archive as the run's artifact, `ruby-archive-PLATFORM`, for 14 days, and its build logs when it fails. The archive's own checks are the task's: the glibc floor, YJIT and ZJIT, the libraries `bin/ruby` links, and no build folder left in `rbconfig.rb`, the pkg-config file, or the headers. Its publish job then runs `.github/scripts/ruby-archive-publish.sh` on both archives, which must be of one version. In a dry run it prints the pre-release's name and notes. Otherwise it creates the pre-release `inputs-fledge-ruby-VERSION-YYYYMMDD-COMMIT` with `gh release create --prerelease --latest=false` on the commit that built them, then downloads each archive back and checks its SHA-256. The name says what the archives are, the day they were published, in UTC, and the commit whose recipe built them. It begins `inputs-`, as every input Fledge keeps does ("Rolling upstream inputs"), so `release.yml` does not run and the pre-release is never the latest release. One that exists is never overwritten, and the notes give each archive's SHA-256 and the run that built it. Only the publish job holds `contents: write`, with the repository's own token. `test/workflow_ruby_builds_test.rb` and `test/integration/ruby_archive_publish_test.rb` test the workflow and the publishing.

The workflow runs on each push to `trunk` that changes the recipe or its pins: the two scripts, the workflow, `tasks/ruby_archive.rb`, the runtime builder's files the task uses, and `runtime/sources.yml`. Every such run is a dry run. So a change that breaks the build, or a package pin Ubuntu has moved past, shows within the day it lands, on the commit that pushed it, and not on the day a pin should move. `runtime/sources.yml` changes most weeks, so that is also how often the package pins are tried. A schedule would add little, and would make red runs that no commit caused. The workflow publishes only when run by hand with `dry-run` turned off. A published archive is an input a pin will name, and inputs arrive on purpose (`architecture.md`, "What the design answers to"), so publishing is a choice made when a pin is to move, never a side effect of a push.

The builds live in Fledge for now, behind the seam Fledge already has for an upstream input: pre-releases of Fledge's own repository, pinned by URL and SHA-256 ("Rolling upstream inputs"). Whether they would be better as a project of their own, as RubyInstaller and rv-ruby are, was weighed against two other homes. A repository of their own now would be a new project to stand up (its rules, CI, gates, and someone to keep it), while the recipes, pins, and license audit it needs are Fledge's, the musl and phone runtimes need them in Fledge regardless, and its shape is unknown until Lota and Tokra have used it. Asking rv-ruby to build snapshots of Ruby's master may be the better home in the end, since rv-ruby is already that service and publishes previews, but whether to ask is the maintainer's. So the builds start in Fledge, behind a pin that moving elsewhere changes by one URL, and move out when something needs them on a cadence that is not Fledge's releases, or after 1.0, whichever comes first.

No runtime builds from these archives yet: every `ruby.platforms` pin of macOS and glibc Linux still names jdx/ruby's, and the move is a release's. A runtime made from one holds another Rust and another OpenSSL than one made from rv-ruby's, so `runtime/licenses.yml` keeps an entry for each build where they differ, marked `ruby_build: upstream` or `ruby_build: fledge`, and the audit takes the entries of the build the platform's pin names, `build: fledge` for these archives, `build: jdx` for jdx/ruby's, and nothing for rv-ruby's (`LicenseAudit.entries`; `doc/contributors/design/license-audit.md`, "The map: runtime/licenses.yml"). Each build is held to its own evidence, and the pin that moves moves the audit with it. The parity check moves too: its reference is the pinned Ruby's own `bin/ruby`, so a runtime made from one of these archives is compared with Fledge's own build, as on musl, and no longer with an independent one. A runtime built from this archive for x86_64-linux showed two justified differences fewer than one from rv-ruby's, `gems` and `requireable`, because the archive, like a standard Ruby, adds no bootsnap or msgpack; every other difference was the same for both.

## What a runtime keeps

Everything a standard Ruby of the pinned version installs that running Ruby code can reach:

- the standard library;
- every default gem, and every gem `runtime/sources.yml`'s `bundled_gems` lists that the Ruby installs (rv-ruby and jdx/ruby install all but win32ole and win32-registry, which only Windows builds; RubyInstaller all but syslog, which needs a Unix);
- each gem's executables, its `.gem` in the cache (`gem pristine` and `Gem::Specification#cache_file` read it), its build information, plugins, and C extensions, and the libraries those extensions carry;
- Ruby's own programs: Fledge's `bin/ruby` on macOS and Linux, and on Windows Fledge's `ruby.exe` and `rubyw.exe` and RubyInstaller's command-line wrappers for the gems (`gem.cmd`, `bundle.bat`, and the rest);
- the library `mkmf` links its checks against: on macOS and Linux the static libruby beside `lib/ruby`, and on Windows the import library of Ruby's DLL (`lib\*.dll.a`). `mkmf` links each check's program against `$(LIBRUBYARG)` (`mkmf.rb`, lines 541 to 553, at Ruby 4.1.0-preview1), which for a static Ruby names `-lruby.X.Y-static` in `$(libdir)`; without the file an app's own `have_func` raises "The compiler failed to generate an executable file". The static libruby comes without its debug information ("What a runtime prunes, and why nothing reads it"). rv-ruby's and jdx/ruby's `lib/libcrypt.a` stays out: it is libxcrypt, which is LGPL, and the linker finds the system's `-lcrypt`; so do jdx/ruby's static zlib and its pkg-config file, since every Linux provides `libz.so.1`;
- Ruby's C headers, `include/ruby-X.Y.0/`, since `require "mkmf"` aborts without `ruby/ruby.h` ("mkmf.rb can't find header files for ruby", `mkmf.rb` line 253 at Ruby 4.1.0-preview1). jdx/ruby's tree also holds, in `include/`, `crypt.h`, whose text is LGPL, and zlib's headers, which stay out;
- on macOS and Linux, the headers, static libraries, and pkg-config files of OpenSSL and libyaml, for `fledge build` alone ("What a runtime keeps for compiling gems", below);
- on Windows, every DLL, those Fledge adds among them, since an extension's manifest may name any of them, and RubyInstaller's own Ruby library in `site_ruby`.

The rule is that code that runs without Fledge runs with it, and what an app did not have to `require` before it still does not (`decisions.md`, 2026-10-26, decision 9), while a small size is not a priority (decision 20). Each thing kept answers a way a smaller runtime failed. A runtime without the bundled gems broke `require "csv"`, and one without `bin/ruby` left `RbConfig.ruby` and `Gem.ruby` naming a program that did not exist. Ruby's headers and its own library, once only in a download that builds fetched, left `require "mkmf"` aborting at run time, which some gems do for `MakeMakefile#find_executable`, and an app's own `have_func` failing (`doc/contributors/research/2026-11-10-findings-from-the-adrs.md`, "Ruby's headers in the runtime: the finding and its cost"). The costs: archives about double the size of the standard library and default gems alone (`doc/contributors/research/2026-11-10-findings-from-the-adrs.md`, "Runtime sizes"); every bundled gem's license comes into every app, each one permissive, which the license audit checks on every build; and the runtime's `bin/ruby` is Fledge's own build of Ruby's `main.c`, since rv-ruby's and jdx/ruby's link libxcrypt statically. The parity check compares the installed gems, whether each one's main file loads, and `RbConfig.ruby` on every platform, and ruby/spec runs in built apps (`doc/contributors/design/parity.md`).

## What a runtime keeps for compiling gems

A gem whose extension links OpenSSL, as Puma's does (the server Sinatra's own instructions and Rails use), or libyaml, as the psych gem does at any version but the runtime's default one, is compiled by `fledge build` against the runtime's Ruby ("Compiling a gem against a runtime", below). What it finds to link decides whether the app builds, whether it behaves as under `bundle exec`, and whether a fix to that library reaches it.

**What `bundle exec` gives such a gem.** The library its own Ruby's openssl or psych extension uses, found through how that Ruby was built. A Ruby built by ruby-build, rbenv, or Homebrew on a Mac was configured `--with-openssl-dir` at Homebrew's OpenSSL, which mkmf's `dir_config` reads back from `RbConfig::CONFIG["configure_args"]`, so the gem links the same shared library. A distribution's Ruby, or one ruby-build compiled on Linux, links the distribution's `libssl.so.3`, and so does the gem. jdx/ruby, mise's default Ruby, copies the headers, static libraries, and pkg-config files of the OpenSSL, libyaml, zlib, and libffi it builds into its own tree (`libexec/package.rb`, `copy_native_gem_dependencies`, lines 615 to 639, at jdx/ruby 09c4b6b), and its `rbconfig.rb` puts the tree's `include`, `lib`, and `lib/pkgconfig` first for every build (`rbconfig_portability_patch`, lines 539 to 613), so the gem links the tree's own OpenSSL statically, headers and library of one version, the version its openssl extension has. RubyInstaller's devkit links MSYS2's import libraries, and the gem loads the same `libssl-3-x64.dll` Ruby's architecture folder holds for its own openssl ("The DLLs a compiled gem finds on Windows"). In every case one OpenSSL version serves the process. rv-ruby offers a gem nothing of the kind: it ships `lib/libcrypt.a` "so that building native gems doesn't need system libcrypt installed" (`Abstract/rv-ruby.rb`, lines 194 and 195, at spinel-coop/rv-ruby 7f7993f) and lets its own OpenSSL build be found by pkg-config, then compiles it into `openssl.bundle` only (line 124), so a gem under rv-ruby finds whatever OpenSSL the computer has.

**The prior art.** Traveling Ruby builds OpenSSL as a shared library inside its runtime and builds the native gems it supplies against it, so a gem and Ruby's openssl share one copy (`osx/setup-runtime`, lines 412 to 440, at phusion/traveling-ruby 0eac139). python-build-standalone's install-only archives, the ones uv installs, hold Python's installation alone; its full archives keep the static libraries an extension module linked under `build/`, for relinking Python, not for compiling a third party's extension (`docs/distributions.rst`, lines 24 to 27 and 555 to 600, at astral-sh/python-build-standalone 98b27f7). Python's answer for a third party is a wheel that carries its own OpenSSL.

**What a runtime held before.** No OpenSSL of its own for a gem: the Unix recipe copied only Ruby's headers and the static libruby. So the result depended on the computer, and on which Ruby ran `fledge build`. On a Mac with Homebrew, Puma 8.1.2 linked Homebrew's `libssl.4.dylib` and was refused, with `macos: carried_libraries` the way on, naming a library whose number follows the computer. On a Mac with no OpenSSL to find, Puma built without TLS and said so only in its own build output, and the app's `Puma::HAS_SSL` was false where the developer's `bundle exec` had true. On glibc Linux, the distribution's `libssl.so.3` was refused, and `linux: system_libraries` would have let an app depend on it, which RHEL 8's computers lack. musl Linux's Ruby keeps `--with-openssl-dir` naming the folder it was built in, so Puma skipped pkg-config; on an Alpine with `openssl-dev` it linked Alpine's and was refused, and in CI's image, which has no OpenSSL headers, it built without TLS. Under a developer's mise Ruby, the leak "What the build takes from the developer's environment" (`gems.md`) closed gave the gem that Ruby's own OpenSSL.

**What was weighed, simplest first.** Saying it where a developer reads, and nothing more, would leave the silent loss of TLS, which is a difference from `bundle exec` nobody is told of (`architecture.md`, "What the design answers to"), and a fix in OpenSSL would reach such an app only when its developer's computer moved. Detecting it is not possible in general: each `extconf.rb` decides what it does without a library, and nothing it leaves says what it dropped; comparing the app's copy with the one the developer's Bundler installed would be a guess, and finds nothing for a path or git gem. One shared OpenSSL for Ruby and the gems, as Traveling Ruby and RubyInstaller have, would mean rebuilding Ruby's openssl extension in Fledge, since no upstream Unix Ruby builds OpenSSL shared. So the runtime gives a gem what its own Ruby was built with, as jdx/ruby gives one under `bundle exec`.

**What a runtime keeps.** On macOS and Linux, `RuntimeBuilder::Unix::GEM_LIBRARIES`: `include/openssl/`, `include/yaml.h`, `lib/libssl.a`, `lib/libcrypto.a`, `lib/libyaml.a`, and their pkg-config files (`openssl.pc`, `libssl.pc`, `libcrypto.pc`, `yaml-0.1.pc`), each pkg-config file naming `${pcfiledir}/../..` as its prefix so that it holds wherever the runtime is unpacked. On macOS and glibc Linux they are jdx/ruby's own, the very files its tree keeps for compiling gems, so the OpenSSL a gem links is the 3.5.5 Ruby's openssl extension has, and its default certificates are the computer's own, by jdx/ruby's edit of OpenSSL's default paths ("Certificates on macOS"). On musl Linux they are the ones `RuntimeBuilder::RubyBuild` builds from `musl-ruby`'s pins and links into Ruby's own extensions (`Musl#gem_libraries`), OpenSSL with the same certificate edit. zlib stays out, since every Linux and every Mac provides it and its fixes then come with the computer's; so does libffi, whose pkg-config file in jdx/ruby's Linux tree names jdx/ruby's build folder and has no static library beside it, and for which ffi's own `--disable-system-libffi` is the way (`doc/gems.md`), while every Mac has its own; and libxcrypt, which is LGPL. On Windows the runtime keeps nothing new: a gem links MSYS2's import libraries, and the DLLs it needs are the runtime's. Until 2026-11-22 the Mac runtime was rv-ruby's, whose tree has none of these files ("The Mac's Ruby is jdx/ruby's").

**How a gem finds them.** mkmf links every extension and every check with `-L$(libdir)` first, which is the runtime's `lib/`, so `-lssl` takes `libssl.a` there before any folder the computer adds; on macOS the linker searches each folder for a dynamic library and then a static one before the next folder (`-search_paths_first`, ld64's default). `NativeBuild::RuntimeRuby#env` then puts the runtime's `lib/pkgconfig` first in `PKG_CONFIG_PATH`, for a gem that asks pkg-config, and its `include` first in `CPATH`, which gcc and clang search before the system's folders, for a gem that looks for `openssl/ssl.h` by name; jdx/ruby's `rbconfig.rb` adds the same folders on its own. Variables were chosen over an edit of the runtime's `rbconfig.rb`, which would change the `RbConfig` an app's code sees from the one its Ruby has (`architecture.md`, "What the design answers to").

**What no app holds.** These files are for `fledge build`, and `Assembly::RuntimeFolder` leaves them out of every app: every folder and file of `include/` but Ruby's own `include/ruby-*`, every static library in `lib/` but the static libruby, and `lib/pkgconfig`. An app keeps Ruby's headers and the static libruby because an app's own `require "mkmf"` and `have_func` work under `ruby main.rb` (above); no rule asks it to carry OpenSSL's headers, which no Ruby but jdx/ruby's tree offers an app's own mkmf either. So the runtime's archive grows and no app does. The license audit owns them (`openssl-jdx`, `libyaml-jdx`, `openssl-musl`, `libyaml-musl` in `runtime/licenses.yml`), and the runtime's `NOTICES.txt` and SBOM list them under those components, as they list `RUBY_DESCRIPTION`, which no app holds either.

**What a developer sees.** Puma, and any gem whose extension links OpenSSL or libyaml, builds on a developer's computer whatever OpenSSL it has or lacks, a Mac with Homebrew's or one with none, links the runtime's statically, needs nothing of the computer an app goes to, and runs with TLS where `bundle exec` has it, with no key in `fledge.yml`; the OpenSSL is the one Ruby's own openssl extension has, so one version serves the app's process, in two copies. `test/fixtures/openssl_gem` builds a gem that finds OpenSSL as Puma does and stops when it finds none, and `test/integration/openssl_gem_test.rb` runs it: the gem's headers, its library, and Ruby's openssl must name one version.

**Security fixes.** A fix reaches such a gem when the runtime's own OpenSSL moves and the app is built again. On musl Linux that is the `musl-ruby` pins, which the watch moves with no person ("Keeping the pins current"). On macOS and glibc Linux it is jdx/ruby's release, and that pin is held: jdx/ruby rebuilds a Ruby with a newer OpenSSL under the tag `VERSION-N`, which the watch's pattern leaves out on purpose (`runtime/upstreams.yml`, `jdx-ruby`), so neither Ruby's own OpenSSL nor a gem's moves until a person moves the Ruby. That is the dependency Fledge states rather than removes ("Why Fledge builds no Ruby for macOS and glibc Linux", `decisions.md`, 2026-11-22), and what it leaves is set out there.

## What a runtime prunes, and why nothing reads it

`RuntimeBuilder::Pruning.prune` (every Unix and phone runtime, and `ruby\lib\ruby` on Windows) and `prune_windows` give each removal its reason in their comments. The Unix recipe also copies only `bin/`, `lib/ruby`, the static libruby, Ruby's own headers in `include/`, `libexec/cert.pem`, and what it keeps for compiling gems ("What a runtime keeps for compiling gems") from the pinned Ruby's prefix, so `share/` (man pages and documentation) never comes along.

| Removed | Why no app can miss it |
|---|---|
| `*.dSYM` | macOS debug symbols, read by debuggers and crash reporters, never by Ruby. |
| `*.a`, `*.h` under `lib/ruby`, `pkgconfig/` | Static libraries, the C headers of gems' extensions, and pkg-config files, for compiling against Ruby. Ruby code never loads them, and `mkmf` reads none of them. Ruby's own headers in `include/` and the static libruby beside `lib/ruby` stay. |
| `lib/ruby/gems/X.Y.0/doc` | RDoc and ri documentation, read by the `rdoc` and `ri` tools a developer runs, never by an app's requires. |
| nkf's `ext/java/` | See "nkf's JRuby sources". |
| `portable_ruby_gems.rb`, and every gem that is neither a default gem nor in `bundled_gems` | rv-ruby's own additions, a load-path helper and the bootsnap and msgpack gems. No standard Ruby installs them, so an app that worked under `ruby` never needed them. Each goes with its specification, cache, build information, extensions, and executables. |
| Windows: `share\` | Ruby's HTML documentation and ri data. |
| Windows: `lib\*.a`, `lib\pkgconfig` | Static libraries and pkg-config files, for compiling against Ruby. The import library of Ruby's DLL (`lib\*.dll.a`) stays, for `mkmf`. |
| Windows: `packages\`, `ridk_use\`, `bin\ridk.cmd`, `bin\ridk.ps1`, `bin\setrbvars.cmd`, `bin\startmenu.rb` | The MSYS2 keyring and `ridk`, which install and select MSYS2 compilers for a developer, and the scripts that set up a developer's shell and Start menu. They work only beside an installed RubyInstaller and MSYS2. |

Debug information goes too, since no running code reads it and no link does. Extensions are stripped of debug sections on Linux, the programs Fledge links are stripped, and the static libruby is stripped with `strip -S`, which GNU's strip and Apple's both take for debug information only (`RuntimeBuilder::Unix#copy_static_libruby`). That keeps each object's code, data, symbols, and relocations, everything a link reads, and the archive's index. On Linux, where Ruby's C is compiled with DWARF, debug information is most of the file: v0.14.0's x86_64-linux runtime held a static libruby of 90,093,822 bytes, 19,478,606 without it, and its x86_64-linux-musl runtime one of 164,970,554, 20,119,082 without it, which takes that runtime's archive from 75 MB to 35 MB. On macOS rv-ruby's C carried no DWARF, and what went, 13,316,232 bytes to 11,458,672, was the debug map of the Rust in YJIT and ZJIT, which names object files on rv-ruby's build machine, so the linker of every mkmf check warned "unable to open object file" for each. Windows' import library holds no debug information, and `strip --strip-debug` leaves its 2,786,214 bytes as they were. `have_func`, `have_library`, and `try_link` succeed against the stripped archive as against the original, with no new warning, and fail without it; the license audit's evidence of the Rust standard library, its `/rustc/` path, is in the code's own strings and stays.

Nobody loses anything by it. The launcher and `bin/ruby`, the programs a debugger or a crash report meets, link the pinned Ruby's own copy of the archive and are stripped themselves, and the program a check links is deleted once it has linked (`mkmf.rb`, `try_link`, lines 642 to 646, at Ruby 4.1.0-preview1). Only a developer who linked a program of their own against the runtime's libruby and debugged it at the source level would miss the line tables, and the pinned Ruby's own release has them. python-build-standalone does the same: its `install_only_stripped` archives run `llvm-strip --strip-debug` over every compiled file, and are "equivalent to install only, but without debug symbols, which results in a smaller download and on-disk footprint" (`src/release.rs`, `convert_to_stripped` and `llvm_strip`, at astral-sh/python-build-standalone 98b27f7; its "Distribution Archives" documentation). Its `install_only` archives leave libpython's static library out altogether, as what "isn't needed in most cases" (`convert_to_install_only`, the same file). A runtime keeps it, since without it an app's own mkmf fails where `ruby` succeeds. rv-ruby ships the archive as `make install` leaves it: `Abstract/rv-ruby.rb` strips nothing (spinel-coop/rv-ruby at fadbfcf).

The parity check lists bootsnap and msgpack, which are pruned, among the differences it allows (`Parity::JUSTIFIED` in `tasks/parity.rb`).

## nkf's JRuby sources

`RuntimeBuilder::Pruning.prune_jruby` removes nkf's `ext/java`, the Java sources of JRuby's nkf, from the gem's folder and from its `.gem` in the cache (`Pruning::JRUBY_ONLY`). CRuby never compiles or loads them: `nkf.gemspec` adds them only to the java-platform gem, and `ext/nkf` is CRuby's. So no running Ruby code reads them. They are EPL-2.0 OR LGPL-2.1-or-later, the only copyleft text a runtime would otherwise carry that is not license data.

`RuntimeBuilder::GemRepack.repack` rewrites the cached `.gem` in RubyGems' own format, with the specification's file list and `checksums.yaml` changed to match, so `Gem::Package#verify` and `gem pristine nkf` accept it. The cached nkf `.gem` therefore differs from RubyGems.org's by those files.

## Fledge's RubyGems defaults

Every runtime ships `runtime/rubygems/operating_system.rb` as `lib/ruby/X.Y.0/rubygems/defaults/operating_system.rb` (`RuntimeBuilder#install_rubygems_defaults`), the hook RubyGems loads for whoever packages Ruby (`rubygems.rb`, line 1465, at Ruby 4.1.0-preview1). rv-ruby ships none; on Windows it replaces RubyInstaller's. The file's own comments give the reasons. It does two things:

- **The app's gems are the runtime's alone.** `Gem.default_path` is `[Gem.default_dir]`. Left alone, it puts `Gem.user_dir` first whenever the person's home folder exists, so a gem the person installed with their own Ruby of the same minor would shadow the app's, json included.
- **A bundled gem the Gemfile does not name activates under a frozen bundle.** While `Gem::BUNDLED_GEMS.force_activate` runs (for `binding.irb`, say), and only on its thread, Bundler is told its bundle is not frozen; the temporary bundle is still never locked. The reason, and the frozen `.bundle/config`, are `doc/contributors/design/gems.md`, "binding.irb and force_activate".

RubyInstaller's own `operating_system.rb` is for a developer's Ruby: it writes and deletes a file in the runtime's gem folder on every start, creates `%ProgramData%\gemrc`, searches for MSYS2 and adds its DLL folder, and leaves `Gem.user_dir` first in `Gem.path`. A runtime needs none of it but the archdir's place in the DLL search: RubyInstaller's own extensions load their DLLs through their manifests, and compiling a gem enables MSYS2 through RubyInstaller's Ruby library, which the runtime keeps (`doc/contributors/design/gems.md`). Fledge's file on Windows loads what RubyInstaller's start-up loads, and of what it calls does only one thing: it adds Ruby's architecture folder to the DLL search, as RubyInstaller's `enable_dll_search_paths` does, and not `RUBY_DLL_PATH` or MSYS2 ("The DLLs a compiled gem finds on Windows"). It requires `ruby_installer/runtime`, so `RubyInstaller` is defined, as under `ruby.exe`, and a gem that tests `defined?(RubyInstaller)`, such as mysql2, takes the branch it takes there. Then it loads the autoloads RubyInstaller's `enable_dll_search_paths` loads, `Msys2Installation` (which includes `Colors`) and `DllDirectory` (which requires `win32/dll_directory` and so defines `Win32`), whose files only define classes and modules when loaded, and calls that call's first `DllDirectory.new`, of Ruby's archdir, which converts the path to UTF-16LE for `AddDllDirectory` and so loads that encoding and its converters. So the app starts with the same `$LOADED_FEATURES` and constants as `ruby.exe`.

On macOS and Linux, whose Rubies ship no such file, the parity check allows the defaults' trace in `$LOADED_FEATURES` (`Parity::JUSTIFIED`).

## The Ruby's description

Every runtime, a phone's too, holds `RUBY_DESCRIPTION` at its top: one line, the `RUBY_DESCRIPTION` of the Ruby it carries as far as the platform's name, `ruby 4.1.0preview1 (2026-10-11 master 2d08b5f42f)` for the preview and `ruby 4.1.0dev (2026-11-10 master 0e25874222)` for Windows' head build. `fledge build` reads the Ruby's version from it as RubyGems reports it (`doc/contributors/design/gems.md`, "The runtime's Ruby version"); no app holds it (`Assembly::RuntimeFolder`).

Ruby records the name of a preview or a development build only in that string. `version.h` defines `RUBY_PATCHLEVEL_STR` as `"dev"`, or as the name a release tarball's `tool/make-snapshot` writes into it (`preview1`), and `version.c` compiles `"ruby "`, `RUBY_VERSION`, `RUBY_PATCHLEVEL_STR`, the date and revision, and the platform into `ruby_description` (`version.h`, lines 57 to 66, and `version.c`, lines 88 to 91, at 2d08b5f42f; `tool/make-snapshot`, lines 272 to 279 and 362). `rbconfig.rb` keeps only `PATCHLEVEL` of `-1`, and Ruby's installed headers no name. So `RuntimeBuilder::RubyDescription` reads the string out of the program or library it was compiled into, in each layout: `bin/ruby` on macOS and Linux, Ruby's DLL in `ruby/bin/` on Windows, each slice's `libfledgeruby.a` on iOS, and each ABI's `libfledgeruby.so` in the AAR on Android, which it reads with `unzip`, as the license audit does. Every one in a runtime must give the same description, less the platform, which differs between slices and ABIs, and a runtime with none or two is not built.

`fledge build` could read the string out of the same files itself, and did not, because Android's library is deflated inside the AAR, a zip, and a computer that builds an Android project may have no tool that reads one: GNU tar, Linux's, reads no zip, and Fledge would have had to read one itself, which "code is a liability" (decisions, 2026-10-28) rules out where a tool does it. The file costs one more entry in each runtime, which the license audit counts as Ruby's, since its words are Ruby's (`runtime/licenses.yml`), and which the runtime's SBOM lists under Ruby's package. Counted as Fledge's, it would head the list of Fledge's own files in every app's `NOTICES.txt`, as the program the app's user runs, and in `doc/licensing.md`'s sentence on them, though no app holds it: both name the files of Fledge's component in the order they sort, the launcher first. A runtime of Fledge 0.13.0 or before has no such file, and `fledge build` then reads its Ruby as rbconfig's `MAJOR.MINOR.TEENY` alone, as it did; the reading of that case can go once `lib/fledge/SHA256SUMS` pins runtimes that hold it.

## Platform names and asset names

A platform is named by its RubyGems platform: `arm64-darwin`, `x86_64-linux`, `aarch64-linux`, `x86_64-linux-musl`, `aarch64-linux-musl`, `x64-mingw-ucrt`, and `aarch64-mingw-ucrt`. A Ruby developer already meets these names in `Gemfile.lock` and in precompiled gems, and they decide which precompiled gem fits a runtime, so Fledge prints no other name for a platform: not in a runtime's asset, `fledge build`'s output, `dist/NAME-PLATFORM`, an error message, a CI job, or the license map. `Fledge::Platform::NAMES` lists them, `Fledge::Platform.local` maps `Gem::Platform.local` to one, and `test/platform_test.rb` checks the mapping. A build's target is the platform Fledge runs on (decisions, 2026-10-28). A phone's targets follow RubyGems' grammar but are chosen so that no desktop gem fits them (`doc/contributors/design/phone-runtimes.md`, "Targets").

RubyGems' names are irregular: `arm64` on macOS against `aarch64` on Linux and Windows, `x64` on Windows against `x86_64` elsewhere. A Mach-O gem may also be named for a macOS version (`arm64-darwin-23`), which fits a runtime only as RubyGems decides, so `fledge build` matches as RubyGems does, not by string. Other ecosystems name platforms differently (LLVM target triples such as `aarch64-apple-darwin`, Go's `darwin/arm64`, Python's wheel tags such as `manylinux_2_39_x86_64`, Electron's `--platform darwin --arch arm64`). Each is more regular, and none tells a Ruby developer which precompiled gem fits.

The assets:

|---|---|---|

| Its NOTICES | `fledge-runtime-VERSION-PLATFORM-NOTICES.txt` | every one |

## Where fledge build finds a runtime

`Fledge::Runtimes` (`lib/fledge/runtimes.rb`) looks for a runtime in this order:

1. the folder `FLEDGE_RUNTIME_DIR` names: a developer's copy of the release, for a build with no network, or a contributor's `tmp/runtime` after `rake runtime`. A runtime there is checked against its pin, when the gem has one (below); when the variable is set and the file is missing, the build fails rather than download;
2. the cache, `$XDG_CACHE_HOME/fledge/runtimes` or `~/.cache/fledge/runtimes`, when its SHA-256 matches the gem's pin;
3. a download from the version's GitHub Release, or from `FLEDGE_RUNTIME_MIRROR`, into the cache, checked against the pin.

A runtime in `FLEDGE_RUNTIME_DIR` that matches its pin is used without a word. One that does not match fails the build, naming the folder, the file, both SHA-256s, and the two ways on: copy the file again from the release, or, for a runtime you built, set `FLEDGE_RUNTIME_DIR_UNCHECKED=1`. With that set, the build uses it and says on standard error that it is unchecked, once per runtime. A runtime the gem pins nothing for, as at a release commit, whose version no pin names until its pin commit, is used, and the build says the same. The variable is read as Bundler reads a switch from the environment: empty, `0`, `f`, `false`, `n`, and `no` are off, in any case, and anything else is on (`Bundler::Settings#to_bool`, `lib/bundler/settings.rb` at bundler 4.0.20). The switch, and an error that names it, follow Bundler's `BUNDLE_DISABLE_CHECKSUM_VALIDATION`, which lets a gem that does not match its checksum install and which Bundler's mismatch error names (`lib/bundler/errors.rb` and `man/bundle-config.1.ronn` at bundler 4.0.20).

The switch exists because the names collide. A runtime's file name carries only Fledge's version, and between releases `trunk` keeps the last release's version and its pins, so `rake runtime` on any ordinary commit writes a file of the very name a pin holds, with other bytes: a check without the switch would fail every build Fledge's CI makes from the runtimes it just built. So every place in this repository that builds apps from its own runtimes says so: each step of `ci.yml`, `ruby-spec.yml`, and `ruby-master.yml` that sets `FLEDGE_RUNTIME_DIR` sets the switch beside it, and passes both into its container; `tasks/parity.rb` and `tasks/mobile_parity.rb` set it for the builds they run; `.github/scripts/check-msix.ps1` sets it with the folder; and `test/test_helper.rb` sets it for the integration tests, while the unit tests pin their fake runtimes themselves (`FakeRuntime.pins`), so they pass whatever the commit's own pins name. Two other designs were weighed. A file that `rake runtime` writes beside its archive to mark it as built here would need no switch, but CI moves runtimes between jobs as artifacts that must be exactly the release's assets (`RuntimeBuilder.release_assets`, checked by the pin and by `release.yml`), so the mark would not travel, and anyone can copy a mark. A second variable for a contributor's builds, leaving `FLEDGE_RUNTIME_DIR` for copies of the release, would draw the line as clearly, but would rename a variable that `doc/runtimes.md` promises 1.x keeps, and that a framework filling the folder with its own builds may already set. Checking only when the folder also holds the release's `SHA256SUMS` would need neither, but would leave unchecked the developer who copies only the archives, as `doc/runtimes.md` tells them to.

A mirror replaces the release's host outright, at the same path below it, `MIRROR/vVERSION/NAME`, which `gh release download vVERSION` fills, so one mirror holds every version a team uses. A mirror that serves other bytes, lacks a file, or cannot be reached fails the build, naming the variable, the mirror, and the file, and the release is never asked. A developer sets a mirror because the release's host is blocked, forbidden, or gone, so a fallback would reach a host they chose not to reach, or hang on one that cannot be reached, and would hide a mirror that lacks a version until the day that host is gone. uv's `UV_PYTHON_INSTALL_MIRROR` is used "exclusively, no automatic fallback" (`crates/uv-python-managed/src/downloads.rs` at astral-sh/uv 4470c33b), and rustup's `RUSTUP_DIST_SERVER` replaces its default the same way; pyenv's `PYTHON_BUILD_MIRROR_URL` falls back, but it is a cache keyed by checksum in front of each package's own URL. The pins make either safe for the bytes, so the choice is only where `fledge build` connects. Fledge has one default host, and a second is the maintainer's to name (decisions.md, 2026-11-04).

## Download retries

`fledge build` downloads runtimes and gems through `Fledge::Download.save`. A download that fails with `Download::Unavailable` (408, 429, or a 5xx) or `Download::Unreachable` (a connection refused, reset, timed out, unresolvable, broken off, or stalled) is tried again after 2, 4, and 8 seconds (`Download::WAITS`), four tries in all, and the last failure is raised when they run out. Each try starts again from the first byte into the same `.part` file and is checked against the pin; nothing reaches the destination unless it matches. A 401 or 403, a 404 or 410, any other 4xx, and a SHA-256 mismatch would answer the same a moment later, so each fails at once. Before each wait, `Fledge::Runtimes` and `Fledge::GemFetcher` say on their log why and how long: `could not download URL: 503 Service Unavailable; trying again in 2 seconds (2 of 4)`.

A mirror is retried the same way and then fails, still without trying the release.

Why these numbers:

- **Four tries** is Bundler's default: `download_gem` runs inside `Bundler::Retry` (`lib/bundler/rubygems_integration.rb`, line 384, at bundler 4.0.20), and `BUNDLE_RETRY` is 3 (`settings.rb`, line 84). Bundler's index requests likewise pass over a refused login, a 404, and other 4xx (`fetcher.rb`, lines 99 to 125).
- **The waits double**, as Bundler's do (`retry.rb`, lines 22 to 31 and 67 to 76), from 2 seconds rather than Bundler's 1, because a release host's outage outlasts a second more often than a gem index's hiccup. They stop at 8, so a host that is truly down fails the build in about 14 seconds.
- **No jitter**: one build's downloads run one after another and are no herd, and a fixed wait is what the log can promise.
- **No setting.** Reading `BUNDLE_RETRY` would tie runtime downloads, which are not Bundler's, to a Bundler setting, and a variable of Fledge's own would be one more name to freeze for a need no one has shown.

`Fledge::Download` starts Net::HTTP with `ignore_eof: false`. By default Net::HTTP reads a body that ends before its `Content-Length` as the whole body (`net/http.rb`, lines 1473 to 1476, net-http 0.10.0 in Ruby 4.1.0-preview1), so a connection that broke off mid-download would be a SHA-256 mismatch, which is never retried. With `ignore_eof: false` it raises `EOFError`, which is `Unreachable`. Net::HTTP's own retry of a GET does not "restart in the middle of a download" (line 2519), so it does not cover this.

A try that keeps sending, but slowly, would never end on Net::HTTP's timeouts, which only bound a single read. So each try keeps a pace (`Download::PACE`): fewer than 10 kB a second, on average, over 30 seconds raises `Download::Stalled`, an `Unreachable`, and the try starts again on a new connection, which usually reaches a faster server. The 30 seconds is also the read timeout, so a server that stops altogether is caught as soon. This is curl's `--speed-limit` and `--speed-time` (curl's window is 30 seconds once asked for a floor) and Cargo's `http.low-speed-limit` (10 bytes a second over `http.timeout`, 30 seconds, after which Cargo "will abort and retry"); the floor is higher than Cargo's because Fledge's files are tens to hundreds of megabytes, where 10 kB a second already means hours. A try still going after 15 seconds says on the log how far it got, every 15 seconds: `NAME: 12.3 MB of 104.9 MB (11%), 0.8 MB/s`.

`Download.save` takes an flock on an empty `NAME.lock` beside its destination before it downloads, and looks again, under the lock, for a file with the pinned SHA-256, as Cargo locks its package cache. So builds that share a cache take turns: the first downloads the file, and each later one says `waiting for another download of NAME to finish` and then finds it there. Without the lock, two `fledge build`s at once streamed into the same `.part` file. The lock files stay: removing one while another process waits on it would let a third take a second lock.

The build tasks' download cache (`tasks/download_cache.rb`) keeps each file in `DownloadCache.folder`, `$XDG_CACHE_HOME/fledge/downloads` or `~/.cache/fledge/downloads`, beside `fledge build`'s own runtimes and gems, in a folder named for its SHA-256 (`downloads/SHA256/NAME`). So every build on a computer shares one copy of each input, and two pins of one name, such as two nights' `rubyinstaller-head-x64.7z`, never replace a file another build is reading. CI keeps that folder between runs ("Pinned downloads in CI", below). It writes each line to standard output and flushes it, since through a pipe Ruby holds standard output back until its buffer fills, and a build killed for its time would lose its last lines. It tries five times, after 5, 10, 20, and 40 seconds, on the same two errors, since a hosted runner can wait longer than a developer at a terminal. It passes `waits: []` to `Download.save`, so its tries replace the product's rather than multiply them.

## Pinned downloads in CI

Each CI job that downloads pinned inputs into the download cache keeps the folder in GitHub's Actions cache, so that its verdict does not hang on a download server answering that runner that day: the runtime jobs, the licenses of the whole upstream tree, the iOS apps, and ruby/spec's jobs. GitHub keeps 10 GB of caches for a repository, removes an entry no run has used for seven days, and past 10 GB evicts the least recently used ("Usage limits and eviction policy", docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching).

These sets were keyed by the SHA-256 of `runtime/sources.yml` (and of `tasks/ruby_spec.rb`, for ruby/spec's), so every change to any pin gave every platform's set a new key, and each job then downloaded all its inputs again, the NDK's gigabyte among them. Between 5 and 19 November 2026 `runtime/sources.yml` changed 16 times and `tasks/ruby_spec.rb` 33, and each change of the first wrote 2.8 GB of new entries, while the old ones stayed until they were evicted. On 20 November the repository's cache held 10.5 GB, 4.4 GB of it in entries no key would match again, and the oldest entry had last been used 21 hours before. The musl jobs kept nothing at all: they download in Alpine's container, under the container's home, and the cache step found no folder to save ("Path Validation Error", job 136031900228), so each one downloaded Ruby's source, OpenSSL, and the rest on every run.

A file in the folder is named for its SHA-256, and `DownloadCache#fetch` takes it only when its bytes have that SHA-256, downloading otherwise. So any earlier set is safe to start from: it cannot hand a build a file other than the pin's. Each job restores the newest set saved under its own prefix, such as `runtime-downloads-x86_64-linux-files-`, which the cache matches by prefix ("Cache key matching", the same page; the `-files-` keeps `x86_64-linux`'s prefix from matching `x86_64-linux-musl`'s sets), and its build downloads only the pins that set lacks. After its last download the job runs `.github/scripts/download_cache_key.rb`, which removes each folder whose SHA-256 no pin in `runtime/sources.yml` or `tasks/ruby_spec.rb` names (`DownloadCache#prune`), so a set does not grow with every pin that ever changed, and writes the SHA-256 of the sorted list of the files left, each as `SHA256/NAME` (`DownloadCache#digest`). The job saves the folder under the prefix and that digest, unless that is the key it restored. The key is everything the entry holds: a file's bytes are its SHA-256's, and the list names every file. So a change to a pin makes a new entry only for the platforms that download it, and a commit that changes no download a platform takes saves nothing for it. The musl jobs mount the runner's folder as the container's own, and key it in the container, whose Ruby the script runs on. The script runs only in a GitHub Actions job, so it never prunes a developer's own cache, which the builds of other commits share.

This costs one full download of every set, the first run after the change, since no old key has the new prefix, and the old entries then go unused and are removed after seven days, or sooner by eviction. A file a build fetches under a SHA-256 that neither pin file names is pruned, and downloaded again the next run; no such pin exists today. `actions/cache`'s single step was not kept, since its post step saves under the key it was given, and a key made of the folder's contents is not known until the job has downloaded. Keying each file by its own SHA-256, one entry for each, would share an input such as llvm-mingw between the jobs that each keep a copy of it, but would need a cache step for each pin, which a workflow cannot generate from `runtime/sources.yml`.

## Caches only trunk saves

A run restores only what its own branch or the default branch saved (GitHub's dependency caching reference, "Restrictions for accessing a cache"), and every branch's entries count against the repository's 10 GB. `trunk` is the only ref whose entries a later run of Fledge's CI is sure to read: the proof of a pin move runs on `pin-move`, which `pin-watch.yml` deletes after each proof, and a release's runs are on `release-next`, and `trunk` reads neither. On 24 November 2026 the repository held 65 entries, 11.2 GB by the sizes the API lists (`actions/caches`, one listing): 5.0 GB saved on `trunk` and 6.2 GB on `pin-move`, among them the Android runtime's downloads (966 MB, twice), four Gradle sets of about 213 MB, and the Windows mise installs (1.2 GB), while `trunk` held no Gradle set and no Android runtime downloads at all (issue 90). Only a later run on the same branch could have used them, and the one such run is Alone proving a pin after Move's proof was red: its keys name the files and pins it proves, so it reuses what Move saved only through a prefix (the downloads' and the Gradle sets'), and a retry that Gradle's own patience already covers does not outweigh 6 GB that push `trunk`'s entries out.

So every step of `ci.yml`, `ruby-spec.yml`, and `runtime-proof.yml` that saves a cache (the downloads, the Gradle sets, a partial one too) runs only when `github.ref == 'refs/heads/trunk'`, and every `jdx/mise-action` sets `cache_save` the same way (the input's description: "if false, action will not write to cache", action.yml at 82a612c5). A run on another ref still restores what `trunk` saved. The installed gems and the examples' bundle are kept by `actions/cache`'s single step, whose post step cannot be conditioned. They save only when the exact key is missing, their keys name the lockfile, the Ruby, and the image, which a pin move or a release leaves as `trunk` has them, and each is 27 to 39 MB, so they are left as they are. `test/workflow_caches_test.rb` fails when a step that saves lacks the condition.

## Pins that name mirrors

A pin in `runtime/sources.yml` may list `mirrors` after its `url`. `DownloadCache#fetch` tries the url, then each mirror in order, and checks every download against the pin's one `sha256`, so a mirror serves the pinned bytes or is refused and the next one tried. When none serves the file, the error names every URL and why it failed. The file keeps the url's name in the cache, in the folder of its SHA-256, whichever URL served it.

One SHA-256 per pin, not one per mirror, keeps the component the same whichever host answered: the license audit and the source bundles read only that a source pin exists.

Only `.github/scripts/fetch_pin.rb` passes mirrors, and only the `replaceability` pins, which it alone reads, name them. `test/runtime_builder_test.rb` fails if any other pin names one, since the runtime builder would never try them, or if a mirror is not HTTPS. Each mirror is downloaded and matched against the pin before it is added.

## Keeping RubyInstaller's head build

RubyInstaller publishes Ruby 4.1 for Windows only as its rolling `rubyinstaller-head` release, and replaces its files every night. Its CI keeps each night's build as an artifact for about 90 days, but without a signature; only the release's `.asc` files let a build be checked against RubyInstaller's key. Fledge moves every platform to each Ruby 4.1 release together (preview2, any later preview, each RC, and 4.1.0), so the Windows runtimes need the head build of each release's day, and that build is gone the next night.

`.github/workflows/keep-rubyinstaller-head.yml` keeps it. Every three hours, at 17 minutes past, it runs `.github/scripts/keep-rubyinstaller-head.sh`, which:

1. asks `cache.ruby-lang.org` for `ruby-VERSION.tar.gz` of each version watched, and takes the newest that is there. Only the newest release's day can still be kept, so an older one that was missed is never kept with a later build. A host that answers anything but found or not found fails the run, so that a release it hid is not passed over;
2. stops when this repository has a pre-release named `inputs-rubyinstaller-head-YYYYMMDD-for-VERSION` for that version. The pre-releases are the only state;
3. reads the times RubyInstaller's API gives its four head files, `rubyinstaller-head-x64.7z`, `rubyinstaller-head-arm.7z`, and their `.asc` signatures, and fails when any is older than the release's tarball (its `Last-Modified`): that build is the night before's, and the next run tries again;
4. downloads the key `runtime/sources.yml` pins for both Windows platforms, checks it against its SHA-256, downloads the four files, and checks both archives with `gpgv` against that key, by fingerprint, as `rake runtime` does ("The RubyInstaller signing key", above);
5. asks RubyInstaller's API again, and fails if the files changed while they downloaded;
6. publishes the four files unchanged on the pre-release, with `gh release create --prerelease --latest=false` on the commit the workflow runs on, and reads each one back from the release and checks its SHA-256.

YYYYMMDD is the day RubyInstaller built the x64 archive, in UTC. The notes give each file's SHA-256 and the time RubyInstaller reports for it, the key's fingerprint and URL, the time the release appeared, and each build's Ruby, read from the `RUBY_DESCRIPTION` in its DLL without running it (`ruby 4.1.0dev (2026-11-12 master 0738c9dfaa) [x64-mingw-ucrt]`, say).

Nothing is overwritten or deleted. A failed download, a bad signature, or a stale build publishes nothing and fails the run, so a failure shows on the Actions page. Only the job's `contents: write` lets it publish, with the repository's own token. Run it by hand with `workflow_dispatch` to try it: `dry-run`, on by default, does everything up to publishing and prints the notes instead. `versions` names the versions to watch; `4.1.0-preview1` shows the whole path, since it exists. The script runs on any computer the same way, with `DRY_RUN=1` and `KEEP_VERSIONS`; its header lists the rest of its environment. `test/integration/keep_rubyinstaller_head_test.rb` runs it against a loopback server standing in for both hosts, and a signing key of its own.

To verify a kept build, download its files and the key, and check them as the workflow did:

## Testing against Ruby's master

A release pins one Ruby, and until the next one is released nothing a runtime builds meets a change in Ruby's master. The phone runtimes edit Ruby's source (ADR 099), the musl runtimes build Ruby from source, the launcher follows Ruby's `main.c`, and the parity and ruby/spec checks compare against Ruby itself: each can break on a commit to Ruby's master, and without a run against it the first day they would meet that commit is the day of the release, and Fledge is to be tested against a recent Ruby on every platform (decisions.md, 2026-11-21). `.github/workflows/ruby-master.yml` runs every night, at 20:43 UTC, and by hand (`gh workflow run ruby-master.yml`). It changes no pin on trunk, and no release carries what it builds.

### Where a recent Ruby comes from

| Source | What it publishes | What a runtime can take from it |
|---|---|---|
| `cache.ruby-lang.org/pub/ruby/snapshot/` | `snapshot-master.tar.gz` (and `.xz`, `.zip`) each day, made by Ruby's own release tool, `tool/make-snapshot`, with `snapshot-master.json` beside it giving the date and each file's SHA-256. Only the newest is kept. The tarball is in a release tarball's shape: a generated `configure`, `revision.h`, and every bundled gem's `.gem` in `gems/`. On 2026-11-21 it was master 21ee43fb1e of 2026-11-20, written at 18:35 UTC. | The source tarball the musl and phone recipes build from, in place of a release's. |
| ruby/ruby-dev-builder | A build of master for each runner image every day, about 19:30 UTC, which ruby/setup-ruby installs as `head`. Built for a fixed prefix, for that image's libraries. | Nothing: a runtime needs a static libruby and a tree that can move. |
| RubyInstaller's `rubyinstaller-head` | The Windows build of master, each night, signed (`Keeping RubyInstaller's head build`). | The Windows runtimes' Ruby, as today. |
| rv-ruby, jdx/ruby | Numbered versions and previews only. | Nothing between releases. |
| mise's `ruby@ruby-dev` and `4.1-dev` | Not builds: ruby-build's definitions that clone master from GitHub and compile it on the computer, against its libraries. | Nothing: not relocatable and not pinnable. A contributor may use one as a development Ruby. It needs a Ruby on `PATH` to compile with: without one, Ruby's `configure` writes `BASERUBY = ./tool/missing-baseruby.bat` and `make` stops at once with "executable host ruby is required. use --with-baseruby option", which is how `mise install ruby@4.1-dev` fails in half a minute on a computer with no Ruby. Under `mise x -- env MISE_RUBY_COMPILE=true mise install ruby@4.1-dev` in this checkout, where `mise.toml`'s Ruby is the baseruby, it compiled master of 2026-11-21 in 135 seconds on a 24-thread Ubuntu 26.04 computer. |

So the run takes the snapshot. `tasks/ruby_snapshot.rb` reads the index, downloads the tarball through the download cache, checked against the index's SHA-256, reads the revision from its `revision.h`, and rewrites, in the run's checkout only, the url and sha256 of `mobile.ruby`, `musl-ruby.ruby`, and `ruby-build.ruby` in `runtime/sources.yml`, and the evidence of Ruby's revision that the license audit looks for in the from-source Rubies' component of `runtime/licenses.yml` (`2d08b5f42f` for 4.1.0-preview1). Every other pin stays, and so does every other check. The first job does it once and hands the two files and the tarball to every other job as the run's `ruby-master` artifact, kept 30 days, so all of them build one Ruby commit, even if the snapshot changes while the run goes, and a red night can be built again from the very bytes it tested: put the artifact's two files in `runtime/` and its tarball in the download cache under its SHA-256's folder (`DownloadCache#fetch`), or make the same tarball from a clone of ruby/ruby at the revision with `tool/make-snapshot`.

macOS and glibc Linux are not in the run: their Ruby is jdx/ruby's, which builds no snapshot, and a runtime built for them from master would take Fledge's own archive of it ("Fledge's own Ruby builds"), which the run does not build yet. Windows is not in it yet either, though RubyInstaller's head build fits: the Windows runtimes would take that night's build, checked against RubyInstaller's key as `rake runtime` checks the pinned one, and its revision is not the snapshot's, since RubyInstaller builds at another hour.

### What runs against it

Each runtime Fledge builds Ruby for: `x86_64-linux-musl` and `aarch64-linux-musl` in the pinned Alpine Ruby image, as ci.yml's `runtime-musl` builds them, and `ios` and `android` as its `runtime-mobile` does. A build runs the scripted edits, the bundled gems' extensions, the builtin binary, every check of the recipe, and the license audit, which fails on any file nothing accounts for. Trunk's downloads for each platform are restored and never saved: the snapshot is a new file every night, so a set saved with it would be a new entry of the whole set, a gigabyte and more for Android, every night ("Pinned downloads in CI").

What Ruby's master changes on purpose is not a failure, and the run tells it apart without loosening a check the releases rely on:

- **Its revision**, which the audit's evidence names: the run rewrites it, so the audit checks that the snapshot's revision is the one compiled in, as it checks the pin's.
- **Its ABI folder** (`4.1.0+6` on master, `4.1.0+5` on preview1) and its `RUBY_DESCRIPTION` (`ruby 4.1.0dev (2026-11-20 master 21ee43fb1e)`): nothing in Fledge keeps either name, and each build reads both from the tree it built ("The Ruby's description").
- **Fixes the edits take from master** (`process_c`, `thread_c`): master already has them, and each edit leaves a Ruby that has its fix as it is, and still fails on one that has neither its old lines nor the fix (`doc/contributors/design/phone-runtimes.md`, "Scripted edits to Ruby's source").
- **Bundled gems' versions**: the recipes take whatever `gems/` holds. A gem added or removed would show as a gem the runtime lacks or does not know, which is a real difference from 4.1.0-preview1 for the release that moves to it, and the run reports it.

What runs: the four builds, and on each musl runtime that built, the parity check, as ci.yml's `parity-musl` runs it, whose reference there is the runtime's own `bin/ruby`, so master's ("musl Linux's Ruby, built in Alpine"). On master 21ee43fb1e every scripted edit applied, the Android runtime built and passed the audit, 2,900 files in 91 components, in under five minutes on a warm computer, and the x86_64-linux-musl runtime, 3,003 files in 102 components, in under four, describing itself as `ruby 4.1.0dev (2026-11-20 master 21ee43fb1e)`, with its library in `4.1.0+6`. A check that could not run because its build failed counts as failed too. The unit and integration tests, ruby/spec, and the phone apps in the Simulator and on emulators are next, each taking the runtime its build made, as ci.yml's jobs do; until they run, a green night says that Fledge can build from master, not that apps behave on it.

### Who hears about a red night

The run reports to one issue, titled "Ruby's master: nightly status", which it opens the first night. Its body says the newest master Fledge passed on, with the run, and what has failed since: the jobs, the first night they failed, and the link that compares the last passing revision with the first failing one on GitHub, the range of Ruby's commits to read (`tasks/ruby_master_status.rb`). An agent that starts a session reads it with `gh issue list --search "in:title \"Ruby's master: nightly status\""`, then `gh issue view NUMBER`.

Each build records its result instead of failing its job (`continue-on-error` on that one step, and `.github/scripts/ruby-master-result.sh`), and the report job fails the run only on a night that is news: a job fails that had not been failing. A job that recorded nothing, as a cancelled one, counts as failed. So a week of master broken upstream sends one failure email, the first night's, and the issue shows the rest; editing an issue's body notifies no one. The two plain choices were worse: a job allowed to fail is green while it is broken and tells no one, and a run that is red every night is the noise the decision of 2026-11-22 rules out. The cost is that a second break in a job already failing is not news; the issue's list of jobs and its range of commits are what tell them apart.
