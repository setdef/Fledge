# ADR 103: On a phone, an app's Ruby drives the platform's own widgets from the main thread, through a bridge over Fiddle

## Context and Problem Statement

A Ruby developer who knows no other language should ship a phone app whose screen is made of the platform's own widgets, UIKit's on iOS and Android's views on Android, and follows each platform's interface guidelines. Every line of Objective-C, Swift, Java, or Kotlin the app needs is Fledge's (README). A phone's Ruby could print and run its program, and nothing more; the one example with a native screen drew it in per-app Objective-C and Java hosts, and was taken off `trunk` (a5ea8ab9).

Two facts bound the answer. UIKit's objects, and an activity's views, are the main thread's alone (`ViewRootImpl.checkThread`). CRuby runs Ruby only on threads it made: a callback that asks for Ruby's lock from any other thread ends the process (`thread.c`, lines 2320 to 2335 at v4.1.0-preview1), and no public API makes a foreign thread a Ruby thread (`include/ruby/thread.h`, lines 111 to 114). How does an app's Ruby reach those widgets, and on which thread does it run?

## Decision Drivers

- The developer writes only Ruby, and the platform's own widgets draw the screen, as its guidelines describe them.
- Code is a liability (`decisions.md`, 2026-10-28): reuse what the runtime already carries before writing C.
- A widget layer of Fledge's own is not Fledge's job; Fledge supplies only the bridge a runtime needs.
- The app's Ruby runs as under `ruby main.rb` (decisions 9, 10, and 20): `$LOAD_PATH`, `Thread.main`, and `exit` behave as there.
- Prior art: rubicon-objc and Toga, rubicon-java, pyjnius, Chaquopy, RubyMotion, NativeScript.

## Considered Options

1. Ruby on the main thread for an app that draws its screen (`kind: windowed`), calling the Objective-C runtime and JNI through Fiddle, with Ruby bridges in each runtime (`Fledge::ObjC`, `Fledge::JNI`) and only the C and Java Ruby cannot reach (the Java VM's pointer, a `java.lang.reflect.Proxy` handler).
2. The same thread model, with the bridges written as C extensions in each runtime.
3. Ruby on its own thread, with every call handed to the main thread and every callback handed back to Ruby's thread, in C.
4. A widget layer of Fledge's own over either bridge, one screen for both phones.

## Decision Outcome

Chosen: option 1, because it is the least code that works under CRuby's rule: Fiddle is in both runtimes already, its closures serve as Objective-C methods and as a native method's code, and every callback then arrives on a Ruby thread. On iOS the program calls `UIApplicationMain` itself, as RubyMotion's generated `main` and NativeScript's script do; on Android it runs inside Android's own main loop with a nested `Looper.loop()`, since, unlike CPython (Chaquopy, `chaquopy_java.pyx`, lines 88 to 92), CRuby cannot give up its lock and return to Java. Option 2 lost on code: C for both phones that Fiddle already does, and on iOS a second libffi beside Fiddle's. Option 3 lost on a rendezvous in C on both phones, a thread switch per call, and deadlocks where the waits cross; no bridge of the prior art works so. Option 4 is a framework's work, above Fledge. The design, its limits, and the evidence are in `doc/contributors/design/phone-widgets.md`.

Confidence: high that it works in the iOS Simulator, on an iPhone and an iPad, and on an Android emulator, where `examples/basket` shows its list, and where the check gives it an item and sees its row drawn (`tasks/mobile_parity.rb`); high that the bridges' core is right on a Mac's Objective-C runtime and a desktop Java VM (`test/objc_bridge_test.rb`, `test/integration/jni_bridge_test.rb`). Unproven: a real iPhone, where libffi's closures must come from pre-signed trampolines, App Review's acceptance of an app whose UIKit calls are sent from Ruby (`doc/contributors/account-tests.md`, IOS-6), and whether Fiddle's per-call cost is felt on a device's scrolling list. No recorded comparison says option 1 is faster or more reliable than option 2; it is the smaller.

### Consequences

- Good, because an app's screen is the platform's own, written in Ruby against the platform's own documentation, with no Fledge vocabulary between them.
- Good, because the bridges are Ruby, about 1,500 lines in all, with a little C and an 82-line Java class.
- Good, because a framework can build a widget toolkit on the bridges, as Toga builds on rubicon.
- Bad, because a windowed phone app's long work on the main thread freezes its screen, as in a native app; such work goes to a Ruby thread of its own.
- Bad, because every call crosses Fiddle, which is slower than compiled glue.
- Bad, because a Ruby exception in a callback cannot unwind through the platform's frames: it is printed, and `exit` there skips `at_exit`.
- Bad, because the bridges cannot yet pass structs by value, make Objective-C blocks, or subclass Java classes.
- Bad, because an app with a `Gemfile` names `fiddle`, a bundled gem, for the bridges to load.
- Bad, because on Android the nested `Looper.loop()` logs Looper's warning once per launch.
- Bad, because the bridges depend on how each platform's runtime loads its classes: UIKit is not in an iOS process until the bridge loads it, and a Java class's static fields read zero until its class is initialized, so the bridge does both, and a call into Ruby after the program ends is answered with nothing, since Ruby's closures are gone while Android's main thread goes on.
- Bad, because the type encodings of a few UIKit protocols are recorded in the bridge by hand, as a fallback for a protocol the Objective-C runtime does not hold.

### Confirmation

`test/objc_bridge_test.rb` (on a Mac) and `test/integration/jni_bridge_test.rb` (with a JDK) test the bridges against real runtimes. CI's mobile parity jobs build and run `examples/basket` in the iOS Simulator and on Android emulators, and fail unless its Ruby, on the main thread, logs the rows the platform asked it for and the app stays open; on Android the check types an item and taps Add, and fails unless the item shows as a row. `test/mobile_build_test.rb` checks that `kind: windowed` compiles iOS's host for the main thread with its 64 MB stack, and `test/mobile_template_contract_test.rb` freezes the marks that choose it.
