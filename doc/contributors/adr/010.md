# ADR 010: Each Platform's App, Built on That Platform with Its Own Tools

## Status
Accepted (requested). Agents wrote this ADR and may change it (AGENTS.md, Questions). It applies the maintainer's words of 2026-10-28 in `doc/contributors/decisions.md` ("Code is a liability and we should _not_ have 4k+ lines of things we could use existing tools for." and "We already have to have target-environment-platform machines to compile on, right? If so, what value does cross-platform non-compilation building add?"), which accepted the orchestrator's recommendation to build each target on its own operating system with that system's maintained tools. It supersedes ADR 001, section 2's promise that any computer builds every platform, and the parts of ADR 006, ADR 008, and ADR 009 that kept it.

## Date
2026-10-28

## Context

Through 0.0.1.pre.7, `fledge build -t PLATFORM` built any platform's app on any computer. A Mac built the Windows program and its installer, and a Linux runner built every platform's app in CI. That promise (ADR 001, section 2) was never the maintainer's; agents made it, and kept it by writing in Ruby what each platform's own tools do, because those tools run only on their own platform.

The promise bought little. A gem with an extension to compile already had to be built on its own platform (ADR 006), so a project with one needed a computer of each platform anyway. A developer needs each platform to test the app on, and to sign it with Apple's or Microsoft's credentials when they have them (decision 17). And the prior art builds each platform on itself:

- **Tauri's bundler** builds for the computer it runs on: `.app` and `.dmg` on macOS with `hdiutil` (`crates/tauri-bundler/src/bundle/macos/dmg/mod.rs`), `.msi` on Windows only, and AppImages on Linux with linuxdeploy and appimagetool (`crates/tauri-bundler/src/bundle/linux/appimage/linuxdeploy.rs`); its `--target` chooses a Rust target triple for the compiler, not another operating system's package.
- **Briefcase** builds an app only on the platform it is for: each platform declares the hosts it builds on, and a Windows app's says "Windows applications can only be built on Windows." (`src/briefcase/platforms/windows/__init__.py`, `supported_host_os` and `supported_host_os_reason`, lines 81 and 82, on its main branch), which its commands raise as `UnsupportedHostError`.
- **Electron's tooling** signs and makes disk images with Apple's tools on a Mac, and edits a Windows program's resources with rcedit, which calls Windows' own `UpdateResource`.

## Decision

### 1. `fledge build` builds for the computer it runs on

`fledge build` builds the app for the platform it runs on, `Platform.local`, and nothing else. Its `-t` and `--target` are gone: given either, it says so and exits 2, as any usage error does, naming what to do instead (build each platform's app on that platform), since a script written for 0.0.1.pre.7 would otherwise read only "unrecognized option". A computer Fledge has no runtime for (Intel macOS, musl Linux, 32-bit Windows) cannot build, and the error lists the platforms that can.

So a gem with an extension to compile is always compiled, for the platform it is for, and the error that named a gem as needing another computer is gone with the case it described.

Fledge's own CI builds each platform's apps on a runner of that platform (`ci.yml`, Build), the job that built every platform's on one Linux runner is gone, and Delivery runs each on a fresh runner of its own platform, as before. The runtimes still build as is simplest: the Windows runtime's launcher is still compiled on Linux by the pinned llvm-mingw, which is a compiler, not a format Fledge wrote.

### 2. Archives: the computer's own tar

A runtime arrives as a `.tar.gz` and a built app leaves as one, or as a `.zip` on Windows. Every computer that builds apps has a tar that reads and writes these and keeps executable bits and symbolic links: GNU tar on Linux, bsdtar (libarchive) on macOS, and on Windows 10 and 11 the bsdtar Windows ships as `C:\Windows\System32\tar.exe`, which writes ZIP too (`--format zip`). So `Fledge::Archive` runs that tar, and Fledge's own tar reader and writer and ZIP writer (`Fledge::TarGz`, `Fledge::Zip`, about 480 lines) are gone. It names `System32\tar.exe` itself on Windows, since Git's GNU tar, often first on a developer's `PATH`, writes no ZIP and reads `C:` as a host name; on macOS it sets `COPYFILE_DISABLE`, so bsdtar adds no AppleDouble files. The runtime builder, the source bundles, and the licensing page's audit pack and unpack with it too.

Considered: rubyzip (BSD-2-Clause) and minitar (Ruby's license or BSD-2-Clause), which would make Fledge depend on gems it has done without, for what every host's tar already does; RubyGems' own `Gem::Package::TarWriter`, which refuses a path longer than ustar's 256 bytes, which a gem's files can exceed; and PowerShell's `Compress-Archive`, which a Ruby program would start for every archive and which has written backslashes into ZIP paths in Windows PowerShell 5.1.

Because each build runs on its own platform, the app's folder is written to disk first and archived from there: the runtime is unpacked, moved into the folder (or a bundle's `Contents/Resources`), the app and its gems copied in, and the launcher placed last; the archive and each installer are made from that folder by the platform's tools. Fledge no longer streams entries into an archive, a disk image, and a file system at once. Reproducible archives (every entry dated `SOURCE_DATE_EPOCH`), which Fledge's own writer gave runtime archives, are not kept: GNU tar and bsdtar spell it differently, and nothing reads the dates.

### 3. macOS: plutil, codesign, and hdiutil

Every Mac has the tools Apple makes bundles and disk images with, in `/usr/bin` with macOS itself (unlike `cc` and `git` there, they are no shims for Xcode's command line tools):

- `Info.plist` is the keys Tauri's bundler writes (ADR 008, section 2), written as JSON and converted by `plutil -convert xml1`; `Fledge::Plist` is gone.
- The bundle is signed ad hoc by `codesign --force --sign - --identifier IDENTIFIER NAME.app`, which seals `Info.plist` and every resource and signs the launcher for them, and `codesign --verify --strict --deep` accepts it, in its folder, in its archive, and in its disk image. `Fledge::AdHocSignature` and `Fledge::CodeResources`, which wrote a SuperBlob, a CodeDirectory, and the seal as codesign writes them (about 450 lines), are gone.
- The disk image is made as Tauri's create-dmg makes one: the bundle, copied with `ditto` (which keeps its signature, links, and modes), beside a link named `Applications` to `/Applications`, in a folder `hdiutil create -volname NAME -srcfolder FOLDER -fs HFS+ -format UDZO` makes a read-only, zlib-compressed image of. `Fledge::HfsPlus` and `Fledge::Udif` (about 600 lines) are gone, and the volume is Mac OS Extended, as create-dmg's are, rather than the case-sensitive HFSX Fledge wrote, so an app that opens its own files by a name of another case runs from the image as it does once dragged out. On macOS 26 and newer, `hdiutil create` prints that `diskutil image create` replaces it; macOS 14 and 15, which Fledge's runners and its oldest supported Macs run, have only `hdiutil`, so Fledge runs it and takes its output only when it fails.

### 4. Icons: each system's own file, as the developer makes it

Fledge read one PNG of 1024 pixels and wrote every size and format itself: a PNG decoder for every color type and interlacing, an area-averaging resampler, and `.icns`, `.ico`, and PNG writers (`Fledge::Png` and `Fledge::Icon`, about 600 lines). Each system has its tool for its own format, and the prior art asks the developer for the files:

- **Briefcase**'s `icon` is "a path ... to an image to use as the icon for the application. The path should *exclude* the extension; Briefcase will append a platform appropriate extension", with "the required size" appended where a platform needs several (`docs/en/reference/configuration.md`, the `icon` setting); macOS apps "use `.icns` format icons", Windows apps "multi-format `.ico` icons" of 16, 32, 48, 64, and 256 pixels, and AppImages `.png` icons of 16, 32, 64, 128, 256, and 512 pixels (`docs/en/reference/platforms/macOS/index.md`, `windows/index.md`, and `linux/appimage.md`, each's "Icon format").
- **Tauri**'s bundler takes the files its `bundle.icon` lists (`icons/32x32.png`, `icons/icon.icns`, `icons/icon.ico`, and the rest), which `tauri icon`, a separate command, generates.

So `fledge.yml`'s `icon` is Briefcase's: a path without an extension, `icon: icons/app`, and each platform's build takes its own file from beside it, as the developer made it: `icons/app.icns` for macOS (which `iconutil -c icns` makes from an `.iconset` of PNGs on any Mac), `icons/app.ico` for Windows, and `icons/app-16.png` to `icons/app-512.png` for Linux, Briefcase's six sizes. A missing file fails the build on that platform, saying what it needs and how to make it; an `icon` that ends in `.png`, `.icns`, or `.ico`, as 0.0.1.pre.7's one PNG did, fails saying to drop the extension. Fledge checks no sizes: it reads none of these formats. `examples/windowed_app` carries its icon in all three, made with `sips` and `iconutil` from the PNG Fledge used to read.

Considered: ImageMagick (its own Apache-2.0-like license), which writes every format with `-define icon:auto-resize`, but is a large program a developer may not have, of different major versions on different Linux distributions, so a pin would be a wish; libvips, which writes no `.ico`; chunky_png (MIT), a pure-Ruby PNG codec whose bilinear resampling blurs an icon shrunk from 1024 to 16 pixels unless Fledge resamples in steps itself, and which writes neither `.icns` nor `.ico`; icoutils' `icotool` (GPL, which would be fine for a tool that ships in no app), which is Linux-only and makes only `.ico`; and macOS's own `sips` and `iconutil`, which make `.icns` but leave Windows and Linux with nothing. Asking for each system's file is less code than any of these, and is what Briefcase and Tauri's bundler ask.

### 5. Windows: rcedit writes a program's identity

Fledge rewrote the launcher's resource section itself: a PE reader and writer that moved `.reloc`, a VS_VERSIONINFO writer whose bytes matched `llvm-rc`'s, and icon resources from its own icon writer (`Fledge::WindowsProgram`, `Fledge::VersionInfo`, and `Fledge::WindowsResources`'s old body, about 560 lines). On Windows, which builds every Windows app now, Windows' own `UpdateResource` does that, and **rcedit**, Electron's tool (MIT), calls it: electron-builder and electron-packager write every Electron app's version information and icon with it. Tauri compiles its resources into its program when it links it (`tauri-build`, through `tauri-winres`, which compiles a resource script and links it in; ADR 008 cites the lines), which a launcher Fledge's CI already linked cannot. `llvm-rc` and `llvm-windres` compile resources but do not put them into a program that is already linked.

Each Windows runtime carries rcedit 2.0.0's `rcedit-x64.exe` in `tools/` (the folder that was `installer/`, renamed, since it holds what fledge build runs as well as what installers copy), pinned by SHA-256 in `runtime/sources.yml` and accounted for by the license audit, which checks that SHA-256 too; no app holds it. `Fledge::WindowsResources` runs it on the app's program: `--set-version-string` for FileDescription, ProductName, and InternalName (the app's name), OriginalFilename (its program's), and CompanyName and LegalCopyright when there are a publisher and a copyright; `--set-file-version` and `--set-product-version` with the version as written, which rcedit keeps as FileVersion and ProductVersion and whose leading numbers it makes FILEVERSION and PRODUCTVERSION; and `--set-icon` with the developer's `.ico`. Fledge still refuses a version part above 65535 itself, since rcedit would let it wrap. rcedit keeps the launcher's manifest. It numbers a new icon group as it numbers one, not 32512 as Fledge and Tauri did; Explorer and the shell show a program's first group whatever its number.

### 6. Linux: AppImage's own runtime, and mksquashfs

Fledge wrote an AppImage's SquashFS in Ruby (`Fledge::Squashfs`, about 350 lines) and built AppImage's type 2 runtime itself, with a C file of its own that loaded the computer's libfuse in place of the libfuse the runtime links (`runtime/appimage/fuse.c`, 240 lines) and a patch that made the runtime extract itself where it could not mount (`runtime/appimage/runtime.patch`). Both existed because one computer built every platform, and because ADR 009 read decision 8 as forbidding libfuse, LGPL-2.1, linked into anything an app carries. The maintainer's replies on the LGPL (2026-10-26: "Source offer for... the app? Or the LGPL'ed library? Former won't be liked, latter is fine and normal.") ask only that no app's own source or object files be required. libfuse is linked into AppImage's runtime, an MIT program that is not the developer's app and not Fledge's launcher; publishing the runtime's complete source with libfuse's is what LGPL-2.1, section 6(a), asks of a work linked with the library, and it asks nothing of the app inside the AppImage, which only runs as a child of it.

So each Linux runtime carries AppImage's runtime exactly as AppImage releases it (release 20251108, commit dd6cebe, one file per architecture), pinned by SHA-256 in `runtime/sources.yml`, in `tools/appimage-runtime`, and `Fledge::AppImage` makes an AppImage as appimagetool does (`src/appimagetool.c` at its 1.9.1 tag, `sfs_mksquashfs`, lines 97 to 215): the app's folder copied into an AppDir with `AppRun`, the icon, and `.DirIcon`; `mksquashfs APPDIR APPIMAGE -offset SIZE -comp zstd -b 128K -root-owned -noappend -mkfs-time 0`, from squashfs-tools 4.4 or newer, which a Linux developer installs from their distribution (`apt install squashfs-tools`); and the runtime written into the room `-offset` left before the file system. appimagetool itself was considered, but it is an AppImage that needs FUSE to run, downloads its runtime unless told otherwise, and does nothing for Fledge but run mksquashfs and validate the desktop entry, which Delivery does with `desktop-file-validate`. squashfs-tools is GPL-2.0, which matters to no app: it runs on the developer's computer and writes a file system, and none of its code is in the AppImage.

AppImage's runtime behaves as every AppImage does: with FUSE it mounts itself, and without FUSE it says so ("Cannot mount AppImage, please check your FUSE setup.") and runs only when asked to extract itself, with `APPIMAGE_EXTRACT_AND_RUN=1` or `--appimage-extract-and-run`, as AppImage documents. Fledge's runtime extracted itself unasked; a person who has met an AppImage before knows the upstream behavior, and Delivery checks both.

The license audit's rule changes to match (`tasks/license_audit/policy.rb`): an LGPL component may ship as its own shared library with its source pinned, as before, or linked into another component that is not Fledge's own and whose source Fledge publishes, with the LGPL library's source published too. Fledge's launcher, the program an app's developer ships as their own, may never hold LGPL code; libfuse's signature anywhere else still fails as `static-copyleft`. `runtime/licenses.yml` lists what AppImage's build links into its runtime (libfuse 3.15.0 with AppImage's patch to its `mount.c`, squashfuse 0.5.2, zstd 1.5.6, zlib 1.3.1, mimalloc 2.1.7, musl 1.2.5, and Alpine's libgcc 14.2.0), each proven present by a string in the file; each Linux release's source bundle holds the runtime's source at its commit, with its build scripts and the patch, and libfuse's release, each with a BUILD.txt that says how to rebuild the runtime with another libfuse; and every Linux app's NOTICES names them.

### 7. Windows: NSIS's own release, and LZMA

Fledge's CI built makensis from NSIS's source for macOS and Linux, with SCons from its wheel, and published one for each computer that builds apps (`tasks/makensis_builder.rb`, `fledge-makensis-VERSION-PLATFORM.tar.gz`), which `fledge build` downloaded beside its runtimes. On Windows, which builds every Windows app now, NSIS's own release runs as it is, and Tauri's bundler runs it there (`crates/tauri-bundler/src/bundle/windows/nsis/mod.rs`, which downloads NSIS's release on Windows). So the Windows runtime carries, in `tools/nsis`, the files of NSIS 3.13's release that compile an installer: its `COPYING`, `Bin/makensis.exe` and the `zlib1.dll` it loads, the stub of solid LZMA compression and the uninstaller's icon, the System and nsDialogs plug-ins, the script headers, and Modern UI 2; `Fledge::Nsis` runs that makensis with `NSISDIR` pointing beside it and `-NOCONFIG`. The makensis builder, its jobs, its release assets, and `Fledge::Runtimes#makensis` are gone.

Installers are compressed with `SetCompressor /SOLID lzma`, NSIS's default and Tauri's, in place of zlib. ADR 009 chose zlib because NSIS's LZMA module is under the Common Public License 1.0, whose section 3 asks that a program distributed in object code state that its source is available and how to obtain it. The maintainer accepted switching to LZMA with NSIS's source published (2026-10-28). Each Windows release's source bundle holds NSIS 3.13's source release, with a BUILD.txt; every Windows app's `notices/NOTICES.txt`, which its setup program installs, names NSIS, its licenses (the zlib license, bzip2's for makensis's bzip2 module, and the CPL), and where its source is; and the license policy gains a category for a license that asks only that a binary say where its source is (`Fledge::LicensePolicy::SOURCE_OFFER`, CPL-1.0), allowed when Fledge publishes the component's source, as the audit checks.

## Consequences

- A developer builds the macOS app on a Mac, the Windows app on Windows, and the Linux apps on Linux, on their own computers or on CI runners of each; one computer no longer builds every platform. Scripts that pass `-t` or `--target` fail, saying why.
- What each platform's build needs is its own system's: on macOS nothing beyond macOS (tar, plutil, codesign, ditto, and hdiutil are in `/usr/bin`); on Windows, Windows 10 or 11, whose `System32\tar.exe` writes the `.zip`, with rcedit and NSIS in the runtime; on Linux, tar, and squashfs-tools 4.4 or newer for an AppImage. Compiling a gem still needs a compiler (ADR 006). A missing tool fails the build with the tool's name and what to install (`Fledge::Command`).
- `fledge.yml`'s `icon` names each system's icon files without an extension, and a developer makes them; 0.0.1.pre.7's one PNG fails, saying what to write.
- About 4,600 lines of Ruby and C that wrote formats and signatures are gone: `Fledge::TarGz`, `Fledge::Zip`, `Fledge::Plist`, `Fledge::CodeResources`, `Fledge::AdHocSignature`, `Fledge::HfsPlus`, `Fledge::Udif`, `Fledge::Png`, the old `Fledge::Icon`, `Fledge::WindowsProgram`, `Fledge::VersionInfo`, `Fledge::Squashfs`, `runtime/appimage/`, and the makensis builder, with their tests. What remains of Fledge's own is what no tool writes: the launcher, the bundle's layout and its `Info.plist` keys, the desktop entry (plain text that `desktop-file-validate` checks; `desktop-file-install` edits one but writes none from nothing), the NSIS script, and the command lines of the tools.
- `Fledge::Binary`, the ELF, Mach-O, and PE readers that the license audit and `Fledge::Linkage` use (about 550 lines), stays, for now: the audit of the Windows runtime runs on Linux, where the runtime is built, and of every runtime in CI's Licenses jobs on one Linux runner, and `fledge build` checks a gem's compiled files on every system. `readelf`, `otool`, and `llvm-readobj` read these formats, but none of them is on every computer that builds apps (`readelf` is binutils', which a Linux developer who compiles nothing may lack; `otool` is Xcode's; Windows has none), so replacing the readers means a tool per platform, or llvm-readobj in every runtime. That is the next step, with the audit run on each runtime's own system.
- Reproducible archives, which Fledge's own tar writer made, are given up until tar's flags for them (`--sort`, `--mtime`, `--owner`) are needed and spelled for both GNU tar and bsdtar.
- Not yet: a disk image made by `diskutil image create`, which replaces `hdiutil create` on macOS 26 and newer; rcedit's icon group numbered as Tauri's, 32512.
