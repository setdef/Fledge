# ADR 019: What a Framework Wrapper May Rely On

## Status
Accepted (requested). Agents wrote this ADR and may change it (AGENTS.md, Questions). It is Plan 003's story "A framework wrapper ships an app through Fledge." It rests on no decision of the maintainer beyond those the earlier ADRs apply; the wrappers are the maintainer's own projects, and AGENTS.md says they will call Fledge. ADR 027 amends section 5 for an `extconf.rb` that runs CMake. ADR 029 widens section 2 into what 1.0 freezes for every developer, and says what a wrapper may not rely on: Fledge's Ruby classes, standard error's wording, and `fledge.cfg`.

## Date
2026-11-01

## Context

Lota (2D games), Tokra (desktop apps), and Rooibos (terminal UIs) are meant to call Fledge, so that a developer who uses one ships an app without learning how. Nothing yet showed that an app built on a wrapper's gems ships through `fledge build`. The story asks for the wrapper whose app is closest to shipping, Fledge pinned from a release tag in its Gemfile, one of its examples built and delivered on each platform it supports with that release's runtimes, what breaks in Fledge fixed, and the contract written down.

The three wrappers, inspected as sibling checkouts (read-only) on 2026-11-01:

- **Rooibos 0.8.0** (terminal UIs) is on RubyGems.org. It is pure Ruby on `ratatui_ruby`, a Rust gem published precompiled for `arm64-darwin`, `x86_64-linux`, and `x64-mingw-ucrt` (and as source, which cargo compiles, for the other platforms). A console app needs nothing from the person's computer but a terminal, which is the kind Fledge has shipped since Plan 001. It has examples (`examples/verify_website_hello_mvu`, `examples/app_fractal_dashboard`), and `examples/native_app` in this repository already ships `ratatui_ruby` through Fledge.
- **Tokra 0.0.1.pre.2** (desktop apps) is on RubyGems.org, but compiles a Rust extension (rb-sys) on every platform, opens a native webview whose Linux libraries (WebKitGTK) the person's computer must have, which Fledge's rule that a person never meets Ruby did not yet answer (ADR 030 answers it for libraries a gem loads), and its examples are `verify_*` scripts that `require_relative` the repository's `lib/`. A windowed app also needs a display to deliver, which GitHub's runners give only to the macOS and Windows desktops.
- **Lota** (2D games) is version 0.0.0, unpublished, a C++ extension, with no examples folder; its own plan (Plan 002, story 9) leaves `lota fuse` waiting on the maintainer's decision about Fledge.

Rooibos is closest. Its first app, the website's "first app" (`examples/verify_website_hello_mvu`, MIT-0), is a program of one file that needs the wrapper and one precompiled Rust gem.

## Decision

### 1. Rooibos is the first wrapper; its first app is the example

The app is the example's `app.rb` as `main.rb` of a project with a Gemfile that locks `rooibos` 0.8.0 and puts Fledge, from a release tag, in the `development` group, which Fledge leaves out of the app:

```ruby
source "https://rubygems.org"
gem "rooibos", "0.8.0"
group :development do
  gem "fledge", git: "https://github.com/setdef/Fledge", tag: "v0.0.1.pre.16"
end
```

`bundle lock --add-platform arm64-darwin x86_64-linux aarch64-linux x64-mingw-ucrt` and `bundle lock --add-checksums` lock the platforms and checksums Fledge requires (ADR 005, section 6); `bundle exec fledge build` builds it.

### 2. What a wrapper may rely on

A wrapper may rely on the following from a Fledge release, and Fledge changes none of it without a CHANGELOG entry (pre-1.0) or a major version (from 1.0).

- **The command.** `fledge build [PATH]` builds the program at PATH (default: the current directory; a folder means its gemspec's executable, or its `main.rb`) on the computer it runs on, for that computer's platform, with `-o DIR` choosing the output folder (default `dist`). It runs as `bundle exec fledge build` from a project whose Gemfile names Fledge by tag. Fledge itself needs Ruby 4.0 to run; the app it builds runs on the runtime's Ruby, 4.0.9 in 0.0.1.pre.16, whatever Rubies the wrapper supports otherwise. The first build downloads the release's runtime, checked against the gem's pins (ADR 014), into `$XDG_CACHE_HOME/fledge/runtimes`; `FLEDGE_RUNTIME_DIR` names a folder of runtimes instead.
- **The project.** The nearest folder from the program up with a Gemfile, `gems.rb`, gemspec, or `fledge.yml` (not above a git repository's top) ships whole, but for `.git`, `.bundle`, `vendor/bundle`, `vendor/cache`, and the output folder, together with the gems the lockfile locks outside the `development` and `test` groups, each as built for the platform (ADR 005). Gems a project uses to develop or test it, and Fledge itself, belong in those groups; a gem outside them ships, and Fledge compiles it when it must.
- **`fledge.yml`.** A YAML mapping of `name`, `kind` (`console`, the default, or `windowed`), `identifier`, `version`, `icon`, `publisher`, `copyright`, `installers` (ADR 008 and ADR 009), and `programs`, which lists several programs of one project to ship in one folder (ADR 024). A wrapper whose app is one of several programs, as `lota fuse` will be for a game's GUI, names its entry point as one of the `programs` and builds the project, or builds that program alone by its path. A wrapper may write it for its developer or read the developer's. An unknown key is refused, naming it, so a wrapper never sees a key silently ignored.
- **Exit statuses.** `fledge` exits 0 when it succeeds, 1 when a build fails, and 2 when it cannot make sense of its arguments (ADR 002). A built app's program exits with its Ruby program's own status; it exits 66 when its program or `fledge.cfg` is missing and 70 when the rest of its folder is broken (ADR 002, section 3). Ctrl-C and a closed terminal reach the app as they reach `ruby` (ADR 015).
- **Output.** On standard output, `fledge build` prints the path of each file it writes, one per line, and nothing else: `dist/NAME-PLATFORM.tar.gz`, or `.zip` on Windows, then the installers of a windowed app. Progress, the runtime and gem downloads (`Downloading ... from URL`), compiler output, and every error and warning go to standard error, an error as `fledge build: ...`, one line for each thing that is wrong. `NAME` is the `fledge.yml` name, else the gemspec's, else the project folder's, camelized.
- **What a built app is.** A folder `NAME-PLATFORM/` (ADR 002, section 2) whose program, `NAME` or `NAME.exe`, needs no Ruby and is unaffected by a Ruby the person has (ADR 001 and ADR 003). Its `ENV`, `$0`, and load path are as under `bundle exec ruby main.rb` (ADR 003 and ADR 005), so a wrapper's own checks such as `__FILE__ == $0` behave as under `ruby` (Rooibos's examples use that one).
- **What it does not rely on.** Fledge builds each platform's app on that platform (ADR 010). A wrapper's CI therefore runs one build job on a runner of each platform it ships to, and a delivery job on a fresh runner of each, which takes the archive and runs it.

### 3. A bug the wrapper's own Gemfile found, fixed

Building Rooibos's repository directly, rather than a project of the kind above, failed: `fledge build: lib/ruby/gems/4.0.0/plugins/rdoc_plugin.rb is in ... already, so the build can't add its own`. Rooibos's Gemfile puts its tools (`irb`, `rubocop`, `rubycritic`, and others) outside the `development` group, so they ship, and `irb` asks for `rdoc`, locked at a version newer than the runtime's. A gem with a RubyGems plugin writes a loader named for the gem in the gem folder's `plugins/`; the runtime's `rdoc_plugin.rb` is there already, and the build refuses to replace a file of the runtime's. Rails and many other applications lock `rdoc` the same way, so the failure was general.

RubyGems' own rule (`Gem::Installer#generate_plugins`, `installer_uninstaller_utils.rb`, `regenerate_plugins_for`, at Ruby 4.0.9) is that installing a gem writes its loader over any other version's. Fledge's gem folder is read by RubyGems and Bundler as they read any other, a loader only matters to a command that installs gems (`gem install` and the hooks that `rubygems_plugin` registers), and an app never installs. The build keeps the runtime's loader and installs the app's gem beside it. `Fledge::RuntimeContents#plugins` lists the runtime's loaders and `Fledge::AppGems` leaves out a loader the runtime has.

### 4. Proven

The experiment workflow on the `experiment/wrapper` branch (run 41360640888) is what Rooibos's own CI would run. On a runner of each platform it writes the project of section 1 from the example at Rooibos's `v0.8.0` tag, installs Fledge from `v0.0.1.pre.16`'s tag with Bundler, and builds with the release's runtime; it then takes the archive to a fresh runner, and runs the program in a pseudo-terminal of 80 by 24 cells (macOS and Linux; `python3`'s `pty`) or in a console of its own (Windows; the console's screen buffer read with `ReadConsoleOutputCharacterW`, keys typed with `WriteConsoleInputW`, as ADR 015 does), with a `PATH` that holds no Ruby and `RUBYOPT`, `RUBYLIB`, and `GEM_HOME` set. The app must show `Current count: 0.`, show `1` after an `a` is typed, restore the terminal, and exit with status 0 when Ctrl-C is typed. It passed on `arm64-darwin`, `x86_64-linux`, `aarch64-linux` (where `ratatui_ruby` compiles with cargo), and `x64-mingw-ucrt`.

### 5. Phones: what Fledge provides, and what a wrapper provides

A wrapper that ships to an iPhone, an iPad, or an Android device may rely on this from a Fledge release (ADR 011, 012, 022, 025). The same CHANGELOG rule applies.

**Fledge provides**

- `fledge build ios` (on a Mac, with Xcode and XcodeGen) and `fledge build android` (on a Mac, x86-64 Linux, or Windows) write an Xcode or Gradle project that holds the project, its gems, and a runtime. The wrapper's team builds, signs, and submits that project with Xcode or Gradle.
- A gem with a C or C++ extension built by an `extconf.rb` is compiled for each of the phone's targets, linked into the app, and registered, so `require "name/name"` finds it. Static libraries an `extconf.rb` links are linked per iOS slice; shared libraries are carried into the Android app.
- `ios: host: DIR` and `android: host: DIR` in `fledge.yml` name a folder of files that `fledge build` copies over the project it writes, so a framework that must own the app's startup (SDL3's `SDL_RunApp` on iOS, an `SDLActivity` on Android) supplies its own files and keeps them across rebuilds.

**The wrapper provides**

- A Ruby program that starts the app, and the gems it needs in the project's `Gemfile.lock`, locked for `ruby` (`bundle lock --add-platform ruby`). A phone runs no shell script, and the wrapper's gems must be in the lockfile, not found on the build computer's paths.
- An extension that an `extconf.rb` builds, loaded with `require "name/name"`, not `require_relative`. The `extconf.rb` may run CMake first to build a library the extension links: Fledge puts each target's toolchain file in `CMAKE_TOOLCHAIN_FILE`, and the `extconf.rb` runs `cmake` in a new build folder as on a desktop, links the library through `$LOCAL_LIBS`, and names the C++ runtime as on a desktop when the extension is C over C++ (ADR 027, section 5). Fledge refuses, naming the gem, an extension that the gemspec says Rake, CMake, or configure builds, with no `extconf.rb`, and a Rust extension.
- Its native libraries, built for the phone's targets and found by the `extconf.rb` (`dir_config`, or `bundle config build.NAME`).
- The host files, when its framework owns startup, in the `host:` folder. ADR 025 section 5 lists what a host may replace.

**Known limits**

- A game built with `fledge build ios` has run on a physical iPad and a physical iPhone (ADR 025, section 6); a game built by Fledge v0.5.1 has run on a physical Android device, a OnePlus Nord N30 5G (Android 14, arm64-v8a), on 2026-11-05 (Plan 003, Android on arm64). The Simulator and x86_64 emulators run the apps in CI; CI does not run the arm64-v8a build.
- An SDL host on iOS runs Ruby on the main thread and sets a 64 MB main-thread stack in the project's linker flags. Apple documents 1 MB for a device's main thread. An iPhone 13 mini granted the 64 MB (ADR 025, section 6); an iPad's grant is not measured, so a deep recursion in Ruby could still fail there.

## Consequences

- Rooibos's own CI can add a build job and a delivery job of the same shape on its runners, in its own repository; Fledge asks nothing of it but the Gemfile above and a lockfile of the platforms it ships to. The maintainer ruled on 2026-11-02 that Fledge depends on no wrapper's repository and wrappers depend on Fledge, so Fledge does not wait on that CI, and the story is done on Fledge's side (Plan 003).
- A wrapper whose CI tests its unreleased source cannot name it as a path gem outside the project (ADR 005, "Not yet"); a git gem at a commit works.
- Rooibos's repository itself is a library's, not an app's; building one of its examples from the repository's root ships its tools. A developer's project, or a project that puts its tools in the `development` group, ships only what runs.
- `aarch64-mingw-ucrt` and the musl platforms are not proven for a Rooibos app: `ratatui_ruby` publishes no ARM64 Windows build.
- Tokra's and Lota's apps remain; each needs its own story once it ships a published, runnable example.
