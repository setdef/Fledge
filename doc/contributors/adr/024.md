# ADR 024: One Project, Several Programs

## Status
Accepted (requested). Agents wrote this ADR and may change it (AGENTS.md, Questions). It carries out Plan 003's story "One project, several programs", whose design the maintainer approved in conversation on 2026-11-02: "a `fledge.yml` section that names each program, its path and its kind (console or windowed). `fledge build` builds all of them into one folder that shares one runtime, one copy of the project, and one set of gems. A windowed program gets its platform's installer entry; a console program sits beside it." A project with no section builds as it did before. It extends ADR 005 (section 3, `fledge.yml`), ADR 008 (identity), ADR 009 and ADR 021 (installers), ADR 016 (signing), ADR 019 (what a wrapper relies on), and ADR 023 (the schema).

## Date
2026-11-02

## Context

A Ruby project often has several ways in that share one codebase. Deckbuilder, the maintainer's game, has `bin/cli` (a line-at-a-time game), `bin/tui` (a Rooibos terminal UI), and a GUI on Lota, and all three open the same save, so a player can quit one and resume in another. `fledge build` makes one program per run, so three programs would be three folders, each with its own copy of the project, the runtime, and the gems, and three things for a player to download. Lota's `lota fuse` will call Fledge for the GUI program, which is a Ruby file in the project (a Lota entry point), not Deckbuilder's `bin/gui` shell script.

Two facts of the platforms decide most of the design:

- **A program's kind is a property of its executable.** On Windows, whether a console opens is the PE header's Subsystem field, which is why a Windows runtime ships `launcher.exe` and `launcherw.exe` (ADR 008, section 3). On macOS, a windowed app is a bundle whose `Info.plist` names one `CFBundleExecutable`, and macOS knows the app by that bundle's `CFBundleIdentifier`. One launcher that takes the program as an argument would need a console on Windows for a windowed program, or none for a console one, and could not be a bundle's executable and a terminal command at once. So each program is its own copy of the launcher, renamed, as today's one program is.
- **On macOS and Linux the launcher is Ruby.** libruby is linked into it, and Ruby takes its prefix from the file that holds libruby (ADR 001, section 1; `runtime/launcher/unix.c`), so every launcher copy sits beside `lib/ruby`. Several programs in one folder share one `fledge.cfg`, which must say what each runs.

Prior art, read for this decision:

- **Tauri's bundler** (`tauri-apps/tauri` at 32576120f) bundles every binary a crate builds into one app, and marks one as the main binary (`crates/tauri-bundler/src/bundle/settings.rs`, `main_binary`, lines 982 to 989). On macOS it copies each into the one bundle's `Contents/MacOS` (`bundle/macos/app.rs`, `copy_binaries_to_bundle`, lines 158 to 171); its NSIS installer installs the others beside the main one (`bundle/windows/nsis/mod.rs`, lines 809 to 820), and makes its shortcut for the main one only (`installer.nsi`, lines 44 and 45, `MAINBINARYNAME`); its `.deb` puts each in `usr/bin` (`bundle/linux/debian.rs`, lines 120 to 125); its AppImage runs the main one (`bundle/linux/appimage/linuxdeploy.rs`, line 63). One app, one face, the other programs beside it: the maintainer's design.
- **PyInstaller's multipackage bundles** (its manual, `doc/spec-files.rst`, "Multipackage Bundles", read from the `develop` branch on GitHub): several `EXE` targets, each its own bootloader built console or windowed, and one shared `COLLECT` that "will collect the external resources for all of the one-folder apps into one directory". One executable per program over one shared folder, as here.
- **Briefcase** (its configuration reference, read on briefcase.beeware.org): "A project that is packaged by Briefcase can declare multiple applications", each under `[tool.briefcase.app.<app name>]`, with `version`, `author`, and `url` among the project's keys and `formal_name`, `icon`, and `console_app` among each app's. Each app builds into a bundle of its own, with its own Python; nothing is shared.
- Briefcase's and PyInstaller's source were not read: neither is checked out on the computer this ADR was written on, and the documentation above was enough for what this ADR takes from them, the split of keys and the one shared folder.

## Decision

### 1. `programs`: a list of each program's path, and what it shows

`fledge.yml` gains one key, `programs`, a list of mappings, one per program, in the order the developer gives them:

```yaml
name: Deckbuilder
version: "1.0.0"
programs:
  - path: gui/main.rb
    kind: windowed
    name: Deckbuilder
    identifier: com.example.Deckbuilder
    icon: icons/deckbuilder
  - path: bin/cli
    name: deckbuilder-cli
  - path: bin/tui
    name: deckbuilder-tui
```

Each program has:

- **path**, required: the program's file, relative to the project's root, with `/` between folders, inside the project. It is what `fledge build PATH` takes today.
- **name**: the program's name, with ADR 008's meaning for an app's name, but for this program: its file name in the built folder, its bundle's name and `CFBundleName` on macOS, its FileDescription and ProductName on Windows, and its desktop entry's `Name`. It defaults to the path's file name less its extension (`bin/cli` is `cli`), as Cargo names a binary after its file. Names are unique among the programs, ignoring case, since Windows and macOS file systems ignore it.
- **kind**, `console` (the default) or `windowed`.
- **identifier** and **icon**, with ADR 008's meaning, for this program. A windowed program needs an identifier. No two programs share an identifier, since Windows groups windows and attributes notifications by it.

The project keeps `name`, `version`, `publisher`, `copyright`, and `installers`, as Briefcase keeps `version` and `author` for its project: they describe what the person downloads, which is one thing. `name` names the folder, its archive, and the installers (`NAME-PLATFORM`); each program's version information carries the project's version, publisher, and copyright. With `programs`, a `kind`, `identifier`, or `icon` at the top is refused, naming the program to move it to: each program has its own, and a value at the top would leave a reader to guess which program it means.

### 2. At most one windowed program

A project with `programs` has one windowed program or none. A windowed program is an app the operating system knows by its identifier, and on macOS that is a bundle, which must hold its runtime to be dragged to Applications, signed, and sealed; two windowed programs would be two bundles, so two runtimes, which is the copy this story exists to remove. An AppImage likewise runs one program from its one desktop entry. Deckbuilder and `lota fuse` each have one window to open. A second windowed program is refused, saying to build it on its own (section 6). Lifting this costs a runtime in each bundle on macOS and an AppImage for each windowed program on Linux.

A project whose programs are all console builds a folder of console programs and no installer, as a console app has none (ADR 009, section 1); `installers` with entries is refused there, as it is for a console app.

### 3. One launcher per program, each finding its part of fledge.cfg by its own name

Each program is a copy of the runtime's launcher, renamed to the program's name: `launcherw` for a windowed program on Windows and `launcher` for every other. `fledge.cfg` (ADR 005) keeps its shared keys at the top and gives each program a section headed by its name, as an INI file or Git's configuration heads one:

```
# Written by fledge build: what this app's programs run (ADR 024).
gemfile = Gemfile

[Deckbuilder]
entry = gui/main.rb
identifier = com.example.Deckbuilder

[deckbuilder-cli]
entry = bin/cli
```

The launcher reads the section whose name is its own file name (less `.exe` on Windows), ignoring case, as the file systems do. Before, any file name ran the one `entry`; with sections, the name decides, and a program renamed by hand finds no section and exits with 66 (EX_NOINPUT), as it does when its entry is missing, naming the name it looked for. `gemfile` stays at the top: every program shares the project's gems. A section holds only `entry` and `identifier`; a file with both sections and an `entry` at the top is damaged, and exits with 70 (EX_SOFTWARE), as other damage does.

A project with no `programs`, or a build of one program (section 6), writes `fledge.cfg` as before, with no section, so the launcher runs it under any name as it always has. An embedded phone runtime reads the same file (ADR 012) and is always given one program.

The alternative, one launcher and an argument, fails on Windows and macOS for the reasons in Context. A launcher per program costs its size per program (6.3 MB in 0.1.0's `arm64-darwin` runtime, where it holds libruby, and tens of kilobytes on Windows, where Ruby is a DLL), which is small beside the runtime it saves.

### 4. The layout: one folder, one runtime, one project, one set of gems

`DIR/NAME-PLATFORM/` holds the runtime and `app/` once, and every program beside them:

- **Windows**: `Deckbuilder.exe` (the GUI launcher), `deckbuilder-cli.exe`, and `deckbuilder-tui.exe` (console launchers), each with its own name and icon in its version information (`Fledge::WindowsResources`), beside `fledge.cfg`, `app\`, and `ruby\`. Each program sets its own identifier as its AppUserModelID, as one program does today.
- **Linux**: `Deckbuilder`, `deckbuilder-cli`, and `deckbuilder-tui` beside `lib/` and `app/`, and the windowed program's `IDENTIFIER.desktop` and `share/icons/` (ADR 008, section 4).
- **macOS**, with a windowed program: everything is in its bundle, `Deckbuilder.app`, as Tauri puts every binary in one bundle; the console programs are copies of the launcher in `Contents/MacOS` beside the bundle's executable, where Apple puts a bundle's helper tools, so the bundle's signature seals them. Beside the bundle, the folder has a symbolic link for each console program, `deckbuilder-cli -> Deckbuilder.app/Contents/MacOS/deckbuilder-cli`, so a person runs it from the folder; the launcher resolves the link to the runtime it lives in (`runtime/launcher/darwin.c`). **macOS** with no windowed program is the Linux layout.

The app's `__dir__`, its project, and its gems are the same for every program, so files one program writes beside the project, or in a home folder, another reads, as the programs do when run with `ruby` from one checkout.

### 5. Installers: one, for the windowed program, holding every program

The installers ADR 009 and ADR 021 describe are written from the folder, as before, for the windowed program, with its identity: its name in the disk image, the setup program's shortcut and uninstall entry, and the AppImage's and `.deb`'s desktop entry. Each holds the whole folder, so every console program installs beside the windowed one, as Tauri's installers install every non-main binary: inside the bundle on macOS, in `%LOCALAPPDATA%\Programs\NAME` on Windows, and in `/usr/lib/IDENTIFIER` from a `.deb`. Nothing puts a console program on a `PATH`; that is the same "other story" ADR 009, section 1, left for console apps. An AppImage runs its windowed program; its console programs are reached through `--appimage-extract`.

One installer for the project, rather than one per program, because the project is one download whose programs share their files: a second installer would install the same runtime again.

### 6. `fledge build PATH` with `programs`

- **A folder** (the default, `.`) builds every program into one folder, as sections 3 to 5 lay it out. `programs` replaces ADR 005's rule that a folder means its gemspec's one executable or its `main.rb`.
- **A file one of the programs names** builds that program alone, as a project with no `programs` builds its one program: its folder, archive, and installers are named after the program, it has the program's name, kind, identifier, and icon and the project's other keys, and its `fledge.cfg` has no section. Cargo builds one of a package's binaries with `cargo build --bin NAME`, and Briefcase one of a project's apps with `-a NAME`; here the program's own path names it, as it always has. A project with two windowed apps builds each this way.
- **Any other file** is refused, listing the programs: `programs` is the project's statement of what it ships, and a file it does not name has no kind or identity of its own.

A phone (`fledge build ios`, `fledge build android`) builds one program: the one PATH names, or else the windowed program, or else the first.

### 7. Signing

`--sign` signs every program, as it signs every program and library now (ADR 016): on Windows signtool signs every PE file of the folder, every launcher copy among them; on macOS, codesign signs each console program in the bundle's `Contents/MacOS` before it signs the bundle, inside out, as Apple asks of nested code, and every Mach-O file of a folder with no bundle. Unsigned builds stay as they are: each launcher copy keeps the signature it arrives with, and the bundle's ad hoc signature seals every file in it.

### 8. Exit statuses and messages

`fledge build` exits as before: 0, 1 for a build that fails, and 2 for a usage error. A built program exits with its app's status, 66 when its entry or its section of `fledge.cfg` is missing, and 70 when the rest is broken. Every refusal names `fledge.yml` and the program, and says what to write instead:

- `fledge.yml: programs must be a list of at least one program, each a mapping such as - path: bin/cli`
- `fledge.yml: program 2 has no path, the program's file in the project, such as path: bin/cli`
- `fledge.yml: program 1's path, "../cli", must name a file in the project, with / between folders, such as path: bin/cli`
- `fledge.yml: the program bin/cli has 'paht', which Fledge does not know. A program knows path, name, kind, identifier, and icon.`
- `fledge.yml: the program bin/cli: kind must be console or windowed, not gui`
- `fledge.yml: a/cli and b/cli.rb are both named cli; give each its own`
- `fledge.yml: gui/main.rb and editor/main.rb are both windowed, and a project has one windowed program; build another on its own, with fledge build editor/main.rb`
- `fledge.yml: with programs, kind belongs to each program; move it into the program it describes`
- `fledge.yml lists the program bin/clli, but the project has no such file. List the program you run, such as path: bin/cli.`
- `bin/protocol is not one of the programs fledge.yml lists. Build the project, or one of gui/main.rb, bin/cli, bin/tui.`
- and from a renamed program, `renamed: this app is incomplete: ROOT/fledge.cfg has no program named renamed`, with 66.

Each names the full path of `fledge.yml`, as Config's other messages do.

## Consequences

- A project with several programs ships as one folder and one installer, and its programs share one runtime, one copy of the project, and one set of gems. A project with no `programs` builds exactly as before, with the same folder, `fledge.cfg`, and output.
- `fledge.cfg` has sections, which only launchers from this release read; a runtime from an older Fledge refuses a multi-program `fledge.cfg` as damaged, as older launchers refuse a key they do not know. Fledge builds with its own release's runtimes, so this is seen only with `FLEDGE_RUNTIME_DIR` pointing at old ones.
- A program renamed by hand in a multi-program folder no longer runs; a single program still does.
- `config.schema.json` describes `programs` and its rules, tested against Config as ADR 023 requires.
- `examples/programs` (a console program and a windowed one sharing a save) builds and delivers on every desktop platform; Delivery checks that both run from the one folder, share one `app/` and runtime, and that a save one writes the other reads.
- Not yet, and left until a developer asks: several windowed programs in one folder (section 2's cost); a console program on a `PATH` from an installer; an AppImage that runs a console program by the name it is called with (AppImage's runtime sets `ARGV0`); defaults for each program's keys from the top of `fledge.yml`.
