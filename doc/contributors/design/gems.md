# How fledge build Reads and Ships an App's Gems

This document says how `fledge build` turns a project's Gemfile and lockfile into the gems a desktop app ships: what it checks, which build of each gem it takes, where it fetches it, how it installs, compiles, and checks it, and what it writes so that the app's Bundler sets up the same gems. The developer's view, with the commands to run, is [Gems in a Fledge app](../../gems.md). Why an app runs the real Bundler is in `doc/contributors/design/launcher.md`, "The Bundler environment", and what ships of the project is in `doc/contributors/design/desktop-apps.md`, "The project and its name"; each section below gives the reasons for its own rules. Phones differ where noted; their extensions are in `doc/contributors/design/phone-projects.md`, "Gems with extensions".

The reference for every rule here is Bundler itself, at the version `Gemfile.lock` pins (Bundler 4.0.20; paths are in its `lib/bundler/`), and the RubyGems of the pinned Ruby (`lib/rubygems/`). Where Fledge does what Bundler does, it calls Bundler's own classes rather than restating them. Code adapted from Bundler sits in SPDX snippets in `lib/fledge/bundle.rb`, `lib/fledge/bundle/selection.rb`, `lib/fledge/git_gem.rb`, and `lib/fledge/git_checkout.rb`.

## Reading the Gemfile and lockfile

`Fledge::Bundle` reads the project's `Gemfile` (or `gems.rb`) and its lockfile (`Gemfile.lock`, or `gems.locked`) with `Bundler::Dsl` and `Bundler::Definition`, with `BUNDLE_GEMFILE` set to the project's Gemfile and Bundler's root reset to it for the read, then put back. Bundler reads a path gem's folder relative to its root, and Bundler's settings (a mirror, a login, the groups, build options) from the project's `.bundle/config`, so the root must be the project, not wherever `fledge build` runs.

The definition is read frozen, whatever the environment says (`Bundler.settings.temporary(frozen: true)`), and `ensure_equivalent_gemfile_and_lockfile` refuses a lockfile the Gemfile has moved past, in Bundler's own words. A definition Bundler may rewrite adds the computer's own platform, which is no more locked for the app than the lockfile says. A project with a Gemfile and no lockfile fails and says to run `bundle lock`. Bundler's message for an empty `CHECKSUMS` entry gets Fledge's advice appended: `bundle lock --add-checksums` fills an entry only for a build installed on this computer or one its server lists, so a gem that only `vendor/cache` holds needs its SHA-256 written by hand, as [Gems in a Fledge app](../../gems.md) shows.

## The lockfile's checks

For each target, before anything is fetched:

- **The lockfile locks the target.** A lockfile platform counts when it is `ruby`, when it is the generic form of the runtime's platform, or when the runtime's platform `===` it, as `Bundler::Definition#validate_platforms!` and `#current_platform_locked?` decide with the running Ruby's platform (`definition.rb`, lines 524 to 530 and 832 to 836). The runtime's platform is `Gem::Platform.new` of the `arch` in the runtime's `rbconfig.rb` (`Fledge::RuntimeContents#arch`), which is what the app's RubyGems and Bundler see on any computer: `arm64-darwin23` for rv-ruby's macOS build. So `arm64-darwin` and `arm64-darwin-23` fit it, and `arm64-darwin-24` does not; a Linux platform fits by its own name or its `-gnu` name. Otherwise the build fails with `Run bundle lock --add-platform PLATFORM`.
- **The Gemfile's `ruby`**, when it has one, must admit the runtime's Ruby, at the version "The runtime's Ruby version" gives (`Bundler::RubyVersion#diff`).
- **Every gem from a gem server has a checksum** in the lockfile's `CHECKSUMS` section, by the name the section gives it (`sqlite3 (2.10.2-arm64-darwin)`). A gem without one fails with `Run bundle lock --add-checksums`. Fledge pins every external input by SHA-256 (AGENTS.md), and an app's gems are Fledge's input here; the lockfile is where the developer pinned them.
- **The lockfile's Bundler has a checksum**, when the app ships it ("The lockfile's Bundler", below): `bundler (VERSION)` in `CHECKSUMS`. Without one the build fails, saying to run `gem install bundler -v VERSION` and then `bundle lock --add-checksums`, for the reason "The lockfile's Bundler" gives.
- **Every git gem is locked to a whole commit**, 40 or 64 hexadecimal digits. Nothing else pins it.
- **Every gem comes from a gem server, git, or a folder.** Any other source fails, naming it.

## The runtime's Ruby version

The Gemfile's `ruby`, each gem's `required_ruby_version`, and the choice among a gem's locked builds are judged against the runtime's Ruby as its own RubyGems and Bundler see it, which is `Fledge::RuntimeContents#ruby_version`. RubyGems' version of Ruby is `Gem.ruby_version`: `RUBY_VERSION`, and, when `RUBY_PATCHLEVEL` is -1, a dot and the name `RUBY_DESCRIPTION` gives the build after `RUBY_VERSION` (`rubygems.rb`, lines 965 to 979, at Ruby 4.1.0-preview1). Bundler's is the same (`Bundler::RubyVersion.system`, `ruby_version.rb`, lines 106 to 113, at Bundler 4.1.0.beta2). `bundle exec`, `bundler/setup`, and an app's Bundler compare the Gemfile's `ruby` with it at every start (`Bundler.setup`, `bundler.rb`, line 158, and `Definition#validate_ruby!`, `definition.rb`, lines 509 to 526), and a gem's `required_ruby_version` is compared with it by Bundler (`MatchMetadata#matches_current_ruby?`, `match_metadata.rb`, lines 9 to 11) and by RubyGems. Bundler reads the Gemfile's version with each `-` as a `.` (`RubyVersion#normalize_version`, `ruby_version.rb`, lines 117 to 122), so a `.ruby-version` of `4.1.0-preview1`, which `ruby file: ".ruby-version"` reads, asks for `4.1.0.preview1`.

So the runtimes of Ruby 4.1.0-preview1 are Ruby 4.1.0.preview1, and Windows', RubyInstaller's head build, is Ruby 4.1.0.dev. `RuntimeContents` makes the version from `rbconfig.rb`'s `MAJOR`, `MINOR`, `TEENY`, and `PATCHLEVEL` and the name in the runtime's `RUBY_DESCRIPTION` file, as `Gem.ruby_version` makes it, since `rbconfig.rb` records no such name (`doc/contributors/design/runtimes.md`, "The Ruby's description").

A Gemfile that asks for `4.1.0-preview1` therefore builds on macOS, Linux, iOS, and Android, as `bundle exec` accepts it on the preview, and fails on Windows ("Gemfile asks for Ruby 4.1.0.preview1, and Fledge's runtime for x64-mingw-ucrt is Ruby 4.1.0.dev."), where `bundle exec` on the head build refuses it too and the app's Bundler would not start. A Gemfile that asks for `4.1.0` fails on every runtime until Ruby 4.1.0 itself, since the app's Bundler would stop at its start with "Your Ruby version is 4.1.0.preview1, but your Gemfile specified 4.1.0"; a requirement such as `>= 4.1.0.a` admits both. Fledge first read the runtime's Ruby as `MAJOR.MINOR.TEENY` alone, 4.1.0, which refused the first Gemfile though Bundler accepts it, and built the second into an app that does not start.

The patch level is compared too, by some Bundlers. Every Bundler checked, 4.0.20, 4.0.22, and 4.1.0.beta1 to beta3, gives the Gemfile's `ruby` the `patchlevel:` it names, or else -1 when the first version it names is a prerelease, and gives the running Ruby `RUBY_PATCHLEVEL` (`RubyVersion#initialize`, `ruby_version.rb`, line 41, and `RubyVersion.system`, lines 108 to 115 at 4.0.22, 106 to 113 at 4.1.0.beta3; `RubyDsl#ruby`, `ruby_dsl.rb`, lines 9 to 27, the same at each). `RUBY_PATCHLEVEL` is -1 on a preview and on a build of Ruby's master, and 0 or more on a release. Bundler 4.0 then refuses a patch level that differs, -1 matching only -1 (`RubyVersion#diff` and `#matches?`, lines 99 to 100 and 126 to 133 at 4.0.22), and Bundler 4.1 compares none: `#diff` has no such clause from 4.1.0.beta1 on (lines 91 to 100 at beta3), and `Definition#validate_ruby!` no message for one (`definition.rb`, lines 509 to 526 at 4.1.0.beta2). So `ruby ">= 4.1.0.a", "< 4.2"` asks for patch level -1, and `ruby "< 4.2", ">= 4.1.0.a"` for none: both start on a preview under either Bundler, and on Ruby 4.1.0 itself only the second starts under Bundler 4.0.

`Fledge::Bundle#check_ruby` gives the runtime's Ruby its `rbconfig.rb`'s `PATCHLEVEL` (`RuntimeContents#patchlevel`), which is `RUBY_PATCHLEVEL`, and judges the patch level as the Bundler the app runs does ("The lockfile's Bundler", below; `Fledge::AppGems#for` passes its version, or the runtime's own), with Bundler 4.0's clause adapted, whatever Bundler runs `fledge build`. That Bundler, the developer's, still answers for the version and the engine, which every Bundler checked compares alike. Before, the runtime's patch level was left out, which Bundler reads as -1 for a prerelease version and as none for a release, so a runtime that records no `RUBY_DESCRIPTION`, whose version reads 4.1.0, refused `ruby ">= 4.1.0.a", "< 4.2"`, which Bundler 4.0 on that runtime, at patch level -1, accepts; and the verdict on a release followed the developer's Bundler, so `fledge build` under Bundler 4.1 would build that Gemfile into an app whose Bundler 4.0 stops at its start. Asking the app's Bundler itself would mean running the runtime's Ruby, which `fledge build` does not do for another platform's runtime.

## Groups

The app sets up the groups `bundle exec` would under the developer's own Bundler settings, and forces none out: `development` and `test` ship unless the developer's `without` names them. `Fledge::Bundle#read_groups` asks Bundler's `Definition#requested_groups` (the Gemfile's groups, less `without` and the optional groups, plus `with`; `definition.rb`, lines 1239 to 1243). The `with` and `without` come from every level Bundler reads: the project's `.bundle/config`, `BUNDLE_WITH` and `BUNDLE_WITHOUT`, and the developer's own.

A gem of a shipped group that has no build for the target fails the build, as Bundler refuses it on that platform at `bundle install`. When the gem comes from a group other than the default, the message names the way out: `bundle config set --local without GROUP`.

An optional group (`group :extras, optional: true`) ships when, and only when, `with` names it. The app's `.bundle/config` always carries `BUNDLE_WITHOUT` and `BUNDLE_WITH`, empty when the developer's settings name no group, so the app's Bundler, and any Ruby the app starts with `bundler/setup`, sets up exactly what was shipped, whatever the person's own `~/.bundle/config` says ("The app's .bundle/config", below).

This is what `bundle exec` sets up, and a program may require a development or test gem at run time, as some do with debug, dotenv, or rake as a library. Warbler leaves those groups out of every app (`bundle_without`, `lib/warbler/config.rb`, line 44, at ac050a9e), and so does Traveling Ruby's tutorial (`--without development`, `TUTORIAL-2.md`, lines 71 and 76, at 0eac139b), both for size; such a program would then raise a `LoadError` naming the gem to the person who runs the app, and decision 20 ranks size below code that just works. Tebako runs a plain `bundle install`, and so ships every group too (v2.8.78, `crates/tebako-cli/src/packager.rs`). Leaving out only a shipped group's gem that has no build for the target would bring the `LoadError` back for that gem, and the app's frozen Bundler would refuse to start without it. So which groups ship stays where Bundler keeps it, with the developer, and a developer who sets `without` gets the same `LoadError` under `bundle exec`. The cost is that every app carries its development and test gems unless `without` names them, and a development gem with an extension, such as debug, is compiled for every target, phones included.

## Choosing each gem's build

`Fledge::Bundle::Selection` walks the dependencies from the Gemfile's own, in the groups the app sets up, and their runtime dependencies (never `development` ones), leaving out Bundler itself. A Gemfile dependency is left out when its `platforms:` names no platform the target's CRuby is, as `Bundler::CurrentRuby` would answer on the runtime: `windows` (and its old names `mswin`, `mswin64`, `mingw`, `x64_mingw`) on Windows, `ruby` and `mri` elsewhere, never `jruby` or `truffleruby`, each with an optional version suffix such as `mri_40`.

For each gem it takes the build Bundler would set up on the runtime, with `Bundler::MatchPlatform.select_best_platform_match` for the runtime's platform and then for `ruby`, honoring the dependency's `force_ruby_platform`. When the gem locks only one candidate, that is it. When it locks more, the first whose `required_ruby_version` admits the runtime's Ruby wins, which falls back to the gem's source build when its precompiled build excludes the runtime's Ruby, as sqlite3 2.10.2's precompiled builds (`>= 3.2, < 4.1.dev`) exclude Ruby 4.1. That is what a frozen Bundler does: `LazySpecification#choose_compatible` skips a locked build whose metadata does not match the running Ruby (`MatchMetadata#matches_current_ruby?`), tries the local platform and then `ruby` ("Ruby platform is last since it requires compilation, but works when precompiled gems are incompatible"), and with none compatible keeps the locked platform's build (`lazy_specification.rb`, lines 137 to 152 and 192 to 216). Fledge keeps it too, and the build then fails naming it ("Checks that are not about licenses"). The chosen build's own locked dependencies are followed.

The lockfile does not record `required_ruby_version`, so Fledge reads it from the build's checksummed `.gem`, fetched only when a gem locks a build to fall back to (`Fledge::AppGems#required_ruby`). A compact index query would be a second, unpinned input.

A gem the lockfile does not lock, or locks no build of for the target, fails, saying to run `bundle lock` or `bundle lock --add-platform`.

On a phone (`Fledge::MobilePlatform`), the target is `ruby`: the lockfile must lock `ruby`, and every gem is its `ruby` build, as the app's Bundler runs with `force_ruby_platform` (`doc/contributors/design/phone-runtimes.md`, "Targets").

## The lockfile's Bundler

`bundle install` installs the Bundler a lockfile names under `BUNDLED WITH`, and `bundle exec`, `bundler/setup`, and every `bundle` command then switch to it from Ruby's own (`Bundler.auto_switch` and `Bundler::SelfManager#restart_with_locked_bundler_if_needed`, `bundler.rb` lines 172 to 174 and `bundler/self_manager.rb` lines 9 to 14, at Bundler 4.0.20). So the app ships that Bundler, and its launcher loads it (`doc/contributors/design/launcher.md`, "The Bundler environment").

With the runtime's own Bundler instead, an app runs a Bundler its developer never ran it with. On Ruby 4.1's preview, whose Bundler is 4.1.0.beta2, `examples/my_cool_app` then showed five differences from `bundle exec`: `$LOAD_PATH`, `$LOADED_FEATURES`, the installed gems, `ENV`, and a child's `ENV` (`doc/contributors/research/2026-11-09-ruby-4.1-spike.md`). Any lockfile another Bundler wrote meets the same on any Ruby, and since `bundle install` never moves `BUNDLED WITH` on its own, most name an older Bundler than the newest Ruby's. Two other answers were weighed. Refusing a lockfile whose `BUNDLED WITH` is not the runtime's Bundler would refuse most real lockfiles, and every app again each time the runtimes move to a newer Ruby. Keeping the runtime's Bundler, with the difference justified, is what Warbler does, warning that "the packed application will boot with the default bundler of the packed JRuby" (`lib/warbler/traits/bundler.rb`, lines 17 to 22 and 142 to 151, at jruby/warbler 3196d5f9). That leaves the surprise the maintainer's words rule out (`decisions.md`, 2026-11-02), and Warbler's reason, that switching restarts the process, which a servlet container or a jar cannot do, does not hold here: the launcher chooses which Bundler to require before any loads, so nothing restarts.

`Fledge::Bundle#bundler_for` chooses it as `SelfManager#find_restart_version` does (lines 190 to 200), with the runtime's Bundler (`RuntimeContents#gems`, the one `bundler-VERSION`) as the running one:

- Bundler's `version` setting, read from every level with Bundler's root at the project, is `system`: the runtime's Bundler.
- The setting is `lockfile`, its default: the `BUNDLED WITH` version, read as `LockfileParser.bundled_with` reads it. Any other value names the version itself. A lockfile without `BUNDLED WITH`, or a version that does not parse, keeps the runtime's.
- A development build's version (ending `.dev`), or the runtime's own version, keeps the runtime's (`#released?` and `#running?`).

The chosen Bundler is a `Fledge::LockedGem` of `bundler`, platform `ruby`, from `https://rubygems.org/`, where Bundler fetches it (`#remote_specs`), through the mirror and login Bundler's settings give that server, checked against `bundler (VERSION)` in `CHECKSUMS`. When its `required_ruby_version`, read from the checksummed `.gem`, excludes the runtime's Ruby, the app keeps the runtime's Bundler, as `bundle install` goes on with the Bundler that runs it when RubyGems.org has no build of the locked one for the running Ruby (`#install_and_restart_with`, lines 48 to 63). Otherwise `Fledge::AppGems#for` installs it with the app's gems ("Installing into the runtime's gem folder"), beside the runtime's own Bundler, whose `bundle` and `bundler` programs stay the runtime's ("Gem executables"), and `fledge.cfg` names its version as `bundler` (`Fledge::Assembly.launch_config`). `fledge build --from` keeps the key, as it keeps the lockfile (`Fledge::BuiltApp#bundler`).

The app's `.bundle/config` keeps `BUNDLE_VERSION: "system"`, so neither the app's Bundler nor one in a Ruby the app starts tries to switch again: the launcher has already chosen.

A lockfile with no checksum for its Bundler fails the build, saying what to run. Bundler writes that checksum from the `.gem` file of the Bundler that runs, in the gem cache; with no such file it keeps the entry already locked, if any; and it writes none for a `.dev` version or under `SKIP_BUNDLER_CHECKSUM` (`LockfileGenerator#bundler_checksum`, `lockfile_generator.rb`, lines 105 to 138 at Bundler 4.0.20, and lines 127 to 160 at 4.1.0.beta2). A Ruby's own Bundler is a default gem, which Ruby installs with no `.gem` file in its gem cache, so a lockfile that a Ruby's own Bundler wrote has no entry for it: Ruby 4.1.0-preview1's Bundler 4.1.0.beta2 writes `BUNDLED WITH 4.1.0.beta2` and no `bundler` line, and `bundle lock --add-checksums` adds none. The app ships that Bundler only where the runtime's own is another version, as on Windows, whose head build carries Bundler 4.1.0.beta3; on the runtimes of Ruby 4.1.0-preview1 it is the runtime's own, and the build asks for no checksum. `bundle install` installs the lockfile's Bundler only when the Bundler running it is another version, and so does nothing on the Ruby that wrote such a lockfile; `gem install bundler -v VERSION` installs it, with its `.gem`, on any Ruby, and `bundle lock --add-checksums` then writes the entry, with the SHA-256 RubyGems.org lists for that file. So the build's advice is those two commands. Two other answers were weighed. Taking the checksum from RubyGems.org's API during the build would check the file only against what the same server says, an input the developer never pinned. Keeping the runtime's Bundler when the lockfile has no checksum for its own would run the app with a Bundler that `bundle exec` does not run it with, the difference this section exists to avoid. A lockfile older than Bundler 2.6 has no checksums for its gems either. The launcher writes the Ruby that loads that Bundler from the version in `fledge.cfg`, so `config.c` takes only a version's characters there. A Bundler much older than the runtime's Ruby may not run on it, and the build cannot tell until the app runs; `bundle exec` fails the same way.

## Fetching a gem's file

`Fledge::GemFetcher` finds each gem's `.gem`, for any platform, in this order, and takes the first whose SHA-256 is the lockfile's:

1. the project's `vendor/cache` (`bundle cache --all-platforms` keeps every platform's there);
2. the `cache` folder of each folder on RubyGems' path;
3. Fledge's own cache, `gems/` beside its runtimes (`$XDG_CACHE_HOME/fledge/gems`, or `~/.cache/fledge/gems`).

Otherwise it downloads `REMOTE/gems/FILE` into its own cache through `Fledge::Download`, which takes the lock on the file, streams to a `.part` file, checks the SHA-256, and only then moves it into place, so builds at once download each gem once (`doc/contributors/design/runtimes.md`, "Download retries").

**Sources, mirrors, and logins.** `Fledge::Bundle::Sources` builds each gem's remote with `Bundler::Source::Rubygems::Remote`, which applies `Bundler.settings.mirror_for` (`bundle config mirror.URL`) and `credentials_for` (`bundle config HOST USER:PASSWORD`, `BUNDLE_HOST`, or a login in the Gemfile's source URL), the same two calls Bundler's fetcher makes, with Bundler's root at the project. `Fledge::LockedGem` keeps the address (with the mirror, without the login) and the login apart, so no message shows a password. The login goes by HTTP Basic authentication to that host and port only, never to another host a redirect leads to. A redirect from HTTPS to plain HTTP is refused. Fledge adds no `fallback_timeout` probe of its own: `mirror_for` runs Bundler's.

**What an answer means.** The advice differs, so the statuses are told apart:

- **404 or 410:** the server has no such file, whatever server it is. This happens when the lockfile was made from a `.gem` in `vendor/cache` or a gem folder since gone, or names a platform the gem's author never published. The build fails naming the gem, the server, the file, and the status, and says to put the file in the project's `vendor/cache` or lock the gem to the source that has it.
- **401:** a login, always: HTTP requires a server to ask for one with `WWW-Authenticate` (RFC 9110, section 15.5.2).
- **403:** read as Bundler reads it, a login the server will not accept (`Bundler::Fetcher::Downloader#fetch`, `fetcher/downloader.rb`, lines 62 to 66, `AuthenticationForbiddenError`), with one exception: a 403 to a request that carried no login, from a host in `GemFetcher::PUBLIC_SERVERS` (`rubygems.org`), means the file is missing. RubyGems.org needs no login for any file it has, and its storage answers 403 `AccessDenied` for a name it does not hold. Bundler never meets that answer, because it fetches only files its index lists; Fledge fetches a locked gem's file for each platform it builds for. A private server's 403 without a login keeps the login advice, as Bundler gives it. A mirror of RubyGems.org is a server of its own, with its own host, so its 403 gets the login advice.
- **401 and 403 advice:** with no login, set one as Bundler reads it (`bundle config set --local HOST USER:PASSWORD`, or `BUNDLE_HOST` with Bundler's escaping); with one, Bundler's login for the host was refused, and `bundle config get HOST` shows it.
- **408, 429, a 5xx, or a connection that fails or breaks off:** asked again after 2, 4, and 8 seconds, four tries in all, as Bundler's default `BUNDLE_RETRY` of 3 makes (`Download::WAITS`), then the build fails. A missing file, a refusal, and a checksum mismatch fail at once. The retry rules are shared with runtime downloads: `doc/contributors/design/runtimes.md`, "Download retries".

## Installing into the runtime's gem folder

A gem the runtime already has at the same full name is the runtime's, already audited, and is not added again (`RuntimeContents#gems`). Every other gem from a gem server is installed into the runtime's own gem folder, `lib/ruby/gems/API` (`ruby/lib/ruby/gems/API` on Windows), where API is the Ruby's ABI version (`4.1.0+5` for Ruby 4.1.0-preview1, `4.1.0+6` for the Windows head build). Bundler's `path.system` setting makes that folder the bundle's, beside Ruby's default and bundled gems.

`Fledge::GemPackage` verifies the file as `Gem::Package#verify` does, then lays it out as `Gem::Installer#install` would (`rubygems/installer.rb`, lines 274 to 325 at Ruby 4.1.0-preview1), as entries in the app rather than by running the installer:

- the gem's files in `gems/FULL_NAME/` (`Gem::Package#extract_files`);
- its specification in `specifications/` (`#write_spec`);
- the `.gem` itself in `cache/` (`#write_cache_file`);
- a loader in `plugins/` for each `rubygems_plugin` file in its require paths (`#generate_plugins`).

Executables are written apart, by the runtime's own RubyGems ("Gem executables"). Each gem ships with all of its own files, its license files among them ("Checks that are not about licenses").

## RubyGems plugin loaders

A gem with a RubyGems plugin gets a loader named for the gem in the gem folder's `plugins/`. When the runtime already has a loader of that name for another version of the gem, the runtime's stays, and the app's gem is installed beside it with no loader of its own (`Fledge::AppGems#for` drops any entry at a path in `RuntimeContents#plugins`). The case is common: irb asks for rdoc, many Gemfiles (Rails's among them) lock an rdoc newer than the runtime's, and the runtime has `rdoc_plugin.rb`.

Do not "fix" this by replacing the runtime's file. RubyGems' own rule is that installing a gem writes its loader over any other version's (`Gem::Installer#generate_plugins`, `installer_uninstaller_utils.rb`, `regenerate_plugins_for`, at Ruby 4.1.0-preview1), but a loader matters only to a command that installs gems (`gem install`, and the hooks a `rubygems_plugin` registers), an app never installs, and a build never overwrites a file of the runtime's.

## Gem executables

Under `bundle exec` the bundle's `bin` folder is first on `PATH`, with every gem's wrapper in it. A built app has no Ruby on the person's computer (ADR 081), so a wrapper that says `#!/usr/bin/env ruby` would help no one. The runtime's own wrappers do: RubyGems, built relocatable, writes `bindir="${0%/*}"` and `exec "$ruby" "-x" "$0"`, with `ruby` the `ruby` beside the wrapper when there is one (`Gem::Installer#bash_prolog_script`, `installer.rb`, lines 1039 to 1054 at Ruby 4.1.0-preview1) on macOS and Linux, and on Windows a `.bat` that runs the `ruby.exe` beside it (`#windows_stub_script`, line 802).

So the runtime's own Ruby writes the wrappers of every gem the app ships that has executables (`NativeBuild#binstubs`, its `STUBS` script), as `gem install` would: for each, a copy with its extensions taken out (they are compiled elsewhere), packed as `gem build` packs it, under `Gem::SilentUI`, and installed into a gem folder of its own with the unpacked runtime's bin folder as its bin folder (`Gem.default_bindir`). `Gem.ruby` is set to `/usr/bin/env ruby` for that run, so the interpreter line after the prolog, which `ruby -x` skips, is the one the runtime's own wrappers have, with no path of the build's computer. The wrappers ship in the runtime's `bin/` (`ruby/bin` on Windows), except a name the runtime already has there (`RuntimeContents#binaries`), whose wrapper finds whichever version of its gem the app's Bundler activates. Gems from a server, from git, and from a folder are all written this way, except the project's own gem, whose executable is the program the app runs. An Android app's are written by `fledge build` itself, with the text the phone's RubyGems writes and no Ruby run (`Fledge::GemWrapper`), since an Android build has no desktop runtime at hand, and the project keeps them apart from the links Android runs (`doc/contributors/design/phone-runtimes.md`, "Gem commands on Android"); iOS lets no app run one, and an iOS app gets none.

A program runs a wrapper by its name, as `system("rake")` does, since the launcher puts the runtime's `bin/` (`ruby/bin` on Windows) first on the app's `PATH`, as a developer's shell has the bin folder of the Ruby they run (`doc/contributors/design/launcher.md`, "The app's Ruby on PATH"); by its path, `File.join(Gem.bindir, NAME)` (`NAME.bat` on Windows); or the executable by `Gem.bin_path`, which never needed the wrapper. Bundler's own `PATH` entry in the app names `lib/ruby/gems/API/bin`, which does not exist, because a relocatable wrapper finds its Ruby beside itself and one there would not; the runtime's `bin/` after it holds them all. Inside the app's bundle, a wrapper runs the runtime's `ruby` with `bundler/setup` in `RUBYOPT`, so `rake` is the version the lockfile locks, as under `bundle exec`; inside `Bundler.with_unbundled_env` the runtime's `bin/` is still first, as the developer's Ruby is under `bundle exec`, and a wrapper runs the runtime's gems without the bundle. The parity check's probe runs rake each of these ways.

Writing executables unpacks the runtime and runs the runtime's Ruby once, even when nothing is compiled.

## Git gems

A git gem (`Fledge::GitGem`) is its repository, the locked commit, the glob its gemspecs are found by, what the Gemfile asked for (a tag, branch, or ref), and whether it asked for submodules.

`Fledge::GitCheckout` keeps a bare clone of each repository in Fledge's cache, `git/` beside its runtimes, named for the repository and a hash of its URI. It fetches only when the locked commit is missing (every branch and tag, then the commit itself, which a server may serve though no branch holds it), and refuses a commit the repository does not hold. It clones the cache into the build's work folder, checks out the commit detached, runs `git submodule update --init --recursive` when the Gemfile says `submodules: true` (as `Bundler::Source::Git::GitProxy#copy_to` does after its `git reset --hard`; without the option submodules stay out, as Bundler leaves them), and then evaluates every gemspec the glob finds and writes it back as `spec.to_ruby`, as `Bundler::Source::Git#serialize_gemspecs_in` does, so a gemspec that runs `git ls-files` loads with no git. Git runs with `GIT_DIR`, `GIT_WORK_TREE`, and `GIT_INDEX_FILE` cleared and `GIT_TERMINAL_PROMPT=0`. Credentials for a git gem or a submodule are git's own (its credential helper), as they are for Bundler. One checkout serves every gem the lockfile takes from that repository at that commit.

`Fledge::GitPackage` ships each locked gem's own folder of the checkout, the one its gemspec is in, less git's files (`.git`, and each submodule's `.git` file), where Bundler keeps it: `GEM_DIR/bundler/gems/BASE-SHORTREF/FOLDER` (`Bundler::Source::Git#install_path` and `#base_name`, with the first 12 digits of the commit). It refuses a gemspec whose version is not the lockfile's. A gem whose gemspec is at the repository's top ships the whole checkout. The app's frozen Bundler finds each gem there by its gemspec, without git; `GitProxy#installed_to?` counts a checkout installed whatever its `.git` holds. The rest of the repository stays behind, though `bundle exec` would find it in its own checkout: a repository holds more than its gems (Ferro's holds its own tooling, and symbolic links a Windows `.zip` cannot hold), and Bundler finds a gem by its gemspec, in its folder, alone.

## Path gems

A gem from a folder (`path:`, or the Gemfile's `gemspec` line) is one of:

- **Inside the project, with no extension and no executable**, or the project's own gem with no extension: it ships as part of the project, in `app/`, with nothing more.
- **Inside the project, with an executable or an extension:** a `Fledge::PathGem` at its folder in `app/`. Its executables are written ("Gem executables"); its extension is compiled, and what the build wrote that ships ("What a compiled gem ships") replaces the project's own files there (`Fledge::AppGems#app_files`, which must therefore be asked after `#for`).
- **Outside the project:** shipped in Bundler's own place for a copy of it. `bundle cache --all` copies such a gem to `vendor/cache/NAME` (`Source::Path#cache`), and a Bundler that finds that folder uses it in place of the original path, even when the original is gone (`#specs` and `#has_app_cache?`). Fledge ships the gem's whole folder, less git's files, with its gemspecs evaluated as a git gem's are, at `app/vendor/cache/NAME`, where NAME is the last part of the path (`#app_cache_dirname`). It ships from the developer's `vendor/cache/NAME` when they have made that copy, since that is what `bundle exec` loads, and from the original path otherwise. A path whose last part is `.` or `..` names no such folder and is refused; so is a folder that is not there. The project's own `vendor/cache` still stays out of the app, so only path gems' folders arrive there.

`Fledge::PathPackage` reads the gemspec named for the gem among those the glob finds (Bundler's `{,*,*/*}.gemspec` by default), and refuses a folder with none, or one of another version than the lockfile's.

## Compiling a gem

A gem whose chosen build has an extension still to compile (a `ruby`-platform gem with `extensions`, a git gem, or a path gem whose gemspec names extensions) is compiled by `Fledge::NativeBuild`, for the platform Fledge runs on, which is the only platform it builds for. A precompiled build that fits always wins over compiling ("Choosing each gem's build"); a gem compiles when it publishes no build for the target, when its precompiled build excludes the runtime's Ruby, or when the Gemfile asks for its source with `force_ruby_platform`, as `examples/nokogiri_app` does.

Compiling fills the gaps precompiled builds leave. Many gems publish no build for every platform: Tokra compiles its Rust extension with rb-sys when it is installed, Ferro's gems are consumed from git tags, and redcarpet and many C gems publish only their source. Bundler never compiles a path gem's extension, so `bundle exec` loads whatever the developer last compiled there. A Gemfile that installs with `bundle install` should ship, since the app's code stays as it is (`decisions.md`, 2026-10-26, decisions 9 and 20). An extension must suit the Ruby that loads it, its headers, `RbConfig`, and ABI, and in an app that is the runtime's Ruby, so compiling with the developer's own Ruby, or shipping what they last compiled, could make a file the runtime's Ruby does not load. Refusing such gems, as Fledge first did, refused Gemfiles that install everywhere else. Cross-compiling for each target, as rake-compiler-dock does, needs a toolchain and a Ruby per target, and each platform's app is built on that platform with its own tools (`decisions.md`, 2026-10-28; ADR 010); the maintainer's concern was "adding a lot of code, complexity, and surface area for bugs re: cross-compiling" (2026-11-04, question D). What compiling costs: a compiler on each platform that builds such an app ("The toolchain and the oldest systems"); a build only as reproducible as the developer's toolchain, since the lockfile pins the gems and crates but not the compiler; and a path gem's compiled file in the app that differs from the one `bundle exec` loads on the developer's computer ("What a compiled gem ships").

The build's work folder is a temporary folder in `Dir.tmpdir`, which `fledge build` removes when it is done, named by each of its folders' long names (`Fledge::LongPath`). Windows writes `TMP` with the 8.3 short name of a user folder whose name is no 8.3 name (`C:\Users\RUNNER~1` for `runneradmin`), and `Dir.tmpdir`'s `File.expand_path` makes only the last folder's name long (`replace_to_long_name` in Ruby's `win32/file.c`, lines 145 to 150 and 563 to 567, at `0e25874222`). mini_portile2, which nokogiri's `extconf.rb` uses, unpacks a `.tar.xz` with `xzcat FILE | tar xf - -C DIR` through cmd.exe, each path escaped by `Shellwords` (`mini_portile.rb`, lines 561 to 570, at 2.8.9), and cmd.exe reads the escaped `\~` as part of a name, so `xzcat` finds no file, `tar` unpacks nothing and succeeds, and the build fails at its next step. Ruby has no call for Windows' `GetLongPathNameW`; `File.absolute_path` names the last folder of what it returns by its long name, so `LongPath` applies it one folder at a time from the root.

`NativeBuild::RuntimeRuby` unpacks the target's runtime, and nothing else, into the build's work folder. The runtime holds what an extension build reads of Ruby (`doc/contributors/design/runtimes.md`, "What a runtime keeps"): its headers, and the library extension builds link against, the static libruby on macOS and Linux, which mkmf links the test programs of `have_func` and the rest against (`mkmf.rb`, line 552, at Ruby 4.1.0-preview1; an extension of a static Ruby links no libruby itself, lines 2790 and 2804 to 2806), and the import library of Ruby's DLL on Windows.

The runtime's own Ruby (`bin/ruby`, or `ruby\bin\ruby.exe`) runs `NativeBuild::SCRIPT` on a plan:

- a gem from a server is installed as RubyGems installs one, `Gem::Installer.at(...).install`, with its build options, `ignore_dependencies`, and no documents, into the build's own gem folder;
- a git gem's or path gem's extensions are built in a copy of its checkout at `bundler/gems/SCOPE` in that folder, with `Gem::Ext::Builder#build_extensions` and the specification's `extension_dir` set as Bundler's `Gem::Specification#extension_dir` would set it (`bundler/gems/extensions/PLATFORM/ABI/` and the scope and folder joined with `-`, `bundler/rubygems_ext.rb`, lines 226 to 236). A path gem is copied from the files its gemspec lists, as `gem build` and `gem install` would see them.

So the headers, `RbConfig`, compiler flags, `Gem::Platform.local`, and `Gem.extension_api_version` are the runtime's (`4.1.0+5-static` for rv-ruby's static Ruby, `4.1.0+6` for RubyInstaller's), and the extension lands where the app's RubyGems and Bundler look. The developer's Ruby compiles nothing.

**Order.** Every gem with an extension is installed after the gems it depends on that come from a gem server, which its `extconf.rb` may require (rb_sys and its rake-compiler-dock for an rb-sys gem, mini_portile2 for nokogiri); those are installed into the build's gem folder first, from the lockfile's own files.

**Environment.** The script, and the one that writes the gems' executables ("Gem executables"), run with the caller's environment less every variable the launcher hides from an app's boot (`RUBY*`, `GEM_*`, `GEMRC`, `BUNDLE_*`, `BUNDLER_*`, `RI_FORCE_PATH_FOR_DLL`; `NativeBuild::SCRUBBED`, after `runtime/launcher/scrub.c`), so that `bundle exec fledge build` cannot load the developer's Bundler into it, with `GEM_HOME` naming the build's gem folder and `GEM_PATH` naming it followed by the path separator, with `RUBYGEMS_USE_PSYCH` set to `true` (below), and on macOS with `MACOSX_DEPLOYMENT_TARGET` set to the runtime's oldest macOS. On Windows the script first runs `RubyInstaller::Runtime.enable_msys_apps(for_gem_install: true)`, as RubyInstaller's own `operating_system.rb` does in its `Gem.pre_install` hook, which finds MSYS2 by `MSYS2_PATH`, beside Ruby, at `C:\msys64`, in the registry, or on `PATH`; the runtime keeps RubyInstaller's Ruby library for this. The compiler's output goes to standard error. A gem that fails to compile fails the build: the script rescues `Gem::Ext::BuildError` and prints its message, which holds the build's output and where its logs are, as `gem install` does, then writes the gem's full name to the result and exits, so that Fledge's last line names the gem ("gem rugged-1.9.6's extension did not compile for arm64-darwin; the compiler's output is above"). Left to escape, the error printed Ruby's own report of an uncaught exception, a backtrace through RubyGems and the script, which no developer needs and which hid the gem's own message among it.

RubyGems reads a `GEM_PATH` that ends in the path separator as that path followed by its default one (`Gem::PathSupport#split_gem_path`, `path_support.rb`, lines 46 to 68, at RubyGems 4.1.0.beta2), which for the runtime's Ruby is the runtime's own gem folder (`runtime/rubygems/operating_system.rb`). So the build finds the lockfile's gems first and then the runtime's, as `gem install` on the runtime's Ruby finds them. A Rakefile needs that: `Gem::Ext::RakeBuilder` runs the rake `Gem.bin_path` finds, and the rake on `PATH` when it finds none (`rake_builder.rb`, lines 22 to 35). A lockfile that locks no rake, or the runtime's own version of it, adds none to the build's gem folder ("Installing into the runtime's gem folder"), and with `GEM_PATH` naming that folder alone the build ran whatever `rake` the developer's `PATH` held, under the developer's Ruby, where it found no rake gem in the build's gem folder and failed.

RubyGems 4.1 (4.1.0.beta2 and 4.1.0.beta3 alike) reads a packed gem's metadata with its own YAML parser, `Gem::YAMLSerializer`, unless `Gem.use_psych?`, and that parser keeps the encoding of the text it is given, which is BINARY: `Gem::Package#load_spec_from_metadata` opens `metadata.gz` with `external_encoding: Encoding::UTF_8`, but `#limit_read` reads it with `IO#read` and a length, which returns BINARY whatever the stream's encoding (`package.rb`, lines 631 to 641 and 926 to 930, at 4.1.0.beta2). So every name in a packed gem's specification, its `name`, `file_name`, and `executables`, is a BINARY string, where RubyGems 4.0, which read the same text with Psych, gave UTF-8. Three things failed for it. `Gem::Installer#generate_bin` joins an executable named outside ASCII to a bin folder named outside ASCII, which raises `Encoding::CompatibilityError` on every system. JSON writes no BINARY string outside ASCII into the scripts' result, so a gem whose executable is named `日本` failed every build. And on Windows `File.expand_path` reads a BINARY name, and the current folder it expands against, in code page 1252 whatever the system's is (`win32/file.c`, `code_page`), so the executables script's path of the gem it packs in a temporary folder named `Jürgen 日本` came out as `J\xFCrgen ??`, which Windows cannot open: a person whose account's name is outside ASCII, whose temporary folder is under it, could build no app whose gems have executables, and Bundler has two. `RUBYGEMS_USE_PSYCH=true` has RubyGems read metadata with Psych, as 4.0 did, which gives UTF-8; it still falls back to its own parser for metadata that is not valid UTF-8 (`Gem::SafeYAML.safe_load`). Psych is in every desktop runtime's Ruby, which is the only Ruby these scripts run on, a phone build's host gems included (`MobileExtensions` builds them with `NativeBuild` and the desktop runtime): the record of what the license audit read of each runtime lists the psych gem (`runtime/audited.yml`), and the audit accounts for its extension with libyaml compiled in (`runtime/licenses.yml`, `libyaml`). Nothing else the build keeps changes with the switch: `Gem.use_psych?` decides only how RubyGems reads YAML through `Gem::SafeYAML` (a gem's metadata and `checksums.yaml.gz`) and how it writes a gem's `metadata.gz` and `checksums.yaml.gz` (`Specification#to_yaml`, `Package#add_checksums`), which only the executables script's repacked copy has and nothing ships, while `Gem::Installer` writes the installed specification as Ruby (`to_ruby_for_cache`) and the gemrc is read with RubyGems' own parser either way (`rubygems.rb`, `load_yaml`, and its callers, at 4.1.0.beta2). A built app's environment does not carry the variable. An app that unpacks a `.gem` itself at run time, with `Gem::Package` or `gem install`, meets the same BINARY names, as it would under `ruby main.rb` on Ruby 4.1, so that is no difference from Ruby's. Relabeling each name in Fledge's scripts would leave RubyGems' own `generate_bin` raising, and patching `limit_read` would be patching a private method. Under code page 1252 on Windows 11, `NativeBuildTest` builds and runs an app whose gem has an executable named `日本`, reading a file named `日本語.txt`, in a temporary folder named `日本`, and one whose gem's executable is ASCII in a temporary folder named `Jürgen 日本`; both failed before. The report for RubyGems is drafted in `doc/contributors/drafts/rubygems-binary-spec-names.md`; the variable can go once the runtimes carry a RubyGems that gives UTF-8 names.

## The toolchain and the oldest systems

The compiler is the developer's: Xcode's command line tools on macOS, a C compiler and make on Linux, MSYS2's UCRT64 toolchain on Windows, and cargo for a Rust extension. A Rust extension for RubyInstaller's Ruby takes Rust's GNU target, as rb-sys requires, and bindgen needs a libclang (`LIBCLANG_PATH` and `BINDGEN_EXTRA_CLANG_ARGS` on Windows, as Ferro's CI and Fledge's set them).

A compiler targets the computer it runs on unless told otherwise, and a runtime runs on older ones. `MACOSX_DEPLOYMENT_TARGET`, which clang and rustc both read, aims macOS builds at the runtime's oldest macOS. `NativeBuild::Floors` then reads every Mach-O and ELF file a build wrote for the platform's processor (a file for another never loads in the app: "A file for another processor") and fails one built for a newer macOS than the platform's oldest (its `LC_BUILD_VERSION`) or needing a newer glibc than the floor (its newest `GLIBC_` symbol version, as auditwheel reads it), saying to keep the deployment target or to build on a Linux with the floor's glibc. The floors are `Fledge::Platform::MACOS_MINIMUM` and `GLIBC_MINIMUM` (`decisions.md`, 2026-10-26, decision 7, for glibc); musl Linux has no glibc floor to check. The release policy for floors is in `doc/contributors/design/releases.md`.

## What a compiled gem ships

`Fledge::CompiledGem` ships:

- what the gem's package holds: a `.gem`'s files, specification, and cache copy, as for a precompiled gem; a git gem's folder; a path gem's folder or files;
- every file the build left in the gem's folder, at its path (`NativeBuild::BuiltFiles.of`): of those, the ones the package lacks, and the ones whose bytes differ from the package's (a path gem's own copy, compiled by its developer for their Ruby, is replaced);
- its extensions folder, with `gem.build_complete`, without `gem_make.out` and `mkmf.log`; without `gem.build_complete`, RubyGems and Bundler take the gem as not yet installed;
- `build_info/FULL_NAME.info`, when it was built with options (`Gem::Installer#write_build_info_file`, which `gem pristine` reads).

Why everything the build left ships. RubyGems leaves a gem's folder as its build left it, and so does `bundle install`, which installs a gem from a server with the same `Gem::Installer`. For an `extconf.rb`, RubyGems runs `make` with the install target pointed at a temporary folder, copies what was installed there into the gem's first require path and its extensions folder, then runs `make clean` and removes the temporary folder (`Gem::Ext::ExtConfBuilder.build`, `ext_conf_builder.rb`, lines 15 to 67, at RubyGems 4.1.0.beta2). mkmf's `clean` removes the extension, its objects, `mkmf.log`, and whatever the `extconf.rb` added to `CLEANFILES`, and leaves the `Makefile`, which only `distclean` removes (`mkmf.rb`, lines 2810 and 2811, 2532 and 2533, and 3009 to 3018, at Ruby 4.1.0-preview1); rb-sys's Makefile removes its Cargo target folder after its install when RubyGems runs it (`rb_sys/mkmf.rb`, lines 108 to 149, at rb_sys 0.9.130, with `SOURCE_DATE_EPOCH`, which `Gem::Ext::Builder.run` sets, `builder.rb`, line 108). For a Rakefile, or an `mkrf_conf` script and the Rakefile it writes, RubyGems runs rake in the extension's folder with `RUBYARCHDIR` and `RUBYLIBDIR` naming the extensions folder, and leaves whatever rake wrote, wherever it wrote it, objects included (`Gem::Ext::RakeBuilder.build`, `rake_builder.rb`, lines 10 to 38). Beyond that, `Gem::Ext::Builder#build_extension` removes only the build's logs (`builder.rb`, lines 255 to 260). So under `bundle exec` a gem's Ruby may read, by its path, any file its build left, and one that does fails in an app that lacks it, though nothing at build time said so (AGENTS.md, Design precedence 2). Gems whose Rakefile builds a library for ffi do: ffi-compiler's `CompileTask` writes it to `ext/ARCH-OS/` beside the Rakefile and ignores `RUBYARCHDIR`, and its `FFI::Compiler::Loader.find` finds it there for `ffi_lib` (ffi-compiler 1.4.3, `compile_task.rb`, lines 124 to 132, and `loader.rb`, lines 8 to 35), as scrypt 3.1.0 (`lib/scrypt/scrypt_ext.rb`, line 11) and llhttp-ffi 0.5.1 (`lib/llhttp.rb`, line 13) use it; rdkafka 0.31.0's Rakefile moves librdkafka to `ext/`, where its `ffi_lib` opens it by path (`ext/Rakefile`, lines 52 and 53, and `lib/rdkafka/bindings.rb`, line 29). So may an `extconf.rb` that generates data beside the gem's root. `test/integration/native_build_test.rb` builds a gem whose Rakefile, and one whose `extconf.rb`, leaves its library outside the require paths, and a path gem whose `extconf.rb` writes `data/table.txt`, and runs each app. A phone's app builds each gem once for each of its targets, and carries of what those builds left only the files they left alike and no compiled code (`doc/contributors/design/phone-projects.md`, "Files a gem's build leaves").

The checks read less than ships. The linkage check and the floors check read what of the build's files Ruby may load (`NativeBuild::BuiltFiles.loaded`): every file in the gem's require paths, and each shared library elsewhere, which is a file named as Ruby's `DLEXT` names an extension (`.so`, `.bundle`, `.dll`) or as ffi's `LIBSUFFIX` names a library (`.so`, `.dylib`, `.dll`), with any version numbers after `.so`, and not inside a `.dSYM` folder of debug symbols. A library is named by its file's suffix wherever Ruby, ffi, or fiddle opens one. The rest of a build tree, its objects and any program it linked, is never loaded, and judging it would refuse apps that run: a program linked against glibc 2.34 or later needs that glibc's `__libc_start_main`, which a shared library does not, and a library's build may link its own tools against libraries the app does not carry. This is the rule "What the check reads of a git or path gem" follows for a gem's own files.

Three other answers were weighed. Shipping only the files in the require paths and the shared libraries, as Fledge did from 0.15.0, left out the rest because no Ruby seemed to read it, but a gem whose Ruby read data its build wrote, outside its require paths, raised `ENOENT` in the app where `bundle exec` worked. Leaving out a list of build intermediates (objects, Makefiles, `extconf.h`, a build tree) would be Fledge's own guess at what no gem reads, where RubyGems already decides what a build leaves, by its `make clean` and by the gem's own build. Asking each gem which files it loads would need a recipe per gem, which "Compiling a gem" already turns down for builds. What it costs: an app carries what `gem install` leaves, so a gem whose build leaves a build tree adds it (libusb 0.8.0's mini_portile2 build of libusb-1.0 leaves its build in the gem's folder and its installed copy in the gem's `ports`: `ext/extconf.rb`, lines 64 to 98, and `lib/libusb/libusb_recipe.rb`, line 13), and the Makefiles and other files a build leaves hold the paths of the build's work folder, which on Windows is under the developer's user folder.

## Build options

`bundle config build.NAME` at any level Bundler reads (the project's `.bundle/config`, `BUNDLE_BUILD__NAME`, or the developer's own) reaches the gem's `extconf.rb`, split as a shell would, as `Bundler::GemInstaller#spec_settings` splits it (`Fledge::Bundle#build_args`). A project that needs an option to build a gem the way it should ship says so as it already would for `bundle install`. `examples/nokogiri_app` keeps `build.nokogiri --disable-xml2-legacy` in its `.bundle/config`, so that its libxml2, built from source on a Mac, links none of the build computer's own libraries (Homebrew's `liblzma`, which the linkage check refuses). nokogiri built from source compiles in libxml2, libxslt, and libgumbo; on a Mac it loads macOS's own iconv, and on Windows its `extconf.rb` builds GNU libiconv and links it in statically, which ships ("Checks that are not about licenses"). ffi is the other one a developer meets: its `extconf.rb` links a libffi it finds on the computer (`pkg_config("libffi")`, then `ffi.h` and `-lffi`, `ext/ffi_c/extconf.rb` lines 7 to 26 at ffi 1.17.4), the same on every system, and the linkage check refuses the result as it does any library; `build.ffi --disable-system-libffi` makes ffi build the libffi it carries. The refusal does not name ffi, for Fledge refuses a gem only when it would not run where the app goes and holds no list of gems and their options to keep true; `doc/gems.md`, "A gem that links a library of your computer", names ffi and the command, which was run with `bundle config` and shown to write `BUNDLE_BUILD__FFI: "--disable-system-libffi"`. What a Mac or a Windows computer finds was read in the code and not run.

## The app's .bundle/config and gemspecs

`Fledge::Bundle#app_files` writes what the app's `app/` folder holds in place of the project's own files:

- **`.bundle/config`**, Warbler's settings for a packed app (`Fledge::Bundle::SETTINGS`; `lib/warbler/traits/bundler.rb`, lines 17 to 32, at jruby/warbler 3196d5f9): `BUNDLE_VERSION: "system"` (never switch to another Bundler at run time, since the launcher already loads the one the lockfile names: "The lockfile's Bundler"), `BUNDLE_FROZEN: "true"` (refuse a Gemfile that moved past its lockfile, and never rewrite or touch the lockfile, so an app in a read-only folder starts; the launcher holds it only while Bundler sets the app up, so the program's `Bundler.frozen_bundle?` is nil, as under `bundle exec`, until something makes Bundler's settings again from this file: `doc/contributors/design/launcher.md`, "The Bundler environment"), `BUNDLE_PATH__SYSTEM: "true"` (the gems are in Ruby's own gem folder), `BUNDLE_AUTO_INSTALL: "false"`, then `BUNDLE_WITHOUT` and `BUNDLE_WITH`, always written, an empty list included, since Bundler takes an empty string at this level as a value and so never reaches the person's `without` or `with` ("Groups"). A phone's app adds `BUNDLE_FORCE_RUBY_PLATFORM: "true"`. This is the local level of Bundler's settings, which wins over every other (`Settings#configs`), in any Ruby the app starts. In the app itself the launcher hands Bundler these settings as `BUNDLE_` variables during its setup, and `BUNDLE_APP_CONFIG` and `BUNDLE_USER_CONFIG` point at an empty `.bundle/none`, so Bundler reads no settings file and the person's `~/.bundle/config` is never read (`doc/contributors/design/launcher.md`).
- **Each gemspec of the project's own gems** (the root's, and path gems' inside the root), evaluated now and written as `spec.to_ruby`, as Bundler caches a git gem's, so a gemspec that runs `git ls-files` needs no git where the app runs. The shipped gemspec starts with a `require_relative` line for each project file its evaluation loads (`lib/my_cool_app/version.rb`, say), in load order, so the app's Bundler loads them at every start, as `bundle exec` does (`Fledge::Bundle#with_requires`).

The developer's own `.bundle` folder, `vendor/bundle`, and `vendor/cache` never ship (`doc/contributors/design/desktop-apps.md`, "The project and its name").

## binding.irb and force_activate

A frozen bundle refuses one thing an unfrozen one allows: a bundled gem the lockfile does not lock, activated for a moment. `binding.irb` in an app whose Gemfile does not name irb fails to require it, and Ruby's `prelude.rb` then calls `Gem::BUNDLED_GEMS.force_activate("irb")`, which sets up the Gemfile's gems and irb as a temporary bundle it never writes to the lockfile (`Definition.no_lock`; `prelude.rb`, lines 9 to 11, and `bundled_gems.rb`, lines 240 to 293, at Ruby 4.1.0-preview1). Frozen, Bundler refuses it ("You have added to the Gemfile: * irb", naming `Gemfile.lock`) and would resolve only the lockfile's gems. A developer's bundle is not frozen, so `bundle exec` works; `bundle exec` in a bundle the developer froze fails the same way.

Fledge's RubyGems defaults (`runtime/rubygems/operating_system.rb`, which RubyGems loads for whoever packages Ruby) prepend to `Gem::BUNDLED_GEMS.force_activate` so that, while it runs and on its thread only, `Bundler.frozen_bundle?` answers false. The modules are anonymous, so an app sees no constant of Fledge's (ADR 081). The bundle the launcher set up stays frozen, and nothing is written. The file creates `Gem::BUNDLED_GEMS` as an empty module when it is not yet defined, since `bundled_gems.rb` loads after it and reopens the module.

Two other ways were weighed and not taken:

- **No `BUNDLE_FROZEN`** in the app's `.bundle/config`: Bundler would touch the lockfile on every setup (`Definition#write_lock`, `definition.rb`, lines 401 to 426), fail in a read-only folder, and add the running platform to its resolution.
- **Adding irb to the app's bundle at build time:** the app's `$LOAD_PATH` and loaded gems would differ from what `bundle exec` gives.

On Windows, `binding.irb` in such a bundle fails under `bundle exec` as well, and the app matches it: reline, which irb requires, requires `fiddle/import` there, and fiddle, a bundled gem, is a dependency of neither irb nor reline, so the temporary bundle leaves it out. With `fiddle` in the Gemfile it opens IRB. `test/integration/built_app_test.rb` skips its `binding.irb` test on Windows for this reason.

## The linkage check

`Fledge::Linkage` reads each compiled file that a gem the app ships holds as a gem ("What the check reads of a git or path gem", below), precompiled or compiled, in the format of the target's own loader (ELF, Mach-O, or PE; a loader loads no other), with `Fledge::Binary`: the system's objdump on macOS and Linux, and on Windows the `llvm-readobj.exe` the runtime carries in its tools folder (why these tools: `doc/contributors/design/license-audit.md`, "Which tools read compiled files"). A file may need only a library that:

- **the target's operating system provides** (`Linkage::SYSTEM_LIBRARIES`): on glibc Linux, the libraries PEP 600 lets a manylinux_2_39 wheel assume (auditwheel 6.4.2's `manylinux-policy.json`, `lib_whitelist`) and glibc's loader; on musl Linux, musllinux_1_2's (auditwheel 6.8.2's `musllinux-policy.json`: musl's C library by its own name and Alpine's, and zlib); on macOS, anything in `/usr/lib` and `/System/Library/Frameworks`; on Windows, the API sets, `combase.dll`, and every DLL in System32 on every Windows of the app's architecture, as delvewheel lists them (`Linkage::SYSTEM_DLLS`; "What Windows provides", below);
- **the runtime ships** (`RuntimeContents#libraries`: Ruby's DLL, `libgmp-10.dll`, `libcrypt.so.2`, and the rest);
- **the gem itself carries**, by file name, and on macOS only where dyld would find it ("dyld's rules on macOS"), or by the name one of its libraries gives itself ("A library the gem loads first", below);
- on Linux, **`fledge.yml` lists** under `linux: system_libraries` ("Libraries from the Linux distribution").

A file that needs another Ruby's DLL (a precompiled gem's `lib/nokogiri/3.4/nokogiri.so`, which needs `x64-ucrt-ruby340.dll`) is built for that Ruby, never loaded, and not judged, and neither is a file for another processor than the app's ("A file for another processor", below). Every other library fails the build. `Fledge::AppGems` collects every problem of every gem, then raises once, so one build shows them all. The message names the gem, the file, and the library, and says to build the gem so that it carries the library or links it statically, and on Linux, to list it when every computer the app goes to has it. The check reads only what each file needs, never what is compiled into it ("Checks that are not about licenses"). An Android app's libraries are judged by the same check once its project holds them, against what Android offers every app (`doc/contributors/design/phone-projects.md`, "What each library needs").

The check is there so that a person who runs the app never meets a loader's error that names a gem (AGENTS.md, Design precedence 1). A gem built on the developer's computer may name a library only that computer has, as nokogiri's libxml2, built from source on a Mac with Homebrew, named Homebrew's `liblzma`: the app starts there and fails everywhere else when Ruby requires the gem. Refusing the build tells the developer, on their own computer, which gem and library, and how to fix it, by one rule for a precompiled gem, a compiled one, a git gem, and a path gem. No alternative was weighed when the check was decided. Two were found later, on 2026-11-10, and are not taken. Repairing the gem by copying the library in and rewriting its run paths or imports, as auditwheel's `repair`, delvewheel, and delocate's `delocate-wheel` do for Python's wheels, would ship more apps unchanged, at the cost of patchelf, install_name_tool, and import-table editing in Fledge, of libraries whose licenses would be the app's, and of a library from the developer's computer that may suit no other. Leaving the gem to fail at run time, as `bundle install` does, breaks the rule the check is for. What the check costs: the developer fixes the gem's build (links the library statically, carries it where a run path reaches it, or builds without it), which may mean a build option or a fork; the lists of what each system provides are Fledge's to keep current, from auditwheel's and delvewheel's lists; and a library a gem opens with `dlopen` is invisible to it.

## A library the gem loads first

A library may need another by a name no file of the gem has, which the other gives itself: its ELF `DT_SONAME`, or its Mach-O install name (`LC_ID_DYLIB`), which `Fledge::Binary#soname` reads. raylib-bindings 0.8.4 carries libraylib as `lib/libraylib.x86_64.so`, whose SONAME is `libraylib.so.600`, and as `lib/libraylib.arm64.dylib`, whose install name is `@rpath/libraylib.600.dylib`; its `raygui` and `physac` libraries need those names, with run paths into the gem author's CI (`/home/runner/work/...`). Its Ruby loads libraylib first, by its path, then the other two (`ffi_lib_flags :now, :global` and `ffi_lib(*lib_paths)`, `lib/raylib.rb` lines 23 and 24), and each system's loader answers the later need with the library already loaded:

- glibc's `_dl_map_object` looks first "for this name among those already loaded", and takes a loaded object whose SONAME equals the name, whatever its file is called (`elf/dl-load.c` at glibc 2.39, lines 1959 to 1985; `_dl_name_match_p`, `elf/dl-misc.c` line 67).
- dyld, "for @rpath paths, first check if already loaded as rpath", takes a loaded image whose install name is the `@rpath/` name before it searches any run path (`Loader::getLoader`, `dyld/Loader.cpp` at dyld-1378, lines 797 to 808). It does this for `@rpath/` names only: an `@loader_path/` or absolute name is looked for as a file.

So the check accepts a need whose name no file of the gem has when, on glibc's Linux, it equals the SONAME of a library the gem carries, or, on macOS, when it begins with `@rpath/` and equals the install name of a dylib the gem carries. Under `bundle exec` on macOS 27.2 arm64 and on Ubuntu 26.04 x86_64, raygui and physac loaded so, and each called function answered; raygui opened alone, with `RTLD_NOW`, failed, on macOS with dyld's "tried: '/Users/runner/work/.../libraylib.600.dylib' (no such file)". On both, the app `fledge build` made from `test/fixtures/raylib` then printed the same, started from `/` with no environment but `PATH=/usr/bin:/bin`; `test/integration/built_app_test.rb` builds and runs it with none at all, on each platform's runtime job.

What the rule still refuses, and what it cannot tell. A need that equals no file name of the gem and no name a library of the gem gives itself is refused, as before, and so is an `@loader_path/` or absolute need on macOS that equals only an install name, since dyld would look for a file the gem does not have. On musl's Linux and on Android the rule does not apply: neither loader's source was read for it, and no gem has been seen to need it there. A need whose file name the gem does carry is judged as before, and on macOS only where dyld's run paths reach it. Whether the gem's Ruby loads the named library before the one that needs it is in its Ruby, which a check of files at rest does not read: a gem that loads raygui first would pass and fail, on the developer's computer under `bundle exec` as on every other, unless the developer's computer has a `libraylib.so.600` of its own where the loader searches. The rule for an absolute install name ("dyld's rules on macOS", last bullet) rests on the same ground. Two other answers were weighed: refusing, as before, refuses a gem that runs wherever it goes, which the check is not for (AGENTS.md, "Licensing": a gem is refused "only when it would not run where the app goes"); and reading the gem's Ruby for its load order is beyond what a check of compiled files can do for every gem.

## A file for another processor

A process loads code for its own processor only, and a gem may carry a library for each of several. raylib-bindings 0.8.4 is one gem for every platform, holding `lib/libraylib.x86_64.so` and `lib/libraylib.aarch64.so`, and the same for raygui and physac; its Ruby picks one by `RUBY_PLATFORM`. On x86-64 Linux the check once judged the aarch64 files too, and refused the app for what they need ("raylib-bindings 0.8.4's lib/libraylib.aarch64.so needs libOpenGL.so.0 ..."), though no x86-64 process can load them, which is not the check's to refuse (AGENTS.md, "Licensing": a gem is refused "only when it would not run where the app goes"). So `Linkage` is given the app's processor (`Platform#cpu`: `x86_64` or `aarch64`, which RubyGems calls `x64` on Windows and `arm64` on macOS), and a file whose code is for none of it is neither judged nor counted as the gem's copy of a library another file needs, since the loader would refuse that copy as well. Each processor considered, and why it is another:

- **x86-64 and aarch64 Linux.** A 64-bit process loads no 32-bit file: i386 on x86-64 and 32-bit ARM on aarch64 are other processors, as aarch64 and x86-64 are to each other. glibc's loader opens no file of another class or machine, and goes on searching as if it were not there (`open_verify`, `elf/dl-load.c` at glibc 2.39, lines 1693 to 1700 and 1735 to 1740).
- **arm64 macOS.** The runtime's Ruby is an arm64 process, and Rosetta translates a whole process, never an Intel library loaded into a native one, so an x86-64 Mach-O file is another processor's. A universal file holds a slice for each of several, and dyld loads the slice for the process's: a universal file with an arm64 slice is the app's, and judged. An arm64e slice counts as arm64 (its cputype is `ARM64`, with a subtype of `E`), which errs toward judging it.
- **x64 and ARM64 Windows.** An x64 DLL does not load into the ARM64 runtime's native Ruby, nor an ARM64 DLL into the x64 one. An ARM64EC DLL's header says x64, and a native ARM64 process loads none, so it is another processor's on ARM64; an ARM64X DLL's header says ARM64, and it is the ARM64 app's.
- **Android.** Each of an app's libraries sits in `lib/ABI/`, placed there for that ABI, where Android's linker would load it, so `AndroidLinkage` judges every file, whatever its processor: a file for another processor there would fail on the phone, and letting it off would hide it.

How the processor is read. An ELF file's comes from its header's `e_machine` (two bytes at offset 18, in the byte order of byte 5, as the gABI's "ELF Header" places them), which `Fledge::Binary` reads as file(1) does. GNU's objdump, which reads ELF for the check on Linux, names a file's processor only among those it was built for: on an x86-64 computer, binutils 2.42's, on Ubuntu, names an aarch64 file `elf64-little` and a 32-bit ARM one `elf32-little`, and reads no Mach-O or ARM64 PE file at all, so a test of a format name would pass on one computer and fail on another. GNU's readelf names every processor, but would be a second tool for every build to run for two bytes. A Mach-O file's comes from the header objdump prints for it (`MH_MAGIC_64 ARM64 ...`), and a PE file's from llvm-readobj's `Arch:` line (`x86_64`, `aarch64`), each named the same by the LLVM tools that read them everywhere. A file whose processor nothing read is judged, so that a reader's silence never lets a file off.

A universal Mach-O file failed every build until this was written: Xcode's objdump, as otool does, heads its output with the file's name alone, or with `(architecture ARCH)` after it for each slice, with no `file format`, which the reader did not take for a file's header, so `fledge build` stopped with "objdump could not read". It prints only the slice for the Mac's own processor when the file has one, so on an arm64 Mac the check reads exactly the slice dyld would load; a universal file without one is read as all its slices together, and judged by what any of them needs.

Two other answers were weighed for the check: judging every file, as before, refuses apps that run; and leaving out a file by the processor its name or folder suggests (`aarch64`, `arm64`) trusts a convention no gem is bound to, where the file's own header is certain.

The same rule, `Binary#for?`, holds wherever a build decides something about the app from a gem's compiled files. The floors check (`NativeBuild::Floors`, "The toolchain and the oldest systems") reads only files for the platform's processor, so an aarch64 library a build leaves beside its x86-64 one, needing a newer glibc than the floor, refuses no x86-64 app. A `.deb`'s `dpkg-shlibdeps` is given only files for the app's processor: given an aarch64 file in an amd64 package, it looks for the file's libraries among aarch64 ones and, on Ubuntu 24.04 with none, stopped the build (`doc/contributors/design/desktop-apps.md`, "Depends"). Nor does it read a file for another system: raylib-bindings carries `lib/libraylib.arm64.dylib` and Windows DLLs beside its `.so` files, and GNU objdump reads no Mach-O file, so a `.deb` of an app that carried it stopped with "no tool on this computer reads macho files"; the checks already read only the format their system loads. Signing is not a decision of this kind: every Mach-O and PE file the app carries is signed, whatever its processor, since Apple's notary service refuses an app with any unsigned code in it, and codesign and signtool sign a file for any processor. A foreign file still ships, at its path, as it does under `bundle exec`.

`test/linkage_test.rb` and `test/native_build_floors_test.rb` judge stand-ins `test/fixtures/binaries/build.rb` makes for each processor (an aarch64, an i386, and a 32-bit ARM ELF file, an x86-64 Mach-O bundle, an ARM64 DLL), `test/integration/linkage_mach_o_test.rb` a universal bundle Xcode's clang links, and `test/integration/deb_dependencies_test.rb` a `.deb` with a stand-in for the other processor (aarch64 or x86-64) beside a file compiled there.

## What Windows provides

On Windows, a compiled file may need any DLL whose lowercase name `lib/fledge/linkage/windows.yml` lists for the app's architecture, `windows` for x64 and `windows-arm64` for ARM64 (`Platform#libraries`), and any API set (`api-ms-win-*.dll`) or `combase.dll`, whatever its case. `tasks/windows_dlls.rb` writes the file from delvewheel's `delvewheel/_dll_list.py`, pinned by commit (`0cf6869e`, whose `_version.py` says 1.13.2) and by SHA-256, and refuses any other file: `ignore_names_x64` is "all the files with extension .dll or .drv found in C:\Windows\System32 on installation discs of Windows x64 Windows 7 SP1, 8, 8.1, 10, and 11 which have exported functions", 1,422 names, and `ignore_names_arm64` is the ARM64 DLLs of System32 on ARM64 Windows 10 and 11, 2,767 names (lines 1333 to 2761 and 2763 to 5535). The API sets and `combase.dll` are delvewheel's `ignore_regexes` (lines 40 to 46): Windows resolves an API set itself, and `combase.dll` is in every Windows from 8 on. Windows 11 is Fledge's floor (decisions.md, 2026-11-21), so a list made of what older Windows also had assumes less than the floor gives, never more; a DLL Windows gained after 7 SP1 that a gem needs, such as `ucrtbase.dll` on x64, is still refused on x64, as delvewheel's README says of its own floor ("Wheels may not work on systems older than Windows 7 SP1 because delvewheel excludes system libraries present in Windows 7 SP1+", line 142).

The Visual C++ runtime is in neither list. `vcruntime140.dll`, `vcruntime140_1.dll`, and `msvcp140.dll`, which a DLL built with Visual Studio needs unless it links the runtime statically (`/MT`), are Microsoft's Visual C++ Redistributable, which a computer has only once something installed it, and delvewheel keeps them out of its lists on purpose (its `vc_redist` pattern, line 97, and `ignore_by_abi_platform`, which ignores `vcruntime140.dll` only for a Python that ships it). A gem whose DLL needs them ships only as the project says ("The Visual C++ runtime", below).

How the list was made before, and why it changed: it was some fifty names picked by hand from delvewheel's lists and `runtime/licenses.yml`, a name added each time a gem's DLL needed one, and it refused LibUI's DLL (the `libui` gem's `vendor/libui.x64.dll`), which needs Direct2D's `d2d1.dll` and DirectWrite's `DWrite.dll`, parts of every Windows. Picking names from a list leaves the next gap for the next gem to find; taking the list whole, from a tool that makes it from the installation discs, leaves none that delvewheel has not found. Three other sources were weighed:

- **PyInstaller** (`PyInstaller/depend/dylib.py` at `abed52cc`, lines 307 to 336) leaves out every DLL found under the building computer's Windows folder, and collects the Visual C++ runtime's DLLs from there all the same (`_win_includes`, lines 54 to 172). That judges the building computer, not the one the app goes to: a DLL an optional feature, a newer Windows, or the Redistributable put in the developer's System32 would pass, and the check, which reads files at rest by name, would need the build computer's folders.
- **Microsoft's documentation** names each function's DLL on that function's page, and has no list of the DLLs every Windows holds; a list made from those pages would be picked by hand again.
- **cx_Freeze** was not read: delvewheel's list already comes from the installation discs themselves, which no other source improves on.

What the list costs: 4,189 names in the gem (81 KB), read once when `fledge build` loads the check; delvewheel's MIT notice in the file, between `SPDX-SnippetBegin` and `SPDX-SnippetEnd`; and an update that is Fledge's to make on purpose, by changing the generator's pins and running it on delvewheel's new file. A DLL that a later Windows than 11 drops, which delvewheel's list for Windows 7 SP1 to 11 would still name, would pass the check and fail on that Windows, until delvewheel's list and Fledge's pins catch up.

## The Visual C++ runtime

A gem's DLL built with Visual Studio needs Microsoft's Visual C++ runtime (`Linkage::VISUAL_C_RUNTIME`, the VC14 runtime's DLLs as PyInstaller lists them in `_win_includes`, `PyInstaller/depend/dylib.py` at `abed52cc`, lines 150 to 165), and Windows does not include it. LibUI's `vendor/libui.x64.dll` needs `MSVCP140.dll`, `VCRUNTIME140.dll`, and `VCRUNTIME140_1.dll`. Microsoft's "Redistribute Visual C++ files" says "Distribution of the Visual C++ Runtime Redistributable package, merge modules, and individual binaries is limited to licensed Visual Studio users and is subject to Microsoft Software License Terms." Visual Studio 2022 Community's license terms, section 4, "Distributable Code", say "You may copy and distribute the object code form of code listed on the Distributable List", and that for any of it "you must: add significant primary functionality to it in your applications; and require distributors and external end users to agree to terms that protect the Distributable Code at least as much as this agreement." Fledge cannot check that a developer holds that license. The maintainer's rule: "An app developer who has the rights to do a thing should _be able_ to do it and distribute their app with Fledge" (`decisions.md`), with the right and the duty the developer's, as a gem's license is.

So the project says how its app comes by the runtime, in `fledge.yml`, with Microsoft's own names for the two ways ("Deployment in Visual C++"):

```yaml
windows:
  visual_c_runtime: local    # or central
```

- **`local`**: "library files are installed in your application folder together with the executable file." `fledge build` copies each DLL of the runtime the gems' files need (`Linkage#visual_c_libraries`), and each DLL of the runtime those need in turn, read with `Fledge::Binary` (`msvcp140.dll` needs `vcruntime140.dll`), from the building computer's System32 (`VisualCRuntime.system32`, `%SystemRoot%\System32`) into the app's `ruby\bin\ruby_builtin_dlls` (`Fledge::VisualCRuntime`). A DLL System32 lacks is refused, with a message that says to install the Redistributable there.
- **`central`**: "library DLL files are installed in the Windows\System32 directory" by the Visual C++ Redistributable. `fledge build` ships none and refuses nothing for them, as Linux's `system_libraries` ships nothing for what the distribution provides. For a `.zip`, `central` means the person installs the Redistributable themselves. `fledge build` writes the runtime's DLLs the gems need, by their lowercase names, into `fledge.cfg`'s `visual_c_runtime` (`AppGems#visual_c_runtime`), and an app started where System32 lacks one names the Redistributable and Microsoft's download and exits 72 before Ruby starts, in a message box when it is windowed (`launcher.md`, "The Visual C++ runtime on Windows"), where Ruby would have raised a `Fiddle::DLError` or `LoadError` from inside the gem. An MSIX package depends on Microsoft's framework package of the runtime instead, which Windows installs with it, and the setup program installs the Redistributable where it is missing (below).
- **Neither**: the gem is refused. The refusal names both values, says Microsoft limits distributing the runtime to licensed Visual Studio users, and names the third way out, a build of the gem that links the runtime statically (`/MT`).

Microsoft recommends `central`. Of the Redistributable packages: "We recommend that you use these packages for your deployments because they enable automatic updating of the Visual C++ libraries." Of the folder `local` copies into: "For servicing reasons, we don't recommend that you use this installation location" (both "Redistribute Visual C++ files"). And "Deployment in Visual C++": "If you decide to use local deployment of the Redistributable libraries, we recommend that you implement your own method of automatically updating the locally deployed libraries." An app built with `local` keeps the copies its build took until its developer builds it again.

**Why the project asks.** PyInstaller copies the runtime whenever a DLL needs it, without asking (`_win_includes`), and delvewheel copies whatever DLLs a wheel needs, with a note in its README: "Redistributing third-party DLLs may have copyright or licensing implications, so be sure to review and comply with the relevant licenses before including them in your wheel" (line 8). cx_Freeze asks: its `include_msvcr` build option, off unless given, does it ("include the Microsoft Visual C++ Redistributable files without needing the redistributable package installed", cx_Freeze's `setup_script` documentation). Copying unasked would have every developer whose gem needs the runtime distributing Microsoft's files without knowing that a license bears on it, and Fledge distributing them through the developer's hands; the maintainer's rule gives the developer the way, and the choice. Asking costs one line in `fledge.yml`, which the refusal names. Design precedence 1 holds either way: an app that needs the runtime is not built until the project says how it gets it.

**Where the copies come from.** Three sources were weighed. The building computer's System32 holds what the Redistributable installed, the newest any program brought, and the developer's own `bundle exec` loads the runtime from there, so the app carries the files the developer's run used (design precedence 2); Microsoft supports only a Redistributable "the same as or newer than your toolset version" ("Determine which DLLs to redistribute"), and the newest installed one comes closest to that for a gem someone else built. Visual Studio's folder, `%VCToolsRedistDir%\ARCH\Microsoft.VC143.CRT`, is the one Microsoft's pages name ("You may use these libraries for local deployment, by installing them in the same directory as your application"), but a developer on RubyInstaller has no Visual Studio, and its version is that developer's toolset's, which may be older than the gem's. A folder the developer names would put one computer's path in a file the project shares. The bytes are Microsoft's in each case; which copy the developer's license covers is the developer's to know. The copies are of the building computer's architecture, since Fledge builds a Windows app on the Windows it is for: an x64 System32 holds x64 DLLs, and an ARM64 Windows's System32 holds ARM64 ones, which no computer has tried with Fledge yet.

**Where the copies go.** Windows looks for a DLL that a loaded DLL imports by its name ("Dynamic-link library search order": "If a DLL has dependencies, then the system searches for the dependent DLLs as if they were loaded by using only their module names"). The launcher and the runtime's `ruby.exe` set the search to `LOAD_LIBRARY_SEARCH_DEFAULT_DIRS` and add `ruby\bin\ruby_builtin_dlls` with `AddDllDirectory` (`launcher.md`, "Windows"). With those flags Windows searches "the application folder", then "paths explicitly added with the AddDllDirectory function", then "the System folder", after the loaded-module list and the known DLLs, which hold no Visual C++ runtime. So a copy in `ruby_builtin_dlls` answers before System32 for every DLL loaded with the process's default search: Ruby's own extensions, and Fiddle's `Fiddle.dlopen` (`#define dlopen(name,flag) ((void*)LoadLibrary(name))`, `ext/fiddle/fiddle.h` line 34 at fiddle 1.1.8), which LibUI uses. A copy beside the launcher would serve the launcher alone, not a Ruby the app starts, whose application folder is `ruby\bin`. On Windows 11 x64, whose System32 held the Redistributable's copies and whose `KnownDLLs` key named none of the runtime, the LibUI app built with `local` and left running loaded `VCRUNTIME140.dll`, `VCRUNTIME140_1.dll`, and `MSVCP140.dll` each from its own `ruby\bin\ruby_builtin_dlls`, as the process's module list showed. Since System32 comes after that folder, a computer without the Redistributable resolves them the same way; a Windows that never had the Redistributable has not run the app yet.

**A DLL that ffi loads.** ffi loads a library named by its full path with `LoadLibraryExA(name, NULL, LOAD_WITH_ALTERED_SEARCH_PATH)` (`ext/ffi_c/DynamicLibrary.c` lines 222 and 223 at ffi 1.17.3), whose alternate search order, as "Dynamic-link library search order" lists it, names "the folder specified by lpFileName" and "the system folder" but not the folders `AddDllDirectory` added. On Windows 11 x64, though, the app's own `ruby.exe`, started afresh, loading LibUI's DLL by its full path with that flag got `vcruntime140.dll` from the app's `ruby_builtin_dlls`, as it did with no flag, while System32 held a copy too. Whether nothing had loaded the runtime in that process before the call was not checked, so this shows the copy is found, not why; no gem that loads its DLL with ffi has been tried.

**What setdef publishes.** Nothing Fledge publishes carries the runtime: not the gem, a runtime, or a release asset. Its tests use stand-ins that `test/fixtures/binaries/build.rb` builds with llvm-mingw, DLLs that only import the runtime's names. An app that CI builds with `local` is built and run within one job, and nothing of it is uploaded, since anyone may download a public repository's workflow artifacts.

**How CI checks it, and publishes none of it.** Nothing setdef publishes carries the runtime, "not an app that Fledge's CI builds and uploads" (`decisions.md`), and a public repository's workflow artifacts are anyone's to download. So `test/fixtures/libui`, the LibUI probe, whose `fledge.yml` says `local`, is built on x64 Windows only after the Build job's last upload, into a folder no upload or cache names, and run there: `.github/scripts/deliver-libui.sh` finds the three DLLs in its `ruby\bin\ruby_builtin_dlls`, starts it from `/` with System32 alone on its `PATH`, and reads the report it writes once its window has shown. Before each upload from Windows, `.github/scripts/check-no-visual-c-runtime.sh` fails the job if a file it would upload, or a file inside an uploaded `.zip` or `.msix`, is one of the runtime's DLLs; a setup program, whose archive no tool on the runner lists, must have its app's `.zip` beside it, which holds the same files. Leaving the build unchecked on CI was the other way, with only the unit tests' refusal without the key; it would leave untested the copy itself, which only a Windows build shows. The runner's System32 has the Redistributable, so this shows the app holds its copies, not that it runs on a Windows that never had them.

**Installers that see to the runtime.** Microsoft's recommended way is central deployment by an installer: "If you use one, run it as a prerequisite on the target system before you install your application" ("Redistribute Visual C++ files"). That makes `central` true for a person who installs the app, without changing what the key means. An MSIX package declares a dependency on Microsoft's Visual C++ runtime framework package, `Microsoft.VCLibs.140.00.UWPDesktop`, which the Store installs with it, and its copy of `fledge.cfg` names no DLL for the launcher to look for, since in a package the DLLs come from the framework package (`desktop-apps.md`, "The Visual C++ runtime in a package"). The NSIS setup program, before it installs anything, looks for the DLLs `fledge.cfg` names where the launcher looks, and when one is missing downloads Microsoft's Redistributable from the link the launcher's message names and runs it, which distributes nothing but needs a network; when the DLL is still missing, the person chooses to abort, retry, or install the app without it (`desktop-apps.md`, "The Visual C++ Redistributable"). Carrying the Redistributable's installer inside the setup program, which is distribution under the same terms as `local`, waits for a developer who needs it. A `.zip` has no installer and keeps the meaning above. `fledge build` does not warn when a project sets `central` and asks for no installer: `central` is Microsoft's recommended way, a developer who sets it has said the computers the app goes to have the Redistributable, and the person whose computer does not is told by the app itself what to install; a warning on every build of a setting chosen on purpose is one developers learn to skip.

## What the check reads of a git or path gem

A gem from a gem server holds what its `.gem` holds, the files its gemspec listed when it was packed, and the check reads them all. A git or path gem ships its whole folder ("Git gems", "Path gems"), and a repository holds more than its gem: its tests, and the compiled fixtures some tests read. The check reads, of that folder, the files the gemspec lists, which are all a RubyGems install of the gem would hold, and every file under its require paths, which Ruby loads whether the gemspec lists it or not (`Fledge::GemFiles`, through each package's `#gem_files`; a compiled gem adds what of its build's files Ruby may load and its extensions folder, `CompiledGem#gem_files`: "What a compiled gem ships"). A gemspec that lists no files says nothing of what the gem holds, and a require path of the folder itself (`.`) lets Ruby load any file in it, so either leaves the whole folder to judge. The app still carries the whole folder, as `bundle exec` has it, fixtures and all.

Fledge's own repository is the case that showed it. `test/fixtures/binaries` holds ELF, Mach-O, and PE files that need libraries on purpose, for the tests of this check, and with `gem "fledge"` from git in a Gemfile's `development` group, as the README says, `fledge build` refused the app on Linux and macOS ("fledge 0.14.0's test/fixtures/binaries/elf-94f785a43dcf.so needs libm.so"), though nothing loads those files and the app runs. A path gem's check read only its require paths before; it now reads the files its gemspec lists too, so a library a gem lists outside them, such as one `ffi_lib` opens from `vendor/`, is judged.

Two other answers were weighed. Reading only the files the gemspec lists, as a `.gem` would hold them, would leave out a compiled file under `lib/` that a git gem's gemspec does not list (`files = Dir["lib/**/*.rb"]` beside a checked-in `lib/foo.so`), which `bundle exec` loads from the checkout: the build would pass, and the person who runs the app would meet the `LoadError` instead, the worse of the two failures. Reading only the require paths, as path gems were read, would miss a listed library outside them. What the rule costs: a git or path gem whose Ruby loads a compiled file it neither lists nor keeps under a require path ships unjudged, and the app fails where the library is missing. Bundler's gem template lists `git ls-files` less `bin/`, `test/`, `spec/`, and `features/`, so most gems list what they load and leave their fixtures out.

## dyld's rules on macOS

A library the gem carries counts only where dyld would find it, so that a bundle that names `@rpath/libfoo.dylib` with the one run path `/opt/homebrew/lib` fails, however the gem's copy is named. `Fledge::Linkage::Dyld` expands each name as `dyld(1)` describes ("Dynamic Library Loading"):

- `@loader_path` is the folder of the file that names the library.
- `@rpath` is tried with each run path the file's LC_RPATH commands give, then those of each file that loaded it, as dyld searches the chain of loaders; the run paths are passed down until no file gains one. A run path that begins with `@loader_path` is the folder of the file whose LC_RPATH it is.

A name that leads to no file of the gem fails, with a message that names the file, the library, where the gem carries it, and the run paths searched, and suggests the `@loader_path` run path that would reach it (`install_name_tool -add_rpath`). The rule refuses only what certainly would not load:

- A run path that is absolute (`/opt/homebrew/lib`, `/Library/Frameworks`) reaches nothing in the app, and a relative one depends on the folder the program starts in; neither is a fault when another run path reaches the library.
- A name or run path that begins with `@executable_path`, or that climbs out of the gem's folder, depends on where the gem sits in the app, which differs between a console app and a macOS bundle, so it is judged by its file name only.
- A library the runtime ships is the runtime's to place, and is judged by its file name.
- Ruby, the program that loads every bundle, contributes no run paths: its own lead into the runtime, never into a gem.
- An absolute name outside `/usr/lib` and `/System/Library/Frameworks` whose file name the gem carries is accepted by that name. dyld would load it only from that path, or from an image already loaded under the same install name, and telling those apart needs the load order, which a check of files at rest does not have.

The fixtures for these rules are built by `test/integration/linkage_mach_o_test.rb` with Xcode's clang and `install_name_tool`, which only a Mac has; elsewhere those tests skip.

## Libraries from the Linux distribution

`fledge.yml`'s `linux: system_libraries` (`Fledge::Config::Linux`) is a list of sonames, each a library's name as a compiled file's `DT_NEEDED` gives it: letters, digits, and `. _ + -`, ending in `.so` and its version numbers, with no folder (`Config::Linux::SONAME`, and the schema's same pattern). A repeat is dropped. No wildcards. The key applies on glibc and musl Linux alike (`Config#system_libraries` answers it for every Linux platform) and every other build ignores it.

- **Accepted:** a compiled file may need any library on the list (`Linkage`'s `system:`).
- **Refused when unlisted:** every other library still fails, and on Linux the message ends with the key to copy: `list it in fledge.yml as linux: { system_libraries: [libxml2.so.2] }`.
- **Refused when unused:** a listed library that no gem's compiled file needs beyond what the baseline, the runtime, and the gems provide fails the build too (`Linkage#unused`), asked after every gem is judged. So the list cannot name what a gem opens with `dlopen`, which no compiled file names.

The list goes into `fledge.cfg` as `system_libraries = …`, which the Linux launcher checks before Ruby starts, exiting 72 with the missing library's name (`doc/contributors/design/launcher.md`). A `.deb` depends on the packages dpkg-shlibdeps finds for the files that need them (`doc/contributors/design/desktop-apps.md`). An AppImage and a `.tar.gz` do not carry them.

The list is for wrappers of desktop libraries. Tokra's extension links WebKitGTK 4.1, GTK 3, libsoup 3, and JavaScriptCoreGTK 4.1, which every desktop distribution provides and the manylinux list leaves out, since a server has none; no gem should carry them, since they are large, LGPL, and tied to the desktop's own GLib, D-Bus, and theme. A soname is the one name every Linux output shares (the `.tar.gz`, the AppImage, the `.deb`, and a later `.rpm`), and the one the check can verify against the files. Debian package names, which Tauri's `deb > depends` and Briefcase's `system_runtime_requires` take, are one distribution family's and sometimes one release's (Ubuntu 24.04 and Debian 13 renamed GLib's to `libglib2.0-0t64`), cannot be checked against the files, mean nothing to an AppImage or an archive, and would need sonames again for an `.rpm`, as Tauri's two lists show. Wildcards, which auditwheel's `--exclude` accepts, cannot be checked exactly, and a new soname is a new ABI for the developer to read before shipping. Bundling the libraries into the AppImage, as Tauri does with linuxdeploy and its GTK plugin, means copying WebKitGTK's helper processes and GTK's modules by hand, the D-Bus and subprocess bugs Briefcase warns of, and LGPL libraries whose sources each developer would have to publish. For the `.deb`, `dpkg -S` names a file's owner but no version, and apt-file reads the archive rather than what is installed; dpkg-shlibdeps is Debian Policy 8.6.1's own procedure. What the list costs: an AppImage is not self-contained for these libraries, building a `.deb` with any listed needs dpkg-dev and objdump, and a library whose package is named differently elsewhere (libjpeg's `libjpeg-turbo8` and `libjpeg62-turbo`) makes a `.deb` for the distribution it was built on only. `examples/system_library` proves the path on Debian and Ubuntu; no wrapper has shipped a WebKitGTK app with the list yet.

The prior art behind the soname list: auditwheel 6.4.2, `src/auditwheel/main_repair.py`, lines 102 to 112 (`--exclude`); delvewheel at 0cf6869e, `delvewheel/__main__.py`, line 63; Tauri at 32576120, `crates/tauri-utils/src/config.rs` lines 339 and 340, `crates/tauri-bundler/src/bundle/linux/debian.rs` lines 204 to 207, `crates/tauri-cli/src/interface/rust.rs` lines 1419 to 1430, and `appimage/linuxdeploy.rs` lines 150 to 165, 197 to 203, and 242 to 245; Briefcase at fee777ed, `docs/en/reference/platforms/linux/system.md` lines 182 to 194 and `appimage.md` lines 55 and 138 to 153; AppImage's excludelist (pkg2appimage at 19e30b27); Debian Policy 8.6.1; dpkg-shlibdeps(1) at dpkg 1.22; sysexits(3). These were read when the list was chosen, on 2026-11-04.

## Checks that are not about licenses

Fledge judges no gem by its license, whether it declares one, or what its compiled files hold. Each check that remains decides whether the app runs where it goes, or whether its inputs are the ones the developer locked:

- **The lockfile locks the target**, as the app's frozen Bundler would refuse it otherwise ("The lockfile's checks").
- **Checksums and git pins:** each `.gem` matches the lockfile's SHA-256, and each git gem is locked to a whole commit. This is about which bytes ship.
- **`required_ruby_version` and the Gemfile's `ruby`:** a gem whose chosen build's `required_ruby_version` excludes the runtime's Ruby fails, naming it, as RubyGems would refuse it (`GemPackage.ruby_problems`), and so does a Gemfile `ruby` the runtime does not satisfy.
- **Path gems:** one outside the project whose folder is missing, or whose path ends in `.` or `..`, fails.
- **Servers:** one that refuses the login, or has no file for the gem, fails ("Fetching a gem's file").
- **Linkage:** each compiled file needs only libraries the system, the runtime, the gem, or the list provides ("The linkage check").
- **Floors:** what Fledge compiled needs no newer macOS or glibc than the runtime's oldest ("The toolchain and the oldest systems").
- **A gem that fails to compile** fails the build.

Two behaviors once given license reasons stand on technical ones: a git gem ships its own folder of the checkout, not the whole repository ("Git gems"), and the runtime prunes nkf's JRuby sources, which is about the runtime (`doc/contributors/design/runtimes.md`).

The maintainer decided it (`decisions.md`, 2026-10-28): which gems an app uses, and whether their licenses suit it, are the developer's call, and decision 8 protects developers only from what Fledge adds through its runtime, which no developer chose. So each gem ships as RubyGems or Bundler would install it, with its own files, license files among them, and each app's `notices/` holds only what Fledge put there, its runtime's `NOTICES.txt` and SBOM. The prior art does the same. PyInstaller says what it builds "can be shipped with whatever license you want, as long as it complies with the licenses of your dependencies" (`doc/license.rst`, lines 15 to 17, at 4469721), and writes no notices for them; Tauri's bundler takes only the app's own license (`crates/tauri-bundler/src/bundle/settings.rs`, lines 651 to 655, at 32576120f); Warbler packs gems as they are installed (`jruby/warbler` at 3196d5f); and `bundle licenses` prints each declared license as information, with no verdict (`bundler/cli.rb`, lines 558 to 569, at Bundler 4.0.20). The cost is that Fledge does not warn that a precompiled gem compiles in an LGPL library, as nokogiri's macOS and Windows builds do; the gem's own notices say so (nokogiri's `LICENSE-DEPENDENCIES.md`), and `doc/licensing.md`, "Your app's own gems", tells developers where to find them.

## Examples that exercise these rules

CI builds each on the desktop platforms named here and runs the result on a fresh runner with no Ruby (`.github/workflows/ci.yml`, the Build and Delivery jobs):

- `examples/my_cool_app`, on every desktop platform but ARM64 Windows: a gem-shaped app (i18n, which needs concurrent-ruby, and sqlite3, whose precompiled builds exclude Ruby 4.1, so it compiles from source), compared with `bundle exec ruby exe/my_cool_app` by the parity check.
- `examples/native_app`, on macOS, both glibc Linuxes, and x64 Windows: redcarpet, a C gem published only as source; a git gem with a Rust extension (ferro-idna, from its tag); libusb, whose precompiled Windows build fits Ruby 4.1 and ships, and which compiles from source everywhere else, with a build option from the example's `.bundle/config`; ffi, which libusb needs, compiled from source everywhere, since its precompiled builds exclude Ruby 4.1, with the libffi it carries, as the example's `.bundle/config` asks; and spreadsheet, with the bigdecimal the runtime's Ruby bundles.
- `examples/nokogiri_app`, on macOS and x64 Windows: nokogiri from source with a build option.
- `examples/real_gems`, on macOS, both glibc Linuxes, and both Windows: a gem through a loopback mirror of RubyGems.org that asks for a login (`.github/scripts/gem-mirror.rb`, named by Bundler's own mirror and credential settings in the example's `.bundle/config`); a path gem with an executable outside the project (`examples/real_gems_shared`); a path gem with a C extension inside it; a git gem with a submodule; and a gem in an optional group the example's `.bundle/config` asks for. CI fails the build unless the mirror served the gems with the login. It runs no `bundle exec` comparison, since Bundler compiles no path gem's extension. Its lockfile was made through the mirror, as a developer behind one would make it, so locking it again needs the mirror.
- `examples/system_library`, on both glibc Linuxes: a path gem whose C extension links libpng, listed under `linux: system_libraries`.
- `test/fixtures/libui`, the LibUI probe, on macOS, both glibc Linuxes, and x64 Windows: LibUI's precompiled gem, whose library links GTK 3 on Linux, listed under `linux: system_libraries`, and needs the Visual C++ runtime on Windows ("The Visual C++ runtime", above). It opens a window and reports it shown: on macOS through its program and `open -W`; on Linux in the `.deb` jobs' containers, first without GTK 3, where it names a library it lacks and exits with 72, then with GTK 3 and Xvfb from apt. LibUI publishes no gem with its library for musl Linux or ARM64 Windows.

On musl Linux the only example that compiles a gem is my_cool_app, whose sqlite3 Alpine's build-base compiles.

On ARM64 Windows the one example that compiles a gem is real_gems, whose path gem's C extension compiles there with MSYS2's CLANGARM64 clang. It builds no native_app: the job installs no Rust, and ferro-idna's rb-sys would build for Rust's `aarch64-pc-windows-gnullvm` target there (`lib/rb_sys/toolchain_info/data.rb` at rb_sys 0.9.130), which no job of Fledge's has tried. The Test (aarch64-mingw-ucrt) job also runs `test/integration/native_build_test.rb`, whose gems compile from source with MSYS2's CLANGARM64 clang, from a gem server, git, and a folder, into apps that run and print what the extension returns. sqlite3 does not compile there, and the fault is mini_portile2's, not Fledge's or SQLite's (`doc/contributors/drafts/mini_portile2-clang-host.md`, a report for the maintainer to file). It publishes no aarch64-mingw-ucrt build, and its `extconf.rb` builds SQLite with mini_portile2 (`minimal_recipe`, `ext/sqlite3/extconf.rb`, lines 153 to 165, at sqlite3 2.10.2), which runs `configure` with `--host` set to the `Target:` line that `$CC -v` prints (`mini_portile.rb`, line 117, `configure_defaults`, lines 415 to 421, and `detect_host`, lines 529 to 545, at mini_portile2 2.8.9). clang prints its triple normalized, `aarch64-w64-windows-gnu` for `aarch64-w64-mingw32`, and the `config.sub` that SQLite 3.54.1's `configure` runs (`autosetup/autosetup-config.sub`, timestamp 2024-05-27, in the tarball sqlite3 2.10.2 carries) refuses it: "Invalid configuration 'aarch64-w64-windows-gnu': Kernel 'windows' not known to work with OS 'gnu'." That `config.sub` is GNU's own, which takes `windows` as a kernel only with `msvc`, and refuses `x86_64-w64-windows-gnu` too; it takes `aarch64-w64-mingw32`, the name autoconf knows. So any autoconf project that mini_portile2 configures with clang targeting MinGW fails alike. Both halves were run on macOS, clang with `--target=aarch64-w64-mingw32 -v` and the `config.sub` on each name; the gem's whole build was not run on ARM64 Windows for this. `gem install sqlite3` runs the same `extconf.rb` with the same compiler on RubyInstaller's ARM64 Ruby, so it fails there too, and Fledge's part is to say so: `doc/gems.md`, "Gems with compiled extensions", tells a developer, and the failed build's output shows them `configure`'s refusal, since mini_portile2 prints `configure`'s log when it fails (`execute`, lines 616 to 628). Fledge does not rename the target for the gem's build: that would be a recipe for one gem's build, which "Compiling a gem" turns down, and `gem install` would still fail. Until sqlite3 publishes an aarch64-mingw-ucrt build that fits the runtime's Ruby, or mini_portile2 gives `configure` the name autoconf knows, my_cool_app does not build on ARM64 Windows, and the parity check's gem-shaped run there takes the same app without sqlite3 (`parity.md`, "The gem-shaped run").
