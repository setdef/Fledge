# ADR 075: A windowed Windows app can ship as an MSIX package, built with the Windows SDK's MakeAppx

## Context and Problem Statement

A windowed Windows app ships as a `.zip` and an NSIS setup program (ADR 009). The Microsoft Store takes a setup program only when the developer's own certificate, chaining to Microsoft's Trusted Root Program, signs it; it takes an MSIX package unsigned, and signs it itself: "The Microsoft Store will automatically re-sign your MSIX/AppX packages with a Microsoft certificate during the publishing process after your app passes certification" (learn.microsoft.com, "App package requirements for MSIX app", "Code signing for Microsoft Store submissions", read 2026-11-12). The maintainer: "Very valuable, let's do it if we can." (`decisions.md`, 2026-11-12). How does `fledge build` make an MSIX package, and with what?

## Decision Drivers

- A developer can ship through the Store with no certificate of their own.
- Code is a liability, and each platform's package is made with its own maintained tool (AGENTS.md; ADR 010).
- What a runtime carries meets Fledge's license policy (AGENTS.md, Licensing).
- An app's identity comes from `fledge.yml`, and nothing that fixes it for good has a default (ADR 008, ADR 064).

## Considered Options

1. MakeAppx, found on the developer's computer as signtool is, run on a manifest Fledge writes, with `installers: [msix]` opting in.
2. MakeAppx carried in the Windows runtime, as electron-builder carries it.
3. `fledge build` downloads the Windows SDK's build tools itself.
4. A package writer of Fledge's own.

## Decision Outcome

Chosen: option 1, because MakeAppx is the tool Microsoft maintains for the format, every Windows SDK and GitHub's Windows runners have it, and nothing of Microsoft's then sits in a runtime. Option 2 is refused for now: MakeAppx comes only under the Windows SDK's license, whose redistribution terms (unmodified, for packing MSIX only, downstream terms "at least as" protective, and an indemnity of Microsoft) fit none of the license categories a runtime may carry; whether a runtime should carry it is the maintainer's question. Option 3 adds download and cache code and passes over NuGet's license prompt. Option 4 is a format writer, which ADR 010 rules out.

`installers: [msix]` is a value a developer adds, never a default, as `.deb` is (ADR 021). The package's identity needs a Publisher matching the developer's Partner Center reservation, so `windows: msix_publisher` has no default and is required when `installers` names `msix`; `windows: msix_name` defaults to the identifier. Its logos are the developer's own `ICON-44.png`, `ICON-50.png`, and `ICON-150.png`, named as ADR 048 names icon files. With `--sign` or `--sign-command` the package is signed as the setup program is; without them it is left unsigned for the Store to sign. How the manifest is written: `doc/contributors/design/desktop-apps.md`.

Confidence: high that the package installs and runs. CI's Delivery, as an administrator on x64 and ARM64 runners, has Windows refuse the unsigned package and the signed one before its certificate is trusted, then install the signed one, check its identity, version, Start menu name, and file association, launch it through its AppUserModelID, and remove it. That the Store certifies it is untested: account test WIN-6, the maintainer's.

### Consequences

- Good, because a developer can ship to the Microsoft Store with no code-signing certificate.
- Bad, because building an MSIX needs the Windows SDK's build tools on the developer's computer, which Fledge does not pin; `mise.toml` pins them for Fledge's own contributors.
- Bad, because a package's new files under AppData are redirected to its private store, so other programs do not see them, as with every packaged desktop app; the app reads them back.
- Bad, because a self-signed package installs only with its certificate trusted machine-wide, which needs an administrator, so a developer without one tests the package through the Store or a signed build.
- Neutral: inside a package Windows gives the app the package's AppUserModelID, so the package's `fledge.cfg` leaves out the identifier the launcher would set (ADR 064).

### Confirmation

`test/integration/built_app_test.rb` reads the package back, the schema test holds `msix_publisher`, and Delivery runs `.github/scripts/deliver-msix.ps1` on both Windows architectures.
