# ADR 030: Fledge as Gems, Each Runtime in a Platform Gem

## Status
Accepted (requested). Agents wrote this ADR and may change it (AGENTS.md, Questions), as long as it stays true to the maintainer's words of 2026-11-03 in `decisions.md`: from 1.0.0 a human releases Fledge on RubyGems.org, and the release does not rely on a GitHub Release or a git tag. It is the design half of Plan 003's story "Fledge as gems on RubyGems.org"; the port of RatatuiRuby's bump tooling, the story's other half, is not part of it. It keeps ADR 014's pins, and amends ADR 028, section 7, on how the human publishes (section 8 below).

## Date
2026-11-04

## Context

Today a developer installs Fledge from a git tag, and `fledge build` downloads its platform's runtime from that tag's GitHub Release and checks it against the SHA-256 the gem pins in `lib/fledge/SHA256SUMS` (ADR 014). A gem pushed to RubyGems.org cannot lean on the Release. It has to carry its runtimes, or find them, by itself.

The runtimes are large. `v0.4.0`'s assets, as `gh release view v0.4.0 --json assets` lists them (2026-11-04): each desktop runtime is 19 to 23 MB, and its build-only companion (`-dev.tar.gz`, the static libruby that compiling a gem's extension links) is 0.1 MB on Windows, 19 MB on macOS, 26 to 27 MB on glibc Linux, and 49 to 51 MB on musl Linux; the iOS runtime is 36 MB and the Android one 22 MB; the LGPL source bundles are 4 to 5 MB; NOTICES and SBOMs are under 4 MB.

What RubyGems.org takes, read from its source at `rubygems/rubygems.org` 8b646ca4 (fetched 2026-11-04):

- **Size.** Its front proxy accepts a request body of at most 500 MiB (`config/deploy/nginx-configmap.yaml.erb`, `client_max_body_size 500M`). A gem's `metadata.gz` and `checksums.yaml.gz` may each unpack to at most 10 MiB (`lib/gem_validator/package.rb`, `DEFAULT_MAX_SIZE`). No other limit on a gem's size is in the push path (`app/models/pusher.rb` records the size and checks none). RubyGems.org's support staff gave the same 500 MB figure in 2017 ("Maximum allowed size of a fat binary gem", help.rubygems.org, fetched 2026-11-04), and the guides at guides.rubygems.org name no limit ("Publishing your gem" and "Specification Reference", fetched 2026-11-04).
- **Platforms.** A gem's version may be pushed once per platform (`app/models/version.rb`, `platform_and_number_are_unique`), and RubyGems and Bundler install the one for the computer they run on. The Specification Reference says a gem with precompiled code sets `platform`, which goes into its file name, "such as: nokogiri-1.6.0-x86-mingw32.gem".
- **Where a gem may be pushed.** `allowed_push_host` limits a gem to one host ("Publishing your gem").

The prior art, each read on 2026-11-04 from RubyGems.org's API (`/api/v1/versions/NAME.json`, `/api/v2/rubygems/NAME/versions/VERSION.json`) and the gem files' sizes:

- **sorbet** is pure Ruby and depends on `sorbet-static` at exactly its own version (`= 0.6.13634`). `sorbet-static` is published only for platforms it has a build for (`x86_64-linux`, `aarch64-linux`, `universal-darwin`, `java`), with no `ruby` gem, so installing it where there is no build fails at install. Its Linux gem is 6 MB.
- **tailwindcss-rails** depends on `tailwindcss-ruby`, which carries Tailwind's CLI program, per platform, at 42 MB for `x86_64-linux-gnu`, plus a `ruby` gem.
- **nokogiri** publishes one gem per platform, `x86_64-linux-gnu` and `x86_64-linux-musl` for Linux, plus a `ruby` gem that compiles from source. Its `arm64-darwin` 1.19.7 gem holds an extension for each Ruby minor it supports and declares `required_ruby_version` `>= 3.2, < 4.1.dev`.
- **libv8-node** publishes a 47 MB `x86_64-linux` and a 48 MB `x86_64-linux-musl` gem of V8's library, and a `ruby` gem.
- **polars-df**'s `x86_64-linux` 0.27.1 gem is 119,756,288 bytes, so RubyGems.org takes and serves gems well past 100 MB.
- **grpc** publishes a gem per platform, `x86-linux-gnu` and `x86_64-linux-musl` among them, and a `ruby` gem.
- **oxidize-rb's `cross-gem` action** (`oxidize-rb/actions` e3668653, `cross-gem/action.yml`) builds one gem per platform, for a list of Ruby versions, in CI.
- **PyInstaller** publishes a wheel per platform carrying its bootloaders (`pyinstaller-6.22.3-py3-none-manylinux2014_x86_64.whl`, `musllinux_1_1_x86_64`, `win_arm64`, and the rest; PyPI's JSON API), so `pip install pyinstaller` brings the bootloader for the computer it runs on and nothing else.
- **Briefcase**, **uv**, and **python-build-standalone** do what Fledge does today: the interpreter is a download from a release, which the tool fetches when it builds (ADR 028, section 3; ADR 014).

Tebako was not read for this ADR.

The license policy binds what travels (AGENTS.md, Licensing): an LGPL library ships as a separate shared library a person can replace, "with its source published beside the runtime", and a license that asks only for its source to be published gets that source beside the runtime too.

## Decision

### 1. A plain `fledge` gem, and a `fledge-runtime` gem per platform

The `fledge` gem stays pure Ruby (0.28 MB) and depends on `fledge-runtime` at exactly its own version, as sorbet depends on `sorbet-static`. `fledge-runtime` is published once per desktop platform, and RubyGems and Bundler install the one for the computer they install on. There is no `ruby` platform `fledge-runtime`: Fledge builds an app only on a platform it has a runtime for (ADR 010), so installing it anywhere else fails at install, naming the gem and the platform, as `sorbet-static` does, rather than at the first build.

The other shape weighed was nokogiri's: one name, `fledge`, published once per platform with the runtime inside, and a `ruby` gem that downloads. It needs no second name, but each platform's gem would repeat Fledge's code, the `ruby` gem would be installed silently wherever a lockfile lists only `ruby`, and its builds would download from the GitHub Release, the dependency the maintainer ruled out from 1.0. The two-gem shape keeps Fledge's code in one gem and the runtime in another, and a computer either gets its runtime or is told it has none.

### 2. The platform strings

Each gem's platform is its runtime's Fledge name (`Fledge::RuntimeGem#platform`), except glibc Linux's, which carries `-gnu`:

| Fledge platform | Gem |
|---|---|
| `arm64-darwin` | `fledge-runtime-VERSION-arm64-darwin.gem` |
| `x86_64-linux` | `fledge-runtime-VERSION-x86_64-linux-gnu.gem` |
| `aarch64-linux` | `fledge-runtime-VERSION-aarch64-linux-gnu.gem` |
| `x86_64-linux-musl` | `fledge-runtime-VERSION-x86_64-linux-musl.gem` |
| `aarch64-linux-musl` | `fledge-runtime-VERSION-aarch64-linux-musl.gem` |
| `x64-mingw-ucrt` | `fledge-runtime-VERSION-x64-mingw-ucrt.gem` |
| `aarch64-mingw-ucrt` | `fledge-runtime-VERSION-aarch64-mingw-ucrt.gem` |

RubyGems installs a gem for plain `x86_64-linux` on musl Linux too: `Gem::Platform#===` lets a Linux gem with no version match a host whose version is `musl` (RubyGems 4.0.20, `lib/rubygems/platform.rb`, lines 201 to 221). A `-gnu` gem matches glibc hosts only. nokogiri, tailwindcss-ruby, and grpc name their glibc gems that way for the same reason. `test/runtime_gem_test.rb` holds each gem to installing on its own platform's computers and no other's, and fails when RubyGems stops matching a plain Linux gem on musl, so the suffix can go when the reason does.

### 3. What a runtime gem holds

Every asset of its runtime from the release, byte for byte, in a `runtime` folder: the runtime archive, its build-only companion, its NOTICES, its SPDX SBOM, and, where the platform has one, its LGPL source bundle. `runtime` is the gem's require path, since RubyGems requires one; it holds no Ruby file.

- **The build-only companion stays in the gem.** A separate `fledge-runtime-dev` gem would save a developer who never compiles a gem 19 to 51 MB once, and cost a second set of gems to publish and a second lookup. Every app with a native gem that has no precompiled build needs the companion, and with it in the gem, the first such build works offline too.
- **The LGPL sources and NOTICES travel in the gem.** "Beside the runtime" is most literally true when whoever gets the runtime gets its source in the same file, from the same server, which is the form of offer LGPL-2.1, section 6(d), accepts as (`LICENSES/LGPL-2.1-only.txt`, line 109) "equivalent access to copy the above specified materials from the same place." Separate `fledge-runtime-source` gems would make 4 to 5 MB optional at the cost of five more gems to publish and an offer that a developer must follow to another name. The GitHub Release keeps its copy as long as Releases are made, and every release keeps its tag (ADR 028, section 7).
- **The phones' runtimes are gems of their own,** `fledge-runtime-ios-VERSION.gem` and `fledge-runtime-android-VERSION.gem`, for the `ruby` platform. Android projects are written on macOS, Linux, and Windows, and iOS projects on a Mac (`Fledge::MobilePlatform::HOSTS`), and few developers build for phones, so putting them in the desktop gems would send 22 to 36 MB each to every developer. `fledge` does not depend on them; a developer who builds for a phone adds the gem (`gem "fledge-runtime-ios"`, or `gem install fledge-runtime-ios -v VERSION`).

The gem's `licenses` are every SPDX identifier the SBOM's components' licenses name, each once, since RubyGems takes identifiers, not SPDX expressions (`Gem::Licenses.match?("Ruby OR BSD-2-Clause")` is false in RubyGems 4.0.20). The list says which licenses are involved; the NOTICES and SBOM in the gem say which apply to what.

### 4. How `fledge build` finds a runtime

`Fledge::Runtimes` looks in four places, in order:

1. `FLEDGE_RUNTIME_DIR`, the developer's own runtimes, unchecked (ADR 014, section 1).
2. The installed runtime gem of this Fledge's version (`Gem::Specification.find_all_by_name(NAME, "= VERSION")`, under Bundler the bundle's gems), whose `runtime` folder holds the asset.
3. The cache.
4. A download from this version's GitHub Release into the cache.

The asset from the gem, the cache, or the download must match its pin in `lib/fledge/SHA256SUMS`. One from the gem that does not is refused, naming the file and `gem pristine fledge-runtime --version VERSION`; nothing falls back to a download, since a changed file in an installed gem means something wrote there. The pins stay what ADR 014 made them. RubyGems checks a gem's files against the gem's own `checksums.yaml.gz`, written by whoever built the gem; Bundler's `CHECKSUMS` pin a gem file a developer's lockfile already locked. Neither ties the runtime to the Fledge that runs it. The pins, fixed in the `fledge` gem, do, and checking the gem's copy costs a hash of 20 to 50 MB, as checking the cache already does.

A Fledge installed from a git tag has no runtime gem and downloads, as before; nothing changes for it.

### 5. The dependency is added when the release's gems are built

`fledge.gemspec` does not name `fledge-runtime`. `tasks/release_gems.rb` adds the dependency when it builds the release's `fledge` gem. Were it in the gemspec, every `gem "fledge", git:` and every commit between releases would ask a gem server for a `fledge-runtime` of a version no server has. This is the one difference between the published `fledge` gem and what `gem build fledge.gemspec` writes; the published gem is built only by `tasks/release_gems.rb`.

### 6. The Rubies a runtime gem installs on

Each runtime gem declares the Ruby minor of the runtime it carries, read from the runtime's `rbconfig.rb`, as nokogiri declares the Rubies its precompiled gems carry extensions for: `>= 4.0, < 4.1.dev` today. RubyGems and Bundler then pick a Fledge whose runtime suits the developer's Ruby, the rule `fledge build` enforces (ADR 028, section 3), before anything is installed. When a 1.x release adds a Ruby minor under the reserved names (ADR 029, section 5), its runtime goes into the same platform gem, beside the first, and the requirement widens, as nokogiri's fat gems do: about 40 to 80 MB more a gem, well inside the limit.

### 7. Sizes against RubyGems.org's limit

The gems of `v0.4.0`'s assets, built on 2026-11-04 with `bundle exec rake "gems[ASSETS]"`:

| Gem | Bytes | Share of 500 MiB |
|---|---:|---:|
| `fledge-0.4.0.gem` | 281,088 | 0.1% |
| `fledge-runtime-0.4.0-arm64-darwin.gem` | 38,538,240 | 7% |
| `fledge-runtime-0.4.0-x86_64-linux-gnu.gem` | 53,748,224 | 10% |
| `fledge-runtime-0.4.0-aarch64-linux-gnu.gem` | 54,556,672 | 10% |
| `fledge-runtime-0.4.0-x86_64-linux-musl.gem` | 78,188,032 | 15% |
| `fledge-runtime-0.4.0-aarch64-linux-musl.gem` | 76,655,104 | 15% |
| `fledge-runtime-0.4.0-x64-mingw-ucrt.gem` | 26,613,760 | 5% |
| `fledge-runtime-0.4.0-aarch64-mingw-ucrt.gem` | 26,093,056 | 5% |
| `fledge-runtime-ios-0.4.0.gem` | 36,265,984 | 7% |
| `fledge-runtime-android-0.4.0.gem` | 22,622,720 | 4% |

The largest is musl's, for its 51 MB companion, at 15% of the limit; polars-df serves a 120 MB gem today. `tasks/release_gems.rb` refuses to finish a build with a gem over 500 MiB, so a growth past it fails in CI, not at the push.

### 8. How a release prepares the gems, and how a person publishes them

The gems are built from the very runtimes the release's pins name, in CI, and kept as an artifact. `.github/workflows/gems.yml`, run by hand once the pin commit's short CI has passed, with the pin commit as `ref` and the parent's CI run (the one `rake runtime:pin` pinned) as `run`:

1. builds every gem with `tasks/release_gems.rb`, which refuses unless every asset matches its pin and every pinned asset goes into exactly one gem, and keeps them with their `SHA256SUMS` as the run's `gems` artifact for 30 days;
2. on a fresh runner of each desktop platform, installs `fledge` and its runtime gem with RubyGems, and again with Bundler from a `vendor/cache` holding every gem, into empty gem folders with no network, and builds and runs hello with every download refused (`tasks/gems_check.rb`); and on a Mac and on Linux, installs `fledge` with `fledge-runtime-ios` or `fledge-runtime-android` and writes hello's project.

It is not a job of `ci.yml`: such a job would be skipped on every other commit, and the release commit's run may skip none (ADR 014, section 5). RubyGems writes the same bytes from the same files and spec (`Gem.source_date_epoch`, `DEFAULT_SOURCE_DATE_EPOCH`), and two builds of `v0.4.0`'s gems had the same SHA-256s, so the maintainer can rebuild the gems from the release's assets with `rake gems` and compare.

The maintainer publishes them by hand, with the checklist in `doc/contributors/handoff.md`: each runtime gem, then each phone's, then `fledge`, by `gem push`, so that no moment exists when `fledge` is on RubyGems.org and its runtime is not. The tag and the GitHub Release follow, as ADR 028, section 7, has them, and nothing in the gems relies on either.

The gems' `allowed_push_host` is RubyGems.org from 1.0.0 and `https://fledge.invalid` below it (`ReleaseGems.push_host`), so a gem built before 1.0 cannot be pushed by anyone, by mistake, and `fledge.gemspec` keeps `https://fledge.invalid`, so a hand-run `gem build` and `gem push` publishes nothing. `rake release` stays a refusal. This amends ADR 028, section 7, which had the maintainer run `rake release`: Bundler's release task builds the gem from `fledge.gemspec` and pushes it, which would publish a `fledge` with no runtime dependency and no runtime gems. The SemVer tag and the move of `stable` that RatatuiRuby's `rake release` makes go with the port of its tooling, to run after the pushes.

RubyGems.org's trusted publishing, which lets a workflow push, was not taken: publishing is a human's act (decisions, 2026-11-02, later, and 2026-11-03).

### 9. What changes before 1.0 and at it

Before 1.0 nothing is pushed. A release may run `gems.yml` to rehearse; its gems can be pushed nowhere. `installed.yml` still installs Fledge from the tag, and `fledge build` downloads, as a developer installs it today.

At 1.0's release commit: the README and `README.rdoc` tell developers to `gem install fledge` or add it to a Gemfile, and `gem "fledge-runtime-ios"` or `-android` for phones; each runtime's NOTICES names the runtime gem as a place its LGPL source is published, beside the GitHub Release (`tasks/license_audit/notices.rb`); and `installed.yml` gains a job that installs from RubyGems.org once the maintainer has pushed.

## Consequences

- A developer who installs `fledge` from RubyGems.org, or with Bundler, gets the runtime for their computer in the same install, and builds offline from then on, phones included once their gem is added.
- A developer on a computer Fledge has no runtime for cannot install `fledge` at all, and is told which gem has no build for their platform.
- Each release has ten gems to push, in order, by hand.
- An `x86_64-linux` lockfile entry for the runtime gem is `fledge-runtime (VERSION-x86_64-linux-gnu)`. Bundler 4.0.20 resolved it on a Mac, offline, from a `vendor/cache` of all ten gems, adding the Linux and macOS platforms it adds by default.
- A Gemfile that lists `fledge` outside the `development` group would ship `fledge` and its runtime gem inside the app, as it ships any gem the Gemfile names; Fledge belongs in `development`, which a built app leaves out (`Fledge::Bundle::WITHOUT`).
- RubyGems' local source (`gem install --local` from a folder of `.gem` files) picks a gem by name and version whatever its platform (`Gem::Source::Local#find_gem`), so installing from a folder of every platform's gems takes the first; a gem server, and Bundler's `vendor/cache`, pick by platform. The checklist and `tasks/gems_check.rb` say which file to install.

## Not yet

- The names `fledge`, `fledge-runtime`, `fledge-runtime-ios`, and `fledge-runtime-android` were free on RubyGems.org on 2026-11-04 and are not reserved; whether to reserve them is the maintainer's (`questions.md`).
- A push to RubyGems.org of a 78 MB gem has not been tried; the limit is read from its source and from polars-df's 120 MB gem.
- Bundler resolving the gems from a real gem server, rather than from `vendor/cache`.
- The 1.0 changes of section 9.
