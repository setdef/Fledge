# ADR 032: Build a New App From an App Already Built, With --from

## Context and Problem Statement

`fledge build` needs Ruby, Bundler, the network for the lockfile's gems, and a compiler for a gem with no build for the platform (ADR 005, ADR 006). A person with none of these cannot make an app, even when every gem their program needs is already compiled inside an app Fledge built.

The maintainer put that person in scope on 2026-11-04 (`decisions.md`): "One third of the reason Fledge exists is to support Lota, which is a faithful port of LÖVE2D to Ruby. Drag-to-fuse is a huge part of why LÖVE2D is successful; CLIs can be scary to newbies." Fledge depends on no framework (`decisions.md`, 2026-11-02: "they are expected to depend upon us, not the other way around"), so it gives frameworks general primitives, and each framework builds its own drop-to-make-an-app on them. How does a person with only a built app make an app of their own?

## Decision Drivers

- A newcomer with no Ruby, no network, and no compiler makes an app from a project that needs no other gems.
- The app's code runs as under `ruby main.rb` (Design precedence 2): `__dir__`, `__FILE__`, and backtraces name real files.
- Each system's app is built on that system with its own tools (ADR 010); a step that only copies may make another system's app, if it adds little code, complexity, or room for bugs (`decisions.md`, 2026-11-04, question D: "My main concern was adding a lot of code, complexity, and surface area for bugs re: cross-compiling. Anything that doesn't do those is fine by me.").
- Prior art: LÖVE's fused games, Electron's prebuilt app with the developer's code in `resources/app` and electron-builder's `--prepackaged`, Python's embeddable distribution.

## Considered Options

1. **A self-extracting single file**: a small program that unpacks the app on its end into a per-user cache and starts it there, as warp-packer, PyInstaller's `--onefile`, and electron-builder's `portable` do.
2. **An app that runs from an archive never unpacked**, through a virtual file system, as Tebako builds over libc.
3. **A new app built from an app already built**: copy that app, put the new project in place of its own, and write the new identity with the system's own tools.

## Decision Outcome

Chosen: option 3, because it downloads, resolves, and compiles nothing, needs only Ruby's standard library and the system's tools, and gives the person exactly what `fledge build` would have built. Option 1 makes the first launch wait, leaves a copy per version in a cache, draws antivirus heuristics, cannot be a single file as a macOS `.app`, and names the cache in `__dir__` and `RbConfig.ruby` rather than where the person put the file. Option 2 fails at the root: Ruby cannot `require` from a zip, load a library from one, or keep its prefix in one, which is the virtual file system ADR 001 turns down.

`fledge build --from APP [OPTIONS] [PATH]` builds the project at PATH, taking the runtime, the gems, the `Gemfile`, and the `Gemfile.lock` from APP, a folder Fledge built. The project's own `fledge.yml` gives the new app its whole identity. `--from` refuses a project with gems of its own, and keys that change the runtime or the gems. An app that is to run `fledge build --from` itself sets `build_tools: true`. `--from` builds for its own platform only (`doc/contributors/design/desktop-apps.md`, "Building from a built app").

Confidence: high for its own platform, which Delivery proves on fresh runners with no Ruby; medium for frameworks' use of it, which no framework has shipped yet.

### Consequences

- Good, because a person with nothing installed but a framework's app makes an app of their own, on that platform, from a project that needs no gems beyond the ones that app ships.
- Good, because the new app holds its project as plain files, and keeps APP's runtime, gems, lockfile, and `notices/` unchanged.
- Bad, because every app built `--from` is as large as APP, and carries Fledge's own Ruby code as a gem.
- Bad, because Fledge gains an option and two keys to keep through 1.x (ADR 029).
- Bad, because an unsigned downloaded APP meets Gatekeeper's and SmartScreen's warnings before anyone builds from it.
- Bad, because `build_tools` cannot carry `mksquashfs`, which is GPL-2.0 and so no part of a runtime; a framework whose users lack squashfs-tools asks for no AppImage.

### Confirmation

`test/build_from_test.rb` and `test/integration/built_app_test.rb` hold the command, its refusals, and `build_tools`. Delivery builds a new app `--from` a built one on one runner and runs it on another (`.github/scripts/deliver-from.sh` and `.ps1`).
