# ADR 078: A phone app's standard streams reach the system log as they are printed, with nothing an app can read changed

## Context and Problem Statement

iOS and Android discard what an app writes to standard output and standard error. On a phone the system log (os_log, logcat) is the only place an app's output can go, and a developer reads it to watch the app run, as one watches a terminal under `ruby main.rb`.

Two things decide whether that works. Where the output is taken: Ruby's `$stdout`, or the process's descriptors 1 and 2, which a C extension and Ruby's own warnings write to as well. And when it arrives: Ruby writes through to a terminal, but buffers standard output to a pipe until the buffer fills or the program ends (`io.c`, `io_binwrite_requires_flush_write`, lines 1941 to 1954 at Ruby 4.1.0-preview1). A game a framework ran in the iPad Simulator logged nothing until it ended, until the game set `$stdout.sync = true` itself. Whatever makes lines arrive must leave what an app reads as `ruby main.rb` leaves it: the maintainer, 2026-11-12 (`decisions.md`), accepts a difference only when it is inherent to where the app ships or truly forbidden by the platform, for "Every difference, every lack of parity, is a knife in Fledge's back." How do a phone app's streams reach the log, and when?

## Decision Drivers

- Everything the app prints reaches the log, its C extensions' output and Ruby's warnings included.
- A line reaches the log when it is printed, as it reaches a terminal.
- `$stdout.sync` is false and `$stdout.tty?` is false, as under `ruby main.rb` with its output to a pipe: a phone has no terminal, and a library that colors terminal output must not send escape codes into the log.
- Prior art: Briefcase's iOS host unbuffers Python's streams, "We want output to appears in the log immediately" (`config.buffered_stdio = 0`); CPython's iOS and Android streams are line-buffered and never claim to be a terminal; Chaquopy's Android stream flushes at each newline.

## Considered Options

1. The embedding API forwards descriptors 1 and 2, each the write end of a pipe a thread reads line by line into the log; gives `$stdout`'s IO the `FMODE_TTY` flag Ruby gives an IO it opens on a terminal, without a terminal; and on Apple's systems leaves the streams alone when `OS_ACTIVITY_DT_MODE` is set.
2. The same forwarding, with `$stdout.sync = true` whenever descriptor 1 is not a terminal.
3. Replace only the language's stream objects with ones that call the log, as CPython's iOS support replaces `sys.stdout` and `sys.stderr`.
4. Make descriptor 1 a pseudo-terminal, which Ruby writes through to.
5. Forward the descriptors and leave `$stdout` buffered, or its sync mode to each developer.

## Decision Outcome

Chosen: option 1. Forwarding the descriptors catches what C extensions and Ruby itself write, which option 3 misses. Ruby already writes a terminal's output line by line through `FMODE_TTY` (`io.c`, lines 1945, 2326, and 5334), and the flag touches nothing an app can read: `$stdout.sync` stays false, and `$stdout.tty?` asks `isatty` of the descriptor (line 5547), so it stays false too. The runtime sets it once, before the program writes (`write_lines_as_printed`). `include/ruby/io.h`'s comment on the field, "You cannot change this" (lines 188 to 191), says that Ruby sets the flag as it opens an IO, not that anything forbids setting it after.

Option 2, which the runtimes shipped until 2026-11-13, makes `$stdout.sync` true on a phone and false under `ruby main.rb`, a difference any app can read. Option 4 makes `$stdout.tty?` true, so libraries color the log and `IO#winsize` answers for a window that does not exist. Option 5 hides an app's log until it ends, which is what surprised the framework's developer.

Forwarding the descriptors makes a loop that option 3 never meets. `OS_ACTIVITY_DT_MODE` makes the unified log copy each entry to standard error for a developer tool that reads the app's streams. Under it, the forwarding thread read the log's copy back from its own pipe and logged it again, nested in the next copy, until the pipe filled and Ruby's `puts` blocked. So on Apple's systems `fledge_ruby_forward_output` does nothing when the variable is present, whatever its value: the tool that asked for the copy reads the streams itself. Android's logcat copies nothing, so it always forwards.

Confidence: high. The mobile parity check runs on CI's iPhone and iPad Simulators and both Android emulators with `$stdout.sync` compared exactly and no justification for it; a line printed before a sleep reaches `os_log` during it on a Mac, and the log during it on the Simulators and emulators; and each app's line is printed once under `OS_ACTIVITY_DT_MODE`.

### Consequences

- Good, because a developer watches the app's lines in Console, `log stream`, or `adb logcat` as they are printed, away from Xcode as from it, and a developer tool that sets the variable shows each line once, from the app's streams.
- Good, because a phone app's `$stdout.sync` and `$stdout.tty?` are what `ruby main.rb` gives with its output to a pipe.
- Bad, because `$stdout` writes through on a phone where `ruby main.rb` with its output to a pipe buffers, which `Parity::MOBILE_JUSTIFIED` justifies as the fact "$stdout writes through".
- Bad, because Ruby's header deprecates writing the field, so the runtime sets it under a compiler pragma, and a later Ruby that moves the flag needs the runtime changed with it.
- Bad, because the rule for Apple's systems rests on `OS_ACTIVITY_DT_MODE`, which Apple calls "an implementation detail" (Quinn, Apple DTS, developer.apple.com/forums/thread/705868). If Apple changes it, the check changes with it.
- Bad, because a log entry holds less than a long line, so such a line goes as several entries in a row.

### Confirmation

`test/integration/mobile_output_test.rb` runs `output.c` and `apple.c` with the real `os_log` on a Mac, with and without the variable, and runs `fledge_ruby.c` linked with the test Ruby to check that a line printed before a sleep reaches the log during it. The mobile parity check compares `$stdout.sync` exactly on both phones, and its probe's fact "$stdout writes through" is measured from Ruby's own warning for a buffered IO.
