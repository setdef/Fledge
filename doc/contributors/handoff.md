# Handoff

Start here if you are a session with no memory of the ones before you. This page says where Fledge stands, how to check it, how to release it, and what to do next. Agents wrote it and keep it current (AGENTS.md, Provenance); when you finish a story or cut a release, update it in the same commit as the plan.

Read these next, in order: `AGENTS.md` (how to work here, and binding), `doc/contributors/decisions.md` (the maintainer's own words, the only authority; never write to it except to add an answer from `questions.md`), `doc/contributors/questions.md`, the plan of record (`doc/contributors/plan/003.md`), and the ADRs its stories cite.

## Where Fledge stands

Fledge is MIT, copyright setdef, since 2026-11-07 (decisions, 2026-11-07): every file of Fledge's own says so, `LICENSE` holds the text, and each app's `notices/NOTICES.txt` carries it. `v0.7.0` and every earlier tag were released under AGPL-3.0-or-later and keep it; the first release after them is the first under MIT, and it drops the `notices/MODIFIED.txt` the AGPL asked for.

The latest release is [`v0.11.0`](https://github.com/setdef/Fledge/releases/tag/v0.11.0), the last on Ruby 4.0.9 (decisions, 2026-11-09), which has everything 1.0.0 will have so far (decisions, 2026-11-08): `fledge build` takes a gem's locked source build when its precompiled build's `required_ruby_version` excludes the runtime's Ruby. The next, 0.12.0, moves every runtime to Ruby 4.1 (ADR 056): 4.1.0-preview1 on macOS, Linux, and the phones, and on Windows RubyInstaller's head build of Ruby's main branch of 2026-11-10, the nearest signed build to the preview's day (ADR 066), which Fledge keeps as a pre-release of its own, `inputs-rubyinstaller-head-20261110`, since RubyInstaller replaces it every night (ADR 065). `.github/workflows/keep-rubyinstaller-head.yml` keeps the head build of each later Ruby 4.1 release's day the same way (`doc/contributors/design/runtimes.md`, "Keeping RubyInstaller's head build"), and each of those releases moves every platform in one Fledge release. ## How to check it

- **The gate**: `bundle exec rake` on your computer, after `bundle exec rake rubocop:autocorrect_all`. It must pass with no errors and no warnings. It skips what needs a runtime unless you build one with `bundle exec rake runtime`.
- **CI**: every push to `trunk` runs `.github/workflows/ci.yml`, about 30 minutes: the gate, every runtime, the tests and parity on each platform, each platform building its own apps, and Delivery on fresh runners. `gh run list --branch trunk --limit 3`, then `gh run view RUN --json conclusion,jobs --jq '.jobs[]|select(.conclusion!="success")|.name'` to see what did not pass, and `gh run view RUN --log-failed | tail -80` to read why.
- **ruby/spec**: `ci.yml` calls `ruby-spec.yml`, which runs ruby/spec on stock Ruby and in a built app from each runtime and fails on an example that fails on one side only, unless `RubySpec::JUSTIFIED` (`tasks/ruby_spec.rb`) explains it: on every push for x86_64-linux and arm64-darwin and in phone apps, in the iOS Simulator on an iPhone and an iPad and on Android emulators with 4 KB and 16 KB pages (`RubySpec::Phone`, against stock Ruby on the Mac or Linux runner, with `RubySpec::Phone::EXCLUDED` leaving out what no phone can run), on a release commit for all seven desktop platforms too, and every night for all of them on trunk's newest green runtimes. `bundle exec rake ruby_spec` runs the desktop's here after `bundle exec rake runtime`, and `ruby tasks/ruby_spec.rb ios RUNTIMES_DIR`, or `android-build RUNTIMES_DIR` and then `android` with an emulator running, the phones'; each run's MSpec output is in `tmp/ruby-spec` (`tmp/ruby-spec-ios`, `tmp/ruby-spec-android`), and in CI in the `ruby-spec-PLATFORM` artifact (`ruby-spec-ios`, `ruby-spec-android-TARGET`).
- **Releases**: `gh release view vX.Y.Z` lists the assets; `gh run list --workflow release.yml --limit 2` shows the release run, which ends by calling `installed.yml`.
- **installed.yml**: it installs Fledge from the tag on a fresh runner of every platform, downloads the release's runtimes, checks them against the tag's pins, and builds and delivers the examples. Its jobs are part of the release run; a release is not verified until they pass.

## How to release

A release is two commits and a tag (AGENTS.md, Releasing; ADR 014):

1. **The release commit**, `chore: release X.Y.Z`: set `Fledge::VERSION` in `lib/fledge/version.rb`; change the old version to the new one in `Gemfile.lock`, README.md and README.rdoc, `doc/licensing.md`, and the `$id` of `lib/fledge/config.schema.json` and the modeline in `Fledge::Config`'s RDoc, which `test/config_schema_test.rb` holds to `Fledge::VERSION`; move the CHANGELOG's Unreleased entries under `## [X.Y.Z] - DATE` and add its link; mark each story it ships "First released in" in the plan. Run the gate, push, and wait for CI to pass on every job.
2. **The pin commit**, `chore: pin X.Y.Z's runtimes`: `bundle exec rake runtime:pin` downloads the runtimes the release commit's CI run built and writes `lib/fledge/SHA256SUMS`. It refuses unless that run passed on every job. Commit that file alone (`git commit lib/fledge/SHA256SUMS`), push, and wait for CI: a pin commit's run is short, the gate and the `Changes` job, which checks the pins against the release commit's runtimes, with every other job skipped (ADR 053; `doc/contributors/design/releases.md`, "A pin commit's short CI").
3. **The tag**: `git tag -a vX.Y.Z -m "Fledge X.Y.Z" PIN_COMMIT && git push origin vX.Y.Z`. `release.yml` does not run CI again: it refuses a tag whose commit changes anything but the pins, whose short CI run on `trunk` has not passed (or is still running), whose parent's run did not pass on every job, or whose pins do not match the runtimes of the parent's run. Watch its run, then `gh release view vX.Y.Z`. A run refused only because a CI run had not finished can be run again once it passes, with `gh run rerun RUN`. After any change to `release.yml`, try it before the next tag depends on it: `gh workflow run release.yml --ref BRANCH -f tag=vLAST` runs every check of a release against the last tag and its runtimes, with the workflow and scripts of BRANCH, and publishes nothing unless given `-f publish=true`.

For `1.0.0`, the release commit also makes the gem pushable and changes the install line, and after the tag the maintainer publishes the gem by hand: `doc/contributors/releasing-1.0.md` lists both. Agents never run `gem push`.

Do all three within 14 days, while CI keeps the runtimes. Never delete a release: each runtime's NOTICES links its LGPL sources there, after the copy in the app's own `notices/sources/`. During a release, pushing to `trunk` cancels the CI run in progress there, and the pin commit needs that run's runtimes, so do not push between the release commit and its CI run's end. Outside a release, push whenever a step is done.

## Known CI flakes, and what to do

- **A macOS job cancelled before any step ran**: the runner never started. Re-run the failed jobs with `gh run rerun RUN --failed`.
- **A run cancelled outright**: a later push to the same branch superseded it (`concurrency` in `ci.yml`); the later run is the one that counts.
- **Mobile jobs that time out**: the iOS Simulator and Android emulators sometimes boot slowly. Read the log; if the app never started, re-run the job, and if it did start, it is a real failure.
- **`apk` says `unable to select packages` and `breaks: world[NAME=VERSION]`** in a musl job: not a flake. Alpine keeps only the newest build of each package in a branch, so when it publishes a new one, the pin in `.github/scripts/alpine-packages.sh` stops resolving. A re-run fails the same way. Find the version Alpine now has (`apk policy NAME` in the pinned image), move the pin, and run each role of the script in that image before pushing.
- **mise's Ruby download timing out after 20 seconds**: a flake of the download; re-run the failed jobs.
- **Anything else**: root-cause it before re-running (AGENTS.md, How to work). A failure that passes on a re-run is still worth a sentence in this list once you know why.
