# ADR 033: Notarize on Request, Through a notarytool Keychain Profile

## Context and Problem Statement

Gatekeeper opens a downloaded Mac app without a warning only when Apple has notarized it. `--sign` (ADR 016) signs an app with a Developer ID, but a signature alone still meets "Apple could not verify" on a person's Mac. Notarizing means sending the app to Apple's notary service with the developer's credentials, waiting for its answer, and stapling the ticket it issues to what ships.

Decision 17 (`decisions.md`, 2026-10-26) asks that a developer who has done Apple's ceremony be able to make macOS not block the app. The maintainer pays for the accounts the work needs and opens them himself (`decisions.md`, 2026-11-04: "I've decided to pay Apple, Microsoft, Google, whoever I need."). How does `fledge build` notarize, and where do its credentials come from?

## Decision Drivers

- Decision 17: the developer's option, with builds that do not notarize unchanged.
- Credentials never pass through Fledge, never sit on a command line where another process can read them, and never sit in `fledge.yml`, which other people build too.
- Notarizing needs the network, an account, and minutes of waiting, which a developer's every signed build should not pay.
- A developer with several teams or keys picks one.

## Considered Options

1. `fledge build --sign IDENTITY --notarize PROFILE`, where PROFILE names a keychain profile the developer made once with `xcrun notarytool store-credentials`.
2. Notarize whenever signing with a real identity, with a profile derived from the team, as Briefcase does.
3. Credentials from the environment, passed to notarytool as arguments, as Tauri's `APPLE_ID`, `APPLE_PASSWORD`, and `APPLE_API_KEY` and @electron/notarize's options are.

## Decision Outcome

Chosen: option 1, because a keychain profile is what Apple made "to avoid including your password as cleartext in a script", it keeps every secret out of Fledge and off its command lines, and asking for it keeps a signed build offline and immediate.

Fledge passes notarytool `--keychain-profile PROFILE` and nothing else that authenticates. No environment variable stands for the option, since the profile is no secret and a variable that made every signed build wait on Apple would surprise. `--notarize` without `--sign`, or with a phone, is a usage error; for Windows, or with the ad hoc identity `-`, which Apple does not notarize, the build fails. Fledge sends the outermost container, staples the ticket, and only then packs the archive, so the archive carries the stapled bundle.

Confidence: medium. Every command, its order, and Apple's answers are tested against a stand-in for notarytool and stapler, built from Apple's documentation and the prior art's source; no run has reached Apple's real service.

### Consequences

- Good, because a developer with a Developer ID notarizes with one option and a profile made once, and one without changes nothing.
- Good, because the profile works with an App Store Connect API key as with an Apple ID and an app-specific password (TN3147), so either kind of credential serves.
- Bad, because a notarized build waits for Apple, usually minutes, and fails without the network.
- Bad, because every macOS build writes its disk image before its archive, so that the archive can carry a stapled bundle.
- Bad, because a failed submission is not sent again, as codesign's timestamps are: a submission is a new request, and Apple limits them to 75 a day.
- Bad, because whether Apple accepts what Fledge signs, and Gatekeeper's verdict on a downloaded copy, wait on the maintainer's own run.

### Confirmation

`test/notary_test.rb` runs every command against `test/support/stand_in_notary.rb`, an `xcrun` first on `PATH` that answers as notarytool and stapler do, and checks that no authenticating option reaches a command line. `test/built_app_test.rb` builds `examples/windowed_app` and `examples/hello` with `--notarize` and the stand-in, and fails if the archive is packed before notarizing. Its `test_a_notarized_build_opens_with_gatekeepers_blessing` runs Apple's real service when `FLEDGE_TEST_NOTARY_PROFILE` is set; the maintainer runs it (`doc/contributors/signing-test.md`; `doc/contributors/account-tests.md`, MAC-1 and MAC-2).
