# ADR 093: Prebuild Each Platform's Runtime in Fledge's CI, and Publish It with the Release

## Context and Problem Statement

An app built with Fledge carries a relocatable Ruby beside the launcher that embeds it (ADR 001). The Ruby on the developer's own computer cannot be that Ruby: one built by a version manager or a package manager records absolute paths and links the machine's shared libraries. Someone has to build a relocatable Ruby for each platform, with its standard library, Fledge's launcher, and its notices, and pass it through the license audit. Who builds it, and when: Fledge, once per release, or each developer, on each computer that builds an app?

## Decision Drivers

- A developer should not need to build a Ruby, or own the toolchain that builds one, to ship an app.
- Every app of one Fledge version should carry the same tested runtime, checked by SHA-256 (`doc/contributors/design/releases.md`, "The pins").
- The runtime must pass the license audit before anything is archived (`doc/contributors/design/license-audit.md`), which needs the license map and its tools.

## Considered Options

1. **Fledge's CI builds one runtime per platform and publishes it as an asset of the release;** `fledge build` downloads it, caches it, and checks it against the SHA-256 its gem pins.

## Decision Outcome

Chosen: option 1, "so that no developer needs to build a Ruby", with python-build-standalone as the model: prebuilt, relocatable CPython builds, published as release assets and pinned by hash, which Briefcase, uv, and others consume rather than building Python themselves. No alternative was weighed when this was decided. The section below reports alternatives found later; they were never the reason. What a runtime holds, and how each is built and published, is `doc/contributors/design/runtimes.md`.

Confidence: high that it works: every Delivery job in CI builds apps from runtimes made this way and runs them on a fresh computer with no Ruby. No recorded comparison says it is better than the alternatives below.

### Consequences

- Good, because a developer needs only a Ruby to run `fledge build` and, for compiled gems, a compiler. Ruby's own build, its libraries, and the audit stay in Fledge's CI.
- Good, because the runtime an app gets is the one CI tested, audited, and delivered, byte for byte.
- Bad, because prebuilt runtimes are part of the product, not an optimization: a Fledge version is tied to the runtimes it pins, and every release builds and publishes dozens of assets.
- Bad, because `fledge build` needs the release's host, or a mirror (`doc/contributors/design/runtimes.md`, "Where fledge build finds a runtime"), the first time it builds for a platform on a computer.
- Bad, because a release needs the CI run that built its runtimes to still hold them (`doc/contributors/design/releases.md`, "How a release is made").

### Confirmation

CI's "Runtime" jobs build every platform's runtime on each push, and `release.yml` publishes them and refuses a release whose assets or pins do not match. `installed.yml` installs Fledge from each tag, downloads the runtimes from the release, and delivers hello.

## More Information

### Later research (2026-11-21)

These alternatives were looked up after the decision. They inform a reader; they were never its reason.

- **Prebuilt portable Rubies from another project.** Traveling Ruby (github.com/trubygems/traveling-ruby, a fork of the unmaintained phusion/traveling-ruby) publishes self-contained Rubies 3.3, 3.4, and 4.0 for glibc and musl Linux, macOS, and Windows, on x86-64 and ARM64, each release with a `SHA256SUMS` file and the native extensions of popular gems prebuilt. Its `truby` packager (the `traveling-ruby` gem, 0.1.0) puts an app and its locked gems beside one of those Rubies, with a launcher script that runs `ruby -rbundler/setup`, and packages for every platform from one computer, since it compiles nothing. Fledge also consumes other projects' prebuilt Rubies (ADR 035); what it adds is a compiled launcher that runs the program in its own process (ADR 001, ADR 081), gems compiled on each platform, desktop and phone apps, and the license audit.
- **Prebuilt runtimes the app fetches when it runs.** Tebako v2 (github.com/tamatebako/tebako) builds patched Rubies 3.1 to 4.0 in its own factory repositories, and a packed app downloads one into `~/.tebako` on its first run, checked by SHA-256, and shares it with every Tebako app on the computer. Fledge's runtime arrives with the app, so the app needs no network when it starts.
- **Building on the developer's computer.** Tebako's first version, now archived as tamatebako/tebako-v1, compiled Ruby from source on the computer that packaged the app. ruby-build (github.com/rbenv/ruby-build) compiles a Ruby into a prefix on the developer's computer. Both need a full C toolchain and Ruby's build dependencies on every computer that builds an app, and give each developer a Ruby that CI never tested.
- **Freezing the developer's own interpreter.** PyInstaller copies the Python that runs it, with its shared libraries, into the app, and Ocran (github.com/largo/ocran) does the same with the developer's Ruby, carrying the shared libraries it loaded but not glibc, so a Linux app runs only where glibc is as new as the build computer's. ADR 001 records why Fledge does not copy a developer's Ruby.
