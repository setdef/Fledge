# ADR 004: Every Runtime Passes a License Audit, and Every Release Publishes What It Found

## Status
Accepted (requested). Amended by ADR 010 (2026-10-28), which allows an LGPL library linked into a component whose source Fledge publishes, and a license that asks only for its source to be published, and on 2026-11-03 by section 9, which lets a source pin name mirrors, and on 2026-11-06 by section 10, which has each Windows app say that `fledge build` modified its programs, and when; section 10 is superseded by the maintainer's decision of 2026-11-07 that Fledge is MIT. Section 5 amended 2026-11-04: each runtime, and so each app, carries the sources in `notices/sources/`. Agents wrote this ADR and may change it (AGENTS.md, Questions). It applies the maintainer's decisions 1, 8, and 24 and the replies of 2026-10-26 in `doc/contributors/decisions.md`, and the orchestrating agent's directions of 2026-10-27, which settled what the spike on `spike/permissive` left open: LGPL libraries stay as separate shared libraries with their source published by Fledge, Fledge's own files stay AGPL-3.0-or-later with no runtime exception, and Fledge hosts the LGPL sources permanently as release assets. Section 7, and the part of section 8 about an app's own gems, are superseded by ADR 007, which applies the maintainer's words of 2026-10-28: the policy here is for what Fledge itself puts into an app, its runtime, and an app's own gems, licenses and all, are its developer's.

## Date
2026-10-27

## Context

Everything in a runtime is copied into every app built with it, so the app's developer distributes all of it. The maintainer's rule is that a developer who buys a commercial license must be able to ship an app with no copyleft obligation beyond notices (decision 8), that an LGPL library may ship only as a separate shared library whose source, never the app's, is published ("Source offer for... the app? Or the LGPL'ed library? Former won't be liked, latter is fine and normal"), that developers are told plainly what they owe ("As long as we're clear about that to app devs, that's great"), and that the list of what ships is generated by the pipeline, not written by hand ("Better to automate this as part of the DevOps pipeline, yes?").

The spike on `spike/permissive` (findings in its `FINDINGS.txt`, at 58edf27, kept in `doc/contributors/research/2026-10-27-permissive-spike.md`) built a license audit in Ruby's standard library alone and ran it on the four runtimes and on the whole trees they come from. It found every runtime within the rule, rv-ruby's own Linux `bin/ruby` outside it (libxcrypt, which is LGPL-2.1-or-later, linked statically), and nkf's JRuby sources (EPL-2.0 OR LGPL-2.1-or-later) the one copyleft text a runtime carries. It priced the alternatives to the two LGPL libraries: musl's crypt in place of libxcrypt silently computes a wrong (DES) hash for yescrypt, the default password hash of current Debian, Ubuntu, and Fedora; and a Windows Ruby built without GMP means forking RubyInstaller's packaging onto MSYS2's rolling toolchain. Trunk had since gained the bundled gems, its own `bin/ruby` built from `runtime/launcher/ruby_main.c`, and the gems' executables, none of which the spike's runtimes carried.

Prior art: cargo-deny's `licenses` check fails a Rust build on any dependency whose license is not on an allow list; the SPDX 2.3 specification defines the software bill of materials format, and the SPDX project's `pyspdxtools` validates it; the REUSE specification, which this repository already follows, attributes every file.

## Decision

### 1. The policy is a file, and the build enforces it

`runtime/licenses.yml` holds the policy and the map. A component's SPDX license expression is judged as SPDX 2.3, annex D, reads it (`OR` takes the least restrictive choice, `AND` the most restrictive part, `WITH` an allowed exception lifts the license it follows), into one of:

- **notice-only** (MIT, BSD, Apache-2.0, Zlib, Ruby, PSF-2.0, OFL-1.1, CC-BY-2.5, the MinGW-w64 runtime's, and the others listed), allowed;
- **first-party**, Fledge's own AGPL-3.0-or-later files (the launcher and `rubygems/defaults/operating_system.rb`), allowed and named as Fledge's;
- **file-level** (MPL-2.0, EPL-2.0), allowed only for a component that ships as unmodified files, such as the CA bundle, whose source form is the file itself;
- **shared-library** (the LGPL), allowed only for a component that ships as its own shared library and has a source pin in `runtime/sources.yml`, or, since ADR 010, that is linked into another component that is not Fledge's own and whose source Fledge publishes too (libfuse, in AppImage's runtime);
- **source-offer** (CPL-1.0, since ADR 010), allowed only for a component whose source Fledge publishes (NSIS, whose LZMA module is under it);
- anything else, unknown licenses and a gem that declares none included, which fails.

`RuntimeBuilder#license` runs the audit (`tasks/license_audit.rb`) on the staged runtime of every platform, after the recipe builds it and before anything is archived, and raises `LicenseAudit::Failure`, naming every violation, when it fails. No runtime that breaks the policy is ever archived, so none reaches a CI artifact, a test, Delivery, or a release.

### 2. The audit reads the runtime, not the build's intentions

It walks every file and gives each to a component of the map or to a gem whose specification the tree holds, and fails on a file no one owns. It reads every compiled file's links itself, in Ruby (ELF dynamic sections, Mach-O dylib commands, PE import and delay-import tables, and the assemblies a Windows manifest names), so one Linux runner audits all four platforms, and fails on a library neither the operating system nor the runtime provides and on a compiled file its owner does not list. It proves each component compiled into another file is still there, at the version the map names, by a string in the binary (`OpenSSL 3.6.2 `, Ruby's revision `3e93b23afc`, Rust's `/rustc/4eb1612.../`, `GCC: (`), so the map cannot go stale quietly. It fails when libxcrypt's or GMP's code (by byte signatures) is in any file but that library's own shared library, when a pinned file's SHA-256 moves (GMP's DLL), and when a text file names a copyleft license and no one has reviewed it. It also opens each gem's `.gem` in RubyGems' cache, which holds files Ruby never installed into the gem's folder, and checks its files the same way. A gem's executables in `bin/` belong to the gem.

On trunk's runtimes the audit confirms what the spike could only predict: `bin/ruby` is Fledge's own build of Ruby's `main.c`, not rv-ruby's, it needs `libcrypt.so.2` from the runtime's `lib/` through its RPATH (`$ORIGIN/../lib`), and it holds no libxcrypt code. rv-ruby's own `bin/ruby` never ships. CI's "Licenses of the whole upstream tree" jobs audit rv-ruby's and RubyInstaller's whole trees and require exactly the findings `.github/license-expectations/` lists (rv-ruby's static libxcrypt in its `bin/ruby` and `libcrypt.a`, nkf's Java sources, MSYS2's GPL keyring), so the audit is shown catching the real thing on every push, and CI's "Licenses" jobs plant a GPL extension, in each platform's own binary format, and a GPL gem in each built runtime and require the audit to fail naming both.

### 3. What the audit finds is what ships

From the same report it writes `notices/NOTICES.txt`, which names every component, its version, license, how it ships, and where its source is, says where the source of Fledge's own files is, says for each LGPL library that it may be replaced and where its exact source is, and then holds the full text of every license, so it stands alone wherever it is copied; and `notices/sbom.spdx.json`, an SPDX 2.3 SBOM listing every file with its SHA-1 and SHA-256, a package per component and gem, and `CONTAINS`, `STATIC_LINK`, and `DYNAMIC_LINK` relationships. CI validates every SBOM with `pyspdxtools` 0.8.3. These replace `notices/README.txt` and the folders of license texts, and `runtime/sources.yml` no longer lists notices: the map is the one place a component's license and notice are recorded. A component whose license text is nowhere fails the build.

### 4. The two LGPL libraries stay, as shared libraries Fledge publishes the source of

libxcrypt 4.5.2 ships on Linux as `lib/libcrypt.so.2`, built by the runtime builder from its pinned release, and GNU MP 6.3.0 on Windows as RubyInstaller's `ruby\bin\ruby_builtin_dlls\libgmp-10.dll`. Neither is linked into any other file. musl's crypt is not a replacement (it gets yescrypt wrong), and a GMP-free Windows Ruby would be a fork to maintain. CI proves the claim made to developers, that whoever receives an app can replace each: "Replace libcrypt" swaps in a libxcrypt rebuilt with only strong hashes and musl's crypt and checks the app loads and behaves as each does; "Replace GMP" swaps in a GNU MP 6.2.1 cross-built with the pinned llvm-mingw and checks `Integer::GMP_VERSION` changes while a large product does not. The runtime job checks that MSYS2's binary package of GMP 6.3.0-2 holds RubyInstaller's DLL byte for byte, which is what makes MSYS2's source package its exact source.

### 5. Every release publishes each runtime's SBOM, NOTICES, and LGPL sources, and is never deleted

The runtime builder writes, beside each archive, the release assets that describe it, named by `RuntimeBuilder#assets`: `fledge-runtime-VERSION-PLATFORM.tar.gz`, `.spdx.json`, `-NOTICES.txt` (copies of the files inside the archive, which CI compares), and, where the platform ships an LGPL library, `-lgpl-sources.tar.gz`, holding the pinned source exactly as published, its license, and a `BUILD.txt` that says how the runtime's copy was built and how to replace it. `release.yml` attaches all of them and a `SHA256SUMS` over them (the gem's own pins since ADR 014), checks that they are exactly `RuntimeBuilder.release_assets` (whose runtime names are `Fledge::Runtimes.file_name`'s), and marks a version with "pre" in it a prerelease. Each runtime's NOTICES links its source bundle at the release, so releases are never deleted. After publishing, `installed.yml` installs Fledge from the tag with Bundler on a fresh runner of each platform, builds hello with runtimes downloaded from the release, and delivers it.

**The sources travel inside the runtime (amended 2026-11-04).** Until 0.4.0, the release asset was the only place a recipient could get the source, and every app shipped named it. The LGPL binds whoever conveys the library, and that is the app's developer, who conveys it inside the app; their compliance depended on a host that could change its terms or vanish, and on Fledge keeping every release. The maintainer's replies of 2026-10-26 accept a source offer for "the LGPL'ed library" ("latter is fine and normal"), "as long as we're clear about that to app devs"; plan 003 asks that the source offer "not name a host that is the only place it can be had". LGPL-2.1, section 6(a), offers the one way that needs no host at all: "Accompany the work with the complete corresponding machine-readable source code for the Library". GPL-3.0, section 6, which LGPL-3.0 uses for GMP, likewise lets source go with the object code, on the same medium (6(a)) or "in the same way through the same place" (6(d)).

So each runtime now carries, in `notices/sources/`, one folder per component that runtime/licenses.yml gives a source pin and the platform ships, with the same contents as that component's folder in the source bundle: the pinned archive exactly as downloaded, its license texts, and `BUILD.txt` (`LicenseAudit::SourceBundle#copy_into`). The runtime builder writes it before the audit, so the audit, the SBOM, and `NOTICES.txt` see it. Every app copies the runtime's `notices/`, and every installer holds the app, so an app that keeps its `notices/` folder is accompanied by the source wherever it goes. `NOTICES.txt` names the folder in the app first and the release's bundle second. The release keeps publishing the bundle, which CI compares with the runtime's folder file by file, for anyone who wants the source without an app. The audit now walks `notices/` too, except the two files it writes (`NOTICES.txt` and `sbom.spdx.json`), and each folder is owned by a component of kind `source` in runtime/licenses.yml (`libxcrypt-source`, `gmp-source`, `appimage-runtime-source`, `libfuse-source`, `nsis-source`), whose license is the component's; the policy allows a `source` component only for a pinned source, and only for files of `notices/sources/` that are not compiled code, so any other file there is unaccounted and fails as before.

What each platform carries, from runtime/licenses.yml: glibc Linux, libxcrypt's source, and AppImage's runtime's with the libfuse linked into it, which ship in the runtime's `tools/` for its AppImage; musl Linux, AppImage's runtime and libfuse, since musl's own crypt serves in place of libxcrypt (ADR 017); Windows, on x64 and on ARM64, GNU MP's and NSIS's, whose LZMA module's Common Public License asks that its source be available (ADR 010); macOS, iOS, and Android, nothing, and no `notices/sources/` at all. An app for Linux or Windows that is not windowed carries the installer tools' sources too, though it never holds the tools: `notices/` is one folder for every app, and the sources cost a few megabytes, and "Tiny filesize is not a priority" (decision 20). Measured against `trunk`'s run 41966470848, the runtime archives of the experiment's run 41971986753 grew by 5.34 MB on `x86_64-linux` (22.3 to 27.6 MB) and 5.32 MB on `aarch64-linux`, 4.64 MB on each musl Linux, and 3.95 MB on each Windows, about the size of each source bundle, since the sources are already compressed.

CI proves it on Delivery: each Linux and Windows app holds each folder, with the archive whose SHA-256 its `BUILD.txt` names, and its NOTICES names the folder; each AppImage holds AppImage's runtime's and libfuse's; and Replace libcrypt builds its modified libxcrypt from the source in the app it replaces it in, as a person who received only the app would. Replace GMP builds an older GNU MP from upstream, as before, since it shows a different version loading and needs no particular source.

### 6. Pruning: nkf's JRuby sources

A runtime removes nkf's `ext/java`, the Java sources of JRuby's nkf, from the gem's folder and from its `.gem` in the cache (`RuntimeBuilder::Pruning.prune_jruby`), which it rewrites in RubyGems' own format with the specification's file list and `checksums.yaml` to match, so `Gem::Package#verify` and `gem pristine nkf` accept it. CRuby never compiles or loads them (`nkf.gemspec` adds them only to the java-platform gem), so no running Ruby code reads them, the bar ADR 003, section 2, sets; they were the only copyleft text left in a runtime that is not license data. The cached `nkf-0.2.0.gem` therefore differs from RubyGems.org's by those six files.

### 7. An app's own gems (superseded by ADR 007)

This section had `fledge build` hold each gem an app's Gemfile.lock adds to this policy, read every compiled file of every native gem for copyleft code, and write the app's `notices/GEMS.txt`. The maintainer ruled on 2026-10-28 that the licenses of an app's gems are its developer's choice and responsibility, not Fledge's, so ADR 007 removed all of it. The policy stays in `lib/fledge/license_policy.rb` (`Fledge::LicensePolicy`) and the reading of compiled files in `lib/fledge/binary.rb` (`Fledge::Binary`, which runs the system's own tools, ADR 013, and which `LicenseAudit::Binaries` calls); the audit reads both, and `Fledge::Linkage` reads `Fledge::Binary` only to check that an app's compiled gems would load where the app goes.

### 8. The licensing page is generated

`tasks/licensing_page.rb` writes `doc/licensing.md` from the audit of all four runtimes: per platform, every component, its license and how it ships, every gem by license, that an app's own gems are its developer's (ADR 007), and what the developer must do, with the LGPL's obligations stated as facts with their section numbers, the AGPL's for Fledge's own files, the maintainer's word that a commercial license will likely be offered, and a plain instruction to ask one's own lawyer. CI's "Licensing page is current" job regenerates it from the runtimes it built and fails when the committed page differs, uploading the page it expected.

### 9. A pin may name mirrors (2026-11-03)

On 2026-11-03 musl.libc.org stopped answering, and with it the only URL for musl-1.2.5.tar.gz, which CI's Replace libcrypt job downloads. The 0.2.0 release run failed on that download. A pin in `runtime/sources.yml` may now list `mirrors` after its `url`. `DownloadCache#fetch` (`tasks/download_cache.rb`) tries the url, then each mirror in order, and checks every download against the pin's one `sha256` with `Fledge::Download.save`, so a mirror serves the pinned bytes or is refused and the next one tried. When none serves the file, the error names every URL and why it failed. The file keeps the url's name in the cache whichever URL served it.

Only `.github/scripts/fetch_pin.rb` passes mirrors, and only the `replaceability` pins, which it alone reads, name them; `test/runtime_builder_test.rb` fails if a pin anywhere else does, since the runtime builder would never try them. musl's mirrors are Alpine's distfiles for its 3.22 release and Debian's original tarball, and GNU MP 6.2.1's is kernel.org's copy of the GNU archive; each was downloaded and matched against the pin before it was added. The audit is unchanged: a mirror holds the same bytes as the url, so the component, its license, and its source are the same, and the audit reads only whether a source pin exists.

### 10. A Windows app says that fledge build modified its programs, and when (2026-11-06)

Superseded on 2026-11-07: Fledge's own files are MIT (decisions, 2026-11-07), which asks for no notice of changes, so `fledge build` no longer writes `notices/MODIFIED.txt` and `Fledge::ModificationNotice` is gone. The section is kept as it was decided.

Every program of an app is a copy of Fledge's launcher, which is AGPL-3.0-or-later. On Linux and macOS the copy is the launcher's bytes under the app's name. On Windows, `place_launcher` (`lib/fledge/assembly.rb`) has rcedit write the app's version information and icon into the copy's resources (`Fledge::WindowsResources`, ADR 010), for every program of the app, `programs` (ADR 024) and `fledge build --from` (ADR 032) included. That is the change a person would make by editing `runtime/launcher/windows.rc` and building again, and it puts the app's strings and icon into the program, so each Windows program is a modified version of the launcher.

The license asks two things of a modified version conveyed as object code. Section 0 (`LICENSES/AGPL-3.0-or-later.txt`, line 36) defines "modify" as "to copy from or adapt all or part of the work in a fashion requiring copyright permission, other than the making of an exact copy". Section 6 (line 91) lets object code be conveyed "under the terms of sections 4 and 5", and section 5(a) (line 80) asks that "The work must carry prominent notices stating that you modified it, and giving a relevant date." Until now each app's `notices/NOTICES.txt` said only that the program is the launcher "renamed for the app", which was not true on Windows, and gave no date. Section 6 also asks for the Corresponding Source, which line 53 defines as "all the source code needed to generate, install, and (for an executable work) run the object code and to modify the work, including scripts to control those activities".

So `fledge build` writes `notices/MODIFIED.txt` into every Windows app (`Fledge::ModificationNotice`), after it places the programs and before it signs anything. The notice names each program, says it is a copy of Fledge's launcher under the AGPL that this release's `fledge build` changed on the date of the build, by renaming it and having rcedit write the version information and icon into its resources from the app's `fledge.yml`, and that nothing else was changed. It lists, for each program, every string and version rcedit wrote and the icon file, saying whether the app holds it in `app/`. It ends where the source is: Fledge's tag for the release, whose `runtime/launcher/` holds the launcher's C and `lib/fledge/windows_resources.rb` the steps. With the strings listed in full and the steps at the tag, the Corresponding Source of each modified program is the launcher's source, those steps, and the icon. rcedit itself is excluded by line 53 as a general-purpose tool used unmodified, and the runtime ships its build in `tools/`, as before. A Windows runtime's `NOTICES.txt` names `notices/MODIFIED.txt` in its section on Fledge's own files, so the notice is found from the file every app's recipient is pointed at. This is the smallest change that meets section 5(a): a notice per app, since the modification and its date happen at build time and differ for every app, rather than a fixed sentence in the runtime.

The date is the day, in UTC, of `SOURCE_DATE_EPOCH` when it is set, as reproducible-builds.org specifies it and as the runtime's SBOM already takes it (`tasks/license_audit/spdx.rb`), or else of the build. A `SOURCE_DATE_EPOCH` that is not a whole number of seconds fails the build, as that specification asks. An app's archive is not reproducible today (ADR 010 gave up reproducible archives), so this only keeps the notice itself from adding to that.

`fledge build --from` copies the old app's `notices/` but leaves its `MODIFIED.txt` behind, since it describes programs the new app does not hold, and the new build writes its own. `build_tools` copies the launchers into the app's `tools/` unchanged, so they are not named.

Two other steps were weighed and are not modification. Signing (codesign on macOS, ADR 016, including the ad hoc signature and bundle identifier `MacBundle` gives a bundle's program, and signtool's Authenticode signature on Windows) computes a seal over an exact copy and adds no work of anyone's to it; the license treats signing keys as "Installation Information" (line 107), something it asks for only for User Products, not as a change to the work. Renaming a file changes no byte of it. Neither has a source-level counterpart a person would edit, which is the test applied here: rcedit's change does (`windows.rc`), signing and renaming do not. A Mac bundle's `Info.plist` and icon are files beside the launcher, not in it.

Delivery on Windows (`.github/scripts/deliver.ps1`) reads the notice back from each built app: it must exist, give a date, name the app's program with the version Windows reads from it, and be named by `NOTICES.txt`.

## Consequences

- A pin that moves (a new rv-ruby, RubyInstaller, OpenSSL, or Rust) fails the runtime build until `runtime/licenses.yml` follows it, and then the licensing page until it is regenerated. That is the point: no one has to remember.
- The audit takes a few seconds per runtime. Each runtime grows by its SBOM (about 2 MB unpacked) and NOTICES (160 to 230 KB).
- Developers get the facts and the obligations in every app, every release, and one page; Fledge's own files remain AGPL-3.0-or-later until setdef offers a commercial license.
- An app built with a Linux runtime needs `lib/libcrypt.so.2` beside it, and a Windows app GMP's DLL; a developer whose policy forbids LGPL-3.0 is told GMP is the one to raise.
