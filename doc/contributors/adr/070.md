# ADR 070: A Windows App Declares UTF-8 as Its ANSI Code Page

## Context and Problem Statement

Ruby's strings for paths are UTF-8 on Windows (`localeinit.c`, lines 117 to 137, at Ruby master 0e25874222), and Ruby's own calls that take a path convert to UTF-16 and use Windows' wide functions: `dln.c` loads an extension with `LoadLibraryW` (lines 337 to 343). A gem that calls one of Windows' narrow, `A`, functions instead passes those UTF-8 bytes to a function that reads them in the process's ANSI code page, 1252 on a Western system. ffi 1.17.4 opens a library that way, with `LoadLibraryExA` (`ext/ffi_c/DynamicLibrary.c`, lines 215 to 225), and Fiddle maps `dlopen` to the same family (`fiddle.h`, line 34).

So an app whose gem loads a DLL through ffi fails when it is installed under a folder whose name is outside ASCII, `C:\Users\José\` or `D:\Fledge test\héllo wörld\`: Windows looks for a path that does not exist, and the gem raises error 126. This was shown three ways: with RubyInstaller's own `ruby.exe` on a Windows computer, with a Fledge app in CI's Delivery from source (run 43237130653, `examples/native_app` loading libusb's DLL), and by the fix, in runs 43268776077 and 43278468138.

Stock Ruby fails the same way, so an app that failed would behave as `ruby main.rb` does (AGENTS.md, Design precedence 2). But the person who installed the app into their own folder would meet a gem's error, which Design precedence 1 forbids, and "When anything below conflicts with this, this wins." the former ADR 041 set aside a UTF-8 code page (its option 4) because it would differ from `ruby.exe`, and the former ADR 003 said the launcher's manifest sets none. How does a Windows app's gem reach a DLL under any folder name?

## Decision Drivers

- A person never meets a gem's error because of where they installed the app (Design precedence 1).
- What the app's Ruby code sees stays what `ruby main.rb` gives wherever precedence 1 does not need otherwise (Design precedence 2), and every difference is told plainly (`doc/differences_from_ruby.md`).
- Fledge never modifies a developer's gems (ADR 007; AGENTS.md).
- One change that covers every gem that calls a narrow function, not ffi alone.

## Considered Options

1. Declare `activeCodePage` UTF-8 in the manifest both Windows launchers embed.
2. Wait for ffi to call the wide functions, and do nothing in Fledge.
3. Patch or replace a developer's gems when building.
4. Call `setlocale(LC_CTYPE, ".UTF8")` in the launcher, and leave the manifest alone.
5. Run the app through 8.3 short names, which are ASCII.
6. Ask people to turn on Windows' system-wide "Beta: Use Unicode UTF-8 for worldwide language support".

## Decision Outcome

Chosen: option 1, because it is the only way to set a process's ANSI code page, which Windows reads from the program's manifest before any of its code runs, with no call to change it afterwards; and because it fixes every narrow call at once: ffi's and Fiddle's `LoadLibrary`, and, since the C runtime's locale follows the code page, a C extension's `fopen`. `runtime/launcher/windows.manifest`, which `windows.rc` embeds in the console launcher and the windowed one, declares it.

Option 2 is complementary, not an alternative: a draft report for ffi is in `doc/contributors/drafts/ffi-windows-utf8-path.md`, for the maintainer to file, but until ffi releases a fix and developers update, apps stay broken, and the fix would cover ffi alone. Option 3 breaks ADR 007. Option 4 fixes `fopen` but leaves `GetACP` at 1252, so `LoadLibraryExA` still fails. Option 5 changes `$0` and `__dir__` from what `ruby main.rb` gives, and short names can be turned off for a volume. Option 6 needs an administrator and a restart, and changes every program on the computer.

Confidence: high that it works on Windows 10 1903 and later and on Windows 11, x64 and ARM64: the new test fails without the manifest and passes with it, Delivery from source loads libusb's DLL under a folder named outside ASCII, and the parity check's counts did not change.

### Consequences

- Good, because a gem's narrow calls, and the C runtime's narrow functions, read paths as UTF-8 wherever the app is installed.
- Good, because what a console app's Ruby code sees does not change: the console keeps its own code page (`Encoding.locale_charmap` takes `GetConsoleCP` first, `localeinit.c` lines 48 to 54), and `default_external`, the filesystem encoding, and `ENV` were UTF-8 already.
- Bad, because a windowed app's `Encoding.locale_charmap` and `Encoding.find("locale")` are UTF-8 where `rubyw.exe` gives Windows-1252, since without a console Ruby takes `GetACP`. `doc/differences_from_ruby.md`, "Windows' ANSI code page", says so. No gate checks it yet: the parity check runs console probes only.
- Bad, because `GetACP` and `GetOEMCP` are 65001 in the app and the C runtime's locale is `.utf8`, so a time zone name outside ASCII under `TZ` comes out as UTF-8, and a gem that meant to pass bytes in the system's code page to a narrow call would be misread (none is known).
- Bad, because Windows 10 before version 1903, LTSC 2019 among them, ignores the setting: there the app behaves as before this ADR, and the fix does not reach it. Fledge's floor is Windows 10 without a version (`doc/contributors/design/releases.md`, "Platform floors").
- Bad, because a child Ruby the app starts is still RubyInstaller's `ruby.exe`, which `RbConfig.ruby` names (ADR 089). It embeds its own manifest, which Windows prefers to any file beside it, so it keeps the system's code page, and a gem loading a DLL through ffi in that child still fails under such a folder. Changing that means changing RubyInstaller's binary or building `ruby.exe`, against ADR 038 and ADR 089; it needs a decision of its own.
- Neutral: Windows' GDI keeps the system's code page for its own narrow functions (Microsoft Learn, "Use UTF-8 code pages in Windows apps").

### Confirmation

`test_a_windows_app_reads_a_narrow_strings_path_as_utf8` in `test/integration/built_app_test.rb` builds a console app and a windowed app and loads the runtime's `libz-1.dll` through `LoadLibraryExA` under a folder named "Ünïcödé 日本"; it fails against v0.12.0's runtime, with code page 1252, and passes in CI's Test (Windows) on x64 and ARM64. Delivery from source loads `examples/native_app`'s libusb DLL through ffi under `D:\Fledge test\…\héllo wörld\`. The parity check's counts on both architectures are unchanged.

## More Information

- This sets aside the former ADR 041's rejection of its option 4, and the former ADR 003's statement that the launcher's manifest sets no `activeCodePage`, which ADR 081 restates with this code page.
- Measured in CI, the launcher against RubyInstaller's programs: `GetACP` 65001 against 1252, `GetOEMCP` 65001 against 437, the C runtime's locale `English_United States.utf8` against `.1252`, and a windowed app's `Encoding.locale_charmap` `CP65001` against `rubyw.exe`'s `CP1252`.
- `doc/contributors/design/launcher.md`, "The locale", says what the manifest holds.
