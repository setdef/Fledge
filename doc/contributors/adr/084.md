# ADR 084: An app sets up the groups bundle exec would, under the developer's own Bundler settings

## Context and Problem Statement

`bundle exec` sets up every group of the Gemfile but those the developer's Bundler settings leave out (`without`), so a program may require a development or test gem at run time, as some do with debug, dotenv, or rake as a library. Fledge left the development and test groups out of every app, after Warbler's `bundle_without`, so such a program worked under `bundle exec` and raised a `LoadError` naming the gem to the person who ran the app. The desktop parity audit found it (`doc/contributors/research/2026-11-12-desktop-parity-audit.md`, J11 to J13). The maintainer, 2026-11-12 (`decisions.md`): a difference is accepted only when inherent to where the app ships or truly forbidden by the platform. Which groups does an app set up?

## Decision Drivers

- A person who runs the app never meets an error that names a gem (AGENTS.md, Design precedence 1).
- The app's code runs as under `bundle exec` (Design precedence 2; ADR 045).
- "Tiny filesize is not a priority; "my ruby code just works" _is_ a (high) priority." (decision 20).

## Considered Options

1. The groups Bundler's `requested_groups` gives under the developer's own settings (the project's `.bundle/config`, `BUNDLE_WITH` and `BUNDLE_WITHOUT`, and their global config), with nothing forced out; a gem of a shipped group with no build for the target fails the build.
2. The same groups, with a gem of a shipped group that has no build for the target left out.
3. Leave the development and test groups out of every app, as Warbler's `bundle_without` and Traveling Ruby's tutorial (`--without development`) do.

## Decision Outcome

Chosen: option 1, because it alone sets up what `bundle exec` sets up, and leaves the choice of groups where Bundler keeps it, with the developer. A developer who wants an app without a group sets `without`, as for any deployment, which is also the setting under which `bundle exec` gives the same `LoadError`, so any difference is the developer's own. Tebako (v2.8.78, `crates/tebako-cli/src/packager.rs`) runs a plain `bundle install` and so ships every group too; PyInstaller ships whatever the program imports.

Option 2 brings the `LoadError` back for that gem, and the app's frozen Bundler would refuse to start without a gem of a group it sets up; Bundler itself refuses the same gem on that platform at `bundle install` unless its group is left out. Option 3 is the difference itself: Warbler and Traveling Ruby leave development out for size, which decision 20 ranks below code that works.

Confidence: high. The parity check compares the gem-shaped app with `bundle exec` on every desktop platform but ARM64 Windows, with the development and test groups' differences no longer justified.

### Consequences

- Good, because a program that requires a development or test gem at run time runs in the app as under `bundle exec`.
- Bad, and breaking, because every app now carries its development and test gems unless the developer sets `without`: Fledge itself, when a project locks it from git in the development group, adds about 7.5 MB.
- Bad, because a development gem with an extension, such as debug, is compiled for each target, phones included, and one with no build for a target fails the build until the developer sets `without`; the error says how.

### Confirmation

`test/bundle_test.rb` holds the groups for each kind of setting, and the error that names `bundle config set --local without GROUP`; the parity check runs with no justification for the development and test groups; the CHANGELOG records the break.
