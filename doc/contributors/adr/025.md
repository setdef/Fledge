# ADR 025: A phone project takes its host's files from the app's own project: `ios: host:` and `android: host:`

## Context and Problem Statement

Some frameworks must start a phone app their own way. SDL3 is the example: on iOS its `SDL_RunApp` starts UIKit and runs the game's main function on the main thread, and on Android its `SDLActivity` is the Activity that owns the surface SDL draws on. So a game over SDL needs its own `Host/main.m`, `Info.plist`, and linker settings on iOS, and its own `MainActivity` and SDL's Java files on Android. No gem's `extconf.rb` can carry those.

`fledge build` writes each phone's project afresh (ADR 012), so a change made in the project lasts until the next build. The SDL spike made its changes after each build with a script, `host/apply.rb`, which patched `Info.plist` and `project.yml` and ran XcodeGen again. Every framework would carry such a script. How does a framework keep its own startup files across builds?

## Decision Drivers

- A framework runs no step of its own after `fledge build`.
- Regenerating the project loses nothing the developer wrote.
- "Code is a liability" (`decisions.md`, 2026-10-28): Fledge writes no merger for property lists, YAML, or Gradle files, formats it does not own.
- Fledge depends on no wrapper's repository (`decisions.md`, 2026-11-02), so the seam knows nothing of SDL.

## Considered Options

1. `fledge.yml` names a folder of the project's own files for each phone (`ios: host: DIR`, `android: host: DIR`), and `fledge build` copies them over the project it writes, each replacing Fledge's file at its path, whole.
2. A patch script the framework runs after each build, as the spike's `host/apply.rb` did.
3. XcodeGen's own `include`, which merges one spec into another.
4. Merging the host's files into Fledge's (property lists, YAML, Gradle).

## Decision Outcome

Chosen: option 1, because it is Vlissides' Generation Gap (*Pattern Hatching*, chapter 3): the generated half and the hand-written half live in separate files, so generating again loses nothing. A patch script is code every framework would carry and keep in step with Fledge's templates. XcodeGen's `include` serves `project.yml` alone, not `main.m`, `Info.plist`, or Android's files. A merger is code of Fledge's for formats it does not own.

The host wins: replacing Fledge's file is the point. The build names on the error stream each of Fledge's files a host replaced, so a developer knows what to compare when a release changes a template. Fledge fills its marks in a host's copy of a marked template, so a copied `project.yml` still takes the app's identity and link flags. One mapping per phone with one key in it matches how Briefcase scopes a setting to a platform and buildozer to Android, and leaves room for a phone's next setting.

Confidence: high. `examples/sdl_phone` builds with `fledge build` alone, and its game draws and takes touches on an iPhone and an iPad in the Simulator, on Android emulators, and on real devices.

### Consequences

- Good, because a wrapper ships its startup files in the game's project and runs no step after `fledge build`.
- Good, because the seam serves any framework that starts an app its own way, not SDL alone, and a pure-Ruby app names no host and keeps Fledge's.
- Bad, because a host's copy of one of Fledge's files is the developer's to keep in step with Fledge's. The build's line names each copy, but nothing compares them.
- Bad, because a host replaces a file whole: to change one key of `Info.plist`, a developer copies the file.
- Neutral: desktop builds ignore both keys, and each phone's build reads only its own, so a desktop build works before a host's files exist.

### Confirmation

`test/config_test.rb` tests how `fledge.yml` reads the keys and refuses a host outside the project. `test/mobile_build_test.rb` tests the copy, the marks filled in a host's file, the line that names replaced files, and the folder left out of the app. `lib/fledge/config.schema.json` describes the keys, and a test fails when it and `Fledge::Config` disagree.
