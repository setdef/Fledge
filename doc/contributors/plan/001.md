# Plan 001: Ship an App That Does Nothing

## Status

In progress (requested). macOS (`arm64-darwin`) and Linux (`x86_64-linux`, `aarch64-linux`) are built end to end: pinned sources, launcher, runtimes in CI, `fledge build`, Delivery, and the release workflow. Windows (`x64-mingw-ucrt`) waits on its spike. No release has been cut.

ADR 001 decides what Fledge is: a launcher that embeds CRuby, prebuilt runtimes per platform from pinned Ruby builds, and `fledge build` copying an app into them. This plan decides the order of the work.

The first slice is a walking skeleton: the thinnest path through every layer, from a folder with a `main.rb` to an archive someone with no Ruby downloads, unpacks, and runs, shipped through the same pipeline every later change will use. It does nothing a person would want. Shipping nothing first forces every decision that is cheap now and expensive later (where Ruby comes from, how the launcher finds it, what a runtime holds, how CI proves an app runs where no Ruby is) while the stakes are lowest. Every later story adds one capability to a pipeline that already delivers.

## The app: hello

`examples/hello/main.rb` prints one line and exits with status 0:

```
Hello from Ruby 4.0.9 on PLATFORM
```

`PLATFORM` is `RUBY_PLATFORM`, as the runtime reports it: `arm64-darwin23` (rv-ruby builds for macOS 14, Darwin 23), `x86_64-linux`, `aarch64-linux`, or `x64-mingw-ucrt`. Ruby has no value that is exactly the RubyGems target name on macOS (question 15). Given a number, hello exits with it (`hello 3` exits 3), so Delivery can check that an app's exit status reaches whoever ran it. Before it prints, the app requires `json` and round-trips a value through `JSON.generate` and `JSON.parse`, because `json` is a C extension in Ruby's standard library: if extensions load from the runtime, this proves it, and if they don't, the app fails with a nonzero status instead of printing.

## Spikes: answer the risky questions with throwaway code

Each spike is a small experiment that answers one question, then gets thrown away. The answer goes in this plan.

1. **Does a Unix launcher run an app on rv-ruby, from anywhere it is unpacked?** Done. Answer: yes, on `arm64-darwin`, `x86_64-linux`, and `aarch64-linux`. With libruby linked statically, the launcher *is* the Ruby interpreter, and rv-ruby's `--enable-load-relative` makes Ruby derive its prefix from the launcher's own folder, so the layout is `NAME`, `lib/ruby/4.0.0`, `lib/ruby/gems/4.0.0`, `libexec/cert.pem`, and `app/` side by side, with no `-I` for the standard library and no path baked in. The folder may not be named `bin` or `lib`, where Ruby would take its parent as the prefix. On macOS the link needs `-Wl,-force_load` of libruby; on Linux, `-rdynamic`, `--whole-archive`, and `-static-libgcc`. On Linux, Ruby recognizes the program that holds libruby by comparing pointers with the original `argv[0]`, so the launcher passes that pointer on. A bare C locale (`env -i`, apps started by a desktop) breaks a non-ASCII install path, so the launcher coerces it to UTF-8, as Python's PEP 538 does. Scrubbing `RUBY*`, `GEM_*`, `GEMRC`, `BUNDLE_*`, and `BUNDLER_*` (rubygems.rb requires `$BUNDLER_SETUP`) and keeping RubyGems out of `~/.gem` made output byte-identical in clean and hostile environments. rv-ruby's Linux builds need glibc 2.39 or newer (question 7); its musl builds cannot be used (question 12). Built-app sizes: a macOS app folder is 28 MB (8.6 MB archived) and a Linux one 31 MB on x86_64 and 34 MB on aarch64 (10 MB archived), without bundled gems (question 9).
2. **Does a Windows launcher run an app on RubyInstaller's Ruby?** Next. On `x64-mingw-ucrt`: a launcher built with RubyInstaller's MSYS2 UCRT toolchain against its `x64-ucrt-ruby*.dll`, finding the DLLs beside itself, running `examples/hello` from another directory on a runner with no Ruby on `PATH`. Answer: TBD. Whether the launcher can be built for Windows from macOS or Linux (cross-compiled with MinGW) or must be built on a Windows runner is part of the answer.

## The walking skeleton, layer by layer

- **Pinned Ruby sources.** Done for macOS and Linux. `runtime/sources.yml` records, per target, the URL and SHA-256 of rv-ruby `20261023`'s build, and of libxcrypt 4.5.2's source; `rake runtime` downloads them into `tmp/downloads/` through `Fledge::Download`, which fails on a mismatch and keeps nothing. RubyInstaller's pin for `x64-mingw-ucrt` comes with the Windows spike.
- **The C launcher.** Done for macOS and Linux, in `runtime/launcher/`: `unix.c` holds what they share and starts Ruby as Ruby's own `main.c` does; `darwin.c` and `linux.c` each find the executable (`_NSGetExecutablePath`, `/proc/self/exe`); a Windows launcher gets its own file. It scrubs every variable starting `RUBY`, `GEM_`, `GEMRC`, `BUNDLE_`, or `BUNDLER_` before Ruby starts, coerces a C locale to UTF-8, and runs `main.rb` with `--disable=rubyopt --yjit -I ROOT/app` on the main thread. Its exit status is the app's. Each runtime also carries `rubygems/defaults/operating_system.rb`, which keeps RubyGems to the runtime's own gems instead of putting `Gem.user_dir` first, as the Windows spike does too; a fake json gem in `~/.gem` or `~/.local/share/gem` no longer loads. It builds with `-Wall -Wextra -Werror -Wpedantic` and more, under the compiler's static analyzer (`clang --analyze` on macOS, `gcc -fanalyzer` on Linux) in `rake runtime`, and clang-format checks it in the gate.
- **A runtime per target, built in CI.** Done for macOS and Linux. `rake runtime` (`tasks/runtime_builder.rb`, one recipe per OS) builds the launcher, copies rv-ruby's standard library and default gems beside it, strips debug information and stale RUNPATHs, and archives the result as `tmp/runtime/fledge-runtime-VERSION-PLATFORM.tar.gz`, with the license notices in `notices/` (Ruby, the Rust standard library in YJIT, OpenSSL, libyaml, the CA bundle, and on Linux zlib and libxcrypt, plus the launcher's own AGPL). On Linux, libxcrypt is a shared library in the runtime's `lib/`, not linked into the launcher (question 8). CI's runtime jobs run it on `macos-15`, `ubuntu-24.04`, and `ubuntu-24.04-arm`; runtimes are CI artifacts until a tag publishes them.
- **`fledge build`.** Done for macOS and Linux targets. It takes each `--target`'s runtime from `FLEDGE_RUNTIME_DIR`, the cache, or this version's GitHub Release (checked against its `SHA256SUMS`, question 14), streams it and the app into `dist/hello-PLATFORM/` and `dist/hello-PLATFORM.tar.gz` at once with the launcher renamed to `hello`, so the archive keeps executable bits and symlinks even when built on a disk that has none. One computer builds every target. `.zip` for Windows comes with its runtime.
- **Delivery.** Done for macOS and Linux, in `.github/scripts/deliver.sh` (POSIX sh, no Ruby). On fresh `macos-15`, `ubuntu-24.04`, and `ubuntu-24.04-arm` runners, and in `debian:trixie-slim` containers with no Ruby installed at all, it unpacks the archive the build job made under a path with spaces and non-ASCII characters, runs the app with an empty `PATH` (checked to hold no `ruby`) and asserts stdout is exactly the hello line, stderr is empty, and the status is 0: in a clean environment, with a json 99 gem in `~/.gem` and in `~/.local/share/gem`, in a hostile environment (`RUBYLIB`, `RUBYOPT`, `GEM_HOME`, `GEM_PATH`, `BUNDLE_GEMFILE`, `BUNDLER_SETUP`, `RUBYGEMS_GEMDEPS`, and a bogus `libcrypt.so.2` on `LD_LIBRARY_PATH`), through a symlink found on `PATH`, and with `hello 3`, which must exit 3. It also checks that libcrypt loads from the runtime on Linux, and that the macOS launcher links only libraries macOS ships. `test/built_app_test.rb` runs the same build-and-run in each platform's test job.
- **Release.** Written, never run: `.github/workflows/release.yml` runs on a `v*` tag, calls CI, and only after every job passes, Delivery included, checks the tag against `Fledge::VERSION` and creates the GitHub Release with each runtime and a `SHA256SUMS`. Never RubyGems.org (ADR 001, section 7). Whether and when to tag is the maintainer's call.
- **The gates.** The gem's gate exists from the first commit: tests, RuboCop, RubyCritic, RDoc coverage, REUSE, actionlint and shellcheck (now over `.github/scripts` too), Steep with no `untyped`, signature parity, and the package check. The launcher's C gates are compiler warnings as errors and the compiler's static analyzer in `rake runtime`, and clang-format (pinned in `mise.toml`) in the gate.

**Done when:** on every push, Delivery passes on all three operating systems: `examples/hello`, built by `fledge build`, unpacked on a fresh runner with no Ruby, prints `Hello from Ruby 4.0.9 on PLATFORM` and exits 0 on `arm64-darwin`, `x86_64-linux`, and `x64-mingw-ucrt`; and every gate passes with zero errors and zero warnings.

## Out of scope for the skeleton

- macOS `.app` bundles, and the windowed kind on every OS.
- Code signing and notarization.
- Vendoring an app's gems (a Gemfile), and gems with native extensions.
- A `fledge doctor` command that explains why an app won't build.
- Framework wrappers (Lota, Tokra, Rooibos) calling Fledge.
- More targets (`x86_64-darwin`, musl Linux). `aarch64-linux` joined the skeleton, since rv-ruby builds it and GitHub has arm64 Linux runners.
- Building Ruby ourselves; that is ADR 001's fallback if a source fails.
