# ADR 058: On a phone, bundled gems with extensions stay gems

## Context and Problem Statement

A phone's Ruby loads no extension from a file, since Fledge links every extension into the app (ADR 011). Ruby's build links its own standard library's extensions that way and registers each in `extinit.c`, but never a bundled gem's: `template/configure-ext.mk.tmpl` builds `.bundle/gems` with `--no-extstatic`, and `ext/extmk.rb` (line 661 at Ruby 4.1.0-preview1) leaves a gem's extension out of `extinit.c`. So bigdecimal, debug, nkf, racc, rbs, and the other bundled gems with C extensions would not load. The mobile spike, after xord/cruby, moved them into the standard library: they loaded, but they were no longer gems (`Gem.loaded_specs["bigdecimal"]` was nil). How does a phone's Ruby ship them?

## Decision Drivers

- "When using fledge, your ruby source code should be able to be identical to how it was without Fledge" (decision 9): an app that names a bundled gem in its Gemfile, or asks RubyGems for it, finds a gem.
- A runtime prunes only what no running code reads (decision 20).
- Use Ruby's own build, not a second one (`decisions.md`, 2026-10-28, "Code is a liability").

## Considered Options

1. Copy each bundled gem's extension sources among Ruby's own, where extmk links and registers them; leave out the gem's own build; mark its extension built, so Ruby's installer installs the gem, specification and all.
2. Fold the gems into the standard library, as the spike and xord/cruby do.

## Decision Outcome

Chosen: option 1, because only it keeps each gem a gem. Under option 2 an app that locks bigdecimal in its Gemfile, or calls `Gem.loaded_specs`, sees a difference from `ruby main.rb` that decision 9 forbids, and rbs was left out altogether.

The build copies each such gem's extension sources to `ext/gems/NAME`, tells `configure --with-out-ext` to skip the gem's own build, and once Ruby is built writes the empty `gem.build_complete` mark RubyGems looks for. Ruby's own `tool/rbinstall.rb` then installs the gem as it installs every bundled gem, and RubyGems loads it rather than "ignoring it because its extensions are not built". When the gem's Ruby requires its extension, `load.c` finds no file and looks among the linked extensions, which have it.

Confidence: high. The parity check finds every default and bundled gem a gem on both phones, and each loads.

### Consequences

- Good, because the standard library and every default and bundled gem are on a phone as on a desktop, each a gem, but for those a phone forbids.
- Good, because it is Ruby's own build and installer, steered by a copy, a configure option, and a mark.
- Bad, because each new Ruby means checking that the gems' sources still fit among Ruby's own, and that the marks are where RubyGems looks. The build checks that every such gem was installed with its specification and its mark.
- Bad, because this is a third thing worth upstreaming to ruby/ruby, beside an embedder's prefix and the builtin binary for cross builds, and until then Fledge carries it.
- Neutral: fiddle is on both phones, with its own libffi (ADR 074).

### Confirmation

`RuntimeBuilder::BundledExtensions.check_installed` fails the runtime build when a gem lacks its specification or mark. The mobile parity check (`tasks/mobile_parity.rb`) compares every gem the probe reports on a phone with `ruby main.rb`, and `test/fixtures/mobile_hello` requires csv, a bundled gem, in the Mobile apps jobs.
