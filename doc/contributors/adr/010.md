# ADR 010: Build Each Platform's App on That Platform, With Its Own Tools

## Context and Problem Statement

Each operating system has its own formats and its own tools for them: a Mac's bundles, signatures, property lists, and disk images; a Windows program's resources; Linux's SquashFS. Those tools run only on their own system. Fledge's agents had promised that any computer would build every platform's app, and kept the promise by writing those formats themselves, in about 4,500 lines of Ruby and C. The maintainer never asked for it.

The maintainer's words of 2026-10-28 (`decisions.md`): "Code is a liability and we should _not_ have 4k+ lines of things we could use existing tools for." and "We already have to have target-environment-platform machines to compile on, right? If so, what value does cross-platform non-compilation building add?" He accepted the orchestrating agent's recommendation to build each target on its own operating system with that system's maintained tools. Where should each platform's app be built, and with what?

## Decision Drivers

- Code is a liability; a maintained tool beats Fledge's own writer of the same format (AGENTS.md, How to work).
- A gem with an extension already has to be compiled on its own platform (ADR 006), so a project with one needs a computer of each platform anyway.
- A developer needs each platform to test the app on, and to sign it with Apple's or Microsoft's credentials (decision 17).
- Prior art: Tauri's bundler builds for the computer it runs on; Briefcase refuses another host ("Windows applications can only be built on Windows."); Electron's tooling signs and makes disk images with Apple's tools on a Mac and edits a Windows program with rcedit.

## Considered Options

1. Build each platform's app on a computer of that platform, with the tools that platform maintains.
2. Build every platform's app on any one computer, with Fledge's own writers of each format.

## Decision Outcome

Chosen: option 1, by the maintainer's words, because it removes code Fledge would otherwise maintain and costs a developer little: the computers it needs are the ones that developer tests and signs on.

`fledge build` builds for the platform it runs on and nothing else. Its old `-t` and `--target` options are a usage error that says to build each platform's app on that platform. On macOS, Fledge runs `plutil`, `codesign`, `ditto`, and `hdiutil`, which ship with macOS in `/usr/bin`. On Windows, it runs rcedit, Electron's resource editor, which calls Windows' own `UpdateResource`; the Windows runtime carries rcedit, pinned by SHA-256. LLVM's `llvm-rc` and `llvm-windres` compile resources but cannot put them into a program already linked, and Tauri's way, compiling them in when the program is linked, does not fit a launcher Fledge's CI has already linked. On Linux, it runs `mksquashfs` and `dpkg-deb`. Archives use the computer's own tar (ADR 047), icons are the developer's own files (ADR 048), and the installers use NSIS's and AppImage's own releases (ADR 049).

Confidence: high. CI builds each platform's apps on a runner of that platform, and Delivery runs them on fresh ones.

### Consequences

- Good, because about 4,600 lines of format writers and their tests are gone, and what Fledge writes is only what no tool writes: the launcher, a bundle's layout and its `Info.plist` keys, a desktop entry, an NSIS script, a `.deb`'s control file, and the tools' command lines.
- Good, because each format is written by the tool its system trusts, so a bundle's seal, a program's resources, and a disk image are what that system expects.
- Bad, because a developer who ships to three systems builds on three computers, their own or CI runners of each.
- Bad, because Fledge depends on tools it does not pin: `hdiutil create` warns on macOS 26 and newer that `diskutil image create` replaces it, and a Linux developer installs squashfs-tools.
- Neutral, because a missing tool fails the build with the tool's name and how to install it (`Fledge::Command`).
- Neutral, because runtimes are still built as is simplest: the Windows launcher is compiled on Linux by the pinned llvm-mingw, a compiler and not a format Fledge writes.

### Confirmation

`test/cli_test.rb` holds the refusal of `-t` and `--target`. CI's Build jobs (`.github/workflows/ci.yml`) build each platform's examples on a runner of that platform, and the Delivery jobs take them to fresh runners of the same platform, with no Ruby.

## More Information

- How each tool is run: `doc/contributors/design/desktop-apps.md` and `doc/contributors/design/signing.md`.
- The maintainer's answer to question D (`decisions.md`, 2026-11-04) keeps this rule for code that writes formats and compiles, and lets a step that only copies make another system's app. `fledge build --from` uses that room only as a limit not yet lifted (ADR 032).
- Compiled files are read with each system's own objdump, and llvm-readobj for Windows (ADR 013).
