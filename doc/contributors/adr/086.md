# ADR 086: Run an App That Has a Gemfile Under the Real Bundler, as bundle exec Does

## Context and Problem Statement

A gem-shaped program runs as `bundle exec exe/my_cool_app`: Bundler puts the project's own `lib` and every gem the lockfile locks on the load path, and the code says `require "my_cool_app"`, not `require_relative`. Many programs also require `bundler/setup` themselves, call `Bundler.require`, read `Gem.loaded_specs`, or start a person's own tools through `Bundler.with_unbundled_env`. For that code to stay as it is (`decisions.md`, 2026-10-26, decision 9), the built app must set up its gems as Bundler does. How does a built app with a Gemfile load its gems?

## Decision Drivers

- The app's Ruby code runs as it does under `bundle exec` (AGENTS.md, Design precedence 2; decisions 9 and 10): same requires, same `Gem.loaded_specs`, same `ENV`.
- A person's own Ruby settings and Bundler settings never change what the app loads (Design precedence 1).
- The app starts in a folder that may be read-only, and never rewrites its lockfile.

## Considered Options

1. The real Bundler, the runtime's default gem (ADR 063 decides which Bundler runs, and since then the lockfile's), set up by the launcher as `bundle exec` sets it up, with Warbler's settings for a packed app in the app's own `.bundle/config`.
2. Bundler's `--standalone`, which writes a `bundler/setup.rb` of load paths that needs no Bundler at run time.

## Decision Outcome

Chosen: option 1, because option 2 breaks the programs that use Bundler themselves. A program that says `require "bundler/setup"` under `--standalone` loads the real Bundler anyway, which looks for a Gemfile from the person's current folder, and `Gem.loaded_specs` knows none of the gems.

The launcher requires Bundler and `bundler/setup` by their paths, in the gem of the Bundler the lockfile names (ADR 063) or else in Ruby's library, while the person's Ruby settings are still set aside, with `BUNDLE_GEMFILE` naming the app's Gemfile and Bundler given the app's own settings in place of the person's. It hands Bundler those settings as `BUNDLE_` variables read from the app's `.bundle/config`, with `BUNDLE_APP_CONFIG` and `BUNDLE_USER_CONFIG` naming a folder that holds nothing, and takes them all out of `ENV` once Bundler is set up: Bundler keeps the variables it found, and reads no settings file that is missing (`settings.rb`, lines 107 to 120 and 802, at Bundler 4.0.20), so RubyGems' YAML serializer, which defines a hollow `Psych` when Psych is not loaded, never runs. Then it gives the program the environment `bundle exec` would, composed over the person's by Bundler's own code. `fledge build` writes the app's `.bundle/config` with Warbler's settings (`jruby/warbler` at 3196d5f9, `lib/warbler/traits/bundler.rb`, lines 17 to 32): `BUNDLE_VERSION: system`, `BUNDLE_FROZEN: true`, `BUNDLE_PATH__SYSTEM: true`, `BUNDLE_AUTO_INSTALL: false`, and the groups the app sets up (ADR 084). That level of Bundler's settings wins over every other, in the app and in any Ruby it starts. An app without a Gemfile runs without Bundler (ADR 081). Removing the hollow `Psych` after setup was weighed and not taken: it would leave the serializer loaded, whose error paths name `Psych`.

Confidence: high. The parity check compares the gem-shaped app with `bundle exec` on every desktop platform but ARM64 Windows, where its sqlite3 has no build and its source does not build (`Parity::WITHOUT_GEM_APP`), and finds only the differences `Parity::JUSTIFIED` explains.

### Consequences

- Good, because `require "bundler/setup"`, `Bundler.require`, `Gem.loaded_specs`, `Bundler.original_env`, and `Bundler.with_unbundled_env` behave as under `bundle exec`, so a Bundler app that runs a person's `bundle exec rspec` runs it as it would have.
- Good, because a frozen bundle refuses a stale lockfile, never touches it, and starts in a read-only folder.
- Bad, because the app carries Bundler's environment: a Ruby it starts runs in the app's bundle, and `GEM_HOME` names the runtime's gem folder, as under `bundle exec`.
- Bad, because a frozen bundle refuses what a developer's unfrozen one allows: a bundled gem the lockfile does not lock, activated for a moment, as `binding.irb` activates irb. Fledge's RubyGems defaults wrap `Gem::BUNDLED_GEMS.force_activate` so that it works, which is code of Fledge's inside Ruby's boot.
- Bad, because the launcher's setup depends on Bundler's internals (`EnvironmentPreserver`, `SharedHelpers.set_bundle_environment`), which a new Bundler may change; the parity check is what notices.
- Bad, because a Ruby the app starts with `bundler/setup`, or `Bundler.reset!`, reads the app's `.bundle/config` as a file, so the hollow `Psych` can appear there, as it does under `bundle exec` for a project with such a file.
- Bad, because a child Ruby the app starts in its bundle under a C locale, in a folder whose name is not ASCII, needs the runtime's `bin/ruby` to coerce the locale as the launcher does (ADR 087).

### Confirmation

The parity check (`tasks/parity.rb`, `checks: [:bundle]`) runs on every desktop platform but ARM64 Windows in CI, comparing `examples/my_cool_app` and the gem-shaped probe with `bundle exec`; Delivery checks that `with_original_env` and `with_unbundled_env` give a child the person's `GEM_HOME` and `RUBYOPT`. `test/bundle_test.rb` covers the settings, and `test/integration/built_app_test.rb` drives `binding.irb` in a built gem-shaped app.
