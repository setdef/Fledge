# ADR 035: Take CRuby from rv-ruby on macOS and glibc Linux, and from RubyInstaller on Windows, x64 and ARM64

## Context and Problem Statement

Each desktop runtime needs a relocatable CRuby built for its platform (ADR 093). Two projects publish one. rv-ruby (spinel-coop/rv-ruby) publishes relocatable CRuby builds for macOS and Linux with a static libruby, YJIT, and OpenSSL, libyaml, libffi, and zlib linked in. RubyInstaller (oneclick/rubyinstaller2) publishes the maintained CRuby for Windows, a MinGW UCRT build, for x64 and for ARM64 from the same release, with a PGP signature beside each archive. The maintainer accepted the Linux floor rv-ruby's builds set: "2.39 is fine" (`decisions.md`, 2026-10-26, decision 7). Should Fledge take its Rubies from these projects, or build CRuby itself?

## Decision Drivers

- Fledge maintains as little as it can (AGENTS.md: code is a liability).
- The Ruby must be relocatable: on macOS and Linux a static libruby the launcher can link (ADR 001), on Windows Ruby's DLL in RubyInstaller's tree.
- Every download is pinned by version and SHA-256, and RubyInstaller's by its signature too.

## Considered Options

1. **rv-ruby on macOS and glibc Linux, and RubyInstaller on Windows, its x64 and its ARM64 builds,** each pinned in `runtime/sources.yml`.
2. **Build CRuby in Fledge's CI for every platform,** as python-build-standalone builds CPython, with the same static-linking choices.

## Decision Outcome

Chosen: option 1, because it gives every platform a maintained, relocatable CRuby that Fledge does not build. Building Ruby itself is a larger project, so it waits until a source stops publishing, publishes a build that fails Delivery, or cannot be relied on. For musl Linux that has happened, and Fledge builds Ruby there (`doc/contributors/design/runtimes.md`, "musl Linux's Ruby, built in Alpine"). Windows on ARM64 takes RubyInstaller's native ARM64 build (`doc/contributors/design/runtimes.md`, "Windows on ARM64").

Confidence: high. Every one of these runtimes builds, passes the license audit and the parity check, and delivers on a fresh runner of its platform in CI.

### Consequences

- Good, because Fledge's Rubies are the ones Ruby's own communities build and test, and a new Ruby is a pin to move.
- Good, because an app runs natively on Windows 11 on ARM64.
- Bad, because Fledge depends on two projects' release schedules: a Ruby release reaches Fledge when rv-ruby and RubyInstaller publish it.
- Bad, because rv-ruby's Linux builds need glibc 2.39 or newer, which sets the Linux floor.
- Bad, because each upstream tree carries what a developer's Ruby needs, which the runtime builder prunes and replaces: rv-ruby's `bin/ruby`, with libxcrypt linked in, and RubyInstaller's RubyGems defaults and developer tools (`doc/contributors/design/runtimes.md`). RubyInstaller's signing key expires on a known date, which whoever moves the pin must follow.

### Confirmation

Every runtime build (`rake runtime`) checks each download against its pin, and RubyInstaller's archive with `gpgv` against the pinned key, by fingerprint. CI's "Licenses of the whole upstream tree" jobs audit each source's whole tree, and CI builds, tests, and delivers every runtime on a runner of its platform.
