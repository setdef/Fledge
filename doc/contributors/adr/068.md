# ADR 068: On a phone, a bundled gem's linked extension is found only while its gem is active

## Context and Problem Statement

On a phone, bundled gems with extensions stay gems, their extensions linked into the runtime and registered under the features their gems require (ADR 058). Ruby looks among linked extensions for any feature it finds no file for (`load.c`, `search_required`, lines 1199 to 1218 at Ruby 4.1.0-preview1), and RubyGems' `require` asks Ruby's own require first, activating a gem only when that raises `LoadError` (`lib/rubygems/core_ext/kernel_require.rb`, lines 79 to 81 and 138 to 148). So where a gem's Ruby file has its extension's name, a plain `require` found the linked extension before RubyGems activated the gem, and the gem's Ruby never loaded: `require "bigdecimal"` gave a `BigDecimal` without `#sqrt`, `#power`, `#**`, or `BigMath`, which bigdecimal's `lib/bigdecimal.rb` defines, and `Gem.loaded_specs["bigdecimal"]` was nil. nkf's `lib/nkf.rb` and, on Android, fiddle's `lib/fiddle.rb` have the same names as their extensions. ruby/spec found it, with 36 to 38 examples failing per run on each phone.

On a desktop the extension is a file in the gem's own folders, which RubyGems puts on `$LOAD_PATH` only as it activates the gem: the gem's require paths and its extension folder, which is named for the gem's full name (`Gem::BasicSpecification#full_require_paths`, `lib/rubygems/basic_specification.rb`, lines 184 to 195). Before activation Ruby's require finds nothing, RubyGems activates the gem, and `lib/bigdecimal.rb` loads and requires `bigdecimal.so` from the gem's folder.

## Decision Drivers

- An app's code runs as under `ruby main.rb` (AGENTS.md, Design precedence 2; decisions 9 and 10): `require "bigdecimal"` loads the bigdecimal gem a desktop loads, its Ruby and its extension.
- ADR 058: a bundled gem is a gem on a phone, which RubyGems activates.
- Change as little of Ruby as can be: each edit to its source is one more to check with each new Ruby.

## Considered Options

1. Edit `load.c` so that its lookup of linked extensions finds a gem's extension only while a folder named for its gem is on `$LOAD_PATH`, from a table, written into the edit, of each gem's extension feature and gem.
2. Register a gem's extension under another name, one a plain `require` of the gem's feature cannot reach.
3. Register no gem's extension at boot, and register each as its gem activates, from a hook into RubyGems in `rubygems/defaults/operating_system.rb`.
4. Put a file in each gem's extension folder for Ruby's require and RubyGems to find, and edit `load.c` to answer it with the linked extension.
5. Fold the gems' Ruby into the standard library, so that the linked extension's name finds the gem's file first.

## Decision Outcome

Chosen: option 1, because only it makes the linked extension reachable exactly when a desktop's file is: while the gem's folders are on `$LOAD_PATH`, whether RubyGems put them there or Bundler's setup did. The edit is one condition in the lookup and a function before `search_required`; Ruby's own linked extensions, which the table does not name, are found as before, and a gem's extension, once found, is registered and recorded in `$LOADED_FEATURES` as every linked extension is.

Option 2 cannot work: Ruby looks up a plain `require "bigdecimal"` as `bigdecimal.so`, the same name `lib/bigdecimal.rb`'s `require "bigdecimal.so"` looks up, so no registered name tells the two apart. Option 3 monkey-patches RubyGems' activation on a phone alone, which an app would meet, and RubyGems has no activation hook to use instead. Option 4 puts files named for shared objects that are not ones into an app, which Ruby's require would find and try to load (`search_required` returns the file, and `require_internal` loads it with `dln_load_feature`), so it needs a larger edit than option 1, to answer each such file with the linked extension, and ships files that pretend to be code. Option 5 is what ADR 058 rejected.

`RuntimeBuilder::BundledExtensions.features` reads the feature of each copied gem's extension from its `extconf.rb`'s `create_makefile`, as extmk registers it, and raises for one it cannot read; `RuntimeBuilder::RubySource.load_c` writes the gate and its table into `load.c`, and raises when the lines it changes are gone.

Confidence: high that it works for the gems Ruby 4.1.0-preview1 bundles, from the checks under Confirmation.

### Consequences

- Good, because `require "bigdecimal"`, `require "nkf"`, and on Android `require "fiddle"` load the gem on a phone as on a desktop, and `RubySpec::JUSTIFIED` no longer excuses bigdecimal's examples.
- Good, because a require the gem's own Ruby makes for its extension, plain or with `.so`, finds it as before, once the gem is active.
- Bad, because it is one more edit to Ruby's source, and a new Ruby means checking that `search_required` still looks up linked extensions so.
- Bad, because one difference stays: a desktop's RubyGems activates a gem for a require of its extension's own feature (`require "racc/cparse"` before racc is active), since it finds the extension's file among the gem's; a phone's gem has no such file, so that require raises `LoadError` until the gem is active. No gem's Ruby requires its extension before its gem is active.

### Confirmation

`test/ruby_source_test.rb` checks the edit against the lines of `load.c` it changes, and compiles the gate's C with this computer's mkmf and Ruby, finding a gem's extension only while its extension folder is on `$LOAD_PATH`, and another always. The parity probe reports a gem whose require loads without activating it as `loads, but not its gem`, which the mobile parity check compares with `ruby main.rb` on both phones; ruby/spec's library/bigdecimal runs on both phones with no justification.
