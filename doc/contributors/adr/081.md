# ADR 081: An app's program runs as `ruby PROGRAM` runs it, with nothing of Fledge's between

## Context and Problem Statement

A developer runs a program with `ruby main.rb`, or `bundle exec`, and ships it with Fledge. Between the person who runs the app and the program sits Fledge's launcher (ADR 001). Anything the launcher adds is something the program sees that `ruby` would not give it: an option, a load path entry, a loaded file, a global or constant, a signal or console handler, a parent process.

The bar is set (`decisions.md`, 2026-10-26): an app's Ruby source is identical with Fledge and without it, so what it had to `require` before it still requires, and what it did not, it still does not (decision 9), and every Ruby global is unsurprising to an app's developer, for the same reason (decision 10). Console code pages and Ctrl-C are the agents' to decide (decision 21).

How does the launcher start the program so that nothing of Fledge's stands between Ruby and the app?

## Decision Drivers

- The app's source is the same with and without Fledge, and its globals surprise no Ruby developer (decisions 9 and 10; `doc/contributors/design/architecture.md`, "What the design answers to").
- Ctrl-C, a closed terminal, and a closed console end the app as they end `ruby main.rb`.
- Every difference from `ruby main.rb` is found by a check, not by a developer.

## Considered Options

1. Run the program in the launcher's own process with the equivalent of `ruby --disable=rubyopt -- PROGRAM ARGS`, adding no option, global, constant, loaded file, or handler.
2. Give Ruby options of Fledge's own: `-I ROOT/app` so `require` finds the app's files, `--yjit`, or a `-r` boot file.
3. Run Ruby as a child of the launcher, which forwards signals and console events and passes on how the child ended, as many launchers do.

## Decision Outcome

Chosen: option 1, because it is the only one that gives the program what `ruby` gives it.

The launcher runs Ruby in its own process with the equivalent of `ruby --disable=rubyopt -- ROOT/app/ENTRY ARGS`, where `fledge.cfg` names ENTRY, installs no signal or console control handler, and once the program runs, exits with the program's status. What Fledge must do before the program runs, such as hiding the person's Ruby settings and setting up Bundler, it does between `ruby_options` and `ruby_run_node`, and leaves no global, constant, or loaded file behind. Where Ruby's start must differ so that the person never meets Ruby, the difference is decided and documented with the mechanism that makes it: a bare C locale, and on Windows the ANSI code page (`doc/contributors/design/launcher.md`, "The locale").

Confidence: high. The parity check compares a built app with `ruby main.rb` and `bundle exec` on every desktop platform, and Delivery ends a console app with Ctrl-C, a hangup, and a closed console, comparing with Ruby itself.

### Consequences

- Good, because what needed a `require` under `ruby` still does, and nothing else does.
- Good, because Ctrl-C and a closed terminal end the app as they end `ruby`, running `ensure` clauses and `at_exit` hooks.
- Bad, because closing a console window on Windows ends the app at once, before any `ensure` or `at_exit`, as it ends `ruby.exe`. An app that wants to clean up then needs a console control handler, which Ruby code cannot install without a native extension.
- Bad, because `$0`, `__FILE__`, and `$PROGRAM_NAME` are the program's absolute path, where `ruby main.rb` gives the path as typed: a person may start the app from any folder.
- Bad, because a new difference from `ruby main.rb`, from a new Ruby or a change to Fledge, fails CI until someone fixes it or writes down why it is right, and the checks cost CI time on every push.

### Confirmation

The parity check (`rake parity`) in CI's Test, Test (Windows), and Parity (musl) jobs fails on any difference from `ruby main.rb`, or from `bundle exec` for a gem-shaped app, that `Parity::JUSTIFIED` does not explain. `doc/contributors/design/parity.md` describes it, and the console, restart, and ruby/spec checks beside it.

## Pros and Cons of the Options

- **Options of Fledge's own:** bad, because each shows in the program: `-I` in `$LOAD_PATH` and in what `require` finds, `--yjit` in `RUBY_DESCRIPTION`, a boot file in `$LOADED_FEATURES` (`doc/contributors/design/launcher.md`, "Ruby's arguments").
- **Ruby as a child of the launcher:** bad, because the launcher would have to forward every signal and console event and pass on how its child ended, and an app would see a parent process `ruby` does not have.

## More Information

`doc/contributors/design/launcher.md` says how the launcher builds Ruby's arguments, what it does between `ruby_options` and `ruby_run_node` and why, how Ruby handles signals and console events ("Signals and the console"), and how a restart through `RbConfig.ruby` starts the app as it first started ("bin/ruby and restarts"). `doc/differences_from_ruby.md` tells app developers every difference and its reason.
