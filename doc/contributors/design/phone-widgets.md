# Phone Widgets

This document says how an app's Ruby draws its screen with each phone's own widgets: UIKit's on iOS and iPadOS, Android's views on Android. On iOS the app's own Ruby calls the Objective-C runtime through Fiddle, which Ruby bundles, and Fledge's runtime carries nothing for it; on Android its own Ruby calls Java through JNI in the same way. Fledge's runtime carries nothing for either phone. The app's Ruby runs on the thread those widgets belong to. Fledge ships no widgets of its own and no layer over them: the app makes the platform's own objects and calls them as the platform documents them. How the runtimes are built is `phone-runtimes.md`; the projects `fledge build` writes around them, `phone-projects.md`; what a developer does, `doc/phones.md`.

## The problem

A developer who knows Ruby, and no other language, should be able to ship a phone app whose screen follows each platform's interface guidelines, because it is made of that platform's widgets. Before this, a phone's Ruby could print to the log and run its program, and nothing else: no Ruby could make a `UILabel` or an Android `TextView`, lay it out, or hear a tap. The first phone app among the examples drew its screen from hosts of its own, 200 lines of Objective-C and 200 of Java per app, which asked the developer for two languages that are not Ruby; it was taken off `trunk` (a5ea8ab9). Every line of Objective-C, Swift, Java, or Kotlin an app needs is Fledge's, in its runtime or its templates, never the developer's.

## What a developer writes

Ruby, calling each platform's own classes. On iOS the app's Ruby is what a Ruby program would be under `ruby` on a Mac with UIKit, since it asks nothing of Fledge: `examples/basket/lib/basket/objc.rb` is such a program's Fiddle code, about 380 lines of Ruby that a developer copies and changes. With it a message is a method call whose name is the selector's first part and whose keywords are the rest, as RubyMotion spells them, and a Ruby class that inherits from one of UIKit's is an Objective-C class of that name:

```ruby
require_relative "objc" # examples/basket/lib/basket/objc.rb
ObjC = Basket::ObjC

class Rows < ObjC::NSObject
  objc_protocols "UITableViewDataSource"
  objc_method("tableView:numberOfRowsInSection:") { |_table, _section| ITEMS.size }
  objc_method("tableView:cellForRowAtIndexPath:") do |table, path|
    cell = table.dequeueReusableCellWithIdentifier("item", forIndexPath: path)
    content = cell.defaultContentConfiguration
    content.text = ITEMS.fetch(path.row)
    cell.contentConfiguration = content
    cell
  end
end
```

On Android the app's own Ruby calls Java through JNI, by the names Android's reference lists, and makes a Java interface's object of a Hash of lambdas. `examples/basket` carries the calls it needs in `lib/basket/android/` ("Android: no bridge of Fledge's", below), so its screen reads:

```ruby
button = Button.new(activity)
button.setText("Add")
button.setOnClickListener(Listener.implement(["android.view.View$OnClickListener"], onClick: -> (_view) { add }))
```

`fledge.yml` says `kind: windowed`, the key a desktop app names to open its own windows, so that the phone runs the app's Ruby on its widgets' thread ("Threads", below). `examples/basket` is such an app: a shopping list, its model in `lib/basket/list.rb`, its screen on iOS in `lib/basket/ios.rb` over its own `lib/basket/objc.rb`, and on Android in `lib/basket/android.rb`, with no file in any language but Ruby and YAML.

The developer writes two screens, one per platform, because each platform's widgets are its own and its guidelines differ: a table under a large navigation title with swipe-to-delete on iOS, a list under the app bar with a long press on Android. A layer that wrote one screen for both would be a widget toolkit, which is a framework's work, above Fledge, as Toga's is above rubicon-objc and rubicon-java; on neither phone does Fledge supply a bridge, and a framework or an app writes one or takes a gem's, since Fiddle is all it takes.

## The ways weighed

1. **The Objective-C runtime and JNI, called from Ruby through Fiddle (chosen).** Fiddle is in both phone runtimes already (`phone-runtimes.md`, "What a phone runtime holds"). On iOS the bridge is Ruby only, and the app's (Basket's `lib/basket/objc.rb`), not the runtime's: `objc_msgSend` with the types each method's encoding gives, `objc_allocateClassPair` and `class_addMethod` with a Fiddle closure for each method a Ruby class defines, as BeeWare's rubicon-objc does from Python's ctypes (beeware/rubicon-objc at 21378c10, `src/rubicon/objc/api.py`, lines 187 to 188, a ctypes function per method encoding; lines 1335 and 1387, the class pair; `runtime.py`, lines 1156 to 1161, a `CFUNCTYPE` as each IMP). On Android the calls are Ruby over JNI's own table of C functions, which Fiddle calls by pointer, and the app's too (Basket's `lib/basket/android/`): `doc/contributors/research/2026-11-25-pure-ruby-android-views.md` found that Ruby alone reaches the Java VM, a Context, and a Java interface's methods, with a class it writes in memory in place of the Java class of 47 lines, `org.setdef.fledge.RubyProxy`, and the dozen lines of C that the runtime carried until then (pyjnius's `NativeInvocationHandler` and rubicon-java's `PythonInstance` are the same shape: kivy/pyjnius at 24a32850, `jnius/src/org/jnius/NativeInvocationHandler.java`, line 38, `native Object invoke0`; `jnius/jnius_proxy.pxi`, lines 170 to 180, `RegisterNatives` and `Proxy.newProxyInstance`; beeware/rubicon-java at 2d3842db, `org/beeware/rubicon/PythonInstance.java`, line 33). What Fledge maintains of either bridge is nothing: Basket's iOS file is about 380 lines of the example's own, and its Android calls about 590. Both bridges were Fledge's until the research of 2026-11-25 (`doc/contributors/research/2026-11-25-pure-ruby-uikit.md` and the Android note above) showed that an app's own Ruby does on each phone all they did, which left no reason for Fledge to give an app a Ruby of its own beyond Ruby's. Android's was `Fledge::JNI`, about 740 lines of Ruby, and the iOS one `Fledge::ObjC`, about 480.
2. **The same bridges as a C extension in each runtime.** Calls would be faster, and the bridge would not need the `fiddle` gem, which a Gemfile must name ("Where the bridge lives"). But it is C that Fledge would write and keep for both phones, much of it the marshalling Fiddle already does, and on iOS it would need its own libffi for closures, where the runtime keeps libffi to Fiddle's extension alone so an app's own ffi gem finds no second copy (`phone-runtimes.md`, "What a phone runtime holds"). Code is a liability (decisions, 2026-10-28), so a bridge is written in C only where Ruby cannot reach, which on neither phone is anywhere now. A bridge that proves too slow on a device moves its hot path to C then, behind the same Ruby methods.
3. **A layer of widgets of Fledge's own** above either bridge, one screen for both phones. Not Fledge's job: Fledge ships a Ruby app, and a toolkit's choices (which widgets, which layout, which look) are a framework's, which the developer picks. Toga, Flutter, and React Native are frameworks, not packagers.
4. **Native hosts for each app,** as the first phone example had: refused, since they are the developer's Objective-C and Java.
5. **HTML in a web view, or an HTTP server on the phone,** to draw the app's own screen: refused. A native app draws with the platform's widgets, and a server on the loopback address is one every app on an Android phone can reach.
6. **Ruby on its own thread, with every call handed to the main thread and every callback handed back.** It would keep one thread model for every app, but CRuby runs Ruby only on its own threads ("Threads"), so each callback from UIKit or a view would wait on Ruby's thread while Ruby's calls waited on the main thread: a rendezvous in C on both phones, a thread switch for each call, and a deadlock wherever the two waits cross. No bridge of the prior art works so; each runs its language on the main thread.

## Threads

UIKit's objects are the main thread's alone, and an Android view is its window's thread's, which for an activity is the main thread: `ViewRootImpl.checkThread` throws "Only the original thread that created a view hierarchy can touch its views" (aosp-mirror/platform_frameworks_base at android-16.0.0_r1, `core/java/android/view/ViewRootImpl.java`, lines 11351 to 11357). So every call into the widgets, and every callback from them, is on the main thread.

CRuby runs Ruby only on a thread it made. A callback that arrives on another thread and asks for Ruby's lock ends the process: `rb_thread_call_with_gvl` prints "[BUG] rb_thread_call_with_gvl() is called by non-ruby thread" and exits (ruby/ruby at v4.1.0-preview1, `thread.c`, lines 2320 to 2335), and "You cannot convert a non-Ruby thread into a Ruby thread using this API" (`include/ruby/thread.h`, lines 111 to 114); no other public function does it. Fiddle's closures ask for the lock that way (fiddle 1.1.8, `ext/fiddle/closure.c`, lines 229 to 232). CPython differs: any thread may take Python's lock, and Python gives it up before it returns to Java (chaquo/chaquopy at 5cbe01a8, `product/runtime/src/main/python/chaquopy_java.pyx`, lines 88 to 92 and 319 to 320), so Python's bridges run Python wherever they are called. Ruby's must run Ruby on the main thread itself.

- **iOS.** For an app of `kind: windowed`, Fledge's `Host/main.m` runs the app's Ruby on the main thread, with the 64 MB stack Ruby has on a thread of its own (`-Wl,-stack_size,0x4000000`, as `test/fixtures/sdl_phone`'s host asks for it, proven on an iPhone; `phone-projects.md`, "A host that owns the main loop"), and the program hands the thread to UIKit by calling `UIApplicationMain` through Fiddle, with an application delegate written in Ruby (`Basket::ObjC.application_main`). That is an Objective-C app's own shape, and RubyMotion's: its generated `main` calls `UIApplicationMain(argc, argv, nil, @"#{delegate_class}")` on the main thread, after Ruby starts there (HipByte/RubyMotion at afc2f632, `lib/motion/project/template/ios/config.rb`, lines 600 to 614); NativeScript's script calls `UIApplicationMain(0, null, null, ...)` itself (NativeScript/NativeScript at 91cc673c, `packages/core/application/application.ios.ts`, line 758). Briefcase's template runs Python on the main thread too, and calls `UIApplicationMain` in C once Python has given up its lock (beeware/briefcase-iOS-Xcode-template at eccb2cde, `main.m`, lines 323 to 344), which Ruby has no way to do and return.
- **Android.** For an app of `kind: windowed`, Fledge's `MainActivity` starts Ruby with `FledgeRuby.startAppOnMainThread`: the asset is unpacked on a thread of its own, so the main thread never waits on the disk, and the app's Ruby then runs on the main thread, as Briefcase's Android template runs Python there, from the activity's `onCreate` (beeware/briefcase-android-gradle-template at 06e840f9, `MainActivity.java`, lines 61 to 131). Python's module returns to Android's loop; Ruby's cannot return and keep running, so the program hands the thread back by calling `Looper.loop()` itself, inside the loop Android's main thread already runs. Android allows that and logs a warning: `if (me.mInLoop) { Slog.w(TAG, "Loop again would have the queued messages be executed before this one completed."); }`, then loops (`core/java/android/os/Looper.java`, lines 319 to 324 at the same tag). Every message, every lifecycle call, and every listener's call into Ruby then comes from that loop. The main thread's stack is the process's, 8 MB on Android, which is what Ruby has on a Linux desktop's main thread.
- **Ruby's other threads** run meanwhile: Fiddle lets Ruby's lock go during each foreign call, `UIApplicationMain` and `Looper.loop` among them, and each callback takes it again. As in a native app, a thread other than the main one leaves the widgets alone, and posts its work to the main thread: on iOS with `performSelectorOnMainThread:withObject:waitUntilDone:` to an object of a class written in Ruby, on Android with a `Handler`'s `post` and a `Runnable` written in Ruby.
- **An app that draws nothing** keeps its Ruby on a thread of its own, as before (`kind: console`, the default), so a program that runs long never holds up the screen, and iOS's watchdog never stops it.

`kind: windowed` is the switch because it already means "this program draws its own screen" on every desktop, and a phone's build ignored it. A host that is not Fledge's, as SDL's is, runs Ruby where its framework does and is not touched (`phone-projects.md`, "A host that owns the main loop").

## Basket's iOS Ruby

`Basket::ObjC` (`examples/basket/lib/basket/objc.rb`) is the example's own Ruby, over Fiddle and nothing else, and it runs under any `ruby` on a computer with the Objective-C runtime; its tests (`examples/basket/test/objc_test.rb`) run on a Mac as any Ruby test does. Fledge's runtime has no part in it, and Basket tells an iPhone from an Android phone, and from a Mac, as any Ruby program could: by whether `RUBY_PLATFORM` includes `android` or `darwin`, and by whether `dlopen` finds UIKit, which a Mac lacks.

- **Classes.** Basket loads UIKit with `dlopen` before it uses it, since a process whose own code names none of UIKit's classes does not have the framework in it, and `objc_getClass` then finds no `UIResponder` (nor `objc_getProtocol` a `UITableViewDataSource`). `ObjC::UILabel` is the Ruby class for Objective-C's `UILabel`, made on first use, with Objective-C's superclasses as its own, so `is_a?` and inherited Ruby methods follow Objective-C's hierarchy. `new` is `[[Class alloc] init]`.
- **Messages.** A call's name and keywords spell the selector: `setTitle("Add", forState: 0)` sends `setTitle:forState:`, and `name = value` sends `setName:`. The method's own encoding, from `method_getTypeEncoding`, gives each argument's and the result's type, as rubicon-objc reads it; `objc_send("display")` sends a selector spelled in full, for a name Ruby's own objects take. A Ruby String passed as an object becomes an NSString, an Array an NSArray, and a Ruby class its Objective-C class. On arm64, the only architecture of Fledge's iOS targets, every result comes back through `objc_msgSend` itself: "The _stret variants only exist on x86-based architectures and ARM32" (rubicon-objc, `runtime.py`, lines 566 to 567).
- **Classes written in Ruby.** `class SceneDelegate < Basket::ObjC::UIResponder` registers an Objective-C class of the Ruby class's name; `objc_protocols` declares its protocols (`objc_getProtocol` finds only a protocol that compiled code in the process refers to, and UIKit's own are not always one, as a Simulator run of Basket showed for `UITableViewDataSource`; for the three UIKit protocols Basket implements, the bridge records each method's encoding from UIKit's headers and adds the methods without declaring conformance, which UIKit does not check, since it asks a delegate or data source `respondsToSelector:`; any other protocol is refused by name); `objc_method`, with a selector and a block, adds a method whose types come from the protocol, or are the ones passed. Objective-C's object and Ruby's are one: the bridge keeps the Ruby object of each instance until Objective-C deallocates it, so its instance variables last, as rubicon-objc keeps them by pointer (`api.py`, line 885).
- **References.** An object the bridge gives Ruby holds one reference to it, which it takes unless the method's family already gave the caller one, by clang's rules for automatic reference counting, as rubicon-objc reads them: `alloc`, `new`, `copy`, `mutableCopy`, and `init`, which also consumes its receiver's (`api.py`, lines 96, 278 to 279, and 974 to 975). When Ruby collects the object, the reference goes back on the main queue, with `dispatch_async_f` and `objc_release`, where rubicon-objc autoreleases on whichever thread Python collects on (`api.py`, lines 1002 to 1007), because UIKit's objects are the main thread's to free. That also keeps an object a Ruby method returns alive until the run loop's next turn, after UIKit has taken its own reference. An instance of a class written in Ruby that Ruby made itself is never given back: it lasts as long as the process, which a delegate, whose holder keeps only a weak reference, needs.
- **Exceptions.** A Ruby exception in a method Objective-C called would unwind through UIKit's frames, which corrupts them, so the bridge prints it as Ruby prints one its program does not rescue and returns zero, nil, or false; `exit` there ends the process with its status, without running `at_exit`. An Objective-C exception thrown under a call from Ruby ends the process, as it ends a native app.

What Basket's does not do, since Basket needs none of it: pass or return a struct by value, make a block, or call a superclass's implementation from a Ruby method. Plain Fiddle reaches the first two on an iPhone (research note, section 3): a `CGRect` is four doubles in arm64's floating-point registers and an `NSRange` two integers, both passed as such; a struct result comes back whole through `NSInvocation`; and a block is a structure in memory Ruby owns, whose class is `_NSConcreteGlobalBlock` and whose function is a `Fiddle::Closure`. Answering a message on a thread Ruby did not make ends the process ("Threads").

## Android: no bridge of Fledge's

An app's Ruby reaches Android's views with what Ruby gives every program: `fiddle`, `zlib`, and `digest`. The runtime holds no pointer to the Java VM, no Java class for Ruby to call, and no Ruby library for either, so the same Ruby runs under any Ruby on Android. `examples/basket` does it in `lib/basket/android/`, about 590 lines of Ruby, which a reader can take as an example or copy. What each part rests on, and the phones it ran on, is in `doc/contributors/research/2026-11-25-pure-ruby-android-views.md`:

- **The VM.** `JNI_GetCreatedJavaVMs`, JNI's own function, found by the first of three routes that answers (`Basket::Android::VM`): `Fiddle.dlopen("libnativehelper.so")`, which Android makes public from Android 12 (API 31); the program's own handle, which finds it on API 26 to 28; and on API 29 and 30, where Android keeps the library out of an app's reach, the address `/proc/self/maps` gives for the library plus the symbol's value in the library's own file. Basket takes the main thread's `JNIEnv` with `GetEnv`, and raises when Java has none for the calling thread, since Basket calls Java only from the main thread, which Java started.
- **Calls into Java** go through JNIEnv's table of C functions, which Fiddle calls by pointer. A call is by name: one call into Java, `Arrays.toString` of a class's `getMethods`, returns text in the format of `Method.toString`'s Javadoc, which lists every method of the class with its parameter types, and Ruby picks the overload whose parameters take the arguments (an Integer is an int or a long, a Float a float, a String a String, a CharSequence, or an Object, nil any object, and a Java object an instance of the parameter's class), then packs them by the JNI signature that listing gives. A constructor is listed the same way with `getConstructors`, and a name that is no static method, called with no arguments, reads a static int field, so `LinearLayout.VERTICAL` is 1. Fields the SDK hides are read with a descriptor spelled out. Strings cross as UTF-16, with `NewString` and `GetStringRegion`, never as JNI's modified UTF-8, which differs past Unicode's first plane (`phone-runtimes.md`, "The Java class"). A Java exception becomes a Ruby one, after it is cleared. Every Java object Ruby holds is a global reference that Ruby's collector deletes, since the local references of a program that never returns to Java would pile up.
- **The first Context.** Android gives a Context only to the components it creates, and no public call gives a program its Application or its Activity. Basket reads four members of `android.app.ActivityThread`, which Android lists as unsupported and allows every app today: `currentApplication()` and `currentActivityThread()`, and the fields `mActivities` and `ActivityClientRecord.activity`, for the Application and the Activity Android made before Ruby started. The public `Application.registerActivityLifecycleCallbacks` then gives it each Activity Android makes afterwards. A later Android may restrict the four, which would break the app and not Fledge.
- **Interfaces written in Ruby** (`Basket::Android::Listener`). ART implements no `DefineClass`, and the SDK has no class that turns a call of an interface's method into a call of native code. So Ruby writes a dex file of one class in memory, an `InvocationHandler` whose `invoke` is native (`Basket::Android::Dex`, about 110 lines), loads it with `InMemoryDexClassLoader`, public since API 26, the runtime's floor, gives `invoke` a Fiddle closure with `RegisterNatives`, and makes each listener with `java.lang.reflect.Proxy`, whose handler is that class. A call of a listener's method reaches the Hash of lambdas by the method's name, with Java's numbers and booleans unboxed, and its boolean or int result is boxed; a Ruby exception is printed and the call answers null, as on iOS. The APK holds no Java class of the app's, so there is no R8 rule to keep, and `FledgeRuby`'s rules keep only what the host calls.
- **The loop.** The program calls `Looper.loop()`, which Android allows inside the message it is handling ("Threads"), and the call never returns while the app runs. A Ruby program that ended with views still on the screen would leave closures behind, which Android's main thread would then call: a program that draws views ends only with its process.

What it does not do: subclass a Java class, an `Activity` or a `View`, which a proxy cannot (each would need a class written in dex, which `Dex` could learn to write); call Java from a thread Java did not start, which raises an Error since that thread has no `JNIEnv`; and call from a thread Ruby did not make, which ends the process ("Threads").

## Where the bridge lives

In the app, on both phones: Basket's `lib/basket/objc.rb` and `lib/basket/android/`. Neither runtime puts anything in Ruby's vendor folder, `lib/ruby/vendor_ruby/fledge/`, so `$LOAD_PATH` is what it is under `ruby main.rb` and the parity check sees no difference. Both need `fiddle`, a gem Ruby bundles: an app with no Gemfile has it, as under `ruby main.rb`, and an app with a Gemfile names it, as under `bundle exec`. An app tells the phones apart as any Ruby program tells platforms apart, by `RUBY_PLATFORM`, and Basket also asks whether UIKit loads, which a Mac's Objective-C runtime does not.

## The stores

- **iOS.** App Review's guideline 2.5.2 forbids an app to download or run code that adds or changes its features, and 2.5.1 asks that it use public APIs (`doc/contributors/research/2026-11-12-ffi-and-fiddle-on-phones.md`). The app's Ruby ships in its bundle, and it sends UIKit's public messages through `objc_msgSend`, which is how every Objective-C call is made. It generates no code: a Fiddle closure is libffi's, which on Apple's arm64 maps a pre-signed trampoline page with `vm_remap`, so no page is both writable and executable (`phone-runtimes.md`, "What a phone runtime holds", `closures.c`, lines 161 to 245). The Simulator does not enforce that, and a device does: fiddle's other path, a page made executable with `mprotect`, runs in the Simulator and is a process's end on a device. What covers it: Basket ran on an iPhone, and a closure there took the trampoline table (`doc/contributors/research/2026-11-25-pure-ruby-uikit.md`, section 1); `test/integration/mobile_closures_test.rb` fails when the device slice's `fiddle.bundle` stops defining `ffi_closure_alloc`, the symbol whose presence selects the path; the iOS Simulator runs Basket in CI; and an unsigned archive of every example passes Fledge's archive check. What does not yet: App Review, which needs an account (`doc/contributors/account-tests.md`, IOS-6).
- **Android.** Google Play's policy forbids downloading executable code from elsewhere than Play. The app's Ruby is in its APK, and so are the bytes of the one class Ruby writes: it comes from code in the APK, and `InMemoryDexClassLoader` and `java.lang.reflect.Proxy` are Java's own ways to load and implement a class at run time, which ART carries out; nothing is downloaded. What the policy's text on record does not say is whether it minds the unsupported `ActivityThread` members or the library found through `/proc/self/maps`, and no app has been submitted (the research note, "Google Play" and "What stays unproven").

## How it is checked

- `examples/basket/test/objc_test.rb`, which `test/basket_bridge_test.rb` runs among Fledge's unit tests, loads Basket's bridge into the test's Ruby on a Mac, whose libobjc and Foundation are iOS's: messages and keywords, strings past the first plane, arrays, a class written in Ruby that Objective-C calls, a protocol's encoding, an exception printed and not raised, a struct refused by name, and the reference each object holds. It skips elsewhere, and `test/phone.rb` runs it on an iPhone or in the Simulator too.
- `test/integration/mobile_closures_test.rb` reads the iOS runtime's device slice and fails unless its `fiddle.bundle` defines `ffi_closure_alloc`, without which a closure on an iPhone would take the `mprotect` path a device kills the process for.
- `examples/basket/test/java_test.rb` checks what Basket does with the text Java lists for a class (the methods and constructors it reads, the JNI signatures it builds, and the overload it chooses for given arguments), which `test/basket_bridge_test.rb` runs on any computer, and, in the app, calls a list, a constant, and a static method by name.
- `examples/basket/test/dex_test.rb` checks the dex file Basket writes for Android, as a computer's Ruby can: its header, its checksum and signature, and the order of its tables. The calls into Java and from it are proven on a phone, by the next item and by `fledge test android test/phone.rb`, which runs Basket's tests of its screen in the app.
- The mobile parity check builds and runs `examples/basket` in the iOS Simulator and on Android emulators (`tasks/mobile_parity.rb`). Its line, `Basket shows N items`, comes on iOS from the scene delegate written in Ruby, after the table asked Ruby's data source for its rows, and on Android from a `Runnable` written in Ruby that the main loop runs once the list is laid out: so it proves Ruby on the main thread, the platform calling Ruby, and Ruby's views on the screen. The check then does what a person does with the list, and Basket prints `Basket added Milk` and `Basket removed Milk`, which the check requires. On Android it types `Milk` into the field with `adb shell input`, presses Enter (`keyevent 66`), which the field's editor action listener written in Ruby turns into adding the item, and waits for UI Automator to show a row of that text, so the adapter inflates a row; then it presses the row for a second and a half, which the list's long-click listener turns into removing it, and waits for the row to go. simctl gives an app no keys or touches, so on iOS the check runs a UI test of its own (`tasks/mobile_parity/ios_ui/ListUITests/ListTest.m`), with XCTest, Apple's own UI testing, which finds the running app by its identifier, types `Milk`, taps the on-screen keyboard's Return key, which UIKit turns into the field's `UIControlEventEditingDidEndOnExit` action, written in Ruby, waits for a row of that text, then swipes the row left, taps Delete, and waits for the row to go: UIKit asks Ruby's data source for the cell, and sends it `tableView:commitEditingStyle:forRowAtIndexPath:` for the swipe. A phone's own keyboard and a finger on its screen are proven only by hand: on an iPhone built from 49c98724, Return added no item though the Add button did, which the Simulator, with the same Basket and runtime, does not reproduce (issue #128); a device's log, where Basket prints `Basket added` and a Ruby exception in its action prints its backtrace, says there whether Return reached Ruby. On an iPhone the UI test has passed twice. The first run, of commit 3830c1f0, was on Basket over the runtime's former bridge, `Fledge::ObjC`, and Basket's console showed `Basket added Milk` and `Basket removed Milk`, so Return reached Ruby there (`doc/contributors/research/2026-11-25-pure-ruby-uikit.md`, section 4). The second run was on Basket over its own bridge, `examples/basket/lib/basket/objc.rb`, built from content identical to a1d3b5ef, and the test passed again on an iPhone 12 mini under iOS 27.2.1, signed for development. On that run Basket's `puts` and NSLog lines did not reach the Mac through `xcrun devicectl device process launch --console`, for a reason not found, so the console lines of the first run were not seen on the second.
