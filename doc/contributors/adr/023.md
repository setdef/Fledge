# ADR 023: A JSON Schema for fledge.yml

## Status
Accepted (requested). Agents wrote this ADR and may change it (AGENTS.md, Questions). The maintainer asked for a JSON Schema of `fledge.yml` that editors can complete and check the file with. It describes the keys ADR 005 (section 3), ADR 008 (section 1), ADR 009, and ADR 021 gave `fledge.yml`, and adds none.

## Date
2026-11-02

## Context

`fledge.yml` refuses an unknown key and checks each value (`Fledge::Config`), but a developer learns of a mistake only when `fledge build` runs. Editors that run Red Hat's YAML language server (VS Code's YAML extension, and other editors that start the same server) complete keys, show descriptions, and mark mistakes as the developer types, once the file names a JSON Schema. The server's README (redhat-developer/yaml-language-server at 7e8061c7, `README.md`) says it reads draft-04, draft-07, 2019-09, and 2020-12 (line 9), and that a file names its schema with a modeline comment, `# yaml-language-server: $schema=<schema-url-or-path>` (lines 81 to 95), or through SchemaStore's catalog (lines 57 to 58).

A schema is a second statement of what Config enforces, so the question is how to keep the two from disagreeing. Two designs were considered:

- **Generate the schema from Config**, with a rake task, a checked-in result, and a gate step that fails when it is stale, as `tasks/licensing_page.rb` keeps `doc/licensing.md`. Tauri generates `tauri.conf.json`'s schema this way, from the Rust types its configuration is parsed into. Config is not a set of types: it is Ruby that checks each value and raises with a message. A generator could read `KEYS`, `KINDS`, `INSTALLERS`, `IDENTIFIER`, and `IDENTIFIER_MAX`, but every description, the version's pattern, the icon's refused extensions, the non-blank rule, and the two rules between keys would live in the generator as literals. The generator would be the schema written in Ruby, plus a task, a staleness check, and its own tests.
- **Write the schema by hand, and test it against Config.** The file is the one place its facts are stated. A test compares its keys, kinds, installers, default installers, identifier pattern, and identifier length with Config's constants, and runs a table of documents through both the schema and Config (with `Fledge::Identity`, which refuses a windowed app with no identifier), failing when either accepts what the other refuses.

## Decision

### 1. The schema is written by hand and tested against Config

`lib/fledge/config.schema.json` is the schema, written by hand, because it is the smaller design: one file, and one test file, `test/config_schema_test.rb`. The test uses json_schemer (MIT, with hana, regexp_parser, and simpleidn, all MIT, and bigdecimal, Ruby's license), a development dependency pinned in the Gemfile and Gemfile.lock; nothing Fledge ships loads it. It reads patterns as ECMA-262 does (`regexp_resolver: "ecma"`), as editors do, so `^` and `$` mean the ends of the text, not of a line. It also checks the schema against draft-07's meta-schema, and that every `fledge.yml` in the repository names the schema and passes both the schema and Config.

A change to a constant in Config, to how Config checks a value, or to the schema fails the test until the other agrees.

### 2. Draft-07, with what Config enforces and nothing it does not

Draft-07 is the draft every editor reads. The schema holds:

- the eight keys, and `additionalProperties: false`, since Config refuses any other key;
- each value as text, or empty (YAML's `name:` with nothing after it), which Config reads as absent; text that is blank to Ruby's `String#strip` is refused, by a pattern that needs one character outside Ruby's whitespace and NUL;
- `kind` from `console` and `windowed`, with `console` as the default;
- `identifier` as Config's `IDENTIFIER` pattern, with `\A` and `\z` written `^` and `$`, in at most 128 characters;
- `version` as RubyGems' `Gem::Version::ANCHORED_VERSION_PATTERN` (RubyGems 4.0.20), which `Gem::Version.correct?` uses, less its leading whitespace, since Config also needs a leading digit, with its atomic group written as a plain one (the group's characters never overlap what follows it, so the two match the same text) and Ruby's `\s` spelled as its six ASCII characters; a number is refused, as Config refuses `version: 1.2`;
- `icon` refused when it ends in `.png`, `.icns`, or `.ico`, in any case;
- `installers` as a list of `dmg`, `nsis`, `appimage`, and `deb`, defaulting to the first three, and only for a windowed app when the list is not empty;
- a windowed app's `identifier`, which Fledge::Identity requires.

Descriptions come from the `fledge.yml` section of `exe/fledge`'s help.

Config rules the schema does not hold: a file that is not valid YAML is the language server's to report, and a YAML value that `YAML.safe_load` refuses (a date, say) is refused by Config as invalid YAML where the schema sees no such type. Neither needs a schema rule.

### 3. The schema's address is the trunk URL until a tag holds it

The gem ships the file at `lib/fledge/config.schema.json`, which the gemspec already packs. Its `$id`, and the modeline the examples and Config's documentation give, is
`https://raw.githubusercontent.com/setdef/Fledge/trunk/lib/fledge/config.schema.json`. Once a release holds it, `https://raw.githubusercontent.com/setdef/Fledge/vX.Y.Z/lib/fledge/config.schema.json` is the same file for that release, and a developer who wants their editor to match the Fledge they build with can name that one instead. The trunk URL may describe a key the developer's release does not have yet; the build, not the editor, decides.

Every `examples/*/fledge.yml` and every `fledge.yml` among the test fixtures starts with the modeline. It is a YAML comment, so neither Config nor a built app reads it.

SchemaStore's catalog would associate the schema with every file named `fledge.yml` without a modeline. Submitting it is a change in another project's repository, so it is left to the maintainer.

## Consequences

- A developer who adds the modeline gets completion, descriptions, and errors for `fledge.yml` in their editor.
- A new key, kind, or installer, or a changed rule, fails `test/config_schema_test.rb` until the schema says the same; the test's table of documents grows with each new rule.
- A RubyGems upgrade that changes what it reads as a version fails the test's version cases, and the schema's pattern follows it.
