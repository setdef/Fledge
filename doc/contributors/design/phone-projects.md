# Phone Projects

This document says what `fledge build ios` and `fledge build android` write, how a gem's extension is compiled for a phone app and carried in it, how a framework's own startup files enter the project, and what CI checks before a store would. The decision is ADR 012 (a project the developer builds and signs); the reasons for the rest are given with what each section describes. The runtime the project holds is `doc/contributors/design/phone-runtimes.md`. What a framework may rely on is `doc/contributors/design/public-interface.md`, "Phones". What a developer does with the project is in `doc/phones.md`; this document adds the internals.

## The projects

### The operand

`fledge build ios [PATH]` and `fledge build android [PATH]` name the phone as the first operand, where Briefcase's `briefcase create iOS` and Flutter's `flutter build ios` name it. Which phone is a question of each build, as which desktop is, and not a property of the app, so `fledge.yml` has no `targets:` key (one build would write several outputs that need different computers), and the command takes no option such as `--ios` (no prior art reads one). The build stays one command, not Tauri's `tauri ios build`, which splits one action in two. A first operand named `ios` or `android` is the phone; a folder of that name is written `./ios`, or follows `--`. `exe/fledge`'s help header documents it, and `test/build_command_test.rb` and `test/mobile_build_test.rb` test the operand, the `./ios` form, and the refusal on a computer that cannot build the phone's project.

### What a build writes

`fledge build ios` and `fledge build android` write `OUT/NAME-ios/` or `OUT/NAME-android/`, named as a desktop's folder is, replacing an earlier one, and print its path. `Fledge::MobileProject` (`lib/fledge/mobile_project.rb`) does what both share:

1. checks the app has an identifier, and that a host folder `fledge.yml` names is a folder in the project;
2. unpacks the phone's runtime, found and checked against the pins as every runtime is (`Fledge::Runtimes`);
3. copies the system's template from `lib/fledge/templates/`;
4. compiles the gems' extensions, when the app has any, and places the runtime and the extensions as the system needs;
5. writes the folder `fledge/`: `fledge.cfg`, the project in `app/` (but the output folder and any host folder), the app's gems in Ruby's gem folder, and the runtime's `notices/`, refusing a file that would replace one of the runtime's Ruby;
6. copies the host's files over the project (see "Host files");
7. fills the template's marks (`@@NAME@@` and the rest) with the app's values;
8. copies the icons, and finishes the project as the system needs.

It writes in a temporary folder inside `OUT` and moves the project into place, and removes what it wrote if the build fails. It writes the project afresh each time, so a change made in it by hand lasts until the next build; a framework keeps its own files across builds in a host folder (see "Host files"). On the phone, Ruby's root is `fledge/` merged with the runtime's `lib/` and `libexec/`.

Each phone's project is built where its tools run (`Fledge::MobilePlatform::HOSTS`): iOS on `arm64-darwin`; Android on `arm64-darwin`, `x86_64-linux`, and `x64-mingw-ucrt`. `aarch64-linux` is left out, since Google publishes no Android SDK build tools for it. Elsewhere the build says where to build it and exits 1.

Nothing configures signing. `xcodebuild` builds for the Simulator, and for a device with `CODE_SIGNING_ALLOWED=NO`; the developer chooses a team in Xcode to run on a device. `./gradlew assembleDebug` and `bundleDebug` sign with the Android SDK's debug key, and `assembleRelease` and `bundleRelease` leave the app unsigned, for the developer's own key. Fledge holds no key and never submits an app. The developer's own tools build the project: Xcode and XcodeGen for iOS, and a JDK and the Android SDK for Android, where Gradle's wrapper fetches the pinned Gradle.

## The Xcode project

`Fledge::MobileProject::IOS` writes XcodeGen's `project.yml` from its template (`lib/fledge/templates/ios/project.yml`), and `xcodegen generate` writes `NAME.xcodeproj`, so Fledge writes no Xcode project file. `project.yml` stays, for the developer to change and generate again. XcodeGen is a tool the developer installs; without it the build names it and how to get it (`MobileProject::IOS::INSTALL`).

- `FledgeRuby.xcframework` is linked, and embedded only where its Ruby is a framework (`FledgeRuby.framework` in each slice, the `@@RUBY_EMBED@@` mark): 0.17.0's runtime is a static library, which an app links and does not embed. `FledgeExtensions.xcframework`, for an app whose gems have extensions, is linked, not embedded, being a static library. Each library for Ruby's ffi that a gem's build made is the other way round: `Frameworks/NAME.xcframework`, embedded and not linked, since Ruby's ffi opens it by its path ("Libraries for ffi on iOS"). So is each extension of Ruby's own that the runtime lists in its slices' `fledge.links` (`MobileProject::IOSRubyExtensions`): the build makes its XCFramework from both slices' files as it makes a library's for ffi, with the same `Info.plist`, and puts in each slice's `lib/ruby` a relative link at the extension's path, where the file was (`doc/contributors/design/phone-runtimes.md`, "Ruby's extensions on iOS"). The list's line for Ruby's own library, `FledgeRuby`, makes no framework, only a link at `lib/libfledgeruby.dylib`, where RbConfig names it, to the embedded `FledgeRuby.framework`'s binary. A runtime that lists none, as 0.17.0's, gets none.
- The build phase "Copy Ruby and the app" copies the slice's `lib/` and `libexec/` for the SDK the build is for, then `fledge/`, into the bundle's `fledge/` folder with `ditto`, as CPython's "Process Python libraries" copies its slice's standard library. User script sandboxing is off for it (`ENABLE_USER_SCRIPT_SANDBOXING: NO`), as CPython's documentation sets it.
- `Host/` holds `main.m`, the app's `Info.plist`, its privacy manifest, and its asset catalog.
- The target builds for `arm64` alone, the only architecture the runtime has, for iOS 15.0 and later, with `TARGETED_DEVICE_FAMILY` `1,2` for iPhone and iPad.
- The marks are JSON strings, which YAML reads as quoted ones: the name, identifier, version, icon name, and the extensions' linker flags in `OTHER_LDFLAGS` (after `$(inherited)`).

## The Gradle project

`Fledge::MobileProject::Android` writes a Gradle project of one app module (`lib/fledge/templates/android/`):

- **Gradle's wrapper,** the very `gradle-wrapper.jar`, `gradlew`, and `gradlew.bat` that the pinned Gradle writes, pinned to the distribution and SHA-256 Fledge's runtime builds with. `runtime/sources.yml` pins the jar's SHA-256 too, and CI validates it with Gradle's own wrapper-validation action. The Android Gradle plugin is the version the runtime builds with (`MobileProject::Android::AGP`).
- **`libs/FledgeRuby.aar`** is its dependency, and `fledge/` holds the runtime's `lib/` and `libexec/`, since one Ruby serves both ABIs, with RubyGems' wrappers of the runtime's and the app's gems' commands in `libexec/commands/`, and a line of `fledge.links` for each that makes `bin/NAME` a link to the ruby program as the app starts (`doc/contributors/design/phone-runtimes.md`, "Gem commands on Android").
- **The task `fledgeAsset`** stores `fledge/` uncompressed as the asset `fledge.zip`, with the Ant that Gradle carries (`ant.zip`), into a folder its task declares as output, which the plugin takes as generated assets on every variant (`addGeneratedSourceDirectory`). The folder must be the task's declared output: Gradle's own `Zip` task writes into a folder that is not one of its outputs, so the plugin never ran it and the asset was missing.
- **`androidResources.noCompress += ['zip']`** keeps `fledge.zip` stored in the APK and in every APK made from the app bundle, and `useLegacyPackaging = true` compresses the native libraries, so that the package installer extracts them into the app's native library folder, the only files Android lets an app run, among them the runtime's ruby program (`doc/contributors/design/phone-runtimes.md`, "The ruby program on Android"), and the only files Ruby loads an extension from, among them Ruby's own extensions and encodings (same document, "Ruby's extensions on Android"). With `useLegacyPackaging = false` the plugin writes `android:extractNativeLibs="false"`, and "your native libraries are stored uncompressed in the APK" and load from it (developer.android.com, `<application>`, `android:extractNativeLibs`). Compressed libraries cost space once installed: the app keeps the extracted libraries beside the APK's compressed ones, and Android's page-size guide warns that such an app "takes up more space when installed" and "might more frequently fail to install" (developer.android.com, "Support 16 KB page sizes"), though its download is smaller. Every Android app pays it, those that never start Ruby too, which is the trade decision 20 makes: "Tiny filesize is not a priority; "my ruby code just works" _is_ a (high) priority." Each library's LOAD segments are aligned for 16 KB pages, as Play requires, and an extracted library needs no alignment in the zip. With `false` no extension of Ruby's own would load, nor any encoding but those Ruby builds in, so every app whose `build.gradle` sets it to `false` is refused ("Refusals"), as it is when `build.gradle` sets nothing, which the plugin takes as `false` for a `minSdk` of 23 or later ("A host's copy after an upgrade"). Until 0.13.0 the template set it to `false`, so a host's copy of `build.gradle` made from it says so. The bundle check fails a bundle whose native libraries are stored (see "The Android App Bundle check").
- It targets and compiles against API 36, as Google Play requires of new apps and updates, and runs on API 26 and later, as the runtime does.
- Its manifest asks for `android.permission.INTERNET`, since a Ruby program may reach the network on a desktop (decision 20).
- The host's Java package is Fledge's own, `org.setdef.fledge.host`, the plugin's `namespace`, apart from the `applicationId`, so no identifier collides with Java's keywords.
- The marks are written as each file reads them: Groovy's single-quoted strings in the Gradle files, and an escaped Android string resource in `strings.xml`.

## Identity on a phone

The app's identity is `fledge.yml`'s (`doc/contributors/design/desktop-apps.md`, "Identity on each system"), where each system shows it:

- **identifier:** the bundle identifier on iOS and the `applicationId` on Android. A phone's app has to have one, so a phone's build without it fails, suggesting one. Android takes only parts that begin with a letter and hold letters, digits, and underscores (`MobileProject::Android::APPLICATION_ID`), so an identifier with a hyphen, or a part that begins with a digit, fails for Android with one it would take.
- **name:** `PRODUCT_NAME` and `CFBundleDisplayName` on iOS, and the label on Android.
- **version:** `MARKETING_VERSION` and `CURRENT_PROJECT_VERSION`, its first three numbers (`Fledge::MacBundle.bundle_version`), on iOS. On Android, `versionName` as it is, and `versionCode` made of its first three numbers, three digits each (1.2.3 is 1002003), as Briefcase pads a version's parts, so each later version has a greater code; 0.0.0 gets 1, Android's lowest, and a version whose code would pass Play's 2,100,000,000 is refused (`MobileProject::Android.version_code`). An app with no `version` is 0.0.0 (see "Export compliance and the build number").
- **icon:** the files `fledge.yml`'s `icon` names, as the desktop's are named: `ICON-1024.png` for iOS, the one size an asset catalog's app icon needs, from which Xcode makes the rest, in `Host/Assets.xcassets`; and `ICON-48.png`, `-72`, `-96`, `-144`, and `-192` for Android, each density's launcher icon in `mipmap-mdpi` to `mipmap-xxxhdpi`. Fledge copies them and reads no image (`doc/contributors/design/desktop-apps.md`, "Icons"). Without an icon, each system shows its own, and the iOS project drops its asset catalog.

## Gems on a phone

No gem publishes a build for a phone, so a phone's app ships each gem's `ruby` build, with Bundler's own `force_ruby_platform` in the app's `.bundle/config` (`doc/contributors/design/phone-runtimes.md`, "Targets"; `Fledge::MobilePlatform#force_ruby_platform?`). A gem that also publishes builds for desktops ships its `ruby` build, and an iOS Ruby, which reports `arm64-darwin`, never resolves a macOS gem. Since the app's Bundler runs with it, the lockfile must lock `ruby`, and a build that finds it unlocked says so, naming `bundle lock --add-platform ruby`. A gem the lockfile locks no `ruby` build of fails as a desktop build fails for a gem with no build for it. A gem with a C or C++ extension is compiled for the phone (see "Gems with extensions"). Gems' licenses stay the developer's business (`doc/contributors/design/gems.md`, "Checks that are not about licenses").

## The host app

Each template's host is as small as the embedding API allows, and the developer's to change (`lib/fledge/templates/ios/Host/main.m`; `lib/fledge/templates/android/src/main/java/org/setdef/fledge/host/MainActivity.java`):

- it shows the app's name on one screen: in the one UIKit scene that apps built with the iOS 26 SDK must use, and in one Android `Activity`;
- it sends standard output and standard error to the system log under the identifier;
- it runs the app with `fledge_ruby_run_app` on a thread of its own with a 64 MB stack, as `FledgeRuby.startApp` does on Android, so the interface never waits for Ruby and iOS's watchdog never stops an app whose program runs long;
- it passes no arguments, since a phone has no command line, and logs `NAME exited with status N` when the program ends;
- on Android, it starts Ruby once per process, so an Activity Android creates again does not start it again, and it loads nothing but what `FledgeRuby` loads itself: the runtime opens `libfledgeext.so` before Ruby boots ("Linking extensions on Android").

The app stays open when the program ends: iOS's guidelines and Android's leave quitting to the person. A framework replaces the host with its own files (see "Host files"), keeping the two calls.

## The privacy manifest

`Host/PrivacyInfo.xcprivacy` declares the APIs Apple requires a reason for ("Describing use of required reason API", developer.apple.com) that Fledge's Ruby calls, as `nm -u` lists the imports of a built app's executable:

- `stat`, `fstat`, `fstatat`, `lstat`, `getattrlist`, and `fgetattrlist`, among Apple's file timestamp APIs, with reason C617.1 (files inside the app's container);
- `mach_absolute_time`, among the system boot time APIs, with reason 35F9.1 (time elapsed between events in the app).

It also says that the app tracks no one and collects nothing, which the developer changes for their own app. Ruby calls no disk space API (`statfs`, `statvfs`), so none is declared.

CI checks each built app's imports against its manifest (`MobileParity::IOS#check_privacy`, `tasks/mobile_parity/ios.rb`), so a Ruby that starts calling another such API fails there. The check also compares reasons: each category the manifest declares that Fledge's template gives a reason must still name it. `getattrlist`, `fgetattrlist`, and `getattrlistat` are not in the check's disk space row, though Apple lists them there too, because Ruby's `dir.c` calls them for the filesystem's type and the check matches by function name only.

## Gems with extensions

`Fledge::MobileExtensions` (`lib/fledge/mobile_extensions.rb`) compiles an app's gems' C, C++, and Rust extensions for every target of the phone, one after the other: `ios-arm64` and `ios-arm64-simulator` with Xcode on a Mac; `aarch64-linux-android` and `x86_64-linux-android` with the NDK on a Mac or x86-64 Linux. An Android build with extensions on Windows is refused (see "Refusals").

For each target and each extension an `extconf.rb` builds, it does the following (a Rakefile's is under "Rakefiles", below):

1. unpacks the gem's source afresh into a folder of the target's own, from where Fledge already has it: a server's `.gem` with `Gem::Package#extract_files`, a path gem with `PathPackage#copy_to`, a git gem from its checkout;
2. runs `bin/ruby --disable-gems -I RBCONFIG -I DEPENDENCIES -r SHIM extconf.rb ARGS` with **this computer's desktop runtime's Ruby**, where RBCONFIG is a folder of the build's own that holds only an `rbconfig.rb` that loads the phone runtime's for the target, at its own path (iOS: in the slice's `lib/ruby/VERSION/arm64-darwin`; Android: `lib/ruby/VERSION/ABI-linux-android`; `MobileExtensions.rbconfig_folder`), not that folder itself, from which this computer's Ruby would load the phone's extensions in place of its own: the iOS runtime keeps its extensions there at a desktop's paths, in a folder of a Mac's name, and the build's `require "json"` then met an iOS library that dlopen refuses; DEPENDENCIES are the require paths of the app's gems that the compiled gems depend on, at any depth (`AppGems#extension_dependencies`, unpacked once), so that an `extconf.rb` finds rb_sys, or mini_portile2, as it would under RubyGems, and ARGS are Bundler's `build.NAME` options for the gem; `rbconfig.rb` finds its prefix from its own path, so mkmf reads the phone Ruby's configuration, `CROSS_COMPILING` included;
3. runs `make static`, which makes `NAME.a`, or for a Rust extension the goal that has Cargo make a static library ("Rust extensions");
4. reads the report the shim wrote, the feature, the archive, and the libraries the `extconf.rb` gave mkmf in `$libs`, and asks make for the Makefile's `LOCAL_LIBS` as make expands it (`Linking.local_libs`), which mkmf links the shared library with on a desktop: the `extconf.rb` may add to it after mkmf is done, as the ffi gem's appends a makefile that builds its own libffi and adds that library there (`ext/ffi_c/libffi.gnu.mk`, line 8 at 1.17.4).

**The shim** (`MobileExtensions::SHIM`) is loaded before the `extconf.rb`. It puts this computer's tools in place of the ones `rbconfig.rb` records, which are the CI machine's paths: Xcode's `clang` and `clang++` aimed at the recorded `-target` triple and the SDK's sysroot, or on Android the NDK's clang of the very name recorded (`aarch64-linux-android26-clang`), `llvm-ar`, and `llvm-ranlib`. It points `rubyhdrdir` at the runtime's headers, and `LIBRUBYARG` at `libfledgeruby` (`-L SLICE -lfledgeruby -lz ...` on iOS), so mkmf's link tests answer as they would in Ruby's own build: `have_func("rb_str_new", "ruby.h")` links. It takes out of `CPPFLAGS`, `CFLAGS`, `CXXFLAGS`, `LDFLAGS`, and `DLDFLAGS` each `-I`, `-L`, `-F`, or `-isystem` that names a folder outside the runtime, and out of `configure_args` each `--with-NAME-dir`, `-include`, or `-lib` option that does: they are the folders of the computer that built the runtime, where its OpenSSL, libyaml, and libffi were (`tasks/runtime_builder/mobile.rb`, `ios.rb`, and `android.rb`), and mkmf starts its flags from them, compiles and links every check with them, and reads the options as the extension's own (`lib/mkmf.rb`, lines 110, 1895, 2778, and 2957 at Ruby 4.1.0-preview1). Where those folders still are, as on a computer that built the runtime, the ffi gem's `have_library("ffi")` found the runtime's own libffi, and the app's link, which has no such folder, failed with `unable to find library -lffi`; everywhere else they name nothing, so the checks now answer everywhere as they did on CI. The compilers themselves search only the phone's sysroot: the NDK's clang its own `sysroot`, and Xcode's clang the SDK `-isysroot` names, so a library this computer has, such as Ubuntu's libffi, is found only where an `extconf.rb` names its folder. The developer's own options for a gem reach mkmf as arguments, and are kept. It sets mkmf's `$static`, as `ext/extmk.rb` does for an extension it links in (line 655 at Ruby 4.1.0-preview1), and wraps `create_makefile` to add `-DInit_NAME=Init_fledge_N`, N counting the app's extensions from 0, as `extmk.rb` renames `Init_cparse` to `Init_racc_cparse`, so two gems' extensions cannot clash in one binary. The define goes into `$CPPFLAGS`, which mkmf writes into the Makefile's `CPPFLAGS` always, not `$defs`, which mkmf leaves off the compile line once an `extconf.rb` has called `create_header` (`mkmf.rb`, lines 2133 and 2175 at Ruby 4.1.0-preview1).

The shim also loads RubyGems, once the phone's `rbconfig.rb` is loaded, though the Ruby starts with `--disable-gems`: on a desktop RubyGems runs an `extconf.rb` with `Gem.ruby`, RubyGems loaded (`Gem::Ext::ExtConfBuilder.build`, `lib/rubygems/ext/ext_conf_builder.rb`, line 26 at Ruby 4.1.0-preview1), and an `extconf.rb` may use it: sassc 2.4.0's reads `Gem::Platform.local` (`ext/extconf.rb`, line 30), which stopped its build for either phone with `uninitialized constant Gem` until the shim loaded it. `Gem::Platform.local` is then made from the phone's `RbConfig::CONFIG["arch"]`.

**A library for ffi from an `extconf.rb`.** An `extconf.rb` may build with mkmf a library that is no extension of Ruby's, which Ruby's ffi opens by its path: sassc 2.4.0's compiles libsass, links no libruby (`$LIBRUBYARG = nil`), and leaves out the export file that would name an `Init_libsass` "which we don't have" (`ext/extconf.rb`, lines 72 to 78), and `lib/sassc/native.rb` opens `lib/sassc/libsass.DLEXT`. On Android such a library is built as a file, as every C or C++ extension is ("Linking extensions on Android"), and linked at the desktop's path, so nothing tells it from an extension; a `strip` its link runs is the NDK's ("The environment kept out"). On iOS, Fledge reads the names the archive `make static` made defines (`Separation::Tools#names`): when its renamed Init function is not among them, it is no extension, registers nothing, and gets no Ruby file at its path. Fledge runs the Makefile's default goal instead, which links on a desktop, with the compilers through `RakeBuild::DYLIB`, so that mkmf's `-bundle` becomes `-dynamiclib`, and the library is a library for ffi ("Libraries for ffi on iOS"), at the path in the gem where a desktop's RubyGems copies it (`lib/sassc/libsass.bundle`). Before, it was linked into the app as an archive, registered under an Init function the archive does not define, and Xcode's build of the app failed. `test/fixtures/ffi_extconf` is such a gem, a path gem whose `extconf.rb` takes each of sassc's steps, and `test/integration/mobile_ffi_extconf_test.rb` builds it and runs it on each phone; sassc 2.4.0 itself, in the fixture's place, printed its CSS in the iOS Simulator and on an x86-64 Android emulator on 2026-11-22.

Running each gem's own `extconf.rb` with mkmf adds no build system: mkmf is the tool every C extension already has, Ruby's own build cross-compiles its extensions with it (`ext/extmk.rb`), and the `extconf.rb` keeps its configuration checks and the `extconf.h` it writes ("code is a liability", decisions, 2026-10-28). The build runs on the computer that builds the phone's project, with that phone's own compilers, Xcode's or the NDK's (decisions, 2026-10-28), and `require "name/name"` finds the extension as on a desktop (decisions 9 and 10; "Registering extensions" and "Linking extensions on Android"). Two other ways were weighed. rake-compiler and rake-compiler-dock, a gem's own Rake task and a Docker image per target, know no phone, and Docker is not the platform's own tool. Gradle's CMake integration, building each gem's sources from a `CMakeLists.txt` Fledge writes, would skip the `extconf.rb`, losing its checks and its `extconf.h`, and iOS has no such path. What it costs: a phone's build with extensions needs this computer's desktop runtime, whose Ruby runs mkmf, beside the phone's, and Android's needs the developer's NDK ("The NDK", below).

**Rust extensions.** A gem that depends on rb_sys has an `extconf.rb` that writes rb-sys's Makefile with `create_rust_makefile`, whose `$(RUSTLIB)` goal runs `cargo rustc --target $(CARGO_BUILD_TARGET)` and exports the Ruby it compiles for as `RBCONFIG_` variables from `RbConfig::CONFIG`, which rb-sys's build script reads in place of a Ruby it runs when `CROSS_COMPILING` is `yes` (`rb-sys-build/src/rb_config.rs`, lines 64 to 108 and 252 to 257 at 0.9.130). Since the shim has already put the phone's headers and compilers in `RbConfig::CONFIG`, bindgen reads the phone Ruby's headers. `MobileExtensions::Rust` adds, for such a gem:

- **Cargo's target** in `CARGO_BUILD_TARGET`, which rb-sys's Makefile and Cargo both read: `aarch64-apple-ios`, `aarch64-apple-ios-sim`, `aarch64-linux-android`, `x86_64-linux-android` (`Rust::TRIPLES`), as Tauri's `tauri ios` and `tauri android` build them, and as rustup names the standard libraries the developer adds (`rustup target add`). `Rust.check` fails, naming the gem and the `rustup target add` to run, when the standard library for the target is missing.
- **For iOS**, `IPHONEOS_DEPLOYMENT_TARGET` from the runtime's triple, which rustc reads; bindgen's `BINDGEN_EXTRA_CLANG_ARGS_<target>` with `-isysroot` and the slice's SDK, which bindgen reads for that target alone (`bindgen/lib.rs`, `get_target_dependent_env_var`, at 0.72.1), so a build script compiled for this computer is not aimed at iOS; and `RBCONFIG_target_os` `ios` in place of the `darwin` the runtime's `rbconfig.rb` records, since rb-sys refuses headers whose system it counts in another family than Cargo's target's, and counts `darwin` and `ios` as two (`validate_cargo_target`, `rb_config.rs`, lines 236 to 250 and 531 to 587).
- **For Android**, the NDK's clang, clang++, and `llvm-ar` in the cc crate's per-target `CC_<target>`, `CXX_<target>`, and `AR_<target>`, for a crate that compiles C, and bindgen's `--target` with the API level of the compiler the runtime was built with (`aarch64-linux-android26`, which the NDK's headers ask for, where bindgen would pass Rust's target, which has none) and `--sysroot` at the NDK's sysroot; and the NDK's own libclang (`LIBCLANG_PATH`, the toolchain's `lib/`, the only folder clang-sys then searches), the clang the C build compiles with, with its own builtin headers by `-resource-dir`, the folder `CC -print-resource-dir` names: the NDK's libclang does not find that folder by itself (a probe that loaded it parsed `#include <stdarg.h>` for `aarch64-linux-android26` with "'stdarg.h' file not found", and with `-resource-dir` cleanly). This computer's libclang was tried first and failed both ways: the build machine's had no builtin headers (`stdarg.h` not found), and adding the NDK clang's with `-isystem` on a runner whose libclang had its own made two `stdint.h` that share one include guard, so the second, which reaches the sysroot's, was skipped (`uint32_t` unknown).
- **A second shim** (`Rust::SHIM`), loaded after the first, which requires RubyGems (rb-sys's `mkmf.rb` requires `rubygems/ext`) and `rb_sys/mkmf`, and wraps `create_rust_makefile`: after the gem's own block, it adds `--crate-type staticlib` to the Cargo arguments, which `cargo rustc` gives the extension's crate alone, to the gem's own (or the developer's `RB_SYS_EXTRA_CARGO_ARGS`, which the Makefile's `?=` would take first, and which is then kept from make); adds `--print=native-static-libs=FILE` to rustc's, the libraries a static library needs, as rustc's documentation tells a C program that links one to ask; and writes a Makefile that includes rb-sys's and has one goal, its `$(RUSTLIB)`. Fledge runs it with `SOEXT=a`, so `$(RUSTLIB)` is the static library. An `extconf.rb` that asks for `use_cargo_build` is refused, since `cargo build` takes no crate type.

The extension keeps its `Init_NAME`, which rb-sys's and magnus's `init` macros name after the extension, as Ruby's `dln.c` would look it up; no `-D` reaches Rust. The build fails when two of an app's extensions would register the same function. The registration and the links are those of a C extension, with the libraries rustc printed as the extension's flags; on iOS without `-lSystem`, `-lc`, `-lm`, and `-lpthread`, which are libSystem, which clang links into every iOS program, so that `xcodebuild archive` does not warn of a duplicate library (`Rust::LIBSYSTEM`). One Rust extension per app is proven; two each carry Rust's standard library, whose names then clash, so each keeps its own copy ("Each linked extension's symbols"), and no app has tried it.

A gem with an rb-sys extension compiles from source on a desktop (`doc/contributors/design/gems.md`, "Compiling a gem"), and builds for a phone too; the maintainer: "Right, Tauri 2 does phones so it must be possible. If that's the case, we should do it." (decisions, 2026-11-12). Running the gem's own `extconf.rb` keeps what it configures, its Cargo arguments, and its features, needs no change to rb-sys, and uses the cross-compiling that rb-sys's build script already has; Tauri 2 builds a phone's Rust the same way, a static library per iOS target and a library per Android ABI, from rustup's targets. Three other ways were weighed. `cargo rustc --crate-type staticlib` run on the crate's `Cargo.toml` would drop what the `extconf.rb` configures and repeat rb-sys's environment by hand. rb-sys-dock and rake-compiler-dock are Docker, not the platform's own tools, and know no phone. A Rust shared library in Android's `jniLibs`, loaded with `dlopen`, would serve Android alone: Fledge builds its iOS Ruby with `--disable-dln`, so that Ruby loads no extension from a file, and an iOS app needs the static library, which Android's `libfledgeext.so` links too ("Linking extensions on Android"). The developer installs Rust with the standard library of each phone target (`rustup target add`); `mise.toml` pins them for Fledge's own builds.

**The NDK** is the developer's own, found as Gradle's Android plugin and Android Studio find it (`MobileExtensions::NDK.find`): `ANDROID_NDK_ROOT`, then `ANDROID_NDK_HOME`, then the newest in `ndk/` of `ANDROID_HOME`, `ANDROID_SDK_ROOT`, or the SDK Manager's default folder. Fledge downloads no toolchain onto a developer's computer, and says how to install the recommended one with `sdkmanager` when there is none. CI pins the NDK it uses by SHA-256, as the runtime build does.

**RubyGems' marks.** RubyGems and Bundler ignore a gem with extensions unless `gem.build_complete` is in its extension folder (`Gem::BasicSpecification#missing_extensions?`). So `fledge build` writes the empty mark where RubyGems looks (`extensions/PLATFORM/ABI-static/NAME-VERSION`) and where Bundler looks for a git gem (`bundler/gems/extensions/PLATFORM/ABI-static/SCOPE`), with `Gem.extension_api_version`'s `-static` suffix for a Ruby with no shared libruby. A path gem needs no mark, as on a desktop.

**The ffi gem** builds through its own `extconf.rb`, with the libffi it bundles, as on a desktop, and Fledge has no code for it: the link takes the Makefile's `LOCAL_LIBS` as make expands it (step 4), the phone's tools are `CC` and `CXX`, and on Android `AR` and `RANLIB`, and `PKG_CONFIG` is `false` ("The environment kept out"), so this computer's own libffi never reaches a phone's slice. Its libffi stays its own, as fiddle's stays fiddle's in the runtime (`doc/contributors/design/phone-runtimes.md`, "What a phone runtime holds"), so the two never collide. One libffi in the runtime for both would need the runtime to export libffi and its headers, which the Android runtime hides, and the ffi gem's path for a system libffi. A gem whose Rakefile builds a library for ffi to load, such as llhttp-ffi or scrypt, builds for each of the phone's targets, with the Rakefile's build-time gems on its load path and ffi compiled for this computer ("Rakefiles"). Ruby's ffi opens each library it builds, or its package holds built for the phone, by the path the gem gives `ffi_lib`, a path in every gem read (`doc/contributors/research/2026-11-19-ffi-libraries-on-phones.md`), so the app has the library answer at that path: on Android it is a native library of the app's own, linked from that path as the app starts ("Linking extensions on Android"), and on iOS a framework of its own, since iOS takes no third-party dynamic library outside one, with a link at that path in the bundle ("Libraries for ffi on iOS"). So the gems whose libraries Ruby's ffi loads work on both phones, as the maintainer decided (decisions, 2026-11-12). Whether App Review accepts an app that carries ffi or fiddle is untested (`doc/contributors/account-tests.md`, IOS-3), and so is whether App Store Connect takes one that embeds such a framework (IOS-4).

**How it is checked.** CI's `mobile-apps-ios` and `mobile-apps-android` jobs build and run an app for each way an extension is built (`tasks/mobile_parity.rb`): `test/fixtures/native_phone`, a C and C++ extension from a path gem; `test/fixtures/cmake_phone`, whose `extconf.rb` runs CMake; `test/fixtures/rake_phone`, digest-crc from rubygems.org, built from its Rakefile; `test/fixtures/rust_phone`, a Rust extension; `test/fixtures/ffi_phone`, the ffi gem from rubygems.org; and `test/fixtures/ffi_library_phone`, llhttp-ffi and scrypt from rubygems.org, whose Rakefiles build libraries for ffi. Each must print its line and exit 0. CI's emulators are x86_64, but each line also matches what the app printed on a real arm64-v8a phone, a OnePlus Nord N30 5G with Android 14, which ran every one of these apps from `trunk` at `88205410` on 2026-11-21, judged by the same code (`doc/contributors/device-test.md`, "Every phone example on the maintainer's phones"). `test/integration/mobile_extensions_build_test.rb` compiles a gem's extension for every target of a phone where this computer has the tools, and `test/mobile_extensions_test.rb` tests which extensions Fledge compiles, the registration unit, the link flags, and where an NDK is found. ## Rakefiles

A gemspec may name a Rakefile or an `mkrf_conf` script in `extensions`, which RubyGems builds with Rake (`Gem::Ext::Builder#builder_for`; `MobileExtensions.rake?`). Most such builds compile nothing: of the 10,000 most-downloaded gems, 30 of the 419 with extensions name a Rakefile, and 21 of those compile nothing (an `mkrf_conf` script installs a dependency and writes a Rakefile of `task :default`, and a Ruby-GNOME gem checks for a system library), 7 build a shared library for ffi to load, and one, digest-crc, builds 27 extensions with mkmf under Rake (`doc/contributors/research/2026-11-12-phone-extension-build-systems.md`, section 2). For each target, `MobileExtensions::RakeBuild`:

1. runs RubyGems' own builder for the extension, `Gem::Ext::RakeBuilder`, under this computer's desktop runtime's Ruby, which runs the `mkrf_conf` script, if any, then `rake RUBYARCHDIR=DEST RUBYLIBDIR=DEST` in the extension's folder, with Bundler's `build.NAME` options;
2. gives every Ruby the build starts the phone's `rbconfig.rb` and the shim's tools (`MobileExtensions::TOOLS`, through `RUBYOPT=-I RBCONFIG -I DEPENDENCIES -r FILE`, RBCONFIG as for an `extconf.rb`), as crossenv and cibuildwheel give a Python build the target's sysconfig, with this computer's Ruby as `RbConfig.ruby` (`FLEDGE_RUBY`) and in `RUBY`, which Rake's `ruby` runs; DEPENDENCIES are the require paths of the gems the gem depends on, at any depth, each with an extension compiled for this computer first by `Fledge::NativeBuild`, as `gem install` would have installed it before the Rakefile ran (`MobileExtensions::HostGems`): RubyGems in a Ruby that reads the phone's `rbconfig.rb` looks for gems in the phone runtime's gem folder and takes the phone for its platform, and ffi-compiler requires ffi, whose extension must be this computer's to load, not the phone's that Fledge compiles for the app. ffi compiles there with `--disable-system-libffi` (`HostGems::BUILD_ARGS`), with the libffi it bundles, as ffi's own gems for each desktop are built (its `ext/ffi_c/extconf.rb`, line 46, at 1.17.4, takes no system libffi under rake-compiler-dock), so that it does not depend on which libffi this computer offers: on GitHub's macos-26 runner, which has Homebrew's pkgconf, ffi chose the system's libffi, and the ffi it compiled did not load (symbol not found in flat namespace '_ffi_type_longdouble', which its header declared and macOS's libffi exports only for x86_64; macOS 27.2's header defines it as `ffi_type_double` on arm64), where a Mac with no pkg-config built and loaded it (`test/integration/host_gems_test.rb`);
3. with them a hook (`RakeBuild::HOOK`), prepended to mkmf's `MakeMakefile` whenever the build loads mkmf, so that each `create_makefile` renames the extension's Init function `Init_fledge_N_NAME`, N counting the app's extensions before the gem's, writes the `static:` rule (mkmf writes it when `$static` is not `nil`, and `false` leaves the Rakefile's own shared link as it is), and reports its folder;
4. runs `make static` in each folder the hook reported, and names each extension by that folder's path in the first of the gem's require paths that holds it, joined to the name `create_makefile` was given (`ext/digest/crc32` in a gem whose require paths hold `ext` gives `digest/crc32/crc32_ext`), or by that name alone when no require path holds it;
5. takes every other shared library (`.so`, `.bundle`, `.dylib`) the build wrote or changed in the gem, and every one the gem's package holds built for the target, for a library for Ruby's ffi, as ffi-compiler and mini_portile2 builds make (`MobileExtensions::FfiLibrary`), with the path in the app where a desktop has it, which is where it is in the gem; and refuses, naming the gem and the library, one the build wrote that `MobileExtensions::BuiltFor` reads as built for another system than the target, with Xcode's `vtool -show-build` or the NDK's `llvm-readelf`, and any shared library the build installed into `DEST`.

The libraries are compared by their bytes before and after the build, not by their paths, since a package may hold a library at the very path the build writes: llhttp-ffi 0.5.1's holds `ext/aarch64-darwin/libllhttp-ext.bundle`, which its author built on a Mac, and which ffi-compiler writes on iOS (`doc/contributors/research/2026-11-19-ffi-libraries-on-phones.md`, sections 1 and 4). A library the package holds that the build left as it was is one of the gem's files, as `gem install` leaves it, and `BuiltFor` reads it as it reads the rest. One built for the target is a library for ffi as if the build had made it: the gem opens it at its path on the phone, as a desktop's gem opens the one its package holds for that desktop. Left among the gem's files, as it was until 20 November 2026, it reached an Android app only inside `fledge.zip`, and Ruby's ffi opened the copy unpacked into the app's own files: an x86_64 emulator of API 36 ran such an app (a path gem holding an NDK-built `libheld.so` for each ABI) and its library's function returned, from `/data/data/ID/files/fledge/app/held/ext/x86_64-linux/libheld.so`. That works because Android's policy lets an app map its own files as code and logs each time it does (`private/untrusted_app_all.te`, lines 24 to 28, `doc/contributors/research/2026-11-13-phone-extensions-as-files.md`), not because Android means it: "We strongly discourage loading code from outside of your application APK" (developer.android.com, "Security tips", "Security with dynamically loaded code", last updated 2026-09-01), and a file in the app's own files is one the app's code may rewrite. It also took the road `doc/contributors/research/2026-11-19-ffi-libraries-on-phones.md` rejects as A2, outside the native library folder that the rest of the app's native code loads from and that Play's per-ABI splits and checks read, unstripped, and unlike the same library had the Rakefile built it. No Android version is known on which that load fails; the change makes one road for every library for ffi, not a fix for a crash. The gem's own copy stays in `fledge.zip`, so where the native libraries are not extracted (`useLegacyPackaging = false`, see "Linking extensions on Android") ffi still opens it from the app's files, as before. One built for macOS is refused on iOS, and one built for a desktop's Linux, which has no `Android` note, on Android: Ruby's ffi takes iOS for `darwin` and Android for `linux` (`lib/ffi/platform.rb` at 1.17.4), so the gem would ask `dlopen` for that library on the phone. One built for anything else, such as the phone's other ABI or the other phone, stays the gem's file, which its own target takes. The iOS project carries each library for ffi as a framework of its own ("Libraries for ffi on iOS"), and the Android project as a native library of the app's own ("Linking extensions on Android"). On iOS the build's compilers, in `CC` and `CXX` and in `rbconfig.rb`, run through a wrapper of Fledge's (`RakeBuild::DYLIB`) that passes `-dynamiclib` wherever the build asks for `-bundle`, so that the library is a dynamic library, the only binary a framework holds ("Libraries for ffi on iOS"). A library the package holds built for iOS went through no compiler of Fledge's, so it is taken as its author linked it; no gem read holds one, and none has been tried.

The builder's own process ignores `RUBYOPT` (`--disable=rubyopt`), so RubyGems finds Rake among this computer's runtime's gems. On iOS, mkmf links an extension of a static Ruby against no Ruby, and the phone's `rbconfig.rb` has no `-undefined dynamic_lookup`, so the hook adds it on Apple targets: the Rakefile's own shared link then succeeds, and no phone loads what it makes. A Rakefile that builds nothing gives no extension, and the gem ships as RubyGems installs it, with its `gem.build_complete` mark.

A gem that installs with `gem install` ships to a phone (decisions 9 and 20), and of gems whose extension builds without an `extconf.rb` the maintainer said: "Python and other languages that have Fledge-like tools must solve this somehow; so can we." (decisions, 2026-11-12). RubyGems' own builder and mkmf's own static rule take every Rakefile gem among the 10,000 that can run on a phone, with no new build system. Three other ways were weighed. A compiler wrapper that makes every shared link a static archive, as kivy-ios's `liblink` does, would serve the same one gem among the 10,000, and otherwise only gems that build with CMake or `configure` alone, of which there are none there; it waits for a real gem that needs it. A recipe per gem, as python-for-android, kivy-ios, Chaquopy, and BeeWare's mobile-forge carry, is a database of other people's gems for Fledge to pin and patch, where Fledge changes no developer's gem (`doc/contributors/design/gems.md`, "Checks that are not about licenses"); those tools carry recipes for the gems their build environment does not reach, not instead of one. Shared libraries, as Python ships its extensions on phones (PEP 730, PEP 738), are what an Android app's C and C++ extensions from an `extconf.rb` are ("Linking extensions on Android"), but on iOS they would reverse the linking of every extension into the app and the runtime's `--disable-dln` ("Linking extensions on iOS"). A gem's Rakefile runs on the developer's computer at build time, as `gem install` runs it, and Fledge adds no sandbox `gem install` lacks. One that compiles without mkmf, hard-codes a compiler, or reads the build computer's files is refused or misbuilds, and Fledge carries no recipe for it.

## Files a gem's build leaves

Under `bundle exec` a gem's Ruby may read, by its path, any file its build left in the gem's folder, since RubyGems leaves the folder as the build left it, and a desktop's app carries all of it (`doc/contributors/design/gems.md`, "What a compiled gem ships"). Until 22 November 2026 a phone's app carried none of it: `AppGems#mark_extensions` gives each compiled gem no built files, and only the extensions and the libraries for ffi left each target's build folder. So a path gem whose `extconf.rb` writes `data/table.txt` beside the gem's root, which its Ruby reads, printed its line under `bundle exec` and raised `Errno::ENOENT` on the phone, with nothing said at build time.

A phone builds each gem once for each target, each in a folder of its own ("Gems with extensions", step 1), and what those builds leave differs. For that gem, each build left its own `Makefile`, which names its target's compiler and `rbconfig.rb`, `mkmf.log`, the object and the archive or shared object, Fledge's `fledge-report.json`, and `data/table.txt`, the one file alike in every build. The app has one Ruby tree for every target: one `fledge/` folder in the Xcode project for the device and the Simulator, and one `fledge.zip` for both of Android's ABIs. So `MobileExtensions::LeftFiles` takes, of each target's build, every file the build left (`NativeBuild::BuiltFiles.of`, the desktop's rule), less compiled code (an ELF or Mach-O file, or a static archive, by its first bytes, `Binary.format_of`) and less Fledge's own files beside an extension; and the app carries, at its path in the gem's folder, each file every target's build left byte for byte alike (`LeftFiles.common`). A file the build rewrote among the gem's own takes its place, as on a desktop (`MobileProject#build`).

Every other file a target's build left, one the targets' builds left differently or only some left, is that target's own (`LeftFiles.apart`): its `Makefile` and `mkmf.log`, and data an `extconf.rb` writes for its target, such as the architecture `RbConfig` names. On Android each ABI's own files are in `fledge.zip` under `.fledge-abi/ABI/PATH`, and `fledge.files` in the Ruby root lists them, a line each, the ABI and the path separated by a tab (`MobileProject::Android#place_apart`). As the app starts, before Ruby boots, beside `fledge_link_libraries`, the runtime's `fledge_place_abi_files` (`runtime/mobile/library_links.c`) moves each file listed for its own ABI, which it was compiled for, to its path, over the gem's own file there, so that a regular file stands where a desktop's build left it, and `File.symlink?` and `File.lstat` say what they say there. It moves each once: `FledgeRuby.unpack` writes the Ruby root anew for each installed version, and a later start finds the ABI's copy gone and the file at its path. The other ABI's copies stay under `.fledge-abi/`, outside every gem's folder. A file whose copy and path are both missing is said on standard error, and Ruby boots, as a link `fledge.links` cannot make is.

Five ways were weighed. Carrying one target's files whenever the targets' differ, the device's, say, would hand the Simulator or the other ABI bytes a build wrote for another target, which is wrong in a way no one sees; refusing such a gem, naming the file, would refuse every gem, since every target's `Makefile` and `mkmf.log` differ; and a warning would leave the app to raise `Errno::ENOENT` on the phone all the same, which a person who runs the app must never meet. Copies for each target, chosen as the app starts, serve a gem that writes different data for each target, and on Android the choice must be made on the phone: one `fledge.zip` serves every ABI, since Android packs no asset for one ABI alone, and only native libraries, `lib/ABI/lib*.so`, are installed for one. Carrying the data as native libraries, extracted and linked as `fledge.links` links an extension, would need no runtime change, but the Android Gradle plugin strips and aligns what it takes for a native library, and Google Play scans each as code; and a link is what a desktop's file is not. The runtime knows its ABI exactly, which the Java host would have to guess from `Build.SUPPORTED_ABIS`, so the choice is the runtime's. Carrying only what lies outside a build's intermediates would be Fledge guessing which of a gem's files are intermediates, where agreement between the targets' builds is a fact the build shows. Compiled code stays out because a phone runs code only from the app's executable, its frameworks, and its native libraries, where Fledge already puts what Ruby loads of it ("Linking extensions on iOS", "Libraries for ffi on iOS", "Linking extensions on Android"): on iOS a Mach-O file in `fledge/` is one no app may carry ("Libraries for ffi on iOS", step 5), and Android discourages code loaded from an app's own files ("Rakefiles").

What it costs, and what still differs from a desktop: an Android app carries each compiled gem's `Makefile`, `mkmf.log`, and Cargo records once for each ABI, a few kilobytes compressed, and its first start after each install moves them. On iOS a gem that writes different data for each slice finds none of it on the phone, and nothing says so at build time, since every gem's `Makefile` would be named too; an iOS app holds no `Makefile`, `mkmf.log`, or Cargo records where a desktop's holds them. That is a defect: the device and the Simulator are separate Xcode builds of one project, so the fix is to have the build phase that copies `fledge/` copy the slice's own files over it, and `MobileProject#place_apart` does nothing for iOS until then. A file the `extconf.rb` named for `make clean`, which a desktop's RubyGems removes and no phone build cleans, ships when it is alike for every target and is not compiled code, such as C source a build generates. Signing and size do not bear on what is carried: on iOS the data is among the bundle's resources, sealed with the app, and on Android it is in `fledge.zip`, compressed. `test/integration/mobile_built_files_test.rb` builds that gem's app for each phone, runs it in the iOS Simulator and on an Android emulator, and checks that the app carries the data and not the `Makefile` or objects among the gem's files, and, on Android, that the gem's Ruby reads the architecture its own ABI's build wrote, and that `.fledge-abi/` holds each ABI's; `test/mobile_extensions_left_files_test.rb` tests the rule, `test/mobile_build_test.rb` what an Android project holds, and `test/integration/mobile_library_links_test.rb` the runtime's move, compiled for this computer.

## Registering extensions

This section is for the extensions linked into the app: every iOS one, and on Android those of Rust and of Rakefiles. An Android extension an `extconf.rb` builds in C or C++ is a file, which needs no registration and no Ruby file at its path ("Linking extensions on Android").

A statically linked extension is found by `require` when its name is in Ruby's table: `load.c`'s `search_required` finds no file and looks the name, with `.so` appended, up in `vm->static_ext_inits`, and `run_static_ext_init` calls the registered function; `ruby_init_ext(name, init)` fills the table (`load.c`, lines 1141 to 1146, 1199 to 1220, and 1535 to 1562 at Ruby 4.1.0-preview1).

`fledge_ruby_add_extension(feature, init)` keeps each registration until Ruby has booted, and `fledge_ruby_run` then calls `ruby_init_ext(feature ".so", init)` for each, after `ruby_options` and before Bundler's setup and the program, when the main namespace exists. A call after Ruby has started returns -1 with `EALREADY`, since the extension would never be registered. `feature` is what the `extconf.rb` gave `create_makefile` (`"adder/adder"`). `require "adder/adder"` and `require "adder/adder.so"` find it. `require_relative "adder/adder"` asks for an absolute path, which is not in the table, so `fledge build` puts a Ruby file at the path a desktop's RubyGems copies the extension to, the gem's first require path joined to the feature (`lib/adder/adder.rb`), that requires `"adder/adder.so"` (`MobileExtensions::Stub`), as CPython on iOS puts a `.fwork` file where a binary module's `.so` was. A require of the path finds that file as it finds any, a second require of the path or the feature finds it loaded, and the `.so` name finds no `.rb`, so the file cannot require itself. It writes none where a require path already has a Ruby file of that name, as bigdecimal's `lib/bigdecimal.rb`, which a desktop's require of the path finds first too, and none for an extension a Rakefile builds, which RubyGems leaves in no require path of its own. A path that names `adder/adder.bundle` or `adder/adder.so`, for which no Ruby file is found, finds the linked extension through the phones' `load.c` edit (`phone-runtimes.md`, "Bundled gems' extensions"), which records it in `$LOADED_FEATURES` as `adder/adder.so`; so does a `require_relative` of an extension a Rakefile built, which gets no Ruby file. The phone runtimes put the same file in each bundled gem's extension folder (`phone-runtimes.md`).

The file needs no edit to Ruby, and it serves what no edit would: a desktop's RubyGems activates a bundled gem for a require of its extension's own feature (`require "racc/cparse"` before racc is active) because it finds the extension's file among the gem's (`Gem::BasicSpecification#have_file?`, `lib/rubygems/basic_specification.rb`, lines 376 to 388), as it does on a phone for a bundled gem, whose extension is a file there too (`phone-runtimes.md`, "Bundled gems' extensions"), but an app gem's extension is linked into the app. The phones' `load.c` edit, which finds the linked extension for the names no Ruby file covers, would serve an app gem's `require_relative` too, but not that activation. Refusing such gems, or accepting the difference, would refuse what nothing on a phone forbids: a difference is accepted only where a platform truly forbids what Ruby does (decisions, 2026-11-12). What it costs: where a desktop records the extension's `.so` path in `$LOADED_FEATURES`, a phone records the file's `.rb` and the linked feature, one more case of a linked extension recorded as a feature, not a file, which the phone parity audit lists (`doc/contributors/research/2026-11-12-phone-parity-audit.md`, row 12).

Fledge writes the **registration unit**, a C file with a `__attribute__((constructor))` that calls `fledge_ruby_add_extension` for each extension and declares each renamed `Init_fledge_N` (`MobileExtensions.registration_source`). A constructor needs no call from the host, so a framework that replaces Fledge's host keeps its own entry point and the extensions still register: on iOS the unit is compiled into the app, and on Android the runtime opens `libfledgeext.so` before Ruby boots ("Linking extensions on Android").

Ruby's weak `Init_extra_exts` (`ruby.c`, lines 1807 to 1815 at Ruby 4.1.0-preview1), whose empty definition "will be replaced with the actual strong symbol by linker", is not used: on Android the call is inside `libfledgeruby.so`, whose objects are built `-fvisibility=hidden`, so a strong definition in another library is never bound to it.

## Linking extensions on iOS

An app gem's extension links into the app's executable, as Ruby's own did until the iOS runtime made each of them a framework (`phone-runtimes.md`, "Ruby's extensions on iOS"); an app gem's is not yet a framework, so it is registered and found as "Registering extensions" says, and `$LOADED_FEATURES` records its bare feature where a desktop records its file's path. Each slice's archives, with each static library an `extconf.rb` named for that slice, and with each name another part of the app also defines made the extension's own ("Each linked extension's symbols"), are merged by Apple's `libtool -static` into `libFledgeExtensions.a`, and the two slices are packed by `xcodebuild -create-xcframework -library ... -library ...` into `FledgeExtensions.xcframework`, which `project.yml` links beside `FledgeRuby.xcframework`. The registration unit is `Host/fledge_extensions.c`, compiled with the host, so its constructor and its `Init_fledge_N` references pull the archives in; it includes the embedding API as `<FledgeRuby/fledge_ruby.h>`, the name Xcode finds a framework's header by, or as `<fledge_ruby.h>` from a static `FledgeRuby.xcframework`'s `Headers`. `OTHER_LDFLAGS` carries the extensions' other libraries and frameworks, and `-lc++` when any extension has C++.

A static library goes with its own slice's archives, not into `OTHER_LDFLAGS`, which every slice shares; otherwise the Simulator's link would take the device's library too. A framework is one flag, `-Wl,-framework,NAME`, the form SDL3's `sdl3.pc` writes, so that merging the flags never splits a name from its `-framework` (`MobileExtensions::Linking.link_flags`).

## Libraries for ffi on iOS

A library for Ruby's ffi (`MobileExtensions::FfiLibrary`), one a gem's Rakefile builds or its package holds built for iOS ("Rakefiles"), or an `extconf.rb` builds with no Init function ("Gems with extensions"), is opened by its path in the gem: ffi-compiler's loader finds `ext/aarch64-darwin/libllhttp-ext.bundle` in llhttp-ffi 0.5.1, ffi hands that path to `dlopen` unchanged, and Ruby's ffi takes iOS for `darwin` and `aarch64`, so the path on an iPhone is a Mac's (`doc/contributors/research/2026-11-19-ffi-libraries-on-phones.md`, section 3). Apple's "Placing content in a bundle" (developer.apple.com) puts a "framework, dynamic library" in an iOS app's `Frameworks/` and says "iOS, watchOS, and tvOS support third-party frameworks but don't support third-party standalone dynamic libraries, which are those outside a framework bundle". Its "Embedding nonstandard code structures in a bundle" says how to serve code that loads a library by a path where no code may sit: "if the code dynamically loads a plug-in via a relative path that leads to a location that cannot hold code, create a symlink at that location that points to where the code is actually placed" ("Use symlinks for gnarly edge cases"), and that "the basic techniques work on all Apple platforms". Fledge does exactly that (`MobileProject::IOSLibraries`):

1. **The library is a dynamic library.** ffi-compiler links with `-bundle` on every Apple system (`lib/ffi-compiler/compile_task.rb`, line 115 at 1.4.3), which makes an `MH_BUNDLE`. A framework's binary is a dynamic library: Apple's table puts a framework and a dynamic library in `Frameworks/` and a plug-in, which a bundle is, in `PlugIns/`; PEP 730 says an iOS app's "dynamic binary content must be compiled as dynamic libraries, not shared objects or binary bundles", and CPython's iOS build links its modules with `-dynamiclib`. So on iOS the Rake build's compilers run through `RakeBuild::DYLIB`, a shell script of a few lines that passes `-dynamiclib` in place of each `-bundle`, adds `-Wl,-headerpad_max_install_names` to every command that links (one with none of `-c`, `-S`, `-E`, `-M`, `-MM`), and passes every other argument as it is, under `CC`, `CXX`, and `rbconfig.rb`'s `CC` and `CXX`. A build that links with `-shared`, as rdkafka's `configure` does, makes a dynamic library already.
2. **A framework per library, per slice.** `fledgeffi.GEM.PATH.framework`, named as Android's `libfledgeffi.GEM.PATH.so` is (see "Linking extensions on Android"), with every character but letters, digits, hyphens, and periods made a hyphen, since the name ends the framework's `CFBundleIdentifier`, which takes only those (CFBundleIdentifier, developer.apple.com): `fledgeffi.scrypt.ext.scrypt.aarch64-darwin.libscrypt-ext.bundle`. Two libraries whose names would come out alike, or slices that built different libraries, fail the build, naming them. The binary is the library, its install name set to `@rpath/NAME.framework/NAME` with `install_name_tool -id`, as Flutter's native assets set it, which keeps the linker's ad hoc signature valid (measured: `codesign --verify` passes after it). The longer name fits only in a header with room for it: without the wrapper's padding, `install_name_tool` refused llhttp-ffi's library because "larger updated load commands do not fit (the program must be relinked, and you may need to use -headerpad or -headerpad_max_install_names)". Its `Info.plist`, written from JSON by `plutil`, has the keys CPython's iOS frameworks have (`Apple/testbed/Python.xcframework/build/iOS-dylib-Info-template.plist` at v3.14.0), with `FMWK` as the package type where CPython writes `APPL`, the slice's platform in `CFBundleSupportedPlatforms`, the app's identifier followed by the name, the app's version, and iOS 15.0.
3. **An XCFramework of the two,** `Frameworks/NAME.xcframework` in the project, made by `xcodebuild -create-xcframework -framework ... -framework ...`, as the runtime's is. `project.yml` names it with `embed: true` and `link: false`, so Xcode copies the slice it builds for into the app's `Frameworks/` and signs it with the app, and the executable does not load it at launch: on a desktop no program links such a library either, and Ruby's ffi opens it when the gem's Ruby asks.
4. **A link at each path where a desktop has the library,** the `FfiLibrary`'s links, in `fledge/`: a relative one, `../` once for each folder from the app bundle's root to the link's folder, then `Frameworks/NAME.framework/NAME`. It dangles in the project and leads to the framework in the built app, where the build phase "Copy Ruby and the app" copies it as a link with `ditto`. It takes the place of the file the gem's package held there, as llhttp-ffi's macOS library.
5. **No other Mach-O file in `fledge/`.** A gem's package may hold what its author built on a Mac, as llhttp-ffi 0.5.1's holds its library and four object files, which no iOS app may carry outside its executable and frameworks. The build leaves every other Mach-O file out of `fledge/` (`MobileProject::IOS.mach_o?`, by its magic number, telling a universal file from a Java class file by the count of architectures) and says which.

Ruby's ffi then opens the library as on a desktop: `FFI::Compiler::Loader.find` globs the gem's folder and finds the link, `File.exist?` follows it, and `dlopen` loads the framework's binary. No Ruby rebuild is needed: the libraries call no Ruby, and ffi and fiddle open them with `dlopen`, not with Ruby's `dln`, which stays `--disable-dln`. What differs from a desktop is what Android's links already make differ: `File.symlink?` is true there and `File.realpath` names `Frameworks/`, and the library's file name inside the app is the framework's.

Four other ways were weighed. A table in the runtime that answers `dlopen` of a gem's path with the framework, by interposing `dlopen`, needs no link but puts every `dlopen` of the process through Fledge's code, and `File.exist?` of the path would be false while `dlopen` succeeds. Linking each library into the app's executable, with a link to the executable at the gem's path, puts every library's symbols in one namespace, and Xcode's dead stripping drops what only `dlsym` reaches. A plain library at the gem's path is what Apple says iOS does not support. A bundle in a framework, as ffi-compiler links it, needs no wrapper, and nothing in Apple's text read forbids it in so many words, but Apple's table gives bundles another folder and PEP 730 forbids them; and the wrapper's other way, `-Wl,-dylib` in `LDFLAGS`, which Apple's linker obeyed when measured, takes the place of ffi-compiler's default `LDFLAGS`, rests on the linker taking the last of two output kinds, and reaches every link a `configure` script makes.

What it costs: the wrapper, which is Fledge's code standing in a compiler's place, as kivy-ios's `liblink` stands in for the linker; a framework per library; and the archive check's rules for them ("The App Store archive check"). What is proven, and where: in the iOS Simulator, by CI's `mobile-apps-ios` job, `test/fixtures/ffi_library_phone` opens llhttp-ffi's and scrypt's libraries through the links and prints its line; the archive check passes for its unsigned device archive. On a device, the maintainer's iPhone 12 mini with iOS 27.0, on 2026-11-21: the app, signed for development by his Personal Team, printed the same line, with each framework signed by the same certificate under the identifier `fledge build` gives it (`doc/contributors/device-test.md`, section 8). Not yet proven anywhere: App Store Connect's validation of an app that embeds them, which waits on the maintainer's account (`doc/contributors/account-tests.md`, IOS-4).

## Linking extensions on Android

A C or C++ extension an `extconf.rb` builds is **a file, as on a desktop**. Android lets an app load the native libraries its package installer extracts, and its Ruby keeps `dln` (only iOS's is built `--disable-dln`), so the differences a linked extension makes from `ruby main.rb`, a feature in `$LOADED_FEATURES` where a desktop records a file, a Ruby file standing at the extension's path, and `$static` set when the `extconf.rb` runs, are Fledge's choice and not the phone's (`doc/contributors/research/2026-11-13-phone-extensions-as-files.md`), and the maintainer accepts a difference only when the platform forces it (`decisions.md`, 2026-11-12). So `MobileExtensions` runs mkmf's default goal for it with `FLEDGE_SHARED` set (`MobileExtensions::SHIM`): the shared object a desktop's mkmf makes, its `Init_` function its own, linked against `-lfledgeruby` (the runtime's own `libfledgeruby.so`, from its AAR, where mkmf would name the `-L` folder of the computer that built the runtime, and bionic resolves a library's symbols only from the libraries it names), with `-Wl,-z,max-page-size=16384`, the run path `$ORIGIN`, and the unwinder's symbols kept to itself (`Targets::DLDFLAGS`; "Each extension file's symbols", below), and C++ linked with `clang++ -shared`, over the NDK's `libc++_shared.so` ("The C++ runtime rule"). What it came to is a `MobileExtensions::Library`. `MobileProject::AndroidLibraries` copies each into `src/main/jniLibs/ABI/` as `libfledgeext.FEATURE.so`, the feature's slashes as dots, a name the installer extracts (`isFilenameSafe` in AOSP's `ApkParsing.cpp` takes letters, digits, and `+,-.=_`), strips it, and writes **`fledge.links`** in the Ruby root: a line per ABI and path, the ABI, the library's name, and the path where a desktop's RubyGems leaves the extension's file, relative to the root: the gem's first require path, which RubyGems copies it into by default (`Gem.install_extension_in_lib`), and, for a gem from a server or git, the gem's extension folder for that ABI's platform (`Library.links`). As the app starts, `fledge_ruby_run` makes each a link to the library in the app's native library folder (`fledge_link_libraries`, `runtime/mobile/library_links.c`), remade when the folder moves with an install, as `bin/ruby` is (`phone-runtimes.md`, "The ruby program on Android"), so Ruby finds, loads, and records the file at the desktop's path. Such an extension registers nothing and gets no Ruby file at its path. It needs `useLegacyPackaging = true`, as the ruby program and Ruby's own extensions do: without it the installer extracts no library, the runtime removes the links and says why on standard error, and the extension does not load, so the build refuses a `build.gradle` that sets it to `false` or sets nothing ("Refusals"). The runtime's own extensions take this road too: `fledge.links` begins with the runtime's lines (`phone-runtimes.md`, "Ruby's extensions on Android"), and the app's follow. A library for ffi needs no such check, since the gem's own copy stays in `fledge.zip` at the path the link would take.

**`libfledgeext.so`** is one more shared library per ABI, in every app with a gem whose extension `fledge build` compiles, a name a host may rely on (`doc/contributors/design/public-interface.md`, "Phones"): every host read for this design names its libraries in a fixed list and fails to start when one is missing, as SDL's `SDLActivity` does (`doc/contributors/research/2026-11-14-android-hosts-and-extension-files.md`), so the name stays whatever the extensions came to. Rust extensions and those a Rakefile builds are linked into it, as every iOS extension is linked in (`MobileExtensions#shared_library`): the registration unit and the archives, each name two of them define made each one's own ("Each linked extension's symbols"), compiled `-fPIC` as the runtime is, against `-lfledgeruby` from the runtime's AAR, with the extensions' flags, `-llog -lm`, `-Wl,-z,max-page-size=16384`, and `-Wl,--exclude-libs,ALL`, then stripped; with none of them, it holds the registration unit alone, which registers nothing. When an extension has C++ it links with `clang++`, over `libc++_shared.so`, which the app then carries ("The NDK's shared C++ runtime"). It goes to `src/main/jniLibs/ABI/`, where the plugin packs it as `lib/ABI/libfledgeext.so`, stored and aligned. The runtime opens it before Ruby boots, from beside `libfledgeruby.so`, or by its name where the native libraries stay inside the APK (`fledge_ruby_load_extensions`, `android.c` and `library_links.c`), and its constructor registers the extensions, so a host need not load it, and what is inside it is Fledge's to change. A host that names it, as `SDLActivity`'s `getLibraries()` names its list, loads the same file, which bionic opens once, matched by device and inode, so its constructor runs once. The library defines no `JNI_OnLoad`: none is needed, since nothing in it is a native method, and one would clash with an extension linked in that defines its own. The registration unit stays in the project's `extensions/` folder for whoever reads it.

**A library for ffi from a Rakefile's gem** (`MobileExtensions::FfiLibrary`) takes the same road as an extension built as a file (`MobileProject::AndroidLibraries`). It is copied into `src/main/jniLibs/ABI/` as `libfledgeffi.GEM.PATH.so`: the gem's name, then the library's path in the gem with its slashes as dots, with `.so` added where the path ends otherwise, as `librdkafka.so.1` would. The line is per ABI because a gem may use one path for both, as rdkafka's `ext/librdkafka.so` does, and Fledge's Ruby root is one tree for both ABIs. The name begins `libfledgeffi`, not `libfledgeext`, so it can never be one of the extensions' names, and not with the library's own name, since two gems may name their libraries alike and a host's own libraries share the folder. It holds the gem's name and the whole path, so two libraries of one app differ in it; where two would still come out alike, as `ext/a.b/lib.so` and `ext/a/b.lib.so`, the build fails naming both rather than let one overwrite the other. A shared library an extension links (`-lNAME` found as `libNAME.so` in one of the extension's `-L` folders), linked in or a file, is copied into `jniLibs/ABI/` beside it (`Linking.carry_shared_libraries`), since Android loads native code only from the libraries the package holds. ### Each extension file's symbols

An extension built as a file exports every symbol it defines, its own objects' and those of the static libraries it links, as a desktop's mkmf links it: Ruby's build limits only its own objects' symbols (`-fvisibility=hidden` in `XCFLAGS`, which mkmf does not pass to an extension, and `RUBY_FUNC_EXPORTED` for the functions it keeps; `configure.ac`, lines 1024 to 1031 and 1885 to 1891 at Ruby 4.1.0-preview1), and on Linux it links an extension with `$(CC) -shared` and no version script (lines 3174 to 3179). `dln.c` opens the file with `RTLD_LAZY | RTLD_GLOBAL`, or `RTLD_LOCAL` when Ruby::Box is on (line 376). Where a desktop's glibc then binds a later extension's references to an earlier one's definitions of the same name, bionic does not. Since API 23 a library is resolved against the global group, which holds the program, `LD_PRELOAD` libraries, and libraries linked `-z global`, and then against its own breadth-first `DT_NEEDED` closure. `RTLD_GLOBAL` adds a library to what `dlsym(RTLD_DEFAULT, ...)` searches, and not to the global group (`linker.cpp`, `make_global_group` and `soinfo_do_lookup`, at android-8.0.0_r1, which is API 26; `linker_namespaces.cpp`, `get_global_group`, at android16-release; `android-changes-for-ndk-developers.md`, "Changes to library search order"). So two extensions that each link a static library defining one name each call their own. So do a library for ffi, which ffi 1.17.4 opens `RTLD_LAZY | RTLD_LOCAL` (`lib/ffi/dynamic_library.rb`, lines 71 to 73), a library a host loaded, and `libfledgeruby.so`, whose OpenSSL, libyaml, and libffi it keeps to itself (`--exclude-libs`, `tasks/runtime_builder/android.rb`) and which was linked before any extension.

What an extension exports does reach the libraries it links: one opened for the first time as its `DT_NEEDED` is resolved with the extension at the head of its group. For C that is what a desktop does, so Fledge leaves it alone, and a library that defines a name the extension's static library also defines calls the extension's. A static copy of the C++ runtime or the unwinder is different. A desktop's extension holds no C++ runtime of its own, since it links the system's shared one, and a C++ extension on Android links the NDK's shared one in the same way ("The C++ runtime rule"); but an extension may still link the NDK's static unwinder, `libunwind.a`, and, where its own `extconf.rb` asks for it, the static C++ runtime. Exported, such a copy takes the place of a library's own: when extension files linked the static C++ runtime, until 20 November 2026, a library the extension links, over `libc++_shared.so`, saw the extension's `std::cout` and not its own. That is the mixing of two C++ runtimes the NDK calls undefined behavior (developer.android.com/ndk/guides/cpp-support, "Static runtimes" and "One STL per app", last updated 2026-11-06), and the NDK asks of a shared library that links libc++ statically: "you must either use libc++_shared or ensure that libc++'s symbols are not exposed by your library" (developer.android.com/ndk/guides/middleware-vendors, "STL", last updated 2026-03-06). So the link passes `-Wl,--exclude-libs,libc++_static.a:libc++abi.a:libunwind.a`, the libraries the NDK's clang links for `-static-libstdc++` and the unwinder, which lld makes local in the output. A C++ fixture of one function, linked with the static runtime, exported 1,929 symbols, 1,721 of them the C++ runtime's, before the flag. Hiding a copy does not make it one runtime: an exception thrown over `libc++_shared.so` still went uncaught in an extension file that held its own copy hidden, which is why the extension files now link the shared one ("The NDK's shared C++ runtime").

Four other ways were weighed. `-Wl,--exclude-libs,ALL`, which `libfledgeext.so` links with, would hide the C static libraries too, and a library the extension links would then call its own definition where a desktop's calls the extension's. A version script that exports only `Init_NAME` would hide what an extension's own sources export, as a desktop does not. `-Bsymbolic` binds the extension's own references first, and not those of the libraries it links, so it changes nothing here. Leaving the link as a desktop's has it would export a static unwinder or C++ runtime no desktop extension holds. Hiding does not shrink the file's code, since mkmf links with no `--gc-sections`; it shrinks only the dynamic symbol table. What it costs: an extension cannot hand a static copy of the unwinder or the C++ runtime to a library that relies on finding one in it, which no desktop's extension could give it either.

`test/integration/mobile_extension_symbols_test.rb` builds the fixtures with the Android runtime and the NDK, and, where `ANDROID_SERIAL` names a device, opens them as `dln.c` does and checks which definition each calls, and that a C++ extension and a C++ library it links over `libc++_shared.so` share one runtime: a string, an exception, type information, the current exception, the terminate handler, and an allocation cross between them as on a desktop, and the same for a shared C++ library the gem's `extconf.rb` builds with CMake ("The C++ runtime CMake links"). CI runs it on both `mobile-apps-android` jobs' x86_64 emulators of API 36, with 4 KB and with 16 KB pages ("Gems with extensions", "How it is checked"). arm64, API levels below 36 on a device, and an app's own linker namespace, as opposed to a shell's, are read from the linker's source and not run. What a shared library a gem's build makes exports of its own C++ runtime is that build's, which Fledge leaves alone.

## Each linked extension's symbols

An extension linked into the app, every iOS one and on Android those of Rust and of Rakefiles in `libfledgeext.so`, shares one image with every other. Two gems that each define a function or variable of one name then meet where a desktop keeps them apart. A Mac's Ruby loads each extension as a bundle of its own, whose calls bind to its own definitions; Android's extension files do the same ("Each extension file's symbols"). In one link they did not, and nothing said so. On 21 November 2026, at `88205410`, three iOS apps built with `fledge build ios` and Xcode 27.2's Debug build linked without a warning and answered wrongly on the iOS 26.1 Simulator: an extension whose `clash_file`, `clash_lib` (from a static library its `extconf.rb` links), and `clash_variable` were in other files got the first extension's, since the link never loaded the second's members; one whose function and variable were beside its Init function got its own function and the other's variable; and one that defined libyaml's `yaml_get_version` got the runtime's. On Android, two Rakefiles' extensions with the first kind of names answered the first's values, and two with the second kind stopped `fledge build` with lld's "duplicate symbol: same_function", which names source files and no gem. The phone's `rbconfig.rb` compiles an extension `-fvisibility=hidden`, so these names are private externs, and hidden ones on Android, which every object of one link still shares.

So `MobileExtensions::Separation`, before a target's extensions are linked, gives each the names it shares. For each linked extension it:

1. links the extension's archive and the static libraries only it links into one relocatable object, with the target's compiler: `clang -r -nostdlib -Wl,-u,INIT` and, on iOS, `-Wl,-keep_private_externs`, since without it Apple's ld makes every hidden name local, the extension's Init function among them (ld(1), `-r` and `-keep_private_externs`); on Android also `-Wl,-d`, which defines a common symbol, and which Xcode 27.2's ld refuses ("unknown options: -d"). `-u` makes the link take, as the app's link would, the archive members its Init function reaches and no others;
2. reads the names the object defines from its symbol table, with `xcrun nm -m --no-llvm-bc` (external and private external, not weak) or the NDK's `llvm-nm --defined-only --extern-only --no-llvm-bc`, which read no LLVM bitcode (below);
3. finds those that another part of the app defines too: another linked extension's object, a static library that several extensions link (the same path in their flags), and on iOS Ruby's framework, `FledgeRuby.framework/FledgeRuby`, whose exported names are Ruby's, or, in a runtime whose Ruby is static, as 0.17.0's, its `libfledgeruby.a`, which held OpenSSL, libyaml, libffi, and Ruby. Android's runtime is a shared library that keeps its libraries to itself (`--exclude-libs`), and `libfledgeext.so` links with `--exclude-libs,ALL`, so there nothing else can take an extension's name;
4. makes only those names local in the object, the Init function kept, with Apple's `nmedit -R`, which changes "the symbol table entries for the global symbols listed" to static ones (nmedit(1)), or the NDK's `llvm-objcopy --localize-symbols`, and archives it in place of the extension's archive, in place of its own static libraries too.

An extension that shares no name is linked as before, its archive and libraries untouched, and so is every extension of an app that has one linked extension on Android. Each local name is then the extension's own, and every other part that defines it keeps its own: psych calls the runtime's libyaml and the extension its `yaml_get_version`. nmedit stops on a listed name the object lacks ("symbols names listed in ... not in"), where llvm-objcopy takes it silently, so the list holds only names read from that object. Prior art: ld(1)'s own example for an object built of others, "ld -o relocatable.o -r a.o b.o c.o" then "nmedit -s interface_symbols relocatable.o"; and the phone runtimes' rule for bundled gems' extensions, which makes every name but the Init function local (`doc/contributors/design/phone-runtimes.md`, "Each extension's symbols").

The names come from the object's symbol table, which the app's link binds by, and never from LLVM bitcode. Rust's standard library, which every Rust extension's static library carries, is compiled with its LLVM bitcode embedded, in a `__LLVM,__bitcode` section on iOS and `.llvmbc` on Android, so that a Rust build can optimize across it: the core library of Rust 1.99.1's `aarch64-apple-ios-sim` target has both `__LLVM,__bitcode` and `__LLVM,__cmdline`. Xcode's `nm` is LLVM's (`nm --version`: "llvm-nm, compatible with GNU nm"), and LLVM's nm reads an object's names from that bitcode, where it has some, in place of the symbol table; LLVM's reader stops at bitcode a newer LLVM wrote. Xcode 27.2's `nm` stops so on that core object ("Not an int attribute (Producer: 'LLVM23.1.1-rust-1.99.1-stable' Reader: 'LLVM APPLE_1_2100.4.1.1_0')"). Whether the prelinked object still has the section is the linker's choice: Xcode 27.2's `ld -r` leaves it out, and Xcode 26.5's, by what CI's run printed, keeps it, so on CI's pinned Xcode `fledge build ios` of `test/fixtures/rust_phone` stopped there, at `116f5967`, which was reverted for it. `--no-llvm-bc`, "Disable LLVM bitcode reader" in LLVM's nm, makes it read only the symbol table. On Android the NDK's `llvm-nm` reads an ELF object's names from bitcode only in the `.llvm.lto` section a fat LTO object carries (`clang -ffat-lto-objects`), and not from Rust's `.llvmbc`: an object with unreadable bytes in `.llvmbc` lists its names, and the same bytes in `.llvm.lto` stop it. So a Rust extension never met this on Android, and the flag there keeps a C extension compiled as fat LTO objects from meeting it. Three other ways were weighed: taking the section out of each object with Xcode's `bitcode_strip`, or rebuilding Rust's standard library without it, changes what the app links to work around how a reader reads, and needs a step for each phone; and reading the symbol table with another tool, `otool` or `objdump`, means parsing a second format of output, when one flag of the same tool keeps the reader off the bitcode. `test/integration/mobile_separation_names_test.rb` reads names, with each phone's tool, from an object whose `__LLVM,__bitcode` or `.llvm.lto` section holds bytes no LLVM reads, after showing that the tool without the flag stops on it, and on iOS from the object of Rust's core library.

What "right" is was decided by the orchestrating agent, not the maintainer: each extension reaches its own definitions, as on a Mac and in Android's extension files. A desktop's glibc binds a later extension's calls to the first one loaded that defines the name, since `dln.c` opens it `RTLD_GLOBAL`, so on Linux the answer depends on which gem was required first: no gem's author intends that, and no app developer could foresee it from a phone. A desktop Linux app built by Fledge behaves as Linux's Ruby does, and that stays.

Four other ways were weighed. Making every name but Init local, as the bundled gems' rule does, would change every extension's link, and an extension a host or another extension calls into would lose what it exports; this way changes only an extension that clashes. A framework or shared library per extension, as CPython ships each binary module on iOS ("they must be stored in the app's Frameworks folder, with each module wrapped in a Framework", PEP 730, "Dynamic libraries"), would change how every iOS app's Ruby is linked, against the runtime's `--disable-dln` ("Linking extensions on iOS"). Renaming the names with `-D` options, as the Init functions are, needs the names before the compile, which only the link shows. Refusing such gems would refuse what a Mac's Ruby runs.

The build refuses, naming each part and the name, two parts that must both keep one name global: a static library several extensions link and the runtime, or two such libraries, which neither can be made local in, and two extensions whose Init functions are one name. What it costs: each extension is linked once more on iOS, and on Android when the app links two or more; a name of an extension's static library that the extension never reaches, which a host or another extension called, is missing once that extension is separated, and the app's link says so; a name read from a shared library's whole archive, not only the members a link takes, can make a refusal where no link would take both; a common symbol, a global without an initializer that Xcode's clang makes common unless an extension is compiled `-fno-common`, is not read on iOS, and two of one name still merge; and a library an extension links by `-lNAME` from a folder, rather than by its path, is left out of the reading.

`test/integration/mobile_linked_symbols_test.rb` builds the five cases above as developers' apps of path gems, with `fledge build`, Xcode's Debug build or Gradle's `assembleDebug`, and runs them on a Simulator and on the Android emulators as `tasks/mobile_parity.rb` runs the examples, checking what each gem answers; `test/mobile_extensions_separation_test.rb` checks which names each part keeps, and the refusals.

## CMake toolchain files

An `extconf.rb` may run CMake to build a library before mkmf builds the extension over it, as a game engine shipped as a gem often does. The phone's `rbconfig.rb` aims mkmf, not CMake, and no environment variable sets `CMAKE_SYSTEM_NAME`, so without a toolchain file CMake configures for this computer: it built a library for macOS on both iOS slices, which `xcodebuild -create-xcframework` refused, and an Android library with undefined symbols (`doc/contributors/research/2026-11-10-findings-from-the-adrs.md`, "CMake in an `extconf.rb`, before and after the toolchain file"). For each target, Fledge writes a toolchain file into its build folder, `toolchains/TARGET.cmake`, and puts its path in `CMAKE_TOOLCHAIN_FILE` in the environment it runs that target's `extconf.rb` in (`MobileExtensions::CMake`). CMake 3.21 and later read that variable when a build folder is new, which it is, since each gem is unpacked afresh for each target. The files never enter the app. Each sets only CMake's own documented variables:

- **An iOS slice** (`CMake.ios`) uses CMake's own iOS support (cmake-toolchains(7), "Cross Compiling for iOS, tvOS, visionOS, or watchOS"): `CMAKE_SYSTEM_NAME` `iOS`; `CMAKE_OSX_SYSROOT`, the slice's SDK as `xcrun --show-sdk-path` gives it, which selects device or Simulator; `CMAKE_OSX_ARCHITECTURES` and `CMAKE_OSX_DEPLOYMENT_TARGET` from the triple the slice's `rbconfig.rb` records; and `CMAKE_C_COMPILER`, `CMAKE_CXX_COMPILER`, `CMAKE_OBJC_COMPILER`, and `CMAKE_OBJCXX_COMPILER`, the very clang and clang++ mkmf is given. The Objective-C compilers serve a library that enables CMake's `OBJC` or `OBJCXX` language; one that compiles `.m` files as C, as SDL3's does, gets the same clang.
- **An Android ABI** (`CMake.android`) sets `ANDROID_ABI` (`arm64-v8a`, `x86_64`) and `ANDROID_PLATFORM` (`android-26`, the API level in the name of the compiler the runtime was built with), and `ANDROID_STL` `c++_shared` unless the build has defined it, then `include()`s the NDK's own `build/cmake/android.toolchain.cmake`, the file Google's documentation and Gradle give CMake. That file reads the variables and makes code position-independent. Setting them in a file that includes the NDK's, rather than as `-D` options, holds in CMake's `try_compile` projects too, which read the toolchain file again. "The C++ runtime CMake links", below, says why `ANDROID_STL`.

With the Makefile and Ninja generators a project handles "target CPU selection and code signing" itself (cmake-toolchains(7)): the architecture is set here, and a static library is not signed. An `extconf.rb` that passes its own `-DCMAKE_TOOLCHAIN_FILE` or `--toolchain` overrides Fledge's, as CMake documents. Fledge's files add no search paths: the NDK's and CMake's iOS platform files decide where `find_package` and `find_library` look. A CMake build that uses either, and CMake's Xcode generator, are untested.

`CMAKE_TOOLCHAIN_FILE` is CMake's own, documented mechanism for cross-compiling, so an `extconf.rb` needs nothing of Fledge's, and a gem written for cibuildwheel, which aims a Python package's CMake at Android the same way, already works. Five other ways were weighed. Options Fledge hands the `extconf.rb`, such as `-DCMAKE_SYSTEM_NAME=iOS` in a variable of Fledge's, would need code in every gem. CMake's environment variables alone (`CC`, `CXX`, `CFLAGS`) set no `CMAKE_SYSTEM_NAME`. leetal/ios-cmake's `ios.toolchain.cmake` predates CMake's own iOS support, which CMake has had since 3.14, and is more than the few lines that set CMake's documented variables, and one more tool to pin. The NDK's `android.toolchain.cmake` alone in `CMAKE_TOOLCHAIN_FILE` reads `ANDROID_ABI` and `ANDROID_PLATFORM` as CMake variables, not from the environment, and without them builds for `armeabi-v7a` (`build/cmake/android.toolchain.cmake`, lines 109 to 126 at r30), so Fledge's file sets them and includes it. CMake's built-in Android support (`CMAKE_SYSTEM_NAME Android`, `CMAKE_ANDROID_NDK`) works too, but Google documents and maintains the NDK's file, and Gradle uses it, so it is the one the rest of an app's Android code builds with.

What it costs: a gem that runs CMake needs CMake 3.21 or later on this computer's `PATH`, which Fledge does not provide; an `extconf.rb` that reuses a build folder an earlier configure made keeps that folder's toolchain; and a `./configure` or Meson build that an `extconf.rb` runs gets the phone's compilers in `CC` and `CXX` ("The environment kept out") but no cross file of Fledge's.

### The C++ runtime CMake links

A desktop's CMake links a shared C++ library with the compiler, which links the system's shared C++ runtime. Given no `ANDROID_STL`, the NDK's file links the static one: at r30 `android.toolchain.cmake` includes `android-legacy.toolchain.cmake` unless `ANDROID_USE_LEGACY_TOOLCHAIN_FILE` is defined (lines 47 to 54), and that file sets `ANDROID_STL` to `c++_static` when it is unset (lines 241 and 242) and links `c++_static` with `-static-libstdc++` (lines 373 and 374), as Google documents: "The default for CMake is c++_static" (developer.android.com/ndk/guides/cpp-support, "Selecting a C++ Runtime", last updated 2026-11-06). So until 20 November 2026 a shared library an `extconf.rb` built with CMake held a copy of the C++ runtime of its own, beside the `libc++_shared.so` that a C++ extension calling it links ("The C++ runtime rule").

A path gem showed what that does. Its `extconf.rb` builds `libthrower.so` with CMake (`add_library(thrower SHARED ...)`) and then a C++ extension that calls it the seven ways of "One C++ runtime in an app", above, and asks `dladdr` where `__cxa_begin_catch`, `__cxa_throw`, and `std::exception`'s `type_info` are, from the extension and from the library. On a Linux desktop both sides found all three in `libstdc++.so.6`, and every crossing answered as one runtime does. On an x86_64 emulator of API 36 the extension left all eight of the library's functions undefined and `libthrower.so` defined them, and three builds behaved three ways:

- **As the NDK's file links it**, the library (3,697,544 bytes for x86_64, 3,905,160 for arm64-v8a) needs no `libc++_shared.so` and exports its copy's names. The extension's needed libraries name `libthrower.so` before `libc++_shared.so`, and bionic resolves each library opened with the extension against the extension's breadth-first group ("Each extension file's symbols"), so the extension and the library both found the three names in `libthrower.so`, and every crossing answered as on the desktop: an exported copy took the place of the shared runtime for the whole group. That rests on the copy being exported and on the order of the extension's needed libraries.
- **When the library hides its copy**, as the NDK asks of a shared library that links the static runtime ("you must either use libc++_shared or ensure that libc++'s symbols are not exposed by your library", developer.android.com/ndk/guides/middleware-vendors, "STL"), here with `-Wl,--exclude-libs,ALL`, the extension found the three names in `libc++_shared.so` and the library in itself. The string crossed, and the exception ended the app: "libc++abi: terminating due to uncaught exception of type St13runtime_error: boom". The two saw different `std::cout` objects too.
- **With `ANDROID_STL` `c++_shared`**, the library (68,616 bytes for x86_64, 72,480 for arm64-v8a) needs `libc++_shared.so` and holds none of the runtime. Both sides found the three names there, and every crossing answered as on the desktop, whether or not the library hides what it links statically.

So Fledge's file sets `ANDROID_STL` to `c++_shared`, as a desktop's CMake links the system's shared runtime, and as every other C++ library Fledge links does ("One C++ runtime in an app"), following the NDK's advice: "If your application includes multiple shared libraries, you should use libc++_shared.so" (cpp-support, "Shared runtimes"). It sets it only where the build has not (`if(NOT DEFINED ANDROID_STL)`): an `extconf.rb` that passes `-DANDROID_STL=c++_static` keeps that choice, and the hazard above, which is that build's, as `-static-libstdc++` in a Rakefile's link is ("The C++ runtime rule"). A static library CMake builds, as `test/fixtures/cmake_phone`'s is, links no C++ runtime itself, since `ANDROID_STL` chooses what a shared library or a program links, and the extension over it links `libc++_shared.so` as before. iOS has one C++ runtime, the system's libc++, and `CMake.ios` sets nothing of it.

Three other ways were weighed. Leaving the NDK's default kept apps working while the copy was exported and named first, which a library that hides it as the NDK asks does not do, and left each such library about 3.6 MB larger for each ABI. Setting `ANDROID_STL` with a plain `set()` would hide the cache variable a gem's `-D` makes, overriding a build's own choice. Refusing a gem whose CMake library links the static runtime would stop one that works on a desktop. What it costs: nothing beyond the `libc++_shared.so` an app with a C++ extension already carries. `test/integration/mobile_extension_symbols_test.rb` builds such a library, hiding what it links statically, and checks that it needs `libc++_shared.so`, holds no `__cxa_throw` or `__cxa_begin_catch` of its own, and answers each crossing on CI's emulators as on a desktop; without the setting, the exception ended its program as it ended the app.

## The environment kept out

A phone's build runs each `extconf.rb` in an environment with the developer's own toolchain variables removed (`MobileExtensions::FOREIGN`), since they would aim mkmf, make, or CMake at the developer's computer or give them the developer's flags: `CC`, `CXX`, `CPP`, `CFLAGS`, `CXXFLAGS`, `CPPFLAGS`, `LDFLAGS`, `SDKROOT`, `IPHONEOS_DEPLOYMENT_TARGET`, `MACOSX_DEPLOYMENT_TARGET`, `MAKEFLAGS`, `CMAKE_OSX_ARCHITECTURES`, `OBJC`, `OBJCXX`, `OBJCFLAGS`, and `OBJCXXFLAGS`, with the variables a desktop's native build removes (`NativeBuild::SCRUBBED`). The phone's own tools take their place under the same names, `CC`, `CXX`, and on Android `AR` and `RANLIB` (`MobileExtensions::Targets#with_tools`), so that a build the Makefile starts with only the environment to go on is aimed at the phone, as rake-compiler-dock and crossenv name the target's compiler: the ffi gem's runs libffi's `configure` so on Android. `PKG_CONFIG` is `false`, as the runtime's own `configure` is given (`PKG_CONFIG=false`), since pkg-config finds this computer's libraries, and mkmf runs the one the environment names when the phone's `rbconfig.rb` names none (`lib/mkmf.rb`, line 1969 at Ruby 4.1.0-preview1): it found a Mac's libffi for the ffi gem, which then linked the Simulator's with `-lffi`. A gem's `--with-pkg-config` option still names one. On Android, a folder of the build's own comes first on `PATH`, whose `strip` is the NDK's `llvm-strip` (`Targets#strip_folder`), since a build may run strip by that plain name, as sassc 2.4.0's `extconf.rb` adds `strip -x $@` to mkmf's link off Apple's systems (`ext/extconf.rb`, lines 68 and 69): this computer's strip refused the ABI's library (GNU strip 2.42: "Unable to recognise the format of the input file"), and the NDK's strips it as a desktop's strips its own. On iOS that line is not added, and Xcode's strip reads the phone's Mach-O files anyway. The developer's `CMAKE_TOOLCHAIN_FILE` is replaced by the target's. `CMAKE_GENERATOR`, `CMAKE_BUILD_TYPE`, `CMAKE_BUILD_PARALLEL_LEVEL`, and the rest pass through: they choose how CMake builds, not what it builds for, and the gem's `extconf.rb` decides them as on a desktop.

## The C++ runtime rule

An extension whose Makefile lists a C++ source (`.cc`, `.cpp`, `.cxx`, `.C` in mkmf's `ORIG_SRCS`) has C++. So does a C extension whose `extconf.rb` names the C++ runtime (`-lc++` or `-lstdc++`, `Linking::CXX_RUNTIMES`), as a C extension over a C++ library must on a desktop (`Linking.cxx_runtime?`). The name itself is left out of the flags the app links (`Linking.link_flags`), and each phone links its own C++ runtime: `-lc++` once in the iOS app's `OTHER_LDFLAGS`, and on Android the NDK's `clang++`, which links its shared C++ runtime, `libc++_shared.so`, for `libfledgeext.so` and for each extension built as a file, whose `-lc++` or `-lstdc++` the shim takes out of mkmf's libraries before linking it with `LDSHAREDXX` (`FLEDGE_LDSHAREDXX`, `$(CXX) -shared`), so that a C extension over a C++ library links as a C++ one does. The app then carries `libc++_shared.so`, and every C++ library in it, Fledge's and those a gem's own build links, shares that one copy, as the NDK asks of an app with several shared libraries ("The NDK's shared C++ runtime" and "One C++ runtime in an app"); an app with no C++ carries none. Until 20 November 2026 Android's links took the static runtime (`clang++ -static-libstdc++`), chosen when no package carried the shared one, and an app whose extension file called a gem's C++ library over the shared one aborted. The rule is for what Fledge links: a library a gem's own build links, such as one for ffi, takes whichever C++ runtime that build chose, which with the NDK's clang++ is the shared one unless the build says otherwise, and with CMake the shared one Fledge's toolchain file names unless the build names another in `ANDROID_STL` ("The C++ runtime CMake links").

The rule reads the C++ runtime from what the `extconf.rb` says, rather than from the archives' symbols, since the `extconf.rb` already names it as it must on a desktop. A gem that names `-lc++` or `-lstdc++` for another reason, of which none is known, links a C++ runtime it does not use.

## Refusals

`MobileExtensions.problems` refuses, naming the gem, what to do, and the Gemfile's `platforms:` that leaves the gem out of the phone's build:

- an extension the gemspec says something other than an `extconf.rb` or Rake builds (a `CMakeLists.txt`, `configure`, or `Cargo.toml` in `extensions`), since RubyGems' own builders for those would each need their own cross-compiling, and none makes the static archive and renamed `Init_` function that mkmf's `$static` does; the message says an `extconf.rb` may run CMake. None of the 10,000 most-downloaded gems names a bare `CMakeLists.txt` or `configure` (`doc/contributors/research/2026-11-12-phone-extension-build-systems.md`);
- for Android, a Windows computer, since compiling an extension there is untested: nobody has tried the Windows runtime's `make` or the NDK's Windows tools on an `extconf.rb`.

The build also fails when a Rakefile's build leaves a shared library not built for the target, or installs one ("Rakefiles", above), when an `extconf.rb` calls `create_makefile` (or `create_rust_makefile`) more than once, since Fledge links one extension for each, when `make static` makes no archive or Cargo no static library, when a Rust target's standard library is missing, when two extensions would register the same Init function, when two parts of the app that must keep a name global both define it ("Each linked extension's symbols"), and when the gems build different extensions for different targets of one phone, since the app registers one list for all of them. On Android it fails, too, when a library Fledge carries needs one that neither Android, the runtime, nor the app provides ("What each library needs"), and when the project's `build.gradle`, read once the host's files are in place, sets `useLegacyPackaging` to `false`, or sets none, in an app with an extension built as a file (`MobileProject::AndroidPackaging`), naming the file, each such extension, and the line to set ("Host files", below); on iOS, when two libraries for ffi would be frameworks of one name, or the slices built different libraries for ffi ("Libraries for ffi on iOS").

## Host files

`ios: host: DIR` and `android: host: DIR` in `fledge.yml` name a folder of the project's own files for that phone (`Fledge::Config::Phone`). Some frameworks start a phone app their own way: SDL3's `SDL_RunApp` starts UIKit and runs the game's main function on the main thread, and its `SDLActivity` is the Activity that owns the surface SDL draws on (see "A host that owns the main loop"). Such a framework needs its own `Host/main.m`, `Info.plist`, and linker settings on iOS, and its own `MainActivity` and Java files on Android, which no gem's `extconf.rb` can carry, and which `fledge build`, writing the project afresh, would otherwise lose at each build. The shape, one mapping for each phone with one key in it, as Briefcase scopes a setting to a platform and buildozer to Android, leaves room for a phone's next setting beside `host`.

1. **It copies every file in the folder over the project,** at the same path relative to the folder, once Fledge has written its template, the runtime, the extensions, and `fledge/`, and before Fledge fills its marks and XcodeGen reads `project.yml` (`MobileProject#place_host`). A host file replaces Fledge's at its path, whole, or joins the project. Fledge merges nothing.
2. **Fledge fills its marks in a host's copy of a marked template:** `project.yml` on iOS; `settings.gradle`, `build.gradle`, `src/main/AndroidManifest.xml`, `src/main/res/values/strings.xml`, and `MainActivity.java` on Android. So a copied `project.yml` still takes the app's name, identifier, version, and the extensions' link flags. The templates' paths and marks are part of the public interface (`test/mobile_template_contract_test.rb`; `doc/contributors/design/public-interface.md`).
3. **The host wins.** The build says, in one line on standard error, where progress goes, which of Fledge's files the host replaced: `host/ios replaces Fledge's Host/Info.plist, Host/main.m, project.yml`. Files the host adds go unmentioned.
4. **It refuses a host it cannot copy.** Reading `fledge.yml`, Fledge refuses a `host` that is not text naming a folder in the project, by the rule a program's path follows: relative, with `/` between folders, and no segment empty, `.`, or `..`, naming the file and the phone. Writing the phone's project, it refuses a host that is not a folder, or that a link leads out of the project, before it writes anything.
5. **The folder stays out of the app.** Its files are the project's, not the program's, so the build leaves the folder out of `fledge/app/`.
6. **Each key is its own phone's.** Desktop builds ignore both, `fledge build ios` ignores `android`, and `fledge build android` ignores `ios`. Only that phone's build looks for the folder.

The copy is Vlissides' Generation Gap (*Pattern Hatching*, chapter 3): the generated half and the hand-written half live in separate files, so generating again loses nothing, and a framework runs no step of its own after `fledge build`. Three other ways were weighed. A script the framework runs after each build to patch the project would be code every framework carries and keeps in step with Fledge's templates. XcodeGen's `include`, which merges one spec into another, serves `project.yml` alone, not `main.m`, `Info.plist`, or Android's files. Merging a host's files into Fledge's would be code of Fledge's for property lists, YAML, and Gradle files, formats it does not own (decisions, 2026-10-28: code is a liability). The seam knows nothing of SDL, since Fledge depends on no wrapper's repository (decisions, 2026-11-02), and a pure-Ruby app names no host and keeps Fledge's files. What it costs: a host's copy of one of Fledge's files is the developer's to keep in step with Fledge's, and nothing compares the two but the line that names each copy and the check "A host's copy after an upgrade" lists; and a host replaces a file whole, so a developer who changes one key of `Info.plist` copies the file.

### A host's copy after an upgrade

A copy made from an older template keeps that template's settings, and what the app needs of them can change with Fledge. What a host's copy must hold, and since when:

- **Android's `build.gradle`:** Fledge's marks, `libs/FledgeRuby.aar` as a dependency, `fledgeAsset` with its generated assets, `noCompress += ['zip']`, and `useLegacyPackaging = true`. The template set `false` until 0.13.0, when the ruby program came (`RbConfig.ruby` then names nothing in a copy that keeps it); from 0.14.0 every C or C++ extension an `extconf.rb` builds is a file among the native libraries, so such a copy builds an app that raises `LoadError` at the extension's `require`. A copy that sets nothing builds the same app, since the plugin's default keeps the libraries stored. Since Ruby's own extensions and encodings became files among the native libraries too, after 0.17.0, no app at all runs from such a copy, and the build refuses both for every app (`MobileProject::AndroidPackaging`), naming the app's extensions built as files and Ruby's own.
- **Android's `MainActivity.java`:** it starts Ruby with `FledgeRuby.startApp`. A copy from before 0.14.0 keeps working: its `@@LOAD_EXTENSIONS@@` mark is now filled with nothing, and one that loads `fledgeext` by name loads the library the runtime has already opened ("Linking extensions on Android").
- **iOS's `project.yml`:** Fledge's marks, `@@EXTENSIONS@@` among the dependencies and `@@LDFLAGS@@` in `OTHER_LDFLAGS`, through which the extensions and, from 0.15.0, the frameworks for ffi arrive, and the build phase "Copy Ruby and the app". From 0.13.0 that phase also copies the slice's `include/`, and a copy without that line builds an app whose `require "mkmf"` aborts for want of Ruby's headers; nothing else needs them, so the build does not check it. A copy without the marks fails in Xcode's link, not on the phone. A copy from 0.17.0 or before names `FledgeRuby.xcframework` with `embed: false`, where the template now has the mark `@@RUBY_EMBED@@`; with a runtime whose Ruby is a framework such a copy would build an app that stops as it starts, for want of `FledgeRuby` in its bundle, so the build refuses it, saying what to write (`MobileProject::IOS#check_ruby_embedded`).
- **iOS's `Host/main.m`:** it calls `fledge_ruby_run_app`, unchanged since 0.12.0.

`test/mobile_template_contract_test.rb` holds the marks and paths to the templates; nothing holds a host's copy to them but the check of `build.gradle` and the line that names each copy.

The other tools that write a project a developer then keeps tell the developer in three ways. Briefcase stamps each project it writes with its template's epoch (`briefcase.toml`, `target_version`) and refuses to build one whose epoch differs from its own, "The app template used to generate this app is not compatible with this version" of Briefcase (`src/briefcase/commands/base.py`, `verify_app_template`, lines 748 to 770 at v0.3.25). Flutter's build runs migrations that rewrite a kept Android file where an old template's text is known to break, as `MinSdkVersionMigration` replaces an old `minSdkVersion` in the app's `build.gradle` (`packages/flutter_tools/lib/src/android/migrations/min_sdk_version_migration.dart`, lines 21 to 49 at 3.24.0). React Native leaves it to the developer, with the Upgrade Helper's diff of the template between two versions: "In case there are changes you need to manually apply them into your project" (reactnative.dev/docs/upgrading, "Upgrade your project files"). Fledge refuses what it can read as certain to fail, as a desktop's build refuses a gem that would not run: an app whose extensions need the libraries extracted, with a `build.gradle` that sets `false` or sets nothing. The plugin documents what nothing means: `useLegacyPackaging` is a `Boolean?`, and "If null, .so files will be uncompressed and page-aligned when minSdk >= 23" (`JniLibsPackaging`, developer.android.com/reference/tools/gradle-api/9.0/com/android/build/api/dsl, read 2026-11-22), and the template's `minSdk` is 26. It was seen so on 22 November 2026 with the pinned plugin, 9.4.1: `test/fixtures/native_phone` built with `fledge build android` and `./gradlew assembleDebug`, once with Fledge's `build.gradle` and once with a host's copy of it without its `packaging { jniLibs { } }` block, then installed on an x86_64 emulator of API 36. With the template, the merged manifest and the APK's say `android:extractNativeLibs="true"`, `unzip -v` shows every `lib/x86_64/*.so` deflated, and the app prints its line. With the copy, they say `false`, every library is stored, the installed app's `lib/x86_64` is empty, and the app exits 1 with `cannot load such file` (`LoadError`) at the extension's `require`. Until then Fledge warned of a copy that set nothing and built it, since a project may set the value in a file Fledge does not read (a script it applies, a convention plugin). A refusal leaves such a project a way past that costs it nothing, the line the message names, which agrees with what it sets elsewhere; a warning left every other such project an app that dies. The manifest is not such a place: a host's `AndroidManifest.xml` with `android:extractNativeLibs="true"` and no setting fails the plugin's own `packageDebug`, which says to "set android.packagingOptions.jniLibs.useLegacyPackaging to true in the build script" instead, as Android's manifest reference says the setting "replaces the extractNativeLibs manifest attribute" from plugin 4.2.0. Rewriting the copy, as Flutter does, would overrule what a host wrote, where the host wins (step 3, above), and `false` is a choice the template's comment offers. A template epoch, as Briefcase keeps, would refuse every copy after any change to the template, those whose change the app does not need included. What it costs: the check reads Groovy as text, the last setting for native libraries outside comments, and so refuses a value it computes, as `useLegacyPackaging = packed`, as if it were none, and misreads a setting in `build.gradle.kts`. It leaves out the setting of the same name for dex files, in a `dex { }` block or as `dex.useLegacyPackaging`, which the Android Gradle plugin keeps apart (`JniLibsPackaging`: "Whether to use the legacy convention of compressing all .so files in the APK. If null, .so files will be uncompressed and page-aligned when minSdk >= 23"; `DexPackaging`: "Whether to use the legacy convention of compressing all dex files in the APK"; developer.android.com/reference/tools/gradle-api/8.13/com/android/build/api/dsl, read 2026-11-20), so a host that packs its dex files another way is not refused for it; and `CHANGELOG.md` names, in each release that changes a template, what a copy must take.

## A host that owns the main loop

Some frameworks start the app and run its main function themselves. SDL3 is the example `test/fixtures/sdl_phone` runs: a path gem, `sdl_demo`, whose `extconf.rb` links SDL3 and whose C extension opens a full-screen window and runs a frame loop that calls a Ruby block each frame. Fledge's API is the same for any such framework: the host forwards output and calls `fledge_ruby_run_app` wherever its framework runs the main function, and `fledge_ruby_run_app` runs Ruby on the calling thread.

**SDL3 itself** is built by `test/fixtures/sdl_phone/sdl3/build.sh` from SDL's release tarball, pinned by SHA-256, with SDL's own CMake build as SDL documents it, once per target:

- **iOS**, on a Mac: `-DCMAKE_SYSTEM_NAME=iOS`, the SDK, `arm64`, deployment target 15.0, static (`-DSDL_SHARED=OFF -DSDL_STATIC=ON`). A static library links into the app's executable as extensions do, so nothing is embedded; SDL's own `SDL3.xcframework`, which the app would embed, is not needed.
- **Android**, with the NDK: its `android.toolchain.cmake`, `ANDROID_ABI`, and `ANDROID_PLATFORM=26`, shared (`-DSDL_SHARED=ON -DSDL_STATIC=OFF`). It has to be shared: SDL registers its Java methods from `libSDL3.so`'s `JNI_OnLoad`, which `System.loadLibrary("SDL3")` calls, and a static SDL in a gem's extension would be in a library Ruby opens, where Android's runtime looks for no `JNI_OnLoad`. The script also copies SDL's Java classes into the example's Android host, where git ignores them.

The gem finds SDL3 through Bundler's build options, as any gem finds a library: `bundle config build.sdl_demo --with-sdl3-builds=OUT`, which Fledge passes to the `extconf.rb` for every target. The `extconf.rb` tells the targets apart by the compiler Fledge gives mkmf, and links what SDL's `sdl3.pc` names. Libraries need no `fledge.yml` key: what an `extconf.rb` links, Fledge links per target and carries into the APK. SDL is Zlib, it is a dependency of the example's gem, and nothing of it goes into a Fledge runtime.

**On iOS, Ruby runs on the main thread, inside `SDL_RunApp`.** SDL's `SDL_RunApp` calls `UIApplicationMain` and, once the scene connects, runs the app's main function on the main thread inside the run loop. SDL's UIKit calls must be on the main thread ("On Apple platforms this is a requirement", SDL's `src/SDL.c`): Ruby on Fledge's own thread fails `SDL_Init`, and with `SDL_SetMainReady` it crashes on a UIKit threading violation. So the example's host (`test/fixtures/sdl_phone/host/ios/`) has:

- `Host/main.m`, whose `main` calls `SDL_RunApp(argc, argv, run_ruby, NULL)`, where `run_ruby` calls `fledge_ruby_run_app`; it declares the two SDL functions it calls, so it needs no SDL headers;
- `Host/Info.plist`, naming `SDLUIKitSceneDelegate` as the scene's delegate;
- `project.yml`, with `-Wl,-stack_size,0x4000000` in the project's `OTHER_LDFLAGS`, which asks for a 64 MB main-thread stack in `LC_MAIN`, and `ENABLE_DEBUG_DYLIB = NO`, since ld takes `-stack_size` only for a main executable and Xcode's Debug configuration otherwise links the app's code into `NAME.debug.dylib`; the UI test's target takes no linker flags of the project's, for the same reason.

kivy-ios runs Python under SDL the same way: its template's `main` becomes SDL's main function and runs Python on the main thread. Running Ruby on its own thread and sending each SDL call to the main thread (`SDL_RunOnMainThread`) would make every call the game's Ruby makes cross threads, and the engine, not Fledge, would carry that.

**On Android, an `SDLActivity` runs Ruby on a 64 MB thread.** SDL's Java side has to be the Activity: it makes the surface SDL draws on, and SDL's video calls back into its static methods. The example's host (`test/fixtures/sdl_phone/host/android/`) replaces Fledge's `MainActivity` with one of the same name and package, so the manifest needs no change. It extends `SDLActivity`, returns `{"SDL3", "fledgeruby", "fledgeext"}` from `getLibraries()`, SDL first, so that its `JNI_OnLoad` registers SDL's methods before anything that needs SDL loads (`fledgeruby` and `fledgeext` may stay in the list, and need not, since the runtime loads `libfledgeext.so` itself), and overrides `main()`, which SDL calls on its SDLThread, to run Ruby with `FledgeRuby.startApp` on a thread with a 64 MB stack and wait for it, so the game ends when Ruby does. Overriding `main()` replaces SDL's `nativeRunMain`, which would look for an `SDL_main` the app does not have. SDLThread itself is made with Java's default stack, about 1 MB, too shallow for Ruby. SDL's Java files enter the Gradle project as sources, as SDL's `android-project` holds them; python-for-android's `PythonActivity` extends `SDLActivity` the same way.

The measurements and device runs behind these choices are in `doc/contributors/research/2026-11-10-findings-from-the-adrs.md`. A real iPhone granted the 64 MB main-thread stack `-stack_size` asks for; Apple documents 1 MB for a device's main thread, and an iPad's grant is not measured.

## A host that draws the app's own screen

`examples/basket`, Basket, is the phone app among the examples, made because the maintainer answered issue 69 ("Make one. You choose the kind."). It is a shopping list: add an item, tick it off, clear the ticked ones. Its Ruby, `main.rb`, keeps the list and saves it as JSON in `Dir.home` at each change, since a phone may stop an app in the background without running `at_exit`. Each phone's own widgets draw it, from a host of the example's own (see "Host files"). `host/ios/Host/main.m` uses UIKit: a table in a navigation controller, a text field to add, a checkmark to tick, and a bar button to clear. `host/android/.../MainActivity.java` uses Android's views: an `EditText`, a `ListView` of check boxes, and a Clear action in the app bar.

**How the host and Ruby talk.** The embedding API gives a host one way in, the arguments of `fledge_ruby_run_app` (`FledgeRuby.startApp` on Android), and no call from the host into a running Ruby. So the host makes two pipes, with `pipe` on iOS and `ParcelFileDescriptor.createPipe` on Android, and passes Ruby their ends as `--in FD --out FD`. It writes one command a line down the first, and a thread of its own reads each answer from the second and shows it on the main thread. Ruby opens the descriptors with `IO.for_fd`, and answers each command, and its start, with the whole list as one line of JSON. Without the options, `main.rb` reads standard input and writes standard output, so `ruby main.rb` runs the same program in a terminal. This is the standard input and output a language server or a coprocess speaks, made of what both systems already offer, so Fledge adds no code for it. The app uses only Ruby's standard library, so it builds on each phone with nothing to compile.

**Why this kind of app.** These kinds were weighed:

- **A list kept by Ruby and drawn natively** was chosen. A Ruby developer recognizes it as a real app. It needs no gem, so it carries none of the risk that took the Lent example off `trunk` (7e31227a: a gem compiled against Homebrew's library on GitHub's macOS runner), and it follows each platform's interface guidelines with its own widgets, as the maintainer asked of the examples.
- **A Sinatra app on a loopback server, shown in a web view,** was the first design. The maintainer ruled out an app that runs an HTTP server only to draw its own screen. It would also listen on the loopback address, which every app on an Android phone shares, so it would have needed a secret to keep other apps out.
- **A game on SDL3**, as `test/fixtures/sdl_phone` is: SDL3 must be built from source for every target by the example's own script, which no CI job runs (issue 56).
- **Ruby that drives UIKit itself,** through `fiddle` and the Objective-C runtime, as BeeWare's rubicon-objc drives it from Python: iOS has the runtime to call, and Android has nothing like it short of a JNI bridge written in Ruby.
- **A gem whose C extension bridges the two:** on Android a Java method's native code must be in a library the host loads by name ("Fledge provides", `public-interface.md`), so the example would carry a library built for each ABI, and a C extension, for a list.
- **A new call in the embedding API** for the host to send Ruby a message: that is new public interface in Fledge, not an example, and the pipes need none.

Each phone is one host, so one example serves both. Separate examples for iOS and Android would each carry the same `main.rb`.

**What it costs.** The hosts are each about 200 lines, Objective-C and Java, in the languages of Fledge's own templates: SwiftUI would need Swift beside the template's Objective-C, and Jetpack Compose or Material Components would need Kotlin, Compose's compiler plugin, and more Maven downloads in CI's Gradle builds (see "Gradle's downloads in CI"). Each host's `main.m` and `MainActivity.java` replace Fledge's whole, so a developer who copies them keeps them in step with the templates (see "A host's copy after an upgrade"). Basket has no icon, so the archive check checks none for it.

**How it is checked.** `tasks/mobile_parity.rb` builds and runs Basket with the other apps, in the Simulator on an iPhone and an iPad and on both Android emulators. A real app stays open, so its `App` says `stays_open`: its launch is done once the host logs `Basket shows 0 items`, after it has drawn the list Ruby sent, and the check fails if Ruby has ended by then. That line proves the whole path: the host started Ruby with the pipes, Ruby answered, and the host's widgets showed the answer. Nothing in CI taps the screen, so a command sent after the start is proven only by `ruby main.rb` in a terminal. `APPS=examples/basket` in the environment builds and runs that app alone, to prove it before a push.

## The Android App Bundle check

Google Play takes an Android App Bundle from a new app, not an APK. The project is a standard application module, so the plugin's `bundleRelease` and `bundleDebug` make one with no change to the template, and three things hold for it:

- **`fledgeAsset` runs for a bundle:** the asset is a generated source of every variant, and the bundle tasks merge the same assets as the APK tasks, so the bundle holds `base/assets/fledge.zip`.
- **`fledge.zip` stays stored:** the plugin writes `noCompress` into the bundle's `BundleConfig.pb`, whose `uncompressedGlob`s (`bundletool dump config`) include `**[zZ][iI][pP]`, so every APK bundletool or Play makes stores the asset.
- **Native libraries are extracted:** with `useLegacyPackaging = true`, the bundle's config does not ask for `uncompressNativeLibraries`, so every APK bundletool or Play makes compresses them and the installer extracts them, the ruby program among them (see "The Gradle project"). Their LOAD segments are aligned for 16 KB pages, which the runtime build and `MobileExtensions#shared_library` check; Android's page-size guide asks for zip alignment only of libraries that stay stored.

`bundleDebug` signs with the SDK's debug key, and `bundleRelease` leaves the bundle unsigned. A developer signs it with their upload key, in a `signingConfigs` block or with `jarsigner`, since `apksigner` signs no bundle, and Play App Signing signs the APKs it serves (`doc/phones.md`, "Google Play"). A Fledge app is all base module: Ruby, its standard library, the app, and its gems are one asset. Play limits a base module to a 500 MB compressed download; an app with hundreds of megabytes of data would move the data into a Play Asset Delivery pack, which Fledge does not build.

CI's `mobile-apps-android` jobs build both bundles of every app beside its APKs (`tasks/mobile_parity/android.rb`). Each release bundle is signed with a throwaway upload key made in the job, verified with `jarsigner -verify`, validated with `bundletool validate`, checked not to ask for uncompressed native libraries, and made into an APK set with `bundletool build-apks`, as Play would. Each split APK must pass `zipalign -c -P 16`; `fledge.zip` in it must be stored and every native library compressed, which `zipalign` alone does not check (`MobileParity::Android.packed_wrongly`); each of the base module's main APKs must hold `fledge.zip` and target API 36, the lowest from API 26; and the largest download must stay under the limit. Each app then runs a second time on the emulators, installed from its APK set with `bundletool install-apks`, which picks the device's splits as Play does, and must print the same line and exit 0. The `mobile-apps-android-hosts` jobs build `test/fixtures/mobile_app`'s release bundle on macOS and Windows and check it the same way. bundletool is pinned by SHA-256 in `runtime/sources.yml` as a tool only CI fetches.

## Gradle's downloads in CI

A Gradle project fledge build writes declares `google()` and `mavenCentral()`, and the Android Gradle plugin's buildscript classpath alone is dozens of modules from Maven Central. Maven Central limits what it serves to the addresses that download the most, and counts a hosted CI's or a cloud's shared addresses as one consumer ("429 Too Many Requests and Maven Central consumption limits", central.sonatype.org/faq/429-error/, which also says that retrying harder makes it worse and that the remedy is caching, not downloading again from clean, ephemeral machines). From 13 to 19 November 2026, nine Gradle builds in CI could not resolve the plugin, in nine full runs on `trunk`, and no commit was at fault in any: eight ran on GitHub runners whose logs name AWS as their cloud, and one, on 13 November, on a macOS runner (job 131807102790, answered 429); none on an Azure runner failed. The cloud does not decide it either way: on 19 November runners on AWS failed some Gradle jobs and built the same template in others. Some were answered 429, which Gradle 9.8.2 itself retries twice, a second and then two apart (`NetworkingIssueVerifier`, `NetworkOperationBackOffAndRetry`), and then reports as `Received status code 429`, and some were answered "Could not find" for guava, kotlin-stdlib, and every other module Central holds. Gradle reports "Could not find" only when every repository answered 404 (`ApacheCommonsHttpClient#processResponse`, where only a 404 is a missing resource and any other status fails with its code), so Central answered those runners 404 for files it has (run 44527956502's job on us-west-2 reported 49 such lines). Which job failed was which cloud its runner came from; any of them can.

So every CI job that runs Gradle restores Gradle's dependency cache, `modules-2` in the Gradle user home, the folder Gradle's guide says may be copied between machines, without its lock files ("Copying and reusing the cache", docs.gradle.org/9.8.2/userguide/dependency_caching.html). A module with a fixed version that the cache holds is never asked for again (only a changing or dynamic one is, "Changing dependencies", the same page), so a job whose key the cache holds asks Central for nothing. A build on Linux from empty Gradle homes showed that the folder alone is enough: the runtime's AAR project and the ten apps CI builds were built once, each home's `modules-2` was copied without its lock files into an empty home, and from that home every one of them built again with `--offline`, as APKs and as bundles, debug and release. Each of the two sets was 325 files and 237 MB. The key is everything that decides what Gradle resolves: the runner's system, since the plugin fetches the aapt2 built for the system it runs on; the plugin's version, `runtime/sources.yml`'s `agp`, which `Fledge::MobileProject::Android::AGP` matches (`test/mobile_platform_test.rb`); and the project's Gradle files, which name the repositories, the plugin, the dependencies, and, in the wrapper's properties, Gradle's version. A key the cache does not hold, after a change to any of them, restores instead the newest set saved for the same system and the same plugin: each restore names that prefix in `restore-keys`, which the cache matches by prefix, taking the most recently created entry ("Cache key matching", docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching). Gradle then asks the repositories only for what that set lacks. It looks up a module it has not yet resolved from a repository, and takes from the cache every module it has ("Repository caches are independent", Gradle's page above); a module the set holds and the build no longer needs is never read. So a change to a template's Gradle file, or to Gradle's version, downloads the modules it adds, not the plugin's whole classpath again. The fallback stops at the plugin's version, so that a set does not carry every earlier plugin's modules forward: a new plugin brings most of a new classpath, and its first run downloads it, as a developer's first build does. Four sets are kept:

- **The template's on Linux,** which the `mobile-apps-android` jobs save once Gradle has built every app, debug and release, as APKs and as bundles. `ruby-spec.yml`'s Android jobs, which build a debug APK, and `installed.yml`'s, which build both APKs from a tag, restore it under the same key and never save, so their smaller set never takes the key.
- **The template's on macOS,** which the `mobile-apps-android-hosts` job on macOS saves.
- **The template's on Windows,** which the `mobile-apps-android-hosts` job on Windows saves.
- **The runtime's AAR project's on Linux** (`runtime/mobile/android/`), which the Android runtime job saves, keyed on that project's Gradle files and the pinned Gradle and plugin, and falling back to the newest set for the same Gradle and plugin.

A job on `trunk` saves a complete set only after its Gradle build succeeded, so the exact key never holds a set that a failed build left half fetched, and it saves whenever the exact key was not restored: a set restored through `restore-keys` leaves `cache-hit` false (`restore/README.md`, actions/cache at 55cc8345), so the job stores it again, with what Gradle added, under the new key. Saving on success under a key of the project's Gradle files is what `actions/setup-java`'s `cache: gradle` does, which Tauri's Android job uses (`.github/workflows/test-android.yml`, tauri-apps/tauri at 61a3537e), and what Briefcase's app checks do for their whole data folder (`.github/workflows/app-build-verify.yml`, beeware/.github at fb3a3550). `setup-java` restores by its exact key alone, so a change to a Gradle file starts from nothing, and it is not used in any case because the projects are written during the job, so the files its key hashes are not there when it runs. Gradle's own `setup-gradle` offers two providers (`docs/setup-gradle.md`, gradle/actions at 8da46b53). Its Basic provider, which is MIT, is `setup-java`'s strategy, with no restore keys (line 466). Its default, Enhanced, restores the closest matching entry through restore keys and keeps each downloaded dependency in an entry of its own (lines 252 to 278), which would remove the same dependence on Central that `restore-keys` removes here; it is not used because it is the proprietary `gradle-actions-caching` library (line 203), and because it keys each entry by job and by commit (lines 230 to 249), so each job writes new entries for every commit into the 10 GB that every other cache of the repository shares. The cache costs the repository's Actions storage the plugin's downloads, and hides only whether Central still serves the same immutable files, which is Central's to keep and not Fledge's to check. When an emulator job's Gradle build fails, Gradle's `--info` log for each app, which records each repository's answer ("Resource missing" for a 404, "Failed to get resource" with any other status), is kept with the job's artifacts, and the failure quotes those lines (`MobileParity::Android.gradle_failure`).

On `trunk` only ("Caches only trunk saves" in runtimes.md: a set saved on another branch serves no run of `trunk`, and `pin-move` is deleted after each proof), a build that fails, a refusal that outlasted Gradle's patience for instance, saves too: Gradle keeps every file a build downloaded, a failed build's included, so the job saves what it fetched under the exact key with `-partial-`, its run's number, and its attempt's number added (`cache/save` runs under `!cancelled()`, and the key reads `job.status`). The exact key is never taken by it, so the next run that has no complete set restores the newest partial one through `restore-keys` and asks Central only for the rest, saves the complete set under the exact key when it passes, and each run on `trunk` after a refusal asks for less than the one before. Before this, a save waited for success, so a run on `trunk` after a pin moved, which found nothing to restore (the proof's sets were saved on `pin-move`, which `trunk` cannot read, below), fetched the whole classpath, failed on a refusal, saved nothing, and the next run did the same: on 24 November 2026 the Android runtime job on `trunk` (run 45292798092) found no set and was answered 429 for the plugin's whole classpath through two full rounds of the patience below, while the two sets for those pins that the proof had saved sat on `pin-move`, and `trunk` held no Gradle set at all. A failed build's set costs the repository the same storage as a complete one, about 200 MB, once per failed run.

Two cases still ask Central for the plugin's classpath, and fail on a runner it refuses: the first run on `trunk` after the plugin's pin changes, which has no set to fall back on and, if it fails, leaves a partial one for the next, and a job whose system and plugin have no set left in the cache at all. GitHub removes an entry no run has used for seven days, and once a repository's caches pass 10 GB it evicts the least recently used until they fit ("Usage limits and eviction policy", the same page); on 20 November 2026 Fledge's held 10.5 GB in 78 entries, and the oldest had last been used 21 hours before. The first case is no longer rare: `pin-watch.yml` moves the Android Gradle plugin's and Gradle's pins by itself (`runtime/upstreams.yml`, `agp` and `gradle`), and the move's proof is a full run of `ci.yml` on the branch `pin-move`, whose every Gradle job then starts with no set for the new pins. A cache saved on `pin-move` serves no run on `trunk` or on a tag either, since a run restores only what its own branch or the default branch saved (GitHub's dependency caching reference, docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching, on which branches a run may restore a cache from). If Central refuses a runner, the proof is red, `pin-watch.yml` proves the pin alone and is red again, and the run fails, which tells the maintainer; nothing runs it again until the next day's watch, and `runnerless.yml` runs again only jobs no runner took, never a job that ran and failed (`tasks/runnerless_runs.rb`). So the path the maintainer asked to run with nobody in the loop (decisions.md, 2026-11-22) would stall for as many days as Central refused, and call him each day. So every CI job that runs Gradle first makes Gradle patient, with `.github/scripts/gradle-patience.sh`, which a unit test (`test/workflow_gradle_test.rb`) requires of every job that restores Gradle's cache. It sets Gradle's own retry, in `gradle.properties` in the Gradle user home, where every build reads its system properties, by the pinned Gradle, a project's wrapper, or a daemon: Gradle 9.8.2 reads `org.gradle.internal.repository.max.tentatives` (3 by default) and `org.gradle.internal.repository.initial.backoff` (1000 ms) in `ErrorHandlingModuleComponentRepository`, and doubles the wait before each try. The script asks for 7 tries from 10 seconds, which waits 10, 20, 40, 80, 160, and 320 seconds, ten and a half minutes in all, before Gradle gives a download up; the test holds that to at most half of each Gradle job's time limit, so a refusal that ends within minutes no longer fails the job, and one that lasts hours fails it before the limit does, with Gradle's own message. Gradle retries only what `NetworkingIssueVerifier` calls transient, an answer of 408, 429, or any 5xx, a refused or reset connection, or a timeout, and reports anything else at once, so a build that fails for its own reasons is not slowed. Each retry asks for that one file again: Gradle keeps every file a build downloaded, a failed build's too, and the next asks only for the rest. Both were shown with Gradle 9.8.2 against a local repository that answered as scripted: three answers of 429, then the file, failed a build with the defaults (tries a second and two seconds apart) and passed one with the settings, as a daemon or not; and after a build failed on one file answered 500, the next asked for that file alone. A 404 for a file Central holds, the "Could not find" above, is not retried, since Gradle cannot tell it from a module that does not exist. Gradle does not remember the miss, though: in the same run of that local repository, a second build in the same Gradle home asked for the file again and passed. So a second Gradle build in the same job reaches it, with nothing downloaded twice, and "A 404 for a file Central holds", below, says where one runs; running a failed job again starts on a fresh runner with nothing kept. Taking both cases off Central entirely would need each set kept where nothing evicts it, which "Pinned sets, not done", below, says is not done. So a refusal that outlasts Gradle's patience, and any 404 for a file Central has, still fails the job, and the move's proof with it; the next day's watch tries the move again.

### A 404 for a file Central holds

Gradle's retries cover a refusal, not an answer of 404 for a module Central holds, which some runners were given. Gradle treats a 404 as a missing file: `NetworkingIssueVerifier` retries only 408, 429, any 5xx, and network failures, it has no setting that adds a status, and it does not cache a 404 (a test with the pinned Gradle found that a second build in the same home asks again and passes). So the retry is of the build, once, where Fledge's own check runs Gradle: `MobileParity::Android.build` appends each try's `--info` log to one file and, when the first try failed and the log holds an answer of "Resource missing" (a 404, as `gradle_failure` reads it), runs the build again, with what the first try fetched already in the home. A failure with no 404 in its log, such as a 429 the retries gave up on, is not run again, so a refusal is not hammered (Sonatype's advice above), and a second 404 is final, so a module that really is absent fails the job as before. The wait before the second try is none: the 404 is not a limit that waiting lifts, and the build's own retries have already waited for any refusal. The one method that holds the rule, `MobileParity::Android.gradle_with_a_second_try`, is what every other Gradle build of Fledge's calls too: `ruby_spec`'s Android build (`tasks/ruby_spec/phone.rb`); the runtime's AAR project, which `RuntimeBuilder::Android#pack_aar` builds with the pinned Gradle at `--info` into a log of its own; and the Gradle steps of the workflow files, `mobile-apps-android-hosts` in `ci.yml` and `installed.yml`'s build of the apps from a tag, which run `.github/scripts/gradle.rb PROJECT TASK...` (it calls `MobileParity::Android.gradle`, which builds with the project's wrapper and, on failure, prints what `gradle_failure` reads from the log) and never `./gradlew` themselves, which `test/workflow_gradle_test.rb` requires of every workflow. The installed job's sparse checkout of the workflow's own commit holds `tasks/` for it.

### Pinned sets, not done

Each of the four sets above could be kept as a file on a pre-release of Fledge's own repository, pinned by URL and SHA-256 in `runtime/sources.yml`, and given to Gradle as a read-only dependency cache (`GRADLE_RO_DEP_CACHE`), so that CI never asked Maven Central. It is not done. It would make Fledge a distributor of about 300 files from other projects, some under EPL-2.0 and MPL-1.1 with duties about source and notices, and a few with no license stated, for CI's convenience alone. The maintainer's word is that this was not worth it (decisions.md, 2026-11-22). Gradle's own retries, `.github/scripts/gradle-patience.sh`, cover a refusal that ends within minutes, and a longer one fails the move for the day and the next day's watch tries again.

Not chosen either: running a failed job again, in every run, would download everything again from a fresh runner, against Sonatype's advice ("the right answer is not to retry harder"); a mirror of Central, or the repository manager Sonatype suggests in front of it, is a second host, which no one pins and none of Fledge's projects declares, so the job would no longer build the project a developer gets; dependency verification would pin each file's SHA-256 but download them all the same, and it lives in the project, as `gradle/verification-metadata.xml`, so it would change what a developer gets; `--offline` on a hit would make the hit's independence certain, but would fail a job whose restored set lacks one module that Central would serve, where a hit already asks nothing for a fixed version; and committing the sets to git would add a plugin's whole build classpath to every clone with each update.

## The App Store archive check

An iOS app reaches the App Store as an archive, which Xcode exports or uploads to App Store Connect. Exporting one for App Store Connect needs an Apple ID of the archive's development team (`man xcodebuild`); validating and uploading (`altool`, Transporter) need App Store Connect credentials. So everything on Apple's servers waits on an account (`doc/contributors/account-tests.md`, IOS-1 to IOS-5), and CI checks what Apple's own tools check without one.

The `mobile-apps-ios` job archives each app's Xcode project with `xcodebuild archive -sdk iphoneos -configuration Release CODE_SIGNING_ALLOWED=NO`, as Product > Archive does with no team, failing on any warning, and checks the archive and the app in it (`tasks/mobile_parity/ios_archive.rb`):

- **The archive:** its `Info.plist` names `Applications/NAME.app` and arm64 only, and it holds `dSYMs/NAME.app.dSYM`, which App Store Connect takes for symbolication.
- **The app's `Info.plist`,** read with `plutil -convert json`, holds the keys Apple's pages say the App Store needs: `CFBundleVersion` and `CFBundleShortVersionString`, `UIRequiredDeviceCapabilities` with `arm64`, the identifier, executable, name, and `APPL` package type, `MinimumOSVersion` 15.0, `UIDeviceFamily` `[1, 2]`, a launch screen, and the `DTXcode`, `DTSDKName`, and `DTPlatformName` keys only a build by Xcode for a device writes. The template writes none of the keys Xcode adds, and the check reads the built file, so a setting that stopped producing one fails it.
- **The executable** is arm64 alone (`lipo -archs`), built for the iOS platform with minimum 15.0 (`vtool -show-build`, so no Simulator slice), holds no bitcode segment (`otool -l`), and loads only `/usr/lib` and `/System/Library` libraries and, where the runtime's Ruby is a framework, `@rpath/FledgeRuby.framework/FledgeRuby` (`otool -L`). There is no `PlugIns`, `Watch`, `SC_Info`, `embedded.mobileprovision`, or `_CodeSignature`, since a Fledge app embeds nothing of those kinds and is unsigned here.
- **The frameworks:** the app's `Frameworks` holds exactly Ruby's, `FledgeRuby.framework`, where the runtime's Ruby is one, and the frameworks the project's `Frameworks/` has an XCFramework of, those of Ruby's extensions (`doc/contributors/design/phone-runtimes.md`, "Ruby's extensions on iOS") and of the libraries for ffi ("Libraries for ffi on iOS"), since Apple puts a framework there ("Placing content in a bundle"). Each has an `Info.plist` naming its binary as `CFBundleExecutable`, with `FMWK` as its package type, `iPhoneOS` as its platform, `MinimumOSVersion` 15.0, an identifier, and versions of one to three integers; is unsigned; and has a binary that is a dynamic library (`otool -hv`), arm64 alone, for the iOS platform with minimum 15.0, without bitcode, loading only Apple's libraries and Ruby's framework beside its own install name, as the executable is checked; and one whose binary exports OpenSSL's `_OPENSSL_init_crypto` holds a `PrivacyInfo.xcprivacy` that passes `plutil -lint`, since Apple lists OpenSSL among the SDKs that need a privacy manifest of their own. No file in the app but the executable and those binaries is Mach-O, found by its magic number, and every link in the app leads to a file inside it, as Apple's links for code loaded by path do ("Embedding nonstandard code structures in a bundle").
- **`PrivacyInfo.xcprivacy`** is in the app, passes `plutil -lint`, and holds the four keys of Apple's "Privacy manifest files" page; its reasons are checked against the imports of the executable and of each framework's binary (see "The privacy manifest").
- **An app whose `fledge.yml` names an icon** has `CFBundleIconName` `AppIcon`, a 1024 pixel image named `AppIcon` in `Assets.car` (`assetutil --info`), and a source PNG with no alpha channel, read from its header (color type 4 or 6, or a `tRNS` chunk): App Store Connect refuses a large app icon with an alpha channel, even an opaque one (ITMS-90717). An app with no icon gets a note, since App Store Connect needs one and only the developer has one to give.
- **Export compliance and the version** are reported, not failed (see the next section).

## Export compliance and the build number

**Export compliance.** App Store Connect asks about an app's encryption on every upload unless its `Info.plist` holds `ITSAppUsesNonExemptEncryption`. The template writes no such key, and the archive check reports whether the key is declared (`IOSArchive.encryption`). The answer is the developer's claim, and Apple's pages do not make `false` plainly right for a Fledge app (`doc/phones.md`, "Export compliance", quotes them, marked as not legal advice; `doc/contributors/research/2026-11-10-findings-from-the-adrs.md`, "Export compliance and version 0.0.0, as Apple's and Google's pages read", holds the reading): the key covers the app with "any third-party libraries you link against", and every Fledge iOS app contains OpenSSL, which Ruby uses for HTTPS and `openssl`; the case Apple names as exempt is encryption built into the operating system, such as HTTPS through `URLSession`, which Ruby's HTTPS does not use; and Apple puts the liability for a wrong claim on the developer. The U.S. regulations Apple points to (EAR 740.17 and 742.15) could not be read from bis.gov's pages, so nothing here rests on them. Writing `false` in the template would make that claim for every app, one whose gems do more than HTTPS included; refusing an iOS build without the key would stop a developer who only runs the app on their own phone, for a key only an upload asks about. So App Store Connect's questionnaire is where a developer answers, once, on the first upload, and the developer adds the key to their host's `Info.plist` afterward. A reading of the regulations that made `false` clearly right for an app that only uses HTTPS would be a reason to write it in the template.

**A version of 0.0.0.** An app with no `version` is 0.0.0, so its `CFBundleVersion` and `CFBundleShortVersionString` are 0.0.0 and its Android `versionCode` is 1. Apple's reference allows it (`CFBundleVersion` is "one to three period-separated integers ... 0 specifies 0.0.0"), no App Store Connect page read refuses it, and Google Play wants "a positive integer". So `fledge build` does not refuse it: refusing would stop every developer who runs an app on their own phone, for a rule no store states. The archive check notes it (`IOSArchive.version_note`), and `doc/phones.md` tells a developer to set a version before a store. Each store wants a new build number for each upload. If App Store Connect is found to refuse 0.0.0, `fledge build ios` should refuse it, citing that.

## Parity on a phone

The mobile parity check (`tasks/mobile_parity.rb`, in the Mobile apps jobs) runs the parity probe as a phone app, built by `fledge build`, in the iOS Simulator on an iPhone and an iPad and on Android emulators with 4 KB and 16 KB pages, and compares its report with `ruby main.rb` under the runner's desktop Ruby, but for `ENV` and a child Ruby's `ENV`, which it compares with the environment the phone gave the app: the probe's host, the one `fledge build` writes with one loop more, logs it a variable a line before it calls anything of Fledge's (`MobileParity::Environment`), so a variable Fledge adds fails the check, where a comparison with the desktop's environment, which shares nothing with a phone's, could only allow everything. The report reaches the check through the system log, as an app's output reaches its developer. Every difference must be justified in `Parity::MOBILE_JUSTIFIED` (`tasks/parity/mobile.rb`), which says why each is right; `doc/contributors/design/parity.md` describes the check. ruby/spec runs in a phone app on the same simulators and emulators too, against stock Ruby on the same computer (`doc/contributors/design/parity.md`, "ruby/spec on phones"). What the probe cannot show, and an app on a phone should expect:

- the working folder is `/`, as for a macOS app started from the Finder;
- standard input is at its end;
- an iOS app's bundle is read-only on a device (writable in the Simulator), so an app writes under `Dir.home` or `Dir.tmpdir`; an Android app's Ruby root is unpacked into its own files folder, which it may write;
- on iOS under Fledge's host, Ruby's thread has 64 MB; under a host that runs Ruby on the main thread, the main thread's stack is what the system grants;
- iOS lets no app start a program (the iOS SDK marks `system` prohibited there, "On iOS, process spawning is unavailable": `usr/include/_stdlib.h`, lines 205 to 208, iOS 27.2 SDK), so there `RbConfig.ruby` names where `bin/ruby` would be, and starting it fails with ENOENT in the Simulator, where nothing is there, and with EPERM on a device, whose sandbox refuses every program. Whether a device lets an app `fork` is unchecked: the same SDK marks `fork` prohibited only on watchOS and tvOS (`usr/include/unistd.h`, line 459), and that a device's sandbox denies it is reported by others, such as CPython's iOS build ("no fork syscall", `configure.ac`, line 7732 at v3.14.0), not said by Apple. An Android app starts the system's programs and the native libraries its installer extracted, but no file it writes (W^X, from target API 29), so `RbConfig.ruby` is a link to the runtime's ruby program, which runs (`doc/contributors/design/phone-runtimes.md`, "The ruby program on Android");
- the system may stop an app in the background without running `at_exit`.
