# ADR 031: A Mirror Can Stand In for the Release's Host

## Status
Accepted (requested). Agents wrote this ADR and may change it until 1.0 (AGENTS.md, Questions); from 1.0 the variable and the layout it reads are frozen (ADR 029, section 2). It carries out part (2) of Plan 003's story "Fledge on RubyGems.org, and runtimes that do not depend on one host", and widens ADR 002, section 2 (`FLEDGE_RUNTIME_DIR`) and ADR 014, section 1 (where `Fledge::Runtimes` downloads from). It names no second default host: the maintainer chooses hosts, and "If you want a second host, you come to me asking" (decisions, 2026-11-04).

## Date
2026-11-04

## Context

`fledge build` downloads each runtime, and when it compiles a gem the runtime's build-only companion, from the GitHub Release of its own version, `https://github.com/setdef/Fledge/releases/download/vVERSION/NAME`, into its cache, and checks every file against the SHA-256 the gem pins for it in `lib/fledge/SHA256SUMS` (ADR 014, section 1). The pins were fixed when the gem was, so they vouch for a file whatever served it. Until now nothing could choose another server: a developer behind a firewall that blocks GitHub, an organization that keeps its own copy of every input, or anyone after GitHub changed its terms, had only `FLEDGE_RUNTIME_DIR`, which takes a folder and checks nothing, since it was made for runtimes a developer built (ADR 014, section 1).

The tools ADR 002, section 2 cites each let a variable replace the host:

- **uv.** `UV_PYTHON_INSTALL_MIRROR` "will replace `https://github.com/astral-sh/python-build-standalone/releases/download`" in each download's URL (`crates/uv-static/src/env_vars.rs`, lines 524 to 532, at astral-sh/uv 4470c33b). The rest of the path, the release's tag and the file's name, stays. When it is set, uv uses it "exclusively, no automatic fallback" (`crates/uv-python-managed/src/downloads.rs`, lines 809 to 818); only uv's own default mirror, which Astral runs, falls back to GitHub (lines 821 to 833). Every file is still checked against the SHA-256 uv carries for it.
- **rustup.** `RUSTUP_DIST_SERVER` "sets the root URL for downloading static resources", "to instead use a local mirror" (`doc/user-guide/src/environment-variables.md`, lines 17 to 20, at rust-lang/rustup 0eafe77d). It replaces the default outright (`src/config.rs`, lines 1159 to 1163), with no fallback.
- **pyenv's python-build.** `PYTHON_BUILD_MIRROR_URL` is tried first, at `MIRROR/SHA256`, and a failure falls back to the package's own URL (`plugins/python-build/bin/python-build`, lines 580 to 611, at pyenv/pyenv 68a076e0). Its mirror is a cache keyed by checksum, and its default mirror is pyenv's own (lines 2696 to 2702).

## Decision

### 1. `FLEDGE_RUNTIME_MIRROR` replaces the releases' download base

When `FLEDGE_RUNTIME_MIRROR` names a base URL, `fledge build` downloads every runtime and companion from `MIRROR/vVERSION/NAME`, the path the release has under `https://github.com/setdef/Fledge/releases/download`, as uv's mirror replaces the same prefix. A mirror is then a copy of the releases' assets in one folder per tag, which `gh release download vVERSION` fills, and one mirror can hold every version a team uses. A trailing slash is ignored, as uv ignores it. Empty means unset.

The name follows the prior art's: `FLEDGE_` as every Fledge variable, `RUNTIME` as `FLEDGE_RUNTIME_DIR`, and `MIRROR` as uv and python-build say. The URL is `http` or `https`, as `Fledge::Download` takes; a folder on disk is `FLEDGE_RUNTIME_DIR`'s.

### 2. Everything from a mirror is checked against the pins

The pins are the same, and so is the check: a file from the mirror is saved only if its SHA-256 is the one the gem pins, and the cache is checked against the pins as before (ADR 014, section 1). A mirror that serves other bytes fails the build with a message that names the variable, the mirror, the file, and both SHA-256s, and nothing is saved. `FLEDGE_RUNTIME_DIR`, when set, still wins over both.

### 3. A mirror that fails is not passed over

When the mirror lacks a file, refuses, or cannot be reached, the build fails, naming the variable and the mirror, and does not try the release. The pins would make a fallback safe for the bytes, so the choice is about where `fledge build` connects. uv and rustup do not fall back from a mirror a person set; python-build does, but its mirror is a cache in front of each package's own URL, and its default mirror is its own. A Fledge developer who sets a mirror usually does so because the release's host is blocked, forbidden by policy, or gone, and a quiet fallback would reach a host they chose not to reach, or hang on one that cannot be reached, and would hide a mirror that is missing a version until the day the release's host is gone too. A failure that names the mirror and the file shows the mirror's owner what to copy. A mirror that fails for a moment, with a 5xx or a broken connection, is asked again as the release is (ADR 014, section 6), and only then fails, still without trying the release.

## Consequences

- An organization can serve Fledge's runtimes from its own server, and a developer can build where GitHub cannot be reached, with the same guarantee as the release: the bytes Fledge's CI built and the gem pinned.
- Fledge still has one default host. A second default, tried after the release, waits for the maintainer to name one (Plan 003); it would be a fallback Fledge chose, unlike section 3's.
- A mirror must hold the files of every version that builds from it, at that version's tag. The asset names, the tag form, and this layout are frozen for 1.x (ADR 029, section 2).
- The tests prove it with real loopback servers: a mirror is used and the release is not asked, a mirror whose file does not match the pins is refused and nothing is cached, and a mirror without a file fails while the release, which has it, receives no request (`test/runtimes_test.rb`).
