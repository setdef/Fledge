# ADR 072: On a phone, a gem's Rakefile runs as RubyGems runs it, and the extensions it builds with mkmf are linked in

## Context and Problem Statement

On a phone every extension is compiled for the target and linked into the app (ADR 022), and Fledge compiled only those an `extconf.rb` builds. A gem whose gemspec names a Rakefile was refused before anything ran. The maintainer asked that such gems build too: "Python and other languages that have Fledge-like tools must solve this somehow; so can we." (`decisions.md`, 2026-11-12).

Of the 10,000 gems with the most downloads, 419 have extensions (`doc/contributors/research/2026-11-12-phone-extension-build-systems.md`, section 2): 388 name an `extconf.rb`, 2 a `Cargo.toml`, none a `CMakeLists.txt` or `configure` alone, and 30 a Rakefile. Of those 30, 21 compile nothing (they install dependencies or check for tools), 7 build a shared library for ffi to load, and one, digest-crc, builds 27 extensions of Ruby's with mkmf under Rake. So the gems refused for their Rakefile are mostly gems with nothing to compile. How does a phone build take a gem whose extension a Rakefile builds?

## Decision Drivers

- The app's code runs as under `ruby main.rb`, and a gem that installs with `gem install` should ship (decisions 9 and 20).
- A person who runs the app never meets an error that names a gem (AGENTS.md, Design precedence 1): a gem that would fail at run time is refused when building.
- Code is a liability (`decisions.md`, 2026-10-28): reuse RubyGems' and Ruby's own tools, and write nothing no real gem needs.
- Fledge never changes a developer's gems (ADR 007).

## Considered Options

1. Run the gem's Rakefile with RubyGems' own `RakeBuilder`, with every Ruby it starts reading the phone's `rbconfig.rb`; link in each extension that mkmf builds under it, through mkmf's own static rule, as ADR 022 does for an `extconf.rb`; and refuse, by name, a shared library the build leaves that no extension's static archive accounts for.
2. Option 1, with the compiler wrapped so that every shared link any build makes becomes a static archive, as kivy-ios's `liblink` does.
3. A recipe per gem, as python-for-android, kivy-ios, Chaquopy, and BeeWare's mobile-forge carry.
4. Shared libraries, as Python ships them on phones (PEP 730, PEP 738): one framework per extension on iOS, `dlopen` on Android.
5. Keep refusing a gem whose gemspec names a Rakefile.

## Decision Outcome

Chosen: option 1, because it takes every Rakefile gem among the 10,000 that can run on a phone, with RubyGems' builder and mkmf's own static rule, in about 100 lines. The 21 that compile nothing build and register nothing; digest-crc's 27 extensions are linked in, named by their folders in the gem's require paths; and a library built for ffi is refused by name, where without the check it would build and fail when the app loads it. How the build is aimed and what it refuses: `doc/contributors/design/phone-projects.md`, "Rakefiles".

Option 2 serves, among the 10,000, the same one gem as option 1, in 161 lines, and otherwise only the CMake and `configure` gems that do not exist there; it waits for a real gem that needs it. Option 3 is a database of other people's gems for Fledge to pin and patch, against ADR 007; the Python tools carry recipes for the gems an environment does not reach, not instead of one. Option 4 reverses ADR 022's static design and the iOS runtime's `--disable-dln`. Option 5 is what the maintainer overruled.

Confidence: high that the 21 gems and digest-crc build: `unf` 0.2.0, `ldclient-rb` 5.5.6, and digest-crc 0.7.0 built for both iOS slices. Android rests on the same mechanism and tests; `examples/rake_phone`'s run on an emulator will confirm it.

### Consequences

- Good, because a gem refused only for naming a Rakefile now builds for a phone, as it installs with `gem install`.
- Good, because an extension mkmf builds under Rake is linked in as one an `extconf.rb` builds is, with no new build system.
- Bad, because a gem's Rakefile runs on the developer's computer at build time, as `gem install` runs it; Fledge adds no sandbox `gem install` lacks.
- Bad, because a Rakefile that compiles without mkmf, or hard-codes a compiler, or reads the build computer's files, is refused or misbuilds; the prior art carries recipes for such gems, and Fledge carries none.
- Neutral: a gem that builds a library for ffi to load is refused by name on both phones; the ffi gem itself works there (ADR 074), and what loading such a library would take is in ADR 074's consequences.

### Confirmation

`test/mobile_extensions_test.rb` checks the refusals; `test/integration/mobile_extensions_build_test.rb` builds a gem shaped like digest-crc (`test/fixtures/rakesum`) for each iOS slice and Android ABI and checks its archives' objects and renamed `Init` functions, and a Rakefile that builds nothing registers nothing.

## More Information

- ADR 022 decides how a phone compiles an extension an `extconf.rb` builds; this ADR adds Rakefiles. A gem whose gemspec names a `CMakeLists.txt` or `configure` alone is still refused.
- The counts and the prior art: `doc/contributors/research/2026-11-12-phone-extension-build-systems.md`.
