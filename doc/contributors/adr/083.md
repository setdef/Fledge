# ADR 083: On Android, RbConfig.ruby names the ruby program through a link at the path stock Ruby derives

## Context and Problem Statement

On Android the runtime carries a ruby program in the app's native library folder, `nativeLibraryDir`, the one place Android lets an app run a file of its own (ADR 082). That folder's name changes with each install. Stock Ruby derives `RbConfig.ruby` from its prefix, `ROOT/bin/ruby`, along with `RbConfig::CONFIG["bindir"]` and `ruby_install_name`, and `Gem.ruby` follows it. How does `RbConfig.ruby` name a program that lives elsewhere, at a path known only once the app is installed?

## Decision Drivers

- An app's code runs as under `ruby main.rb` (decisions 9, 10, and 20): `RbConfig.ruby` and `Gem.ruby` name a Ruby that runs, and `RbConfig` itself stays what stock Ruby's is.
- `ENV` stays as `ruby main.rb` has it (decisions 9 and 10).
- Gems read `RbConfig` for other ends: RubyGems takes `bindir` as where to install executables, and `ruby_install_name` for their shebangs.

## Considered Options

1. `RbConfig` as stock Ruby has it, `ROOT/bin/ruby` from the prefix Ruby derives, made a symbolic link to the program in `nativeLibraryDir` before Ruby boots.
2. Rewrite `rbconfig.rb` at run time, so that `bindir` is `nativeLibraryDir` and `ruby_install_name` is `libfledgerubyexe`.
3. An environment variable naming the program.

## Decision Outcome

Chosen: option 1, because it leaves `RbConfig.ruby`, `Gem.ruby`, `RbConfig::CONFIG["bindir"]`, and `ruby_install_name` what stock Ruby derives from the prefix, as on a desktop. Before Ruby boots in the app, the runtime makes `ROOT/bin/ruby` a link to the program wherever the installer put it, whenever it is not that link already. The kernel runs the file a link resolves to, and the program finds `ROOT` from the path it was run by. How: `doc/contributors/design/phone-runtimes.md`, "The ruby program on Android".

Option 2 changes values of `RbConfig` that gems read for other ends. Option 3 adds to the app's `ENV`, which decisions 9 and 10 keep as `ruby main.rb` has it, and still needs a program.

Confidence: high. On CI's Android emulators, API 36 with 4 KB and 16 KB pages, the parity probe's `RbConfig.ruby is a program` and `RbConfig.ruby runs` match `ruby main.rb`, and a OnePlus Nord, arm64-v8a with API 34, ran a child Ruby through `system` and `IO.popen` from an app with no unjustified parity difference.

### Consequences

- Good, because `RbConfig` is stock Ruby's, so a gem that reads it for another end reads what it would on a desktop.
- Bad, because the app writes the link into its own files on the first start after each install, before Ruby boots.
- Bad, because where the native libraries load from inside the APK, as when a developer sets `useLegacyPackaging = false`, there is no program to link, the runtime removes any old link, and `RbConfig.ruby` names nothing.
- Neutral: iOS has no program, and its runtime makes no link (ADR 082).

### Confirmation

`test/integration/mobile_ruby_program_test.rb` runs the program by its path, a relative path, and a link; the mobile parity check compares `RbConfig.ruby is a program` and `RbConfig.ruby runs` with `ruby main.rb` on both Android emulators.

## More Information

- With ADR 082, this supersedes ADR 069, which held both decisions.
