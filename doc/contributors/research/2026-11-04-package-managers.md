# Can a Fledge console app go through a package manager?

## Short answer

The maintainer's decision brings the system package managers into scope for console programs (decisions.md, last entry on the maintainer's side; it is not yet on `trunk` at a737305). Read against what Fledge writes today, the answer splits in two.

Channels that take a prebuilt archive and need only a text file (a manifest, a formula, a PKGBUILD) work **today**, with no change to the archive: a Scoop bucket, a Homebrew tap, a winget manifest, an AUR `-bin` package, a Chocolatey package that downloads the zip, a Nix flake **(guess for NixOS; see section 14)**, and the GitHub-release installers `mise`, `aqua`, and `ubi`. What is missing is the text file, a checksum list, and (for apt, dnf, pacman repositories) a package format for a console program.

Channels whose official repositories build from source refuse a Fledge app by their own written rules: `homebrew/core`, Debian, Ubuntu's PPAs, Fedora, Flathub, and (second-hand) nixpkgs and Arch's official repositories. Each has a third-party route (a tap, a hosted repository, a Copr project, the AUR) that does take it.

The launcher is already safe to start through a symlink, a shim script, and a parent process that spawns it, on macOS (tested, section 2). On Linux the source reads as safe (not run here). On Windows the launcher reads its own path with `GetModuleFileNameW` and never resolves a symlink; whether that returns the link or the target is not settled by any page I found, and winget's default for a portable package is a symlink (section 2, 3).

## 1. What a console build produces today

Read from the repository at a737305, and run.

- **Archive.** `README.md` (the table under "Why Fledge?") says a `console` app is a `.tar.gz` holding the program on macOS and Linux, and a `.zip` holding `NAME.exe` on Windows. `Fledge::Archive.pack` (`lib/fledge/archive.rb`) packs the folder under its own name with the computer's `tar`, so the archive unpacks into `NAME-PLATFORM/`. Platform names are RubyGems' (`lib/fledge/platform.rb` line 51): `arm64-darwin`, `x86_64-linux`, `aarch64-linux`, `x86_64-linux-musl`, `aarch64-linux-musl`, `x64-mingw-ucrt`, `aarch64-mingw-ucrt`. There is no Intel macOS platform.
- **Layout (run on this Mac with `examples/hello`).** `dist/Hello-arm64-darwin.tar.gz` is 19,629,691 bytes (62 MB unpacked); it unpacks to `Hello-arm64-darwin/` holding `Hello` (the launcher, a 6 MB Mach-O, ad hoc signed), `fledge.cfg`, `app/`, `bin/` (Ruby's own `ruby` and the gems' executables), `include/`, `lib/`, `libexec/`, `notices/`. On Windows, ADR 003 says the runtime "keeps RubyInstaller's `ruby.exe`, `rubyw.exe`, and the gems' wrappers", so the Windows folder holds several `.exe` files.
- **No version in the file name, no checksum file.** `fledge build` prints one path and writes nothing else beside the archive. Every manager below wants a versioned URL and a SHA-256; GitHub Releases supplies the URL, the developer computes the hash.
- **Installers.** ADR 009, section 1: "A console app gets none, and a console app that lists any fails the build ... Packages that do put a program on a `PATH` (Homebrew, `.deb`, winget) are other stories." `lib/fledge/installers.rb` line 75 returns `[]` unless the app is windowed. ADR 021 builds a `.deb` for a windowed app only, installing to `/usr/lib/PACKAGE`; its consequences list "a `/usr/bin` link" as not yet done.
- **Several programs.** With `programs:` (README, "Several programs in one app") one folder holds several launchers; "A console program takes its file's name, such as `shared-save`, the command your users type." A package that links commands must link each.

## 2. How the launcher finds its folder, and what I ran

Sources read: `runtime/launcher/unix.c` (header comment, `find_app_folder`, `build_ruby_arguments`), `darwin.c`, `linux.c`, `windows.c`.

- **macOS** (`darwin.c`): `_NSGetExecutablePath` then `realpath`. The file's comment says it handles "a link someone put on their PATH".
- **Linux** (`linux.c`): `realpath("/proc/self/exe")`. The comment: the kernel's link names the file the process runs "whatever argv[0] says, whether the launcher was found on PATH, run through a symlink, or run by a relative path." I did not run this: this computer is a Mac.
- **Windows** (`windows.c` lines 237 to 252, `own_path`): `GetModuleFileNameW(NULL, ...)`; no `GetFinalPathNameByHandle`, no reparse-point handling anywhere in the file (grep for `GetFinalPathName`, `REPARSE`, `symlink` finds nothing). I searched for whether `GetModuleFileName` returns a symlink's own path or its target; the Microsoft page (`learn.microsoft.com/windows/win32/api/libloaderapi/nf-libloaderapi-getmodulefilenamew`, via a search result) does not say. **(guess)**: it returns the path the process was started through, the link. I could not test on Windows.

Runs on this Mac, `examples/hello` built with the current build, unpacked in the scratchpad (`/private/tmp/claude-501/-Users-kerrick-Developer-fledge/d6d0d1bf-ad31-416a-b16b-83cf355da34c/scratchpad/x`, `exp1.sh`, `exp2.sh`, `exp3.sh`):

| Case | Style it imitates | Result |
| --- | --- | --- |
| Absolute symlink in a PATH folder, run as `hello 3` | Scoop-like `current` links, winget portable, Cask `binary` | Prints the Hello line, exit 3 (status forwarded) |
| `bin/hello -> ../libexec/Hello/Hello`, then `brewbin/hello -> ../cellar/hello/1.0/bin/hello` | Homebrew `bin.install_symlink libexec/"Hello"` (relative, two hops) | Works, exit 0 |
| `#!/bin/bash` script `exec`ing the launcher by full path | Homebrew `write_exec_script`, Scoop/Chocolatey-like shim scripts | Works, exit 4 |
| A parent process that `spawn`s the launcher by full path, waits, forwards the status | Scoop's `shim.exe`, Chocolatey's ShimGen exe | Works, exit 7 |
| Symlink in a folder with a space and non-ASCII letters (`bin é dir`) | Any | Works |
| `exec -a weird` through the symlink | A shim that changes `argv[0]` | Works |
| Relative symlink run from its own folder (`./hello`) | Any | Works |

| **The whole tree extracted flat into a folder named `bin`** | `ubi --extract-all` into `~/.local/bin` **(guess that it places files there; the docs I fetched do not say)** | **Fails** with the same message, exit 70 |
| Tree in `lib/hello/` (Debian `/usr/lib/PACKAGE` style) | ADR 021 | Works |

Launcher defects found. None in symlink handling on macOS. Two things to know:

1. **The "bin" and "lib" refusal is by design, but a package manager can trigger it.** `unix.c` header: "when that folder is named bin (in any case) or lib, ruby.c takes its parent as the prefix instead. The launcher refuses to run from such a folder rather than run with a standard library from somewhere else." This is a documented restriction (`unix.c` header), not a defect, but every recipe in this note must keep the tree in a folder with another name (`libexec/NAME`, `/opt/NAME`, `/usr/lib/NAME`) and link or shim only the launcher.
2. **Windows symlinks are an open risk, not a measured defect.** If `GetModuleFileNameW` returns the link, the launcher looks for `fledge.cfg` in winget's `Links` folder and fails with "this app is incomplete". Fix if so: resolve the path with `CreateFileW` + `GetFinalPathNameByHandleW` in `own_path`. The cheaper workaround in the manifest is `ArchiveBinariesDependOnPath: true` (section 3), which makes winget add the install folder to `PATH` and make no symlink.

Gatekeeper: I set `com.apple.quarantine` on a copied launcher and ran it from a shell, once with a malformed value (killed) and then with well-formed values (ran, exit 0), and `spctl --assess --type execute` printed "rejected". The malformed-value run made macOS show a "Hello Not Opened" dialog in the maintainer's own session; I should not have run it there, and I ran nothing quarantined after the coordinator said so. What this shows, and no more: a terminal run of a quarantined, ad hoc signed launcher was not blocked on this Mac, and `spctl` rejects it for the double-click path. Whether a Cask download, which Homebrew quarantines, runs from a shell without a dialog is **(guess)** the same; I did not test it.

## 3. winget

**Format.** Manifest schema 1.12.0 is current on the Learn page (`learn.microsoft.com/windows/package-manager/package/manifest`, updated 2026-09-15). The minimal singleton needs `PackageIdentifier` (`Publisher.package`), `PackageVersion`, `PackageLocale`, `Publisher`, `PackageName`, `License`, `ShortDescription`, and an `Installers` list with `Architecture`, `InstallerType`, `InstallerUrl`, `InstallerSha256`. "The singleton format is only valid for packages containing a single installer and a single locale", so a package with several architectures uses the multi-file form (version, default locale, installer). Architectures are `x86`, `x64`, `arm`, `arm64`, `neutral` (`github.com/microsoft/winget-pkgs/blob/master/doc/manifest/schema/1.10.0/installer.md`).

**A Fledge zip.** The installer page: "Zip packages are supported as of Windows Package Manager 1.5"; "NestedInstallerType is required when InstallerType is an archive type such as '.zip'"; `NestedInstallerFiles[].RelativeFilePath` is "The relative path to the installer file contained within the archive"; `PortableCommandAlias` is "The alias which is added to the PATH for calling the package from the command line" and valid only for `NestedInstallerType: portable`. So a manifest is `InstallerType: zip`, `NestedInstallerType: portable`, `RelativeFilePath: Hello-x64-mingw-ucrt\Hello.exe`, `PortableCommandAlias: hello`. **(guess)** that the whole zip extracts to the package folder, so the sibling `lib\` and `app\` stay beside the launcher; the page does not say it.

**PATH and upgrades.** `ArchiveBinariesDependOnPath`: "Specifying `true` will add the install location directly to the `PATH` environment variable", and "Specifying `false` or leaving the value unset will use the default behavior of adding a symlink to the `links` folder, if supported, or adding the install location directly to `PATH` if symlinks are not supported" (same page). The default for a Fledge app is therefore a symlink; set it `true`. Upgrade is by version: `winget upgrade` compares `PackageVersion`; `UpgradeBehavior: uninstallPrevious` exists (same page).

**Submission.** A pull request to `microsoft/winget-pkgs` under `manifests/<letter>/<Publisher>/<Package>/<version>`; "Microsoft reserves the right to refuse a submission for any reason" (`.../package/repository`, updated 2026-07-14). Automated checks: schema, URL reputation, an installer scan through "several antivirus programs", install and uninstall "for both administrators and non-administrators", a silent mode; then "manually reviewed by a moderator". "The installer comes directly from the publisher's website"; the label `Validation-Indirect-URL` says "a redirector has been used. This is not allowed". A GitHub release asset URL redirects to a CDN; whether the validator treats `github.com/.../releases/download` as direct is not stated **(guess: yes, since it is the common form)**.

**Policy for a bundled interpreter.** `learn.microsoft.com/.../windows-package-manager-policies` (document date 2021-05-22): 1.1.4 "The InstallerUrl must be the ISV's release location"; 1.2.1 bars code that downloads and runs a remote script; 1.2.3 "The Product may contain fully integrated middleware". Nothing bars a bundled language runtime. The unknown is the Defender and antivirus scan of a Windows launcher plus a Ruby runtime; the page says an app flagged as potentially unwanted "can't be added". Unknown until a submission. Signing: no page I fetched requires a signed installer for winget.

**Cost.** None stated; a GitHub account for the pull request. Tools: `wingetcreate` (`winget install wingetcreate`) writes and submits a manifest; GoReleaser's `winget` publisher generates manifests and opens the PR (`goreleaser.com/customization/winget/`).

**(1) Works today?** Yes by the docs. By hand: write the manifests, set `ArchiveBinariesDependOnPath: true`. **(2) Lacks:** a generator and the symlink question. **(3)** compatible on paper. **(4)** no money. **(5)** GoReleaser.

## 4. Chocolatey

**Format.** A `.nupkg` is a zip of a `.nuspec` (XML, NuGet's format) and a `tools` folder with `chocolateyInstall.ps1` (`docs.chocolatey.org/en-us/create/create-packages/`). "Only the nuspec is required." The page names two ways to ship a binary: embed it ("the most reliable and deterministic packages") or "download binaries from official distribution locations at runtime", with `Install-ChocolateyZipPackage` among the helpers.

**Shims.** "EXE files in the package/downloaded to package folder from chocolateyInstall.ps1 will get a link to the command line." To stop one: "create an empty file named after it with `.ignore` appended" (case sensitive). ShimGen "creates a small binary, known as a 'shim', that simply calls the executable", which "Runs the target executable where it is" (`.../features/shim/`). So the shim is an exe that starts the real path: the launcher's `GetModuleFileNameW` sees the real file. **Danger:** a Fledge Windows zip holds `ruby.exe`, `rubyw.exe`, and gem wrapper `.exe` files (ADR 003), and Chocolatey would put every one on the user's `PATH`, which hands a person a `ruby` command: against Design precedence 1. The package needs a `.ignore` for each `.exe` but the launcher. **(guess)** that the shim also needs `--shimgen-usetargetworkingdirectory`; the app does not depend on its working directory, so probably not.

**Submission.** "all new versions of packages are human reviewed prior to approval" (`.../community-repository/moderation/`); "There are also trusted packages, which only go through automated moderation review". Binaries: "If binaries are included, the maintainer must have distribution rights"; scripts "should download from the official project site". The validator's rule CPMR0060 (binaries included: exe, msi, dll, zip, gz, tar, ...) is "a Note, not a hard requirement. A package version can be approved without addressing Note comments", and wants a license file and a `VERIFICATION.txt`. Download scripts should check checksums (CPMR0027, CPMR0073). Silent install is expected. A package that downloads a zip from the developer's release and checks its SHA-256 fits. Not found in what I fetched: cost, whether signing is required, notability. The disclaimer page mentions none of them.

**Unknown until a submission:** the VirusTotal-style scan results for a Windows launcher plus Ruby; I fetched nothing on it.

**(2) Lacks:** a generator for the nuspec and the install script, and the `.ignore` files. **(4)** An account at `community.chocolatey.org` **(guess for the API key)**. **(5)** GoReleaser has a `chocolatey` section (`goreleaser.com/customization/`).

## 5. Scoop

**Format.** A JSON manifest: `version`, `description`, `homepage`, `license`, `architecture` (`32bit`, `64bit`, `arm64`) wrapping `url` and `hash`, `extract_dir`, `bin`, `checkver`, `autoupdate` (`github.com/ScoopInstaller/Scoop/wiki/App-Manifests`). "Hashes are SHA256 by default." `bin` is "A string or array of strings of programs (executables or scripts) to make available on the user's path", and an entry can alias: `["Hello-x64/Hello.exe", "hello"]` **(guess on path form; `extract_dir` strips the folder: the page says it "Extracts only one named directory from a compressed archive")**.

**Shim.** `github.com/ScoopInstaller/Shim`: `shim.exe` reads `NAME.shim`, whose `path` is resolved from the shim's folder, starts the target, "waits for the child process to finish and forwards its exit code". The target is named by full path, so the launcher sees its real folder. Only the entries in `bin` get shims, so `ruby.exe` stays off the `PATH`. Scoop installs to `C:\Users\<YOU>\scoop` without admin (`raw.githubusercontent.com/ScoopInstaller/Scoop/master/README.md`).

**Hosting.** "A bucket is a Git repository containing JSON app manifests" and users run `scoop bucket add <name> <repo-url>`; the Buckets page recommends the BucketTemplate repo, which includes GitHub Actions workflows (`.../wiki/Buckets`). Installing from a bare manifest URL is not documented on the pages I fetched **(guess: it works)**.

**Official buckets.** Main bucket criteria (`.../wiki/Criteria-for-including-apps-in-the-main-bucket`): "a reasonably well-known and widely used developer tool", "a non-GUI tool", "a fairly standard install". No rule on prebuilt binaries appeared. The Extras bucket's page returned 404.

**(1)** Works today with a manifest. **(2)** A JSON generator (about 25 lines). **(3)** nothing found. **(4)** free. **(5)** GoReleaser `scoop`.

## 6. Homebrew formula

**Official core.** `docs.brew.sh/Acceptable-Formulae` and the shared policy (`raw.githubusercontent.com/Homebrew/brew/HEAD/docs/Package-Acceptance-Policy.md`, `last_review_date: 2026-07-18`): "A formula in `homebrew/core` must be open source under a licence compatible with the DFSG. It must either build from source or install portable, platform-independent output such as Java bytecode. Proprietary or platform-specific binary-only software belongs in a cask." A Fledge app is a platform-specific prebuilt tree, so core refuses it even for an open source app. Notability: "at least 30 forks, 30 watchers or 75 stars", and 90/90/225 for a self-submission. `livecheck` is required.

**Own tap.** "Software that does not meet the official criteria can generally be maintained in a third-party tap" (same policy, "Scope and third-party taps"). The tap guide (`docs.brew.sh/How-to-Create-and-Maintain-a-Tap`): a repo named `homebrew-NAME`, formulae in `Formula/`, `brew tap-new` scaffolds it, `brew install user/repository/formula` taps and installs; "Non-official taps require explicit trust. Use `brew trust --formula user/repository/foo` ... or `brew trust --tap`." That trust step costs the user one more command; how it appears is **(guess)**, since I did not run `brew`. A formula may use `url`/`sha256` and `bin.install_symlink libexec/"Hello"`: "`libexec` is reserved for private use by the formula and therefore is not symlinked into `HOMEBREW_PREFIX`", and "The symlinks created by `install_symlink` are guaranteed to be relative" (`docs.brew.sh/Formula-Cookbook`). The Cookbook does not show per-platform `url`s; it says inside `def install` use `OS.mac?` and `Hardware::CPU.arm?`. I tested exactly this layout by hand (section 2).

**Unknown: relocation.** Whether `brew install` rewrites Mach-O load commands in a non-bottle keg (and so invalidates the launcher's ad hoc signature), or marks the files in some way the launcher dislikes, is not covered by any page I fetched. Test: install from a local tap on a spare Mac, which I did not do because `brew install` writes outside the worktree.

**Cost.** Free; a GitHub repository. `brew` runs on Linux too; the Linux launcher is glibc 2.39 or musl **(guess for Homebrew's Linux baseline)**.

**(2) Lacks:** a formula generator that takes the release URL and hashes. **(5)** cargo-dist's `homebrew` installer "fetches and installs executables" (`axodotdev.github.io/cargo-dist/book/installers/index.html`); GoReleaser.

## 7. Homebrew cask

`docs.brew.sh/Acceptable-Casks` (`last_review_date: 2026-08-25`): "Casks distribute applications and other pre-built files published by the upstream developer. Open-source command-line-only software normally belongs in `homebrew/core` as a formula built from source." So an open source CLI is steered to core, which refuses a prebuilt tree: "A rejection from `homebrew/core` does not by itself make the software eligible for `homebrew/cask`." The cask rules add: "On macOS, apps, installers and other executable artefacts that Gatekeeper can assess must pass Homebrew's Gatekeeper checks and must not require System Integrity Protection or Gatekeeper to be disabled", and "Homebrew applies macOS quarantine attributes to Cask downloads" and "deprecates, disables and eventually removes casks that fail Gatekeeper checks" (`Homebrew-Security-and-Supply-Chain.md`). Fledge does not notarize (README, "Signing"), and `spctl --assess` rejected the ad hoc launcher here. So an official cask needs Plan 002's notarization, which needs Apple's US$99 a year. A cask in the developer's own tap has no review. The cask's `binary` stanza: "Relative path to a Binary that should be linked into the `$(brew --prefix)/bin` folder on installation" (`Cask-Cookbook.md`): a symlink, which the launcher survives on macOS. Notability exceptions mention "when the repository is used only to host its binaries".

**Cost.** Own tap free. Official cask free but needs notarization.

## 8. apt, pacman, dnf: the Linux packages

**A console `.deb`.** ADR 021 builds one with `dpkg-deb --build --root-owner-group` for windowed apps, installs to `/usr/lib/PACKAGE`, depends on `libc6 (>= 2.39)`, and lists "a `/usr/bin` link" as not done. A console `.deb` is the same builder with one more entry: `/usr/bin/NAME -> ../lib/PACKAGE/NAME`, a relative symlink, which the launcher follows (`linux.c`, from the source; not run). Debian's policy 9.1.1 allows `/usr/lib/PACKAGE`. Hosting: the app-stores note cites `wiki.debian.org/DebianRepository/UseThirdParty` and `/Setup` for `reprepro` and `aptly`, and the official archives' refusal (DFSG source requirement, Policy 4.13, PPAs). I did not refetch them.

**Arch.** The Arch Wiki, `man.archlinux.org` partly, and `aur.archlinux.org` returned an access-denied page to the fetch tool (Anubis), so most of this is second-hand.
- Man pages that loaded: `repo-add(8)`: `repo-add [options] <path-to-db> <package> ...`, `--sign` "Generate a PGP signature file using GnuPG", the database "is a tar file, optionally compressed". `pacman.conf(5)`: a section such as `[core]` with `Server`: "A full URL to a location where the database, packages, and signatures (if available) for this repository can be found", and `SigLevel` (`man.archlinux.org/man/repo-add.8.en`, `.../pacman.conf.5.en`). `PKGBUILD(5)`: "Additional architecture-specific sources can be added by appending an underscore and the architecture name"; "There must be a corresponding integrity array with checksums"; `arch=('any')` for architecture-neutral packages only (`.../PKGBUILD.5.en`).
- **(second-hand)** AUR rules from a search summary of the Arch Wiki "AUR submission guidelines": "Packages that use prebuilt deliverables, when the sources are available, must use the -bin suffix"; "Submitted PKGBUILDs must not build applications already in any of the official binary repositories".
- A `-bin` PKGBUILD for a Fledge app: `source_x86_64=("$url/Hello-x86_64-linux.tar.gz")`, `sha256sums_x86_64=(...)`, `package()` copying the tree to `$pkgdir/opt/hello` and linking `/usr/bin/hello` **(guess; written from the pieces above)**. Arch packages are built by the user's machine with `makepkg`, so the user needs only the AUR helper. A developer-hosted pacman repository takes an Arch package; nfpm writes the `archlinux` format.

**Fedora, dnf.**
- Copr: "Copr is a build system available for everybody. You provide the src.rpm and Copr provides a yum repository"; accounts need a Fedora Account System login; builds from SRPM URL, upload, SCM, RubyGems, PyPI; `dnf copr enable` (`docs.copr.fedorainfracloud.org/user_documentation.html`). "Packages don't have to follow Fedora Packaging Guidelines"; licenses must be on Fedora's acceptable list; "Packages that download proprietary content at build time without including it in the RPMs are not allowed" pending a Fedora Legal ruling; the page "doesn't specifically address repackaging upstream binaries". Cost: not stated, free software. A spec that copies a prebuilt tarball in `%install` is what the RPM Packaging Guide says is fine: "If a pre-compiled binary needs to be packaged, you can also use this method since the binary would also just be a file" (`rpm-packaging-guide.github.io`). So Copr is an **unknown until a submission**.
- Fedora archive: **(second-hand)** from a search summary of `docs.fedoraproject.org/packaging-guidelines/what-can-be-packaged/` (the fetch tool got an access-denied page): "All program binaries and program libraries included in Fedora packages must be built from the source code that is included in the source package." Refused.
- A developer-hosted yum repository takes an `.rpm`; Fledge writes none. ADR 021: "Not yet: `.rpm` (rpmbuild, the same shape)". I did not fetch `createrepo_c` or `.repo` file docs **(guess)**.
- nfpm (`nfpm.goreleaser.com/docs/configuration/`) turns one YAML into `deb`, `rpm`, `apk`, `archlinux`, `ipk`, with `contents` entries including `type: symlink`, `arch`, and "The package is signed if a key_file is set". It is a Go tool that runs on any computer; AGENTS.md says to prefer a maintained tool over writing a format, and ADR 021 already prefers `dpkg-deb`; the ADR for a `.rpm` has to weigh `rpmbuild` (Fedora, Debian, and macOS have it) against nfpm.

## 9. Nix

- `nixpkgs`: "Source-available software should be built from source where possible"; "Binary blobs risk supply chain attacks and vendored outdated libraries"; repackaged binary formats "should usually set `meta.sourceProvenance` to `lib.sourceTypes.binaryNativeCode`"; "Upstream developers submitting their own projects is often a sign the package isn't yet widely used. Consider waiting for another user to submit it" (`raw.githubusercontent.com/NixOS/nixpkgs/master/pkgs/README.md`). So a binary package is allowed with a mark; self-submission is discouraged.
- NixOS: "running a downloaded binary ... will almost never work. This is due to hard-coded paths in the executable"; the loader at `/lib64/ld-linux-x86-64.so.2` "is in general not available under NixOS"; `autoPatchelfHook` is "the preferred way to package binaries" (`wiki.nixos.org/wiki/Packaging/Binaries`). A Fledge Linux runtime is glibc-linked and its launcher links `libcrypt` from `$ORIGIN/lib` through `DT_RPATH` (`unix.c`). **(guess)** `autoPatchelfHook` rewrites the interpreter and RPATH, the launcher's `/proc/self/exe` lookup survives that, and `bin/ruby` and the extension `.so` files need the same hook.
- A flake in the developer's own repository: "A flake is a filesystem tree that contains a file named `flake.nix` in the root directory", referenced as `github:owner/repo` (`nix.dev/manual/nix/stable/command-ref/new-cli/nix3-flake.html`). Free. Test: a NixOS container in CI **(guess)**.
- macOS: Nix works there; the launcher is a Mach-O, not touched by `autoPatchelfHook`; **(guess)** it runs.

## 12. `mise`, `aqua`, `ubi`: GitHub release installers

- **mise** (`mise.jdx.dev/dev-tools/backends/github.html`): picks the asset by scoring OS, CPU, and C library; `asset_pattern` overrides; `bin_path` "Names the directory, relative to the install directory, that holds the executables" and "When `bin_path` is unset, mise adds `bin/` or the subdirectory containing the executable to `PATH`". If the archive has a single top-level directory, mise strips it. So the extracted tree is kept whole and its folder goes on `PATH`: the launcher runs in place. Note `Hello-arm64-darwin/bin` exists inside the tree and holds `ruby` and the gems' executables; the launcher is at the top, so the automatic "subdirectory containing the executable" rule should find `Hello`; set `bin_path` to be safe **(guess)**. Checks GitHub attestations when present; `checksum` pins by hand. Whether the scoring recognizes `x64-mingw-ucrt` as Windows is **(guess)**: unknown; `asset_pattern` per platform avoids it.
- **ubi** (`github.com/houseabsolute/ubi`): filters assets by OS and CPU, finds "an exact match on the project name" inside the archive and extracts that file; "`--extract-all`: extract all files from the archive. If all contents share a top-level directory, that directory will be removed". Without `--extract-all` it takes one file, and the launcher alone cannot run (it is not in a runtime folder). With `--extract-all` into the install directory, the tree lands flat in whatever folder the user names; if that folder is `bin`, the launcher refuses (section 2).
- **aqua** (`aquaproj.github.io/docs/reference/registry-config/`): a `github_release` package has `asset`, `format`, `replacements`, `files` ("The list of executable files"), `supported_envs`, `checksum`, `overrides`. The page does not cover how `files[].src` finds a file inside an archive or the registry's PR process; I did not read them. aqua installs an executable and runs it through its proxy; whether it keeps sibling files is **unknown**.
- A rule they all share: the asset name should carry `darwin`/`linux`/`windows` and `arm64`/`amd64`-style words. Fledge's names use RubyGems' (`arm64-darwin`, `x86_64-linux`, `x64-mingw-ucrt`), which `replacements` or `asset_pattern` can map **(guess for mise's auto-detect)**.

## 13. `gem install` and RubyGems.org as a channel

`guides.rubygems.org/specification-reference/`: "Executables included may only be ruby scripts, not scripts for other languages or compiled binaries"; `platform` can be `Gem::Platform::CURRENT`; the page states no size limit. A gem per platform (`hello-1.0-arm64-darwin.gem`) could hold the whole runtime tree with a Ruby executable that `exec`s the launcher; `guides.rubygems.org/gems-with-extensions/` shows platform gems being built (`my_malloc-1.0-x86_64-linux.gem`). The user must already have Ruby and RubyGems, which makes this a channel for developers, not for the people Fledge serves (Design precedence 1), and AGENTS.md bars agents from `gem push`. Size limits and how `gem install` picks among platform gems are not on the pages I fetched. Not recommended.

## 14. Prior art

- **GoReleaser** is the nearest: one config produces and publishes `homebrew_casks`, `winget`, `scoop`, `aur`, `nix` (NUR), `nfpm` (deb, rpm, apk), `snapcraft`, `chocolatey`, `flatpak`, `msi`, `nsis`, `pkg`, `dmg` (`goreleaser.com/customization/`). Its winget publisher opens a pull request from a fork and needs a token. Its archive-based winget use is a paid feature, quoted: `use: archive` "only available in GoReleaser Pro" (`goreleaser.com/customization/winget/`).

- **python-build-standalone, PyInstaller one-folder apps, Briefcase**: the app-stores note and ADR 009 cite them for installers; I found no page where one of them is submitted to winget, Scoop, or Homebrew **(guess: PyInstaller apps are published this way by their authors)**.

## 15. Proposed Plan 003 stories

Proposals; `plan/003.md` is unchanged. Ordered by cost, then value.

1. **A symlink delivery check on every platform** (1.0, small). Add a step to the existing Delivery scripts: put a symlink to the launcher in a `PATH` folder and run the app through it, plus (macOS and Linux) a relative two-hop link and a `#!/bin/sh` shim. On Windows also make a symlink and a junction. This proves or breaks the Windows `GetModuleFileNameW` question, which every Windows manager here depends on. If it breaks, resolve the path in `own_path` with `GetFinalPathNameByHandleW`. Value: protects winget, any user-made link, and Scoop's `current` junction. Cost: about 30 lines of shell and PowerShell, 10 lines of C if needed.
2. **A checksum list beside each archive** (1.0, small). `fledge build` writes `NAME-SHA256SUMS` (or prints the hash) for each archive. Every manager needs one; today the developer runs `shasum` by hand. Cost: a few lines and a test; one CHANGELOG line.
3. **A README section, "Publishing a console app"** (1.0, no code). GitHub Release, the asset names, a hand-written Scoop bucket, Homebrew tap formula, winget manifest (with `ArchiveBinariesDependOnPath: true`), and the "keep the tree out of a folder named `bin`" rule. Mark the official repositories that refuse (Homebrew core, Debian, Fedora, Flathub). Cost: one paragraph per manager; each recipe is first tested by hand. Reads both README files in full first (AGENTS.md).
4. **`fledge publish` text files** (after 1.0, medium, in this order): Scoop JSON, Homebrew formula (tap), winget manifests, Chocolatey nuspec with `.ignore` files, AUR PKGBUILD. Input: `fledge.yml`, a release URL, and the checksum list from story 2. Each is a template, 30 to 100 lines, and a Delivery check on that platform's own tool (`scoop install` from a local bucket, `brew install --formula` from a local tap, `winget install --manifest`, `choco install` from a local folder, `makepkg` in an Arch container). Not one needs money or an account to test. Start with Scoop and Homebrew: no review and no signing.
5. **Console `.deb` with a `/usr/bin` link, then `.rpm`** (after 1.0, medium). Extends `Fledge::Deb` (ADR 021) and ADR 009's rule that a console app gets no installer, which needs a decision: a console app may now list `deb` (and `rpm`). Docs: hosting with `reprepro`/`aptly` and `createrepo_c`. An ADR weighs `rpmbuild` against nfpm.
6. **A Nix flake template, tested on NixOS** (after 1.0, small; value unknown).
7. **Notarization (Plan 002) gains a reason**: an official Homebrew cask requires Gatekeeper to pass, as does the double-click path. This costs US$99 a year, so it is a question for the maintainer (kind 2). No default is needed: the own tap works without it.
8. **Record in an ADR** that Fledge does not target `homebrew/core`, Debian, Fedora, Flathub, or (second-hand) nixpkgs and Arch's official repositories, and why (each requires a source build), alongside the app-stores note's conclusion.
