# ADR 104: On a phone, an app's Ruby drives the platform's widgets from the main thread, with only what Ruby gives every program

## Context and Problem Statement

A Ruby developer who knows no other language should ship a phone app whose screen is made of the platform's widgets, UIKit's on iOS and Android's views on Android, and follows each platform's interface guidelines (#100). The developer writes no Objective-C, Swift, Java, or Kotlin (README).

Two facts bound the answer. A program may touch UIKit's objects, and an activity's views, only from the main thread (`ViewRootImpl.checkThread`). CRuby runs Ruby only on threads it made: a callback that asks for Ruby's lock from any other thread ends the process (`thread.c`, lines 2320 to 2335 at v4.1.0-preview1), and no public API makes a foreign thread a Ruby thread (`include/ruby/thread.h`, lines 111 to 114).

Each phone runtime carried a bridge of Fledge's for an app's Ruby to call, `Fledge::ObjC` on iOS and `Fledge::JNI` on Android. No Ruby has either under `ruby main.rb`, so a program that calls one runs only under Fledge (#130, #131). Under `ruby main.rb`, `Thread.main` is the thread the process started on; on a phone, Fledge's hosts gave Ruby the main thread only when `fledge.yml` says `kind: windowed`, and ran every other program's Ruby on a second thread, beside a screen of Fledge's that shows the program's output (#137). What does an app's Ruby reach the widgets with, what does Fledge supply for it, and on which thread does a program's Ruby run?

## Decision Drivers

- The developer writes only Ruby, and the platform's widgets draw the screen as its guidelines describe them (#100).
- The app's Ruby runs as under `ruby main.rb` (AGENTS.md, design precedence 2; `decisions.md`, decisions 9 and 10, and 2026-11-02, later again). A program that runs only under Fledge, or whose `Thread.main` is not the process's main thread, meets a difference, and a difference that could be closed is a bug (`decisions.md`, 2026-11-12).
- UIKit and Android's views call back on the main thread, where CRuby can answer only if Ruby already runs there.
- iOS on an iPhone ends a process that runs code from a page made executable at run time, and the Simulator does not (`doc/contributors/research/2026-11-25-pure-ruby-uikit.md`, section 1).
- Code is a liability (`decisions.md`, 2026-10-28): use what Ruby already bundles before writing C.
- A widget toolkit is a framework's work, not Fledge's.
- Prior art: rubicon-objc and Toga, rubicon-java, pyjnius, Chaquopy, RubyMotion, NativeScript.

## Considered Options

How Ruby reaches the widgets:

1. The app's Ruby calls the Objective-C runtime and JNI through Fiddle, a gem Ruby bundles, with nothing of Fledge's between: the app, or a gem its developer chooses, carries the bridging it uses.
2. The same, with Fledge's Android host handing Ruby what Android gives only to Java or compiled code: the Activity (`FledgeRuby.activity()`) and the Java VM's pointer (`fledge_ruby_java_vm`, or `JNI_GetCreatedJavaVMs` exported from `libfledgeruby.so`).
3. A bridge of Fledge's in each runtime, in Ruby over Fiddle (`Fledge::ObjC`; `Fledge::JNI` with the Java class `org.setdef.fledge.RubyProxy`), which Fledge's agents built and landed on `trunk`.
4. The same bridges as C extensions in each runtime.
5. A widget layer of Fledge's over either bridge, one screen for both phones.

Which thread a program's Ruby runs on:

1. The process's main thread, for every program, whatever its `kind`.
2. The main thread for an app of `kind: windowed`, and a second thread, with Fledge's output screen, for every other.
3. A second thread for every program, with every call handed to the main thread and every callback handed back.

## Decision Outcome

Chosen: the first option of each list, because each is how Ruby behaves under `ruby main.rb`. A script there reaches the Objective-C runtime and JNI through Fiddle with nothing Fledge alone has, and its `Thread.main` is the thread the process started on. What an app needs beyond Ruby is the app's code or a gem's, and where pure Ruby falls short on a phone, the fix is to make the runtime's Ruby behave as under `ruby main.rb`, never a helper of Fledge's. A host that is not Fledge's, such as SDL's, runs Ruby where its framework does.

The bridges in the runtimes (option 3) were built, and lost on precedence 2: no Ruby has them under `ruby main.rb`, and the research of 2026-11-25 found that an app's Ruby does without them what they did, on an iPhone and on Android. A handover from the host (option 2) lost for the same reason, since it is a library of Fledge's by another name (#138). C extensions (option 4) lost as option 3 did, and add C for both phones that Fiddle already does, with a second libffi on iOS beside Fiddle's. A widget layer (option 5) is a framework's work, above Fledge, as Toga is above rubicon-objc and rubicon-java. The main thread for `kind: windowed` alone lost on precedence 2: a program on the second thread can read that its `Thread.main` is not the main thread (`pthread_main_np()` is 0 on iOS, and on Android `Thread.main.native_thread_id` is not `Process.pid`), can never answer a widget's callback, and gets an output screen that no Ruby gives a program (#137). Ruby on a second thread with every call handed across lost on a rendezvous in C on both phones, a thread switch per call, and a deadlock wherever the two waits cross; no bridge of the prior art works so.

The decision lands in three stages:

1. **iOS, done.** Basket drives UIKit through `examples/basket/lib/basket/objc.rb`, Basket's code: 400 lines of Ruby over Fiddle, besides comments and blank lines, and the iOS runtime carries no bridge (4ffc058f removed `Fledge::ObjC`). It came first because its research, on an iPhone, settled every question in #130, and Android's is the harder half (#131).
2. **Android, in progress under #131.** Basket's Ruby takes the route the Android note found: it reaches the Java VM, reaches its Activity through four non-SDK members of `android.app.ActivityThread`, and takes Java's calls through a class it writes in memory and `java.lang.reflect.Proxy`. `Fledge::JNI`, `RubyProxy`, `fledge_ruby_java_vm`, and `FledgeRuby.activity()` leave the runtime. Until that lands, Android's runtime carries them and Basket calls `Fledge::JNI`.
3. **Every program on the main thread, after both.** Fledge's hosts run every phone program's Ruby on the main thread, the output screen goes, and a phone's host no longer chooses a thread by `kind`. Until then, only an app of `kind: windowed` has the main thread. It waits for the first two stages because neither needs it: Basket's `fledge.yml` says `kind: windowed`, so its Ruby has the main thread already (#137).

How each phone's Ruby reaches its widgets, and the threads, citations, and limits, are in `doc/contributors/design/phone-widgets.md`.

Confidence: none was recorded. What the evidence shows: on an iPhone 12 mini under iOS 27.2.1, a probe that requires only `fiddle` made Objective-C classes whose methods are Fiddle closures, which ran from libffi's trampoline table with no page both writable and executable, and Basket, on the bridge the runtime then carried, itself Ruby over Fiddle, passed the mobile parity check's UI test, which adds an item and deletes it (`doc/contributors/research/2026-11-25-pure-ruby-uikit.md`, sections 1 and 4). Basket on `lib/basket/objc.rb` runs in CI's Simulator on an iPhone and an iPad; no run of it on a device is recorded. On Android, a probe with Fiddle alone, and nothing of Fledge's, reached the Java VM, the Activity, calls from Java, and the main loop on an arm64 phone of API 34 and on emulators of API 26, 28, 29, 30, and 36 (`doc/contributors/research/2026-11-25-pure-ruby-android-views.md`); Basket's screen on that route is stage 2's to prove. On an iPhone, iOS's launch watchdog ended a program that held the main thread for 20 seconds without calling `UIApplicationMain` (the iOS note, section 2). No recorded comparison says the chosen route is faster or more reliable than the bridges in the runtimes: the choice rests on precedence 2. Unproven: App Review of such an app (`doc/contributors/account-tests.md`, IOS-6) and Google Play's review (AND-2); whether a later Android restricts the non-SDK members Basket uses; the watchdog anywhere but a device launch without a debugger, such as the Simulator or Xcode's Run; and whether Fiddle's cost per call shows on a device's scrolling list.

### Consequences

- Good, because an app's Ruby is a Ruby program like any other: Basket's `objc.rb` runs under `ruby` on a Mac, and its tests run there as any Ruby test does.
- Good, because a phone runtime holds nothing for an app to call, so Fledge maintains no bridge, no Java class, and no C that only an app's Ruby uses.
- Good, because a developer reads Basket's bridging and copies or changes it, and a gem can offer one, as rubicon-objc offers one to Toga.
- Bad, because each app that draws widgets carries the bridging it uses, or a gem's: 400 lines of Ruby for Basket on iOS, besides comments and blank lines, and by the Android note's estimate about 325 on Android, and Fledge's tests cover only Basket's.
- Bad, because on Android Basket reaches its Activity through members Android marks "unsupported", and on API 29 and 30 its Java VM by reading `/proc/self/maps`; a later Android that blocks them leaves Basket without a screen, and nothing in Fledge can fix it.
- Bad, because a program that holds the main thread freezes its screen, as a native app does: iOS's watchdog ends one that has not called `UIApplicationMain` within 20 seconds of launch, Android reports one as not responding once an input event has waited 5 seconds, and, once the output screen goes, a program that draws nothing shows nothing while it runs.
- Bad, because on an iPhone a closure is safe only while the runtime's libffi takes its trampoline table and fiddle is built with `ffi_closure_alloc`: a closure in a runtime built otherwise falls back to a page a device ends the process for, and only a device, never the Simulator, shows it, so whoever changes the runtime's libffi or fiddle relies on `test/integration/mobile_closures_test.rb`.
- Bad, because every call crosses Fiddle, which is slower than compiled glue.
- Bad, because a Ruby exception in a callback cannot unwind through the platform's frames: the app's bridging prints it, and `exit` there skips `at_exit`.
- Bad, because the developer of an app with a `Gemfile` adds `fiddle`, a bundled gem, to it, as for any program under `bundle exec` that uses Fiddle.
- Bad, because on Android a program that keeps the main thread calls `Looper.loop()` inside the loop that started it, for which Android logged a warning once per launch on API 30, 34, and 36.

### Confirmation

`test/integration/mobile_closures_test.rb` fails unless the iOS runtime's device slice of `fiddle.bundle` defines `_ffi_closure_alloc`. `test/basket_bridge_test.rb` runs Basket's bridge tests (`examples/basket/test/objc_test.rb`) against a Mac's Objective-C runtime among Fledge's unit tests. CI's mobile parity jobs (`tasks/mobile_parity.rb`) build and run Basket in the iOS Simulator and on Android emulators, and fail unless it logs `Basket shows N items`, then `Basket added Milk` and `Basket removed Milk` as the check adds and removes an item; the same jobs fail on any difference between the parity probe and `ruby main.rb` that `Parity::MOBILE_JUSTIFIED` does not justify. Nothing automated fails when a library of Fledge's for an app to call returns to a runtime, or when a program's `Thread.main` is not the main thread: only a review against design precedence 2 catches either.
