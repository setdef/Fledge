# ADR 049: Installers Use NSIS's and AppImage's Own Releases, With the Sources Their Licenses Ask For

## Context and Problem Statement

Two installers carry code of their maker's into every app that ships in them. Every NSIS setup program holds NSIS's stub and its compressor's decoder. Every AppImage starts with AppImage's runtime, which mounts or extracts it, and AppImage's own build links libfuse 3, LGPL-2.1, into that runtime. NSIS's LZMA module, its default compressor, is under the Common Public License 1.0, whose section 3 asks that a program distributed as object code say where its source is.

Fledge had read decision 8 as forbidding both, and built around them: NSIS with its zlib module and a makensis Fledge's CI built for every computer, and AppImage's runtime built by Fledge with no libfuse, a C file of its own that loaded the computer's libfuse, and a patch that extracted the AppImage where it could not mount. The maintainer's replies on the LGPL (`decisions.md`, 2026-10-26, later) ask less: "Source offer for... the app? Or the LGPL'ed library? Former won't be liked, latter is fine and normal." On 2026-10-28 (`decisions.md`), with "Code is a liability and we should _not_ have 4k+ lines of things we could use existing tools for.", the maintainer accepted the orchestrating agent's recommendation to switch NSIS to LZMA with NSIS's source published, and to use the upstream AppImage runtime with its LGPL sources published. Which builds of NSIS and AppImage's runtime should installers use?

## Decision Drivers

- No app's own source or object files are ever asked of its developer (decision 8 and the LGPL replies).
- A library's source published beside the runtime is "fine and normal".
- Code is a liability: no builds or patches of Fledge's own where a maintained release does the work.
- An AppImage behaves as every AppImage does, so a person who has met one knows it.

## Considered Options

1. NSIS's own release, compressing with LZMA, and AppImage's released runtime, each pinned by SHA-256 and carried in the runtime's `tools` folder, with their sources and libfuse's published in every release's source bundles.
2. Fledge's own builds that avoid them: NSIS with zlib and a makensis Fledge builds for each computer; AppImage's runtime built without libfuse, with Fledge's own loader of the computer's libfuse and a patch to extract itself where it cannot mount.

## Decision Outcome

Chosen: option 1, by the maintainer's acceptance, because it publishes the sources the licenses ask for and asks nothing of the app. libfuse is linked into AppImage's runtime, an MIT program that is neither the developer's app nor Fledge's launcher; publishing the runtime's source with libfuse's is what LGPL-2.1, section 6(a), asks of a work linked with the library, and the app inside the AppImage only runs as its child. NSIS's LZMA asks only that its source be available, which Fledge publishes.

An AppImage is made as appimagetool makes one, with `mksquashfs` and the released runtime. appimagetool itself is not run: it is an AppImage that needs FUSE to run, downloads its runtime unless told otherwise, and does nothing more for Fledge than run `mksquashfs` and validate the desktop entry, which Delivery does with `desktop-file-validate`.

Confidence: high. The license audit accounts for both in every runtime build, and Delivery runs both installers on fresh computers.

### Consequences

- Good, because Fledge maintains no build of makensis or of AppImage's runtime, no loader of libfuse, and no patch, and installers are compressed with NSIS's default, as Tauri's are.
- Good, because each Windows release's source bundle holds NSIS's source, each Linux release's holds AppImage's runtime at its commit with its build scripts and libfuse's release, and every app's `notices/NOTICES.txt` names them and says where their source is.
- Bad, because the license policy grows two rules: an LGPL library may ship linked into another component that is not Fledge's, with both sources published; and a license that asks only that its source be published (CPL-1.0) is allowed when Fledge publishes it. Fledge's launcher may still never hold LGPL code.
- Bad, because an AppImage on a computer without FUSE says so and runs only when asked to extract itself (`APPIMAGE_EXTRACT_AND_RUN=1` or `--appimage-extract-and-run`), where Fledge's build extracted itself unasked.
- Neutral, because `mksquashfs` is GPL-2.0, which reaches no app: it runs on the developer's computer, and none of its code is in the AppImage.

### Confirmation

`tasks/license_audit/policy.rb` and `runtime/licenses.yml` account for NSIS and AppImage's runtime, and for each library AppImage's build links in, in every runtime build; the audit refuses a runtime that holds anything they do not. `.github/scripts/deliver-installer.ps1` installs and uninstalls a setup program on fresh Windows runners, and `.github/scripts/deliver-appimage.sh` runs an AppImage with FUSE, and without it, extracted on request.
