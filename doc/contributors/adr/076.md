# ADR 076: A phone app's $stdout writes through as a terminal's, with $stdout.sync false

## Context and Problem Statement

A phone app's standard output reaches the system log through a pipe (ADR 059). Ruby buffers standard output to a pipe until the buffer fills or the program ends (`io.c`, lines 1941 to 1954 at Ruby 4.1.0-preview1), so a developer watching the log would see nothing until then. ADR 059 put `$stdout` in sync mode on a phone, so each line arrives as printed. That makes `$stdout.sync` true on a phone and false under `ruby main.rb`, a difference any app can read. The maintainer, 2026-11-12 (`decisions.md`): a difference is accepted only when inherent to where the app ships or truly forbidden by the platform; "Every difference, every lack of parity, is a knife in Fledge's back." Sync mode is neither. How does a line reach the log as it is printed, with nothing an app can read differing from `ruby main.rb`?

## Decision Drivers

- A line reaches the log when it is printed, as it reaches a terminal (ADR 059).
- `$stdout.sync` is false, as under `ruby main.rb`, and `$stdout.tty?` is false, since a phone has no terminal and a library must not send escape codes into the log (ADR 059).
- Nothing the platform forbids is in the way.

## Considered Options

1. Give `$stdout`'s IO the `FMODE_TTY` flag Ruby gives an IO it opens on a terminal, without a terminal.
2. Keep `$stdout.sync = true` (ADR 059's option 1).
3. Make descriptor 1 a pseudo-terminal.
4. Leave standard output buffered.

## Decision Outcome

Chosen: option 1, because Ruby already writes a terminal's output line by line through that flag (`io.c`, lines 1945, 2326, and 5334), and the flag touches nothing an app can read: `$stdout.sync` stays false, and `$stdout.tty?` asks `isatty` of the descriptor (line 5547), so it stays false too. The runtime sets it once, before the program writes (`write_lines_as_printed`). ADR 059 set this option aside only for `include/ruby/io.h`'s comment on the field, "You cannot change this" (lines 188 to 191), which says that Ruby sets the flag as it opens an IO, not that anything forbids setting it after.

Option 2 leaves a difference any app can read. Option 3 makes `$stdout.tty?` true, so libraries color the log. Option 4 hides an app's log until it ends.

Confidence: high. The mobile parity check runs on CI's iPhone and iPad Simulators and both Android emulators with `$stdout.sync` compared exactly and no justification for it, and a line printed before a sleep reaches `os_log` during it on a Mac.

### Consequences

- Good, because a phone app's `$stdout.sync` and `$stdout.tty?` are what `ruby main.rb` gives with its output to a pipe, and each line still reaches the log as printed.
- Bad, because `$stdout` writes through on a phone where `ruby main.rb` with its output to a pipe buffers, which `Parity::MOBILE_JUSTIFIED` justifies as the fact "$stdout writes through".
- Bad, because Ruby's header deprecates writing the field, so the runtime sets it under a compiler pragma, and a later Ruby that moves the flag needs the runtime changed with it.

### Confirmation

`test/integration/mobile_output_test.rb` checks that a line printed before a sleep reaches the log during it, and the parity probe's fact "$stdout writes through" is measured from Ruby's own warning for a buffered IO.

## More Information

- This supersedes ADR 059's choice of sync mode; ADR 059's forwarding of descriptors 1 and 2 stands.
