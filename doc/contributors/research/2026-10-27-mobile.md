# Shipping embedded CRuby on iOS/iPadOS and Android: store rules and JIT

Research done for Lota on 2026-10-27. Every source was fetched that day. Quotes are verbatim. Anything not confirmed from a primary source is marked as such.

## Short answer

| Channel | Policy | JIT |
|---|---|---|
| App Store / TestFlight / Ad Hoc | Allowed with conditions | Interpreter only |
| EU / Japan alternative distribution | Same DPLA §3.3.1(B) applies | Interpreter only (browser-engine JIT not available to games) |
| iOS development / sideloaded builds | Not a distribution channel | Debugger-attach JIT only: fragile, and YJIT's mprotect approach still incompatible |
| Google Play | Allowed with conditions (bundle the Ruby; target API 36; 16 KB alignment by 2027-02-01) | The OS allows it; stock CRuby builds no JIT for Android; forcing YJIT is untested |

Apple's App Review Guidelines don't mention JIT at all; they regulate downloaded code. The barrier is technical: iOS code signing gives a third-party app no executable memory, and the only documented JIT path, BrowserEngineKit, is limited to alternative browser engines in the EU (and Japan, per guideline 2.5.6).

## 1. Apple App Store: allowed with conditions

Bundled Ruby source is fine. Downloaded code is restricted.

**App Review Guidelines**, "Last Updated: October 16, 2026" (https://developer.apple.com/app-store/review/guidelines/):
- **2.5.2:** "Apps should be self-contained in their bundles, and may not read or write data outside the designated container area, nor may they download, install, or execute code which introduces or changes features or functionality of the app, including other apps." The only exception is for educational coding apps.
- **4.7:** "Apps may offer certain software that is not embedded in the binary, specifically HTML5 and JavaScript mini apps and mini games, streaming games, chatbots, and plug-ins". Ruby is not on that list.
- **2.5.6:** "You may apply for an entitlement to use an alternative web browser engine … for the EU and Japan."
- **2.5.19:** "Don't include any hidden, dormant, or undocumented features in your app".
- **4.2.6:** "Apps created from a commercialized template or app generation service will be rejected unless they are submitted directly by the provider of the app's content". A packaging tool must not submit apps on developers' behalf.
- The full text contains no rule naming "JIT" and none naming "interpreter".

**Apple Developer Program License Agreement**, §3.3.1(B) "Executable Code" (https://developer.apple.com/support/terms/apple-developer-program-license-agreement/):
- "an Application may not download or install executable code. Interpreted code may be downloaded to an Application but only so long as such code: (a) does not change the primary purpose of the Application … (b) does not bypass signing, sandbox, or other security features of the OS; and (c) for Applications distributed on the App Store, does not create a store or storefront for other Applications."
- §3.3 binds "Any Application that will be submitted to the App Store, Custom App Distribution, or TestFlight, or that will be distributed through Ad Hoc distribution".
- Attachment 14 (EU, "effective as of October 1, 2026"): apps on alternative marketplaces or distributed from websites "must follow the terms of this Attachment and the Agreement, including the Notarization Review Guidelines".

**Precedent:**
- Balatro, a LÖVE/Lua game: https://apps.apple.com/us/app/balatro/id6502453075 (released 2024-09-26, Playstack). LuaJIT's `src/lj_arch.h` (v2.1) disables its JIT on iOS at compile time: `#if LJ_TARGET_IOS || LJ_TARGET_CONSOLE` / `/* Runtime code generation is restricted on iOS. Complain to Apple, not me. */` / `#define LJ_OS_NOJIT 1`.
- RubySketch embeds CRuby: https://apps.apple.com/us/app/rubysketch-graphics-games/id1491477639 (v2.12, 2026-05-19). Its listing says "This app includes Ruby language interpreter known as CRuby or MRI", and the app runs user-edited scripts.

## 2. iOS JIT, technically: interpreter only

- **`com.apple.security.cs.allow-jit` and `com.apple.security.cs.allow-unsigned-executable-memory`:** Apple's documentation metadata lists the platform as macOS 10.7+ only (https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.allow-jit).
- **BrowserEngineKit** (iOS 17.4+), "Protecting code compiled just in time" (https://developer.apple.com/documentation/browserenginekit/protecting-code-compiled-just-in-time):
  - The web content extension adds `com.apple.security.cs.allow-jit` and `com.apple.developer.kernel.extended-virtual-addressing`.
  - Pages are toggled with `be_memory_inline_jit_restrict_rwx_to_rx_with_witness`, and arm64e pointer authentication is expected.
- **Eligibility** (https://developer.apple.com/support/alternative-browser-engines/):
  - The app must "Be distributed solely on iOS and/or iPadOS in the European Union".
  - The Web Browser Engine entitlement also needs the default-browser entitlement.
  - The embedded-engine entitlement needs "in-app browsing as the primary focus".
  - Both need 90% of Web Platform Tests and 80% of Test262.
  - A game qualifies under neither.
- **Even with an entitlement,** YJIT and ZJIT as written would not work: they mprotect anonymous memory to executable, while iOS JIT requires MAP_JIT plus BrowserEngineKit's JIT-write APIs.
- **Sideloaded development builds (`get-task-allow`):** JIT is possible by attaching a debugger. SideStore's docs (https://docs.sidestore.io/docs/advanced/jit, around 2026-06-17) say "iOS 26 has broken JIT once again, and 26.6 and 27 only work with a few apps". This is a third-party source, and the path is a development convenience, not distribution.
- **Not verified from a primary source:** that the private `dynamic-codesigning` entitlement is unobtainable (Apple doesn't document it), and any iOS 27 change. Secondary sources say nothing changed in iOS 27, for example https://builds.io/blog/retro-games/best-iphone-emulators-not-on-app-store/: Apple "still does not allow third-party apps, emulators included, to use Just-In-Time compilation outside a narrow browser exception, and that hasn't changed with iOS 27."

## 3. CRuby on iOS in practice: works, interpreter only

xord/cruby (https://github.com/xord/cruby, last commit 2026-10-27) is the runtime behind RubySketch. It builds Ruby 4.0.7 (`config.rb`: `ruby-4.0.7.tar.gz`) into an iOS 14+ xcframework for iphoneos arm64. Its Rakefile shows what iOS needs:
- `yjit = rustc_target != nil && !ios`: YJIT is off on iOS.
- `withouts << 'fiddle' if ios # to pass the App Store review`. The comment is the project's own and gives no further reason. It is consistent with DPLA §3.3.1(A), "must not use or call any private APIs".
- `--with-static-linked-ext` and `--disable-shared dln`: C extensions are linked statically, not loaded at runtime.
- `ac_cv_func_{backtrace,system,syscall,__syscall,getentropy,dup3,pipe2}=no`.
- Source patches: a dummy `sys/vnode.h`, `system()` guarded out of `vm_dump.c`, and `sys_icache_invalidate` in `yjit.c`.

DragonRuby GTK ships to iOS and Android, but on mruby, not CRuby. That comes from secondary sources (AppSignal blog, itch.io), not DragonRuby's own docs. No App Store rejection specific to Ruby was found.

## 4. Google Play: allowed with conditions

**Device and Network Abuse policy** (https://support.google.com/googleplay/android-developer/answer/16273414; no date shown):
- "an app may not download executable code (such as dex, JAR, .so files) from a source other than Google Play. This restriction does not apply to code that runs in a virtual machine or an interpreter where either provides indirect access to Android APIs (such as JavaScript in a webview or browser)."
- "Apps or third-party code, like SDKs, with interpreted languages (JavaScript, Python, Lua, etc.) loaded at run time (for example, not packaged with the app) must not allow potential violations of Google Play policies."
- Bundled Ruby is clearly fine. Downloaded Ruby is riskier, since CRuby gives direct, not "indirect", access to the platform, especially with fiddle.
- Nothing in the policy forbids JIT.

**Target SDK** (https://developer.android.com/google/play/requirements/target-sdk, updated 2026-10-16): "Starting August 31 2026: New apps and app updates must target Android 16 (API level 36) or higher". Extensions to 2026-11-01 are available on request.

**SELinux** (AOSP `system/sepolicy`, main branch):
- `private/app.te`: "# WebView and other application-specific JIT compilers" / "allow appdomain self:process execmem;".
- `private/domain.te` keeps only "neverallow * self:process { execstack execheap };" and blocks new `execmod`.
- So anonymous mmap followed by mprotect(PROT_EXEC), which is YJIT's method, is permitted for apps at every target SDK.

**CRuby itself** (ruby-4.0.7 `configure.ac` lines 3916–3933): "we can't easily cross-compile with rustc so we don't support that". JIT is only auto-enabled when `cross_compiling = no`, and `[*android*], [JIT_TARGET_OK=no]`. Termux's Ruby 4.0.7 build script (termux-packages/packages/ruby/build.sh) builds Ruby for Android without YJIT. Forcing `--enable-yjit` with an `aarch64-linux-android` Rust target is untested and unsupported.

Balatro is also on Google Play, per a secondary source: https://www.gematsu.com/2024/09/balatro-coming-to-ios-android-and-apple-arcade-on-september-26

## 5. Other blockers

**Android 16 KB pages** (https://developer.android.com/guide/practices/page-sizes, updated 2026-10-16):
- "all apps targeting Android 15 (API level 35) and higher must support 16 KB memory page sizes on 64-bit devices on Google Play. Starting February 1, 2027, if your app updates don't support 16 KB memory page sizes, you won't be able to release these updates."
- To comply: use NDK r28+ (16 KB-aligned by default) or `-Wl,-z,max-page-size=16384`, use AGP 8.5.1+, and remove any hard-coded `PAGE_SIZE` or 4096.
- Ruby 4.0.7 reads the page size at runtime (`getpagesize`, and `sysconf(_SC_PAGESIZE)` in `thread_pthread.c`, `cont.c`, `gc/default/default.c` and `io_buffer.c`), and `HEAP_PAGE_SIZE` is 64 KB. No hard-coded 4096 was found in Ruby's core. This was not tested on a 16 KB device.
- Not re-verified today: Play's long-standing 64-bit native library requirement.

**Apple privacy manifest** (https://developer.apple.com/documentation/bundleresources/describing-use-of-required-reason-api): "Starting May 1, 2024, apps that don't describe their use of required reason API in their privacy manifest file aren't accepted by App Store Connect."
- Ruby uses `stat`, `fstat` and `lstat`, which fall under FileTimestamp; reason C617.1 covers files inside the app container.
- Ruby (`process.c`) and LÖVE (`src/modules/timer/Timer.cpp:158`) use `mach_absolute_time`, which falls under SystemBootTime; reason 35F9.1 or 0A2A.1 applies.
- If anything calls `statfs` or `statvfs`, a DiskSpace reason is also needed.
- Neither LÖVE nor love-apple-dependencies ships a `PrivacyInfo.xcprivacy`.

## What an embedded-CRuby app needs on mobile

**iOS:**
- A separate runtime, configured with `--disable-yjit --disable-zjit`.
- Static C extensions (or signed embedded frameworks), and no fiddle.
- No `system`, `fork` or `syscall`.
- Bundled Ruby source only, with no downloaded code that changes features.
- A `PrivacyInfo.xcprivacy`.
- Each developer submits their own app.

**Android:**
- An NDK r28+ build targeting API 36, with `.so` files aligned for 16 KB pages.
- Interpreter-only, unless someone spikes forcing YJIT on.

**Both:** plan performance budgets for interpreter speed.

## Also noted: matz/spinel

Spinel (https://github.com/matz/spinel, active as of 2026-10-28) is an ahead-of-time Ruby compiler. It infers types across the whole program, emits C, and compiles it with `cc`; its binaries "need only libc + libm", and its README claims "~8.5x faster than Ruby 4.0.4 with --yjit". Because it produces native code ahead of time, it would avoid the executable-memory problem on mobile entirely. The costs: no `eval`, and no runtime-computed `send`, `define_method` or `method_missing`; C extensions only through a restricted C extension API; and its docs list no iOS or Android target. Cross-compiling was not verified.
