# ADR 031: FLEDGE_RUNTIME_MIRROR Replaces the Release's Host, Checked Against the Pins, With No Fallback

## Context and Problem Statement

`fledge build` downloads each runtime, and its build-only companion when it compiles a gem, from the GitHub Release of its own version, `https://github.com/setdef/Fledge/releases/download/vVERSION/NAME`. It checks every file against the SHA-256 the gem pins (ADR 014). The pins were fixed when the gem was, so they vouch for a file whatever served it.

A developer behind a firewall that blocks GitHub, an organization that keeps its own copy of every input, or anyone after GitHub changed its terms, had only `FLEDGE_RUNTIME_DIR`. That takes a folder, and checks nothing, since it is for runtimes a developer built. The maintainer chooses hosts: "If you want a second host, you come to me asking" (decisions.md, 2026-11-04). How can a developer download Fledge's runtimes from a server of their own, with the release's guarantee?

## Decision Drivers

- The same guarantee as the release: the bytes Fledge's CI built and the gem pinned.
- A developer who sets a mirror usually does so because the release's host is blocked, forbidden, or gone.
- A mirror missing a version should be found the day it is set, not the day the release's host disappears.
- No second default host, which is the maintainer's to name.

## Considered Options

1. A variable that replaces the release's download base, `MIRROR/vVERSION/NAME`, checked against the pins, with no fallback to the release, as uv's `UV_PYTHON_INSTALL_MIRROR` and rustup's `RUSTUP_DIST_SERVER` work.
2. A mirror tried first, falling back to the release when it fails, as pyenv's `PYTHON_BUILD_MIRROR_URL` works.

## Decision Outcome

Chosen: option 1, because a fallback would reach a host the developer chose not to reach, or hang on one that cannot be reached, and hide a mirror that lacks a version. When `FLEDGE_RUNTIME_MIRROR` names a base URL, every runtime and companion comes from `MIRROR/vVERSION/NAME`, the path the release has under `https://github.com/setdef/Fledge/releases/download`. A mirror is a copy of the releases' assets in one folder per tag, which `gh release download vVERSION` fills, so one mirror holds every version a team uses. Every file is checked against the pins. A mirror that serves other bytes, lacks a file, or cannot be reached fails the build, naming the variable, the mirror, and the file, and the release is never asked. `FLEDGE_RUNTIME_DIR` still wins over both. `doc/contributors/design/runtimes.md`, "Where fledge build finds a runtime" and "Download retries", give the download rules.

The pins would make a fallback safe for the bytes, so the choice is only about where `fledge build` connects.

Confidence: high. The tests prove each refusal against real servers, and the design is uv's and rustup's.

### Consequences

- Good, because an organization can serve the runtimes from its own server, and a developer can build where GitHub cannot be reached, with the release's guarantee.
- Good, because a failure that names the mirror and the file shows the mirror's owner what to copy.
- Bad, because a mirror must hold every version that builds from it, at that version's tag, or those builds fail.
- Bad, because the variable, the asset names, the tag form, and the layout are frozen for 1.x (`doc/contributors/design/public-interface.md`).
- Neutral, because Fledge still has one default host. A second default, tried after the release, would be a fallback Fledge chose, and waits for the maintainer to name one.

### Confirmation

`test/runtimes_test.rb`, with real loopback servers: a mirror is used and the release is not asked; a mirror whose file does not match the pins is refused and nothing is cached; and a mirror without a file fails while the release, which has it, receives no request.

## Pros and Cons of the Options

### A mirror with a fallback to the release

- Good, because a mirror missing one version still builds while the release is up.
- Bad, because it connects to the host the developer meant to avoid, and hides the missing version until that host is gone. pyenv's mirror is a cache keyed by checksum in front of each package's own URL, and its default mirror is pyenv's own, which is a different case from a mirror a developer sets.

## More Information

The prior art, read on 2026-11-04. uv's `UV_PYTHON_INSTALL_MIRROR` "will replace `https://github.com/astral-sh/python-build-standalone/releases/download`" in each URL (`crates/uv-static/src/env_vars.rs`, lines 524 to 532, at astral-sh/uv 4470c33b), and when set is used "exclusively, no automatic fallback" (`crates/uv-python-managed/src/downloads.rs`, lines 809 to 818); only uv's own default mirror falls back to GitHub (lines 821 to 833). rustup's `RUSTUP_DIST_SERVER` "sets the root URL for downloading static resources" (`doc/user-guide/src/environment-variables.md`, lines 17 to 20, at rust-lang/rustup 0eafe77d) and replaces the default outright (`src/config.rs`, lines 1159 to 1163). pyenv's python-build tries `PYTHON_BUILD_MIRROR_URL` first, at `MIRROR/SHA256`, and falls back to the package's own URL (`plugins/python-build/bin/python-build`, lines 580 to 611, at pyenv/pyenv 68a076e0).

The name follows them: `FLEDGE_` as every Fledge variable, `RUNTIME` as `FLEDGE_RUNTIME_DIR`, and `MIRROR` as uv and python-build say. `doc/runtimes.md` tells app developers how to set one up.
