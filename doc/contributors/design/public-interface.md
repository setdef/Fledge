# The Public Interface

This document lists what Fledge promises from 1.0: what 1.x freezes, what any release may change, how 1.x adds without breaking anyone, the names held for later, and what a framework wrapper may rely on. Which Rubies and platform floors 1.x keeps is in `doc/contributors/design/releases.md`. App developers read the short form in `doc/runtimes.md`, "What 1.x keeps".

Before 1.0, everything here may still change, with a CHANGELOG entry. From 1.0, each frozen item changes only in a major (`doc/contributors/design/releases.md`, "Versions").

SemVer asks a project to declare its public API. Fledge's is the command and the files it reads and writes: what you type, what `fledge build` reads from a project, and what it writes. That is the surface every developer and CI job already uses, and it leaves the code under `lib/` free to change in 1.x. Declaring the Ruby classes as well, as their RDoc might suggest, would let a framework build in its own process, at the cost of freezing every method, keyword, and return value of code that changes with every story. Tauri 2 declares `tauri.conf.json` and its command, and Briefcase `pyproject.toml`'s `[tool.briefcase]` tables and the `briefcase` command, the same way (`doc/contributors/research/2026-11-04-one-point-oh-surface.md`, section 1).

## What counts as compatible

A change is compatible when every project that builds with 1.0 builds with a later 1.x to the same output, and every app it built behaves the same. Turning a refusal into an acceptance is compatible: a new key, a new value of `kind`, lifting an "at most one". Changing a default, a file name, a printed line, or the meaning of a value Fledge accepts is not.

## Frozen for 1.x

- **The command.** `fledge build [OPTIONS] [PATH]`, `fledge build --from APP [OPTIONS] [PATH]`, `fledge build ios|android [OPTIONS] [PATH]` (`doc/contributors/design/phone-projects.md`, "The operand"), `--help` (`-h`, `-?`), `--version` (`-v`), `-o`/`--out`, `--from APP`, `--sign`, `--sign-command COMMAND` (Windows only), `--notarize PROFILE` (macOS only, with `--sign`; all three in `doc/contributors/design/signing.md`), and `--`, with their meanings and defaults (`.` for PATH, `dist` for `--out`). `--sign` with `--sign-command` is a usage error, and so is `--notarize` without `--sign`. `FLEDGE_SIGN_COMMAND`, which stands for `--sign-command` on a Windows build whose command line gives neither it nor `--sign`, is frozen with them. A bare word Fledge reads as a platform, today `ios` and `android`, is read as one; a folder of that name is written `./NAME` (see "Reserved names").
- **Exit statuses** ("The command's conventions"; `doc/contributors/design/launcher.md`, "Messages and exit statuses"). `fledge`: 0; 1 for a failed build; 2 for a usage error. A built program: its Ruby program's status; 66 when its entry, `fledge.cfg`, or its section of `fledge.cfg` is missing; 72 on Linux when a library `linux: system_libraries` lists is not on the computer (`doc/contributors/design/gems.md`, "Libraries from the Linux distribution"); 70 for other damage. `bin/ruby`: 70 when it cannot run the app's launcher. The phone runtimes: `FLEDGE_RUBY_NO_APP` and `FLEDGE_RUBY_SOFTWARE` (`runtime/mobile/fledge_ruby.h`).
- **Standard output.** One path per line: the archive `fledge build` writes, then each installer, or a phone project's folder. `--help` and `--version` print there too. Nothing else goes to standard output, the checksum files included.
- **`fledge.yml`.** Every key, every value it accepts, every default, and the refusal of a key it does not know. The keys are `Fledge::Config::KEYS`, and `lib/fledge/config.schema.json` describes each: among them `installers` and its default (`dmg`, `nsis`, `appimage`), `programs`, `ios` and `android` with `host` (`doc/contributors/design/phone-projects.md`, "Host files"), `linux` with `system_libraries` and `deb_changelog`, `macos` with `build`, `file_associations` and what each system makes of it, and `build_tools`; `doc/contributors/design/desktop-apps.md` says what each does on a desktop.
- **The schema's address.** `$id` and the documented modeline name the file at the release's tag, and that address keeps serving the release's file ("The fledge.yml schema").
- **What `fledge build` writes.** `DIR/NAME-PLATFORM/`; its archive, `.tar.gz`, or `.zip` on Windows; `NAME-arm64-darwin.dmg`, `NAME-PLATFORM-setup.exe`, `NAME-PLATFORM.AppImage`, and `NAME-PLATFORM.deb`; beside the archive and each installer its checksum file, `FILE.sha256`; `DIR/NAME-ios/`, `DIR/NAME-android/`; and `DIR/CACHEDIR.TAG`.
- **What a built app holds.** `app/`, the project as copied, so an app's code finds its files through `__dir__`; `notices/NOTICES.txt` and `notices/sbom.spdx.json`; on Linux and Windows `notices/sources/`, the source of each component whose license asks for it (`doc/contributors/design/license-audit.md`, "notices/sources/ and the source bundles"), whose folders follow what the runtime ships; each program's name and where it sits; on macOS a windowed program's `NAME.app`, with the console programs in the bundle of the first windowed program; on Linux `IDENTIFIER.desktop` and `share/icons/hicolor/`.
- **Where an installer puts the app.** On Windows `%LOCALAPPDATA%\Programs\NAME`, the shortcut's AppUserModelID, and the uninstall key `HKCU\...\Uninstall\IDENTIFIER`; a `.deb`'s package name, the identifier in lower case, and its folder `/usr/lib/PACKAGE`. Each system knows the app by its identifier, so changing `identifier` makes a new app as far as that system is concerned, and the help says so.
- **How a built app differs from `ruby main.rb`.** `Parity::JUSTIFIED` (`tasks/parity.rb`) and `MOBILE_JUSTIFIED` (`tasks/parity/mobile.rb`) may only shrink in 1.x. A new difference is a change in how Ruby behaves under Fledge, the surprise Design precedence 2 forbids; removing one is a bug fixed toward `ruby main.rb`.
- **Phone projects.** The project folder's names and `fledge/`; the paths in the templates a host may replace (`doc/contributors/design/phone-projects.md`, "Host files"); the `@@NAME@@` marks Fledge fills; the embedding API: `fledge_ruby_run`, `fledge_ruby_run_app`, `fledge_ruby_add_extension`, and `fledge_ruby_forward_output` in `runtime/mobile/fledge_ruby.h`, and `org.setdef.fledge.FledgeRuby.startApp` on Android; and on Android the native libraries a host may load by name, `libfledgeruby.so`, and `libfledgeext.so` in every app with a gem whose extension `fledge build` compiles.
- **Releases and runtimes.** The tag form `vX.Y.Z`, with a prerelease in SemVer's form, such as `v1.0.0-beta.1`; the asset names `fledge-runtime-VERSION-PLATFORM.tar.gz`, `-NOTICES.txt`, `.spdx.json`, and `-lgpl-sources.tar.gz`, with VERSION Fledge's; `SHA256SUMS` in `sha256sum`'s format; `FLEDGE_RUNTIME_DIR` as a folder of those names; and `FLEDGE_RUNTIME_MIRROR` as the base URL of a copy of the releases that holds them as `vVERSION/NAME`, checked against the pins and never passed over for the release (`doc/contributors/design/runtimes.md`, "Where fledge build finds a runtime").
- **Ruby and the platform floors.** The rule that an app gets the runtime of the Ruby minor that runs `fledge build`, and the refusal of a minor with no runtime; every Ruby minor 1.0 has a runtime for; and the platform floors (`doc/contributors/design/releases.md`).

Every frozen item is tested where it is built: the CLI's tests, the schema test, `Parity`, and the Delivery jobs. A test that would let one change without failing is a bug in that test.

## Not frozen

Each item below may change in any release, with a CHANGELOG entry when a developer could notice.

- **Fledge's Ruby code.** `Fledge::CLI`, `Fledge::Config`, `Fledge::App`, and every other class and module under `lib/`, their methods, and their RDoc. They document how Fledge works, for its contributors. A wrapper runs `fledge build` as a command.
- **Standard error's wording.** Progress lines, warnings, and every `fledge build: ...` message improve from release to release. A wrapper tells success from failure by the exit status, and finds the files by standard output.
- **`fledge.cfg`.** `fledge build` writes it, and the launchers of the same release read it; nothing else should. Its keys and sections may change in any release, and runtimes of another release named by `FLEDGE_RUNTIME_DIR` are not supported.
- **The `tools` folder's layout.** What `build_tools: true` puts in an app, and where. Only a `fledge build --from` of the same release reads it. The key and its effect are frozen; the folder's contents are not.
- **The runtime's tree** below what Ruby itself answers: `RbConfig.ruby`, `RbConfig::CONFIG`, `Gem.dir`, `Gem.bindir`, and `__dir__`. An app that asks Ruby where things are keeps working when a folder moves.
- **The templates' contents.** The files a phone project starts from may change in any release; a host's copy of one is the developer's to keep in step, and the build names each copy it uses (`doc/contributors/design/phone-projects.md`, "Host files"). Google Play's target API level and the Xcode version App Store uploads need live there.
- **The caches.** `~/.cache/fledge/` and what it holds. On Windows a later release may move it to `%LOCALAPPDATA%`, which costs one download.
- **How Fledge is built and tested**: CI, `tasks/`, and the runtimes' sources and pins.

## How 1.x adds

- A new option, key, value, `kind`, command, or environment variable is compatible, since today's parser and `fledge.yml` refuse every one they do not know.
- A new installer is opt-in for all of 1.x, as `deb` is (`doc/contributors/design/desktop-apps.md`, "The .deb"). A new default would print a new line and need a new tool on a computer that built yesterday.
- A new icon size for a target is optional: a build that passed keeps passing.
- A new line on standard output comes only with a file the developer asked for, such as an opt-in installer. The built folder is not printed: a wrapper derives it from the archive's name. A file written beside every archive, as the checksum file is, is not printed either, and adding one is compatible.
- A limit lifted ("at most one windowed program", one PATH, one `--sign`, one `host`) is compatible, as long as what a project with one builds stays the same. When several windowed programs come, the console programs stay in the first one's bundle.
- A runtime for a new Ruby minor comes under the reserved names, and a runtime's patch may move (`doc/contributors/design/releases.md`).

## The command's conventions

`fledge` follows GNU's conventions, with Ruby's and Windows' short options, so a developer keeps the habits they bring and a script tells a call it got wrong from a build that failed. The maintainer asked that agents follow the standards here, and accepted these (`decisions.md`, 2026-10-26, decisions 4 and 16, and later, reply 4).

- `-h`, `-?`, and `--help` print the help, and `-v` and `--version` the version, to standard output, and exit 0, as the GNU Coding Standards ask (4.8.1 and 4.8.2). `-v` is how `ruby`, `gem`, and `bundle` spell it; `-?` is how `dotnet` and `winget` do, after `cmd`'s `/?`.
- A usage error, a bare `fledge` included, prints the message, the short usage, and `Try 'fledge --help'.` to standard error, as GNU's `ls` does after BSD's one-line `usage:`, and exits 2, as `grep`, `diff`, and `cmp` do, whose statuses POSIX specifies, and GNU `ls` and `bash`'s builtins. Status 1, which most coreutils and BSD `usage()` functions give, would make 1 mean two things, and sysexits' `EX_USAGE` (64) is one few command-line tools use, so scripts do not expect it.
- A build that fails prints `fledge build: ...` and exits 1.

The short usage is the help header's SYNOPSIS, so the CLI and `exe/fledge`'s header change together. `Fledge::UsageError` carries a usage error out of a command to `Fledge::CLI`, which owns the usage text. A built app's launcher has its own statuses, sysexits', in `doc/contributors/design/launcher.md`, "Messages and exit statuses".

## The checksum file

`fledge build` writes `FILE.sha256` beside the archive and each installer, always, in `sha256sum`'s format, and 1.x keeps both. What it holds and why is in `doc/contributors/design/desktop-apps.md`, "The folder and the archive".

## The fledge.yml schema

A project says what Fledge cannot learn from it in an optional `fledge.yml` at its root, a YAML mapping, as RuboCop's `.rubocop.yml`, Kamal's `config/deploy.yml`, and Standard's `.standard.yml` are. An app that needs no configuration has no file, any shape of project can have one, it stays out of what a gem publishes, and Ruby's standard library reads it; its presence also marks a project's root (`doc/contributors/design/desktop-apps.md`, "The project and its name"). A gemspec's `metadata` holds only strings, is published to RubyGems.org with the gem, and does not exist for an app with only a Gemfile; a Ruby file, as Warbler's `config/warble.rb` is, is code to run rather than data to check; and TOML needs a gem Fledge does not depend on. JSON, as Tauri reads `tauri.conf.json`, and a section of a file the project already has, as Briefcase reads `pyproject.toml`, were read as prior art but not compared, and no reason against them was recorded beyond YAML's being what Ruby tools use, so YAML is not known to be the better choice. YAML has its surprises (`no` read as false, an unquoted version read as a number), so `Fledge::Config` checks each value's type and says what it wanted. It refuses any key it does not know, naming it, so a typo or a removed key fails the build and a wrapper never sees a key silently ignored. Every key is a promise kept through 1.x, so a key is added only when an app needs it.

`lib/fledge/config.schema.json` is draft-07, the draft every editor reads, and holds what `Fledge::Config` enforces and nothing it does not . It is written by hand, not generated from `Fledge::Config` as Tauri generates `tauri.conf.json`'s schema from the Rust types it parses: Config is Ruby that checks each value and raises with a message, not a set of types, so a generator would need every description, pattern, and rule between keys as literals, which is the schema written in Ruby plus a task and tests of its own. `test/config_schema_test.rb` keeps the two from disagreeing. It compares the schema's keys, kinds, installers, default installers, and identifier rules with Config's constants, runs a table of documents through both the schema and Config (with `Fledge::Identity`) and fails when either accepts what the other refuses, checks the schema against draft-07's meta-schema, and checks every `fledge.yml` in the repository against both. It needs json_schemer, a development dependency that nothing Fledge ships loads. Submitting the schema to SchemaStore's catalog, which would match every `fledge.yml` without a modeline, is a change in another project's repository and is left to the maintainer. Its descriptions come from the `fledge.yml` section of `exe/fledge`'s help. Where Config's Ruby and JSON Schema differ, the schema says the same thing another way, and a reader should not "fix" these:

- `additionalProperties: false`, since Config refuses an unknown key.
- A value may be text or empty (YAML's `name:` with nothing after it), which Config reads as absent. Text that is blank to Ruby's `String#strip` is refused by a pattern that needs one character outside Ruby's whitespace and NUL.
- Patterns are read as ECMA-262 reads them, as editors do, so Config's `\A` and `\z` are written `^` and `$`.
- `version` is RubyGems' `Gem::Version::ANCHORED_VERSION_PATTERN`, which `Gem::Version.correct?` uses, less its leading whitespace, since Config also needs a leading digit. Its atomic group is written as a plain one, since the group's characters never overlap what follows it, and Ruby's `\s` is spelled as its six ASCII characters. A YAML number is refused, as Config refuses `version: 1.2`.
- The rules between keys, such as `installers` only for a windowed app and a windowed app's required `identifier` (which `Fledge::Identity` checks), are `if`/`then` rules.

What the schema does not hold: a file that is not valid YAML is the language server's to report, and a value `YAML.safe_load` refuses (a date, say) is refused by Config as invalid YAML where the schema sees no such type.

Every `fledge.yml` in `examples/` and the test fixtures starts with a modeline that names the schema beside it by a relative path, such as `$schema=../../lib/fledge/config.schema.json`. A modeline is a YAML comment, so neither Config nor a built app reads it.

A developer's modeline and the schema's `$id` name the file at the release's tag, `https://raw.githubusercontent.com/setdef/Fledge/vX.Y.Z/lib/fledge/config.schema.json`, and each release commit moves both. No build reads a modeline, so an address that served another Fledge's schema would offer keys the developer's Fledge refuses, and nothing would say so. A tag's file never changes, and needs no host, branch, or account. `trunk`'s file would describe the next major after 1.0, and an address per major, as Tauri 2 serves `https://schema.tauri.app/config/2`, needs a host or a branch Fledge does not have. The cost is that a developer who upgrades Fledge changes the modeline by hand, and that the address lasts as long as the tag and GitHub's raw files do; every release keeps its tag (`doc/contributors/design/releases.md`, "Where releases are"). `test/config_schema_test.rb` fails until `$id` and the documented modeline name this version's tag.

## Reserved names

Each name below is held, so that the feature it names arrives under it and nothing else takes it first.

- **`ios: build`**, a string of one to three whole numbers separated by periods, the shape `macos: build` has for the same Apple key, for `CFBundleVersion` and `CURRENT_PROJECT_VERSION`; and **`android: version_code`**, a whole number for `versionCode`. Each overrides the number Fledge derives from `version`, as Tauri's `bundleVersion` and `versionCode` and Briefcase's `build` and `version_code` do. Without them both stores see `1.0.0.pre.1` and `1.0.0` as one build, and refuse a second upload of a version. The derivation (`lib/fledge/mobile_project/ios.rb` and `android.rb`) stays the default, frozen; only the override is to come.
- **Runtime asset names with the Ruby's version**: `fledge-runtime-VERSION-ruby-X.Y.Z-PLATFORM.tar.gz`, and the same `-ruby-X.Y.Z-` part in the name of each asset beside it, for the runtime of a Ruby minor that a 1.x release adds. Throughout 1.x, the names without it mean the runtime of the Ruby minor 1.0 ships (`doc/contributors/design/releases.md`, "Ruby minors and runtimes").
- **Platform words in PATH.** A bare word that names a platform Fledge may write a project for (`ios` and `android` today; `visionos`, `tvos`, `watchos`, or another later) is read as that platform by every release that adds it. `fledge --help` says to write `./NAME` for a folder of such a name, so a developer who follows the help is never broken by a new platform. Briefcase reads `briefcase build iOS` the same way.

Waiting for a developer or a framework to ask, and compatible when they come, since each turns a refusal into an acceptance (`doc/contributors/design/desktop-apps.md`, "Building from a built app"):

- a copy-only `fledge build --from` for an APP built for another system;
- a single Windows file that runs without unpacking by hand.

## A framework wrapper's view

Lota, Tokra, and Rooibos call Fledge so that a developer who uses one ships an app without learning how. Fledge depends on no wrapper's repository; wrappers depend on Fledge (decisions.md, 2026-11-02). A wrapper relies on the frozen list above, and on nothing in "Not frozen". In a wrapper's terms:

- **The command.** `fledge build [PATH]` builds the program at PATH (default: the current directory; a folder means its gemspec's executable, or its `main.rb`) on the computer it runs on, for that computer's platform, with `-o DIR` choosing the output folder (default `dist`). It runs as `bundle exec fledge build` from a project whose Gemfile names Fledge by tag, in the `development` group; the app ships that group too, unless the developer's own `without` names it. The app runs on the runtime's Ruby, the minor of the Ruby running `fledge build`, whatever Rubies the wrapper supports otherwise. The first build downloads the release's runtime, checked against the gem's pins, into `$XDG_CACHE_HOME/fledge/runtimes`; `FLEDGE_RUNTIME_DIR` names a folder of runtimes instead.
- **The project.** The nearest folder from the program up with a Gemfile, `gems.rb`, gemspec, or `fledge.yml` (not above a git repository's top) ships whole, but for `.git`, `.bundle`, `vendor/bundle`, `vendor/cache`, and the output folder, with the gems the lockfile locks in the groups `bundle exec` would set up, `development` and `test` among them, each as built for the platform (`doc/contributors/design/desktop-apps.md`, "The project and its name"). The lockfile locks each platform the wrapper ships to, with checksums (`bundle lock --add-platform`, `bundle lock --add-checksums`). Every group ships unless the developer's own `without` setting names it (`bundle config set --local without test`), and Fledge compiles a gem when it must (`doc/contributors/design/gems.md`, "Compiling a gem"). A gem of a shipped group with no build for the platform fails the build.
- **`fledge.yml`.** A wrapper may write it for its developer or read the developer's. An unknown key is refused, naming it, so a wrapper never sees a key silently ignored. A wrapper whose app is one of several programs, as `lota fuse` would be for a game's GUI, names its entry point as one of the `programs` and builds the project, or builds that program alone by its path (`doc/contributors/design/desktop-apps.md`, "Several programs").
- **Output and statuses.** On standard output, the path of each file `fledge build` writes, one per line, and nothing else. Progress, the downloads, compiler output, and every error and warning go to standard error, an error as `fledge build: ...`, one line for each thing that is wrong. `NAME` is the `fledge.yml` name, else the gemspec's, else the project folder's, camelized. A wrapper tells success from failure by the exit status.
- **What a built app is.** A folder `NAME-PLATFORM/` whose program, `NAME` or `NAME.exe`, needs no Ruby and is unaffected by a Ruby the person has (`doc/contributors/design/launcher.md`, "Hiding and restoring the person's Ruby settings"). Its `ENV`, `$0`, and load path are as under `bundle exec ruby main.rb` (ADR 081; `doc/contributors/design/launcher.md`, "The Bundler environment"), so a wrapper's checks such as `__FILE__ == $0` behave as under `ruby`. Ctrl-C and a closed terminal reach the app as they reach `ruby` (ADR 081).
- **Each platform on its own computer.** Fledge builds each platform's app on that platform (ADR 010). A wrapper's CI runs one build job on a runner of each platform it ships to, and a delivery job on a fresh runner of each, which takes the archive and runs it.
- **Not to rely on.** Fledge's Ruby classes, standard error's wording, and `fledge.cfg`. A wrapper that runs `Fledge::CLI` in its own process does so without a promise.

A wrapper whose CI tests its unreleased source names Fledge, or itself, as a git gem at a commit. A library's own repository is not an app: building one of its examples from the repository's root ships the tools its Gemfile keeps in groups that `bundle exec` sets up.

### Building from a built app

For a framework's drop-to-make-an-app (decisions.md, 2026-11-04), Fledge gives general primitives and knows no framework's concepts (`doc/contributors/design/desktop-apps.md`, "Building from a built app").

**Fledge provides**, frozen with the rest: `fledge build --from APP`, its refusals, statuses, and output; `file_associations` and what each system makes of it; `build_tools`; and that an app built `--from` keeps APP's runtime, gems, `Gemfile.lock`, and `notices/` unchanged, and holds the new project as plain files, so `__dir__`, `__FILE__`, `require_relative`, and backtraces name real files. `--from` builds for the computer's own platform only.

**A framework provides**: the app it publishes for people to build from, built with `fledge build` in its own CI, with its gems, Fledge in its Gemfile in a group the app ships (any group its developer's `without` does not name), `build_tools`, and `file_associations`; receiving a drop, through its GUI library's events, and the screen that asks for one; turning what was dropped into a project, which may mean unpacking a zip, reading its own configuration, writing `fledge.yml` with a name and a unique identifier, and writing the program that starts the dropped content; running `fledge build --from` and saying where the output went; and everything its programs do at run time, such as where they save. A framework runs the `fledge` that RubyGems writes into the app's `Gem.bindir`, with `RUBYOPT=-rbundler/setup` and no `RUBYLIB`, so the person's own `RUBYOPT` and `RUBYLIB` do not reach it as they would reach a child under `bundle exec`. `doc/contributors/research/2026-11-05-drag-to-fuse.md` maps one framework's needs onto these primitives as an example.

### Phones

A framework that ships to an iPhone, an iPad, or an Android device through Fledge may rely on what follows from a Fledge release; it is part of Fledge's public interface, and changes only as this document says. How each part works is in `doc/contributors/design/phone-runtimes.md` and `doc/contributors/design/phone-projects.md`.

**Fledge provides:**

- `fledge build ios`, on a Mac with Xcode and XcodeGen, and `fledge build android`, on a Mac, x86-64 Linux, or Windows, which write an Xcode or Gradle project holding the project, its gems, and a runtime. The framework's team builds, signs, and submits that project with Xcode or Gradle.
- A gem with a C or C++ extension built by an `extconf.rb` is compiled for each of the phone's targets, linked into the app, and registered, so `require "name/name"` finds it. Static libraries an `extconf.rb` links are linked per iOS slice; shared ones are carried into the Android app.
- An `extconf.rb` that runs CMake finds each target's toolchain file in `CMAKE_TOOLCHAIN_FILE`.
- A gem whose gemspec names a Rakefile or an `mkrf_conf` script is built as RubyGems builds it, for each of the phone's targets, with the phone's `rbconfig.rb` in every Ruby the build starts and this computer's Ruby as `RbConfig.ruby`. Each extension it builds with mkmf is linked in and registered under its folder's path in the gem's require paths and the name `create_makefile` was given, as `require "digest/crc32/crc32_ext"` finds digest-crc's.
- `ios: host: DIR` and `android: host: DIR` in `fledge.yml` name a folder of files that `fledge build` copies over the project it writes, so a framework that must own the app's startup supplies its own files and keeps them across builds (see `doc/contributors/design/phone-projects.md`, "Host files"). The templates' file paths and marks stay, so a host's copy keeps working.
- The embedding API, `fledge_ruby_forward_output` and `fledge_ruby_run_app` (and on Android `FledgeRuby.startApp`), which a framework's host calls wherever its framework runs the main function.
- On Android, two native libraries a host may load by name, in each ABI of the app: `libfledgeruby.so`, from the runtime's AAR, in every app, and `libfledgeext.so`, in every app with a gem whose extension `fledge build` compiles. A host need not load either, since `FledgeRuby` loads the first and the runtime the second before Ruby boots; one that does may load them in any order, on any thread, before or after Ruby starts, and each loads once. What is inside `libfledgeext.so` is Fledge's to change, and so is every other library Fledge puts in the app: a host names no other.

**The framework provides:**

- A Ruby program that starts the app, and the gems it needs in the project's `Gemfile.lock`, locked for `ruby` (`bundle lock --add-platform ruby`). A phone runs no shell script, and the gems must be in the lockfile, not found on the build computer's paths.
- An extension that an `extconf.rb` builds with mkmf, calling `create_makefile` once, in C or C++, loaded with `require "name/name"`, `require "name/name.so"`, or, from the gem's own Ruby, `require_relative "name/name"`, never by a path that names the `.so` or `.bundle`, with its Init function named `Init_NAME` for the target's basename, as mkmf expects (Fledge renames it). The `extconf.rb` requires nothing but Ruby's standard library and the gems its gem depends on, since it runs with `--disable-gems` and those gems' code on its load path.
- Or a Rust extension whose `extconf.rb` calls rb-sys's `create_rust_makefile` once, with `cargo rustc` (not `use_cargo_build`), whose crate builds as a static library, and whose Init function is `Init_NAME` for the target's basename, as rb-sys's and magnus's macros name it (Fledge keeps the name, so no two of an app's Rust extensions share one); with Rust, Cargo, and the standard library of each of the phone's Rust targets on the build computer, and a libclang for bindgen.
- On iOS, no `dlopen` of a file it ships, and no `fork` or `exec`; on Android, no program run from the app's own files, which Android forbids from API 29, and no `exec`, which ends the app's process; on both, no code that writes executable files.
- When the `extconf.rb` runs CMake first: run `cmake` with a new build folder each time, inside the folder the `extconf.rb` runs in, and let CMake find its toolchain in `CMAKE_TOOLCHAIN_FILE`; pass no `CMAKE_SYSTEM_NAME`, sysroot, or compiler of its own, but `CMAKE_BUILD_TYPE` and the project's options as on a desktop; link what CMake built through `$LOCAL_LIBS` by path; build static libraries position-independent (`POSITION_INDEPENDENT_CODE ON`); name the C++ runtime as on a desktop (`-lc++` or `-lstdc++`) when the extension is C over C++, and Fledge links the phone's; and have CMake 3.21 or later on the build computer's `PATH`.
- Its native libraries, built for the phone's targets: a static library per iOS slice (or an XCFramework), and a shared library per Android ABI, found by the `extconf.rb` through `dir_config` or Bundler's `build.NAME` options (`bundle config build.NAME --with-NAME-dir=...`), which Fledge passes as `extconf.rb` arguments for every target.
- On Android, every native method its Java or Kotlin declares, in a shared library of its own that its `extconf.rb` links and its host loads by name, as SDL keeps its in `libSDL3.so`: Android's runtime finds no function of a gem's extension.
- Its host files, when its framework owns startup, in the `host:` folder: on iOS any of `Host/main.m`, `Host/Info.plist`, `Host/PrivacyInfo.xcprivacy`, the asset catalog, and `project.yml`; on Android `MainActivity.java` at its package's path, the manifest, the Gradle files, `strings.xml`, and any Java sources of its own.

Fledge refuses, naming the gem, an extension that the gemspec says CMake, configure, or Cargo builds with no `extconf.rb`, and a Rakefile's build that leaves a shared library mkmf did not build.

**Known limits:**

- CI runs the apps in the iOS Simulator and on x86_64 Android emulators. It builds and checks the iOS device slice and the arm64-v8a library, but runs neither: no free GitHub-hosted runner boots an arm64-v8a emulator. Games built with `fledge build` have run on a physical iPad Pro, iPhone 13 mini, and OnePlus Nord N30 5G (arm64-v8a).
- An SDL host on iOS runs Ruby on the main thread and asks for a 64 MB main-thread stack in the project's linker flags. Apple documents 1 MB for a device's main thread. An iPhone 13 mini granted the 64 MB; an iPad's grant is not measured, so a deep recursion in Ruby could still fail there.
