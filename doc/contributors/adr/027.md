# ADR 027: Aim an `extconf.rb`'s CMake at the phone through `CMAKE_TOOLCHAIN_FILE`

## Context and Problem Statement

A game engine shipped as a gem is often C++ that CMake builds, with a thin Ruby extension over it. Its `extconf.rb` runs `cmake` to build the engine's library, then calls mkmf's `create_makefile` for the extension, which links that library. The gemspec names only the `extconf.rb`.

Fledge aims mkmf at the phone by giving it the phone runtime's `rbconfig.rb` and this computer's Xcode or NDK compilers (ADR 022). A `cmake` that the `extconf.rb` runs sees none of that, and Fledge keeps the developer's `CC` and `CXX` out of the build. So CMake configured for the Mac or Linux computer. `examples/cmake_phone` showed the result: on iOS a macOS library merged into each slice, and `xcodebuild -create-xcframework` refused it; on Android the linker skipped the foreign objects and linked a library with undefined symbols, which would have failed when the app loaded it. How does a CMake build an `extconf.rb` runs aim at each of a phone's targets?

## Decision Drivers

- A gem's `extconf.rb` runs `cmake` as it does on a desktop, with no code that knows Fledge.
- CMake's own, documented mechanism for cross-compiling, and the NDK's own toolchain file, which Gradle uses.
- "Code is a liability" (`decisions.md`, 2026-10-28): no vendored toolchain to pin and keep.
- Prior art: cibuildwheel builds a Python package's CMake code for Android by writing a toolchain file and setting `CMAKE_TOOLCHAIN_FILE` in the build's environment.

## Considered Options

1. Write a toolchain file for each target and put its path in the `CMAKE_TOOLCHAIN_FILE` environment variable, which CMake 3.21 and later read when a build folder is new.
2. Options Fledge hands the `extconf.rb`, such as a `FLEDGE_CMAKE_ARGS` with `-DCMAKE_SYSTEM_NAME=iOS`.
3. CMake's environment variables alone (`CC`, `CXX`, `CFLAGS`), with no toolchain file.
4. A toolchain from elsewhere: leetal/ios-cmake's `ios.toolchain.cmake`.
5. The NDK's `android.toolchain.cmake` itself in `CMAKE_TOOLCHAIN_FILE`.
6. CMake's built-in Android support (`CMAKE_SYSTEM_NAME Android`, `CMAKE_ANDROID_NDK`).

## Decision Outcome

Chosen: option 1, because it is CMake's own variable, so an `extconf.rb` needs nothing of Fledge's, and a gem written for cibuildwheel's Android builds already works this way. Options Fledge hands over would need code in every gem. No environment variable sets `CMAKE_SYSTEM_NAME`, so without a toolchain file CMake configures for the build computer. ios-cmake predates CMake's iOS support, which CMake has had since 3.14, and is more than the few lines that set CMake's documented variables. The NDK's file reads `ANDROID_ABI` and `ANDROID_PLATFORM` as CMake variables, not from the environment, and without them builds for `armeabi-v7a`, so Fledge's file sets them and includes it. CMake's built-in Android support works, but Google documents and maintains the NDK's file, and Gradle uses it, so it is the one the developer's other Android code builds with.

A C extension over a C++ library names the C++ runtime as it must on a desktop (`-lc++` or `-lstdc++`). Fledge reads either name as "this extension has C++" and links each phone's own C++ runtime instead, rather than reading the archives' symbols for C++, since the `extconf.rb` already says so.

Confidence: high for a CMake library built with the Makefile generator, which runs on both phones in CI. Low for `find_package` and the Xcode generator, which were not tried.

### Consequences

- Good, because a gem whose `extconf.rb` builds its library with CMake compiles for the iOS device and Simulator and for Android's arm64-v8a and x86_64 with no change and no `fledge.yml` key.
- Good, because an `extconf.rb` that passes its own `-DCMAKE_TOOLCHAIN_FILE` or `--toolchain` overrides Fledge's, as CMake documents.
- Bad, because the build computer needs CMake 3.21 or later on its `PATH` for such a gem, which Fledge does not provide.
- Bad, because an `extconf.rb` that reuses a build folder from an earlier configure keeps that folder's toolchain.
- Bad, because a gem that names `-lc++` or `-lstdc++` for another reason (none is known) links a C++ runtime it does not use.
- Bad, because other tools an `extconf.rb` might run (`./configure`, plain `make`, Meson) stay unaimed; each would need its own cross files.
- Neutral: a gemspec that names a `CMakeLists.txt` directly is still refused (ADR 022). Its author can add a one-file `extconf.rb` that runs CMake and `create_makefile`.

### Confirmation

`test/mobile_extensions_test.rb` compiles `examples/cmake_phone` for both iOS slices and both Android ABIs and checks each object's platform and each library's symbols; without the toolchain file it fails. The `mobile-apps-ios` and `mobile-apps-android` jobs build and run `examples/cmake_phone`, which prints the system CMake built for.
