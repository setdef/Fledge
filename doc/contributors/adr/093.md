# ADR 093: Prebuild Each Platform's Runtime in Fledge's CI, and Publish It with the Release

## Context and Problem Statement

An app built with Fledge carries a relocatable Ruby beside the launcher that embeds it (ADR 001). The Ruby on the developer's own computer cannot be that Ruby: one built by a version manager or a package manager records absolute paths and links the machine's shared libraries. Someone has to build a relocatable Ruby for each platform, with its standard library, Fledge's launcher, and its notices, and pass it through the license audit (ADR 004). Who builds it, and when: Fledge, once per release, or each developer, on each computer that builds an app?

## Decision Drivers

- A developer should not need to build a Ruby, or own the toolchain that builds one, to ship an app.
- Every app of one Fledge version should carry the same tested runtime, checked by SHA-256 (ADR 014).
- The runtime must pass the license audit before anything is archived (ADR 004), which needs the license map and its tools.

## Considered Options

1. **Fledge's CI builds one runtime per platform and publishes it as an asset of the release;** `fledge build` downloads it, caches it, and checks it against the SHA-256 its gem pins.

## Decision Outcome

Chosen: option 1, "so that no developer needs to build a Ruby", with python-build-standalone as the model: prebuilt, relocatable CPython builds, published as release assets and pinned by hash, which Briefcase, uv, and others consume rather than building Python themselves. No alternative was weighed when this was decided. The section below reports alternatives found later; they were never the reason.

A runtime is a `.tar.gz` on every platform, Windows included, since only Fledge reads it. Each is built on the computer its recipe needs (ADR 010), audited, and archived with its SBOM, NOTICES, and source bundle beside it. A release publishes them, and the gem pins each by SHA-256 (ADR 014).

Confidence: high that it works: every Delivery job in CI builds apps from runtimes made this way and runs them on a fresh computer with no Ruby. No recorded comparison says it is better than the alternatives below.

### Consequences

- Good, because a developer needs only a Ruby to run `fledge build` and, for compiled gems, a compiler. Ruby's own build, its libraries, and the audit stay in Fledge's CI.
- Good, because the runtime an app gets is the one CI tested, audited, and delivered, byte for byte.
- Bad, because prebuilt runtimes are part of the product, not an optimization: a Fledge version is tied to the runtimes it pins, and every release builds and publishes dozens of assets.
- Bad, because `fledge build` needs the release's host, or a mirror (ADR 031), the first time it builds for a platform on a computer.
- Bad, because a release needs the CI run that built its runtimes to still hold them (ADR 053).

### Confirmation

- CI's "Runtime" jobs build every platform's runtime on each push; `release.yml` publishes them and checks the assets against `RuntimeBuilder.release_assets`.
- `installed.yml` installs Fledge from each tag, downloads the runtimes from the release, and delivers hello.
- `test/runtimes_test.rb` checks where `Fledge::Runtimes` finds a runtime and that it matches its pin.

### Later research (2026-11-10)

These alternatives were looked up after the decision. They inform a reader; they were never its reason.

- **Prebuilt portable Rubies from another project.** Traveling Ruby (Phusion, github.com/phusion/traveling-ruby) published self-contained Ruby binaries for Linux, macOS, and Windows; its README says it supports Ruby 2.4.10. A fork carries it on as trubygems/traveling-ruby, with releases of Ruby 3.3 and 3.4 per platform, musl Linux included. Fledge does consume another project's prebuilt Rubies (rv-ruby and RubyInstaller, ADR 035); what it adds is its launcher, pruning, defaults, and the audit, which no such project ships.
- **Building on the developer's computer.** Tebako (github.com/tamatebako/tebako) compiles Ruby from source on the computer that packages the app, and packs it with the app into one executable. ruby-build (github.com/rbenv/ruby-build) compiles a Ruby into a prefix on the developer's computer. Both need a full C toolchain and Ruby's build dependencies on every computer that builds an app, and give each developer a Ruby that CI never tested.
- **Freezing the developer's own interpreter.** PyInstaller copies the Python that runs it, with its shared libraries, into the app. ADR 001 records why a developer's Ruby cannot be copied that way.
