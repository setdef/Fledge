# ADR 063: Run the Bundler the Lockfile Names, as bundle exec Does

## Context and Problem Statement

A lockfile records the Bundler that wrote it under `BUNDLED WITH`. `bundle install` installs that Bundler, and `bundle exec`, `bundler/setup`, and every `bundle` command switch to it from Ruby's own (`Bundler.auto_switch` and `Bundler::SelfManager`, `bundler.rb` lines 172 to 174 and `bundler/self_manager.rb` lines 9 to 14 and 70 to 96, at Bundler 4.0.20). The program then runs with that Bundler's lib first on `$LOAD_PATH`, and with `BUNDLER_VERSION`, `BUNDLE_BIN_PATH`, `BUNDLER_SETUP`, `RUBYLIB`, and `RUBYOPT` naming it.

A built app ran the runtime's default Bundler, whatever the lockfile said, since its `.bundle/config` says `BUNDLE_VERSION: system`, after Warbler (ADR 095). On Ruby 4.0.9 the two matched for Fledge's examples, which Bundler 4.0.20 locked. On Ruby 4.1's preview, whose Bundler is 4.1.0.beta2, `examples/my_cool_app` showed five unjustified differences from `bundle exec`: `$LOAD_PATH`, `$LOADED_FEATURES`, the installed gems, `ENV`, and a child's `ENV` (`doc/contributors/research/2026-11-09-ruby-4.1-spike.md`). Any app whose lockfile another Bundler wrote meets the same on any Ruby. `bundle install` never moves `BUNDLED WITH` on its own, so most lockfiles name an older Bundler than the newest Ruby's.

Which Bundler should a built app run?

## Decision Drivers

- A person who runs the app never meets Ruby: no Bundler error, install, or download at run time (AGENTS.md, Design precedence 1).
- The app's Ruby code runs as under `bundle exec`, and a difference is a bug unless it is justified (Design precedence 2); Fledge must never surprise an app developer with how Ruby behaves compared with not using Fledge (decisions.md, 2026-11-02).
- Every external input is pinned by SHA-256 (AGENTS.md).
- Code is a liability (decisions.md, 2026-10-28).
- It works on Ruby 4.0 and on 4.1.

## Considered Options

1. Ship the Bundler the lockfile names, checked against the lockfile's checksum for it, and have the launcher load it in place of the runtime's own.
2. Refuse a lockfile whose `BUNDLED WITH` is not the runtime's Bundler, saying how to relock.
3. Keep the runtime's Bundler, and list the difference in `Parity::JUSTIFIED` with its reason. Warbler does this, and warns at build time that "the packed application will boot with the default bundler of the packed JRuby" (`lib/warbler/traits/bundler.rb`, lines 17 to 22 and 142 to 151, at jruby/warbler 3196d5f9).

## Decision Outcome

Chosen: option 1, because it alone gives the app what `bundle exec` gives it with nothing at run time that a person could meet. Option 3 leaves the app on a Bundler its developer never ran it with, which is the surprise the maintainer's words of 2026-11-02 rule out. Warbler's reason for it, that switching restarts the process, which a servlet container or a jar cannot do, does not hold for Fledge: the launcher chooses which Bundler to require before any loads, so nothing restarts. Option 2 changes nothing at run time, but refuses most real lockfiles, refuses every app again each time Fledge's runtime moves to a newer Ruby, and asks developers to work with Fledge's Bundler rather than their own.

`fledge build` chooses the Bundler as Bundler's `SelfManager` does, fetches it from RubyGems.org as Bundler does, checks it against the lockfile's `bundler (VERSION)` checksum, installs it beside Ruby's own, and names its version in `fledge.cfg`. The launcher, on every system, and the phones' embedding API, put that gem's lib first on `$LOAD_PATH`, where `bundle exec`'s `RUBYLIB` puts it, and require its `bundler/setup` by path, where `bundle exec`'s `RUBYOPT` does. Bundler then sets `ENV` as `bundle exec` would (ADR 095). `doc/contributors/design/gems.md` ("The lockfile's Bundler") and `doc/contributors/design/launcher.md` ("The Bundler environment", "fledge.cfg") hold the rules.

Confidence: high that a built app now matches `bundle exec` on macOS and Linux, where the parity check and Delivery showed it. Medium elsewhere: the jobs below are in place for every platform but have not run yet on the commit that added them, and on phones whose parity check has no app that names another Bundler.

### Consequences

- Good, because an app runs with the Bundler its developer runs it with, on any Ruby, and parity needs no justification of what Bundler does, only of where its files are.
- Good, because a person still installs and downloads nothing: the Bundler ships in the app, and the launcher never restarts.
- Bad, because a build may download one more gem, about 450 KB, and the app carries one more Bundler, about 2 MB unpacked.
- Bad, because a lockfile with no checksum for its Bundler now fails the build, with what to run. Bundler 2.6 and newer write that checksum; an older lockfile has no checksums for its gems either, so an app with gems failed before.
- Bad, because the launcher's C now writes the Ruby that loads Bundler from a version in `fledge.cfg`, and must check that the version holds only a version's characters.
- Neutral, because a Bundler much older than the runtime's Ruby may not run on it. `bundle exec` fails the same way, and the build cannot tell until the app runs.

### Confirmation

- `rake parity`, in every Test job in CI, builds `test/fixtures/bundled_with`, whose lockfile Bundler 4.0.19 wrote, a version no runtime ships, and compares it with `bundle exec` after `bundle install`. The differences it allows are only where each Bundler's files are (`Parity::JUSTIFIED`, recorded in `test/parity_justified.yml`).
- Delivery runs the same fixture on a fresh computer with no Ruby, and it must print what `bundle exec` printed where it was built.
- Unit tests cover the choice of Bundler (`test/bundle_test.rb`), the build (`test/gem_app_build_test.rb`), `fledge.cfg` (`test/assembly_test.rb`, `test/build_from_test.rb`), and the launcher's reader and code (`test/integration/launcher_bundler_test.rb`).
