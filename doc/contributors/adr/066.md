# ADR 066: Keep Every Platform on One Ruby 4.1 Release at a Time

## Context and Problem Statement

Fledge carries Ruby 4.1's previews until Ruby 4.1.0 (ADR 056). On macOS and glibc Linux its runtimes come from rv-ruby's builds of each release (ADR 035); on musl Linux, iOS, and Android it builds Ruby from the release's own tarball. RubyInstaller builds no preview, so on Windows the only signed Ruby 4.1 is its `rubyinstaller-head` build of Ruby's main branch, a new one every day, which Fledge keeps as a pre-release of its own (ADR 065). No head build exists from preview1's day: RubyInstaller's head builds failed on 2026-10-11 and the nights after (rubyinstaller2 CI runs 38185486568 and 38335369785). So 4.1.0-preview1 and Windows' Ruby are a month apart: Ruby's main branch at 0e25874222, of 2026-11-10, whose library folders are named `4.1.0+6` where the preview's are `4.1.0+5`.

How should Windows' Ruby follow the other platforms' until RubyInstaller builds Ruby 4.1.0?

## Decision Drivers

- An app's code runs as under `ruby main.rb` on each platform (AGENTS.md, Design precedence 2), and its developer chooses when it moves to a new Ruby (ADR 055).
- Lota waits on the first Fledge release on Ruby 4.1.
- Code is a liability (decisions.md, 2026-10-28), and building Ruby for a platform a maintained build serves is deferred until that build fails (ADR 035).
- Every input is pinned by SHA-256 and every release is green on every job (AGENTS.md).

## Considered Options

1. Keep every platform on one Ruby 4.1 release at a time: Windows on RubyInstaller's head build taken on the day each release appears, every other platform on the release, and RubyInstaller's numbered build at 4.1.0.
2. Build every platform from one commit of Ruby's main branch, with Fledge building Ruby from source for macOS and glibc Linux.
3. Release a patch on every day's head build.
4. Take RubyInstaller's build from preview1's day.

## Decision Outcome

Chosen: option 1. Until preview2, Fledge 0.12.0 ships Windows on RubyInstaller's head build of 2026-11-10 and every other platform on 4.1.0-preview1. On the day each later release appears (preview2, any later preview, each release candidate, 4.1.0), Fledge keeps that day's signed head build as an `inputs-rubyinstaller-head-<date>` pre-release, and a Fledge release then moves every platform to that Ruby together, and records the difference between the Windows build's revision and the release's own commit. At 4.1.0 RubyInstaller's numbered build replaces head, and every platform matches exactly.

Option 2 is days of work, delaying the release Lota waits on, and two more Ruby builds to keep for good, which ADR 035 defers until a source fails. Option 3 costs an hour of CI and about 41 release assets a day, turns trunk red whenever Ruby's main branch breaks, and has Lota move its pin daily. Option 4 is impossible, since no build exists.

The head build must be taken on its day: RubyInstaller's CI keeps each successful head build as an artifact for about 90 days (run 42745223477 keeps `installer-head-x64-ucrt` and `installer-head-arm-ucrt` until 2027-02-08), but the `.asc` the Windows build checks exists only on the release asset, which the next day's build replaces. `.github/workflows/keep-rubyinstaller-head.yml` keeps it: on each Ruby 4.1 release's day, it publishes RubyInstaller's signed head build of that day as the pre-release `inputs-rubyinstaller-head-<date>-for-<version>`. `doc/contributors/design/runtimes.md` ("Sources and pins", "Rolling upstream inputs") holds the details.

Confidence: medium. The runtimes of both Rubies build, pass the license audit, and pass the parity check on their own platforms; how far Ruby's main branch moves between two previews is not Fledge's to know.

### Consequences

- Good, because 0.12.0 ships now, every platform on a Ruby 4.1, with no Ruby build of Fledge's own to keep.
- Good, because every Fledge release moves all platforms at once, so each release's Windows Ruby is the nearest signed build to its other platforms'.
- Bad, because until 4.1.0 Windows runs a Ruby other than the other platforms': another revision, other default and bundled gem versions, another ABI version in its folders, and C API changes a preview lacks (Ruby's main branch declares `rb_range_beg_len` with `rb_len_t`, so nokogiri before 1.19.7 does not compile there). Code that runs on one may not on the other.
- Bad, because a head build that appears broken on a release's day leaves Windows on the previous one until a later day's build works.
- Neutral, because the parity check compares each Windows app with the very head build its runtime came from, so the gap between platforms is not a parity difference.

### Confirmation

`runtime/sources.yml` names each platform's Ruby, and the CHANGELOG each move. CI's every job, Windows' parity and Delivery among them, passes on each release's runtimes before it is tagged (ADR 053).

## More Information

ADR 056 is why Fledge carries a preview, ADR 065 how it keeps a head build, and ADR 035 where each platform's Ruby comes from. Revisit at Ruby 4.1.0, when this ends, or before Ruby 4.2's previews.
