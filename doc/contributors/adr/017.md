# ADR 017: Build musl Linux's Ruby from Source in Alpine

## Context and Problem Statement

Alpine Linux, and the CI images and containers built on it, use musl's C library in place of glibc's. A program linked against glibc does not start there, so Fledge's `x86_64-linux` and `aarch64-linux` apps cannot run on Alpine. The maintainer asked for musl: "Many CI platforms only run on musl for Linux, so I'd like to support it eventually, but it's not a blocker to continuing to iterate. It may be a blocker to 1.0 though." (`decisions.md`, 2026-10-26, decision 12). RubyGems names the platforms `x86_64-linux-musl` and `aarch64-linux-musl` (`doc/contributors/design/runtimes.md`, "Platform names and asset names").

On glibc Linux, Fledge takes Ruby from rv-ruby (ADR 035). rv-ruby publishes musl builds too, but configures them `--with-static-linked-ext` (`alpine/4.sh`, spinel-coop/rv-ruby at 7a0e584): every extension of the standard library is linked into rv-ruby's own `bin/ruby`, and only `libruby-static.a` ships without them. Fledge's launcher is the interpreter: it links libruby and loads extensions as shared objects (ADR 001). A launcher linked against rv-ruby's musl libruby has no `json`, `openssl`, or `psych` at all. Where does a musl runtime's Ruby come from?

## Decision Drivers

- A musl runtime must be what every other runtime is: the pinned Ruby, relocatable, its extensions shared objects, its libraries linked statically into the extensions that use them (ADR 039).
- It must run on any musl Linux, not only on the Alpine it was built in.
- Every input is pinned by version and SHA-256 (AGENTS.md).
- It is built on a computer of its own platform (ADR 010).

## Considered Options

1. **Build Ruby from its release tarball in Alpine,** configured as rv-ruby configures its glibc builds but with each extension a shared object, with OpenSSL, libyaml, libffi, and zlib built from pinned sources.
2. **rv-ruby's musl builds,** whose extensions are linked into their own `bin/ruby`.
3. **Alpine's own `ruby` package.**

## Decision Outcome

Chosen: option 1, because it alone gives a runtime the launcher can embed whole and that runs on any musl Linux. rv-ruby's musl builds leave the launcher without the standard library's extensions. Alpine's package is built for `/usr` and links Alpine's shared OpenSSL and libyaml, which an app's computer may lack (commit 1b98636). Building from source is the fallback ADR 035 foresaw, taken up for the one family of platforms where no prebuilt Ruby fits, as python-build-standalone builds CPython.

musl's own `crypt(3)` serves `String#crypt`, so no libxcrypt ships, and the launcher and `bin/ruby` need nothing but musl's C library.

Confidence: high. CI builds both runtimes on runners of each architecture, and delivers apps built with them in a bare Alpine with no Ruby.

### Consequences

- Good, because apps run on Alpine and other musl distributions, built on a computer of that platform, such as an Alpine container.
- Good, because a musl runtime is the same Ruby, at the same commit, as every other runtime, and passes the same audit, parity check, and Delivery.
- Bad, because Fledge maintains a Ruby build of its own, and moves its pins (Ruby, OpenSSL, libyaml, libffi, zlib, the Alpine image and its packages) on purpose. A Ruby release means rebuilding, and rechecking the build's two scripted edits for OpenSSL's certificate variable.
- Bad, because CI builds each musl runtime with `docker run` on a runner of its architecture, since GitHub's JavaScript actions cannot run inside an Alpine container on ARM.
- Bad, because musl's crypt does not know every hash that current glibc systems use; an app that checks such hashes on Alpine meets what `ruby` does there.
- Neutral, because rv-ruby's musl builds would serve, and this build could go, if they kept their extensions as shared objects.

### Confirmation

- CI's "Runtime" jobs for both musl platforms build and audit each runtime in Alpine.
- CI's "Parity" jobs for musl compare the built probe with the runtime's own `bin/ruby` and the gem-shaped probe with `bundle exec`, in Alpine.
- CI's "Delivery (…, alpine:3.24)" jobs run built apps in a bare Alpine with no Ruby; `installed.yml` installs Fledge from each tag in Alpine and delivers.
- `test/runtime_builder_test.rb` checks that the musl sources are pinned.
