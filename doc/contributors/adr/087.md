# ADR 087: Turn a bare C locale into a UTF-8 one in every Ruby of a runtime, where the app is started with no locale

## Context and Problem Statement

Ruby's `main.c` sets `LC_CTYPE` from the environment (`setlocale(LC_CTYPE, "")`, `main.c` lines 51 to 63 at Ruby 4.1.0-preview1), and that locale decides `Encoding.default_external`, `Encoding.find("locale")`, and `Encoding.find("filesystem")`. A desktop, a service manager, `env -i`, and a phone start an app with no `LANG` at all, which is the C locale, whose character set is ASCII. Then Ruby boots, but gives a folder named `Ünïcödé` three encodings: BINARY in `$LOAD_PATH`, US-ASCII with invalid bytes in `__dir__`, `$0`, and some loaded features, and UTF-8 in others (`ruby.c`, lines 2546 to 2589; `file.c`, `copy_path_class`, lines 7996 to 8006). Bundler fails setting up a bundle there (`clean_load_path`, `shared_helpers.rb`, line 391, raises `Encoding::CompatibilityError`), and the app's own code that matches or joins its paths raises "invalid byte sequence in US-ASCII" (`doc/contributors/research/2026-11-13-c-locale.md`). Python met the same problem and coerces the C locale (PEP 538).

An app's Ruby is not one process. The launcher starts the app, and `bin/ruby`, which `RbConfig.ruby` names, starts every child Ruby, every restart (ADR 089), and every gem's executable. A coercion in the launcher alone leaves each of those in the C locale.

Coercing is a difference from `ruby`. The agents argued that Design precedence 1 justifies it, and the maintainer answered (`decisions.md`, 2026-11-03): "I can buy that for now, but will easily be swayed by the first app dev who gets upset by the deviation. And we shouldn't be cagey about it or hide it."

The maintainer later set a stricter bar (`decisions.md`, 2026-11-12): a difference is accepted only when it is inherent to where the app ships or a platform truly forbids what Ruby does; "Every difference, every lack of parity, is a knife in Fledge's back." Where the app ships, it often has no locale: an app LaunchServices starts on macOS gets no `LANG` or `LC_*` (`launchctl getenv LANG` is empty), and a phone gives none. A configured Linux desktop does, since systemd passes `LANG` from `/etc/locale.conf` to every session and service, but containers, minimal images, `env -i`, and SSH do not (the same research).

## Decision Drivers

- A path outside ASCII must not break the app's boot or its gems (AGENTS.md, Design precedence 1).
- A locale the person chose stays theirs, and `ENV` stays what `ruby main.rb` gives (Design precedence 2).
- Every Ruby the app starts sees the locale the app sees.
- The deviation is documented plainly, and stays only until an app developer objects (the maintainer, 2026-11-03).

## Considered Options

1. Turn a C locale that comes from `LANG` or from no variable at all into the first UTF-8 locale the system has, in every Ruby of a runtime (the launcher, `bin/ruby`, and the phones' runtime), exporting nothing.
2. No coercion: `setlocale(LC_CTYPE, "")`, as `main.c` does.
3. PEP 538 as written: also coerce an explicit `LC_CTYPE=C`, and export `LC_CTYPE`, so every child process inherits the coerced locale.
4. On Windows, a UTF-8 code page for every app, through `activeCodePage` in the launcher's manifest.
5. No coercion, with the failures fixed where they start: Ruby tags a path not valid in the filesystem encoding as BINARY everywhere, and Bundler and its vendored Thor compare and match paths as bytes.

## Decision Outcome

Chosen: option 1, because it alone keeps a non-ASCII path from breaking the app and its gems while leaving every locale a person chose, and `ENV`, as `ruby` leaves them. Under the 2026-11-12 bar the difference is inherent to where the app ships: a macOS app and a phone app are started with no locale, where `ruby main.rb` runs in a terminal that has one.

Option 2 breaks an app a desktop starts in a folder whose name is not ASCII. Option 3 overrides a person who set `LC_CTYPE`, the one category Ruby's encoding comes from, and so has said which character set they want (Design precedence 2 over 4); PEP 538 itself never coerces when `LC_ALL` is set and documents `LC_ALL=C` as the way to keep the C locale (CPython v3.13.0, `Python/pylifecycle.c`, lines 189 to 194 and 293 to 294). Its export would add a variable to the app's `ENV`. Option 4 is no answer to the C locale, since `Encoding.default_external` is UTF-8 on Windows whatever the code page (Feature #16604); Windows takes it for another reason, gems that call its narrow functions (ADR 070). Option 5 does not close the difference but moves it: the app then sees what `env -i ruby main.rb` gives, US-ASCII paths with invalid bytes, so its own regular expressions, splits, and joins on its paths raise for a person whose folder name is not ASCII, which Design precedence 1 forbids; its fixes to Ruby and Bundler are worth sending upstream, with a proposal that Ruby treat the C locale as UTF-8, as PEP 540 does for Python, which is the only path that removes the difference.

`runtime/launcher/locale.c`'s `fledge_coerce_locale` does what `main.c` does, then, when neither `LC_ALL` nor `LC_CTYPE` names a locale and the result is C or POSIX, tries `C.UTF-8`, `C.utf8`, `UTF-8`, and `en_US.UTF-8`, keeping the first whose character set is UTF-8. `doc/contributors/design/launcher.md`, "The locale", gives the rule.

Confidence: medium. It works, and tests check every kind of locale; but the maintainer keeps it only until a developer reports it as a surprise.

### Consequences

- Good, because an app a desktop starts reads its folder and the person's home as UTF-8, and its gems set up under a path outside ASCII, in the app and in every Ruby it starts.
- Bad, because with no locale, or `LANG=C`, the three encodings are UTF-8 where `ruby` gives US-ASCII. A person who runs `bin/ruby` by hand that way gets UTF-8 too.
- Bad, because a program the app starts that is not Ruby sees the person's locale, since nothing is exported.
- Bad, because `bin/ruby` carries Fledge's `locale.c` beside Ruby's `main.c`.
- Neutral: `doc/differences_from_ruby.md`, "The locale", tells app developers, and asks them to open an issue if it surprises them; `Parity::JUSTIFIED` and `RubySpec::JUSTIFIED` list it.

### Confirmation

- The parity check runs the probe with no locale variable at all, where only the three encodings may differ, and under `LC_ALL=C` and `LC_CTYPE=C`, where nothing may (`Parity::LOCALE_FACTS`, `checks: [:no_locale]`).
- `test/integration/built_app_test.rb` runs the launcher and `bin/ruby` under each kind of locale.
- Delivery unpacks every app under `My Apps/Ünïcödé 日本` and runs it with `env -i`.

## More Information

- This supersedes ADR 041, which it restates with the failures as Ruby 4.1 has them and the maintainer's 2026-11-12 bar. The research: `doc/contributors/research/2026-11-13-c-locale.md`.
**Reversal.** When an app developer reports the coercion as a surprise, it goes:

1. In `runtime/launcher/locale.c`, make `fledge_coerce_locale` do only `setlocale(LC_CTYPE, "")`, for its three callers: `runtime/launcher/ruby_main.c`, `runtime/launcher/unix.c`, and `runtime/mobile/fledge_ruby.c`.
2. Delete the `LOCALE_FACTS` entries of `Parity::JUSTIFIED` and their lines in `test/parity_justified.yml`, and the locale entry of `RubySpec::JUSTIFIED`.
3. Change the tests that expect UTF-8 in a bare C locale, rewrite `doc/differences_from_ruby.md`'s "The locale", and record the change in the CHANGELOG.

What returns is the problem above: an app started with no locale reads its folder and the person's home as US-ASCII, and in a folder whose name is not ASCII, Bundler fails setting up the app's gems, and app code that matches or joins its own paths raises. A phone, which starts every app with no locale, would read all text as US-ASCII.
