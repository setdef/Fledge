# ADR 080: On a phone, a Ruby file stands where a desktop has an extension's file, and requires the linked extension

## Context and Problem Statement

On a phone every extension is linked into the app and registered under its feature (ADR 022), and Ruby looks a linked extension up only by the name a require was given (`load.c`, `search_required`, lines 1199 to 1218 at Ruby 4.1.0-preview1). A desktop's extension is also a file: in the gem's require path for an app's gem, and in the gem's extension folder for a bundled gem. Two kinds of code find it as a file, and both failed on a phone with `LoadError`.

- A gem that loads its extension by its path, with `require_relative "name/name"`, as Bundler's `bundle gem --ext` templates wrote it from 2.2.0 to 4.0.0.
- A require of a bundled gem's extension before its gem is active, such as `require "racc/cparse"`. RubyGems activates a gem when a file of its extension folder matches (`Gem::BasicSpecification#have_file?`, `lib/rubygems/basic_specification.rb`, lines 376 to 388), and a phone had no file there. ADR 068's gate rightly hides the linked extension until the gem is active.

The phone parity audit found both (`doc/contributors/research/2026-11-12-phone-parity-audit.md`, rows 43 and 44, and finding 1). The maintainer, 2026-11-12 (`decisions.md`): a difference is accepted only where the platform truly forbids what Ruby does. How does such code find a linked extension?

## Decision Drivers

- The app's code runs as under `ruby main.rb` (decisions 9 and 20): `require_relative` of an extension, and a require that activates a bundled gem, work as on a desktop.
- Fledge changes no developer's gem (ADR 007).
- Change as little of Ruby as can be: each edit to its source is one more to check with each new Ruby (ADR 068).

## Considered Options

1. A Ruby file at the path where a desktop has the extension's file, which requires the linked extension by its `.so` name: written by `fledge build` in an app gem's require path, and by the runtime build in each bundled gem's extension folder.
2. Extend ADR 068's `load.c` edit to map an absolute path to a linked extension's feature.
3. Refuse such gems, and justify `require "racc/cparse"` before racc is active as a difference.

## Decision Outcome

Chosen: option 1, because Ruby needs no edit for it. A require of the path finds the `.rb` as it finds any file, a second require of the path or of the feature sees it loaded, and the `.so` name cannot find the file again. RubyGems finds a bundled gem by the file and activates it, and the file's require then passes ADR 068's gate. CPython's iOS support does the same, with a `.fwork` file where a binary module's `.so` was. Where a gem's `lib/` already has a Ruby file of the extension's name, as bigdecimal, nkf, and fiddle have, no file is written, since it would hide the gem's own. How: `doc/contributors/design/phone-projects.md`, "Registering extensions", and `doc/contributors/design/phone-runtimes.md`.

Option 2 is a further edit to Ruby's source in every app's runtime, and a second require of the path would fail once Ruby deletes the registration it ran, unless the edit also searched the loaded features. Option 3 refuses gems that nothing on a phone forbids.

Confidence: high on Android, where the parity check compares a require of racc's extension before racc is active and a require of syslog's extension by its path, with no unjustified difference, from a debug APK and a release bundle, and `examples/native_phone` loads its extension with `require_relative`. iOS is proven by CI's Mobile apps job.

### Consequences

- Good, because a gem that loads its extension with `require_relative`, Rust ones such as ferro-idna included, and a require that activates a bundled gem through its extension, work on a phone. This removes the costs ADRs 022, 068, and 073 name for them.
- Bad, because a path that names the `.so` or `.bundle` itself still fails, as two of the gems surveyed do, and a Rakefile's extensions get no file, since RubyGems leaves them in no require path of their own (ADR 072).
- Bad, because `$LOADED_FEATURES` holds the file's `.rb` and the linked feature where a desktop holds the extension's `.so` path. That is one more case of a linked extension recorded as a feature, not a file, which the phone parity audit lists as closable (row 12), and which extensions loaded as files on a phone would close.

### Confirmation

`test/mobile_extensions_test.rb` and `test/integration/mobile_extension_stub_test.rb` hold where a file is written and what it requires, and where none is; the `rust_phone` integration tests check a Rust extension gets one; the mobile parity check compares the two probe facts above on both phones, and `examples/native_phone` requires its extension with `require_relative`.
