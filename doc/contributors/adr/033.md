# ADR 033: Notarizing a Mac App, and Signing a Windows App With the Developer's Own Command

## Status
Accepted (requested), built, and waiting for the maintainer's own credentials to prove it. Agents wrote this ADR and may change it (AGENTS.md, Questions). It carries out Plan 003's stories "Notarization and real trust chains" (its notarization half) and "A Windows signing command", which the orchestrator pulled ahead of 1.0, and amends ADR 016, sections 3 and 4. It applies decision 17 in `doc/contributors/decisions.md` ("Ideally, fledge developers should have the option to make it so Windows/macOS don't block the use of the app. But not every app dev will have the done the required ceremony with Microsoft and/or Apple."). Section 6's checks passed on `experiment/signing-ready` in run 42461943288 (all nine jobs green: Test, Build, and Delivery on arm64-darwin, x64-mingw-ucrt, and aarch64-mingw-ucrt), with trunk's runtimes from run 42453865685. setdef's Apple Developer Program enrollment and a Windows certificate are pending, so no run with real credentials has happened; `doc/contributors/signing-test.md` walks the maintainer through the first one.

## Date

## Context

ADR 016 signs an app with the developer's own identity. Two things were left out. Gatekeeper opens a downloaded Mac app without a warning only when Apple has notarized it, and ADR 016, section 4, left notarization until an account could prove it. On Windows, `--sign THUMBPRINT` reaches only a certificate in Windows' store, while a certificate that lives in a cloud or hardware service (Microsoft's Artifact Signing, formerly Trusted Signing; DigiCert KeyLocker; SSL.com eSigner; a key in a cloud KMS) signs only through that service's own tool.

No agent holds a credential, and no CI runner has one. So the work follows the maintainer's method: test-first in small steps (Beck), a port Fledge owns around each third-party tool, with end-to-end tests at the edge and mocks only of what Fledge owns (Freeman and Pryce), a seam at the command line, where a stand-in executable first on `PATH` takes the tool's place (Feathers), and a Gateway with a Service Stub (Fowler). The contract of each stand-in comes from the tool's documentation and the prior art's source, cited below, and a contract test runs the real tool when the maintainer has credentials.

## Decision

### 1. `--notarize PROFILE`, with `--sign`, on macOS

`fledge build --sign IDENTITY --notarize PROFILE` has Apple notarize the app it signed. PROFILE is the name of a notarytool keychain profile, which the developer makes once with `xcrun notarytool store-credentials PROFILE` and an App Store Connect API key or an Apple ID with an app-specific password. Fledge passes notarytool `--keychain-profile PROFILE` and nothing else that authenticates: it never sees an Apple ID, a password, a team, or a key, and puts none on a command line, where another process could read it, as Tauri's and @electron/notarize's password and key arguments are. Nothing goes in `fledge.yml`, which other people build too (ADR 016, section 1).

An option and not Briefcase's default: Briefcase notarizes whenever it signs with a real identity, and derives the profile from the team. Fledge keeps a signed build what it was, offline and immediate, and notarizes only when asked, since notarizing needs the network, an account, and minutes of waiting; the profile is named, not derived, so a developer with several teams or keys picks one. No environment variable stands for it: the profile is not a secret, and an environment variable that made every signed build wait on Apple would surprise. ADR 029, section 4 makes a new option compatible in 1.x, and one that takes notarytool's `--keychain`, or credentials from the environment as Tauri does, can come when a developer asks.

Usage errors (exit 2): `--notarize` without `--sign` (also with `--sign-command`), and with a phone's build. Build errors (exit 1): `--notarize` for Windows, and with the ad hoc identity `-`, which Apple does not notarize, as Briefcase refuses.

### 2. What is sent, what is stapled, and in which order

`Fledge::Notary` is the Gateway to notarytool and stapler, and `Fledge::Assembly` calls it after the installers are written and before the archive is packed. Fledge used to pack the archive first; installers are now written first on every platform, and what each holds is unchanged.

- **A windowed app with a disk image** (the default): the signed `.dmg`, which holds the signed bundle, is the one submission, since Apple says to notarize only the outermost container and Briefcase sends only the image. Fledge staples the ticket to the image, and then to the bundle in the app's folder, which the service issued a ticket for as a nested file, as Tauri staples its bundle; then the archive is packed, so it holds the stapled bundle, as Apple asks of a zip ("run `stapler` against each item that you added to the archive"; a `.tar.gz` is no different). The bundle inside the image is not stapled, since stapling would change a signed image ("Code-signing a supported file format invalidates any stapled tickets" says what the order must be: sign the image, then notarize it, then staple it); Gatekeeper reads the image's ticket when it opens the image, and the bundle's online after it is copied out, as with Briefcase's images.
- **A windowed app without a disk image** (`installers: []`): the bundle, in a zip that ditto makes, then stapled, as Tauri and Briefcase's zip format do.
- **A console app**: its whole folder, in a zip that ditto makes, so every Mach-O file in it is notarized, and nothing is stapled, since a lone program cannot hold a ticket; Gatekeeper looks the ticket up online the first time someone runs it.

Every zip is `ditto -c -k --sequesterRsrc --keepParent`, Apple's command with the `--sequesterRsrc` that Briefcase, Tauri, and @electron/notarize all add, which keeps extended attributes in the archive's `__MACOSX` folder and out of the bundle. After each staple, `xcrun stapler validate` checks it. stapler runs from the folder that holds the file, with its name, as @electron/notarize and Tauri run it. The checksum files, which `fledge build` writes after Assembly returns, are of the stapled files. Each step's progress goes to standard error.

### 3. Apple's answer

Fledge runs `xcrun notarytool submit FILE --keychain-profile PROFILE --wait --output-format json`, as @electron/notarize does, and reads the JSON whatever notarytool's exit status, since neither Apple's pages nor the prior art pins what that status is for an Invalid answer. Only `"status": "Accepted"` notarizes. Any other status (Invalid, Rejected, or In Progress, should the wait be cut short) fails the build with the submission's ID and the status, then with what `xcrun notarytool log ID --keychain-profile PROFILE` says, its `statusSummary` and each issue's severity, path, message, and documentation link, as Briefcase lists them, and how to read the whole log. When notarytool prints no submission, as when it cannot reach Apple, the build fails with notarytool's own words; for exit status 69, the missing profile, it adds how to store one under that name. There is no `--timeout`, as neither Tauri nor @electron/notarize sets one: Apple says 98 percent finish within 15 minutes, and a developer who stops waiting stops the build. Fledge does not submit again on failure, unlike codesign's timestamps (ADR 016, section 6): a submission is not a lost reply but a new request, and Apple limits them to 75 a day.

### 4. `--sign-command COMMAND` and `FLEDGE_SIGN_COMMAND`, on Windows

This is Plan 003's story "A Windows signing command", whose contract holds: `Fledge::SignCommand` runs COMMAND once for each PE file Fledge signs, the programs, Ruby's DLLs, and its extensions, in the order of their paths (`WindowsSigning.files`, the same files `--sign` signs), and then makensis runs it on the uninstaller and on the setup program through `!uninstfinalize` and `!finalize`, as Tauri runs its `signCommand`. Exit status 0 means signed; anything else fails the build and names the file. It is Windows only, a build error elsewhere, a usage error for a phone, and it excludes `--sign`, a usage error. The command's behavior, its tool, its account, its timestamp server, is its author's: Fledge owns the files, their order, and the failure.

- **How it runs.** Through `cmd.exe`, exactly as makensis runs the same command for the setup program: Fledge hands Ruby `IF 1==1 LINE`, which Ruby runs as `%COMSPEC% /c "IF 1==1 LINE"`, the line NSIS's `sane_system` builds. So a command behaves the same for a program and for the setup program, environment variables and a `.cmd` file included. Tauri splits its string on spaces and runs no shell, which would make the two differ, since makensis always uses `cmd.exe`.
- **The path.** Fledge replaces each `%1`, bare or in double quotes, with the file's absolute path, with Windows' backslashes, in double quotes, since an app's name may hold spaces; a command with no `%1` gets the path at its end, so a `.cmd` file of the developer's own is a whole command. makensis gets the command with `"%1"` in the same places and fills it in itself. makensis has no escape for a quote of the kind a string is quoted with, so the command goes to it in the first of `'`, `` ` ``, and `"` that it does not hold, and a command that holds all three fails the build, saying to put it in a `.cmd` file.
- **The failure.** For a program or library, the error names the file, the exit status, and what the command printed. For the setup program and the uninstaller, Fledge reads makensis's "Finalize command returned N" and "UninstFinalize command returned N" and names the setup program, or its uninstaller. Fledge never prints the command, which may hold a secret (eSigner's CodeSignTool takes a password), and makensis, run at `-V2`, prints only that line and the command's own output.
- **The environment.** `FLEDGE_SIGN_COMMAND` stands for `--sign-command` in a Windows build whose command line gives neither `--sign` nor `--sign-command`, as an environment variable is a default that an option overrides; a build for another system ignores it, since it means nothing there, so a developer who sets it in a shared profile can still build for macOS and Linux. It stays Windows-only for all of 1.x: a signing command for another system would need a variable of its own. A CI secret can then hold the whole command.
- **Not taken.** An option for each service (Artifact Signing's `/dlib` and metadata file, KeyLocker's `smctl`, eSigner's CodeSignTool): each would be code and a test for a service no agent can reach, where one seam reaches all of them, as the plan's story weighed. Batching files into one run, as `--sign` gives signtool 50 at a time: the contract is one file per run, which every tool named takes, and a developer's script can batch on its own.

### 5. YJIT's entitlement under a Developer ID

ADR 016, section 2, keeps `com.apple.security.cs.allow-unsigned-executable-memory` until a Developer ID run shows it unneeded. The documents settle this much: Apple's "Allow Unsigned Executable Memory Entitlement" is for memory made writable and executable without `MAP_JIT`, and "Allow Execution of JIT-compiled Code" for memory made with it; Ruby 4.0.9's YJIT reserves its region with `mmap` and no `MAP_JIT`, and makes pages executable with `mprotect` (ADR 016, Context), so of the two, only the first could apply. Apple's "Hardened Runtime" page says the exceptions are entitlements of the executable, which its libraries inherit; "Resolving common notarization issues" names a missing hardened runtime and `get-task-allow`, not a runtime exception, among what fails; and Briefcase notarizes apps that carry the same two entitlements on every Mach-O file (`__init__.py`, lines 463 to 467 and 905 to 915). What no document says is whether the kernel treats a Developer ID's hardened runtime differently from a self-signed one's, on which CI's YJIT wrote code with no entitlement at all. So the entitlement stays, since notarization accepts it and dropping it could break an app that enables YJIT, and only the maintainer's run answers the question: the walk-through's optional step signs the built app again, without entitlements, with his Developer ID, and runs `examples/windowed_app`'s YJIT check. If YJIT still writes code, a later change may drop the entitlement; the windowed app's report says whether it did.

### 6. What is proven, and how

- **Stand-in notary.** `test/support/stand_in_notary.rb` puts an `xcrun` first on `PATH` that answers `notarytool submit` with notarytool's JSON (Accepted; Invalid with exit 1; an offline error; notarytool 1.1.4's message and exit 69 for a missing profile), `notarytool log` with Apple's own example log from "Customizing the notarization workflow", and `stapler` by writing a mark where stapler puts a bundle's ticket (`Contents/CodeResources`, which `codesign --verify --strict --deep` leaves alone, as on macOS 27.0) or on an image's end, and records each call and each file submitted. `test/notary_test.rb` checks every command and its order, the issues of an Invalid answer, notarytool's words for a failure, the hint for a missing profile, and that no authenticating option reaches a command line. `test/built_app_test.rb` builds `examples/windowed_app` and `examples/hello` through `fledge build --sign IDENTITY --notarize fledge-test` with CI's self-signed identity and the stand-in: the image went to Apple signed, with the signed bundle in it; the image and then the bundle were stapled; the archive holds the stapled bundle, which still verifies; the checksum is of the stapled image; the console app went as a zip of its folder. It skips with the ad hoc identity, which `--notarize` refuses. Moving the archive before notarization fails it.
- **Stand-in signer.** `test/support/stand_in_signer.rb` is a `.cmd` file on Windows (a shell script elsewhere) that records each path and appends a mark to the file. `test/sign_command_test.rb` checks the path's place, makensis's form, one run per PE file in order, a failure that names the file and not the command, and, on Windows with a runtime, a whole build through `FLEDGE_SIGN_COMMAND`: every PE file, then the uninstaller, then the setup program; the archive's program and the setup program carry the mark; the checksum is of the signed setup program; and a command that fails on the setup program fails the build naming it.
- **Real signtool.** CI's Windows Build jobs build `examples/hello` and `examples/windowed_app` again with `--sign-command`, running the Windows SDK's signtool with CI's self-signed certificate, and the Windows Delivery jobs verify them on fresh runners with `.github/scripts/deliver-signed.ps1`, as they verify `--sign`'s.
- **Contract.** `test/built_app_test.rb`'s `test_a_notarized_build_opens_with_gatekeepers_blessing` runs only when `FLEDGE_TEST_NOTARY_PROFILE` is set: Apple's real service, then `stapler validate` and `spctl --assess` saying "source=Notarized Developer ID" for the image and the bundle. The maintainer runs it (`doc/contributors/signing-test.md`).

## Consequences

- A developer with a Developer ID notarizes with one option and one profile made once; one without changes nothing (decision 17).
- A developer whose Windows certificate is in a cloud or a hardware service signs with that service's own tool, with no code in Fledge for any service.
- Every macOS build now writes its disk image before its archive, and a notarized one waits for Apple, usually minutes.
- Not proven until the maintainer's run: that Apple accepts what Fledge signs (the hardened runtime, the timestamps, the entitlements on every Mach-O file, as Briefcase signs them); that stapling the bundle after notarizing only the image finds the bundle's ticket; Gatekeeper's verdict on a downloaded copy; YJIT under a Developer ID without the entitlement (section 5); Artifact Signing, KeyLocker, or eSigner through `--sign-command`; and SmartScreen's verdict on a setup program signed through a real chain. A CI job that notarizes needs a profile in a runner's keychain, which waits for an account and for the maintainer to want it there.
