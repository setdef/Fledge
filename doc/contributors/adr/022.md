# ADR 022: Native Gems on Phones

## Status
Accepted (requested). Agents wrote this ADR and may change it (AGENTS.md, Questions). It applies the maintainer's words of 2026-11-02 in `doc/contributors/decisions.md` ("iPadOS, iOS, and Android are our priorities for 0.2.0."), with decisions 9, 10, and 20, and the words of 2026-10-28 on code as a liability and on building each target on its own system. It replaces the sentences of ADR 011 (sections 1 and 4) and ADR 012 (section 4) that left native gems on phones for after 1.0, and carries Plan 003's story "Native gems on phones". The maintainer ruled on 2026-11-02 that no money is spent; everything below was built and checked on this Mac and in GitHub's free runners.

## Date
2026-11-02

## Context

Lota, a game engine that is a C++ native extension over SDL3 and other libraries, is the first expected consumer of Fledge on phones. A phone's Ruby loads no extension from a file (ADR 011, section 4): iOS forbids it (`--disable-dln`), and Android lets an app run native code only from the libraries its package carries (`lib/<abi>/lib<name>.so`; developer.android.com/ndk/guides/abis, "Native code in app packages"), not from files it writes. ADR 012 therefore refused every gem with an extension. This ADR settles how such a gem is compiled for a phone, linked into the app, found by `require`, and set up by Bundler, how it coexists with a host such as SDL3 that owns the app's main loop, and what an extension author provides.

## Decision

### 1. Compiling: mkmf, cross, with the host's runtime Ruby

An extension is built by its own `extconf.rb`, which `require "mkmf"`, and mkmf is Ruby's own tool for it. Cross-compiling with mkmf is old practice: rake-compiler loads the target Ruby's `rbconfig.rb` under the host's Ruby through a generated `fake.rb` (`lib/rake/extensiontask.rb` lines 432 to 483 at 2c001a7dce); Ruby's own build links its extensions statically with `ext/extmk.rb`, which sets mkmf's `$static` (line 651) and runs `make static` (line 268) against the Makefile mkmf writes (`lib/mkmf.rb` lines 2503, 2504, 2535, and 2686 to 2693 at 4.0.9: `EXTSTATIC`, `STATIC_LIB`, the `static` target, the `$(AR)` rule).

`Fledge::MobileExtensions` does the same, with no build system of its own:

- It runs `bin/ruby --disable-gems -I ARCHDIR -r SHIM extconf.rb` with **this computer's desktop runtime's Ruby** (the 4.0.9 that `NativeBuild` already runs, ADR 006), where ARCHDIR is the folder of the phone runtime's `rbconfig.rb` (iOS: `FledgeRuby.xcframework/SLICE/lib/ruby/4.0.0/arm64-darwin`; Android: `lib/ruby/4.0.0/ABI-linux-android`). `rbconfig.rb` finds its prefix from its own path (`TOPDIR`, line 17), so mkmf reads the phone Ruby's configuration, `CROSS_COMPILING` included.
- The shim (`MobileExtensions::SHIM`, a dozen lines) puts this computer's tools in place of the ones `rbconfig.rb` records, which are the CI machine's paths (`/Applications/Xcode_26.5.app/...`, `/home/runner/...`): Xcode's `clang`, aimed at the recorded `-target` triple and the SDK's sysroot (`xcrun --sdk iphoneos|iphonesimulator`); on Android the NDK's `clang` of the very name recorded (`aarch64-linux-android26-clang`), `llvm-ar`, and `llvm-ranlib`. For iOS it also points mkmf at the slice's `Headers/`, where the XCFramework puts Ruby's headers (ADR 011, section 2), and makes mkmf's link tests link `libfledgeruby` (`-L SLICE -lfledgeruby -lz ...`), so `have_func("rb_str_new", "ruby.h")` answers as it would in Ruby's own build (checked: yes, with zlib; without `-lz` the test fails, as the library needs it).
- It sets `$static` and wraps `create_makefile` to add `-DInit_NAME=Init_fledge_N`, N counting the app's extensions from 0, as `extmk.rb` renames `Init_cparse` to `Init_racc_cparse` (lines 561 to 562), so that two gems' extensions cannot clash in one binary; and it writes a report of the target name, the archive, and the libraries the extconf.rb added.
- `make static` makes `NAME.a`. Compiler flags stay in the objects; the report's `-l`, `-L`, `-framework` flags and archives the gem built (`$libs`, `$LOCAL_LIBS`) go to the link.

It does this for every target of the phone, in a folder per target: `ios-arm64` and `ios-arm64-simulator`, and `aarch64-linux-android` (arm64-v8a) and `x86_64-linux-android` (x86_64). Each target runs on its own system's tools (ADR 010): **iOS on a Mac**, with Xcode; **Android on a Mac or x86-64 Linux**, with the NDK (Windows is refused for gems with extensions, naming the gem: its `make` and the NDK's Windows toolchain were not tried). The NDK is the developer's own, as Gradle's Android plugin and Android Studio find it (`ANDROID_NDK_ROOT`, then `ANDROID_NDK_HOME`, then the newest in `ndk/` of `ANDROID_HOME`, `ANDROID_SDK_ROOT`, or the SDK Manager's default folder); Fledge downloads no toolchain onto a developer's computer, and says how to install one (`sdkmanager "ndk;30.0.16248370"`, the r30 the runtime is built with) when there is none. CI pins the NDK it uses by SHA-256 as the runtime build does.

The source of each gem is unpacked per target from where Fledge already has it: a server's `.gem` with `Gem::Package#extract_files`, a path gem with `PathPackage#copy_to`, a git gem from its checkout.

Considered, and why not: **rake-compiler / rake-compiler-dock** (a gem's own `Rakefile` task and a Docker image per target; neither knows a phone, and Docker is not the platform's own tool); **compiling with Gradle's CMake integration** (it would build each gem's sources from a CMakeLists Fledge writes, skipping `extconf.rb`: the configuration checks and `extconf.h` would be lost, and iOS has no such path); **dlopen of a built `.so` on Android** (the extension as a shared library in `jniLibs`, found with `dlsym("Init_x")`: workable, but iOS cannot, and one mechanism for both is smaller); **rb-sys** (see section 7).

### 2. Registration: `fledge_ruby_add_extension`, from a generated constructor

A statically linked extension is found by `require` when its name is in Ruby's table: `load.c`'s `search_required` finds no file and looks the name, with ".so" appended, up in `vm->static_ext_inits` (lines 1126 to 1145 at 4.0.9); `run_static_ext_init` calls the registered function (lines 1200 to 1212); `ruby_init_ext(name, init)` fills the table (lines 1480 to 1498); and `Init_ext` is what `extinit.c` (`template/extinit.c.tmpl`) uses for Ruby's own extensions, called from `ruby_opt_init` (`ruby.c` line 1828). Ruby also has a weak `Init_extra_exts` (`ruby.c` lines 1805 to 1812) called right after, "to be replaced with the actual strong symbol by the linker". It was considered and rejected: on Android the call is inside `libfledgeruby.so`, where Ruby's objects are built `-fvisibility=hidden`, so a strong definition in another library is never bound to it.

The embedding API gains one function (`runtime/mobile/fledge_ruby.h`):

```c
int fledge_ruby_add_extension(const char *feature, void (*init)(void));
```

`feature` is what the extconf.rb gave `create_makefile` (`"adder/adder"`). Registrations are kept until Ruby has booted; `run_ruby` then calls `ruby_init_ext(feature ".so", init)` for each, after `ruby_options` and before Bundler's setup and the program run, when the main namespace exists. A call after Ruby has started returns -1 with `EALREADY` (an extension added then would never be registered). `require "adder/adder"` and `require "adder/adder.so"` find it, as they find `json/ext/parser`. **`require_relative "adder/adder"` does not**: it asks for an absolute path, which is not in the table. Registering the files' paths too was considered; it needs the gem's install folder at run time for no gem that Fledge has met, and the message of a `LoadError` names the feature. It is a limit of this release (section 7).

Fledge writes the **registration unit**, a C file with a `__attribute__((constructor))` that calls `fledge_ruby_add_extension` for each extension and declares each renamed `Init_fledge_N` (`MobileExtensions.registration_source`). A constructor needs no call from the host, so a framework that replaces Fledge's host (Lota with SDL's `SDL_main`, Tokra with Tauri's) keeps its entry point and links the unit; a host that prefers can call the function itself.

Bundler and RubyGems also check a gem with extensions: `Gem::BasicSpecification#missing_extensions?` is true unless `gem.build_complete` is in the gem's extension folder (`lib/rubygems/basic_specification.rb`, line 89 and `extension_dir`, line 114), and such a gem is ignored. So `fledge build` writes the empty `gem.build_complete` where RubyGems (`extensions/PLATFORM/4.0.0-static/NAME-VERSION`) and Bundler for a git gem (`bundler/gems/extensions/PLATFORM/4.0.0-static/SCOPE`) look, as ADR 011 marks the bundled gems; `Gem.extension_api_version` is `4.0.0-static` for a Ruby with no shared libruby (`lib/rubygems.rb` line 506). A path gem needs no mark, as on a desktop.

### 3. Linking into the projects

**iOS: static, into the app's executable.** iOS Ruby has `--disable-dln`, and Apple's rules (App Store Review Guideline 2.5.2) leave an app no code it did not ship. Each slice's archives are merged by Apple's `libtool -static` and the two slices packed by `xcodebuild -create-xcframework -library ... -library ...` into `FledgeExtensions.xcframework`, which `project.yml` links beside `FledgeRuby.xcframework` (one library per platform variant is what that command takes). The registration unit is `Host/fledge_extensions.c`, a source Xcode compiles with the host, so its constructor and the `Init_fledge_N` references pull the archives in. `OTHER_LDFLAGS` carries the extensions' libraries, and `-lc++` when any has C++. A gem that needs a framework or a static library adds it in its extconf.rb (`$libs`, `$LOCAL_LIBS`), which the report carries here.

**Android: shared, because the package carries libraries only that way.** libfledgeruby.so is a shared library with Ruby's C API exported (ADR 011, section 2), so the extensions are linked into **one more shared library, `libfledgeext.so`**, per ABI: the registration unit and the archives (compiled `-fPIC`, as the runtime is), `-L libfledgeruby's folder -lfledgeruby -llog -lm`, the extensions' flags, `-Wl,-z,max-page-size=16384` (developer.android.com/guide/practices/page-sizes: "NDK r27 and lower"; NDK r28 and later do it by default), `--exclude-libs,ALL`, and `clang++` when an extension has C++, so the NDK's `libc++` is linked in as its documentation describes. It goes to `src/main/jniLibs/<abi>/`, where the Android Gradle plugin packs it as `lib/<abi>/libfledgeext.so`, uncompressed and zip-aligned (`useLegacyPackaging = false`, ADR 012). `MainActivity` loads it after `libfledgeruby` (`System.loadLibrary`), and its constructor registers the extensions with Ruby. Two ABIs are built and packed: arm64-v8a, which the CI only builds and checks, and x86_64, which runs.

### 4. Platform names and Bundler

Nothing changes in ADR 011, section 1, or ADR 012, section 4: the app's Bundler runs with `force_ruby_platform`, so a gem with an extension is its `ruby` build, whose `extensions` Fledge compiles; a gem that publishes a precompiled build for a desktop (nokogiri's) still ships its `ruby` build, which is compiled from source for the phone, and one that cannot be (the lockfile locks no `ruby` build) fails as before. A gem's own `platforms:` in the Gemfile leave it out of a phone's build, which the refusals suggest.

### 5. A host that owns the main loop (SDL3)

What was read, in SDL3 at `ee8c1f8af5` (`~/Developer/libsdl-org/SDL`):

- **iOS**: `SDL_RunApp` stores the app's `main` and calls `UIApplicationMain` (`src/video/uikit/SDL_uikitappdelegate.m` lines 43 to 62); once the scene connects, `postFinishLaunch` runs `SDL_CallMainFunction(...)` **on the main thread, inside the run loop's selector** (lines 463 to 465 and 552 to 565). `SDL_main_impl.h` renames the app's `main` to `SDL_main` and generates the real `main` (lines 62 to 156). So Ruby would run on the main thread, whose stack on iOS is the system's, not the 64 MB `main.m` gives Ruby's own thread (ADR 012, section 6), and every UIKit call SDL makes needs the main thread.
- **Android**: `SDLActivity` starts a Java `Thread` named "SDLThread" with the default stack size (`SDLActivity.java` lines 965 to 976) which calls `nativeRunMain`, which `dlopen`s the library `getMainSharedObject()` names (default "main") and `dlsym`s `SDL_main` (`src/core/android/SDL_android.c` lines 925 to 1004) and calls it through `SDL_RunApp`. Ruby would run on SDLThread, not the UI thread, with ART's default stack.

`fledge_ruby_run_app` runs Ruby on the calling thread (ADR 012, section 5), so with a host like this Ruby runs wherever `SDL_main` is called. On Android that suits: SDLThread is a thread that may block; the stack is the open point (the host can subclass `SDLActivity` and override `main()` to start `new Thread(null, runnable, "ruby", 64 MB)` and join it, as `FledgeRuby.startApp` does). On iOS the choice is between running Ruby in `SDL_main` on the main thread (small stack: `-Wl,-stack_size` may enlarge it, unverified) and on a thread of its own, from which Ruby may call SDL only through `SDL_RunOnMainThread` for the video calls that UIKit needs on the main thread. Lota's native code decides it; Fledge's API is the same either way. **Not verified** (section 8): neither an SDL3 app nor a spike of this was built.

### 6. What an extension author provides

- An `extconf.rb` that uses mkmf and calls `create_makefile` **once** (Fledge refuses a second call in the same extconf.rb), and sources in C or C++ that mkmf compiles; no other build system (Rake, CMake, configure, Cargo) and no other gem than the Ruby standard library in the extconf.rb (it runs with `--disable-gems`).
- The extension loaded by `require "name/name"` or `require "name/name.so"`, never `require_relative`.
- No `dlopen` of a file it ships, and no code that writes executable files; no use of `fork` or `exec` (ADR 011, section 6).
- A library it needs for the phone (SDL3, for Lota) found by its extconf.rb through `dir_config` and Bundler's `build.NAME` options, which Fledge passes as extconf.rb arguments (`bundle config build.lota --with-sdl3-dir=...`), pointing at a build of the library for the target: an XCFramework or static library per slice on iOS (SDL3's own `docs/README-ios.md` recommends `SDL3.xcframework`, a framework the app embeds), and a shared `libSDL3.so` per ABI on Android, which the app must also package in `jniLibs` and load before `libfledgeext.so`. Fledge does not yet carry such a library into the project (section 8).
- Its Init function named `Init_NAME` for the target's basename, as mkmf expects; Fledge renames it.

### 7. Refused, naming the gem and what to do

An extension that Rake, CMake, configure, or Cargo builds, a Rust one (`rb_sys` among its dependencies; its Makefile would need `cargo` aimed at `aarch64-apple-ios`, `aarch64-apple-ios-sim`, `aarch64-linux-android`, and `x86_64-linux-android`, a `staticlib`, and rb-sys's `RbConfig` reading the phone Ruby's, which `rb-sys` supports for desktop cross-compilation (`gems/rb_sys` at 7ade413d44) and was not tried here), and, for Android, a Windows computer. The message names the gem, what Fledge compiles, and the Gemfile's `platforms:` that leaves it out.

### 8. What was verified, and what was not

Verified (the `experiment/phones` branch, run 41492629986, every job green: it trimmed `ci.yml` to the mobile jobs, and the Mobile apps jobs build and run `examples/native_phone`, a gem `adder` with `adder.c` and `total.cc`, which prints `NativePhone adds 5 and totals 10 with a C extension (C and C++) on PLATFORM`):

- **iOS Simulator, iPhone 17 Pro (iOS 26.5) and iPad Pro 13-inch (M5)**: the line above on `arm64-darwin`, status 0, from os_log. The same app, built on a Mac with Xcode 27.2, ran on an iPhone 17 and an iPad Pro 13-inch (iOS 26.1 Simulator) while this ADR was written. Xcode builds the project for the Simulator and, unsigned, for devices with no warning, and the device slice links with the extension (`ios-arm64` is compiled and linked in the Mobile apps job like the Simulator's).
- **Android x86_64 emulator, API 36, with 4 KB and with 16 KB pages**: the line, on `x86_64-linux-android`. The extension is `libfledgeext.so` in the APK, which `zipalign -c -P 16` accepts for both ABIs.
- **arm64-v8a**: `libfledgeext.so` is compiled and linked by the NDK for arm64-v8a, is in the debug and the unsigned release APK, and passes `zipalign -c -P 16`. It was not run: no free runner boots an arm64-v8a emulator (ADR 011, Consequences). Nor did anything run the iOS device slice.
- mkmf's configuration checks work under the cross configuration (`have_func("rb_str_new", "ruby.h")` links `libfledgeruby`, on both systems), a C++ source in the same extension compiles and links (the NDK's `libc++` linked statically with `-static-libstdc++`; without it the library would need `libc++_shared.so`, which the package does not carry: caught by reading `NEEDED` with `llvm-readelf`), and `libfledgeext.so`'s `NEEDED` entries are `libfledgeruby.so`, `liblog.so`, `libm.so`, `libdl.so`, and `libc.so`.
- A path gem needed no `gem.build_complete` mark. The marks for gems from a server and from git are written and tested for their paths (`test/mobile_build_test.rb`, with fake runtimes) but no CI app has such a gem: `examples/native_phone` uses a path gem.

Not verified:

- A gem from a server or from git with an extension, in a running app (the marks of section 2); `extconf.rb` arguments from `bundle config build.NAME`; an extconf.rb that needs a gem or `pkg-config`; an extension that links a vendored static library (`$LOCAL_LIBS`) or a framework.
- An Android build on Windows (refused), and on x86-64 Linux with NDK versions other than r30 (CI uses r30); iOS device slices on a device.
- Any SDL3 app on a phone. Section 5 is what the sources say; nothing was built. **The spike of SDL3 owning the main loop with Ruby inside `SDL_main`, in the Simulator and an Android emulator, was not done** (an optional extra: it needs an SDL3 build for each of iOS's slices and Android's ABIs, a host project of its own, and a way to run Ruby on a 64 MB stack on iOS's main thread or hand SDL's video calls to it; about a day of work, with CI jobs of the Mobile apps shape).
- Rust extensions (section 7), and `require_relative` of an extension.

## Consequences

- `fledge build ios` and `fledge build android` take apps with C and C++ gems. The Mobile apps jobs gain one more app (about two more minutes on iOS, where Xcode builds one more project, and the NDK links two libraries on Android) and need this computer's desktop runtime (`runtime-arm64-darwin`, `runtime-x86_64-linux`) beside the mobile one, and the pinned NDK on Linux.
- The embedding API has a third function, `fledge_ruby_add_extension`, so the mobile runtimes change (their APIs are additive; hosts that do not call it are unaffected).
- A developer's Android build now needs the NDK installed (`ANDROID_NDK_ROOT`, or in the SDK's `ndk/` folder) for an app with extensions; Fledge downloads none. A developer's iOS build needs nothing more than before.
- A gem that loads its extension with `require_relative` fails with a `LoadError` naming the feature. A gem that has precompiled builds for desktops still ships its `ruby` build, compiled from source for the phone.
- Question A in `questions.md` asks whether `fledge.yml` should carry an app's other native libraries (SDL3); the default is that it does not.
