# Plan 001: Ship an App That Does Nothing

ADR 001 decides what Fledge is: a launcher that embeds CRuby, prebuilt runtimes per platform from pinned Ruby builds, and `fledge build` copying an app into them. This plan decides the order of the work.

The first slice is a walking skeleton: the thinnest path through every layer, from a folder with a `main.rb` to an archive someone with no Ruby downloads, unpacks, and runs, shipped through the same pipeline every later change will use. It does nothing a person would want. Shipping nothing first forces every decision that is cheap now and expensive later (where Ruby comes from, how the launcher finds it, what a runtime holds, how CI proves an app runs where no Ruby is) while the stakes are lowest. Every later story adds one capability to a pipeline that already delivers.

## The app: hello

`examples/hello/main.rb` prints one line and exits with status 0:

```
Hello from Ruby 4.0.9 on PLATFORM
```

`PLATFORM` is the target's RubyGems platform name (`arm64-darwin`, `x86_64-linux`, or `x64-mingw-ucrt`), as the runtime reports it. Before it prints, the app requires `json` and round-trips a value through `JSON.generate` and `JSON.parse`, because `json` is a C extension in Ruby's standard library: if extensions load from the runtime, this proves it, and if they don't, the app fails with a nonzero status instead of printing.

## Spikes: answer the risky questions with throwaway code

Each spike is a small experiment that answers one question, then gets thrown away. The answer goes in this plan.

1. **Does a Unix launcher run an app on rv-ruby, from anywhere it is unpacked?** In progress. On `arm64-darwin` and `x86_64-linux`: a launcher statically linked against rv-ruby's libruby, finding its runtime from its own path, with the environment scrubbed, running `examples/hello` from a directory other than the one it was built in, loading `json`. Answer: TBD.
2. **Does a Windows launcher run an app on RubyInstaller's Ruby?** Next. On `x64-mingw-ucrt`: a launcher built with RubyInstaller's MSYS2 UCRT toolchain against its `x64-ucrt-ruby*.dll`, finding the DLLs beside itself, running `examples/hello` from another directory on a runner with no Ruby on `PATH`. Answer: TBD. Whether the launcher can be built for Windows from macOS or Linux (cross-compiled with MinGW) or must be built on a Windows runner is part of the answer.

## The walking skeleton, layer by layer

- **Pinned Ruby sources.** A file in the repository records, per target, the source URL and SHA-256 of the Ruby build ADR 001, section 3 names: rv-ruby `20261023` for `arm64-darwin` and `x86_64-linux`, RubyInstaller `RubyInstaller-4.0.9-1` for `x64-mingw-ucrt` (PGP signature checked when the pin is recorded). A Rake task downloads and verifies them into `tmp/`, and fails on a mismatch.
- **The C launcher.** The smallest C program that embeds CRuby as Ruby's own `main.c` does. Per OS, it finds its own executable (`_NSGetExecutablePath`, `/proc/self/exe`, `GetModuleFileNameW`) and from there the runtime's Ruby and the app. It scrubs `RUBYLIB`, `RUBYOPT`, `RUBYSHELL`, `GEM_HOME`, `GEM_PATH`, `GEM_SPEC_CACHE`, `BUNDLE_GEMFILE`, `BUNDLE_PATH`, and every other `BUNDLE_` variable before Ruby starts, and runs `main.rb` on the process's main thread with the app's folder on the load path. Its exit status is the app's. Built with warnings as errors, and checked by its own gate.
- **A runtime per target, built in CI.** A CI job per target builds the launcher, unpacks the pinned Ruby beside it, and archives the result as that target's runtime, with the license notices Ruby and its libraries require. Runtimes are CI artifacts until a tag publishes them.
- **`fledge build`.** Downloads (or reuses from a cache) the runtime for each `--target`, checks its SHA-256, copies the app into it as `dist/hello-PLATFORM/`, and archives it as `dist/hello-PLATFORM.tar.gz` (or `.zip` for Windows). Tested first through `Fledge::CLI` with injected streams, as `--help` is today.
- **Delivery.** A CI job per OS, on a fresh runner with no Ruby on `PATH` (checked, not assumed), downloads the built archive for its platform, unpacks it into a different directory from the one it was built in, runs the launcher, and asserts stdout is exactly `Hello from Ruby 4.0.9 on PLATFORM` and the exit status is 0. A second run with `RUBYOPT`, `RUBYLIB`, `GEM_HOME`, and `BUNDLE_GEMFILE` set to values that would break Ruby must print the same thing.
- **Release.** On a `vX.Y.Z` tag, after every Delivery job passes, a job creates the GitHub Release and attaches each target's runtime, with its SHA-256. Never RubyGems.org (ADR 001, section 7). Whether and when to tag is the maintainer's call.
- **The gates.** The gem's gate exists from the first commit: tests, RuboCop, RubyCritic, RDoc coverage, REUSE, actionlint and shellcheck, Steep with no `untyped`, signature parity, and the package check. The launcher adds its own C gates (compiler warnings as errors, and a formatter and static analyzer to be chosen with it).

**Done when:** on every push, Delivery passes on all three operating systems: `examples/hello`, built by `fledge build`, unpacked on a fresh runner with no Ruby, prints `Hello from Ruby 4.0.9 on PLATFORM` and exits 0 on `arm64-darwin`, `x86_64-linux`, and `x64-mingw-ucrt`; and every gate passes with zero errors and zero warnings.

## Out of scope for the skeleton

- macOS `.app` bundles, and the windowed kind on every OS.
- Code signing and notarization.
- Vendoring an app's gems (a Gemfile), and gems with native extensions.
- A `fledge doctor` command that explains why an app won't build.
- Framework wrappers (Lota, Tokra, Rooibos) calling Fledge.
- More targets (`aarch64-linux`, `x86_64-darwin`, musl Linux).
- Building Ruby ourselves; that is ADR 001's fallback if a source fails.
