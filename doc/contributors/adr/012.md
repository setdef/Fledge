# ADR 012: Mobile Apps from `fledge build`

## Status
Accepted (requested). Agents wrote this ADR and may change it (AGENTS.md, Questions). It carries Plan 002's story "Mobile apps from fledge build" and applies the maintainer's words of 2026-10-27 in `doc/contributors/decisions.md` ("We should, if we can, support iOS and iPadOS and Android."), decisions 9, 10, 18, and 20, decision 8 as the words of 2026-10-28 bound it to Fledge's own runtime, and the words of 2026-10-28 on code as a liability, on building each target on its own system, and on waiting for an Apple Developer account until the last responsible moment. It builds on ADR 011, the mobile runtimes and their embedding API, which it extends by one function, and replaces the host app ADR 011, section 6, ran the parity probe in.

## Date
2026-10-28

## Context

ADR 011 made Ruby a library an iOS or Android app links: an XCFramework and an AAR, with two C functions and a Java class. A developer still had to make an Xcode or Gradle project, link the runtime, copy Ruby's library and the app's code into the bundle or the asset, set up the app's gems, and write the few lines that start Ruby. Each step has a way to go wrong that only a phone shows.

A phone also changes what `fledge build` makes. No phone builds an app, and no store takes an app Fledge signs: the developer signs with their own Apple or Google credentials, and submits it themselves, as App Store guideline 4.2.6 asks of anything built from a template ("Apps created from a commercialized template or app generation service will be rejected unless they are submitted directly by the provider of the app's content"; `doc/contributors/research/2026-10-27-mobile.md`, section 1). So the prior art writes a project the developer then builds, runs, signs, and submits with the platform's own tools:

- **Briefcase**'s `briefcase create iOS` and `briefcase create android` write an Xcode project and a Gradle project from templates, with Gradle's wrapper in the Android one; its iOS projects are made on macOS only, and its Android ones on macOS, Windows, and Linux (its documentation, "iOS" and "Android" platform pages, read 2026-10-28). `briefcase build` then runs xcodebuild or Gradle.
- **Flutter** writes `ios/` and `android/` projects with `flutter create`, builds iOS on macOS only, and Android wherever Google's SDK runs.
- **Tauri**'s `tauri ios init` writes XcodeGen's `project.yml` and runs XcodeGen to make the Xcode project, asking the developer to install XcodeGen; `tauri android init` writes a Gradle project with Gradle's wrapper.
- **React Native**'s template holds an Xcode project and a Gradle project, wrapper and all.
- **CPython**'s iOS support (PEP 730; "Using Python on iOS" in Python's documentation) has the developer drag `Python.xcframework` into an Xcode project, turn off user script sandboxing, and add a run-script phase, "Process Python libraries", that copies the standard library of the XCFramework slice the build is for into the app's bundle.

## Decision

### 1. `fledge build ios` and `fledge build android`

A phone's name, first, asks for its project: `fledge build ios [PATH]` and `fledge build android [PATH]`, as Briefcase's `briefcase create iOS` and Flutter's `flutter build ios` name the platform. `fledge build [PATH]` still builds for the computer it runs on (ADR 010). A first operand named `ios` or `android` is the phone; a folder of that name is `./ios`, or follows `--`. `fledge.yml` gains no key: which phone to build for is a question of each build, as which desktop is, not of the app. Considered: a `targets:` key in `fledge.yml`, which would make one build write several outputs that need different computers; an option (`--ios`), which no prior art uses; and Tauri's `fledge ios build`, a second command for what is still a build.

Each phone's project is built where its tools run, as Briefcase's platforms declare their hosts (ADR 010): iOS on a Mac (`arm64-darwin`), since only Xcode builds for it; Android on a Mac, on x86-64 Linux, and on Windows, where Google supports its SDK and Android Studio. `aarch64-linux` is left out: Google publishes no Android SDK build tools for it, so Gradle could not build the project there. Elsewhere, `fledge build` says where to build it and exits 1.

The project is `OUT/NAME-ios/` or `OUT/NAME-android/`, named as a desktop's folder is, and `fledge build` prints its path. The developer opens it in Xcode or Android Studio, or builds it with `xcodebuild` or `./gradlew`.

### 2. What a project holds

Each project holds the phone's runtime from Fledge's release, found and checked against the SHA-256 the gem pins, as every runtime is (`Fledge::Runtimes`; ADR 014), its template's files (`lib/fledge/templates/`), and the folder `fledge/`: what the app's Ruby root holds besides Ruby, as a desktop's built folder holds it beside the launcher: `fledge.cfg`, the project in `app/`, the app's gems in Ruby's gem folder, and the runtime's `notices/`, so the app carries them. On the phone, Ruby's root is that folder merged with the runtime's `lib/` and `libexec/`.

- **iOS**: `NAME.xcodeproj`, which XcodeGen writes from `project.yml`, as Tauri's are made, so Fledge writes no Xcode project file; `project.yml` stays, for the developer to change and generate again. `FledgeRuby.xcframework` is linked, not embedded, being a static library. A run-script phase, "Copy Ruby and the app", copies the slice's `lib/` and `libexec/` for the SDK the build is for, and then `fledge/`, into the bundle's `fledge/` folder with `ditto`, as CPython's "Process Python libraries" copies its slice's standard library, with user script sandboxing off for it, as CPython's documentation sets it. `Host/` holds `main.m`, the app's `Info.plist`, and its privacy manifest. The project builds for arm64 alone, the only architecture the runtime has, on devices and on Apple-silicon Simulators. XcodeGen is a tool the developer installs, as Tauri asks; without it, `fledge build ios` names it and how to get it.
- **Android**: a Gradle project of one app module, with Gradle's wrapper, the very `gradle-wrapper.jar`, `gradlew`, and `gradlew.bat` that Gradle 9.8.2 writes, pinned to the distribution and SHA-256 Fledge's runtime builds with (`runtime/sources.yml` pins the jar's SHA-256 too, and CI validates it with Gradle's own wrapper-validation action), as Briefcase's, Tauri's, and React Native's projects carry one. `libs/FledgeRuby.aar` is its dependency; `fledge/` holds the runtime's `lib/` and `libexec/` too, since one Ruby serves both ABIs; and the task `fledgeAsset` stores `fledge/` uncompressed as the asset `fledge.zip`, which `org.setdef.fledge.FledgeRuby` unpacks (ADR 011, section 2), with the Ant that Gradle carries (`ant.zip`), into a folder its build declares as output, which the Android Gradle plugin takes as generated assets (`addGeneratedSourceDirectory`). Gradle's own `Zip` task was the first choice, but the folder it writes into is not one of its outputs, so the plugin never ran it; the asset was missing until the task declared its folder. It targets API 36, as Google Play requires of new apps and updates since 2026-08-31, runs on API 26 and later, as the runtime does, and stores its native libraries uncompressed and aligned for 16 KB pages (`useLegacyPackaging = false`). The plugin is the version the runtime builds with. The app may reach the network (`android.permission.INTERNET`), as a Ruby program may on a desktop (decision 20).

Nothing configures signing. `xcodebuild` builds for the Simulator, and for a device with `CODE_SIGNING_ALLOWED=NO`; the developer chooses a team in Xcode to run on a device. `./gradlew assembleDebug` signs with the Android SDK's debug key, as every Android project does, and `assembleRelease` leaves the app unsigned, for the developer's own key. Fledge never submits an app.

### 3. Identity

The app's identity is `fledge.yml`'s (ADR 008), where each system shows it (decision 18):

- **identifier**: the bundle identifier on iOS and the `applicationId` on Android. A phone's app has to have one, so a phone's build without it fails, suggesting one, as a windowed desktop app's does. Android takes only parts that begin with a letter and hold letters, digits, and underscores, so an identifier with a hyphen, or a part that begins with a digit, fails for Android with one it would take. The host's Java package is Fledge's own, `org.setdef.fledge.host`, apart from the `applicationId`, as the Android Gradle plugin keeps `namespace` apart, so no identifier collides with Java's keywords.
- **name**: `PRODUCT_NAME` and `CFBundleDisplayName` on iOS, and the label on Android, written as each file reads it: as YAML's quoted strings in `project.yml` (JSON's strings, which YAML reads), as Groovy's single-quoted strings in the Gradle files, and as an Android string resource, escaped, in `strings.xml`.
- **version**: `MARKETING_VERSION` and `CURRENT_PROJECT_VERSION`, its first three numbers (`Fledge::MacBundle.bundle_version`), on iOS; `versionName` as it is, and `versionCode` made of its first three numbers, three digits each (1.2.3 is 1002003), as Briefcase pads a version's parts into its code, so each later version has a greater code; 0.0.0 gets 1, Android's lowest.
- **icon**: the files `fledge.yml`'s `icon` names, as Briefcase names them and as the desktop's are named (ADR 008): `ICON-1024.png` for iOS, the one size an asset catalog's app icon has needed since Xcode 14, from which Xcode makes the rest, in `Host/Assets.xcassets`; and `ICON-48.png`, `-72`, `-96`, `-144`, and `-192` for Android, each density's launcher icon in `mipmap-mdpi` to `mipmap-xxxhdpi`. Fledge copies them; Xcode's and Android's tools read them. Without an icon, each system shows its own.

### 4. Pure-Ruby gems, set up by Bundler

No gem publishes a build for a phone, and Fledge does not compile one for a phone before 1.0 (Plan 002). So a phone's app ships each gem's `ruby` build, with Bundler's own `force_ruby_platform` in the app's `.bundle/config` (ADR 011, section 1), which Bundler's documentation describes as "Ignore the current machine's platform and install only `ruby` platform gems" (`lib/bundler/man/bundle-config.1.ronn`, at Bundler 4.0.20): a gem that also publishes builds for desktops, such as one precompiled for Linux, ships its `ruby` build, and an iOS Ruby, which reports `arm64-darwin`, never resolves a macOS gem. As the app's Bundler runs with it, the lockfile must lock `ruby`, and a build says so, naming `bundle lock --add-platform ruby`. A gem with a C or C++ extension is compiled and linked into the app (ADR 022); one whose extension no extconf.rb builds, or that is Rust, fails the build, naming it; a gem the lockfile locks no `ruby` build of fails as a desktop build fails for a gem with no build for it. Gems' licenses stay the developer's business (ADR 007).

### 5. `fledge_ruby_run_app`, the launcher's work on a phone

The embedding API gains one function:

```c
int fledge_ruby_run_app(const char *root, int argc, char *const *argv);
```

It reads `root/fledge.cfg` with the launcher's own reader (`runtime/launcher/config.c`, now in both mobile runtimes) and runs `root/app/ENTRY`, as `fledge_ruby_run` would; for an app with a Gemfile, between `ruby_options` and `ruby_run_node`, as the desktop launcher's `setup_bundler` does (ADR 005), it sets `BUNDLE_GEMFILE` to the app's Gemfile, whose `.bundle/config` Bundler then reads as the app's settings, and requires `bundler/setup` from Ruby's own library, which sets `ENV` as `bundle exec` would (`Bundler::Runtime#setup`, `set_bundle_environment`, at Bundler 4.0.20). It returns 66 (EX_NOINPUT) when `fledge.cfg` or the program is missing, and 70 when the config is damaged or Bundler cannot set up the gems, as the launcher exits. Unlike the launcher, it pins nothing of RubyGems' and sets nothing aside: a phone starts an app with an environment no person sets (ADR 011, section 5). The Java class gains `runApp` and `startApp`, the same through JNI.

Considered: having each host read the program and Gemfile from its `Info.plist` or manifest and call Bundler itself, which would put the launcher's work in two hosts, in Objective-C and Java, rather than once, in C, beside the code the desktop launcher already runs; and a boot script that sets up Bundler and `load`s the program, which would make `$0` and every backtrace name a file the app never had (decision 10).

### 6. The host app

Each template's host is as small as the embedding API allows, and the developer's to change: it shows the app's name, on one screen (in the one UIKit scene apps built with the iOS 26 SDK must use, and one Android `Activity`), sends standard output and standard error to the system log under the identifier, runs the app with `fledge_ruby_run_app` on a thread of its own with a 64 MB stack, as `FledgeRuby.startApp` does on Android, so the interface never waits for Ruby and iOS's watchdog never stops an app whose program runs long, passes no arguments, since a phone has no command line, and logs `NAME exited with status N` when the program ends. The app stays open: iOS's guidelines and Android's leave quitting to the person. A framework such as Lota or Tokra replaces the host with its own, keeping the two calls.

### 7. The privacy manifest

`Host/PrivacyInfo.xcprivacy` declares the APIs Apple requires a reason for ("Describing use of required reason API", developer.apple.com) that Fledge's Ruby calls, as `nm -u` lists the imports of a built app's executable: `stat`, `fstat`, `fstatat`, `lstat`, `getattrlist`, and `fgetattrlist`, which Apple lists among the file timestamp APIs, with reason C617.1 (files inside the app's container), and `mach_absolute_time`, among the system boot time APIs, with reason 35F9.1 (time elapsed between events in the app); and that the app tracks no one and collects nothing, which the developer changes for their own app. Ruby calls no disk space API (`statfs`, `statvfs`), so none is declared. The research's list (`doc/contributors/research/2026-10-27-mobile.md`, section 5) named the same two categories. CI checks each built app's imports against the manifest (section 8), so a Ruby that starts calling another such API fails there. The check also compares reasons: each category the manifest declares that Fledge's template gives a reason (C617.1, 35F9.1) must still name it. `getattrlist`, `fgetattrlist`, and `getattrlistat` are not in the check's disk space row, though Apple lists them there too, because Ruby's `dir.c` calls them for the filesystem's type and the check matches by function name only.

### 8. Proof

The Mobile apps jobs (`tasks/mobile_parity.rb`) build four apps with `fledge build ios` and `fledge build android` from the runtimes CI just built: `examples/hello`; `examples/mobile_app`, a gem-shaped app whose gems, i18n and concurrent-ruby, are pure Ruby and which says Bundler set them up; `test/fixtures/mobile_hello`, which requires json and csv, a bundled gem, and reaches rubygems.org over HTTPS; and the parity probe. Each Xcode project builds with `xcodebuild` for the Simulator and, unsigned, for devices, with no warning, and each device build's imports are checked against its privacy manifest; each Gradle project builds with its wrapper, debug and unsigned release, as APKs and as app bundles (section 9), and each APK is checked with the SDK's `zipalign -c -P 16` and `aapt2 dump badging` for 16 KB pages and API 36. Then each app runs in the iOS Simulator on an iPhone and an iPad, and on Android emulators with 4 KB and 16 KB pages, its lines read from os_log and logcat: each must print its line and exit with status 0, and the probe's report must differ from `ruby main.rb` on the desktop only as ADR 011, section 6, justifies. These jobs replace the parity check's own host apps (`test/fixtures/mobile/`), which the generated projects now are. On macOS and Windows, `examples/mobile_app`'s Android project is written and built with Gradle too.

### 9. The app bundle Google Play takes

Google Play takes an Android App Bundle from a new app, not an APK: "From August 2021, new apps are required to publish with the Android App Bundle on Google Play" (`developer.android.com/guide/app-bundle`, read 2026-11-07). Briefcase's `briefcase package android` makes an AAB by default, with release and debug APKs as the other formats ("Android" platform page, Gradle, read 2026-11-07), and Flutter's `flutter build appbundle` writes `build/app/outputs/bundle/release/app.aab` ("Build and release an Android app", `docs.flutter.dev/deployment/android`, read 2026-11-07). The project Fledge writes is a standard application module, so the Android Gradle plugin's `bundleRelease` and `bundleDebug` make one with no change to the template. Three things had to hold, and each was checked on a built bundle before any CI ran:

- **`fledgeAsset` runs for a bundle.** The asset is registered with `addGeneratedSourceDirectory` on every variant, and the plugin's bundle tasks merge the same assets as its APK tasks, so `bundleRelease` runs `fledgeAsset` and the bundle holds `base/assets/fledge.zip`.
- **`fledge.zip` stays stored.** A bundle compresses its own entries; what counts is what the APKs made from it hold. The plugin writes `androidResources.noCompress` into the bundle's `BundleConfig.pb`, and `bundletool dump config` shows `**[zZ][iI][pP]` among its `uncompressedGlob`s, so every APK bundletool or Play makes stores the asset, which `FledgeRuby` unpacks. Android's documentation names the same mechanism: "you can also specify which file types to leave uncompressed when packaging APKs using glob patterns" (`developer.android.com/build/building-cmdline`, "Customize downstream APK generation", read 2026-11-07).
- **Native libraries stay stored and 16 KB-aligned.** With `useLegacyPackaging = false`, the bundle's config asks for `uncompressNativeLibraries` with `PAGE_ALIGNMENT_16K`, the value Android's page-size guide tells a developer to look for with `bundletool dump config` ("If you see `PAGE_ALIGNMENT_16K` then you know your bundle requests 16 KB zip alignment"; `developer.android.com/guide/practices/page-sizes`, read 2026-11-07). The guide warns that with the plugin's 8.3 to 8.5 "`bundletool` does not zipalign APKs by default. So, the app may appear to work, but when built from a bundle in Play, it won't install"; Fledge's plugin is 9.4.1, and each split APK passes `zipalign -c -P 16`.

**Signing.** Fledge configures none, as section 2 says. `bundleDebug` signs with the SDK's debug key; `bundleRelease` leaves the bundle unsigned. A developer signs it with their upload key, with a `signingConfigs` block or with `jarsigner`, since "You cannot use `apksigner` to sign your app bundle" (`developer.android.com/build/building-cmdline`, "Build an app bundle with Gradle"), and Play App Signing signs the APKs it serves with the app's own key, as Flutter's guide describes the two keys. `doc/phones.md` says how; Fledge holds no key.

**Size.** Play limits a bundle's base module to a 500 MB compressed download, and an app's modules and install-time asset packs to 4 GB together ("Optimize your app's size and stay within Google Play app size limits", `support.google.com/googleplay/android-developer/answer/9859372`, read 2026-11-07). A Fledge app is all base module: Ruby, its standard library, the app, and its gems are one asset. `examples/mobile_app`'s release bundle is 23.9 MB, and bundletool's `get-size total` measures its largest download, the base and one ABI's split for API 29 to 31 on arm64-v8a, as 17.3 MB, with the master APK holding the 30.3 MB `fledge.zip` stored. An app with tens of megabytes of gems is far inside the limit. One that carries hundreds of megabytes of data, as a game might, would move that data into a Play Asset Delivery pack, a module of its own that the app reads through Play's AssetPackManager or, for an install-time pack, through Android's `AssetManager`; Fledge builds no pack, and the asset Ruby boots from stays in the base module.

**The check.** CI's Mobile apps (Android) jobs build both bundles of every app beside its APKs (`tasks/mobile_parity/android.rb`). Each release bundle is signed with a throwaway upload key made in the job, verified with `jarsigner -verify`, validated with `bundletool validate`, checked for `PAGE_ALIGNMENT_16K`, and made into an APK set with `bundletool build-apks`, as Play would make it; each split APK passes `zipalign -c -P 16`, every native library and `fledge.zip` in it is stored, which `zipalign` alone does not check, since it passes a compressed entry, each of the base module's main APKs holds `fledge.zip` and targets API 36, the lowest from API 26, and the largest download stays under the limit. On the emulators with 4 KB and 16 KB pages, each app then runs a second time, installed from its APK set with `bundletool install-apks`, which picks the device's splits as Play does, and must print the same line and exit 0. The Android project jobs on macOS and Windows build `examples/mobile_app`'s release bundle and check it the same way. bundletool 1.18.3 is pinned by SHA-256 in `runtime/sources.yml`, beside XcodeGen, as a tool only CI fetches.

In CI, on the `experiment/android-aab` branch, whose workflow runs only these jobs with the runtimes of trunk's run 42428270566 (5f851d2): **run 42435210013, every job green**, with no change to how the template builds; only its comments changed, to name the bundle tasks and `jarsigner`. All six apps, run from their bundles' APKs on both emulators, printed the same lines as from their APKs and exited 0, and the probe found 16 differences, all justified, either way. The release bundles were 22.9 to 23.9 MB, and their largest downloads 16.3 MB (`examples/hello`) to 17.3 MB (`examples/mobile_app`); `examples/native_phone`'s and `examples/cmake_phone`'s `libfledgeext.so` was stored at 16 KB in every split. The emulator jobs took about ten minutes, four more than before. `examples/sdl_phone`'s host is not in this check: it needs SDL built by its `sdl3/build.sh`, which no CI job on trunk runs. Not proven: an upload to Play, which needs the developer account the maintainer has not opened; Play's own review; and an arm64-v8a device running the bundle's arm64-v8a split, which no free runner can emulate (Consequences).

## Consequences

- A developer with a pure-Ruby app runs `fledge build ios` on a Mac or `fledge build android` on a Mac, Linux, or Windows, opens the project, and runs the app in the Simulator or an emulator; to run it on a device, or ship it, they sign it and submit it themselves.
- Not yet proven: App Store review of an app with Fledge's runtime and privacy manifest, which needs the Apple Developer account the maintainer will get at the last responsible moment (decisions, 2026-10-28). A game built with `fledge build ios` ran on a real iPad and a real iPhone 13 mini on 2026-11-05, signed with a free Personal Team, so a device needs no paid account (ADR 025, section 6). `questions.md` raises it. Android's arm64-v8a build runs on no emulator in CI: ADR 011 records, with runs, that no free GitHub-hosted runner can boot one with hardware acceleration, and the maintainer ruled on 2026-11-02 that no money is spent on a device cloud or a machine for it.
- Each iOS project builds only on Apple silicon and for arm64, as the runtime is.
- The templates are Fledge's own code under the AGPL, as the embedding API is, and the host's compiled code ships in every phone's app: `doc/licensing.md` says so. Gradle's wrapper, which no app holds, is Gradle's, under Apache-2.0.
- XcodeGen and a JDK with the Android SDK are tools the developer installs; Fledge pins neither on their computer, but names XcodeGen when it is missing, and the Gradle wrapper pins Gradle.
- A project that keeps the developer's changes when Fledge writes it again, are later stories.
