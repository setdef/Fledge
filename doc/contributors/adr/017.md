# ADR 017: musl Linux, From Ruby Built in Alpine

## Status
Accepted (requested). Agents wrote this ADR and may change it (AGENTS.md, Questions). It applies the maintainer's decision 12 in `doc/contributors/decisions.md` ("Many CI platforms only run on musl for Linux, so I'd like to support it eventually, but it's not a blocker to continuing to iterate. It may be a blocker to 1.0 though.") and takes up ADR 001, section 3's fallback, building Ruby in Fledge's CI, for the one family of platforms where no prebuilt Ruby fits. It is Plan 002's story "musl Linux."

## Date
2026-11-01

## Context

Alpine Linux, and the CI images and containers built on it, use musl's C library instead of glibc's. A program linked against glibc does not start there, so Fledge's `x86_64-linux` and `aarch64-linux` apps, whose launchers link glibc 2.39 (ADR 001, section 3), cannot run on Alpine. RubyGems names these platforms `x86_64-linux-musl` and `aarch64-linux-musl`, what `Gem::Platform.local` reports on Alpine and what precompiled gems publish for it (sqlite3 2.10.2 among them; PEP 656 names the same platforms `musllinux` for Python).

rv-ruby publishes musl builds of Ruby 4.0.9 (`ruby-4.0.9.x86_64_linux_musl.tar.gz` and `arm64_linux_musl`, release 20261023), but configures them `--with-static-linked-ext` (`alpine/4.sh`, spinel-coop/rv-ruby at 7a0e584): every extension of the standard library is linked into its own `bin/ruby`, and only `libruby-static.a` ships, without them. Fledge's launcher is the interpreter (it links libruby statically and loads extensions as shared objects; ADR 001, section 1), so a launcher linked against that libruby has no `json`, `openssl`, or `psych` at all (Plan 001, spike 1, found this first).

A spike (the `experiment/signing` branch's runs of 2026-11-01) built Ruby 4.0.9 from its release tarball in Alpine, configured as rv-ruby configures its glibc builds but with each extension a shared object, linked Fledge's unchanged Unix launcher against its `libruby-static.a` with `-rdynamic`, and ran an app that required `json`, `openssl`, `psych`, `fiddle`, and `bigdecimal` and enabled YJIT, on x86-64 and on ARM64, from a folder with a space in its name, in a bare Alpine with no Ruby. GitHub's `ubuntu-24.04` and `ubuntu-24.04-arm` runners run Alpine containers with `docker run`; their JavaScript actions cannot run inside an Alpine container on ARM, which rv-ruby's own `build-alpine.yml` notes too.

## Decision

### 1. Two targets, `x86_64-linux-musl` and `aarch64-linux-musl`

`Fledge::Platform` adds both, RubyGems' names, which `Platform.local` maps from `Gem::Platform`'s `linux` with version `musl`. They are Linux (`os` is `linux`, so a windowed app gets a desktop entry and an AppImage), with no glibc floor (`glibc_minimum` is `nil`), and the libraries an app's compiled gems may assume (`Platform#libraries`, `linux-musl`) are those PEP 656 lets a `musllinux_1_2` wheel assume, auditwheel 6.8.2's `musllinux-policy.json`: musl's C library, by its own name (`libc.so`) and Alpine's (`libc.musl-ARCH.so.1`), its dynamic linker, and zlib. A Gemfile.lock locks them as Bundler writes them (`bundle lock --add-platform x86_64-linux-musl`).

### 2. The runtime builds Ruby from its pinned source, in Alpine

`RuntimeBuilder::Musl` (`tasks/runtime_builder/musl.rb`) builds, on a computer of each architecture, in Alpine 3.24 (CI's `ruby:4.0.9-alpine3.24` image, pinned by digest, its packages pinned by version in `.github/scripts/alpine-packages.sh`):

- zlib 1.3.2, libyaml 0.2.5, libffi 3.5.2, and OpenSSL 3.6.5, from the sources `runtime/sources.yml` pins under `musl-ruby`, static and position-independent, so each links into the one extension that uses it, as rv-ruby's glibc builds link them; OpenSSL renamed to read its certificates from `PORTABLE_RUBY_SSL_CERT_FILE` and Ruby's `openssl.rb` set to point it at `libexec/cert.pem`, Mozilla's CA bundle, unless `SSL_CERT_FILE` names others, as rv-ruby does (`Formula/rv-portable-openssl.rb`, line 77; `Abstract/rv-ruby.rb`, lines 203 to 208);
- Ruby 4.0.9 from its release tarball, `--enable-load-relative --disable-shared --enable-yjit`, every extension a shared object, with Alpine's Rust 1.96.1 for YJIT and GCC 15.2.0, and `-static-libgcc`;
- then what every Unix runtime is (`RuntimeBuilder::Unix`): the launcher and `bin/ruby` linked against that `libruby-static.a`, the standard library, default and bundled gems, Fledge's RubyGems defaults, pruning, AppImage's own runtime in `tools/`, and the license audit.

No libxcrypt ships: musl's own `crypt(3)` serves `String#crypt`, and the launcher and `bin/ruby` need nothing but musl's C library, which the build checks. musl's crypt does not know every hash yescrypt-era glibc systems use (Plan 002, "Copyleft-free runtimes"); an app that checks such hashes on Alpine meets what `ruby` does there.

Building from source rather than taking Alpine's own `ruby` package keeps the runtime what every other runtime is, the same Ruby 4.0.9 at the commit `RUBY_DESCRIPTION` names, relocatable, with the same static libraries, and pinned; Alpine's package is built for `/usr` and links Alpine's shared OpenSSL and libyaml, which an app's computer may lack.

### 3. Proven as every runtime is

- **The license audit** reads each musl runtime with binutils' objdump in Alpine; `runtime/licenses.yml` names its components (Ruby, OpenSSL 3.6.5, libyaml, libffi, zlib, Rust's standard library at 1.96.1, GCC's runtime library at 15.2.0, Mozilla's CA bundle, AppImage's runtime and what it links), and a musl release publishes the LGPL source bundle AppImage's runtime needs, as glibc Linux's does.
- **Parity:** `tasks/parity.rb` compares the built probe with `ruby main.rb` on the Ruby the runtime was built from, which for musl is the runtime's own `bin/ruby` (Ruby's `main.c` against the same libruby) with Fledge's RubyGems defaults taken out, and the gem-shaped probe with `bundle exec`, in Alpine (`ci.yml`, Parity).
- **Build and Delivery:** CI builds hello, the probes, my_cool_app (sqlite3 precompiled for musl), the console probe, and windowed_app in Alpine with Ruby, as a developer on Alpine would, and delivers each in a bare `alpine:3.24` with no Ruby: `deliver.sh --no-ruby-installed`, the console's Ctrl-C and hangup (ADR 015), the desktop entry, and the AppImage, which a container runs extracted.
- **`installed.yml`** installs Fledge from each tag in Alpine, builds with the musl runtime from the release, and delivers.

## Consequences

- Apps run on Alpine and other musl distributions, built on a computer of that platform (ADR 010), such as an Alpine container.
- Fledge maintains a Ruby build of its own for these two targets, and moves its pins (Ruby, OpenSSL, the Alpine image and its packages) on purpose. rv-ruby's musl builds would serve if they kept their extensions as shared objects.
- `examples/native_app` is not built for musl: its lockfile locks no musl platform, and its Rust gem's toolchain in Alpine is another story. Compiling a gem from source works as on glibc Linux (ADR 006), against the runtime's build-only companion.
