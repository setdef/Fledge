# ADR 073: On a phone, a gem's Rust extension is built by its own extconf.rb, as a static library, and linked in

## Context and Problem Statement

On a phone every extension is compiled for the target and linked into the app (ADR 022). Fledge refused a gem whose extension is Rust, built with rb-sys, because rb-sys had never been tried against a phone's Ruby. The maintainer asked that such gems build: "Right, Tauri 2 does phones so it must be possible. If that's the case, we should do it." (`decisions.md`, 2026-11-12). On the desktops they already compile from source (ADR 006), as ferro-idna does.

An rb-sys gem's `extconf.rb` calls `create_rust_makefile`, which writes a Makefile that runs Cargo. Cargo builds a shared library for the computer it runs on, and rb-sys's build script runs bindgen against Ruby's headers through the computer's libclang. A phone needs a static library for its own target, built against the phone Ruby's headers. How does a phone build compile a gem's Rust extension?

## Decision Drivers

- The app's code runs as under `ruby main.rb` (decisions 9 and 20): `require` finds the extension as on a desktop.
- The gem's own build, configuration, and Cargo arguments are kept (ADR 007).
- Each target is built on its own system, with its own tools (`decisions.md`, 2026-10-28), and every tool is pinned (AGENTS.md).
- One mechanism for both phones, as ADR 022 has for C.

## Considered Options

1. Run the gem's own `extconf.rb` under the phone's `rbconfig.rb`, as ADR 022 does, with `create_rust_makefile` wrapped so that Cargo builds a static library for the phone's Rust target, rb-sys reads the phone's Ruby, and bindgen parses with the target's own compiler front end; then link and register the library as a C extension's.
2. Run `cargo rustc --crate-type staticlib` on the crate's `Cargo.toml` directly, skipping the `extconf.rb`.
3. rb-sys's own cross tooling, rb-sys-dock or rake-compiler-dock.
4. On Android, a Rust shared library in `jniLibs`, loaded with `dlopen`.

## Decision Outcome

Chosen: option 1, because it keeps the gem's own `extconf.rb`, its Cargo arguments, and its features, needs no change to rb-sys, and uses the cross-compiling rb-sys's build script already supports: it reads a target Ruby from the `RBCONFIG_*` variables its Makefile exports when `CROSS_COMPILING` is `yes` (rb-sys-build 0.9.130, `rb_config.rs`). Tauri 2 builds Rust for phones the same way, a static library per iOS target and a library per Android ABI from rustup's targets. How the build is aimed, per target, and how bindgen gets the phone's headers: `doc/contributors/design/phone-projects.md`.

Option 2 drops what the `extconf.rb` configures and duplicates rb-sys's own environment. Option 3 is Docker, not the platform's own tool, and knows no phone. Option 4 serves Android alone, since iOS loads no library from a file.

On Android, bindgen parses with the NDK's own libclang, given its resource folder explicitly: the build computer's libclang lacked the builtin headers on one computer and clashed with the NDK's on GitHub's runners, and the NDK's libclang finds its own headers only with `-resource-dir` (a probe on Linux showed "'stdarg.h' file not found" without it and no diagnostics with it). So C and Rust are parsed by one compiler front end.

Confidence: high. `examples/rust_phone`'s gem, built with rb-sys 0.9.130 and magnus 0.9.3, runs in CI's iPhone Simulator and on Android emulators with 4 KB and 16 KB pages, from the debug APK and the release bundle, and its device slice archives without warnings.

### Consequences

- Good, because a gem with an rb-sys extension builds for both phones with no `fledge.yml` key.
- Bad, because a developer needs Rust with the standard library of each phone target; `mise.toml` pins them for Fledge's own builds.
- Bad, because a Rust extension keeps the `Init` name rb-sys gives it, since no `-D` reaches Rust, so two extensions with the same name are refused; two Rust extensions in one app are untested, and each carries its own copy of Rust's standard library.
- Bad, because a gem that loads its extension with `require_relative`, as ferro-idna and Bundler's `bundle gem --ext` template do, builds but fails to load, as any such gem does on a phone (ADR 022).

### Confirmation

`test/integration/mobile_extensions_build_test.rb` builds a Rust extension for each iOS slice and Android ABI and checks its archives; `test/mobile_extensions_test.rb` checks the build's settings; the Mobile apps jobs run `examples/rust_phone` on every phone target.

## More Information

- ADR 022 decides how a phone compiles an extension an `extconf.rb` builds with mkmf; this ADR adds Rust through rb-sys.
- Rust's documentation of `--print native-static-libs`, which names the libraries a static Rust library needs; on iOS, those that are libSystem are left out, since every iOS program links it.
