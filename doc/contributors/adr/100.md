# ADR 100: Take CRuby from jdx/ruby on macOS and glibc Linux, and from RubyInstaller on Windows

## Context and Problem Statement

Each desktop runtime needs a relocatable CRuby built for its platform (ADR 093). Fledge took it from rv-ruby (spinel-coop/rv-ruby) on macOS and glibc Linux, and from RubyInstaller (oneclick/rubyinstaller2) on Windows. Two things rv-ruby's builds could not give moved Fledge off it, one platform at a time.

On glibc Linux, rv-ruby builds on Ubuntu 24.04, so an app needed glibc 2.39 or newer, and did not run on Ubuntu 22.04, Debian 12, RHEL 8 or 9 and their clones, or Amazon Linux 2023. The maintainer had accepted that floor ("2.39 is fine", `decisions.md`, 2026-10-26, decision 7); on 2026-11-22, shown the systems it leaves out, he allowed the Linux Ruby's source to change, "and so would be switching away from rv-ruby entirely if you so judge it valuable".

On macOS, rv-ruby's tree keeps no OpenSSL for gems to compile against. A gem that links OpenSSL, as Puma's does, linked Homebrew's library on a developer's Mac that had one, and `fledge build` refused the app; on a Mac without one it built with no TLS, where the developer's `bundle exec` had it.

jdx/ruby (github.com/jdx/ruby), a fork of rv-ruby that publishes the precompiled Rubies mise downloads, builds the same shape of tree. Its Linux builds are made in manylinux2014 containers and fail if a file needs more than glibc 2.17. Its trees keep the headers, static libraries, and pkg-config files of the OpenSSL and libyaml its Ruby is built with. Its macOS files declare macOS 26.0 as their minimum, where Fledge's floor was 15. Which project's Ruby does each platform take, or does Fledge build its own?

## Decision Drivers

- An app should run on the Linux people run: the distributions their vendors still support.
- A gem that compiles on the developer's computer under `bundle exec` should compile into the app the same way, with no setting (Design precedence 2).
- Fledge maintains as little as it can (AGENTS.md: code is a liability), and takes a maintained project's portable Ruby before it builds one (`decisions.md`, 2026-11-22).
- The Ruby must be relocatable: on macOS and Linux a static libruby the launcher can link (ADR 001), with its extensions as files; on Windows Ruby's DLL in RubyInstaller's tree.
- Every download is pinned by version and SHA-256, and RubyInstaller's by its signature too.
- The app's Ruby behaves as the same Ruby does under `ruby main.rb` (Design precedence 2).

## Considered Options

1. **jdx/ruby on macOS and glibc Linux, RubyInstaller on Windows,** each pinned in `runtime/sources.yml`, with the macOS floor raised to 26.
2. **jdx/ruby on glibc Linux, rv-ruby on macOS, with an OpenSSL for gems that Fledge builds for the Mac,** keeping the macOS floor at 15.
3. **jdx/ruby on glibc Linux, rv-ruby on macOS, as it stood,** with gems that link OpenSSL left to a `fledge.yml` setting.
4. **rv-ruby on macOS and glibc Linux,** as before either move.
5. **Build CRuby in Fledge's CI for these platforms,** in an old-glibc container and on a Mac, as python-build-standalone builds CPython and as Fledge already builds Ruby for musl Linux.

## Decision Outcome

Chosen: option 1, because it lowers the Linux floor and gives gems the runtime's own OpenSSL on both platforms with a maintained Ruby that Fledge does not build, and leaves one upstream for macOS and glibc Linux.

On glibc Linux, jdx/ruby's builds measured at most GLIBC_2.17 in every file, on x86-64 and ARM64. Fledge's own compiled parts (the launcher, `bin/ruby`, libxcrypt) set the floor above that: they are built in the manylinux_2_28 image, pinned by digest, because the compiler of manylinux2014 reports a double free in the launcher that is not there under the analyzer gate, and the gate is not weakened. So the floor is glibc 2.28, which every distribution named above has.

On macOS, option 2 lost because Fledge would build, audit, and keep current an OpenSSL of its own on macOS runners, and a Mac app would then hold two OpenSSL versions in one process, Ruby's and the gems'. Option 3 lost because a gem that builds under `bundle exec` would still be refused or lose TLS. The cost of option 1 is the floor: every file of jdx/ruby's macOS build declares macOS 26.0. The maintainer had allowed it: "I'd be okay moving the floor to 15 for now, and maybe 26 if it becomes costly to keep it at 15." (`decisions.md`, 2026-11-22), and, asked to choose between the floor and a Fledge-built OpenSSL, left the weighing to the agents. macOS 26 runs on every Apple silicon Mac.

Windows stays on RubyInstaller, its x64 and its ARM64 builds. For musl Linux Fledge builds Ruby itself (`doc/contributors/design/runtimes.md`, "musl Linux's Ruby, built in Alpine"). Building Ruby for macOS and glibc Linux too waits until jdx/ruby stops publishing, publishes a build that fails Delivery, or cannot be relied on.

Confidence: high that it works on x86-64 Linux and on Apple silicon. The runtimes built from jdx/ruby pass the license audit, the parity check, and Delivery on a computer of each platform, and a gem that links OpenSSL compiles against the runtime's and runs with the same version Ruby's own `openssl` reports, on glibc Linux, on musl Linux, and on a Mac that has Homebrew's OpenSSL installed. No file in the glibc runtime needs more than GLIBC_2.25, and every file in the Mac runtime declares macOS 26.0. The ARM64 Linux runtime, Delivery on the oldest distributions the floor admits, and the Mac's CI jobs on macOS 26 runners are CI's to show. No recorded comparison says jdx/ruby's builds are better kept than rv-ruby's; what was measured is the glibc each needs, the macOS each declares, and what each tree holds for gems.

### Consequences

- Good, because an app runs on Ubuntu 22.04, Debian 12, RHEL 8 and 9, and Amazon Linux 2023.
- Good, because a gem that links OpenSSL or libyaml compiles against the runtime's own, on macOS and Linux, with no `fledge.yml` setting, and the app holds one version of each.
- Good, because Fledge's Rubies are still ones other projects build and test, and a new Ruby is a pin to move.
- Good, because an app trusts the computer's own certificate store first, as jdx/ruby's Ruby does and as a native program does, and the bundled file only where the computer has none.
- Bad, because a Mac app needs macOS 26 or newer, and no maintained project publishes a portable Ruby for Intel Macs that Fledge now takes, so Fledge builds no Intel Mac apps.
- Bad, because the macOS minimum is the default of the runner jdx/ruby builds on, not a setting of its recipe. A later build may declare a newer macOS; the license audit then refuses the runtime, and the pin cannot move until the floor does.
- Bad, because the libraries inside jdx/ruby's builds are as current as its recipe, which a person there edits: on 2026-11-22 it compiled in OpenSSL 3.5.5, where OpenSSL's newest 3.5 release was 3.5.9. Fledge's pin watch moves the libraries of the runtimes Fledge builds itself, and cannot move these.
- Bad, because Fledge depends on two projects' release schedules for its desktop Rubies, and jdx/ruby is one maintainer's.
- Bad, because the Linux runtime is built in a container, which needs three Perl packages the image lacks, each pinned by SHA-256, and those are not watched for newer builds.
- Bad, because jdx/ruby's tree carries no notices or SBOM, so `runtime/licenses.yml` names what it compiles in (OpenSSL, zlib, libffi, libyaml, libxcrypt, Rust's standard library) from its recipes, and whoever moves the pin checks them again.
- Bad, because jdx/ruby's `rbconfig.rb` puts its own folder first in `PKG_CONFIG_PATH` each time Ruby starts, so the app's value differs from `bundle exec`'s, which starts Ruby twice; `Parity::JUSTIFIED` says so.
- Bad, because a gem compiled on the developer's computer still needs that computer's glibc, so an app with such a gem has the higher floor of the two.
- Bad, because the Mac's Ruby has YJIT and not ZJIT, which rv-ruby's build had.
- Bad, because each upstream tree carries what a developer's Ruby needs, which the runtime builder prunes and replaces, and RubyInstaller's signing key expires on a known date, which whoever moves the pin must follow.

### Confirmation

Every runtime build (`rake runtime`) checks each download against its pin, and RubyInstaller's archive with `gpgv` against the pinned key, by fingerprint. A glibc runtime build fails if any file it stages needs a newer glibc than the platform's floor, and the license audit refuses a macOS runtime with a file whose minimum macOS is above the floor (`doc/contributors/design/license-audit.md`, the `macos-floor` rule). `test/integration/openssl_gem_test.rb` compiles a gem against the runtime's OpenSSL and compares its version with Ruby's. CI's "Licenses of the whole upstream tree" jobs audit each source's whole tree, and CI builds, tests, and delivers every runtime on a runner of its platform.

## Pros and Cons of the Options

### rv-ruby on macOS, with an OpenSSL for gems that Fledge builds

- Good, because the macOS floor stays at 15.
- Bad, because Fledge builds and keeps an OpenSSL for the Mac, on macOS runners, and a Mac app holds two OpenSSL versions.

### rv-ruby on macOS and glibc Linux, as before

- Good, because its tree carries notices and an SBOM, and one project serves macOS and Linux.
- Bad, because its Linux builds need glibc 2.38 on x86-64 by measurement, and 2.39 by the runner they are built on, and its trees keep no OpenSSL for gems.

### Fledge's own build for these platforms

- Good, because Fledge would choose the floors and the libraries, and its pin watch could move them.
- Bad, because Fledge would maintain a build of Ruby on its most used platforms.
