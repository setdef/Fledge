# ADR 099: On a phone, Fledge builds Ruby from source with Ruby's own build

## Context and Problem Statement

Phones are in scope: iOS, iPadOS, and Android, aimed at 1.0 unless they prove incredibly burdensome ([`decisions.md`](https://github.com/setdef/Fledge/blob/7cda540210d56162b0a8698cfc99a0528fe93089/doc/contributors/decisions.md), 2026-10-27).

A phone runs no program of Fledge's own. An iOS app is one signed binary in a bundle, which may load code only from frameworks the bundle carries, never a loose library. An Android app is an APK whose native code Java loads, and whose assets are not files. So a phone's runtime cannot be a launcher with a relocatable Ruby beside it, as a desktop's is (ADR 001). Ruby has to be a library, linked into an app that Xcode or Gradle builds. No one publishes a prebuilt CRuby for either system. Where does the phone's Ruby come from?

## Decision Drivers

- The app's Ruby code runs as under `ruby main.rb`: the whole standard library, every default and bundled gem ([decisions 9, 10, and 20](https://github.com/setdef/Fledge/blob/7cda540210d56162b0a8698cfc99a0528fe93089/doc/contributors/decisions.md)).
- "Code is a liability" ([`decisions.md`](https://github.com/setdef/Fledge/blob/7cda540210d56162b0a8698cfc99a0528fe93089/doc/contributors/decisions.md), 2026-10-28): use maintained tools, and write only what none does.
- Each target is built on its own system, with that system's tools ([`decisions.md`](https://github.com/setdef/Fledge/blob/7cda540210d56162b0a8698cfc99a0528fe93089/doc/contributors/decisions.md), 2026-10-28).
- Every input is pinned by version and SHA-256 (`doc/contributors/design/architecture.md`, "What the design answers to").
- The runtime carries no copyleft obligation beyond notices (decision 8).

## Considered Options

1. Build CRuby from its release tarball with Ruby's own `configure` and `make`, cross-compiled with Xcode's or the NDK's compilers, after xord/cruby's iOS recipe and Termux's Android one, and pack it as an XCFramework and an AAR.
2. Use xord/cruby's Rakefile itself (the build behind RubySketch, on the App Store).
3. Use Termux's Ruby packages (`termux-packages/packages/ruby/build.sh`).
4. Port CPython's `Apple/` and `Android/` build scripts to Ruby.

## Decision Outcome

Chosen: option 1, because it alone gives a standard Ruby that Fledge pins, with nothing it does not need. xord/cruby's Rakefile builds an older Ruby and folds every bundled gem into the standard library, so the gems stop being gems. Termux's packages build for Termux's own prefix, with its `libandroid-support`. CPython's scripts build Python, and porting them would be more code of Fledge's than following Ruby's own build. What is Fledge's own is the order of the maintained tools' commands, a few scripted edits to Ruby's source, and the embedding API.

How the runtime is built and what it holds is `doc/contributors/design/phone-runtimes.md`. The shape of the library the build makes, shared with each extension a file, follows from [decisions 9, 10, and 20](https://github.com/setdef/Fledge/blob/7cda540210d56162b0a8698cfc99a0528fe93089/doc/contributors/decisions.md) and is in that document too, in "Why Ruby is a shared library, with each extension a file".

Confidence: high that it works in the iOS Simulator and on Android emulators. With Xcode 27.2, on an iPhone and an iPad in the Simulator, every parity app and the iOS integration tests pass, and ruby/spec shows no unjustified difference; every example archives unsigned for devices and passes Fledge's checks of an archive's structure. Android's shared library passed the same checks on an x86-64 emulator.

### Consequences

- Good, because the runtime is Ruby's own build, with every default and bundled gem a gem, so the parity check finds only the differences a phone forces.
- Good, because each input, from Ruby's tarball to the NDK and Gradle, is pinned in `runtime/sources.yml`.
- Good, because the iOS runtime builds on a Mac with Xcode, and the Android runtime on Linux or a Mac with Google's NDK, each with its own tools.
- Bad, because a cross build needs work Ruby's build does not do, which each new Ruby means checking again: scripted edits to its source, and a builtin binary written by a miniruby for the build machine (`doc/contributors/design/phone-runtimes.md`).
- Bad, because the Android arm64-v8a library runs on no CI runner, only on a real phone (`doc/contributors/design/public-interface.md`, "Phones").
- Bad, because CI builds both runtimes on every push, which costs macOS and Linux runner minutes.
- Neutral: App Store and Play review need the developer accounts, which are paid for ([`decisions.md`](https://github.com/setdef/Fledge/blob/7cda540210d56162b0a8698cfc99a0528fe93089/doc/contributors/decisions.md), 2026-11-04). [`doc/contributors/account-tests.md`](https://github.com/setdef/Fledge/blob/7cda540210d56162b0a8698cfc99a0528fe93089/doc/contributors/account-tests.md) lists those tests.

### Confirmation

CI's `runtime-mobile` jobs build both runtimes from `runtime/sources.yml` and run the license audit on them. The `mobile-apps-ios` and `mobile-apps-android` jobs build apps on them and run each in the Simulator and on emulators with 4 KB and 16 KB pages (`tasks/mobile_parity.rb`), and the mobile parity check compares the probe with `ruby main.rb`. `test/mobile_runtime_test.rb` checks the runtimes' targets, pins, and configuration, `test/ruby_source_test.rb` the edits to Ruby's source, and `test/integration/mobile_default_gems_test.rb` the default gems of built ones: an Android runtime's in the `mobile-apps-android` jobs, and an iOS runtime's in the `mobile-tests-ios` job, which runs the iOS integration tests and fails one that would skip for want of a runtime or a tool (`FLEDGE_REQUIRE_IOS`).
