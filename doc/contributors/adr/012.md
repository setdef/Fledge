# ADR 012: For a phone, `fledge build` writes a project the developer builds, signs, and submits

## Context and Problem Statement

A phone's runtime is Ruby as a library: an XCFramework and an AAR (ADR 079). With only that, a developer still has to make an Xcode or Gradle project, link the runtime, copy Ruby's library and the app's code into the bundle or an asset, set up the app's gems, and write the lines that start Ruby. Each step can go wrong in a way only a phone shows.

No phone builds an app, and no store takes an app that Fledge signs. The developer signs with their own Apple or Google credentials and submits the app themselves. App Store guideline 4.2.6 asks this of anything built from a template: "Apps created from a commercialized template or app generation service will be rejected unless they are submitted directly by the provider of the app's content" (`doc/contributors/research/2026-10-27-mobile.md`). What should `fledge build` hand a developer for a phone?

## Decision Drivers

- A person who runs the app never meets Ruby (precedence 1), and a developer who ships one should not have to learn how Ruby embeds.
- The developer's own tools build, sign, and submit (Xcode, Gradle, Android Studio), as stores expect.
- "Code is a liability" (`decisions.md`, 2026-10-28): Fledge writes no Xcode project file or Gradle build of its own making where a maintained tool writes one.
- Prior art: Briefcase's `briefcase create iOS` and `create android`, Flutter's `flutter create`, Tauri's `tauri ios init` and `android init`, and React Native's template all write a project the developer then builds.

## Considered Options

1. `fledge build` writes a whole project around the runtime, with the app and its gems in it, which the developer builds, runs, signs, and submits with the platform's tools.
2. The developer integrates the runtime by hand, as CPython's iOS documentation asks: drag `Python.xcframework` into an Xcode project, turn off user script sandboxing, and add a build phase that copies the standard library.

## Decision Outcome

Chosen: option 1, because every step option 2 leaves to the developer is a step Fledge can get right once, as Briefcase, Flutter, Tauri, and React Native do. Option 2 is what the runtime alone offered, and it asked the developer to learn the runtime's layout. Nothing in the project configures signing, and Fledge never submits an app.

Confidence: high that the projects build and run: CI builds, archives, and runs them. Medium for the stores: no Fledge app has been through App Review or Play's review yet.

### Consequences

- Good, because a developer with a pure-Ruby app runs `fledge build ios` or `fledge build android`, opens the project, and runs it in the Simulator or an emulator.
- Good, because the project is the developer's to change, in Xcode or Android Studio.
- Good, because signing and submission stay with the developer's own keys, certificates, and accounts. Fledge holds none.
- Bad, because the developer installs XcodeGen, and a JDK with the Android SDK.
- Bad, because `fledge build` writes the project afresh each time, so a change made in it by hand lasts until the next build.
- Bad, because the templates are Fledge's code, and their compiled host ships in every phone app, so `doc/licensing.md` names it (MIT, decisions, 2026-11-07).
- Neutral: the store checks that need an account wait on the accounts the maintainer pays for (`decisions.md`, 2026-11-04), listed in `doc/contributors/account-tests.md`.

### Confirmation

CI's `mobile-apps-ios` job builds every example's project with `xcodebuild` for the Simulator, archives it unsigned for devices and checks the archive (`tasks/mobile_parity/ios_archive.rb`), runs each app in the Simulator on an iPhone and an iPad, and runs the iOS integration tests of what a project holds (`test/integration/mobile_extensions_build_test.rb`), where a test skipped for want of a runtime or a tool fails the job. The `mobile-apps-android` jobs build each project with its wrapper as APKs and app bundles, check them (`tasks/mobile_parity/android.rb`), and run each app on emulators with 4 KB and 16 KB pages; they also run the Android integration tests of what a project holds and of what its native libraries export (`test/integration/mobile_extensions_build_test.rb`, `test/integration/mobile_extension_symbols_test.rb`), where a test skipped for want of a runtime, a tool, or a device fails the job. `mobile-apps-android-hosts` builds a project on macOS and Windows. `test/mobile_build_test.rb` and `test/mobile_template_contract_test.rb` test the projects' contents.
