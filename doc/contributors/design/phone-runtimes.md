# Phone Runtimes

This document says how Fledge's phone runtimes are built and what they hold, how the embedding API starts an app's Ruby, and what a phone runtime's licenses are. ADR 097 records why a phone's Ruby is a static library Fledge builds from source; the rest of the design, and why each part is as it is, is here. The projects `fledge build` writes around a runtime, and what CI checks before a store would, are `doc/contributors/design/phone-projects.md`. What a developer does with the project is in `doc/phones.md`; this document adds the internals.

## Targets

A phone runtime has two targets, named in RubyGems' grammar so that no desktop gem fits them. `RuntimeBuilder::Mobile::PLATFORMS` (`tasks/runtime_builder/mobile.rb`) holds them.

| Runtime | Target | What | Its Ruby's `RUBY_PLATFORM` | Compiler triple |
|---|---|---|---|---|
| `ios` | `arm64-ios` | iPhones and iPads | `arm64-darwin` | `arm64-apple-ios15.0` |
| `ios` | `arm64-ios-simulator` | the iOS Simulator on Apple silicon | `arm64-darwin` | `arm64-apple-ios15.0-simulator` |
| `android` | `aarch64-linux-android` | arm64-v8a phones and tablets | `aarch64-linux-android` | `aarch64-linux-android` (API 26) |
| `android` | `x86_64-linux-android` | x86_64 emulators and Chromebooks | `x86_64-linux-android` | `x86_64-linux-android` (API 26) |

Gem::Platform reads `arm64-ios` as `arm64-unknown`, which matches no desktop gem, and reads the Android names as Linux with Android's C library, which no `-linux`, `-gnu`, or `-musl` gem matches. The floors are iOS 15.0 (xord/cruby's and the spike's) and API 26, Android 8.0, the first whose C library has `nl_langinfo`, which Ruby's `localeinit.c` calls.

The names keep Ruby's own platform true to the system and keep desktop gems out where Fledge decides. Ruby built for iOS reports `RUBY_PLATFORM` `arm64-darwin`, as macOS does, so its own `Gem::Platform.local` matches every `arm64-darwin` gem, and Bundler, resolving a lockfile there, would pick nokogiri's macOS build, which can never load on a phone. A name that said `darwin` would read as macOS. Configuring Ruby for an `ios` host, so that `RUBY_PLATFORM` itself said `ios`, would leave out what Ruby's `configure.ac` does for a Darwin host, which the iOS build relies on, as xord/cruby's does, and an app's `RUBY_PLATFORM =~ /darwin/` would stop matching a system that is Darwin. Apple's `arm64-apple-ios` and `arm64-apple-ios-simulator`, PEP 730's (the same), and Rust's `aarch64-apple-ios` and `aarch64-apple-ios-sim` carry a vendor or an abbreviation that RubyGems' Linux names drop (`aarch64-linux-android`, not `aarch64-unknown-linux-android`); Fledge's iOS names drop the vendor the same way. The Android names are Ruby's own `RUBY_PLATFORM` there.

No gem publishes a build for these names, so a phone's app takes each gem's `ruby` build, and its Bundler runs with `force_ruby_platform`, for which the lockfile has to lock `ruby` (`doc/contributors/design/phone-projects.md`, "Gems on a phone"). Fledge's iOS names are its own: no RubyGems tool knows them, and a gem cannot publish a build for them. An app sees the platform Ruby reports on that system, so `RUBY_PLATFORM`, `RUBY_DESCRIPTION`, and the load path's platform folders differ from a desktop Ruby's, which `Parity::MOBILE_JUSTIFIED` (`tasks/parity/mobile.rb`) justifies. `test/mobile_runtime_test.rb` checks that no desktop platform matches any phone target, and `test/mobile_platform_test.rb` checks the lockfile's names and `force_ruby_platform?`.

The iOS runtime is built on a Mac (`arm64-darwin`), since only Xcode builds for iOS. The Android runtime is built on x86-64 Linux in CI, and a Mac may build it too, with Google's NDK. An x86-64 Linux computer with KVM builds it, and the apps around it, and runs them on an emulator with nothing but what `mise.android.toml` pins by SHA-256: the JDK, the NDK, and the SDK's packages, which `bin/android-sdk` lays out as one SDK and `bin/android-emulator` boots an emulator from (`CONTRIBUTING.md`, "Android on Linux"). Neither is built on the other's runner.

## What a phone runtime holds

Each runtime is a release asset of its own, `fledge-runtime-VERSION-ios.tar.gz` and `fledge-runtime-VERSION-android.tar.gz`, with its SBOM and NOTICES beside it as every runtime has (`doc/contributors/design/license-audit.md`).

**iOS** is `FledgeRuby.xcframework`, made by Apple's `xcodebuild -create-xcframework` from one static library per target, in the slices `ios-arm64` and `ios-arm64-simulator`. Each slice holds:

- `libfledgeruby.a`: Ruby, its extensions and encodings, OpenSSL, libyaml, and the embedding API, merged by Apple's `libtool -static`, with debug information stripped;
- `Headers/`: Ruby's headers, with the slice's `ruby/config.h` moved beside the rest so one folder serves `#include <ruby.h>`, and the embedding API's `fledge_ruby.h` with a Clang module map (`runtime/mobile/module.modulemap`), so Swift imports it as `FledgeRuby` and linking it adds libz and the Security and CoreFoundation frameworks;
- `lib/ruby` and `libexec/cert.pem`: the Ruby the slice runs, which the app copies into its bundle for the slice it builds, as CPython's iOS XCFramework carries its standard library per slice.

The two slices' Rubies differ only in the compiler their `rbconfig.rb` records. One binary runs on iPhone and iPad.

**Android** is `FledgeRuby.aar`, packed by the pinned Gradle and Android Gradle plugin from `runtime/mobile/android/`, holding, for arm64-v8a and x86_64, `libfledgeruby.so`, the ruby program `libfledgerubyexe.so` (see "The ruby program on Android"), and each of Ruby's own extensions, encodings, and bundled gems' extensions as a native library of its own, `libfledgerubyext.PATH.so` (see "Ruby's extensions on Android"), and the Java class `org.setdef.fledge.FledgeRuby`. Beside it are `fledge.links`, which lists where under the app's Ruby each of those extensions belongs, one `lib/ruby` for both ABIs (Ruby names each ABI's folder of platform-specific files for its platform, so both fit one tree, and the build fails if any other file differs between them), `libexec/cert.pem`, `include/`, and `bin/`, with the wrappers RubyGems wrote for the gems' commands, as a desktop runtime's `bin/` has them, but not the `ruby` program Ruby's `make install` put beside them (see "Gem commands on Android").

`libfledgeruby.so` is Ruby's shared library, so native code that links it finds Ruby's whole C API, as it finds it in a desktop's `libruby.so`. OpenSSL, libyaml, and libffi are not in it: each is linked into the one extension that uses it, `openssl.so`, `psych.so`, and `fiddle.so`, as a desktop's extension links its library, and none of the three links another library by name, so an app's own copies cannot clash with them (Android's linker resolves a library's symbols against the libraries it needs, and nothing needs an extension). The build fails unless `libfledgeruby.so` and each extension need only Android's `libc`, `libm`, `libdl`, `liblog`, and `libz`, and the extensions `libfledgeruby.so` too, and unless every LOAD segment is aligned to 16 KB, which Google Play requires of 64-bit apps from 2027-02-01.

Each runtime's top also holds `RUBY_DESCRIPTION`, the description its Ruby compiled into `libfledgeruby` (`ruby 4.1.0preview1 (2026-10-11 master 2d08b5f42f)`), which `fledge build` reads and no project copies (`doc/contributors/design/runtimes.md`, "The Ruby's description").

The iOS runtime has no Ruby program and no gems' commands, since iOS lets no app run one. The Android runtime's ruby program is a native library by name, which the app's installer extracts, and `ROOT/bin/ruby` is a link to it that the embedding API makes as the app starts (see "The ruby program on Android"); so is each gem's command, `ROOT/bin/NAME` (see "Gem commands on Android").

fiddle is in both runtimes, as in a desktop's, so `require "fiddle"` works on a phone as under `ruby main.rb` (decisions 9 and 20), and the mobile parity check compares it. xord/cruby leaves it out of its iOS Ruby "to pass the App Store review" (`Rakefile`, line 577 at 11d62c4), and the maintainer asked that a reason to leave it out be cited, not assumed (decisions, 2026-11-12). No source forbids it (`doc/contributors/research/2026-11-12-ffi-and-fiddle-on-phones.md`, with each source and when it was read): App Review Guidelines 2.5.1 and 2.5.2 govern which functions an app calls and whether it downloads code, and name no FFI; `dlopen` and `dlsym` are public in the iPhoneOS SDK; CPython's iOS build compiles `ctypes` against libffi (v3.13.0, `iOS/README.rst`, lines 179 to 188), and BeeWare's iOS Python and Pythonista ship it; and on Apple's arm64, libffi makes closures from a pre-signed page remapped with `vm_remap` (`closures.c`, lines 161 to 245), so no page is both writable and executable. Each runtime keeps fiddle's libffi to fiddle, Android's in `fiddle.so` and iOS's in fiddle's own object (see "Building Ruby for a phone"), so an app whose gem links a libffi of its own, as the ffi gem does, finds no second definition of any (`doc/contributors/design/phone-projects.md`, "Gems with extensions").

## Ruby's C headers on a phone

Both phone runtimes ship Ruby's C headers, for the computer that builds the app: each iOS slice in `Headers/`, and the Android runtime in `include/` (both ABIs' `include/ruby-VERSION/` merged, with each ABI's configuration folder, and `fledge_ruby.h`). mkmf compiles a gem's extension against them (see `doc/contributors/design/phone-projects.md`, "Gems with extensions"), and native code that links the runtime includes them.

The app on the phone carries Ruby's headers too, as a desktop runtime does, since mkmf looks for `ruby/ruby.h` under `RbConfig::CONFIG["rubyhdrdir"]` before anything else and aborts where it is missing (`doc/contributors/design/runtimes.md`). Each iOS slice holds its Ruby's `include/` beside `lib/` and `libexec/`, all three of which the iOS project's build phase copies into the bundle, and the Android project puts the runtime's `lib/` and `libexec/` in `fledge/`, with the runtime's `include/ruby-VERSION/` in `fledge/include/`, leaving `fledge_ruby.h` to the native code that links the runtime. So `require "mkmf"` loads on a phone, and on Android `find_executable` finds the system's programs, but nothing compiles there: a phone has no compiler for mkmf to run, iOS lets an app start no program, and Android only the ones its package carries. The parity probe reports whether mkmf's header is where it looks. The headers add about 1.6 MB to each app before compression.

## Building Ruby for a phone

`RuntimeBuilder::IOS` and `RuntimeBuilder::Android` (`tasks/runtime_builder/ios.rb` and `android.rb`, over `mobile.rb`) build the pinned Ruby from its release tarball with Ruby's own `configure` and `make`, after xord/cruby's Rakefile on iOS and Termux's `packages/ruby/build.sh` on Android. Every input is pinned by version and SHA-256 under `mobile:` in `runtime/sources.yml`: Ruby's tarball, OpenSSL, libyaml, libffi, the NDK for each computer that runs it, Gradle and the Android Gradle plugin, Mozilla's CA certificates as curl publishes them, XcodeGen, and bundletool. Xcode is chosen by version on the runner, since Apple publishes no download to pin.

For each target the build:

1. builds libyaml and libffi with their own `configure` (`--enable-static --disable-shared --with-pic`), and OpenSSL with its own `Configure` target for the platform (`ios64-xcrun`, `iossimulator-arm64-xcrun`, `android-arm64`, `android-x86_64`), with no shared library, programs, tests, documents, or modules;
2. unpacks Ruby's tarball into a folder of the target's own, makes the scripted edits (see "Scripted edits to Ruby's source"), on iOS copies the bundled gems' extensions in (see "Bundled gems' extensions"), and configures Ruby in that folder, its source, with `--enable-load-relative --without-gmp`, on iOS `--disable-shared --with-static-linked-ext` and on Android `--enable-shared --with-soname=fledgeruby` (see "Ruby's extensions on Android"), the target's JITs (see "The JITs", below), the dependencies' folders, `--with-out-ext` for Windows' extensions and, on iOS, the bundled gems' own builds, and `PKG_CONFIG=false`, so nothing of the build machine's leaks in. `--without-git` keeps a preview's `gems/bundled_gems`, which names commits for some bundled gems, from having `extract-gems` clone them from GitHub, unpinned, in place of the gems in the tarball that the SHA-256 pins. `--with-dump-ast` names the `dump_ast` built beside the build machine's miniruby (see "The builtin binary"), since a cross build cannot run the one it would build for the target;
3. writes the builtin binary (see "The builtin binary"), runs `make` with `yes_cross_compiling=` empty, so that `common.mk` does not hand the bundled gems' build the `--without-ext` that a cross build takes and that would bring their builds back, on iOS marks the bundled gems' extensions built, and runs `make install-nodoc`;
4. on iOS checks the bundled gems were installed, prunes the tree as a desktop runtime is pruned, and installs Fledge's RubyGems defaults (`doc/contributors/design/runtimes.md`).

Ruby is built in its source folder because a desktop's is: rv-ruby runs `./configure` and `make` there (`Abstract/rv-ruby.rb`, lines 157 to 174 at spinel-coop/rv-ruby f57186e), and what Ruby's install writes depends on the folder it runs in. `tool/rbinstall.rb` writes each default gem's specification by evaluating the gem's gemspec in the folder `make` runs in, and its `load_gemspec` (lines 921 to 928 at Ruby 4.1.0-preview1) puts `lib/` before each `.rb` file the gemspec lists that it finds no file for there; bundler's gemspec also globs its files from that folder. The phone runtimes used to configure Ruby in a folder beside its source, and their specifications differed from a desktop's: io-nonblock's listed `lib/ext/io/nonblock/extconf.rb`, so RubyGems' `register_default_spec` (`lib/rubygems.rb`, lines 1312 to 1342) took it for a gem whose files sit under `lib/` and left out `io/nonblock.bundle`, which is not under `lib/` and has a slash. `require "io/nonblock"` loaded the linked extension without activating the gem, and `Gem.loaded_specs` had no io-nonblock. Bundler's listed none of its manual pages and templates, and fileutils, forwardable, ipaddr, pp, and the gems with an `extconf.rb` listed their own files twice. Ruby's main branch has since changed `load_gemspec` (ruby/ruby 2cdfc0d20e, for Bug #22420), so that it registers the extension of every gem the build collects, io-console's among them; a phone takes whatever the pinned Ruby does, built as a desktop's is. Each target unpacks the tarball into a folder of its own, since a build in place leaves its objects among the source, and the build machine's miniruby (see "The builtin binary") builds beside one more.

What each system adds:

- **iOS** builds with Xcode's clang (`xcrun --sdk iphoneos|iphonesimulator`), aimed at the target's triple and the SDK's sysroot, configured for the host `aarch64-apple-darwin` so that Ruby's `configure.ac` does what it does for Darwin. After xord/cruby it passes `--disable-dln`, tells configure that iOS has no `system`, `syscall`, `__syscall`, `backtrace`, `getentropy`, `dup3`, or `pipe2` (`RuntimeBuilder::IOS::MISSING`), adds a stub `sys/vnode.h` the SDK lacks (xord/cruby's, with its MIT notice as an SPDX snippet in `ruby_source.rb`; it is a header Ruby compiles against, and nothing of it ships), and builds with `-Os -fvisibility=hidden` and `-framework Security`. OpenSSL's Simulator build takes `-mios-simulator-version-min`, since with `-mios-version-min` its assembly is tagged for devices and the Simulator's link fails. fiddle's relocatable object takes in the libffi it links, which `libfledgeruby.a` then leaves out, so libffi's symbols are local to fiddle, as they are in Android's `fiddle.so`, and an app whose gem links a libffi of its own, as the ffi gem does, finds no second definition of any (`RuntimeBuilder::IOS#relocatable`).
- **Android** builds with the NDK's `TRIPLE26-clang`, `llvm-ar`, and `llvm-ranlib`, and tells configure what it cannot find out by compiling (`RuntimeBuilder::Android::CONFIGURE`). Android's seccomp filter for apps stops a process with SIGSYS when it calls `setgid`, `setuid`, `setregid`, `setreuid`, `setresgid`, or `setgroups`, and lets it call `setresuid` (bionic, `libc/SECCOMP_BLOCKLIST_APP.TXT`, lines 9 to 30 at 731631f); bionic's `setegid` calls `setresgid`, its `initgroups` calls `setgroups`, and its `seteuid` calls `setresuid`. configure finds every one of them in bionic, as on Linux, and the `process_c_ids` edit (below) has `process.c` call its own of each in their place, which answer as Linux answers a process without `CAP_SETUID` or `CAP_SETGID`, as an app's is, and make only the calls the filter allows: `Process.gid=`, `Process.egid=`, `Process.uid=`, `Process.euid=`, and the changes of `Process::GID`, `Process::UID`, and `Process::Sys` succeed for the app's own ID and raise `EPERM` for any other, and `Process.groups=` and `Process.initgroups` raise `EPERM`. So configure is told only that there is no libcrypt, as Termux tells it, so `String#crypt` is Ruby's own `missing/crypt.c`, and Termux's fix for clang (`rb_cv_type_deprecated`). Termux also tells configure that `setgroups`, `setreuid`, and `setresuid` are missing (termux-packages, `packages/ruby/build.sh`, line 19 at 750b3fc), "to fix compilation on android", not for the filter; Fledge's build compiles with them. The NDK is unpacked from its pinned download and checked to be the revision `runtime/sources.yml` names.

Then each system packs what it built. iOS merges every archive Ruby's build made (libruby, each extension's, the encodings' and transcoders'), `extinit.o` and `encinit.o`, the libraries, and the embedding API's objects into `libfledgeruby.a` per slice, leaving out libruby's `dmyext.o` and `dmyenc.o`, the empty `Init_ext` and `Init_enc` of a Ruby without static extensions: the linker would take them before `extinit.o`'s and `encinit.o`'s, and `require "json"` would fail. Android links `libfledgeruby.so` per ABI again, as Ruby's build links its shared library (`template/Makefile.in`, lines 354 to 360 at Ruby 4.1.0-preview1), from the objects of `libfledgeruby-static.a` with `dmyext.o` and `dmyenc.o`, by which Ruby loads its extensions and encodings from files, and the embedding API's, with `-soname,libfledgeruby.so` and `-z max-page-size=16384`; makes local the symbols Ruby's build makes local there (`Init_*`, `InitVM_*`, `ruby_static_id_*`, `*_threadptr_*`, `*_ec_*`); and strips it. The embedding API's C is compiled with the launcher's warnings as errors and checked by clang's static analyzer.

**The JITs.** Android's Ruby has YJIT and ZJIT, each off until the app enables it, as the Rubies of the macOS and Linux runtimes have them, and iOS's has neither. iOS gives no app memory it may write code into and run, but a browser's web content extension (BrowserEngineKit, "Protecting code compiled just in time"), so its Ruby is configured `--disable-yjit --disable-zjit`, which `Parity::MOBILE_JUSTIFIED` justifies. Android lets an app write code and run it: AOSP's sepolicy allows `execmem` to every app, under "WebView and other application-specific JIT compilers" (`private/app.te`, lines 188 and 189), and Google Play's Device and Network Abuse policy exempts code that "runs in a virtual machine or an interpreter" from its rule against downloaded code. Ruby's `configure.ac` builds no JIT by itself for a cross build, since "we can't easily cross-compile with rustc" (lines 3894 to 3910 at Ruby 4.1.0-preview1), so the Android build passes `--enable-yjit --enable-zjit` (`RuntimeBuilder::Android.jit_options`). With both, `configure.ac` takes its release build of the two together, which needs `rustc` alone and passes `rustc_flags` to every crate, so `rustc_flags=--target=TRIPLE` aims both at the target; the NDK's `ld.lld` and `llvm-objcopy` are `LD` and `OBJCOPY`, which configure would otherwise take from the build machine. A build with Cargo (`--enable-yjit=dev` or `=stats`) would need Cargo where the release build needs only `rustc`. YJIT alone, or no JIT, would be a difference no platform requires: ZJIT is experimental in Ruby 4.1, but it is in the Rubies a developer runs, and an app may enable it. The build machine's miniruby has the same JITs (see "The builtin binary"). Building the Android runtime then needs Rust with Android's two standard libraries, which `mise.toml` adds, and `libfledgeruby.so` carries Rust's standard library, under MIT or Apache-2.0 (see "Licenses of a phone runtime"). `test/mobile_runtime_test.rb` holds each system's JIT options, the parity probe measures `RubyVM::YJIT.enabled?`, `RubyVM::ZJIT.enabled?`, and `RbConfig`'s `YJIT_SUPPORT` and `ZJIT_SUPPORT`, and MobileHello on Android enables YJIT and reports machine code.

## Scripted edits to Ruby's source

`RuntimeBuilder::RubySource` (`tasks/runtime_builder/ruby_source.rb`) makes a few edits to Ruby's source before it builds. Each fails the build when the lines it replaces are gone, so a new Ruby shows which to look at again. The two that take a fix from Ruby's master, `process_c` and `thread_c`, first look for that fix as the commit wrote it, and leave a Ruby that has it as it is, so a snapshot of Ruby's master builds with the edits the pinned release needs; one that has neither the old lines nor the fix still fails.

| Edit | System | What it does | From |
|---|---|---|---|
| `psych_extconf` | both | psych's `extconf.rb` stops preferring pkg-config's libyaml | xord/cruby |
| `vm_dump` | iOS | `vm_dump.c` stops calling `system()` | xord/cruby |
| `configure_macos_minimum` | iOS | the generated `configure` keeps its check for macOS 10.6 or later for a macOS target only, since the iOS SDK reports 10.5 for an iOS one (ruby/ruby 3e96f16643) | Fledge; `doc/contributors/drafts/ruby-ios-configure.md` |
| `configure` | Android | the generated `configure` stops appending `-android` twice, so the platform is `aarch64-linux-android`, not `aarch64-linux-android-android` | Termux's guard |
| `configure_soname` | Android | the generated `configure` names the shared Ruby `libfledgeruby.so`, with that SONAME, without Linux's version (see "Ruby's extensions on Android") | Fledge, after `configure`'s own names for macOS |
| `openssl_extconf` | Android | ext/openssl's `extconf.rb` links `openssl.so` with `--wrap=X509_get_default_cert_file`, after its checks, and `openssl_certificates.c` is copied beside its sources (see "Certificates") | Fledge |
| `ruby_c` | both | `ruby.c` gains `ruby_embed_libruby_path`, through which an embedder names the file Ruby would otherwise find with `dladdr` and derive its prefix from (`runtime_libruby_path`, lines 593 to 663 at Ruby 4.1.0-preview1) | Fledge |
| `prism_compile_c`, `ruby_c_source` | Android, in lines compiled only under `__ANDROID__` | Prism's `pm_load_file` and parse.y's `open_load_file` ask `ruby_embed_source_path`, when an embedder set it, for a file to read in place of the one they are given, which stays the file's name; the runtime reads a gem's command's wrapper in place of its link (see "Gem commands on Android") | Fledge |
| `load_c` | both | `load.c` finds a bundled gem's linked extension only while its gem is active (on iOS; Android links none in), and any linked extension, an Android app's in `libfledgeext.so` among them, by the path or DLEXT name of its file (see "Bundled gems' extensions") | Fledge |
| `setproctitle_c` | Android | `$0=` and `Process.setproctitle` write the title into the process's own argument area, which `/proc/self/stat` names, where the argv Ruby was given is not in it, as an app's is not, so `ps` and `/proc/PID/cmdline` show it as on Linux | Fledge, after Android's `AndroidRuntime::setArgv0` |
| `process_c_ids` | Android | `process.c` answers `setgid`, `setegid`, `setregid`, `setresgid`, `setgroups`, `initgroups`, `setuid`, and `setreuid` as Linux answers a process without `CAP_SETUID` or `CAP_SETGID`, without the calls Android's seccomp filter stops | Fledge |
| `file_c` | iOS | `rb_group_member` answers that the process is in no other group when `getgroups` fails, where it took the -1 for a count | Fledge; `doc/contributors/drafts/ruby-group-member.md` |
| `process_c`, `thread_pthread_c` | Android | the child of a fork resets its copy of the fork lock without unlocking it | ruby/ruby e06b9da3f2 |
| `thread_c` | Android, and the musl runtimes (`RuntimeBuilder::Musl::EDITS`) | `Thread#name=` names the native thread only of a thread that has not ended | ruby/ruby 6fdd452087 |
| `process_c_umask`, `file_c_umask` | Android | the `umask:` option and `File.umask` give `umask` only a mask's permission bits, as Linux keeps them, since bionic's fortified `umask` aborts on any other bit | Fledge; `doc/contributors/drafts/ruby-umask-fortify.md` |
| `dir_c` | Android | `dir.c` gets the `IFTODT` bionic lacks, so it reads each entry's type from `d_type` as on Linux | Fledge; `doc/contributors/drafts/ruby-glob-base-dir.md` |

`ruby_c` exists because on Android Ruby's library sits in a folder of native libraries alone, and an iOS app may keep Ruby anywhere in its bundle, so neither prefix is where `dladdr` would point.

`prism_compile_c` and `ruby_c_source` exist because an Android app may run no script from its own files, so a gem's command is a link to the ruby program, and Ruby must read RubyGems' wrapper wherever it reads that link as Ruby. Every Ruby file Ruby 4.1 reads goes through one of two readers: Prism's `pm_load_file` (`prism_compile.c`, lines 11034 to 11080 at Ruby 4.1.0-preview1), for the main script (`ruby.c`, `prism_script`, line 2277), `load` and `require` (`load.c`, line 749), and `RubyVM::InstructionSequence.compile_file` (`iseq.c`, line 2044); and `open_load_file` (`ruby.c`, lines 2914 to 2984), for `--parser=parse.y` and the main script's `DATA` (line 2298). Each edit adds, after the reader's first lines, a call of `ruby_embed_source_path` that may name another file to open, and opens the path it was given otherwise; the path it was given stays the name `__FILE__`, `$0`, backtraces, and every message carry. With no function set, as in every Ruby but an Android app's, and for every path the function declines, Ruby reads exactly what it read before, a path that fails to open included. The added lines sit inside `#ifdef __ANDROID__`, so the iOS runtime's Ruby, or any other, would compile to the same Ruby with the edit as without; `test/ruby_source_test.rb` checks that removing those blocks gives back Ruby's own lines. At each new Ruby, check that these two readers are still the only ones: `grep -n 'pm_load_file\|open_load_file\|pm_source_mapped_new\|pm_string_mapped_init' *.c` in its source, and every caller of a new one. Both edits apply to the pinned Ruby and to Ruby's master snapshot of 2026-11-20. The license audit finds Ruby in `libfledgeruby.so` by its revision, `2d08b5f42f` (`runtime/licenses.yml`), which no edit here changes.

`setproctitle_c` exists because an Android app's Ruby is a library in a process the zygote forked, and starts with an argv `fledge_ruby_run` allocates, so Ruby's `missing/setproctitle.c`, which writes the title over that argv, wrote it where the kernel never looks. Android names an app's process by clearing the zygote's argument area and copying the name in, cut to the area's length (`AndroidRuntime::setArgv0`, `core/jni/AndroidRuntime.cpp`, lines 328 to 347 at android-14.0.0_r1), a call it hides from apps. The kernel gives that area's bounds in `/proc/self/stat` (`arg_start` and `arg_end`, fields 48 and 49), and Ruby's own `setproctitle` clears and writes it the same way once pointed there. That area holds only the zygote's own command line, which `setArgv0` overwrote with the app's identifier, so a longer title would be cut there. Linux's Ruby has more room: it copies `environ` to its own memory and writes on into the environment's strings, which follow the arguments (`compat_init_setproctitle`, `missing/setproctitle.c`, lines 155 to 166 at 4.1.0-preview1), and the kernel reads a title on into them (`get_mm_cmdline`, `fs/proc/base.c`, lines 313 to 320 at v6.12). So does an app's: where the environment's strings follow the argument area (`env_start` and `env_end`, fields 50 and 51), as the zygote's do, the edit gives `setproctitle` both, as Linux's Ruby measures them, once Ruby has copied `environ`. The risk is the one Linux's Ruby takes, larger: `getenv` reads Ruby's copies, but a pointer some library kept into the old strings reads the title, and in an app the zygote, ART, and the app's Java ran before Ruby and had more chances to keep one. No run has shown one. The parity probe's title is 150 characters, longer than an app's argument area, so its fact `$0= titles the process` measures the length as well as the title on every Android parity run (`doc/contributors/design/parity.md`, "The mobile parity"). The `ruby` program an app starts has its argv in its own area and keeps Ruby's way. Neither renames a thread: `setArgv0` names the thread that calls it, Android's main thread, while an app's Ruby runs on a thread of its own, and Linux's Ruby leaves the kernel's name for its process alone.

`process_c_ids` exists because Android's seccomp filter for apps ends a process that calls `setgid`, `setuid`, `setregid`, `setreuid`, `setresgid`, or `setgroups` (bionic, `libc/SECCOMP_BLOCKLIST_APP.TXT`, lines 9 to 30 at 731631f), yet an app's process has no `CAP_SETUID` or `CAP_SETGID`, so Linux's answer to each is settled without the call (`kernel/sys.c` and `kernel/groups.c` at v6.12): an ID the process already holds as its real, effective, or saved one may be asked for, as each call's rules say, and any other is `EPERM`, as `setgroups` always is. The edit puts a function of Fledge's own for each after `process.c`'s includes, and a `#define` that names it in place of the system's: a group ID's change, which no allowed call could make, succeeds only when it changes nothing, and a user ID's goes through `setresuid`, which the filter allows. Ruby is then built with each, where configure had been told they were missing and Ruby raised `NotImplementedError`, and so with `Process.maxgroups=`, which only stores the number `Process.maxgroups` reads (lines 6845 to 6862 at Ruby 4.1.0-preview1) but which Ruby defines only where configure found `setgroups` (line 6835).

The last five mend bugs of CRuby's that a phone's C library brings out and a desktop's does not, each found by ruby/spec on the phones (`doc/contributors/design/parity.md`, "ruby/spec on phones"). In the iOS Simulator `getgroups` fails, since Darwin's looks the process's user up with `getpwuid`, and an app runs as the Mac's user, whom the Simulator's user database does not know (Libc, `sys/getgroups.c`, lines 35 to 58 at Libc-1752.120.2; a device, which runs an app as a user of its own, is unchecked), and `file.c` took the -1 for a count, so `File::Stat#readable?` raised `ArgumentError` for a file of another group. bionic's `pthread_rwlock_unlock` refuses a write lock that another thread ID took (`libc/bionic/pthread_rwlock.cpp`, lines 487 to 495 at 731631f), and a forked child's thread has an ID of its own, so `fork`'s child stopped in Ruby's `[BUG]` handler; Ruby's master has since stopped unlocking there, for macOS, and the edits take its change. bionic aborts on a `pthread_t` of a thread that has ended (`libc/bionic/pthread_internal.cpp`, lines 96 to 125), which `Thread#name=` passed, and Ruby's master has since stopped; musl's `pthread_setname_np` reads the same freed `pthread_t`, which crashed stock Ruby and the app alike there, so the musl runtimes take that edit too. bionic's `dirent.h` has `d_type` but no `IFTODT`, so `dir.c` stats every entry a glob reads, and one of those stats takes the entry's path with a `base:` `Dir`'s own path before it, relative to that `Dir`, so a `Dir` opened by a relative path found nothing; Ruby's master has the same lines. Ruby passes the `umask:` option's mask and `File.umask`'s argument to `umask` as they are, and Ruby's build compiles with `-D_FORTIFY_SOURCE=2`, with which bionic's `umask` aborts the process for a mask with any bit beyond 0777 (`libc/bionic/fortify.cpp`, lines 400 to 406), where Linux keeps a mask's permission bits and drops the rest, so `umask: -1` ended the app; Ruby's master has the same lines. Ruby's master's fixes arrive with Ruby 4.1.0, and the edits for them go then.

## The builtin binary

A cross build cannot run its own miniruby, so `configure.ac` (lines 1628 to 1632 at Ruby 4.1.0-preview1) leaves out the builtin binary, and Ruby falls back to `mini_builtin.c`, which never loads `gem_prelude.rb`: such a Ruby boots with no RubyGems. An iseq binary depends only on Ruby's version, endianness, and word size (`compile.c`, `ibf_load_setup_bytes`), so the build makes a miniruby for the build machine from the same source, once per runtime, and has it write `builtin_binary.rbbin` from Ruby's own template into each target's build folder. It then sets the Makefile's `BUILTIN_BINARY` to `yes` and adds a rule to `GNUmakefile` that keeps `make` from replacing the file with the empty stub a cross build writes. It fails when the binary or the Makefile line is not what it expects.

The build machine's miniruby is configured with the target's JITs, since the binary holds only the builtins it loaded, and a Ruby built with YJIT stops at boot without `yjit.rb`'s ("[BUG] builtin_lookup: can not find yjit"); the build compares the two Makefiles' `YJIT_SUPPORT` and `ZJIT_SUPPORT` and fails when they differ.

## Ruby's extensions on Android

The Android runtime's Ruby is built as a desktop Linux runtime's is, as a shared library with every extension a file (`--enable-shared`), so that its own extensions, its encodings and transcoders, and its bundled gems' extensions load from the paths Ruby gives them, and `$LOADED_FEATURES` and `RbConfig::CONFIG["archdir"]` are what they are under `ruby main.rb`: `ARCHDIR/json/ext/parser.so`, `ARCHDIR/enc/encdb.so`, and an `archdir` that holds `etc.so`. Ruby's own build makes each file. Without static extensions, `configure.ac` (lines 3141 to 3150 at Ruby 4.1.0-preview1) links `dmyenc.o`, whose `Init_enc` requires `enc/encdb.so` and `enc/trans/transdb.so` as Ruby boots, and `template/configure-ext.mk.tmpl` builds each bundled gem's extension with `--no-extstatic`, which `tool/rbinstall.rb` installs, marked built, in the gem's require path and its extension folder, `extensions/PLATFORM/4.1.0+5/NAME-VERSION/`, as on a desktop.

- **Named.** Android's package installer extracts only a native library whose name is `lib*.so`, so `--with-soname=fledgeruby` names Ruby's library `libfledgeruby.so`, and the `configure_soname` edit (see "Scripted edits to Ruby's source") takes the version out of the name and the SONAME Linux would give it (`configure.ac`, lines 3568 to 3570 and 3618 to 3626), as `configure` names a shared Ruby on macOS. Each extension then needs `libfledgeruby.so` by that name, which the Java class has loaded already.
- **Carried.** Once installed, every ELF `.so` file under each ABI's `lib/ruby` is copied, stripped, and checked as `libfledgeruby.so` is, into the AAR's folder for its ABI as `libfledgerubyext.PATH.so`, `PATH` its path under `lib/ruby` with its slashes as dots, one library for each file's bytes, since a bundled gem's extension is installed twice; and it is taken out of the tree, which then holds the same files for both ABIs. `fledge.links` at the runtime's top has a line for each path: the ABI, the library's name, and `lib/ruby/PATH` (`RuntimeBuilder::Android#extension_files`).
- **Ruby's library where Ruby's install puts it.** A shared Ruby's install puts its library at `libdir/LIBRUBY_SO`, where ruby/spec's `rbconfig` spec ("libdir/LIBRUBY_SO is the path to libruby and it exists if and only if ENABLE_SHARED", `library/rbconfig/rbconfig_spec.rb`) and a program that links Ruby look for it. On Android `libdir` is `ROOT/lib`, from the prefix Ruby derives, and `LIBRUBY_SO` is `libfledgeruby.so`, so `fledge.links` holds, for each ABI, the line `ABI`, `libfledgeruby.so`, `lib/libfledgeruby.so` (`RuntimeBuilder::Android#library_line`). Ruby's install would put no other name for it beside it: `configure_soname` makes `LIBRUBY_SONAME` the same name and leaves `LIBRUBY_ALIASES` empty. The license audit reads the library in the AAR, as `FledgeRuby.aar!jni/ABI/libfledgeruby.so`, where the embedding API is linked into it, and only the lines under `lib/ruby` as the paths the app's Ruby has (`LicenseAudit#linked`).
- **Linked.** `fledge build android` starts the app's `fledge.links` with the runtime's, which `fledge_link_libraries` makes into links as the app starts, before Ruby boots, as it does for an app's own extensions built as files (`doc/contributors/design/phone-projects.md`, "Linking extensions on Android"). Ruby then loads each extension, and records it, at the path a desktop has.

The cost: the package installer extracts native libraries only when the Android Gradle plugin packs them compressed, `useLegacyPackaging = true`, so every Android app needs it, which Fledge's template sets and `fledge build android` requires of a host's own `build.gradle` (`MobileProject::AndroidPackaging`). An app carries about 180 more native libraries per ABI, compressed in its package and extracted on install. A runtime from before this change, 0.17.0's, linked everything into `libfledgeruby.so` and listed nothing in `fledge.links`, and `fledge build` reads which it has (`MobileProject::Android#runtime_extensions?`, and `RuntimeContents#extension_api`, which names a gem's extension folder `4.1.0+5` for a shared Ruby and `4.1.0+5-static` for a static one).

Loading the extensions from the APK, uncompressed and aligned, without extraction, was weighed: Ruby loads an extension by its path in the app's Ruby, which no file in the APK has, so it would need an edit to `dln.c`, every ABI's libraries would be stored uncompressed in every split, and Google Play's 16 KB check reads only `lib/ABI/`.

## Ruby's extensions on iOS

The iOS runtime is still static, with every extension of its own linked in (see "Bundled gems' extensions"), so `$LOADED_FEATURES` and `archdir` differ from `ruby main.rb`, a defect `doc/phones.md` tells developers of. The difference is Ruby's own behavior for a static build: `ruby_init_ext` registers each linked extension under its feature (`load.c`, lines 1553 to 1562 at Ruby 4.1.0-preview1), and `search_required` answers a `require` from that table with the bare feature as the path, `json/ext/parser.so` (lines 1199 to 1219), which `require_internal` records (line 1453). For a file it finds on `$LOAD_PATH` it records the path it found, `ARCHDIR/json/ext/parser.bundle` (lines 1172 to 1188), and that path, not where a link leads, since it resolves a real path only to tell whether the same file was loaded before (lines 1396 to 1397 and 1454 to 1457). `dln.c` then opens the path with `dlopen` (lines 376 to 377), refuses a file whose `ruby_xmalloc` is not the running Ruby's (lines 287 to 293), and calls the extension's `Init_` function from its own handle (lines 482 to 497).

So the design that closes it on iOS is the one that closed it on Android, in the form iOS allows, and needs no edit to Ruby's loader:

- **Ruby shared, as a framework.** An extension that is a dynamic library needs Ruby's symbols from a library: an executable lends them only to a bundle (`-bundle_loader`, `configure.ac`, lines 3193 to 3199), which iOS takes in no framework, and `-undefined dynamic_lookup` draws a deprecation warning from Xcode's linker on iOS, which the archive check fails on (`doc/contributors/research/2026-11-13-phone-extensions-as-files.md`, "iOS"). So Ruby is configured `--enable-shared`, without `--disable-dln` or `--with-static-linked-ext`, its extensions linked `LDSHARED='$(CC) -dynamiclib'`, which `configure.ac` takes in place of its Darwin default of `-dynamic -bundle` (line 3188), and its library becomes `FledgeRuby.framework`, as PEP 730 makes libpython a framework: "a static `libpython3.x.a` iOS library will not be supported" (python/peps, `peps/pep-0730.rst`, lines 247 to 255).
- **A framework per extension,** with a link at the path where a desktop has the file, as Fledge already carries an app's libraries for ffi ("Libraries for ffi on iOS" in `doc/contributors/design/phone-projects.md`, proven through such links on an iPhone). CPython wraps every binary module of its standard library, and Briefcase every module of an app's packages too, one framework each (`Apple/testbed/Python.xcframework/build/utils.sh`, lines 63 to 149 at v3.14.0; briefcase-iOS-Xcode-template, `project.pbxproj`, line 214), and puts a text file naming the framework where the module was, which its importer reads (`Lib/importlib/_bootstrap_external.py`, lines 1464 to 1502), so a module's `__file__` ends in `.fwork`. A link keeps Ruby's own path and name, and Apple's "Embedding nonstandard code structures in a bundle" names a link for code loaded by a path where code may not sit.
- **Linked by `fledge build`.** Each slice lists its extensions in `fledge.links`, a line for each path, the framework's name and the path under the slice (`lib/ruby/PATH`), with the extension's file at that path, as Android's runtime lists its own. `fledge build ios` makes each framework from the two slices' files as it makes a library's for ffi, with the app's identifier before the framework's name in its `Info.plist`, as CPython names its modules' frameworks after the app's (`Apple/testbed/Python.xcframework/build/utils.sh`, `install_dylib`, lines 63 to 112 at v3.14.0), though CPython's own `Python.framework` is `org.python.python` (`configure.ac`, lines 545 to 549), so a framework's identifier need not begin with the app's, puts the link in place of each file, and embeds `FledgeRuby.xcframework` when its slices hold `FledgeRuby.framework` (`MobileProject::IOSRubyExtensions`; `doc/contributors/design/phone-projects.md`, "The Xcode project"). An extension that links a library Apple lists among the SDKs that need a privacy manifest, as OpenSSL is listed, carries that library's own manifest: each slice keeps it as `privacy/NAME.xcprivacy`, beside `fledge.links` and out of Ruby's tree, and the build copies it into the framework as `PrivacyInfo.xcprivacy`, as CPython's build copies `OpenSSL.xcprivacy` beside its `_ssl` and `_hashlib` modules and moves each into the module's framework (`Apple/__main__.py`, lines 658 to 673, and `utils.sh`, `install_dylib`, at v3.14.0; `Doc/using/ios.rst`, lines 348 to 361). The manifest is OpenSSL's own, `os-dep/Apple/PrivacyInfo.xcprivacy` in the pinned OpenSSL source, never one written here. That part has landed before the runtime that needs it: a runtime that lists nothing and holds no framework, as 0.17.0's, builds the same project as before.

Two cheaper shapes fail Ruby's loader. Extensions merged into a few frameworks, or into Ruby's own, with a link per feature: every link to one binary has one real path, so after the first, `require_internal` takes each as loaded already and never calls its `Init_` function (lines 1396 to 1397). Staying static, with a file at each path that Ruby answers from its table of linked extensions: Ruby finds the table's entry before any file (lines 1199 to 1219), so it needs an edit to `load.c`, and the file is not the extension, which is the reason "Found only while its gem is active", below, gives against files "that pretend to be code": `File.size` and `Fiddle.dlopen` of the path tell it from a desktop's. Keeping the encodings linked (`--with-static-linked-ext=enc`, `configure.ac`, lines 3141 to 3147) would leave `enc/encdb.so` and `enc/trans/transdb.so` bare.

What it costs, and what is not yet known. About 180 frameworks in every iOS app, each padded to 16 KB pages (on the order of 10 MB installed, little in the download), each signed when Xcode embeds it; Ruby's framework is loaded at launch, and each extension's only when it is required, as on a desktop. The executable then loads one library that is not Apple's, which the archive check allows today only of an ffi library's own install name. Whether App Store Connect takes an app with that many frameworks and links is what `doc/contributors/account-tests.md`, IOS-4, asks of one, and only an upload can show. What would falsify the design: an upload refused for the links or the number of frameworks (then CPython's placeholder file, with an edit to `dln.c`), or a start on a device made slower than a person notices by the extensions Ruby requires as it boots.

## Bundled gems' extensions

The iOS runtime links every extension of its own in, by Fledge's choice: it is configured `--with-static-linked-ext` and `--disable-dln`, after xord/cruby (ADR 097). iOS does not forbid loading an extension from a file: it loads a dynamic library from a framework in the app (`doc/contributors/research/2026-11-13-phone-extensions-as-files.md`), as the Android runtime loads its own from the app's native libraries (see "Ruby's extensions on Android", and "Ruby's extensions on iOS" for the design that would do the same there). Ruby's build links its standard library's extensions in and registers each in `extinit.c`, but not a bundled gem's: `template/configure-ext.mk.tmpl` builds `.bundle/gems` with `--no-extstatic`, and `ext/extmk.rb` (lines 273 and 660 at Ruby 4.1.0-preview1) leaves a gem's extension out of `extinit.c`, so bigdecimal, debug, nkf, racc, rbs, and the other bundled gems with C extensions would not load. `RuntimeBuilder::BundledExtensions` keeps those gems gems, so that an app that names one in its Gemfile, or asks RubyGems for it, finds a gem, as under `ruby main.rb` (decision 9):

1. It copies each bundled gem's extension sources (its `ext/`, and the `lib/`, `include/`, and `src/` its `extconf.rb` reads beside it) among Ruby's own, to `ext/gems/NAME`, where extmk links them in and registers each under the feature the gem requires (`bigdecimal.so`, `racc/cparse.so`, `rbs_extension.so`).
2. It gives each copied extension the rules `BundledExtensions::RELOCATABLE` holds, after the gem's own `depend` file, which mkmf appends to the extension's Makefile, so that the extension's static library holds one object in which every symbol but its Init function is local (see "Each extension's symbols", below).
3. `configure --with-out-ext` leaves out the gem's own build, by the names extmk matches a gem by (`NAME` and `NAME-*`, `ext/extmk.rb` lines 514 to 529 at Ruby 4.1.0-preview1).
4. Once Ruby is built, it writes each gem's `gem.build_complete` where its own build would (`.bundle/extensions/PLATFORM/ABI-static/NAME-VERSION/`), so `tool/rbinstall.rb` installs the gem, specification and all, and RubyGems loads it rather than ignoring it because its extensions are not built.
5. After install it checks that every such gem has its specification and its mark.

When the gem's Ruby requires its extension, `load.c`'s `search_required` finds no file and looks among the statically linked extensions, which have it.

Folding the gems into the standard library, as xord/cruby does, loads them, but they are no longer gems: `Gem.loaded_specs["bigdecimal"]` is nil, and an app that locks bigdecimal in its Gemfile sees a difference from `ruby main.rb`. Copying their sources keeps Ruby's own build and installer, steered by a copy, a configure option, and a mark. The cost is that each new Ruby means checking that the gems' sources still fit among Ruby's own and that the marks are where RubyGems looks, which step 5 does; the mobile parity check compares every gem the probe reports on a phone with `ruby main.rb`.

fiddle is on both phones (see "What a phone runtime holds"). win32ole and win32 are Windows' alone. Every other bundled and default gem is as a desktop runtime has it.

### Each extension's symbols

Linked statically, every symbol an extension defines is global, and two copies of one library collide. prism is a bundled gem whose extension compiles its own libprism, and libruby holds another, for its parser and for `Ruby::Prism` (`prism_init.c`, which registers `ruby/prism/prism.so`): linked into one library, they fail with "duplicate symbol: pm_parse" and every other `pm_` symbol. On a desktop the two never meet: the gem's extension is a shared object, Ruby looks up only its Init function in it, and prism's `extconf.rb` compiles it with `-fvisibility=hidden` (prism 1.9.0, `ext/prism/extconf.rb`, line 108; libprism's functions are exported only under `PRISM_EXPORT_SYMBOLS`, `include/prism/defines.h`, lines 45 to 55, which the extension never sets). So each bundled gem's extension on a phone gets what Ruby uses of its shared object on a desktop: its Init function, with every other symbol its own.

The rules link the extension's objects with `cc -r` into one object, in which every symbol but the Init function is made local. On iOS Apple's ld links it with `-keep_private_externs`, since without it ld makes every hidden symbol local, and the iOS runtime's `-fvisibility=hidden` hides most gems' Init functions; then Apple's `nmedit -s` keeps only the Init function global (`IOS#relocatable`). The rules also compile the extension with `-fno-common`, as mkmf's `CCDLFLAGS` compiles its shared object on a Mac and mkmf leaves out of a static build: Xcode's clang otherwise makes a global without an initializer, such as prism's `VALUE rb_cPrism;`, a common symbol, which stays global and merges with libruby's of the same name. The Init function is the one extmk names for the extension's feature (`ext/extmk.rb`, line 565 at 4.1.0-preview1): `Init_racc_cparse` for `racc/cparse`. That is what lets prism's extension, which compiles its own libprism, sit beside libruby's: its `pm_parse` and every other `pm_` symbol are local to it, and its `Init_prism` is `Init_prism_prism`, which does not meet libruby's `Init_prism`.

One rule covers every bundled gem's extension, with the platforms' own tools, and needs no list of names, so a new libprism, or another gem that compiles a library libruby or another gem also holds, needs no change. Five other ways were weighed. Making local only the symbols the extension hides (`llvm-objcopy --localize-hidden`, or Apple's ld, which makes hidden symbols local when it links with `-r`) fails on iOS: the runtime's `-fvisibility=hidden` hides the Init functions of bigdecimal, debug, nkf, racc, rbs, and syslog, whose sources do not export them, so the link of Ruby's `ruby` finds none of them. Doing either for prism alone, or with `objcopy --localize-symbol` for a list of libprism's names, is a special case, or a list that changes with every libprism. Renaming libprism's symbols in the gem's build, with a header of `#define`s or `-D` options, edits the gem's build for every one of libprism's hundreds of names; nothing recorded weighs it against the chosen rule beyond the size of that change. Building the gem's extension against libruby's libprism compiles it against headers it was not written for: both say 1.9.0 (`prism/version.h`), but Ruby 4.1.0-preview1's `prism/` is a later libprism, which allocates from an arena (`arena.c`) and has `internal/` headers the gem lacks, the gem has a `pack.c` that Ruby's lacks, and the gem's `lib/prism` is generated for its own nodes and serialization. Answering `require "prism"` with libruby's own extension gives an app another prism, whose API "may change incompatibly between Ruby minor versions" (`prism_init.c`), and the gem's Ruby would not be the code that runs.

The cost: every bundled gem's extension is linked one step more, and a new Ruby means checking that mkmf's static rule still archives `$(OBJS)` and that extmk still names the Init function so; a wrong name fails the link of Ruby's `ruby` at once. An extension that meant another extension to call one of its functions could not; no bundled gem's does. A phone app carries two libprisms, as a desktop process that loads the gem does. `test/integration/bundled_extensions_test.rb` builds a fake prism with this computer's mkmf and compiler, its Init function hidden, with the rules `relocate` writes, links it into a program that has its own `pm_parse`, and checks that each calls its own. `test/fixtures/mobile_hello` requires prism and prints what it parses, in the iOS Simulator and on Android emulators, where prism's extension is a file of its own, as on a desktop.

### Found only while its gem is active

Ruby looks among the linked extensions for any feature it finds no file for, so a linked extension would be found by a plain `require` of its feature before RubyGems has activated its gem. RubyGems' `require` asks Ruby's own first, and activates a gem only when that raises `LoadError` (`lib/rubygems/core_ext/kernel_require.rb`, lines 79 to 81 and 138 to 148 at Ruby 4.1.0-preview1). Where a gem's Ruby file has its extension's name, as bigdecimal's `lib/bigdecimal.rb` has `bigdecimal.so`'s, nkf's `lib/nkf.rb` `nkf.so`'s, and fiddle's `lib/fiddle.rb` `fiddle.so`'s, `require "bigdecimal"` loaded the extension alone: the gem was never activated, and its Ruby, which defines `BigDecimal#sqrt`, `#power`, and `BigMath`, never loaded. On a desktop the extension is a file in the gem's own folders, which RubyGems puts on `$LOAD_PATH` only as it activates the gem (`Gem::BasicSpecification#full_require_paths`, `lib/rubygems/basic_specification.rb`, lines 184 to 195), the gem's extension folder, named for its full name, among them. So the `load_c` edit gives the lookup a gate: a table of each copied gem's extension, by the feature it is registered as, with its gem's full name (`BundledExtensions.features`, from each `extconf.rb`'s `create_makefile`), and a check that lets the lookup find a gem's extension only while a folder named for the gem is on `$LOAD_PATH`. `require "bigdecimal"` then fails in Ruby's own require, RubyGems activates the gem and requires it again, and the gem's `lib/bigdecimal.rb` loads first and requires `bigdecimal.so`, as on a desktop. Bundler's setup puts the same folders on `$LOAD_PATH`, so a gem in an app's Gemfile is found as it is activated. Every other linked extension, Ruby's own, is found as before. A desktop's RubyGems also activates a gem for a require of its extension's own feature (`require "racc/cparse"` before racc is active), since it finds the extension's file among the gem's (`Gem::BasicSpecification#have_file?`, `lib/rubygems/basic_specification.rb`, lines 376 to 388). So after `make`, the build writes in each copied gem's extension folder, which `tool/rbinstall.rb` installs whole, a Ruby file at the extension's path (`racc/cparse.rb`) that requires its `.so` name, the file `fledge build` puts beside an app gem's extension (`BundledExtensions.write_stubs`, `MobileExtensions::Stub`): RubyGems finds the gem by it and activates it, and the file's require then passes the gate. A gem whose `lib/` has a Ruby file of its extension's name, as bigdecimal, nkf, and fiddle have, gets none, since the extension folder comes first on `$LOAD_PATH` and the file would hide the gem's own. The parity probe reports a gem whose require loads without activating it as `loads, but not its gem`, which the mobile parity check compares with `ruby main.rb`.

The gate makes a linked extension reachable exactly when a desktop's file is: while the gem's folders are on `$LOAD_PATH`, whether RubyGems put them there or Bundler's setup did. It is one condition in the lookup and a function before `search_required`, and a gem's extension, once found, is registered and recorded in `$LOADED_FEATURES` as every linked extension is. Registering a gem's extension under another name cannot work: a plain `require "bigdecimal"` looks up `bigdecimal.so`, the same name `lib/bigdecimal.rb`'s `require "bigdecimal.so"` looks up, so no registered name tells the two apart. Registering each extension only as its gem activates, from a hook in `rubygems/defaults/operating_system.rb`, would patch RubyGems' activation on a phone alone, which an app would meet, and RubyGems has no activation hook to use instead. A file named for the extension's shared object in each gem's extension folder, which `load.c` would answer with the linked extension, is found by Ruby's require and loaded as a shared object (`search_required` returns the file, and `require_internal` loads it with `dln_load_feature`), so it needs a larger edit, and ships files that pretend to be code. The cost is one more edit to Ruby's source: a new Ruby means checking that `search_required` still looks up linked extensions so, and `RubySource.load_c` raises when the lines it changes are gone. `test/integration/ruby_source_gate_test.rb` compiles the gate's C with this computer's mkmf and Ruby, and checks that it finds a gem's extension only while a folder named for the gem is on `$LOAD_PATH`, and another always.

### Required by its file's path

A require that names an extension's file finds no Ruby file either: an explicit `.so` path (`require File.join(dir, "name.so")`), a `require_relative "name/name.so"`, and on iOS a require of the platform's own extension name, `require "name/name.bundle"`, since iOS's DLEXT is `.bundle`. Ruby looks the table of linked extensions up by exactly the name it was given (`load.c`, lines 1203 to 1223 at Ruby 4.1.0-preview1), where a desktop's require loads the file. So where a require of a name with `.so` or DLEXT, or of an absolute path, finds no file and the lookup fails, the `load_c` edit goes on to the feature that name stands for (`RubySource::LINKED_FEATURES`): DLEXT made `.so`, and an absolute path made relative to each folder on `$LOAD_PATH` that holds it, where a desktop's RubyGems leaves the extension's file. If that feature is loaded, the require answers false, as a second require of a desktop's file does, though Ruby deleted the registration when it ran it; if it is registered and through the gate, the require runs it and records the feature (`RubySource::LINKED_LOOKUP`). The parity probe compares a require of nkf's extension by the path of its file.

The lookup reaches app gems' extensions and bundled gems' alike, and needs no new embedding API. Registering aliases from `fledge_ruby_add_extension`, the absolute path and the DLEXT name beside `FEATURE.so`, would know an absolute path only once the app boots, so it would need a new embedding API and a generated wrapper for each extension's Init; it would still run an Init twice when the feature loads first and the path next, since `rb_feature_p` does not match an absolute request against a relative feature; and it would not reach bundled gems. Refusing such gems would refuse what nothing on a phone forbids. The cost is one more piece of `load.c` that Fledge edits, which fails the build when the lines it follows are gone, and `$LOADED_FEATURES` records the linked feature where a desktop records the file's path, which `Parity::MOBILE_JUSTIFIED` justifies. `test/ruby_source_test.rb` checks where the edit lands, and `test/integration/ruby_source_gate_test.rb` compiles the lookup with iOS's DLEXT and checks it.

## The embedding API

`runtime/mobile/fledge_ruby.h` is the embedding API, in C, compiled into both runtimes with `fledge_ruby.c`, `output.c`, `apple.c` or `android.c` with `library_links.c`, and the launcher's `locale.c`, `config.c`, and `bundler.c`. Its header comments are the reference for each function.

| Function | What it does |
|---|---|
| `fledge_ruby_forward_output(tag)` | Sends standard output and standard error to the system log (see "Output to the system log"). |
| `fledge_ruby_run(root, script, argc, argv)` | Runs a Ruby file on the calling thread, as `ruby SCRIPT ARGS` would, and returns its status. |
| `fledge_ruby_run_app(root, argc, argv)` | Runs the app `fledge build` put in `root`, as the desktop launcher runs one. |
| `fledge_ruby_add_extension(feature, init)` | Tells Ruby that an extension is linked in (see `doc/contributors/design/phone-projects.md`, "Registering extensions"). |

`fledge_ruby_run` starts Ruby as the desktop launcher does, after Ruby's own `main.c` (`doc/contributors/design/launcher.md`): the locale, `ruby_sysinit`, then `ruby_start_main`, whose callback runs `RUBY_INIT_STACK`, `ruby_init`, and `ruby_run_node(ruby_options(...))`, with `ruby --disable=rubyopt -- SCRIPT ARGS`. Between `ruby_options` and `ruby_run_node` it registers the extensions added so far and gives `$stdout` a terminal's line timing when descriptor 1 is not a terminal ("Line timing", below). Ruby's prefix is `root`, through `ruby_embed_libruby_path`, so the load path and `Gem.path` are `root/lib/ruby`, which Fledge's RubyGems defaults keep `Gem.path` to. A bare C locale becomes a UTF-8 one, with the launcher's own `fledge_coerce_locale` (`doc/contributors/design/launcher.md`, "The locale"). Ruby boots once per process, so a second call returns 70 (`FLEDGE_RUBY_SOFTWARE`).

`fledge_ruby_run_app` reads `root/fledge.cfg` with the launcher's reader and runs `root/app/ENTRY`. For an app with a Gemfile it sets `BUNDLE_GEMFILE` to the app's Gemfile, whose `.bundle/config` Bundler then reads as the app's settings, and requires `bundler/setup` from Ruby's own library, or from the gem of the Bundler `fledge.cfg` names, as the desktop launcher does (`doc/contributors/design/launcher.md`, "The Bundler environment"), which sets `ENV` as `bundle exec` would (`Bundler::Runtime#setup`, `set_bundle_environment`). It returns 66 (`FLEDGE_RUBY_NO_APP`) when `fledge.cfg` or the program is missing, and 70 when the configuration is damaged or Bundler cannot set up the gems.

So the launcher's work is written once, in C, beside the code the desktop launcher runs: `runtime/launcher/config.c` is compiled into both phone runtimes, so a change to how the launcher reads `fledge.cfg` reaches the phones with it, and a host is two calls, forward the output and run the app, wherever its framework runs the main function (`doc/contributors/design/phone-projects.md`, "A host that owns the main loop"). Each host could instead read the program and the Gemfile from its `Info.plist` or manifest and call Bundler itself, which would put the work in two hosts, in Objective-C and Java, and in every framework's host. A boot script that set up Bundler and `load`ed the program would make `$0` and every backtrace name a file the app never had, unlike `bundle exec ruby main.rb` (decision 10). The embedding API is part of the runtime, so a change to it changes every phone runtime, and its functions are only ever added. The `mobile-apps-ios` and `mobile-apps-android` jobs run `examples/hello`, `examples/mobile_app`, whose gems Bundler sets up, `test/fixtures/mobile_hello`, and the parity probe through `fledge_ruby_run_app`, and `test/integration/mobile_output_test.rb` compiles `fledge_ruby.c` with the launcher's `config.c` and runs it against the Ruby that runs the tests.

On Android, `fledge_ruby_run` first opens `libfledgeext.so`, when the app has one, from beside `libfledgeruby.so` (`fledge_ruby_load_extensions`), before Ruby has started, so that its constructor's `fledge_ruby_add_extension` calls count, whether or not the host loaded it; then it makes `root/bin/ruby` a link to the runtime's ruby program (see "The ruby program on Android"), and each path `root/fledge.links` lists a link to the app's native library it names (`fledge_link_libraries`, `library_links.c`; `doc/contributors/design/phone-projects.md`, "Linking extensions on Android"), a gem's command among them, a link to the ruby program whose wrapper Ruby reads in its place (`fledge_ruby_read_commands`, `commands.c`; see "Gem commands on Android"). Once `ruby_options` has run, it puts the app's Ruby's `bin` folder first on `PATH`, as the desktop launcher does (same section).

Unlike the desktop launcher, neither function sets anything of the environment aside: iOS and Android start an app with an environment of their own, which no person sets. Ruby needs a deep stack: Fledge's hosts run it on a thread with 64 MB.

Swift needs no shim: the module map imports the C functions.

## The ruby program on Android

A Ruby program that runs Ruby again asks Ruby where it is: `system(RbConfig.ruby, "script.rb")`, `IO.popen([Gem.ruby, "-e", code])`. iOS lets no app run a program. An Android app may run only the files its package installer extracts from the APK into its native library folder, `nativeLibraryDir`, whose name changes with each install, and the installer extracts only the APK's `lib/ABI/lib*.so` entries, and only when its native libraries are compressed. The files in the app's own folders it may not run (W^X, from target API 29): "Untrusted apps that target Android 10 cannot invoke `execve()` directly on files within the app's home directory" (developer.android.com, "Behavior changes: apps targeting Android 10", "Removed execute permission for app home directory"). The Android runtime therefore carries its ruby program as a native library by name, `libfledgerubyexe.so`, beside `libfledgeruby.so` in each ABI's folder of the AAR, and the Gradle project packs native libraries compressed (`doc/contributors/design/phone-projects.md`, "The Gradle project"). `RbConfig.ruby`, `Gem.ruby`, `system`, `spawn`, backquotes, and `IO.popen` then start Ruby on Android as on a desktop, with the app's gems through Bundler's `RUBYOPT`, and ruby/spec's examples that run a child Ruby through MSpec's `ruby_exe`, and its files that start processes, run on Android and are compared with stock Ruby (`tasks/ruby_spec/phone_config.rb`). The iOS runtime builds no program, and `apple.c`'s `fledge_ruby_link_program` does nothing.

**Where else it could live.** Unpacked from the asset into the app's files as `ROOT/bin/ruby`, it is what Android 10 forbids. Targeting API 28, as Termux does to keep running its packages from its files (termux/termux-app issue 1072, "No more exec from data folder on targetAPI >= Android Q"), keeps an app off Google Play, which takes no new app or update that targets API 28. Running it through the system's linker, `/system/bin/linker64 ROOT/bin/ruby`, maps its code from the app's files with execute permission, which the same rule forbids. No program at all, with a child Ruby started in a process of Android's own, a `Service` with `android:process`, as an app embedding Python with Chaquopy or Buildozer does, leaves `RbConfig.ruby` naming nothing, and an app would need Android-only code to start Ruby. Python on Android made that choice: "There is no `python3` executable, Python's `sys.executable` is empty. To run a Python script in a new process, we use an Android Service" (Android-for-Python's users' guide to Buildozer, `README.md`), and PEP 738 loads `libpython3.x.so` into the app's process, so that "A python3.x executable will not be officially supported on this platform", since "apps may only run executables in certain locations, none of which are writable at runtime" (PEP 738, "App lifecycle"). Fledge puts Ruby's behavior first, and Android does let an app run what its installer extracts, so Fledge ships the program Python chose not to.

**Built.** `RuntimeBuilder::Android#program` compiles `runtime/mobile/ruby_program.c`, a `main` that calls `fledge_ruby_program_main`, as a position-independent executable linked against `libfledgeruby.so` with the run path `$ORIGIN`, which bionic's linker expands to the folder of the program's own file (so it is a few kilobytes, where a static copy of Ruby would add as much again as `libfledgeruby.so` to every ABI), and with `-z max-page-size=16384`. It checks the program with clang's static analyzer, strips it, and fails unless it needs only Android's libraries and `libfledgeruby.so`, has that run path, and aligns every LOAD segment to 16 KB. It carries no Ruby of its own: Ruby's `main.c` is `fledge_ruby_main` in `fledge_ruby.c`. Linked statically with all of Ruby, as a desktop's `bin/ruby` is, it would add as much again as `libfledgeruby.so` to every ABI.

**Named.** `RbConfig.ruby` is `ROOT/bin/ruby`, from the prefix Ruby derives, as a desktop's is. Before Ruby boots in the app, `fledge_ruby_run` calls `fledge_ruby_link_program` (`android.c`), which finds `nativeLibraryDir` with `dladdr` on `libfledgeruby.so`, and makes `ROOT/bin/ruby` a link to the program there, through a new link renamed into place, whenever it is not that link already: the folder changes with each install. Where the libraries load from inside the APK (`base.apk!/lib/ABI/`), not extracted, there is no program, and an old link is removed. `RbConfig` stays stock Ruby's, rather than naming the program in `nativeLibraryDir` by rewriting `rbconfig.rb` at run time, because gems read its values for other ends: RubyGems takes `bindir` as where to install executables and `ruby_install_name` for their shebangs. An environment variable naming the program would add to the app's `ENV`, which decisions 9 and 10 keep as `ruby main.rb` has it.

**Run.** The kernel runs the file the link resolves to. `fledge_ruby_program_main` finds `ROOT` from the path the program was run by, which the kernel keeps as `AT_EXECFN` (`getauxval`): the parent of its folder, `ROOT/bin`, resolved, since `/proc/self/exe` and `dladdr` name the file in `nativeLibraryDir`. `fledge_ruby_main` loads `libfledgeext.so` from beside `libfledgeruby.so` when the app has one, as `fledge_ruby_run` does in the app, so that its constructor registers the app's gems' extensions; `libfledgeext.so` has the run path `$ORIGIN` too, so that a shared library an extension carries is found beside it outside the app's library namespace (`doc/contributors/design/phone-projects.md`, "Linking extensions on Android"). Otherwise `fledge_ruby_main` is what a desktop's `bin/ruby` is (`runtime/launcher/ruby_main.c`): the locale, the certificates, and Ruby's prefix as `fledge_ruby_run` has them, then `ruby_sysinit` and `ruby_start_main`, with the extensions registered between `ruby_options` and `ruby_run_node`, and Ruby's arguments as given, `RUBYOPT` honored. When its first argument is the program `ROOT/fledge.cfg` names, compared by device and inode as the desktop's `fledge_relaunch` compares it, it runs `fledge_ruby_run_app` with the arguments after it instead, as the host ran the app: the desktop's `bin/ruby` hands such a program to the app's launcher (`doc/contributors/design/launcher.md`, "bin/ruby and restarts"), and an Android app's starting is its host's, which the program does in its own process.

A Ruby the app starts inherits the app's environment and standard streams, so its output reaches the log through the same pipe, buffered as Ruby buffers a pipe. It has no Java virtual machine, so nothing in it can call Android's Java APIs, and Android may stop it with the app. `exec RbConfig.ruby, $0` replaces the app's own process, Java virtual machine and all, so on a phone an app restarts its Ruby with `system` or `spawn`. The program is a native library by name only: a tool that lists an app's libraries lists it, and `System.loadLibrary("fledgerubyexe")` would fail.

`test/integration/mobile_ruby_program_test.rb` compiles `fledge_ruby_main` with this computer's Ruby and runs it: `-e` and another script as plain Ruby with `RUBYOPT`, and the app's program by its path, a relative path, and a link, as the host runs it; an option before the program, or no `fledge.cfg`, leaves it plain. The mobile parity check runs the probe on Android emulators, where `RbConfig.ruby is a program` and `RbConfig.ruby runs` match `ruby main.rb`.

## Gem commands on Android

Under `bundle exec`, or `ruby main.rb` from a developer's shell, a program runs a gem's command and Ruby itself by name: `system("rake")`, backquotes, `Open3`, a child Ruby doing the same, `ruby -S rake`, and `system("ruby", ...)` (`doc/contributors/design/launcher.md`, "The app's Ruby on PATH"). Ruby searches `PATH` itself for `system` and `spawn`, for a regular file it may execute (`process.c`, line 2542, and `dln_find.c`, lines 263 to 266, at Ruby 4.1.0-preview1), and `ruby -S` searches `RUBYPATH` and then `PATH` for a regular file, executable or not, which it reads as Ruby (`ruby.c`, lines 2478 to 2489). A desktop's command is RubyGems' wrapper, a shell script whose prolog runs the `ruby` beside it with `-x` and whose rest is Ruby (`Gem::Installer#bash_prolog_script`, `rubygems/installer.rb`, lines 1039 to 1054), so it serves both. An Android app may run neither a script nor a program from its own files, only the native libraries its installer extracts (see "The ruby program on Android").

So on Android:

- **`PATH`.** `fledge_ruby_run` puts the app's Ruby's `bin` folder first on `PATH`, as the desktop launcher does, with the launcher's own `fledge_ruby_on_path_code`, after `ruby_options` and before Bundler loads (`put_ruby_on_path`, `fledge_ruby.c`). `ENV["PATH"]`, what Bundler records, and a child's `PATH` are then a developer's, with the app's Ruby in the place of theirs. iOS lets no app run a program, and its `PATH` is left as the system gave it.
- **Each command is a link to the ruby program.** `ROOT/bin/NAME` is a line of `ROOT/fledge.links`, `ABI`, `libfledgerubyexe.so`, `bin/NAME`, for each ABI, so the embedding API makes it a link to the program as the app starts, as it makes `bin/ruby` and an extension's links (`fledge_link_libraries`). The kernel runs it, and `system("rake")` finds and runs it as on a desktop.
- **RubyGems' wrapper is kept in `ROOT/libexec/commands/NAME`.** The runtime's own are the wrappers Ruby's `make install` wrote, which the runtime keeps in `bin/` as a desktop runtime does (see "What a phone runtime holds"); an app's locked gems' are written by `fledge build` itself, as the phone's RubyGems writes one, with no Ruby run (`Fledge::GemWrapper`, `AppGems#phone_executables`). The Android project moves both out of `bin/` and writes their links (`MobileProject::Android#place_commands`).

**Who writes a locked gem's wrapper.** A desktop build has the runtime's own RubyGems write them, since it has that runtime at hand (`doc/contributors/design/gems.md`, "Gem executables"). An Android build has no Ruby of the phone's to run where it writes the project, and the only Ruby that could run RubyGems' own code there is a desktop runtime, or the developer's. Three ways were weighed:

- *The desktop runtime of the computer that builds*, whose Ruby, and so whose RubyGems, is the phone's. It wrote them at first, and made every Android build need that runtime, which before only an app with an extension to compile had: a developer with a pure-Ruby app downloaded one for nothing, and CI's jobs that write an Android project on macOS and Windows, which have only the Android runtime, stopped. Needing it only when a locked gem has a command would not help much: a lockfile whose `BUNDLED WITH` is not the runtime's Bundler locks that Bundler, whose commands are `bundle` and `bundler`, as `examples/mobile_app`'s does, so most apps would still need it.
- *The developer's own RubyGems, in `fledge build`'s process*, through `Gem::Installer#app_script_text`. Its text is that of the developer's RubyGems, which `gem update --system` moves away from the phone's, and it reads the developer's `.gemrc` (`custom_shebang`) and the developer's `rbconfig.rb`, and needs `Gem.ruby` changed for the whole process.
- *The text itself*, which is what was chosen. RubyGems' wrapper is a function of the gem's name, the command's name, the options on the `#!` line of the command's script, and three settings that are the same for every wrapper Fledge's runtimes write: `Gem.ruby`, `/usr/bin/env ruby` (`NativeBuild::STUBS`); no `custom_shebang`; and a Ruby built with `--enable-load-relative`, which writes the shell prolog (`Gem::Installer#app_script_text`, `#gemdeps_load`, `#explicit_version_requirement`, `#shebang`, and `#bash_prolog_script`, `rubygems/installer.rb`, lines 746 to 800, 588 to 622, and 1039 to 1056, at Ruby 4.1.0-preview1). `Fledge::GemWrapper` is those methods adapted, some forty lines, and writes a wrapper only for a script the gem has, as `Gem::Installer#generate_bin` does (lines 489 and 490). `test/gem_wrapper_test.rb` holds its text, for Bundler's and others', with and without options or a `#!` line, to the text the RubyGems of the Ruby `mise.toml` pins writes, which is the Ruby the runtimes carry; so a new Ruby whose RubyGems writes another fails that test until the adaptation follows it. The cost is that adaptation, to read again at each Ruby.
- **The program run as a command runs its wrapper.** `fledge_ruby_program_main` (`android.c`) takes the name it was run by from `AT_EXECFN`, and for any name but `ruby` that has a wrapper it runs Ruby as the wrapper's prolog does on a desktop, `ruby -x ROOT/bin/NAME ARGS`.
- **Ruby reads the wrapper wherever it reads the link.** The scripted edits `prism_compile_c` and `ruby_c_source` let the runtime name the file Ruby's two readers read in place of the one asked for (see "Scripted edits to Ruby's source"), and `runtime/mobile/commands.c` names the wrapper for a path whose folder is `ROOT/bin`, however spelled, and whose name has one. So `ruby -S rake`, found on `PATH` or on an app's own `RUBYPATH` by Ruby's own search, `ruby -w ROOT/bin/rake`, `load File.join(Gem.bindir, "rake")`, and the program run as `rake` read the wrapper, with `$0`, `__FILE__`, and every message naming `ROOT/bin/rake`, as on a desktop. Every other path reads as it did (`test/integration/mobile_commands_test.rb`).

**What still differs.** A program that reads `ROOT/bin/NAME`'s bytes, `File.read(File.join(Gem.bindir, "rake"))`, gets the ruby program's, not the wrapper's text. Android forbids the one file that would serve both: an app may run only the native libraries its installer extracts, and "Untrusted apps that target Android 10 cannot invoke `execve()` directly on files within the app's home directory" (developer.android.com, "Behavior changes: apps targeting Android 10", "Removed execute permission for app home directory"). `doc/phones.md` says so for developers.

**What was weighed.**

- *Each wrapper packed as a native library*, `lib/ABI/libfledgebin.NAME.so`, with `bin/NAME` a link to it: the kernel runs a script through its first line, so even reading its bytes would match a desktop. It was built, and Fledge's own linkage check of an app's native libraries refused it as no ELF object. Every reader of an APK's native libraries expects one, and on a device with 16 KB pages the package installer reads the program headers of every `lib/ABI/` entry when it installs an app, and returns an error for the whole APK when one has none (`core/jni/com_android_internal_content_NativeLibraryHelper.cpp`, `checkLoadSegmentAlignment` and `checkApkAlignment`, AOSP `main` as read on 2026-11-21). What the Android Gradle plugin's strip, bundletool, and Google Play's 16 KB check do with such a file was not found in their published sources. It would also add a file per command per ABI to every app's native libraries.
- *A `RUBYPATH` the runtime sets* only while `ruby_options` runs, naming the wrappers' folder in `bin/`'s place, so that `ruby -S` finds a wrapper, needed no edit to Ruby, but left `ruby -w ROOT/bin/rake`, with an option before the path, and `load` of that path reading the program; closing the first meant parsing Ruby's options before Ruby does, a grammar of `ruby.c`'s `proc_options` to keep in step at each Ruby; a `bundler/setup` that `RUBYOPT` requires during `ruby_options` would record the variable in `Bundler.original_env`; and `$0` would name the wrappers' folder. The edit costs two scripted edits of a few lines, compiled for Android alone, to keep at each Ruby, and closes all of those.
- *Two folders on `PATH`*, the links' and the wrappers', or a folder other than `RbConfig::CONFIG["bindir"]`, would make `ENV["PATH"]` differ from a developer's.

The mobile parity check compares the probe's gem commands on Android with `ruby main.rb` under a reference Ruby whose `bin` folder is first on `PATH`, as a developer's is (`tasks/mobile_parity.rb`, `MobileParity.reference_environment`), and `test/fixtures/mobile_commands`, which locks thor, a gem no runtime has, runs `thor` by name, from a shell, and with `ruby -S` on the emulator.

## Output to the system log

iOS and Android discard an app's standard streams unless a debugger holds them. `fledge_ruby_forward_output` (`runtime/mobile/output.c`) makes standard output and standard error each the write end of a pipe, which a thread of its own reads line by line into the system log:

- on Apple's systems, os_log with the tag as subsystem (`apple.c`);
- on Android, logcat with the tag as tag, standard error's lines as warnings, as CPython's Android support logs them (`android.c`).

The descriptors are forwarded, not only Ruby's `$stdout` and `$stderr`, so that what C extensions and Ruby's own warnings write reaches the log too. Replacing only the language's stream objects with ones that call the log, as CPython's iOS support replaces `sys.stdout` and `sys.stderr`, would miss them.

A line longer than an entry holds (logcat cuts one at about 4,000 bytes) goes as several entries in a row of at most 1,000 bytes (`FLEDGE_LOG_ENTRY_MAX`, `mobile.h`). The cut falls between UTF-8 characters and before whitespace, never after it, since the unified log drops an entry's trailing whitespace (`log show` prints `a ` as `a`), which would take a space out of the line the entries make (`fledge_log_chunk`).

**`OS_ACTIVITY_DT_MODE`.** When the process's environment holds this variable, the unified log copies each entry to standard error, for a developer tool that reads the app's streams. Then `fledge_ruby_forward_output` leaves the streams alone and returns 0 (`fledge_log_echoes` in `apple.c`), since forwarding standard error would send each copy back to the log, which would copy it again, until the pipe filled and Ruby's `puts` blocked. What counts is that the variable is present, not its value: `NO`, `0`, and an empty value turn the copy on as `YES` does. Android's `fledge_log_echoes` is always false, since logcat copies nothing to an app's streams. Xcode 15 and newer read the log itself and set the variable only when a scheme asks for the old way (`IDELogRedirectionPolicy=oslogToStdio`). With the variable set, a developer tool shows each of the app's lines once, from its streams, and the log holds none of Ruby's. On an iPhone 12 mini with iOS 27.0, launched by `xcrun devicectl device process launch --console` with the variable set, every example showed each of Ruby's lines once, on `devicectl`'s standard output, and the log's copies of the host's entries on its standard error (`doc/contributors/device-test.md`, section 8). Apple calls the variable "an implementation detail" (Quinn, Apple DTS, developer.apple.com/forums/thread/705868), so if Apple changes it, `fledge_log_echoes` changes with it.

**Line timing.** Ruby writes through to a terminal but buffers standard output to a pipe until its buffer fills or the program ends (`io.c`, `io_binwrite_requires_flush_write`, lines 1942 to 1953 at Ruby 4.1.0-preview1: only `FMODE_SYNC` or `FMODE_TTY` writes at once); standard error is in sync mode already (`rb_io_prep_stderr`). So `fledge_ruby_run`, after `ruby_options` and before Bundler's setup and the program, whenever descriptor 1 is not a terminal, gives `$stdout`'s IO the `FMODE_TTY` Ruby gives an IO on a terminal (`io_check_tty`), which only Ruby's writes read for a descriptor other than standard input (`write_lines_as_printed`, `fledge_ruby.c`). `$stdout` then writes through as to a terminal, while `$stdout.sync` stays false, as under `ruby main.rb`, and `$stdout.tty?`, which asks `isatty` of the descriptor, stays false, so no library sends escape codes into the log. Ruby's header deprecates the field and says of the flag "You cannot change this" (`include/ruby/io.h`, lines 188 to 191), since Ruby sets it once, as it opens the IO; Fledge sets it once too, before the program writes anything. Setting `$stdout.sync = true` whenever descriptor 1 is not a terminal would make `$stdout.sync` true on a phone and false under `ruby main.rb`, a difference any app can read; making descriptor 1 a pseudo-terminal would make `$stdout.tty?` true, so libraries would color the log and `IO#winsize` would answer for a window that does not exist; and leaving `$stdout` buffered would hide an app's output until it ends. Other embedders time their output so too: Briefcase's iOS host unbuffers Python's streams, "We want output to appears in the log immediately" (`config.buffered_stdio = 0`), CPython's iOS and Android streams are line-buffered and never claim to be a terminal, and Chaquopy's Android stream flushes at each newline. The cost is that `$stdout` writes through on a phone where `ruby main.rb` with its output to a pipe buffers, which `Parity::MOBILE_JUSTIFIED` justifies as the fact "$stdout writes through", and that the runtime sets a field Ruby's header deprecates, under a compiler pragma, so a later Ruby that moves the flag needs the runtime changed with it. The parity probe's "$stdout writes through" measures it: Ruby warns when `IO#syswrite` would pass bytes still in the buffer. That holds under `OS_ACTIVITY_DT_MODE` too: the streams then go to the developer tool, which reads them as the log is read (`simctl launch --console` gives the app pipes). On a terminal (`simctl launch --console-pty`) Ruby already writes through, and the flag is Ruby's own.

`test/integration/mobile_output_test.rb` runs `output.c` and `apple.c` with the real `os_log` on a Mac, with and without `OS_ACTIVITY_DT_MODE`, and runs `fledge_ruby.c` linked with the test Ruby to check that a line printed before a sleep reaches the log during it. The mobile parity check compares `$stdout.sync` exactly on both phones.

## Certificates

OpenSSL's compiled-in certificate folder is the build machine's, so the runtime carries Mozilla's CA certificates as `libexec/cert.pem` and points OpenSSL at them as rv-ruby's Ruby, the macOS reference, does (`tasks/runtime_builder/certificates.rb`, the same two edits the musl runtimes make, `runtimes.md`, "musl Linux's Ruby, built in Alpine"): OpenSSL's `SSL_CERT_FILE` is renamed `PORTABLE_RUBY_SSL_CERT_FILE` in its source, and the installed `openssl.rb` sets that to `SSL_CERT_FILE`, or else to `libexec/cert.pem` beside `RbConfig.ruby`, before it loads `openssl.so`. So an app's `ENV` holds nothing of the runtime's when it starts, and gains the one variable at `require "openssl"`, as under rv-ruby's `ruby main.rb`; the parity probe's "ENV from require 'openssl'" compares it.

Both phones keep rv-ruby's way, though the glibc Linux reference is now jdx/ruby, whose `openssl.rb` sets no variable and trusts the computer's own certificates first. That suits a computer, whose administrator and distribution keep its certificates where its OpenSSL looks. A phone's trusted certificates are the system's, managed through its own security APIs, and the runtime's OpenSSL is not set up to read them, so the certificates beside the Ruby are what it trusts either way, and following jdx/ruby would change only that the variable is absent. Fledge's runtime reading the phone's own store would be new work, which this does not take on. The Android parity check, run against jdx/ruby, allows that one variable in the app alone (`doc/contributors/design/parity.md`, "The mobile parity").

- **iOS:** OpenSSL reads the variable.
- **Android:** OpenSSL reads no environment variable in an app. `ossl_safe_getenv` refuses them where `AT_SECURE` is set (`crypto/uid.c`, `OPENSSL_issetugid`), and every app inherits `AT_SECURE` from zygote, which Android starts in an SELinux domain of its own; setting `SSL_CERT_FILE` alone fails on an emulator. So `openssl.so`, where OpenSSL is linked in, is linked with the linker's `--wrap=X509_get_default_cert_file`, which the `openssl_extconf` edit adds to the extension's link after its checks, and which sends OpenSSL's every call of that function to `runtime/mobile/openssl_certificates.c`, compiled into the extension beside its sources, which answers with the file the variable names, read with `getenv`, which `AT_SECURE` does not stop, or else the runtime's own (`fledge_ruby_certificates`, in `libfledgeruby.so`). So a developer's `SSL_CERT_FILE` counts as on a desktop, and `OpenSSL::X509::DEFAULT_CERT_FILE` names the file. The linker's option needs no edit to OpenSSL's source, and reaches every caller, not only Ruby's default store. Putting it in `configure`'s `DLDFLAGS` instead would have reached `rbconfig.rb`, and so every app gem's `extconf.rb`. Apple's linker has no such option and needs none.

## The Java class

Android needs Java for what C cannot do, in `org.setdef.fledge.FledgeRuby` (`runtime/mobile/android/src/main/java/org/setdef/fledge/FledgeRuby.java`):

- **Unpack the asset.** An app carries `lib/`, `libexec/`, and its own code as one stored zip asset, which the class unpacks into the app's files folder on the first launch of each installed version, and leaves on later launches.
- **Set `HOME`** to the app's files folder when Android sets none, as iOS gives every app one, so `Dir.home` is writable.
- **Pass strings as UTF-8 bytes,** not through JNI's `GetStringUTFChars`, which writes modified UTF-8 that differs past Unicode's first plane, and paths canonical: an app's files folder is `/data/user/0/PACKAGE/files`, through a link to `/data/data`, which Ruby resolves `__dir__` through, as the desktop launcher resolves its own folder.
- **Start Ruby on its own thread** with a 64 MB stack (`STACK_SIZE`), never the UI thread, which Android stops an app for blocking: `start` and `startApp`, with `run` and `runApp` for a caller that has its own thread.

It is Java, not Kotlin, so an app need not depend on Kotlin's standard library; Kotlin calls it as it is.

## Licenses of a phone runtime

Each phone runtime passes the license audit before it is archived (`doc/contributors/design/license-audit.md`), and ships only what decision 8 allows, with no LGPL library. Its components are recorded in `runtime/licenses.yml`: Ruby, OpenSSL, libyaml, libffi (on Android in the extension files `openssl.so`, `psych.so`, and `fiddle.so`, not in `libfledgeruby.so`), the NDK's compiler-rt builtins and libunwind on Android (`compiler-rt-ndk`), the Rust standard library in Android's JITs (`rust-std-android`), Mozilla's CA certificates as a file, and Fledge's own embedding API (`fledge-embedding`, MIT), which includes the Android runtime's ruby program. GMP is configured out, iOS's `crypt` is its libSystem's, and Android's `String#crypt` is Ruby's own `missing/crypt.c`, so neither runtime carries libxcrypt.

Two things in the audit exist for phones. An iOS runtime has a Ruby per slice, so a platform's map entry names several prefixes (`runtime/licenses.yml`, `prefixes`), and each gem in them is one component. An AAR is a zip whose entries the app ships, so the audit reads each entry with `unzip`, as `FledgeRuby.aar!ENTRY`, and a copyleft library's code in one fails as it would in a file. The audit's readers for the Android runtime are the NDK's own LLVM tools (`RuntimeBuilder::Android#readers`).

The templates and the embedding API are Fledge's own code, MIT, and the host's compiled code ships in every phone app, which `doc/licensing.md` says. Gradle's wrapper, which no app holds, is Gradle's, under Apache-2.0.
