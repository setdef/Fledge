# ADR 028: Version Fledge by SemVer, With a Major Whenever a Break Is Ready, After a Deprecation

## Context and Problem Statement

From 1.0, a developer installs Fledge from RubyGems.org as well as from its tag (decisions.md, 2026-11-03 and 2026-11-04) and writes a constraint such as `~> 1.2` in a Gemfile, so Bundler reads the version number on every update. The maintainer chose SemVer's form for the versions: "we can go from A.B.C.pre.D to 0.1.0 sem-ver style" (decisions.md, 2026-11-02). He also set what takes a major: "I require a major version bump to drop support for a ruby, or to drop support for an OS "version" (the thing that differentiates MacOS 26 from MacOS 27, not patches etc.)" (decisions.md, 2026-11-03).

His words leave open when a major ships, and how a break reaches developers. Those are this ADR's.

## Decision Drivers

- A built app is a frozen artifact. A Fledge version affects only the next build, and most breaks then fail loudly.
- Fledge embeds Ruby, OpenSSL, and libyaml. A developer who stays on an old Fledge ships an old runtime, and the stores raise their requirements about once a year.
- A compatibility flag costs more than a line of code: a key in `Fledge::Config`, the schema, the help, the docs, and a test matrix across every target.
- A small team cannot patch many old lines.

## Considered Options

1. A major whenever a breaking change is ready, with the number a label, a deprecation in an earlier minor, and no compatibility flags.
2. A major on a schedule, as Ember does, sweeping every deprecation and default switch into it.
3. No majors for as long as possible, with breaking changes behind opt-in flags.
4. A major as a marketing event.

## Decision Outcome

Chosen: option 1, because it fits the drivers: a break fails loudly at the next build rather than in a shipped app, so it can ship when it is ready; a flag costs more than the break it hides; and the old lines to patch are bounded by the live Rubies, not by how many majors Fledge has shipped. A breaking change is a change to what `doc/contributors/design/public-interface.md` freezes (ADR 029). A removal or a changed default is announced by a build-time message and a CHANGELOG entry in at least one earlier minor release. No flag keeps the old behavior: the notice warns, and the major switches. No one holds a change back to shape the number.

The orchestrating agent compared the four ways for the maintainer on 2026-11-03 (decisions.md, 2026-11-03, the bracket of the first entry).

Confidence: medium. It rests on reasoning and on other projects' practice. Fledge has shipped no major yet, so no developer has met a break under it.

### Consequences

- Good, because the patched lines number about one per live Ruby minor, however high the number climbs, since support follows live Rubies rather than majors (`doc/contributors/design/releases.md`).
- Good, because no flag multiplies the test matrix or outlives its reason.
- Bad, because a store that forces a platform floor up forces a major, which can mean a major in a year with no other break.
- Bad, because a developer several majors behind moves through each deprecation notice and migration note.
- Neutral, because the minimum time between a deprecation and its removal, beyond one minor, is not decided.

### Confirmation

The CHANGELOG, which records every breaking change under the version that makes it (AGENTS.md, Changelog), and review of each release commit against `doc/contributors/design/public-interface.md`. No gate checks a version bump against the changes it carries.

## Pros and Cons of the Options

### A major on a schedule

- Good, because developers can plan for it.
- Bad, because a fix that breaks waits for the date, and every sweep is large.

### Opt-in flags instead of majors

- Good, because a developer chooses when to move.
- Bad, because each flag is a key, a schema entry, a help line, and a test axis, kept for as long as anyone uses it.

### A major as a marketing event

- Bad, because the number then says nothing a developer's Gemfile can rely on.

## More Information
