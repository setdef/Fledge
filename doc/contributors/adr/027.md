# ADR 027: An extconf.rb That Runs CMake, on Phones

## Status
Accepted (requested). Agents wrote this ADR and may change it (AGENTS.md, Questions). It extends ADR 022, which compiles a gem's `extconf.rb` for each target of a phone, to an `extconf.rb` that runs CMake before mkmf, and amends ADR 019, section 5, and ADR 022, section 6, on what an extension's author provides. It applies the maintainer's words of 2026-11-02 in `doc/contributors/decisions.md` (a Ruby game on a wrapper for 2D games playtested on a tablet and a phone is 0.2.0's test, and Fledge depends on no wrapper's repository) and those of 2026-10-28 on code as a liability and on each target built on its own system. It adds no `fledge.yml` key and asks nothing of the maintainer.

## Date
2026-11-03

## Context

A game engine shipped as a gem is often C++ that CMake builds, with a thin Ruby extension over it. Its `extconf.rb` runs `cmake` to configure and build the engine's library, then calls mkmf's `create_makefile` for the extension, which links that library through `$LOCAL_LIBS`. The gemspec names only the `extconf.rb`. This is a common shape: the extension is still mkmf's, and CMake is a tool the `extconf.rb` runs, as it might run `pkg-config`.

ADR 022 runs such an `extconf.rb` under the phone runtime's `rbconfig.rb`, with Xcode's or the NDK's compilers put in place of the ones that file records. mkmf's compiles then aim at the phone. A `cmake` the `extconf.rb` runs sees none of that: it reads no `rbconfig.rb`, and Fledge took `CC`, `CXX`, and the flags out of the environment (`MobileExtensions::FOREIGN`). So CMake configures for the computer it runs on.

`examples/cmake_phone` reproduces this without any real engine: a path gem, `tally`, whose `extconf.rb` runs `cmake -S lib -B tally-build` and `cmake --build tally-build` to build `libtally.a` from `tally.cc`, then builds `tally.c`, a C extension that links it. The library reports which system CMake configured it for (`CMAKE_SYSTEM_NAME`, compiled in) and which processor and platform its compiler aimed at (`__aarch64__`, `__x86_64__`, `TARGET_OS_SIMULATOR`). Built with `fledge build` at 19efbfa, with the runtimes of trunk's CI run 41764673083 and CMake 4.3.2:

- **iOS**: CMake found `/usr/bin/c++` (AppleClang 21) and built `libtally.a` for macOS, for both slices. mkmf's `tally.a` was for iOS. `libtool -static` merged the two into each slice's `libFledgeExtensions.a`, and `xcodebuild -create-xcframework` refused it: `binaries with multiple platforms are not supported`.
- **Android**: the same macOS `libtally.a`. The NDK's `ld.lld` warned `archive member 'tally.cc.o' is neither ET_REL nor LLVM bitcode`, skipped it, and linked `libfledgeext.so` anyway, with `tally_sum` and `tally_built_for` undefined (`llvm-readelf --dyn-syms`). The build succeeded; the app would have failed when Android loaded the library. It also needed `libc++_shared.so`, which the package does not carry: the `extconf.rb` names the C++ runtime (`-lstdc++` for Android's `host_os`, `-lc++` on a Mac), as a C extension over a C++ library does on a desktop, and the NDK's clang linked that `-lstdc++` as the shared C++ runtime (its `-lc++` is no better: `sysroot/usr/lib/x86_64-linux-android/26/libc++.so` is the linker script `INPUT(-lc++_shared)`).

ADR 022, section 7, refuses an extension that Rake, CMake, configure, or Cargo builds. That refusal reads the gemspec's `extensions` and never applied here: this gemspec names an `extconf.rb`. The failure was a library built for the wrong system, and on Android a silent one.

## Decision

### 1. CMake's own variable: CMAKE_TOOLCHAIN_FILE

CMake cross-compiles from a toolchain file, which sets `CMAKE_SYSTEM_NAME` and the compilers before the first `project()` (cmake-toolchains(7), "Cross Compiling"). Since 3.21 it reads one from the environment: "The `CMAKE_TOOLCHAIN_FILE` environment variable specifies a default value for the `CMAKE_TOOLCHAIN_FILE` variable when there is no explicit configuration given on the first run while creating a new build tree" (`Help/envvar/CMAKE_TOOLCHAIN_FILE.rst`, lines 4 to 12, at CMake 4.3.2).

So **Fledge writes a toolchain file for each target of the phone and puts its path in `CMAKE_TOOLCHAIN_FILE`** in the environment it runs each `extconf.rb` in (`MobileExtensions::CMake`, and `Target#environment`). An `extconf.rb` runs `cmake` with nothing of Fledge's: the same `system("cmake", "-S", source, "-B", build)` that builds for a desktop builds for each slice and ABI, as long as the build folder is new, which it is, since Fledge unpacks each gem afresh for each target (ADR 022, section 1). An `extconf.rb` that passes its own `-DCMAKE_TOOLCHAIN_FILE` or `--toolchain` overrides Fledge's, as CMake documents.

This is how cibuildwheel builds a Python package's CMake code for Android: it writes `toolchain.cmake` beside the build and sets `build_env["CMAKE_TOOLCHAIN_FILE"]` (`cibuildwheel/platforms/android.py`, lines 320 to 344, called at line 252, at 61c3ae34ca, version 4.3.5), and the package's own build, scikit-build-core or `setup.py`, runs CMake as it always does. scikit-build-core passes a toolchain it is told of as `--toolchain` or `-DCMAKE_TOOLCHAIN_FILE` (`src/scikit_build_core/cmake.py`, lines 266 to 272, at 845e3f6fc4) and otherwise leaves CMake to read the environment.

### 2. The toolchain files

Each is a few lines that set CMake's own variables, which CMake documents, and nothing of Fledge's. Fledge writes them into its build folder, `toolchains/TARGET.cmake`, and they never enter the app.

- **An iOS slice** (`CMake.ios`) uses CMake's own iOS support, as cmake-toolchains(7) describes it ("Cross Compiling for iOS, tvOS, visionOS, or watchOS", lines 585 to 619): `CMAKE_SYSTEM_NAME` `iOS`; `CMAKE_OSX_SYSROOT`, the slice's SDK as `xcrun --sdk iphoneos|iphonesimulator --show-sdk-path` gives it, which selects the device or the Simulator; `CMAKE_OSX_ARCHITECTURES` and `CMAKE_OSX_DEPLOYMENT_TARGET` from the target triple the slice's `rbconfig.rb` records (`arm64-apple-ios15.0-simulator`: `arm64`, `15.0`); and `CMAKE_C_COMPILER`, `CMAKE_CXX_COMPILER`, `CMAKE_OBJC_COMPILER`, and `CMAKE_OBJCXX_COMPILER`, the very clang and clang++ that mkmf is given, so one Xcode compiles everything. The Objective-C compilers are there for a library that enables CMake's `OBJC` or `OBJCXX` language, which CMake would otherwise look for on its own; a library that compiles `.m` files as C, as SDL3's does (`project(SDL3 LANGUAGES C ...)`, `CMakeLists.txt` line 8, and its `-fobjc-arc`, lines 4204 to 4212), gets the same clang. The same document warns that with the Makefile and Ninja generators a project handles "target CPU selection and code signing" itself (lines 588 to 591): the architecture is set here, and a static library is not signed.
- **An Android ABI** (`CMake.android`) sets `ANDROID_ABI` (`arm64-v8a`, `x86_64`) and `ANDROID_PLATFORM` (`android-26`, the API level in the name of the compiler the runtime was built with, `x86_64-linux-android26-clang`), then `include()`s the NDK's own `build/cmake/android.toolchain.cmake`, the file Google's documentation and Gradle's `externalNativeBuild` give CMake with those two variables (developer.android.com/ndk/guides/cmake). At r30 that file hands over to `android-legacy.toolchain.cmake` unless told otherwise (`android.toolchain.cmake`, lines 47 to 57), which reads `ANDROID_ABI` and falls back to `armeabi-v7a` without it (`android-legacy.toolchain.cmake`, lines 160 to 162), reads `ANDROID_PLATFORM` (lines 183 to 228), defaults to the static C++ runtime, `c++_static` (lines 241 to 242), and makes code position-independent (lines 260 and 551 to 553), as a library linked into `libfledgeext.so` must be. Setting the two variables in a file that includes the NDK's, rather than passing `-D` options, holds in CMake's `try_compile` projects too, which read the toolchain file again (the NDK's file lists the variables to carry into them for those who pass `-D`, lines 266 to 280).

### 3. What does not reach the extconf.rb

CMake reads more of the environment than mkmf does (cmake-env-variables(7)). Fledge already kept the developer's `CC`, `CXX`, `CFLAGS`, `CXXFLAGS`, `LDFLAGS`, `SDKROOT`, and deployment targets from a phone's build; it now also keeps `CMAKE_OSX_ARCHITECTURES`, `OBJC`, `OBJCXX`, `OBJCFLAGS`, and `OBJCXXFLAGS`, which would aim CMake at the developer's Mac or give it the developer's flags (`MobileExtensions::FOREIGN`). The developer's `CMAKE_TOOLCHAIN_FILE` is replaced by the target's. `CMAKE_GENERATOR`, `CMAKE_BUILD_TYPE`, `CMAKE_BUILD_PARALLEL_LEVEL`, and the rest pass through: they choose how CMake builds, not what it builds for, and the gem's `extconf.rb` decides them as it does on a desktop (`tally`'s passes `-DCMAKE_BUILD_TYPE=Release`).

### 4. The C++ runtime an extconf.rb names

A C extension over a C++ library has no C++ source of its own, so mkmf links it as C, and its `extconf.rb` adds the C++ runtime to `$libs`, as it must for a desktop: `-lc++` on a Mac and `-lstdc++` on Linux. On a phone neither is right. On iOS the extension's archive goes into the app, which links `-lc++` once for every extension with C++ (ADR 022, section 3). On Android both led to the NDK's `libc++_shared.so` (Context); ADR 022 links an extension with C++ sources with `clang++ -static-libstdc++` instead, so that the package needs no shared C++ runtime.

So **an extension whose `extconf.rb` names `-lc++` or `-lstdc++` is one with C++**, as one with a `.cc` source is (`Linking.cxx_runtime?`, `Linking::CXX_RUNTIMES`), and the name itself is left out of the flags the app links (`Linking.link_flags`). Each phone then links its own C++ runtime as it already does for C++ sources.

### 5. What an extension's author provides (amends ADR 019, section 5, and ADR 022, section 6)

An `extconf.rb` that uses mkmf and calls `create_makefile` once, as before, and that may first run CMake to build libraries the extension links:

- **Run `cmake` with a new build folder each time**, inside the folder the `extconf.rb` runs in (`File.expand_path("tally-build")`), and let CMake find its toolchain in `CMAKE_TOOLCHAIN_FILE`. Pass no `CMAKE_SYSTEM_NAME`, sysroot, or compiler of your own on a phone; pass `CMAKE_BUILD_TYPE` and your project's options as on a desktop.
- **Link what CMake built through `$LOCAL_LIBS`** by path, as mkmf links any static library; Fledge links it into the phone's slice or ABI it was built for (ADR 025, section 2).
- **Build static libraries position-independent** (`POSITION_INDEPENDENT_CODE ON`): on a desktop they go into a shared extension, and on Android into `libfledgeext.so`. The NDK's toolchain turns it on for Android anyway.
- **Name the C++ runtime as on a desktop** when the extension is C over a C++ library (`-lc++` or `-lstdc++`); Fledge links the phone's.
- CMake 3.21 or later on the build computer's `PATH`. Fledge does not provide CMake, as it provides no compiler (ADR 022, section 1); Xcode's and the NDK's are the developer's own.

Fledge still refuses, naming the gem (ADR 022, section 7), an extension that the gemspec says something other than an `extconf.rb` builds: a `CMakeLists.txt`, `Rakefile`, `configure`, or `Cargo.toml` in `extensions`, and a Rust extension. Its message now says that an `extconf.rb` may run CMake. RubyGems builds those with its own builders (`Gem::Ext::CmakeBuilder`, `RakeBuilder`, `ConfigureBuilder`, `CargoBuilder`), each of which would need its own cross-compiling, and none of which makes the static archive and renamed `Init_` function that mkmf's `$static` does.

### 6. Considered, and why not

- **Options Fledge would hand the `extconf.rb`**, such as a `FLEDGE_CMAKE_ARGS` with `-DCMAKE_SYSTEM_NAME=iOS ...`: every gem would need code that knows Fledge. CMake's own variable needs none, and a gem written for cibuildwheel's Android builds already works this way.
- **Only CMake's environment variables, without a toolchain file**: CMake takes compilers from `CC` and `CXX` and flags from `CFLAGS`, but no variable sets `CMAKE_SYSTEM_NAME`, and without it CMake configures for the build computer (`CMAKE_CROSSCOMPILING` false, macOS's or Linux's platform files, `find_*` in the computer's folders).
- **A toolchain from elsewhere**: leetal/ios-cmake's `ios.toolchain.cmake` (b36d5bce6f, 1,227 lines, BSD-3-Clause) predates CMake's iOS support and chooses the slice with its own `PLATFORM` names (`OS64`, `SIMULATORARM64`; lines 58 to 76). CMake has done this itself since 3.14, and a file Fledge would vendor and pin is more than eight lines that set CMake's documented variables. On Android, the NDK's file is the maintained one, and Fledge uses it.
- **The NDK's file itself in `CMAKE_TOOLCHAIN_FILE`**: it reads `ANDROID_ABI` and `ANDROID_PLATFORM` as CMake variables, not from the environment, so the `extconf.rb` would have to pass them, and without them it builds for `armeabi-v7a`.
- **CMake's built-in Android support** (`CMAKE_SYSTEM_NAME Android`, `CMAKE_ANDROID_NDK`, `CMAKE_ANDROID_ARCH_ABI`; cmake-toolchains(7), "Cross Compiling for Android with the NDK"): it works, and cibuildwheel uses a variant with its own compiler wrappers; Google documents and maintains the NDK's file, and Gradle uses it, so it is the one the developer's other Android code builds with.
- **Detecting C++ from the archives an extension links**, by reading their symbols for `__gxx_personality_v0` or `std::` names: it would work for any C++ library, but it reads binaries for what the `extconf.rb` already says in `$libs`, and a desktop link needs that name anyway.

### 7. Verified

On this Mac (Xcode 27.2, CMake 4.3.2, NDK r30), with the runtimes of trunk's run 41764673083 (19efbfa), in `test/mobile_extensions_test.rb`:

- `examples/cmake_phone` compiled for both iOS slices: the `tally.cc.o` CMake built is `platform IOS` in `ios-arm64` and `platform IOSSIMULATOR` in `ios-arm64-simulator` (`xcrun vtool -show-build`), and each extension is C++. Without `CMAKE_TOOLCHAIN_FILE` the same test fails on both.
- Compiled and linked for both Android ABIs: each `libfledgeext.so` is for its machine (AArch64, x86-64), has no undefined `tally_` symbol or C++ runtime symbol, and needs no `libc++_shared.so`. Without the toolchain file it fails on the undefined `tally_sum`, and without the C++ runtime rule on undefined C++ runtime symbols.

In CI, on the `experiment/cmake-phone` branch, whose workflow runs only the Mobile apps jobs, for `examples/cmake_phone` and `examples/native_phone`, with the same runtimes: **run 41779653817, every job green**, with the runners' CMake (4.4.4 on macOS, 3.31.6 on Ubuntu), Xcode 26.5, and the pinned NDK r30.

- **iOS Simulator, iPhone 17 Pro and iPad Pro 13-inch (M5), iOS 26.5**: `CmakePhone totals 10 in C++ that CMake 4.4.4 built for iOS Simulator on arm64, on arm64-darwin`, and status 0, on each. The unsigned Release build for devices links (`minos 15.0, sdk 26.5`), with no warning from xcodebuild.
- **Android x86_64 emulator, API 36, with 4 KB and with 16 KB pages**: `CmakePhone totals 10 in C++ that CMake 3.31.6 built for Android on x86_64, on x86_64-linux-android`, and status 0, on each. The debug and the unsigned release APK pass the job's checks of 16 KB alignment and target API for both ABIs.
- `NativePhone` printed its line on all four, as before.

Not verified: the device slice and arm64-v8a running (built and linked only, as for ADR 022's extensions); a CMake build that looks for other libraries with `find_package` or `find_library` (Fledge's files add no search paths; the NDK's and CMake's iOS platform files decide where CMake looks); the Xcode generator, through `CMAKE_GENERATOR=Xcode`; and an Android APK built on a Mac (this Mac compiled and linked both ABIs in the tests above, and CI built the APKs on Linux).

## Consequences

- A gem whose `extconf.rb` builds its C or C++ library with CMake compiles for the iOS device and Simulator and for Android's arm64-v8a and x86_64 with no change, and no `fledge.yml` key.
- `fledge build ios` and `fledge build android` need CMake on the `PATH` only for such a gem, as its desktop build does; an `extconf.rb` that finds none says so in its own words.
- A C extension that names `-lc++` or `-lstdc++` links as a C++ one on a phone. A gem that named them for another reason (none is known) would link the C++ runtime it does not use.
- A gem whose gemspec names a `CMakeLists.txt` directly is still refused; its author can add a one-file `extconf.rb` that runs CMake and `create_makefile`.
- Not done: other build tools an `extconf.rb` might run (`./configure`, plain `make`, Meson). Each would need its own way to aim at the phone (`--host`, cross files); CMake is the one a game engine meets. An `extconf.rb` that reuses a build folder from an earlier configure keeps that folder's toolchain, as CMake documents.
