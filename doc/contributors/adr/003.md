# ADR 003: An App's Ruby Code Runs as It Does Under ruby main.rb

## Status
Accepted (requested). Agents wrote this ADR and may change it (AGENTS.md, Questions). It applies the maintainer's decisions 9, 10, 20, and 21 in `doc/contributors/decisions.md`. Section 3 follows the orchestrating agent's direction of 2026-10-26, given after it explained decision 11's question to the maintainer; `decisions.md` does not yet quote the maintainer's answer, and `questions.md`, entry C, tracks that.

## Date
2026-10-26

## Context

A developer writes an app, runs it with `ruby main.rb`, and ships it with Fledge. The maintainer's decisions set the bar: the app's source stays identical with and without Fledge, so what needed a `require` still does and what did not still does not (decision 9); every global is what a Ruby developer expects (decision 10); and "my ruby code just works" outranks a small download (decision 20).

The walking skeleton missed that bar in several places, each invented without being asked for:

- The launcher passed `-I ROOT/app`, so `require "foo"` found the app's `foo.rb`. Under `ruby main.rb` it does not; apps use `require_relative`. An app that worked under Fledge could fail under `ruby`, and `$LOAD_PATH` held an entry no Ruby developer expects.
- The launcher passed `--yjit` on macOS and Linux, so `RUBY_DESCRIPTION` read `+YJIT` and `RubyVM::YJIT.enabled?` was true, unlike under `ruby`.
- Runtimes left out Ruby's bundled gems (csv, bigdecimal, minitest, and 36 others), so `require "csv"` failed in a built app and worked under `ruby`.
- macOS and Linux runtimes had no `bin/ruby`, so `RbConfig.ruby` and `Gem.ruby` named a program that did not exist, and an app could not start Ruby again.
- The launcher removed the person's `RUBYOPT`, `GEM_HOME`, `BUNDLE_GEMFILE`, and the rest for good, so the app's `ENV`, and every program it started, differed from what `ruby main.rb` would have seen.

Precedence still holds: nothing of a Ruby the person happens to have may change how the app runs (AGENTS.md, Design precedence 1). Where the two pull apart, the app's own boot and its own gems are protected, and everything else matches `ruby main.rb`.

## Decision

### 1. The launcher runs main.rb as ruby main.rb does

It runs Ruby with the equivalent of `ruby --disable=rubyopt -- ROOT/app/main.rb ARGS`: no `-I`, no `--yjit`, no `-r`, no global or constant of Fledge's own. `--disable=rubyopt` changes nothing an app can see, since `RUBYOPT` is hidden from Ruby's boot anyway (section 3); it guards that boot twice. An app that wants YJIT enables it as Rails does, with `RubyVM::YJIT.enable`. An app that needs its own folder uses `__dir__`, as it would under `ruby`.

### 2. A runtime is a standard Ruby 4.0.9, less only what no running code reads

A runtime keeps every default gem and every bundled gem in Ruby 4.0.9's `gems/bundled_gems` (pinned in `runtime/sources.yml`) that its Ruby installs, with their executables, `.gem` cache, build information, plugins, and C extensions, and the libraries those extensions carry (libffi, with fiddle, whose notice `notices/NOTICES.txt` carries). Every bundled gem is permissively licensed (Ruby, BSD-2-Clause, MIT, or PSF), so none conflicts with decision 8, and the license audit checks each one's declared license on every build (ADR 004).

A macOS or Linux runtime ships `bin/ruby`, built from Ruby's own `main.c` (`runtime/launcher/ruby_main.c`) against the same static libruby and with the same link line as the launcher, and the gems' executables beside it. A Windows runtime keeps RubyInstaller's `ruby.exe`, `rubyw.exe`, and the gems' wrappers. `RbConfig.ruby` and `Gem.ruby` name a program that runs.

A runtime prunes only what no running Ruby code reads: documentation (RDoc, ri, HTML, man pages), C headers, static and import libraries, pkg-config files, debug symbols, and nkf's JRuby-only Java sources (`ext/java`, from the gem's folder and its cached `.gem`), which CRuby never compiles or loads (ADR 004, section 6). It also prunes what a standard Ruby 4.0.9 does not install: rv-ruby's bootsnap and msgpack gems and its `portable_ruby_gems.rb`, and RubyInstaller's tools for setting up MSYS2 and a developer's shell (`ridk`, `setrbvars.cmd`, `startmenu.rb`, the MSYS2 keyring). `RuntimeBuilder.prune` and `prune_windows` say why for each. Runtime archives roughly double (section "Consequences").

### 3. The person's Ruby settings are hidden from Ruby's boot, then restored

Before Ruby starts, the launcher sets aside every variable `scrub.c` names (`RUBY*`, `GEM_*`, `GEMRC`, `BUNDLE_*`, `BUNDLER_*`, `RI_FORCE_PATH_FOR_DLL`) and removes it, so the person's `RUBYOPT`, `RUBYLIB`, `BUNDLER_SETUP`, and the rest cannot change how Ruby, RubyGems, and the app's first requires load. After `ruby_options` returns (Ruby has booted, RubyGems has loaded, and `main.rb` has been compiled but not run), the launcher:

1. has RubyGems work out its paths with `Gem.paths`, from the environment Ruby booted with. `Gem.paths` reads `GEM_HOME`, `GEM_PATH`, and `GEM_SPEC_CACHE` once and keeps the answer (`rubygems.rb` and `rubygems/path_support.rb` at Ruby 4.0.9), so the app's gems stay the runtime's;
2. puts every variable back with its original value (`setenv` on Unix; `_wputenv_s` and `SetEnvironmentVariableW` on Windows), so `ENV`, and every program the app starts, see what they would under `ruby main.rb`;
3. runs `main.rb`.

Ruby's own `gem_prelude.rb` sets the precedent: it removes `BUNDLER_SETUP` while RubyGems loads and puts it back afterwards. Doing this in C, between `ruby_options` and `ruby_run_node`, adds nothing to `$LOADED_FEATURES` or `$LOAD_PATH`, which a `-r` boot file would; the one line of Ruby it evaluates (`Gem.paths if defined?(Gem.paths)`) leaves no trace an app can see.

What still reaches the app is what Ruby and RubyGems read after boot, as under `ruby main.rb`: `GEM_REQUIREMENT_<NAME>` when a gem is activated, `GEMRC` when RubyGems' configuration is first read, `BUNDLE_*` when the app requires Bundler, and `RUBYSHELL` when the app spawns a shell on Windows. Plan 002's vendoring story pins Bundler before section 3's restore when an app ships a Gemfile.

### 4. A parity check proves it on every platform

`tasks/parity.rb` (`rake parity`, run by every Test job in CI) builds the probe app in `test/fixtures/parity` with `fledge build`, runs it, and runs the same `main.rb` with the very Ruby the runtime was made from, unpacked as it ships, as `ruby main.rb` from the app's folder, with the same arguments and environment: the caller's, less their Ruby settings, with an empty `HOME`, and with a `GEM_HOME` and two `RUBY_`/`BUNDLE_` markers standing for a person's. It compares `$0`, `__FILE__`, `__dir__`, `$PROGRAM_NAME`, `ARGV`, `$LOAD_PATH`, `$LOADED_FEATURES`, `RbConfig.ruby` (that it exists and runs), `Gem.ruby`, `Gem.path`, `Gem.dir`, the installed gems and whether each one's main file loads, the default encodings, the standard streams' `sync`, `$VERBOSE`, `$DEBUG`, `ENV` (keys and values), the `ENV` a child Ruby sees, `RUBY_PLATFORM`, `RUBY_DESCRIPTION`, and whether YJIT is on. On Windows it runs both again under code page 437.

Every difference must match an entry in `Parity::JUSTIFIED`, which names the elements it allows and why; anything else fails the job. The allowed differences are:

- **`$0`, `__FILE__`, `$PROGRAM_NAME`:** `main.rb` under `ruby main.rb`, `ROOT/app/main.rb` in the app. The launcher cannot know a relative path, since a person may start the app from any folder; it is what `ruby /path/to/app/main.rb` gives.
- **`Gem.path` and `Gem.dir`:** the person's `GEM_HOME` and `Gem.user_dir` appear under `ruby main.rb` only. The app's gems are the runtime's (Design precedence 1); the person's settings still reach its `ENV` and its child processes.
- **The installed gems, and what loads (macOS and Linux):** rv-ruby's bootsnap and msgpack, which section 2 prunes.
- **`$LOADED_FEATURES`:** the runtime loads Fledge's `rubygems/defaults/operating_system.rb`, which rv-ruby lacks and which replaces RubyInstaller's (ADR 001, section 8), so on Windows RubyInstaller's runtime files, the `win32/dll_directory` extension, and the encodings RubyInstaller's runtime loads appear under `ruby main.rb` only. Ruby loads an encoding when code first needs it, so an app that uses one finds it either way.

### 5. Consoles and code pages match ruby.exe

On Windows the launcher's manifest does not set `activeCodePage`, so a console's code page decides `Encoding.default_external` exactly as it does for `ruby.exe`; the parity check runs both under code page 437 and requires the same answers. A UTF-8 code page for every app would be a difference from `ruby.exe`. On macOS and Linux the launcher turns a bare C locale into a UTF-8 one (Plan 001, spike 1, after Python's PEP 538), because a desktop starts apps with no `LANG`, where a non-ASCII install path would break Ruby's boot; with any other locale it matches `ruby`. Ctrl-C reaches Ruby's own console handler, as for `ruby.exe`; nobody has checked it yet (Plan 002, "Ctrl-C and the console").

## Consequences

- Apps load their own files with `require_relative`, as under `ruby`. The help header says so.
- Runtime archives about double, as CI built them on 2026-10-26: macOS 8.6 MB to 18.7 MB (its folder 28 MB to 58 MB), Linux about 10 MB to 21.0 MB on x86_64 and 21.2 MB on aarch64, and Windows 9.3 MB to 16.8 MB.
- A child Ruby an app starts (`system(RbConfig.ruby, ...)`) runs with the person's own `RUBYOPT` and `GEM_HOME`, as it would under `ruby main.rb`. An app that wants its children isolated clears those variables itself.
- A new difference between Fledge and `ruby main.rb` fails CI until someone fixes it or writes down why it is right.
