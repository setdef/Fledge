# ADR 028: Versions and Support After 1.0

## Status
Draft (requested). Agents wrote this ADR and may change it (AGENTS.md, Questions). The maintainer read the policy in conversation on 2026-11-03 and called it good enough for a first draft. It is not final, and `decisions.md` records only one decision behind it: from 1.0.0 a human releases Fledge on RubyGems.org, without relying on a GitHub Release or a git tag. Everything else here is for the maintainer to confirm.

## Date
2026-11-03

## Context

1.0 tells developers the CLI, `fledge.yml`, and what a built app contains will not change without a major version (Plan 003). After 1.0 a developer installs Fledge from RubyGems.org and writes a constraint such as `~> 1.2` in a Gemfile, so the version number is something Bundler reads on every update.

Four ways to time major versions were weighed in conversation:

1. A major on a schedule, like Ember's, sweeping every deprecation and default switch into it.
2. No majors for as long as possible, with breaking changes behind opt-in flags.
3. A major as a marketing event.
4. A major whenever a breaking change is ready, with the number a non-event.

Facts that decided between them:

- A built app is a frozen artifact. A Fledge version affects only the next build, and most breaks then fail loudly.
- Fledge embeds Ruby, OpenSSL, and libyaml. A developer who stays on an old Fledge ships apps with an old runtime, and the stores raise their minimum SDK levels about once a year.
- Compatibility flags cost more than a line of code. Each one adds a key to `Fledge::Config`, the schema, the help, the docs, and a test matrix across nine targets.
- A published calendar is a commitment that an off-cycle major would break. A calendar for one thing only does not have that problem.
- A mislabeled break is the ordinary risk of any gem. It does not need machinery of its own.
- A small team cannot patch many old lines. A rule that follows live Rubies bounds the lines by the number of Rubies in use, not by how many majors Fledge has shipped.

This ADR names Ember's release process, Rails' maintenance policy, and Ruby's own maintenance schedule from memory. Check each against its source before relying on a date or a number.

## Decision

1. **Semantic versioning.** A breaking change is a change to what 1.0 freezes (ADR 029, section 2). A major ships whenever a breaking change is ready. The number is a label, and no one holds a change back to shape it.
2. **Deprecation before removal.** A removal or a changed default is announced by a build-time message and a CHANGELOG entry in at least one earlier minor release. No compatibility flags are added for breaking changes: the notice warns, and the major switches.
3. **The default Ruby switches once a year.** The first major after Ruby's December release makes the newest Ruby the default, once its first patch release is out and the bundled gems are tested, and by the end of March. A new Ruby arrives earlier, as a minor release, as an extra runtime a developer selects. Where the selection lives (the Gemfile's `ruby` directive or `fledge.yml`) is for a later ADR. A year in which Ruby does not change needs no major for this.
4. **Dropping a Ruby minor is a major.**
5. **Support follows live Rubies.** For each Ruby minor that is not end-of-life, the last Fledge line to support it gets security fixes for the embedded runtime, and platform-deadline fixes where feasible, until that Ruby is end-of-life. The last minor before a Ruby is dropped says so at build time and in its CHANGELOG, and names the line the long-term line for that Ruby, with the date. The repository keeps a maintenance branch for each such line, for example `lts/ruby-4.0`. A line that is the last for no live Ruby gets nothing. A new feature never goes to an old line.
6. **Publishing.** The maintainer publishes each release on RubyGems.org. Agents prepare it and never run `gem push` (AGENTS.md, Releasing).

## Consequences

- At any time the patched lines number about one per live Ruby minor, so three or four, however high the Fledge number climbs.
- A developer who wants the Ruby of an older line must move to that line's last release. If several majors lie between, the deprecation notices and per-major migration notes carry the cost.
- A platform-deadline fix may need newer toolchains and rebuilt runtimes on an old line. The promise there is best effort, and the CHANGELOG says when a fix cannot be made.
- CI builds runtimes for every supported line on every target. A cost that grows is a reason to drop an old Ruby sooner.
- ADR 029 is the 1.0 contract this policy versions, and applies sections 3 and 4 here to Ruby's version and the platform floors until the maintainer confirms them (`questions.md`, entry A).

## Not decided

- Where a developer selects the Ruby, and how a Gemfile `ruby` constraint maps to a runtime.
- The minimum time between a deprecation and its removal, beyond one minor release.
- Whether `fledge build` should warn when a newer patch of its embedded Ruby exists. Bundler already reports newer gems, so only the embedded runtime and platform deadlines would be new; there is no evidence yet that developers need it.
- The exact end-of-life dates, which come from ruby-lang.org's maintenance page when this policy is adopted.
