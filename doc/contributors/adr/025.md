# ADR 025: A Game Whose SDL3 Owns the Main Loop, on Phones

## Status
Accepted (requested). Agents wrote this ADR and may change it (AGENTS.md, Questions). It is the SDL3 spike that ADR 022, sections 5 and 8, describes and did not run, and the first half of Plan 003's story "A game plays on a tablet and a phone". It applies the maintainer's words of 2026-11-02 in `doc/contributors/decisions.md` ("iPadOS, iOS, and Android are our priorities for 0.2.0", no money spent, and Fledge depends on no wrapper's repository) and those of 2026-10-28 on code as a liability and on each target built on its own system. It asks nothing of the maintainer: the agents decide the `host` key (AGENTS.md, Questions). Amended the same day with the `host` key of section 5, which replaced the spike's `host/apply.rb`.

## Date
2026-11-02

## Context

A game engine built as a gem's C or C++ extension over SDL3, as a wrapper for 2D games is, hands SDL the screen, the touches, and the frame loop. ADR 022 compiles such an extension for each target of a phone and links it into the app, and read in SDL3's source how SDL starts on each phone, but built nothing. It left four questions to running code:

1. **iOS: SDL's `SDL_RunApp` and `UIApplicationMain` against Fledge's host.** Fledge's `Host/main.m` (ADR 012, section 5) starts `UIApplicationMain` with its delegates and runs Ruby with `fledge_ruby_run_app` on a separate thread with a 64 MB stack. SDL3 starts UIKit itself and runs the game's main function on the main thread, inside the run loop (`src/video/uikit/SDL_uikitappdelegate.m` at `release-3.4.18`, lines 43 to 64, 354 to 420, and 481 to 489).
2. **iOS: the main thread's stack.** If Ruby has to run where SDL's main runs, it runs on the main thread, whose stack Apple gives as 1 MB on iOS and 8 MB on macOS (Threading Programming Guide, "Thread Costs", Table 2-1), not the 64 MB Fledge gives Ruby's own thread.
3. **Android: SDL's `SDLActivity` against Fledge's `MainActivity`.** SDL's Java side is an Activity that makes the surface SDL draws on, loads SDL's libraries by name, and runs the game's main on a thread it names SDLThread (`android-project/app/src/main/java/org/libsdl/app/SDLActivity.java`, lines 254 to 262, 295 to 311, and 2169 to 2190).
4. **The libraries.** SDL3 has to be built for each iOS slice and Android ABI, linked into the app, and, on Android, carried in the APK; and the question is whether `fledge.yml` needs keys for that, or whether the gem's `extconf.rb` and `bundle config` carry it.

Fledge depends on no wrapper's repository (decisions, 2026-11-02), so the spike is `examples/sdl_phone`: a path gem, `sdl_demo`, whose `extconf.rb` links SDL3 and whose C extension (`sdl_demo.c`) opens a full-screen window and runs a frame loop that calls a Ruby block each frame. Ruby picks each frame's background color, which cycles, and where a white square goes, which follows the last touch, and prints the frames drawn, each touch, and the thread it runs on.

## Decision

### 1. SDL3 is built by SDL's CMake, from a pinned release

`examples/sdl_phone/sdl3/build.sh` downloads `SDL3-3.4.18.tar.gz` from SDL's GitHub release `release-3.4.18`, checks its SHA-256 (`9c75cf16330322c217dedd2e0609f1124f1b54b8633e763467b4684d0f4334a3`, the digest GitHub lists for the asset), and builds it with SDL's CMake build as SDL documents it, once per target, into `OUT/TARGET`:

- **iOS**, on a Mac with Xcode: `-DCMAKE_SYSTEM_NAME=iOS -DCMAKE_OSX_SYSROOT=iphoneos` (or `iphonesimulator`) `-DCMAKE_OSX_ARCHITECTURES=arm64 -DCMAKE_OSX_DEPLOYMENT_TARGET=15.0` (`docs/README-cmake.md`, lines 178 to 264), static (`-DSDL_SHARED=OFF -DSDL_STATIC=ON`), into `ios-arm64` and `ios-arm64-simulator`. A static library links into the app's executable as Fledge links extensions on iOS (ADR 022, section 3), so nothing is embedded. SDL's iOS README recommends its `SDL3.xcframework`, a framework the app embeds (`docs/README-ios.md`, lines 15 to 37); the project Fledge writes embeds no framework of an extension's, and a static build needs none.
- **Android**, with the NDK Fledge's Android build uses (r30, `ANDROID_NDK_ROOT`): the NDK's `android.toolchain.cmake` with `-DANDROID_ABI=arm64-v8a` (or `x86_64`) `-DANDROID_PLATFORM=26` (`docs/README-android.md`, lines 602 to 612), shared (`-DSDL_SHARED=ON -DSDL_STATIC=OFF`). It has to be shared: SDL registers its Java methods from `libSDL3.so`'s `JNI_OnLoad` (`src/core/android/SDL_android.c`, lines 578 to 606), which `System.loadLibrary("SDL3")` calls, and Fledge links `libfledgeext.so` with `--exclude-libs,ALL` (ADR 022, section 3), which would hide a static SDL's `JNI_OnLoad`. The script also copies SDL's Java classes, `android-project/app/src/main/java/org/libsdl/app/`, into the example's Android host, `host/android/src/main/java/org/libsdl/app/`, which git ignores (section 5).

SDL's release script (`build-scripts/build-release.py`, `create_android_archives`, lines 987 to 1100) makes the same builds into an AAR, and its release assets include a prebuilt AAR and a disk image of `SDL3.xcframework`. Building from the source tarball keeps the input one file pinned by SHA-256 and the tools SDL's own documentation names.

**Licenses.** SDL3 is Zlib (`LICENSE.txt`), and so are its Java files, which carry no license header and fall under that file. Zlib asks only that its notice stay in source distributions and that altered sources be marked. **Nothing of SDL goes into a Fledge runtime**, so it is in neither `runtime/sources.yml` nor `runtime/licenses.yml`: it is a dependency of the example's gem, built for the example, and an app's gems and what they link are the developer's choice and responsibility (AGENTS.md, Licensing; ADR 007). `build.sh` writes SDL's `LICENSE.txt` beside the builds.

### 2. `extconf.rb` and `bundle config` carry the library

The gem finds SDL3 the way ADR 022, section 6, says a gem finds a library: `bundle config build.sdl_demo --with-sdl3-builds=OUT` (or `BUNDLE_BUILD__SDL_DEMO`), which Fledge passes to the `extconf.rb` for every target. The `extconf.rb` tells the targets apart by the compiler Fledge gives mkmf (`-target arm64-apple-ios15.0-simulator`, `x86_64-linux-android26-clang`), takes `OUT/TARGET/include`, and links what SDL's `lib/pkgconfig/sdl3.pc` names: on iOS `libSDL3.a` by its path, the fifteen frameworks, `-lpthread`, and `-lm`; on Android `-L OUT/TARGET/lib -lSDL3`. mkmf's checks then link SDL as they link Ruby (`have_func("SDL_Init", "SDL3/SDL.h")`).

Running it found three faults in ADR 022's linking, which Fledge now fixes (tests in `test/mobile_extensions_test.rb`):

- **Frameworks lost their names.** `MobileExtensions.link_flags` kept `-framework NAME` as two words, and the flags were merged with `uniq`, so `-framework UIKit -framework Metal` became `-framework UIKit Metal`. A framework is now one flag, `-Wl,-framework,NAME`, the form `sdl3.pc` writes and clang passes to the linker.
- **Each slice's static library went to both.** A static library an `extconf.rb` named went into `OTHER_LDFLAGS`, which every slice of the Xcode project shares, so the Simulator's link took the device's `libSDL3.a` too. `MobileExtensions.target_build` now puts such a library with that target's archives, which `libtool -static` merges into the target's slice of `FledgeExtensions.xcframework` (and which the NDK links into `libfledgeext.so` on Android). The project also no longer points at a file in the developer's build folder.
- **`libSDL3.so` stayed out of the APK.** `libfledgeext.so` needs it (`NEEDED`), and Android loads native code only from the libraries the package holds. `MobileExtensions.carry_shared_libraries` copies each `-lNAME` that the extension's `-L` folders hold as `libNAME.so` into `src/main/jniLibs/ABI/`, beside `libfledgeext.so`; a name found in none of them is the system's, as `-llog` is.

So **libraries need no `fledge.yml` key**: what the gem's `extconf.rb` links, Fledge links and carries.

### 3. iOS: Ruby runs on the main thread, inside SDL's main

What was run, in the iOS Simulator (iOS 26.1, Xcode 27.2, on this Mac):

- **Fledge's host, unchanged** (Ruby on the 64 MB thread Fledge starts, UIKit started by Fledge's delegates): `SDL_Init` refuses, `SDL_Init: Application didn't initialize properly, did you include SDL_main.h in the file containing your main() function?`. SDL's video wants SDL's `SDL_RunApp`, or at least `SDL_SetMainReady`.
- **The same, with Ruby's thread calling `SDL_SetMainReady` first** (`SdlDemo.claim_main_thread`): the app dies with `EXC_BREAKPOINT` as soon as SDL's video starts. The crash report's faulting thread is Ruby's, in `SDL_InitSubSystem`, `SDL_VideoInit`, `UIKit_SuspendScreenSaver`, and `-[UIApplication _setIdleTimerDisabled:forReason:]`, ending in `BSServiceMainRunLoopQueue` with "threading violation: expected the main thread". SDL's UIKit code makes UIKit calls that must be on the main thread, and SDL says as much (`src/SDL.c`, lines 401 to 407: "On Apple platforms this is a requirement").
- **SDL's host**: a `main` that calls `SDL_RunApp(argc, argv, run_ruby, NULL)`, where `run_ruby` calls `fledge_ruby_run_app`, and an `Info.plist` that names `SDLUIKitSceneDelegate` as the scene's delegate. Ruby runs on the main thread, inside SDL's run loop, calls SDL directly from the block, and SDL's `SDL_PollEvent` turns the run loop. It drew and took touches, as section 6 shows.

This is how kivy-ios runs Python under SDL: its template `main.m` includes `SDL_main.h` (`kivy_ios/tools/templates/{{ cookiecutter.project_name }}-ios/main.m` at fd363d49ed, line 9), so its `main` (line 15) becomes SDL's main function, which starts Python (line 66) and runs the program (line 91) on the main thread.

Running Ruby on a separate thread and sending each SDL call to the main thread (`SDL_RunOnMainThread`, `dispatch_sync`) was considered and not built: SDL's renderer and window functions are documented for the main thread, so every call the game's Ruby makes would cross threads, and the engine, not Fledge, would carry that.

**The stack.** Measured on the main thread under SDL's host (`pthread_get_stacksize_np`): **8176 KB** in the Simulator with no flag, and **65536 KB** with `-Wl,-stack_size,0x4000000` in `OTHER_LDFLAGS`; the unsigned device build's `LC_MAIN` holds `stacksize 67108864`. Ruby's thread under Fledge's host has 65548 KB. How deep Ruby recurses before `SystemStackError`, through a C method at every level (a lambda calling itself from `Array#each`): **3970 levels in all three**, because there Ruby's VM stack, 1 MB for the main thread, runs out first. The machine stack decides it below that: the same probe on this Mac's desktop Ruby 4.0.9, with `ulimit -s` setting the main thread's stack, recursed **392 levels at 512 KB, 807 at 1 MB, and 3970 at 8 MB** (6601 at 8 MB with `RUBY_THREAD_VM_STACK_SIZE` at 64 MB), about 1.25 KB a level. So on a device's 1 MB main thread, if iOS keeps Apple's documented size, Ruby would get about a fifth of the depth it has in the Simulator, raising `SystemStackError` cleanly; `-Wl,-stack_size` asks for 64 MB, and whether a device's kernel grants it was not run (no device; decisions, 2026-11-02). Two limits found: ld takes `-stack_size` only for a main executable ("-stack_size option can only be used when linking a main executable"), and Xcode's Debug configuration links the app's code into `NAME.debug.dylib` (`ENABLE_DEBUG_DYLIB`), so the host sets `ENABLE_DEBUG_DYLIB = NO`.

### 4. Android: an SDLActivity under Fledge's name, Ruby on a 64 MB thread

SDL's Java side has to be the Activity: it makes the `SDLSurface` that SDL draws on, and SDL's video calls back into `SDLActivity`'s static methods. The smallest arrangement found is one class, `examples/sdl_phone/host/android/src/main/java/org/setdef/fledge/host/MainActivity.java`, in place of the `MainActivity` Fledge writes, with the same name and package, so the manifest Fledge writes needs no change. It extends `SDLActivity`, returns `{"SDL3", "fledgeruby", "fledgeext"}` from `getLibraries()` (SDL first, so its `JNI_OnLoad` registers SDL's methods before Ruby's extensions load), and overrides `main()`, which SDL calls on SDLThread, to run Ruby with `FledgeRuby.startApp` on a thread with FledgeRuby's 64 MB stack, and wait for it, so the game ends when Ruby does. Overriding `main()` replaces SDL's `nativeRunMain`, which `dlopen`s a library and looks up `SDL_main` (`SDL_android.c`, lines 827 to 916); the app has no `SDL_main`. SDL's video then runs on Ruby's thread, which SDL takes for its video thread on Android (`SDL.c`, lines 401 to 407: "On other platforms, this is the definition"). Launched with the extra `fledge.sdlthread`, it runs Ruby on SDLThread itself instead, to measure that thread's stack.

**The stack, measured** on x86_64 emulators, API 36 (`pthread_getattr_np`, and the probe of section 3): Ruby's thread has **66593 KB** and recurses **3970** levels, with 4 KB and with 16 KB pages. SDLThread, made with Java's default stack size, has **1057 KB**; with 4 KB pages Ruby there recurses **867** levels, and with 16 KB pages the probe's `rescue SystemStackError` did not hold: the program ended with `main.rb:28:in 'each': stack level too deep (SystemStackError)` and status 1, in two runs out of two. Why the rescue missed was not established. Either way SDLThread is too shallow for Ruby, and the 64 MB thread is the arrangement.

SDL's twelve Java files enter the Gradle project as sources, in `src/main/java/org/libsdl/app/`, as SDL's `android-project` holds them (`docs/README-android.md`, line 124, which also advises subclassing `SDLActivity`, lines 177 to 198). python-for-android does the same: its `PythonActivity` extends `SDLActivity` (`pythonforandroid/bootstraps/sdl2/build/src/main/java/org/kivy/android/PythonActivity.java` at 1c9a4b4f81, line 39) and loads its own libraries (line 68).

### 5. What a project supplies, and how: `host`

Beyond the gem and its `extconf.rb`, a game whose SDL owns the main loop supplies its host, which no `extconf.rb` can carry:

- **iOS**: `Host/main.m` calling `SDL_RunApp` with a main function that runs `fledge_ruby_run_app` (`examples/sdl_phone/host/ios/Host/main.m`, 50 lines, which declares the two SDL functions it calls so that it needs no SDL headers); `SDLUIKitSceneDelegate` in `Host/Info.plist`; and a `project.yml` that puts `-Wl,-stack_size,0x4000000` in the project's `OTHER_LDFLAGS`, which the target's `$(inherited)` takes, and sets `ENABLE_DEBUG_DYLIB = NO`.
- **Android**: the `MainActivity` above, and SDL's Java files, which `sdl3/build.sh android` copies from SDL's release into the host.

`fledge build` writes each phone's project afresh (ADR 012), so a change made in that project lasts until the next build. The spike's first runs made these changes after each build with a script, `host/apply.rb`, which patched `Info.plist` and `project.yml` and ran XcodeGen a second time. A framework would carry such a script for every game. Instead, the files live in the app's own project, and `fledge.yml` names their folder for each phone:

```yaml
ios:
  host: host/ios
android:
  host: host/android
```

This is Vlissides' Generation Gap (*Pattern Hatching*, chapter 3): the generated half and the hand-written half sit in separate files, so generating again loses nothing. Fledge's build is the template method and the host's files its hooks, as Fowler's Plugin (*Patterns of Enterprise Application Architecture*) puts a replaceable part behind a fixed seam. The shape, one mapping for each phone with one key in it, matches how Briefcase scopes a setting to a platform (a table of its own for `iOS` or `android` under the app's) and buildozer to Android (its `android.` options), and leaves room for a phone's next setting beside `host`. What it does:

1. **It copies every file in the folder over the project**, at the same path relative to the folder, once Fledge has written its template, the runtime, the extensions, and `fledge/`, and before Fledge fills its marks (`@@NAME@@` and the rest) and XcodeGen reads `project.yml`. A host file replaces Fledge's at its path, whole, or joins the project. Fledge merges nothing: a merge of YAML, property lists, or Gradle files would be code of Fledge's for formats it does not own (decisions, 2026-10-28). XcodeGen's own `include`, which merges one spec into another, was considered and not taken, since it serves `project.yml` alone, not `main.m`, `Info.plist`, or Android's files. The one thing Fledge does to a host's file is fill its marks in a host's copy of a template it marks (`project.yml` on iOS; `settings.gradle`, `build.gradle`, the manifest, `strings.xml`, and `MainActivity.java` on Android), so a copied `project.yml` still takes the app's name, identifier, version, and the extensions' link flags from `fledge.yml` and the gems, as Briefcase fills a project's own template with the app's values.
2. **The host wins.** Replacing Fledge's file is the point. The build says which of Fledge's files the host replaced, in one line on the error stream, where progress goes, since standard output holds only the project's path: `host/ios replaces Fledge's Host/Info.plist, Host/main.m, project.yml`. When a release of Fledge changes a template, that line names the copies to compare with it. Files the host adds go unmentioned.
3. **It refuses a host it cannot copy.** When it reads `fledge.yml`, Fledge refuses a `host` that is not text naming a folder in the project, by the rule a program's path follows (ADR 024): relative, with `/` between folders, and no segment empty, `.`, or `..`, so `../shared` and `/Users/me/host` fail, naming the file and the phone. When it writes the phone's project, it refuses a host that is not a folder, or that a link leads out of the project, before it writes anything.
4. **The folder stays out of the app.** Its files are the project's, not the program's, so the build leaves the folder out of `fledge/app/`.
5. **Each key is its own phone's.** Desktop builds ignore both, `fledge build ios` ignores `android`, and `fledge build android` ignores `ios`. Only that phone's build looks for the folder, so a desktop build succeeds before `sdl3/build.sh` has made anything.

`examples/sdl_phone` names `host/ios` (`Host/main.m`, `Host/Info.plist`, `project.yml`, and the UI test of section 6 with its target) and `host/android` (`MainActivity.java` at its package's path, and SDL's Java). Fledge's own hosts are unchanged: a pure-Ruby app names no host, keeps Ruby on its own thread, and shows Fledge's screen.

### 7. Libraries need no fledge.yml key

The `extconf.rb` and `bundle config build.NAME` carried SDL3 to every target, and Fledge links static libraries per target and carries shared ones into the APK (section 2). So `fledge.yml` has no key for libraries. The host did need something: the iOS changes and the Android Activity and Java files of section 5 come from no gem's `extconf.rb`, and have to be laid on the project after every build. Section 5's `host` key does that, as the Generation Gap pattern (Vlissides, *Pattern Hatching*) asks: the developer's files live apart from the generated ones, and regenerating the project never loses them. The agents decided it (AGENTS.md, Questions), since the files it copies are the project's and the project Fledge writes was already the developer's to change (ADR 012). To remove it, delete `Config::Phone` and `MobileProject#place_host`; a framework then changes the project after each build.

## Consequences

- A game engine over SDL3 can ship on iOS and Android through `fledge build` with its library linked by its `extconf.rb`, and an SDL host: Ruby on the main thread inside `SDL_RunApp` on iOS, and an `SDLActivity` that runs Ruby on a 64 MB thread on Android.
- Native gems that link a static library on iOS link it per slice, frameworks link whole, and Android apps carry the shared libraries their extensions link; ADR 022's not-yet-verified "an extension that links a vendored static library or a framework" is now verified for a library outside the gem.
- Fledge's runtimes and hosts are unchanged, and no SDL ships in a runtime.
- A wrapper ships SDL's host as files in the game's project, named by `ios: host:` and `android: host:` in `fledge.yml`, and runs no step of its own after `fledge build`. A host's copy of one of Fledge's templates is the developer's to keep in step with Fledge's, and the build names each copy it used.
- What remains before a game on that wrapper runs, on Fledge's side: a run on a real Android phone, and the main thread's stack measured on a device (an iPad ran a game on 2026-11-05, which did not measure it); and the engine's C++ extension and its other SDL libraries built the same way.
