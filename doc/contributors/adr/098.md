# ADR 098: Take CRuby from jdx/ruby on glibc Linux, from rv-ruby on macOS, and from RubyInstaller on Windows

## Context and Problem Statement

Each desktop runtime needs a relocatable CRuby built for its platform (ADR 093). Fledge took it from rv-ruby (spinel-coop/rv-ruby) on macOS and glibc Linux, and from RubyInstaller (oneclick/rubyinstaller2) on Windows. rv-ruby builds its Linux Rubies on Ubuntu 24.04, so an app needed glibc 2.39 or newer, and did not run on Ubuntu 22.04, Debian 12, RHEL 8 or 9 and their clones, or Amazon Linux 2023. The maintainer had accepted that floor ("2.39 is fine", `decisions.md`, 2026-10-26, decision 7); on 2026-11-22, shown the systems it leaves out, he allowed the Linux Ruby's source to change, "and so would be switching away from rv-ruby entirely if you so judge it valuable".

jdx/ruby (github.com/jdx/ruby), a fork of rv-ruby that publishes the precompiled Rubies mise downloads, builds the same shape of tree in manylinux2014 containers and fails its own build if a file needs more than glibc 2.17. Which project's Ruby does each platform take, or does Fledge build its own?

## Decision Drivers

- An app should run on the Linux people run: the distributions their vendors still support.
- Fledge maintains as little as it can (AGENTS.md: code is a liability).
- The Ruby must be relocatable: on macOS and Linux a static libruby the launcher can link (ADR 001), with its extensions as files; on Windows Ruby's DLL in RubyInstaller's tree.
- Every download is pinned by version and SHA-256, and RubyInstaller's by its signature too.
- The app's Ruby behaves as the same Ruby does under `ruby main.rb` (Design precedence 2).

## Considered Options

1. **jdx/ruby on glibc Linux, rv-ruby on macOS, RubyInstaller on Windows,** each pinned in `runtime/sources.yml`.
2. **rv-ruby on macOS and glibc Linux, RubyInstaller on Windows,** as before.
3. **jdx/ruby on macOS as well as glibc Linux.**
4. **Build CRuby in Fledge's CI for glibc Linux,** in an old-glibc container, as python-build-standalone builds CPython and as Fledge already builds Ruby for musl Linux.

## Decision Outcome

Chosen: option 1, because it lowers the Linux floor with a maintained Ruby that Fledge does not build. jdx/ruby's glibc builds measured at most GLIBC_2.17 in every file, on x86-64 and ARM64. Fledge's own compiled parts (the launcher, `bin/ruby`, libxcrypt) set the floor above that: they are built in the manylinux_2_28 image, pinned by digest, because the compiler of manylinux2014 reports a double free in the launcher that is not there under the analyzer gate, and the gate is not weakened. So the floor is glibc 2.28, which every distribution named above has.

macOS stays on rv-ruby because jdx/ruby's macOS files declare macOS 26.0 as their minimum, where rv-ruby's declare 14.0. Windows stays on RubyInstaller, its x64 and its ARM64 builds. For musl Linux Fledge builds Ruby itself (`doc/contributors/design/runtimes.md`, "musl Linux's Ruby, built in Alpine"). Building Ruby for glibc Linux too waits until jdx/ruby stops publishing, publishes a build that fails Delivery, or cannot be relied on; whether to do it then is the maintainer's (`questions.md`, I).

Confidence: high that it works on x86-64: the runtime built from jdx/ruby in the pinned image passes the license audit and the parity check, and no file in it needs more than GLIBC_2.25. The ARM64 runtime, and Delivery on the oldest distributions the floor admits, are CI's to show.

### Consequences

- Good, because an app runs on Ubuntu 22.04, Debian 12, RHEL 8 and 9, and Amazon Linux 2023.
- Good, because Fledge's Rubies are still ones other projects build and test, and a new Ruby is a pin to move.
- Good, because an app trusts the computer's own certificate store first, as jdx/ruby's Ruby does and as a native Linux program does, and the bundled file only where the computer has none.
- Bad, because Fledge now depends on three projects' release schedules, and jdx/ruby is one maintainer's.
- Bad, because the Linux runtime is built in a container, which needs three Perl packages the image lacks, each pinned by SHA-256, and those are not watched for newer builds.
- Bad, because jdx/ruby's tree carries no notices or SBOM, so `runtime/licenses.yml` names what it compiles in (OpenSSL, zlib, libffi, libyaml, libxcrypt) from its recipes, and whoever moves the pin checks them again.
- Bad, because jdx/ruby's `rbconfig.rb` puts its own folder first in `PKG_CONFIG_PATH` each time Ruby starts, so the app's value differs from `bundle exec`'s, which starts Ruby twice; `Parity::JUSTIFIED` says so.
- Bad, because a gem compiled on the developer's computer still needs that computer's glibc, so an app with such a gem has the higher floor of the two.
- Bad, because each upstream tree carries what a developer's Ruby needs, which the runtime builder prunes and replaces, and RubyInstaller's signing key expires on a known date, which whoever moves the pin must follow.

### Confirmation

Every runtime build (`rake runtime`) checks each download against its pin, and RubyInstaller's archive with `gpgv` against the pinned key, by fingerprint; a glibc runtime build fails if any file it stages needs a newer glibc than the platform's floor. CI's "Licenses of the whole upstream tree" jobs audit each source's whole tree, and CI builds, tests, and delivers every runtime on a runner of its platform.

## Pros and Cons of the Options

### rv-ruby on glibc Linux, as before

- Good, because its tree carries notices and an SBOM, and one project serves macOS and Linux.
- Bad, because its Linux builds need glibc 2.38 on x86-64 by measurement, and 2.39 by the runner they are built on.

### jdx/ruby on macOS too

- Good, because macOS and glibc Linux would share one upstream.
- Bad, because its macOS files declare a minimum of macOS 26.0, far above the floor Fledge states.

### Fledge's own build for glibc Linux

- Good, because Fledge would choose the floor and the libraries.
- Bad, because Fledge would maintain a build of Ruby on its most used Linux platforms, and keeping its libraries current would be Fledge's own work.
