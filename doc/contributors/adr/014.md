# ADR 014: Each Version Pins Its Runtimes by SHA-256

## Status
Accepted (requested). Agents wrote this ADR and may change it (AGENTS.md, Questions). It carries out AGENTS.md's rule to pin every downloaded input by SHA-256 for Fledge's own runtimes, and supersedes ADR 001, section 2's second paragraph, which left a version's runtimes checked only against its release's `SHA256SUMS` until 1.0. It is Plan 002's story "Pin runtimes by hash."

## Date
2026-11-01

## Context

`fledge build` downloads a runtime, and to compile a gem its build-only companion, from the GitHub Release of its own version (ADR 001, section 2; ADR 006), and a phone's runtime the same way (ADR 012). Through 0.0.1.pre.11 it checked each download against the release's `SHA256SUMS`, fetched from the same release at the same moment. That catches a damaged download. It does not catch a release whose asset and `SHA256SUMS` were both replaced, by anyone who can write to the repository's releases or who controls the connection's trust: the check and the thing checked come from one place.

Every tool that downloads prebuilt interpreters pins them in its own code instead. uv commits `crates/uv-python-managed/download-metadata.json` (astral-sh/uv at 564a2074), a `sha256` for every python-build-standalone build it can install, written by `fetch-download-metadata.py` from builds python-build-standalone already published; a uv release knows every hash before it ships. Homebrew does the same for its own builds: its CI builds a formula's bottles as workflow artifacts, `brew pr-pull` downloads those artifacts (`Library/Homebrew/dev-cmd/pr-pull.rb` at Homebrew/brew 1f55ebf8, lines 160 to 176), and `brew pr-upload` runs `brew bottle --merge --write`, which commits each bottle's SHA-256 into the formula, and then uploads the same bottles (`dev-cmd/pr-upload.rb`, lines 55 to 62 and 116 to 122). Bundler pins each gem in a lockfile's `CHECKSUMS` section, which Fledge already requires of an app (ADR 005).

Fledge's case is Homebrew's, not uv's: the runtimes are built by the same repository, for the same version, and their file names carry that version (`fledge-runtime-VERSION-PLATFORM.tar.gz`). A version cannot pin hashes of files built after it is tagged. Building them first and pinning them after is easy only if a second build of the same commit gives the same bytes, and it does not: since ADR 010 each runner's own tar writes the archives, with the time of the build in them, and the launcher is compiled on each runner. Making every runtime build reproducible (fixed timestamps, sorted entries, the same compilers' output byte for byte on macOS, Linux, and Windows) is a larger project with nothing to show a developer until it is complete, and it would have to stay complete through every change to the runtime.

## Decision

### 1. The gem ships its release's SHA256SUMS

`lib/fledge/SHA256SUMS` holds the SHA-256 of every asset of the version's release, one line per asset, sorted by name, in the form `sha256sum` writes and `sha256sum -c` reads. It is the release's `SHA256SUMS`, byte for byte, so anyone can check a release with the gem's own file. `Fledge::Runtimes` takes the SHA-256 for every runtime and companion it downloads from this file, never from the release, and checks a runtime found in the cache against it too, downloading it again when it does not match, since a cache is a folder any program the developer runs can write to. A version whose file names no SHA-256 for a runtime is not a released Fledge (a commit between releases, whose runtimes no release holds) and says so, naming `FLEDGE_RUNTIME_DIR`. Runtimes in `FLEDGE_RUNTIME_DIR` are the developer's own builds and are not checked.

A plain `SHA256SUMS` was chosen over a YAML or JSON file of Fledge's own because its format is the one release already publishes and every system's tools read (GNU's `sha256sum`, `shasum -a 256 -c` on macOS); it needs no generator beyond writing a hash and a name.

### 2. A release is two commits, and publishes what the first one's CI built

1. **The release commit** bumps `Fledge::VERSION` and the CHANGELOG, as before, and is pushed to `trunk`. CI builds every runtime from it and delivers each, as on every push, and keeps the runtimes as workflow artifacts for 14 days.
2. **The pin commit.** `bundle exec rake runtime:pin` (`tasks/runtime_pins.rb`) downloads that CI run's runtime artifacts with the GitHub CLI, refuses unless they are exactly `RuntimeBuilder.release_assets` for the version, and writes their SHA-256s into `lib/fledge/SHA256SUMS`. That file is the commit's only change. It is pushed, its CI must pass, and it is the commit that is tagged.
3. **`release.yml`**, on the tag, runs CI on the tagged commit, then checks that the tagged commit changes nothing but `lib/fledge/SHA256SUMS` from its parent, finds the parent's successful CI run on `trunk`, downloads that run's runtimes (not the tag's own run's, which are new bytes), checks that their names are exactly the release's and that each matches its pin with `sha256sum --strict -c`, and publishes them with the pins as the release's `SHA256SUMS`. A tag whose pins do not match the runtimes it would publish fails before anything is published.
4. **`installed.yml`** then checks the published `SHA256SUMS` against the tag's `lib/fledge/SHA256SUMS` and every asset against it, and installs Fledge from the tag on each platform, whose `fledge build` downloads the runtimes and checks them against the gem's pins.

The pin commit changing only the pins is what ties the published runtimes to the tagged source: every file a runtime is built from is the same in both commits. Homebrew's bottle commit, likewise, changes only the formula's `bottle do` block.

The 14-day artifact retention bounds the window between the two commits; a release that misses it pushes the release commit's work again (any new commit), and pins that.

### 3. 0.0.1.pre.11's pins came from its release

The first `lib/fledge/SHA256SUMS` is `v0.0.1.pre.11`'s published `SHA256SUMS`, taken from the release on 2026-11-01, so that a gem installed from `trunk` between releases, whose version is still 0.0.1.pre.11, downloads and checks that release's runtimes. From 0.0.1.pre.12 on, every version's pins come from the runtimes its release commit's CI built.

## Consequences

- A release asset replaced after its version was tagged fails every `fledge build` that downloads it, with the expected and actual SHA-256, and leaves nothing in the cache. The tests prove it with a loopback server whose asset and `SHA256SUMS` agree with each other and not with the pins.
- Releasing takes one more push and one more CI run, about 25 minutes. AGENTS.md, Releasing, gives the steps.
- The runtimes a release publishes were delivered by their own CI run on `trunk`, and `installed.yml` delivers them again from the release; the tag's own CI run proves the tagged source, whose runtimes it builds and throws away.
- A commit between releases cannot download runtimes for its own version, which no release holds; it never could.
- Reproducible runtime builds would let one commit do, and would let anyone rebuild a release and compare. They stay open; nothing here prevents them.
