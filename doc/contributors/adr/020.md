# ADR 020: The Gems Real Apps Lock

## Status
Accepted (requested). Agents wrote this ADR and may change it (AGENTS.md, Questions). It finishes what ADR 005 and ADR 006 listed as "not yet" for an app's Gemfile, and applies the maintainer's decisions 9, 10, and 20 in `doc/contributors/decisions.md` (an app's code runs as it does under `bundle exec`) and the words of 2026-10-28 (an app's gems, licenses and all, are its developer's choice: nothing here checks, warns about, or refuses a gem for its license). It amends ADR 005 (section 5, the settings of the app's `.bundle/config`; section 6, which refused path gems outside the project; the closing "Not yet") and ADR 006 (section 7, which refused git submodules and path gems with extensions).

## Date
2026-11-01

## Context

Plan 003's story "The gems real apps lock" named six kinds of Gemfile that `fledge build` could not ship, or shipped in a way that differed from `bundle exec`. Bundler's own behavior is the reference for each, read at Bundler 4.0.20 (the version pinned in `Gemfile.lock`; paths are in `lib/bundler/` of that gem) and Ruby 4.0.9's RubyGems (`lib/rubygems/`).

What already worked, which this ADR leaves alone: git gems without submodules (ADR 006, section 7), gems from `vendor/cache` (ADR 005, section 6), build options from `bundle config build.NAME` (ADR 006, section 6), gems in the `development` and `test` groups left out, and a path gem inside the project without an extension or an executable, which ships as part of the project.

What did not:

1. **Optional groups.** The plan says they ship like any other group. They do not under `bundle exec`: `Definition#requested_groups` is the Gemfile's groups, less the `without` setting and the optional groups, plus the `with` setting (`definition.rb` lines 1239 to 1243; `Dsl#group`, `dsl.rb` lines 197 to 205, records `optional: true` groups). Fledge shipped every group but `development` and `test`, and wrote `BUNDLE_WITHOUT: development:test` and nothing else into the app's `.bundle/config`. So an optional group's gems shipped, and Bundler in the app never put them on the load path; and a project that asks for one in its own `.bundle/config` (`BUNDLE_WITH: extras`), as `bundle exec` would honor, got an app whose Bundler did not set it up.
2. **Gem servers that need credentials or mirrors.** Fledge downloaded `REMOTE/gems/FILE` with the lockfile's remote and no login.
3. **Git submodules.** Refused.
4. **Path gems outside the project.** Refused.
5. **Path gems with extensions.** Refused.
6. **Gem executables.** Fledge installed no executable of a gem it shipped, as ADR 005 section 6 chose ("only a shell uses them, and they would name the Ruby that built the app"), but under `bundle exec` the bundle's `bin` folder is on `PATH` with every gem's wrapper in it.

## Decision

### 1. Groups are Bundler's, and the app's own settings carry them

`Fledge::Bundle` asks Bundler for the groups the app sets up with the project's settings (the project's `.bundle/config`, `BUNDLE_WITH` and `BUNDLE_WITHOUT` in the environment, the developer's own), by `Definition#requested_groups`, with `development` and `test` always added to `without` and removed from `with`: a built app has no development gems (ADR 005). It ships exactly the gems of those groups, and writes the same two settings into the app's `.bundle/config` (`BUNDLE_WITHOUT`, and `BUNDLE_WITH` when the project asks for a group), the level of Bundler's settings that wins, so Bundler in the app sets up what was shipped. An optional group ships when, and only when, the project's `with` names it; the plan's "ship like any other" was wrong and is corrected.

### 2. A gem server is asked as Bundler asks it

`Fledge::Bundle::Sources` builds each gem's remote with `Bundler::Source::Rubygems::Remote` (`source/rubygems/remote.rb`, line 9 on), which applies `Bundler.settings.mirror_for` (`bundle config mirror.URL`; `settings.rb` line 176) and `credentials_for` (`bundle config HOST USER:PASSWORD`, or a login in the Gemfile's source URL; line 185), the same two calls Bundler's own fetcher makes, and runs with Bundler's root at the project, so the project's `.bundle/config` is read. `Fledge::LockedGem` carries the address (`remote`, with the mirror, without a login) and the login (`credentials`) apart, so nothing Fledge prints shows a password. `Fledge::Download` sends the login by HTTP Basic authentication to that host and port only, never to another a redirect leads to. A server that answers 401 or 403 fails the build with a message that names the gem and the server and says how to set the login as Bundler reads it (`bundle config set --local HOST USER:PASSWORD`, or `BUNDLE_HOST`). Not done: Bundler's `fallback_timeout` for an unreachable mirror is Bundler's own probe (`Mirrors#for`), which `mirror_for` runs; Fledge adds none.

### 3. Submodules are checked out as Bundler checks them out

A git source with `submodules: true` gets `git submodule update --init --recursive` in the checkout, before its gemspecs are evaluated (`Bundler::Source::Git::GitProxy#copy_to`, `git_proxy.rb` lines 137 to 176, which runs it after `git reset --hard`). Without the option the submodules stay out, as Bundler leaves them. Git's own files, a `.git` file in each submodule among them, stay behind (`Fledge::GitPackage`).

### 4. A path gem outside the project ships in Bundler's place for a copy

Bundler has its own way to ship a path gem that is outside the project: `bundle cache --all` copies it to `vendor/cache/NAME` (`Source::Path#cache`, `path.rb` line 84), and a Bundler that finds that folder uses it in place of the original path, even when the original is gone (`#specs`, line 102, and `#has_app_cache?`, line 145). `fledge build` does the same in the built app: the gem's whole folder, less git's files, with its gemspecs evaluated (as a git gem's are, ADR 006), at `app/vendor/cache/NAME`, where NAME is the last part of the path as written in the lockfile (`#app_cache_dirname`). A path that ends in `.` or `..` names no such folder and is refused with the gem's name and what to change. A folder that is not there is refused with the gem's name and where it was expected. If the developer has run `bundle cache --all`, their `vendor/cache/NAME` is the copy `bundle exec` would load, and it is the folder Fledge ships. The project's own `vendor/cache` still stays out of the app (ADR 005), so only path gems' folders arrive there.

### 5. A path gem with an extension is compiled for the runtime's Ruby

Bundler compiles no path gem's extension (`Source::Path#install` generates its executables with `disable_extensions: true`, `path.rb` line 80), so `bundle exec` loads whatever the developer last compiled into the gem's `lib` for their own Ruby (usually with rake-compiler). A built app has the runtime's Ruby, so the file must be built against it. `Fledge::NativeBuild` compiles it as it compiles a git gem (ADR 006, section 2) in a copy of the files the gemspec lists, as `gem build` and `gem install` would see them, and the files the build wrote into the gem's require paths are what ships, over the developer's own: inside the project, as files that replace the project's (`Fledge::AppGems#app_files`), and outside, in the copy of section 4. `Fledge::NativeBuild` now counts a file the build wrote that differs from the package's file at the same path as new, which it had counted only when the path was new. The project's own gem (the `gemspec` line of its Gemfile) is such a gem when its gemspec has an extension. The same checks as for any compiled file apply (ADR 006, sections 4 and 8).

### 6. A gem's executables are written by the runtime's RubyGems into the runtime's bin folder

A built app's `PATH` has no bundle `bin`, and the person's computer has no Ruby (ADR 003), so a wrapper that says `#!/usr/bin/env ruby` helps no one. The runtime already has wrappers that do: RubyGems, built relocatable, writes `bindir="${0%/*}"` and `exec "$bindir/ruby" -x "$0"` (`Gem::Installer#bash_prolog_script`, `installer.rb` line 979) on macOS and Linux, and on Windows a `.bat` that runs the `ruby.exe` beside it when the folder holds one (`#windows_stub_script`, line 783). Fledge has the runtime's own Ruby write the wrappers of every gem it ships that has executables, as `gem install` would: it packs a copy of each gem with its extensions taken out (they are compiled elsewhere) as `gem build` packs it, and installs that into a gem folder of its own with the unpacked runtime's bin folder as the bin folder (`NativeBuild::STUBS`), then ships the wrappers in the runtime's `bin/` (`ruby/bin` on Windows), except a name the runtime already has there, whose wrapper finds whichever version of its gem the app's Bundler activates. The one change to RubyGems' output is the interpreter line after the prolog, which `ruby -x` skips: Fledge sets `Gem.ruby` to `/usr/bin/env ruby` for that run, as the runtime's own wrappers have it, so that no path of the build's computer is in them. Gems from a gem server, from git, and from a folder (other than the project's own gem, whose executable is the program the app runs) are all written this way. A program finds one at `File.join(Gem.bindir, NAME)` (`NAME.bat` on Windows) or by `Gem.bin_path`, which never needed the wrapper.

Not done, and why: the app's `PATH` still does not include the runtime's `bin/`, so `system("name")` finds a gem's program only if the app (or the person) puts `Gem.bindir` on `PATH`. Under `bundle exec` the bundle's bin folder is first on `PATH`; in the app Bundler's `PATH` entry names a folder that does not exist (`lib/ruby/gems/4.0.0/bin`) because RubyGems' relocatable wrapper finds its Ruby beside itself, and a wrapper there would not. Adding `Gem.bindir` to the app's `PATH` is a change to `ENV` that decision 9 asks us to avoid and the launcher would have to make; it stays out until an app needs it, and the cost is a line in the launcher's Bundler environment (`runtime/launcher/bundler.c`) plus a justified difference in the parity report.

### 7. Refusals that remain

Fledge refuses, naming the gem and what to do: a path gem outside the project whose folder is not there, or whose path ends in `.` or `..` (section 4); a git gem not pinned to a commit (ADR 006); a gem without a checksum (ADR 005); a server that refuses the login (section 2); and, on a phone, a gem with an extension, as before (ADR 012).

## Consequences

- `examples/real_gems` uses every kind in one app: `rainbow` through a loopback mirror of RubyGems.org that asks for a login (`.github/scripts/gem-mirror.rb`, named as Bundler's own mirror and credential settings in the example's `.bundle/config`); `shared`, a path gem with an executable in a folder beside the project (`examples/real_gems_shared`); `greeter`, a path gem with a C extension inside the project; `fledge_submodule_gem`, a git gem with a submodule (the `experiment/submodule-gem` branch of this repository, whose submodule is `github.com/octocat/Hello-World`); and `paint`, in an optional group the example's `.bundle/config` asks for. CI builds it with the mirror running, fails the build unless the mirror served the gems with the login, and Delivery runs it on a fresh runner of macOS, x86-64 and ARM64 Linux, and Windows, with no Ruby, and compares the one line it prints. It runs no `bundle exec` comparison: Bundler compiles no path gem's extension, so the example would not run there without a build step of its own. The musl and ARM64 Windows builds are not part of it, as they are not of `examples/native_app`: they have no C toolchain in CI.
- `examples/real_gems`'s lockfile was made through the mirror with `bundle lock`, as a developer behind one would; its `BUNDLE_MIRROR__HTTPS://RUBYGEMS__ORG/` setting has to be reachable to lock again.
- `Fledge::AppGems#app_files` must be asked after `#for` (the build does), since what was compiled for a project's own path gems arrives with it.
- The runtime's `RuntimeContents` lists its bin folder's files (`binaries`) so a gem never overwrites one.
- A build that has a gem with executables now unpacks the runtime and runs its Ruby once to write them, which it had done only for a gem to compile.
- Not yet: `Gem.bindir` on the app's `PATH` (section 6); credentials for a git gem or a submodule are git's own (its credential helper), as they are for Bundler.
