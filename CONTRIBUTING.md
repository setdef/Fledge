# Contributing

Fledge's code, tests, and documents are written by LLM agents at the maintainer's direction. The gates in CI, and the Delivery jobs that run a built app on a clean computer, are the review.

## Ask for what you want

Open an [issue](https://github.com/setdef/Fledge/issues). Describe the problem or the feature, the platform you build on, the platform you run on, and what `bundle exec fledge --version` prints. The maintainer decides what Fledge does, and an agent builds it.

## Work on Fledge

Start with [AGENTS.md](AGENTS.md), which is binding, then read:

- [`doc/contributors/decisions.md`](doc/contributors/decisions.md): the maintainer's own words, which are the only authority.
- The open issues of the milestone "1.0.0 release candidate" at [github.com/setdef/Fledge](https://github.com/setdef/Fledge/milestones): the work left before the candidate (`gh issue list --milestone "1.0.0 release candidate"`). [`doc/contributors/plan/`](doc/contributors/plan) holds the stories and the direction, with the current plan last.
- [`doc/contributors/design/`](doc/contributors/design): how each part works, and why, with [`architecture.md`](doc/contributors/design/architecture.md) as the overview and [`releases.md`](doc/contributors/design/releases.md) for how a release is made.
- [`doc/contributors/adr/`](doc/contributors/adr): the decisions behind each behavior.
- [`doc/contributors/documentation_style.md`](doc/contributors/documentation_style.md): how to write the documents.

A fault in a gem, a platform, or another project is theirs, and not Fledge's bug: report it with the primary source that shows it, and have Fledge refuse, or say so plainly where a developer reads, and never hide it.

Install git and [mise](https://mise.jdx.dev/), 2026.10.11 or later, the mise CI runs; you need nothing else, not even a Ruby, but for the few system tools that some builds below name. Then run these two lines, the same in sh, cmd, Windows PowerShell, PowerShell 7, and Git Bash:

```
mise trust -q mise.toml
mise x -- ruby tasks/setup.rb
```

`mise x` installs every tool `mise.toml` pins, with no prompt, before it starts Ruby, so the first run on a computer with nothing installed takes some minutes. `tasks/setup.rb` is the one file that holds every step of setup, on every system: it installs the tools `mise.toml` pins (and those of `mise.android.toml` or `mise.rust.toml`, when `MISE_ENV` names one), each by version, and the gems the `Gemfile.lock` locks, and builds the API documentation. `bin/setup` holds the same two lines, for the habit of starting a run with `bin/setup`. Like a Rails app's `bin/setup`, setup is safe to run at any time ([Rails' template](https://github.com/rails/rails/blob/v8.0.2/railties/lib/rails/generators/rails/app/templates/bin/setup.tt#L10-L11)): once it has run, it installs nothing, asks nothing, prints nothing, and finishes in seconds, and it needs no administrator's rights. Two setups at once in one cache would break mise's download store, so the second waits on a lock in mise's cache folder. The `mise trust` line is a courtesy: `mise install` and `mise exec` trust this folder's `mise.toml` themselves, and record that trust as `mise trust` would, because running them is already your decision to run the project's code ([mise's security page, "Implicit trust"](https://mise.jdx.dev/security.html#implicit-trust)). So read `mise.toml` before your first run if you want to know what that decision covers: beyond the downloads it pins, it sets environment variables from its `[env]` table and the files in `.config/mise/`, and on Linux runs your C compiler once to find its headers. Fledge runs on the Ruby its runtimes come from: on macOS and Linux, the Ruby release `runtime/sources.yml` names, from jdx/ruby's builds, which mise downloads and never compiles; on Windows, until RubyInstaller builds that release, the very archive of RubyInstaller's head build the Windows runtimes are built from, which mise downloads from Fledge's `inputs-rubyinstaller-head-*` pre-release and checks against the SHA-256 that `runtime/sources.yml` pins, with the two MSYS2 DLLs that build needs and lacks, pinned the same way. mise also installs, on Windows, the MSYS2 that compiles a gem's C for RubyInstaller's Ruby, the build of it that ruby/setup-ruby uses, pinned to one day's release, and points RubyInstaller at it with `MSYS2_PATH`.
mise puts that Ruby first on `PATH` only in a shell it has activated (`eval "$(mise activate zsh)"`, or bash's, in your shell's startup file), and only once that shell is in this folder; there `ruby -v` prints the version `mise.toml` pins. A script, an editor's task, a CI job, or a shell you have not activated runs none of the hooks `mise activate` installs, so it keeps whatever Ruby its `PATH` already had, or none, and `bundle exec` there stops with Bundler's stack trace, because the gemspec needs that very Ruby. Start each command there with `mise x --`, as `tasks/setup.rb`'s own commands do. `mise x` puts the pinned tools first on `PATH` for that one command, and installs first any of them that is missing ([`mise exec`](https://mise.jdx.dev/cli/exec.html)). It finds `mise.toml` from the folder the command starts in, so a command started in a folder outside the checkout, such as a scratch app you build there, finds none and runs whatever Ruby the computer has, which may be an older one than the project's: a lockfile made there names gems the runtime's Ruby refuses, and a proof run that way proves nothing about Fledge. Run `bundle lock` and every other command that must use the project's Ruby with `mise x -C CHECKOUT --`, or copy `mise.toml` beside the scratch app, and print `ruby -v` beside the result.

`bundle exec rake runtime` builds this computer's runtime, which the gate otherwise skips the checks of. On glibc Linux, build it with `mise x -- .github/scripts/glibc-runtime.sh x86_64-linux` (or `aarch64-linux`) instead, as CI does: the script runs the build in the manylinux_2_28 image `runtime/sources.yml` pins, whose glibc 2.28 is the runtime's floor, and `rake runtime` run on a newer glibc fails the floor check ([`doc/contributors/design/runtimes.md`](doc/contributors/design/runtimes.md), "The glibc floor"). The script runs the image with docker, or, on a computer without docker, with crane, which mise installs from `mise.toml`, and your system's bubblewrap (`bwrap`), with no root and no daemon, wherever the kernel lets you make user namespaces, as Ubuntu, Debian, and Fedora do. The image holds every compiler and tool the build runs. Other runtimes built on Linux, such as Windows' and Android's (`rake "runtime[x64-mingw-ucrt]"`), need a C compiler, binutils, make, perl, and xz from your system, and patchelf 0.18.0, which mise installs from `mise.toml`, pinned by SHA-256.

Building `test/fixtures/native_app` or `test/fixtures/rust_lengths` compiles a Rust gem (ferro-idna, or the fixture's own, which native_app leaves out on Windows), whose build runs bindgen, which loads libclang to read Ruby's headers. On Linux and macOS mise installs the Rust it needs. A Mac has libclang with Xcode's command-line tools; on Linux mise installs LLVM's libclang 18.1.1, from PyPI's `libclang` wheel (a 25 MB download), pinned by SHA-256, names its folder in `LIBCLANG_PATH`, and gives bindgen your C compiler's headers, which the wheel lacks. On x64 Windows neither the wheel nor MSYS2's headers serve, and mise installs LLVM's own release, which CI's Windows runners have, with Rust's GNU toolchain, since RubyInstaller's Ruby is a MinGW build, only when you ask for them, since LLVM is a 276 MB download and 4 GB on disk: run `MISE_ENV=rust mise install` and each command that builds a Rust gem under `MISE_ENV=rust mise x --` (or `$env:MISE_ENV = "rust"` in PowerShell). It names LLVM's folder in `LIBCLANG_PATH` and points bindgen's clang at the MSYS2 above, as CI's Build job does. On Windows, mise also keeps rustup's and cargo's homes in its own data folder (`rustup` and `cargo` beside its tools), since rustup asks Windows for your profile folder and ignores `HOME`, and would otherwise put the toolchain in `%USERPROFILE%\.rustup`, shared with every other Rust project and with any rustup you installed yourself, which Fledge then leaves alone; elsewhere the homes are rustup's own. ARM64 Windows has no Rust from mise yet. mise sets these only under `mise x --` or in a shell it has activated.

`examples/my_cool_app`, and the gem-shaped app that `bundle exec rake parity` and the integration tests build from it, depend on sqlite3. sqlite3's precompiled gems for Macs ask for a Ruby older than 4.1 (`required_ruby_version` `< 4.1.dev` in 2.10.2), so on the Ruby 4.1 that `mise.toml` pins, Bundler and `fledge build` compile sqlite3 from source, and nokogiri, which `test/fixtures/nokogiri_app` depends on, the same way. Their builds run the `pkg-config` command, and nokogiri's unpacks libxml2's source with `xzcat`; a stock Mac has neither. On a Mac mise installs both, pinned by SHA-256: pkgconf from PyPI's `pkgconf` wheel, as `pkg-config`, and xz from pkgx's build. Under `mise x --` they come before any of your own, Homebrew's included, so every Mac compiles these gems with the same tools; CI's Mac jobs install only the tools each names, and use their runners' own.

### Before a push

Run `mise x -- ruby bin/check`, and read its own exit status: `mise x -- ruby bin/check | tail -1 && git push` pushes after a failed check, because a pipeline's status is that of its last command. It is one command, the same in bash, zsh, cmd, and PowerShell, on Linux, macOS, and Windows, and it works on a computer that has nothing but git and mise, as a fresh clone on a fresh CI runner does: `mise x` installs whatever tool `mise.toml` pins that is missing, the Ruby among them, and starts `bin/check` with that Ruby. The first run downloads and installs everything, which takes some minutes; after that, setting up takes seconds. `bin/check` runs `tasks/setup.rb` first, then checks the commits since `origin/trunk` (or since the commit you name after it): it fails one whose `Provenance: requested` trailer git does not parse, and runs each of the gate's lints that reads a file they change, on just the files they change where it can: RuboCop on the Ruby files (on every file when they change its configuration or `Gemfile.lock`), shellcheck on the shell scripts, actionlint on the workflows, and clang-format on the C; then the REUSE lint, Steep and the RBS checks when they change `lib/` or `sig/`, RDoc's coverage when they change the Ruby it counts, the unit tests, and the check of the packaged gem, which builds the gem, installs it with no network into an empty `GEM_HOME`, and runs its `fledge --version` and `--help` with none of the bundle's gems, so that a file the gem forgot to pack, or a `require` of a gem the gemspec does not name, fails here, in about two seconds, and not in an app built an hour later. Among those is the check that `doc/licensing.md`, which is generated, is current: a change to Fledge's version, to `runtime/licenses.yml`, or to the page's generator changes the page, and when the check fails, `mise x -- bundle exec rake licensing` writes it again, with `runtime/audited.yml` ([`doc/contributors/design/license-audit.md`](doc/contributors/design/license-audit.md), "The licensing page"). On a change that touches all of them it takes about half a minute once set up. It leaves to the gate RubyCritic, which fails nothing, and the integration tests. Two things it does not look for, because the gate's fixers mend them after the push: a new Ruby file needs an empty line after its SPDX header's `#++`, and a commit's `Provenance: requested` trailer and the footer under it need no blank line between them, or git does not read the trailer. Run beside it the one test of the behavior your change alters, which no command can guess: `TEST=test/gem_app_build_test.rb` for how `fledge build` lays out a gem-shaped app's gems, and `TEST=test/integration/launcher_environment_test.rb` for what the launcher hides from Ruby. Check it on the system where the behavior lives, or on whichever you have when it is the same everywhere, and on several only for a change about how the systems differ.

A workflow step is a script, and `bin/check` only lints it: a step that has never run anywhere fails the first time CI runs it, so run the script itself, with the inputs the step gives it, before you push, as a new test is run once where it is meant to run. When you change what several jobs consume (a tool pin, `mise.toml`, `tasks/setup.rb`, a script a workflow shares, a fixture that every system builds), read each caller, and check each distinct way it is consumed, which is a different command and not the same command on another system. Try a change to how iOS extensions link against every kind of extension `examples/` has (C, C++, Rust, a Rakefile, CMake, ffi libraries), and a change that makes a build need something new, such as a runtime or a tool, on the jobs that lack it: CI's host jobs build a pure-Ruby Android project with only the Android runtime. A test of a build that passes because a warm checkout already held its outputs proves nothing: know that yours rebuilt what the change touched.

Then fetch and rebase, and push: `git fetch origin trunk`, `git rebase origin/trunk`, `git push origin HEAD:trunk`. Fetch `trunk` alone, because `git fetch origin` fails in a checkout that has stale copies of the branches automation force-pushes (`pin-move` and `release-next`). A rejected push means someone pushed first: rebase, run the check again, and push again.

### Before the push of a runtime change

A runtime change reaches checks no unit test does: what `runtime/sources.yml` or `runtime/licenses.yml` pins, how `tasks/runtime_builder.rb` builds a runtime, how the launcher starts its Ruby, or which Ruby a parity check compares a runtime with. Only an app built from the new runtime, run as a person with no Ruby runs it, shows what such a change breaks. So on a computer of the platform the change touches, run instead:

```sh
mise x -- ruby bin/check --runtime
```

It runs the fast check, and once that passes, `rake runtime:prove` (`tasks/runtime_proof.rb`), which runs CI's own checks of apps built from that runtime, each by the script or task CI runs it with, and stops at the first that fails:

1. It builds this computer's runtime as CI's Runtime job does (on glibc Linux, by `.github/scripts/glibc-runtime.sh`), unless `FLEDGE_RUNTIME_DIR` names a folder that holds one.
2. It runs the parity check, `tasks/parity.rb`.
3. It builds hello, my_cool_app, and the parity probe of each, and runs each app with `.github/scripts/deliver.sh`, as the Delivery jobs do.
4. It builds the app that builds apps with `.github/scripts/prepare-from.sh` and has it build a game with `.github/scripts/deliver-from.sh`, as Delivery of `build --from` does. On Linux that needs `mksquashfs` and `dpkg-deb`, as CI's job installs them.
5. It runs the licensing page's integration test with LLVM's readers from the `llvm-mingw` pin, as the gate runs it, where a test that would skip for want of a reader fails.

On an x86-64 Linux computer it took a quarter of an hour, the fast check and the runtime's build four minutes of it. Run it once, on one platform: a change to every desktop runtime alike is proven on whichever you have, and CI proves the others after the push.

For a change to the Android runtime, or to the glibc x86-64 Linux Ruby, which Android's parity check and ruby/spec compare the phone's Ruby with, run on an x86-64 Linux computer with KVM, set up as "Android on Linux" (below) says:

```sh
MISE_ENV=android mise x -- ruby bin/check --runtime=android
```

It builds both runtimes, then runs `tasks/mobile_parity.rb` and `tasks/ruby_spec.rb` in an emulator, as the Mobile apps (Android emulator) and ruby/spec jobs do.

Some runtimes are not built where they run. `rake runtime` refuses on Windows (x64-mingw-ucrt runtimes build only on x86_64-linux, aarch64-linux, and arm64-darwin), so a Windows computer never builds one: `fledge build` there downloads the last release's runtime, which serves when your change is not in the runtime. Windows runtimes are built on Linux or macOS (`mise x -- bundle exec rake "runtime[x64-mingw-ucrt]"`): copy the folder that holds the archive to the Windows computer and name it in `FLEDGE_RUNTIME_DIR`. There the proof runs the parity check and the licensing page's test, and leaves Delivery to CI: `.github/scripts/deliver.ps1` has run only on CI's Windows runners, though it writes only in the folder its `-Work` names (the system's temporary folder by default, which may be on another drive than the system's, so name a folder you mean to fill), and `deliver-from.ps1` works under `RUNNER_TEMP`, which no computer but a runner sets, and installs the app it builds. musl runtimes are built in CI's Alpine image (`ci.yml`, the musl Runtime job), so on a musl computer name a runtime in `FLEDGE_RUNTIME_DIR` too. A glibc Linux computer with neither docker nor user namespaces cannot build its runtime; there, a runtime CI built or one a release published, in a folder named by `FLEDGE_RUNTIME_DIR`, proves a change to Fledge's own code against that runtime, though not a change to the runtime itself. The other checks of CI's full run stay CI's, after the push: every other platform, Delivery in other systems' images (the oldest glibc, Debian, a .deb's install), the signed and windowed apps, iOS, and the integration tests that need a runtime.

### After a push

After the push, CI runs the gate, `bundle exec rake`, on every system: every test and every lint, with zero errors and zero warnings. Its Mac jobs run on `macos-26`, the macOS floor, which has the Xcode 26.5 the Mac and iOS runtimes build with; [`doc/contributors/design/releases.md`](doc/contributors/design/releases.md), "Which macOS each job runs on", says why, so a new Mac job follows the same rule.

Every push gets a verdict in minutes from the fast tier: `.github/workflows/fast.yml`, the lint and the package check on Linux and the unit tests on Linux and Windows, and `.github/workflows/fast-macos.yml`, the unit tests on macOS, whose verdict comes whenever GitHub has a macOS runner for it. A push to `trunk` that changes what a runtime or an app built from one is made from also gets `.github/workflows/runtime-proof.yml`, in about a quarter of an hour: the very proof "Before the push of a runtime change" runs, `rake runtime:prove[x86_64-linux]`, on one Linux runner (`releases.md`, "The runtime's commit stage"). Every push to `trunk` also queues `.github/workflows/ci.yml`, about an hour: the gate, every runtime, the tests and parity on each platform, each platform building its own apps, and Delivery on fresh runners. A push never cancels a full run in progress on `trunk`, so each full run covers the batch of commits pushed since the one before it, and the fast tier's verdicts narrow a red batch to its commit (`releases.md`, "Runs, batches, and the release commit"). `ci.yml` calls `ruby-spec.yml`, which runs ruby/spec on stock Ruby and in a built app and fails on an example that fails on one side only (`doc/contributors/design/parity.md`, "ruby/spec"), and every night `ruby-master.yml` builds the runtimes from Ruby's master and keeps the issue "Ruby's master: nightly status" current (`doc/contributors/design/runtimes.md`, "Testing against Ruby's master"), and every morning `pin-watch.yml` asks each upstream of `runtime/sources.yml` whether it has released a newer version than the pin, keeps what it found as the run's `pin-watch` artifact, and moves each pin behind, proves the move with a run of `ci.yml` on its own branch, `pin-move`, and puts it on `trunk` as `github-actions[bot]` when that run passes (`runtimes.md`, "Keeping the pins current"); it fails when an upstream could not be read, or when a pin behind could not be moved, failed its proof, or has been held for a person for longer than 30 days.

A trunk is red when the newest push's verdict from the fast tier or from `runtime-proof.yml` is red, or when the newest full run of `ci.yml` that has finished is red. A red full run blames its whole batch, and the fast tier's verdicts on the batch's pushes say which commit; the fix, or the revert of that commit, comes at once (AGENTS.md, "Committing"). A full run shown as cancelled is no failure: it was waiting when a newer push's run took its place, and the newer run covers its commits. A run that failed only for jobs no runner took is run again by `runnerless.yml`, as "When CI fails" says. The newest commit a full run has passed is the head of the newest successful run:

```sh
gh run list --branch trunk --workflow ci.yml --status success --limit 1 --json headSha,createdAt
```

Scheduled workflows do not judge a push, and a failure of one does not make `trunk` red. `ruby-master.yml` builds the runtimes from Ruby's master each night, and reports to the issue "Ruby's master: nightly status", whose body says the newest master Fledge passed on and what has failed since; its run fails only on a night that is news, when a job fails that had not been failing. `ruby-spec.yml` runs each night on the runtimes of trunk's newest passing run of `ci.yml`, and its failure shows as a failed run of its own. `pin-watch.yml`, above, fails when it cannot read an upstream or cannot move or prove a pin. `keep-schedules.yml` and `keep-rubyinstaller-head.yml` fail only when GitHub's API refuses or a kept build does not verify. `ruby-builds.yml` runs on a push to `trunk` that changes the recipe or its pins, and never publishes from one.

To read the verdicts:

```sh
gh run list --branch trunk --workflow fast.yml --limit 5     # each push's; fast-macos.yml for macOS
gh run list --branch trunk --workflow runtime-proof.yml --limit 5  # each runtime push's
gh run list --branch trunk --workflow ci.yml --limit 3       # the full runs
gh run view RUN --json jobs --jq '.jobs[]|select(.conclusion!="success")|[.name,.conclusion]'
gh run view RUN --log-failed | tail -80                      # why they failed
gh run list --workflow pin-watch.yml --limit 1               # the newest watch of the pins
gh run download RUN -n pin-watch                             # what it found, as pin-watch.json
```

### When CI fails

Root-cause a failure before you run it again (AGENTS.md, How to work), and make a reproduction show its premise first: a "did not reproduce" from a build in which nothing crossed the boundary under test says nothing. Once you know why one passes on a second try, add a sentence for it here. These are known:

- **A job cancelled before any step ran, with the annotation "The job was not acquired by Runner of type hosted"**: no runner took it, most often a macOS one. On `trunk`, `.github/workflows/runnerless.yml` runs such jobs again by itself when they are a run's only red, at most twice, and its run, named "Runnerless jobs", says what it did (`releases.md`, "A job no runner took"). When another job of the run failed for real, it leaves the run: root-cause that failure, then `gh run rerun RUN --failed`. On a branch, run it again by hand.
- **A run cancelled outright**: on a branch, a later push superseded it; on `trunk`, it was waiting and a newer push's run took its place and covers its commits.
- **A Mobile apps job that times out**: the iOS Simulator and Android emulators sometimes boot slowly, and a macOS runner is sometimes slow throughout. Read the log: if the app never started, run the job again; if it started, the failure is real. The iOS apps job's long step, "Build the apps with fledge build ios, and run them in the iOS Simulator" (about 28 minutes, 38 on a slow runner; limit 45), and the iOS integration tests job's "Run the iOS integration tests" (13 to 16; limit 25) each have a limit of their own, and the run's annotation names the step that hit it; each job's own limit, 55 and 40 minutes, is the backstop. A step cancelled at its limit with its last lines still making progress is a slow runner: run the job again. One that stopped printing is a hang, and a real failure.
- **A Windows Test job that times out**: each Windows platform's tests run in two shards, Test (PLATFORM, 1 of 2) and Test (PLATFORM, 2 of 2), and the step "Run the tests" has a limit of 35 minutes in each. A slow runner, which ARM64 Windows sometimes is, shows as tests still finishing at the limit: run the job again. To run one shard's tests yourself, set `N` (shard 1) or `X` (shard 2) to the job's `SHARD_1_TESTS` before `bundle exec rake test:all`; in Git Bash, set `MSYS2_ENV_CONV_EXCL='N;X'` too, or Git Bash may rewrite the pattern into a path. On Windows, an `N` or `X` with `^`, `*`, `(`, or `|` in it matches nothing, because rake hands minitest the pattern with the backslashes `Shellwords.escape` added: write such a pattern with `.` and `+` instead.
- **`apk` says `unable to select packages` and `breaks: world[NAME=VERSION]`** in a musl job: not a flake, and a second run fails the same way. Alpine keeps only each package's newest build, so the pin under `alpine-packages` in `runtime/sources.yml` stopped resolving. The pin watch moves it on its next daily run and proves the move (`doc/contributors/design/runtimes.md`, "Alpine's packages"); to mend it sooner, run `gh workflow run pin-watch.yml`, or find the version Alpine now has (`apk policy NAME` in the pinned image), move the pin, and run each role of `.github/scripts/alpine-packages.sh` in that image before you push.
- **A .deb's Delivery job whose step "Fetch apt's package lists and the packages the job installs" fails with `apt-get did not fetch the lists and packages in N seconds` or `did not fetch every list and package`**: Ubuntu's archive did not answer in time from any of the hosts the step tries (`.github/scripts/apt-update.sh` says which, and why), and the `Get:` and `Err:` lines above the message say which host gave what. Run the failed job again. An `E:` line from apt, such as `Unable to locate package`, is no flake: a package the job installs, or a `.deb`'s dependency, is not in the archive as named.
- **mise's Ruby download timing out after 20 seconds**: run the failed jobs again.
- **A Gradle build that fails with `Received status code 429 from server: Too Many Requests`, or `Could not find` for modules Maven Central has**: Central refused the runner's shared address (`doc/contributors/design/phone-projects.md`, "Gradle's downloads in CI", says what the cache spares and where a failed job's `--info` log is). Run the failed job again, which may land on another runner.

To try a change to CI without disturbing `trunk`, push it to an `experiment/*` branch with a workflow that runs only the jobs in question; a push there runs the fast tier, and `ci.yml` only when started by hand (`gh workflow run ci.yml --ref BRANCH`); the spikes of musl Linux and Windows on ARM ran that way, on `experiment/signing`. A spike's code is thrown away and its findings kept, in `doc/contributors/research/`. Leave every such branch in place: `experiment/submodule-gem` is the git gem with a submodule that `test/fixtures/real_gems` locks.

### Android on Linux

On an x86-64 Linux computer with KVM (`/dev/kvm`, which your user can read and write), you can build the Android runtime and Android apps, and run them on an emulator, as CI's Runtime (android) and Mobile apps (Android emulator) jobs do. `mise.android.toml` pins what that needs, each by its SHA-256: Temurin's JDK 21, the NDK the Android runtime is built with, the CMake that `examples/cmake_phone` runs, and the packages of Android's SDK CI uses (platform-tools, the API 36 platform, build-tools 36.0.0 and 37.0.0, the emulator, and the API 36 system images with 4 KB and 16 KB pages). mise reads it only when `MISE_ENV` is `android`, so `mise install` leaves out its five gigabytes otherwise. `bin/android-sdk` lays its packages out as one SDK in `tmp/android/sdk`, which `ANDROID_HOME` names, and downloads nothing. `bin/android-emulator TARGET -- COMMAND` boots an API 36 emulator with no window from the system image `google_apis` (4 KB pages) or `google_apis_ps16k` (16 KB), runs the command with `ANDROID_SERIAL` naming the emulator, and shuts it down. The last two commands run the Android integration tests, as the Mobile apps (Android emulator) jobs do: those that need no device, then `test/integration/mobile_extension_symbols_test.rb`, which runs its program on the emulator.

```sh
export MISE_ENV=android
mise install
mise x -- bin/android-sdk
mise x -- .github/scripts/glibc-runtime.sh x86_64-linux   # whose Ruby compiles a gem's extension for the phone
mise x -- ruby tasks/runtime_builder.rb android
mise x -- bash -c 'BUNDLETOOL=$(ruby .github/scripts/fetch_pin.rb mobile bundletool) ruby tasks/mobile_parity.rb android-build tmp/runtime'
mise x -- bash -c 'BUNDLETOOL=$(ruby .github/scripts/fetch_pin.rb mobile bundletool) bin/android-emulator google_apis -- ruby tasks/mobile_parity.rb android'
mise x -- bundle exec rake test:integration TEST=test/integration/mobile_extensions_build_test.rb,test/integration/mobile_default_gems_test.rb
mise x -- bin/android-emulator google_apis -- bundle exec rake test:integration TEST=test/integration/mobile_extension_symbols_test.rb
```

## The tests

Fledge's tests come in two tiers, by folder, as Rails keeps its system tests in `test/system` and Hanami and dry-rb keep `spec/unit` apart from `spec/integration`.

- **Unit tests** are every test file under `test/` but those in `test/integration/`. Each runs in milliseconds, in the test's own Ruby process, on any computer, with or without a runtime. It may write a temporary folder, read the repository, serve a `LoopbackServer` in its own process, and run a short-lived tool such as tar. It builds no runtime, reads none that `rake runtime` built, builds no app that it then runs, compiles nothing, starts no Ruby or shell script, runs no signing or disk image tool, and reaches nothing past this computer. A wait the code under test would make, such as a retry's, is made short by passing the waits in, as `Fledge::Download` and `Fledge::Dmg` take them.
- **Integration tests**, in `test/integration/`, are the rest: a real runtime, a built app run as a person runs it, a compiler, `exe/fledge` or a script in a process of its own, codesign, hdiutil, makensis, gpg, a repository that git makes, or the network. They take seconds, some take minutes, and many skip on a computer without what they need. CI runs each where it has what that test needs, and there a skip for want of it fails instead: the Test jobs run them all on each desktop platform with its runtime (`FLEDGE_REQUIRE_RUNTIME`), the Mobile apps (Android emulator) jobs run the Android tests with the Android runtime, the NDK, CMake, Rust's Android targets, and an emulator (`FLEDGE_REQUIRE_ANDROID`, `test/support/android.rb`), and the iOS integration tests (iOS Simulator) job runs the iOS tests with the iOS runtime, the Xcode `runtime/sources.yml` pins, XcodeGen, CMake, and Rust's iOS targets (`FLEDGE_REQUIRE_IOS`, `test/support/ios.rb`). "Android on Linux", above, says how to run the Android tests yourself. On a Mac, `bin/setup` installs the XcodeGen and the Rust targets the iOS tests need, and they run once `bundle exec rake runtime` and `bundle exec rake runtime[ios]` have built this Mac's runtime and the iOS one, with Xcode and CMake installed.

A new test file is a unit test unless you put it in `test/integration/`. A unit test that writes files, compares their contents, or handles paths can pass on one system and fail on another, so run the unit tests once on Windows before you push it: a fixture written as text gets two-byte line ends there, an expanded path begins with a drive letter, and a test that joins paths uses `File::PATH_SEPARATOR`. A new integration test is run once on a system that lacks what it needs, to see it skip and not error: a test that calls `xcrun` must ask for a Mac first. When a unit test needs one of the things above, or takes more than about a tenth of a second on your computer, make it fast without weakening it, or move it. Tests of one class can be in both tiers: `test/assembly_test.rb` and `test/integration/assembly_tools_test.rb` share `test/support/assembly.rb`.

A fixture or example that CI hands to `.github/scripts/deliver.sh` or `deliver.ps1` must end its program with `exit Integer(ARGV.fetch(0, "0"))`: Delivery runs every app with the argument 3 and fails unless it exits 3. `test/workflow_delivery_apps_test.rb` reads the workflows for those apps, so a new one is covered without editing it, and names the program that lacks the line; before it, only a full CI run an hour later said so. Apps that another script delivers, because they differ on purpose, are not read.

A fixture app's lockfile is made by a real `bundle lock --add-checksums`, never by hand, so that its checksums are the ones Bundler writes.

An app under `examples/` is a small real app that does something a person would use, however simple; one that only starts, reports, and exits is a fixture under `test/fixtures/`, with an integration test. Together the examples show what Fledge does, so each has a reason to be what it is. An example that is a server is a server because other computers connect to it, and does something only a server does: an app that listens on `127.0.0.1` alone could be a windowed or a terminal app. Read an example's program as a developer would, start to finish, before it lands: a summary and passing proofs are not a reading. At least one example shows file associations, and at least one shows several programs in one app, so that `doc/` has an app to point to for each.

While you work:

- `bundle exec rake test` runs the unit tests, in seconds. Run it as often as you like. CI's fast tier runs them on every push: `.github/workflows/fast.yml` on Linux and Windows, beside the lint, and `.github/workflows/fast-macos.yml` on macOS, a workflow of its own because a macOS runner often takes twenty minutes or more to come.
- `bundle exec rake test:integration` runs the integration tests, and `bundle exec rake test:all` runs both, as the gate and CI do. Build a runtime first (`bundle exec rake runtime`), or the tests that need one skip.
- `bundle exec rake test TEST=test/foo_test.rb` runs just that file, of either tier; several files, or globs, go comma-separated.
- `N=/name/` runs just the tests whose names match, and `A=-v` names each test with its time as it runs. Always read the runner's "N runs, N assertions" line: a pattern that matched nothing runs nothing and still exits 0. In Git Bash, an argument written `N=/name/` is rewritten into a Windows path and matches nothing, so name the test in full without slashes (`N=test_the_whole_name`), or set `MSYS2_ARG_CONV_EXCL='N='` for that command (and `MSYS2_ENV_CONV_EXCL='N;X'` when you set `N` or `X` as an environment variable).
