# ADR 005: Ship the Executable You Already Run, With the Gems It Locks

## Status
Accepted (requested). Agents wrote this ADR and may change it (AGENTS.md, Questions). It applies the maintainer's replies of 2026-10-26, later, reply 2 (the executable you already run, with the project root where the Gemfile or gemspec is, configuration only where needed, and NAME from the project) and reply 11 (the person's own Ruby settings restored, so the app's `ENV` and its child processes look as they would without Fledge), and replies 8 and 24 (LGPL only as a separate, replaceable shared library, with its source, and app developers told plainly what they owe), and decisions 5, 8, 9, 10, and 20 in `doc/contributors/decisions.md`. It replaces "an app is a folder with a `main.rb`" in ADR 001, 002, and 003. ADR 006 extends it to gems that must be compiled and gems from git. ADR 007 supersedes section 7, and section 3's `licenses` and `compiled` keys, which judged an app's gems by their licenses: the maintainer ruled on 2026-10-28 that an app's gems, licenses and all, are its developer's choice and responsibility.

## Date
2026-10-27

## Context

A Ruby developer already has an entry point. A gem has `exe/my_cool_app`, an app has `bin/server`, a script is a `main.rb`, and each runs from its project's root, where the Gemfile or gemspec is. The maintainer accepted building that program, with NAME from the project, camelized (`MyCoolApp`), which configuration may override (reply 2; decision 5).

A gem-shaped program is run as `bundle exec exe/my_cool_app`: Bundler puts the project's own `lib` and every gem the Gemfile.lock locks on the load path, and its code says `require "my_cool_app"`, not `require_relative`. For its source to stay identical under Fledge (decision 9), the built app must do what Bundler does, with the same gems, for each target platform, from a computer that may be another platform. (This ADR first held that a gem a developer ships falls under decision 8's license rule, as Fledge copies it into the app; ADR 007 undoes that.)

Prior art, read for this decision:

- **Warbler** (`jruby/warbler` at 3196d5f9, `lib/warbler/traits/bundler.rb`) packs a project's Gemfile, Gemfile.lock, and the gems of every group but `development`, `test`, and `assets` (line 44) into a jar, and writes the packed app a `.bundle/config`, "the highest-precedence documented configuration level", of `BUNDLE_VERSION: system`, `BUNDLE_FROZEN: true`, `BUNDLE_PATH__SYSTEM: true`, and `BUNDLE_AUTO_INSTALL: false`, so a host's `BUNDLE_PATH` or `~/.bundle/config` cannot leak in (lines 17 to 32). The app then runs with Bundler.
- **Bundler's `--standalone`** writes a `bundler/setup.rb` of load paths that needs no Bundler at run time. But a program that itself says `require "bundler/setup"` then loads the real Bundler, which looks for a Gemfile from the person's current folder, and `Gem.loaded_specs` knows none of the gems.
- **Bundler's own git sources** cache each gemspec evaluated, as `spec.to_ruby`, so that a gemspec that runs `git ls-files` keeps working in a checkout without git (`Bundler::Source::Git#serialize_gemspecs_in`, `bundler/source/git.rb` lines 321 to 331 at Bundler 4.0.20).
- **Briefcase** installs a Python app's requirements for the target platform from binary wheels only when cross-building, and fails naming the package that has none. **PyInstaller** and **OCRAN** collect what the program loads on the build machine, which works only for the build machine's platform. **Tebako** runs `bundle install` into its image, on the platform it builds for.
- **RubyGems' installer** (`rubygems/installer.rb` at Ruby 4.0.9, `Gem::Installer#install`, lines 268 to 305) extracts a gem into `gems/FULL_NAME`, builds its extensions, writes its executables, its plugins' loaders, its specification (`write_spec`, `to_ruby_for_cache`), and its `.gem` in `cache/`. `gem fetch --platform` and RubyGems.org serve any platform's `.gem` at `/gems/FILE`.
- **Bundler at run time** (Bundler 4.0.20): `bundler/setup` (`setup.rb`) auto-switches to the lockfile's Bundler and auto-installs when its settings say so; `Definition#write_lock` (`definition.rb` lines 401 to 426) touches the lockfile on every setup unless frozen; settings are read local first, then `BUNDLE_*` in the environment, then `~/.bundle/config` (`Settings#[]` and `#configs`, `settings.rb` lines 109 to 120 and 327 to 335), and the global file can be named by `BUNDLE_USER_CONFIG` (`#global_config_file`, lines 464 to 474); `SharedHelpers.set_bundle_environment` sets `BUNDLE_GEMFILE`, `RUBYOPT=-r.../bundler/setup`, `GEM_HOME`, `PATH`, and the rest, as `bundle exec` hands them to its program; a frozen Bundler refuses a platform the lockfile does not lock (`Definition#validate_platforms!`, lines 524 to 530) and picks each gem's build for the running platform (`Bundler::MatchPlatform.select_best_platform_match`).
- **Configuration formats.** Ruby tools configure in YAML (RuboCop's `.rubocop.yml`, Kamal's `config/deploy.yml`, Standard's `.standard.yml`), which Ruby's standard library reads; a gemspec's `metadata` holds only strings, is published to RubyGems.org with the gem, and does not exist for an app with only a Gemfile; Warbler's `config/warble.rb` is Ruby to execute; TOML needs a gem Fledge does not depend on; Tauri reads `tauri.conf.json`, Briefcase a section of the project's own `pyproject.toml`.

## Decision

### 1. The entry point is the path you build

`fledge build PATH` takes the program to ship. A file is the entry point. A folder means the one executable its project's gemspec names (`bindir`/`executables`), or else the folder's `main.rb`, so `fledge build` in a gem with one executable builds it, and a LÖVE-style folder with a `main.rb` still builds; any other folder fails with a message that says which program to name.

The project's **root** is the nearest folder, from the entry point's up, holding a `Gemfile`, a `gems.rb`, a gemspec, or a `fledge.yml`, as Bundler finds a Gemfile by walking up (`SharedHelpers.find_file`); the walk stops at a folder holding `.git`, so a script never joins a project above its repository, and a root that is the developer's home folder is refused rather than shipped. A script with none of these is a project of its own folder. `examples/hello` and the parity probe carry a `fledge.yml` for this reason: each sits inside Fledge's own gem, whose Gemfile it must not take.

Everything in the root ships, as the built app's `app/`, except `.git`, `.bundle` (the developer's Bundler settings), `vendor/bundle` and `vendor/cache` (gems Bundler installed or cached for the developer's computer), and the build's own output: decision 20 puts "my ruby code just works" ahead of size, and an app that reads a file of its project at run time finds it.

### 2. NAME comes from the project

NAME is `fledge.yml`'s `name`, or else the root's gemspec's name, or else the root folder's name, camelized as Bundler's gem template names a gem's module (each run of letters and digits begins with a capital; `my_cool_app` is `MyCoolApp`, `hello` is `Hello`), without the `::` a file name cannot hold. A name no operating system can use for a program and a folder (empty, a character Windows forbids, a name Windows reserves, such as `CON`) fails the build and says to name the app in `fledge.yml`.

### 3. Configuration is an optional fledge.yml

A project that needs to tell Fledge something writes `fledge.yml` at its root: a YAML mapping, as RuboCop's and Kamal's configuration are, read with Ruby's standard library, possible for an app with only a Gemfile, and kept out of what a gem publishes. It knows one key, `name`, and refuses any other so that a typo fails. (It also knew `licenses` and `compiled`, which answered Fledge's own questions about an app's gems' licenses; ADR 007 removed them, and a file that still has either fails like any unknown key.) App identity (icons, version information, the display name of Plan 002's "App identity") will be more keys in the same file.

### 4. The launcher reads fledge.cfg beside it

The launcher is the same program for every app, and on macOS it is signed, so nothing about one app is written into it. `fledge build` writes `fledge.cfg` beside it, lines of `key = value` as Python's interpreter reads the `pyvenv.cfg` beside it (PEP 405): `entry`, the program in `app/`, and `gemfile`, the project's Gemfile, if it has one, each relative to `app/` with `/` between folders. The launcher (`runtime/launcher/config.c`) refuses a key it does not know and a path that leaves `app/`, since `fledge build` and the runtime come from the same Fledge; a missing `fledge.cfg` or entry point exits 66 (`EX_NOINPUT`) and a damaged one 70 (ADR 002). It runs `ROOT/app/ENTRY` as it ran `main.rb`, so `$0` is that path, as under `ruby /path/to/app/exe/my_cool_app`.

### 5. An app with a Gemfile runs with Bundler, as bundle exec runs it

The built app runs with the real Bundler, the runtime's default gem, so that a program that requires `bundler/setup`, calls `Bundler.require`, or reads `Gem.loaded_specs` behaves as under `bundle exec`, and one that requires none of it still finds its gems. Between `ruby_options` and `ruby_run_node`, after RubyGems has settled its paths and while the person's Ruby settings are still set aside (ADR 003, section 3), the launcher:

1. requires Bundler, by its path in Ruby's library, so the environment Bundler records as the one it started from (`Bundler.original_env`) is the one Ruby booted with;
2. sets `BUNDLE_GEMFILE` to the app's Gemfile, and `BUNDLE_USER_CONFIG` to the app's own `.bundle/config`, so that the person's `~/.bundle/config` is never read;
3. requires `bundler/setup` by its path, as `bundle exec`'s `RUBYOPT=-r.../bundler/setup` does (required by name, RubyGems would first activate the bundler gem, loading what `bundle exec` does not), printing Bundler's message and exiting 70 if it fails;
4. removes `BUNDLE_USER_CONFIG` and has RubyGems settle its paths again;
5. gives the app the environment `bundle exec` would have given it, built over the person's (`runtime/launcher/bundler.c`, one string of Ruby the launcher evaluates, with the variables it set aside written into it in hexadecimal): it takes the person's environment as the one Ruby booted with plus the variables set aside, records it as the one Bundler started from, by `Bundler::EnvironmentPreserver#restore` as a Bundler started under `bundle exec` does (so a person who starts the app from inside a bundle gets their own environment from before it), replaces `ENV` with the preserver's `backup` (every `BUNDLER_ORIG_*` recording the person's value), puts back the app's `BUNDLE_GEMFILE` and `BUNDLE_LOCKFILE` from the protected setup, and calls `Bundler::SharedHelpers.set_bundle_environment`, which composes `PATH`, `RUBYOPT`, and `RUBYLIB` over the person's values exactly as `bundle exec` does (`-r.../bundler/setup` before the person's `RUBYOPT`), then puts back the `GEM_HOME` (and `GEM_PATH`, when Bundler set one) that names the runtime's gem folder, and Bundler's `MANPATH` when Bundler set one.

So `ENV` is `bundle exec`'s, and `Bundler.original_env`, `Bundler.with_original_env`, `Bundler.unbundled_env`, and `Bundler.with_unbundled_env` give the person's own environment, so that a Bundler app that starts a person's own tools (a terminal UI that runs `bundle exec rspec` in the person's project, say) starts them as `bundle exec exe/my_cool_app` would have. The app's own boot is still protected: RubyGems' paths were fixed and Bundler's settings read before any of the person's variables came back (Bundler's `Settings` reads `ENV` once, when it is created; `Gem.paths` once), and Bundler's own memoized `bundle_path` names the runtime's gems.

`fledge build` writes the app's `.bundle/config` with Warbler's settings for a packed app, which win over every other level of Bundler's settings, in the app and in any Ruby it starts: `BUNDLE_VERSION: system`, `BUNDLE_FROZEN: true` (so Bundler refuses a stale lockfile and never touches it, and an app in a read-only folder starts), `BUNDLE_PATH__SYSTEM: true`, `BUNDLE_AUTO_INSTALL: false`, and `BUNDLE_WITHOUT: development:test`. It ships each gemspec of the project's own gems (the root's, and path gems inside the root) evaluated, as `spec.to_ruby`, as Bundler caches a git gem's, so a gemspec that runs `git ls-files` needs no git where the app runs.

An app without a Gemfile runs without Bundler, exactly as before (ADR 003).

### 6. The gems ship installed in Ruby's own gem folder, for each target

`fledge build` reads the Gemfile and lockfile with Bundler itself (`Bundler::Dsl` and `Bundler::Definition`, with Bundler's root at the project for the read), refuses a lockfile the Gemfile has moved past in Bundler's own words, and for each target:

- **checks the lockfile locks the target.** A target is locked by its own RubyGems name in `PLATFORMS`, or for Linux its `-gnu` name, which RubyGems treats as the same (`Gem::Platform#===`), or by `ruby`; a macOS platform with a Darwin version, such as `arm64-darwin-25`, does not count, since Bundler would refuse it on another macOS. Otherwise: `run bundle lock --add-platform PLATFORM`.
- **picks the gems Bundler would set up there:** every dependency outside the `development` and `test` groups (Warbler's `bundle_without`), and outside any `platforms:` the target is not (Bundler's `CurrentRuby` names, answered for a CRuby on the target), and their dependencies, each the build Bundler picks on that platform (`Bundler::MatchPlatform.select_best_platform_match`).
- **refuses** a gem from a folder outside the project (a folder inside it ships with the project), and a Gemfile `ruby` the runtime's Ruby does not satisfy. A gem from git ships at the commit the lockfile locks, as Bundler lays it out (ADR 006, section 7).
- **fetches each gem's `.gem`**, checked against the SHA-256 in the lockfile's `CHECKSUMS` section (Bundler 4 writes it; `bundle lock --add-checksums` adds it), from the project's `vendor/cache` (`bundle cache --all-platforms`), the caches of RubyGems' path, Fledge's cache (`~/.cache/fledge/gems`), or its gem server. A lockfile without a gem's checksum fails: Fledge pins every external input by SHA-256 (AGENTS.md), and an app's gems are Fledge's input here.
- **installs each gem** the runtime does not already have at the same version into the runtime's gem folder (`lib/ruby/gems/4.0.0`, or `ruby\lib\ruby\gems\4.0.0` on Windows), as `Gem::Installer` lays one out, after `Gem::Package#verify`: its files, its specification, its `.gem`, and its plugins' loaders, but no executables in `bin/`, which only a shell uses and which would name the Ruby that built the app. Bundler's system gems are RubyGems' path, so it finds them there, beside Ruby's own.

A gem with an extension still to compile (a `ruby`-platform gem with `extensions`) is compiled when the target is the platform Fledge runs on, against the runtime's own Ruby, and fails the build for any other target, naming the gem and the target and saying to build on that platform or choose a version with a precompiled build for it (ADR 006): compiling needs the target's toolchain and Ruby headers, which a cross-build does not have. A gem whose `required_ruby_version` excludes the runtime's Ruby fails too, as RubyGems would refuse it.

### 7. An app's gems and their licenses (superseded by ADR 007)

This section held each gem an app ships to the runtimes' license policy (ADR 004), read every compiled file of every native gem for copyleft libraries and attributed the rest to a map of reviewed gems (`lib/fledge/compiled_code.yml`) or to `fledge.yml`, and wrote `notices/GEMS.txt`. ADR 007 removed all of it, on the maintainer's words of 2026-10-28: Fledge takes no position on the licenses of the gems an app depends on. What remains of it checks only that a gem's compiled files would load where the app goes (`Fledge::Linkage`; ADR 006, section 8). Each gem ships with its own files, its license files among them, where RubyGems installs it.

## Consequences

- `fledge build exe/my_cool_app` builds `dist/MyCoolApp-PLATFORM/`, whose program runs `exe/my_cool_app` with its gems on every platform, from any one of them. `examples/my_cool_app` (i18n, which needs concurrent-ruby, and sqlite3, precompiled for all four targets) builds and delivers on every platform in CI, and the parity check compares it with `bundle exec ruby exe/my_cool_app` on the runtime's own Ruby.
- NAME changes for every app: `examples/hello` ships as `Hello`. Pre-1.0, with no users, that is free (CHANGELOG).
- A built app with a Gemfile carries Bundler's environment over the person's, as `bundle exec` gives it: a Ruby the app starts runs in the app's bundle (`RUBYOPT=-r.../bundler/setup` followed by the person's own `RUBYOPT`, `BUNDLE_GEMFILE`), `GEM_HOME` names the runtime's gem folder, and `BUNDLER_ORIG_*` records the person's values. `Bundler.with_original_env` and `with_unbundled_env` give the person's own `RUBYOPT`, `GEM_HOME`, and the rest, which Delivery checks on every platform with a person's `GEM_HOME` and `RUBYOPT` set.
- Under a C locale, Bundler 4.0.20 cannot set up a bundle whose path is not ASCII (`SharedHelpers#clean_load_path` compares a US-ASCII string with a binary one), so a child Ruby a built app starts in its own bundle fails there, as it would under `bundle exec`. The launcher coerces only its own locale (ADR 003, section 5), not its children's.
- The parity check's differences for the gem-shaped app (`Parity::JUSTIFIED`, `checks: [:bundle]`): the program's path as typed; each gem's load path and `GEM_HOME` and `PATH`, which name the person's GEM_HOME on their computer and the runtime's gem folder in the app; `$VERBOSE`, which the person's `RUBYOPT` sets under `bundle exec` only (ADR 003, section 4); `Bundler.original_env`, `Bundler.unbundled_env`, and what a child Ruby sees inside `with_original_env` and `with_unbundled_env` do not differ at all; the development gems, which the app leaves out; RubyGems' YAML serializer, which reading the app's `.bundle/config` loads, and Bundler's feature flags, which it never needs to ask where the gems are, since that file says; and the project's `lib/my_cool_app/version.rb`, which Bundler's evaluation of the original gemspec loads before the program runs, and which in the app loads when the program requires it.
- A build reads each runtime archive one more time, for its gem folder, its gems, and its Ruby's version, and downloads each gem once into Fledge's cache.
- Not yet: path gems outside the project, gem servers that need credentials or mirrors (Bundler's `BUNDLE_MIRROR__*` and credentials are not read), gems that must be compiled for another platform than Fledge runs on (ADR 006), Bundler's optional groups (`group ..., optional: true`, which ship like any other group), and gem executables in `bin/`.
