# Phone Runtimes

This document says how Fledge's phone runtimes are built and what they hold, how the embedding API starts an app's Ruby, and what a phone runtime's licenses are. The decisions are ADR 011 (Ruby as a static library built from source), ADR 057 (target names), ADR 058 (bundled gems stay gems), ADR 067 (their extensions keep every symbol but their Init functions), ADR 078 (output to the system log), ADR 061 (`fledge_ruby_run_app`), and ADR 082 (the ruby program on Android), ADR 083 (how `RbConfig.ruby` names it). The projects `fledge build` writes around a runtime, and what CI checks before a store would, are `doc/contributors/design/phone-projects.md`. What a developer does with the project is in `doc/phones.md`; this document adds the internals.

## Targets

A phone runtime has two targets, named in RubyGems' grammar so that no desktop gem fits them (ADR 057). `RuntimeBuilder::Mobile::PLATFORMS` (`tasks/runtime_builder/mobile.rb`) holds them.

| Runtime | Target | What | Its Ruby's `RUBY_PLATFORM` | Compiler triple |
|---|---|---|---|---|
| `ios` | `arm64-ios` | iPhones and iPads | `arm64-darwin` | `arm64-apple-ios15.0` |
| `ios` | `arm64-ios-simulator` | the iOS Simulator on Apple silicon | `arm64-darwin` | `arm64-apple-ios15.0-simulator` |
| `android` | `aarch64-linux-android` | arm64-v8a phones and tablets | `aarch64-linux-android` | `aarch64-linux-android` (API 26) |
| `android` | `x86_64-linux-android` | x86_64 emulators and Chromebooks | `x86_64-linux-android` | `x86_64-linux-android` (API 26) |

Gem::Platform reads `arm64-ios` as `arm64-unknown`, which matches no desktop gem, and reads the Android names as Linux with Android's C library, which no `-linux`, `-gnu`, or `-musl` gem matches. The floors are iOS 15.0 (xord/cruby's and the spike's) and API 26, Android 8.0, the first whose C library has `nl_langinfo`, which Ruby's `localeinit.c` calls.

The iOS runtime is built on a Mac (`arm64-darwin`), since only Xcode builds for iOS. The Android runtime is built on x86-64 Linux in CI, and a Mac may build it too, with Google's NDK. An x86-64 Linux computer with KVM builds it, and the apps around it, and runs them on an emulator with nothing but what `mise.android.toml` pins by SHA-256: the JDK, the NDK, and the SDK's packages, which `bin/android-sdk` lays out as one SDK and `bin/android-emulator` boots an emulator from (`CONTRIBUTING.md`, "Android on Linux"). Neither is built on the other's runner.

## What a phone runtime holds

Each runtime is a release asset of its own, `fledge-runtime-VERSION-ios.tar.gz` and `fledge-runtime-VERSION-android.tar.gz`, with its SBOM and NOTICES beside it as every runtime has (`doc/contributors/design/license-audit.md`). It has no build-only companion: its headers are in it.

**iOS** is `FledgeRuby.xcframework`, made by Apple's `xcodebuild -create-xcframework` from one static library per target, in the slices `ios-arm64` and `ios-arm64-simulator`. Each slice holds:

- `libfledgeruby.a`: Ruby, its extensions and encodings, OpenSSL, libyaml, and the embedding API, merged by Apple's `libtool -static`, with debug information stripped;
- `Headers/`: Ruby's headers, with the slice's `ruby/config.h` moved beside the rest so one folder serves `#include <ruby.h>`, and the embedding API's `fledge_ruby.h` with a Clang module map (`runtime/mobile/module.modulemap`), so Swift imports it as `FledgeRuby` and linking it adds libz and the Security and CoreFoundation frameworks;
- `lib/ruby` and `libexec/cert.pem`: the Ruby the slice runs, which the app copies into its bundle for the slice it builds, as CPython's iOS XCFramework carries its standard library per slice.

The two slices' Rubies differ only in the compiler their `rbconfig.rb` records. One binary runs on iPhone and iPad.

**Android** is `FledgeRuby.aar`, packed by the pinned Gradle and Android Gradle plugin from `runtime/mobile/android/`, holding `libfledgeruby.so` and the ruby program `libfledgerubyexe.so` for arm64-v8a and x86_64 (see "The ruby program on Android"), and the Java class `org.setdef.fledge.FledgeRuby`. Beside it are one `lib/ruby` for both ABIs (Ruby names each ABI's folder of platform-specific files for its platform, so both fit one tree, and the build fails if any other file differs between them), `libexec/cert.pem`, and `include/`.

`libfledgeruby.so` holds all of Ruby, so native code that links it finds Ruby's whole C API. It keeps OpenSSL's, libyaml's, and libffi's symbols to itself (`--exclude-libs`), so an app's own copies cannot clash with them. The build fails unless it needs only Android's `libc`, `libm`, `libdl`, `liblog`, and `libz`, and unless every LOAD segment is aligned to 16 KB, which Google Play requires of 64-bit apps from 2027-02-01.

Neither runtime has the gems' executables, and the iOS runtime has no Ruby program, since iOS lets no app run one. The Android runtime's ruby program is a native library by name, which the app's installer extracts, and `ROOT/bin/ruby` is a link to it that the embedding API makes as the app starts (ADR 083).

## Ruby's C headers on a phone

Both phone runtimes ship Ruby's C headers, for the computer that builds the app: each iOS slice in `Headers/`, and the Android runtime in `include/` (both ABIs' `include/ruby-VERSION/` merged, with each ABI's configuration folder, and `fledge_ruby.h`). mkmf compiles a gem's extension against them (see `doc/contributors/design/phone-projects.md`, "Gems with extensions"), and native code that links the runtime includes them.

The app on the phone carries no headers. The iOS project's build phase copies the slice's `lib/` and `libexec/` into the bundle, and the Android project puts the runtime's `lib/` and `libexec/` in `fledge/`, so the Ruby root an app runs from has no `include/`. `require "mkmf"` on a phone therefore aborts as it does where Ruby's headers are missing. A desktop runtime keeps its headers for that reason (`doc/contributors/design/runtimes.md`); a phone has no compiler for mkmf to run, iOS lets an app start no program, and Android only the ones its package carries, so the mobile parity check does not test it.

## Building Ruby for a phone

`RuntimeBuilder::IOS` and `RuntimeBuilder::Android` (`tasks/runtime_builder/ios.rb` and `android.rb`, over `mobile.rb`) build the pinned Ruby from its release tarball with Ruby's own `configure` and `make`, after xord/cruby's Rakefile on iOS and Termux's `packages/ruby/build.sh` on Android. Every input is pinned by version and SHA-256 under `mobile:` in `runtime/sources.yml`: Ruby's tarball, OpenSSL, libyaml, libffi, the NDK for each computer that runs it, Gradle and the Android Gradle plugin, Mozilla's CA certificates as curl publishes them, XcodeGen, and bundletool. Xcode is chosen by version on the runner, since Apple publishes no download to pin.

For each target the build:

1. builds libyaml and libffi with their own `configure` (`--enable-static --disable-shared --with-pic`), and OpenSSL with its own `Configure` target for the platform (`ios64-xcrun`, `iossimulator-arm64-xcrun`, `android-arm64`, `android-x86_64`), with no shared library, programs, tests, documents, or modules;
2. unpacks Ruby's tarball into a folder of the target's own, makes the scripted edits (see "Scripted edits to Ruby's source"), copies the bundled gems' extensions in (see "Bundled gems' extensions"), and configures Ruby in that folder, its source, with `--enable-load-relative --disable-shared --with-static-linked-ext --disable-yjit --disable-zjit --without-gmp`, the dependencies' folders, `--with-out-ext` for Windows' extensions and the bundled gems' own builds (see "Bundled gems' extensions"), and `PKG_CONFIG=false`, so nothing of the build machine's leaks in. `--without-git` keeps a preview's `gems/bundled_gems`, which names commits for some bundled gems, from having `extract-gems` clone them from GitHub, unpinned, in place of the gems in the tarball that the SHA-256 pins. `--with-dump-ast` names the `dump_ast` built beside the build machine's miniruby (see "The builtin binary"), since a cross build cannot run the one it would build for the target;
3. writes the builtin binary (see "The builtin binary"), runs `make` with `yes_cross_compiling=` empty, so that `common.mk` does not hand the bundled gems' build the `--without-ext` that a cross build takes and that would bring their builds back, marks the bundled gems' extensions built, and runs `make install-nodoc`;
4. checks the bundled gems were installed, prunes the tree as a desktop runtime is pruned, and installs Fledge's RubyGems defaults (`doc/contributors/design/runtimes.md`).

Ruby is built in its source folder because a desktop's is: rv-ruby runs `./configure` and `make` there (`Abstract/rv-ruby.rb`, lines 157 to 174 at spinel-coop/rv-ruby f57186e), and what Ruby's install writes depends on the folder it runs in. `tool/rbinstall.rb` writes each default gem's specification by evaluating the gem's gemspec in the folder `make` runs in, and its `load_gemspec` (lines 921 to 928 at Ruby 4.1.0-preview1) puts `lib/` before each `.rb` file the gemspec lists that it finds no file for there; bundler's gemspec also globs its files from that folder. The phone runtimes used to configure Ruby in a folder beside its source, and their specifications differed from a desktop's: io-nonblock's listed `lib/ext/io/nonblock/extconf.rb`, so RubyGems' `register_default_spec` (`lib/rubygems.rb`, lines 1312 to 1342) took it for a gem whose files sit under `lib/` and left out `io/nonblock.bundle`, which is not under `lib/` and has a slash. `require "io/nonblock"` loaded the linked extension without activating the gem, and `Gem.loaded_specs` had no io-nonblock. Bundler's listed none of its manual pages and templates, and fileutils, forwardable, ipaddr, pp, and the gems with an `extconf.rb` listed their own files twice. Ruby's main branch has since changed `load_gemspec` (ruby/ruby 2cdfc0d20e, for Bug #22420), so that it registers the extension of every gem the build collects, io-console's among them; a phone takes whatever the pinned Ruby does, built as a desktop's is. Each target unpacks the tarball into a folder of its own, since a build in place leaves its objects among the source, and the build machine's miniruby (see "The builtin binary") builds beside one more.

What each system adds:

- **iOS** builds with Xcode's clang (`xcrun --sdk iphoneos|iphonesimulator`), aimed at the target's triple and the SDK's sysroot, configured for the host `aarch64-apple-darwin` so that Ruby's `configure.ac` does what it does for Darwin. After xord/cruby it passes `--disable-dln`, tells configure that iOS has no `system`, `syscall`, `__syscall`, `backtrace`, `getentropy`, `dup3`, or `pipe2` (`RuntimeBuilder::IOS::MISSING`), adds a stub `sys/vnode.h` the SDK lacks (xord/cruby's, with its MIT notice as an SPDX snippet in `ruby_source.rb`; it is a header Ruby compiles against, and nothing of it ships), and builds with `-Os -fvisibility=hidden` and `-framework Security`. OpenSSL's Simulator build takes `-mios-simulator-version-min`, since with `-mios-version-min` its assembly is tagged for devices and the Simulator's link fails. fiddle's relocatable object takes in the libffi it links, which `libfledgeruby.a` then leaves out, so libffi's symbols are local to fiddle, as Android's library keeps them to itself, and an app whose gem links a libffi of its own, as the ffi gem does, finds no second definition of any (`RuntimeBuilder::IOS#relocatable`).
- **Android** builds with the NDK's `TRIPLE26-clang`, `llvm-ar`, and `llvm-ranlib`, and tells configure what it cannot find out by compiling (`RuntimeBuilder::Android::CONFIGURE`). Android's seccomp filter for apps stops a process with SIGSYS when it calls `setgid`, `setuid`, `setregid`, `setreuid`, `setresgid`, or `setgroups`, and lets it call `setresuid` (bionic, `libc/SECCOMP_BLOCKLIST_APP.TXT`, lines 9 to 30 at 731631f); bionic's `setegid` calls `setresgid`, its `initgroups` calls `setgroups`, and its `seteuid` calls `setresuid`. configure finds every one of them in bionic, so it is told that each the filter would stop is missing, and Ruby raises `NotImplementedError` for a call that needs one, as it does wherever a call is missing: `Process.egid=`, `Process.gid=`, `Process::GID`'s changes, `Process.initgroups`, and `Process.groups=`. `Process.uid=` and `Process.euid=` use `setresuid` and work as on Linux. Like Termux, it also says there is no libcrypt, so `String#crypt` is Ruby's own `missing/crypt.c`. Termux's own answers (termux-packages, `packages/ruby/build.sh`, line 19 at 750b3fc) were what Fledge first followed, but Termux gives them "to fix compilation on android", not for the filter: they leave out `setresuid`, which the filter allows, and keep `setresgid` and `setuid`, which it stops, so `Process.egid=` and `Process.uid=` ended the app. The NDK is unpacked from its pinned download and checked to be the revision `runtime/sources.yml` names.

Then each system packs what it built. iOS merges every archive Ruby's build made (libruby, each extension's, the encodings' and transcoders'), `extinit.o` and `encinit.o`, the libraries, and the embedding API's objects into `libfledgeruby.a` per slice. Android links the same into `libfledgeruby.so` per ABI with `-Wl,--whole-archive`, `--exclude-libs` for the libraries, `--wrap=X509_get_default_cert_file` (see "Certificates"), and `-z max-page-size=16384`, then strips it. Both leave out libruby's `dmyext.o` and `dmyenc.o`, the empty `Init_ext` and `Init_enc` of a Ruby without static extensions: the linker would take them before `extinit.o`'s and `encinit.o`'s, and `require "json"` would fail. The embedding API's C is compiled with the launcher's warnings as errors and checked by clang's static analyzer.

## Scripted edits to Ruby's source

`RuntimeBuilder::RubySource` (`tasks/runtime_builder/ruby_source.rb`) makes a few edits to Ruby's source before it builds. Each fails the build when the lines it replaces are gone, so a new Ruby shows which to look at again.

| Edit | System | What it does | From |
|---|---|---|---|
| `psych_extconf` | both | psych's `extconf.rb` stops preferring pkg-config's libyaml | xord/cruby |
| `vm_dump` | iOS | `vm_dump.c` stops calling `system()` | xord/cruby |
| `configure_macos_minimum` | iOS | the generated `configure` keeps its check for macOS 10.6 or later for a macOS target only, since the iOS SDK reports 10.5 for an iOS one (ruby/ruby 3e96f16643) | Fledge; `doc/contributors/drafts/ruby-ios-configure.md` |
| `configure` | Android | the generated `configure` stops appending `-android` twice, so the platform is `aarch64-linux-android`, not `aarch64-linux-android-android` | Termux's guard |
| `ruby_c` | both | `ruby.c` gains `ruby_embed_libruby_path`, through which an embedder names the file Ruby would otherwise find with `dladdr` and derive its prefix from (`runtime_libruby_path`, lines 593 to 663 at Ruby 4.1.0-preview1) | Fledge |
| `load_c` | both | `load.c` finds a bundled gem's linked extension only while its gem is active (see "Bundled gems' extensions") | Fledge |
| `setproctitle_c` | Android | `$0=` and `Process.setproctitle` write the title into the process's own argument area, which `/proc/self/stat` names, where the argv Ruby was given is not in it, as an app's is not, so `ps` and `/proc/PID/cmdline` show it as on Linux | Fledge, after Android's `AndroidRuntime::setArgv0` |
| `process_c_maxgroups` | Android | `Process.maxgroups=` is defined where `Process.maxgroups` is, not only where configure found `setgroups` | Fledge |
| `file_c` | iOS | `rb_group_member` answers that the process is in no other group when `getgroups` fails, where it took the -1 for a count | Fledge; `doc/contributors/drafts/ruby-group-member.md` |
| `process_c`, `thread_pthread_c` | Android | the child of a fork resets its copy of the fork lock without unlocking it | ruby/ruby e06b9da3f2 |
| `thread_c` | Android, and the musl runtimes (`RuntimeBuilder::Musl::EDITS`) | `Thread#name=` names the native thread only of a thread that has not ended | ruby/ruby 6fdd452087 |
| `process_c_umask`, `file_c_umask` | Android | the `umask:` option and `File.umask` give `umask` only a mask's permission bits, as Linux keeps them, since bionic's fortified `umask` aborts on any other bit | Fledge; `doc/contributors/drafts/ruby-umask-fortify.md` |
| `dir_c` | Android | `dir.c` gets the `IFTODT` bionic lacks, so it reads each entry's type from `d_type` as on Linux | Fledge; `doc/contributors/drafts/ruby-glob-base-dir.md` |

`ruby_c` exists because on Android Ruby's library sits in a folder of native libraries alone, and an iOS app may keep Ruby anywhere in its bundle, so neither prefix is where `dladdr` would point.

`setproctitle_c` exists because an Android app's Ruby is a library in a process the zygote forked, and starts with an argv `fledge_ruby_run` allocates, so Ruby's `missing/setproctitle.c`, which writes the title over that argv, wrote it where the kernel never looks. Android names an app's process by clearing the zygote's argument area and copying the name in, cut to the area's length (`AndroidRuntime::setArgv0`, `core/jni/AndroidRuntime.cpp`, lines 328 to 347 at android-14.0.0_r1), a call it hides from apps. The kernel gives that area's bounds in `/proc/self/stat` (`arg_start` and `arg_end`, fields 48 and 49), and Ruby's own `setproctitle` clears and writes it the same way once pointed there; a title longer than the area, the app's identifier and a NUL, is cut, where Linux's Ruby also has the environment's area to write into. The `ruby` program an app starts has its argv in its own area and keeps Ruby's way. Neither renames a thread: `setArgv0` names the thread that calls it, Android's main thread, while an app's Ruby runs on a thread of its own, and Linux's Ruby leaves the kernel's name for its process alone.

`process_c_maxgroups` exists because the Android runtime is configured without `setgroups`, which Android's seccomp filter for apps stops (`RuntimeBuilder::Android::CONFIGURE`), and Ruby defines `Process.maxgroups=` only where configure found `setgroups` (`process.c`, line 6835 at Ruby 4.1.0-preview1), though the setter only stores the number `Process.maxgroups` reads and calls nothing of the system's (lines 6845 to 6862). The edit defines it on the condition Ruby defines the getter on (line 6632), so it works as on Linux, where it raised `NotImplementedError`.

The last five mend bugs of CRuby's that a phone's C library brings out and a desktop's does not, each found by ruby/spec on the phones (`doc/contributors/design/parity.md`, "ruby/spec on phones"). In the iOS Simulator `getgroups` fails, since Darwin's looks the process's user up with `getpwuid`, and an app runs as the Mac's user, whom the Simulator's user database does not know (Libc, `sys/getgroups.c`, lines 35 to 58 at Libc-1752.120.2; a device, which runs an app as a user of its own, is unchecked), and `file.c` took the -1 for a count, so `File::Stat#readable?` raised `ArgumentError` for a file of another group. bionic's `pthread_rwlock_unlock` refuses a write lock that another thread ID took (`libc/bionic/pthread_rwlock.cpp`, lines 487 to 495 at 731631f), and a forked child's thread has an ID of its own, so `fork`'s child stopped in Ruby's `[BUG]` handler; Ruby's master has since stopped unlocking there, for macOS, and the edits take its change. bionic aborts on a `pthread_t` of a thread that has ended (`libc/bionic/pthread_internal.cpp`, lines 96 to 125), which `Thread#name=` passed, and Ruby's master has since stopped; musl's `pthread_setname_np` reads the same freed `pthread_t`, which crashed stock Ruby and the app alike there, so the musl runtimes take that edit too. bionic's `dirent.h` has `d_type` but no `IFTODT`, so `dir.c` stats every entry a glob reads, and one of those stats takes the entry's path with a `base:` `Dir`'s own path before it, relative to that `Dir`, so a `Dir` opened by a relative path found nothing; Ruby's master has the same lines. Ruby passes the `umask:` option's mask and `File.umask`'s argument to `umask` as they are, and Ruby's build compiles with `-D_FORTIFY_SOURCE=2`, with which bionic's `umask` aborts the process for a mask with any bit beyond 0777 (`libc/bionic/fortify.cpp`, lines 400 to 406), where Linux keeps a mask's permission bits and drops the rest, so `umask: -1` ended the app; Ruby's master has the same lines. Ruby's master's fixes arrive with Ruby 4.1.0, and the edits for them go then.

## The builtin binary

A cross build cannot run its own miniruby, so `configure.ac` (lines 1628 to 1632 at Ruby 4.1.0-preview1) leaves out the builtin binary, and Ruby falls back to `mini_builtin.c`, which never loads `gem_prelude.rb`: such a Ruby boots with no RubyGems. An iseq binary depends only on Ruby's version, endianness, and word size (`compile.c`, `ibf_load_setup_bytes`), so the build makes a miniruby for the build machine from the same source, once per runtime, and has it write `builtin_binary.rbbin` from Ruby's own template into each target's build folder. It then sets the Makefile's `BUILTIN_BINARY` to `yes` and adds a rule to `GNUmakefile` that keeps `make` from replacing the file with the empty stub a cross build writes. It fails when the binary or the Makefile line is not what it expects.

## Bundled gems' extensions

Ruby's build links its standard library's extensions in and registers each in `extinit.c`, but not a bundled gem's: `template/configure-ext.mk.tmpl` builds `.bundle/gems` with `--no-extstatic`, and `ext/extmk.rb` (lines 273 and 660 at Ruby 4.1.0-preview1) leaves a gem's extension out of `extinit.c`. `RuntimeBuilder::BundledExtensions` keeps those gems gems (ADR 058):

1. It copies each bundled gem's extension sources (its `ext/`, and the `lib/`, `include/`, and `src/` its `extconf.rb` reads beside it) among Ruby's own, to `ext/gems/NAME`, where extmk links them in and registers each under the feature the gem requires (`bigdecimal.so`, `racc/cparse.so`, `rbs_extension.so`).
2. It gives each copied extension the rules `BundledExtensions::RELOCATABLE` holds, after the gem's own `depend` file, which mkmf appends to the extension's Makefile: the extension's static library holds one object, its objects linked with `cc -r`, in which every symbol but the extension's Init function is local, as Ruby looks up only that function in its shared object on a desktop (ADR 067). On iOS Apple's ld links it with `-keep_private_externs`, since without it ld makes every hidden symbol local, and the iOS runtime's `-fvisibility=hidden` hides most gems' Init functions; then Apple's `nmedit -s` keeps only the Init function global (`IOS#relocatable`). On Android the NDK's lld links it and `llvm-objcopy --keep-global-symbol` does the same (`Android#relocatable`). The rules also compile the extension with `-fno-common`, as mkmf's `CCDLFLAGS` compiles its shared object on a Mac and mkmf leaves out of a static build: Xcode's clang otherwise makes a global without an initializer, such as prism's `VALUE rb_cPrism;`, a common symbol, which stays global and merges with libruby's of the same name. The Init function is the one extmk names for the extension's feature (`ext/extmk.rb`, line 565 at 4.1.0-preview1): `Init_racc_cparse` for `racc/cparse`. That is what lets prism's extension, which compiles its own libprism, sit beside libruby's: its `pm_parse` and every other `pm_` symbol are local to it, and its `Init_prism` is `Init_prism_prism`, which does not meet libruby's `Init_prism`.
3. `configure --with-out-ext` leaves out the gem's own build, by the names extmk matches a gem by (`NAME` and `NAME-*`, `ext/extmk.rb` lines 514 to 529 at Ruby 4.1.0-preview1).
4. Once Ruby is built, it writes each gem's `gem.build_complete` where its own build would (`.bundle/extensions/PLATFORM/ABI-static/NAME-VERSION/`), so `tool/rbinstall.rb` installs the gem, specification and all, and RubyGems loads it rather than ignoring it because its extensions are not built.
5. After install it checks that every such gem has its specification and its mark.

When the gem's Ruby requires its extension, `load.c`'s `search_required` finds no file and looks among the statically linked extensions, which have it.

Ruby looks there for any feature it finds no file for, so a linked extension would be found by a plain `require` of its feature before RubyGems has activated its gem. RubyGems' `require` asks Ruby's own first, and activates a gem only when that raises `LoadError` (`lib/rubygems/core_ext/kernel_require.rb`, lines 79 to 81 and 138 to 148 at Ruby 4.1.0-preview1). Where a gem's Ruby file has its extension's name, as bigdecimal's `lib/bigdecimal.rb` has `bigdecimal.so`'s, nkf's `lib/nkf.rb` `nkf.so`'s, and fiddle's `lib/fiddle.rb` `fiddle.so`'s, `require "bigdecimal"` loaded the extension alone: the gem was never activated, and its Ruby, which defines `BigDecimal#sqrt`, `#power`, and `BigMath`, never loaded. On a desktop the extension is a file in the gem's own folders, which RubyGems puts on `$LOAD_PATH` only as it activates the gem (`Gem::BasicSpecification#full_require_paths`, `lib/rubygems/basic_specification.rb`, lines 184 to 195), the gem's extension folder, named for its full name, among them. So the `load_c` edit gives the lookup a gate: a table of each copied gem's extension, by the feature it is registered as, with its gem's full name (`BundledExtensions.features`, from each `extconf.rb`'s `create_makefile`), and a check that lets the lookup find a gem's extension only while a folder named for the gem is on `$LOAD_PATH`. `require "bigdecimal"` then fails in Ruby's own require, RubyGems activates the gem and requires it again, and the gem's `lib/bigdecimal.rb` loads first and requires `bigdecimal.so`, as on a desktop. Bundler's setup puts the same folders on `$LOAD_PATH`, so a gem in an app's Gemfile is found as it is activated. Every other linked extension, Ruby's own, is found as before. One difference stays: a desktop's RubyGems also activates a gem for a require of its extension's own feature (`require "racc/cparse"` before racc is active), since it finds the extension's file among the gem's; a phone's gem has no such file, so that require raises `LoadError` until the gem is active. The parity probe reports a gem whose require loads without activating it as `loads, but not its gem`, which the mobile parity check compares with `ruby main.rb`.

fiddle is on both phones. xord/cruby leaves it out of its iOS Ruby "to pass the App Store review", but none of Apple's guidelines forbids it, CPython's and BeeWare's iOS builds ship Python's `ctypes`, and libffi makes fiddle's callbacks on iOS without writable code (`doc/contributors/research/2026-11-12-ffi-and-fiddle-on-phones.md`). win32ole and win32 are Windows' alone. Every other bundled and default gem is as a desktop runtime has it.

## The embedding API

`runtime/mobile/fledge_ruby.h` is the embedding API, in C, compiled into both runtimes with `fledge_ruby.c`, `output.c`, `apple.c` or `android.c`, and the launcher's `locale.c`, `config.c`, and `bundler.c`. Its header comments are the reference for each function.

| Function | What it does |
|---|---|
| `fledge_ruby_forward_output(tag)` | Sends standard output and standard error to the system log (see "Output to the system log"). |
| `fledge_ruby_run(root, script, argc, argv)` | Runs a Ruby file on the calling thread, as `ruby SCRIPT ARGS` would, and returns its status. |
| `fledge_ruby_run_app(root, argc, argv)` | Runs the app `fledge build` put in `root`, as the desktop launcher runs one (ADR 061). |
| `fledge_ruby_add_extension(feature, init)` | Tells Ruby that an extension is linked in (see `doc/contributors/design/phone-projects.md`, "Registering extensions"). |

`fledge_ruby_run` starts Ruby as the desktop launcher does, after Ruby's own `main.c` (`doc/contributors/design/launcher.md`): the locale, `ruby_sysinit`, then `ruby_start_main`, whose callback runs `RUBY_INIT_STACK`, `ruby_init`, and `ruby_run_node(ruby_options(...))`, with `ruby --disable=rubyopt -- SCRIPT ARGS`. Between `ruby_options` and `ruby_run_node` it registers the extensions added so far and gives `$stdout` a terminal's line timing when descriptor 1 is not a terminal ("Line timing", below; ADR 078). Ruby's prefix is `root`, through `ruby_embed_libruby_path`, so the load path and `Gem.path` are `root/lib/ruby`, which Fledge's RubyGems defaults keep `Gem.path` to. A bare C locale becomes a UTF-8 one, with the launcher's own `fledge_coerce_locale` (ADR 041). Ruby boots once per process, so a second call returns 70 (`FLEDGE_RUBY_SOFTWARE`).

`fledge_ruby_run_app` reads `root/fledge.cfg` with the launcher's reader and runs `root/app/ENTRY`. For an app with a Gemfile it sets `BUNDLE_GEMFILE` to the app's Gemfile, whose `.bundle/config` Bundler then reads as the app's settings, and requires `bundler/setup` from Ruby's own library, or from the gem of the Bundler `fledge.cfg` names, as the desktop launcher does (`doc/contributors/design/launcher.md`, "The Bundler environment"), which sets `ENV` as `bundle exec` would (`Bundler::Runtime#setup`, `set_bundle_environment`). It returns 66 (`FLEDGE_RUBY_NO_APP`) when `fledge.cfg` or the program is missing, and 70 when the configuration is damaged or Bundler cannot set up the gems.

On Android, `fledge_ruby_run` first makes `root/bin/ruby` a link to the runtime's ruby program (see "The ruby program on Android").

Unlike the desktop launcher, neither function sets anything of the environment aside: iOS and Android start an app with an environment of their own, which no person sets. Ruby needs a deep stack: Fledge's hosts run it on a thread with 64 MB.

Swift needs no shim: the module map imports the C functions.

## The ruby program on Android

An Android app may run only the files its package installer extracts from the APK into its native library folder, `nativeLibraryDir`, and only when its native libraries are compressed, so that the installer extracts them; the files in the app's own folders it may not run (W^X, from target API 29). The Android runtime therefore carries its ruby program as a native library by name, `libfledgerubyexe.so`, beside `libfledgeruby.so` in each ABI's folder of the AAR, and the Gradle project packs native libraries compressed (`doc/contributors/design/phone-projects.md`, "The Gradle project"). ADR 082 weighs where else it could live.

**Built.** `RuntimeBuilder::Android#program` compiles `runtime/mobile/ruby_program.c`, a `main` that calls `fledge_ruby_program_main`, as a position-independent executable linked against `libfledgeruby.so` with the run path `$ORIGIN`, which bionic's linker expands to the folder of the program's own file (so it is a few kilobytes, where a static copy of Ruby would add as much again as `libfledgeruby.so` to every ABI), and with `-z max-page-size=16384`. It checks the program with clang's static analyzer, strips it, and fails unless it needs only Android's libraries and `libfledgeruby.so`, has that run path, and aligns every LOAD segment to 16 KB. It carries no Ruby of its own: Ruby's `main.c` is `fledge_ruby_main` in `fledge_ruby.c`. Linked statically with all of Ruby, as a desktop's `bin/ruby` is, it would add as much again as `libfledgeruby.so` to every ABI.

**Named.** `RbConfig.ruby` is `ROOT/bin/ruby`, from the prefix Ruby derives, as a desktop's is. Before Ruby boots in the app, `fledge_ruby_run` calls `fledge_ruby_link_program` (`android.c`), which finds `nativeLibraryDir` with `dladdr` on `libfledgeruby.so`, and makes `ROOT/bin/ruby` a link to the program there, through a new link renamed into place, whenever it is not that link already: the folder changes with each install. Where the libraries load from inside the APK (`base.apk!/lib/ABI/`), not extracted, there is no program, and an old link is removed. `RbConfig` stays stock Ruby's, rather than naming the program in `nativeLibraryDir` by rewriting `rbconfig.rb` at run time, because gems read its values for other ends: RubyGems takes `bindir` as where to install executables and `ruby_install_name` for their shebangs. An environment variable naming the program would add to the app's `ENV`, which decisions 9 and 10 keep as `ruby main.rb` has it.

**Run.** The kernel runs the file the link resolves to. `fledge_ruby_program_main` finds `ROOT` from the path the program was run by, which the kernel keeps as `AT_EXECFN` (`getauxval`): the parent of its folder, `ROOT/bin`, resolved, since `/proc/self/exe` and `dladdr` name the file in `nativeLibraryDir`. It loads `libfledgeext.so` from beside `libfledgeruby.so` when the app has one, as the host loads it, so that its constructor registers the app's gems' extensions; `libfledgeext.so` has the run path `$ORIGIN` too, so that a shared library an extension carries is found beside it outside the app's library namespace (`doc/contributors/design/phone-projects.md`, "Linking extensions on Android"). Then `fledge_ruby_main` runs, which is what a desktop's `bin/ruby` is (`runtime/launcher/ruby_main.c`): the locale, the certificates, and Ruby's prefix as `fledge_ruby_run` has them, then `ruby_sysinit` and `ruby_start_main`, with the extensions registered between `ruby_options` and `ruby_run_node`, and Ruby's arguments as given, `RUBYOPT` honored. When its first argument is the program `ROOT/fledge.cfg` names, compared by device and inode as the desktop's `fledge_relaunch` compares it, it runs `fledge_ruby_run_app` with the arguments after it instead, as the host ran the app: the desktop's `bin/ruby` hands such a program to the app's launcher (ADR 026), and an Android app's starting is its host's, which the program does in its own process.

A Ruby the app starts inherits the app's environment and standard streams, so its output reaches the log through the same pipe, buffered as Ruby buffers a pipe. It has no Java virtual machine, and Android may stop it with the app.

## Output to the system log

iOS and Android discard an app's standard streams unless a debugger holds them. `fledge_ruby_forward_output` (`runtime/mobile/output.c`) makes standard output and standard error each the write end of a pipe, which a thread of its own reads line by line into the system log (ADR 078):

- on Apple's systems, os_log with the tag as subsystem (`apple.c`);
- on Android, logcat with the tag as tag, standard error's lines as warnings, as CPython's Android support logs them (`android.c`).

A line longer than an entry holds (logcat cuts one at about 4,000 bytes) goes as several entries in a row of at most 1,000 bytes (`FLEDGE_LOG_ENTRY_MAX`, `mobile.h`). The cut falls between UTF-8 characters and before whitespace, never after it, since the unified log drops an entry's trailing whitespace (`log show` prints `a ` as `a`), which would take a space out of the line the entries make (`fledge_log_chunk`).

**`OS_ACTIVITY_DT_MODE`.** When the process's environment holds this variable, the unified log copies each entry to standard error, for a developer tool that reads the app's streams. Then `fledge_ruby_forward_output` leaves the streams alone and returns 0 (`fledge_log_echoes` in `apple.c`), since forwarding standard error would send each copy back to the log, which would copy it again, until the pipe filled and Ruby's `puts` blocked. What counts is that the variable is present, not its value: `NO`, `0`, and an empty value turn the copy on as `YES` does. Android's `fledge_log_echoes` is always false, since logcat copies nothing to an app's streams. Xcode 15 and newer read the log itself and set the variable only when a scheme asks for the old way (`IDELogRedirectionPolicy=oslogToStdio`). With the variable set, a developer tool shows each of the app's lines once, from its streams, and the log holds none of Ruby's.

**Line timing.** Ruby writes through to a terminal but buffers standard output to a pipe until its buffer fills or the program ends (`io.c`, `io_binwrite_requires_flush_write`, lines 1942 to 1953 at Ruby 4.1.0-preview1: only `FMODE_SYNC` or `FMODE_TTY` writes at once); standard error is in sync mode already (`rb_io_prep_stderr`). So `fledge_ruby_run`, after `ruby_options` and before Bundler's setup and the program, whenever descriptor 1 is not a terminal, gives `$stdout`'s IO the `FMODE_TTY` Ruby gives an IO on a terminal (`io_check_tty`), which only Ruby's writes read for a descriptor other than standard input (`write_lines_as_printed`, `fledge_ruby.c`). `$stdout` then writes through as to a terminal, while `$stdout.sync` stays false, as under `ruby main.rb`, and `$stdout.tty?`, which asks `isatty` of the descriptor, stays false, so no library sends escape codes into the log. Ruby's header deprecates the field and says of the flag "You cannot change this" (`include/ruby/io.h`, lines 188 to 191), since Ruby sets it once, as it opens the IO; Fledge sets it once too, before the program writes anything. `$stdout.sync = true`, which this replaced, was a difference an app could read, and a pseudo-terminal would have made `$stdout.tty?` true. The parity probe's "$stdout writes through" measures it: Ruby warns when `IO#syswrite` would pass bytes still in the buffer. That holds under `OS_ACTIVITY_DT_MODE` too: the streams then go to the developer tool, which reads them as the log is read (`simctl launch --console` gives the app pipes). On a terminal (`simctl launch --console-pty`) Ruby already writes through, and the flag is Ruby's own.

## Certificates

OpenSSL's compiled-in certificate folder is the build machine's, so the runtime carries Mozilla's CA certificates as `libexec/cert.pem` and points OpenSSL at them as rv-ruby's Ruby, the desktops' reference, does (`tasks/runtime_builder/certificates.rb`, the same two edits the musl runtimes make, `runtimes.md`, "musl Linux's Ruby, built in Alpine"): OpenSSL's `SSL_CERT_FILE` is renamed `PORTABLE_RUBY_SSL_CERT_FILE` in its source, and the installed `openssl.rb` sets that to `SSL_CERT_FILE`, or else to `libexec/cert.pem` beside `RbConfig.ruby`, before it loads `openssl.so`. So an app's `ENV` holds nothing of the runtime's when it starts, and gains the one variable at `require "openssl"`, as under rv-ruby's `ruby main.rb`; the parity probe's "ENV from require 'openssl'" compares it.

- **iOS:** OpenSSL reads the variable.
- **Android:** OpenSSL reads no environment variable in an app. `ossl_safe_getenv` refuses them where `AT_SECURE` is set (`crypto/uid.c`, `OPENSSL_issetugid`), and every app inherits `AT_SECURE` from zygote, which Android starts in an SELinux domain of its own; setting `SSL_CERT_FILE` alone fails on an emulator. So `libfledgeruby.so` is linked with the linker's `--wrap=X509_get_default_cert_file`, which sends OpenSSL's every call of that function to `android.c`, which answers with the file the variable names, read with `getenv`, which `AT_SECURE` does not stop, or else the runtime's own. So a developer's `SSL_CERT_FILE` counts as on a desktop, and `OpenSSL::X509::DEFAULT_CERT_FILE` names the file. The linker's option needs no edit to OpenSSL's or Ruby's source, and reaches every caller, not only Ruby's default store. Apple's linker has no such option and needs none.

## The Java class

Android needs Java for what C cannot do, in `org.setdef.fledge.FledgeRuby` (`runtime/mobile/android/src/main/java/org/setdef/fledge/FledgeRuby.java`):

- **Unpack the asset.** An app carries `lib/`, `libexec/`, and its own code as one stored zip asset, which the class unpacks into the app's files folder on the first launch of each installed version, and leaves on later launches.
- **Set `HOME`** to the app's files folder when Android sets none, as iOS gives every app one, so `Dir.home` is writable.
- **Pass strings as UTF-8 bytes,** not through JNI's `GetStringUTFChars`, which writes modified UTF-8 that differs past Unicode's first plane, and paths canonical: an app's files folder is `/data/user/0/PACKAGE/files`, through a link to `/data/data`, which Ruby resolves `__dir__` through, as the desktop launcher resolves its own folder.
- **Start Ruby on its own thread** with a 64 MB stack (`STACK_SIZE`), never the UI thread, which Android stops an app for blocking: `start` and `startApp`, with `run` and `runApp` for a caller that has its own thread.

It is Java, not Kotlin, so an app need not depend on Kotlin's standard library; Kotlin calls it as it is.

## Licenses of a phone runtime

Each phone runtime passes the license audit before it is archived (ADR 004; `doc/contributors/design/license-audit.md`), and ships only what decision 8 allows, with no LGPL library. Its components are recorded in `runtime/licenses.yml`: Ruby, OpenSSL, libyaml, libffi, the NDK's compiler-rt builtins and libunwind on Android (`compiler-rt-ndk`), Mozilla's CA certificates as a file, and Fledge's own embedding API (`fledge-embedding`, MIT), which includes the Android runtime's ruby program. GMP is configured out, iOS's `crypt` is its libSystem's, and Android's `String#crypt` is Ruby's own `missing/crypt.c`, so neither runtime carries libxcrypt.

Two things in the audit exist for phones. An iOS runtime has a Ruby per slice, so a platform's map entry names several prefixes (`runtime/licenses.yml`, `prefixes`), and each gem in them is one component. An AAR is a zip whose entries the app ships, so the audit reads each entry with `unzip`, as `FledgeRuby.aar!ENTRY`, and a copyleft library's code in one fails as it would in a file. The audit's readers for the Android runtime are the NDK's own LLVM tools (`RuntimeBuilder::Android#readers`).

The templates and the embedding API are Fledge's own code, MIT, and the host's compiled code ships in every phone app, which `doc/licensing.md` says. Gradle's wrapper, which no app holds, is Gradle's, under Apache-2.0.
