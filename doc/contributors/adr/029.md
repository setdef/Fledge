# ADR 029: Fledge's Public Interface Is Its Command and the Files It Reads and Writes

## Context and Problem Statement

SemVer 2.0.0's first item says software that uses it "MUST declare a public API", and its eighth says a backward-incompatible change to that API increments the major version. Fledge follows SemVer (ADR 028), and 1.0 tells developers what will not change without a major. The maintainer's words bound it: no 1.0 "until at least some of these things are proven" (decisions.md, 2026-11-02), and dropping a Ruby or an operating system version takes a major (decisions.md, 2026-11-03).

Fledge had declared no API. Its Ruby classes carry RDoc and examples, which reads as a promise. A wrapper such as Lota's `lota fuse` that called `Fledge::CLI` in its own process, read `fledge.cfg`, or matched a `fledge build:` message would hold each of those against every refactor of 1.x. What is Fledge's public interface?

## Decision Drivers

- A developer and a framework wrapper must know what to hold Fledge to, and what not to read.
- Fledge's contributors must stay free to refactor `lib/` and reword messages in 1.x.
- Every promise should be one a test already checks where it is built.

## Considered Options

1. The command, `exe/fledge`, and the files it reads and writes: what you type, what `fledge build` reads from a project, and what it writes.
2. The Ruby classes under `lib/`, as their RDoc and examples suggest, as well as the command.

## Decision Outcome

Chosen: option 1, because it is the surface every developer and CI job already uses, and it leaves the code free. Code that calls Fledge calls the command, as a person or a CI job does. `fledge --help`, the header of `exe/fledge`, documents it; the README and `lib/fledge/config.schema.json` describe the same thing. Fledge's Ruby classes, standard error's wording, `fledge.cfg`, and the runtime's tree below what Ruby answers are not part of it. `doc/contributors/design/public-interface.md` lists what 1.x freezes, what it does not, how 1.x adds, and the names held for later.

A change is compatible when every project that builds with 1.0 builds with a later 1.x to the same output, and every app it built behaves the same.

Confidence: high that this is the interface Fledge can keep. Tauri 2 and Briefcase declare theirs the same way.

### Consequences

- Good, because a wrapper knows what to rely on: the command, its output and statuses, and the files.
- Good, because contributors refactor `lib/` freely in 1.x, and the RDoc stays, for them.
- Bad, because a framework that wants to run Fledge in its own process gets no promise for it. It runs the command, which costs a process and a Ruby start.
- Bad, because every frozen item is a promise the gate does not check by itself. Each is tested where it is built, and a test that lets one change without failing is a bug in that test.
- Bad, because a message on standard error can change in any release, so a script that matched one breaks without a major.

### Confirmation

`test/cli_test.rb`, through injected streams, and `test/integration/exe_test.rb`, as a subprocess, hold the command, its statuses, and standard output. `test/config_schema_test.rb` holds `fledge.yml`. `Parity` (`tasks/parity.rb`) holds how a built app differs from `ruby main.rb`. The Delivery jobs in `.github/workflows/ci.yml` hold what a built app holds and where installers put it.

## Pros and Cons of the Options

### The Ruby classes as API

- Good, because a framework could build in its own process without a subprocess.
- Bad, because every method, keyword, and return value of `lib/` would be frozen, and Fledge's internals change with every story.

## More Information

Prior art, read on 2026-11-04 for the 1.0 review (`doc/contributors/research/2026-11-04-one-point-oh-surface.md`, section 1). Tauri 2 declares `tauri.conf.json`, whose schema is served per major, and a command; its Rust crates are a separate API with versions of their own. Briefcase declares `pyproject.toml`'s `[tool.briefcase]` tables and the `briefcase` command. cibuildwheel pins its build tools with each release, so upgrading cibuildwheel is how a project takes newer tools.

ADR 054 decides the schema's address, and ADR 092 the mirror's layout, both frozen with the interface. `doc/contributors/design/releases.md` says which Rubies and platform floors 1.x keeps.
