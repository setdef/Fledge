> Findings of 2026-11-14 on how an Android app can carry its gems' extensions as files without breaking a framework's own host. Requested: written by an agent and not reviewed line by line. It changes no code and no ADR; the orchestrator decides and writes any ADR.

# Android Hosts and Extension Files

On Android, Fledge links every gem's extension into one shared library per ABI, `libfledgeext.so`, whose constructor registers each extension with Ruby (ADR 022). The host loads it after `libfledgeruby.so`. Fledge's own `MainActivity` does so in a static block it writes for each build (`lib/fledge/templates/android/src/main/java/org/setdef/fledge/host/MainActivity.java`, lines 26 to 28; `lib/fledge/mobile_project/android.rb`, line 143). A framework that owns the app's startup replaces that file with its own (ADR 025). `examples/sdl_phone`'s host does, and names the library itself: `getLibraries()` returns `{"SDL3", "fledgeruby", "fledgeext"}` (`examples/sdl_phone/host/android/src/main/java/org/setdef/fledge/host/MainActivity.java`, line 28), as `doc/contributors/design/phone-projects.md`, "A host that owns the main loop", tells a host to.

The findings of 2026-11-13 (`doc/contributors/research/2026-11-13-phone-extensions-as-files.md`) showed that Android lets an app load a library its installer extracts, so linking every extension in is Fledge's choice, not the phone's. Commit 10b0cfe2 acted on that. It shipped each C or C++ extension an `extconf.rb` builds as a native library of its own, `libfledgeext.FEATURE.so`, which Ruby loads through a link at the desktop's path. An app whose extensions were all of that kind then had no `libfledgeext.so`. Fledge's `MainActivity` stopped loading it, but a host's file is fixed. SDL's activity refuses to start an app when a library it names is missing, so every game over SDL would have stopped at launch. Commit b6d7cdf2 reverted the change an hour later, before any release. No CI job builds an app with a host of its own, so nothing ran into it.

These findings ask how an Android app should carry its gems' extensions so that two things hold. The app's Ruby sees what it sees under `ruby main.rb` wherever Android allows it; the maintainer accepts a difference "only when it is inherent to where the app ships or a platform truly forbids what Ruby does" (`decisions.md`, 2026-11-12). And any framework's host keeps working without knowing how Fledge packaged the extensions, with a contract in Fledge's own terms: the maintainer, on one framework's needs, "We gotta support Tokra (a Tauri port), and any other framework in the future."

## Verdict

The two hold together. What broke the host was not loading extensions from files. It was that the one library name hosts are told to load stopped existing.

Every host read here names the libraries of its own framework and of the language runtime it embeds, by fixed name, and none can know how a packager split the rest. So the contract a host can rely on is a short list of names that always exist, loaded in a stated order, plus one rule for the native methods its Java code declares: they live in a shared library of the framework's own, which the host loads by name. Fledge can keep `libfledgeext.so` as such a name whatever is inside it, and can load it itself, so that a new host need not name it at all.

The recommendation, at the end, is to load C and C++ extensions from files on Android, as 10b0cfe2 did, while keeping `libfledgeext.so` in every Android app that has a compiled extension, loading it from the runtime before Ruby boots, and writing the host's contract into `doc/contributors/design/public-interface.md`, with a test that fails when a promised library is missing.

## How hosts load native code

| Host | Names it loads, and how | Thread | A missing name |
|---|---|---|---|
| SDL3's `SDLActivity` | `getLibraries()`, `{"SDL3", "main"}` by default, each with `System.loadLibrary` | UI, in `onCreate` | An alert, and the app does not start |
| Tauri (wry, tao) | One, the app crate's own library, from a Kotlin `object`'s `init` | UI, at the first lifecycle call | `UnsatisfiedLinkError` at that call |
| python-for-android | A fixed list, each optional name only if its file is in `nativeLibraryDir`, then `libmain.so` | UI, in `onCreate` | Optional names skipped; others thrown |
| Chaquopy | Its own list, inside `Python.start`; the app's code names none | The caller's | Thrown |
| Flutter | `libflutter.so` from the embedding's Java; the engine opens the app's `libapp.so` itself | A background thread | Thrown, with a message about split APKs |
| React Native | `SoLoader.loadLibrary(name)`, through a map of merged names | The caller's | Thrown |

**SDL3.** `SDLActivity.onCreate` (line 346) calls `loadLibraries()`, which calls `SDL.loadLibrary` for each name `getLibraries()` returns (lines 307 to 311). That uses ReLinker when the app has it, and otherwise `System.loadLibrary` (`SDL.java`, lines 44 to 88). On `UnsatisfiedLinkError` the activity sets `mBrokenLibraries` and shows "An error occurred while trying to start the application" instead of starting (lines 379 to 421). The default `getLibraries()` documents the rule: "An array returned by a new implementation must at least contain "SDL3". Also keep in mind that the order the libraries are loaded may matter" (lines 287 to 304). `libSDL3.so` has to be one of them because its `JNI_OnLoad` registers SDL's Java methods with `RegisterNatives` (`SDL_android.c`, lines 568 to 596), and ART calls `JNI_OnLoad` only for a library it loads. By default SDL takes the last name as the library holding `SDL_main` (`getMainSharedObject`, lines 268 to 277), and its `nativeRunMain` opens that file again with `dlopen` by its full path and looks the function up (`SDL_android.c`, lines 827 to 851). So SDL itself relies on a second `dlopen` of a library Java has loaded returning the same one. `sdl_phone` overrides `main()`, so that path is not taken there.

**Tauri.** The generated `MainActivity` extends `TauriActivity` (`crates/tauri-cli/templates/mobile/android/app/src/main/MainActivity.kt`, line 6), which extends wry's `WryActivity` (`crates/tauri/mobile/android-codegen/TauriActivity.kt`, line 14). `WryActivity.onCreate` calls `Rust.onCreate(this)` (`wry/src/android/kotlin/WryActivity.kt`, line 130), and the first use of the Kotlin `object Rust` runs its `init`, `System.loadLibrary("{{library}}")` (`Rust.kt`, lines 14 to 17), on the UI thread. `{{library}}` is filled at build time from `WRY_ANDROID_LIBRARY` (`wry/build.rs`, line 41), which the CLI sets to the app crate's library name (`crates/tauri-cli/src/mobile/android/mod.rs`, line 170); cargo-mobile2 builds it as `lib{name}.so` and links it into `app/src/main/jniLibs/ABI/` (`src/android/config.rs`, lines 255 and 256; `jnilibs.rs`, lines 64 to 68), with `libc++_shared.so` beside it when the library needs it (`target.rs`, lines 317 to 329). Every `external fun` of `Rust` (`Rust.kt`, lines 20 to 43) and of Tauri's `PluginManager` (`PluginManager.kt`, lines 238 and 239) is found by name: tao's `android_fn!` writes a `#[no_mangle]` function named `Java_{domain}_{package}_{class}_{function}` (`tao-macros/src/lib.rs`, lines 214 to 215 and 247 to 249), and nothing calls `RegisterNatives`. The CLI refuses a library whose dynamic symbol table lacks `Java_app_tauri_plugin_PluginManager_handlePluginResponse` (`android_studio_script.rs`, lines 179 to 184). So a Tauri-style host needs one library, loaded by its own name, whose exported symbols hold every native method its Kotlin declares, before the first Activity's `onCreate` returns.

**python-for-android.** `PythonUtil.getLibraries` lists `sqlite3`, `ffi`, `ssl.*`, SDL2's and SDL3's libraries, and the rest, each added only when a file of that name is in `nativeLibraryDir` (`addLibraryIfExists`, lines 19 to 37 and 59), then `libpython3.N.so` and `libmain.so`; `loadLibraries` loads each with `System.loadLibrary` (lines 70 to 100). Its SDL3 bootstrap's `PythonActivity` extends `SDLActivity` and overrides `loadLibraries()` with that list (`bootstraps/sdl3/.../PythonActivity.java`, lines 38 and 67 to 71). The host asks the folder what exists, rather than fixing the list. Extension modules are not among these; Python's importer opens them from the app's files (the 2026-11-13 findings).

**Chaquopy.** The app calls `Python.start(new AndroidPlatform(context))` (`Python.java`, line 44); `AndroidPlatform.loadNativeLibs` loads OpenSSL, SQLite, `libpython`, and `libchaquopy_java.so` (`AndroidPlatform.java`, lines 261 to 280). The app's own code names no library. When Chaquopy renamed its OpenSSL and SQLite libraries, it kept the old names as libraries of their own that link the new ones, "for compatibility with existing wheels" (`target/package-target.sh`, lines 97 to 105).

**Flutter.** `FlutterJNI.loadLibrary` loads `libflutter.so` (`FlutterJNI.java`, lines 144 to 169), from a task `FlutterLoader` runs on a background thread (`FlutterLoader.java`, lines 197 to 205 and 291). The app's compiled Dart, `libapp.so`, is never loaded from Java: the engine opens it, first by name, then by its full path in `nativeLibraryDir` "as a workaround for devices where that fails" (lines 544 to 557).

**React Native.** 0.76 merged most of its libraries into `libreactnative.so`. Code that called `SoLoader.loadLibrary("fabricjni")` kept working through a map from each old name to the merged one, with a call of each old library's `JNI_OnLoad` (`OpenSourceMergedSoMapping.kt`, lines 23 and 52), and the release post called it "a breaking change for both app and library developers": every app changed its `Application.onCreate` to pass that map to `SoLoader.init`.

**What one real host relies on.** Lota's orchestrator reported these facts from setdef/Lota at trunk 0a002644, which these findings could not read or verify. Its host's `getLibraries()` returns `{"SDL3", "openal", "fledgeruby", "fledgeext"}`, it has no `System.loadLibrary` of its own and no `build.gradle`, and its extension defines no JNI function: JNI goes from C++ up to Java through SDL's environment, and nothing opens `libfledgeext.so` by name. It relies on Fledge running its `extconf.rb` per ABI with mkmf's `$static` set and linking every extension's archive into the app's one library, so that its engine, a static archive, and its extension are in the same library; on `libSDL3.so` and `libopenal.so` beside it, loaded first; on the library linking `libfledgeruby.so`; and on its being loaded on the UI thread before Ruby starts. The name also appears in its notices and build tasks.

So across six frameworks, a host names libraries by fixed names it owns or was told, loads them on the UI thread or a thread of its choosing before the language runtime starts, and fails at once on a missing name unless, like python-for-android, it checks first. Two of them, Chaquopy and React Native, changed how they packaged their libraries and kept the old names working.

## What Android's loader and ART require

**Where a native method's implementation must be.** ART looks a `native` method up, on its first call, in the libraries `System.load` or `System.loadLibrary` loaded for the class loader of the method's class, and only those (`java_vm_ext.cc`, lines 319 to 345: "We only search libraries loaded by the appropriate ClassLoader"). It tries the short and the long JNI name with `dlsym` on each library's handle (lines 171 to 175 and 336 to 338). Failing that, the error asks "is the library loaded, e.g. System.loadLibrary?" (line 314). A library that native code opened with `dlopen` is not in that table, so its `Java_` functions are never found and its `JNI_OnLoad` never runs. The alternative is `RegisterNatives`, which JNI tips recommends calling from `JNI_OnLoad` and which needs only `JNI_OnLoad` exported. Two consequences for Fledge:

- An extension Ruby opens with `dlopen`, as a file, can hold no native method a Java class declares, unless something registers it. That is true of 10b0cfe2's files.
- It is already true of today's `libfledgeext.so`. Fledge links it with `-Wl,--exclude-libs,ALL` (`lib/fledge/mobile_extensions/android_library.rb`, lines 53 to 55), and lld makes every symbol an archive member defines unexported, `JNIEXPORT` or not (`lld/ELF/Driver.cpp`, lines 2299 to 2320: "all public symbols from the archive become private"). Every extension reaches that link as an archive, so no extension's `Java_` function or `JNI_OnLoad` is visible to ART today.

So no framework can keep its JNI in a gem's extension under either design. Every host read here keeps it in a library its own Java loads by name: `libSDL3.so`, a Tauri app's crate, `libchaquopy_java.so`, `libflutter.so`. In Fledge's terms, that is a shared library the framework's `extconf.rb` links, which Fledge already copies beside the extensions (`phone-projects.md`, "Linking extensions on Android", line 153), and which the host loads by name before Ruby starts. `examples/sdl_phone` works that way.

**`JNI_OnLoad` through a handle.** `dlsym` on a handle searches the library and then its `DT_NEEDED` libraries, breadth first (`linker.cpp`, lines 709 to 737 and 740 to 770; `do_dlsym`, line 2345), and ART finds `JNI_OnLoad` that way (`java_vm_ext.cc`, line 1120). Today's `libfledgeext.so` defines none it exports, needs `libfledgeruby.so`, which defines none, and in `sdl_phone` needs `libSDL3.so`, which does. So by reading, `System.loadLibrary("fledgeext")` calls SDL's `JNI_OnLoad` a second time, which SDL's code survives, since it registers the same methods again. A library of Fledge's that defines its own `JNI_OnLoad`, returning `JNI_VERSION_1_6`, would stop the search. This was not measured.

**One handle or two.** When `dlopen` is given a path, bionic opens and `fstat`s the file, and returns the library already loaded with the same device, inode, and file offset, "Already loaded under different name/path", unless the caller forces a new load (`linker.cpp`, lines 1102 to 1133 and 1190 to 1201). A symbolic link resolves to the file it names, so a library Java loaded from `nativeLibraryDir` and the same file opened by Ruby through a link in the app's files are one handle, and its constructors run once. ART keys its own table by the path it was asked for (`java_vm_ext.cc`, lines 964 and 1036 to 1047), so a `System.loadLibrary` of a library native code already opened adds ART's entry and calls `JNI_OnLoad` once, for ART's first sight of it, without running constructors again. The reverse order is the same handle too. ART opens with `RTLD_NOW` (`native_loader.cpp`, line 315); Ruby's `dln.c` opens with `RTLD_LAZY | RTLD_GLOBAL`.

**Resolving one library's symbols against another's.** Since API 23 a library's symbols resolve against the global group, the main executable, `LD_PRELOAD` libraries, and libraries linked `-z global`, then its own breadth-first `DT_NEEDED` closure (`android-changes-for-ndk-developers.md`, lines 62 to 91; `linker.cpp`, lines 1635 and 1728 to 1733). `RTLD_GLOBAL` adds a library to what `dlsym(RTLD_DEFAULT, ...)` searches (lines 795 to 812), not to what later libraries resolve against. So each extension built as a file has to name `libfledgeruby.so` in its `DT_NEEDED`, which 10b0cfe2's did, and an extension that calls functions another extension exports finds them only if it names that library too, where glibc's `RTLD_GLOBAL` would have found them on Linux. Linked into one library, as today, they meet at link time.

**Android 17.** For an app that targets API 37, "Safer Native DCL" extends to native libraries: "All native files loaded using System.load() must be marked as read-only. Otherwise, the system throws UnsatisfiedLinkError." The text names `System.load`, not `dlopen`. Libraries the installer extracts are not the app's to write, so the rule reaches only libraries kept in the app's own files, and is one more reason not to keep extensions there.

## What a gem's own build assumes

mkmf writes a `static:` goal and a `$(STATIC_LIB)` rule only when `$static` is not `nil`, and that archive holds the extension's own objects alone: `$(AR) ... $@ $(OBJS)` (`lib/mkmf.rb`, lines 2510, 2511, 2542, and 2693 to 2700). The shared object links `$(OBJS) ... $(LOCAL_LIBS) $(LIBS)` (`LINK_SO`, lines 2963 to 2970). So for an extension over an engine CMake built as a static archive and linked through `$LOCAL_LIBS` (ADR 027):

- **Linked in, today.** `make static` archives the extension alone; Fledge reads `LOCAL_LIBS` from the Makefile and links it with every extension's archive into `libfledgeext.so` (`phone-projects.md`, "Gems with extensions", step 4). Engine and extension share one library. Two extensions that link one engine archive share one copy of it.
- **A file, as in 10b0cfe2.** mkmf's default goal links the engine into the extension's own `.so`. Engine and extension still share one library. Two extensions that link one engine archive each carry a copy, with globals of their own, as they would on a desktop that links the engine statically.

An `extconf.rb` can branch on `$static`, which Fledge's shim sets before it runs in the linked build and which 10b0cfe2 left `nil`, as a desktop has it (`lib/fledge/mobile_extensions.rb`, lines 187 to 198). An `extconf.rb` that reads `$static` sees a desktop's value only as a file.

Lota reports relying on `$static` being set. Whether its `extconf.rb` reads `$static`, or only relies on the one library that results, was not established. Nor was whether its engine has more than one extension sharing an archive's state.

## What 10b0cfe2 got right and wrong

Right, by these findings: each extension is the shared object mkmf makes on a desktop, with its own `Init_` function and `$static` as a desktop has it; it names `libfledgeruby.so`, which bionic's resolution rules require; its LOAD segments are aligned for 16 KB pages; and its name, `libfledgeext.FEATURE.so`, is one the installer extracts. It lives where the installer puts native code, which Android 17's rule does not reach. The links at the desktop's paths, remade when an install moves the folder (`runtime/mobile/library_links.c`), give one handle with any load of the same file (bionic, above). That runtime half is still on trunk, inert while the build half is reverted. The commit also weighed the Ruby tree inside `fledge.zip` and gave reasons against it that still hold: one tree for both ABIs, and files Play's per-ABI splits and checks never see.

Wrong: it made a name hosts load conditional. `libfledgeext.so` was written only when something was still linked in (the `linked?` guard in `MobileProject::Android`), and its own unit test asserted the library's absence (`refute_path_exists ... libfledgeext.so`). It changed Fledge's `MainActivity` to match, and the host section of `phone-projects.md` with it, but left "A host that owns the main loop" telling hosts to name the library unconditionally, so the design document contradicted itself. It cited "ADR 094", which does not exist. And nothing it changed or ran builds an app with a host. Trunk's full CI never ran on it: its run stayed queued while later pushes overtook it, so no emulator in CI loaded an extension from a file on trunk either.

## How the seam gets tested

The smallest check that fails on 10b0cfe2 is a unit test. 10b0cfe2's own test built an Android project from extensions it described in memory, with no NDK, in milliseconds (its `android_project_with_library` helper), and asserted that `libfledgeext.so` was absent. A test that holds the libraries a host may name as part of the public interface asserts the opposite. It belongs beside the template paths and marks in `test/mobile_template_contract_test.rb`, whose comment already says a path that goes away "breaks every host that copied it". It would hold a frozen list, `fledgeruby` and `fledgeext`, and build a project for each case: only extensions built as files, only linked ones, and, if Fledge promises it, none. It asserts each promised `src/main/jniLibs/ABI/libfledgeext.so`, and that the AAR the project depends on carries `libfledgeruby.so`.

On an emulator, the cheapest check is an app with a host whose list is fixed. `examples/cmake_phone` is already built and run by CI's `mobile-apps-android` jobs on 4 KB and 16 KB pages, and it is a game engine's shape without SDL: a C++ library CMake builds and an extension over it. Give it an `android: host:` folder whose `MainActivity` is the template's, but with `System.loadLibrary("fledgeruby")` and `System.loadLibrary("fledgeext")` written in its static block unconditionally, as `SDLActivity` loads a fixed list. That costs one Java file of about 40 lines and no new job. It makes `cmake_phone` the first CI app that proves ADR 025's seam on an emulator. It stops `cmake_phone` testing the template's own `MainActivity` on Android, which `native_phone`, `rust_phone`, `ffi_phone`, and `mobile_app` still test. It is not SDL work: it builds nothing of SDL's and copies none of SDL's Java.

Building `sdl_phone` in CI would test SDL's own host, but it is SDL work: `sdl3/build.sh` downloads and builds SDL for four targets and copies SDL's Java into the host. It would add those builds to every Android job and tie Fledge's CI to SDL's releases.

## What only a run can settle

- That an Android app with extensions built as files, and a host that names `fledgeext` unconditionally, starts and prints its line on API 36 with 4 KB and 16 KB pages. The `cmake_phone` host above, run by `tasks/mobile_parity.rb android` as CONTRIBUTING.md's "Android on Linux" runs it, settles it once the change exists.
- Whether Lota's engine needs to be loaded on the UI thread, which files would change: under files, the engine loads with its extension, at `require`, on Ruby's thread. Only an app of Lota's can show it.
- Whether SDL's `JNI_OnLoad` runs twice in `sdl_phone` today, as the reading above says. Only an SDL app shows it, so these findings leave it read, not measured.

## Options

**A. Keep ADR 022: link every extension into `libfledgeext.so`.** Costs nothing now. Closes nothing: on Android, `$LOADED_FEATURES` keeps features where a desktop has files, `archdir` stays empty, ADR 080's stub files and ADR 088's `load.c` mapping stay, and an `extconf.rb` sees `$static` set. Under the maintainer's words of 2026-11-12 these are differences Android does not force. Hosts keep working, and the contract is still unwritten.

**B. 10b0cfe2 as it was.** Closes those differences for C and C++ extensions. Breaks every host that names `fledgeext` for an app with no linked extension, a game engine's app above all, and gives hosts nothing to rely on. Listed to be rejected.

**C. Files, with `libfledgeext.so` kept as a promised name, loaded by the runtime.** 10b0cfe2's build, with three changes. Every Android app that has a compiled extension carries `libfledgeext.so`, holding whatever is still linked (Rust's and Rakefiles' extensions), or nothing but an empty registration, with a `JNI_OnLoad` of its own so that ART's search stops there. The runtime opens it with `dlopen` from beside `libfledgeruby.so` before Ruby boots, as the ruby program already does (`runtime/mobile/android.c`, lines 304 to 321), so a host need not name it; a host that names it loads the same handle. And `public-interface.md` states the contract (see "Recommendation"). Costs: the 10b0cfe2 build back, an empty library per ABI in apps with only file extensions, a few lines in the runtime and its template, the unit test and the `cmake_phone` host, and ADRs 022, 080, and 088 rewritten for Android. Closes the same differences as B for C and C++ extensions; keeps the `fledgeext` name Lota was promised, so no host changes a line. It changes when an engine's code loads, from the host's start to the extension's `require`.

- **C1:** the library exists whenever the app has an extension Fledge compiles, which is today's condition. No new runtime artifact; a pure-Ruby app still has none, as today.
- **C2:** the library exists in every Android app. The runtime would carry an empty prebuilt `libfledgeext.so` for each ABI, outside the AAR, for Fledge to copy when it builds none, since an app with no extensions needs no NDK today. One more runtime file for the license audit to account for. A host can then name `fledgeext` for any app at all.

**D. Files, with `libfledgeext.so` as an umbrella the host loads.** As C, but `libfledgeext.so` names every extension file in its `DT_NEEDED`, so `System.loadLibrary("fledgeext")` loads them all on the host's thread before Ruby starts, and ART's search through its handle finds their exported `Java_` functions. Keeps Lota's "loaded on the UI thread" and would let a gem's extension hold a host's native methods. Costs C's, plus a `SONAME` per extension and an eager load of every extension at launch. It brings back a difference C closes: an extension that fails to load, which a desktop reports as a `LoadError` that `rescue` catches at `require`, stops the app before Ruby starts.

**E. Files only when Fledge writes the host.** Apps with `android: host:` keep everything linked. Hosts keep working with no contract change. But Ruby then behaves one way in a framework's app and another way in a plain one, and the frameworks are the apps that most need parity. Two mechanisms on Android, chosen by a key that is about startup, not Ruby.

**F. Files in the Ruby tree inside `fledge.zip`.** A choice of where files live, not of the host's seam: it removes `libfledgeext.so` for C extensions just as B does, so it needs C's promise anyway. 10b0cfe2's reasons against it stand, and Android 17's rule for libraries loaded from an app's files points the same way.

**G. Hosts ask Fledge what to load.** A call such as `FledgeRuby.loadLibraries()`, as React Native's apps pass `OpenSourceMergedSoMapping` to `SoLoader` and python-for-android's activities call `PythonUtil.loadLibraries`. Hides any future packaging. Costs a new frozen API, and every host changes once, which React Native called a breaking change. C's runtime load does the same work inside `FledgeRuby.startApp` and `runApp`, which every host already calls.

## Recommendation

**C, with C1 now and C2 if the orchestrator wants the name unconditional.** And whichever is chosen, the contract in `public-interface.md`, "Phones", in words such as these:

> On Android, a host may rely on these native libraries in each ABI of the app: `libfledgeruby.so`, from the runtime's AAR; `libfledgeext.so`, whenever the app has an extension Fledge compiles; and each shared library an `extconf.rb` links, by its own name. A host that loads any of them does so after the libraries its framework needs loaded first and before it starts Ruby, on any thread. It need not load `libfledgeext.so`: `FledgeRuby` loads it before Ruby boots. Fledge loads every other extension itself, when Ruby requires it, and names no other library a host may load. A native method a framework's Java declares lives in a shared library of the framework's own, which its `extconf.rb` links and its host loads by name; Fledge never loads an extension so that ART can find its methods.

The reasons, in Fledge's order of design precedence:

1. **A person never meets Ruby.** C and A both start every app. B fails at launch with SDL's alert, which is the failure this rule exists to prevent.
2. **Ruby code runs as under `ruby main.rb`.** C loads an extension from a file at `require`, records its path, gives `$static` a desktop's value, and raises `LoadError` where a desktop does. A and E keep differences the maintainer calls bugs, and D brings back one.
3. **Ruby's own conventions.** `dln` loads an extension from a file when it is required; C uses Ruby's own loader for it.
4. **Prior art.** No host read here loads a language runtime's extension modules itself. Python's tools load them from files when imported, and hosts load only fixed names of the framework's own. Chaquopy and React Native kept old names working when they repackaged; C keeps `fledgeext` the same way, with no host change, which also keeps the promise made to Lota's orchestrator that no release drops or renames it without notice. Every framework read here keeps its JNI in a library its own Java loads, which C's contract states.
5. **Ruby culture** yields to these.

C changes one thing Lota's host may feel: its engine would load when Ruby requires its extension, on Ruby's thread, not when its host loads `fledgeext` on the UI thread. If Lota's engine needs the UI thread, D is the fallback for that framework's needs, at D's parity cost. Lota would then change nothing in its host files, but would need a Fledge release of D's kind. That question goes to Lota's maintainers before C lands, with the `cmake_phone` run above as the evidence that the rest holds.
