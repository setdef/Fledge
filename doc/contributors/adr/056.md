# ADR 056: Move Fledge to Ruby 4.1 Now, and Release 1.0 Only After Ruby 4.1.0

## Context and Problem Statement

Fledge's runtimes carry Ruby 4.0. Ruby 4.1 is in preview; Ruby has released each new minor on 25 December. The Lota agent, which orchestrates work on Lota (a game framework that builds through Fledge), proposed that both projects require Ruby 4.1, previews included, after Fledge's spike built runtimes from 4.1 previews and ran apps on them (`doc/contributors/research/2026-11-09-ruby-4.1-spike.md`).

Once 1.0 ships, Fledge keeps every Ruby minor 1.0 has a runtime for until the next major, since dropping a Ruby takes a major (decisions.md, 2026-11-03). Ruby does not follow SemVer, so 4.1 is expected to break what ran on 4.0, and no Fledge release moves an app to it (ADR 055). Which Ruby minor should 1.0 carry, and when does Fledge move?

## Decision Drivers

- A 1.0 on Ruby 4.0 would oblige Fledge to keep 4.0's runtimes through all of 1.x.
- Lota moves together with Fledge.
- The spike's open problems must be fixed or explained before a release depends on 4.1.

## Considered Options

1. Move to Ruby 4.1 previews now, after one last release on Ruby 4.0.9, and hold 1.0 until Ruby 4.1.0 is released.
2. Release 1.0 on Ruby 4.0, and add 4.1 later in a minor release under the reserved asset names.
3. Carry Ruby 4.0 and 4.1 side by side before 1.0.

## Decision Outcome

Chosen: option 1, by the maintainer, once Fledge's orchestrating agent and the Lota agent both agreed (decisions.md, 2026-11-09):

> If the Fledge agent and Lota agent agree, I'd rather see Fledge and Lota ship 4.1-preview now, drop 4.0 now, and not ship Fledge 1.0.0 or Lota 1.0.0 until 4.1 releases.

> I am okay with a last-release on Ruby 4.0.9 first, as long as it doesn't meaningfully delay "now". Call it "now-ish" :)

Fledge's orchestrating agent agreed because a 1.0 on 4.0 would keep 4.0 through all of 1.x, on the condition that the spike's open problems are fixed or explained before the first release on 4.1. The Lota agent agreed on the condition that Lota's own move lands with that release.

The record weighs option 1 against option 2. It gives no reason for preferring option 1 over option 3, beyond the maintainer's words "drop 4.0 now".

Fledge's releases carry Ruby 4.1 preview runtimes in place of 4.0's from the first release whose CI passes on every job with them. Before 1.0, a release may carry a preview and move to a later preview or the final release in any 0.x release. 1.0 waits for Ruby 4.1.0, as well as for the maintainer's testing that his accounts block.

Confidence: medium. The previews ran on every platform the spike reached, with no unjustified parity difference for a lone `main.rb` on Linux and macOS. The spike found problems, and did not run some platforms; the spike note lists both (`doc/contributors/research/2026-11-09-ruby-4.1-spike.md`, "Problems found" and "Not verified"), and the first release on 4.1 waits until each is fixed or explained.

### Consequences

- Good, because 1.x starts on the newest Ruby minor and carries one, and the reserved names for a second minor stay unused until a 1.x release adds 4.2 or later.
- Good, because Lota and Fledge move once, together.
- Bad, because a developer must run Ruby 4.1 to build (ADR 055), so one on 4.0 is refused, and `fledge.gemspec`'s `required_ruby_version` follows.
- Bad, because a preview's runtime may change between 0.x releases, and a preview's folders are named by its ABI (`4.1.0+5`), not its version.
- Bad, because the move needs new license audit entries (BLAKE3, `digest/crc32`, rdoc 8.1.0), a fifth scripted edit of Ruby's configure for iOS, `--with-dump-ast` for cross builds, and a 4.1 Ruby to run each cross build's install.
- Bad, because RubyInstaller publishes 4.1 only as a rolling head snapshot before 4.1.0, so a Windows pin holds only as long as that snapshot is served.
- Bad, because 1.0's date now depends on Ruby's release, which Fledge does not control.
- Neutral, because a person's `RUBY_MN_THREADS` never takes effect in a built app, since the launcher restores `RUBY*` variables only after Ruby has read its options (ADR 040). That is what Lota wants.

### Confirmation

The first release on 4.1 is tagged only when CI passes on every job with the 4.1 runtimes (ADR 053), the parity check included, with no new unjustified difference (`tasks/parity.rb`). `runtime/sources.yml` names the pinned Ruby of each platform.

## More Information

The spike note holds the inputs, the runs, and each open problem. `doc/contributors/design/releases.md` says what a release may do with Ruby minors, before 1.0 and after. ADR 066 says how Windows, for which RubyInstaller builds no preview, follows Ruby 4.1's releases until 4.1.0.
