# ADR 016: Signing With the Developer's Own Identity

## Status
Accepted (requested). Section 6 added 2026-11-07. Sections 3 and 4 amended 2026-11-08 by ADR 033, which notarizes (`--notarize`) and signs a Windows app through the developer's own command (`--sign-command`), both waiting for the maintainer's credentials to prove them. Agents wrote this ADR and may change it (AGENTS.md, Questions). It applies the maintainer's decision 17 in `doc/contributors/decisions.md` ("Ideally, fledge developers should have the option to make it so Windows/macOS don't block the use of the app. But not every app dev will have the done the required ceremony with Microsoft and/or Apple.") and the words of 2026-10-28 on an Apple Developer account (wait until the last responsible moment), and carries out Plan 002's story "Signing and notarization" as far as it goes without one. Notarization, and Azure Trusted Signing, waited on accounts; ADR 033 builds both for the maintainer to prove with his own.

## Date
2026-11-01

## Context

macOS's Gatekeeper refuses to open an app downloaded from the internet unless a Developer ID signature that Apple has notarized vouches for it; a person can still open it, through System Settings. Windows' SmartScreen warns about a program downloaded from the internet that no certificate it trusts has signed, and Smart App Control on Windows 11 checks every program and library a process loads. Every app Fledge builds runs where it lands (ADR 008 signs a macOS bundle ad hoc, which Apple Silicon needs to run it at all), but none is signed by anyone those checks trust.

A signature seals what it covers, so signing has to come after Fledge has written everything into an app (the program's resources on Windows, a bundle's `Info.plist` and seal on macOS; ADR 008) and before the archive and the installers, which carry the signed files, and which are signed themselves.

The prior art agrees on the shape:

- **Briefcase** signs with `briefcase package --identity`: on macOS a code signing identity from the keychain, every Mach-O file inside out, with the hardened runtime (but for the ad hoc identity), then the app, then notarization, and grants every app two entitlements, `com.apple.security.cs.allow-unsigned-executable-memory` and `com.apple.security.cs.disable-library-validation` (`src/briefcase/platforms/macOS/__init__.py`, lines 463 to 467, beeware/briefcase at 0bdaaf5); on Windows the SHA-1 thumbprint of a certificate in the certificate store, with signtool, SHA-256, and a timestamp from `http://timestamp.digicert.com` by default (`src/briefcase/platforms/windows/__init__.py`, lines 557 to 616).
- **Tauri's bundler** takes `signingIdentity` (or `APPLE_SIGNING_IDENTITY`) on macOS, signs the app's binaries and then the bundle with the hardened runtime, and signs the disk image; on Windows `certificateThumbprint`, `digestAlgorithm`, and `timestampUrl` for signtool, or a `signCommand` of the developer's own, which is how it reaches Azure Trusted Signing; it signs the NSIS installer and the uninstaller inside it.
- **NSIS** 3.08 and later sign the uninstaller they write into an installer, and the installer itself, through `!uninstfinalize` and `!finalize`, which run a command on each file as makensis writes it.
- **Apple** asks of notarized software: every executable signed with a Developer ID, with the hardened runtime, with a secure timestamp (Apple's documentation, "Resolving common notarization issues"). Under the hardened runtime, `com.apple.security.cs.allow-unsigned-executable-memory` "indicates whether the app may create writable and executable memory without using the MAP_JIT flag", and `com.apple.security.cs.allow-jit` covers memory made with MAP_JIT.
- **Ruby's YJIT** reserves its code region with `mmap(PROT_NONE, MAP_PRIVATE | MAP_ANONYMOUS)` and makes it executable with `mprotect(PROT_READ | PROT_EXEC)`, with no MAP_JIT (`jit.c`, `rb_jit_reserve_addr_space` and `rb_jit_mark_executable`, at Ruby 4.0.9). Tebako's signing specification (`docs/spec/31-macos-signing-notarization.md`, tamatebako/tebako at d65a127) gives YJIT `allow-jit` "for MAP_JIT on arm64", which Ruby 4.0.9's source does not bear out.

## Decision

### 1. `fledge build --sign IDENTITY`

One option, as Briefcase's `--identity`, whose value each system's own signer takes as it is: on macOS a code signing identity in the developer's keychain, by name or SHA-1 hash, as `codesign --sign` takes it, such as `"Developer ID Application: Example, Inc. (ABCDE12345)"`; on Windows the SHA-1 thumbprint of a code signing certificate in the certificate store, as `signtool sign /sha1` takes it, which `(Get-ChildItem Cert:\CurrentUser\My -CodeSigningCert).Thumbprint` shows. A Linux build with `--sign` fails, saying a Linux app carries no signature for its system to check; a phone's build with it is a usage error, since Xcode and Gradle sign a phone's app. Without it, nothing changes: unsigned builds stay the default (decision 17).

The identity is the developer's own and stays on their computer: Fledge reads no certificate, key, or password, and keeps none in `fledge.yml`, which is committed.

### 2. macOS: codesign, inside out, with the hardened runtime

`Fledge::MacSigning` signs, with `codesign --force --sign IDENTITY --options runtime --timestamp --entitlements ENTITLEMENTS`:

1. every Mach-O program and library of a console app's folder, or of a windowed app's `Contents/Resources` (the launcher, `bin/ruby`, Ruby's extensions, the app's gems' compiled files), found by their first bytes (`Fledge::Binary.format_of`), leaving out object files (`MH_OBJECT`), which a gem's build can leave beside its extension and which nothing runs or loads, and symbolic links;
2. a windowed app's bundle, in place of the ad hoc signature ADR 008 gives it, as its identifier, which seals the rest;
3. its disk image, after `hdiutil` writes it (`codesign --sign IDENTITY --timestamp`), as notarization asks of an image it staples a ticket to.

The entitlements (`lib/fledge/templates/macos/entitlements.plist`) are Briefcase's two, for the same reasons a Python app has. `com.apple.security.cs.allow-unsigned-executable-memory` is what Apple's documentation names for executable memory made without MAP_JIT, as YJIT makes it, and an app may enable YJIT as Rails does (ADR 003). CI found YJIT writing code under the hardened runtime with no entitlement at all when the identity was self-signed, but Apple documents the entitlement for this memory and checks a Developer ID more strictly, so it stays until a Developer ID run shows it unneeded (ADR 033, section 5). `com.apple.security.cs.disable-library-validation` lets Ruby load a library its app did not sign: Fledge signs every library in the app, but a gem may load one from elsewhere (FFI, a plug-in), and without it an ad hoc signature, which has no Team ID, could load none of Ruby's extensions (macOS's loader says "mapping process and mapped file (non-platform) have different Team IDs").

The ad hoc identity, `--sign -`, signs the same way but for the timestamp, which needs a certificate to stamp. Briefcase signs ad hoc without the hardened runtime; Fledge keeps it, so that any Mac, with no certificate, proves the same signing a Developer ID gets (`test/built_app_test.rb` with `FLEDGE_TEST_SIGN_IDENTITY=-`). Gatekeeper trusts it no more than the ad hoc signature Fledge gives every bundle.

### 3. Windows: signtool, with SHA-256 and a timestamp

`Fledge::WindowsSigning` signs every PE file of the app's folder (`.exe`, `.dll`, and Ruby's `.so` extensions, found by their first bytes) after Fledge has written the program's version information and icon (ADR 008, ADR 010), with `signtool sign /sha1 THUMBPRINT /fd sha256 /tr http://timestamp.digicert.com /td sha256`, Briefcase's defaults: SHA-256, and a timestamp from a server that stamps any certificate's signature, so the signature stays valid after the certificate expires. It signs Ruby's own DLLs too, which RubyInstaller ships unsigned, because Smart App Control checks every library a process loads. A windowed app's NSIS installer runs the same command through `!uninstfinalize` and `!finalize`, so makensis signs the uninstaller before it is packed into the installer and then the installer, and fails unless signtool exits 0.

signtool comes with the Windows SDK, which puts it on no `PATH`: Fledge takes the first on `PATH`, or else the newest the SDK installed for the computer's architecture under `%ProgramFiles(x86)%\Windows Kits\10\bin\VERSION\x64` (or `arm64`), and names the SDK when there is none.

Azure Trusted Signing (now Artifact Signing), which signs through signtool with Microsoft's `/dlib` plug-in and an account's metadata file, and which Tauri reaches through a `signCommand`, is reached the same way: `--sign-command` runs the developer's own command for every file this section signs (ADR 033, section 4). A thumbprint covers certificates in the store, hardware tokens included.

### 4. Notarization (amended 2026-11-08)

`--notarize PROFILE` notarizes what this ADR signs, with notarytool and a keychain profile, and staples the ticket to the disk image and the bundle before the archive is packed (ADR 033, sections 1 to 3). Everything notarization asks of the code, the hardened runtime, a secure timestamp, every Mach-O file signed, and a signed disk image, is what section 2 does. It waits for the maintainer's Apple Developer Program enrollment to be proven: CI notarizes against a stand-in for Apple's service (ADR 033, section 6).

### 5. What CI proves without accounts

No CI runner has a certificate macOS or Windows trusts, so CI makes one: a self-signed code signing certificate, made fresh in each run, in a temporary keychain on macOS (trusted for code signing in the runner's system keychain, as `security add-trusted-cert` does) and in the current user's store on Windows (and its root store, so signtool can verify the chain). The Build jobs build `examples/hello` and `examples/windowed_app` with `--sign`, and the macOS and Windows Test jobs run `test/built_app_test.rb`'s signed build with it (`FLEDGE_TEST_SIGN_IDENTITY`; on any Mac, `-` runs it ad hoc). Delivery, on fresh runners, verifies: on macOS `codesign --verify --strict` on every Mach-O file, `--deep` on the bundle, the hardened runtime and a timestamp on each, the entitlement, the signed disk image, the apps running, and YJIT writing code; on Windows, `signtool verify /pa` on every PE file, the setup program, and the uninstaller it installed, after trusting the test certificate, and refusing them before. Unsigned builds still pass every Delivery job, as before.

### 6. codesign runs again when Apple's timestamp server does not answer (amended 2026-11-07)

`--timestamp` asks Apple's timestamp server for a secure timestamp over each signature, so every signed build depends on that server. CI's signed build of `examples/windowed_app` once failed on it and passed when run again: run 42126058497, attempt 1, job Build (arm64-darwin), where `codesign` stopped on Ruby's `enc/windows_1254.bundle` with "A timestamp was expected but was not found." That is the description of `errSecTimestampMissing` (-67882) in `<Security/SecBase.h>` (line 693 of the macOS 27.0 SDK), whose line 696 describes `errSecTimestampServiceNotAvailable` (-67885) as "The timestamp service is not available."

The prior art signs again on those words, and only on them:

- **VS Code** retries `codesign` up to five times, waiting 10 seconds and doubling, when its message holds "A timestamp was expected but was not found." or "The timestamp service is not available.", and notes that signing again is safe because every file is signed with `--force` (`build/darwin/sign.ts`, lines 44 to 75, at microsoft/vscode b4bd9bd). It also retries "The specified item could not be found in the keychain.", a short-lived keychain problem on its own build agents.
- **Defold** signs again up to five times, waiting 5 seconds and doubling, when the output holds "The timestamp service is not available." (`build_tools/codesigning.py`, lines 146 to 160, at defold/defold d4ca5d4).
- **Datadog's agent** runs its `codesign` calls through a generic retry script, "Sometimes the timestamp service is not available, so we retry" (`omnibus/config/software/datadog-agent-finalize.rb`, lines 260 and 261, at DataDog/datadog-agent 6c2b960).

`Fledge::MacSigning` runs every `codesign` it runs (each slice of a folder's files, a bundle's helpers and the bundle, and the disk image) through one method that, when `codesign` fails and its output holds either of the two descriptions (`MacSigning::TIMESTAMP_FAILURES`), waits and runs the same command again: after 5, 10, 20, and 40 seconds (`MacSigning::WAITS`), five runs in all, as Defold does. Any other failure, or a fifth one of these, fails the build with codesign's own words, as before. Every command has `--force`, so a run again replaces whatever the failed run signed. The keychain message VS Code retries is not retried: VS Code's agents sign with one known identity, while on a developer's Mac a keychain that cannot give up the identity named with `--sign` is the developer's to fix, as is an identity it lacks (`codesign --sign Nobody` says "Nobody: no identity found", on macOS 27.0.1), and waiting would only delay saying so. Matching the text rather than the exit status, which is 1 for every failure, keeps a real error from costing 75 seconds, as `Fledge::Dmg` does for hdiutil (ADR 010, section 3).

The waits are longer than a download's (ADR 014, section 6) because a signing build is a release, not a developer's every build, and a timestamp outage that cleared within seconds would not have failed CI's run. They are fixed, so that a test can name them. The failure cannot be provoked on demand, so `test/mac_signing_test.rb` puts a `codesign` first on `PATH` that fails with each message as many times as a test asks and then runs the real `/usr/bin/codesign`, and the real `Fledge::Command`, `Fledge::Dmg`, and hdiutil run around it.

Not covered: signtool's timestamp from DigiCert on Windows (section 3), which no run has seen fail and which makensis also runs, through `!finalize`, where Fledge cannot run it again; and notarytool, which ADR 033, section 3, does not run again.

## Consequences

- A developer with an identity signs with one option; one without changes nothing.
- A signed macOS app runs under the hardened runtime, which an unsigned one does not, with Briefcase's two entitlements. An app that needs others (the camera, the microphone) needs an option for the developer's own entitlements, which waits for one who needs it.
- Notarization, a real Developer ID's trust chain and Gatekeeper's verdict, and Azure Artifact Signing through `--sign-command` are built (ADR 033) and not proven, and wait on the maintainer's accounts (`doc/contributors/signing-test.md`).
- The README tells people who receive an unsigned app how to open it on each system.
