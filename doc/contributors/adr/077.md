# ADR 077: Android's Ruby has YJIT, off until the app enables it, as on a desktop

## Context and Problem Statement

Fledge built a phone's Ruby with no JIT, so `RubyVM::YJIT` was not defined there, where every desktop runtime has it. On iOS that follows from the platform: an app gets no memory it may write code into and run, save a browser's web content extension (BrowserEngineKit, "Protecting code compiled just in time"). On Android it followed only from Ruby's `configure.ac` (lines 3896 to 3910 at 4.1.0-preview1), which leaves Android out of the JITs it builds by default, for cross builds, with no reason given (ruby/ruby 3703a81491), and which `--enable-yjit` overrides. Android grants apps such memory: AOSP's sepolicy reads "WebView and other application-specific JIT compilers / allow appdomain self:process execmem" (`private/app.te`, lines 188 to 189), and Google Play's Device and Network Abuse policy exempts code that "runs in a virtual machine or an interpreter" from its rule against downloaded code (read 2026-11-12). The maintainer, 2026-11-12 (`decisions.md`): a difference is accepted only where a platform truly forbids it. Does Android's Ruby build YJIT, and how?

## Decision Drivers

- The app's code runs as under `ruby main.rb` (AGENTS.md, Design precedence 2): `RubyVM::YJIT` is there, off until the app enables it, as on a desktop.
- What a platform forbids is shown from its own sources.
- A cross build of Ruby never boots the Ruby it builds, so what it needs at boot must be checked when building.

## Considered Options

1. Configure Android's Ruby with `--enable-yjit`, compiled by `rustc` for each target and linked with the NDK's `ld.lld` and `llvm-objcopy`, with the build machine's miniruby configured with the same JITs.
2. Keep Android's Ruby without a JIT, and justify the difference.
3. Build YJIT with Cargo (`--enable-yjit=dev` or `=stats`).
4. YJIT and ZJIT together.

## Decision Outcome

Chosen: option 1, because nothing forbids a JIT on Android, and the only reason for leaving it out was a cross build's default. The build machine's miniruby must have the target's JITs: it writes the builtin binary, which holds only the builtins it loaded (`template/builtin_binary.rbbin.tmpl`), and a Ruby built with YJIT stops at boot without `yjit.rb`'s (`builtin.c`, line 68: "[BUG] builtin_lookup: can not find yjit"). So the build compares the two Makefiles' `YJIT_SUPPORT` and `ZJIT_SUPPORT` and fails when they differ. How: `doc/contributors/design/phone-runtimes.md`, "Building Ruby for a phone" and "The builtin binary".

Option 2 justifies a difference no platform requires. Option 3 needs Cargo, where a release build needs only `rustc`. Option 4 waits: ZJIT is experimental, and the desktops' ZJIT is a difference of its own that the parity probe does not yet measure.

Confidence: high. On both API 36 x86_64 emulators, with 4 KB and 16 KB pages, an app that enables YJIT reports machine code compiled and run, from its debug APK and its release bundle, the parity check finds no unjustified difference, and ruby/spec passes. The arm64-v8a build is linked and audited, and runs on no emulator.

### Consequences

- Good, because an Android app's `RubyVM::YJIT` is a desktop's, and an app that enables it runs compiled code.
- Bad, because building the Android runtime needs Rust with Android's two targets, and `libfledgeruby.so` carries Rust's standard library, under MIT or Apache-2.0, a notice only.
- Bad, because the library is larger, by an amount not yet measured.
- Neutral: iOS's Ruby has no JIT, which `Parity::MOBILE_JUSTIFIED` justifies from Apple's documentation.

### Confirmation

`test/mobile_runtime_test.rb` holds Android's JIT options and the build machine's miniruby to the target's JITs; the mobile parity check compares `RubyVM::YJIT` on both phones; MobileHello on Android enables YJIT and must report machine code.
