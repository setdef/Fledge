# Desktop Runtimes

This document says what a desktop runtime holds and how `rake runtime` (`tasks/runtime_builder.rb`) builds one: the layout on each platform, where each input comes from and how it is pinned, what is kept and what is pruned, Fledge's RubyGems defaults, the `tools/` folder, what compiling a gem takes from a runtime, the platform names, and the release assets. ADR 093 decides that Fledge's CI prebuilds the runtimes, and ADR 035 where their Ruby comes from. The license audit every runtime passes is `doc/contributors/design/license-audit.md`; the phones' runtimes are `doc/contributors/design/phone-runtimes.md`. For app developers, `doc/runtimes.md` says which runtime an app gets.

## What a runtime is

A runtime is a folder: Fledge's launcher at its top, a relocatable CRuby beside it in Ruby's own layout, the tools `fledge build` runs, and `notices/`. `fledge build` unpacks it, copies the app in, and archives the result. Nothing in a runtime records where it was built: on macOS and Linux, Ruby is configured `--enable-load-relative` and finds its library from the program that holds libruby; on Windows, Ruby finds its prefix from its DLL's own path.

Every runtime is a `.tar.gz` with one top folder, named as the asset is without its extension (`tasks/release_archive.rb`), on Windows too: only Fledge reads it.

The build runs in this order (`RuntimeBuilder#call`):

1. the platform's recipe builds the folder (`tasks/runtime_builder/`);
2. `RuntimeBuilder::RubyDescription.write` copies the description of the folder's Ruby into `RUBY_DESCRIPTION` ("The Ruby's description");
3. `LicenseAudit::SourceBundle#copy_into` writes `notices/sources/`;
4. `RuntimeBuilder#license` audits the folder and writes `notices/NOTICES.txt` and `notices/sbom.spdx.json`, or raises and archives nothing;
5. the folder is archived, and the SBOM, NOTICES, and source bundle are written beside it.

A recipe builds only on the computers it names (`Recipe#hosts`): each Unix runtime on its own platform, since its launcher links that platform's libruby; the Windows runtimes on any computer llvm-mingw is pinned for.

## Layout on macOS and Linux

| Path | What it is |
|---|---|
| `launcher` | Fledge's launcher, `runtime/launcher/unix.c` and the rest, linked with the static libruby. `fledge build` renames it for the app. |
| `bin/ruby` | Ruby's own `main.c` (`runtime/launcher/ruby_main.c`), linked with the same libruby and the same link line, so `RbConfig.ruby` and `Gem.ruby` run. Given the app's own program, it hands it back to the app's launcher (`doc/contributors/design/launcher.md`, "bin/ruby and restarts"). |
| `bin/*` | The default and bundled gems' executables, as rv-ruby installs them. |
| `include/ruby-X.Y.0/` | Ruby's C headers, which `require "mkmf"` reads at run time ("What a runtime keeps"). |
| `lib/libruby*-static.a` | Ruby's static library, stripped of its debug information, which `mkmf` links the test program of every `have_func`, `have_library`, and `try_link` against ("What a runtime keeps"). |
| `lib/ruby/` | The standard library, `gems/X.Y.0` with every default and bundled gem, `site_ruby`, and `vendor_ruby`, as Ruby lays them out. |
| `lib/libcrypt.so.2` | libxcrypt, glibc Linux only ("libxcrypt on glibc Linux"). |
| `libexec/cert.pem` | Mozilla's CA bundle, which Ruby's `openssl.rb` points OpenSSL at unless `SSL_CERT_FILE` names others. |
| `tools/appimage-runtime` | Linux only, glibc and musl ("The tools folder"). |
| `RUBY_DESCRIPTION` | The description Ruby compiled into `bin/ruby`, which `fledge build` reads and no app holds ("The Ruby's description"). |
| `notices/` | `NOTICES.txt`, `sbom.spdx.json`, and, on Linux, `sources/`. |

`X.Y.0` is the pinned Ruby's ABI folder.

How each program is linked (`tasks/runtime_builder/darwin.rb`, `linux.rb`, `musl.rb`):

- **macOS:** libruby linked whole with `-force_load`, `-mmacosx-version-min` set to the macOS floor, stripped with `strip -x`, and signed ad hoc, since Apple Silicon runs only signed code. The build fails if the program links anything outside `/usr/lib` and `/System/Library`.
- **glibc Linux:** libruby linked whole and its symbols exported (`-rdynamic`), so extensions find them; libgcc's unwinder taken statically (`-static-libgcc`); libxcrypt linked dynamically. Each program has an RPATH, never a RUNPATH, which `LD_LIBRARY_PATH` would override: `$ORIGIN/lib` for the launcher, `$ORIGIN/../lib` for `bin/ruby`. The build fails if a program needs a library beyond glibc's and libcrypt. Extensions are stripped of debug sections, and `patchelf` removes the RUNPATHs rv-ruby's build machine left in some (`zlib.so` names a Linuxbrew folder).
- **musl Linux:** as glibc Linux, but with no libxcrypt and no RPATH; the programs may need only musl's C library.

Each program builds with warnings as errors (`RuntimeBuilder::WARNINGS`) and under a static analyzer: clang's on macOS and Windows, gcc's `-fanalyzer` on Linux.

## Layout on Windows

| Path | What it is |
|---|---|
| `launcher.exe` | The console launcher (`runtime/launcher/windows.c`), which loads Ruby's DLL when it runs. |
| `launcherw.exe` | The same launcher built as a GUI program, for windowed apps (`doc/contributors/design/desktop-apps.md`, "Windows"). |
| `ruby\` | RubyInstaller's tree, its shape unchanged: `bin\` with Ruby's DLL (`x64-ucrt-ruby410.dll` or `aarch64-ucrt-ruby410.dll` for Ruby 4.1), `ruby.exe`, `rubyw.exe`, the gems' wrappers, and `ruby_builtin_dlls\`; `include\`; `lib\ruby\`. `ruby.exe` and `rubyw.exe` are Fledge's, Ruby's `main.c` built against that DLL in their place (`RuntimeBuilder::Windows#compile_ruby`; `launcher.md`, "bin/ruby and restarts"). Fledge adds two DLLs RubyInstaller leaves out (`windows-dlls` in `runtime/sources.yml`, `RuntimeBuilder::Windows#add_missing_dlls`): `libz-1.dll` in Ruby's architecture folder under `lib\ruby\`, named in `zlib.so`'s assembly manifest, and, on x64, `libgcc_s_seh-1.dll` in `ruby_builtin_dlls\`. |
| `tools\nsis\`, `tools\rcedit.exe`, `tools\llvm-readobj.exe` | What `fledge build` runs ("The tools folder"). |
| `RUBY_DESCRIPTION` | The description Ruby compiled into its DLL, which `fledge build` reads and no app holds ("The Ruby's description"). |
| `notices\` | `NOTICES.txt`, `sbom.spdx.json`, and `sources\`. |

The launchers may import only `KERNEL32.dll` and the universal C runtime's `api-ms-win-crt-*.dll`, and the windowed one `USER32.dll` for its message box. The build reads each one's PE Subsystem and imports with llvm-mingw's `llvm-readobj` and fails otherwise.

RubyInstaller's tree stays whole because Ruby and its DLLs depend on its shape. Ruby takes its prefix from its DLL's own path: a DLL in `PREFIX\bin` makes `PREFIX` the prefix (`ruby.c`, `runtime_libruby_path` and `ruby_init_loadpath`, at Ruby 4.1.0-preview1). The DLL's own dependencies load through the private assembly its embedded manifest names (`ruby_builtin_dlls`), and each extension's through its `*.so-assembly.manifest`, so a DLL moved out of the tree breaks what loads it. Kept whole, the tree works as RubyInstaller ships it, and a new Ruby pin unpacks into the same place. The app's program stays at the top of its folder and reaches the tree by loading Ruby's DLL when it runs (`doc/contributors/design/launcher.md`, "Windows").

Two other layouts worked when tried, and were worse for the person who opens the folder: the launcher inside `ruby\bin`, beside the DLL, and a side-by-side manifest that reshapes the tree (`doc/contributors/research/2026-11-10-findings-from-the-adrs.md`, "The Windows launcher spike: importing Ruby's DLL, and the layouts tried"). One layout on every system, a Ruby built statically for Windows or the Unix runtimes moved into `ruby/` with a shared libruby, would be a large change for nothing an app can observe: Ruby and RubyGems answer every question about the layout (`RbConfig::CONFIG["prefix"]`, `RbConfig.ruby`, `Gem.dir`, and `__dir__`), so app code needs no branch for it, which is what the maintainer asked of a layout that differs (`decisions.md`, 2026-10-26, decision 23). The cost is that the assembly, the license audit, and signing each know two layouts.

How the launcher loads Ruby's DLL, its manifest, and the variables it hides are `doc/contributors/design/launcher.md`.

## The Windows launcher, cross-compiled with llvm-mingw

The Windows launcher needs only Ruby's headers to build, never a library to link, since it loads Ruby's DLL at run time. So it cross-compiles with llvm-mingw's UCRT toolchain, pinned by version and SHA-256 in `runtime/sources.yml` for each computer that may build a Windows runtime (x86_64 and aarch64 Linux, Apple Silicon macOS). CI builds both Windows runtimes on Linux.

- **UCRT, not msvcrt.** The launcher must share RubyInstaller's C runtime, so that removing a variable from its environment removes it from the one Ruby reads. Ubuntu's own mingw-w64 targets the older msvcrt.
- **Pinned, not MSYS2's.** MSYS2's gcc on a Windows runner rolls and cannot be pinned.
- **One toolchain, two targets.** The triple is `x86_64-w64-mingw32` for `x64-mingw-ucrt` and `aarch64-w64-mingw32` for `aarch64-mingw-ucrt` (`RuntimeBuilder::Windows::TARGETS`).
- **Resources.** llvm-mingw's `windres` compiles `runtime/launcher/windows.rc`, which embeds the manifest (`windows.manifest`), into each launcher.
- **The audit's readers.** The Windows recipe's license audit reads the runtime with the same llvm-mingw's `llvm-objdump` and `llvm-readobj` (`doc/contributors/design/license-audit.md`, "Which tools read compiled files").

## Sources and pins

Every input that comes from outside the repository is in `runtime/sources.yml`, pinned by version and SHA-256, and `DownloadCache#fetch` (`tasks/download_cache.rb`) refuses a download whose SHA-256 differs. The file's comments say what each pin is and why; its top-level keys group the pins by what they feed: each platform's Ruby (`ruby`, `musl-ruby`, `mobile`), the Windows launcher's compiler (`llvm-mingw`), the libraries a runtime adds (`libxcrypt`, `gmp`, `windows-dlls`), the tools of a runtime's `tools/` folder (`rcedit`, `llvm-readobj`, `nsis`, `appimage-runtime`, `libfuse`), and what only CI's replaceability jobs read (`replaceability`). The phones' pins are described in `doc/contributors/design/phone-runtimes.md`.

`test/runtime_builder_test.rb` checks the pins' shape. CI's tools that build runtimes are pinned beside them: the Ubuntu packages and Xcode version in `ci.yml`'s Runtime job, and the Alpine image and packages for musl ("musl Linux's Ruby, built in Alpine").

The Ruby versions pinned today: on macOS and Linux, `ruby`, `mobile.ruby`, and `musl-ruby.ruby` name the same release, 4.1.0-preview1, and the musl build runs in the Alpine Ruby image of that version. On Windows, `ruby` names RubyInstaller's head build of Ruby's main branch instead ("Windows' Ruby until Ruby 4.1.0", below). A move to a new Ruby moves all of them together.

`runtime/upstreams.yml` says where each pin is released, so that a newer release upstream is found without anyone looking ("Keeping the pins current", below).

## Keeping the pins current

A pin holds a runtime to one release of each input. When OpenSSL, zlib, or Ruby itself fixes a security hole, no app built with Fledge gets the fix until the pin moves and Fledge releases, and nothing in a pin says upstream has moved. So the candidate for 1.0.0 has automation that moves the pins itself: when an input has a newer release, Fledge moves the pin, proves the new runtimes in CI, and releases, and nobody is told unless that path fails (decisions.md, 2026-11-22; `releases.md`, "Versions"). It is built in four steps, and only the first exists yet:

1. **The watch**, `tasks/pin_watch.rb`, finds what is newer. Built.
2. **The move** rewrites the pin and everything that names its version. Not built.
3. **The proof**: a scheduled workflow puts the move on a branch and has CI run on it. Not built.
4. **The release**: the release commit, the pin commit, the tag, and `release.yml`, run by the workflow. Not built.

Until steps 2 to 4 exist, the candidate's requirement is not met, and the watch's report is for an agent to act on by hand.

### The watch

`runtime/upstreams.yml` names, for each watched input, the components of `runtime/sources.yml` it is the upstream of, the key that holds the version, and where its releases are listed: a GitHub repository, with a pattern for its tags, or a page with a pattern for the versions on it. Components that are not watched are listed there with the reason, such as GMP and the two DLLs Windows adds, which move with RubyInstaller's build and not on their own, and libfuse, which moves with AppImage's runtime. `test/pin_watch_test.rb` fails when a component of `runtime/sources.yml` is in neither list, so a new pin is watched or says why not.

`ruby tasks/pin_watch.rb REPORT` asks each upstream once, compares its newest release with the pin, prints one line for each, writes them to REPORT as JSON, and exits 0 when every pin is current, 3 when one has a newer release, and 1 when an upstream could not be read or listed nothing its pattern takes. It reads public listings and needs no token, though GitHub gives an anonymous caller 60 requests an hour and the workflow passes its own. Releases GitHub marks as drafts or prereleases are left out, and so is any version with a letter in it, as `4.1.0-preview2` or `9.6.0-alpha05`, unless the pin is a prerelease too: while Ruby's pin is 4.1.0-preview1, preview2 is its next version.

An input with `line` stays in a line: OpenSSL in 3.6, the line RubyInstaller's Ruby links, and Ruby in 4.1. A newer release in the line is the pin's next version, and one beyond it is reported as `beyond` and not taken, since a new line of OpenSSL or a new Ruby minor is planned work (`releases.md`, "Ruby minors and runtimes"), which AGENTS.md has arrive on purpose. Every other input takes its newest release, and CI is what proves it fits.

Run by hand on 2026-11-22 against the real upstreams, it found ten pins behind: rv-ruby (20261023, newest 20261119), llvm-mingw (20261020, 20261117), llvm-readobj (23.1.4, 23.1.6), libyaml (0.2.5, 0.2.6), libffi (3.5.2, 3.8.1), zlib (1.3.2, 1.4), the CA certificates (2026-03-19, 2026-11-05), Gradle (9.8.2, 9.9.2), the Android Gradle plugin (9.4.1, 9.5.2), and XcodeGen (2.46.0, 2.48.0); OpenSSL 3.6.5 is the newest of its line, with 4.1.0 beyond it. The tests read what each upstream answered that day, cut down to the lines that name a version, in `test/fixtures/pin_watch/`; no test reaches an upstream.

### What each upstream offers

| Upstream | Listing | What it gives besides the version |
|---|---|---|
| GitHub releases: rv-ruby, RubyInstaller, llvm-mingw, libxcrypt, rcedit, LLVM, AppImage's runtime, OpenSSL, libyaml, libffi, zlib, XcodeGen, bundletool | GitHub's REST API, `GET /repos/OWNER/REPO/releases` | Each asset's `digest`, its SHA-256 as GitHub recorded it on upload ("Release assets", docs.github.com/en/rest/releases/assets), the very SHA-256 `runtime/sources.yml`'s comments say its GitHub pins hold (on 2026-11-22 it matched the pins of OpenSSL 3.6.5 and of rv-ruby's x86_64 Linux archive); OpenSSL's and RubyInstaller's PGP signatures beside their files |
| Ruby | `cache.ruby-lang.org/pub/ruby/index.txt`, a plain listing of every release | Each file's SHA-1, SHA-256, and SHA-512 |
| Gradle | `services.gradle.org/versions/current`, a JSON API | The distribution's URL, and its SHA-256 beside it as `.sha256` |
| Android's NDK | `dl.google.com/android/repository/repository2-3.xml`, the repository Android Studio's SDK manager reads, with a channel for each package | Each archive's size and SHA-1 |
| Android Gradle plugin | Google's Maven repository's `maven-metadata.xml` | Maven's checksums beside each file |
| Mozilla's CA certificates | curl's page, `curl.se/docs/caextract.html` | A `.sha256` beside each dated file |
| NSIS | SourceForge's RSS feed of the NSIS 3 folder | SourceForge's SHA-1 and MD5 of each file |

None of the listings is signed. The watch reads the version only; the move (step 2) takes the SHA-256 from the upstream's own record where it has one, GitHub's digest or Ruby's index, and checks a signature where the upstream signs, as the RubyInstaller pins already are.

### Tools considered

The watch is about 150 lines because no maintained tool fits the shape of `runtime/sources.yml`. Dependabot updates the manifests of package managers, GitHub Actions' `uses:`, and Docker images; it has no notion of a URL and SHA-256 pinned in a YAML file. Renovate does, with its regex managers and its `github-releases` and custom datasources, and its `automergeType: "branch"` is the shape step 3 takes ("automergeType", docs.renovatebot.com/configuration-options/). But it runs as a Node application with a write token, its branches pushed with the workflow's token start no CI, exactly as this workflow's would not, and the rest of a move (the SHA-256 from GitHub's digest, `runtime/licenses.yml`'s versions and evidence, the release) would still be Fledge's code, behind a configuration as long as `runtime/upstreams.yml`. nvchecker, the version checker Arch Linux's packagers use, finds versions from GitHub and from pages much as the watch does, but brings a Python tool to pin, gives a version without an asset or its SHA-256, and leaves the comparison with the pins to Fledge. Homebrew's livecheck has the same strategies (GitHub's latest release, a page and a pattern) and its autobump opens a pull request every three hours for formulae on its list (docs.brew.sh/Autobump), but it runs only inside Homebrew. So the watch takes their way of finding a version, a listing and a pattern, and keeps the pins' own shape.

### What the watch cannot know

It knows releases, not fixes. A fix backported without a new version, as a distribution's patched package, is invisible to it; MSYS2's package release numbers (`1.4-2`) would show one, but those inputs move with RubyInstaller. An advisory for a version that has no fixed release yet leaves nothing to move to. rv-ruby compiles its own OpenSSL into each Ruby (3.6.2 in the pinned release, by `runtime/licenses.yml`'s evidence), so OpenSSL's fixes reach macOS and glibc Linux only through a newer rv-ruby release, which the watch does see. An advisory feed would be a second source: OSV and GitHub's advisory database index package managers' packages, not C libraries' release tarballs, and would need a mapping from each pin to the identifier each database uses; ruby-advisory-db covers Ruby itself and is cheap to read. Neither is wired in: what Fledge can act on is a release, and the watch sees every one.

The pins outside `runtime/sources.yml` are not watched: the Alpine image and packages the musl runtimes build in (`.github/scripts/alpine-packages.sh`, whose pins stop resolving by themselves when Alpine moves on), the Ubuntu packages and Xcode of CI's runtime jobs, the tools `mise.toml` pins, and the actions every workflow pins.

## Windows' Ruby until Ruby 4.1.0

The Ruby versions pinned today are not one release everywhere. While that release is a preview, which RubyInstaller does not build, the Windows pins name RubyInstaller's head build of Ruby's main branch taken on the day the release appeared, or the nearest day with one: today the build of 2026-11-10, ruby 4.1.0dev at 0e25874222, beside 4.1.0-preview1 at 2d08b5f42f everywhere else, since no head build exists from preview1's day. Its library folders may carry another ABI version (`4.1.0+6` beside the preview's `4.1.0+5`); nothing in Fledge keeps that name, which `RuntimeBuilder.ruby_abi` and `LicenseAudit#abi` read from each tree. RubyGems and Bundler call it Ruby 4.1.0.dev, where the others are 4.1.0.preview1 (`Gem.ruby_version`), so a Gemfile that asks for `ruby "4.1.0-preview1"` builds and starts everywhere but Windows, under `bundle exec` as in an app (`doc/contributors/design/gems.md`, "The runtime's Ruby version"). Each move to a later preview, a release candidate, or 4.1.0 moves every platform in one Fledge release, takes that day's head build, and says in `runtime/sources.yml` and the CHANGELOG which revision Windows runs against the release's own; at 4.1.0, RubyInstaller's numbered build replaces head.

Building every platform from one commit of Ruby's main branch would have Fledge build Ruby for macOS and glibc Linux too, two more builds to keep, which ADR 035 defers until a maintained build fails. A Fledge release on every night's head build would turn trunk red whenever Ruby's main branch broke, and move every app's Ruby each day. So until 4.1.0 Windows runs another revision than the other platforms, with other default and bundled gem versions, another ABI version in its folders, and C API changes the preview lacks, and code that runs on one may not run on the other. The parity check compares each Windows app with the very head build its runtime came from, so that gap is not a parity difference.

## Rolling upstream inputs

Some inputs are published at a URL that serves a new file every day, as RubyInstaller's `rubyinstaller-head` release does. A pin of such a URL would stop resolving the next day, and with it every build, parity check, and audit that fetches it. Fledge keeps the exact files it pins, unchanged, as assets of a pre-release of its own repository, named `inputs-<source>-<date>` for where they came from and the day they were taken, such as `inputs-rubyinstaller-head-20261110`, or `inputs-rubyinstaller-head-<date>-for-<version>` when it is taken for a Ruby release, and the pins name that copy. Fledge's own Ruby builds are kept the same way, as `inputs-fledge-ruby-<version>-<date>-<commit>` ("Fledge's own Ruby builds"). The tag does not start with `v`, so `release.yml` does not run, and the pre-release is never the latest release. The pin keeps its SHA-256, and its signature and key where it has them, so the copy is held to the same bytes and the same signer as the original; `runtime/sources.yml` names the original URL in a comment, for provenance. Whoever publishes the pre-release checks each file's SHA-256 and signature again before publishing it; such a pre-release is never deleted, since every commit that pins it builds from it. A head build must be taken on its day: RubyInstaller's CI keeps each successful build as an artifact for about 90 days, but the `.asc` the build checks exists only on the release asset, which the next day's build replaces; `.github/workflows/keep-rubyinstaller-head.yml` takes it on each Ruby 4.1 release's day.

A copy that a release published beside its runtimes would not exist until that release's pin commit passed CI, which needs the input first. The Actions cache holds only on the branch that filled it, and for at most seven days unused, and committing the files would put tens of megabytes of binaries in every clone. The cost is that the files must be taken on the day upstream serves them, and that the releases list holds pre-releases that are not versions of Fledge.

## The glibc symbols rv-ruby's builds need

rv-ruby's Linux builds call functions glibc added in 2.38 and 2.39 (`pidfd_spawnp`, `pidfd_getpid`, `__isoc23_strtol`, `strlcpy`), so a glibc Linux app needs glibc 2.39 or newer: Ubuntu 24.04, Debian 13, Fedora 40, and later. That is the floor `Fledge::Platform::GLIBC_MINIMUM` names; the floors and when they may move are `doc/contributors/design/releases.md`, "Platform floors".

## libxcrypt on glibc Linux

rv-ruby links libxcrypt, which is LGPL-2.1-or-later, statically into its own `bin/ruby`. A glibc Linux runtime never ships that `bin/ruby`. It builds the same libxcrypt release from its pin with rv-ruby's configure options, shared instead of static, and with libxcrypt's own `--disable-werror` (`RuntimeBuilder::Linux::LIBXCRYPT_CONFIGURE`). That option drops only the `-Werror` libxcrypt's configure adds, and keeps every warning it enables: libxcrypt 4.5.2 assigns `strchr`'s result to a `char *` in `crypt-sm3-yescrypt.c` and `crypt-gost-yescrypt.c`, which GCC 15, compiling C23 by default against glibc 2.43's `strchr` that keeps its argument's `const`, reports as a discarded qualifier, so with `-Werror` the release does not build on a current distribution. libxcrypt fixed those lines after 4.5.2 (commit 174c24d6e8), in no release yet. The runtime installs `libcrypt.so.2` into the runtime's `lib/`, stripped, and links the launcher and its own `bin/ruby` against it. The source bundle's `BUILD.txt` prints those options as the way the runtime's copy was built.

libxcrypt ships as a shared library a person can replace, as the license policy asks of an LGPL library (`doc/contributors/design/license-audit.md`, "LGPL linked into a component that is not Fledge's"). Linked statically, as rv-ruby links it, its code would sit inside a program an app's developer ships as their own. musl's crypt in its place would keep `String#crypt` from behaving as under `ruby`: it silently computes a DES hash for yescrypt, the default password hash of current Debian, Ubuntu, and Fedora (`doc/contributors/research/2026-11-10-findings-from-the-adrs.md`, "The permissive spike: what the first license audit found"). The cost is a library Fledge builds in each glibc Linux runtime build, following rv-ruby's release of it.

musl Linux ships no libxcrypt: musl's own `crypt(3)` serves `String#crypt`. It does not know every hash current glibc systems use, so an app that checks such hashes on Alpine meets what `ruby` does there.

## The RubyInstaller signing key

Every Windows runtime build checks RubyInstaller's archive against its detached PGP signature (`RuntimeBuilder::Windows#verify`):

1. the signature and the key are downloaded and checked against their SHA-256s;
2. the key's ASCII armor is decoded (`RuntimeBuilder::Armor`, with its CRC-24 checked), since `gpgv` reads only a binary keyring;
3. `gpgv` checks the signature against a keyring of that one key;
4. the signature must be that key's, by the fingerprint the pin names (`VALIDSIG`).

The key is RubyInstaller's package signing key as `oneclick/rubyinstaller2` records it, `recipes/unpack/appveyor-repo-key.asc`, at a pinned commit. Both Windows archives are signed with it.

The pin records the key's expiry. `gpgv` does not judge a key's expiry, so an archive already pinned keeps verifying after that date. When the Ruby pin moves to a RubyInstaller release signed by a renewed or a new key, whoever moves it pins that key the same way: its URL in `oneclick/rubyinstaller2` at a commit, its SHA-256, its fingerprint, and its expiry. `test/runtime_builder_test.rb` checks that every Windows pin has all four.

## Windows on ARM64

`aarch64-mingw-ucrt` is built as `x64-mingw-ucrt` is, from RubyInstaller's ARM64 archive of the same release, with llvm-mingw for `aarch64-w64-mingw32` (ADR 035). It is a native runtime, not the x64 runtime under Windows' emulation, since a native program runs at full speed and the maintainer wants ARM ("I'd like to support Windows on ARM", `decisions.md`, 2026-10-26, decision 22); the x64 runtime under emulation was the other option, and no recorded reason preferred it. It costs little: RubyInstaller's ARM64 archive comes from the same release, signed with the same key, and the pinned llvm-mingw already targets `aarch64-w64-mingw32`, so the recipe is the x64 one with another archive and triple. What differs:

- **GNU MP.** The audit pins the ARM64 `libgmp-10.dll` by its own SHA-256. It is byte for byte the DLL of MSYS2's CLANGARM64 package of the same source package as x64's, which CI's Runtime job checks, and the source bundle's `BUILD.txt` says how to build a replacement for `aarch64-w64-mingw32`.
- **No GCC runtime.** LLVM built RubyInstaller's ARM64 tree, so `runtime/licenses.yml` lists no libgcc for it. The MinGW-w64 runtime and winpthreads are as on x64.
- **The tools are x64 and x86 programs** (rcedit, NSIS, `llvm-readobj`), which Windows 11 on ARM64 runs under its own emulation. None ships in an app.
- **Temporary copies of the tools.** The emulator's cache service, XtaCache, holds an emulated program's file open for a while after it exits, so a folder that held the program cannot be deleted at once. So `Fledge::Nsis` runs makensis, `Fledge::WindowsResources` runs rcedit, and `Fledge::AppGems` runs `llvm-readobj` from a copy in the system's temporary folder (`Dir.mktmpdir`), which each removes as far as Windows lets it and leaves the rest to the temporary folder. They do so on every Windows computer, so the code has one path.

## musl Linux's Ruby, built in Alpine

`RuntimeBuilder::Musl` (`tasks/runtime_builder/musl.rb`) builds Ruby from source on a computer of each architecture, in Alpine. CI runs it in the Alpine Ruby image `ci.yml` pins by digest (`ALPINE_RUBY`), whose Ruby is the build's `--with-baseruby`, with the packages `.github/scripts/alpine-packages.sh build` pins by version: a C toolchain, Rust for YJIT, Perl for OpenSSL's build, and binutils, whose objdump the license audit reads with. Before it configures Ruby, it makes one edit to Ruby's source, `thread_c` (`RuntimeBuilder::Musl::EDITS`; `doc/contributors/design/phone-runtimes.md`, "Scripted edits to Ruby's source"): `Thread#name=` on a thread that has ended passed its freed `pthread_t` to musl's `pthread_setname_np`, which crashed stock Ruby and the app alike in ruby/spec's `core/thread/to_s_spec.rb` (run 43354884978), until Ruby 4.1.0 brings ruby/ruby 6fdd452087.

1. **Libraries.** zlib, libyaml, and libffi are built from their `musl-ruby` pins, static and position-independent (`-fPIC`), and OpenSSL `no-shared` the same way, so each links into the one extension that uses it, as rv-ruby's glibc builds link them.
2. **Certificates.** As rv-ruby does (`Formula/rv-portable-openssl.rb`, line 77; `Abstract/rv-ruby.rb`, lines 203 to 208, at 7a0e584), OpenSSL's `SSL_CERT_FILE` is renamed `PORTABLE_RUBY_SSL_CERT_FILE` in its source, so no other program's OpenSSL reads it, and the installed `openssl.rb` sets it to `SSL_CERT_FILE`, or else to `libexec/cert.pem` beside the Ruby, before it loads `openssl.so`. Each edit fails the build when the line it replaces is gone.
3. **Ruby.** From its release tarball, configured and built in its source folder, as rv-ruby builds it (`Abstract/rv-ruby.rb`, lines 157 to 174, at f57186e), `--enable-load-relative --disable-shared --enable-yjit --without-gmp`, every extension a shared object, `win32` and `win32ole` left out, linked `-static-libgcc`, and installed with `make install-nodoc`. Built beside its source, Ruby's install wrote default gems' specifications unlike a desktop's, and RubyGems did not activate io-nonblock for `require "io/nonblock"` (`doc/contributors/design/phone-runtimes.md`, "Building Ruby for a phone").
4. **The CA bundle** from its pin, as `libexec/cert.pem`.
5. **The rest is the Unix recipe:** the launcher and `bin/ruby` linked against that `libruby-static.a`, the standard library, pruning, Fledge's RubyGems defaults, AppImage's runtime in `tools/`, and the audit.

Fledge builds this Ruby because no prebuilt one fits, the fallback ADR 035 names, as python-build-standalone builds CPython. rv-ruby's musl builds are configured `--with-static-linked-ext` (`alpine/4.sh`, spinel-coop/rv-ruby at 7a0e584): every extension of the standard library is linked into their own `bin/ruby`, and their `libruby-static.a` ships without them, so a launcher linked against it has no `json`, `openssl`, or `psych` (`doc/contributors/research/2026-11-10-findings-from-the-adrs.md`, "musl Linux: the Alpine build spike"). Alpine's own `ruby` package is built for `/usr` and links Alpine's shared OpenSSL and libyaml, which an app's computer may lack. Built this way, a musl runtime is the pinned Ruby every other runtime is, and runs on any musl Linux, not only the Alpine it was built in. The maintainer asked for musl because "Many CI platforms only run on musl for Linux" (`decisions.md`, 2026-10-26, decision 12). The cost is a Ruby build Fledge keeps, with its pins moved on purpose and the certificate edits rechecked at each Ruby release; CI runs it with `docker run` on a runner of each architecture, since GitHub's JavaScript actions cannot run inside an Alpine container on ARM. If rv-ruby's musl builds kept their extensions as shared objects, they would serve, and this build could go.

The parity check's reference on musl is this build's own `bin/ruby` with Fledge's RubyGems defaults taken out (`doc/contributors/design/parity.md`).

## Fledge's own Ruby builds

The maintainer asked for apps and frameworks to be tested on Rubies much newer than the last numbered one ("we've gotta figure out how to start testing not just Windows on much more recent rubies"), and for Fledge to help Lota and Tokra "in _their_ goals to test with Fledge's releases and shipping sample apps on more recent rubies too" (decisions.md, 2026-11-21). rv-ruby, whose builds the macOS and glibc Linux runtimes take (ADR 035), publishes numbered versions and previews only, and no other project publishes a relocatable build of Ruby's master with a static libruby ("Where a recent Ruby comes from", below). So Fledge builds one for those platforms itself: `tasks/ruby_archive.rb` (`RubyArchive`, run as `ruby tasks/ruby_archive.rb PLATFORM`) writes `tmp/ruby-archive/ruby-VERSION-PLATFORM.tar.gz`.

One archive serves a runtime and a developer:

- **rv-ruby's shape.** The archive holds `ruby/VERSION/`, a prefix in Ruby's own layout (`bin/`, `include/`, `lib/` with the static libruby and `lib/ruby`, `libexec/cert.pem`), as rv-ruby's archives hold theirs, so a runtime's `ruby.platforms` pin can name either by URL and SHA-256 and the Unix recipe copies a runtime from either alike (`Unix#unpack_ruby` finds `*/VERSION`). Moving the build to another home later changes a URL.
- **The musl runtimes' Ruby.** `RuntimeBuilder::RubyBuild` builds it, the steps the musl recipe takes ("musl Linux's Ruby, built in Alpine"): a static libruby configured `--enable-load-relative`, every extension a shared object, and OpenSSL, libyaml, libffi, and zlib from `musl-ruby`'s pins, linked statically into the extensions that use them. The source is `runtime/sources.yml`'s `ruby-build.ruby`, a release-shaped tarball, and takes no scripted edit.
- **YJIT and ZJIT.** Both are configured in (`--enable-yjit --enable-zjit`), so a Ruby without either fails to configure rather than build without it, and the build fails unless `ruby --yjit` and `ruby --zjit` each report their JIT enabled. Lota runs both. The Rust compiler and standard library are `ruby-build.rust`'s pins, the release `mise.toml`'s Rust names, installed into the build folder by their own installers.
- **libxcrypt on glibc Linux,** built from its pin as a glibc runtime builds it ("libxcrypt on glibc Linux"), shared: `lib/libcrypt.so.2`, with `lib/libcrypt.so` for a gem's `-lcrypt`, and `bin/ruby` finds it through the RPATH `$ORIGIN/../lib`. rv-ruby links it statically into its `bin/ruby` instead. The build fails if `bin/ruby` needs any other library than glibc's and that one.
- **Headers and RbConfig that move.** `include/` and the static libruby are what `mkmf` compiles and links a gem against, as in a runtime ("What a runtime keeps"), and with `--enable-load-relative` RbConfig's prefix, library, and header folders follow the folder the archive is unpacked in. Lota's C++ extension, whose CMake reads Ruby's paths, and Tokra's rb-sys read more than those: the flags and the configure arguments in `rbconfig.rb`, and Ruby's pkg-config file, which record every folder of the build. So `RubyArchive#relocate` rewrites them once Ruby is installed. libxcrypt's library folder becomes `$(libdir)`, where its library now is, and its headers' folder goes, since no installed header includes `crypt.h`; the `--with-*-dir` arguments that named the folder of the statically linked libraries go, since nothing outside the build has it and `mkmf`'s `dir_config` would read them; the prefix, left in `configure_args` and in the fallback for an `rbconfig.rb` loaded from somewhere else, becomes `/ruby/VERSION`, the folder's name in the archive; and the pkg-config file's `prefix` becomes `${pcfiledir}/../..`, the folder pkg-config found the file in. python-build-standalone leaves such paths in its builds (`/build` and `/install` on Linux) for its installer, uv, to fix up where it unpacks one (`docs/quirks.rst`, "References to Build-Time Paths", lines 148 to 192, in astral-sh/python-build-standalone's main branch on 2026-11-21); Fledge's archive has no installer of its own, since mise's http backend only unpacks it, so the archive carries the fix itself. The build fails if `rbconfig.rb`, a pkg-config file, or a header still names the build folder.
- **An embedder finds Ruby from where it sits.** A program that links the static libruby and starts Ruby as Ruby's `main.c` does (`ruby_sysinit`, `RUBY_INIT_STACK`, `ruby_init`, then `ruby_run_node(ruby_options(...))`, as Fledge's launcher does) gets its prefix from its own path, since with `--enable-load-relative` Ruby finds its load path from the file that holds its code, which `dladdr` names (`ruby.c`, from line 592, `dladdr` at line 645, at 4.1.0-preview1), and with a static libruby that file is the program. Built with the archive's pkg-config flags and `RbConfig`'s `LIBRUBYARG_STATIC`, such a program ran from the prefix's `bin/` with its load path inside the archive, and from any other folder stopped with `cannot load such file -- rbconfig`, exactly as one built against rv-ruby's archive did. So an embedder sits in the prefix's `bin/`, as Fledge's launcher sits where the runtime's Ruby expects it, or sets the load path itself. One that evaluates code after `ruby_init` alone, unprotected, turns that LoadError into a crash.
- **What differs from rv-ruby's archive.** Of rv-ruby's 3,188 files and this archive's 3,036, 2,968 are in both. rv-ruby's alone holds its own bookkeeping (`INSTALL_RECEIPT.json`, `.brew/`, an SBOM, Ruby's README, NEWS, and COPYING files), `lib/libcrypt.a` and `portable_ruby_gems.rb`, the bootsnap and msgpack gems it adds, which no standard Ruby installs, and more of Prism's files; this one alone holds `lib/libcrypt.so` and `.so.2`, and win32-registry's specification, which `make install` writes on every system.

The floors are two, and differ on purpose. An app's floor on glibc Linux stays glibc 2.39, the maintainer's (decisions.md, 2026-10-26, decision 7): Fledge's launcher and `bin/ruby` are linked on Ubuntu 24.04 and need it. The archive's floor is glibc 2.35 (`RubyArchive::GLIBC_FLOOR`), Ubuntu 22.04's, because Lota's CI installs its development Ruby there, so the archive is built in Ubuntu 22.04 and the build fails if `bin/ruby` or any extension needs a newer `GLIBC_` symbol version. A runtime built from it still needs 2.39, for its own programs. python-build-standalone builds against an old glibc for the same reason, so that one build installs on as many systems as can run it. On macOS the archive's floor is the apps' floor, macOS 14 (`MACOSX_DEPLOYMENT_TARGET`). Building in Ubuntu 22.04 needs a Ruby 4.1 to run Fledge's tasks there, which neither rv-ruby's nor jdx/ruby's builds can be, since they need glibc 2.39; the build runs on ruby/setup-ruby's own build of the same Ruby for Ubuntu 22.04, from ruby/ruby-builder, checked by its SHA-256.

`.github/scripts/ruby-archive.sh PLATFORM` builds the archive in Ubuntu 22.04 with every input pinned, on a computer with Docker of that platform's architecture, and refuses one of the other architecture rather than emulate it. It runs `ubuntu:22.04` by the digest of its index of images for every architecture, installs with apt each package the build needs at the version it pins, downloads the driver Ruby, ruby-builder's `ruby-4.1.0-preview1-ubuntu-22.04-x64.tar.gz` or `-arm64.tar.gz`, and checks it by the SHA-256 it pins for that architecture, unpacks it at the folder it was built for (`/opt/hostedtoolcache/Ruby/4.1.0-preview1`), and runs `ruby tasks/ruby_archive.rb PLATFORM`, whose downloads go to the computer's own download cache, each checked by its SHA-256. A contributor runs the same command. The package pins are top-level packages, as `.github/scripts/alpine-packages.sh` pins musl's: a compiler's own parts depend on its exact version, so `gcc-11` and `binutils` hold theirs, and other dependencies come at whatever version apt then picks. Ubuntu's `-updates` and `-security` pockets keep only each package's newest build, so a pin stops resolving when Ubuntu publishes a newer one, and the build fails with apt's `Version '...' was not found`. Move it on purpose, as an Alpine pin is moved; the script's header says how. Ubuntu's snapshot service, `snapshot.ubuntu.com`, would pin every package, dependencies too, to one moment, and no pin would rot. It was weighed and set aside. On 2026-11-21 it served amd64's archive over HTTPS only, and its `ubuntu-ports` path, where arm64's packages are, answered 401. An image with no CA certificates cannot reach it before apt has installed them from the live archive. Each pin resolved on both architectures on that day, in jammy's own indexes.

`.github/workflows/ruby-builds.yml` runs the script on a runner of each architecture, `ubuntu-24.04` and `ubuntu-24.04-arm`, with `docker run` as the musl runtimes are built. It keeps each archive as the run's artifact, `ruby-archive-PLATFORM`, for 14 days, and its build logs when it fails. The archive's own checks are the task's: the glibc floor, YJIT and ZJIT, the libraries `bin/ruby` links, and no build folder left in `rbconfig.rb`, the pkg-config file, or the headers. Its publish job then runs `.github/scripts/ruby-archive-publish.sh` on both archives, which must be of one version. In a dry run it prints the pre-release's name and notes. Otherwise it creates the pre-release `inputs-fledge-ruby-VERSION-YYYYMMDD-COMMIT` with `gh release create --prerelease --latest=false` on the commit that built them, then downloads each archive back and checks its SHA-256. The name says what the archives are, the day they were published, in UTC, and the commit whose recipe built them. It begins `inputs-`, as every input Fledge keeps does ("Rolling upstream inputs"), so `release.yml` does not run and the pre-release is never the latest release. One that exists is never overwritten, and the notes give each archive's SHA-256 and the run that built it. Only the publish job holds `contents: write`, with the repository's own token. `test/workflow_ruby_builds_test.rb` and `test/integration/ruby_archive_publish_test.rb` test the workflow and the publishing.

The workflow runs on each push to `trunk` that changes the recipe or its pins: the two scripts, the workflow, `tasks/ruby_archive.rb`, the runtime builder's files the task uses, and `runtime/sources.yml`. Every such run is a dry run. So a change that breaks the build, or a package pin Ubuntu has moved past, shows within the day it lands, on the commit that pushed it, and not on the day a pin should move. `runtime/sources.yml` changes most weeks, so that is also how often the package pins are tried. A schedule would add little, and would make red runs that no commit caused. The workflow publishes only when run by hand with `dry-run` turned off. A published archive is an input a pin will name, and AGENTS.md has inputs arrive on purpose, so publishing is a choice made when a pin is to move, never a side effect of a push.

The builds live in Fledge for now, behind the seam Fledge already has for an upstream input: pre-releases of Fledge's own repository, pinned by URL and SHA-256 ("Rolling upstream inputs"). Whether they would be better as a project of their own, as RubyInstaller and rv-ruby are, was weighed against two other homes. A repository of their own now would be a new project to stand up (its rules, CI, gates, and someone to keep it), while the recipes, pins, and license audit it needs are Fledge's, the musl and phone runtimes need them in Fledge regardless, and its shape is unknown until Lota and Tokra have used it. Asking rv-ruby to build snapshots of Ruby's master may be the better home in the end, since rv-ruby is already that service and publishes previews, but whether to ask is the maintainer's. So the builds start in Fledge, behind a pin that moving elsewhere changes by one URL, and move out when something needs them on a cadence that is not Fledge's releases, or after 1.0, whichever comes first.

No runtime builds from these archives yet: every `ruby.platforms` pin still names rv-ruby's, and the move is a release's. A runtime made from one holds another Rust and another OpenSSL than one made from rv-ruby's, so `runtime/licenses.yml` keeps an entry for each build where they differ, marked `ruby_build: upstream` or `ruby_build: fledge`, and the audit takes the entries of the build the platform's pin names, `build: fledge` for these archives and nothing for rv-ruby's (`LicenseAudit.entries`; `doc/contributors/design/license-audit.md`, "The map: runtime/licenses.yml"). Each build is held to its own evidence, and the pin that moves moves the audit with it. The parity check moves too: its reference is the pinned Ruby's own `bin/ruby`, so a runtime made from one of these archives is compared with Fledge's own build, as on musl, and no longer with an independent one. A runtime built from this archive for x86_64-linux showed two justified differences fewer than one from rv-ruby's, `gems` and `requireable`, because the archive, like a standard Ruby, adds no bootsnap or msgpack; every other difference was the same for both.

## What a runtime keeps

Everything a standard Ruby of the pinned version installs that running Ruby code can reach:

- the standard library;
- every default gem, and every gem `runtime/sources.yml`'s `bundled_gems` lists that the Ruby installs (rv-ruby installs all but win32ole and win32-registry, which only Windows builds; RubyInstaller all but syslog, which needs a Unix);
- each gem's executables, its `.gem` in the cache (`gem pristine` and `Gem::Specification#cache_file` read it), its build information, plugins, and C extensions, and the libraries those extensions carry;
- Ruby's own programs: Fledge's `bin/ruby` on macOS and Linux, and on Windows Fledge's `ruby.exe` and `rubyw.exe` and RubyInstaller's command-line wrappers for the gems (`gem.cmd`, `bundle.bat`, and the rest);
- the library `mkmf` links its checks against: on macOS and Linux the static libruby beside `lib/ruby`, and on Windows the import library of Ruby's DLL (`lib\*.dll.a`). `mkmf` links each check's program against `$(LIBRUBYARG)` (`mkmf.rb`, lines 541 to 553, at Ruby 4.1.0-preview1), which for a static Ruby names `-lruby.X.Y-static` in `$(libdir)`; without the file an app's own `have_func` raises "The compiler failed to generate an executable file". The static libruby comes without its debug information ("What a runtime prunes, and why nothing reads it"). rv-ruby's `lib/libcrypt.a` stays out: it is libxcrypt, which is LGPL, and the linker finds the system's `-lcrypt`;
- Ruby's C headers, `include/`, since `require "mkmf"` aborts without `ruby/ruby.h` ("mkmf.rb can't find header files for ruby", `mkmf.rb` line 253 at Ruby 4.1.0-preview1);
- on Windows, every DLL, those Fledge adds among them, since an extension's manifest may name any of them, and RubyInstaller's own Ruby library in `site_ruby`.

The rule is the maintainer's: code that runs without Fledge runs with it, and "the things you didn't have to `require` before the app dev still shouldn't have to require" (`decisions.md`, 2026-10-26, decision 9), while "Tiny filesize is not a priority" (decision 20). Each thing kept answers a way a smaller runtime failed. A runtime without the bundled gems broke `require "csv"`, and one without `bin/ruby` left `RbConfig.ruby` and `Gem.ruby` naming a program that did not exist. Ruby's headers and its own library, once only in a download that builds fetched, left `require "mkmf"` aborting at run time, which some gems do for `MakeMakefile#find_executable`, and an app's own `have_func` failing (`doc/contributors/research/2026-11-10-findings-from-the-adrs.md`, "Ruby's headers in the runtime: the finding and its cost"). The costs: archives about double the size of the standard library and default gems alone (`doc/contributors/research/2026-11-10-findings-from-the-adrs.md`, "Runtime sizes"); every bundled gem's license comes into every app, each one permissive, which the license audit checks on every build; and the runtime's `bin/ruby` is Fledge's own build of Ruby's `main.c`, since rv-ruby's links libxcrypt statically. The parity check compares the installed gems, whether each one's main file loads, and `RbConfig.ruby` on every platform, and ruby/spec runs in built apps (`doc/contributors/design/parity.md`).

## What a runtime prunes, and why nothing reads it

`RuntimeBuilder::Pruning.prune` (every Unix and phone runtime, and `ruby\lib\ruby` on Windows) and `prune_windows` give each removal its reason in their comments. The Unix recipe also copies only `bin/`, `lib/ruby`, the static libruby, `include/`, and `libexec/cert.pem` from rv-ruby's prefix, so `share/` (man pages and documentation) never comes along.

| Removed | Why no app can miss it |
|---|---|
| `*.dSYM` | macOS debug symbols, read by debuggers and crash reporters, never by Ruby. |
| `*.a`, `*.h` under `lib/ruby`, `pkgconfig/` | Static libraries, the C headers of gems' extensions, and pkg-config files, for compiling against Ruby. Ruby code never loads them, and `mkmf` reads none of them. Ruby's own headers in `include/` and the static libruby beside `lib/ruby` stay. |
| `lib/ruby/gems/X.Y.0/doc` | RDoc and ri documentation, read by the `rdoc` and `ri` tools a developer runs, never by an app's requires. |
| nkf's `ext/java/` | See "nkf's JRuby sources". |
| `portable_ruby_gems.rb`, and every gem that is neither a default gem nor in `bundled_gems` | rv-ruby's own additions, a load-path helper and the bootsnap and msgpack gems. No standard Ruby installs them, so an app that worked under `ruby` never needed them. Each goes with its specification, cache, build information, extensions, and executables. |
| Windows: `share\` | Ruby's HTML documentation and ri data. |
| Windows: `lib\*.a`, `lib\pkgconfig` | Static libraries and pkg-config files, for compiling against Ruby. The import library of Ruby's DLL (`lib\*.dll.a`) stays, for `mkmf`. |
| Windows: `packages\`, `ridk_use\`, `bin\ridk.cmd`, `bin\ridk.ps1`, `bin\setrbvars.cmd`, `bin\startmenu.rb` | The MSYS2 keyring and `ridk`, which install and select MSYS2 compilers for a developer, and the scripts that set up a developer's shell and Start menu. They work only beside an installed RubyInstaller and MSYS2. |

Debug information goes too, since no running code reads it and no link does. Extensions are stripped of debug sections on Linux, the programs Fledge links are stripped, and the static libruby is stripped with `strip -S`, which GNU's strip and Apple's both take for debug information only (`RuntimeBuilder::Unix#copy_static_libruby`). That keeps each object's code, data, symbols, and relocations, everything a link reads, and the archive's index. On Linux, where Ruby's C is compiled with DWARF, debug information is most of the file: v0.14.0's x86_64-linux runtime held a static libruby of 90,093,822 bytes, 19,478,606 without it, and its x86_64-linux-musl runtime one of 164,970,554, 20,119,082 without it, which takes that runtime's archive from 75 MB to 35 MB. On macOS rv-ruby's C carries no DWARF, and what goes, 13,316,232 bytes to 11,458,672, is the debug map of the Rust in YJIT and ZJIT, which names object files on rv-ruby's build machine, so the linker of every mkmf check warned "unable to open object file" for each. Windows' import library holds no debug information, and `strip --strip-debug` leaves its 2,786,214 bytes as they were. `have_func`, `have_library`, and `try_link` succeed against the stripped archive as against the original, with no new warning, and fail without it; the license audit's evidence of the Rust standard library, its `/rustc/` path, is in the code's own strings and stays.

Nobody loses anything by it. The launcher and `bin/ruby`, the programs a debugger or a crash report meets, link rv-ruby's own copy of the archive and are stripped themselves, and the program a check links is deleted once it has linked (`mkmf.rb`, `try_link`, lines 642 to 646, at Ruby 4.1.0-preview1). Only a developer who linked a program of their own against the runtime's libruby and debugged it at the source level would miss the line tables, and rv-ruby's own release has them. python-build-standalone does the same: its `install_only_stripped` archives run `llvm-strip --strip-debug` over every compiled file, and are "equivalent to install only, but without debug symbols, which results in a smaller download and on-disk footprint" (`src/release.rs`, `convert_to_stripped` and `llvm_strip`, at astral-sh/python-build-standalone 98b27f7; its "Distribution Archives" documentation). Its `install_only` archives leave libpython's static library out altogether, as what "isn't needed in most cases" (`convert_to_install_only`, the same file). A runtime keeps it, since without it an app's own mkmf fails where `ruby` succeeds. rv-ruby ships the archive as `make install` leaves it: `Abstract/rv-ruby.rb` strips nothing (spinel-coop/rv-ruby at fadbfcf).

The parity check lists bootsnap and msgpack, which are pruned, among the differences it allows (`Parity::JUSTIFIED` in `tasks/parity.rb`).

## nkf's JRuby sources

`RuntimeBuilder::Pruning.prune_jruby` removes nkf's `ext/java`, the Java sources of JRuby's nkf, from the gem's folder and from its `.gem` in the cache (`Pruning::JRUBY_ONLY`). CRuby never compiles or loads them: `nkf.gemspec` adds them only to the java-platform gem, and `ext/nkf` is CRuby's. So no running Ruby code reads them. They are EPL-2.0 OR LGPL-2.1-or-later, the only copyleft text a runtime would otherwise carry that is not license data.

`RuntimeBuilder::GemRepack.repack` rewrites the cached `.gem` in RubyGems' own format, with the specification's file list and `checksums.yaml` changed to match, so `Gem::Package#verify` and `gem pristine nkf` accept it. The cached nkf `.gem` therefore differs from RubyGems.org's by those files.

## Fledge's RubyGems defaults

Every runtime ships `runtime/rubygems/operating_system.rb` as `lib/ruby/X.Y.0/rubygems/defaults/operating_system.rb` (`RuntimeBuilder#install_rubygems_defaults`), the hook RubyGems loads for whoever packages Ruby (`rubygems.rb`, line 1465, at Ruby 4.1.0-preview1). rv-ruby ships none; on Windows it replaces RubyInstaller's. The file's own comments give the reasons. It does two things:

- **The app's gems are the runtime's alone.** `Gem.default_path` is `[Gem.default_dir]`. Left alone, it puts `Gem.user_dir` first whenever the person's home folder exists, so a gem the person installed with their own Ruby of the same minor would shadow the app's, json included.
- **A bundled gem the Gemfile does not name activates under a frozen bundle.** While `Gem::BUNDLED_GEMS.force_activate` runs (for `binding.irb`, say), and only on its thread, Bundler is told its bundle is not frozen; the temporary bundle is still never locked. The reason, and the frozen `.bundle/config`, are `doc/contributors/design/gems.md`, "binding.irb and force_activate".

RubyInstaller's own `operating_system.rb` is for a developer's Ruby: it writes and deletes a file in the runtime's gem folder on every start, creates `%ProgramData%\gemrc`, searches for MSYS2 and adds its DLL folder, and leaves `Gem.user_dir` first in `Gem.path`. A runtime needs none of it: RubyInstaller's DLLs load through their manifests without its runtime, and compiling a gem enables MSYS2 through RubyInstaller's Ruby library, which the runtime keeps (`doc/contributors/design/gems.md`). Fledge's file on Windows loads what RubyInstaller's start-up loads and calls none of it. It requires `ruby_installer/runtime`, so `RubyInstaller` is defined, as under `ruby.exe`, and a gem that tests `defined?(RubyInstaller)`, such as mysql2, takes the branch it takes there. Then it loads the autoloads RubyInstaller's `enable_dll_search_paths` loads, `Msys2Installation` (which includes `Colors`) and `DllDirectory` (which requires `win32/dll_directory` and so defines `Win32`), whose files only define classes and modules when loaded, and converts Ruby's archdir to UTF-16LE, as that call's first `DllDirectory.new` does for `AddDllDirectory`, which loads only the encoding and its converters. So the app starts with the same `$LOADED_FEATURES` and constants as `ruby.exe`.

On macOS and Linux, whose Rubies ship no such file, the parity check allows the defaults' trace in `$LOADED_FEATURES` (`Parity::JUSTIFIED`).

## The Ruby's description

Every runtime, a phone's too, holds `RUBY_DESCRIPTION` at its top: one line, the `RUBY_DESCRIPTION` of the Ruby it carries as far as the platform's name, `ruby 4.1.0preview1 (2026-10-11 master 2d08b5f42f)` for the preview and `ruby 4.1.0dev (2026-11-10 master 0e25874222)` for Windows' head build. `fledge build` reads the Ruby's version from it as RubyGems reports it (`doc/contributors/design/gems.md`, "The runtime's Ruby version"); no app holds it (`Assembly::RuntimeFolder`).

Ruby records the name of a preview or a development build only in that string. `version.h` defines `RUBY_PATCHLEVEL_STR` as `"dev"`, or as the name a release tarball's `tool/make-snapshot` writes into it (`preview1`), and `version.c` compiles `"ruby "`, `RUBY_VERSION`, `RUBY_PATCHLEVEL_STR`, the date and revision, and the platform into `ruby_description` (`version.h`, lines 57 to 66, and `version.c`, lines 88 to 91, at 2d08b5f42f; `tool/make-snapshot`, lines 272 to 279 and 362). `rbconfig.rb` keeps only `PATCHLEVEL` of `-1`, and Ruby's installed headers no name. So `RuntimeBuilder::RubyDescription` reads the string out of the program or library it was compiled into, in each layout: `bin/ruby` on macOS and Linux, Ruby's DLL in `ruby/bin/` on Windows, each slice's `libfledgeruby.a` on iOS, and each ABI's `libfledgeruby.so` in the AAR on Android, which it reads with `unzip`, as the license audit does. Every one in a runtime must give the same description, less the platform, which differs between slices and ABIs, and a runtime with none or two is not built.

`fledge build` could read the string out of the same files itself, and did not, because Android's library is deflated inside the AAR, a zip, and a computer that builds an Android project may have no tool that reads one: GNU tar, Linux's, reads no zip, and Fledge would have had to read one itself, which AGENTS.md rules out where a tool does it. The file costs one more entry in each runtime, which the license audit counts as Ruby's, since its words are Ruby's (`runtime/licenses.yml`), and which the runtime's SBOM lists under Ruby's package. Counted as Fledge's, it would head the list of Fledge's own files in every app's `NOTICES.txt`, as the program the app's user runs, and in `doc/licensing.md`'s sentence on them, though no app holds it: both name the files of Fledge's component in the order they sort, the launcher first. A runtime of Fledge 0.13.0 or before has no such file, and `fledge build` then reads its Ruby as rbconfig's `MAJOR.MINOR.TEENY` alone, as it did; the reading of that case can go once `lib/fledge/SHA256SUMS` pins runtimes that hold it.

## Compiling a gem against a runtime

A desktop runtime alone serves `fledge build` when it compiles a gem's extension (`Fledge::NativeBuild`; `doc/contributors/design/gems.md`, "Compiling a gem"): it holds Ruby's headers and the library mkmf links against, the static libruby on macOS and Linux and the import library of Ruby's DLL on Windows ("What a runtime keeps"). ## Platform names and asset names

A platform is named by its RubyGems platform: `arm64-darwin`, `x86_64-linux`, `aarch64-linux`, `x86_64-linux-musl`, `aarch64-linux-musl`, `x64-mingw-ucrt`, and `aarch64-mingw-ucrt`. A Ruby developer already meets these names in `Gemfile.lock` and in precompiled gems, and they decide which precompiled gem fits a runtime, so Fledge prints no other name for a platform: not in a runtime's asset, `fledge build`'s output, `dist/NAME-PLATFORM`, an error message, a CI job, or the license map. `Fledge::Platform::NAMES` lists them, `Fledge::Platform.local` maps `Gem::Platform.local` to one, and `test/platform_test.rb` checks the mapping. A build's target is the platform Fledge runs on (ADR 010). A phone's targets follow RubyGems' grammar but are chosen so that no desktop gem fits them (`doc/contributors/design/phone-runtimes.md`, "Targets").

RubyGems' names are irregular: `arm64` on macOS against `aarch64` on Linux and Windows, `x64` on Windows against `x86_64` elsewhere. A Mach-O gem may also be named for a macOS version (`arm64-darwin-23`), which fits a runtime only as RubyGems decides, so `fledge build` matches as RubyGems does, not by string. Other ecosystems name platforms differently (LLVM target triples such as `aarch64-apple-darwin`, Go's `darwin/arm64`, Python's wheel tags such as `manylinux_2_39_x86_64`, Electron's `--platform darwin --arch arm64`). Each is more regular, and none tells a Ruby developer which precompiled gem fits.

The assets:

`RuntimeBuilder#assets` names what a release publishes for each platform, and `RuntimeBuilder.release_assets` lists them all, which `release.yml` checks a release against.

| Asset | Name | Platforms |
|---|---|---|
| The runtime | `fledge-runtime-VERSION-PLATFORM.tar.gz` (`Fledge::Runtimes.file_name`) | every desktop and phone runtime |
| Its SBOM | `fledge-runtime-VERSION-PLATFORM.spdx.json` | every one |
| Its NOTICES | `fledge-runtime-VERSION-PLATFORM-NOTICES.txt` | every one |
| Its sources | `fledge-runtime-VERSION-PLATFORM-lgpl-sources.tar.gz` (`LicenseAudit::Notices.source_bundle`) | each platform that ships a component whose source Fledge publishes: glibc and musl Linux, and Windows |

`PLATFORM` is the RubyGems name, or `ios` and `android` for the phones. The SBOM and NOTICES assets are copies of the files inside the runtime, which CI compares. The source bundle keeps its `lgpl-sources` name though it holds NSIS's source, under the CPL, too. `SHA256SUMS` covers them all (`doc/contributors/design/releases.md`).

## Where fledge build finds a runtime

`Fledge::Runtimes` (`lib/fledge/runtimes.rb`) looks for a runtime in this order:

1. the folder `FLEDGE_RUNTIME_DIR` names: a developer's copy of the release, for a build with no network, or a contributor's `tmp/runtime` after `rake runtime`. A runtime there is checked against its pin, when the gem has one (below); when the variable is set and the file is missing, the build fails rather than download;
2. the cache, `$XDG_CACHE_HOME/fledge/runtimes` or `~/.cache/fledge/runtimes`, when its SHA-256 matches the gem's pin;
3. a download from the version's GitHub Release, or from `FLEDGE_RUNTIME_MIRROR`, into the cache, checked against the pin.

A runtime in `FLEDGE_RUNTIME_DIR` that matches its pin is used without a word. One that does not match fails the build, naming the folder, the file, both SHA-256s, and the two ways on: copy the file again from the release, or, for a runtime you built, set `FLEDGE_RUNTIME_DIR_UNCHECKED=1`. With that set, the build uses it and says on standard error that it is unchecked, once per runtime. A runtime the gem pins nothing for, as at a release commit, whose version no pin names until its pin commit, is used, and the build says the same. The variable is read as Bundler reads a switch from the environment: empty, `0`, `f`, `false`, `n`, and `no` are off, in any case, and anything else is on (`Bundler::Settings#to_bool`, `lib/bundler/settings.rb` at bundler 4.0.20). The switch, and an error that names it, follow Bundler's `BUNDLE_DISABLE_CHECKSUM_VALIDATION`, which lets a gem that does not match its checksum install and which Bundler's mismatch error names (`lib/bundler/errors.rb` and `man/bundle-config.1.ronn` at bundler 4.0.20).

The switch exists because the names collide. A runtime's file name carries only Fledge's version, and between releases `trunk` keeps the last release's version and its pins, so `rake runtime` on any ordinary commit writes a file of the very name a pin holds, with other bytes: a check without the switch would fail every build Fledge's CI makes from the runtimes it just built. So every place in this repository that builds apps from its own runtimes says so: each step of `ci.yml`, `ruby-spec.yml`, and `ruby-master.yml` that sets `FLEDGE_RUNTIME_DIR` sets the switch beside it, and passes both into its container; `tasks/parity.rb` and `tasks/mobile_parity.rb` set it for the builds they run; `.github/scripts/check-msix.ps1` sets it with the folder; and `test/test_helper.rb` sets it for the integration tests, while the unit tests pin their fake runtimes themselves (`FakeRuntime.pins`), so they pass whatever the commit's own pins name. Two other designs were weighed. A file that `rake runtime` writes beside its archive to mark it as built here would need no switch, but CI moves runtimes between jobs as artifacts that must be exactly the release's assets (`RuntimeBuilder.release_assets`, checked by the pin and by `release.yml`), so the mark would not travel, and anyone can copy a mark. A second variable for a contributor's builds, leaving `FLEDGE_RUNTIME_DIR` for copies of the release, would draw the line as clearly, but would rename a variable that `doc/runtimes.md` promises 1.x keeps, and that a framework filling the folder with its own builds may already set. Checking only when the folder also holds the release's `SHA256SUMS` would need neither, but would leave unchecked the developer who copies only the archives, as `doc/runtimes.md` tells them to.

A mirror replaces the release's host outright, at the same path below it, `MIRROR/vVERSION/NAME`, which `gh release download vVERSION` fills, so one mirror holds every version a team uses. A mirror that serves other bytes, lacks a file, or cannot be reached fails the build, naming the variable, the mirror, and the file, and the release is never asked. A developer sets a mirror because the release's host is blocked, forbidden, or gone, so a fallback would reach a host they chose not to reach, or hang on one that cannot be reached, and would hide a mirror that lacks a version until the day that host is gone. uv's `UV_PYTHON_INSTALL_MIRROR` is used "exclusively, no automatic fallback" (`crates/uv-python-managed/src/downloads.rs` at astral-sh/uv 4470c33b), and rustup's `RUSTUP_DIST_SERVER` replaces its default the same way; pyenv's `PYTHON_BUILD_MIRROR_URL` falls back, but it is a cache keyed by checksum in front of each package's own URL. The pins make either safe for the bytes, so the choice is only where `fledge build` connects. Fledge has one default host, and a second is the maintainer's to name (decisions.md, 2026-11-04).

## Download retries

`fledge build` downloads runtimes and gems through `Fledge::Download.save`. A download that fails with `Download::Unavailable` (408, 429, or a 5xx) or `Download::Unreachable` (a connection refused, reset, timed out, unresolvable, broken off, or stalled) is tried again after 2, 4, and 8 seconds (`Download::WAITS`), four tries in all, and the last failure is raised when they run out. Each try starts again from the first byte into the same `.part` file and is checked against the pin; nothing reaches the destination unless it matches. A 401 or 403, a 404 or 410, any other 4xx, and a SHA-256 mismatch would answer the same a moment later, so each fails at once. Before each wait, `Fledge::Runtimes` and `Fledge::GemFetcher` say on their log why and how long: `could not download URL: 503 Service Unavailable; trying again in 2 seconds (2 of 4)`.

A mirror is retried the same way and then fails, still without trying the release.

Why these numbers:

- **Four tries** is Bundler's default: `download_gem` runs inside `Bundler::Retry` (`lib/bundler/rubygems_integration.rb`, line 384, at bundler 4.0.20), and `BUNDLE_RETRY` is 3 (`settings.rb`, line 84). Bundler's index requests likewise pass over a refused login, a 404, and other 4xx (`fetcher.rb`, lines 99 to 125).
- **The waits double**, as Bundler's do (`retry.rb`, lines 22 to 31 and 67 to 76), from 2 seconds rather than Bundler's 1, because a release host's outage outlasts a second more often than a gem index's hiccup. They stop at 8, so a host that is truly down fails the build in about 14 seconds.
- **No jitter**: one build's downloads run one after another and are no herd, and a fixed wait is what the log can promise.
- **No setting.** Reading `BUNDLE_RETRY` would tie runtime downloads, which are not Bundler's, to a Bundler setting, and a variable of Fledge's own would be one more name to freeze for a need no one has shown.

`Fledge::Download` starts Net::HTTP with `ignore_eof: false`. By default Net::HTTP reads a body that ends before its `Content-Length` as the whole body (`net/http.rb`, lines 1473 to 1476, net-http 0.10.0 in Ruby 4.1.0-preview1), so a connection that broke off mid-download would be a SHA-256 mismatch, which is never retried. With `ignore_eof: false` it raises `EOFError`, which is `Unreachable`. Net::HTTP's own retry of a GET does not "restart in the middle of a download" (line 2519), so it does not cover this.

A try that keeps sending, but slowly, would never end on Net::HTTP's timeouts, which only bound a single read. So each try keeps a pace (`Download::PACE`): fewer than 10 kB a second, on average, over 30 seconds raises `Download::Stalled`, an `Unreachable`, and the try starts again on a new connection, which usually reaches a faster server. The 30 seconds is also the read timeout, so a server that stops altogether is caught as soon. This is curl's `--speed-limit` and `--speed-time` (curl's window is 30 seconds once asked for a floor) and Cargo's `http.low-speed-limit` (10 bytes a second over `http.timeout`, 30 seconds, after which Cargo "will abort and retry"); the floor is higher than Cargo's because Fledge's files are tens to hundreds of megabytes, where 10 kB a second already means hours. A try still going after 15 seconds says on the log how far it got, every 15 seconds: `NAME: 12.3 MB of 104.9 MB (11%), 0.8 MB/s`.

`Download.save` takes an flock on an empty `NAME.lock` beside its destination before it downloads, and looks again, under the lock, for a file with the pinned SHA-256, as Cargo locks its package cache. So builds that share a cache take turns: the first downloads the file, and each later one says `waiting for another download of NAME to finish` and then finds it there. Without the lock, two `fledge build`s at once streamed into the same `.part` file. The lock files stay: removing one while another process waits on it would let a third take a second lock.

The build tasks' download cache (`tasks/download_cache.rb`) keeps each file in `DownloadCache.folder`, `$XDG_CACHE_HOME/fledge/downloads` or `~/.cache/fledge/downloads`, beside `fledge build`'s own runtimes and gems, in a folder named for its SHA-256 (`downloads/SHA256/NAME`). So every build on a computer shares one copy of each input, and two pins of one name, such as two nights' `rubyinstaller-head-x64.7z`, never replace a file another build is reading. CI keeps that folder between runs ("Pinned downloads in CI", below). It writes each line to standard output and flushes it, since through a pipe Ruby holds standard output back until its buffer fills, and a build killed for its time would lose its last lines. It tries five times, after 5, 10, 20, and 40 seconds, on the same two errors, since a hosted runner can wait longer than a developer at a terminal. It passes `waits: []` to `Download.save`, so its tries replace the product's rather than multiply them.

## Pinned downloads in CI

Each CI job that downloads pinned inputs into the download cache keeps the folder in GitHub's Actions cache, so that its verdict does not hang on a download server answering that runner that day: the runtime jobs, the licenses of the whole upstream tree, the iOS apps, and ruby/spec's jobs. GitHub keeps 10 GB of caches for a repository, removes an entry no run has used for seven days, and past 10 GB evicts the least recently used ("Usage limits and eviction policy", docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching).

These sets were keyed by the SHA-256 of `runtime/sources.yml` (and of `tasks/ruby_spec.rb`, for ruby/spec's), so every change to any pin gave every platform's set a new key, and each job then downloaded all its inputs again, the NDK's gigabyte among them. Between 5 and 19 November 2026 `runtime/sources.yml` changed 16 times and `tasks/ruby_spec.rb` 33, and each change of the first wrote 2.8 GB of new entries, while the old ones stayed until they were evicted. On 20 November the repository's cache held 10.5 GB, 4.4 GB of it in entries no key would match again, and the oldest entry had last been used 21 hours before. The musl jobs kept nothing at all: they download in Alpine's container, under the container's home, and the cache step found no folder to save ("Path Validation Error", job 136031900228), so each one downloaded Ruby's source, OpenSSL, and the rest on every run.

A file in the folder is named for its SHA-256, and `DownloadCache#fetch` takes it only when its bytes have that SHA-256, downloading otherwise. So any earlier set is safe to start from: it cannot hand a build a file other than the pin's. Each job restores the newest set saved under its own prefix, such as `runtime-downloads-x86_64-linux-files-`, which the cache matches by prefix ("Cache key matching", the same page; the `-files-` keeps `x86_64-linux`'s prefix from matching `x86_64-linux-musl`'s sets), and its build downloads only the pins that set lacks. After its last download the job runs `.github/scripts/download_cache_key.rb`, which removes each folder whose SHA-256 no pin in `runtime/sources.yml` or `tasks/ruby_spec.rb` names (`DownloadCache#prune`), so a set does not grow with every pin that ever changed, and writes the SHA-256 of the sorted list of the files left, each as `SHA256/NAME` (`DownloadCache#digest`). The job saves the folder under the prefix and that digest, unless that is the key it restored. The key is everything the entry holds: a file's bytes are its SHA-256's, and the list names every file. So a change to a pin makes a new entry only for the platforms that download it, and a commit that changes no download a platform takes saves nothing for it. The musl jobs mount the runner's folder as the container's own, and key it in the container, whose Ruby the script runs on. The script runs only in a GitHub Actions job, so it never prunes a developer's own cache, which the builds of other commits share.

This costs one full download of every set, the first run after the change, since no old key has the new prefix, and the old entries then go unused and are removed after seven days, or sooner by eviction. A file a build fetches under a SHA-256 that neither pin file names is pruned, and downloaded again the next run; no such pin exists today. `actions/cache`'s single step was not kept, since its post step saves under the key it was given, and a key made of the folder's contents is not known until the job has downloaded. Keying each file by its own SHA-256, one entry for each, would share an input such as llvm-mingw between the jobs that each keep a copy of it, but would need a cache step for each pin, which a workflow cannot generate from `runtime/sources.yml`.

## Pins that name mirrors

A pin in `runtime/sources.yml` may list `mirrors` after its `url`. `DownloadCache#fetch` tries the url, then each mirror in order, and checks every download against the pin's one `sha256`, so a mirror serves the pinned bytes or is refused and the next one tried. When none serves the file, the error names every URL and why it failed. The file keeps the url's name in the cache, in the folder of its SHA-256, whichever URL served it.

One SHA-256 per pin, not one per mirror, keeps the component the same whichever host answered: the license audit and the source bundles read only that a source pin exists.

Only `.github/scripts/fetch_pin.rb` passes mirrors, and only the `replaceability` pins, which it alone reads, name them. `test/runtime_builder_test.rb` fails if any other pin names one, since the runtime builder would never try them, or if a mirror is not HTTPS. Each mirror is downloaded and matched against the pin before it is added.

## Keeping RubyInstaller's head build

RubyInstaller publishes Ruby 4.1 for Windows only as its rolling `rubyinstaller-head` release, and replaces its files every night. Its CI keeps each night's build as an artifact for about 90 days, but without a signature; only the release's `.asc` files let a build be checked against RubyInstaller's key. Fledge moves every platform to each Ruby 4.1 release together (preview2, any later preview, each RC, and 4.1.0), so the Windows runtimes need the head build of each release's day, and that build is gone the next night.

`.github/workflows/keep-rubyinstaller-head.yml` keeps it. Every three hours, at 17 minutes past, it runs `.github/scripts/keep-rubyinstaller-head.sh`, which:

1. asks `cache.ruby-lang.org` for `ruby-VERSION.tar.gz` of each version watched, and takes the newest that is there. Only the newest release's day can still be kept, so an older one that was missed is never kept with a later build. A host that answers anything but found or not found fails the run, so that a release it hid is not passed over;
2. stops when this repository has a pre-release named `inputs-rubyinstaller-head-YYYYMMDD-for-VERSION` for that version. The pre-releases are the only state;
3. reads the times RubyInstaller's API gives its four head files, `rubyinstaller-head-x64.7z`, `rubyinstaller-head-arm.7z`, and their `.asc` signatures, and fails when any is older than the release's tarball (its `Last-Modified`): that build is the night before's, and the next run tries again;
4. downloads the key `runtime/sources.yml` pins for both Windows platforms, checks it against its SHA-256, downloads the four files, and checks both archives with `gpgv` against that key, by fingerprint, as `rake runtime` does ("The RubyInstaller signing key", above);
5. asks RubyInstaller's API again, and fails if the files changed while they downloaded;
6. publishes the four files unchanged on the pre-release, with `gh release create --prerelease --latest=false` on the commit the workflow runs on, and reads each one back from the release and checks its SHA-256.

YYYYMMDD is the day RubyInstaller built the x64 archive, in UTC. The notes give each file's SHA-256 and the time RubyInstaller reports for it, the key's fingerprint and URL, the time the release appeared, and each build's Ruby, read from the `RUBY_DESCRIPTION` in its DLL without running it (`ruby 4.1.0dev (2026-11-12 master 0738c9dfaa) [x64-mingw-ucrt]`, say).

Nothing is overwritten or deleted. A failed download, a bad signature, or a stale build publishes nothing and fails the run, so a failure shows on the Actions page. Only the job's `contents: write` lets it publish, with the repository's own token. Run it by hand with `workflow_dispatch` to try it: `dry-run`, on by default, does everything up to publishing and prints the notes instead. `versions` names the versions to watch; `4.1.0-preview1` shows the whole path, since it exists. The script runs on any computer the same way, with `DRY_RUN=1` and `KEEP_VERSIONS`; its header lists the rest of its environment. `test/integration/keep_rubyinstaller_head_test.rb` runs it against a loopback server standing in for both hosts, and a signing key of its own.

To verify a kept build, download its files and the key, and check them as the workflow did:

## Testing against Ruby's master

A release pins one Ruby, and until the next one is released nothing a runtime builds meets a change in Ruby's master. The phone runtimes edit Ruby's source and link bundled gems' extensions by hand (ADR 079), the musl runtimes build Ruby from source, the launcher follows Ruby's `main.c`, and the parity and ruby/spec checks compare against Ruby itself: each can break on a commit to Ruby's master, and without a run against it the first day they would meet that commit is the day of the release, and Fledge is to be tested against a recent Ruby on every platform (decisions.md, 2026-11-21). `.github/workflows/ruby-master.yml` runs every night, at 20:43 UTC, and by hand (`gh workflow run ruby-master.yml`). It changes no pin on trunk, and no release carries what it builds.

### Where a recent Ruby comes from

| Source | What it publishes | What a runtime can take from it |
|---|---|---|
| `cache.ruby-lang.org/pub/ruby/snapshot/` | `snapshot-master.tar.gz` (and `.xz`, `.zip`) each day, made by Ruby's own release tool, `tool/make-snapshot`, with `snapshot-master.json` beside it giving the date and each file's SHA-256. Only the newest is kept. The tarball is in a release tarball's shape: a generated `configure`, `revision.h`, and every bundled gem's `.gem` in `gems/`. On 2026-11-21 it was master 21ee43fb1e of 2026-11-20, written at 18:35 UTC. | The source tarball the musl and phone recipes build from, in place of a release's. |
| ruby/ruby-dev-builder | A build of master for each runner image every day, about 19:30 UTC, which ruby/setup-ruby installs as `head`. Built for a fixed prefix, for that image's libraries. | Nothing: a runtime needs a static libruby and a tree that can move. |
| RubyInstaller's `rubyinstaller-head` | The Windows build of master, each night, signed (`Keeping RubyInstaller's head build`). | The Windows runtimes' Ruby, as today. |
| rv-ruby, jdx/ruby | Numbered versions and previews only. | Nothing between releases. |
| mise's `ruby@ruby-dev` and `4.1-dev` | Not builds: ruby-build's definitions that clone master from GitHub and compile it on the computer, against its libraries. | Nothing: not relocatable and not pinnable. A contributor may use one as a development Ruby. It needs a Ruby on `PATH` to compile with: without one, Ruby's `configure` writes `BASERUBY = ./tool/missing-baseruby.bat` and `make` stops at once with "executable host ruby is required. use --with-baseruby option", which is how `mise install ruby@4.1-dev` fails in half a minute on a computer with no Ruby. Under `mise x -- env MISE_RUBY_COMPILE=true mise install ruby@4.1-dev` in this checkout, where `mise.toml`'s Ruby is the baseruby, it compiled master of 2026-11-21 in 135 seconds on a 24-thread Ubuntu 26.04 computer. |

So the run takes the snapshot. `tasks/ruby_snapshot.rb` reads the index, downloads the tarball through the download cache, checked against the index's SHA-256, reads the revision from its `revision.h`, and rewrites, in the run's checkout only, the url and sha256 of `mobile.ruby`, `musl-ruby.ruby`, and `ruby-build.ruby` in `runtime/sources.yml`, and the evidence of Ruby's revision that the license audit looks for in the from-source Rubies' component of `runtime/licenses.yml` (`2d08b5f42f` for 4.1.0-preview1). Every other pin stays, and so does every other check. The first job does it once and hands the two files and the tarball to every other job as the run's `ruby-master` artifact, kept 30 days, so all of them build one Ruby commit, even if the snapshot changes while the run goes, and a red night can be built again from the very bytes it tested: put the artifact's two files in `runtime/` and its tarball in the download cache under its SHA-256's folder (`DownloadCache#fetch`), or make the same tarball from a clone of ruby/ruby at the revision with `tool/make-snapshot`.

macOS and glibc Linux are not in the run: their Ruby is rv-ruby's, which builds no snapshot, and a runtime built for them from master would take Fledge's own archive of it ("Fledge's own Ruby builds"), which the run does not build yet. Windows is not in it yet either, though RubyInstaller's head build fits: the Windows runtimes would take that night's build, checked against RubyInstaller's key as `rake runtime` checks the pinned one, and its revision is not the snapshot's, since RubyInstaller builds at another hour.

### What runs against it

Each runtime Fledge builds Ruby for: `x86_64-linux-musl` and `aarch64-linux-musl` in the pinned Alpine Ruby image, as ci.yml's `runtime-musl` builds them, and `ios` and `android` as its `runtime-mobile` does. A build runs the scripted edits, the bundled gems' extensions, the builtin binary, every check of the recipe, and the license audit, which fails on any file nothing accounts for. Trunk's downloads for each platform are restored and never saved: the snapshot is a new file every night, so a set saved with it would be a new entry of the whole set, a gigabyte and more for Android, every night ("Pinned downloads in CI").

What Ruby's master changes on purpose is not a failure, and the run tells it apart without loosening a check the releases rely on:

- **Its revision**, which the audit's evidence names: the run rewrites it, so the audit checks that the snapshot's revision is the one compiled in, as it checks the pin's.
- **Its ABI folder** (`4.1.0+6` on master, `4.1.0+5` on preview1) and its `RUBY_DESCRIPTION` (`ruby 4.1.0dev (2026-11-20 master 21ee43fb1e)`): nothing in Fledge keeps either name, and each build reads both from the tree it built ("The Ruby's description").
- **Fixes the edits take from master** (`process_c`, `thread_c`): master already has them, and each edit leaves a Ruby that has its fix as it is, and still fails on one that has neither its old lines nor the fix (`doc/contributors/design/phone-runtimes.md`, "Scripted edits to Ruby's source").
- **Bundled gems' versions**: the recipes take whatever `gems/` holds. A gem added or removed would show as a gem the runtime lacks or does not know, which is a real difference from 4.1.0-preview1 for the release that moves to it, and the run reports it.

What runs: the four builds, and on each musl runtime that built, the parity check, as ci.yml's `parity-musl` runs it, whose reference there is the runtime's own `bin/ruby`, so master's ("musl Linux's Ruby, built in Alpine"). On master 21ee43fb1e every scripted edit applied, the Android runtime built and passed the audit, 2,900 files in 91 components, in under five minutes on a warm computer, and the x86_64-linux-musl runtime, 3,003 files in 102 components, in under four, describing itself as `ruby 4.1.0dev (2026-11-20 master 21ee43fb1e)`, with its library in `4.1.0+6`. A check that could not run because its build failed counts as failed too. The unit and integration tests, ruby/spec, and the phone apps in the Simulator and on emulators are next, each taking the runtime its build made, as ci.yml's jobs do; until they run, a green night says that Fledge can build from master, not that apps behave on it.

### Who hears about a red night

The run reports to one issue, titled "Ruby's master: nightly status", which it opens the first night. Its body says the newest master Fledge passed on, with the run, and what has failed since: the jobs, the first night they failed, and the link that compares the last passing revision with the first failing one on GitHub, the range of Ruby's commits to read (`tasks/ruby_master_status.rb`). An agent that starts a session reads it with `gh issue list --search "in:title \"Ruby's master: nightly status\""`, then `gh issue view NUMBER`.

Each build records its result instead of failing its job (`continue-on-error` on that one step, and `.github/scripts/ruby-master-result.sh`), and the report job fails the run only on a night that is news: a job fails that had not been failing. A job that recorded nothing, as a cancelled one, counts as failed. So a week of master broken upstream sends one failure email, the first night's, and the issue shows the rest; editing an issue's body notifies no one. The two plain choices were worse: a job allowed to fail is green while it is broken and tells no one, and a run that is red every night is the noise the maintainer asked not to have. The cost is that a second break in a job already failing is not news; the issue's list of jobs and its range of commits are what tell them apart.
