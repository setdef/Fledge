# ADR 006: Compile a Gem That Has No Fitting Build, on Its Own Platform, Against the Runtime's Own Ruby

## Context and Problem Statement

Many gems ship no build for every platform. Tokra compiles its Rust extension with rb-sys when it is installed; Ferro's gems bind Rust crates and are consumed from git tags; redcarpet and many C gems publish only their source; ratatui_ruby publishes precompiled builds for three platforms but not for `aarch64-linux`; a precompiled build's `required_ruby_version` may exclude the runtime's Ruby. A path gem with an extension is in the same position: Bundler never compiles one, so `bundle exec` loads whatever the developer last compiled there, for their own Ruby.

An extension must suit the Ruby that loads it: its headers, its `RbConfig`, its ABI (`Gem.extension_api_version`, which differs between rv-ruby's static Ruby and RubyInstaller's). In a built app that Ruby is the runtime's, not the developer's. How does `fledge build` ship a gem whose extension has no build fit for the app?

## Decision Drivers

- The app's code stays as it is (`decisions.md`, 2026-10-26, decisions 9 and 20): a Gemfile that installs with `bundle install` should ship.
- A precompiled build stays the way a gem ships when one fits: compiling fills only the gaps (the orchestrating agent's direction of 2026-10-27, after the maintainer asked about gems that ship precompiled builds).
- Each platform's app is built on that platform, with its own tools, and Fledge adds no cross-compiling (`decisions.md`, 2026-10-28; 2026-11-04, question D: "My main concern was adding a lot of code, complexity, and surface area for bugs re: cross-compiling.").
- A person who runs the app never meets an error that names a gem (AGENTS.md, Design precedence 1).

## Considered Options

1. Compile it on the platform Fledge runs on, against the runtime's own Ruby, with the developer's toolchain, as `gem install` would.
2. Refuse it, as Fledge first did for every gem with an extension still to compile, every git gem, and every path gem with an extension.
3. Cross-compile it for each target, as rake-compiler-dock does, with a toolchain and a Ruby per target.
4. Compile it with the developer's own Ruby, or ship what the developer last compiled, as `bundle exec` loads a path gem's extension.

## Decision Outcome

Chosen: option 1, because it alone meets every driver. Option 2 refuses Gemfiles that install everywhere else. Option 3 needs a toolchain and a Ruby per target, which was the reason for leaving cross-compiling as later work when this was decided, and ADR 010 since rules it out. Option 4 builds against the wrong headers and ABI: the runtime's Ruby may not load the result.

`fledge build` takes each gem's build as the app's Bundler would choose it, so a precompiled build that fits the target and the runtime's Ruby always wins. A gem whose chosen build still has an extension to compile, from a gem server, from git, or from a folder (the project's own gem among them), is compiled by the runtime's own Ruby, unpacked with its build-only companion, so the headers, `RbConfig`, `Gem::Platform.local`, and extension folder are the runtime's. The compiler is the developer's, held to the runtime's oldest macOS and glibc.

Confidence: high that a gem with no fitting build compiles and runs: `examples/native_app` (redcarpet, and ferro-idna's Rust extension from git) and `examples/real_gems` (a path gem with a C extension) build and run on a fresh computer in CI on arm64-darwin, x86_64-linux, aarch64-linux, and x64-mingw-ucrt, and `examples/nokogiri_app` on arm64-darwin and x64-mingw-ucrt. The musl and ARM64 Windows builds compile none of these examples. That a fitting build wins where one fits is proved by a real gem: `examples/native_app` ships libusb's precompiled build on x64 Windows, where it fits Ruby 4.1, and compiles libusb from source on macOS and both glibc Linuxes, where no build fits; ffi's precompiled builds all exclude Ruby 4.1, so ffi compiles everywhere, a build for another Ruby giving way to the source. CI delivers it on fresh Linux and x64 Windows runners; on macOS it was run on a Mac, and CI's build there runs with each full run.

### Consequences

- Good, because Tokra- and Ferro-shaped Rust gems, C gems published only as source, git gems, and path gems with extensions all ship.
- Good, because the extension is built against the Ruby that will load it, and laid out where RubyGems and Bundler look for it.
- Bad, because building such an app needs a compiler on each platform: Xcode's command line tools, a C compiler and make, MSYS2's UCRT64 toolchain on Windows, and cargo and libclang for a Rust gem.
- Bad, because a compiled build is only as reproducible as the developer's toolchain: the lockfile pins the gems and crates, not the compiler.
- Bad, because each release carries a build-only companion beside each runtime, which a build downloads when it compiles a gem or writes a gem's executables.
- Bad, because a path gem's compiled file in the app differs from the one `bundle exec` loads on the developer's computer; the app's is the one that loads.

### Confirmation

`test/integration/native_build_test.rb`, `test/native_build_floors_test.rb`, and `test/integration/native_gems_test.rb`; CI's Build and Delivery from source jobs build `examples/native_app` and `examples/real_gems` on arm64-darwin, x86_64-linux, aarch64-linux, and x64-mingw-ucrt, and `examples/nokogiri_app` on arm64-darwin and x64-mingw-ucrt, and run them on a fresh runner with no Ruby.
