# What fledge build Writes on a Desktop

This document says what `fledge build` writes for a macOS, Windows, or Linux app: what it takes from the project, the folder and archive it writes, the identity each system reads, the icons, a project of several programs, the installers, the files an app opens, and `fledge build --from`. It is for Fledge's contributors; an app's developer reads `doc/desktop_apps.md` and `doc/building_from_an_app.md`, which this document does not repeat. Each section says why its part is as it is: the options weighed, and the prior art followed. They rest on ADR 010, that each platform's app is built on that platform with its own tools. Signing and notarizing are in `doc/contributors/design/signing.md`; the launcher and `fledge.cfg` are in `doc/contributors/design/launcher.md`; the gems are in `doc/contributors/design/gems.md`.

## The project and its name

`fledge build PATH` takes the program to ship: the one its developer already runs, such as a gem's `exe/my_cool_app`, an application's `bin/server`, or a script's `main.rb`. A file is the entry point. A folder means the one executable its project's gemspec names (`bindir` and `executables`), or else the folder's `main.rb`; any other folder fails, saying which program to name. With `programs` in `fledge.yml`, a folder means every listed program (see "Several programs").

The project's root is the nearest folder, from the entry point's up, that holds a `Gemfile`, a `gems.rb`, a `fledge.yml`, or a gemspec, as Bundler finds a Gemfile by walking up (`SharedHelpers.find_file`). The walk stops at a folder that holds `.git`, so a script never joins a project above its repository; a script with none of these is a project of its own folder. A root that is the developer's home folder is refused. A root with a gemspec but no Gemfile is refused, saying to add one and run `bundle lock`. (`Fledge::App.at`.)

Everything in the root ships, as the built app's `app/`, except:

- `.git`, `.bundle` (the developer's Bundler settings), and `vendor/bundle` and `vendor/cache` (gems Bundler installed or cached for the developer's computer): `App::NEVER_SHIPPED`;
- the folder this build writes to, `--out`;
- every folder that holds a valid cache directory tag, with all it holds.

The tag is how a build's output stays out of later builds, wherever they write. When a build makes the folder it writes to, or finds it empty, it writes `CACHEDIR.TAG` there, beginning with `Signature: 8a477f597d28d172789f06886806bc55`, as the Cache Directory Tagging Specification (https://bford.info/cachedir/) defines it and as Cargo tags its `target` folder (`Fledge::CacheTag`). The copy of the project leaves out every folder whose tag is a regular file, not a link, beginning with those bytes, as GNU tar's `--exclude-caches-all` does. Without the tag, a build into `dist` and then one into `out` would ship the first app inside the second. Do not replace the tag with a rule that recognizes a build by its contents: that needs a pattern for each platform and installer, misses a folder whose app was deleted but whose archive stayed, and could take a developer's own file for a build. Its limits:

- a folder that held anything when the first build went to it gets no tag, so a tag never marks a developer's own files as a cache, and a later build elsewhere ships it unless it is emptied or tagged by hand;
- any tool's valid tag keeps its folder out of the app, which is what the tag means;
- the default `dist` is no exception: a project's own `dist` of source files, which no build went to, ships when the build goes elsewhere.

**NAME** is `fledge.yml`'s `name`, or else the root's gemspec's name, or else the root folder's name, camelized as Bundler's gem template names a module (`Fledge::App.camelize`: each run of letters and digits begins with a capital, and nothing else stays; `my_cool_app` is `MyCoolApp`). A name no system can give a program and a folder fails the build, saying to name the app in `fledge.yml`: an empty one, one with a character some file systems forbid (`/ \ : * ? " < > |` or a control character), one Windows keeps for a device (`CON`, `PRN`, `AUX`, `NUL`, `COM1`, `LPT1`, and the rest, with or without an extension), and one that ends in a period or a space. Taking the name from the project follows the maintainer's instinct "to use the app's primary class/module's name, like MyCoolApp" (`decisions.md`, 2026-10-26, decision 5).

**Why the program you run, with its whole project.** A project already has an entry point, run from its root, and its code may `require` its own library and read its own files at run time; shipping that program with everything beside it keeps all of that working with no file moved, as decision 9 asks. The other shapes weighed were a folder with a `main.rb`, as LÖVE's fused games take one, a configuration file naming the entry point, and the gemspec's `executables`. The first and the last remain as cases of this rule, and configuration is needed only where nothing else says which program to run. The maintainer accepted it ("Ok.", `decisions.md`, 2026-10-26, later, reply 2). It costs size, since an app carries files it may never read, such as its tests, which decision 20 ("Tiny filesize is not a priority") accepts. It also costs the root walk's rules, which keep a stray marker file or an old build from pulling the wrong files in, and which are Fledge's to keep true to Bundler's. A project inside another, as `examples/hello` sits inside Fledge's own gem, marks its root with a `fledge.yml`.

## The build's command line

The options, their forms, and the exit statuses are `exe/fledge`'s help header, which `fledge --help` prints, and `doc/contributors/design/public-interface.md`, "The command's conventions". `--out=DIR` and `--out DIR` both work, and `--` ends the options (GNU Coding Standards, 4.8; POSIX Utility Syntax Guideline 10). `--out` may not be the project's root. `-t` and `--target` are a usage error that says a build is for this computer (ADR 010). Where runtimes come from (`FLEDGE_RUNTIME_DIR`, `FLEDGE_RUNTIME_MIRROR`, the cache) is in `doc/contributors/design/runtimes.md`.

## The folder and the archive

A build writes `OUT/NAME-PLATFORM/`, to try, and `OUT/NAME-PLATFORM.tar.gz`, or `.zip` on Windows, to ship (`Fledge::Assembly`). PLATFORM is the RubyGems platform of the computer that builds (`doc/contributors/design/runtimes.md`, "Platform names and asset names"). The folder is the runtime with the app in it, as LÖVE's fused games and PyInstaller's one-folder bundles ship a folder beside the program:

- **macOS and Linux:** the program `NAME`, `fledge.cfg`, `app/`, the runtime's `bin/`, `lib/`, and `libexec/`, and `notices/` with `NOTICES.txt` and `sbom.spdx.json` from the license audit. A windowed macOS app's folder holds `NAME.app` in their place (see "Identity on each system"); a windowed Linux app's adds `IDENTIFIER.desktop` and `share/icons/`, and `share/mime/packages/IDENTIFIER.xml` when it defines a file type ("Files an app opens").
- **Windows:** `NAME.exe`, `fledge.cfg`, `app\`, `notices\`, and RubyInstaller's tree in `ruby\` (`doc/contributors/design/runtimes.md`, "Layout on Windows").

The layout of the runtime itself is in `doc/contributors/design/runtimes.md`.

**Order.** The build first removes any earlier `NAME-PLATFORM/`, its archive, and every installer of that base name, then works in a temporary folder `.fledge-build-*` inside OUT, so the moves stay on one disk. It unpacks the runtime with tar, moves it into the folder (or a bundle's `Contents/Resources`), writes `fledge.cfg`, copies the project and its gems in, and places each program last, once everything it must describe or seal is there; then it signs, copies `build_tools`, writes the installers, notarizes, and packs the archive. A build that fails removes what it wrote.

**Collisions.** A program may not be named `app`, `fledge.cfg`, or, with `build_tools`, `tools`, ignoring case, nor take the name of a file the runtime holds. Nothing the build adds may replace a file of the runtime's. A Windows app may not hold a symbolic link, which a `.zip` for Windows cannot carry; the build refuses one and says to replace it with what it points to.

**tar** (`Fledge::Archive`) is the computer's own: GNU tar on Linux, bsdtar on macOS, and on Windows the bsdtar Windows ships in `System32`. Every computer that builds apps has it, it keeps modes and symbolic links, and it adds neither code nor a dependency, as the maintainer's words of 2026-10-28 ask ("Code is a liability", `decisions.md`). The rubyzip and minitar gems would be dependencies for what every computer's tar does, and RubyGems' `Gem::Package::TarWriter` refuses a path longer than ustar's 256 bytes, which a gem's files can pass. The cost is that a build writes the app's folder to disk before it archives it, that archives are not reproducible, since GNU tar and bsdtar spell `--sort`, `--mtime`, and `--owner` differently, and that each tool has quirks to work around:

- On Linux and macOS, `tar -czf FILE NAME-PLATFORM` run in OUT, so the archive holds one top folder. On macOS `COPYFILE_DISABLE=1` keeps bsdtar from adding AppleDouble files.
- On Windows the `.zip` is written by .NET's `System.IO.Compression.ZipFile.CreateFromDirectory`, with the folder's own name as the archive's top folder, run by Windows PowerShell 5.1 (`%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe`, named in full), which Windows 11 has, with the two paths in its environment. Windows' `tar.exe` (bsdtar 3.8.9 on Windows 11 in November 2026) cannot write it for every app: it reads its arguments in the ANSI code page, so under code page 1252 an app named `日本語ツール` failed with "Failed to open '??????-x64-mingw-ucrt.zip'", and given only ASCII arguments, run in the folder, it crashed (a segmentation fault) on any name inside the folder that the code page cannot write, such as `日本`, with or without `--options hdrcharset=UTF-8`, and wrote one it can, `Prüfung ü`, in code page 437 with no UTF-8 flag, which Expand-Archive does not unpack as `ü`. .NET writes every name in UTF-8 with the ZIP's UTF-8 flag (bit 11), and keeps empty folders and dotfiles, and Expand-Archive unpacks every name as it was. Windows PowerShell's .NET Framework 4.8 separates a name's folders with backslashes, which the ZIP format forbids (PKWARE's APPNOTE.TXT, 4.4.17.1), unless the program sets `Switch.System.IO.Compression.ZipFile.UseBackslash` to false first, so `Fledge::Archive` sets it. `Compress-Archive`, the cmdlet over the same library, takes no such switch and writes backslashes; 7-Zip and Info-ZIP's `zip` are not on Windows. A ZIP written so carries no Unix modes, which Windows does not read. The cost is starting Windows PowerShell once a build.
- Unpacking is `tar -xf ARCHIVE -C INTO`, but on Windows tar reads the archive from standard input in the folder it unpacks into (`tar -xf -`), since Windows' `tar.exe` reads its arguments in the ANSI code page and cannot open a path outside it; listing a runtime and reading one file from it do the same (`tar -tf -`, `tar -xOf - NAME`), with only a name inside the runtime, all of which are ASCII, as an argument. So a person whose account's name is outside the code page, and whose cache, `TMP`, and projects are in a folder so named, builds as anyone does: on Windows 11 under code page 1252, with the runtime cache, `TMP`, `--out`, and the project all in a folder named `Jürgen 日本`, `fledge build` unpacked the runtime into its work folder there, and the app, with a folder named `挨拶 ü` inside, ran. Nothing Windows' tar unpacks holds such a name inside: a `.gem` is read by RubyGems' own tar reader, in Ruby (`Fledge::GemPackage`), and `--from` takes a folder, never an archive. `ArchiveTest` keeps unpacking, listing, and reading in folders named `Prüfung 日本` on every system CI tests.
- Nothing on Windows packs a `.tar.gz`: an app there ships as a `.zip`, and runtimes are built on Linux and macOS. Windows' tar packs one only for `ArchiveTest`, which needs an archive to unpack, from a folder whose name, and every name in it, the code page can write.

**Standard output.** `fledge build` prints the archive's path and then each installer's, one per line, each joined to `--out` as the developer wrote it; progress and warnings go to standard error (GNU Coding Standards, 4.8). The folder is not printed: a wrapper derives it from the archive's name.

**Checksum files.** Beside the archive and each installer, `fledge build` writes `FILE.sha256`, one line in GNU coreutils' `sha256sum` format, `HEX  NAME` (`Fledge::Checksum`), after the file is final, so a notarized or signed file's checksum is of what ships. Ruby's `Digest::SHA256` writes it, since no tool on all three systems prints that format (macOS has `shasum`, Windows `Get-FileHash` and `certutil`). The file is always written, not behind an option, since every package manager that installs a console app from a release names its SHA-256 and an option would cost a developer a flag for what each of them needs. It is one per archive, as cargo-dist ("a .sha256 file for each archive", `axodotdev.github.io/cargo-dist/book/reference/config.html`) and GoReleaser with `split` (`goreleaser.com/customization/checksum/`) write them, and never one list per release: each platform's app is built on its own computer, so one list under one name would be written once on each. `sha256sum -c` and `shasum -a 256 -c` check it, and `cat *.sha256` makes a release page's list. Every package manager that installs a console app from a release names its SHA-256 (`doc/package_managers.md`).

## Identity on each system

`fledge.yml`'s keys and their rules are `lib/fledge/config.schema.json`. Their defaults (`Fledge::Identity`):

- **name**: NAME, above.
- **kind**: `console`, or `windowed` (see "Windows", below).
- **identifier**: none. A windowed app without one fails, suggesting `io.github.OWNER.NAME` when the gemspec's homepage is on `github.com`, as Flathub names such apps, or else `com.example.NAME`, NAME stripped to letters, digits, and hyphens. It is reverse-DNS; the schema holds its pattern, and 128 characters is an AppUserModelID's limit. A console app may have one, and on Windows it then becomes the process's AppUserModelID.
- **version**: the gemspec's, or else `0.0.0`. It begins with a number and is a version RubyGems reads. A version YAML reads as a number is refused, saying to quote it, since YAML would read `1.10` as `1.1`.
- **publisher**: the gemspec's authors, joined with commas.
- **copyright**, **description** (one line), **long_description**, **homepage** (an `http` or `https` URL with no spaces), and **icon**: none.
- **windows**: an MSIX package's `msix_name`, the identifier by default, and its `msix_publisher`, which `installers: [msix]` requires ("The MSIX package", below); and `visual_c_runtime`, `local` or `central`, how the app comes by Microsoft's Visual C++ runtime when a gem's DLL needs it, none by default (`gems.md`, "The Visual C++ runtime").

These keys put what every system shows in the developer's hands, as the maintainer asked: "Would this affect what shows up in the taskbar? task manager? start menu? desktop icons? app window top-left corner and/or title bar? If so, app devs need to be able to control it." (`decisions.md`, 2026-10-26, decision 18). One `name` serves every place, as Tauri's `productName` does, so the program, its folder, its archive, its bundle, its version information, and its desktop entry never disagree; a display name beside a file name was the other option, and no reason against it was recorded beyond that. A name may hold spaces, so it is a poor command name, and no installer puts the program on a `PATH`. `publisher` defaults to the gemspec's authors, the Ruby project's own statement of who made it, where Tauri takes a part of the identifier, which in Ruby says less. Fledge makes no legal statement for a developer, so `copyright` has no default.

The identifier has no default because none could name a domain the developer controls, and macOS and Windows remember an app by it: a bundle, a Start menu shortcut, a code signature, a desktop entry, a `.deb`, and an uninstall key all name the same string, so a made-up one would follow the app for good. Tauri, Briefcase, and Flatpak require one too. The cost is that a windowed app's first build fails until its developer writes one.

### macOS

A windowed app is `NAME.app` (`Fledge::MacBundle`); a console app stays a folder, since a terminal tool has no bundle.

```
NAME-PLATFORM/NAME.app/Contents/Info.plist
                              MacOS/NAME                    the launcher
                              MacOS/{app,bin,fledge.cfg,lib,libexec} -> ../Resources/...
                              MacOS/HELPER                  each console program (see "Several programs")
                              Resources/NAME.icns
                              Resources/{app,bin,fledge.cfg,lib,libexec,notices}
                              _CodeSignature/CodeResources
```

The runtime and the app live in `Contents/Resources`, and symbolic links in `Contents/MacOS` point at them. Ruby takes its prefix from the program that holds libruby (ADR 001), and the launcher reads `fledge.cfg` and `app/` beside itself, so its neighbors must be reachable from `Contents/MacOS`; but Apple's tools expect only code there, and codesign wants a data file in a nested-code location signed on its own. The launcher runs the app from its real folder under `Resources`, so `__dir__` and `$0` agree (`doc/contributors/design/launcher.md`).

`Info.plist` holds Tauri's keys, less those that describe Tauri's own runtime (`CSResourcesFileMapped`, `LSRequiresCarbon`):

| Key | Value |
|---|---|
| `CFBundleDevelopmentRegion` | `en` |
| `CFBundleDisplayName`, `CFBundleName`, `CFBundleExecutable` | the name |
| `CFBundleIdentifier` | the identifier |
| `CFBundleInfoDictionaryVersion` | `6.0` |
| `CFBundlePackageType` | `APPL` |
| `CFBundleShortVersionString` | the version's leading whole numbers, at most three, as Apple's reference asks (`0.0.1.pre.6` is `0.0.1`) |
| `CFBundleVersion` | `fledge.yml`'s `macos: build`, or else the short version |
| `LSMinimumSystemVersion` | the runtime's floor, `Platform::MACOS_MINIMUM` |
| `NSHighResolutionCapable` | true |
| `CFBundleIconFile` | `NAME.icns`, with an icon |
| `NSHumanReadableCopyright` | the copyright, when there is one |
| `CFBundleDocumentTypes` | the files the app opens (see "Files an app opens") |

Fledge writes these as JSON and converts them with `plutil -convert xml1`. plutil, codesign, ditto, and hdiutil, the tools that make a bundle and its disk image, ship with macOS in `/usr/bin`. Unsigned, the bundle is signed ad hoc with `codesign --force --sign - --identifier IDENTIFIER NAME.app`, which seals `Info.plist` and every resource and signs the launcher for them: Apple Silicon runs only signed code, and `codesign --verify --strict --deep` calls a bundle broken unless its program's signature seals the rest. With `--sign`, the bundle is signed as `doc/contributors/design/signing.md` says.

### Windows

A windowed app's program is the runtime's `launcherw.exe` renamed, and a console app's is `launcher.exe`; the other never ships. Whether Windows gives a program a console is its PE header's Subsystem field, fixed in the executable, so the kind is fixed when the app is built. Each runtime carries both launchers, built from one source, as RubyInstaller ships `rubyw.exe` beside `ruby.exe` and PyInstaller a windowed bootloader beside its console one, and *console* and *windowed* are PyInstaller's names for the two kinds. Flipping one launcher's Subsystem field in `fledge build` was the other option, but one program serving both kinds would carry the windowed kind's message box, and every console app would import USER32 for nothing (`doc/contributors/design/launcher.md`, "Windows"). A windowed app's standard streams reach no console, as `rubyw.exe`'s do not, so a developer who wants its output redirects it. Every program, console or windowed, gets its identity from rcedit (`Fledge::WindowsResources`), from the runtime's `tools\rcedit.exe`, copied to a temporary folder and run from there, since on Windows on ARM the emulator's cache service keeps an emulated program open after it exits (`doc/contributors/design/runtimes.md`):

- `--set-version-string` for FileDescription, ProductName, and InternalName (the name), OriginalFilename (the program's file name), and, when there are, CompanyName (the publisher), LegalCopyright (the copyright), and Comments (the description). Task Manager shows FileDescription.
- `--set-file-version` and `--set-product-version` with the version as written; rcedit keeps it as FileVersion and ProductVersion and makes its leading numbers FILEVERSION and PRODUCTVERSION.
- `--set-icon` with the developer's `.ico`.

FILEVERSION and PRODUCTVERSION hold at most four parts of 16 bits each. Fledge refuses a version that does not begin with a number, or that has a part above 65535 among its first four leading whole numbers, itself, since rcedit would let it wrap. rcedit keeps the launcher's manifest. The launcher makes `fledge.cfg`'s `identifier` the process's AppUserModelID before any window opens (`doc/contributors/design/launcher.md`).

### Linux

A windowed app is the same folder as a console one, with `IDENTIFIER.desktop` at its top, as an AppImage's AppDir keeps it, and its icons at `share/icons/hicolor/SIZExSIZE/apps/IDENTIFIER.png`, with the definitions of the file types it defines at `share/mime/packages/IDENTIFIER.xml` ("Files an app opens"), the layout of `$XDG_DATA_HOME`, so installing it by hand is copying `share` into `~/.local/share` and the desktop entry into its `applications` with the program's full path in `Exec`, then running `update-mime-database ~/.local/share/mime` when it defines a file type. A console app gets no desktop entry. The entry (`Fledge::DesktopEntry`), which `desktop-file-validate` accepts:

```
[Desktop Entry]
Type=Application
Version=1.5
Name=NAME
Comment=DESCRIPTION          when there is a description
Exec=PROGRAM                 PROGRAM %F when the app opens files
Icon=IDENTIFIER              when there is an icon
Terminal=false
MimeType=TYPE;...            when the app opens files
```

`Name` and `Comment` escape backslashes, line breaks, tabs, and a leading space as the Desktop Entry Specification asks. `Exec` doubles `%` and quotes a program whose name holds a space or a reserved character, escaping `"`, `` ` ``, `$`, and `\` inside the quotes (`Exec="Hello Window"`). A window class (`StartupWMClass`) is not written: the GUI library chooses it.

## Icons

`fledge.yml`'s `icon` is a path without an extension, relative to the root (`Fledge::Icon`), as Briefcase's `icon` is, to which each build adds its system's extension. An `icon` that ends in an extension fails, saying to drop it. Each build takes its own files:

- **macOS:** `ICON.icns`, copied to `Contents/Resources/NAME.icns`.
- **Windows:** `ICON.ico`, written into each program by rcedit and into the setup program by makensis; and for an MSIX package `ICON-44.png`, `ICON-50.png`, and `ICON-150.png` (`Icon::MSIX`), its logos.
- **Linux:** `ICON-16.png`, `ICON-32.png`, `ICON-64.png`, `ICON-128.png`, `ICON-256.png`, and `ICON-512.png` (`Icon::LINUX`), Briefcase's six. The build ships each one there is into `share/icons/hicolor`, names the missing ones on standard error as a warning, and fails only when there is none, naming the smallest. The AppImage's top-level icon is the 256-pixel PNG, or else the largest there is, as Tauri's bundler picks the largest square.

A missing file fails that platform's build with what it needs and how to make it (`Icon::MAKE`). Fledge reads none of these formats and checks no sizes, so it cannot tell a developer that an `.ico` lacks a size Windows shows; Windows scales the nearest. The developer makes three kinds of file, where a converter could make them all from one PNG, and each icon is exactly what they drew at each size; `iconutil -c icns` on any Mac makes the `.icns` from an `.iconset`. This is less code than any other way, and what Briefcase and Tauri's bundler ask, whose separate `tauri icon` command makes the files its `bundle.icon` lists. The others weighed each fall short: ImageMagick is a large program a developer may lack, of different major versions on different Linux distributions, so a pin would be a wish; libvips writes no `.ico`; chunky_png's bilinear resampling blurs an icon shrunk from 1024 to 16 pixels, and it writes neither `.icns` nor `.ico`; icoutils' `icotool` runs only on Linux and makes only `.ico`; macOS's `sips` and `iconutil` leave Windows and Linux with nothing; and a PNG codec, resampler, and icon writers of Fledge's own are the code the maintainer's words of 2026-10-28 remove ("Code is a liability", `decisions.md`). rcedit numbers a program's icon group itself, not 32512 as Tauri does; Explorer shows a program's first group whatever its number. A phone's icons come from the same key (`doc/contributors/design/phone-projects.md`, "Identity on a phone").

## Several programs

A project often has several ways in that share one codebase, such as a command-line program, a terminal program, and a graphical one that share a save file. `programs` ships them as one download, with one runtime, one copy of the project, and one set of gems, so programs that share files read each other's, as they do when run with `ruby` from one checkout. Each program is a renamed copy of the launcher over that one folder, as PyInstaller's multipackage bundles share one `COLLECT` and Tauri's bundler puts every binary of a crate in one app. One launcher that took the program as an argument could not be both a console program and a windowed one on Windows, nor a bundle's executable and a terminal command on macOS; and a bundle of its own for each program, as Briefcase builds each app of a project, would copy the runtime that `programs` exists to share. The agents chose this from that prior art; `decisions.md` records no word of the maintainer's on it.

`fledge.yml`'s `programs` is a list of mappings, one per program, in the developer's order (`Fledge::Config::Program`). Each has:

- **path**, required: the program's file, relative to the root, with `/` between folders, inside the project.
- **name**: as an app's name, but for this program. A console program's defaults to the path's file name less its extension (`bin/cli` is `cli`), as Cargo names a binary: it is the command someone types. A windowed program's defaults to the project's NAME, since it is what the Dock, the Start menu, and the window list show, and `gui/main.rb` would otherwise show "main". No two programs share a name, ignoring case, since Windows' and macOS's file systems ignore it.
- **kind**: `console`, the default, or `windowed`.
- **identifier** and **icon**, as an app's, for this program. A windowed program needs an identifier, and no two programs share one, since Windows groups windows and attributes notifications by it.

With `programs`, `kind`, `identifier`, and `icon` at the top of `fledge.yml` are refused, naming where to move them. `name`, `version`, `publisher`, `copyright`, and `installers` stay at the top: `name` names the folder, its archive, and the installers, and each program's version information carries the project's version, publisher, and copyright. At most one program is windowed: on macOS a windowed program is a bundle, which must hold its runtime to be dragged to Applications, signed, and sealed, so a second would need a second runtime, and on Linux an AppImage of its own. A project whose programs are all console gets no installers, and `installers` with entries is refused there.

**fledge.cfg.** With several programs, `fledge.cfg` keeps `gemfile` and `system_libraries` at the top and gives each program a section headed by its name, holding its `entry` and `identifier`. Each launcher reads the section whose name is its own file name, less `.exe`, ignoring case. A project with one program, or a build of one program, writes `fledge.cfg` with no section, and its launcher runs under any name. The format, and what a launcher does with a missing or damaged section, are in `doc/contributors/design/launcher.md`.

**Layout.** One folder holds the runtime and `app/` once, and every program beside them:

- **Windows:** `NAME.exe` for the windowed program (`launcherw.exe` renamed) and one `.exe` per console program (`launcher.exe` renamed), each with its own name and icon from rcedit and the project's version, beside `fledge.cfg`, `app\`, and `ruby\`.
- **Linux:** each program beside `lib/` and `app/`, and the windowed program's desktop entry and icons.
- **macOS with a windowed program:** everything is in its bundle. Each console program is a copy of the launcher in `Contents/MacOS`, beside the bundle's executable, where Apple puts a bundle's helper tools, so the bundle's signature seals them. The folder beside the bundle holds a symbolic link for each, `my-game-cli -> MyGame.app/Contents/MacOS/my-game-cli`, and the launcher resolves the link to the runtime it lives in.
- **macOS with no windowed program:** the Linux layout.

**Installers.** The installers are the windowed program's, with its identity: its name in the disk image, the setup program's shortcut and uninstall entry, the AppImage's and the `.deb`'s desktop entry. Each holds the whole folder, so every console program installs beside the windowed one, as Tauri's installers install every binary but the main one: inside the bundle on macOS, in `%LOCALAPPDATA%\Programs\NAME` on Windows, and in `/usr/lib/PACKAGE` from a `.deb`. Nothing puts a console program on a `PATH`. An AppImage runs its windowed program; its console programs are reached through `--appimage-extract`.

**Signing.** `--sign` signs every program: signtool signs every PE file of the folder, every launcher copy among them; codesign signs each console program in `Contents/MacOS` before the bundle, inside out, and every Mach-O file of a folder with no bundle. Unsigned, each launcher copy keeps the signature it arrives with, and the bundle's ad hoc signature seals every file in it.

**Building one program.** `fledge build FILE`, where FILE is one of the listed programs, builds that program alone, as Cargo's `--bin` and Briefcase's `-a` build one, and as a project with no `programs` builds its one program: its folder, archive, and installers are named after the program, with the program's name, kind, identifier, and icon and the project's other keys, and its `fledge.cfg` has no section. A FILE `programs` does not list is refused, listing the programs. A phone's build takes one program: the one PATH names, or else the windowed one, or else the first.

**Messages.** `fledge build` exits 0, 1 for a build that fails, and 2 for a usage error. Each refusal names the full path of `fledge.yml` and the program, and says what to write instead:

- `fledge.yml: programs must be a list of at least one program, each a mapping such as - path: bin/cli`
- `fledge.yml: program 2 has no path, the program's file in the project, such as path: bin/cli`
- `fledge.yml: program 1's path, "../cli", must name a file in the project, with / between folders, such as path: bin/cli`
- `fledge.yml: the program bin/cli has 'paht', which Fledge does not know. A program knows path, name, kind, identifier, and icon.`
- `fledge.yml: the program bin/cli: kind must be console or windowed, not gui`
- `fledge.yml: a/cli and b/cli.rb are both named cli; give each its own`, and the same when a windowed program takes the project's name and another program has it
- `fledge.yml: gui/main.rb and editor/main.rb are both windowed, and a project has one windowed program; build another on its own, with fledge build editor/main.rb`
- `fledge.yml: with programs, kind belongs to each program; move it into the program it describes`
- `fledge.yml lists the program bin/clli, but the project has no such file. List the program you run, such as path: bin/cli.`
- `bin/protocol is not one of the programs fledge.yml lists. Build the project, or one of gui/main.rb, bin/cli, bin/tui.`

A program renamed by hand in a folder of several exits with 66 and `renamed: this app is incomplete: ROOT/fledge.cfg has no program named renamed`.

## Installers

A windowed app gets the installers its platform has (`Fledge::Installers`), or the ones `installers` lists, which may be `[]`. Each is written beside the archive, from the built folder, named as the archive is, with no version, so a script finds it by platform:

| Value | Platform | File |
|---|---|---|
| `dmg` | macOS | `NAME-PLATFORM.dmg` |
| `nsis` | Windows | `NAME-PLATFORM-setup.exe`, ending as Tauri's do |
| `appimage` | Linux | `NAME-PLATFORM.AppImage` |
| `deb` | glibc Linux, `x86_64-linux` and `aarch64-linux` | `NAME-PLATFORM.deb` |
| `msix` | Windows | `NAME-PLATFORM.msix` ("The MSIX package", below) |

The default is `dmg`, `nsis`, and `appimage` (`Config::DEFAULT_INSTALLERS`); `deb` and `msix` are never defaults, since a default set for 1.x takes new values only on request, and `msix` needs the Windows SDK's MakeAppx and `windows: msix_publisher`, which the build refuses to go without. A build makes the listed ones for its own platform and ignores the rest, so `deb` builds nothing on musl. An unknown value fails, and a console app that lists any fails. What the setup program and the AppImage copy in comes from the runtime's `tools` folder, which no app holds unless `build_tools` is set (`doc/contributors/design/runtimes.md`). With `license_file`, the setup program shows it and the `.deb` holds it; the file must be UTF-8, and a byte order mark at its start is dropped.

**Why these, by default.** An archive is all a terminal tool needs, but not all a desktop app's people expect, nor all the systems need: Windows shows an app's notifications only when a Start menu shortcut carries its AppUserModelID, which no zip makes; Mac apps are downloaded as disk images more than any other way, and notarization staples its ticket to one; and Linux users take an app as one AppImage more readily than a tarball. So a windowed app gets every installer its platform has, as Tauri's `bundle.targets` defaults to all, with no configuration. The choice lives in `fledge.yml`, not on the command line, because what an app ships is a property of the app, which every computer that builds it should agree on; and one list serves every platform, since each build makes its own platform's and ignores the rest. A console app gets none, since none of them would put its program on a `PATH`; it reaches people through the package managers (`doc/package_managers.md`). The cost is time, compressing a disk image or a file system and running makensis, which `installers: []` skips, and `mksquashfs` on the Linux computer that builds an AppImage. A default needs no tool some computers of the platform lack, which is why `deb` is opt-in ("The .deb"), and the default set takes new values only on request through 1.x (`doc/contributors/design/public-interface.md`, "How 1.x adds"). Waiting for a developer who needs them: `.msi` and `.rpm`, a per-machine NSIS install, NSIS in other languages, closing a running copy of the app before reinstalling it, and installers for console apps.

## The disk image

`Fledge::Dmg` makes what Tauri's create-dmg makes: the bundle, copied with `ditto` (which keeps its signature, links, and modes), beside a link named `Applications` to `/Applications`, in a staging folder; then `hdiutil create -volname NAME -srcfolder STAGE -fs HFS+ -format UDZO -ov FILE`, a read-only, zlib-compressed image of a Mac OS Extended volume, as create-dmg's are. With `--sign`, the image is then signed (`doc/contributors/design/signing.md`). A background picture and a laid-out window, which create-dmg writes as a `.DS_Store` of Finder's private format, are left out.

On macOS 26 and newer, `hdiutil create` prints that `diskutil image create` replaces it; Fledge runs it anyway and reads its output only when it fails, since macOS 14 and 15, the oldest Fledge apps run on, have only `hdiutil`.

**"Resource busy."** `hdiutil create -srcfolder` makes a container, puts a file system in it, and copies the folder to it (`man hdiutil`, DESCRIPTION), mounting that scratch volume while it copies and detaching it before it writes the image. It fails with "create failed - Resource busy" when another process holds the volume as it detaches; `man hdiutil`, DIAGNOSTICS, says EBUSY "often appears when a volume can't be unmounted". GitHub's macOS runners hit it now and then, and the runner image's maintainers traced it to `XProtectBehaviorService` holding the new image and recommend trying again (actions/runner-images#7522). Fledge cannot keep XProtect or Spotlight off a volume hdiutil mounts inside its own run, so it does what create-dmg does (`create-dmg`, lines 34 and 49 to 86, at a2b71d0): when the error holds "Resource busy", it waits and runs the same command again, after 2, 4, 8, and 16 seconds (`Dmg::WAITS`), five runs in all. Any other failure, or a fifth busy one, fails the build with hdiutil's words. Matching the text rather than the exit status, which is 1 for real errors too, keeps a real error from costing 30 seconds. electron-builder retries every hdiutil command up to five times for exit codes it calls transient, and dmgbuild retries `hdiutil detach` twelve times; create-dmg's rule is the narrowest. The race cannot be provoked on demand, so `test/integration/dmg_test.rb` puts an `hdiutil` first on `PATH` that fails with the runner's message before it runs the real one.

## The NSIS setup program

`Fledge::Nsis` writes an NSIS script as Tauri's `installer.nsi` does for its default `currentUser` mode, without Tauri's own plug-in (`Fledge::Nsis::Script`), and compiles it with the Windows runtime's `tools\nsis\Bin\makensis.exe` (NSIS's own release), copied to a temporary folder, run as `makensis -V2 -NOCD -NOCONFIG -INPUTCHARSET UTF8 SCRIPT` with `NSISDIR` pointing at the copy, so every computer builds the same installer from the same pieces. The script is UTF-8 with a byte order mark. What the runtime's `tools\nsis` holds is listed in `tasks/runtime_builder/windows.rb` (`NSIS`).

- **Settings:** `Unicode true`, `ManifestDPIAware true`, `SetCompressor /SOLID lzma` (NSIS's default and Tauri's), `RequestExecutionLevel user`, Modern UI 2, and English.
- **Where:** `InstallDir "$LOCALAPPDATA\Programs\NAME"`, Windows' known folder for programs one person installs (`FOLDERID_UserProgramFiles`), as electron-builder's per-user installers use; Tauri's `$LOCALAPPDATA\NAME` sits beside apps' data. No administrator is needed. The folder page lets a person choose another, and `.onInit` reads the uninstall entry's `InstallLocation`, so a reinstall goes where the last install went.
- **Pages:** with `license_file`, Modern UI's license page first (`MUI_PAGE_LICENSE`), as Tauri's is, which a person accepts before anything else; then the folder, the files, and the finish page, which offers to run the app and, through its "show readme" check box, unchecked, as Tauri does, to make a desktop shortcut. The uninstaller shows a confirm page and its progress. A silent install (`/S`) shows no page and makes no desktop shortcut. The license page reads a copy of the file with a UTF-8 byte order mark, as Tauri's bundler writes one for its Unicode installer, and DOS line endings, which NSIS's manual asks of `LicenseData` (section 4.8.1.26).
- **The Visual C++ Redistributable:** for an app built with `windows: visual_c_runtime: central`, a first section, before anything is installed, installs Microsoft's Redistributable when the computer lacks a DLL the app's launcher looks for ("The Visual C++ Redistributable", below).
- **Install:** if the folder holds an `uninstall.exe`, run it first, silently, in place (`ExecWait '"…\uninstall.exe" /S _?=$INSTDIR'`), as electron-builder's installers do, so a file the old version had and the new one does not is not left behind; then copy the folder, write `uninstall.exe`, and make `$SMPROGRAMS\NAME.lnk` to the program.
- **The shortcut's AppUserModelID:** each shortcut's `System.AppUserModel.ID` is set to the identifier, the AppUserModelID the launcher gives the process, through IShellLink, IPersistFile, and IPropertyStore with NSIS's System plug-in and its COM headers, as Tauri's `SetLnkAppUserModelId` macro does, but as the `VT_LPWSTR` the property is (`Win\Propkey.nsh`). Windows shows an app's toasts only when a Start menu shortcut carries the same ID the process has.
- **Uninstall key:** `HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall\IDENTIFIER`, by identifier rather than Tauri's product name, since two apps may share a name but not an identifier: `DisplayName`, `DisplayVersion`, `Publisher` (when there is one), `URLInfoAbout` and `HelpLink` (the homepage, when there is one, as Tauri's `installer.nsi` writes them), `DisplayIcon`, `InstallLocation`, `UninstallString`, `QuietUninstallString` (with `/S`), `NoModify`, `NoRepair`, and `EstimatedSize` in KiB.
- **Version information** of the setup program, by `VIAddVersionKey`: ProductName, FileDescription (`NAME Setup`), FileVersion and ProductVersion (the version as written), CompanyName and LegalCopyright when there are, and `VIProductVersion` and `VIFileVersion` of the four Windows numbers. The app's `.ico` is its icon and the uninstaller's (`MUI_ICON`, `MUI_UNICON`). `BrandingText` is the copyright, or the name.
- **Uninstall:** delete the shortcuts, then by name each file the install wrote, then each folder it made, deepest first, then the install folder only if it is empty, as Tauri's does, so nothing a person put there is lost; then the uninstall key and the file associations.
- **Signing:** with `--sign` or `--sign-command`, `!uninstfinalize` and `!finalize` lines (`doc/contributors/design/signing.md`).

A build that fails reports makensis's output, and names a signing command's failure on the setup program or its uninstaller.

**NSIS's own release.** Every setup program carries NSIS's stub and its compressor's decoder. LZMA, NSIS's default, is under the Common Public License 1.0, whose section 3 asks that a program distributed as object code say where its source is; Fledge publishes NSIS's source beside each Windows runtime and names it in every app's notices (`doc/contributors/design/license-audit.md`, "notices/sources/ and the source bundles"), and nothing is asked of the app. The alternative, NSIS with its zlib compressor and a makensis Fledge built for every computer, kept that license out at the cost of a build of Fledge's own to maintain. On 2026-10-28 the maintainer accepted the orchestrating agent's recommendation to use LZMA with NSIS's source published, with "Code is a liability" (`decisions.md`).

**The Visual C++ Redistributable.** An app built with `windows: visual_c_runtime: central` carries none of Microsoft's Visual C++ runtime, and its `fledge.cfg` names the runtime's DLLs its gems need, which its launcher looks for in System32 before Ruby starts (`gems.md`, "The Visual C++ runtime"). Microsoft's way for such an app is an installer that runs the Redistributable "as a prerequisite on the target system before you install your application" ("Redistribute Visual C++ files"), so its setup program does that, in a section `VisualCRuntime` before `Install`, as Tauri's `installer.nsi` puts its `WebView2` section before its own (`webview2.nsh`, Tauri at `c51c182d`). `Nsis` reads the names from the folder's `fledge.cfg`, as `Msix` does, so a setup program built with `--from` agrees with the folder it installs; an app without them gets no such section.

- **How it tells.** It looks for those files in the native System32, the check the launcher makes. The setup program is 32-bit, which Windows shows SysWOW64 for System32, so it looks in `$WINDIR\Sysnative`, the native folder's name to a 32-bit program (Microsoft's "File System Redirector"). The other way is the registry value the Redistributable writes, `Installed` under `HKLM\SOFTWARE\Microsoft\VisualStudio\14.0\VC\Runtimes\x64` (or `arm64`), which Tauri's guide's example hook reads. The key is the installer's record and the files are what the app needs, and the two can disagree: Microsoft's x64 Redistributable "contains both ARM64 and X64 binaries" and installs the ARM64 ones on an ARM64 computer ("Latest supported Visual C++ Redistributable downloads"), so an ARM64 app's DLLs can be there with no `arm64` key, and a DLL another program put in System32 has no key at all. A setup program that checks what the launcher checks never installs what the app would not have asked for, and never passes a computer the app then refuses. Neither checks the DLLs' version, which Microsoft asks to be at least the building tools'.
- **How it downloads.** From Microsoft's permanent link for the platform, the one the launcher's message names (`Nsis::REDISTRIBUTABLES`: `https://aka.ms/vc14/vc_redist.x64.exe`, or `vc_redist.arm64.exe` for `aarch64-mingw-ucrt`, as Microsoft's page asks: "The redistributable package architecture must match your app's target architecture"), into `$PLUGINSDIR`, the setup program's own temporary folder, which NSIS deletes when it exits. It calls urlmon's `URLDownloadToFileW` through the System plug-in, which the runtime's NSIS carries already for the shortcut's AppUserModelID. Tauri downloads with the NSISdl plug-in, and the inetc plug-in is another's; either would be a new component in every Windows runtime, with its license and its source to publish. `URLDownloadToFileW` goes through WinINet, which follows the link's redirect to Microsoft's download host, checks its HTTPS certificate, and uses the computer's proxy settings.
- **How it installs.** The call's status is not trusted alone: an earlier attempt's file is deleted before the download, and the installer runs only when the download returned `S_OK` and left a file with something in it; a failed download, a download that left nothing, and an installer that could not be started (`ExecWait`'s error flag) each say so in the details. It runs the download with Microsoft's switches, `/install /passive /norestart`, which shows Microsoft's progress and asks nothing, or `/quiet` in its place when the setup program itself runs silently (`/S`); `/norestart` as Tauri's guide advises. The Redistributable installs for the whole computer and asks for an administrator itself, through UAC, where Windows shows its verified publisher; the setup program stays per-user (`RequestExecutionLevel user`) and asks for nothing more. Its exit status is shown in the details, not judged: the setup program looks for the files again, which is what decides, so a status that means success with a restart pending, or a newer version already there, needs no table of its own.
- **When it is still missing.** Offline, with elevation declined, or with the Redistributable's installer failed, a message box names the missing DLL and Microsoft's link and offers Abort, Retry, and Ignore. Abort leaves the computer as it was, since nothing is installed yet, an earlier version of the app included; Retry looks again, and downloads again, once the person has connected or installed it from the link; Ignore installs the app, whose launcher names the Redistributable when it starts. A silent install aborts, with NSIS's status 2, as Tauri's `WebView2` section aborts when its download or install fails, so a deployment tool sees the failure rather than an app that cannot start.
- **What it does not check.** No hash: the permanent link serves whichever version is newest, so there is none to pin. No signature: `WinVerifyTrust`, which the System plug-in could call, proves only that some trusted publisher signed the file, and proving the publisher Microsoft means reading the signer's certificate too (`CryptQueryObject`, `CertGetNameStringW`), code of Fledge's own in every setup program to repeat what HTTPS from Microsoft's own host gives, and what a person gets who follows the launcher's link in a browser. Tauri's download checks neither. Before the installer runs as administrator, UAC shows its signer.
- **What it does not carry.** The Redistributable's installer is not put inside the setup program: that is distributing Microsoft's files, under the terms `local` is, and nothing setdef publishes or CI uploads may carry them (`decisions.md`, "Neither should setdef, right?"). A setup program that carries it, for computers with no network, waits for a developer who needs it, as a choice of their own.
- **Uninstalling** leaves the Redistributable, which other programs share, as Tauri's guide advises.

`test/nsis_test.rb` checks the section's text, and `test/integration/makensis_test.rb` runs a compiled setup program on Windows that needs a DLL no computer has, with a loopback server in place of Microsoft's link and a silent NSIS program the test compiles in place of the Redistributable: it must download it, run it with `/install /quiet /norestart`, and, the DLL still missing, abort before it installs anything. The address comes in through `Nsis.new`'s `redistributable:`, a Ruby argument that `fledge build` never gives, and neither `fledge.yml` nor the command line has; Fledge's Ruby classes are not part of the public interface (`public-interface.md`). Unproven: the real download and install on a computer without the Redistributable, which needs one, a person to approve the elevation, and ARM64 Windows for the ARM64 one.

## The AppImage

`Fledge::AppImage` makes a type 2 AppImage as appimagetool does (`src/appimagetool.c` at its 1.9.1 tag, `sfs_mksquashfs`, lines 97 to 215), without running appimagetool, which is itself an AppImage that needs FUSE to run, downloads its runtime unless told otherwise, and does nothing more for Fledge than run `mksquashfs` and validate the desktop entry, which Delivery does with `desktop-file-validate`:

1. Copy the built folder, which already has the desktop entry at its top and its icons under `share/icons`, into an `AppDir`, keeping modes and links.
2. Add `AppRun`, a symbolic link to the program (the launcher finds its runtime through `/proc/self/exe`, so a link is all it needs), and, with an icon, `IDENTIFIER.png` at the top, the 256-pixel PNG or else the largest, and `.DirIcon`, a link to it.
3. Run `mksquashfs APPDIR FILE -offset SIZE -comp zstd -b 128K -root-owned -noappend -mkfs-time 0 -quiet`, SIZE being the runtime's size, from squashfs-tools 4.4 or newer, which a Linux developer installs from their distribution. A computer without it is told to install squashfs-tools.
4. Write the runtime, `tools/appimage-runtime` from the Linux runtime, AppImage's own release, into the room `-offset` left, and make the file executable.

Update information (zsync) and a signature, which appimagetool can embed in the runtime's sections, are left empty. The AppImage behaves as every AppImage does: with FUSE it mounts itself; without FUSE it says "Cannot mount AppImage, please check your FUSE setup." and runs only when asked to extract itself, with `APPIMAGE_EXTRACT_AND_RUN=1` or `--appimage-extract-and-run`. `--appimage-extract` unpacks the AppDir, notices included. A person who downloads one makes it executable, as with any AppImage. Delivery runs it with FUSE and without (`.github/scripts/deliver-appimage.sh`).

**AppImage's released runtime.** AppImage's own build links libfuse 3, LGPL-2.1, into its runtime, an MIT program that is neither the developer's app nor Fledge's launcher. Publishing that runtime's source with libfuse's is what LGPL-2.1, section 6(a), asks of a work linked with the library, and the app inside only runs as its child, so nothing is asked of the app (`doc/contributors/design/license-audit.md`, "LGPL linked into a component that is not Fledge's"). The alternative was a runtime Fledge built without libfuse, with a loader of the computer's libfuse and a patch that extracted the AppImage where it could not mount; the maintainer accepted the released runtime on 2026-10-28, with NSIS's release above. So an AppImage behaves as every AppImage does, and on a computer without FUSE runs only when asked to extract itself. `mksquashfs` is GPL-2.0, which reaches no app: it runs on the developer's computer, and none of its code is in the AppImage.

## The .deb

`Fledge::Deb` lays the built folder out as a package's tree, writes `DEBIAN/control`, and runs `dpkg-deb --build --root-owner-group TREE FILE`, as Briefcase does. `--root-owner-group` (dpkg 1.19.0 and newer) makes every entry root's. A computer without `dpkg-deb` is told to install dpkg.

A Debian or Ubuntu user installs software with `apt`, which tracks what a package put on the computer and removes exactly that; an AppImage is a file to run, which adds no menu entry of its own. The maintainer asked for the `.deb` ("Go for .deb", `decisions.md`, 2026-11-02). `dpkg-deb` is Debian's own maintained tool, which every Debian and Ubuntu has, where Tauri's bundler writes the archive with a tar and `ar` writer of its own; the control file is a stanza of text, an input to `dpkg-deb`, not a format Fledge writes. It is opt-in, never a default, because a default that needed `dpkg-deb` would fail, on every Linux computer without it (Fedora, Arch, and the rest), builds that pass today, to make a package for a family that computer is not in. The package is unsigned: `apt` installs a local file without a signature, and a repository is a channel Fledge does not run. `.rpm`, which `rpmbuild` would make in the same shape, waits for a developer who asks, as do a `/usr/bin` link, a maintainer's address, and `Recommends` and `Suggests`.

**The tree.**

- `/usr/lib/PACKAGE/`: the built folder, less its desktop entry and its `share` folder. Debian Policy 9.1.1 lets a subdirectory of `/usr/lib` hold "a mixture of architecture-independent and architecture-dependent files", which a runtime and an app are.
- `/usr/share/applications/IDENTIFIER.desktop`: the desktop entry, with `Exec` the program's full path, `/usr/lib/PACKAGE/NAME`, quoted as the specification asks.
- `/usr/share/icons/`: the folder's `share/icons`, where desktops look.
- `/usr/share/mime/packages/IDENTIFIER.xml`: the folder's `share/mime`, the definitions of the file types the app defines, when it defines any ("Files an app opens").
- With `license_file`, `/usr/share/doc/PACKAGE/copyright`, the file's text, 0644: Policy 12.5 asks every package to carry "a verbatim copy of its distribution license(s)", neither compressed nor a link. No machine-readable copyright format (DEP-5) is written; Fledge copies the developer's text as it is.
- With `linux: deb_changelog`, `/usr/share/doc/PACKAGE/changelog.gz`, made by the system's `gzip -n -9`, whose `-n` leaves out the file's name and time, as Debian's `dh_compress` does. Policy 12.7 names a package's one changelog `changelog.gz` when "there is no separate upstream maintainer", which is a Fledge app's case.

No program is linked into `/usr/bin`, since a windowed app starts from a menu and a name with spaces is no command. There are no maintainer scripts: the desktop and icon caches, and the MIME database, are updated by the triggers that `desktop-file-utils`, the icon theme tools, and `shared-mime-info` register (Debian's shared-mime-info 2.4-5, `debian/triggers`: `interest-noawait /usr/share/mime/packages`, whose `postinst` runs `update-mime-database /usr/share/mime` when triggered, at install and at removal), and the app writes nothing under `/usr/lib` when it runs, so removing the package removes everything it installed.

**The control file**, Debian Policy 5.3's fields:

| Field | Value |
|---|---|
| `Package` | the identifier in lower case (`com.example.CoolApp` is `com.example.coolapp`), which Policy 5.6.7's name rules allow and which cannot collide with a distribution's package |
| `Version` | the version as Policy 5.6.12 spells it: RubyGems' pre-release `1.2.3.pre.4` is `1.2.3~pre.4`, which sorts before `1.2.3` as RubyGems sorts them |
| `Architecture` | `amd64` or `arm64` |
| `Maintainer` | the publisher, or else the name, on one line; Policy 5.6.2's address is left out, and `dpkg-deb` accepts the field without one |
| `Installed-Size` | the regular files' bytes, in KiB, rounded up (Policy 5.6.20) |
| `Depends` | `libc6 (>= GLIBC)`, `Platform::GLIBC_MINIMUM`, then what dpkg-shlibdeps finds |
| `Section`, `Priority` | `misc`, `optional` |
| `Homepage` | the homepage, when there is one (Policy 5.6.23) |
| `Description` | the description, or else the name, as the synopsis; then `long_description`, each line after one space and an empty line as ` .` (Policy 5.6.13) |

**Depends.** The runtime carries its Ruby, OpenSSL, libyaml, libffi, zlib, and libcrypt, so with nothing else listed, `Depends` is glibc alone. A gem that opens a library with `dlopen`, as SDL opens X11, Wayland, OpenGL, and audio libraries, names none of them in its compiled files, so Fledge cannot know them; a desktop install has them. When `fledge.yml`'s `linux: system_libraries` lists sonames (`doc/contributors/design/gems.md`, "Libraries from the Linux distribution"), the build reads the ELF files in the tree with objdump (a gem's Mach-O and PE files, which GNU objdump may not read, are not Linux's), picks those for the app's processor that need a listed library, and runs `dpkg-shlibdeps -O -xlibc6 -lDIR... -eFILE...` in its work folder, with an empty `debian/control` there, as Debian Policy 8.6.1's procedure does. Its `shlibs:Depends` follows `libc6`: for `examples/system_library`, built on Ubuntu 24.04, `libc6 (>= 2.39), libpng16-16t64 (>= 1.6.2)`. `-xlibc6` leaves out glibc's own entry, which the floor already names. dpkg-shlibdeps maps each soname to the package that provides it on the computer that builds, with the oldest version whose symbols the files use, so a `.deb` names that distribution's packages. It looks for a file's libraries among those of the file's own processor, so for an aarch64 file in an amd64 `.deb`, which a gem for every platform carries beside its x86-64 one, dpkg-shlibdeps 1.22.6 on Ubuntu 24.04 stopped the build ("cannot find library libz.so.1 needed by .../libwrapper.aarch64.so"); the app never loads such a file, so it is not given one (`doc/contributors/design/gems.md`, "A file for another processor"; `test/integration/deb_dependencies_test.rb`). It is in dpkg-dev, which build-essential brings; a computer without it is told to install dpkg-dev. With nothing listed, dpkg-shlibdeps never runs.

**Delivery.** CI's "Delivery of a .deb" jobs install `examples/windowed_app`'s and `examples/system_library`'s `.deb` with apt in fresh `debian:trixie-slim` and `ubuntu:24.04` containers of each architecture, so apt resolves `Depends` from the distribution's archive as a person's computer does; nothing else proves that, so the archive is the one network input the check is about. Before Hello Window's `.deb` goes in, the MIME database `shared-mime-info` compiles must know no `*.hellowindow` file; once it is in, the database must give such a file `application/x-hellowindow`, the type the app defines, by the name its entry gives it; and once it is removed, know nothing of it again (`.github/scripts/deliver-deb.sh`). `.github/scripts/apt-update.sh` fetches, once per job and in one step, the lists and every package the job's later steps install: the validator and `shared-mime-info`, and what each `.deb` depends on, which apt resolves from the `.deb` itself (`test/workflow_apt_test.rb` holds the step to the job's installs). A later `apt-get install` fetches from the host the lists came from, with no bound but the job's, so fetching there would undo the limits below; apt takes a package it finds in its archives folder at the size the lists give and downloads nothing (`pkgAcqArchive` in apt's `apt-pkg/acquire-item.cc`), and that folder is the script's own, since Debian's images delete every `.deb` in `/var/cache/apt/archives` after each dpkg run (the `docker-clean` file debuerreotype writes). In amd64 Ubuntu it asks Canonical's Azure mirror, `azure.archive.ubuntu.com`, which GitHub's runners use for themselves (actions/runner-images, `configure-apt-sources.sh`), instead of the image's `archive.ubuntu.com` and `security.ubuntu.com`, which in five of fifteen jobs from 2026-11-15 to 11-19 took 80 to 586 seconds and twice held a job to its limit; the mirror carries the same archive under the same signing key. apt's own bounds do not hold a stalled host to a time: measured on apt 2.8.4 with a first mirror that accepts and never answers, `Acquire::Retries 1` and `Acquire::http::Timeout 15` through a `mirror+file` list fetched 13 files in 900 seconds, because the timeout applies to each file in turn and the mirror method tries the stalled mirror again for every file. So the script limits the fetch itself, three minutes for the mirror and then four for the image's hosts, and fails, saying which, when neither gives every list and package; `apt-get update` calls an unfetched list a warning and exits 0, so its `W: Failed to fetch` lines fail it too. The limits and that check were proven on apt 2.8.4 against a silent host, a refused port, and the mirror. So were the fetch of the packages and the limit around both commands, run as an ordinary user with apt's state in a folder of its own and an empty dpkg status: from the mirror, `desktop-file-utils` and a local `.deb` that depends on `libpng16-16t64` brought both packages and their dependencies in five seconds; the same install again, with no update, needed "0 B" from the network; a silent host failed the step at its limit, leaving no apt process running; and an unknown package failed it saying so. apt reads an argument as a file only when it begins with `/`, `./`, or `../` (`AddIfVolatile` in `apt-private/private-install.cc`), so the job names its `.deb`s as `./delivered/*.deb`; that proof showed `delivered/FILE.deb` taken for a package named `delivered`. A root install from that folder, the fallback to the image's hosts, the containers themselves, and the Debian and arm64 legs (which keep their sources) are proven only by CI. The job now depends on the mirror's address; if Canonical retires it, the fallback still runs, after three minutes. A prebuilt image holding the lists and the dependencies, or `dpkg -i` with them resolved some other way, would stand in for the archive with a fixed answer, but would no longer show apt resolving the `.deb` against the archive a person has, and would need rebuilding as that archive moves.

## The MSIX package

`Fledge::Msix` packs the built folder into an MSIX package with Microsoft's MakeAppx, as Microsoft's "Generating MSIX package components" packs a desktop app by hand, without Visual Studio: a manifest, `AppxManifest.xml`, a mapping file that lists each file and where it goes in the package, and `makeappx pack /o /h SHA256 /f MAPPING /p FILE`. The Microsoft Store re-signs an MSIX package with Microsoft's certificate once the app passes certification (Microsoft Learn, "App package requirements for MSIX app", "Code signing for Microsoft Store submissions"), so without `--sign` or `--sign-command` the package is left unsigned, for the Store; with either, it is signed after MakeAppx writes it, as the setup program is (`doc/contributors/design/signing.md`).

**MakeAppx** is the Windows SDK's, found as signtool is (`Fledge::WindowsSdk`): the first `makeappx.exe` on `PATH`, or else the newest in `%ProgramFiles(x86)%\Windows Kits\10\bin\VERSION\ARCH`. Microsoft lets MakeAppx be redistributed only under the Windows SDK's own license (its REDIST list, "Windows Packaging Tools"), which none of the runtime license policy's categories covers, so no runtime carries it. GitHub's Windows runners have the SDK; a contributor's Windows computer gets the same tools from Microsoft's `Microsoft.Windows.SDK.BuildTools` package, which `mise.toml` pins by SHA-256 and puts on `PATH`.

The package exists so that a developer can ship through the Store with no certificate of their own, since the Store takes a setup program only when the developer's own certificate signs it; the maintainer: "Very valuable, let's do it if we can." (`decisions.md`, 2026-11-12). MakeAppx is the tool Microsoft maintains for the format, and every Windows SDK and GitHub's Windows runners have it. Carrying it in the Windows runtime, as electron-builder carries it, would put a component under the SDK's redistribution terms in a runtime, and whether a runtime should is the maintainer's question; having `fledge build` download the SDK's build tools would add download and cache code and pass over NuGet's license prompt; and a package writer of Fledge's own is a format writer, which ADR 010 rules out. The cost is a tool on the developer's computer that Fledge does not pin, and a self-signed package that installs only once its certificate is trusted machine-wide, which takes an administrator. That the Store certifies a package Fledge builds is untested (`doc/contributors/account-tests.md`).

**The manifest** (`Msix#manifest`):

| Element | Value |
|---|---|
| `Identity` `Name` | `windows: msix_name`, Partner Center's Package/Identity/Name, or else the identifier; 3 to 50 letters, digits, periods, and hyphens (the schema's `ST_PackageName`) |
| `Identity` `Publisher` | `windows: msix_publisher`, required when `installers` lists `msix`: Partner Center's Package/Identity/Publisher, or the subject of the signing certificate, which Windows requires to match |
| `Identity` `Version` | the version's first three numbers (`WindowsResources.numbers`) and a 0, since the Store keeps the fourth for itself ("App package requirements for MSIX app", "Version numbering for Windows 10 and 11 packages") |
| `Identity` `ProcessorArchitecture` | `x64` or `arm64` |
| `Properties` | `DisplayName` the name, `PublisherDisplayName` the publisher, which Partner Center's Package/Properties/PublisherDisplayName must match, `Description` the description or the name, and `Logo` the 50-pixel logo |
| `Resources` | `en-us` |
| `TargetDeviceFamily` | `Windows.Desktop`, `MinVersion` `10.0.17763.0` (Windows 10 1809, electron-builder's MSIX default), `MaxVersionTested` `10.0.26100.0` |
| `PackageDependency` | for an app built with `windows: visual_c_runtime: central` whose gems need Microsoft's Visual C++ runtime, as its `fledge.cfg`'s `visual_c_runtime` records: `Microsoft.VCLibs.140.00.UWPDesktop`, `MinVersion` `14.0.24217.0`, and Microsoft's publisher (`Msix::VISUAL_C_RUNTIME`), as "C++ Runtime framework packages for Desktop Bridge" gives them ("The Visual C++ runtime in a package", below) |
| `Capabilities` | `rescap:runFullTrust`, which a full-trust app needs ("App capability declarations") |
| `Application` | `Id` `App`, `Executable` `NAME.exe`, `EntryPoint` `Windows.FullTrustApplication`, which installs on Windows 10 before 2004, where `uap10:RuntimeBehavior` does not |
| `uap:VisualElements` | the name, the description, `BackgroundColor` `transparent`, and the 150- and 44-pixel logos |
| `uap:Extension` `windows.fileTypeAssociation` | one for each of `file_associations`' entries that names `extensions` (`Msix#extensions`), which lists the app in each extension's "Open with" and never makes it the default, as the setup program does ("Files an app opens"); folders and MIME types alone have no place in a package's manifest |

**The logos** are the developer's PNGs beside the icon (`Icon::MSIX`), `ICON-44.png`, `ICON-50.png`, and `ICON-150.png`, the base sizes of `Square44x44Logo`, `StoreLogo`, and `Square150x150Logo` ("Construct your Windows app's icon"), mapped to `Assets\` in the package. Fledge reads none and checks no sizes ("Icons"). Scaled variants (`.scale-200`) would need MakePri's resource index, which the package does without.

**`fledge.cfg` without the identifier, or the Visual C++ runtime.** In a package, Windows gives the process the package's own AppUserModelID, `PACKAGE_FAMILY_NAME!App`, which its Start menu entry and its notifications use. The launcher makes `fledge.cfg`'s `identifier` the process's explicit AppUserModelID, which would override it and part the app's windows from its Start menu entry, as Microsoft's "Application User Model IDs" warns of an app a deployment framework manages. The mapping file therefore puts a copy of `fledge.cfg` with its `identifier` lines removed (`Msix.packaged_config`) in the package; the folder and the other installers keep theirs. The copy has no `visual_c_runtime` line either: in a package the runtime's DLLs come from the framework package, and the launcher, which looks for them in System32 (`launcher.md`, "The Visual C++ runtime on Windows"), would refuse a computer whose System32 lacks them though the package's dependency holds them.

**The Visual C++ runtime in a package.** Microsoft's page "C++ Runtime framework packages for Desktop Bridge" says a packaged desktop app that needs the runtime "must specify the corresponding version of the C++ Runtime framework package for Desktop Bridge during creation of the application package. This must be done instead of just redistributing the C++ Runtime libraries", and that such an app "cannot use the C++ Runtime libraries that are included with Visual Studio or VCRedist"; it gives the `PackageDependency` the table names, and "The application will now install the C++ Runtime DLLs from the dependency package when it's deployed." A process of a package has a package graph made from the manifest's `PackageDependency` elements, from which it loads DLLs ("Framework packages and the package graph", in Microsoft's "MSIX framework packages and dynamic dependencies"). The framework packages "are distributed and updated through the Microsoft Store", so a package the Store installs gets its dependency with it, and the dependency carries none of Microsoft's files in the developer's package: `central` stays true to its meaning, and nothing is distributed. For a package installed outside the Store, `Add-AppxPackage` takes a dependency the account already has ("If a package is already installed for a user, you can skip adding it to the DependencyPath") or one given with `-DependencyPath`. On a Windows 11 computer (10.0.26300) that had never had a Fledge package, the account already had `Microsoft.VCLibs.140.00.UWPDesktop` 14.0.33728.0, for x64 and x86, by exactly the publisher the manifest names, holding `vcruntime140.dll`, `vcruntime140_1.dll`, and `msvcp140.dll` at 14.40.33728.0, and the one package that depended on it was Microsoft's App Installer (`Microsoft.DesktopAppInstaller`), as `Get-AppxPackage` showed; so a computer with App Installer, which opens sideloaded packages, has the dependency. Whether App Installer fetches a missing framework package from the Store when a person opens a sideloaded package, none of Microsoft's pages on App Installer or `Add-AppxPackage` says, and Fledge has not tried it. An app built with `local` carries its copies in the package, which Microsoft's page warns against; no app has been tried that way. The minimum version is the page's, the first release of the version 14 package; a gem built with a newer Visual Studio may need a newer runtime than that ("Determine which DLLs to redistribute"), which the framework package's updates through the Store bring.

**What differs in a package.** A package installs under `C:\Program Files\WindowsApps`, read-only, for one person. Windows gives a full-trust packaged app a merged view of `AppData`: a file or folder it creates under `AppData\Local` or `AppData\Roaming` goes to a folder of the package's own, which the app reads back where it wrote it, and which another program outside the package does not see; a file that was already there is changed in place ("Understanding how packaged desktop apps run on Windows", "Write under AppData"). Removing the package removes what it wrote there. An app's Ruby code sees the same paths, `ENV`, and standard library as outside a package, but a file it creates under `AppData` is not there for a program outside the package, such as an editor a person opens it in. The manifest's `desktop6:FileSystemWriteVirtualization`, with the restricted capability `unvirtualizedResources`, turns this off; Fledge does not set it, since the Store reviews each restricted capability, and no app has needed it yet.

## Files an app opens

A framework's drag-to-make-an-app ("Building from a built app") needs the system to hand an app what was dropped on it, and a person expects "Open With" to list an app for the files it opens. `file_associations` (`Fledge::Config::FileAssociation`) declares them once, with Tauri's and electron-builder's `fileAssociations` keys, and Fledge writes each system's form of it. It is a list of entries, each with:

- `name`, required;
- `role`: `viewer`, the default, or `editor`;
- `extensions`, without the dot and of one part, since Windows associates only an extension's last part; `mime_types`; and `content_types`, macOS's uniform types;
- or `folders: true`, which an entry for files may not also say, since macOS reads `LSItemContentTypes` in place of extensions, so one entry for both would lose the files there;
- and `defines_type: true` for files of a type the app defines, which no other program does, such as a game engine's `*.lota`: the entry then names the type's one MIME type and at least one extension, since a definition is one type and the names its files have.

An entry that names nothing to open is refused, and so is the key in a console app's `fledge.yml`, since only a windowed app has a bundle, a desktop entry, or a setup program to declare them in. With `programs`, the windowed program declares them.

**Offered, never the default.** The app is ranked `Alternate` on macOS and only listed in each extension's "Open with" on Windows, so it is offered for what it opens and a person's defaults never change. The prior art sets the default: Tauri's `HandlerRank` (`crates/tauri-utils/src/config.rs`, lines 1150 to 1165, at 2e23492) and its `FileAssociation.nsh` (`APP_ASSOCIATE`, lines 68 to 80, at 2e23492), and electron-builder's own `FileAssociation.nsh` (lines 66 and 67, at c63f98a); that makes the app the default for an extension another app may already open, which no person asked for. An app that wants to be the default asks each person to choose it. Fledge does not turn macOS's Apple event into arguments, since `ruby main.rb` gets none either (Design precedence 2): the app receives a drop through its GUI library's event loop, as SDL3's `SDL_EVENT_DROP_FILE`, and a macOS app with no GUI event loop does not see what was dropped on it.

- **macOS:** one `CFBundleDocumentTypes` entry each, with `CFBundleTypeName`, `CFBundleTypeRole` (`Viewer` or `Editor`), `LSHandlerRank` `Alternate`, `CFBundleTypeExtensions` and `CFBundleTypeMIMETypes` as electron-builder writes them, and `LSItemContentTypes` (`public.folder` for folders, or the `content_types`). No tool in `/usr/bin` maps an extension to a uniform type without a file of that type, so extensions go in as extensions, and Launch Services matches them through the dynamic type it gives each. A drop or `open -a` arrives as an Apple event, which the app's GUI library receives.
- **Windows:** a dropped file or folder arrives in `ARGV` with nothing declared. The setup program writes, under `HKCU\Software\Classes`, for each extension, a ProgID with the first listing entry's name as its default value, `DefaultIcon` the program's first icon, and `shell\open\command` = `"PROGRAM" "%1"`, and lists the ProgID as a value of `.EXT\OpenWithProgids` with `WriteRegNone`, as electron-builder writes it. It never sets the extension's default. For folders, it writes the verb `Directory\shell\IDENTIFIER`, "Open with NAME", with the same command. Then it calls `SHChangeNotify(SHCNE_ASSOCCHANGED, SHCNF_FLUSH)`, as both prior installers do. An MSIX package declares a `uap:FileTypeAssociation` for each entry that lists extensions, named with the entry's name's letters and digits in lower case, as the schema asks, and a number after it when two entries share one; its `uap:SupportedFileTypes` are the extensions, in lower case. Windows lists a package's app in each extension's "Open with" through a ProgID of its own (`AppX` and a hash) and never makes it the default without the person's choice. A package has no plain verb for folders (a folder's menu entry in a package is a COM `IExplorerCommand`), so `folders: true` adds nothing to it, nor do MIME types or `role`. A portable folder registers nothing.
- **Linux:** `MimeType=` lists the `mime_types`, and `inode/directory` for folders, as electron-builder's `LinuxTargetHelper.ts` lists its own, and `Exec` ends in `%F` when it lists any. `extensions` alone does nothing there. A desktop takes a file's type from the shared MIME-info database, which matches the file's name against each type's globs before it reads the file's contents (the Shared MIME-info Database specification 0.21, "Recommended checking order"); with no glob, a file is `text/plain` or `application/octet-stream`, and an app whose entry names another type is not offered for it. So, for each entry with `defines_type`, `Fledge::SharedMimeInfo` writes the app's own package of that database, `share/mime/packages/IDENTIFIER.xml`, as the specification asks ("Each application ... will install a single XML file, named after the application, into one of the three `<MIME>/packages/` directories", "Directory layout"): a `mime-type` with the entry's MIME type, its name as the `comment`, and a `glob` `*.EXT` for each extension, lowercased once each, since a glob matches either case unless it says `case-sensitive`.

**Defining a type.** The prior art defines its own types on Linux. LÖVE installs `platform/unix/love.xml` (at its 11.5 tag), `application/x-love-game` for `*.love`, into `$(datarootdir)/mime/packages` (`platform/unix/Makefile.am`, lines 8 and 13), and Debian's `love` package installs it through `debian/love.sharedmimeinfo` (11.5-4). electron-builder writes a `mime-type` for every association with a `mimeType`, a glob of its `ext`, and its `description` as the comment (`packages/app-builder-lib/src/targets/LinuxTargetHelper.ts`, `computeMimeTypeFiles`, lines 28 to 52, at v26.0.12), installs it as `/usr/share/mime/packages/EXECUTABLE.xml` (`FpmTarget.ts`, lines 245 to 247), and runs `update-mime-database` after install (`templates/linux/after-install.tpl`, lines 21 to 23). Flatpak exports an app's `share/mime/packages` (`common/flatpak-dir.c`, `flatpak_export_dir`, lines 8104 to 8112, at 1.16.1), after dropping its magic and setting each glob's weight to 5, so that an app's definition cannot "override the system ones in any weird ways" (`rewrite_mime_xml`, lines 7433 to 7437). Tauri's bundler lists the MIME types in the desktop entry and defines none (`crates/tauri-bundler/src/bundle/linux/freedesktop/mod.rs`, lines 133 to 156, at 2e23492), which is the gap Fledge had.

Fledge defines a type only when the entry says so, where electron-builder defines every type it is given. `update-mime-database` reads the packages in name order and keeps, of each type's comments in one language, the last it reads (`src/update-mime-database.cpp` in shared-mime-info 2.4, `scan_source_dir` sorting at line 823, `remove_old`, lines 620 to 648), so an app that listed `application/zip` and had its definition written would rename every zip file on the computer to "Project archive" whenever its identifier sorts after `freedesktop.org`. Flatpak's way, every type defined but with weak globs and no other change, would not rename a type, but a type it defined would have no name a person can read, and it would still be a definition of a type the app does not own. A key that says the type is the app's own is also what macOS needs to export a type (below), so one key serves both. Defining a type needs its one MIME type and the extensions, so the key refuses an entry without them; an icon for the type is left to the desktop's generic document icon, as electron-builder's `x-office-document` is, and magic, subclasses, and translated comments wait for a developer who asks.

**Where the definition goes.** The folder keeps it in `share/mime/packages`, beside `share/icons`, where `$XDG_DATA_HOME` keeps it, so a person who installs the app by hand copies `share` into `~/.local/share` and runs `update-mime-database ~/.local/share/mime`. The `.deb` installs `share` in `/usr/share`, and shared-mime-info's dpkg trigger compiles the database when the package is installed and again when it is removed ("The .deb"). An AppImage and the archive install nothing, so until someone installs the app a file of the type has none of the app's, and `doc/desktop_apps.md` says so: the AppDir carries the file, but neither AppImage's runtime nor Fledge adds it to the database.

**macOS.** Fledge ranks the app `Alternate` and declares no type of its own, where LÖVE's app is `Owner` of `.love` and exports `org.love2d.love-game`. That leaves macOS with no gap of this kind: Launch Services gives an extension that no declared type claims a dynamic type of its own and matches the app's `CFBundleTypeExtensions` through it, and Delivery shows it offering Hello Window for an empty `dropped.hellowindow` (`.github/scripts/deliver-windowed.sh`, `URLsForApplicationsToOpenURL`). An exported type (`UTExportedTypeDeclarations`, which Apple's "Defining file and data types for your app" asks of a type an app owns) would give the type a stable identifier that other apps, Quick Look, and Spotlight can use, and a conformance, such as to `public.zip-archive`. Whether a double-click opens such a file with the app when its only handler ranks itself `Alternate` is unproven. Exporting a type for an entry with `defines_type`, and ranking the app its `Owner`, is a story of its own, and `defines_type` changes nothing on macOS until then.

**The ProgID** (`Nsis::Script#prog_id`) is one per extension, and depends on nothing that can move: the identifier with every character but letters, digits, and periods removed, periods squeezed, leading digits and periods removed, cut to 28 characters with no trailing period (`App` when nothing is left), then a period and the first ten hexadecimal digits of the SHA-256 of the identifier, a newline, and the lowercased extension: `io.github.someone.myverylong.5b36e4ccbc`. Microsoft's ProgID key page asks for "no more than 39 characters", "no punctuation (including underscores and slashes) except one or more periods", and not starting with a digit, where an identifier may hold hyphens and 128 characters. The hash keeps two identifiers that sanitize alike apart, and extensions apart within an app. A ProgID named for an entry's place in the list would rename itself when the list is reordered and leave the old one on people's computers, since the uninstaller knows only the current list. An entry's `name` is deliberately not part of it: renaming an entry changes only the ProgID's friendly name, which the next install overwrites. An extension two entries list gets one ProgID, named for the first entry.

The uninstaller deletes each ProgID, its value in `OpenWithProgids`, the `OpenWithProgids` key and the extension's key when nothing else is left in them, and the folders' verb, then calls `SHChangeNotify` again. An extension dropped from `file_associations` in a later version stays registered until the person removes it.

## Building from a built app

`fledge build --from APP [OPTIONS] [PATH]` (`Fledge::BuiltApp`) builds the project at PATH as `fledge build` does, but takes the runtime and the gems from APP, the folder `fledge build` wrote (`NAME-PLATFORM/`, or on macOS the `.app` in it), instead of downloading a runtime and installing the lockfile's gems. Nothing is downloaded: a computer that can download a runtime can run `fledge build` itself, and the person `--from` is for may have no network.

**Why.** `fledge build` needs Ruby, Bundler, the network, and sometimes a compiler, which a newcomer may have none of, even when every gem their program needs is already compiled inside an app Fledge built. The maintainer put that person in scope: "One third of the reason Fledge exists is to support Lota, which is a faithful port of LÖVE2D to Ruby. Drag-to-fuse is a huge part of why LÖVE2D is successful; CLIs can be scary to newbies." (`decisions.md`, 2026-11-04). Fledge depends on no framework, so it gives frameworks general primitives (`doc/contributors/design/public-interface.md`, "Building from a built app"), after LÖVE's fused games, Electron's prebuilt app with the developer's code in `resources/app` and electron-builder's `--prepackaged`, and Python's embeddable distribution. Copying a built app downloads, resolves, and compiles nothing, needs only Ruby's standard library and the system's tools, and gives the person what `fledge build` would have built, with the project as plain files, so `__dir__`, `__FILE__`, and backtraces name real files. A self-extracting single file, as warp-packer, PyInstaller's `--onefile`, and electron-builder's `portable` make, would make the first launch wait, leave a copy per version in a cache, draw antivirus heuristics, could not be a single file as a macOS `.app`, and would name the cache in `__dir__` and `RbConfig.ruby` rather than where the person put the file. An app run from an archive never unpacked, through a virtual file system as Tebako builds, fails at the root: Ruby cannot `require` from a zip, load a library from one, or keep its prefix in one. The costs: every app built `--from` is as large as APP and carries Fledge's own Ruby code as a gem, and an unsigned downloaded APP meets Gatekeeper's and SmartScreen's warnings before anyone builds from it. `doc/contributors/research/2026-11-05-drag-to-fuse.md` holds the research and the spike.

**Another system's APP.** The maintainer allows a step that only copies to make another system's app: "My main concern was adding a lot of code, complexity, and surface area for bugs re: cross-compiling. Anything that doesn't do those is fine by me." (`decisions.md`, 2026-11-04, question D). `--from` still builds for its own platform only, a limit not yet lifted; a copy-only form, and a single Windows file, wait for a developer or a framework to ask, and either is compatible in 1.x (`doc/contributors/design/public-interface.md`, "Reserved names").

**How APP is recognized.** The first line of every `fledge.cfg` a desktop build writes is a comment the launcher skips: `# Written by fledge build VERSION for PLATFORM: what this app's program runs.`, or `programs run.` with sections (`Assembly#launch_config`). `--from` reads VERSION and PLATFORM from it (`BuiltApp::HEADER`). A key would be the cleaner record, as `pyvenv.cfg` has `version`, but the launcher refuses a key it does not know, so a key would need a launcher of the same release. A phone project's `fledge.cfg` keeps a first line with no release, since no app is built from it. The program's name comes from `fledge.cfg`'s sections, or for one program from the bundle's name or the folder's `NAME-PLATFORM`.

**What the new app takes from APP.** Its runtime, its gems, and `notices/`, unchanged, and of its project the paths Bundler needs to set up those gems: the `Gemfile` (or `gems.rb`) and its lockfile, `.bundle/config`, `vendor/cache`, and each folder inside the project that the lockfile's `PATH` sections name, read with `Bundler::LockfileParser`. `fledge.cfg`'s `system_libraries` stays, since the gems that load them do. The new project's `fledge.yml` gives everything else: the program, `name`, `identifier`, `version`, `icon`, `publisher`, `copyright`, `kind`, `installers`, `file_associations`, `linux: deb_changelog`, and `macos: build`.

**What goes of APP.** Its `fledge.cfg`, its programs, its `tools` folder, and its identity: on macOS its bundle's `Info.plist`, program, seal, and `NAME.icns` (only `Contents/Resources` is copied); on Linux each `IDENTIFIER.desktop`, `share/icons/hicolor/*/apps/IDENTIFIER.png`, and `share/mime/packages/IDENTIFIER.xml`, with the folders they leave empty. An old app's definition of its file types, left in the new app, would install under the old identifier, and dpkg refuses to install a second package with a file the first one installed.

**The program.** On macOS and Linux, the program is a copy of APP's, which is the runtime's launcher renamed; on macOS it is first signed again ad hoc (`codesign --force --sign -`), so a console app made from a bundle carries no seal naming APP's identifier. On Windows, APP's program holds APP's icon, company, and copyright, which rcedit can replace but not remove, and its subsystem is APP's kind; so the Windows build takes `launcher.exe` or `launcherw.exe`, and rcedit and NSIS, from APP's `tools` folder when APP has them, or else from Fledge's runtime for the platform when the computer has it at hand (`Runtimes#at_hand`: in `FLEDGE_RUNTIME_DIR`, or in the cache when it matches its pin), unpacking only those. On every platform a runtime at hand also gives the tools folder, which an AppImage needs. The identity is then written as `fledge build` writes it.

**Refusals.** Status 2, a usage error: `--from` without APP, and `--from` with a phone. Status 1, a failed build:

- an APP that is not a folder, has no `fledge.cfg` or no program, was built by another Fledge release, or is for another platform than the computer's ("--from APP is an app for PLATFORM, and this computer builds for PLATFORM. Build from an app for this computer.");
- a PATH with a `Gemfile`, `gems.rb`, or gemspec of its own;
- a `fledge.yml` with `programs`, `linux: system_libraries`, `ios`, or `android`, which change the runtime or the gems;
- a PATH that holds a file at one of the paths APP's Bundler needs;
- an APP whose lockfile takes a gem from the project's own folder (`gemspec`, or `path: "."`), since replacing the project would take the gem away;
- on Windows, no launchers in APP's tools and no runtime at hand, naming where to put one.

`--from` takes a folder only; unpacking a zip a person dropped is the caller's, since Linux has no zip reader every computer has.

**build_tools.** `build_tools: true` (default false) puts in the app, in a `tools` folder beside its runtime, what `--from` would take from a runtime at hand (`Assembly::BuildTools`): on Windows, the runtime's `launcher.exe` and `launcherw.exe` and its tools folder but `llvm-readobj.exe`, which `--from` has no use for, since it compiles nothing; on Linux, the tools folder, AppImage's runtime; on macOS nothing, since the app's program is the launcher and `/usr/bin` has the rest. The tools go in after the app's code is signed and before the installers and the archive, so `--sign` signs none of them: a launcher signed by the developer and then changed by rcedit in a later `--from` would carry a broken signature. They are copied as the runtime holds them, so the installers hold them too. APP's `tools` never passes to the new app; the new app carries its own only when its own `fledge.yml` sets `build_tools`. Fledge itself is a gem the app's Gemfile ships, in a group the app sets up, which the app runs as the `fledge` RubyGems writes into `Gem.bindir`; since the app's Fledge built the app, the two agree on `fledge.cfg`. `build_tools` cannot carry `mksquashfs`, which is GPL-2.0 and so no part of a runtime, nor `dpkg-deb`, which every Debian and Ubuntu has. Every tool it carries is in the runtime's license audit already, and `runtime/licenses.yml` says each ships in an app when `build_tools` is set.

**What a framework does around it.** The person's `RUBYOPT` and `RUBYLIB` reach a child Ruby as under `bundle exec`, so a framework runs the `fledge` command with `RUBYOPT=-rbundler/setup` and no `RUBYLIB`. What a framework may rely on is in `doc/contributors/design/public-interface.md`.
