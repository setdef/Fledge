# ADR 054: The JSON Schema's Address Is Its Release's Tag

## Context and Problem Statement

A developer's `fledge.yml` names its JSON Schema (`doc/contributors/design/public-interface.md`, "The fledge.yml schema") with a modeline comment, and the schema's `$id` gives the same address. An editor then completes and checks the file against whatever that address serves. A modeline is a comment, so no build ever reads it: if the address serves a schema of another Fledge, the editor offers keys the developer's Fledge refuses, or marks keys it accepts, and nothing says so.

After 1.0, `trunk` heads toward the next major. A developer on 1.4 whose modeline names `trunk` would get completion for a key 1.4 refuses. Which address describes the Fledge that builds the app, and stays good for as long as that release is in use?

## Decision Drivers

- The schema a developer's editor reads must be the one their Fledge enforces.
- The file at the address must never change.
- Nothing Fledge does not already have: no new host, and no branch per major.
- A release commit must not forget to move the address.

## Considered Options

1. The file at the release's tag: `https://raw.githubusercontent.com/setdef/Fledge/vX.Y.Z/lib/fledge/config.schema.json`, with X.Y.Z `Fledge::VERSION`.
2. The file on `trunk`.
3. An address per major, whose `$id` names the exact release, as Tauri 2 serves its schema (`https://schema.tauri.app/config/2`, whose `$id` is `https://schema.tauri.app/config/2.12.5`).

## Decision Outcome

Chosen: option 1, because a tag's file never changes, which is what an exact release's address needs, and it needs nothing Fledge does not have. A developer names the tag their `Gemfile` installs Fledge from, so the editor describes the Fledge that builds the app. Each release commit moves `$id` and the modeline that `Fledge::Config`'s RDoc and the README give.

The repository's own `fledge.yml` files, in `examples/` and the test fixtures, name the schema beside them by a relative path instead, which the language server reads as a path. So `trunk`'s examples check against `trunk`'s schema.

Confidence: high. The address is the release's own file, and every release keeps its tag.

### Consequences

- Good, because a modeline written for one release keeps describing that release, however far `trunk` moves.
- Good, because the address costs no host, branch, or account.
- Bad, because a developer who upgrades Fledge must change the modeline by hand, or their editor describes the old release. No build warns them.
- Bad, because the address works only while the tag exists. Every release keeps its tag, before 1.0 and after, and no tag is ever deleted (`doc/contributors/design/releases.md`). The address now depends on that rule.
- Bad, because the address depends on GitHub serving raw files. A change in GitHub's terms would cost every developer's modeline.

### Confirmation

`test/config_schema_test.rb` fails until the schema's `$id` and the documented modeline name `vFledge::VERSION`'s tag, and checks that each relative modeline in the repository reaches the file. `doc/contributors/handoff.md`, "How to release", lists the address among the release commit's changes.

## Pros and Cons of the Options

### `trunk`

- Good, because it needs no change at release.
- Bad, because after 1.0 it describes the next major, not the developer's release.

### An address per major

- Good, because a developer's modeline survives every minor of a major.
- Bad, because it needs a host or a branch per major, which Fledge does not have, and serves one release's schema to developers on older minors of the same major.

## More Information

The 1.0 review found the cost of `trunk` (`doc/contributors/research/2026-11-04-one-point-oh-surface.md`, section 4.3). `doc/contributors/design/public-interface.md` freezes the address's form for 1.x.
