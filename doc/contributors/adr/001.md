# ADR 001: What Fledge Is

## Status
Proposed (requested). An agent wrote this ADR without review; the maintainer accepts, amends, or rejects it. The questions it leaves open are in `doc/contributors/questions.md`.

## Date
2026-10-26

## Context

A Ruby app runs where Ruby is installed. Almost nobody who would play a Ruby game, open a Ruby desktop app, or run a Ruby terminal tool has Ruby installed, and asking them to install one (the right version, with a compiler for the gems that need one) loses most of them before the app starts. A developer who wants to hand someone an app has no answer that ends in "unzip it and double-click."

The Ruby on the developer's own computer cannot be copied along with the app. A Ruby built by a version manager or a package manager records absolute paths at build time (its prefix, its library directory, the location of OpenSSL and libyaml) and links against the machine's shared libraries. A copy on another machine looks for those paths and libraries, and fails.

Other Ruby implementations are not the answer. JRuby needs a Java runtime, which only moves the problem. TruffleRuby ships large native images and is not CRuby, so C extensions and CRuby's own behavior differ. IronRuby is no longer maintained. People who use Ruby, and the frameworks Fledge serves, run CRuby.

Other languages have solved this, and their solutions are the models:

- **LÖVE's fused games.** A LÖVE game is a folder with a `main.lua`. To ship it, the developer joins the zipped game to LÖVE's own executable, a renamed `.exe` beside its DLLs or a renamed `.app`, and at boot LÖVE notices the game it carries and runs it. The player never meets LÖVE or Lua. Lota's ADR 002 (`setdef/lota`, `doc/contributors/adr/002.md`) applies the same design to Ruby: a small C launcher that embeds CRuby, following Ruby's own `main.c`, and a spike proved it on macOS with a 35-line launcher and a prebuilt Ruby 4.0.9.
- **The Tauri bundler.** Builds platform-native output (an app folder, an installer, an archive) per target from one project description, with target names taken from the platform's own conventions.
- **PyInstaller and Briefcase.** Freeze a Python app with an interpreter beside it. PyInstaller names the two kinds of app this ADR uses: *console*, which runs in a terminal and has standard streams, and *windowed*, which on Windows uses the GUI subsystem so no console window appears.
- **python-build-standalone.** Prebuilt, relocatable CPython builds, published as release assets and pinned by hash, which Briefcase, uv, and others consume rather than building Python themselves.

For Ruby, the same pieces now exist. rv-ruby (`spinel-coop/rv-ruby`) publishes relocatable CRuby builds for macOS and Linux with a static libruby, YJIT, and static OpenSSL, libyaml, libffi, and zlib. RubyInstaller (`oneclick/rubyinstaller2`) publishes the maintained CRuby for Windows, a MinGW UCRT build, with a PGP signature beside each archive.

Fledge generalizes Lota's ADR 002 from games to any Ruby app, so that Lota, Tokra, Rooibos, and apps with no framework at all share one way to ship.

## Decision

### 1. Embed CRuby in a small launcher

Each runtime carries a small C launcher, the executable a person runs. It embeds CRuby as Ruby's own `main.c` does at the pinned version (`setlocale`, `ruby_sysinit`, and `ruby_start_main`, whose callback runs `RUBY_INIT_STACK`, `ruby_init`, `ruby_options`, and `ruby_run_node`), finds its own location by each operating system's own means (`_NSGetExecutablePath` on macOS, `/proc/self/exe` on Linux, `GetModuleFileNameW` on Windows), and points the interpreter at the Ruby beside it. It scrubs the Ruby environment of whoever runs it (`RUBYLIB`, `RUBYOPT`, `RUBYSHELL`, `GEM_HOME`, `GEM_PATH`, `GEM_SPEC_CACHE`, `BUNDLE_GEMFILE`, `BUNDLE_PATH`, and the other `BUNDLE_` variables), so nothing on their machine changes the app. It runs the app on the process's main thread, where macOS needs windows and events.

Single-file packagers such as Tebako and OCRAN unpack to a temporary directory or mount a virtual filesystem on every launch, and control less of a macOS app's layout and signing than a launcher does. A launcher is also what LÖVE, Tauri, and PyInstaller ship.

### 2. Prebuild a runtime per platform in Fledge's CI, published as release assets

A runtime is the launcher, a relocatable Ruby with its whole standard library and default gems, and the license notices those require. Fledge's CI builds one runtime per target platform and publishes it as an asset of a GitHub Release. `fledge build` downloads (and caches) the runtime for each target, checks its SHA-256 against the value pinned in the Fledge version that asked for it, and copies the app into it.

Because runtimes are prebuilt, any machine can build for every platform: a developer on a Mac builds the Windows and Linux apps too, as long as the app's gems are pure Ruby or precompiled for each target. Building runtimes on demand would need each platform's toolchain on the developer's machine, which is what Fledge exists to avoid.

The standard library ships whole: every library and default gem Ruby installs. An app that requires a library and finds it missing is broken, and LÖVE likewise ships the whole of Lua's. Ruby's bundled gems (csv, bigdecimal, minitest, and the rest), which Ruby installs as ordinary gems, are left out until an app can ask for them in a Gemfile (questions.md, question 9).

A runtime is a folder with the launcher at its top and Ruby's own layout beside it (`lib/ruby/4.0.0`, `lib/ruby/gems/4.0.0`, `libexec/cert.pem`), plus `notices/`. Ruby built with `--enable-load-relative` finds its library from the launcher's own folder, so nothing in a runtime records where it was built (Plan 001, spike 1).

### 3. Take Ruby from rv-ruby on macOS and Linux, and from RubyInstaller on Windows

- **macOS and Linux:** rv-ruby's release `20261023`, assets `ruby-4.0.9.arm64_sonoma.tar.gz` (`arm64-darwin`, macOS 14 or newer), `ruby-4.0.9.x86_64_linux.tar.gz` (`x86_64-linux`), and `ruby-4.0.9.arm64_linux.tar.gz` (`aarch64-linux`), pinned in `runtime/sources.yml`. These Linux builds need glibc 2.39 or newer (question 7). rv-ruby links libxcrypt, which is LGPL, statically; Linux runtimes instead build the same libxcrypt release as a shared library and ship it in their `lib/`, so the launcher carries no LGPL code (question 8).
- **Windows:** RubyInstaller's release `RubyInstaller-4.0.9-1`, asset `rubyinstaller-4.0.9-1-x64.7z` (`x64-mingw-ucrt`), whose PGP signature (`.asc`) is verified when the pin is first recorded.

Each source is pinned by version and SHA-256 in the repository, and a CI build that downloads anything else fails. If a source stops publishing, publishes a build that fails Delivery, or cannot be relied on, the fallback is to build Ruby ourselves in Fledge's CI, as python-build-standalone does for Python, with the same static-linking choices. That fallback is a larger project, so it waits until a source fails.

### 4. Name targets by RubyGems platform

Targets are RubyGems platform names (`arm64-darwin`, `x86_64-linux`, `aarch64-linux`, `x64-mingw-ucrt`), the names Ruby developers already meet in `Gemfile.lock` and in precompiled gems, and the names that decide which precompiled gem fits a runtime. The default target is the platform Fledge runs on.

### 5. Ship two kinds of app: console and windowed

A *console* app runs in a terminal with standard input, output, and error, and its exit status is the app's. A *windowed* app opens its own windows and shows no terminal: on Windows it is a GUI-subsystem executable, and on macOS it is an `.app` bundle. These are PyInstaller's terms. The walking skeleton builds console apps only; windowed apps come with the first framework that needs one.

### 6. Write to dist/ by default

`fledge build` writes each target to `dist/NAME-PLATFORM/` and archives it beside the folder, as `dist/NAME-PLATFORM.zip` for Windows and `dist/NAME-PLATFORM.tar.gz` elsewhere. `dist/` is where Python, JavaScript, and Rust packagers write, and `--out` changes it.

### 7. Release by tags and GitHub Releases, never RubyGems.org

Fledge is released as git tags and GitHub Releases at https://github.com/setdef/Fledge, carrying the runtimes as assets, as Ferro releases by tag. It is never published to RubyGems.org: the gemspec's `allowed_push_host` points nowhere, and `rake release` refuses. Developers install Fledge from its git tag.

## Consequences

- Fledge's CI builds and publishes a runtime per supported platform, so prebuilt runtimes are part of the product, not an optimization, and a Fledge version is tied to the runtimes it pins.
- A built app carries a Ruby interpreter and its whole standard library: tens of megabytes before compression, more than a fused LÖVE game.
- Apps whose gems have native extensions build only for targets those gems are precompiled for. Vendoring gems, and native gems, are later work.
- Delivery is testable end to end: a CI job per OS unpacks a built app on a fresh runner with no Ruby on `PATH`, in a directory other than the one it was built in, and checks what it prints (Plan 001).
- The license of the launcher and the other files Fledge copies into an app binds every app built with Fledge. Under AGPL-3.0-or-later it could bind apps whose authors chose otherwise; that is a question for the maintainer (`doc/contributors/questions.md`), and the launcher stays AGPL-3.0-or-later until it is answered.
- The runtimes ship Ruby (Ruby's license or BSD-2-Clause) and the libraries rv-ruby and RubyInstaller link (OpenSSL under Apache-2.0, libyaml, zlib, libxcrypt, the Rust standard library in YJIT, Mozilla's CA bundle, and MinGW's runtime), so each runtime carries their notices in `notices/`, indexed by `notices/README.txt`, with the launcher's own license.
