# ADR 013: Compiled Files, Read by the System's Own Tools

## Status
Accepted (requested). Agents wrote this ADR and may change it (AGENTS.md, Questions). It applies the maintainer's words of 2026-10-28 in `doc/contributors/decisions.md` ("Code is a liability and we should _not_ have 4k+ lines of things we could use existing tools for."), and supersedes ADR 010's reason for keeping `Fledge::Binary` (ADR 010, Consequences).

## Date
2026-11-01

## Context

Fledge reads compiled files for five questions. Which shared libraries a file needs: the license audit asks it of every file of a runtime (ADR 004), to resolve every link and to tell a library in its own file from one compiled into another, and `Fledge::Linkage` asks it of every compiled file of an app's gems, so that a gem that would not load where the app goes fails the build (ADR 006, ADR 007). Which side-by-side assemblies a Windows file's manifest names, for the audit. The oldest macOS a Mach-O file says it runs on, and the newest glibc symbol version an ELF file needs, for a gem Fledge compiles (ADR 006). And whether a Windows program is a console or a GUI program, for the runtime builder and Delivery (ADR 008).

Through 0.0.1.pre.10, `Fledge::Binary` answered the first four by reading ELF's section headers, dynamic section, and version needs, Mach-O's load commands, and PE's import and delay import tables itself, in about 550 lines of Ruby, and the runtime builder, a test, and two Delivery scripts read a PE file's Subsystem at its offset. ADR 010 kept the readers because no one tool was on every computer that builds apps, and because the audit of the Windows runtime, and CI's audit of every runtime, ran on Linux.

Every format has maintained tools that read it:

- **GNU binutils**' `objdump -p` prints an ELF file's dynamic section (a `NEEDED` line per library) and its version references (a line per `GLIBC_X.Y` it needs), and `readelf -d` and `-V` the same; it reads PE too, and on Ubuntu no Mach-O.
- **LLVM**'s `llvm-objdump -p` prints ELF's dynamic section and version references in GNU's form, and a Mach-O file's load commands as `otool -l` does (it is otool's own code: Xcode's `otool` and `objdump` are LLVM's); it prints a PE file's import table but not its delay import table. `llvm-readobj --coff-imports` prints both tables, and `--file-headers` the Subsystem. `llvm-readobj --elf-output-style=JSON` prints JSON, for ELF only.
- **Xcode**'s command line tools install LLVM's objdump as `/usr/bin/objdump` (and otool, vtool, and nm), which read ELF and Mach-O, so every Mac that compiles a gem already has them.
- **Windows** has none. Its shell's `SHGetFileInfo` with `SHGFI_EXETYPE` says whether a program is a console or a GUI program, but nothing names a file's DLLs.

LLVM ships llvm-objdump and llvm-readobj in llvm-mingw, which `runtime/sources.yml` already pins for every computer that builds the Windows runtime (x86_64 and aarch64 Linux, Apple Silicon macOS; 78 to 124 MB, with a 149 MB `libLLVM` the tools load), in the Android NDK the Android runtime builds with, and in LLVM's own releases (one file each in the Windows release, linked statically: llvm-readobj is 8 MB and imports only Windows' own DLLs, inside a 277 MB archive; the Linux and macOS releases are 0.9 to 1.2 GB).

## Decision

### 1. Fledge parses the tools' output, not the formats

`Fledge::Binary` picks out the files that begin as compiled code does (ELF's `\x7FELF`, Mach-O's four magics, DOS's `MZ`, and an archive's `!<arch>`), as file(1) does, and hands them to the tool for their format, many at once. What the tool prints is all it reads: `objdump -p` for ELF and Mach-O (`Fledge::Binary::Objdump`), and `llvm-readobj --file-headers --coff-imports` for PE (`Fledge::Binary::Readobj`). A file the tool does not recognize, a Java class that shares Mach-O's universal magic or a text that begins with MZ, holds no code, as the readers' own checks decided before; LLVM's tools stop at the first such file, so the files after it are handed over again. A static archive is still code that links nothing, which no tool need read. The assemblies a manifest names are found in the file's bytes, as `strings` would find them: a manifest is XML in a resource, and no tool prints it. `Fledge::Binary::Elf`, `MachO`, `Pe`, and `Reader`, the runtime builder's `pe_subsystem`, and the tests' own writers of each format are gone; the tests read files LLVM's clang and lld made (`test/fixtures/binaries/build.rb`), checked in.

One form of output, objdump's, answers ELF and Mach-O on every computer, from GNU's tool and LLVM's alike, which is why Fledge reads `objdump -p` rather than `readelf`, `otool`, and `llvm-readobj`'s JSON, three forms where one does. PE is read by llvm-readobj alone, since objdump does not print the delay import table.

### 2. Which tool, on which computer

Each platform's app is built on that platform (ADR 010), so `fledge build` reads its own platform's files with its own platform's tool (`Fledge::Binary::Readers.local`):

| Computer | Reads | With | Pinned |
|---|---|---|---|
| macOS (arm64) | Mach-O, and ELF for the audit | `objdump`, Xcode's command line tools' (LLVM's) | by Xcode, as codesign is; no download |
| Linux (x86_64, aarch64) | ELF | `objdump`, binutils' | by the distribution; no download |
| Windows (x64) | PE | `tools/llvm-readobj.exe`, which the Windows runtime carries | LLVM 23.1.4's release for Windows, by its archive's SHA-256 and the file's |

The license audit reads every format of every runtime with LLVM's own tools where it needs them (`Fledge::Binary::Readers.llvm`), and otherwise with the computer's: the Windows runtime's build with llvm-mingw's, which it compiles the launcher with; the Android runtime's with the NDK's, which it compiles Ruby with; the macOS and iOS runtimes' builds with Xcode's objdump, and the Linux runtimes' with binutils', which those builds already have; and CI's Licenses jobs, the upstream audits, the licensing page, and the gate, each on one Linux runner, with the pinned llvm-mingw's, through `FLEDGE_LLVM`. A file that begins as compiled code of a format no tool on the computer reads is a violation (`unreadable`), so the audit fails rather than pass code it did not read; a Mac or Linux runtime holds no PE, and CI audits every runtime with LLVM's tools anyway.

`Fledge::Linkage` judges only the files of its own system's format, ELF on Linux, Mach-O on macOS, and PE on Windows, since a loader loads no other; a gem that carries another system's files no longer fails the build for what those files would need there.

The runtime builder reads its Windows launchers' Subsystem and imports with llvm-mingw's llvm-readobj, and Delivery asks Windows' shell, `SHGetFileInfo` with `SHGFI_EXETYPE`, whether the delivered program is a console or a GUI program, as Explorer does. The Android runtime's 16 KB alignment stays the NDK's `llvm-readelf -lW`, and Delivery's `zipalign -c -P 16`.

### Considered

- **llvm-readobj alone, everywhere**, with JSON for ELF: one tool, but Linux and macOS would download it (LLVM's releases for them are 0.9 to 1.2 GB, llvm-mingw's 78 to 124 MB with its 149 MB libLLVM), or every runtime would carry it, where a Mac with Xcode and a Linux with binutils already have a reader.
- **llvm-objdump alone**: it omits PE's delay import table, which `Fledge::Binary` read and the audit resolves.
- **readelf, otool, and vtool**: three forms of output for what objdump prints in one.
- **llvm-mingw's tools in the Windows runtime**: llvm-readobj there loads libLLVM, libc++, and libunwind, 33 MB compressed, against LLVM's own static build's 3 MB.
- **The Ruby readers, kept**: the code AGENTS.md says not to write.

## Consequences

- The readers of ELF, Mach-O, and PE (547 lines, 251 of them code) and the tests' writers of each format (96 lines) are gone. What replaces them is not much shorter, 192 lines of code that find a computer's tools, run them, and pick out what they print, and 33 more in the audit, but none of it knows where a format keeps anything: a malformed or new kind of file is the tool's to read, and a new format version the tool's maintainers'. The tests' 32 fixtures are files a real linker made, by a script of 145 lines that runs clang, lld, and llvm-dlltool.
- On a Mac, an app whose gems carry compiled files needs Xcode's command line tools (`xcode-select --install`), which compiling any gem needs too; on Linux, binutils (`sudo apt install binutils`). A missing tool fails the build with what to install.
- Each Windows runtime carries `tools/llvm-readobj.exe` (Apache-2.0 WITH LLVM-exception, with zlib 1.3.2 and Zstandard 1.5.7 linked in), which the license audit accounts for and checks by SHA-256, and which no app holds. Building the Windows runtime needs `zstd` too, to unpack LLVM's release.
- The audit, and the tests, read every format only where LLVM's tools are; `FLEDGE_LLVM` names them, and without it a test of a format no tool on the computer reads skips (the gate sets `FLEDGE_REQUIRE_READERS`, so none skips there).
- A Mach-O file names its oldest macOS only for platform macOS: an iOS file names none, where the reader took the first version command it found.
