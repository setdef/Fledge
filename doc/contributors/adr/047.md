# ADR 047: Pack and Unpack Archives With the Computer's Own tar

## Context and Problem Statement

Archives are everywhere in Fledge. A runtime arrives as a `.tar.gz`. A built app leaves as a `.tar.gz`, or as a `.zip` on Windows, which Explorer opens with a double-click. The runtime builder, the source bundles, and the license audit pack and unpack them too. Each archive must keep executable bits and symbolic links. Fledge had its own tar reader and writer and its own ZIP writer, about 480 lines.

The maintainer's words of 2026-10-28 (`decisions.md`): "Code is a liability and we should _not_ have 4k+ lines of things we could use existing tools for." What should read and write Fledge's archives?

## Decision Drivers

- No format code of Fledge's own where a maintained tool does the work (ADR 010).
- No new gem for Fledge, or a developer's computer, to install.
- Executable bits and symbolic links survive, and a gem's long paths fit.
- Every computer that builds apps has the tool already.

## Considered Options

1. The computer's own tar: GNU tar on Linux, bsdtar (libarchive) on macOS, and on Windows 10 and 11 the bsdtar Windows ships as `C:\Windows\System32\tar.exe`, which writes ZIP too.
2. The rubyzip (BSD-2-Clause) and minitar (Ruby's license or BSD-2-Clause) gems.
3. RubyGems' own `Gem::Package::TarWriter`.
4. PowerShell's `Compress-Archive` on Windows.
5. Fledge's own tar and ZIP writers.

## Decision Outcome

Chosen: option 1, because every computer that builds apps already has it, it reads and writes both formats with links and modes, and it adds no code or dependency. The gems would make Fledge depend on code it has done without, for what every host's tar does. `TarWriter` refuses a path longer than ustar's 256 bytes, which a gem's files can exceed. `Compress-Archive` would start PowerShell for every archive, and Windows PowerShell 5.1's has written backslashes into ZIP paths. Fledge's own writers are the code the maintainer's words remove.

`Fledge::Archive` runs tar. On Windows it names `System32\tar.exe` itself, since Git's GNU tar, often first on a developer's `PATH`, writes no ZIP and reads `C:` as a host name.

Confidence: high. Every build packs with it, every runtime is unpacked with it, and Delivery unpacks every archive on fresh runners.

### Consequences

- Good, because about 480 lines of Fledge's own format code are gone, and nothing is installed to pack or unpack.
- Bad, because each build writes the app's folder to disk first and archives it from there, where Fledge's writers streamed entries into the archive.
- Bad, because archives are no longer reproducible: GNU tar and bsdtar spell `--sort`, `--mtime`, and `--owner` differently, and nothing reads the dates.
- Bad, because each tar has its quirks Fledge works around: bsdtar on macOS adds AppleDouble files unless `COPYFILE_DISABLE` is set, and Windows' `tar.exe` reads its arguments in the ANSI code page.
- Neutral, because a Windows app may not hold a symbolic link, which Windows would unpack as a text file; the build refuses one.

### Confirmation

`test/archive_test.rb` packs and unpacks with the computer's own tar, including names outside ASCII. Every Delivery job unpacks a built app's archive on a fresh runner of its platform and runs it.

## More Information

- The flags each system's tar gets, and the Windows workarounds: `doc/contributors/design/desktop-apps.md`, "The folder and the archive".
- An archive and each installer get a checksum file, which Ruby's `Digest::SHA256` writes, since no tool on all three systems prints `sha256sum`'s format (same section).
