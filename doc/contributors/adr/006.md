# ADR 006: Compile Native Gems, and Fetch Git Gems, for the Platform Fledge Runs On

## Status
Accepted (requested). Agents wrote this ADR and may change it (AGENTS.md, Questions). It follows the orchestrating agent's directions of 2026-10-27, and applies the maintainer's decisions 8 (nothing Fledge copies into an app may carry copyleft obligations beyond notices, with the replies of 2026-10-26, later: LGPL only as a separate, replaceable shared library), 9 and 20 (an app's code runs as it does without Fledge; "my ruby code just works" outranks size), and 7 (glibc 2.39 is the Linux floor), in `doc/contributors/decisions.md`. It replaces ADR 005's refusal of every gem with an extension still to compile (section 6) and of every git gem, and extends ADR 005's audit of compiled code (section 7) to what Fledge compiles. ADR 007 supersedes the parts that judged an app's gems by their licenses (section 8's license checks, section 9's refusal of nokogiri on Windows, and section 10), on the maintainer's words of 2026-10-28: an app's gems, licenses and all, are its developer's choice and responsibility. Section 8's linkage check stays.

## Date
2026-10-27

## Context

ADR 005 ships the gems an app's Gemfile.lock locks, each as built for the target, which works for pure-Ruby gems and for gems precompiled for every target. It refused two kinds of gem, and both have users waiting:

- **Gems that compile at install.** Tokra (a Ruby port of Tauri) compiles its Rust extension with rb-sys when it is installed (`tokra.gemspec`: `spec.extensions = ["ext/tokra/extconf.rb"]`, `spec.add_dependency "rb_sys"`). Ferro's gems bind Rust crates the same way, each shipping its Cargo.lock so an install compiles exactly the versions the repository tested (`gems/idna/ferro-idna.gemspec`, and `ext/ferro_idna/extconf.rb`, `create_rust_makefile` with `--locked`). Many C gems publish only their source (redcarpet, among the most used).
- **Gems from git.** Ferro's gems are consumed from git tags, `gem "ferro-idna", git: "https://github.com/setdef/Ferro", tag: "ferro-idna/v0.1.0.pre.1", glob: "gems/*/*.gemspec"`.

A precompiled build stays the way a gem ships whenever there is one that may: the orchestrating agent directed, on 2026-10-27, after the maintainer asked about gems that ship precompiled builds, that they stay the preferred path, and that compiling only fills the gaps, a target with no precompiled build (or, until ADR 007, one whose build the license policy refused). ratatui_ruby, the maintainer's own Rust gem, is the case for both: 1.5.2 publishes precompiled builds for `arm64-darwin`, `x86_64-linux`, and `x64-mingw-ucrt`, each a fat gem with one binary per Ruby from 3.2 to 4.0 (`lib/ratatui_ruby/4.0/ratatui_ruby.bundle`), and its source, but none for `aarch64-linux`; 1.5.1 named its macOS build `arm64-darwin-23`. It is LGPL-3.0-or-later, which ADR 005's rule for an app's gems (notice-only, or refused) refused outright until section 10, and then ADR 007, which judges no gem by its license.

A third case comes from the license audit: nokogiri 1.19.4's precompiled `arm64-darwin` and `x64-mingw-ucrt` builds compile GNU libiconv in statically (ADR 005, section 7), so they were refused until ADR 007. Its precompiled builds are cross-compiled, and its `extconf.rb` builds GNU libiconv from source when it cross-compiles or builds on Windows (`ext/nokogiri/extconf.rb` at 1.19.4, `if cross_build_p || windows?`, line 767, and `unless unix?`, line 827), but a native build on a Mac takes macOS's own `iconv.h` (line 853).

An extension must suit the Ruby that loads it: its headers, its `RbConfig`, its ABI (RubyGems names the folder an extension goes in by `Gem.extension_api_version`, which is `4.0.0-static` for rv-ruby's static Ruby and `4.0.0` for RubyInstaller's). In a built app that Ruby is the runtime's, not the developer's.

Prior art, read for this decision:

- **`gem install`** builds a gem's extensions for the Ruby running it, on the computer running it (`Gem::Installer#install`, `rubygems/installer.rb` lines 268 to 305 at Ruby 4.0.9; `Gem::Ext::Builder#build_extensions`, `rubygems/ext/builder.rb` lines 257 to 277, which installs each extension into the gem's extensions folder and its require path and marks it `gem.build_complete`), and writes the options it built with into `build_info/FULL_NAME.info` (`Gem::Installer#write_build_info_file`, lines 902 to 918). It runs `make clean` after it installs, so a gem's folder keeps no objects, but keeps the Makefile and, in the extensions folder, `gem_make.out` and `mkmf.log`, which hold the build machine's paths.
- **mkmf** links no libruby into an extension of a static Ruby (`mkmf.rb` at Ruby 4.0.9, lines 2753 to 2769: `$LIBRUBYARG` stays empty unless Ruby is shared), but links the test programs of `have_func` and the rest against `LIBRUBYARG`, which for a static Ruby is the static libruby (line 542).
- **Bundler** passes `bundle config build.NAME` to a gem's `extconf.rb`, split as a shell would (`Bundler::GemInstaller#spec_settings`, `bundler/installer/gem_installer.rb` lines 59 to 65 at Bundler 4.0.20). It never compiles a path gem's extension (`Bundler::Source::Path#install` generates its executables with extensions disabled, `bundler/source/path.rb` line 80). It keeps a git gem's checkout of the locked revision at `GEM_DIR/bundler/gems/BASE-SHORTREF` (`Bundler::Source::Git#install_path` and `#base_name`, `bundler/source/git.rb` lines 128 to 139 and 370 to 380), with every gemspec evaluated and written back so no git is needed to load it (`#serialize_gemspecs_in`, lines 321 to 332), counts a checkout installed whatever its `.git` holds (`GitProxy#installed_to?`, `git_proxy.rb` lines 179 to 183), and puts a git gem's extensions in `GEM_DIR/bundler/gems/extensions/PLATFORM/ABI/BASE-SHORTREF-FOLDER` (`Gem::Specification#extension_dir`, `bundler/rubygems_ext.rb` lines 226 to 236).
- **RubyInstaller** puts MSYS2's tools on `PATH` before RubyGems builds a gem with extensions (its `rubygems/defaults/operating_system.rb`, a `Gem.pre_install` hook calling `RubyInstaller::Runtime.enable_msys_apps(for_gem_install: true)`, line 39 at RubyInstaller 4.0.9-1), finding MSYS2 by `MSYS2_PATH`, beside Ruby, at `C:\msys64`, in the registry, or on `PATH` (`msys2_installation.rb`, `iterate_msys_paths`).
- **Briefcase** installs a Python app's requirements from binary wheels only when it builds for another platform, and fails naming a package that has none; **rake-compiler-dock** cross-compiles gems in containers, a toolchain per target.
- **auditwheel** (6.4.2, `policy/manylinux-policy.json`) says which shared libraries a Linux binary may assume of every distribution with a given glibc (`lib_whitelist`), and reads which glibc a binary needs from its symbol versions; PEP 600 defines the manylinux tags it checks.
- **cargo-deny**'s licenses check judges every crate a Rust build resolves, build dependencies included, against an allow list; **cargo metadata** reports, for a manifest and its Cargo.lock, every package, its license, and the resolved dependency graph with each edge's kind (normal, build, dev), filterable to one target platform.

## Decision

### 1. Compile only for the platform Fledge runs on, and only what has no build that may ship

`fledge build` takes each gem's build as the built app's Bundler would choose it (ADR 005, section 6), so a precompiled build that fits the target always wins, and only a gem whose lockfile entry for the target is its source build, because it publishes no build for the target or because `force_ruby_platform` asks for its source (as `examples/nokogiri_app` does, to show a large C gem that builds its own libraries compiling), compiles. A gem with an extension still to compile (a `ruby`-platform gem, or a git gem, whose specification names extensions) is compiled when the target is the platform Fledge runs on (`Fledge::Platform.local`), and fails the build for any other target, naming the gem, the target, and this computer, and saying to build on that platform (a CI runner of it) or choose a version precompiled for it. This is what `gem install` does; cross-compiling C and Rust for another platform, as rake-compiler-dock does, needs a toolchain and a Ruby per target and stays later work. A project that ships to every platform from one machine still can when its gems are pure Ruby or precompiled (ADR 001, section 2); one with a gem that only compiles builds each target on that target's own computer.

The built app's Bundler runs as the runtime's Ruby's platform, `Gem::Platform.local`, which RubyGems takes from RbConfig's `arch` (`arm64-darwin23` for rv-ruby's macOS 14 build), whatever computer it runs on. So `fledge build` reads that `arch` from the runtime's `rbconfig.rb` and judges both whether the lockfile locks the target and which build of each gem fits it exactly as that Bundler would (`Bundler::Definition#current_platform_locked?`, `bundler/definition.rb` lines 832 to 836 at Bundler 4.0.20, and RubyGems' `Gem::Platform#===`): a lockfile platform or a gem's build named `arm64-darwin` or `arm64-darwin-23` fits, `arm64-darwin-24` does not, and a gem with only an `arm64-darwin-24` build falls back to its source build, as RubyGems would refuse to load it on the runtime.

### 2. Against the runtime's own Ruby, which runs the build

`Fledge::NativeBuild` unpacks the target's runtime and its build-only companion (section 3) into the build's work folder, and runs the runtime's own Ruby (`bin/ruby`, or `ruby\bin\ruby.exe` on Windows) on a small script that installs each gem as RubyGems installs one (`Gem::Installer.at(...).install`, with the gem's build options and without its dependencies, which it installs first) into a gem folder of its own, and for a git gem builds its extensions in a copy of its checkout into Bundler's extensions folder (`Gem::Ext::Builder#build_extensions`, with the specification's `extension_dir` set as Bundler's would be). So the headers, `RbConfig`, compiler flags, `Gem::Platform.local`, and `Gem.extension_api_version` are the runtime's, and the extension is laid out where the built app's RubyGems and Bundler look for it. The developer's Ruby compiles nothing.

The script runs with the caller's environment less every variable the launcher hides from an app's boot (`RUBY*`, `GEM_*`, `GEMRC`, `BUNDLE_*`, `BUNDLER_*`, `RI_FORCE_PATH_FOR_DLL`; `runtime/launcher/scrub.c`), so `bundle exec fledge build` cannot load the developer's Bundler into it, and with `GEM_HOME` and `GEM_PATH` naming the build's gem folder. The gems a compiled gem needs to build (rb_sys and its rake-compiler-dock for an rb-sys gem, mini_portile2 for nokogiri) are installed there first, in dependency order, from the lockfile's own files.

### 3. A build-only companion beside each runtime

A runtime prunes what no running code reads, headers and static and import libraries among it (ADR 003, section 2), and its SBOM lists every file it holds, so it cannot carry them and still be what ships. Each runtime build therefore writes a companion, `fledge-runtime-VERSION-PLATFORM-dev.tar.gz`, with the runtime's own top folder so it unpacks over it, holding Ruby's headers (`include/`), the library extension builds link against (static libruby on macOS and Linux, for mkmf's test programs; the import library of Ruby's DLL, `lib/libx64-ucrt-ruby400.dll.a`, on Windows), and `DEV-NOTICES.txt` with the text of Ruby's license and, beside a static libruby, Rust's (the Rust standard library is compiled into YJIT). The license audit's map already owns these files as Ruby's (`runtime/licenses.yml`), and CI's audit of rv-ruby's and RubyInstaller's whole trees finds no copyleft code in them; rv-ruby's `lib/libcrypt.a`, which is libxcrypt, never comes along. Releases publish the companion beside each runtime, `Fledge::Runtimes#dev_archive` finds it as it finds the runtime (from `FLEDGE_RUNTIME_DIR`, the cache, or the release, checked against `SHA256SUMS`), and `fledge build` fetches it only when it compiles a gem. Nothing in it is copied into an app.

### 4. The developer's toolchain, held to the runtime's floors

The compiler is the developer's: Xcode's command line tools on macOS, the C compiler and make on Linux, MSYS2's UCRT64 toolchain on Windows, which the script enables as RubyInstaller's own hook does (the runtime keeps RubyInstaller's Ruby library, so `RubyInstaller::Runtime.enable_msys_apps(for_gem_install: true)` finds MSYS2 where RubyInstaller would), and cargo for a Rust extension. A Rust extension for RubyInstaller's Ruby takes Rust's GNU target, as rb-sys requires, and bindgen needs a libclang (Ferro's CI, `.github/workflows/ci.yml`, sets `LIBCLANG_PATH` and `BINDGEN_EXTRA_CLANG_ARGS` for Windows; Fledge's CI does the same).

A compiler targets the computer it runs on unless told otherwise, and a runtime runs on older ones. So the build sets `MACOSX_DEPLOYMENT_TARGET` to the runtime's oldest macOS, 14.0 (ADR 001, section 3), which clang and rustc both read, and Fledge reads every file the build wrote and fails one built for a newer macOS (its `LC_BUILD_VERSION`) or needing a newer glibc than 2.39 (its newest `GLIBC_` symbol version, as auditwheel reads it), saying what to change.

### 5. What a compiled gem ships

A compiled gem ships what its package holds (the `.gem`'s files, specification, and cache copy, as ADR 005 installs a precompiled gem, or a git gem's checkout), the files its build wrote into its require paths (where RubyGems installs an extension), its extensions folder with `gem.build_complete`, without `gem_make.out` and `mkmf.log`, and its `build_info` when it had build options. The build's other leftovers (the Makefile beside `extconf.rb`, a Cargo target folder, debug symbols) stay behind: nothing an app runs reads them, and they hold the build machine's paths.

### 6. Build options are Bundler's

`bundle config build.NAME` at any level Bundler reads (the project's `.bundle/config`, `BUNDLE_BUILD__NAME`, or the developer's own) reaches the gem's `extconf.rb`, split as Bundler splits it. A project that needs an option to build a gem the way it should ship says so the way it already would for `bundle install`; `examples/nokogiri_app` keeps `build.nokogiri --disable-xml2-legacy` in its `.bundle/config`.

### 7. Git gems ship at the locked commit, as Bundler lays them out

`Fledge::Bundle` takes a git gem as a `Fledge::GitGem`: its repository, the revision the lockfile locks, which must be a whole commit (40 or 64 hexadecimal digits; anything else is refused, since nothing else pins it), the glob its gemspecs are found by, and what the Gemfile asked for (a tag, branch, or ref, for the notices). A git source with submodules is refused for now. `Fledge::GitCheckout` keeps a bare clone of each repository in `~/.cache/fledge/git`, fetches only when the locked commit is missing, refuses a commit the repository does not hold, checks the commit out into the build's work folder, and evaluates every gemspec there as Bundler does. `Fledge::GitPackage` ships each locked gem's own folder of the checkout, the one its gemspec is in, less `.git`, where Bundler keeps it (`GEM_DIR/bundler/gems/BASE-SHORTREF/FOLDER`), and refuses a gemspec whose version is not the lockfile's. The built app's Bundler, frozen, finds each gem there by its gemspec, without git. The rest of the repository stays behind, though `bundle exec` would find it in its own checkout, because a repository holds more than its gems: Ferro's holds its own tooling, and symbolic links, which a Windows `.zip` cannot hold (ADR 002, section 2), as CI found the first time it built Ferro's gem for Windows. (This section once gave a license reason too, that Ferro's tooling is AGPL; ADR 007 leaves an app's gems' licenses to its developer, and the technical reason stands alone.) A gem whose gemspec is at its repository's top ships the whole checkout, as its folder. A git gem with nothing to compile ships for every target from any computer; one with an extension compiles as section 1 says.

A path gem inside the project still ships as part of the project (ADR 005), but one whose gemspec has an extension fails the build: Bundler never compiles it, so `bundle exec` loads whatever the developer last compiled there for their own Ruby, which the runtime's Ruby may not load. Take such a gem from git or a gem server.

### 8. Everything compiled must load where the app goes

Every gem an app ships, precompiled or compiled, passes one check of its compiled files, `Fledge::Linkage`: a compiled file may need only libraries the target's operating system provides (on Linux, those manylinux_2_39 allows, auditwheel 6.4.2's list, and glibc's loader; on macOS, `/usr/lib` and `/System/Library/Frameworks`; on Windows, the system DLLs `runtime/licenses.yml` lists and `bcryptprimitives.dll`, which Rust's standard library imports), the runtime ships (Ruby's DLL, `libgmp-10.dll`, `libcrypt.so.2`, and the rest), or the gem itself carries. Anything else fails the build: the app would not load it on another computer. A file built for another Ruby (a precompiled gem's `lib/nokogiri/3.4/nokogiri.so`, which needs `x64-ucrt-ruby340.dll`) is never loaded and not judged. The check found its first real case at once: nokogiri's vendored libxml2, built from source on a Mac with Homebrew, linked Homebrew's `liblzma`.

This section also judged what a gem's compiled files held by license: a copyleft library's code compiled in failed whatever anyone declared, the rest had to be attributed to a review in `compiled_code.yml` or to `fledge.yml`, and each Rust crate a Rust extension compiled in, or ran while compiling, was read with `cargo metadata` (`Fledge::RustCrates`) and had to ask nothing beyond notices. ADR 007 removed all of that.

### 9. nokogiri

Built from source on a Mac (`gem "nokogiri", force_ruby_platform: true`, with `bundle config build.nokogiri --disable-xml2-legacy` so its libxml2 links none of the build machine's own libraries), nokogiri 1.19.4 compiles in libxml2, libxslt, and libgumbo, and loads macOS's own iconv. On Windows its `extconf.rb` builds GNU libiconv from source and links it in statically; this section once refused that build for it, and since ADR 007 it ships. `examples/nokogiri_app` builds and delivers on both in CI. Its precompiled builds ship on every platform.

### 10. LGPL gems (superseded by ADR 007)

This section let a gem under the LGPL ship, as its own files whoever receives the app may replace, only when its exact source was pinned, and named that source in `notices/GEMS.txt`; GPL, AGPL, and MPL gems still failed. ADR 007 ships every gem whatever its license.

## Consequences

- An app whose gems include Tokra- and Ferro-shaped Rust extensions, from a gem server or from git, and C gems published only as source, builds and runs on each platform when built on that platform. `examples/native_app` (redcarpet, and ferro-idna from its git tag) builds and delivers on macOS, both Linux architectures, and Windows in CI, each on its own runner, beside the one Linux runner that cross-builds everything without a source-only gem.
- Building for a target with a source-only gem needs a computer of that platform with a compiler, and on Windows MSYS2's UCRT64 toolchain; a Rust gem needs cargo, and rb-sys needs libclang.
- Each release carries four more assets, the build-only companions, as CI built them on 2026-10-27: 0.5 MB for Windows, 19.3 MB for macOS, and 26.6 MB and 27.4 MB for x86_64 and aarch64 Linux, nearly all of it static libruby, downloaded only when compiling.
- A compiled build is only as reproducible as the developer's toolchain; the lockfile pins the gems and crates, not the compiler.
- Not yet: cross-compiling; git submodules; and path gems with extensions.
