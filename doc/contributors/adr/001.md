# ADR 001: Ship an app as a small C launcher that embeds CRuby

## Context and Problem Statement

A Ruby app runs where Ruby is installed. Almost nobody who would play a Ruby game, open a Ruby desktop app, or run a Ruby terminal tool has Ruby. Asking them to install the right version, with a compiler for the gems that need one, loses most of them before the app starts. A developer who wants to hand someone an app has no answer that ends in "unzip it and double-click."

What runs an app's Ruby code on a computer that has no Ruby, and what is the program the person starts? This is the top of every app Fledge builds, on every desktop platform.

## Decision Drivers

- A person who runs the app never meets Ruby: no install step, no error that names Ruby (AGENTS.md, Design precedence 1).
- The app's code runs as under `ruby main.rb`, so C extensions and CRuby's own behavior are CRuby's (Design precedence 2).
- On macOS the program is a bundle's executable, which Fledge lays out and signs as Apple's tools expect.
- macOS wants windows and events on the process's main thread.
- Lota, Tokra, Rooibos, and apps with no framework share one way to ship.

## Considered Options

1. A small C launcher that embeds CRuby as Ruby's own `main.c` does, beside a relocatable Ruby, as LÖVE's fused games, Tauri, and PyInstaller ship a program beside their runtime.
2. A single-file packager: Tebako or OCRAN.
3. A copy of the developer's own Ruby, shipped with the app.
4. Another Ruby: JRuby, TruffleRuby, or IronRuby.

## Decision Outcome

Chosen: option 1, a launcher, because it is the only option that runs CRuby itself, starts it with no unpacking, and leaves the bundle's layout and signing to Fledge.

The launcher is the executable a person runs, renamed to the app's name. It finds the folder beside it, reads `fledge.cfg` there to learn which program to run, and starts CRuby with the calls `main.c` makes. Ruby runs on the process's main thread. On macOS and Linux libruby is linked into the launcher, so the launcher is the interpreter; on Windows it loads Ruby's DLL (ADR 038). It runs the app's program as `ruby PROGRAM` runs it (ADR 081), with the person's Ruby settings hidden from Ruby's boot (ADR 040). `doc/contributors/design/launcher.md` says how it does each step.

Confidence: high. Delivery runs built apps on fresh computers with no Ruby on every desktop platform, and Lota's spike had proved the same launcher on macOS before Fledge began.

### Consequences

- Good, because nothing unpacks to a temporary folder or mounts a file system when the app starts; it starts as `ruby` starts.
- Good, because the launcher is the same program for every app. Each app's details live in `fledge.cfg` beside it, so nothing about one app is written into a signed program (ADR 016), and on macOS the launcher is the bundle's own executable (ADR 008).
- Good, because C extensions, YJIT, and the standard library are CRuby's, as the app's developer ran them.
- Bad, because an app is a folder with a whole Ruby in it: tens of megabytes before compression, more than a fused LÖVE game.
- Bad, because Fledge needs a relocatable CRuby for each platform, prebuilt and pinned (ADR 093, ADR 035).
- Bad, because Fledge maintains C code adapted from Ruby's `main.c` in two variants, `unix.c` and `windows.c`, and must follow `main.c` when Ruby changes it.
- Neutral: the code adapted from `main.c` carries Ruby's license in SPDX snippets, and `runtime/launcher/ruby_main.c`, Ruby's `main.c` itself, is under Ruby's license; the rest of the launcher is Fledge's, under MIT.

### Confirmation

- The Delivery jobs of `.github/workflows/ci.yml` unpack each built app on a fresh runner, in a folder other than the one it was built in, with no Ruby on `PATH`, and check what it prints (`.github/scripts/deliver.sh`, `deliver.ps1`). In containers, `deliver.sh --no-ruby-installed` refuses to run on a computer that has a Ruby at all.
- `.github/workflows/installed.yml` does the same from a released tag, with the published runtimes.
- The parity check proves the app sees the Ruby it would see under `ruby main.rb` (ADR 081).

## Pros and Cons of the Options

### A single-file packager (Tebako, OCRAN)

- Good, because the person gets one file.
- Bad, because it unpacks to a temporary folder or mounts a virtual file system on every launch.
- Bad, because it controls less of a macOS app's layout and signing than a launcher does.

### A copy of the developer's own Ruby

- Bad, because a Ruby built by a version manager or a package manager records absolute paths when it is built (its prefix, its library folder, where OpenSSL and libyaml are) and links the computer's shared libraries. A copy on another computer looks for those paths and libraries, and fails.

### Another Ruby

- Bad, because JRuby needs a Java runtime, which only moves the problem.
- Bad, because TruffleRuby ships large native images and is not CRuby, so C extensions and CRuby's behavior differ.
- Bad, because IronRuby is no longer maintained.
- Bad, because people who use Ruby, and the frameworks Fledge serves, run CRuby.

## More Information

- LÖVE's fused games join a game to LÖVE's own executable, which notices the game it carries and runs it; the player never meets LÖVE or Lua. Lota's ADR 002 (`setdef/lota`, `doc/contributors/adr/002.md`) applies the same design to Ruby, with a small C launcher after Ruby's `main.c`, and its spike proved it on macOS with a 35-line launcher and a prebuilt Ruby. Fledge generalizes it from games to any Ruby app.
- The Tauri bundler and PyInstaller ship a program beside the runtime it needs; Briefcase and python-build-standalone show the same for Python with prebuilt, relocatable interpreters.
- Related: ADR 081 (what the launcher passes Ruby), ADR 037 (console and windowed launchers), ADR 038 (Windows), ADR 040 (the person's Ruby settings), ADR 093 and ADR 035 (the runtimes), and `doc/contributors/design/architecture.md` for how the parts fit.
