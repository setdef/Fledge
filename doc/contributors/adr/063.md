# ADR 063: A Built App Runs the Bundler Its Lockfile Names

## Context and Problem Statement

A Gemfile.lock records the Bundler that wrote it under `BUNDLED WITH`. `bundle install` installs that Bundler, and `bundle exec`, `bundler/setup`, and every `bundle` command then switch to it from Ruby's own: `Bundler.auto_switch` (`bundler.rb`, lines 172 to 174, at Bundler 4.0.20) calls `Bundler::SelfManager#restart_with_locked_bundler_if_needed`, which re-executes the program under the locked version when it is installed (`bundler/self_manager.rb`, lines 9 to 14 and 70 to 96). The program then runs with `BUNDLER_VERSION`, `BUNDLE_BIN_PATH`, `BUNDLER_SETUP`, `RUBYLIB`, and `RUBYOPT` naming that Bundler, and that Bundler's lib first on `$LOAD_PATH` (`bundler/shared_helpers.rb`, `set_bundle_variables`, `set_rubyopt`, and `set_rubylib`).

A built app always ran the runtime's default Bundler, since its `.bundle/config` says `BUNDLE_VERSION: system`, after Warbler (ADR 005, section 5). With Ruby 4.0.9 the two matched for Fledge's examples, which Bundler 4.0.20 locked. On Ruby 4.1's preview, whose Bundler is 4.1.0.beta2, `examples/my_cool_app` showed five unjustified differences from `bundle exec` in the gem-shaped parity check: `$LOAD_PATH`, `$LOADED_FEATURES`, the installed gems, `ENV`, and a child's `ENV` (`doc/contributors/research/2026-11-09-ruby-4.1-spike.md`, Problems found, item 2). Any app whose lockfile another Bundler wrote meets the same on any Ruby, and `bundle install` never moves `BUNDLED WITH` on its own, so most lockfiles name an older Bundler than the newest Ruby's.

Which Bundler should a built app run?

## Decision Drivers

* A person who runs the app never meets Ruby: no Bundler error, install, or download at run time (AGENTS.md, Design precedence 1).
* The app's Ruby code runs as under `bundle exec`, and a difference is a bug unless it is justified (Design precedence 2). Fledge must never surprise an app developer with how Ruby behaves compared with not using Fledge (decisions, 2026-11-02).
* Every external input is pinned by SHA-256.
* Code is a liability (decisions, 2026-10-28).
* The fix works on Ruby 4.0.9 and on 4.1.

## Considered Options

1. The built app runs the Bundler the lockfile names, as `bundle exec` does. `fledge build` ships that Bundler's gem, fetched and checked as every locked gem is, and the launcher loads it in place of the runtime's own.
2. `fledge build` refuses a lockfile whose `BUNDLED WITH` differs from the runtime's Bundler, saying how to relock.
3. The app keeps the runtime's Bundler, and `Parity::JUSTIFIED` lists the difference with its reason. Warbler does this, and warns at build time that "the packed application will boot with the default bundler of the packed JRuby" (`lib/warbler/traits/bundler.rb`, lines 17 to 22 and 142 to 151, at jruby/warbler 3196d5f9).

## Decision Outcome

Chosen: option 1, because it alone gives the app what `bundle exec` gives it with nothing at run time that a person could meet. Option 3 leaves the app running a different Bundler from the one its developer tested with, which is the surprise the maintainer's 2026-11-02 words rule out, and Warbler's reason for it, that a switch restarts the process, which a servlet container or a jar cannot do, does not hold for Fledge: the launcher chooses which Bundler to require before any runs, so no restart is needed. Option 2 makes no difference at run time, but refuses most real lockfiles, and every app again each time Fledge's runtime moves to a newer Ruby, and it asks developers to change the Bundler they work with to Fledge's.

Confidence: high that the app now matches `bundle exec`, which the parity check shows on every platform CI runs it on. Medium on phones, whose runtimes compile the same code but whose parity check has no app that names another Bundler.

What `fledge build` does, following `Bundler::SelfManager#find_restart_version` (lines 190 to 200):

* It takes the version from `BUNDLED WITH`, or from Bundler's own `version` setting when that names one, and ships nothing when the setting is `system`, the version is a development build (`.dev`), or it is the runtime's own Bundler.
* It fetches that Bundler's `.gem` from RubyGems.org, through Bundler's mirror and with its login, as Bundler fetches it (`#remote_specs`), checks it against the lockfile's `CHECKSUMS` entry for `bundler (VERSION)`, which Bundler 2.6 and newer write, and refuses a lockfile without one. When the gem's `required_ruby_version` excludes the runtime's Ruby, the app keeps the runtime's Bundler, as `bundle install` does when it finds no build of the locked Bundler for the running Ruby (`#install_and_restart_with`, lines 48 to 63).
* It installs the gem in the runtime's gem folder beside Ruby's own Bundler, and `fledge.cfg` names its version as `bundler = VERSION`. `fledge build --from` keeps it, as it keeps the lockfile.

The launcher on every system, and the phones' embedding API, read that key and put the gem's lib first on `$LOAD_PATH`, where `bundle exec`'s `RUBYLIB` puts it, then require its `bundler` and `bundler/setup` by path, as `bundle exec`'s `RUBYOPT` does (`runtime/launcher/bundler.c`). Bundler itself then sets `ENV` as `bundle exec` would (ADR 005, section 5). The app's `.bundle/config` keeps `BUNDLE_VERSION: system`, so that neither the app nor a Ruby it starts ever tries to switch again.

### Consequences

* Good, because an app runs with the Bundler its developer runs it with, on any Ruby, and the parity check holds without a new justification of what Bundler does, only of where its files are.
* Good, because a person still installs and downloads nothing: the Bundler ships in the app, and the launcher never restarts.
* Bad, because a build may download one more gem, about 450 KB, and an app grows by the Bundler it carries, about 2 MB unpacked.
* Bad, because a lockfile with no checksum for its Bundler, which Bundler before 2.6 wrote, now fails the build with what to run. Such a lockfile had no checksums for its gems either, so it failed for any app with gems before.
* Bad, because the launcher's C now writes the Ruby that loads Bundler from a version in `fledge.cfg`, which the launcher must check holds only a version's characters.
* Neutral, because a Bundler much older than the runtime's Ruby may not run on it. `bundle exec` fails the same way, and the build cannot tell until the app runs.

### Confirmation

* `rake parity`, in every Test job in CI, builds `test/fixtures/bundled_with`, whose lockfile Bundler 4.0.19 wrote, a version no runtime ships, and compares it with `bundle exec` after `bundle install`. Its allowed differences are only where each Bundler is: the person's `GEM_HOME` or the runtime's gem folder (`Parity::JUSTIFIED`).
* Delivery runs the same fixture's program on a fresh computer with no Ruby, and it must print what `bundle exec` printed where it was built: the Bundler that set it up, and the `BUNDLER_VERSION` it hands a Ruby it starts.
* Unit tests cover the choice of version (`test/bundle_test.rb`), the build (`test/gem_app_build_test.rb`), `fledge.cfg` (`test/assembly_test.rb`, `test/build_from_test.rb`), and the launcher's reader and code (`test/launcher_bundler_test.rb`).
