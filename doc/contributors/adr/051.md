# ADR 051: Sign a Windows App Through the Developer's Own Command, Run Through cmd.exe as makensis Runs It

## Context and Problem Statement

`--sign THUMBPRINT` (ADR 016) reaches only a certificate in Windows' certificate store. A certificate kept in a cloud or a hardware service signs only through that service's own tool: Microsoft's Artifact Signing (formerly Trusted Signing) through signtool with its `/dlib` plug-in and an account's metadata file, DigiCert KeyLocker through `smctl`, SSL.com eSigner through CodeSignTool, a cloud KMS through its own. Decision 17 (`decisions.md`, 2026-10-26) asks that a developer who has done Microsoft's ceremony be able to make Windows not block the app.

A Windows app's files are signed twice over: Fledge signs each program and library, and makensis signs the uninstaller and the setup program as it writes them, through NSIS's `!uninstfinalize` and `!finalize`, which run a command line through `cmd.exe`. How does a developer sign with a service Fledge has no code for?

## Decision Drivers

- One seam reaches every service, with no code in Fledge for any of them, since no agent holds an account to test one.
- The command behaves the same for a program as for the setup program, which makensis signs.
- The command may hold a secret, so Fledge never prints it.
- A CI secret can hold the whole command.

## Considered Options

1. `--sign-command COMMAND`, run once for each file, with `%1` for the file's path, through `cmd.exe` exactly as makensis runs its finalize commands.
2. An option for each service: Artifact Signing's `/dlib` and metadata file, KeyLocker's `smctl`, eSigner's CodeSignTool.
3. Tauri's `signCommand`: a string split on spaces and run with no shell.

## Decision Outcome

Chosen: option 1, because one command reaches every service and every hardware token, and running it as makensis runs it makes a command behave the same for every file it signs, environment variables and `.cmd` files included. Option 2 would be code and a test for each service, none of which an agent can reach. Option 3 would make the programs and the setup program differ, since makensis always uses `cmd.exe`.

Fledge runs COMMAND for each PE file it signs, in the order of their paths, and makensis runs it on the uninstaller and then the setup program; Fledge then runs it on an MSIX package (ADR 075). Exit status 0 means signed; anything else fails the build, naming the file and never the command. `FLEDGE_SIGN_COMMAND` stands for the option in a Windows build whose command line gives neither `--sign` nor `--sign-command`, as an environment variable is a default an option overrides; a build for another system ignores it. `--sign-command` and `--sign` exclude each other, and `--sign-command` is a build error outside Windows and a usage error for a phone.

Confidence: medium. A stand-in signer and the Windows SDK's real signtool, run through `--sign-command` with CI's self-signed certificate, prove the seam; no run has reached a real service.

### Consequences

- Good, because a developer whose certificate lives in a cloud or a hardware service signs with that service's own tool, and Fledge owns only the files, their order, and the failure.
- Good, because the same command signs the setup program and its uninstaller, so nothing a person downloads is unsigned.
- Bad, because the command is run once per file, which is slower than `--sign`'s batches of 50 for a tool that takes many; a developer's script can batch on its own.
- Bad, because makensis has no escape for a quote of the kind a string is quoted with, so a command that holds `'`, `` ` ``, and `"` all fails the build, saying to put it in a `.cmd` file.
- Neutral, because `FLEDGE_SIGN_COMMAND` stays Windows-only through 1.x; a signing command for another system would need a variable of its own.

### Confirmation

`test/sign_command_test.rb` checks the path's place and makensis's form, and `test/integration/sign_command_signer_test.rb` runs `test/support/stand_in_signer.rb`, a `.cmd` file on Windows and a shell script elsewhere that records each path and marks each file: it checks one run per file in order, and a failure that names the file and not the command; `test/integration/windows_signed_build_test.rb` runs, on Windows with a runtime, a whole build through `FLEDGE_SIGN_COMMAND`. CI's Windows Build jobs build `examples/hello` and `examples/windowed_app` with `--sign-command` running the real signtool, and `.github/scripts/deliver-signed.ps1` verifies them on fresh runners.
