# ADR 055: An App Gets the Runtime of the Ruby Minor That Runs fledge build

## Context and Problem Statement

A Fledge release carries a runtime for each Ruby minor it supports. Something must pick which one an app gets. The maintainer's words of 2026-11-03 (decisions.md) set the bounds:

> A minor release can make additional rubies available, but can only change the defaults' patch versions--unless we abandon the concept of default entirely, and require app devs to specify a version (maybe better?); then it's limited to e.g. generated config files, which can change in a minor version because they don't get re-generated on upgrade.
>
> Ruby doesn't follow SemVer, so 4.1 is expected to have breaking changes from 4.0.

So an app must never move to a new Ruby minor unless its developer chooses it. He left to the agents whether Fledge has a default at all. How does Fledge pick an app's Ruby?

## Decision Drivers

- The app's Ruby must be the one its developer's tests ran on (Design precedence 2).
- No release moves an app to a new Ruby minor.
- A lone `main.rb` with no Gemfile, the README's greeter, should build as it is.
- One statement of the app's Ruby, which cannot disagree with another.

## Considered Options

1. No default: the Ruby that runs `fledge build` picks the runtime of its own minor.
2. A default Ruby that Fledge moves to a new minor once a year, the first draft of 2026-11-03.
3. Require a `ruby` line in the Gemfile, as Heroku recommends.
4. Read `.ruby-version` in Fledge.
5. A `ruby` key in `fledge.yml`, written by a generator such as `fledge init`, which the maintainer suggested.

## Decision Outcome

Chosen: option 1, because the Ruby running Fledge is the one the developer already chose and tested on, and each other option adds a second statement of it that can disagree. The build uses the runtime of that Ruby's major and minor version, such as 4.1, at the patch the Fledge release ships. It fails, naming both versions, when the release has no runtime for that minor. A developer on a Ruby minor Fledge has no runtime for is refused, and so is one on a minor Fledge has dropped. A Gemfile's `ruby` line must still accept the runtime's Ruby, as `Fledge::Bundle` checks.

The selection names a minor, not a patch. A runtime carries one patch of its minor, and Fledge moves it. A developer who wants an exact patch writes `ruby "X.Y.Z"` in the Gemfile, and Bundler and Fledge then refuse every other.

Confidence: high that it works, and it adds nothing to a project; the prior art agrees, since Briefcase and PyInstaller work this way.

### Consequences

- Good, because no project names its Ruby anywhere new, and the greeter builds as before.
- Good, because no Fledge release ever moves an app to a new Ruby minor. A new Ruby reaches apps as fast as developers adopt it.
- Bad, because an app's Ruby follows the computer that builds it: a laptop on one minor and a CI runner on another build different apps. The remedy is `.ruby-version`, with `ruby file: ".ruby-version"` in the Gemfile, which `doc/runtimes.md` gives.
- Bad, because a developer who moves to a new Ruby before Fledge has its runtime cannot build until a release adds one.
- Bad, because `fledge build` reads the runtime's `rbconfig.rb` for every app, which takes one more pass over the runtime archive.
- Neutral, because the maintainer's rule that generated files may change in a minor applies to no file Fledge writes, since this design adds no generator.

### Confirmation

`Fledge::CLI::Build#same_ruby` (`lib/fledge/cli/build.rb`) refuses a mismatch on every desktop and phone build. `test/build_command_test.rb` and `test/mobile_build_test.rb` hold the refusal and its message.

## Pros and Cons of the Options

### A default Ruby

- Bad, because a default must one day move to a new minor, which breaks apps (Ruby does not follow SemVer), and the maintainer limited a minor to changing a default's patch.

### A required Gemfile `ruby` line

- Good, because Heroku has to ask: no Ruby runs the app before Heroku builds it, and without the line its default "isn't sticky" (Heroku Dev Center, "Ruby Support", fetched 2026-11-04).
- Bad, because Fledge always runs inside the developer's Ruby, and a lone `main.rb` would need a Gemfile only to say what that Ruby already says.

### Reading `.ruby-version`

- Bad, because mise, asdf, rbenv, chruby, rv, and `ruby/setup-ruby` already read it to choose the Ruby that runs Fledge, and Bundler reads it for `ruby file: ".ruby-version"`. A second reader would repeat their work.

### A generated `fledge.yml` key

- Good, because a generated file may change in a minor, as the maintainer noted.
- Bad, because it adds a command, a key in Config and the schema, and a statement that can disagree with the running Ruby. A file that said one minor on a computer running another would ship code tested on one to the other, unless Fledge also checked the running Ruby, which is option 1 with a file and a command added.

## More Information

Briefcase: "the version of Python used to run Briefcase will be the version of Python used by the bundled app" ("Native System Packages", stable docs, fetched 2026-11-04). PyInstaller builds with the interpreter that runs it ("Using PyInstaller", fetched 2026-11-04). python-build-standalone publishes each Python and has no default; the tool that picks one decides. ADR 056 decides which Ruby minors Fledge carries before 1.0.
