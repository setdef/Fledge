# ADR 061: The phone runtime does the launcher's work, in C: `fledge_ruby_run_app`

## Context and Problem Statement

On a desktop, Fledge's launcher reads `fledge.cfg`, finds the app's program, and for an app with a Gemfile sets up Bundler before the program runs, as `bundle exec` would (ADR 086). A phone runs no launcher of Fledge's: the app is a host that Xcode or Gradle builds, which calls the embedding API (ADR 011). The project `fledge build` writes for a phone (ADR 012) holds the same `fledge.cfg`, program, and gems a desktop app holds. What reads them on a phone, and starts the program?

## Decision Drivers

- The app's Ruby code runs as under `bundle exec ruby main.rb`: same `$0`, same backtraces, same `ENV` (decisions 9 and 10).
- The launcher's work is written once, not once per host language.
- A framework that replaces Fledge's host keeps the same call (ADR 025).

## Considered Options

1. The embedding API gains `fledge_ruby_run_app(root, argc, argv)`, in C, which reads `root/fledge.cfg` with the launcher's own reader and runs the program, setting up Bundler between `ruby_options` and `ruby_run_node` as the desktop launcher does.
2. Each host reads the program and Gemfile from its `Info.plist` or manifest and calls Bundler itself.
3. A boot script that sets up Bundler and `load`s the program.

## Decision Outcome

Chosen: option 1, because the launcher's work stays in one place, in C, beside the code the desktop launcher already runs (`runtime/launcher/config.c` is compiled into both phone runtimes). Option 2 would put it in two hosts, in Objective-C and Java. Option 3 would make `$0` and every backtrace name a file the app never had (decision 10).

`fledge_ruby_run_app` returns 66 (`EX_NOINPUT`) when `fledge.cfg` or the program is missing, and 70 (`EX_SOFTWARE`) when the configuration is damaged or Bundler cannot set up the gems, as the launcher exits (ADR 002). Unlike the launcher, it sets nothing of the environment aside: a phone starts an app with an environment of its own, which no person sets. The Java class `org.setdef.fledge.FledgeRuby` offers the same as `runApp` and `startApp`.

Confidence: high. Every phone app in CI, the pure-Ruby ones and those with gems that Bundler sets up, starts through it.

### Consequences

- Good, because a host is two calls: forward the output, then run the app.
- Good, because a framework's host, such as SDL's, calls the same function wherever its framework runs the main function.
- Good, because a change to how the launcher reads `fledge.cfg` reaches the phones with it.
- Bad, because the embedding API is part of the runtime, so changing it changes every phone runtime; its functions are only ever added.
- Bad, because Ruby boots once per process, so a second call returns 70: a host cannot run a second app.

### Confirmation

The `mobile-apps-ios` and `mobile-apps-android` jobs run `examples/hello`, `examples/mobile_app` (whose gems Bundler sets up, which it says), `test/fixtures/mobile_hello`, and the parity probe through it, and each must print its line and exit 0. `test/integration/mobile_output_test.rb` compiles `fledge_ruby.c` with the launcher's `config.c` and runs it against the Ruby that runs the tests.
