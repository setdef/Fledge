# Plan 002: Toward 1.0

## Status

Planned (requested). Agents wrote this plan and may reorder or rewrite it (AGENTS.md, Questions). Each story names the maintainer's decision it serves (`doc/contributors/decisions.md`), why it matters, and when it is done. Plan 001's walking skeleton delivers on every platform; this plan is what stands between it and a 1.0 that developers can ship real apps with.

Stories near the top come first. A story marked **1.0** must be done before 1.0; one marked **maybe 1.0** is decided when 1.0 is near.

## Stories

### Ship the executable you already run

**Why.** Today an app is a folder with a `main.rb`, an invented layout that no Ruby project has (decision 2 asked for the other options). A Ruby developer already has an entry point: `exe/my_cool_app` in a gem, `bin/server` in an app, run from the project root where its Gemfile or gemspec sits. The name a person sees should be the app's own, from its primary class or module, such as `MyCoolApp` (decision 5), not a folder's.

**What.** The orchestrating agent offered the maintainer four layouts on 2026-10-26 and recommended pointing `fledge build` at the executable you already run, with the project root found by its Gemfile or gemspec, a configuration file only where that is not enough, and NAME taken from the project (the gemspec's name or the folder's, camelized) unless configuration names it. The maintainer answered "Ok." (`decisions.md`, 2026-10-26, later, reply 2). With the executable as the entry point, `$0` becomes that executable's path, as under `ruby exe/my_cool_app`, which also answers how an app finds the program the person ran.

**Done when.** `fledge build exe/my_cool_app` builds `dist/MyCoolApp-PLATFORM/` whose program runs `exe/my_cool_app` as `ruby exe/my_cool_app` would, the parity check passes with the executable as entry point, a folder with only a `main.rb` still builds or fails with a message that says what to do, and the help header, ADR 001, and this plan say so.

**Status.** Done (requested), ADR 005, with "Vendor an app's gems" below, since a gem-shaped program runs as `bundle exec exe/my_cool_app` and needs its gems to run at all. `fledge build` takes the program as its PATH (a folder means its gemspec's one executable, or its `main.rb`), finds the project's root by its Gemfile, `gems.rb`, gemspec, or `fledge.yml`, names the app from the gemspec or folder, camelized, unless `fledge.yml` names it, and writes `fledge.cfg`, which the launcher reads to run `app/ENTRY`. `examples/hello` ships as `Hello`; `examples/my_cool_app` ships as `MyCoolApp`, and the parity check compares it with `bundle exec ruby exe/my_cool_app` on every platform. First released in [`v0.0.1.pre.2`](https://github.com/setdef/Fledge/releases/tag/v0.0.1.pre.2), from which `installed.yml` built both examples with the published runtimes and delivered them on a fresh runner of every platform.

### Copyleft-free runtimes **1.0**

**Why.** Developers who buy a commercial license must be able to ship an app with no copyleft obligation beyond notices (decision 8, and decision 24 for GMP). Two components still carry LGPL code: libxcrypt on Linux, linked dynamically from the runtime's `lib/`, and GMP on Windows, as `libgmp-10.dll`. An LGPL library may stay only as a separate shared library a person can replace, never linked statically, and with its source published; no GPL or AGPL third-party code may ship at all (AGENTS.md, Licensing).

**What.** The spike on branch `spike/permissive` found every runtime within the rule but for rv-ruby's own Linux `bin/ruby`, which links libxcrypt statically and which no runtime ships (each builds its own from Ruby's `main.c` against the shared `lib/libcrypt.so.2`), and nkf's JRuby sources, which runtimes now prune. Both LGPL libraries stay as separate shared libraries: musl's crypt gets yescrypt wrong, and a GMP-free Windows Ruby would be a fork of RubyInstaller to maintain. CI proves each can be replaced in a built app (ADR 004).

**Done when.** Every third-party component in every runtime is permissive, or LGPL as a separate, replaceable shared library whose source the release publishes; the license gate below enforces it; and Delivery still passes.

**Status.** Done (requested), ADR 004: the audit passes all four runtimes inside every runtime build, finds no LGPL code outside `lib/libcrypt.so.2` and `libgmp-10.dll`, and Delivery passes.

### Tell app developers what they owe, from CI **1.0**

**Why.** A developer shipping an app needs to know, for each platform, what Fledge's runtime puts inside it, under which license, and exactly what that asks of them: the notices (which Fledge puts in the app), the source of any LGPL library (which Fledge publishes with each runtime release, never the app's own source), keeping that library replaceable, and allowing reverse engineering to debug a replacement. Fledge's own launcher and runtime files are AGPL-3.0-or-later, and setdef will likely offer a commercial license for apps that don't want to follow the AGPL (decision 1). A table written by hand goes stale the first time a pin moves.

**What.** CI derives a component inventory from each built runtime: every file, how each binary links, each gem's license, and a checked map of what is linked statically into what. A license policy gate fails the build for anything not permissive, any LGPL code that is not a separate shared library, any unknown license, and any binary the inventory does not account for. From the same data CI generates an SPDX SBOM and the `NOTICES` shipped in every runtime and attached to every release, alongside a source tarball of each LGPL library, and a licensing page for app developers that lists every obligation plainly and tells readers to ask their own lawyer, as setdef.com does ("The site makes no legal claims about what any license requires"). Delivery checks that the built app carries the generated notices. The `spike/permissive` branch is prototyping this.

**Done when.** The gate runs on every push and has failed at least once on purpose in a test; every release carries the SBOM, the notices, and the LGPL sources; and the licensing page is generated, linked from the README, and accurate for every platform.

**Status.** Done (requested), ADR 004, and first released in `v0.0.1.pre.1`: `RuntimeBuilder` runs the audit on every runtime and refuses to archive one that fails; `test/runtime_builder_test.rb` and `test/license_audit_test.rb` fail it on purpose, and CI's Licenses jobs plant a GPL extension and a GPL gem in each built runtime; each runtime carries `notices/NOTICES.txt` and `notices/sbom.spdx.json`, which Delivery checks and CI validates with the SPDX tools; `release.yml` attaches them and the LGPL source bundles; and `doc/licensing.md` is generated from the four runtimes, checked by CI, and linked from the README. It covers what Fledge puts into an app, not the app's own gems, whose licenses are the developer's to comply with (the maintainer's words of 2026-10-28; ADR 007); the page says so.

### Pin runtimes by hash **1.0**

**Why.** `fledge build` checks each downloaded runtime against the release's `SHA256SUMS` (ADR 001, section 2). That catches a damaged download, but not a release whose assets and sums were both replaced.

**What.** Release in two steps: build the runtimes from one commit, commit their SHA-256s into `lib/`, then tag that commit, whose release attaches the same runtimes. Reproducible runtime builds would let one step do.

**Done when.** `Fledge::Runtimes` checks every runtime against a hash in the gem, and `release.yml` refuses a tag whose pinned hashes do not match the runtimes it publishes.

### Vendor an app's gems

**Why.** An app with a Gemfile needs its gems in the runtime, pure Ruby or precompiled for each target. Bundler reads `BUNDLE_*` when the app requires it, and those are the person's after the launcher restores them (ADR 003, section 3).

**What.** `fledge build` installs the app's locked gems for each target into the built app, and the launcher sets up Bundler for them before it restores the person's environment.

**Done when.** An app whose Gemfile locks a pure-Ruby gem and a precompiled native gem builds for every target, runs in Delivery, and passes the parity check against `bundle exec ruby main.rb`.

**Status.** Done (requested), ADR 005, with the story above. `examples/my_cool_app` locks i18n (pure Ruby, which needs concurrent-ruby) and sqlite3 (precompiled for all four targets); one Linux runner builds it for every target, each with that target's build of sqlite3 from its Gemfile.lock, checked against the lockfile's SHA-256, and Delivery runs it on every platform. The gems install into Ruby's own gem folder, the launcher has Bundler set them up as `bundle exec` would, with Warbler's settings for a packed app, first released in [`v0.0.1.pre.3`](https://github.com/setdef/Fledge/releases/tag/v0.0.1.pre.3) with Bundler apps' children getting `bundle exec`'s environment over the person's. Through `v0.0.1.pre.4` each gem also had to meet the runtimes' license policy, reported in `notices/GEMS.txt`; since the maintainer's words of 2026-10-28, Fledge takes no position on an app's gems' licenses, ships each with its own notices, and checks only that its compiled files would load where the app goes (ADR 007). Left for "Native gems from source" below, and done there: gems that must be compiled, and git gems. Not yet supported, and refused with a message that says so: path gems outside the project, gem servers that need credentials or mirrors.

### Native gems from source

**Why.** A native gem without a precompiled build for a target (an older version, or a gem that publishes only its source) cannot ship: `fledge build` refused it, naming the gem and the target (ADR 005, section 6), and refused every gem from git. A developer whose app needs one has no way through. The motivating cases are Rust extensions: Tokra, a Ruby port of Tauri, compiles its Rust extension with rb-sys when it is installed, and Ferro's gems, which bind Rust crates one to one, compile theirs the same way against the Cargo.lock each ships, and are consumed from git tags (`gem "ferro-arboard", git: "https://github.com/setdef/Ferro", tag: ..., glob: "gems/*/*.gemspec"`). nokogiri's precompiled macOS and Windows builds compile GNU libiconv in, which this plan took decision 8 to forbid until ADR 007, and a source build on a Mac uses macOS's own iconv.

**What.** Compile such a gem when Fledge runs on the target's own platform, against the runtime's own Ruby, which runs the build with headers and libraries from a build-only companion each release publishes beside the runtime (ADR 003 prunes them from the runtime itself), with the compiler the developer has; cross-compiling for another platform, as rake-compiler-dock does, is a larger step. Fetch a git gem at the revision its lockfile locks and lay it out as Bundler does. What the extensions link goes through the check every precompiled gem passes, that it loads where the app goes (ADR 006, section 8). (This plan once had their licenses, and a Rust extension's crates, judged too; ADR 007 removed that.)

**Done when.** A test app whose Gemfile locks a gem with only a source build, and a Rust gem from git, builds on each platform for that platform, and runs in Delivery.

**Status.** Done (requested), ADR 006. `fledge build` compiles a gem with an extension when the target is the platform it runs on, with the runtime's own Ruby and `bundle config build.NAME`'s options, and refuses it for any other target, naming it; it fetches git gems into `~/.cache/fledge/git` at the locked commit and ships each checkout where Bundler keeps it; it checks that every compiled file loads where the app goes (and, through `v0.0.1.pre.4`, judged each one's licenses and each Rust crate's, which ADR 007 removed). Precompiled builds stay the preferred path, and compiling fills only the gaps. `examples/native_app` (redcarpet, a C gem published only as source; ferro-idna, a Rust gem from its git tag; ratatui_ruby, an LGPL Rust gem precompiled for three platforms, each build for several Rubies, and compiled from source for `aarch64-linux`, which it publishes no build for; and spreadsheet, a GPL gem whose bigdecimal compiles) builds on macOS, both Linux architectures, and Windows, each on its own runner, and delivers on fresh runners; `examples/nokogiri_app` builds nokogiri from source and delivers on macOS, and since ADR 007 on Windows too, where it links GNU libiconv in. First released in [`v0.0.1.pre.4`](https://github.com/setdef/Fledge/releases/tag/v0.0.1.pre.4), whose `installed.yml` run installed Fledge from the tag on a fresh runner of every platform, downloaded each runtime and its build-only companion from the release, built `examples/native_app` from source, and delivered it. Not yet: cross-compiling, git submodules, and path gems with extensions.

### Signing and notarization

**Why.** Windows SmartScreen and macOS Gatekeeper warn about, or refuse, an unsigned app downloaded from the internet. Developers who have done Apple's and Microsoft's ceremony should be able to sign so neither blocks their app; those who have not should still get an app that works (decision 17).

**What.** An option to sign each built app with the developer's own credentials (Authenticode through `signtool` or Azure Trusted Signing on Windows; `codesign` and `notarytool` on macOS, which also needs the `.app` bundle of the windowed story), run after Fledge writes the folder and before it writes the archive. Unsigned builds stay the default, and the README tells end users how to open an unsigned app on each OS.

**Done when.** A signed build verifies with each platform's own tool in Delivery, an unsigned build still passes Delivery, and the end-user instructions exist. Signing with a Developer ID and notarizing need an Apple Developer account, which this story reaches at its last responsible moment (decisions, 2026-10-28): raise it in `questions.md` then.

### App identity

**Why.** Windows shows a program's icon and version resource in Explorer, desktop and Start menu shortcuts, the taskbar, Alt-Tab, Task Manager's name and icon, and a window's title-bar icon; macOS shows a bundle's name and icon in the Dock, Cmd-Tab, the menu bar, and Finder; Linux desktops show a `.desktop` file's name and icon. Today every app shows the launcher's: no icon, no version information. Developers must control all of it (decision 18).

**What.** Configuration for an app's display name, icon, version, and publisher, and its identifier. On Windows, Fledge writes `VERSIONINFO` and the icon into the copied launcher's resources (as rcedit does for Electron); on macOS, an `Info.plist` and `.icns` in the `.app` bundle; on Linux, a `.desktop` file and icon beside the program.

Tokra's sessions found two identities the operating system checks before it lets an app notify anyone. macOS delivers a notification only from an app with a real bundle identifier (`CFBundleIdentifier`), which lives in an `Info.plist` inside a `.app` bundle: a bare executable, which a console app is, has none. Windows shows a toast only for an app whose AppUserModelID is installed, set on a Start menu shortcut to the program (`System.AppUserModel.ID`), which an unzipped folder never has. So the identifier is configuration too, such as `com.example.MyCoolApp`, used as both.

**Done when.** A test app's configured name, icon, and version appear in each OS's own tools (PowerShell's `(Get-Item NAME.exe).VersionInfo`, `plutil`, `desktop-file-validate`) in Delivery; on macOS, `plutil -extract CFBundleIdentifier` reads the configured identifier from the built `.app`; and on Windows, the installed Start menu shortcut carries the configured AppUserModelID, which Delivery reads back.

### Windowed apps

**Why.** Lota's games and Tokra's desktop apps open windows and want no terminal (ADR 001, section 5).

**What.** A `windowed` kind: the GUI-subsystem launcher on Windows, which already builds; an `.app` bundle on macOS; a `.desktop` launcher on Linux.

Tauri's bundler, the prior art for a desktop app's packages, produces `.app` and `.dmg` on macOS, `.msi` (WiX) and an NSIS setup `.exe` on Windows, and `.deb`, `.rpm`, and `.AppImage` on Linux. Fledge plans these, each for a reason the app needs: the `.app`, always, since a windowed macOS app and its bundle identifier live in one, and a `.dmg` to download it in, which macOS opens with a drag to Applications and which, unlike a `.zip`, notarization can staple a ticket to (Plan 002, "Signing and notarization"); on Windows, the `.zip` stays, and an NSIS setup `.exe` installs the Start menu shortcut that carries the AppUserModelID toasts need, which NSIS's `makensis` builds from macOS or Linux too, keeping ADR 001's one machine for every platform (Tauri builds NSIS installers from other platforms for the same reason, and an `.msi` only on Windows), so `.msi` waits for a developer who needs one for managed deployment; on Linux, the `.tar.gz` stays, with a `.desktop` file and icon in it, and an `.AppImage`, one file a person runs on any distribution without installing, comes next, while `.deb` and `.rpm`, each one family of distributions, wait.

**Done when.** A windowed test app builds for every target and Delivery starts it without a console and reads its result.

### musl Linux **maybe 1.0**

**Why.** Many CI platforms run only on musl (Alpine), and the maintainer wants them supported eventually (decision 12). rv-ruby's musl builds link the standard library's extensions into their own `bin/ruby`, so a launcher linked against their libruby cannot load them (Plan 001, spike 1).

**What.** A musl Ruby whose extensions load from a launcher: from rv-ruby if its musl builds change, or built in Fledge's CI (ADR 001's fallback).

**Done when.** `x86_64-linux-musl` and `aarch64-linux-musl` targets build, pass the parity check, and deliver in Alpine containers.

### iOS, iPadOS, and Android **1.0 if feasible**

**Why.** The maintainer wants Fledge to support iOS, iPadOS, and Android, ideally before 1.0, unless that proves incredibly burdensome (decisions, 2026-10-27). Lota wants its games there. The store rules and what CRuby needs on each are in `doc/contributors/research/2026-10-27-mobile.md`.

**Status.** Spiked: not incredibly burdensome. CRuby 4.0.9, interpreter only, runs a bundled `main.rb` that requires `json` in the iOS and iPadOS Simulators and on Android emulators with 4 KB and 16 KB pages, in CI (runs 40630328845 and 40630328941; `spike/mobile/FINDINGS.txt` on branch `spike/mobile`). A CI run costs about 18 minutes for iOS and 9 for Android; each Ruby release means rechecking six small scripted patches. Everything linked in is permissive. Not yet proven: a real device, App Store review, and Android's arm64 build, which GitHub's runners cannot run. The stories below carry it on: pure-Ruby apps and the standard library before 1.0, native gems after.

### Mobile runtimes **1.0**

**Why.** An app has to have a Ruby on the phone before `fledge build` can ship it there.

**What.** iOS and iPadOS, and Android, runtimes built in CI from pinned sources (Xcode 26.5, NDK r30), interpreter only, with the bundled gems kept as gems, a CA bundle, and a UTF-8 locale. iOS gets a target name of its own, since it reports `arm64-darwin`, as macOS does, and Bundler would pick macOS's native gems. They pass the runtime license audit and ship as release assets: an XCFramework for iOS and an AAR for Android, with a small embedding API.

**Done when.** The runtimes are released, and a parity Delivery job runs a script on each in the iOS Simulator and an Android emulator.

### Mobile apps from fledge build **1.0**

**Why.** A developer should not have to wire a runtime into Xcode or Gradle by hand.

**What.** `fledge build` writes an Xcode project for iOS and iPadOS and a Gradle project for Android around the app and its pure-Ruby gems, with the privacy manifest Ruby needs on iOS and a 16 KB-aligned Android build. The developer signs and submits; Fledge never submits for them (App Store guideline 4.2.6). Native gems on mobile come after 1.0, since no gem publishes mobile builds and each would be compiled into the app.

**Done when.** A built project for each platform builds unsigned and runs in the simulator and emulator in CI. Running on a real device and passing App Store review need an Apple Developer account, which this story reaches at its last responsible moment (decisions, 2026-10-28): raise it in `questions.md` then.

### Windows on ARM **maybe 1.0**

**Why.** The maintainer wants Windows on ARM eventually (decision 22). Linux on ARM already ships as `aarch64-linux`. Windows on ARM runs today's `x64-mingw-ucrt` apps under emulation, more slowly.

**What.** An `aarch64-mingw-ucrt` target from RubyInstaller's ARM64 build (`rubyinstaller-4.0.9-1-arm.7z`), with the launcher cross-compiled by llvm-mingw for ARM64, and Test, parity, and Delivery jobs on GitHub's Windows ARM64 runners.

**Done when.** An `aarch64-mingw-ucrt` app delivers natively on a Windows ARM64 runner.

### Ctrl-C and the console

**Why.** Ctrl-C in a console should end an app as it ends `ruby.exe` or `ruby`, through Ruby's own handler, with the same exit status (ADR 003, section 5). Nobody has checked.

**What.** Delivery checks on each OS: send SIGINT on macOS and Linux, and `GenerateConsoleCtrlEvent` to a process group on Windows, to an app that sleeps, and compare its status and output with the reference Ruby's.

**Done when.** Those checks run in Delivery on every platform.

### The first GitHub pre-release

**Why.** Before 1.0, agents may push tags and create GitHub Releases, never publish to RubyGems.org (decision 6). A pre-release lets developers try `fledge build` without building runtimes themselves.

**What.** Once runtimes are copyleft-free, tag `v0.0.1.pre.1` (RubyGems' prerelease form, so `Fledge::VERSION` stays a valid gem version) on a commit whose CI is green on every job; `release.yml` publishes the runtimes, their SBOMs, NOTICES, and LGPL sources, and their sums, marks the release a prerelease, and `installed.yml` installs Fledge from the tag on each platform and builds and delivers hello with runtimes downloaded from the release.

**Done when.** `fledge build` from that tag downloads its runtimes from the release and builds `examples/hello` on a computer that has never built a runtime.

**Status.** Done (requested): [`v0.0.1.pre.1`](https://github.com/setdef/Fledge/releases/tag/v0.0.1.pre.1), published on 2026-10-27, and `installed.yml` built and delivered hello from it on a fresh runner of every platform.
