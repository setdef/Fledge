# ADR 046: Refuse a Gem Whose Compiled Files Need a Library the App's Computer May Lack

## Context and Problem Statement

A compiled file names the shared libraries the system's loader must find for it. A gem built on a developer's computer can name one only that computer has. The first real case came at once: nokogiri's vendored libxml2, built from source on a Mac with Homebrew, linked Homebrew's `liblzma`. Such an app starts on the developer's computer and fails everywhere else, when Ruby requires the gem, with a loader's error that names the gem. What does `fledge build` do with a gem, precompiled or compiled, whose compiled files need a library the app may not find where it goes?

## Decision Drivers

- A person who runs the app never meets an error that names a gem (AGENTS.md, Design precedence 1).
- The developer learns of the problem when building, on their own computer, not from a person who ran the app.
- Fledge judges only whether a gem loads, never what it compiles in or its license (ADR 007).

## Considered Options

1. Refuse the build, naming the gem, the file, and the library, and saying what to change.

## Decision Outcome

Chosen: option 1, for Design precedence 1. No alternative was weighed when it was decided.

Every gem an app ships passes one check of its compiled files in the format of the target's own loader. A file may need only libraries the target's operating system provides, the runtime ships, or the gem carries; on Linux also those `fledge.yml` lists as the distribution's (ADR 030). On macOS a library the gem carries counts only where dyld would find it. A file built for another Ruby, such as a precompiled gem's copy for an older Ruby, is never loaded and is not judged. The check names every problem of every gem at once.

Confidence: high that it keeps such apps from shipping; `test/native_gems_test.rb` passes every one of nokogiri's real precompiled builds, so the check does not refuse gems that work. It makes no claim to be better than repairing the gem, which was never compared.

### Consequences

- Good, because an app that would fail on another computer never ships, and the build says which gem and library, and how to fix it.
- Good, because the rule is the same for a precompiled gem, one Fledge compiled, a git gem, and a path gem.
- Bad, because the developer must fix the gem's build (link the library statically, carry it with a run path that reaches it, or build without it), which may mean a build option or a fork.
- Bad, because the list of what each system provides is Fledge's to keep current; it follows auditwheel's and delvewheel's lists and `runtime/licenses.yml`.
- Bad, because a library a gem opens with `dlopen` is invisible to it.
- Bad, because the macOS rule must follow dyld's search, which a check of files at rest cannot follow fully; it refuses only what certainly would not load.

### Confirmation

`test/linkage_test.rb` (with fixtures built by Xcode's clang and `install_name_tool` on a Mac) and `test/native_gems_test.rb`; CI's Build jobs run the check for every example on every platform, and Delivery runs the result on a fresh computer.

## More Information

The lists, the dyld rules, and the messages: `doc/contributors/design/gems.md`, "The linkage check".

### Later research (2026-11-10)

These alternatives were found on 2026-11-10. They were never the reason for the decision, which was made without them.

- **Repair the gem by copying the library in.** auditwheel's `repair` "copies these external shared libraries into the wheel itself" and "automatically modifies the appropriate `RPATH` entries such that these libraries will be picked up at runtime" (pypa/auditwheel, README). delvewheel does the same for Windows wheels, renaming each copied DLL with a hash of its contents and editing the importing module's import table (adang1345/delvewheel, README). delocate's `delocate-wheel` copies the libraries outside macOS's system trees into a `.dylibs` folder and rewrites install names and run paths to `@loader_path` (matthew-brett/delocate, README). Repairing would ship more apps without a change to the gem, at the cost of patchelf, install_name_tool, and import-table editing in Fledge, of libraries in the app whose licenses would be the app's to meet, and of a library copied from the developer's computer that may suit no other.
- **Leave it to fail at run time,** as `bundle install` on the developer's own computer does: no check, and Ruby's `LoadError` when the gem loads. It costs nothing to build and breaks Design precedence 1.
