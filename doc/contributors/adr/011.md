# ADR 011: On a phone, Ruby is a static library Fledge builds from source

## Context and Problem Statement

The maintainer asked for phones: "We should, if we can, support iOS and iPadOS and Android. Ideally before 1.0 but I could be swayed if it turns out incredibly burdensome." (`decisions.md`, 2026-10-27).

A phone runs no program of Fledge's own. An iOS app is one signed binary in a bundle, which may load code only from frameworks the bundle carries, never a loose library. An Android app is an APK whose native code Java loads, and whose assets are not files. So a phone's runtime cannot be a launcher with a relocatable Ruby beside it, as a desktop's is (ADR 001). Ruby has to be a library, linked into an app that Xcode or Gradle builds. No one publishes a prebuilt CRuby for either system. Where does the phone's Ruby come from, and what shape does it take?

## Decision Drivers

- The app's Ruby code runs as under `ruby main.rb`: the whole standard library, every default and bundled gem (decisions 9, 10, and 20).
- "Code is a liability" (`decisions.md`, 2026-10-28): use maintained tools, and write only what none does.
- Each target is built on its own system, with that system's tools (`decisions.md`, 2026-10-28).
- Every input is pinned by version and SHA-256 (AGENTS.md).
- The runtime carries no copyleft obligation beyond notices (decision 8).

## Considered Options

1. Build CRuby from its release tarball with Ruby's own `configure` and `make`, cross-compiled with Xcode's or the NDK's compilers, static and interpreter only, after xord/cruby's iOS recipe and Termux's Android one, and pack it as an XCFramework and an AAR.
2. Use xord/cruby's Rakefile itself (the build behind RubySketch, on the App Store).
3. Use Termux's Ruby packages (`termux-packages/packages/ruby/build.sh`).
4. Port CPython's `Apple/` and `Android/` build scripts to Ruby.

## Decision Outcome

Chosen: option 1, because it alone gives a standard Ruby that Fledge pins, with nothing it does not need. xord/cruby's Rakefile builds an older Ruby and folds every bundled gem into the standard library, so the gems stop being gems (ADR 058). Termux's packages build for Termux's own prefix, with its `libandroid-support`. CPython's scripts build Python, and porting them would be more code of Fledge's than following Ruby's own build. What is Fledge's own is the order of the maintained tools' commands, a few scripted edits to Ruby's source, and the embedding API (ADR 061).

Confidence: high. The runtimes build on every push, and apps on them run in the iOS Simulator, on Android emulators, and on a real iPad, iPhone, and Android phone.

### Consequences

- Good, because the runtime is Ruby's own build, with every default and bundled gem a gem, so the parity check finds only the differences a phone forces.
- Good, because each input, from Ruby's tarball to the NDK and Gradle, is pinned in `runtime/sources.yml`.
- Good, because the iOS runtime builds on a Mac with Xcode, and the Android runtime on Linux or a Mac with Google's NDK, each with its own tools.
- Bad, because a cross build needs work Ruby's build does not do: scripted edits to its source, a builtin binary written by a miniruby for the build machine, and bundled gems' extensions linked in. Each new Ruby means checking them again. Each fails the build when the lines it changes are gone, so a new Ruby shows where to look.
- Bad, because a phone's Ruby has no JIT: iOS gives no app memory it may write code into and run, and Ruby builds none for Android.
- Bad, because an iOS app that links this runtime and another OpenSSL sees their symbols clash: a static library cannot hide them, as the Android library does.
- Bad, because the Android arm64-v8a library runs on no CI runner (no free runner boots an arm64-v8a emulator), so only the x86_64 library is proven on emulators; the arm64-v8a library is built and checked, and run only on a real phone (`doc/contributors/design/public-interface.md`, "Phones").
- Bad, because CI builds both runtimes on every push, which costs macOS and Linux runner minutes.
- Neutral: App Store and Play review need the developer accounts the maintainer pays for (`decisions.md`, 2026-11-04). `doc/contributors/account-tests.md` lists those tests.

### Confirmation

CI's `runtime-mobile` jobs build both runtimes from `runtime/sources.yml` and run the license audit on them. The `mobile-apps-ios` and `mobile-apps-android` jobs build apps on them and run each in the Simulator and on emulators with 4 KB and 16 KB pages (`tasks/mobile_parity.rb`), and the mobile parity check compares the probe with `ruby main.rb`. `test/mobile_runtime_test.rb` checks the runtimes' shape.
