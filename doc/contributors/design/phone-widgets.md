# Phone Widgets

This document says what Fledge gives an app whose Ruby draws its screen with each phone's widgets, UIKit's on iOS and iPadOS and Android's views on Android, and on which thread that Ruby runs. Fledge gives it nothing beyond what Ruby gives every program, and runs it on the main thread, the one thread that may touch those widgets. ADR 105 records the decision; this document holds how it works, the ways weighed, and their citations. How the runtimes are built is `phone-runtimes.md`; the projects `fledge build` writes around them, `phone-projects.md`; what a developer does, `doc/phones.md`. `examples/basket` is such an app, and its README and its code say how it is written.

## The problem

A developer who knows Ruby, and no other language, should be able to ship a phone app whose screen follows each platform's interface guidelines, because it is made of that platform's widgets. A program reaches those widgets only through each platform's interfaces, the Objective-C runtime on iOS and the Java VM on Android, and only from the main thread. Every line of Objective-C, Swift, Java, or Kotlin an app needs is Fledge's, in its runtime or its templates, never the developer's, and nothing of Fledge's may stand between the app's Ruby and the platform that `ruby main.rb` would not have (design precedence 2).

## What the runtime gives an app's Ruby

What Ruby gives every program, and nothing of Fledge's. Fiddle, a gem Ruby bundles, is in both phone runtimes (`phone-runtimes.md`, "What a phone runtime holds"). Through it an app's Ruby calls the Objective-C runtime's C functions on iOS, and JNI's table of C functions on Android, which Fiddle calls by pointer. Neither runtime puts anything in Ruby's vendor folder, `lib/ruby/vendor_ruby/fledge/`, and the Android runtime holds no pointer to the Java VM, no Java class for Ruby to call, and no Ruby library for either, so `$LOAD_PATH` is what it is under `ruby main.rb`, the parity check sees no difference, and the same Ruby code runs under any Ruby on that system. An app with no Gemfile has `fiddle`, as under `ruby main.rb`, and an app's Gemfile lists it, as under `bundle exec`. The bridging an app uses is the app's code, or a gem's that its developer chooses.

On Android a program reaches more than JNI's functions, and each step rests on Android, not on Fledge (`doc/contributors/research/2026-11-25-pure-ruby-android-views.md`). JNI's own `JNI_GetCreatedJavaVMs` gives the Java VM. Android gives a Context only to the components it creates, so a program finds its Application and its Activity through members of `android.app.ActivityThread` that Android lists as unsupported. ART implements no `DefineClass`, so a program takes Java's calls of an interface's methods through a class it writes in memory, loaded with `InMemoryDexClassLoader`, and `java.lang.reflect.Proxy`. A later Android that restricts those members would break such an app, and nothing in Fledge could mend it: the fix for pure Ruby that falls short on a phone is a truer Ruby, never a helper of Fledge's.

The developer writes two screens, one per platform, because each platform's widgets are its own and its guidelines differ. A layer that wrote one screen for both would be a widget toolkit, which is a framework's work, above Fledge, as Toga's is above rubicon-objc and rubicon-java.

## The ways weighed

1. **The Objective-C runtime and JNI, called from the app's Ruby through Fiddle (chosen).** Fiddle is in both phone runtimes already. On iOS the bridge is `objc_msgSend` with the types each method's encoding gives, and `objc_allocateClassPair` and `class_addMethod` with a Fiddle closure for each method a Ruby class defines, as BeeWare's rubicon-objc does from Python's ctypes (beeware/rubicon-objc at 21378c10, `src/rubicon/objc/api.py`, lines 187 to 188, a ctypes function per method encoding; lines 1335 and 1387, the class pair; `runtime.py`, lines 1156 to 1161, a `CFUNCTYPE` as each IMP). On Android it is Ruby over JNI's table of C functions, with a class written in memory whose native `invoke` is a Fiddle closure; pyjnius's `NativeInvocationHandler` and rubicon-java's `PythonInstance` are the same shape (kivy/pyjnius at 24a32850, `jnius/src/org/jnius/NativeInvocationHandler.java`, line 38, `native Object invoke0`; `jnius/jnius_proxy.pxi`, lines 170 to 180, `RegisterNatives` and `Proxy.newProxyInstance`; beeware/rubicon-java at 2d3842db, `org/beeware/rubicon/PythonInstance.java`, line 33). The research of 2026-11-25 (`doc/contributors/research/2026-11-25-pure-ruby-uikit.md` and the Android note above) found that an app's Ruby does all of it on each phone, which leaves no reason for Fledge to give an app any Ruby beyond Ruby's. What Fledge maintains of either bridge is nothing.
2. **The same bridges as a C extension in each runtime.** Calls would be faster, and the bridge would not need the `fiddle` gem, which a Gemfile must name ("What the runtime gives an app's Ruby"). But it is C that Fledge would write and keep for both phones, much of it the marshalling Fiddle already does, and on iOS it would need its own libffi for closures, where the runtime keeps libffi to Fiddle's extension alone so an app's own ffi gem finds no second copy (`phone-runtimes.md`, "What a phone runtime holds"). Code is a liability (decisions, 2026-10-28), so a bridge is written in C only where Ruby cannot reach, which on neither phone is anywhere now. A bridge that proves too slow on a device moves its hot path to C then, behind the same Ruby methods, in the app or its gem.
3. **A layer of widgets of Fledge's own** above either bridge, one screen for both phones. Not Fledge's job: Fledge ships a Ruby app, and a toolkit's choices (which widgets, which layout, which look) are a framework's, which the developer picks. Toga, Flutter, and React Native are frameworks, not packagers.
4. **Native hosts for each app,** in Objective-C and Java: refused, since they are the developer's Objective-C and Java.
5. **HTML in a web view, or an HTTP server on the phone,** to draw the app's own screen: refused. A native app draws with the platform's widgets, and a server on the loopback address is one every app on an Android phone can reach.
6. **Ruby on its own thread, with every call handed to the main thread and every callback handed back.** It would keep one thread model for every app, but CRuby runs Ruby only on its own threads ("Threads"), so each callback from UIKit or a view would wait on Ruby's thread while Ruby's calls waited on the main thread: a rendezvous in C on both phones, a thread switch for each call, and a deadlock wherever the two waits cross. No bridge of the prior art works so; each runs its language on the main thread.

## Threads

UIKit's objects are the main thread's alone, and an Android view is its window's thread's, which for an activity is the main thread: `ViewRootImpl.checkThread` throws "Only the original thread that created a view hierarchy can touch its views" (aosp-mirror/platform_frameworks_base at android-16.0.0_r1, `core/java/android/view/ViewRootImpl.java`, lines 11351 to 11357). So every call into the widgets, and every callback from them, is on the main thread.

CRuby runs Ruby only on a thread it made. A callback that arrives on another thread and asks for Ruby's lock ends the process: `rb_thread_call_with_gvl` prints "[BUG] rb_thread_call_with_gvl() is called by non-ruby thread" and exits (ruby/ruby at v4.1.0-preview1, `thread.c`, lines 2320 to 2335), and "You cannot convert a non-Ruby thread into a Ruby thread using this API" (`include/ruby/thread.h`, lines 111 to 114); no other public function does it. Fiddle's closures ask for the lock that way (fiddle 1.1.8, `ext/fiddle/closure.c`, lines 229 to 232). CPython differs: any thread may take Python's lock, and Python gives it up before it returns to Java (chaquo/chaquopy at 5cbe01a8, `product/runtime/src/main/python/chaquopy_java.pyx`, lines 88 to 92 and 319 to 320), so Python's bridges run Python wherever they are called. Ruby's must run Ruby on the main thread itself.

- **iOS.** Fledge's `Host/main.m` runs every app's Ruby on the main thread, whatever its `kind`, as `ruby main.rb` runs a program on the thread the process started on, with a 64 MB stack (`-Wl,-stack_size,0x4000000`, as `test/fixtures/sdl_phone`'s host asks for it; `phone-projects.md`, "A host that owns the main loop"), and the program hands the thread to UIKit by calling `UIApplicationMain` through Fiddle, with an application delegate written in Ruby. That is an Objective-C app's own shape, and RubyMotion's: its generated `main` calls `UIApplicationMain(argc, argv, nil, @"#{delegate_class}")` on the main thread, after Ruby starts there (HipByte/RubyMotion at afc2f632, `lib/motion/project/template/ios/config.rb`, lines 600 to 614); NativeScript's script calls `UIApplicationMain(0, null, null, ...)` itself (NativeScript/NativeScript at 91cc673c, `packages/core/application/application.ios.ts`, line 758). Briefcase's template runs Python on the main thread too, and calls `UIApplicationMain` in C once Python has given up its lock (beeware/briefcase-iOS-Xcode-template at eccb2cde, `main.m`, lines 323 to 344), which Ruby has no way to do and return.
- **Android.** Fledge's `MainActivity` starts every app's Ruby with `FledgeRuby.startAppOnMainThread`, whatever its `kind`: the asset is unpacked on a thread of its own, so the main thread never waits on the disk, and the app's Ruby then runs on the main thread, as Briefcase's Android template runs Python there, from the activity's `onCreate` (beeware/briefcase-android-gradle-template at 06e840f9, `MainActivity.java`, lines 61 to 131). Python's module returns to Android's loop; Ruby's cannot return and keep running, so the program hands the thread back by calling `Looper.loop()` itself, inside the loop Android's main thread already runs. Android allows that and logs a warning: `if (me.mInLoop) { Slog.w(TAG, "Loop again would have the queued messages be executed before this one completed."); }`, then loops (`core/java/android/os/Looper.java`, lines 319 to 324 at the same tag). Every message, every lifecycle call, and every listener's call into Ruby then comes from that loop, and a program that draws views ends only with its process, since closures it left behind would be called after it. The main thread's stack is the process's, 8 MB on Android, which is what Ruby has on a Linux desktop's main thread.
- **Ruby's other threads** run meanwhile: Fiddle lets Ruby's lock go during each foreign call, `UIApplicationMain` and `Looper.loop` among them, and each callback takes it again. As in a native app, a thread other than the main one leaves the widgets alone, and posts its work to the main thread: on iOS with `performSelectorOnMainThread:withObject:waitUntilDone:` to an object of a class written in Ruby, on Android with a `Handler`'s `post` and a `Runnable` written in Ruby.
- **A program that draws nothing** runs on the main thread too, and shows nothing while it runs, since the host shows no screen of its own. As in a native app, while Ruby holds the main thread and has not handed it to the system, no frame is drawn and no touch is handled.

No key chooses the thread. A program that a host ran on a thread of its own could read that its `Thread.main` is not the process's main thread, could never answer a widget's callback, and would see a screen of the host's that no Ruby gives a program, so every program runs on the main thread (ADR 105). A host that is not Fledge's, as SDL's is, runs Ruby where its framework does and is not touched (`phone-projects.md`, "A host that owns the main loop").

### A program that runs long

Each system bounds how long a program may hold the main thread, and the bound reaches every program, a console program and a test suite among them:

- **On an iPhone,** iOS ends an app that has not called `UIApplicationMain` within 20 seconds of its launch, with `0x8BADF00D`, "process-launch watchdog transgression": a program that slept on the main thread without calling it, launched with no debugger, was ended so (`doc/contributors/research/2026-11-25-pure-ruby-uikit.md`, section 2). A native app that does 20 seconds of work in `main` before `UIApplicationMain` meets the same end.
- **In the iOS Simulator,** nothing ends it: a program that held the main thread for 40 seconds without calling `UIApplicationMain`, with `pthread_main_np()` 1, ran to its end and exited 0 under `fledge test ios`.
- **On Android,** the input dispatcher reports an app as not responding once an input event has waited 5 seconds (`UNMULTIPLIED_DEFAULT_DISPATCHING_TIMEOUT_MILLIS`, frameworks/native at android-16.0.0_r1, `libs/input/android/os/IInputConstants.aidl`, lines 22 to 26), and offers the person to close it. A program that takes no input meets no such bound: ruby/spec runs to its end in an app on an emulator's main thread (`parity.md`, "ruby/spec on phones").

A program that must run longer on an iPhone does what an iOS program does: it calls `UIApplicationMain` within the 20 seconds, with delegates written in Ruby, and does its long work on a Ruby thread of its own meanwhile, which runs while the main thread is inside `UIApplicationMain`, since Fiddle lets Ruby's lock go during the call ("Ruby's other threads", above), or from a callback once the app has launched. That is the program's code, and Ruby's, not Fledge's. On an iPhone, launched with no debugger, a program that called `UIApplicationMain` at once and kept a Ruby thread working ran that thread for 45 seconds, and the process for minutes after. Three other ways were weighed:

1. **Fledge's host calls `UIApplicationMain` and runs Ruby inside the run loop once the app has launched,** as SDL's `SDL_RunApp` runs a game's main function. No program would meet the watchdog, but every app would carry an application delegate and a scene of Fledge's, a program that draws with UIKit could not call `UIApplicationMain`, since UIKit makes one `UIApplication` a process, and a program would start inside a callback of Fledge's rather than from `main`, as no program does under `ruby main.rb`.
2. **A thread of its own for a program that draws nothing:** it loses on design precedence 2 (ADR 105), and gives a program a `Thread.main` that no Ruby gives it.
3. **A helper of Fledge's** that a program calls to keep iOS waiting: a library no Ruby has under `ruby main.rb`, which ADR 105 rules out.

`fledge test ios` runs only in the Simulator, where a suite of any length runs to its end on the main thread, so the watchdog never meets it (`phone-projects.md`, "Tests in the app"). A suite run on an iPhone by other means, as by Xcode's Run, meets the watchdog unless the debugger holds it off, which was not measured.

## The stores

- **iOS.** App Review's guideline 2.5.2 forbids an app to download or run code that adds or changes its features, and 2.5.1 asks that it use public APIs (`doc/contributors/research/2026-11-12-ffi-and-fiddle-on-phones.md`). The app's Ruby ships in its bundle, and it sends UIKit's public messages through `objc_msgSend`, which is how every Objective-C call is made. It generates no code: a Fiddle closure is libffi's, which on Apple's arm64 maps a pre-signed trampoline page with `vm_remap`, so no page is both writable and executable (`phone-runtimes.md`, "What a phone runtime holds", `closures.c`, lines 161 to 245). The Simulator does not enforce that, and a device does: fiddle's other path, a page made executable with `mprotect`, runs in the Simulator and is a process's end on a device. What covers it: on an iPhone a closure took the trampoline table (`doc/contributors/research/2026-11-25-pure-ruby-uikit.md`, section 1); `test/integration/mobile_closures_test.rb` fails when the device slice's `fiddle.bundle` stops defining `ffi_closure_alloc`, the symbol whose presence selects the path; and an unsigned archive of every example passes Fledge's archive check. What does not yet: App Review, which needs an account (`doc/contributors/account-tests.md`, IOS-6).
- **Android.** Google Play's policy forbids downloading executable code from elsewhere than Play. The app's Ruby is in its APK, and so are the bytes of any class its Ruby writes in memory: they come from code in the APK, and `InMemoryDexClassLoader` and `java.lang.reflect.Proxy` are Java's own ways to load and implement a class at run time, which ART carries out; nothing is downloaded. What the policy's text on record does not say is whether it minds the unsupported `ActivityThread` members, or a library found through `/proc/self/maps`, and no such app has been submitted (the Android research note, "Google Play" and "What stays unproven").

## How it is checked

- `test/integration/mobile_closures_test.rb` reads the iOS runtime's device slice and fails unless its `fiddle.bundle` defines `ffi_closure_alloc`, without which a closure on an iPhone would take the `mprotect` path a device kills the process for.
- The parity probe reports whether `Thread.main` is the thread the process started on (`test/fixtures/parity/main.rb`, `main_thread?`): `pthread_main_np()` on Darwin, and on Linux and Android whether `Thread.main.native_thread_id` is `Process.pid`. The mobile parity check fails when a phone app's answer is not `ruby main.rb`'s, `true`, and `Parity::MOBILE_JUSTIFIED` justifies no difference there, so a host that moves Ruby off the main thread fails it.
- The mobile parity check builds and runs `examples/basket` in the iOS Simulator and on Android emulators (`tasks/mobile_parity.rb`), and fails unless it logs `Basket shows N items`, which it prints only once the platform has called its Ruby back on the main thread with its views on the screen, and then `Basket added Milk` and `Basket removed Milk` as the check adds an item and removes it. So the check proves Ruby on the main thread, the platform calling Ruby, and Ruby's widgets on the screen, with nothing of Fledge's between. On Android the check types with `adb shell input` and waits for UI Automator to show the row; simctl gives an app no keys or touches, so on iOS it runs a UI test of its own with XCTest, Apple's UI testing (`tasks/mobile_parity/ios_ui/ListUITests/ListTest.m`). A phone's own keyboard and a finger on its screen are proven only by hand (`doc/contributors/device-test.md`).
- `test/basket_bridge_test.rb` runs Basket's own tests of its Objective-C bridging among Fledge's unit tests, on a Mac, whose libobjc and Foundation are the ones an iPhone has, and the part of its calls into Java that needs no Java on any computer. `fledge test android test/phone.rb` runs Basket's tests of its screen in the app (`phone-projects.md`, "Tests in the app").
