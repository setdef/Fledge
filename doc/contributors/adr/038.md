# ADR 038: On Windows, keep RubyInstaller's tree whole and load Ruby's DLL at run time

## Context and Problem Statement

On Windows an app's Ruby is RubyInstaller's (ADR 035), a MinGW UCRT build in which Ruby is a DLL, not a static library. Ruby derives its prefix from the DLL's own path: a DLL in `PREFIX\bin` makes `PREFIX` the prefix (`ruby.c`, `runtime_libruby_path` and `ruby_init_loadpath`, at Ruby 4.0.9). The DLL's own dependencies load through the private assembly its embedded manifest names (`ruby_builtin_dlls`), and each extension's through its `*.so-assembly.manifest`, so moving a DLL out of the tree breaks what loads it. Windows resolves an executable's imports before any of its code runs, searching the executable's folder, System32, and `PATH`, never a folder below its own: a launcher at the top of the app that imports Ruby's DLL fails to start, with `0xC0000135`.

On macOS and Linux libruby is linked into the launcher, so Ruby's `lib/` sits beside it (ADR 001). Asked whether a different layout on Windows would trouble developers, the maintainer asked back (`decisions.md`, 2026-10-26, decision 23): "Would this require app devs to have a bunch of `if`s or polymorphic objects used throughout their app to handle the difference?" Where does Ruby go in a Windows app, and how does the launcher at its top reach it?

## Decision Drivers

- The person who opens the app's folder finds the app's program at its top.
- RubyInstaller's DLLs and manifests keep working as RubyInstaller ships them.
- No DLL loads from the current folder or `PATH`, where another Ruby's may be.
- App code needs no branch for the layout (decision 23).

## Considered Options

1. RubyInstaller's tree whole, in `ruby\`, and the launcher at the top, loading `ruby\bin`'s DLL by absolute path when it runs.
2. The launcher inside `ruby\bin`, beside the DLL.
3. A side-by-side manifest that reshapes the tree.
4. One layout on every system: a Ruby built statically for Windows, or Unix runtimes moved into `ruby/` with libruby a shared library.

## Decision Outcome

Chosen: option 1. Options 2 and 3 both work when tried, and both are worse for the person who opens the folder. Option 4 is a large change for nothing an app can observe: Ruby and RubyGems answer every question about the layout (`RbConfig::CONFIG["prefix"]`, `RbConfig.ruby`, `Gem.dir`, and `__dir__` for the app's own files), as they do for a developer's own Ruby on each system, so an app needs no branch for it.

A Windows app is `NAME.exe`, `fledge.cfg`, `app\`, `notices\`, and `ruby\`, which is RubyInstaller's tree with its shape unchanged. The launcher first keeps every DLL loaded by name to System32 and the folders a DLL names for itself (`SetDefaultDllDirectories`), then loads `ruby\bin`'s DLL by absolute path with `LoadLibraryExW` and looks up the functions Ruby's `main.c` calls with `GetProcAddress`. It is built for UCRT, RubyInstaller's C runtime, so that a variable it removes from its environment is gone from the copy Ruby reads too. `doc/contributors/design/launcher.md`, "Windows", gives the details.

Confidence: high. Delivery runs built apps on fresh x64 and ARM64 Windows runners, and the parity check runs on both.

### Consequences

- Good, because RubyInstaller's tree is unchanged, so its DLLs, manifests, `ruby.exe`, and `rubyw.exe` work, and moving the Ruby pin unpacks a new release into the same place.
- Good, because no folder joins `PATH`, and no other program's DLL loads in Ruby's place.
- Bad, because a Windows app's folder differs from a macOS or Linux app's, so the assembly, the license audit, and signing each know two layouts.
- Bad, because the launcher calls Ruby through function pointers typed by Ruby's headers, and is built against the DLL's name (`FLEDGE_RUBY_DLL`); a missing or damaged DLL is a damaged app, which exits 70.
- Bad, because `RbConfig.ruby` is RubyInstaller's console `ruby.exe`, so a restart through it is plain Ruby (ADR 026).

### Confirmation

- The Delivery (Windows) jobs of `.github/workflows/ci.yml` run built apps on fresh runners (`.github/scripts/deliver.ps1`), from a folder they were not built in and through a symbolic link in another folder, as winget links a portable app.
- The Test (Windows) jobs run the parity check on `x64-mingw-ucrt` and `aarch64-mingw-ucrt`.
- `tasks/runtime_builder/windows.rb` refuses a launcher that imports any DLL Windows does not ship, Ruby's included.
