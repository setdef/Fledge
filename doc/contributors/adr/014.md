# ADR 014: The Gem Pins Its Release's Runtimes by SHA-256, From a Pin Commit

## Context and Problem Statement

`fledge build` downloads a runtime, and to compile a gem its build-only companion, from the GitHub Release of its own version (ADR 034). A check against the release's own `SHA256SUMS`, fetched from the same place at the same moment, catches a damaged download. It does not catch a release whose asset and `SHA256SUMS` were both replaced, by anyone who can write to the repository's releases or who controls the connection's trust. The check and the thing checked come from one place. AGENTS.md asks that every downloaded input be pinned by SHA-256.

The runtimes are built by this repository, for this version, and their names carry the version (`fledge-runtime-VERSION-PLATFORM.tar.gz`). A version cannot pin files built after it is tagged. Building them first and pinning them after is easy only if a second build of the same commit gives the same bytes, and it does not: each runner's own tar writes the archives, with the build's time in them (ADR 047), and each runner compiles the launcher.

How does a version of the gem know the SHA-256 of runtimes that do not exist when its code is written?

## Decision Drivers

- The check must not come from the host that serves the file.
- Runtime builds are not reproducible, and making them so is a project of its own.
- Anyone should be able to check a release with tools every system has.
- Releasing should stay a few steps an agent can follow.

## Considered Options

1. Build the runtimes on the release commit, write their SHA-256s into the gem in a second commit that changes nothing else, and tag that one, as Homebrew does for bottles.
2. Keep checking each download against the release's own `SHA256SUMS`.
3. Pin hashes of files already published, as uv pins python-build-standalone.
4. Make runtime builds reproducible, so one commit can pin what a later build will produce.

## Decision Outcome

Chosen: option 1, because it is the only one that pins the very bytes a release publishes without reproducible builds. `lib/fledge/SHA256SUMS` holds the SHA-256 of every asset of the version's release, in the form `sha256sum` writes, and is the release's `SHA256SUMS` byte for byte. `Fledge::Runtimes` takes every SHA-256 from that file, never from the release, and checks a cached runtime against it too. The release commit's CI builds the runtimes; `rake runtime:pin` writes the pin commit from that run; the pin commit is tagged. `doc/contributors/design/releases.md` says how.

A plain `SHA256SUMS` was chosen over a YAML or JSON file of Fledge's own because the release already publishes that format and every system's tools read it (`sha256sum -c`, `shasum -a 256 -c`).

Confidence: high. Every release since it was decided was made this way, and `installed.yml` checks each published asset against the tag's pins.

### Consequences

- Good, because a release asset replaced after its tag fails every `fledge build` that downloads it, naming both SHA-256s, and leaves nothing in the cache.
- Good, because a cache is a folder any program can write to, and the cache is checked against the pins as well.
- Good, because anyone can check a release with the gem's own file and `sha256sum -c`.
- Bad, because a release is two commits and two CI runs, and the second must come within the 14 days CI keeps the first run's runtimes. ADR 053 keeps the second run short.
- Bad, because a commit between releases pins no runtime of its own version. It says so, naming `FLEDGE_RUNTIME_DIR`, which holds a developer's own builds and is not checked.
- Neutral, because reproducible builds stay possible. They would let one commit do and let anyone rebuild a release to compare, and nothing here prevents them.

### Confirmation

`test/runtimes_test.rb` serves an asset and a `SHA256SUMS` from a loopback server that agree with each other and not with the pins, and the build fails. `tasks/runtime_pins.rb` refuses a set of runtimes that is not exactly `RuntimeBuilder.release_assets`. `release.yml` and the pin commit's CI check every runtime against its pin with `.github/scripts/check-pins.sh`, and `release.yml` refuses a tagged commit that changes anything but `lib/fledge/SHA256SUMS`.

## Pros and Cons of the Options

### The release's own SHA256SUMS

- Good, because it needs no second commit.
- Bad, because the check and the file come from one host, so one write replaces both.

### uv's metadata

uv commits `crates/uv-python-managed/download-metadata.json` (astral-sh/uv at 564a2074), a `sha256` for every build python-build-standalone already published.

- Good, because a uv release knows every hash before it ships.
- Bad, because it pins files another project built earlier. Fledge builds its runtimes for the very version that pins them.

### Reproducible builds

- Good, because one commit would pin, and anyone could rebuild and compare.
- Bad, because it needs fixed timestamps, sorted entries, and the same compilers' output byte for byte on macOS, Linux, and Windows, and must stay true through every change to a runtime. It shows a developer nothing until it is complete.

## More Information

Homebrew's CI builds a formula's bottles as workflow artifacts; `brew pr-pull` downloads them (`Library/Homebrew/dev-cmd/pr-pull.rb` at Homebrew/brew 1f55ebf8, lines 160 to 176), and `brew pr-upload` runs `brew bottle --merge --write`, which commits each bottle's SHA-256 into the formula, and then uploads the same bottles (`dev-cmd/pr-upload.rb`, lines 55 to 62 and 116 to 122). The bottle commit changes only the formula's `bottle do` block, as Fledge's pin commit changes only its pins. Bundler pins each gem the same way in a lockfile's `CHECKSUMS`, which Fledge requires of an app.

ADR 053 decides how a release publishes the runtimes it pinned. ADR 031 lets a mirror serve them, checked against the same pins.
