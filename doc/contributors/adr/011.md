# ADR 011: Mobile Runtimes

## Status
Accepted (requested). Agents wrote this ADR and may change it (AGENTS.md, Questions). It applies the maintainer's words of 2026-10-27 in `doc/contributors/decisions.md` ("We should, if we can, support iOS and iPadOS and Android. Ideally before 1.0 but I could be swayed if it turns out incredibly burdensome."), with decisions 8, 9, 10, and 20, the replies of 2026-10-26 on the LGPL, and the words of 2026-10-28 on code as a liability, on building each target on its own system, and on waiting for an Apple Developer account until the last responsible moment. It carries Plan 002's story "Mobile runtimes" and the mobile spike (branch `spike/mobile`, `spike/mobile/FINDINGS.txt`, CI runs 40630328845 and 40630328941), whose recipes it ports.

## Date
2026-10-28

## Context

A phone runs no program of Fledge's own. An iOS app is one signed binary in a bundle that may load no code from files; an Android app is an APK whose native code Java loads, and whose assets are not files. So a mobile runtime cannot be a launcher with a relocatable Ruby beside it, as a desktop runtime is (ADR 001): it is Ruby as a library, linked into an app that a developer, or a framework such as Lota or Tokra, builds with Xcode or Gradle. No prebuilt Ruby exists for either system. xord/cruby builds the CRuby behind RubySketch, on the App Store, as an XCFramework (its Rakefile, at 11d62c4), and Termux builds CRuby for Android (`termux-packages/packages/ruby/build.sh`); the spike built CRuby 4.0.9 both ways, statically and interpreter only, and ran a script in the iOS Simulator and on Android emulators.

The spike also found what it left for this story: iOS reports `arm64-darwin`, as macOS does, so a target named after `RUBY_PLATFORM` would let Bundler pick macOS's native gems; the bundled gems with C extensions could link in only by ceasing to be gems; iOS's Ruby started in a US-ASCII locale; and HTTPS failed for want of CA certificates.

## Decision

### 1. Targets, named by RubyGems' grammar, and matching no desktop gem

A mobile runtime has two targets each, named as RubyGems names platforms, CPU first, then the system, then what RubyGems calls the version (`Gem::Platform#initialize`, `lib/rubygems/platform.rb` at Ruby 4.0.9), which for Linux is the C library (`aarch64-linux-musl`), and which LLVM's triples call the environment:

| Target | What | Its Ruby's `RUBY_PLATFORM` | Gem::Platform reads it as |
|---|---|---|---|
| `arm64-ios` | iPhones and iPads | `arm64-darwin` | `arm64-unknown` |
| `arm64-ios-simulator` | the iOS Simulator on Apple silicon | `arm64-darwin` | `arm64-unknown` |
| `aarch64-linux-android` | arm64-v8a phones and tablets | `aarch64-linux-android` | `aarch64-linux-android` |
| `x86_64-linux-android` | x86_64 emulators and Chromebooks | `x86_64-linux-android` | `x86_64-linux-android` |

The iOS names drop the vendor from Apple's own triples, `arm64-apple-ios` and `arm64-apple-ios-simulator`, as RubyGems' Linux names drop it from `aarch64-unknown-linux-android`; CPython's iOS support (PEP 730) names the same two `arm64-apple-ios` and `arm64-apple-ios-simulator`, and Rust names them `aarch64-apple-ios` and `aarch64-apple-ios-sim`. The Android names are Ruby's own `RUBY_PLATFORM` there, which Gem::Platform reads as Linux with Android's C library, and which no `aarch64-linux`, `-gnu`, or `-musl` gem fits, rightly, since bionic loads none of them.

RubyGems knows no iOS: a name whose system is `ios` reads as an unknown one (`arm64-unknown`), and one that says `darwin` reads as macOS. An iOS Ruby reports `arm64-darwin` (xord/cruby's does too, configured with `--host=aarch64-apple-darwin`), so its own `Gem::Platform.local` matches every `arm64-darwin` gem, and Bundler, resolving a lockfile there, would pick nokogiri's macOS build, which can never load on a phone. Fledge's target names keep the two apart where Fledge decides: `Gem::Platform.new("arm64-darwin") === Gem::Platform.new("arm64-ios")` is false, and so for every desktop name and every mobile target (`test/mobile_runtime_test.rb`). Building apps for these targets is the next story (Plan 002, "Mobile apps from fledge build"): `fledge build` will refuse every precompiled build for them, since none exists for any mobile target, and set Bundler's own `force_ruby_platform` in the app's `.bundle/config`, which Bundler documents as "Ignore the current machine's platform and install only `ruby` platform gems" (`lib/bundler/man/bundle-config.1.ronn`, at Bundler 4.0.20), so the app's Bundler resolves its lockfile's `ruby` gems only. Changing `RUBY_PLATFORM` itself was considered: configuring Ruby for an `ios` host leaves out what Ruby's `configure.ac` does for Darwin, which xord/cruby and the spike rely on, and an app's own `RUBY_PLATFORM =~ /darwin/` would stop matching a system that is Darwin. Native gems on a phone come after 1.0.

### 2. What a mobile runtime is

Each is a release asset of its own, `fledge-runtime-VERSION-ios.tar.gz` and `fledge-runtime-VERSION-android.tar.gz`, with its SBOM and NOTICES beside it, as every desktop runtime has (ADR 004), and no build-only companion, since its headers are in it.

- **iOS and iPadOS**: `FledgeRuby.xcframework`, made by `xcodebuild -create-xcframework`, Apple's tool, from two static libraries, one per target (slices `ios-arm64` and `ios-arm64-simulator`). Each slice holds `libfledgeruby.a`, which is Ruby, its extensions and encodings, OpenSSL, libyaml, and the embedding API merged by Apple's `libtool`; its headers, Ruby's with its configuration header beside the rest so one folder serves `#include <ruby.h>`, and the embedding API's with a Clang module map, so Swift imports it as `FledgeRuby` and linking it adds libz and the Security and CoreFoundation frameworks; and, as CPython's iOS XCFramework does, the Ruby the slice runs, its `lib/ruby` and `libexec/cert.pem`, which an app copies into its bundle for the slice it builds. The two Rubies differ only in the compiler their `rbconfig.rb` records. One binary runs on iPhone and iPad (the host app is built with `TARGETED_DEVICE_FAMILY` 1,2).
- **Android**: `FledgeRuby.aar`, packed by Gradle and the Android Gradle plugin from `runtime/mobile/android/`, holding `libfledgeruby.so` for arm64-v8a and x86_64 and the Java class `org.setdef.fledge.FledgeRuby`; beside it, one `lib/ruby` for both ABIs (Ruby names each ABI's folder of platform-specific files for its own platform, so both fit one tree), `libexec/cert.pem`, and `include/`. An app carries `lib/`, `libexec/`, and its own code in `app/` as one stored zip asset, which the Java class unpacks into the app's files folder on the first launch of each installed version, as the spike's host did (1.5 to 2.8 seconds on CI's emulators, then milliseconds). `libfledgeruby.so` holds all of Ruby, so native code that links it (Lota's) finds Ruby's whole C API, and keeps OpenSSL's, libyaml's, and libffi's symbols to itself (`--exclude-libs`). It needs only Android's `libc`, `libm`, `libdl`, `liblog`, and `libz`, and every LOAD segment is aligned to 16 KB, as Google Play requires from 2027-02-01; the host app is checked with `zipalign -c -P 16` and targets API 36.

Neither runtime has a `bin/ruby`, or the gems' executables: nothing on a phone could run them.

### 3. Building CRuby for a phone

`RuntimeBuilder::IOS` and `RuntimeBuilder::Android` (`tasks/runtime_builder/`) build Ruby 4.0.9 from its release tarball with Ruby's own `configure` and `make`, cross-compiling with Xcode's clang (`xcrun`) or the NDK's, against OpenSSL 3.6.5 (RubyInstaller's release) and libyaml 0.2.5 built the same way, and on Android libffi 3.5.2: `--with-static-linked-ext --disable-shared --disable-yjit --disable-zjit --enable-load-relative --without-gmp`, with `PKG_CONFIG=false` so nothing of the build machine's leaks in, after xord/cruby on iOS (`--disable-dln`, and configure told that iOS has no `system`, `syscall`, `backtrace`, `getentropy`, `dup3`, or `pipe2`) and Termux on Android (no `setgroups`, `setresuid`, `setreuid`, or libcrypt; API 26, the first with `nl_langinfo`). Every input is pinned by version and SHA-256 in `runtime/sources.yml`: the tarballs, the NDK r30 for each computer that runs it, Gradle 9.8.2 with the Android Gradle plugin 9.4.1, Mozilla's CA certificates as curl publishes them, and XcodeGen 2.46.0, which writes CI's host app's project; Xcode 26.5 is chosen by version on the runner, since Apple publishes no download to pin.

Each builds on its own system, with that system's tools (decisions, 2026-10-28): iOS on a Mac, since only Xcode builds for it; Android on Linux in CI, where Google's NDK runs as it does on a Mac, which may build it too. Neither is built on the other's runner.

Ruby's source gets four scripted edits (`RuntimeBuilder::RubySource`), each failing the build when the lines it replaces are gone, so that a new Ruby shows which to look at again: psych's `extconf.rb` stops preferring pkg-config's libyaml (xord/cruby's edit); `vm_dump.c` stops calling `system()` on iOS (xord/cruby's); the generated `configure` stops appending `-android` twice (Termux's guard, which gives `aarch64-linux-android`, not `aarch64-linux-android-android`); and `ruby.c` gains `ruby_embed_libruby_path`, through which an embedder names the file Ruby would otherwise find with `dladdr` and derive its prefix from (`runtime_libruby_path`, lines 591 to 664 at 4.0.9), since on Android that file is in a folder of native libraries alone and an iOS app may keep Ruby anywhere in its bundle. On iOS a stub `sys/vnode.h`, which the SDK lacks, is xord/cruby's, with its MIT notice.

A cross build cannot run its own miniruby, so `configure.ac` (lines 1584 to 1588) leaves out the builtin binary, and Ruby falls back to `mini_builtin.c`, which never loads `gem_prelude.rb`: the spike's first Ruby booted with no RubyGems. An iseq binary depends only on Ruby's version, endianness, and word size (`compile.c`, `ibf_load_setup_bytes`), so a miniruby built for the build machine from the same source writes the target's, once per runtime build. And libruby's `dmyext.o` and `dmyenc.o`, the empty `Init_ext` and `Init_enc` of a Ruby without static extensions, are left out of what links, or the linker takes them before `extinit.o`'s and `encinit.o`'s and `require "json"` fails (the spike's finding; xord/cruby leaves them out too).

Considered, and the reasons none fit: xord/cruby's Rakefile itself, which builds Ruby 4.0.7 and folds every bundled gem into the standard library; Termux's packages, which build for Termux's own prefix with its `libandroid-support`; CPython's `Apple/` and `Android/` build scripts, which build Python; and a Ruby configured for an `ios` host (section 1). What is Fledge's own is the order of the maintained tools' commands, four edits, and the embedding API (section 5).

### 4. Bundled gems stay gems

A mobile Ruby loads no extension from a file, so every extension is linked in. Ruby links its own that way, registering each in `extinit.c`, but never a bundled gem's: `template/configure-ext.mk.tmpl` builds `.bundle/gems` with `--no-extstatic`, and `ext/extmk.rb` (line 656) leaves a gem's extension out of `extinit.c`. The spike moved bigdecimal, debug, nkf, racc, and syslog into the standard library, so they loaded but were no longer gems (`Gem.loaded_specs["bigdecimal"]` was nil), and left rbs out; an app that names one in its Gemfile, or asks RubyGems for it, would notice (decision 9).

Instead (`RuntimeBuilder::BundledExtensions`), each such gem's extension sources (its `ext/`, and the `lib/`, `include/`, and `src/` its `extconf.rb` reads beside it) are copied among Ruby's own, to `ext/gems/NAME`, where extmk links them in and registers each under the feature its gem requires (`bigdecimal.so`, `racc/cparse.so`, `rbs_extension.so`); `configure --with-out-ext` leaves out the gem's own build, by the names extmk matches a gem by (`NAME` and `NAME-*`, `ext/extmk.rb` lines 519 to 523); and once Ruby is built, each gem's extension is marked built (`.bundle/extensions/PLATFORM/4.0.0-static/NAME-VERSION/gem.build_complete`), as its own build would have marked it, so `tool/rbinstall.rb` installs the gem, specification and all, as it installs every bundled gem, and RubyGems loads it rather than "ignoring it because its extensions are not built". When the gem's Ruby requires its extension, `load.c`'s `search_required` finds no file and looks among the statically linked extensions, which have it. The build checks that every such gem was installed with its specification and its mark. On iOS, fiddle is left out, as xord/cruby leaves it out "to pass the App Store review": it calls any C function by name. win32ole is Windows' alone. Every other bundled and default gem is as a desktop runtime has it, rbs included.

### 5. The embedding API

`runtime/mobile/fledge_ruby.h`, in C, is two functions:

```c
int fledge_ruby_forward_output(const char *tag);
int fledge_ruby_run(const char *root, const char *script, int argc, char *const *argv);
```

`fledge_ruby_run` starts Ruby on the calling thread as Fledge's launcher does, after Ruby's own `main.c` (ADR 003): `ruby_sysinit`, `ruby_start_main`, and `RUBY_INIT_STACK`, `ruby_init`, `ruby_run_node(ruby_options(...))`, with `ruby --disable=rubyopt -- SCRIPT ARGS`. Ruby's prefix is `root`, through `ruby_embed_libruby_path`, so the load path and `Gem.path` are the runtime's own (`root/lib/ruby`, with Fledge's RubyGems defaults keeping `Gem.path` to it, ADR 001, section 8); OpenSSL trusts `root/libexec/cert.pem`, since its compiled-in folder is the build machine's, through the `SSL_CERT_FILE` it reads itself on iOS; and a bare C locale becomes a UTF-8 one, with the launcher's own `fledge_coerce_locale`, now in `runtime/launcher/locale.c` for both. Ruby boots once per process, so a second call returns 70 (EX_SOFTWARE). Nothing is set aside from the environment, as the launcher sets RUBYOPT and the rest aside: iOS and Android start an app with an environment of their own, which no person sets.

`fledge_ruby_forward_output` makes standard output and standard error each the write end of a pipe, which a thread of its own reads line by line into the system log, which iOS and Android otherwise discard an app's streams for: os_log, with the tag as subsystem, on iOS; logcat, with the tag as tag, on Android, standard error's lines as warnings, as CPython's Android support logs them. A line longer than a log entry holds (logcat cuts one at about 4,000 bytes) goes as several entries of at most 1,000 bytes in a row, cut between UTF-8 characters.

On Android, OpenSSL reads no environment variable in an app: `ossl_safe_getenv` refuses them where `AT_SECURE` is set (`crypto/uid.c`, `OPENSSL_issetugid`, at 3.6.5), and every app inherits `AT_SECURE` from zygote, which Android starts in an SELinux domain of its own; the spike's HTTPS failure on Android was this, and setting `SSL_CERT_FILE` alone failed the same way on an emulator. So the Android library is linked with the linker's own `--wrap=X509_get_default_cert_file`, which sends OpenSSL's every call of that function to the embedding API, which answers with the runtime's file; `OpenSSL::X509::DEFAULT_CERT_FILE` names it too. Patching OpenSSL, or Ruby's `openssl/ssl.rb`, was considered; the linker's option needs no source edit, and reaches every caller, not only Ruby's default store. Apple's linker has no such option and needs none.

Swift needs no shim: the module map imports the C functions. Android needs Java for what C cannot do, in `org.setdef.fledge.FledgeRuby`: unpack the app's asset, set HOME to the app's files folder when Android sets none (iOS gives every app one, and `Dir.home` should be writable), send Java's strings as their UTF-8 bytes (JNI's `GetStringUTFChars` writes modified UTF-8, which differs past Unicode's first plane) and its paths canonical (an app's files folder is `/data/user/0/PACKAGE/files`, through a link to `/data/data`, which Ruby resolves `__dir__` through, as the desktop launcher resolves its own folder), and start Ruby on a thread with a 64 MB stack, never the UI thread, which Android stops an app for blocking. It is Java, not Kotlin, so an app need not depend on Kotlin's standard library; Kotlin calls it as it is.

### 6. What decisions 9 and 10 mean on a phone

The parity check runs on phones too (`tasks/mobile_parity.rb`, CI's Mobile parity jobs): the parity probe, run through the embedding API by a small host app of CI's own (`test/fixtures/mobile/`) in the iOS Simulator on an iPhone and an iPad and on Android emulators with 4 KB and 16 KB pages, against `ruby main.rb` under the desktop Ruby of the runner (rv-ruby's, as the desktop check uses), with no arguments on either side, since a phone has no command line; its report reaches the check through the system log, as an app's output reaches its developer. A script that requires json and csv, a bundled gem, and reaches rubygems.org over HTTPS, must print `["csv","3.3.5"]` and status 200. Every difference must be justified in `Parity::MOBILE_JUSTIFIED`, for the mobile targets only. They are:

- **No inherited environment.** `ENV` is the system's: HOME and TMPDIR in the app's own container, on iOS the Simulator's variables, nothing of a shell's, and the runtime's SSL_CERT_FILE (and on Android its HOME).
- **No subprocesses.** iOS lets no app run a program, and Android lets no app run a file of its own (W^X, from target API 29), so there is no `bin/ruby`; `RbConfig.ruby` names where it would be, and starting it fails with ENOENT, as where Ruby is missing. On an iOS device, Apple's sandbox denies `fork` too (not seen here, for want of a device; the Simulator allows it).
- **The platform's own names.** `RUBY_PLATFORM`, `RUBY_DESCRIPTION`, and the folders of platform-specific files on `$LOAD_PATH` say `arm64-darwin` or `ARCH-linux-android` where rv-ruby's say `arm64-darwin23` or `x86_64-linux`.
- **Extensions linked in.** `$LOADED_FEATURES` records each extension as the feature it registers (`json/ext/parser.so`, `encdb.so`), not a file, and holds Fledge's RubyGems defaults, as on every desktop runtime.
- **Interpreter only.** `RubyVM::YJIT` is not defined: iOS gives no app memory it may write code into and run, and Ruby builds no JIT for Android.
- **No fiddle on iOS** (section 4).

Everything else the probe reports is the same on a phone: the standard library and every default and bundled gem, each a gem and each loading (but fiddle on iOS); `Gem.path` and `Gem.dir`; the encodings, UTF-8; the standard streams' modes; the globals. What the probe cannot show, and an app on a phone should expect: the working folder is `/`, as for a macOS app started from the Finder; standard input is at its end; the app's bundle is read-only on a device (writable in the Simulator), so an app writes under `Dir.home` or `Dir.tmpdir`; on iOS the main thread's stack is the system's; and the system may stop an app in the background without running `at_exit`.

### 7. Licenses

Each mobile runtime passes the license audit before it is archived (ADR 004), and ships only what decision 8 allows without an LGPL library: Ruby (Ruby OR BSD-2-Clause), OpenSSL (Apache-2.0), libyaml and libffi (MIT), on Android the NDK's compiler-rt builtins and libunwind (Apache-2.0 WITH LLVM-exception), Mozilla's CA certificates (MPL-2.0, as a file), and Fledge's own embedding API (AGPL-3.0-or-later, first party, under component `fledge-embedding`). GMP is configured out, iOS's `crypt` is its libSystem's, and Android's String#crypt is Ruby's own `missing/crypt.c`, so neither carries libxcrypt; the audit's signatures of libxcrypt, GMP, and libfuse find none of them.

The audit needed two changes, and no new reader of binaries: `Fledge::Binary` already reads a static archive, and the audit's evidence strings find what is linked into one. An iOS runtime has a Ruby per slice, so a platform's map entry may name several prefixes (`runtime/licenses.yml`, `prefixes`), and each gem in them is one component. And an AAR is a zip, whose entries the app ships, so the audit reads each entry, with `unzip`, as `FledgeRuby.aar!ENTRY`, as it already names the files inside a cached `.gem`; a copyleft library's code in one fails as it would in a file.

## Consequences

- Fledge's CI builds an iOS and an Android runtime on every push (about 14 minutes on a macOS runner and 12 on a Linux one) and checks them in the Simulator and on emulators (about 8 macOS minutes and twice 6 Linux minutes), and each release publishes them. `fledge build` does not build mobile apps yet; Plan 002's next story writes the Xcode and Gradle projects around these runtimes.
- A developer, or a framework, links the XCFramework or the AAR and calls two C functions, or one Java method; the README says so. Each mobile release carries its runtime's NOTICES and SBOM; `doc/licensing.md`, which describes the apps `fledge build` builds, gains the mobile platforms with the story that builds them.
- Each Ruby release means rechecking the four source edits, the builtin binary, and the bundled gems' extensions, each of which fails loudly when it stops applying; three are worth upstreaming to ruby/ruby (an embedder's prefix, the builtin binary for cross builds, and static bundled gems).
- Not yet proven, for want of devices: a real iPhone or iPad (which needs an Apple Developer account, the maintainer's to get at the last responsible moment; the device slice is built and linked, unsigned, in CI) and App Store review. GitHub's Linux runners emulate x86_64 only, so CI runs the arm64-v8a library on nothing; the parity check passed with it, and hello.rb reached rubygems.org, on an arm64-v8a API 36 emulator on an Apple-silicon Mac while this ADR was written, which is not a gate.
- An iOS app that links both this runtime and another OpenSSL would see their symbols clash, since a static library cannot hide them as the Android library does.
