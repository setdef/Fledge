# ADR 065: Keep an Input Whose URL Rolls Over as a Pre-release of Fledge

## Context and Problem Statement

Every input a runtime is built from is pinned by version and SHA-256 (AGENTS.md), and the build, the license audit, and the parity check fetch it from the pinned URL. RubyInstaller publishes no build of a Ruby preview, so while Fledge carries Ruby 4.1's previews (ADR 056) its Windows runtimes take RubyInstaller's `rubyinstaller-head` release, whose URLs serve a new build every day in place of the last (`https://github.com/oneclick/rubyinstaller2/releases/tag/rubyinstaller-head`). A pin of those URLs resolved for one day: from 2026-11-11 the bytes pinned on 2026-11-10 were gone, and every job that fetched them without the Actions cache failed. RubyInstaller's CI keeps each successful head build as an artifact for about 90 days, but without the `.asc` signature the build checks, which exists only on the release asset.

Where should Fledge fetch an input whose upstream URL rolls over?

## Decision Drivers

- Every input is pinned by SHA-256, and RubyInstaller's archive by its signature against a pinned key (ADR 035).
- A pin must keep resolving for as long as any commit that names it may be built, CI and releases included.
- An agent never publishes and never opens an account (AGENTS.md; decisions.md, 2026-11-02 and 2026-11-04).
- Code is a liability (decisions.md, 2026-10-28).

## Considered Options

1. Keep the exact files, unchanged, as assets of a pre-release of Fledge's own repository named `inputs-<source>-<date>`, and pin that copy.
2. Pin the upstream URL, with the copy as a mirror that a release publishes beside its runtimes.
3. Rely on the Actions cache of each branch.
4. Commit the files to the repository.

## Decision Outcome

Chosen: option 1. The copy is the same bytes under the same SHA-256 and the same signature, so it is the input, not a rebuild of it, and a GitHub Release asset of Fledge's own repository is a host Fledge already depends on for its runtimes. A tag that does not start with `v` runs no `release.yml`, and a pre-release is never the latest release. Option 2 fails before the release that would publish the copy exists, since that release's pin commit needs CI to pass first. Option 3 holds only on the branch that filled the cache, and for at most seven days unused. Option 4 puts tens of megabytes of binaries in every clone.

A workflow publishes such a pre-release where one can (`.github/workflows/keep-rubyinstaller-head.yml` for RubyInstaller's head builds, ADR 066); otherwise the agent who pins an input hands its files and their SHA-256s to the session that orchestrates, which checks each SHA-256 and signature again and publishes it; the pins then name it alone, and `runtime/sources.yml` names the upstream URL in a comment, for provenance. Such a pre-release is never deleted. `doc/contributors/design/runtimes.md` ("Rolling upstream inputs") holds the rules.

Confidence: high. The first, `inputs-rubyinstaller-head-20261110`, serves both Windows archives and their signatures, and the Windows runtimes build and verify from it.

### Consequences

- Good, because a pin of a rolling input resolves for as long as the repository's releases do, on every branch and in every release's checks.
- Good, because the signature check still proves RubyInstaller signed what Fledge builds from.
- Bad, because the files must be taken on the day upstream serves them, and published by the orchestrating session, not by the agent who pins them.
- Bad, because the repository's releases list holds pre-releases that are not versions of Fledge.

### Confirmation

`test/runtime_builder_test.rb` checks that each Windows pin names the copy, with its signature beside it; the Windows runtime jobs and the Windows parity checks fetch it and verify its signature on every CI run.

## More Information

ADR 056 is why Fledge carries a Ruby preview, and ADR 066 how Windows follows the previews. Revisit this when RubyInstaller publishes a numbered build of the Ruby Fledge carries, which needs no copy.
