# ADR 008: Windowed Apps, and the Identity Every App Shows

## Status
Accepted (requested). Agents wrote this ADR and may change it (AGENTS.md, Questions). It applies the maintainer's decision 18 in `doc/contributors/decisions.md` ("Would this affect what shows up in the taskbar? task manager? start menu? desktop icons? app window top-left corner and/or title bar? If so, app devs need to be able to control it."), decision 17 (signing is an option for developers with Apple's and Microsoft's credentials, and unsigned builds still work), and the words of 2026-10-28 on an Apple Developer account (wait until the last responsible moment, which this ADR does not reach: ad hoc signing needs none). It carries out ADR 001, section 5 (console and windowed apps) and Plan 002's stories "Windowed apps" and "App identity", and keeps ADR 001's promise that one computer builds every platform.

## Date
2026-10-28

## Context

Every app Fledge built through 0.0.1.pre.5 was a console app with the launcher's identity: no icon, no version information, and a name that was only a file name. Lota's games and Tokra's desktop apps open windows and want no terminal, and every operating system shows an app's name and icon in places a developer cares about: Windows in Explorer, the taskbar, Alt-Tab, Task Manager (whose process list names a program by its version information's FileDescription), and a window's title bar; macOS in the Dock, Cmd-Tab, the menu bar, and Finder, all read from a bundle; Linux desktops from a `.desktop` file and icon theme. Tokra's sessions found two identities the operating systems check before an app may notify anyone: macOS's `CFBundleIdentifier`, which exists only in a bundle's `Info.plist`, and Windows' AppUserModelID, which a toast needs registered on a Start menu shortcut (Plan 002, "App identity").

Three constraints shape the answer. The launcher is compiled once per runtime, in Fledge's CI, so each app's identity goes into its copy when `fledge build` runs. That build runs on any computer, Linux included, for every target (ADR 001, section 2), so nothing in it may need a platform's own tools: no `codesign` or `plutil`, which run only on macOS, no `rc.exe` or `UpdateResource`, which run only on Windows. And the parity check (ADR 003) must keep passing for console apps.

Prior art, read for this decision:

- **Tauri's bundler** (`tauri-apps/tauri` at 32576120f). Its `Info.plist` (`crates/tauri-bundler/src/bundle/macos/app.rs`, `create_info_plist`, lines 203 to 410) sets `CFBundleDisplayName`, `CFBundleExecutable`, `CFBundleIconFile`, `CFBundleIdentifier`, `CFBundleInfoDictionaryVersion` 6.0, `CFBundleName`, `CFBundlePackageType` APPL, `CFBundleShortVersionString` and `CFBundleVersion` from the app's version, `LSMinimumSystemVersion`, `NSHighResolutionCapable`, and `NSHumanReadableCopyright` from its copyright. Its Windows resources (`crates/tauri-build/src/lib.rs`, lines 600 to 650) set FILEVERSION and PRODUCTVERSION from the version's major, minor, and patch, ProductName, CompanyName (the publisher, or else the identifier's second part), FileDescription from the product's name, LegalCopyright, and the icon as resource 32512. Its configuration requires an `identifier` "in reverse domain name notation", of "alphanumeric characters (A-Z, a-z, and 0-9), hyphens (-), and periods (.)" (`crates/tauri-utils/src/config.rs`, lines 3308 to 3312), and its build refuses the template's default one (`crates/tauri-cli/src/build.rs`, lines 164 to 166).
- **Go's linker** writes ad hoc signatures itself, with no Apple tool (`cmd/internal/codesign/codesign.go` in Go 1.27.3): a SuperBlob holding one CodeDirectory, version 0x20400, of SHA-256 page hashes, with the executable segment's offset, size, and main-program flag, after the layout of xnu's `cs_blobs.h`.
- **Apple's `codesign --sign -`** on macOS 15, run by hand on bundles shaped as below, as the oracle: it accepts symbolic links in `Contents/MacOS` that point into `Contents/Resources`, records them in `files2` as links, seals every other file with SHA-256 (`files2`) and those under `Resources/` with SHA-1 too (`files`), leaves Mach-O files under `Resources/` as they are and seals them as resources, writes an empty requirement set and an empty CMS blob beside the CodeDirectory, and binds `Info.plist` and the seal through the CodeDirectory's special slots 1 and 3.
- **LLVM's `llvm-rc`** (llvm-mingw 20261020, the pinned toolchain) as the oracle for a VERSIONINFO resource's bytes.
- **The freedesktop.org Desktop Entry Specification** (1.5) and **Icon Theme Specification**, with `desktop-file-validate` (desktop-file-utils 0.27) as the oracle, and **AppImage**'s AppDir, which keeps the desktop entry at the top of the folder beside the program.
- **Microsoft's documentation**: "PE Format" (the resource section), "Version Information" (VS_VERSIONINFO), "Icons" (the ICO format and its sizes), and `SetCurrentProcessExplicitAppUserModelID` (shell32), which sets a process's AppUserModelID and must run before its first window.
- **PyInstaller's** console and windowed bootloaders, and **RubyInstaller's** `ruby.exe` and `rubyw.exe`: one program per subsystem, shipped side by side.

## Decision

### 1. Two kinds, and the developer's identity, in fledge.yml

`fledge.yml` (ADR 005, section 3) knows `name`, `kind` (`console`, the default, or `windowed`), `identifier`, `version`, `icon`, `publisher`, and `copyright`, and refuses anything else. Each has a default, so a project with no `fledge.yml` still builds the console app it built before:

- **name** is the app's name everywhere: its program, folder, and archive, a bundle's `CFBundleName` and `CFBundleDisplayName`, Windows' FileDescription, ProductName, and InternalName, and a desktop entry's `Name`. It may hold spaces, as `Hello Window` does. One name, as Tauri's `productName` is, rather than a display name beside a file name, because every place a person sees the app should agree.
- **identifier** is reverse-DNS: two or more parts of letters, digits, and hyphens between dots, as Tauri and Apple allow, in at most 128 characters, an AppUserModelID's limit. It is `CFBundleIdentifier`, the AppUserModelID, the code signature's identifier, and the desktop entry's file name and icon name. A windowed app must have one, as Tauri, Briefcase, and Flatpak require one: no default could name a domain the developer controls, and a wrong one is what macOS and Windows would remember the app by. The build fails and suggests one (`io.github.OWNER.NAME` for a gemspec whose homepage is on GitHub, as Flathub names such apps, or else `com.example.NAME`). A console app may have one; on Windows it then becomes its AppUserModelID too.
- **version** defaults to the gemspec's, as Tauri takes the crate's, and to `0.0.0` for a project with no gemspec. It must begin with a number and be a version RubyGems reads; YAML's `1.2` must be quoted, since YAML reads it as a number and `1.10` would become `1.1`.
- **icon** is one square PNG of at least 1024 pixels a side, relative to the project's root, as Tauri's and Electron's icon tools start from one large image. Fledge makes every other size from it (section 5). Without one, each system shows its generic icon.
- **publisher** defaults to the gemspec's authors, the Ruby project's own statement of who made it; Tauri defaults to a part of the identifier, which in Ruby says less. **copyright** has no default: Fledge makes no legal statement on a developer's behalf.

### 2. On macOS, a windowed app is an .app bundle, signed ad hoc

```
NAME-arm64-darwin/NAME.app/Contents/Info.plist
                              MacOS/NAME              the launcher
                              MacOS/{app,bin,fledge.cfg,lib,libexec} -> ../Resources/...
                              Resources/NAME.icns
                              Resources/{app,bin,fledge.cfg,lib,libexec,notices}
                              _CodeSignature/CodeResources
```

Ruby derives its prefix from the program that holds libruby (ADR 001, section 1; `--enable-load-relative`), and the launcher reads `fledge.cfg` and `app/` beside itself, so its neighbors must be reachable from `Contents/MacOS`. Apple's tools expect only code there, and a data file in a nested-code location is something codesign wants signed on its own. So the runtime and the app live in `Contents/Resources`, and symbolic links in `Contents/MacOS` point at them, which codesign verified strictly and deeply in Apple's own signing and in Fledge's. The app's `__dir__` is its real folder under `Resources`, as Ruby resolves the script it runs. A console app on macOS stays a folder: a terminal tool has no bundle.

`Info.plist` holds Tauri's keys, less those that describe Tauri's own runtime (`CSResourcesFileMapped`, `LSRequiresCarbon`): the bundle identifier, name, display name, executable, package type, `CFBundleIconFile` when there is an icon, `CFBundleDevelopmentRegion` `en`, `CFBundleShortVersionString` and `CFBundleVersion` (the version's leading numbers, at most three, as Apple's reference asks, so `0.0.1.pre.6` is `0.0.1`), `LSMinimumSystemVersion` 14.0 (the runtime's own floor, `Platform::MACOS_MINIMUM`), `NSHighResolutionCapable`, and `NSHumanReadableCopyright` when there is a copyright. Fledge writes the XML property list itself (`Fledge::Plist`).

Apple Silicon runs only signed code, and `codesign --verify --strict --deep` calls a bundle broken unless its program's signature seals `Info.plist` and every resource. The launcher arrives signed, but alone, so `fledge build` signs it again for each bundle, ad hoc (with no certificate, so no Apple Developer account): `Fledge::CodeResources` writes the seal as codesign writes it, with codesign's own rules, and `Fledge::AdHocSignature` replaces the launcher's signature with a SuperBlob of a CodeDirectory (version 0x20400, SHA-256 over 4 KiB pages, as Go's linker writes it, with the identifier, the executable segment, and special slots for `Info.plist`, the empty requirements, and the seal), the empty requirements, and an empty CMS blob, as codesign writes them, resizing `__LINKEDIT` and `LC_CODE_SIGNATURE` to fit. It runs in Ruby on any computer; a Mac and a Linux runner write the same bytes.

The launcher is not signed with the hardened runtime, so YJIT, which an app may enable (ADR 003), needs no entitlement now; a Developer ID signature with the hardened runtime, which notarization requires, will need `com.apple.security.cs.allow-jit` for it. That, and signing the Mach-O files under `Resources`, which notarization also requires, belong to Plan 002's "Signing and notarization", which will sign after this step.

### 3. On Windows, the GUI launcher, and the identity in the program's resources

A Windows runtime ships two launchers, built from the same source: `launcher.exe`, a console program, and `launcherw.exe`, a GUI-subsystem one (`-DFLEDGE_WINDOWED -mwindows`) that shows its own failures in a message box, as RubyInstaller ships `rubyw.exe` beside `ruby.exe` and PyInstaller a windowed bootloader beside its console one. A windowed app's program is `launcherw.exe` renamed; a console app's, `launcher.exe`; the other never ships. Flipping the subsystem field of one program would leave the console launcher importing USER32 and calling `MessageBoxW` for nothing.

Every Windows app, console or windowed, gets its identity in its program's resources (`Fledge::WindowsResources`): RT_VERSION, a VS_VERSIONINFO in U.S. English and Unicode whose bytes match `llvm-rc`'s for the same statement (`Fledge::VersionInfo`), with FileDescription, ProductName, and InternalName the app's name, OriginalFilename its program's, FileVersion and ProductVersion the version as written, CompanyName the publisher, LegalCopyright the copyright, and FILEVERSION and PRODUCTVERSION the version's leading numbers, at most four of 16 bits each (a part above 65535 fails the build); and, with an icon, an RT_ICON per image and an RT_GROUP_ICON listing them, numbered 32512 (IDI_APPLICATION) as Tauri numbers it. The launcher's manifest (long paths, `asInvoker`) stays as it is. `Fledge::WindowsProgram` reads the program's resource directory and writes a new resource section in place of the old one, moving the base relocations after it (`.reloc`, which nothing points into and which point only into other sections) and fixing the headers that describe them, on any computer. A program with an Authenticode signature is refused: resources change before signing, which a later step will do (decision 17).

The launcher reads `identifier` from `fledge.cfg` and, before anything else, makes it the process's AppUserModelID with `SetCurrentProcessExplicitAppUserModelID`, loaded from System32's shell32 only when there is one; a failure changes how Windows groups and names the app, never whether it runs, so it is ignored. The taskbar groups the app's windows under it and Windows attributes its notifications to it. Windows shows an app's toasts only when a Start menu shortcut carries the same `System.AppUserModel.ID`, which an installer writes: a windowed app's NSIS installer makes that shortcut (ADR 009, section 3).

### 4. On Linux, a desktop entry and icons in the folder

A windowed Linux app is the same folder as a console one, with `ID.desktop` at its top, as an AppImage's AppDir keeps it, and its icon at `share/icons/hicolor/SIZExSIZE/apps/ID.png` for 16 to 512 pixels, the layout of `$XDG_DATA_HOME`, so installing it is copying `share` into `~/.local/share` and the desktop entry into its `applications` with the program's full path. The desktop entry (`Fledge::DesktopEntry`) has `Type=Application`, `Version=1.5`, `Name`, `Exec` naming the program beside it, quoted and escaped as the specification asks (`Exec="Hello Window"`), `Icon` the identifier when there is an icon, and `Terminal=false`. `desktop-file-validate` accepts it. An AppImage comes later (Plan 002, "Windowed apps"); a console app on Linux gets no desktop entry, as terminal tools usually have none.

### 5. Icons are converted in Ruby

`Fledge::Png` reads every PNG the specification defines (each color type and depth, palettes and their transparency, Adam7) and writes 8-bit RGBA, with Ruby's zlib; `Fledge::Icon` shrinks the source by area averaging that weighs each pixel's color by its alpha, through halvings of 1024 so each step averages whole pixels, and writes an `.icns` (PNGs for `icp4`, `icp5`, `ic07` to `ic14`, and `ic10`, 16 to 1024 pixels with their Retina doubles), Windows icon images (32-bit bitmaps from 16 to 96 pixels, which every Windows reads, and a PNG at 256), and PNGs for Linux. An icon library would be a native gem that every computer building an app must compile, and `iconutil` and `sips` run only on macOS. Converting a 1024-pixel icon takes a few seconds, once per build.

### 6. Delivery reads it all back with each system's own tools

`examples/windowed_app` is a pure-Ruby app packaged as windowed, with every key of section 1, a name with a space, and an icon. It opens no window, so given a path it writes a report there (on Windows, through Fiddle, whether it has a console and what its AppUserModelID is) and exits with the status it is given. One Linux runner builds it for all four targets; Delivery checks, on a fresh runner of each, that macOS's `codesign --verify --strict --deep` accepts the bundle, `plutil` reads its identity, and it runs through `open -W` and through its own program (`.github/scripts/deliver-windowed.sh`); that Linux's `desktop-file-validate` accepts its desktop entry and its icons and program are there and run; and that on Windows its PE subsystem is GUI, `(Get-Item).VersionInfo` reads its version information, Windows extracts its icon, and `Start-Process -Wait` gets its status and a report saying it had no console and had its identifier as its AppUserModelID (`.github/scripts/deliver-windowed.ps1`). Every console app delivered on Windows must name itself in its version information too.

## Consequences

- Every Windows app shows its name and version in Task Manager and Explorer, and its icon when it has one; every windowed macOS app is a bundle with its name, icon, and identifier in the Dock and Finder; every windowed Linux app carries what a desktop needs to list it.
- A windowed app needs an identifier in `fledge.yml`, and its build fails until it has one. A version above 65535 in any part fails a Windows build.
- Windows runtimes carry `launcherw.exe`; a Windows runtime from 0.0.1.pre.5 or earlier cannot build a windowed app, and older launchers refuse a `fledge.cfg` that names an identifier, as they refuse any key they do not know.
- Fledge now writes PE resources, Mach-O signatures, property lists, and PNGs itself, each checked against the platform's own tool in tests or Delivery: `llvm-rc` for version information, codesign for signatures and seals, plutil for property lists, desktop-file-validate for desktop entries, and Windows itself for resources and icons.
- Not yet, and since done in ADR 009: a Start menu shortcut, and so toasts on Windows, from an NSIS installer; a `.dmg`; an AppImage. Not yet: Linux installation into a desktop's menus; signing with credentials and notarizing (Plan 002, "Signing and notarization"); desktop entries for console apps; a window class (`StartupWMClass`) in desktop entries, which the GUI library chooses.
