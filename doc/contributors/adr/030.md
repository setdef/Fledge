# ADR 030: Libraries a Gem Loads from the Linux Distribution

## Status
Accepted (requested). Agents wrote this ADR and may change it until 1.0 (AGENTS.md, Questions); from 1.0 the key it adds is frozen (ADR 029, section 2). It carries out Plan 003's story "Linux system libraries a gem needs", which Tokra's session raised on 2026-11-03. It amends ADR 006, section 8 (what a gem's compiled files may need), ADR 021, section 3 (a `.deb`'s `Depends`), and ADR 002, section 3 (a launcher's exit statuses), and applies decision 7 (glibc 2.39 is the floor) and the maintainer's words of 2026-10-28 (code is a liability; use the maintained tool) in `doc/contributors/decisions.md`.

## Date
2026-11-04

## Context

`Fledge::Linkage` refuses a gem whose compiled files need a library that neither the target's baseline (on glibc Linux, auditwheel's manylinux_2_39 list; on musl, its musllinux_1_2 list), nor the runtime, nor the gem provides (ADR 006, section 8). That keeps an app from failing on a computer that lacks the library, with a loader's error that names a gem (AGENTS.md, Design precedence 1). It also refuses every wrapper of a desktop library. Tokra's extension links WebKitGTK 4.1, GTK 3, libsoup 3, and JavaScriptCoreGTK 4.1, which every desktop's distribution provides, which no gem should carry (they are large, LGPL, and tied to the desktop's own GLib, D-Bus, and theme), and which the manylinux list leaves out because a server has none of them.

Prior art, read for this decision:

- **auditwheel** (6.4.2, `src/auditwheel/main_repair.py`, lines 102 to 112) repairs a Linux wheel by copying in each library outside its policy, except those `--exclude SONAME` names, which the wheel then expects of the system: "Please make sure wheel metadata reflects your dependencies." The names are sonames, as a compiled file's `DT_NEEDED` gives them.
- **delvewheel** (`delvewheel/__main__.py` at 0cf6869e, line 63) does the same for Windows wheels with `--exclude` (or `--no-dll`), DLL names.
- **Tauri's bundler** (tauri-apps/tauri at 32576120) takes Debian package names for a `.deb`, `bundle > linux > deb > depends` (`crates/tauri-utils/src/config.rs`, lines 339 and 340), and writes them into `Depends` (`crates/tauri-bundler/src/bundle/linux/debian.rs`, lines 204 to 207). Its CLI adds `libwebkit2gtk-4.1-0` and `libgtk-3-0` for the `.deb` and, for the `.rpm`, the sonames `libwebkit2gtk-4.1.so.0` and `libgtk-3.so.0` (`crates/tauri-cli/src/interface/rust.rs`, lines 1419 to 1430): one requirement, written twice, because each package format names it differently. Its AppImage bundles them: linuxdeploy runs with `--plugin gtk` (`crates/tauri-bundler/src/bundle/linux/appimage/linuxdeploy.rs`, lines 197 to 203), Tauri's fork of linuxdeploy-plugin-gtk (lines 242 to 245), and copies WebKitGTK's helper processes in by hand (lines 150 to 165).
- **Briefcase** asks for `system_runtime_requires`, "system packages that your app requires at runtime", such as `["libgtk-3-0 (>=3.14)", "libwebkit2gtk-4.1-0"]`, per distribution family (`docs/en/reference/platforms/linux/system.md` at beeware/briefcase fee777ed, lines 182 to 194). For an AppImage it offers `linuxdeploy_plugins`, `gtk` among them (`docs/en/reference/platforms/linux/appimage.md`, lines 138 to 153), and warns that "the AppImage packaging process frequently introduces bugs related to DBus integration or libraries like WebKit2 that use subprocesses" (line 55).
- **AppImage's excludelist** (AppImageCommunity/pkg2appimage at 19e30b27, `excludelist`) lists the libraries an AppImage assumes of the host and must not carry: glibc's, `libGL.so.1`, and the rest; its own notes on bundling GLib (lines 95 to 111) are a list of the symbol errors that follow.
- **Debian Policy** 8.6.1, "Generating dependencies on shared libraries": a package with compiled binaries "must run dpkg-shlibdeps on each shared library and compiled binary to determine the libraries used and hence the dependencies needed", which reads the symbols or shlibs files the libraries' own packages install. **dpkg-shlibdeps(1)** (dpkg 1.22) writes them with `-O`, takes `-x PACKAGE` to leave one out and `-l DIR` to add a folder of private libraries, and reads `debian/control` in the folder it runs in.
- **sysexits(3)**: `EX_OSFILE` (72), "Some system file ... does not exist, cannot be opened, or has some sort of error."

## Decision

### 1. `linux: system_libraries`, a list of sonames

```yaml
linux:
  system_libraries: [libwebkit2gtk-4.1.so.0, libgtk-3.so.0, libsoup-3.0.so.0, libjavascriptcoregtk-4.1.so.0]
```

Each item is a library's name as a compiled file's `DT_NEEDED` gives it, its soname: letters, digits, and `. _ + -`, ending in `.so` and its version numbers (`Fledge::Config::Linux::SONAME`, and the schema's same pattern), with no folder, listed once each (a repeat is dropped, as `installers` drops one). It is the name `fledge build` puts in the error that refuses the gem, so the developer copies it from there, and the name the loader looks for on every distribution.

Package names were considered, as Tauri's `depends` and Briefcase's `system_runtime_requires` take them, and not taken. A package name is one distribution family's, and sometimes one release's (Ubuntu 24.04 and Debian 13 renamed GLib's to `libglib2.0-0t64`); the library check reads sonames and cannot check a package name against the files; an AppImage and a `.tar.gz` have no package manager; and a later `.rpm` would need sonames again, as Tauri's two lists show. A soname is what every one of them shares, and auditwheel and delvewheel take the same kind of name. Wildcards, as auditwheel's `--exclude` allows, are not taken: a list of exact names is what the refusal of section 2 can check, and a new soname is a new ABI, which a developer should read before shipping.

The key sits under `linux`, a mapping beside `ios` and `android`, because sonames are Linux's: a Windows build's DLLs, should a wrapper need one from the system, would take `windows: system_libraries`, the same shape, without changing this one. Every other build ignores `linux`, as a desktop build ignores `ios`. It applies to glibc's Linux and musl's alike: a soname is the same on Alpine, and the check and the launcher work the same there.

`fledge.yml` is frozen at 1.0 (ADR 029), so the name is chosen to keep: `system_libraries` is the term Fledge already uses for what a system provides (`Fledge::Linkage::SYSTEM_LIBRARIES`, `runtime/licenses.yml`'s `system_libraries`), and `linux` leaves room for anything else a Linux build may need to be told.

### 2. The library check accepts what is listed, and refuses what is listed and not needed

`Fledge::Linkage` takes the list (`system:`) and lets a compiled file need any library on it. Every other library still fails, and on Linux the message now ends with the key: `Build the gem so that it carries the library, or links it statically, or, when every computer the app goes to has it from its Linux distribution, list it in fledge.yml as linux: { system_libraries: [libxml2.so.2] }.`

A listed library that no gem's compiled file needs beyond what the baseline, the runtime, and the gems provide fails the build too (`Linkage#unused`), as Plan 003 asks: `fledge.yml's linux: system_libraries lists libgtk-3.so.0, which none of the gems' compiled files needs beyond what every Linux distribution, Fledge's runtime, and the gems themselves provide. Remove it.` A list that says only what is true keeps a `.deb` from depending on a package nothing loads, and a launcher from refusing a computer that would have run the app. It also means the list cannot name what a gem opens with `dlopen` (SDL's X11 and Wayland): no compiled file names those, so nothing can check them, and they stay the desktop's, as ADR 021 says.

### 3. A `.deb` depends on what dpkg-shlibdeps finds for them

With libraries listed, `Fledge::Deb` reads the compiled files in the package's tree (`Fledge::Binary`, with objdump), picks those that need a listed library, and runs `dpkg-shlibdeps -O -xlibc6 -lDIR... -eFILE...` on them in its work folder, with an empty `debian/control` there and the tree's `DEBIAN` folder beside its files, so dpkg-shlibdeps takes them as a package's. Its `shlibs:Depends` follows `libc6 (>= 2.39)` in `Depends`: for `examples/system_library`, built on Ubuntu 24.04, `libc6 (>= 2.39), libpng16-16t64 (>= 1.6.2)`. glibc's own entry is left out (`-xlibc6`), since the runtime's floor already names it; any other package those files need comes with it. With nothing listed, `Depends` stays `libc6 (>= 2.39)` and dpkg-shlibdeps never runs, so a `.deb` that built before still builds, on a computer without dpkg-dev.

This is Debian Policy 8.6.1's own procedure, with Debian's own tool, which maps each soname to the package that provides it on the computer that built the gem and gives the oldest version whose symbols the files use. The alternatives were worse:

- **The developer's package names** beside the sonames, as Tauri and Briefcase take them: two lists to keep in step, with no check that they agree, and a version a developer would guess.
- **`dpkg -S`** on each library's path: in dpkg, which every Debian has, but it answers only which package owns a file, so Fledge would find the path itself (the loader's search, `/usr/lib` against `/lib` on a merged `/usr`, multiarch folders) and give no version. That is the part of dpkg-shlibdeps Fledge would rewrite.
- **apt-file**: a database of every package's files in the archive, not of what is installed, so it would name a package for a library the build computer does not have, and it needs its own download.

dpkg-shlibdeps is in dpkg-dev, which build-essential brings and every computer that compiles a gem on Debian or Ubuntu has; a computer without it is told `Install dpkg-dev, which has it, such as with sudo apt install dpkg-dev (build-essential brings it).` A `.deb` built on Ubuntu 24.04 names Ubuntu 24.04's packages, which Debian 13 has under the same names for every library CI tries; a library whose package is named differently in another distribution (libjpeg's `libjpeg-turbo8` and `libjpeg62-turbo`) makes a `.deb` for the distribution it was built on, which is what Debian's own packages are.

### 4. An AppImage, and the `.tar.gz`, expect them on the host, and the app says which is missing

An AppImage does not bundle the listed libraries in this version. Bundling WebKitGTK, as Tauri does, means linuxdeploy and its GTK plugin, both downloaded tools Fledge does not use today; WebKitGTK's helper processes, GTK's modules, loaders, and schemas, copied by hand as Tauri copies them; tens of megabytes; the D-Bus and subprocess bugs Briefcase warns of; and the excludelist's GLib problems, since GTK and GLib must come together. It would also put LGPL libraries in the AppImage, which AGENTS.md's Licensing allows only as separate, replaceable shared libraries with their source published beside the runtime, and these would be the app's, not the runtime's, so the source would be for each developer to publish for each app, a duty Fledge would then have to explain and check. That is more cost than the first version of the key is worth. The AppImage, like the `.tar.gz`, runs on a desktop that has the libraries, as AppImage's excludelist expects `libGL.so.1` and glibc of the host.

A computer that lacks one must not meet a gem's `LoadError`. So `fledge build` writes the list into `fledge.cfg` (`system_libraries = libwebkit2gtk-4.1.so.0 libgtk-3.so.0`, above any program's section), and the Linux launcher, before Ruby starts, has the loader look for each (`fledge_find_system_libraries`, `runtime/launcher/linux.c`). It asks in a child process, which `dlopen(3)`s each with `RTLD_LAZY | RTLD_LOCAL` and exits, so the app's own process loads nothing early and runs as it would under `ruby main.rb`: a library's constructors run when the gem loads it. On the first that fails it prints, and exits with `EX_OSFILE` (72):

```
System Library: this app needs libpng16.so.16, which this computer does not have (libpng16.so.16: cannot open shared object file: No such file or directory). Install it from your Linux distribution's packages, then run the app again
```

The message names a library, which a person installs from a software center, and never Ruby or a gem. A computer that cannot fork or make a pipe skips the check, and the gem's own loading decides, as it would have. The `.deb` gets the check too, where `apt` has already met it.

## Consequences

- A wrapper of a desktop library ships on Linux: its developer lists the sonames the build's error names, `apt` installs their packages with the `.deb`, and an AppImage or archive on a computer without them says which to install.
- `examples/system_library` is the acceptance test: a path gem whose C extension links libpng, which Debian and Ubuntu leave out of a bare system. CI builds it on glibc Linux, checks the `.deb` depends on `libpng16-16t64`, installs it with `apt` in fresh `debian:trixie-slim` and `ubuntu:24.04` containers, which have no libpng until `apt` brings it, runs it, runs the `.tar.gz` and the AppImage in a fresh container without libpng and expects status 72 and the library's name, and builds it with the key removed and expects the refusal that names the key.
- A launcher's exit statuses gain 72, on Linux (ADR 002, section 3; ADR 029, section 2).
- Building a `.deb` with libraries listed needs dpkg-dev and binutils' objdump, which a computer that compiles gems has.
- Not yet: bundling the listed libraries into an AppImage, with linuxdeploy's plugins, for a developer who asks; `windows: system_libraries`; a `.rpm`, whose `Requires` would take the sonames as they are; and libraries a gem opens with `dlopen`, which nothing can check.
