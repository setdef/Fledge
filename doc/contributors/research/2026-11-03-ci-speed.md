> Analysis by an agent session on 2026-11-03, from GitHub's job timings of Fledge's CI and release runs, two pairs of local runtime builds on an Apple-silicon Mac, and the runtime artifacts of two CI runs of the same runtime source. Requested: written by an agent and not reviewed line by line. Nothing here changes code, workflows, or rules; section 5 says which recommendations would change ADR 014 or AGENTS.md, and those changes wait for the maintainer.

# Why a release takes hours, and how to make CI faster without weakening a gate

## Short answer

A push to `trunk` takes a median of 33 minutes of wall-clock time (seven full runs, 29 to 55 minutes), and its critical path is the iOS chain: `Runtime (ios)`, about 12 minutes, then `Mobile apps (iOS Simulator, iPhone and iPad)`, 15 to 21 minutes. The Windows chain, `Build (x64-mingw-ucrt)` at 22 to 24 minutes followed by its Delivery, is a close second. When a run is slow, the extra time is almost always macOS queue: 10 to 27 minutes in three of the seven runs.

A release takes 88 to 119 minutes when nothing fails, because it runs all of CI three times in a row: on the release commit, on the pin commit, and on the pin commit again inside `release.yml`. The third run tests the same commit the second one already tested, and throws its runtimes away (ADR 014, Consequences). 0.2.0 was never published. Its third run failed on a download from `musl.libc.org` in a job unrelated to the runtimes it would have published, and so did its re-run.

The runtimes are much closer to reproducible than ADR 014 assumed. Across two CI runs of the same runtime source, every file inside the desktop glibc and macOS runtimes was byte-identical except the SBOM's `created` date. Every remaining difference traces to one of four causes, each fixable with a setting the tools already have: archive metadata (mtimes, owners, on macOS the gzip timestamp and extended attributes), `SOURCE_DATE_EPOCH` taken from HEAD instead of from the runtime's inputs, no `SOURCE_DATE_EPOCH` at all in the mobile job, and `ar` dates in the iOS library. Repacking two local builds with those settings gave identical bytes for `arm64-darwin` and for `x64-mingw-ucrt`.

The largest saving needs no reproducibility. If `release.yml` checks that the tagged commit already has a green CI run, instead of running CI again, each release saves about 28 minutes and avoids one chance to fail on a flake. If a pin-only commit then runs only the jobs a pin can affect, a release drops to about 45 minutes. Both change ADR 014's rules.

## What was measured, and what was not

Measured:

- Job timings from the REST API (`gh api repos/setdef/Fledge/actions/runs/RUN/jobs?filter=latest`), which gives each job's `created_at`, `started_at`, and `completed_at`. Queue time is `started_at - created_at`; run time is `completed_at - started_at`. Full push runs on `trunk`: 41649344171, 41591463741, 41584541749, 41557715929, 41548182485, 41534087536, 41429073210 (all attempt 1, all green). Pin commits: 41397046913, 41433966954, 41596806895. Release runs: 41399910853 (0.0.1.pre.17), 41439991871 (0.1.0), 41600809633 (0.2.0, failed).
- Step timings of the slowest jobs, median over those seven push runs, and the timestamps in the iOS Simulator job's log from run 41649344171.
- Two `arm64-darwin` runtime builds in different folders, a third in the folder of the first, and two `x64-mingw-ucrt` builds, all on this Mac with `SOURCE_DATE_EPOCH=1793714315` (the commit time of 3b136be) and cached downloads. Each `arm64-darwin` build took 15 to 18 seconds, and each `x64-mingw-ucrt` build 55 to 84 seconds.
- The `runtime-*` artifacts of run 41591463741 (the 0.2.0 release commit, f89006d) and run 41596806895 (its pin commit, addaa55), which were built from identical runtime source, compared archive by archive, entry by entry, and byte by byte.

Not measured:

- No Linux, musl, iOS, or Android runtime was built locally; what this page says of them comes from the two CI runs' artifacts and the build scripts.
- No fix was tried in CI. The repacking experiment ran on this Mac's bsdtar only; the GNU tar options for Linux come from reproducible-builds.org and were not run.
- Runner image drift: both CI runs compared here ran on the same day, presumably on the same images. Builds on different image versions were not compared.
- The 0.2.1 release was still in progress when this was written: its release commit's CI run, 41656379469, was queued at 14:42:43Z and running when this page was committed, so it is not in the tables.
- The cause of the macOS queue is inferred, not observed. GitHub's documented limit for the Free plan is 5 concurrent macOS jobs out of 20 (https://docs.github.com/en/actions/reference/limits), shared by every repository and workflow of the account. One CI run asks for 9 macOS jobs (7 on `macos-15`, 2 on `macos-26`). This page did not check which plan the organization is on.

## 2. Why the runtimes are not reproducible

ADR 014 assumed the bytes differ because "each runner's own tar writes the archives, with the time of the build in them, and the launcher is compiled on each runner." CI already sets `SOURCE_DATE_EPOCH` to HEAD's commit time for the desktop and musl runtime jobs (`ci.yml`, `Build the runtime`), and the SBOM honors it (`tasks/license_audit/spdx.rb`, line 24). But `Fledge::Archive.pack` runs a plain `tar -czf`, which ignores it.

### What differs between two CI runs of the same source

Runs 41591463741 and 41596806895 built every runtime from the same files; the only difference between f89006d and addaa55 is `lib/fledge/SHA256SUMS`, which no runtime contains. Every `.tar.gz`, `-dev.tar.gz`, `-lgpl-sources.tar.gz`, and `.spdx.json` differed; every `-NOTICES.txt` was identical. Inside the archives, entry names and order were the same on every platform. File contents that differed:

| Platform | Files whose bytes differ, besides `notices/sbom.spdx.json` | Cause |
|---|---|---|
| arm64-darwin | none: the launcher, `bin/ruby`, and every library match, codesign's ad hoc signature included | |
| x86_64-linux, aarch64-linux | none: the launcher and libxcrypt match | |
| x64-mingw-ucrt, aarch64-mingw-ucrt | `launcher.exe`, `launcherw.exe`: 2 bytes each | The PE header's TimeDateStamp, which lld set to `SOURCE_DATE_EPOCH`: 1793688075 (06:41:15Z, f89006d's commit time) against 1793691048 (07:30:48Z, addaa55's) |
| x86_64-linux-musl, aarch64-linux-musl | `openssl.so`: 25 bytes | OpenSSL's `built on:` string, which `util/mkbuildinf.pl` (OpenSSL 3.6.5, lines 17 to 19) takes from `SOURCE_DATE_EPOCH`, and the GNU build ID, which hashes it |
| ios | `libfledgeruby.a` (device and simulator): 6372 bytes | Each of 1447 `ar` members' date field (file mtimes at build time), and one member, `libcrypto-lib-cversion.o`, whose `built on:` is the build's wall clock time: the mobile job sets no `SOURCE_DATE_EPOCH` |
| android | `FledgeRuby.aar`: two members, `jni/*/libfledgeruby.so`, 518,917 bytes of 16,402,456 | Again only OpenSSL's `built on:` (06:46:55Z against 07:35:34Z). `strings` finds no other difference; lld's string merging lays `.rodata` out differently around the changed string, which moves code and relocations (453,875 bytes differ in `.rodata`, 50,686 in `.text`, 14,356 in `.rela.dyn`). Gradle already writes every AAR entry with a fixed 1980-02-01 timestamp |

Every platform's SBOM differs in one line, `"created"`, because `SOURCE_DATE_EPOCH` is HEAD's commit time and the two commits were made 49 minutes apart. The mobile SBOMs use the wall clock.

Archive metadata that differed:

- Every entry's mtime: the time the builder wrote the file. Files copied with their times from rv-ruby's or RubyInstaller's archives keep 1970-01-01 or their upstream dates; the rest carry the build's minute.
- The gzip header's MTIME on macOS (bsdtar writes the time it ran). On Linux it is already 0: GNU tar pipes into gzip.
- Owner names: `runner`/`staff` on macOS, `runner`/`runner` and `root` on Linux, `root` in Alpine. They are stable on a given runner and differ elsewhere.
- Locally only: bsdtar stored each file's `com.apple.provenance` extended attribute in a pax header (3337 of them in a 6674-entry archive). The CI runner's files had none.
- Entry order was the same in both runs, but it is the order the file system lists folders in, which nothing guarantees (reproducible-builds.org, "Archive metadata", https://reproducible-builds.org/docs/archives/).

### What two local builds showed

Two `arm64-darwin` builds, in two folders, with one `SOURCE_DATE_EPOCH`: the NOTICES, the SBOM, and every file inside the archive were identical, the launcher included, even though it was compiled in a different folder. The archives differed only in the metadata above. Repacking each build's stage folder with bsdtar 3.5.3, entries in byte order (`-n -T` with a sorted list), every mtime set to `SOURCE_DATE_EPOCH` with `File.lutime`, `--uid 0 --gid 0 --uname "" --gname ""`, `--no-xattrs --no-mac-metadata --no-acls --no-fflags`, and `--options gzip:!timestamp` (bsdtar(1), "gzip:timestamp") gave byte-identical archives (SHA-256 c1793583…). The same repacking of two `x64-mingw-ucrt` builds also gave identical archives (82c37694…): with one `SOURCE_DATE_EPOCH`, the two launchers were identical too.

### Each cause, its fix, and its cost

| Cause | Fix with a maintained tool or setting | Work |
|---|---|---|
| Entry mtimes, order, owners, in every runtime, companion, and LGPL source archive | GNU tar (Linux runners, Alpine's pinned `tar=1.35-r5`): `--sort=name --mtime="@${SOURCE_DATE_EPOCH}" --clamp-mtime --owner=0 --group=0 --numeric-owner --pax-option=exthdr.name=%d/PaxHeaders/%f,delete=atime,delete=ctime`, as reproducible-builds.org gives it. macOS's bsdtar 3.5.3 has no `--sort` or `--mtime` (checked in `man bsdtar`), so set mtimes first and pass a sorted list with `-n -T`, as the experiment did | Small. `ReleaseArchive.pack` (`tasks/release_archive.rb`) and `LicenseAudit::SourceBundle` call `Fledge::Archive.pack`, which also packs developers' apps; giving the release tasks their own packing keeps apps as they are |
| gzip timestamp on macOS | `--options gzip:!timestamp` (bsdtar), or `gzip -n` in a pipe | Trivial |
| macOS extended attributes | `--no-xattrs --no-mac-metadata` | Trivial; it matters on developers' Macs, not on the runner |
| `SOURCE_DATE_EPOCH` is HEAD's commit time, so the release and pin commits get different SBOM dates, PE timestamps, and OpenSSL strings | Take the commit time of the last commit that changed anything but `lib/fledge/SHA256SUMS`: HEAD's, or HEAD^'s when HEAD changes only the pins. `git log -1 --format=%ct -- . ':(exclude)lib/fledge/SHA256SUMS'` needs history; the checkout's default depth of 1 makes HEAD a root commit and silently returns HEAD's time, so the runtime jobs would need `fetch-depth: 2` | Small, in `ci.yml` |
| The mobile job sets no `SOURCE_DATE_EPOCH` | Set it as the other runtime jobs do | Trivial |
| `ar` member dates in the iOS library | `ZERO_AR_DATE=1` for `xcrun libtool -static` and `xcrun ar -d` (`tasks/runtime_builder/ios.rb`, lines 117 and 118). Tried here: two `libtool -static` runs two seconds apart, and two `ar -d` runs, each gave identical archives with it and different ones without | Trivial |
| Compilers not pinned by the build: the macOS launcher uses the runner image's default `clang`, the Linux launcher the image's `gcc` | Not fixable by a setting. llvm-mingw, the NDK, Xcode for iOS, and the Alpine image are pinned; the macOS and Linux desktop compilers change when GitHub updates an image. Two runs on different images may differ; a check that compares bytes has to say so instead of failing mysteriously | Nothing to do; a known limit |

With the first six fixes, the evidence above predicts identical bytes for every runtime from two CI runs on the same images. That prediction was tested for `arm64-darwin` and `x64-mingw-ucrt` only, and only locally.

## 3. Alternatives that need no reproducibility

ADR 014 already publishes the release commit's runtimes, never rebuilt ones: `release.yml` downloads the artifacts of the parent's CI run and checks them against the pins. The later builds are checks, not sources of bytes. What each full run protects against:

1. **The release commit's CI** builds the runtimes that ship and delivers apps made from them on fresh runners. Nothing replaces it.
2. **The pin commit's CI** keeps AGENTS.md's rule that only a commit whose CI is green on every job is tagged. The pin commit differs from its parent only in `lib/fledge/SHA256SUMS`, which `release.yml` enforces. In CI, every job that builds an app uses `FLEDGE_RUNTIME_DIR`, whose runtimes `Fledge::Runtimes` does not check against the pins (ADR 014, section 1), so the file is read only by the gate: `test/runtime_pins_test.rb` line 64, `test/runtimes_test.rb` line 164, and the package check. The rest of that run tests bytes it then throws away.
3. **`release.yml`'s CI** guards against a tag on a commit that never passed CI. It tests the same commit as run 2. Its runtimes are thrown away (ADR 014, Consequences). Its jobs cannot catch anything run 2 missed, except a change in the world between the two runs: a gem server, a mirror, a runner image. It also re-draws every flake; 0.2.0 shows the cost.
4. **`installed.yml`** installs Fledge from the tag and delivers the examples with the published runtimes. It is the only check of what a developer downloads, and it takes 5 to 8 minutes.

Options, each keeping run 1 and `installed.yml`:

- **A. Replace `release.yml`'s CI job with a lookup.** Before publishing, require that the tagged commit has a successful CI run on `push` to `trunk` (the same `gh run list --commit --status success` query `release.yml` already makes for the parent), and refuse otherwise. Saves 26 to 28 minutes per release and one exposure to flakes. The rule "tag only a commit whose CI is green" stays true; the check moves from re-running to looking it up.
- **B. Run a pin-only commit's CI as a short job set.** A first job reads `git diff --name-only HEAD^ HEAD` (with `fetch-depth: 2`); when the only change is `lib/fledge/SHA256SUMS`, only the gate runs, plus one new job that downloads the parent's runtime artifacts and checks them against the pins, as `release.yml` does. Every other job gets an `if:` that skips it. Saves about 25 minutes per release. GitHub reports a skipped job as successful for required checks, so "green on every job" would then mean "green on every job that ran" for this one kind of commit; AGENTS.md would say so in words. `on.push.paths` cannot do this: it skips the whole workflow, and `release.yml`'s lookup would find no run.
- **C. Tag the release commit itself.** This is impossible under ADR 014: the tagged gem has to carry the pins, the pins can only be written once the runtimes exist, and the runtimes carry the version in their names and NOTICES. Two commits remain; three full runs do not.

A and B together make a release one full CI run (about 33 minutes), a gate-and-pins run (about 3 minutes, the gate's median plus a download), publishing, and `installed.yml`: about 45 minutes plus the minutes between pushes, against 88 to 119 measured.

Reproducible runtimes add something different: with them, the pin commit's run (or anyone, later) could rebuild the runtimes and compare them with the pins, which proves the published bytes come from the tagged source instead of relying on "the pin commit changes nothing else". That is a stronger check, not a faster one. It also makes the cache in section 4 invisible, since a cache hit then returns the bytes a rebuild would have made.

## 4. Cutting queue time and compute without money

The repository is public, so GitHub-hosted minutes cost nothing. What limits throughput is the macOS concurrency limit and the length of the two chains.

| Option | Saving | Effect on gates |
|---|---|---|
| **Boot both simulators while the apps build.** `tasks/mobile_parity/ios.rb` builds the simulator apps, then creates and boots the iPhone, runs it, deletes it, then creates and boots the iPad. Boot takes about 6 minutes each (14:23:45 to 14:29:44 for the iPad in run 41649344171). Creating and booting both devices in the background before the device and simulator builds (about 9 minutes, the first boot included) overlaps both boots with those builds. The log does not separate the simulator builds from the iPhone's boot, so how much of the 7.9 minutes is boot was not measured | 6 minutes (the iPad's boot) to about 10, off the critical path; no extra runner | None: the same apps on the same devices. The risk is memory pressure from two simulators on one runner, which would show up as new timeouts |
| **Split the iOS Simulator job by device** (matrix of iPhone and iPad), instead of the above | About 8 minutes | None, but one more `macos-26` job per run, against a 5-job macOS limit |
| **Cache the host bundles of the examples** in `Build (x64-mingw-ucrt)`'s `Run the examples with bundle exec` (8.9 minutes, mostly compiling nokogiri for the runner's Ruby to print the expected output), keyed on each `Gemfile.lock` and the Ruby version | About 7 minutes off the Windows chain | None. The `.expected` files come from the host's `bundle exec`, not from Fledge. `Build nokogiri_app from source` (7.8 minutes) is the gate itself (ADR 006) and stays uncached |
| **Cache runtime builds keyed on their inputs**: the hash of every file the builder reads (`runtime/`, `tasks/runtime_builder*`, `tasks/license_audit*`, `lib/fledge/version.rb`, `lib/fledge/platform.rb`, `lib/fledge/runtimes.rb`, `lib/fledge/archive.rb`, the Alpine digest, the Xcode version), plus `ImageOS` and `ImageVersion` | Runtime (ios) 11 to 12 minutes off the critical path on every push that changes none of them (most pushes are docs, tests, or `lib/`); Runtime (android) and the musl runtimes 6 to 7 minutes each, off the chains that wait on them | ADR 004's license audit ran when the cached runtime was built and travels inside it. The risk is a key that misses an input, which would test a stale runtime. Listing inputs by hand is how that goes wrong; hashing `git ls-files` of whole folders is safer. A cache that skips the build also skips the `-Werror` compile and the analyzer, which only matter when their inputs change. GitHub's cache holds 10 GB per repository; the runtimes are 22 to 78 MB each |
| **Split `needs: build` per platform**, so each platform's Delivery waits for its build only. GitHub Actions cannot depend on one matrix leg, so this means one Build job and one Delivery set per platform, or a reusable workflow per platform | Up to 15 minutes for Mac and Linux Delivery, which today waits for Windows; it removes the macOS queue that landed on the critical path in runs 41534087536 and 41429073210 | None |
| **Shard the Windows tests** across two jobs each | About 6 minutes on two jobs that are not on the critical path | None, but four more Windows jobs per run; not worth it until the other chains are shorter |
| **Path filters for ordinary pushes** (a docs-only commit skips the platform jobs) | Up to the whole run for docs commits | This weakens what "trunk is green" means: a docs commit that changes `exe/fledge`'s help header, examples, or a page `tasks/licensing_page.rb` checks would skip jobs that read it. Not recommended beyond option B's single, exact case |

With the first, third, and fourth options, the iOS chain would drop to about 15 minutes, and the Windows chain to about 20, which would then set the pace: a push would take about 20 minutes on a quiet day instead of 33. That figure is an estimate from the step timings above, not a measurement.

## 5. Recommendation, ranked by saving per effort

1. **Look up the tagged commit's CI run in `release.yml` instead of running CI again** (option A). Saves 26 to 28 minutes per release and removes the failure that stopped 0.2.0. About twenty lines of YAML. The rule that the tagged commit's CI is green is unchanged; what goes is the re-run after the tag, so a change in the outside world between the pin commit's run and the tag goes unseen until `installed.yml`, which still runs. **This changes ADR 014, section 2, step 3, and the header of `release.yml`; tell the maintainer.**
2. **Overlap the simulators' boot with the builds in the iOS job.** Saves 6 to 10 minutes on every push. A small change to `tasks/mobile_parity/ios.rb`. No gate changes. If two booted simulators prove flaky, split the job by device instead.
3. **Give a pin-only commit a short CI: the gate and a check of the pins against its parent's runtimes** (option B). Saves about 25 minutes per release. A first job and an `if:` on each other job. **This changes AGENTS.md, Releasing ("Tag only a commit whose CI is green on every job"), and ADR 014, section 2, step 2; tell the maintainer, and say that skipped jobs count as green.** With 1, a release takes about 45 minutes.
4. **Make the runtimes reproducible**: clamp, sort, and strip owners in the release archives; take `SOURCE_DATE_EPOCH` from the last commit that changed anything but the pins; set it in the mobile job; `ZERO_AR_DATE=1` for the iOS library. Saves no time by itself. A day's work, most of it in testing on each platform. It turns option B's trust in "the pin commit changes nothing else" into a byte-for-byte check, lets anyone rebuild a release and compare it, and makes 5 safe. **It fulfils ADR 014's last Consequence ("Reproducible runtime builds ... stay open"); tell the maintainer if a check that fails on a mismatch is added, since a runner image update between two runs would then fail a release.**
5. **Cache runtime builds keyed on their inputs and the runner image.** Saves about 11 minutes on most pushes, more when macOS queues. Moderate work, most of it in choosing the key. No rule changes, but the key needs a test that fails when a builder input is left out of it.
6. **Cache the examples' host bundles in the Windows build** (7 minutes off the Windows chain) and **split `needs: build` per platform** (removes Windows' wait from Mac and Linux Delivery). Together they make the Windows chain no longer the limit once 2 and 5 are done. No gate changes.

Not recommended: path filters for ordinary pushes, which would let a commit skip jobs that read the files it changes, and caching anything `fledge build` compiles, which is what Delivery proves.
