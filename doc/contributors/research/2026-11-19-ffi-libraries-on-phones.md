> Findings of 2026-11-19 on how a gem whose build makes a library for Ruby's ffi to load can work in an iOS and an Android app Fledge builds. Requested: written by an agent and not reviewed line by line. It changes no code, no test, and no design document; the orchestrator decides.

# ffi Libraries on Phones

The ffi gem itself works on both phones: its `extconf.rb` builds its extension and the libffi it bundles, and Fledge compiles them as any extension (`doc/contributors/design/phone-projects.md`, "Gems with extensions", paragraph "The ffi gem"). A gem that builds a library of its own for ffi to open does not. `MobileExtensions::RakeBuild` refuses any shared library a Rakefile leaves that mkmf did not make (`lib/fledge/mobile_extensions/rake_build.rb`, lines 179 to 186), and `test/integration/mobile_extensions_build_test.rb`, `test_a_library_for_ffi_a_rakefile_links_is_refused_by_name`, holds that refusal. The maintainer ruled on 2026-11-12: "*Governs:* gems whose libraries Ruby's ffi loads work on iOS and Android, and fiddle is in the iOS runtime, unless checked sources show App Review or iOS forbids them; the reason to leave either out must be cited, not assumed."

`phone-projects.md` names three things Fledge would have to do: install the Rakefile's build dependencies for this computer, wrap the iOS library in a framework, and make the path the gem gives `ffi_lib` reach it. These findings test those three claims against five gems' source, ffi's own, Apple's and Google's text, and what CPython and Chaquopy do, and propose a design.

## Verdict

No source read forbids it on either phone, and all three claims hold, each with a correction.

- **Every gem read gives `ffi_lib` an absolute path inside its own folder,** and ffi hands that path to `dlopen` unchanged. So an unmodified gem works when a loadable library answers `dlopen` at that path. On both phones the answer is a symbolic link at the path the desktop build leaves the file, to a library where the phone lets an app keep one.
- **On Android that is already built.** Fledge carries each C extension an `extconf.rb` builds as `jniLibs/ABI/libfledgeext.FEATURE.so`, and the runtime links it at the desktop's path from `fledge.links` as the app starts (`phone-projects.md`, "Linking extensions on Android"). A library for ffi can take the same road with no new runtime code.
- **On iOS it needs a framework per library,** embedded and signed in the app's `Frameworks` folder, because Apple says iOS does not support a standalone dynamic library. No library read here calls Ruby, so none needs Ruby itself as a dynamic framework. That cost sank loading extensions from files on iOS (`doc/contributors/research/2026-11-13-phone-extensions-as-files.md`), and it does not apply here.
- **The build needs the Rakefile's own gems,** among them ffi compiled for this computer, on the load path of every Ruby the build starts. RubyGems' activation does not reach them, since that Ruby reads the phone's `rbconfig.rb`.

Three things only a run can settle, and two of them need the maintainer's devices or account: whether iOS loads a library through a link inside the bundle, whether it loads one that ffi-compiler links as a Mach-O bundle rather than a dynamic library, and whether App Store Connect accepts either.

## 1. What such gems do

| Gem | Built by | Build-time gems | Where the library lands | How its Ruby finds it |
|---|---|---|---|---|
| llhttp-ffi 0.5.1 | `ext/Rakefile`, ffi-compiler | ffi-compiler, ffi, rake | `ext/ARCH-OS/libllhttp-ext.SUFFIX` | `FFI::Compiler::Loader.find`, a path |
| scrypt 3.1.0 | `ext/scrypt/Rakefile`, ffi-compiler | ffi-compiler, ffi, rake | `ext/scrypt/ARCH-OS/libscrypt_ext.SUFFIX` | `Loader.find`, a path |
| webp-ffi 1.0.0 | `ext/webp_ffi/Rakefile`, ffi-compiler | ffi-compiler, ffi, rake | `ext/webp_ffi/ARCH-OS/libwebp_ffi.SUFFIX` | `Loader.find`, a path |
| rdkafka 0.31.0 | `ext/Rakefile`, mini_portile2 and librdkafka's `configure` | mini_portile2, rake | `ext/librdkafka.dylib` or `ext/librdkafka.so` | `ffi_lib` of that path |
| sassc 2.4.0 | `ext/extconf.rb`, mkmf | none | `lib/sassc/libsass.DLEXT` | `ffi_lib` of that path |

**ffi-compiler** (1.4.3; 1.3.2 differs only in also compiling `.m` files). `CompileTask` takes the compiler from `ENV['CC'] || RbConfig::CONFIG['CC']`, and `CXX` the same way (`lib/ffi-compiler/compile_task.rb`, lines 262 to 268). It takes `CFLAGS`, `CXXFLAGS`, and `LDFLAGS` from the environment in place of its defaults (lines 56 to 58). Where `FFI::Platform.mac?` it links with `-bundle`, and elsewhere with `-shared` (lines 110 to 123; the branch for `/linux/` on line 117 never runs, since `FFI::Platform.name` is Ruby's `Module#name`, `"FFI::Platform"`, and that branch would raise `NameError`, naming `lib_name` before line 133 assigns it). It writes the library into a folder named `ARCH-OS`, from ffi's own `FFI::Platform::ARCH` and `OS`, under the task's folder (lines 125 to 133), and names it `lib` plus the task's name plus `bundle` on a Mac or ffi's `LIBSUFFIX` elsewhere (`lib/ffi-compiler/platform.rb`, lines 3 and 9 to 11). The file requires `ffi` (`compile_task.rb`, line 4), so the build loads ffi's compiled extension on the computer that runs it. A task with `export` runs Ruby again with ffi-compiler's own stand-in for ffi, `fake_ffi`, to write a C header (lines 185 to 196). It ignores `RUBYARCHDIR`, so the library stays in the gem's folder, outside its require paths.

At run time `FFI::Compiler::Loader.find(name)` returns a path: first `spec.extension_dir` joined to the library's name, when an active gem holds the caller and that file exists; then the first match of `**/ARCH-OS/LIBRARY`, then of `**/LIBRARY`, under the caller's folder and each folder above it, up to the gem's root (`lib/ffi-compiler/loader.rb`, lines 8 to 35).

**llhttp-ffi.** The Rakefile is two lines: `require "ffi-compiler/compile_task"` and `FFI::Compiler::CompileTask.new("llhttp-ext")` (`ext/Rakefile`, lines 3 and 5). `lib/llhttp.rb` calls `ffi_lib(FFI::Compiler::Loader.find("llhttp-ext"))` (line 13). The gemspec names `ext/Rakefile` as its one extension and ffi-compiler and rake as runtime dependencies. The package also holds an `ext/llhttp/extconf.rb` it does not name, and a library its author built on a Mac: `ext/aarch64-darwin/libllhttp-ext.bundle` (`file` says "Mach-O 64-bit bundle arm64") and four object files beside it. On iOS, ffi's `OS` is `darwin` and its `ARCH` `aarch64`, so the build writes its own library at exactly that path.

**scrypt.** The Rakefile adds flags by what `RbConfig` and ffi's platform say: `-msse -msse2` when the architecture contains `86`, `-D_POSIX_C_SOURCE=200809L` when `host_os` matches `linux`, and an `export` of `lib/scrypt/scrypt_ext.rb` (`ext/scrypt/Rakefile`, lines 3 to 21). `lib/scrypt/scrypt_ext.rb` calls `ffi_lib FFI::Compiler::Loader.find('scrypt_ext')` (line 11).

**webp-ffi.** The Rakefile calls `WebPFFI::BuildConfig.define_tasks('webp_ffi')` (`ext/webp_ffi/Rakefile`, lines 1 to 3), which checks for libwebp, libpng, libjpeg, libtiff, and zlib, adds Homebrew's and MacPorts' folders (`build_config.rb`, lines 14 and 19 to 26), and then runs ffi-compiler (lines 57 to 68). On a phone those libraries would have to be the developer's own builds for the phone, as for any gem that links a system library; nothing here is special to ffi.

**rdkafka.** The Rakefile's default task builds librdkafka from the tarball the gem carries with mini_portile2, configured `--host=#{recipe.host}`, which mini_portile2 takes from `RbConfig`, and moves `librdkafka.1.dylib` or `librdkafka.so.1` to `ext/librdkafka.dylib` or `ext/librdkafka.so` (`ext/Rakefile`, lines 16 to 17, 32, 43, and 45 to 53). On a Mac with Homebrew it points `CPPFLAGS` and `LDFLAGS` at Homebrew's OpenSSL unless they are set (lines 21 to 24). `lib/rdkafka/bindings.rb` calls `ffi_lib File.join(__dir__, "../../ext/librdkafka.#{lib_extension}")`, `dylib` when `host_os` matches `darwin` (lines 19 to 29).

**sassc.** Its `extconf.rb` is mkmf's, but what it builds is no extension: it compiles libsass, sets `$LIBRUBYARG = nil` ("Don't link libruby"), drops the export file that would name an `Init_libsass` "which we don't have", and calls `create_makefile 'sassc/libsass'` (`ext/extconf.rb`, lines 72 to 78 and 92). `lib/sassc/native.rb` calls `ffi_lib File.expand_path("libsass.#{dl_ext}", __dir__)` with mkmf's `DLEXT`, and on `LoadError` the same name in `ext/` (lines 9 to 14). So a library for ffi can come from an `extconf.rb` too, where Fledge takes it for an extension.

**RubyGems.** `Gem::Ext::RakeBuilder` runs `ruby -rrubygems RAKE RUBYARCHDIR=DEST RUBYLIBDIR=DEST` in the extension's folder (`lib/rubygems/ext/rake_builder.rb`, lines 22 to 35), and nothing copies what the Rakefile builds anywhere else. So on a desktop these libraries stay where the build wrote them, inside the gem's folder. `Gem::Package#extract_files` sets no file's modification time (`lib/rubygems/package.rb`, `extract_tar_gz`, lines 514 to 560), so files get the time they were unpacked, in the archive's order.

## 2. What each phone allows

### iOS

Apple's "Placing content in a bundle" puts a "framework, dynamic library" in `Frameworks/` on "iOS, tvOS, visionOS", and says: "iOS, watchOS, and tvOS support third-party frameworks but don't support third-party standalone dynamic libraries, which are those outside a framework bundle, typically with the .dylib filename extension." It also says "iOS and tvOS support frameworks and Swift system libraries at the topmost app level; a nested bundle, like an app extension, can't include a framework." That is the only rule found on where a library may sit. It bears on packaging. It does not forbid loading one.

App Review Guideline 2.5.2: "Apps should be self-contained in their bundles, and may not read or write data outside the designated container area, nor may they download, install, or execute code which introduces or changes features or functionality of the app, including other apps." A library the app builds and ships in its bundle is self-contained there, and nothing is downloaded. Guideline 2.5.1 asks for public APIs, and `dlopen` is one (`doc/contributors/research/2026-11-12-ffi-and-fiddle-on-phones.md`, claim 3). No guideline names ffi, fiddle, libffi, or `dlopen`.

PEP 730 lists stricter rules: "Dynamic binary content must be compiled as dynamic libraries, not shared objects or binary bundles"; "They must be packaged in the app bundle as Frameworks"; "Each Framework can only contain a single dynamic library"; "The Framework *must* be contained in the iOS App's `Frameworks` folder"; "A Framework may not contain any non-library content" (`pep-0730.rst`, lines 104 to 116). It ties them to "the iOS App Store guidelines" without citing a page. CPython's `Doc/using/ios.rst` says the same as App Store policy, adding "there can be no executable binary material outside the `Frameworks` folder" (lines 72 to 80). Apple's own text, as read here, says nothing on a bundle (`MH_BUNDLE`) inside a framework, so that rule is PEP 730's, not a source of Apple's.

What CPython does. Its build phase finds each `.so` under the standard library and the app's packages (`utils.sh`, lines 122 to 126 and 144 to 148), moves it to `Frameworks/DOTTED.NAME.framework/DOTTED.NAME`, writes an `Info.plist` from a template with `CFBundleExecutable` and an identifier made from the dotted name, leaves a `.fwork` text file where the `.so` was, and signs the framework (lines 63 to 111). It does not change the library's install name; it only moves the file. CPython builds its modules with `-dynamiclib`, not `-bundle` (the 2026-11-13 findings, "CPython"). Its importer reads the `.fwork` file. Nothing in that script handles a `.dylib` a package opens with `ctypes` by its path, so an unmodified Python package that does so is not served on iOS by CPython's own tooling.

What a framework needs, from the sources read: a binary, an `Info.plist` naming it, an identifier, and a minimum iOS version, and a signature. Flutter's native assets also set the install name to `@rpath/NAME.framework/NAME` (the 2026-11-13 findings, "Flutter"). XcodeGen embeds a framework dependency and has Xcode sign it on copy with `embed: true` and `codeSign`, which defaults to true (`Docs/ProjectSpec.md`, lines 612 and 614 at 2.46.0).

Measured on this Mac. `xcrun --sdk iphoneos clang -target arm64-apple-ios15.0 -bundle` links a one-function library with no warning, and `-dynamiclib` too; given both, clang stops with "invalid argument '-bundle' not allowed with '-dynamiclib'". A folder `Thing.framework` holding that bundle as `Thing` and an `Info.plist` signs ad hoc with `codesign -s -`, and `codesign --verify --strict` reports it "valid on disk". `vtool -show-build` reads platform IOS, minos 15.0. `install_name_tool -id` on the bundle exits 0 and adds nothing, since a bundle has no `LC_ID_DYLIB`.

### Android

The installer extracts `lib/ABI/lib*.so` entries into the app's native library folder, and an app may `dlopen` a library from there or from its own files (the 2026-11-13 findings, "Android"). With `useLegacyPackaging = false`, libraries stay stored in the APK and load from it: "In API level 23 and above, it's possible to open a .so file directly from your APK", and `dlopen` takes a path of the form `my_zip_file.zip!/libs/libstuff.so` (bionic, `android-changes-for-ndk-developers.md`, lines 150 to 166). A link then has no file to point at, which is why Fledge's extension files already need `useLegacyPackaging = true`, as its template writes it.

A library's dependencies resolve only from its own `DT_NEEDED` closure and the global group, not from libraries opened with `RTLD_GLOBAL` (the 2026-11-14 findings, "Resolving one library's symbols against another's"). Chaquopy shows what that costs a Python app: it replaces `ctypes.util.find_library` and wraps `ctypes.CDLL.__init__` to find a library among the app's requirements and to load its `DT_NEEDED` libraries first, since "the caller may load the library in another way (e.g. soundfile uses ffi.dlopen)" (`importer.py`, lines 130 to 178). It also extracts a non-Python `.so` that a package finds itself and loads with `CDLL` (lines 237 to 239). No library read here needs another of its gem's.

16 KB pages: the NDK r28 changelog says "The default alignment of shared libraries for arm64-v86 and x86_64 is now 16k. To revert to 4k alignment, set APP_SUPPORT_FLEXIBLE_PAGE_SIZES (ndk-build) or ANDROID_SUPPORT_FLEXIBLE_PAGE_SIZES (CMake) to false." It names only ndk-build and CMake. Whether the NDK r30 that Fledge pins aligns a library linked by its clang directly, as ffi-compiler and libtool link, was not read. Fledge passes `-Wl,-z,max-page-size=16384` to its own links (`lib/fledge/mobile_extensions/targets.rb`, line 78), and ffi-compiler takes `LDFLAGS` from the environment, as `configure` does.

## 3. What ffi does with what it is given

At ffi 1.17.4, `ffi_lib(*names)` calls `FFI::DynamicLibrary.load_library` for each name with `RTLD_LAZY | RTLD_LOCAL` unless `ffi_lib_flags` says otherwise (`lib/ffi/library.rb`, lines 89 to 97). `load_library` tries each name and its `FFI.map_library_name` (`lib/ffi/dynamic_library.rb`, lines 69 to 96). `LibraryPath.wrap` returns a value with a slash in it unchanged, and adds `LIBPREFIX` and `LIBSUFFIX` only to a bare name (`lib/ffi/library_path.rb`, lines 62 to 75 and 88 to 97). The C side passes the string to `dlopen` (`ext/ffi_c/DynamicLibrary.c`, lines 101 and 147). A path that fails is not searched for elsewhere (`dynamic_library.rb`, line 83); only a bare name is tried in `SEARCH_PATH`, which on Apple systems is `LD_LIBRARY_PATH`, `DYLD_LIBRARY_PATH`, `/opt/homebrew/lib`, `/opt/local/lib`, `/usr/local/lib`, and `/usr/lib` (lines 37 to 58).

`FFI::Platform::OS` comes from `RbConfig::CONFIG['host_os']`: `linux` for anything matching `/linux/` and `darwin` for `/darwin/` (`lib/ffi/platform.rb`, lines 40 to 59). `ARCH` is `aarch64` for `arm64` or `aarch64` and `x86_64` for `x86_64` (lines 65 to 86). `LIBSUFFIX` is `dylib` on `darwin` and `so` on Linux (lines 124 to 127). Fledge's iOS Ruby is configured for the host `aarch64-apple-darwin` (`doc/contributors/design/phone-runtimes.md`, "Building Ruby for a phone"), and Android's reports `linux-android`. So the paths each unmodified gem asks `dlopen` for, relative to the gem's folder in the app's Ruby root, are:

| Gem | iOS, both slices | Android arm64-v8a | Android x86_64 |
|---|---|---|---|
| llhttp-ffi | `ext/aarch64-darwin/libllhttp-ext.bundle` | `ext/aarch64-linux/libllhttp-ext.so` | `ext/x86_64-linux/libllhttp-ext.so` |
| scrypt | `ext/scrypt/aarch64-darwin/libscrypt_ext.bundle` | `ext/scrypt/aarch64-linux/libscrypt_ext.so` | `ext/scrypt/x86_64-linux/libscrypt_ext.so` |
| rdkafka | `ext/librdkafka.dylib` | `ext/librdkafka.so` | `ext/librdkafka.so` |
| sassc | `lib/sassc/libsass.bundle` | `lib/sassc/libsass.so` | `lib/sassc/libsass.so` |

The iOS paths are the macOS ones, since ffi reads iOS as `darwin`. Two of the four gems use one Android path for both ABIs. Fledge's Android Ruby root is one tree for both ABIs (`phone-runtimes.md`, "What a phone runtime holds"), so a file at that path could serve only one ABI. A link made on the device for its own ABI serves each.

## 4. What Fledge already has

**How a Rakefile gem builds today.** `RakeBuild#call` runs RubyGems' own builder under this computer's runtime's Ruby with `--disable=rubyopt`, and every Ruby the build starts gets `RUBYOPT=-I ARCHDIR -r FILE`, the phone's `rbconfig.rb` and Fledge's tools and hook (`rake_build.rb`, lines 149 to 176). That is right for these gems: ffi-compiler reads the phone's `FFI::Platform` through it, so it names its folder and library as the phone's Ruby will look for them. A Mac's own `rbconfig.rb` would make an Android build write `aarch64-darwin/….bundle` with `-bundle`. `CC` and `CXX` are the phone's compilers with their flags: on iOS `clang -target TRIPLE -isysroot SDK` (`targets.rb`, line 109), on Android the NDK's `aarch64-linux-android26-clang` (line 130), with `PKG_CONFIG=false` (line 160). ffi-compiler and mini_portile2 both take `CC` from the environment.

**What it does not give the build.** An `extconf.rb` gets the require paths of the gems its gem depends on, at any depth, on its load path (`MobileExtensions#load_path` and `#extconf_build`, `lib/fledge/mobile_extensions.rb`, lines 565 to 581). A Rakefile's build gets none (`#rake_build`, lines 570 to 572). In that build's Rubies RubyGems reads the phone's `rbconfig.rb`, so its gem folder is the phone runtime's and `Gem::Platform.local` is the phone's; a gem installed for this computer would look unbuilt there. So `require "ffi-compiler/compile_task"` raises `LoadError` today, before any library is built. That was read, not run. And ffi's `lib/ffi.rb` requires `ffi_c`, its compiled extension (lines 1 to 8), so the build needs ffi compiled for this computer's Ruby, not the phone copy Fledge compiles for the app. The lockfile already holds every such gem, since each is a runtime dependency of the gem. `Fledge::NativeBuild` already installs a gem's server dependencies before it, compiled for this computer by the runtime's Ruby, for a desktop build (`doc/contributors/design/gems.md`, "Compiling a gem", "Order").

**What it knows about what a build leaves.** `RakeBuild` lists the shared libraries in the unpacked gem before the build and after, and refuses any new one that is not an extension mkmf made (`rake_build.rb`, lines 154 and 161 to 162; `SHARED`, line 107). It compares real paths, so a library the build writes over one the package already holds is not new to it. llhttp-ffi's iOS build writes its library over the package's macOS one, so that check would miss it; and if Rake found that file newer than its sources, the build would leave the macOS one in place. The two files would also differ in their platform. The list is relative to the gem's root, which is the path the gem's Ruby asks `dlopen` for.

**How a file reaches an Android app.** `MobileExtensions` builds each C or C++ extension an `extconf.rb` builds as a `Library` (`files: phone.name == "android"`, `lib/fledge/cli/build.rb`, lines 226 to 228). `MobileProject::Android` copies it into `jniLibs/ABI/` as `libfledgeext.FEATURE.so`, strips it, and writes a line of `fledge.links` for each path where a desktop has its file (`Library.links`, `lib/fledge/mobile_extensions/library.rb`, lines 71 to 81). `fledge_link_libraries` makes each link as the app starts, its parent folders first, and makes it again when an install moves the native library folder (`runtime/mobile/library_links.c`, lines 6 to 15, 59 to 63, and 108). Nothing in that code is particular to Ruby's extensions: a line's path may be any file under the Ruby root.

**sassc today, by reading.** On Android, sassc's library is built as a `Library` and linked at `lib/sassc/libsass.so`, the path its `native.rb` asks for, so it may already work; no app has tried it. On iOS, `make static` archives libsass, the registration unit calls `Init_fledge_N`, which libsass does not define, and the app's link fails on an undefined symbol that names nothing a developer would recognize.

**Where iOS refuses a framework today.** The archive check fails an app with a `Frameworks` folder or any Mach-O file besides its executable (`tasks/mobile_parity/ios_archive.rb`, lines 262 to 270), since a Fledge iOS app embeds nothing.

**A desktop finding.** On a desktop build, `NativeBuild` ships only the files the build wrote into the gem's require paths (`lib/fledge/native_build.rb`, lines 305 to 319). A library ffi-compiler leaves in `ext/` is in none of them, so by reading, a desktop app with scrypt or rdkafka ships without its library and raises `LoadError`. A desktop app with llhttp-ffi 0.5.1 on an Apple-silicon Mac ships the library the author packaged rather than the one the build made. No desktop app with these gems was built for these findings.

## 5. Options

### The three claims

1. **"Install the Rakefile's build dependencies for this computer."** Holds, but "install" is the wrong word. The gems are in the lockfile already. They have to be on the load path of every Ruby the build starts, as an `extconf.rb`'s are, with each that has an extension, ffi among them, compiled for this computer. RubyGems activation cannot do it under the phone's `rbconfig.rb`.
2. **"Wrap the iOS library in a framework, since iOS takes no third-party dynamic library outside one."** Holds, from Apple's own sentence. Apple's text reads as a packaging rule, not a ban on loading one.
3. **"Make the path the gem gives `ffi_lib` reach it."** Holds. Every gem read gives a path, never a bare name, and ffi passes it to `dlopen` untouched. Only a file or a link at that path serves an unmodified gem.

### For the build (both phones)

**B1. Run the Rakefile as today, with its gems on the load path.** Add to `RUBYOPT` for the build the require paths of the gem's dependencies, as `extconf.rb` builds get them. For a dependency with an extension, add the folders of a copy compiled for this computer by `NativeBuild`, in a folder of the build's own. Then collect each shared library the build wrote or changed, by contents rather than by real path, and check each is built for the target. Costs: a few lines in `RakeBuild` and `MobileExtensions`, plus one `NativeBuild` run per such dependency; a C compiler for this computer, which a Mac building for iOS has in Xcode, and which a Linux computer building for Android has if it can build a desktop app with such a gem; and the ffi gem compiled twice, once for each computer. Parity: the Rakefile runs under real ffi and real ffi-compiler, as under `gem install`.

**B2. A stand-in for ffi at build time,** after ffi-compiler's own `fake_ffi`, defining `FFI::Platform` from `RbConfig`. Saves compiling ffi for this computer. But it is Fledge's code pretending to be a gem, and it answers only what Fledge foresaw; a Rakefile that does more with ffi gets a different answer than under `gem install`. Rejected: under `gem install` the Rakefile runs real ffi.

**B3. Fledge reads the CompileTask and builds the library itself,** as a recipe would. Rejected: it is a build system of Fledge's own for one tool, it misses rdkafka's and webp-ffi's builds, and `phone-projects.md`, "Rakefiles", already rejects recipes per gem.

**B4. The precompiled ffi gem for this computer** (ffi publishes `arm64-darwin` and Linux builds) in place of compiling it. Rejected: a phone app's lockfile locks `ruby` alone, with `force_ruby_platform`, so that file is not in the lockfile, and no checksum pins it.

### For iOS

**I1. A framework per library, and a link at the gem's path.** Fledge packs each library a build made into `Frameworks/NAME.framework/NAME`, with an `Info.plist` (executable, identifier, `FMWK`, `MinimumOSVersion` 15.0). It makes one XCFramework per library from the two slices with `xcodebuild -create-xcframework`, as it does for `FledgeExtensions.xcframework`. `project.yml` embeds it with `embed: true`, and Xcode signs it. In `fledge/` at the gem's path it writes a relative link, `../…/Frameworks/NAME.framework/NAME`, which dangles in the project and resolves in the bundle; the "Copy Ruby and the app" phase copies links as links with `ditto`. It replaces any file the package held at that path. Costs: the packing (Fledge writes an `Info.plist` and runs Apple's tools), a framework name scheme unique in `Frameworks` (CPython's dotted path, with the gem's full name, since two gems may name one library alike), the archive check rewritten to accept those frameworks and check each (arm64, IOS platform, minimum 15.0, signed in an export), and the privacy check made to read each framework's imports (scrypt calls `sysctl`, `ext/scrypt/memlimit.c`, line 69). No Ruby rebuild: these libraries call no Ruby, and fiddle and ffi `dlopen` without Ruby's `dln`, which stays `--disable-dln`. Parity: `File.symlink?` is true and `File.realpath` names `Frameworks/` where a desktop has a plain file, as for Android's extension files; `dlopen`, `ffi_lib`, `Fiddle.dlopen`, and `Loader.find`'s glob all find it. App-store risk: two unknowns. App Store Connect may refuse a link inside the bundle, though the link is not "executable binary material". And ffi-compiler links an `MH_BUNDLE`, which PEP 730 says must not ship, but which Apple's text read here does not mention.

**I1a. As I1, but each library relinked as a dynamic library.** Removes PEP 730's bundle doubt. ffi-compiler puts `-bundle` before `LDFLAGS` and clang refuses `-dynamiclib` beside it (measured), so Fledge would have to rewrite the link: a compiler wrapper that swaps the flag, as kivy-ios's `liblink` stands in for the linker, or a second link of the objects the build left. Both are code Fledge would own for one tool's choice. Kept as the fallback if the experiments show a bundle in a framework does not load or does not pass App Store Connect.

**I2. A table instead of a link.** The runtime answers `dlopen` of a gem's path with the framework, from a list `fledge build` writes, by interposing `dlopen` or by renaming the ffi gem's and fiddle's calls of it at link time. Needs no link in the bundle. Costs: every `dlopen` in the process passes through Fledge's code; Mach-O interposition from the main executable, or a symbol renamed in the ffi gem's archive, needs its own proof; and `File.exist?` of the path is false while `dlopen` succeeds, a difference a gem can read. Kept only as the fallback if App Store Connect refuses links.

**I3. Link the library into the app, and a link at the gem's path to the app's own executable.** No frameworks. Rejected: every library's symbols share one namespace, so two libraries that define one name clash at the app's link, and a lookup that should fail, such as a gem probing for a function its library lacks, finds the app's; and Xcode's dead stripping drops what only `dlsym` reaches.

**I4. A plain library at the gem's path.** Rejected: Apple's "don't support third-party standalone dynamic libraries".

**I5. Keep refusing.** Rejected: no source read forbids it, which the ruling of 2026-11-12 asks for.

### For Android

**A1. Each library in `jniLibs`, and a link at the gem's path.** Copy each library a build made into `jniLibs/ABI/` under a name the installer extracts, such as `libfledgeffi.GEM.PATH.so` with the slashes as dots, strip it, check its alignment, and add a `fledge.links` line for its ABI and path. Costs: a name scheme and a few lines that build `Library`-like entries from a Rake build's leftovers; no runtime change. It needs `useLegacyPackaging = true`, as extensions as files do. Parity as I1. App-store risk: none found. Google Play forbids downloaded native code, not the package's own (the 2026-11-13 findings).

**A2. The library at the gem's path inside `fledge.zip`.** Rejected: one Ruby tree for both ABIs, and rdkafka and sassc use one path for both, so one ABI's library would be missing; and Play's per-ABI splits and checks never see a library in an asset.

### What only a run can settle

None of these was run. Each is the narrowest run found that settles one question.

1. **iOS Simulator, a library through a link.** In a project from `fledge build ios examples/hello`, embed `Thing.framework` built for the Simulator (`xcrun --sdk iphonesimulator clang -target arm64-apple-ios15.0-simulator -bundle -o Thing thing.c`), add a relative link in `fledge/app/` to `Frameworks/Thing.framework/Thing`, and make `main.rb` print `Fiddle::Function.new(Fiddle.dlopen(File.join(__dir__, "libthing.bundle"))["thing"], [], Fiddle::TYPE_INT).call`. fiddle is in the iOS runtime, so this needs no ffi gem and no change to Fledge. Build it again with `-dynamiclib` in place of `-bundle`. This settles whether dyld loads a bundle from a framework and whether it follows the link.
2. **A device, the same app,** signed with a team, the maintainer's own Personal Team as `doc/contributors/account-tests.md` says his devices already use. Settles whether a device's code signing and library validation accept it.
3. **App Store Connect,** the same app archived and uploaded, both the bundle and the dynamic library: a new account test beside IOS-1, which only the maintainer can run.
4. **An NDK, no emulator.** `aarch64-linux-android26-clang -shared -o libthing.so thing.c` with NDK r30, then `llvm-readelf -l libthing.so`, settles whether a library ffi-compiler links is aligned to 16 KB without Fledge's `LDFLAGS`.
5. **An Android emulator, sassc.** An app that locks sassc 2.4.0 and compiles a stylesheet, run as `tasks/mobile_parity.rb android` runs the examples, settles whether today's trunk already serves an `extconf.rb` that builds a library for ffi.
6. **The build alone.** RakeBuild with B1, for llhttp-ffi and scrypt, for each of the four targets on a Mac with Xcode and the NDK, and no device. Settles whether ffi-compiler builds under the phone's `rbconfig.rb` with host ffi on the load path. This is the first story's integration test.

### What stays refused

- **A library not built for the target,** found by its platform (`vtool -show-build` on iOS, `llvm-readelf -h` on Android). For example: "llhttp-ffi 0.5.1's Rakefile left ext/aarch64-darwin/libllhttp-ext.bundle built for macOS, not ios-arm64-simulator: the gem's package holds it, and its build did not replace it. Fledge ships only libraries built for the phone. Leave the gem out of the app's ios build (gem "llhttp-ffi", platforms: [...] in the Gemfile)."
- **On iOS, a library that calls Ruby's own functions,** since it could link only with `-undefined dynamic_lookup`, which Apple's linker reports as deprecated on iOS (the 2026-11-13 findings, measured), and the archive check fails on any warning: "GEM's library PATH calls Ruby's own functions (rb_…), which a library for ffi on iOS cannot reach, since iOS's Ruby is linked into the app. Leave the gem out of the app's ios build (gem "NAME", platforms: [...] in the Gemfile)." None of the five gems read does this.
- **A build on Windows,** as for every extension today.
- **A library a gem names by a bare name,** such as `ffi_lib "sodium"`, is not refused, since a build cannot know it. It fails at run time with ffi's `LoadError`, as on a desktop without the library. A developer supplies it as a framework's or `extconf.rb`'s library.

## 6. Recommendation

**B1 for the build, A1 for Android now, and I1 for iOS once experiments 1 to 3 pass,** with I1a ready if a bundle fails and I2 if a link fails.

The reasons, in Fledge's order of precedence. A person never meets Ruby: the library loads where the gem looks, and a missing one fails at `require` as on a desktop. Ruby code runs as under `bundle exec`: the gem, ffi, and fiddle run unmodified, and only `File.symlink?` and `File.realpath` tell the link apart, as they already do for Android's extension files. Ruby's conventions: RubyGems' own builder and the gem's own Rakefile run, under real ffi. Prior art: CPython, Briefcase, and Flutter wrap each iOS library in its own framework; CPython leaves a marker where the file was, which its own importer reads, where Fledge leaves a link that `dlopen` follows, since Fledge changes neither ffi nor the gem. On Android every Python tool loads native code from files, and Chaquopy finds libraries that a package's own code opens. Code is a liability: Android needs no runtime code, and iOS needs packing with Apple's own tools and no change to Ruby.

**Stories,** each small and green:

1. **The build.** `RakeBuild` runs with the gem's dependencies on its Rubies' load path, those with extensions compiled for this computer by `NativeBuild`. It lists the libraries a build wrote or changed by contents, and refuses one not built for the target by name. The existing refusal of every other library stays, with the gem's library named rightly. Test: `test/integration/mobile_extensions_build_test.rb`, a path gem whose Rakefile uses ffi-compiler, built for iOS's two slices, must report its library at `ext/aarch64-darwin/`; a gem whose package holds a macOS library the build does not replace must be refused by that message. The existing test changes its expectation from "refused" to "reported".
2. **Android.** Those libraries go into `jniLibs` and `fledge.links`; the 16 KB check and strip cover them; `LDFLAGS` carries `-Wl,-z,max-page-size=16384` unless experiment 4 shows it needless. A unit test beside the `fledge.links` tests in `test/mobile_build_test.rb`, from libraries described in memory, with no NDK: the file and the link line. Example: `examples/ffi_library_phone`, locking llhttp-ffi 0.5.1 and scrypt 3.1.0, printing a parsed request's method and a scrypt hash; CI's `mobile-apps-android` jobs run it on 4 KB and 16 KB emulators.
3. **sassc's kind.** An `extconf.rb` extension whose archive or library defines no `Init_NAME` is a library for ffi, not an extension: on Android a file at its path as today, and on iOS one more library for story 5, not a registration. Test: an `extconf.rb` that sets `$LIBRUBYARG = nil` and defines no Init function, built for iOS, is not registered.
4. **The iOS experiments,** 1 and 4 by an agent in a throwaway project outside the repository, 2 and 3 by the maintainer, with the account test added to `doc/contributors/account-tests.md` in the same commit that adds `examples/ffi_library_phone` to iOS.
5. **iOS.** Frameworks, XCFrameworks, `embed: true`, and the links; the archive check accepts exactly those frameworks and checks each; the privacy check reads each framework's imports. The example joins CI's `mobile-apps-ios` job on an iPhone and an iPad Simulator.
6. **Documents.** `phone-projects.md`'s "The ffi gem" and "Rakefiles" step 5, `phone-runtimes.md` where it lists what an app holds, `doc/phones.md`, and the CHANGELOG.

**`public-interface.md`, "Phones",** would gain under "Fledge provides" a line such as: "A shared library that a gem's Rakefile or `extconf.rb` builds for ffi or fiddle to open is built for each of the phone's targets and found at the path where a desktop's build leaves it: on iOS in a framework of its own in the app's `Frameworks` folder, with a link at that path, and on Android a native library of the app's own, linked at that path as the app starts." Under "The framework provides", the iOS clause "no `dlopen` of a file it ships" would become "no `dlopen` of a file it ships, but a library its gems' builds make, which Fledge places", with the Rakefile's build-time gems in the lockfile and, for a gem with an extension among them, a C compiler for the build computer.

## Lines these findings make untrue

These are for the orchestrator, who changes the documents.

- **`doc/contributors/design/phone-projects.md`, "Gems with extensions", paragraph "The ffi gem":** "Fledge would have to install the Rakefile's build dependencies for this computer, wrap the iOS library in a framework, since iOS takes no third-party dynamic library outside one …, and make the path the gem gives `ffi_lib` reach it."
