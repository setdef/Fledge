# ADR 030: Libraries a Gem Loads From the Linux Distribution Are Listed by Soname and Expected of the Host

## Context and Problem Statement

`fledge build` refuses a gem whose compiled files need a library that neither every Linux distribution (auditwheel's manylinux_2_39 list, or musllinux_1_2 on musl), nor the runtime, nor the gem provides (ADR 046). That refuses every wrapper of a desktop library. Tokra's extension links WebKitGTK 4.1, GTK 3, libsoup 3, and JavaScriptCoreGTK 4.1: every desktop's distribution provides them, no gem should carry them (they are large, LGPL, and tied to the desktop's own GLib, D-Bus, and theme), and the manylinux list leaves them out because a server has none. How does a developer ship such a gem, and how does the app still keep a person from meeting a gem's `LoadError` on a computer that lacks one?

## Decision Drivers

- A person who runs the app never meets an error that names a gem (AGENTS.md, Design precedence 1).
- One name for a library that every kind of Linux output can use: the `.tar.gz`, the AppImage, the `.deb`, and a later `.rpm`.
- A list Fledge can check against the files, so it says only what is true.
- Code is a liability: use Debian's own tool where one exists (`decisions.md`, 2026-10-28).
- Nothing in a runtime or app that Fledge cannot meet the license policy for (AGENTS.md, Licensing).

## Considered Options

1. `linux: system_libraries` in `fledge.yml`, a list of sonames: accepted by the library check, refused when unlisted or unused, checked by the launcher before Ruby starts, not bundled into an AppImage, and mapped to `.deb` packages by dpkg-shlibdeps.
2. Debian package names, as Tauri's `bundle > linux > deb > depends` and Briefcase's `system_runtime_requires` take them.
3. Sonames with wildcards, as auditwheel's `--exclude` accepts.
4. Bundling the libraries into the AppImage, as Tauri does with linuxdeploy and its GTK plugin.
5. For the `.deb`, finding packages with `dpkg -S` on each library's path, or with apt-file.

## Decision Outcome

Chosen: option 1, because a soname is the one name every output shares and the library check can verify. A package name (option 2) is one distribution family's, sometimes one release's (Ubuntu 24.04 and Debian 13 renamed GLib's to `libglib2.0-0t64`), cannot be checked against the files, means nothing to an AppImage or a `.tar.gz`, and would need sonames again for an `.rpm`, as Tauri's two lists show. Wildcards (option 3) cannot be checked exactly, and a new soname is a new ABI a developer should read before shipping. Bundling (option 4) means linuxdeploy and its plugin, WebKitGTK's helper processes and GTK's modules copied by hand, tens of megabytes, the D-Bus and subprocess bugs Briefcase warns of, and LGPL libraries that would be the app's, whose sources each developer would have to publish. `dpkg -S` (option 5) names only a file's owner, so Fledge would rewrite the loader's search and still have no version; apt-file reads the archive, not what is installed, and needs its own download. dpkg-shlibdeps is Debian Policy 8.6.1's own procedure and gives the oldest version whose symbols the files use.

The key sits under `linux` because sonames are Linux's; it applies to glibc and musl alike. A listed library that no gem's compiled file needs fails the build, and the launcher on Linux checks each listed library before Ruby starts, exiting with `EX_OSFILE` (72) and never naming Ruby or a gem (`doc/contributors/design/gems.md` and `launcher.md` say how).

Confidence: medium. `examples/system_library` proves the whole path on Debian and Ubuntu, but no wrapper has shipped a WebKitGTK app with it yet, and a `.deb` names the packages of the distribution it was built on.

### Consequences

- Good, because a wrapper of a desktop library ships on Linux: its developer copies the sonames from the build's refusal, `apt` installs their packages with the `.deb`, and an AppImage or archive on a computer without them says which to install.
- Bad, because a library a gem opens with `dlopen` (SDL's X11 and Wayland) cannot be listed: no compiled file names it, so nothing checks it.
- Bad, because building a `.deb` with libraries listed needs dpkg-dev and objdump; a computer that compiles gems has both.
- Bad, because a library whose package is named differently elsewhere (libjpeg's `libjpeg-turbo8` and `libjpeg62-turbo`) makes a `.deb` for the distribution it was built on only.
- Bad, because an AppImage is not self-contained for these libraries.
- Neutral, because the launcher's exit statuses gain 72 on Linux (ADR 002), and `fledge.yml`'s key is part of what 1.0 freezes (ADR 029).

### Confirmation

`test/linkage_test.rb`, `test/config_test.rb`, `test/deb_test.rb`, and `test/assembly_test.rb`. CI builds `examples/system_library` (a path gem whose C extension links libpng) on glibc Linux, builds it again with the key removed and expects the refusal that names the key, checks the `.deb` depends on `libpng16-16t64`, installs it with `apt` in fresh `debian:trixie-slim` and `ubuntu:24.04` containers, and runs the `.tar.gz` and AppImage in a container without libpng, expecting status 72 and the library's name.
