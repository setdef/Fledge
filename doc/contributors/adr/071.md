# ADR 071: Trunk's Full CI Runs Are Never Cancelled, and a Fast Tier Judges Every Push

## Context and Problem Statement

`ci.yml` builds every runtime, tests each platform, builds the examples, and delivers them on fresh runners: about an hour a run. Its concurrency cancelled the run in progress on any ref when a newer push arrived. Several agents land small gated commits on `trunk` every few minutes, so on 2026-11-12 every trunk run from 14:25 to 16:56 UTC was cancelled by the next push, and trunk went hours with no finished run. Nobody learned whether trunk was green, and a release commit pushed then would have had its run cancelled too.

Holding pushes until a run finishes is not trunk-based development, which integrates every change as it is ready (the trunk-based-development skill; trunkbaseddevelopment.com, "Continuous Integration"), and the maintainer rejected it. How does every push to trunk get a verdict, and every run finish, without anyone waiting to push?

ADR 053 decides what a release proves from the runs of the release commit and the pin commit; that still holds, but a run that can be cancelled or replaced puts those two runs at risk.

## Decision Drivers

- Trunk-based development: anyone pushes a gated commit whenever it is done, and nobody waits for CI to push.
- Every run of `ci.yml` that starts on trunk finishes, so trunk's state is always known within about two hours.
- Each push gets a verdict of its own in minutes.
- A release commit and a pin commit each get a run of their own that finishes (ADR 014, ADR 053).
- No more runner time than the free plan's queue can carry: a full run asks for many macOS and Windows jobs.

## Considered Options

1. Never cancel a trunk run, let a newer push replace only the waiting one, give release and pin commits a group of their own, and add a fast workflow that runs the lint and the unit tests on every push.
2. Keep cancelling, and hold pushes while a run is in progress.
3. Run all of `ci.yml` on every push to trunk, never cancelled and never replaced.
4. Option 1 without the fast tier.

## Decision Outcome

Chosen: option 1, as Lota does (`doc/contributors/ci.md` in setdef/lota, "What runs on a push"). `ci.yml`'s concurrency cancels the run in progress only on a ref other than the repository's default branch. On trunk GitHub keeps at most one run going and one waiting per group, and a newer push replaces the waiting one, so every run that starts finishes and covers every commit pushed since the run before it started. A commit whose message starts `chore: release ` or `chore: pin ` gets a group named for its commit, so its run starts at once and no push replaces it; the release commit's ruby/spec on every desktop platform already keys on the same message. `.github/workflows/fast.yml` runs `bundle exec rake lint steep` on Linux and `bundle exec rake test`, the unit tier, on Linux, macOS, and Windows, with a group per trunk commit, so no push cancels or replaces another's verdict. It is a workflow of its own because GitHub ends a run only when its slowest job ends.

Option 2 is the hold the maintainer rejected. Option 3 would queue hours deep: a run asks for about an hour of several macOS and Windows runners, and the queue would grow with every push. Option 4 leaves a push without a verdict for up to two hours, and blames a batch for a red run with nothing to narrow it.

The Gate job stays in `ci.yml`. It runs `bundle exec rake`, the whole gate, with the integration tier and the readers of compiled files (`FLEDGE_REQUIRE_READERS`), and fails when the gate's autocorrect changed a file; the fast tier runs only what needs no runtime and fixes nothing. A pin commit's short run is the gate and `Changes` (ADR 053), so the gate has to be in that run. Its lint repeats the fast tier's, at the cost of about a minute of one Linux runner.

Confidence: medium. GitHub documents the one-running, one-waiting behavior of a concurrency group; the release groups depend on commit messages, which `doc/contributors/handoff.md`, "How to release", fixes. Trunk's behavior shows only on trunk.

### Consequences

- Good, because every trunk run that starts finishes, and trunk's state is known.
- Good, because each push gets a verdict on three systems in minutes, from a run nobody cancels.
- Good, because a release commit's run starts at once and is never replaced, so a release no longer asks agents to stop pushing while it runs.
- Bad, because a red full run blames a batch: every commit pushed since the run before it started. The fast tier's per-push verdicts narrow it, and otherwise someone bisects.
- Bad, because a commit inside a batch has no run of its own, so `tasks/ci_runs.rb` finds none for it, and it cannot be a release commit or a pin commit's parent. A release commit pushed alone is the head of its push and gets a run of its own.
- Bad, because the pin commit's parent must still be the release commit (ADR 014), so nothing else lands on trunk between them. That window is now the release commit's run and no longer, but it is still a hold.
- Bad, because the fast tier's macOS job waits for a macOS runner like any other job. GitHub's free plan runs five macOS jobs at once for the whole account, and full runs on trunk and on experiment branches fill them, so the macOS verdict can come long after the Linux and Windows ones: on `experiment/ci-concurrency`'s first run, Linux's unit tests took 21 seconds and Windows' 3 minutes 36, and the macOS job waited in the queue for over half an hour. Nothing in a workflow raises a job's priority; fewer macOS jobs in full runs, or larger runners, which cost money, would.
- Neutral, because the release and pin groups key on commit messages: a release commit with another message falls into trunk's group, where a newer push can replace its waiting run.

### Confirmation

`test/workflow_concurrency_test.rb` holds both workflows to cancelling on branches only, `ci.yml` to its release and pin groups, and `fast.yml` to its jobs. `test/ci_runs_test.rb` holds the message `tasks/ci_runs.rb` gives a commit with no run. A second push to a branch cancels its runs (shown on `experiment/ci-concurrency`). On trunk, a run that finishes after a newer push, and a waiting run replaced instead of a running one cancelled, confirm the rest.

## More Information

GitHub's documentation, "Control the concurrency of workflows and jobs": "When a concurrent job or workflow is queued, if another job or workflow using the same concurrency group in the repository is in progress, the queued job or workflow will be pending. Any existing pending job or workflow in the same concurrency group, if it exists, will be canceled and the new queued job or workflow will take its place." `doc/contributors/design/releases.md`, "Runs, batches, and the release commit", gives the details.
