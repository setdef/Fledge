# ADR 090: Android's Ruby has YJIT and ZJIT, each off until the app enables it, as on a desktop

## Context and Problem Statement

Fledge built a phone's Ruby with no JIT, so `RubyVM::YJIT` and `RubyVM::ZJIT` were not defined there. Fledge's desktop Rubies have both: rv-ruby's builds, which the macOS and glibc Linux runtimes and the phones' parity reference come from, are configured `--enable-yjit --enable-zjit`, with `ZJIT_SUPPORT` "yes" in their `rbconfig.rb`, and the musl runtimes get ZJIT by default from `configure.ac`. RubyInstaller's Windows builds have neither JIT. On iOS no JIT is possible: an app gets no memory it may write code into and run, save a browser's web content extension (BrowserEngineKit, "Protecting code compiled just in time"). On Android the JITs were left out only by Ruby's `configure.ac` (lines 3896 to 3910 at 4.1.0-preview1), which builds none by default for a cross build, with no reason given (ruby/ruby 3703a81491). Android grants apps such memory: AOSP's sepolicy reads "WebView and other application-specific JIT compilers / allow appdomain self:process execmem" (`private/app.te`, lines 188 to 189), and Google Play's Device and Network Abuse policy exempts code that "runs in a virtual machine or an interpreter" from its rule against downloaded code (read 2026-11-12). The maintainer, 2026-11-12 (`decisions.md`): a difference is accepted only where a platform truly forbids it. Which JITs does Android's Ruby build, and how?

## Decision Drivers

- The app's code runs as under `ruby main.rb` (AGENTS.md, Design precedence 2): `RubyVM::YJIT` and `RubyVM::ZJIT` are there, each off until the app enables it, as on a desktop.
- What a platform forbids is shown from its own sources.
- A cross build of Ruby never boots the Ruby it builds, so what it needs at boot must be checked when building.

## Considered Options

1. Configure Android's Ruby with `--enable-yjit --enable-zjit`, compiled by `rustc` for each target and linked with the NDK's `ld.lld` and `llvm-objcopy`, with the build machine's miniruby configured with the same JITs.
2. YJIT alone, with ZJIT's absence justified.
3. No JIT, with the difference justified.
4. Build the JITs with Cargo (`--enable-yjit=dev` or `=stats`).

## Decision Outcome

Chosen: option 1, because nothing forbids a JIT on Android, and the only reason for leaving either out was a cross build's default. With both JITs, `configure.ac` takes its release build of YJIT and ZJIT together (lines 4033 to 4040), which needs `rustc` alone and passes its flags to every crate, so the target and the NDK's tools serve both. The build machine's miniruby must have the target's JITs: it writes the builtin binary, which holds only the builtins it loaded (`template/builtin_binary.rbbin.tmpl`), and a Ruby built with a JIT stops at boot without its builtins (`builtin.c`, line 68: "[BUG] builtin_lookup: can not find yjit"). So the build compares the two Makefiles' `YJIT_SUPPORT` and `ZJIT_SUPPORT` and fails when they differ. How: `doc/contributors/design/phone-runtimes.md`, "Building Ruby for a phone" and "The builtin binary".

Options 2 and 3 justify differences no platform requires: ZJIT is experimental in Ruby 4.1, but it is in the Rubies a developer runs, and an app may enable it. Option 4 needs Cargo, where a release build needs only `rustc`.

Confidence: high. On both API 36 x86_64 emulators, with 4 KB and 16 KB pages, from the debug APK and the release bundle, an Android runtime built with both JITs finds no unjustified difference in the parity check with `ruby main.rb`; MobileHello enables YJIT and reports machine code; and ruby/spec passes. The arm64-v8a build is linked and audited, and runs on no emulator.

### Consequences

- Good, because an Android app's `RubyVM::YJIT` and `RubyVM::ZJIT` are a desktop's, and an app that enables either runs compiled code.
- Bad, because building the Android runtime needs Rust with Android's two targets, and `libfledgeruby.so` carries Rust's standard library, under MIT or Apache-2.0, a notice only.
- Bad, because the library is larger, by an amount not yet measured.
- Neutral: iOS's Ruby has no JIT, which `Parity::MOBILE_JUSTIFIED` justifies, for both JITs and `RbConfig`'s record of them, from Apple's documentation.

### Confirmation

`test/mobile_runtime_test.rb` holds Android's JIT options and the build machine's miniruby to the target's JITs; MobileHello on Android enables YJIT and must report machine code.
