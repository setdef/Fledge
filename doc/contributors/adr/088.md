# ADR 088: On a phone, a require of a linked extension's file by its path finds the extension

## Context and Problem Statement

On a phone every extension is linked into the app and registered as `FEATURE.so` (ADR 022), and ADR 080 puts a Ruby file where a desktop has the extension's file, so `require_relative "name/name"` finds it. A require that names the extension's file itself still failed with `LoadError`: an explicit `.so` path (`require File.join(dir, "name.so")`), a `require_relative "name/name.so"`, and on iOS a require of the platform's own extension name, `require "name/name.bundle"`, since iOS's `DLEXT` is `.bundle`. A name that ends in `.so` or `.bundle` never resolves to a Ruby file, and when Ruby finds no file it looks the table of linked extensions up by exactly the name it was given (`load.c`, lines 1203 to 1223 at Ruby 4.1.0-preview1). ADR 080 named this among its costs, as two of the gems surveyed do. The maintainer, 2026-11-12 (`decisions.md`): a difference is accepted only where a platform truly forbids what Ruby does. How does such a require find the linked extension?

## Decision Drivers

- The app's code runs as under `ruby main.rb` (decisions 9 and 20): a require of an extension's file by its path works on a phone as on a desktop.
- Fledge changes no developer's gem (ADR 007).
- Change as little of Ruby as can be (ADR 068).

## Considered Options

1. Extend the phones' existing `load.c` edit (ADR 068): after Ruby's own lookup of linked extensions, and only when no file was found, map the name to the feature it stands for (`DLEXT` made `.so`, and an absolute path made relative to each `$LOAD_PATH` folder that holds it), answer that it is already loaded when that feature is loaded, and otherwise return the registered extension, through ADR 068's gate.
2. Register aliases from `fledge_ruby_add_extension`, the absolute path and the `DLEXT` name beside `FEATURE.so`.
3. Refuse such gems by name, and justify the difference.

## Decision Outcome

Chosen: option 1, because it needs no new embedding API and covers app gems and bundled gems alike. Checking the loaded features first answers the objection ADR 080 raised against a `load.c` edit for paths: Ruby deletes a registration once it has run it, so a second require of the path would otherwise fail; here it sees the feature loaded and answers false, as a desktop's second require of the file does. `$LOADED_FEATURES` records `name/name.so`, as for any linked extension. How: `doc/contributors/design/phone-runtimes.md`, "Bundled gems' extensions", and `doc/contributors/design/phone-projects.md`, "Registering extensions".

Option 2 knows an absolute path only once the app boots, so it needs a new embedding API and a generated wrapper for each extension's Init, and it still runs an Init twice when the feature loads first and the path next, since `rb_feature_p` does not match an absolute request against a relative feature; it does not reach bundled gems. Option 3 refuses gems nothing on a phone forbids.

Confidence: high on Android, where the parity probe's fact "require nkf's extension by the path of its file" (an absolute `.so` or `.bundle` path before nkf's extension is loaded, again, then the relative `DLEXT` name) matches `ruby main.rb` on both page sizes, from a debug APK and a release bundle, and a compiled harness checks the lookup with iOS's `DLEXT`. iOS is checked by trunk's CI.

### Consequences

- Good, because a gem that requires its extension by the file's own path or name works on a phone, and a `require_relative` of an extension a Rakefile built, which gets no file of ADR 080's, works too.
- Bad, because it is one more piece of Ruby's `load.c` that Fledge edits, and a new Ruby means checking that the lines it follows are still there; the edit fails the build when they are gone.
- Bad, because `$LOADED_FEATURES` records the linked feature where a desktop records the file's path, the difference the phone parity audit lists as row 12.

### Confirmation

`test/ruby_source_test.rb` checks where the edit lands and that it raises when Ruby's lines move; `test/integration/ruby_source_gate_test.rb` compiles the lookup with iOS's `DLEXT` and checks it; the mobile parity check compares the probe fact above on both phones.

## More Information

- ADR 068's gate, which this lookup passes through, and ADR 080's files for `require_relative "name/name"`, stand as decided.
