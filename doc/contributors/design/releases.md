# Versions and Releases

This document says how Fledge is versioned, what each kind of release may change, which Rubies and platforms a release keeps, and how a release is made and published, with the reason for each. ADR 093 decides that the runtimes a release publishes are prebuilt in Fledge's CI. "How a release is made" gives a release's steps and their commands. What 1.x freezes is in `doc/contributors/design/public-interface.md`. App developers read the same rules in `doc/runtimes.md`.

## Versions

Fledge's versions are SemVer's MAJOR.MINOR.PATCH (decisions.md, 2026-11-02). Before 1.0 they are 0.MINOR.PATCH, and any 0.x release may break a build; the CHANGELOG says how. Agents cut 0.x releases as work accumulates, so that the newest 0.x release has what 1.0.0 will (decisions.md, 2026-11-08).

Which number of a 0.x version moves is a signal, not a promise. SemVer leaves 0.y.z open: "Anything MAY change at any time" (semver.org, item 4). So Fledge follows what Bundler's `~>` and Cargo's caret take a 0.x version to mean, which is that `~> 0.14.0` and `^0.14.0` both stop short of 0.15.0: the last number moves for fixes and for additions that break no build, and the middle number moves for a change that can break one. The maintainer left the choice to the agents.

The middle number also moves for the release candidate for 1.0.0, so that the release under test is plain to see. The candidate is a 0.x release that has everything 1.0.0 will, and no bug the project knows of: a known defect is fixed before a release is called the candidate, never listed beside it (decisions.md, 2026-11-21). A fault in a platform, a gem, or another project is that project's bug and not one of Fledge's: it is shown from that project's own documentation or source, and said where a developer reads, and it does not keep a release from being the candidate; anything Fledge itself could close is Fledge's (decisions.md, 2026-11-22). The candidate also has the automation that keeps a runtime's inputs current: when one has a newer release upstream, Fledge moves the pin, proves the new runtimes in CI, and releases, with nobody in the loop unless that fails, so that a security fix upstream never waits on a person (decisions.md, 2026-11-22). The maintainer's testing, of what his developer accounts block (`doc/contributors/account-tests.md`), is done on it, and if all of it passes, 1.0.0 is made from it (decisions.md, 2026-11-19): the 1.0.0 release commit changes only what `doc/contributors/releasing-1.0.md` lists, and no feature or fix lands between the two. A fix his testing calls for is released as the next 0.x version, and that release is the candidate from then on. The candidate does not wait for Ruby 4.1.0: it carries whatever Ruby the runtimes carry on the day it is cut, which today is Ruby 4.1's preview, with RubyInstaller's head build on Windows, while 1.0.0 waits for Ruby 4.1.0 (decisions.md, 2026-11-22). Between the candidate and 1.0.0 nothing is meant to change but the pin to Ruby 4.1.0 and what newer builds of Ruby force, such as a later head build on Windows.

From 1.0, a breaking change is a change to what `doc/contributors/design/public-interface.md` freezes, and it ships in the next major whenever it is ready. A removal or a changed default is announced first, by a build-time message and a CHANGELOG entry, in at least one earlier minor release. No compatibility flag keeps the old behavior: the notice warns, and the major switches.

Majors come when a break is ready, not on a schedule as Ember's do, and no flag holds a break back. A built app is a frozen artifact, so a break fails loudly at the next build, not in an app already shipped. A flag costs a key in `Fledge::Config`, the schema, the help, the docs, and a test axis on every target, for as long as anyone uses it. And the old lines to patch are bounded by the live Rubies, not by the number of majors ("Support follows live Rubies"). The cost is that a store that forces a platform floor up forces a major, even in a year with no other break. The maintainer set SemVer's form and what takes a major (decisions.md, 2026-11-02 and 2026-11-03); when a major ships was left to the agents. How long a deprecation stands before its removal, beyond one minor, is not decided.

A prerelease tag takes SemVer's form, such as `v1.0.0-beta.1`, not RubyGems' `v1.0.0.pre.beta.1`. `release.yml` marks a version with anything but digits and periods in it a prerelease on GitHub.

## What a patch, minor, or major release may change

- **A patch release** fixes. It may move each runtime to a newer patch of its Ruby minor, such as 4.1.0 to 4.1.1, with a CHANGELOG entry: Ruby's patch releases fix bugs and security problems.
- **A minor release** adds what a 1.0 project does not use until it chooses to (`doc/contributors/design/public-interface.md`, "How 1.x adds"). It may add a runtime for a new Ruby minor, under the reserved asset names. It may move a runtime's patch, as a patch release may. A generated file may change in a minor release, since an upgrade does not regenerate it (decisions.md, 2026-11-03); Fledge writes no generated file a developer keeps.
- **A major release** may change anything frozen. Only a major drops the runtime of a Ruby minor, raises a platform floor, or stops `fledge build` running on an operating system version the last release ran on (decisions.md, 2026-11-03).

No release moves an app to a new Ruby minor. Ruby does not follow SemVer, so a new minor is expected to break what ran on the old one (decisions.md, 2026-11-03). Only the developer moves an app to it, by running `fledge build` with that Ruby ("Ruby minors and runtimes").

## Ruby minors and runtimes

A release carries one runtime of each Ruby minor it supports, for each platform, at one patch, the one `runtime/sources.yml` pins (on Windows, until RubyInstaller builds the release, a snapshot of Ruby's main branch: `doc/contributors/design/runtimes.md`, "Windows' Ruby until Ruby 4.1.0"). `fledge build` takes the runtime of the minor of the Ruby running it, and refuses a Ruby whose minor the release has no runtime for, naming both versions (`Fledge::CLI::Build#same_ruby`). The rule names a minor, not a patch: a developer who wants an exact patch writes `ruby "X.Y.Z"` in the Gemfile, and Bundler and Fledge then refuse every other.

Fledge has no default Ruby. The Ruby running `fledge build` is the one the developer chose and tested on, and every other way of naming an app's Ruby is a second statement of it that can disagree. A default would one day move to a new minor and break apps, which the maintainer allowed no minor release to do (decisions.md, 2026-11-03). A required Gemfile `ruby` line is what Heroku asks for, since no Ruby runs an app before Heroku builds it; Fledge always runs inside the developer's Ruby, and a lone `main.rb` would need a Gemfile only to say so. Reading `.ruby-version` would repeat what mise, rbenv, chruby, rv, `ruby/setup-ruby`, and Bundler's `ruby file:` already do. A `ruby` key in `fledge.yml` written by a generator, which the maintainer suggested, adds a command, a key, and a file that could name one minor on a computer running another. Briefcase and PyInstaller package the Python that runs them, the same way. The cost is that an app's Ruby follows the computer that builds it, so `doc/runtimes.md` tells developers to name it in `.ruby-version`, with `ruby file: ".ruby-version"` in the Gemfile.

The runtimes' asset names without a Ruby version mean the runtime of the Ruby minor 1.0 ships, for all of 1.x. A 1.x release that adds a second minor names that minor's assets with the reserved `-ruby-X.Y.Z-` part (`doc/contributors/design/public-interface.md`, "Reserved names"). Two minors side by side double the runtimes every CI run and release builds.

Before 1.0, a release may carry a preview of a Ruby minor, and any 0.x release may move it to a later preview or to the minor's final release; Windows runs RubyInstaller's head build of the day the preview appeared until RubyInstaller builds the release. 1.0 carries Ruby 4.1, which only a major drops, and waits for Ruby 4.1.0, by the maintainer's choice once Fledge's and Lota's agents agreed (decisions.md, 2026-11-09). Fledge's agents agreed because a 1.0 on Ruby 4.0 would have kept 4.0's runtimes through all of 1.x. So 1.0's date depends on Ruby's, which Fledge does not control.

### The day Ruby 4.1.0 appears

That is the day 1.0.0 waits for, not the candidate ("Versions"). Whether 1.0.0 ships on that day with RubyInstaller's head build of that day on Windows, or waits for RubyInstaller's own 4.1.0 build, is the maintainer's to decide, and nothing in Fledge assumes either. The evidence, from each project's release page, timed from Ruby's own tarball on `cache.ruby-lang.org` (its `Last-Modified`):

| Source | Ruby 4.0.0 (tarball 2025-12-25 04:08 UTC) | Ruby 4.1.0-preview1 (tarball 2026-10-12 09:07 UTC) |
|---|---|---|
| ruby/setup-ruby's builds (ruby/ruby-builder) | 3 hours | 1 hour |
| rv-ruby | 20 hours (release 20251225) | 11 days (release 20261022) |
| RubyInstaller | 2 days 9 hours (RubyInstaller-4.0.0-1) | none: it builds no preview |
| jdx/ruby | not datable: every release was republished on 2026-10-02 | 10 days |

- **On the day, with that day's head build.** `.github/workflows/keep-rubyinstaller-head.yml` keeps the head build of the day the tarball appears ("Keeping RubyInstaller's head build" in `runtimes.md`), a build of Ruby's master, not of the tag: Windows runs master of that day while every other platform runs 4.1.0, as Windows has run master beside each preview. Ruby moves master to the next minor near a release, so that build may already call itself 4.2.0dev, whose ABI and `RUBY_VERSION` are not 4.1's; it is usable only if it still says 4.1.0, which nothing in Fledge has checked on a past release day. A patch release then moves Windows to RubyInstaller-4.1.0-1. macOS and glibc Linux need not wait on rv-ruby either if their runtimes take Fledge's own build of the tag ("Fledge's own Ruby builds" in `runtimes.md`). The cost: 1.0.0's Windows runtimes are not 4.1.0, and its `RUBY_DESCRIPTION` there says `4.1.0dev`, so `Gem.ruby_version` is 4.1.0.dev on Windows and a Gemfile's `ruby "4.1.0"` fails there until the patch.
- **Either way, Windows' Ruby is configured unlike the others.** Ruby 4.1 adds `rb_len_t`, the type of String, Array, and MatchData lengths in the C API, "`long`, except on 64-bit mswin, where they are 64 bits" (`NEWS.md`, "Type for lengths and indices", Feature #22400, at ruby/ruby 72d4cf2e9a). RubyInstaller's head package, which is MinGW and not mswin, sets `CPPFLAGS+=" -DSIZEOF_RB_LEN_T=8"` (`mingw-w64-ruby-head/PKGBUILD`, line 62, at oneclick/rubyinstaller2-packages 3dd5c657), so there `rb_len_t` is 64 bits where `long` is 32. RubyInstaller added it on 2026-10-29 "to early raise issues with that change in gems" (commit 0f441be0), and no other package of theirs has it. So one Ruby commit on every runtime is not one build configuration. The kept head build of 2026-11-10, which the Windows runtimes are built from, has the flag: its `RbConfig::CONFIG["CPPFLAGS"]` begins `-DSIZEOF_RB_LEN_T=8`, and `RbConfig::SIZEOF` gives `rb_len_t` 8 bytes and `long` 4, read on x64 Windows from the archive `mise.toml` installs there. The struct layouts agree either way: an `RString` or `RArray` keeps its length in a field padded to eight bytes, so every offset is the same. Calls do not agree. A Rust gem built through rb_sys's Makefile binds `rb_len_t` 32 bits there under `gem install`; `fledge build` gives bindgen the flag, so a gem on rb-sys alone agrees with Ruby and a gem on magnus 0.9 does not compile (`gems.md`, "Rust gems on Windows and `rb_len_t`"). Whether RubyInstaller-4.1.0-1 keeps the flag is unknown, since no `mingw-w64-ruby41` package exists yet.
- **Waiting for RubyInstaller-4.1.0-1.** By 4.0.0's evidence, two to three days after the tarball, and longer if RubyInstaller's build falls on a holiday, as 4.0.0's did. Every platform then runs 4.1.0 in 1.0.0. The cost is the wait, and that the day itself is not 1.0's.

## Platform floors

A floor is the oldest operating system version a platform's apps run on. Fledge's are:

- macOS 26, on Apple silicon (`Fledge::Platform::MACOS_MINIMUM`), raised from 14 to 15 and then to 26 before 1.0, by the maintainer's leave, who would raise it to 26 if keeping 15 became costly (decisions.md, 2026-11-22): it did, when the Mac's Ruby moved to jdx/ruby's, whose files need macOS 26, to give gems the OpenSSL the runtime's Ruby has (`doc/contributors/design/runtimes.md`, "The Mac's Ruby is jdx/ruby's"). macOS 26 runs on every Mac with Apple silicon (Apple's "macOS Tahoe 26 is compatible with these computers", support.apple.com, article 122867);
- Windows 11, on x64 and on ARM64;
- iOS 15 (`lib/fledge/templates/ios/project.yml`);
- Android 8.0, API 26 (`minSdk` in `lib/fledge/templates/android/build.gradle`);
- glibc 2.28 on `x86_64-linux` and `aarch64-linux` (`Fledge::Platform::GLIBC_MINIMUM`), manylinux_2_28's, in which the runtime's own programs are compiled (`doc/contributors/design/runtimes.md`, "The glibc floor"). The maintainer first accepted 2.39, then asked for a lower floor "where a maintained upstream gives it" (decisions.md, 2026-10-26, decision 7, and 2026-11-22). It admits RHEL 8 and its clones, Debian 10 and later, Ubuntu 20.04 and later, and Amazon Linux 2023;
- musl 1.2 on the musl targets, the series PEP 656's `musllinux_1_2` tag names.

Linux has no single operating system version, so its floors are the C library's, as PEP 600's `manylinux_2_28` and PEP 656's `musllinux_1_2` tags name a Linux platform. Raising either drops whole distribution releases at once: glibc 2.29 would drop RHEL 8 and its clones, and Debian 10. So each counts as an operating system version: raising glibc 2.28 or musl 1.2 is a major, and so is dropping a distribution release that meets them. A patch within an operating system or C library version is not a floor.

The glibc floor is the runtime's, and an app's may be higher. A gem's extension compiled on the developer's computer needs the glibc it was compiled with, as glibc's symbol versions make it, when it calls a function glibc has changed or added since 2.28: compiled on Ubuntu 24.04, its glibc 2.39. `fledge build` ships such an app, because it runs wherever that glibc is, says in a warning what glibc the app now needs and that building on an older Linux lowers it, and gives its `.deb` that glibc in `Depends` (`doc/contributors/design/gems.md`, "The toolchain and the oldest systems"). It does not refuse the build, as it did while the floor was 2.39, Ubuntu 24.04's: then a developer on the newest Ubuntu met the floor exactly, and now nearly every developer's computer has a newer glibc than the floor, so a refusal would refuse nearly every app with a compiled gem. An app with no compiled gem, or only precompiled ones built for manylinux_2_28 or older, keeps the floor. This is how PEP 600 treats a wheel built on a newer system: `auditwheel` names the newest manylinux tag its files meet, rather than refusing it.

Raising a floor is a major, always, even when a store's rule forces it. A store's yearly rule that drops no version is not a floor: Google Play's target API level and the Xcode version App Store uploads need live in the phone templates, which any release may change, with a CHANGELOG entry. Android's `minSdk` and iOS's deployment target are floors.

Windows 11 is the floor because Microsoft's support for Windows 10 ended on 2025-10-14 (support.microsoft.com, "Windows 10 support has ended on October 14, 2025"), before Fledge's first release, and the maintainer would not have Fledge name it (decisions.md, 2026-11-21). Nothing in an app refuses Windows 10: the launcher's manifest names the `supportedOS` that Windows 10 and 11 share, and an MSIX package's `MinVersion` is Windows 10 1809, as electron-builder's is (`doc/contributors/design/desktop-apps.md`, "The MSIX package"). But no run there is recorded, and none is promised. Windows 11 is proven on x64 by CI's Delivery on Windows Server 2025, which is build 26100 as Windows 11 24H2 is, and by a game on a real computer: the maintainer installed, played, reinstalled, and uninstalled Dot Popper 0.8.1, built with Fledge v0.5.0, on a Windows 11 PC on 2026-11-05 (setdef/dot_popper, `doc/playtests/2026-11-05-windows.md`). On ARM64 it is proven by CI's Delivery on `windows-11-arm`.

The macOS 26 floor is proven by running, as the others are: CI builds and runs apps on `macos-26` ("Which macOS each job runs on"). The build aims at it too: the launcher and `bin/ruby` are built with `-mmacosx-version-min` at the floor (`doc/contributors/design/runtimes.md`), a Mac app's `Info.plist` names it as `LSMinimumSystemVersion`, so macOS 14 will not open the app, and what Fledge compiles for an app is aimed at it with `MACOSX_DEPLOYMENT_TARGET` (`doc/contributors/design/gems.md`, "The toolchain and the oldest systems"). The license audit refuses a runtime with a Mach-O file that needs a newer macOS than the floor (`doc/contributors/design/license-audit.md`); jdx/ruby's Ruby, which every file of the runtime but Fledge's own programs comes from, is built for macOS 26 by its runner's default, not by a setting of its own, so a build of it on a newer runner would fail that check rather than raise the floor (`runtimes.md`, "The Mac's Ruby is jdx/ruby's"). While the floor was 14, it stood on the build alone, since GitHub retired its macOS 14 runners on 2026-11-02 and no workflow of Fledge's ever named one.

The same rule holds where `fledge build` runs: a release that stops building on an operating system version the last release built on is a major.

## Support follows live Rubies

For each Ruby minor that is not end-of-life, the last Fledge minor line to support it gets security fixes for the embedded runtime, and platform-deadline fixes where feasible, until that Ruby is end-of-life. The last minor before a Ruby is dropped says so at build time and in its CHANGELOG, and names itself the long-term line for that Ruby, with the date. That line's release branch, such as `release/1.7`, takes its fixes. A line that is the last for no live Ruby gets nothing. A new feature never goes to an old line.

So the patched lines number about one per live Ruby minor, three or four, however high the Fledge number climbs. A platform-deadline fix on an old line may need newer toolchains and rebuilt runtimes; that promise is best effort, and the CHANGELOG says when a fix cannot be made. End-of-life dates come from ruby-lang.org's maintenance page when a line becomes a long-term line.

## Where releases are

Every release is a git tag, `vX.Y.Z`, and a GitHub Release at https://github.com/setdef/Fledge made from it, which carries the prebuilt runtimes as assets, before 1.0 and after (decisions.md, 2026-11-04). Before 1.0 that is the only way a release can be found, and developers install Fledge from its tag with Bundler, as Ferro releases by tag.

Agents push `trunk`, push tags, and create GitHub Releases before 1.0 (decisions.md, 2026-10-26, decision 6). Agents never publish to RubyGems.org; that is a human-only activity, now and after Fledge is there (decisions.md, 2026-11-02, later). The gemspec's `allowed_push_host` points nowhere, and `tasks/package.rake` replaces `rake release` with one that refuses. From 1.0.0, each release is also published on RubyGems.org, and the tag and the GitHub Release stay (decisions.md, 2026-11-03 and 2026-11-04): by the maintainer's hand, or by a deterministic process he has decided to trust with it, such as a release workflow that RubyGems.org is set to trust, which counts as his act (decisions.md, 2026-11-22). `release.yml`'s last job is that workflow, and does nothing until he sets it up: setting RubyGems.org to trust it, and the repository variable that says he has, are done in his account, and `doc/contributors/releasing-1.0.md` is his checklist for both ("release.yml", below).

A GitHub Release holds, for each desktop platform:

- `fledge-runtime-VERSION-PLATFORM.tar.gz`, the runtime;
- `fledge-runtime-VERSION-PLATFORM.spdx.json`, its SPDX SBOM;
- `fledge-runtime-VERSION-PLATFORM-NOTICES.txt`, its notices;
- `fledge-runtime-VERSION-PLATFORM-lgpl-sources.tar.gz`, the sources its licenses ask for, on the platforms that ship such a component.

A phone runtime has the first three. A `SHA256SUMS` over all of them is the tagged commit's `lib/fledge/SHA256SUMS`. `RuntimeBuilder.release_assets` (`tasks/runtime_builder.rb`) is the list, and `release.yml` refuses any other set.

A release is never deleted. Each runtime's NOTICES links its source bundle at the release, after the copy in the app's own `notices/sources/` (`doc/contributors/design/license-audit.md`, "notices/sources/ and the source bundles"), and the schema's address names the release's tag (`doc/contributors/design/public-interface.md`, "The fledge.yml schema").

## The pins

`lib/fledge/SHA256SUMS` holds one line per release asset, sorted by name, in the form `sha256sum` writes and `sha256sum -c` reads: the hash in lowercase hex, two spaces, and the name. `Fledge::Runtimes` takes the SHA-256 of every runtime it downloads from this file, and checks a runtime in the cache against it too, downloading it again when it does not match. A version whose file names no SHA-256 for a runtime is a commit between releases, and `fledge build` says it is not a released Fledge, naming `FLEDGE_RUNTIME_DIR`. A runtime in `FLEDGE_RUNTIME_DIR` is checked against its pin too, when the file has one, since that folder is how a developer builds offline from a copy of the release; a contributor's own build there is used only when `FLEDGE_RUNTIME_DIR_UNCHECKED` says so, as every workflow and task that builds apps from fresh runtimes does (`doc/contributors/design/runtimes.md`, "Where fledge build finds a runtime").

The pins come from the gem, never from the release: a `SHA256SUMS` fetched from the host that serves the file catches a damaged download, but not a release whose assets and sums were both replaced. A version cannot pin files built after its tag, and runtime builds are not reproducible, since each runner's tar writes the archives and each runner compiles the launcher. So the release commit's CI builds the runtimes and a child commit pins those very bytes, as Homebrew's `brew pr-upload` commits a formula's bottle hashes from the bottles its CI built and then uploads the same bottles (`Library/Homebrew/dev-cmd/pr-upload.rb` at Homebrew/brew 1f55ebf8). uv's pins of python-build-standalone fit files another project built earlier, not ones built for the very version that pins them. Reproducible builds would let one commit pin, at the cost of byte-identical output on every system, and nothing here rules them out. The file is `sha256sum`'s format because the release already publishes it and every system's tools read it.

`rake runtime:pin` (`tasks/runtime_pins.rb`) writes the file. It downloads the runtime artifacts of the release commit's CI run with the GitHub CLI, refuses unless that run passed on every job and its artifacts are exactly `RuntimeBuilder.release_assets` for the version, and writes their SHA-256s. It takes every artifact named `runtime-*`, as the pin commit's check and `release.yml` do, so only a runtime job's release assets carry such a name: a runtime job that fails keeps its build's logs as `logs-runtime-PLATFORM`, because a job that fails once and passes when run again leaves that artifact in the run for good, where the pin and the release would take it for an asset and refuse the run (`test/workflow_artifacts_test.rb`).

## How a release is made

A release is two commits and a tag, made off `trunk` on a branch of their own, and then one commit on `trunk` that records it. `.github/workflows/cut.yml` makes them all, with nobody in the loop, and `pin-watch.yml` runs it once a move of the pins is green on trunk (`runtimes.md`, "Keeping the pins current"). By hand, on a commit whose run of `ci.yml` passed on every job ("Which runs are a commit's"):

```sh
gh workflow run cut.yml -f commit=SHA                 # both commits and their CI; stops before the tag
gh workflow run cut.yml -f commit=SHA -f publish=true # the release
```

Its Cut job runs `.github/scripts/release-cut.sh` on the picked commit:

1. **The release commit**, with the message `chore: release X.Y.Z`, on the picked commit. `tasks/release_commit.rb` chooses X.Y.Z from the CHANGELOG's `[Unreleased]` entries at that commit by the rule of "Versions": before 1.0, an entry that starts "Breaking", or a `### Removed`, moves the middle number, and anything else, a moved pin among them, the last; from 1.0, a break moves the first, an addition or a deprecation the middle, and anything else the last. It writes the version wherever a release names it (`Fledge::VERSION`, `Gemfile.lock`, README.md and README.rdoc, the `$id` of `lib/fledge/config.schema.json`, and the modeline in `Fledge::Config`'s RDoc, the last two of which `test/config_schema_test.rb` holds to `Fledge::VERSION`), moves the unreleased entries under `## [X.Y.Z] - DATE` with its link, and `rake licensing` writes the version into `doc/licensing.md`. The script pushes it to the branch `release-next`, which only `cut.yml` writes, and starts a full run of `ci.yml` there, which builds every runtime, delivers each on a fresh runner, and runs ruby/spec on all seven desktop platforms; beside it, `installed.yml` on the picked commit against the last release ("installed.yml", below). It waits for both.
2. **The pin commit**, with the message `chore: pin X.Y.Z's runtimes`, changes only `lib/fledge/SHA256SUMS`, which `rake runtime:pin` writes from the release commit's run ("The pins"). It is pushed to the same branch, and its short run ("A pin commit's short CI") is started and waited for.
3. **The tag** goes on the pin commit, `vX.Y.Z`. Its push starts `release.yml` by itself, which publishes on a pushed tag ("release.yml", below), so the cut starts no run of it and waits for the one the push started; it ends by running `installed.yml` on the release, and the release is verified when that passes. Then the branch is deleted.

Its Record job then runs `.github/scripts/release-record.sh` on `trunk` as it stands by then: the same version strings, the pins of the pin commit, `doc/licensing.md`, and the CHANGELOG with the entries that were unreleased at the picked commit moved under the release, and those that landed since left under `[Unreleased]` (a pin's line that a second move rewrote after the pick names, as the version it moved from, the one the release shipped), in one commit, `chore: record X.Y.Z on trunk`. A push another push beat is made again on the new trunk, three times. From that commit on, trunk's commits name the release and its pins, as commits between releases always have ("installed.yml", below). Without `publish`, it stops before the tag, so a change to the release's path is tried by running it so, and it publishes and records nothing.

Any job of the runs it waits for failing fails the run, which calls a person: GitHub tells the account that owns the schedule of `pin-watch.yml`, or whoever started `cut.yml` by hand (`runtimes.md`, "The proof"). The runs it starts notify nobody, since their actor is `github-actions[bot]`, which is why it waits for each in the job.

**The push token.** The run's own token holds no `workflows` permission, so GitHub refuses a push that brings in a workflow file no branch holds, which is so of any picked commit that comes after a change to the workflows on `trunk`; and a push made with it starts no workflow. A release cannot do with either. So the Cut job names the environment `release`, which is limited to the branch `trunk` and holds the secrets `RELEASE_APP_ID` and `RELEASE_APP_PRIVATE_KEY` of a GitHub App the maintainer registered for this alone (issue 74: GitHub itself recommends an App over a deploy key, "About creating GitHub Apps", for its fine-grained permissions and its tokens that expire, where a deploy key with write access can push anything and never expires). The App was asked to have the repository permissions Contents and Workflows, both read and write, and to be installed on this repository only; only the maintainer can see either. The job mints an installation token with `actions/create-github-app-token`, pinned by commit as every action is, asking for those two permissions and no more, in a step before each push (the release commit's, the pin commit's, the tag's, and the branch's deletion), since a token lasts an hour and the job runs for hours. `release-cut.sh` is therefore run in stages, one step each between the mints, and takes the token as `RELEASE_PUSH_TOKEN`, which it uses for those pushes only. Everything else the job does, starting and waiting for runs among it, and the Record job's push to `trunk`, keep the run's own token, which is why the one is named in each place.

Because a push made with an App's token starts workflows, the push of the tag starts `release.yml` (`on: push: tags`) by itself, and the cut waits for that run, found by its commit and its event, and never dispatches another: two runs of it would race to create the same release. The push of a branch starts the fast tier (`fast.yml`, `fast-macos.yml`) on `release-next`, as a push to any branch does; no run of `ci.yml`, which the cut starts on the branch itself. The environment's rule is on the branch the run is from, so it is met by `cut.yml` started by hand on `trunk` and by `pin-watch.yml`'s schedule alike, since both run from `trunk`. Until 2026-11-23 the pushes were made with the run's own token, and a cut passed only on a commit whose workflow files equalled `trunk`'s when it started (issue 25).

For 1.0.0, the release commit also makes the gem pushable and changes the install line, and `release.yml` publishes the gem once the maintainer has set up the trust it needs; `doc/contributors/releasing-1.0.md` lists all three. The step to 1.0.0, and the release candidate's middle number, are a person's to name: `tasks/release_commit.rb` never chooses either.

The pin commit changing only the pins is what ties the published runtimes to the tagged source: every file a runtime is built from is the same in both commits. So the pin commit is the release commit's child, and nothing lands between them; on `release-next` nothing else ever does. The two commits were made on `trunk` itself until 2026-11-22, each pushed alone. A release commit's run takes one to three hours, and on a trunk that takes a push every few minutes the pin commit then almost never finds its parent at trunk's head, so a release with nobody to wait for a quiet hour could not land. Other ways were weighed. Freezing trunk for the hour is the wait trunk-based development forbids. A release with no release commit, its version stamped from the tag at build time, as a release from a tag on trunk can be, does not fit Fledge: Bundler installs the gem from the tagged commit's own files, so the version and the pins have to be committed, and the pins only after the runtimes they name are built. So the release is picked, not built up: it tags a commit CI proved, wherever trunk has gone, and trunk is written once, after, by a commit nothing waits for. The tagged commits are not on trunk's line; the tag keeps them, and a release is never deleted. A commit made before `cut.yml` existed cannot be cut by it, since it uses the picked commit's own `tasks/release_commit.rb`.

## Runs, batches, and the release commit

A push to `trunk` never cancels the run of `ci.yml` in progress there. GitHub keeps at most one run going and one waiting in a concurrency group, and a newer push replaces the waiting one. So every run that starts finishes, and it covers a batch: every commit pushed since the run before it started. A red run blames the whole batch. The fast tier runs on every push, never cancelled on `trunk`, and its verdict on each push narrows the blame: `.github/workflows/fast.yml`, the lint and the package check on Linux and the unit tests on Linux and Windows, in a few minutes, and `.github/workflows/fast-macos.yml`, the unit tests on macOS, whose verdict comes when a macOS runner does. A push to any other branch cancels that branch's runs of the fast tier, and starts no run of `ci.yml`: a full run asks for about an hour of several macOS and Windows runners, so a branch gets one when it is started on purpose (`gh workflow run ci.yml --ref BRANCH`), as `pin-watch.yml` and `cut.yml` start theirs on `pin-move` and `release-next`, or for a pull request, and then a newer one cancels it. From 2026-11-08 to 2026-11-14, before this, about a hundred full runs started on `experiment/*` branches, a fifth of all of them, and 34 were cancelled part way by the next push.

So every push gets a verdict, and nobody waits for CI to push, which trunk-based development forbids. Cancelling a trunk run for each newer push would leave trunk with no finished run while agents push every few minutes. Running all of `ci.yml` on every push, never replaced, would queue hours deep, since a run asks for about an hour of several macOS and Windows runners. Without the fast tier a push would wait up to two hours for a verdict, and a red batch would have nothing to narrow it. The fast tier is a workflow of its own because GitHub ends a run only when its slowest job ends, and the whole gate stays in `ci.yml`, since a pin commit's short run needs it. The package check, the gate's last task, runs in the fast tier as well, and in `bin/check` before the push, because it takes about two seconds and nothing else there loads Fledge as an installed gem, with only the gemspec's gems: on 2026-11-22 a `require` of `prism`, a gem Ruby 4.1 no longer carries as a default gem and the gemspec did not name, passed the fast tier and failed eight jobs of the full run an hour later. The costs are the batch's blame, and the macOS leg's wait.

That wait is why the macOS leg is a workflow of its own too. GitHub's hosted macOS runners on Apple silicon come late when demand is high ("During periods of high demand, jobs that run on macOS runners may take longer to start", GitHub's [GitHub-hosted runners reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)), and the jobs that waited longest carry GitHub's annotation "Due to capacity constraints, jobs targeting macOS arm64 runners may experience longer queue times." When the macOS unit tests were a job of `fast.yml`, on `macos-15`, they held the verdict of every push: over the 155 pushes to `trunk` from 2026-11-12 to 2026-11-19, the job waited a median of 22 minutes for a runner, 56 at the 90th percentile and two and a half hours at worst, and then ran for 41 seconds, while the Linux and Windows jobs waited seconds. Three ways out were weighed:

- **Another label for the same job.** `macos-26` waits less, but not little: in the full runs of the same week, a job created on `macos-26` at the same instant as one on `macos-15` waited a mean of 11 minutes to the other's 19 (79 such pairs), and a job on `macos-26` waited a median of 6 minutes and 35 at the 90th percentile on 2026-11-19. The verdict would still wait on GitHub's macOS capacity.
- **No macOS in the per-push tier.** The verdict comes in minutes, and the unit tests that only a Mac runs (those that call `plutil`, and the Mac app bundle's tests in `test/support/assembly.rb`) are judged only once a batch, by `ci.yml`'s Test (arm64-darwin), so a red batch from one of them has nothing to narrow it.
- **The macOS leg in a workflow of its own,** which was chosen. `fast.yml`'s verdict comes in minutes, and every push still gets a macOS verdict of its own, later. It gives up nothing that the per-push tier proved, at the cost of a second workflow with the steps of `fast.yml`'s unit job, and a second verdict per push to read.

The macOS leg runs on `macos-26`, because any current macOS on Apple silicon will do for the unit tests, and its runners came sooner; it no longer runs the unit tests on macOS 15 for each push, which `ci.yml`'s Test (arm64-darwin) still does for each batch. Its bundle cache is keyed by the runner's image, as every installed-gems cache is ("Installed gems in CI"), so a bundle built on macOS 26 is never restored on `macos-15`.

A run belongs to the commit at the head of its push, or of the branch it was started on ("Which runs are a commit's", below). A commit pushed with others after it, or one whose waiting run a newer push replaced, has no run of its own, and `tasks/ci_runs.rb` finds nothing for it: it says so, and that the commit has to be pushed alone, as the head of its push. A batch's run proves its head, so a commit inside a batch cannot be a release commit, and cannot be a pin commit's parent.

The release commit and the pin commit are made on `release-next`, and each is the head of the run `cut.yml` starts for it there, so neither is ever inside a batch. A release or pin commit pushed to `trunk` by hand, as releases were made until 2026-11-22, gets a concurrency group of its own, named for its commit, when its message starts `chore: release ` or `chore: pin `, so that its run starts at once and no later push replaces it. `ruby-spec.yml` runs on all seven desktop platforms for a commit whose subject starts `chore: release `, however its run was started.

## The full run's longest path

A full run takes as long as its longest chain of jobs, each of which waits for the jobs it needs. That chain is the iOS one: Runtime (ios), which compiles Ruby for the phone on `macos-26`, then the jobs that use that runtime. In the four full runs on `trunk` of 2026-11-22 that ran every job, Runtime (ios) took 13.5 minutes, and Mobile apps (iOS Simulator) 47: 28 to build the apps and run them in the Simulator, then 13 to 16 for the iOS integration tests, in the same job. Those 60 minutes were nearly all of each run's 57 to 65. No other chain came within ten minutes of it: Test (aarch64-mingw-ucrt), the longest of the rest, took 32 after a runtime of one, until its tests were split in two (below).

The apps and the integration tests share nothing but their setup: each builds its own apps, from the same two runtimes, on a Simulator of its own. So they are two jobs, Mobile apps (iOS Simulator) and iOS integration tests (iOS Simulator), which start together once the runtimes are built, and the run waits for the longer of the two instead of their sum. The cost is the setup run twice, mise's Ruby and Rust, the Xcode, XcodeGen, and the two runtimes' download, a few minutes of a macOS runner a run, and a second macOS runner at once, which GitHub may be slow to give ("Which macOS each job runs on"). Whatever a test or an app checked before, it checks still, on the same runner image; only when it runs changed. Continuous Delivery's advice for a slow acceptance stage is the same: run its tests in parallel, on as many machines as the stage needs (Humble and Farley, *Continuous Delivery*, chapter 8, "Parallel Testing").

The Windows tests are split the same way, for a reason of their own: room under their limit. Their one step, `rake test:all`, took 26 minutes on ARM64 on one runner, and on a slower one ran out its 35-minute limit, which turned a full run red with no commit at fault and held back the pin move and the release that wait for a green one. So each Windows platform's tests run as two jobs at once, Test (PLATFORM, 1 of 2) and Test (PLATFORM, 2 of 2). Shard 1 runs the tests of `test/integration/built_app_test.rb` whose names say `bundle`, and the parity check; shard 2 runs every other test, and the console checks. In a green x64 run of 2026-11-22 those seven tests took 438 seconds of the 1,157, and parity 367, so the shards come to about 13 and 12 minutes, where the one job ran 19.5 and then 6. The pattern is one value, `SHARD_1_TESTS`, handed to minitest as `N` in shard 1 and as `X` in shard 2, and minitest's include and exclude filters test a name with the same expression (`Minitest::Runnable.filter_runnable_methods`, minitest 6.0.6), so the two shards are complements by construction: no test runs twice, and none is left out, whatever tests are added. `test/workflow_shards_test.rb` keeps the workflow so, and the two jobs' "runs" lines sum to what the unsplit job ran. Two things on Windows bend the pattern on its way to minitest. Git Bash, the shell of those steps, rewrites a value that looks like a path when it starts a Windows program, so the step names `N` and `X` in `MSYS2_ENV_CONV_EXCL`; were that ever ignored, shard 1 would match nothing and fail, as minitest fails a run whose include filter ran no test. And `Minitest::TestTask` passes `N` and `X` through `Shellwords.escape`, whose backslashes a POSIX shell removes and nothing on Windows does, so `^`, `*`, `(`, and `|` would reach minitest escaped, match nothing, and leave shard 1 empty and shard 2 the whole suite; the pattern is written in characters that escape leaves alone (`/BuiltAppTest.test_.+bundle/`), which the unit test checks. The limits stay as they were, 35 minutes for the step and 45 for the job, now with room on the slowest runner seen. The cost is the setup, about a minute, run twice on each platform, and one more Windows runner at once, which is cheap beside a red run.

## The runtime's commit stage

The fast tier judges each push's lint and unit tests, and nothing in it builds a runtime, so until 2026-11-22 a commit that broke a runtime, or an app built from one, was judged only in the batch of the next full run, an hour later or more, beside every other commit of that batch. Such batches were the reddest: of the 105 full runs on `trunk` from 2026-11-08 to 2026-11-22, the 44 whose batch changed what a runtime is built from went red 23 times, and the other 61 went red 11 times.

So `.github/workflows/runtime-proof.yml` runs on each push to `trunk` that changes what the proof reads, in a group of its own named for its commit, as `fast.yml`'s are: the proof a contributor runs before the push of a runtime change, `rake runtime:prove[x86_64-linux]`, which `bin/check --runtime` runs once its fast check passes (CONTRIBUTING.md, "Before the push of a runtime change"). It builds the x86-64 Linux runtime as the Runtime job does, then runs the parity check, Delivery of hello and my_cool_app with their parity probes, Delivery of `build --from`, and the licensing page's test, on one `ubuntu-24.04` runner in about a quarter of an hour. The command before the push and the job after it are one task, so the two cannot drift apart; the fast check is left out of the job because `fast.yml` runs it on the same push. This is the commit stage of Humble and Farley's deployment pipeline (*Continuous Delivery*, chapters 5 and 7, "The Commit Stage"), and Duvall's staged builds (*Continuous Integration*, chapter 4, "Stage Builds"): a short build on every commit, ahead of the long one that covers the batches.

Its paths are generous, because a push it skips is judged only in its batch: what a runtime is built from (`runtime/`, the launcher in it, `tasks/`, `lib/`, `mise.toml` and `.config/mise/`, which pin the reference Ruby, `LICENSE` and `LICENSES/`), what builds and runs the apps (`exe/`, `.github/scripts/`, `bin/`, `examples/`, `test/fixtures/`, the bundle), and what the licensing test reads. `test/workflow_runtime_proof_test.rb` follows `tasks/runtime_proof.rb`'s `require_relative`s and the paths of the repository they name, and fails when the paths miss one. In the week to 2026-11-22, 176 of trunk's 249 commits touched those paths, about 25 a day: some six hours of a Linux runner a day, about $2.25 at list price, against the full runs' $9.6 each.

It adds to the full run and takes nothing from it: `ci.yml` still builds every runtime and tests and delivers each on its own platform, the release still needs every job of a full run green, and `cut.yml` and `pin-watch.yml` still look only at `ci.yml`'s runs. One platform is enough for a commit stage because most runtime changes reach every desktop runtime alike, as the proof before the push assumes; the others, the phones among them, stay the full run's. The Android proof (`bin/check --runtime=android`) builds two runtimes and boots an emulator, about 19 minutes on a Linux computer with KVM, which is no commit stage's length, so it stays a proof before the push.

### Why each full run builds its runtimes again

The iOS, Android, and musl runtimes compile Ruby, and each full run builds them again even when its batch changed nothing they are built from. Reusing an earlier run's build when nothing changed is Humble and Farley's "Only Build Your Binaries Once" (*Continuous Delivery*, chapter 5). It was weighed on 2026-11-22 and not taken. A reused runtime proves the commit only if its key covers every input, and a key that covers them for certain changes with anything under `runtime/`, `lib/`, `tasks/`, `.github/`, `mise.toml`, or the pins, and on every release commit. Of the 106 full runs on `trunk` from 2026-11-08 to 2026-11-22, 11 had a batch that changed none of those, only documents, tests, or examples. A hit saves about $0.97 at list price (Runtime (ios), 13.5 minutes of `macos-26`; Android's, 9.8 of Linux; the two musl ones, about 12), so about 1% of what the full runs cost, and 13 minutes of the longest path in one run in ten. That does not pay for a key, and for a lookup of another run's artifacts, on the path that proves a release. A narrower key, made of the files the phones' builders read, would hit more often, and would prove nothing on the day it missed one.

## The Android setup from nothing

`.github/workflows/android-setup.yml` runs the setup CONTRIBUTING.md's "Android on Linux" has a person type, on an `ubuntu-24.04` runner with no cache of mise's downloads: `MISE_ENV=android mise x -- ruby tasks/setup.rb`, which installs every tool `mise.android.toml` pins, then `bin/android-sdk`, then `.github/scripts/check-android-sdk.sh`, which reads the SDK through its links and runs `java`, `cmake`, and `adb`. No other job does: CI's Android jobs use the runner image's own JDK, CMake, and SDK, so a change to the setup, or a pinned download that its host removed, would break the documented way to build the Android runtime with nothing to show it (issue 14). It downloads about five gigabytes (the same setup took about five minutes from an empty workspace on a build machine), so it is not a job of `ci.yml`, which every push queues. It runs on a push to `trunk` that changes `mise.android.toml`, `tasks/setup.rb`, `bin/android-sdk`, or its own two files, and once a week, which finds a download that has gone from its host. It is a workflow of its own, not a job of `runtime-proof.yml`, whose paths take every change under `tasks/` and `runtime/`, or of `ruby-spec.yml` or `ruby-master.yml`, which run every night on what trunk passed. As every scheduled workflow does, it reports by failing its run, which GitHub tells the account that owns the schedule; `keep-schedules.yml` enables it again if GitHub disables it. It judges no push, so a red run of it does not make `trunk` red.

## Which runs are a commit's

A run of `ci.yml` is a commit's run when it tested that commit's files with the jobs that commit calls for. A push's run does: its `GITHUB_SHA` is the commit pushed. So does a run started on a branch whose head is the commit, by hand or by a workflow (`workflow_dispatch`), whose `GITHUB_SHA` is the last commit on the branch it was started on ("Events that trigger workflows", docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows, the table of each event's `GITHUB_SHA`), which the API reports as the run's `head_sha`, and whose workflow file is that commit's own. A pull request's run is not one: its `GITHUB_SHA` is a merge of the pull request's head into its base, whose files are not the head's. And `ci.yml` chooses its jobs from the commit alone: `Changes` tells a pin commit by its files and a release commit by its subject, on a push and a dispatch alike, and no job asks which event or branch started it.

So `tasks/ci_runs.rb` takes a run of a push or of a dispatch of the commit, on any branch, and never a pull request's, and `rake runtime:pin`, a pin commit's check, and `release.yml` take a dispatched run as they take a push's. A push made with a workflow's own token starts no run (`runtimes.md`, "The proof"), so this is what lets a workflow prove a commit at all. What a dispatched run does not share with a push's is its concurrency group: a dispatched run has no `head_commit`, so even a release or pin commit's run shares its branch's group, where on any branch but trunk it cancels the run before it. That changes when a run starts, not what it proves.

Taking only runs of a push to trunk, as `tasks/ci_runs.rb` did until 2026-11-22, held the pins and the release to commits a person or an agent had pushed, since a workflow's push starts no run. A token of an account or an app whose pushes do start runs would keep that rule, at the cost of an account and a stored secret, which are the maintainer's to give (AGENTS.md, "Questions"), for no difference in what the run proves. The cut's App is such a token (above), and takes no run of `ci.yml` from it: `ci.yml` runs on no branch but `trunk` by a push, so the cut still starts its runs on `release-next` by dispatch.

## A job no runner took

GitHub's hosted runners run short now and then, macOS arm64's most of all. A job that no runner takes waits, and after a while GitHub cancels it with no runner, no steps, no log, and a failure annotation: "The job was not acquired by Runner of type hosted even after multiple attempts" (`gh api repos/setdef/Fledge/check-runs/JOB/annotations`). The jobs that need it are skipped, so the run is red though nothing in it failed, and it proves little. Of this repository's runs from 2026-11-10 to 2026-11-19, it happened to 19 jobs in 15 runs, 10 of them on `trunk`, the first on 2026-11-12, and every one of them a macOS job (`macos-15`, or `macos-26` for the iOS Simulator). In those runs no job lost a runner it had: every other job cancelled with no steps was cancelled by a person, by a newer run in its concurrency group, or by its time limit, each with an annotation that says so.

`.github/workflows/runnerless.yml` puts such a run right. It runs when a run of CI, Fast, Fast (macOS), or ruby/spec on `trunk` ends, and `tasks/runnerless_runs.rb` reads the run's jobs and their annotations from GitHub's API. Only when the run failed, and every red job in it was cancelled with no runner, no steps, and that annotation, does it ask GitHub to run the failed jobs again, as `gh run rerun --failed` does (`POST /repos/OWNER/REPO/actions/runs/RUN/rerun-failed-jobs`). GitHub then runs those jobs and every job that needs them, and keeps each job that passed, with what it uploaded ([Re-running workflows and jobs](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs)). A run in which any job ran a step and failed, or was cancelled for another reason, by a person, a newer push, or its time limit, stays exactly as it is, runnerless jobs and all: whoever runs it again decides about the real failure too. A run is run again at most twice (`RunnerlessRuns::ATTEMPTS`), and perhaps only once (below), so a runner that never comes leaves the run for a person.

Only `trunk`'s own runs are run again, never a pull request's. A rerun joins its run's concurrency group again, and on any other branch a newer push's run is in progress there, which the branch's `cancel-in-progress` would cancel; a pull request's run is in its pull request's group, and its head branch may be a fork's `trunk`. The workflow's trigger sends no other run, and `tasks/runnerless_runs.rb` leaves any other it is given, so running the workflow by hand with `dry-run` off does only what the trigger would have done: the safety is in the code that asks for the rerun, not only in which events start it. On `trunk` a rerun of a run in trunk's shared group waits behind the run in progress, as any run does, and a newer push replaces it while it waits; the newer run covers its commits. GitHub keeps one run waiting in a group, and a rerun would replace a newer push's run already waiting there ([Control the concurrency of workflows and jobs](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)), so a run is not run again while a newer run waits in its own group. A run waiting in another group, a pull request's from a fork's `trunk` among them, is no reason to leave it, since its rerun cannot touch that run. The API names no run's group, so `tasks/runnerless_runs.rb` reads it as each workflow's `concurrency` block names it, from the run's event, commit, and commit message: in `ci.yml` a push of a release or pin commit has a group named for its commit, and every other run shares trunk's; in `fast.yml` and `fast-macos.yml` every run of `trunk` has its commit's own; `ruby-spec.yml` has none. So a release commit's run and a pin commit's run again at once, whatever waits in trunk's group, which while agents push is most of the time; so does a run of the fast tier, unless a run of its own commit waits; and a run of a workflow whose group the code does not know is left. `test/runnerless_runs_test.rb` holds a copy of each workflow's `concurrency` block, and fails when one changes until the code reads the new one. A few seconds pass between the look at what waits and the request for the rerun, and a push's run that begins to wait in them is replaced by the rerun; the next push's run covers its commits, as it covers every replaced run's, and the fast tier has judged each of them meanwhile.

A healed run leaves nothing that the pins or the release refuse. A job that never started uploaded nothing, and its rerun uploads what it would have uploaded the first time. `tasks/ci_runs.rb` takes each job's latest attempt, so `rake runtime:pin`, a pin commit's check, and `release.yml` count a healed run once its jobs pass: 0.14.0's runtimes come from run 44513751573, whose Delivery (arm64-darwin) never got a runner on its first attempt and passed on its second.

The workflow's own `GITHUB_TOKEN` is enough, with `actions: write` and `checks: read`. It is a GitHub App installation access token ([GITHUB_TOKEN](https://docs.github.com/en/actions/concepts/security/github_token), "About the GITHUB_TOKEN"), and the rerun endpoints take such a token with the Actions permission to write ([REST API endpoints for workflow runs](https://docs.github.com/en/rest/actions/workflow-runs), "Re-run failed jobs from a workflow run"). The rule that events the token triggers create no workflow run is about new runs; a rerun is another attempt of a run that exists, and it runs with the privileges of the actor who started the run, not of whoever asked for it (Re-running workflows and jobs). GitHub says that "events triggered by the GITHUB_TOKEN will not create a new workflow run", but for `workflow_dispatch` and `repository_dispatch` (GITHUB_TOKEN, "When GITHUB_TOKEN triggers workflow runs"), and does not say whether the end of an attempt the token asked for is such an event. If it is, no `workflow_run` follows the second attempt, and "at most twice" is once in practice: a second attempt that also finds no runner stays red for a person. Which it is is not known until a healed run's second attempt loses a runner too.

Other ways were weighed. GitHub has no setting that retries a job no runner took, and no `retry` key for a job ([Workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax)). k1LoW/rerun-action (`action.yml` at 85ba44f8) runs every failed job again when a pattern shows in their logs: a job no runner took has no log, and the action would run a real failure again beside it. A step at the end of each workflow that starts a rerun workflow with `workflow_dispatch` would be one more job in every workflow, and GitHub reruns only a run that has ended, which the run's own last job cannot wait for. Runners of Fledge's own, or GitHub's larger runners, would need hardware or billing the project does not have. Projects that met the same failure settled on the same shape: a `workflow_run` workflow that reads the annotations and runs failed jobs again only when every red job carries GitHub's "not acquired" annotation, capped at a few attempts: cesiumlang/zfls (`.github/workflows/rerun-unacquired.yml` at 0c3fee9b), link-foundation/csharp-ai-driven-development-pipeline-template (`scripts/runner-acquisition.mjs` at 88bb7183, which also finds that a job with no runner and no steps is not enough evidence, since a job its concurrency cancelled looks the same but for its annotation), and pyreon/pyreon (`.github/workflows/required-check-autoheal.yml` at 01cec18c, which also leaves a run that a newer one superseded).

A `workflow_run` workflow runs only from the default branch, so `runnerless.yml` cannot be tried on a branch before it is on `trunk`. What can be shown beforehand is shown: `test/runnerless_runs_test.rb` serves GitHub's recorded answers for real runs, some to run again and some to leave, and `ruby tasks/runnerless_runs.rb RUN ATTEMPT --dry-run` asks GitHub's real API and runs nothing again, as running the workflow by hand does with its default `dry-run`.

## Which macOS each job runs on

GitHub's standard runners on Apple silicon have the labels `macos-15`, `macos-26`, `macos-latest`, and `xcode-27` ([GitHub-hosted runners reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners), "Standard GitHub-hosted runners for public repositories"). The runner images' README (`README.md` at actions/runner-images fbb26cb0) says what each is: `macos-latest` is the macOS 26 image, as `macos-26` is, until a "-latest migration" that "happens over 1-2 months" moves it; `xcode-27` is a preview; and "All macOS 14 images retired from GitHub Actions on November 2, 2026." Each image carries the Xcodes of one major version per macOS ("only one major version of Xcode will be supported per macOS version"): `macos-15` has Xcode 16.0 to 16.4, its default, and 26.0.1 to 26.3; `macos-26` has 26.0.1 to 26.6 and no Xcode 16 (`images/macos/macos-15-arm64-Readme.md` and `macos-26-arm64-Readme.md`, "Xcode", at the same commit). So Fledge's workflows name a macOS version, never `macos-latest`, which would move a job to another macOS and another Xcode with no commit, and they use no preview image.

A job runs on the label whose macOS or Xcode is part of what it proves. Since the macOS floor became 26 (2026-11-22, "Platform floors"), that is `macos-26` for every job:

- **`macos-26`, for its macOS.** macOS 26 is the floor, and a release that stops building on an operating system version, or raises a floor, is a major. So the jobs that build apps with `fledge build` on a Mac, or run what it built, run there: Test (arm64-darwin), whose integration tests build and run apps, Build (arm64-darwin), the four Delivery jobs of arm64-darwin, ruby/spec (arm64-darwin), Mobile apps (Android project on arm64-darwin), which runs `fledge build android` and Gradle on a Mac, and `installed.yml`'s and `package-managers.yml`'s arm64-darwin jobs, which do the same from a release. They take the image's default Xcode, as a developer's Mac has whichever Xcode it has.
- **`macos-26`, for its Xcode.** Runtime (arm64-darwin) builds the launcher and `bin/ruby` with Xcode 26.5, and the iOS runtime, the iOS Simulator's apps, ruby/spec in the iOS Simulator, and `installed.yml`'s iOS project build with the same, the one whose iOS 26.5 Simulator runtime the image installs (`ci.yml`, the comment on runtime-mobile). Both select it by `runtime/sources.yml`'s `mobile.xcode`, since Apple publishes no download to pin. Until the floor moved, Runtime (arm64-darwin) ran on `macos-15` with its Xcode 16.4, and every job that built or ran a Mac's apps ran there too, on the oldest macOS GitHub had and the floor of the day.
- **`macos-26`, because any Mac will do.** The fast tier's macOS unit tests (`fast-macos.yml`, "Runs, batches, and the release commit") prove nothing about one macOS.

## Installed gems in CI

Each job that runs Fledge's own tests or lints installs the gems `Gemfile.lock` locks, and keeps them between runs in GitHub's Actions cache, so that `bundle install` takes a second instead of compiling every extension again. A bundle's compiled extensions target the Ruby they were compiled against and the image they were compiled on, its system libraries and compiler. A cache keyed by less than that hands a job extensions built for another Ruby or another image, and the job fails, or passes, for no commit's reason.

So every installed-gems key is `gems-` and the system and processor (`runner.os`, `runner.arch`), the runner's image (`ImageOS`, which GitHub's images set, such as `ubuntu24`, `win25-vs2026`, or `macos15`, and which mise-action keys its own cache by, `getRunnerImageId` in `src/index.ts` at jdx/mise-action 82a612c5), the Ruby (`RUBY_VERSION`, `RUBY_REVISION`, and `RUBY_PLATFORM`; the revision tells `4.1.0-preview1` from the next preview, which share a `RUBY_VERSION`), and the SHA-256 of `Gemfile.lock`. On Windows the key hashes `mise.toml` too, which pins the RubyInstaller build and the MSYS2 that compiles the extensions. Only an exact match restores. A label GitHub moves to a newer image, such as `ubuntu-latest`, which the gate runs on and which was Ubuntu 26.04 by 26 October 2026 (the gate's logs) while every other Linux job stayed on `ubuntu-24.04`, then changes the key with it.

Jobs on one image share one entry: on `ubuntu-24.04`, `fast.yml`'s Lint and Unit tests, `ci.yml`'s Test (x86_64-linux), and the Android emulator jobs, which only restore it; on `macos-26`, `fast-macos.yml`'s Unit tests and `ci.yml`'s iOS integration tests (iOS Simulator), which only restores it. `test/workflow_caches_test.rb` fails when a key lacks any of these parts, when jobs on different labels share a key that names no image, or when a job that only restores has no job on its label saving that key.

## How long a run keeps what it made

GitHub bills an artifact's storage by the gigabyte-hour for as long as it is kept, and in November 2026 storage was about 4 percent of what Fledge's Actions cost. Most of what a full run uploads is read only by its own later jobs: the apps each Build job makes (`apps-PLATFORM`, `signed-PLATFORM`), the phone apps (`mobile-apps-ios`, `mobile-apps-android-TARGET`), and the GNU MP that the Replace GMP jobs swap into a built Windows app (`gmp-replacement-PLATFORM`). Those are kept three days, long enough to run a failed job again over a weekend, after which a job that needs them is run again with the jobs that make them. What a later workflow reads from a run is kept two weeks: the runtimes (`runtime-PLATFORM`), which `release.yml` publishes from the CI run of the commit it tags, and the licensing page, which the pin proof (`.github/scripts/pin-prove.sh`) takes from its run. A failed runtime build's logs are kept two weeks too, for the person who reads them. `test/workflow_retention_test.rb` fails when an upload is kept for another length, or when another workflow or script asks for one kept three days.

## A pin commit's short CI

A commit with one parent and `lib/fledge/SHA256SUMS` as its only change, pushed or dispatched, runs two jobs of `ci.yml`:

- **The gate**, as on every commit, whose tests read the pins.
- **`Changes`**, which runs on every commit and tells a pin commit apart with `.github/scripts/pins-only.sh`. On a pin commit, pushed or dispatched, it finds the parent's newest run in which every job ran and passed (`tasks/ci_runs.rb`), downloads its runtimes, and runs `.github/scripts/check-pins.sh`: the runtimes must be exactly `RuntimeBuilder.release_assets`, the pins must name exactly those, and each must match its pin under `sha256sum --strict -c`.

Every other job is skipped. A merge, a first commit, a pull request, a clone without the parent, and any commit that changes anything else run all of CI. The pin check is a step of `Changes`, not a job of its own, because a job of its own would be skipped on every other commit, and a release commit's run may skip none.

A pin commit is green for tagging when its own short run passed, counting skipped jobs, and its parent's run passed on every job with none skipped. Every file of the tagged commit was then tested by a run that passed on every job: the pins by the gate and the check against the runtimes they name, and everything else by the parent's run, since those files are the parent's.

A full run on the tag, or on the pin commit, would test the same bytes again, throw its runtimes away, and draw every flaky download a second time, and flakes in jobs that publish nothing have kept a release from going out (`doc/contributors/research/2026-11-03-ci-speed.md`). Skipping the pin commit's run with `on.push.paths` would leave it no run to look up.

## release.yml

`.github/workflows/release.yml` runs on a pushed tag `vX.Y.Z`. Before it writes anything, it checks:

- that the tag matches `Fledge::VERSION`;
- that the tagged commit changes nothing but `lib/fledge/SHA256SUMS` from its parent;
- that the tagged commit has a run of `ci.yml` of its own ("Which runs are a commit's") whose latest attempt of every job passed or was skipped;
- that its parent's newest such run passed on every job, none skipped, and that run's runtimes are exactly the release's and each matches its pin.

It asks GitHub's REST API through `tasks/ci_runs.rb`, which reads 50 jobs a page, asks again after a 5xx, and takes each job's latest attempt, so a run whose failed jobs were run again counts once they pass. A tag that fails a check fails before anything is published, naming the run and each job that did not pass. A run refused only because CI had not finished can be run again once it passes (`gh run rerun RUN`).

Only its Publish job writes to the repository: it checks the assets against the pins once more and creates the GitHub Release with them.

From 1.0.0 its last job publishes the gem on RubyGems.org, after `installed.yml` has passed on every platform, and it pushes the very `.gem` that `installed.yml`'s Gem job built from the tag and every platform then installed and delivered apps from. It runs only on a release that publishes, for a version that does not start `0.`, and when the repository variable `RUBYGEMS_TRUSTED_PUBLISHING` is `true`, which the maintainer sets once he has set RubyGems.org to trust this workflow. Its push token comes from RubyGems.org's trusted publishing: the job, in the environment `release` and with `id-token: write`, gives GitHub's OpenID Connect token for the run to `rubygems/configure-rubygems-credentials`, which exchanges it for an API key that may push only this gem, for a short time, so no secret is stored ("Trusted Publishing", the `rubygems/guides` repository's `trusted-publishing.md`). RubyGems' own `rubygems/release-gem` action was not taken: it runs `rake release`, which Fledge's refuses, and which would build its own gem and push a tag; its `action.yml` at v1.4.2 pins `configure-rubygems-credentials` at the commit this job pins. Before it pushes, the job checks that the gem is the release's version and that its `allowed_push_host` is RubyGems.org, which only the 1.0.0 release commit makes it (`releasing-1.0.md`). Three things stand between a 0.x release and RubyGems.org, then: the version, the variable, and the gemspec's host; and the trust itself, without which RubyGems.org refuses the token. Run by hand (`workflow_dispatch`) with an existing tag, it runs every check against that tag's commit and runtimes, with the workflow and scripts of the branch it runs from, keeps the assets it would publish as the run's artifact, and publishes nothing unless given `publish`. A change to `release.yml` is tried that way before a release depends on it: `gh workflow run release.yml --ref BRANCH -f tag=vLAST`, with the last release's tag.

## installed.yml

After publishing, `release.yml` calls `.github/workflows/installed.yml`, which can also be run by hand on any published tag. Run by hand, it checks out the tag's files but runs the steps of the branch it is started from, which name the apps by the paths that branch has them at; a tag from before an app moved (`v0.17.0` and earlier have `examples/native_app` where trunk has `test/fixtures/native_app`) is checked again from the tag itself, `gh workflow run installed.yml --ref vX.Y.Z -f tag=vX.Y.Z`. It checks the published `SHA256SUMS` against the tag's `lib/fledge/SHA256SUMS` and every asset against it. On a fresh runner of each platform, it installs Fledge from the tag with Bundler, never from RubyGems.org, both ways the README gives and with the README's own Gemfile line, which `test/workflow_installed_test.rb` reads out of both files: in hello's own Gemfile, building hello in its folder, and in a Gemfile of Fledge's own, building the other examples by their paths. v0.13.0 and v0.14.0 shipped when the first way built no desktop app, while the workflow proved only a line of its own. With no `FLEDGE_RUNTIME_DIR` and an empty cache builds the examples with runtimes downloaded from the release, compiles `test/fixtures/native_app`'s gems against the runtime alone, and delivers each app as CI does. It installs the windowed app's installer and runs the app, writes phones' projects from the tag and builds them with Xcode and Gradle, and builds the `.gem` from the tag and installs that file on each platform. A release is not verified until its jobs pass. `package-managers.yml` installs hello with the package managers' recipes from `doc/package_managers.md`.

`installed.yml` is where a change in the world between the push and the tag shows, since the release runs no CI of its own.

Run after publishing, its proof comes when a red leg means another release. So `cut.yml` also runs it before the tag, beside the release commit's CI, on the commit the release commit goes on, as `gh workflow run installed.yml --ref BRANCH -f tag=vLAST -f commit=SHA` does by hand, with the last release's tag and the commit's full SHA. Given a commit, it checks out the commit's files where it checked out the tag's, writes the README's Gemfile line and then names the commit (`ref: "SHA"`) where the line names the tag, and runs every other step as on the tag. Between releases a commit's `Fledge::VERSION` is the last release's and its `lib/fledge/SHA256SUMS` is the last pin commit's, so the commit's Fledge downloads the last release's runtimes and checks them against pins that match; the `fledge --version` check fails a commit whose version is not the tag's, as a release commit's or a pin commit's is, and the sums job checks the release against the commit's pins rather than the tag's. The package managers' job installs the tag alone, so it is skipped. `workflow_call` declares no commit and `release.yml` passes only the tag, so a release's own run is what it was (`test/workflow_installed_test.rb`).

That run shows, on a fresh runner of every platform, what the run after publishing shows of the README's way: Bundler cloning Fledge from GitHub at the commit, both Gemfiles' installs and their time within each job's limit, the steps' shell on each system (bash on Windows among them), the commit's `fledge build` of every example with runtimes downloaded from a release and checked against its pins, `test/fixtures/native_app`'s gems compiled against that runtime alone, each app delivered and its installer run, the phones' projects built with Xcode and Gradle, and the `.gem` built from the commit and installed. What it cannot show, the run after publishing does: the new runtimes, which the release commit's CI builds and delivers on fresh runners from `FLEDGE_RUNTIME_DIR`, coming from the new release; the new version's `fledge --version`; the published `SHA256SUMS`; and the package managers' recipes. The release commit changes only version strings and documents (How a release is made), so nothing else of Fledge's differs between the two runs. Other ways were weighed: running each system's steps by hand on a computer of each kind, which proves the scripts but not GitHub's runners and leaves no run anyone can read; seeding the cache with the release commit's own runtimes from its CI run and running at the pin commit, which would prove those very runtimes too, at the cost of a second source of runtimes in every job and of the run waiting on the pin commit; and leaving the first run until after publishing, where a red leg is fixed only by another release, as the README's way that 0.13.0 and 0.14.0 shipped broken is fixed only by the next.

## From 1.0: release branches and a human publishing

Before 1.0, every commit and every release is on `trunk`, with no release branches: there is no older series to patch. Releases through 1.0.0 are cut by `cut.yml`, as "How a release is made" says.

After 1.0, Fledge reuses the version and git tooling of RatatuiRuby and Rooibos, which works differently before 1.0.0 and after it (decisions.md, 2026-11-03), and the tooling is not in this repository yet (decisions.md, 2026-11-07). From then on:

- every change lands on `trunk` first, and each minor has a release branch, `release/X.Y`, cut from `trunk` when `X.Y.0` is released;
- a fix goes to each release branch that needs it by `git cherry-pick -x`, and the patch release is made from the branch; this is how a long-term line gets its fixes (see "Support follows live Rubies");
- every release has a SemVer tag, and `stable`, the repository's default branch, sits at the newest stable release;
- each release branch keeps its own CHANGELOG;
- a human publishes: the gem reaches RubyGems.org by `release.yml`'s last job, which pushes only once the maintainer has set RubyGems.org to trust that workflow, and so is his act (decisions.md, 2026-11-22; "release.yml", above), and never by `rake release`, which Fledge's refuses. Agents prepare the bump, the branch, the backports, the CHANGELOG, and green CI, and the maintainer's run of the release tooling makes the tag and moves `stable`, which AGENTS.md forbids agents to force-push.

Fledge's runtimes are not in the gem. A runtime is files Fledge copies into an app, built once per target by CI and checked against the gem's pins, so there is nothing to build per platform inside the gem. The tag and the GitHub Release stay, because they hold the runtimes and the source bundles each app's notices name. Plan 003, "1.0", describes the RatatuiRuby tooling Fledge will reuse and what waits on its extraction.
