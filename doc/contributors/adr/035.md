# ADR 035: Take CRuby from rv-ruby on macOS and glibc Linux, and from RubyInstaller on Windows, x64 and ARM64

## Context and Problem Statement

Each desktop runtime needs a relocatable CRuby built for its platform (ADR 093). Two projects publish one. rv-ruby (spinel-coop/rv-ruby) publishes relocatable CRuby builds for macOS and Linux with a static libruby, YJIT, and OpenSSL, libyaml, libffi, and zlib linked in. RubyInstaller (oneclick/rubyinstaller2) publishes the maintained CRuby for Windows, a MinGW UCRT build, for x64 and for ARM64 from the same release, with a PGP signature beside each archive.

Windows 11 on ARM64 runs x64 programs under emulation, more slowly, and native ARM64 programs at full speed. The maintainer wants ARM: "I'd like to support Windows on ARM (and Linux on ARM) eventually, but it's not a blocker to continuing to iterate. It may be a blocker to 1.0 though." (`decisions.md`, 2026-10-26, decision 22). He accepted the Linux floor that rv-ruby's builds set: "2.39 is fine, and even newer may be fine if there becomes good reason to raise the floor." (decision 7). And he left RubyInstaller's signing key to the agents (decision 19).

Should Fledge take its Rubies from these projects, or build CRuby itself?

## Decision Drivers

- Fledge maintains as little as it can (AGENTS.md: code is a liability).
- The Ruby must be relocatable, and on macOS and Linux a static libruby the launcher can link (ADR 001); on Windows, Ruby's DLL in RubyInstaller's tree (ADR 038).
- Every download is pinned by version and SHA-256, and RubyInstaller's by its signature too.
- Windows on ARM64 should run natively.

## Considered Options

1. **rv-ruby on macOS and glibc Linux, and RubyInstaller on Windows, its x64 and its ARM64 builds,** each pinned in `runtime/sources.yml`.
2. **Build CRuby in Fledge's CI for every platform,** as python-build-standalone builds CPython, with the same static-linking choices.

## Decision Outcome

Chosen: option 1, because it gives every platform a maintained, relocatable CRuby that Fledge does not build. Building Ruby itself is a larger project, so it waits until a source stops publishing, publishes a build that fails Delivery, or cannot be relied on. For musl Linux that has happened, and Fledge builds Ruby there (ADR 017). For Windows on ARM64, RubyInstaller's ARM64 build comes from the same release and key as its x64 one, and the pinned llvm-mingw already targets `aarch64-w64-mingw32`, so the target is the x64 recipe with another archive and triple, not a Ruby Fledge builds, "which would have been one more thing to maintain" (commit 4eba6bc). Windows on ARM64 is a second question, native build or the x64 runtime under emulation, which the same ADR settles: native, since a native program runs at full speed and the maintainer wants ARM (decision 22). Commit 4eba6bc records that reason. The x64 runtime under emulation was the state before, and no recorded reason preferred it.

Confidence: high. Every one of these runtimes builds, passes the audit and the parity check, and delivers on a fresh runner of its platform in CI.

### Consequences

- Good, because Fledge's Rubies are the ones Ruby's own communities build and test, and a new Ruby is a pin to move.
- Good, because an app runs natively on Windows 11 on ARM64.
- Bad, because Fledge depends on two projects' release schedules: a Ruby release reaches Fledge when rv-ruby and RubyInstaller publish it.
- Bad, because rv-ruby's Linux builds need glibc 2.39 or newer, which sets the Linux floor.
- Bad, because rv-ruby links libxcrypt statically into its own `bin/ruby`, so Linux runtimes build libxcrypt as a shared library themselves and replace `bin/ruby` (ADR 042).
- Bad, because RubyInstaller's tree carries what a developer's Ruby needs, which the runtime prunes and replaces (Fledge's RubyGems defaults; ADR 085), and its signing key expires on a known date, which the agent who moves the pin must follow.
- Bad, because the runtime's Windows tools are x64 and x86 programs, which ARM64 Windows runs emulated, and its emulator's cache holds them open after they exit, so `fledge build` runs them from temporary copies.

### Confirmation

- `test/runtime_builder_test.rb` checks that every platform pins a Ruby by SHA-256, and that both Windows archives pin their signature and the key, by URL at a commit, SHA-256, fingerprint, and expiry.
- Every runtime build checks RubyInstaller's archive with `gpgv` against the pinned key, by fingerprint.
- CI's "Licenses of the whole upstream tree" jobs audit each source's whole tree.
- CI builds, tests, and delivers on `macos-15`, `ubuntu-24.04`, `ubuntu-24.04-arm`, `windows-latest`, and `windows-11-arm`.
