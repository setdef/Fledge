# ADR 009: Installers for Windowed Apps, Built on Any Computer

## Status
Accepted (requested). Agents wrote this ADR and may change it (AGENTS.md, Questions). It carries out the installers Plan 002's "Windowed apps" story plans (a `.dmg` for macOS, an NSIS setup program for Windows, an AppImage for Linux) and the Start menu shortcut "App identity" left for an installer, which ADR 008, section 3, says Windows needs before it shows an app's notifications. It applies decision 18 in `doc/contributors/decisions.md` (what shows in a Start menu and a Dock is the developer's to control) and decision 8 (nothing Fledge copies into an app may carry copyleft obligations beyond notices, LGPL code only as a separate, replaceable shared library), and keeps ADR 001's promise that one computer builds every platform. Signing an installer with a developer's credentials is Plan 002's "Signing and notarization", not this ADR's.

## Date
2026-10-28

## Context

Through 0.0.1.pre.6 a windowed app ships as an archive: a `.tar.gz` holding a macOS bundle or a Linux folder, a `.zip` holding a Windows folder. A person unpacks it and runs the program, and that is all most apps need, but not all a desktop app's people expect, and not all the operating systems need. Windows shows an app's toast notifications only when a Start menu shortcut carries its AppUserModelID (`System.AppUserModel.ID`), and a zip makes no shortcut; Tokra, a Ruby port of Tauri, is about to send notifications. A Mac app is downloaded as a disk image more than any other way, and notarization staples its ticket to a disk image, not a zip. Linux users take an app as one AppImage file more readily than a tarball to unpack. Tauri's users, whom Tokra serves, expect exactly these.

Two constraints from earlier ADRs shape the answer. Any computer builds every platform (ADR 001, section 2), so an installer cannot need a tool that runs only on its own platform: `hdiutil` only on macOS, `appimagetool` only on Linux. And everything Fledge puts into an app passes the license audit (ADR 004): an installer's own machinery, which every person who installs the app receives, is something Fledge puts into the app.

## Decision

### 1. A windowed app gets every installer its platforms have, unless fledge.yml says

As Tauri's `bundle.targets` defaults to all, `fledge build` writes, for a windowed app, the installer of each target it builds beside that target's archive: `NAME-PLATFORM.dmg` for macOS, `NAME-PLATFORM-setup.exe` for Windows (ending as Tauri's do), and `NAME-PLATFORM.AppImage` for Linux, and prints each after its archive. `fledge.yml` may list the ones it wants, `installers: [dmg, nsis, appimage]`, or none, `installers: []`; the names are the formats', which are what a developer searches for, and a typo fails the build as any unknown value does. That one key is the whole surface: the archive stays, every installer is built from the same entries as it, and there is no command-line option, since what an app ships is a property of the app, as Tauri's targets are configuration. Names carry no version, as Fledge's archives carry none, so a script finds them by platform.

A console app gets none, and a console app that lists any fails the build. A terminal tool is installed by putting its program on a `PATH`, which a disk image's drag to Applications, a Start menu shortcut, and an AppImage all leave undone, and none of them has a window for the person to see. Packages that do put a program on a `PATH` (Homebrew, `.deb`, winget) are other stories.

The installers' pieces that are not Fledge's Ruby ship in the runtime for their platform, in a folder named `installer` that `fledge build` reads and never copies into an app: `installer/appimage-runtime` in each Linux runtime and `installer/nsis/` in the Windows one. So the license audit (ADR 004) accounts for them in every runtime build, their notices are in every app's `notices/NOTICES.txt` (which the AppImage and the NSIS installer hold, since each holds the app), and a runtime and its installer pieces cannot disagree.

### 2. macOS: a disk image Fledge writes itself

`Fledge::Dmg` writes what create-dmg writes for Tauri: a volume named after the app, holding the bundle the build signed ad hoc, `NAME.app`, and a symbolic link named `Applications` to `/Applications`, onto which a person drags the app. It writes it in Ruby, on any computer, as Mozilla's builds write theirs on Linux; hdiutil would make a Mac the one computer that could, and Fledge already writes Mach-O signatures, PE resources, and property lists itself for the same reason (ADR 008).

`Fledge::HfsPlus` writes the volume as TN1150 lays it out, in its case-sensitive variant, HFSX, so its catalog orders names by their UTF-16 code units and needs no copy of Apple's table of case folding: the volume header and its copy in the last 1024 bytes, an allocation bitmap with every block in use, an extents overflow B-tree with no records (each file is one extent), and the catalog B-tree, with leaf and index nodes of 8 KiB, a folder or file record and a thread record for every item, and each folder's count of the folders in it, which HFSX requires. Every file's data is written as it arrives, so the volume streams to a temporary file. Modes are the entries', owners are 99 (shown as whoever mounts the volume), names are decomposed as Apple decomposes them, and a symbolic link is a file of type `slnk`, creator `rhap`, whose data is its target. The volume is read-only and exactly full. `Fledge::Udif` compresses it into a read-only, zlib-compressed image ("UDZO"), laid out as `hdiutil create -layout NONE` lays one out: chunks of 2048 sectors, each zlib-compressed, stored as it is when zlib cannot shrink it, or, when all zeros, stored as nothing; a property list whose `blkx` resource describes them; the 512-byte `koly` trailer; and hdiutil's two CRC-32 checksums. The image's ID is a hash of it, so the same app makes the same image.

`fsck_hfs` finds the volume sound, `hdiutil verify` accepts the image's checksums, `hdiutil attach` mounts it, and `codesign --verify --strict --deep` accepts the bundle inside the mounted image and once it is copied out: the seal covers file contents and links, which the volume keeps byte for byte, and the volume adds no extended attributes or resource forks for `--strict` to refuse.

A case-sensitive volume is a difference an app could see only when it runs from the mounted image and opens its own files by a name of another case, which already fails on Linux; dragged to Applications, it is on the Mac's own case-insensitive APFS. A background picture and a laid-out window, which create-dmg writes as a `.DS_Store` of Finder's private format, are left out: they are decoration, and the image works without them. Signing the image itself, and notarizing it, belong to "Signing and notarization".

### 3. Windows: an NSIS setup program, per user, that makes the shortcut toasts need

`Fledge::Nsis` writes an NSIS script as Tauri's `installer.nsi` does for its default `currentUser` mode, without Tauri's own plug-in, and compiles it with makensis:

- It needs no administrator (`RequestExecutionLevel user`), and installs into `%LOCALAPPDATA%\Programs\NAME`, Windows' known folder for programs one person installs, as electron-builder's per-user installers do (Tauri uses `%LOCALAPPDATA%\NAME`, beside apps' data). The folder page lets a person choose another, and a reinstall goes where the last install went, as the uninstall entry's `InstallLocation` says.
- It makes `NAME.lnk` in the Start menu, to the app's program, and sets the shortcut's `System.AppUserModel.ID` to the app's identifier, the AppUserModelID the launcher gives the process (ADR 008, section 3), with IShellLink, IPersistFile, and IPropertyStore through NSIS's System plug-in and its COM headers, as Tauri's `SetLnkAppUserModelId` does, but as the `VT_LPWSTR` the property is. Windows then attributes the app's windows and notifications to that shortcut.
- It offers a desktop shortcut, unchecked, on its last page, through the "show readme" check box as Tauri does, with the same AppUserModelID; a silent install (`/S`), which shows no pages, makes none. That page also offers to run the app.
- It registers the uninstaller under `HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall\IDENTIFIER`, by identifier rather than Tauri's product name, since two apps may share a name but not an identifier: `DisplayName`, `DisplayVersion`, `Publisher`, `DisplayIcon`, `InstallLocation`, `UninstallString`, `QuietUninstallString` (with `/S`), `NoModify`, `NoRepair`, and `EstimatedSize`.
- The uninstaller deletes, by name, the files it installed, then each folder it made, deepest first, and the install folder only if it is then empty, as Tauri's does, so nothing a person put there is lost; then the shortcuts and the registry key. A new version runs the installed version's uninstaller before it installs, as electron-builder's do, so a file the old version had and the new one does not is not left behind.
- The setup program carries the app's icon (as an `.ico`, `Fledge::Icon#ico`) and its version information: ProductName, FileDescription (`NAME Setup`), CompanyName, LegalCopyright, and the version, written by makensis's `VIAddVersionKey`.
- It compresses with zlib, solid. NSIS's default and Tauri's choice, LZMA, is under the Common Public License, which asks whoever distributes it to say where its source is, more than decision 8 lets an installer ask of an app's developer; NSIS's zlib module is under the zlib license, like the rest of what the installer holds.

What the installer is compiled from, NSIS 3.13's stubs for zlib (and the uninstaller's icon), its System and nsDialogs plug-ins, its script headers, and Modern UI 2 with its dialogs, graphics, and language files, comes from NSIS's pinned release and ships in the Windows runtime's `installer/nsis/`, audited as NSIS under the zlib license. The compiler, makensis, runs on the computer that builds the app and is in no app. NSIS publishes it only for Windows, so Fledge's CI builds it from NSIS's pinned source for each other computer that builds apps (`tasks/makensis_builder.rb`, `rake makensis`), as NSIS's "Building on POSIX" builds it, alone, with SCons from its pinned wheel, and statically linked to libstdc++ on Linux, and for Windows repacks the release's own `makensis.exe`; each is compiled against the release's stubs in CI and published beside the runtimes as `fledge-makensis-VERSION-PLATFORM.tar.gz`, which `Fledge::Runtimes#makensis` finds and downloads as it does a runtime and unpacks into its cache. `fledge build` points it at the runtime's NSIS with `NSISDIR` and gives it `-NOCONFIG`, so every computer builds the same installer from the same pieces; Tauri's use of whatever makensis a Mac or Linux computer has would let a distribution's older NSIS build a Fledge app's installer.

### 4. Linux: an AppImage, with Fledge's build of AppImage's runtime

`Fledge::AppImage` writes a type 2 AppImage: the runtime, then a SquashFS of the app's folder laid out as an AppDir. The folder already has the desktop entry at its top and its icons under `share/icons` (ADR 008, section 4); the AppImage adds `AppRun`, a symbolic link to the app's program (the launcher, which finds its runtime through `/proc/self/exe`, so the link is all it needs), the 256-pixel icon at the top, named as the desktop entry's `Icon` names it, and `.DirIcon`, a link to it. `Fledge::Squashfs` writes the file system in Ruby, on any computer, as squashfs-tools-ng's format document specifies it: zlib (the format's "gzip", which Ruby's standard library writes) for data and metadata, blocks of 128 KiB, each file's tail packed into shared fragments, each directory's entries sorted by their bytes, root as every item's owner, and the build's time as every item's. The runtime, which mounts or extracts it, reads zlib, so nothing else is needed.

The runtime is AppImage's type 2 runtime, pinned at a commit, built by Fledge's CI into each Linux runtime as `installer/appimage-runtime`, with one change that decision 8 requires and one it allows. AppImage's own build links libfuse 3, LGPL-2.1, statically into the runtime, which Fledge would then put into every Linux app's AppImage. Fledge's build links no libfuse: `runtime/appimage/fuse.c`, Fledge's own, stands in for the 23 functions of libfuse that the runtime and squashfuse call and loads them, at the symbol versions of the headers it was compiled against, from the computer's own `libfuse3.so.3` when the AppImage is about to mount, as AppImageKit's old runtime loaded `libfuse.so.2`. libfuse is then a library of the computer, like glibc, never one Fledge ships. So the runtime links only glibc dynamically, which every computer an app runs on has at 2.39 or newer (ADR 001, section 3), with squashfuse (BSD-2-Clause) and zlib linked statically; the license audit checks that it holds no libfuse code (`runtime/licenses.yml`'s signatures), and that it is the build it names. Fledge's patch to `runtime.c` (`runtime/appimage/runtime.patch`) makes the runtime extract the AppImage into a temporary folder and run it from there, removing it after, when the computer has no FUSE to mount with (no `/dev/fuse` it may open, or no libfuse 3) or mounting fails, where AppImage's runtime prints that FUSE is missing and stops; a person never needs FUSE, and `APPIMAGE_EXTRACT_AND_RUN=1` and `--appimage-extract-and-run` still choose extracting, as AppImage documents. Everything else is AppImage's runtime as it is: `--appimage-extract`, `--appimage-offset`, `--appimage-mount`, and the `APPIMAGE`, `APPDIR`, `ARGV0`, and `OWD` it gives the app.

The AppImage is executable as written, and a person who downloads one makes it executable (`chmod +x`), as with any AppImage. Update information (zsync) and a signature, which appimagetool can embed in the runtime's sections, are left empty.

### 5. Delivery installs each on a fresh computer and runs what it installed

`examples/windowed_app` builds with all three on CI's one Linux runner, and on a fresh runner of each platform:

- macOS (`.github/scripts/deliver-dmg.sh`): hdiutil verifies the image and attaches it; the volume has the app's name, the bundle, and the link to `/Applications`; codesign verifies the bundle strictly and deeply in the image, where the app runs; dragged (copied with `ditto`, as Finder copies) to an Applications folder, its signature still verifies and it runs through its own program and through `open -W`.
- Windows (`.github/scripts/deliver-installer.ps1`): the setup program carries the app's icon and version information; installed silently with no administrator, the app is in `%LOCALAPPDATA%\Programs`, the Start menu shortcut points at it and its `System.AppUserModel.ID`, read back through the shell's IPropertyStore and through Shell.Application, is the identifier, there is no desktop shortcut, and the uninstall entry is in HKCU; started from the shortcut, through the shell, the app reports that it has no console and that the AppUserModelID it gave itself is the shortcut's, which is what Windows checks before it shows a toast, and a toast is shown through Windows' notifier for that ID, its result reported; installed again over itself, it is whole; and its silent uninstaller removes its files, its shortcut, and its registry key.
- Linux (`.github/scripts/deliver-appimage.sh`), on Ubuntu 24.04 of both architectures with FUSE, and in Debian 13 containers without: it runs from its mount where there is FUSE and extracted where there is not, and extracted with `APPIMAGE_EXTRACT_AND_RUN=1`, from a path with spaces and characters outside ASCII, with no Ruby on its PATH, and in a hostile Ruby environment, leaving nothing behind; and `--appimage-extract` unpacks the AppDir with its notices.

`installed.yml` does the same with the installers built from a release, makensis downloaded from it.

## Consequences

- A windowed app's developer gets a `.dmg`, a setup program, and an AppImage from one computer, Linux, macOS, or Windows, with no tool to install; a Tokra app's toasts can work on Windows once installed.
- A build takes longer for a windowed app (compressing an image and a file system of the runtime, and running makensis), and `installers: []` skips it.
- Windows runtimes carry `installer/nsis/` and Linux runtimes `installer/appimage-runtime`; runtimes from 0.0.1.pre.6 and earlier have neither, and a windowed app built with them fails until its `installers` leave those out. Releases carry `fledge-makensis-VERSION-PLATFORM.tar.gz` for each computer that builds apps.
- Every app's `notices/NOTICES.txt` names NSIS, on Windows, or AppImage's runtime and squashfuse, on Linux, since its installer may hold them.
- Fledge now writes HFS Plus volumes, UDIF images, and SquashFS file systems itself, and builds AppImage's runtime and makensis, each checked against the platform's own tools: fsck_hfs, hdiutil, and codesign; unsquashfs and the runtime itself; and Windows' own shell.
- Not yet: a disk image's background and window layout; signing the image, the setup program, and the AppImage (Plan 002, "Signing and notarization"); `.msi`, `.deb`, and `.rpm`, which wait for a developer who needs them (Plan 002, "Windowed apps"); a per-machine NSIS install; NSIS in other languages; closing a running copy of the app before reinstalling it, which Tauri's plug-in does; file associations and URL schemes; AppImage update information and signatures; installers for console apps.
