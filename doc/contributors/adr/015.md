# ADR 015: Ctrl-C and the Console Reach Ruby as They Reach ruby

## Status
Accepted (requested). Agents wrote this ADR and may change it (AGENTS.md, Questions). It applies the maintainer's decision 21 in `doc/contributors/decisions.md` (Windows console code pages and Ctrl-C are the agents' to decide) and ADR 003, section 5, which said Ctrl-C reaches Ruby's own handler and that nobody had checked; it is Plan 002's story "Ctrl-C and the console."

## Date
2026-11-01

## Context

A person ends a console app by typing Ctrl-C, or by closing its terminal or console window. An app's Ruby code meets these as Ruby defines them: Ctrl-C raises `Interrupt` in the main thread, which runs `ensure` clauses and `at_exit` hooks and, uncaught, ends the process by the signal; a closed terminal on macOS and Linux sends SIGHUP, which raises `SignalException` the same way (Ruby installs handlers for SIGINT and SIGHUP, `signal.c`, `install_sighandler`, and re-raises the signal with its default action after cleanup, `eval.c`, `rb_ec_cleanup`, and `signal.c`, `ruby_default_signal`, at Ruby 4.0.9). A shell reports a process ended by signal N as 128 + N: 130 for SIGINT and 129 for SIGHUP. On Windows, Ruby's C runtime, UCRT, turns the console's CTRL_C_EVENT into SIGINT, Ruby raises `Interrupt`, and `ruby_default_signal`'s `raise(SIGINT)` with the default action ends the process, with exit code 3, as CI measured for `ruby.exe` before any app.

A launcher could stand in the way: a launcher that ran Ruby as a child, as many do, would have to forward signals and console events and pass on how its child ended; one that installed a handler of its own, or ignored SIGINT, would change what the app sees. Fledge's launcher is not a parent: on macOS and Linux libruby is linked into it, so it is the interpreter, and on Windows it loads Ruby's DLL into its own process (ADR 001, sections 1 and 8). It installs no signal handler and no console control handler; `ruby_sysinit` and `ruby_init` install Ruby's own, as in `ruby` and `ruby.exe`.

Windows consoles also have a code page. Since Ruby 3.0 (Feature #16604), `Encoding.default_external` is UTF-8 on Windows whatever the code page, while `Encoding.locale_charmap` is the console's input code page (`localeinit.c`, `locale_charmap`, `GetConsoleCP`), and Ruby writes a string to a console with `WriteConsoleW` (`win32/win32.c`, `rb_w32_write_console`), so text outside the code page still shows as written. ADR 003, section 5, keeps `activeCodePage` out of the launcher's manifest so that the code page decides what it decides for `ruby.exe`; the parity check compares both under code page 437.

A windowed Windows app is a GUI-subsystem program (ADR 008), like `rubyw.exe`. Typed into a console, Windows gives it no console, and neither PowerShell nor an interactive `cmd.exe` waits for it. PyInstaller's windowed programs, Tauri's `windows_subsystem = "windows"`, and Electron's apps behave the same; none attaches to the console that started it.

## Decision

### 1. The launcher stays out of the way, and Delivery proves it

The launcher installs no handler, ignores no signal, and runs Ruby in its own process, so it has nothing to forward. That is the design already (ADR 001), and Plan 002 asked that it be checked on every platform. `test/fixtures/console` is a probe that prints a line outside ASCII, records its locale and default external encoding and "ready" in a log, and sleeps in a `begin`/`ensure`, with an `at_exit` hook, so that what ran on the way out is in its log.

- **macOS and Linux:** `.github/scripts/deliver-console.sh` runs the probe in a terminal of its own, a pseudo-terminal that `script(1)` opens (BSD's on macOS, util-linux's on Linux), through a shell that records its exit status, and types Ctrl-C into it, which the terminal's line discipline turns into SIGINT for the foreground process group, and, in a second terminal, sends SIGHUP to that group, as a closing terminal does (POSIX's "Closing a Terminal Device File"; a shell sends it on to its jobs). The probe must record `ensure ran (Interrupt: )` and `at_exit ran` and end with status 130, or `ensure ran (SignalException: SIGHUP)` and 129, and the terminal must show its UTF-8 line byte for byte and, for Ctrl-C, Ruby's message for the `Interrupt`. The script runs the terminal in the foreground and the scenario in the background: a program a script starts in the background starts with SIGINT ignored (POSIX, "Asynchronous Lists"), and Ruby keeps an ignored SIGINT ignored.
- **Windows:** `.github/scripts/deliver-console.ps1` runs the probe in a new console, sets its code page to 65001 and then 437, and sends Ctrl-C with `GenerateConsoleCtrlEvent(CTRL_C_EVENT, 0)`, from a PowerShell attached to the same console that ignores Ctrl-C itself (set after the probe started, so the probe does not inherit it). The probe must record its locale as `CP65001` or `CP437`, `UTF-8` as its default external encoding, the `ensure` clause and the `at_exit` hook, and end with exit code 3; and the console's screen buffer, read back with `ReadConsoleOutputCharacterW`, must show its line, `café ✓`, on both code pages. The windowed example, typed into the console as a person types it, must return the console to them at once and report that it had no console.

Each script runs the built app in Delivery and, with `--reference`, `ruby main.rb` (or `ruby.exe` and `rubyw.exe`) in the Test jobs, with the same expectations, so the built app ends as Ruby itself does. `test/built_app_test.rb` runs the Unix script on the built probe and on `ruby main.rb` wherever a runtime is.

### 2. Closing a Windows console is not proven in CI

Closing a console window sends CTRL_CLOSE_EVENT to every process attached to it. UCRT maps only CTRL_C_EVENT and CTRL_BREAK_EVENT to signals, Ruby installs no console control handler of its own, and neither does the launcher, so Windows's default handler ends `ruby.exe` and a built app alike, at once, before any `ensure` clause runs. CI could not make a console close on GitHub's Windows runners: `WM_SYSCOMMAND` with `SC_CLOSE` and `WM_CLOSE` posted to the console's window, and stopping its `conhost.exe`, each left the process running (the `experiment/signing` branch's runs, 2026-11-01). The claim rests on the launcher's code, which installs no handler, and on the Ctrl-C checks, which show Ruby's handling reaching the app unchanged.

## Consequences

- Ctrl-C, a hangup, and the console's code page reach an app as they reach `ruby main.rb`; an app that wants to clean up on Ctrl-C rescues `Interrupt` or uses `ensure`, as under `ruby`.
- A built app started in the background of a shell script ignores Ctrl-C, as `ruby` does there.
- Delivery fails if a change to the launcher makes a console app end differently from Ruby, on any platform.
