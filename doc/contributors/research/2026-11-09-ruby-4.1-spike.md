> Findings of the Ruby 4.1 preview spike of 2026-11-09. Requested: written by an agent and not reviewed line by line. The spike's code stays off trunk, on branches named below; ADRs cite these findings by this file.

# Ruby 4.1 spike: what a move to 4.1 costs Fledge

Lota, a game framework that builds through Fledge, wants to judge a move to Ruby 4.1. This spike builds Fledge's runtimes from 4.1 previews and runs apps on them. The code is throwaway. These findings are what the spike is for.

## Where the code is

- Branch `experiment/ruby-4.1`, pushed to origin, tip 9923b89. It covers Linux, Android, macOS, and iOS.
- Branch `experiment/ruby-4.1-windows`, at 80d2a6e. It exists only on one computer and was never pushed.

## Inputs

- Ruby 4.1.0-preview1. The source tarball's SHA-256 is fb530bb88e90de3ae91c1310a27ae090e6bd989b8726de50ef12a890a85b88ef.
- rv-ruby release 20261023, its ruby-4.1.0-preview1 builds.
- RubyInstaller's rolling `rubyinstaller-head` snapshot of 2026-11-09: `ruby 4.1.0dev (2026-11-09 master 165bb8173f)`. The 7z's SHA-256 is 0c43806b202473b1fa2563a5802b1fbac99bcef9a6d618e6cd3b49d4195dc352. It is signed by the key Fledge already pins, fingerprint 79D1D4E12FF93365DEAA8DCEF98B8484BE8BF1C5.

## Verdict

On these results, Ruby 4.1 is workable for Fledge. A release could pin 4.1.0 once rv-ruby and RubyInstaller publish it, after the open problems below are fixed or explained. ADR 029, section 5, reserves the Ruby-versioned asset names for shipping two Ruby minors side by side.

## What ran

x86_64-linux, built on a Linux laptop:

- The runtime built. Its license audit passed with 2988 files in 102 components.
- `examples/hello` printed "Hello from Ruby 4.1.0 on x86_64-linux" and exited 0.
- `examples/my_cool_app` ran once sqlite3 compiled from source.

Android:

- The runtime built. Its audit passed with 2731 files in 89 components.
- `examples/hello` ran on an x86_64 API 36 emulator.
- The same app ran on a OnePlus Nord N30 5G (arm64-v8a): "Hello from Ruby 4.1.0 on aarch64-linux-android", exit 0.

macOS, in CI run 42735512934:

- The runtime built.
- Delivery on a fresh runner printed "Hello from Ruby 4.1.0 on arm64-darwin23". `my_cool_app` ran with sqlite3 2.10.2 built from source. The Ctrl-C and hangup checks passed.
- The runtime was also built locally, where its audit passed with 2974 files in 87 components.

iOS:

- CI built the runtime. Locally, the audit passed with 5381 files in 86 components (36.8 MB).
- `examples/hello` and `examples/native_phone` (a C and C++ extension) ran in the iOS 26.5 Simulator on iPhone 17 Pro and iPad Pro 13-inch (M5).
- `native_phone` ran on a physical iPhone 12 mini, signed with a free Personal Team: "NativePhone adds 5 and totals 10 with a C extension (C and C++) on arm64-darwin", exit 0. It was the first Fledge app on an iPhone 12 mini.

Windows x64, from the head snapshot:

- `examples/hello`, `examples/windowed_app`, and its NSIS installer ran with no Ruby on PATH.
- The license audit refused the runtime (problem 3). It was archived unaudited, for testing only.

Parity of a lone `main.rb` against `ruby main.rb`:

- 0 unjustified differences on Linux and macOS, in the default environment, with no locale, under LC_ALL=C, and under LC_CTYPE=C.
- On Windows, 1 unjustified difference: zlib fails to load.

## What 4.1 changed, and what each change needed

- A preview's folders are named by its ABI, `4.1.0+5` for preview1 and `4.1.0+6` for the head snapshot, not by its version.
- The bundled gems changed. prism, tsort, and win32-registry are in. net-ftp and net-pop are out.
- The license audit needed three things: a new revision string, 2d08b5f42f; entries for `digest/blake3.so` and `digest/crc32.so`; and a reviewed entry for rdoc 8.1.0. BLAKE3 is under CC0-1.0, Apache-2.0, or Apache-2.0 WITH LLVM-exception, and is not in Ruby's LEGAL. The origin of `digest/crc32.so` was not checked. rdoc 8.1.0's license is "Ruby or GPL-2.0-only".
- Ruby 4.1 generates its `.rbinc` files with a C program, `dump_ast`. The cross build compiled it for the target, so the host build supplies it with `--with-dump-ast`.
- Ruby 4.1's `common.mk` passes `--without-ext=-test-` to configure-ext.mk when cross-compiling. That overrides Fledge's `--with-out-ext`, and bundled gems' extensions were built twice. The spike generated `uncommon.mk` and added Fledge's list there.
- prism's bundled-gem extension compiles its own libprism, which collides with libruby's copy when linked statically (duplicate `pm_parse`). The spike leaves that extension out on Android and iOS, so `require "prism"` fails on a phone. The collision was not verified on iOS.
- ruby/ruby 3e96f16643, "Require Mac OS X 10.6 or later" (configure.ac lines 439 to 451), refuses every darwin target whose `MAC_OS_X_VERSION_MIN_REQUIRED` is below 10.6. An iOS cross build is darwin, and the iOS SDK's AvailabilityMacros.h (lines 96 to 111) sets the macro to 10.5 when clang gives no macOS deployment target. So configure stops with "Unsupported OS X version is required". A fifth scripted edit makes the check apply only when `__ENVIRONMENT_MAC_OS_X_VERSION_MIN_REQUIRED__` is defined. This is an upstream bug for anyone who embeds Ruby on iOS. It has not been reported.
- The Ruby that runs a 4.1 cross build's install (baseruby) has to be 4.1. With 4.0.9, `rbinstall.rb` fails at `lib/monitor.rb:89` with "uninitialized constant MonitorMixin::Monitor", because 4.1 moved Monitor into core. mise could not install the 4.1 preview on macOS, so rv-ruby's build was used.
- RUBY_MN_THREADS is read in `ruby_mn_threads_params` (thread_sched.c line 1818), called from `process_options` (ruby.c line 2455) inside `ruby_options`. The desktop launcher restores the person's `RUBY*` variables only after `ruby_options`, so a person's RUBY_MN_THREADS never takes effect in a built app. That is by design (ADR 003, section 3), and it is what Lota wants. This comes from reading the source. It was not observed.

## Problems found

1. A Fledge bug on any Ruby, fixed on trunk in 44d04ff.
   - On 4.1, sqlite3 2.10.2's precompiled builds exclude the runtime's Ruby. Fledge picked them and refused them, where Bundler falls back to the source build.
   - The fix's CI run, 42716904223, passed all 77 jobs.
   - The spike merged it in 9923b89.
2. Gem-shaped parity, open.
   - It has 5 unjustified differences on Linux and macOS: `$LOAD_PATH`, `$LOADED_FEATURES`, `gems`, `ENV`, and `child ENV`.
   - Almost all come from Bundler choosing its version. `examples/my_cool_app/Gemfile.lock` says BUNDLED WITH 4.0.20, so `bundle exec` installs and switches to 4.0.20 (bundler/self_manager.rb lines 70 to 96). A built app always uses the runtime's default Bundler, 4.1.0.beta2 in preview1. The gap always existed. It stayed hidden while the two versions matched.
   - Relocking with 4.1's Bundler left 1 difference on Linux: rake's load path. rake 13.4.2 is a bundled gem in 4.1, and the existing justification matches only the person's gem folder.
   - On macOS the reference also loads `lib/my_cool_app/version.rb` and the app does not. This was not analysed.
   - Whether a built app should honor BUNDLED WITH is undecided.
3. Windows, from the head snapshot.
   - `zlib.so` imports `libz-1.dll`, but the snapshot ships zlib as `zlib1.dll` (byte for byte MSYS2's `mingw-w64-ucrt-x86_64-zlib-1.4-2`) and names it in `zlib.so-assembly.manifest`.
   - `digest/blake3.so` imports `libgcc_s_seh-1.dll` for one symbol, `__popcountdi2`, and the snapshot does not ship that DLL.
   - OpenSSL, libyaml, and libffi ship and load with no MSYS2.
   - RubyInstaller restricts DLL search to its own directories, so a person's MSYS2 on PATH cannot leak in.
   - Bundling libgcc would put GCC's runtime library, `GPL-3.0-or-later WITH GCC-exception-3.1`, in a runtime. AGENTS.md's licensing rules make that an ADR decision.
   - Both look like RubyInstaller packaging bugs. Neither has been reported.
4. Build machine. The laptop's GCC 15 fails libxcrypt 4.5.2 under `-Werror` ("initialization discards 'const' qualifier", crypt-sm3-yescrypt.c:139). CI's older toolchain is unaffected.
