# ADR 096: A restart through `RbConfig.ruby` starts the app's launcher again

## Context and Problem Statement

A Ruby program that restarts itself asks Ruby where it is and runs itself again, as Puma's hot restart does (`exec Gem.ruby, $0, ...`):

```ruby
exec RbConfig.ruby, $0, *ARGV
```

In a built app `RbConfig.ruby` names the runtime's own Ruby: `bin/ruby` on macOS and Linux, Ruby's `main.c` built against the launcher's libruby (ADR 085), and RubyInstaller's `ruby.exe` on Windows (ADR 038), until Fledge built its own. Plain Ruby hides nothing from its boot. A probe of every desktop platform found the restart broke: it booted with the person's `RUBYOPT`, `RUBYLIB`, `GEM_HOME`, and `BUNDLER_SETUP`, which the launcher had put back (ADR 040), without the Bundler setup the first start had, and on macOS outside the bundle's program. Running the app's launcher again had none of these problems, but an app has no Ruby answer that names its launcher.

The maintainer framed the question (`decisions.md`, 2026-11-02, later again): "Remember: this entire rule is because _Fledge should never surprise an app dev with how it behaves or causes Ruby or its globals, built-ins, and standard library to behave compared to not using Fledge_." A developer who writes the line above expects the app to start again as it first started.

## Decision Drivers

- No app needs code of Fledge's own to restart, and `ENV` stays what `ruby main.rb` gives (decisions 9 and 10).
- No app needs a branch per operating system (decision 23: "Would this require app devs to have a bunch of `if`s or polymorphic objects used throughout their app to handle the difference?").
- A restart keeps the process, and on macOS the app's bundle.
- `RbConfig.ruby` still runs any script and takes Ruby's options, as RubyGems' tools and the parity check use it.
- The launcher's work lives in one program.

## Considered Options

1. `bin/ruby` hands the app's own program back to the app's launcher, which it runs in its place with `execv`.
2. Leave `bin/ruby` plain Ruby, Ruby's `main.c` as it is.
3. A constant or an environment variable that names the launcher, such as `FLEDGE_LAUNCHER`.
4. `bin/ruby` does the launcher's work itself, hiding the person's settings and setting up Bundler, when it runs the app's program.
5. `RbConfig.ruby` names the launcher.
6. A shell script in place of `bin/ruby`.

## Decision Outcome

Chosen: option 1, because it alone restarts the app as it first started with no code of Fledge's in the app and the launcher's work in one place.

On macOS and Linux, when `bin/ruby`'s first argument is not an option and is the program a launcher of this app runs, `bin/ruby` runs that launcher in its own process with `execv`. The launcher then hides the person's settings, chooses the locale, sets up Bundler, and puts the settings back, exactly as the first time. `execv` keeps the PID, and on macOS the launcher is the bundle's program. `system(RbConfig.ruby, $0, ...)` and `spawn` start the app again the same way, as a child. Anything else stays plain Ruby: an option before the program, any other script, and a gem's executable. Fledge adds nothing an app reads to find itself: `$0`, `__FILE__`, `__dir__`, `RbConfig.ruby`, `RbConfig::CONFIG["prefix"]`, `Gem.dir`, and `Gem.path` are true inside a built app. `doc/contributors/design/launcher.md`, "bin/ruby and restarts", gives the detection.

On Windows, the runtime's `ruby.exe` and `rubyw.exe` are Fledge's: Ruby's `main.c` built with the llvm-mingw that builds the launchers, against RubyInstaller's DLL through the tree's import library, with the launchers' manifest, in place of RubyInstaller's. Replacing them in place, rather than adding programs beside them, keeps `rbconfig.rb`, RubyGems' `.bat` wrappers, and mkmf untouched, since each names `ruby.exe` by its place, and keeps the tree's shape (ADR 038). Windows has no `exec` that keeps the process: Ruby's own starts the program, waits for it, and exits with its status. So when the first argument is the program a launcher of this app runs, matched by volume serial and file index, `ruby.exe` runs that launcher with the rest of the command line as given, waits, and exits with its status, as Ruby's `exec` does there. The restart then has the app's environment, Bundler setup, code page (ADR 070), and AppUserModelID. Since Windows' variable names ignore case, the launcher gives each of a person's Bundler variables back the person's spelling, as `bundle exec` keeps it, except `BUNDLE_GEMFILE` and `BUNDLE_LOCKFILE`, which name the app's own files and keep Bundler's spelling: Bundler's settings read `ENV` by that spelling alone (`bundler/settings.rb`, `Settings#initialize`), so a child's `bundler/setup` would otherwise take the Gemfile a person's own `.bundle/config` names (Design precedence 1); only its new PID, and a console for a windowed app restarted through `ruby.exe`, are Windows' limits. A launcher must hold a mark the launcher keeps, so an installer's `uninstall.exe` beside it never passes for it.

Confidence: high on every desktop platform, where tests and Delivery restart a lone script, a gem-shaped app, and a macOS `.app` or a Windows windowed app in a clean, a person's, and a hostile environment.

### Consequences

- Good, because `exec RbConfig.ruby, $0, *ARGV`, `system`, `spawn`, and `Gem.ruby` in their place start the app as it first started, with the same PID and bundle, on macOS and Linux.
- Good, because a restart adds no new difference: hiding the person's settings from the app's boot is the one the first start already makes (ADR 040).
- Bad, because `bin/ruby` is no longer only `main.c`. It reads `fledge.cfg` and the folder beside it when its first argument is a file, a few system calls for every Ruby the app starts with a script, and it carries Fledge's code (`relaunch.c`, `config.c`, `locale.c`), which `runtime/licenses.yml` records.
- Bad, because a restart with an option first, such as `exec RbConfig.ruby, "--yjit", $0`, stays plain Ruby with the person's settings. Finding the script behind Ruby's options means parsing Ruby's command line as `ruby.c` does, and merging those options with the launcher's. Such a program enables options in Ruby instead, or clears the person's settings itself.
- Bad, because on Windows a restart is a new process with a new PID, as under Ruby's own `exec` there, and the runtime builds two more programs against RubyInstaller's DLL.
- Bad, because when `bin/ruby` finds the launcher but `execv` fails, it exits 70, as for a damaged app, rather than run the app as plain Ruby.

### Confirmation

- `test/integration/built_app_test.rb` restarts the parity probe through `RbConfig.ruby`, checks that `bin/ruby` hands only the app's program to its launcher and leaves a program behind an option to Ruby, and checks status 70 when it cannot run the launcher, on Windows too.
- Delivery (`.github/scripts/deliver.sh` and `deliver.ps1`) restarts the probe on fresh macOS, Linux, and Windows runners and in the Debian and Alpine containers, in a clean, a person's, and a hostile environment, from a folder whose name is not ASCII; the probe must report that nothing changed, the PID included, except on Windows.
- `doc/contributors/design/parity.md`, "Restart checks", describes them.

## Pros and Cons of the Options

- **Plain `bin/ruby`:** bad, because the restart boots with the person's settings, without Bundler's setup, and on macOS outside the bundle: the surprise the maintainer's words name.
- **A constant or variable naming the launcher:** bad, because the app would need Fledge-specific code to restart, and its `ENV` would differ from `ruby main.rb`'s (decisions 9 and 10).
- **`bin/ruby` doing the launcher's work:** bad, because on macOS the process would still be `Contents/Resources/bin/ruby`, outside the bundle's program, and the launcher's work would live in two programs.
- **`RbConfig.ruby` naming the launcher:** bad, because `RbConfig.ruby` must run any script and take Ruby's options, and the launcher runs only the app.
- **A shell script:** bad, because it costs a process and a shell for every Ruby the app starts, and keeps the PID through its own `exec` no better than C does.
