# ADR 022: Compile a phone's extensions with mkmf against the phone Ruby, link them in, and register them

## Context and Problem Statement

The maintainer set phones as the work of 0.2.0: "iPadOS, iOS, and Android are our priorities for 0.2.0." (`decisions.md`, 2026-11-02). The first framework expected there, a game engine, is a C++ extension over SDL3.

A phone's Ruby loads no extension from a file. iOS forbids it, so its Ruby is built with `--disable-dln`. Android runs native code only from the libraries its package carries (`lib/ABI/libNAME.so`), not from files an app writes. No gem publishes a build for a phone. How does a gem's C or C++ extension get compiled for each of a phone's targets, into the app, and found by `require`?

## Decision Drivers

- The app's Ruby code is the same as without Fledge: `require "name/name"` finds the extension (decisions 9 and 10).
- "Code is a liability" (`decisions.md`, 2026-10-28): reuse Ruby's own tools and the gem's own build.
- Each target is built on its own system, with that system's tools (`decisions.md`, 2026-10-28).
- One mechanism for both phones where one serves.

## Considered Options

1. Run each gem's own `extconf.rb` with mkmf, under the desktop runtime's Ruby, given the phone runtime's `rbconfig.rb` and this computer's Xcode or NDK compilers; make a static archive with mkmf's `$static`, as Ruby's `ext/extmk.rb` does for its own extensions; link it into the app; and register it with Ruby.
2. rake-compiler and rake-compiler-dock: a gem's own Rake task and a Docker image per target.
3. Gradle's CMake integration, building each gem's sources from a `CMakeLists.txt` Fledge writes.
4. On Android, a shared library per extension in `jniLibs`, loaded with `dlopen` and found with `dlsym("Init_NAME")`.
5. rb-sys, for Rust extensions.

## Decision Outcome

Chosen: option 1, because mkmf is the tool every C extension already has, and Ruby's own build cross-compiles and links extensions statically with it, so Fledge adds no build system. rake-compiler knows no phone, and Docker is not the platform's own tool. Gradle's CMake would skip the `extconf.rb`, losing its configuration checks and `extconf.h`, and iOS has no such path. `dlopen` works on Android but not on iOS, and one mechanism for both is smaller. rb-sys was not tried: Rust extensions are refused, naming the gem.

The registration is a C file Fledge writes, whose constructor calls the embedding API's `fledge_ruby_add_extension` for each extension before Ruby boots. A host that replaces Fledge's keeps it with no call of its own.

Confidence: high for C and C++ extensions from a path gem, which run in CI on both phones. Medium for gems from a server or git, whose marks are tested but which no CI app has yet.

### Consequences

- Good, because `fledge build ios` and `fledge build android` take apps with C and C++ gems, compiled from each gem's own `extconf.rb`.
- Good, because a gem that publishes a precompiled desktop build ships its `ruby` build, compiled from source for the phone.
- Good, because a library an `extconf.rb` links, such as SDL3, needs no `fledge.yml` key: Fledge links static libraries per target and carries shared ones into the Android app (ADR 025).
- Bad, because an Android build with extensions needs the developer's NDK, which Fledge finds but never downloads. Windows is refused for gems with extensions, since its `make` and the NDK's Windows tools were not tried.
- Bad, because `require_relative` of an extension fails: it asks for a path, which is not in Ruby's table of linked extensions.
- Bad, because an extension built by something other than an `extconf.rb` (Rake, CMake, configure, or Cargo in the gemspec), and a Rust one, are refused.
- Bad, because the Mobile apps jobs build one more app on each phone and need this computer's desktop runtime beside the phone's.

### Confirmation

The `mobile-apps-ios` and `mobile-apps-android` jobs build and run `examples/native_phone`, a C and C++ extension, and `examples/cmake_phone` (ADR 027), and each must print its line and exit 0. `test/integration/mobile_extensions_build_test.rb` compiles extensions for every target, and `test/mobile_extensions_test.rb` reads what the links need. `test/mobile_build_test.rb` tests the marks RubyGems and Bundler read.
