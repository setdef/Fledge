# ADR 003: An app's program runs as `ruby PROGRAM` runs it, with nothing of Fledge's between

## Context and Problem Statement

A developer runs a program with `ruby main.rb`, or `bundle exec` (ADR 045), and ships it with Fledge. Between the person who runs the app and the program sits Fledge's launcher (ADR 001). Anything the launcher adds is something the program sees that `ruby` would not give it: an option, a load path entry, a loaded file, a global or constant, a signal or console handler, a code page.

The maintainer set the bar (`decisions.md`, 2026-10-26): "When using fledge, your ruby source code should be able to be identical to how it was without Fledge, so the things you had to `require` before you can still need the app dev to `require`, but the things you didn't have to `require` before the app dev still shouldn't have to require." (decision 9) and "All the ruby globals should be non-surprising to app devs, for the same motivation as #9." (decision 10). Of console code pages and Ctrl-C he said "I don't understand what I'd be deciding here." (decision 21), leaving them to the agents.

How does the launcher start the program so that nothing of Fledge's stands between Ruby and the app?

## Decision Drivers

- The app's source is the same with and without Fledge, and its globals surprise no Ruby developer (decisions 9 and 10; AGENTS.md, Design precedence 2).
- Ctrl-C, a closed terminal, and a closed console end the app as they end `ruby main.rb`.
- Nothing of a Ruby the person happens to have changes how the app starts (Design precedence 1), which ADR 040 settles without adding to what the app sees.
- Every difference from `ruby main.rb` is found by a check, not by a developer.

## Considered Options

1. Run the program in the launcher's own process with the equivalent of `ruby --disable=rubyopt -- PROGRAM ARGS`, adding no option, global, constant, loaded file, or handler.
2. Give Ruby options of Fledge's own: `-I ROOT/app` so `require` finds the app's files, `--yjit`, or a `-r` boot file.
3. Run Ruby as a child of the launcher, which forwards signals and console events and passes on how the child ended, as many launchers do.

## Decision Outcome

Chosen: option 1, because it is the only one that gives the program what `ruby` gives it.

- The launcher runs Ruby with the equivalent of `ruby --disable=rubyopt -- ROOT/app/ENTRY ARGS`, where `fledge.cfg` names ENTRY. There is no `-I`, so an app loads its own files with `require_relative`, as under `ruby`. There is no `--yjit`; an app that wants YJIT enables it, as Rails does, with `RubyVM::YJIT.enable`. `--disable=rubyopt` changes nothing an app sees, since `RUBYOPT` is hidden from Ruby's boot anyway (ADR 040); it guards that boot twice.
- No global, constant, or loaded file of Fledge's appears. The Ruby the launcher evaluates between `ruby_options` and `ruby_run_node` (ADR 040, ADR 045) leaves none behind.
- Ruby runs in the launcher's process: libruby is linked in on macOS and Linux, and Ruby's DLL is loaded on Windows (ADR 038). There is no parent process with anything to forward. The launcher installs no signal handler and no console control handler, and ignores no signal; `ruby_sysinit` and `ruby_init` install Ruby's own.
- On Windows the launcher's manifest sets no `activeCodePage`, so the console's code page decides what it decides for `ruby.exe`.
- Once the program runs, the exit status is the program's own.

The one thing the launcher changes before Ruby's boot is a bare C locale, which ADR 041 decides and documents as a difference.

Confidence: high. The parity check compares a built app with `ruby main.rb` and `bundle exec` on every desktop platform, and Delivery ends a console app with Ctrl-C, a hangup, and a closed console, comparing with Ruby itself.

### Consequences

- Good, because what needed a `require` under `ruby` still does, and nothing else does.
- Good, because Ctrl-C raises `Interrupt` in the main thread, runs `ensure` clauses and `at_exit` hooks, and ends the app by SIGINT (130 to a shell on macOS and Linux, exit code 3 on Windows); a closed terminal raises `SignalException` for SIGHUP (129). A built app started in the background of a shell script ignores Ctrl-C, as `ruby` does there.
- Bad, because closing a console window on Windows ends the app at once, before any `ensure` or `at_exit`, with STATUS_CONTROL_C_EXIT, as it ends `ruby.exe`. An app that wants to clean up then needs a console control handler, which Ruby code cannot install without a native extension.
- Bad, because `$0`, `__FILE__`, and `$PROGRAM_NAME` are the program's absolute path, where `ruby main.rb` gives the path as typed: a person may start the app from any folder. `Parity::JUSTIFIED` lists it.
- Bad, because a new difference from `ruby main.rb`, from a new Ruby or a change to Fledge, fails CI until someone fixes it or writes down why it is right. The parity check, ruby/spec, and the console checks cost CI time on every push.

### Confirmation

- The parity check (`rake parity`, `tasks/parity.rb`), in CI's Test, Test (Windows), and Parity (musl) jobs: every difference from `ruby main.rb`, and from `bundle exec` for a gem-shaped app, must match an entry of `Parity::JUSTIFIED`, or the job fails.
- The ruby/spec comparison (`.github/workflows/ruby-spec.yml`, `tasks/ruby_spec.rb`), with `RubySpec::JUSTIFIED`.
- The console checks, `.github/scripts/deliver-console.sh` and `deliver-console.ps1`, against Ruby itself in the Test jobs and against the built app in Delivery, and `test/built_app_test.rb`.
- `doc/contributors/design/parity.md` describes each check. `doc/differences_from_ruby.md` tells app developers every difference and its reason.

## Pros and Cons of the Options

### Options of Fledge's own

- Bad, because with `-I ROOT/app`, `require "foo"` finds the app's `foo.rb` where `ruby main.rb` does not, so an app that works under Fledge can fail under `ruby`, and `$LOAD_PATH` holds an entry no Ruby developer expects.
- Bad, because `--yjit` makes `RUBY_DESCRIPTION` read `+YJIT` and `RubyVM::YJIT.enabled?` true, unlike under `ruby`.
- Bad, because a `-r` boot file adds itself to `$LOADED_FEATURES`.

### Ruby as a child of the launcher

- Bad, because the launcher would have to forward every signal and console event, and pass on how its child ended, and an app would see a parent process `ruby` does not have.

## More Information

- Ruby installs handlers for SIGINT and SIGHUP (`signal.c`, `install_sighandler`), and re-raises the signal with its default action after cleanup (`eval.c`, `rb_ec_cleanup`, and `signal.c`, `ruby_default_signal`, at Ruby 4.0.9). On Windows, the C runtime UCRT turns CTRL_C_EVENT into SIGINT and maps no other console event to a signal, and neither Ruby nor the launcher installs a console control handler.
- Since Ruby 3.0 (Feature #16604), `Encoding.default_external` on Windows is UTF-8 whatever the code page, while `Encoding.locale_charmap` is the console's input code page.
- How the launcher builds Ruby's arguments: `doc/contributors/design/launcher.md`. How the checks run: `doc/contributors/design/parity.md`. The restart through `RbConfig.ruby`: ADR 026.
